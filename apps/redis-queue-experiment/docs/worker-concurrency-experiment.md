# 워커 동시성 실험

## 실험 목적

CPU 작업을 동시에 처리할 워커 수를 정하고, 작업 실행시간 p99가 5초 이내인지와 작업이 모두 정상 완료되는지를 확인했습니다.

## 조건과 측정 기준

- 실험 서버: EC2 `t3.micro`, vCPU 2개, 보고된 메모리 약 908MiB
- 부하: CPU 작업 100건을 동시에 접수
- 작업 내용: 생성한 2048×2048 JPEG를 512×512 썸네일로 변환하고 JPEG로 1회 인코딩
- Redis 세마포어 용량: 워커 수를 비교할 때 100개
- 측정 구간: 작업이 `PROCESSING`이 된 `startedAt`부터 `completedAt`까지
- p99: 완료된 작업 실행시간을 오름차순 정렬한 99번째 값(Nearest Rank)

측정 p99에는 Redis 대기열에서 기다린 시간이 포함되지 않습니다. 요청 접수부터 완료까지의 지연시간 p99는 별도로 봐야 합니다.

## 결과

| 워커 수 | 워커 실행시간 p99 | 완료 건수 | 결과 |
| ---: | ---: | ---: | --- |
| 1 | 0.25초 | 100/100 | 완료 |
| 2 | 1.15초 | 100/100 | 완료 |
| 3 | 1.16초 | 100/100 | 완료 |
| 4 | 1.49초 | 100/100 | 완료 |
| 5 | 1.55초 | 100/100 | 완료 |
| 6 | 2.32초 | 100/100 | 완료 |
| 7 | 3.18초 | 100/100 | 완료 |
| 8 | 3.39초 | 100/100 | 완료 |
| 10 | 3.73초, 3.89초 | 두 번 모두 100/100 | 두 번 모두 완료 |
| 15 | 한 번은 4.56초 | 한 번은 100/100 | 다른 두 번은 4건·5건이 `PROCESSING`에 남음 |
| 20 | 유효한 p99 측정 불가 | 90/100 | 10건이 `PROCESSING`에 남음 |

15개와 20개 실험에서 완료되지 않은 작업은 원인을 조사한 뒤 실험 데이터에서 `FAILED`로 정리하고 permit을 제거했습니다. 완료가 확인되지 않은 작업은 p99 계산에 포함하지 않았습니다.

## 선정

현재 기준 워커 수는 **10개**입니다. 두 번 반복한 실험 모두 100건이 완료됐고, worker 실행시간 p99도 5초 이내였습니다. 워커 15개는 한 번 기준을 만족했지만 반복 실험에서 미완료 작업이 남았고, 20개도 미완료 작업이 발생했습니다.

현재 EC2 서비스 설정은 `WORKER_COUNT=10`, `SEMAPHORE_CAPACITY=10`입니다. 워커 수와 세마포어 용량은 별도 설정이며, 세마포어 용량은 모든 앱 인스턴스에서 동시에 실행할 작업 수를 제한합니다.

## 세마포어 자료구조와 장애 시 주의점

대기 작업은 Redis LIST에 FIFO 순서로 저장하고, 사용 중 permit은 Redis SET에 UUID 토큰으로 저장합니다. Lua 스크립트가 SET의 원소 수를 확인하고, 자리가 있을 때 대기열에서 작업을 꺼내 토큰을 추가합니다. 작업 완료 시 해당 토큰을 제거합니다.

현재 permit 토큰에는 자동 만료나 작업자 장애 복구가 없습니다. 작업자가 permit을 확보한 뒤 비정상 종료하면 작업 상태가 `PROCESSING`으로 남고 permit도 계속 점유할 수 있습니다. 15개와 20개 실험에서 관찰된 미완료 작업이 이 상태로 남았으며, 실험을 이어가기 위해 수동 정리했습니다. 이 장애 복구 동작은 별도 개선 과제입니다.
