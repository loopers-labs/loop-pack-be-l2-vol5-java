# RPS·세마포어 용량 비교 실험

## 목적

동일한 요청 유입률에서 Redis 세마포어 용량 3개와 10개를 비교합니다. 목표는 작업 실행 동시성에 따른 CPU 사용량과 대기시간 차이를 확인하고, 접수된 작업의 p99 완료시간이 10초 이내인지 검증하는 것입니다.

## 2 RPS 기준선 실험 계획

| 항목 | 설정 |
| --- | --- |
| 요청 유입 방식 | 일정한 간격으로 보내는 open-loop 부하 |
| 요청 속도 | 초당 2건(2 RPS) |
| 요청 지속 시간 | 1분 |
| 총 작업 수 | 120건 |
| 작업 종류 | CPU 썸네일 변환 |
| 작업 내용 | 작업당 2048×2048 JPEG 생성 후 512×512로 변환·JPEG 인코딩 1회 |
| 워커 수 | 10개로 고정 |
| 비교할 세마포어 용량 | 3개, 10개 |
| 대기열 초기 상태 | 각 실행 전 대기 작업 0건, 활성 permit 0개 확인 |

### 측정 항목

- 접수부터 완료까지의 시간: `submittedAt` → `completedAt` (큐 대기 포함, SLO 판정 기준)
- 큐 대기시간: `submittedAt` → `startedAt`
- 실제 worker 실행시간: `startedAt` → `completedAt`
- CPU 사용률: 실험 중 1초 간격 표본의 평균
- 대기열 최대 관측치, 접수·완료·실패 건수, 전체 작업이 끝날 때까지 걸린 시간

p99는 각 실행의 완료 작업 지연시간을 오름차순으로 정렬한 99번째 값(Nearest Rank)으로 계산합니다. SLO 목표는 **접수된 작업의 p99 완료시간 10초 이내**입니다. 모든 작업이 완료되고 실패가 없어야 해당 실행을 안정 완료로 봅니다.

### 진행 순서

1. 워커 10개, 세마포어 용량 3개로 대기열이 빈 상태를 확인합니다.
2. 2 RPS를 1분간 유지해 CPU 작업 120건을 보냅니다.
3. 유입을 멈춘 뒤 대기열과 실행 작업이 모두 0이 될 때까지 기다려 결과를 기록합니다.
4. 대기열이 빈 상태를 확인한 뒤 세마포어 용량만 10개로 바꾸고 같은 부하를 반복합니다.
5. 두 결과의 p99, 큐 대기시간, CPU 평균, 완료 건수를 비교합니다.

## 결과

### 2 RPS 기준선

두 실행 모두 2 RPS를 실제로 유지해 120건을 접수했고, 120건 모두 실패 없이 완료했습니다. 전체 처리는 요청 유입 시작 후 약 61초 만에 끝났습니다.

| 세마포어 용량 | 유입 RPS | 접수 건수 | 완료/실패 | 완료시간 p99 | 큐 대기 p99 | worker 실행 p99 | CPU 평균 | 대기열 최대 관측치 | 결과 |
| ---: | ---: | ---: | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 3 | 2.0 | 120 | 120/0 | 0.325초 | 0.079초 | 0.312초 | 24.1% | 1건 | SLO 통과 |
| 10 | 2.0 | 120 | 120/0 | 1.066초 | 0.078초 | 1.026초 | 23.0% | 0건 | SLO 통과 |

### 결론

2 RPS 유입에서는 세마포어 용량 3개만으로도 처리량을 따라가 대기열이 거의 쌓이지 않았습니다. 두 용량 모두 완료시간 p99 10초 목표를 넉넉히 만족했습니다. 용량을 10개로 늘려도 CPU 평균은 비슷했고 완료시간 p99와 worker 실행시간 p99는 오히려 길어졌습니다. 이 조건에서는 permit 3개가 충분하며, 동시 실행을 늘려도 처리량 이득이 관찰되지 않았습니다.

이번 비교 후 실험 서버는 앞서 정한 설정을 유지해 `WORKER_COUNT=10`, `SEMAPHORE_CAPACITY=10`으로 두었습니다. 실제 운영 용량은 더 높은 RPS 부하와 반복 측정 결과를 보고 조정해야 합니다.

## 100 RPS 미니 서비스 비교 실험 계획

미니 서비스에서 세마포어가 동시 처리와 대기시간에 미치는 영향을 높은 유입률에서 비교합니다. 각 조건에서 CPU 작업을 초당 100건씩 10초간 접수해 1,000건을 보냅니다. 워커는 10개로 고정합니다. 앱은 `54.180.231.58`에서 실행하고, 로컬 부하 생성기는 SSH 터널을 통해 요청했습니다. Redis는 같은 VPC의 사설 IP를 사용하고 Redis DB 15로 기존 데이터와 분리했습니다.

- 세마포어 제한: 용량 3개
- 세마포어 제한이 걸리지 않는 기준: 용량 100개. 워커가 10개이므로 permit 용량은 실제 동시 실행을 제한하지 않습니다. Lua와 Redis permit 처리 경로는 계속 사용됩니다.
- 작업: CPU 썸네일 변환 1회
- 측정: 접수부터 완료까지 p99, 큐 대기 p99, worker 실행 p99, 1초 표본 CPU 평균, 최대 관측 대기열, 완료·실패 수, 큐가 빌 때까지의 시간
- 실행 전 대기열과 활성 permit은 0건이어야 합니다. 요청 유입을 멈춘 뒤 모든 작업이 끝날 때까지 측정합니다.

CPU 평균은 `/experiment/metrics`의 `systemCpuPercent`를 1초 간격으로 읽은 시스템 전체 CPU 사용률입니다. Java 프로세스만의 CPU 사용률(`processCpuPercent`)과는 다른 지표입니다.

## 100 RPS에서 대기열 상한 탐색

permit 4·worker 10을 유지하고 100 RPS로 10초간 1,000건을 보내며 `MAX_QUEUE_SIZE`를 조정했습니다. 각 실행 전 앱을 종료하고 페이지 캐시를 정리한 뒤 새 JVM·전용 Redis DB에서 시작했습니다. P99는 접수된 작업의 요청 시점부터 완료까지 계산했고, 429는 별도로 집계했습니다. 이 실험은 단일 EC2에 직접 요청했으며 로드밸런서는 포함하지 않았습니다.

| 대기열 상한 | 실제 유입 RPS | 접수/완료 | HTTP 429 | 완료 P99 | 전체 배출 시간 | OOM |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 20 | 100.08 | 56/56 | 944 | 7.457초 | 14.13초 | 없음 |
| 30 | 100.06 | 66/66 | 934 | 9.819초 | 16.17초 | 없음 |
| 30 (기본값 빌드 검증) | 100.07 | 66/66 | 934 | 9.972초 | 16.15초 | 없음 |
| 32 (1차) | 100.06 | 68/68 | 932 | 9.910초 | 17.13초 | 없음 |
| 32 (재측정) | 100.07 | 63/63 | 937 | 11.217초 | 17.15초 | 없음 |
| 33 | 100.08 | 67/67 | 933 | 10.950초 | 16.13초 | 없음 |
| 35 | 100.05 | 71/71 | 929 | 10.530초 | 17.13초 | 없음 |
| 40 | 100.04 | 73/73 | 927* | 12.060초 | 18.26초 | 없음 |

`*` queue40 실행은 비-202 응답 수만 저장했고 HTTP 상태별 집계는 남기지 못했습니다. 나머지 상한 실행에서는 거절 응답이 모두 429였습니다.

queue30은 두 번 모두 P99 10초 이내였고, 기본값을 30으로 바꾼 빌드에서도 같은 결과를 확인했습니다. queue32는 1차 통과 후 재측정에서 목표를 넘겼고, queue33·35·40도 목표를 넘겼습니다. 따라서 현재 실험 설정은 `SEMAPHORE_CAPACITY=4`, `WORKER_COUNT=10`, `MAX_QUEUE_SIZE=30`으로 둡니다. queue30에서도 1,000건 중 934건(93.4%)이 429로 거절됐으므로, 이 결과는 100 RPS 전체 수용을 뜻하지 않습니다. P99는 접수·완료된 66건만 기준으로 했고 10초 목표 여유가 작아 반복 검증이 더 필요합니다.

페이지 캐시 정리 후 부하 직전 `MemAvailable`은 queue30 두 실행에서 326.1 MiB와 320.7 MiB였습니다. 다른 상한 실행은 300.4–342.2 MiB 범위였습니다. 캐시 정리는 실행 전 메모리 상태를 비슷하게 맞췄지만 완전히 동일하게 만들지는 못했습니다. 1초 표본은 [queue cap 100 RPS CSV](data/queue-cap-100rps-samples.csv)에 저장했습니다.

별도로 permit 6·queue 상한 10,000의 무제한 대기열 실행에서는 1,000건을 모두 접수한 뒤 `Java heap space` OOM으로 종료됐습니다. 종료 전 820건 완료, Redis 대기 174건·활성 permit 6개였으며, 이 실행에도 유효한 P99가 없습니다.
