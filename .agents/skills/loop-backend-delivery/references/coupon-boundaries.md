# 쿠폰 구현에서 보존할 경계

이 내용은 작업에서 추출한 경계다. 현재 저장소의 사용자 결정/설계를 다시 읽고 변경됐으면 최신 결정을 따른다.

| 개수/상태 | 원본과 역할 |
|---|---|
| 준비 슬롯 수 | DB coupon_slots의 전체 행 수. 발급된 슬롯도 포함하며 준비 확인용 |
| 실제 발급/총량 | DB 쿠폰·슬롯·issuedCount를 같은 발급 TX로 보호 |
| 서버 처리 여력 | 인스턴스별 Java Semaphore. 발급 재고/전역 한도와 다름 |
| Redis 누적 집계 | CouponIssueCounter 추상화 뒤의 조회 집계. DB 원본과 별도로 누락/중복/복구를 다룸 |

- 완료 쿠폰 재요청은 기존 couponId를 반환한다. 동시에 실행된 요청 두 개가 쿠폰 두 장을 뜻하지 않는다.
- 미발급 슬롯을 SKIP LOCKED로 못 골랐다고 바로 품절로 판단하지 않는다. 실제 잠금과 최신 업무 상태를 구분한다.
- 슬롯 변경/쿠폰 INSERT/마지막 발급 수 갱신은 한 TX다. 실패하면 모두 rollback하며 처리 permit 반환으로 DB 발급 수를 감소시키지 않는다.
- 마지막 캠페인 잠금 뒤 DB 시각으로 기간·활성·한도를 검사한다. 마감 전 검증 통과 뒤 늦게 commit하는 계약과 commit 시각 제한을 혼동하지 않는다.
- 쿠폰/슬롯 유일 제약·관계 FK의 실제 동작은 DB에서 검증한다. 도메인 단위 검사나 JPA validate만으로 동시성/모든 제약이 검증됐다고 하지 않는다.
- HTTP 연결 종료/timeout은 DB 작업 종료의 증거가 아니다. 종료 불명이면 permit을 보류하고 해당 인스턴스를 닫는다.
- 복구는 확인된 자기 실행 ID만 대상으로 하며 open과 분리한다. 이전 boot의 permit을 새 Semaphore에 release하지 않는다.
- Redis 집계 성공을 발급 성공으로 바꾸거나, 집계 장애를 이미 commit된 쿠폰의 취소로 바꾸지 않는다.
- C01 준비 TX의 REQUIRES_NEW 선택을 다른 모든 업무 TX에 자동 복제하지 않는다. 각 단계의 실제 조율 계약을 먼저 확인한다.
- C01 명시 DDL 검증과 C02 실제 발급/잠금 검증, C04 수용 검증은 서로 다른 완료 근거다.
