# Red 검증

테스트 작성이 끝나면 아래 순서로 검증한다. 하나라도 만족하지 않으면 Green 구현을 시작하지 않는다.

## 1. 규칙 근거

- 각 `@Nested`의 `@DisplayName`에 적은 `INV-<개념>-<번호>`가 `docs/week2/domain-rules.yaml`에 실제로 존재하는지 확인한다.
- 규칙 문장을 `domain-rules.yaml`에서 **글자 그대로** 옮겼는지 대조한다.
- 테스트의 입력, 경계값, 성공 결과, 오류 코드, 불변 상태가 그 규칙이나 규칙이 연결한 확정 계약에 있는지 대조한다.
- 근거가 `domain-rules.yaml`, 확정된 API 계약, ADR 어디에도 없으면 테스트하지 않고 사용자에게 정책을 질문한다.
- 구현 편의를 위한 동작, 일반적인 관례, 예상 가능한 추가 예외를 임의로 테스트하지 않는다.
- 조회 계약·접근 경계·응답 계약을 검증하는 통합·HTTP 테스트는 `docs/week2/requirements.md`의 요구사항 ID를 쓴다. 이때는 요구사항이 실재하는지 대조한다.

## 2. 기법을 끝까지 적용했는가

라벨이 붙었는지가 아니라 **라벨한 기법이 요구하는 값을 다 썼는지**를 본다. 절반만 적용한 테스트가 라벨만 달고 통과하는 것을 막는 단계다.

- 규칙 하나는 `@Nested` 하나로 표현한다.
- 각 시나리오의 `@DisplayName`이 실제 사용한 기법을 표시하는지 확인한다.
- 그 기법의 자리를 표로 세어 본다. **빈 자리가 있으면 통과가 아니다.**

| 라벨 | 다 썼다고 말하려면 |
| --- | --- |
| 경계값 분석 | 최소 바로 아래·최소값·최대값·최대 바로 위 **네 자리**가 각각 시나리오를 갖는다 |
| 동등 클래스 분할 | 무효 클래스가 몇 개인지 먼저 세고, 유효 클래스와 무효 클래스 **전부**에 대표값이 하나씩 있다 |
| 의사결정표 | 조건이 둘 이상이고 조합이 모두 있다. **조건이 하나면 동등 클래스 분할로 고쳐 단다** |
| 상태 전이 | 허용되는 전이와 막히는 전이가 모두 있다 |
| 오류 추측 | 자리 수가 정해지지 않는다. 대신 무엇을 추측했는지 `@DisplayName`에 드러난다 |

- 규칙 문장이 `"~ 이하다"`, `"~ 이상이다"`처럼 한쪽 끝만 말하면, **반대쪽 끝은 문장이 아니라 파라미터 타입이 정한다.** 그 자리도 세어야 한다.
- 같은 기대를 다른 ID에 중복해 붙이지 않는다. 여러 ID가 같은 동작을 요구하면 각 ID가 추가로 보장하는 관찰값을 구분한다.

## 3. 범위 밖 기대값과 비워 둔 자리

작성한 테스트마다 다음 질문에 모두 답한다.

1. 이 입력값을 고른 근거가 규칙에 있는가?
2. 이 반환값 또는 상태 변경을 규칙이 약속하는가?
3. 이 오류 코드를 확정 계약이 약속하는가?
4. 거절 뒤 그대로라고 확인하는 상태가 이 동작의 책임 범위인가?

하나라도 아니면 테스트를 삭제하거나 기대값을 약하게 바꾸지 않는다. 근거가 있는 올바른 테스트 위치로 옮기거나, 미정 정책으로 사용자에게 확인한다.

그리고 **쓰지 않은 테스트**에 대해 하나를 더 답한다.

5. 2절이 요구한 자리 중 비어 있는 곳이 있는가? 있다면 왜 비었는가?

근거가 없어서 비었다면 **그것이 바로 질문할 정책이다.** 조용히 비워 두고 Red 검증을 끝내지 않는다. 비운 자리와 질문을 최종 보고에 남긴다.

```
INV-POINT-20 결제액은 현재 잔액 이하다.
  최대       잔액과 같은 금액      ✅
  최대+1     잔액보다 1 큰 금액    ✅
  최소       가장 작은 유효 결제액  ❌ 규칙이 말하지 않는다 → 질문
  최소-1     그 바로 아래          ❌ 규칙이 말하지 않는다 → 질문
```

## 4. Red 상태

- production 코드는 메서드 시그니처, 타입, 패키지처럼 테스트 컴파일에 필요한 최소 골격만 허용한다.
- 도메인 규칙, 상태 변경, 오류 정책을 구현해 새 테스트를 통과시키지 않는다.
- 관련 테스트가 컴파일되는지 확인한다.
- 기존에 구현된 동작의 테스트는 통과할 수 있다. 아직 구현되지 않은 시나리오는 적어도 하나 이상 실패해야 한다.
- 실패 원인이 규칙 미구현 또는 기대값 불일치인지 확인한다. 잘못된 fixture, `null` 골격의 우발적 NPE, 잘못된 mock, 환경 오류는 Red로 인정하지 않는다.
- 실패 보고에는 테스트 수, 통과 수, 실패 수와 대표 실패 원인을 남긴다.

## 5. Green 에이전트로 넘기기

Red 검증을 모두 통과한 뒤에만 Green으로 넘긴다.

Red 에이전트는 다음 정보만 파일과 최종 보고에 남기고 종료한다.

1. 작성하거나 변경한 테스트 파일
2. 각 테스트 파일에 배치한 규칙 ID
3. 관련 테스트 실행 명령
4. 테스트 수, 통과 수, 실패 수
5. 각 실패가 미구현 동작 때문에 발생했다는 확인 결과
6. **2절에서 비워 둔 경계 자리와 그에 대한 질문**

구현 아이디어, 예상 클래스 내부 구조, Green 코드 제안은 인계하지 않는다. Green은 이전 대화 문맥을 공유하지 않는 별도 에이전트가 저장소의 규칙·테스트·현재 코드만 읽고 수행한다.
