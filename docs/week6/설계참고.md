# 6주차 설계 참고 · 현재 코드 구조 조사

6주차 과제(`docs/week6/6주차-Kafka-과제.md`) 설계를 시작하기 전에 현재 코드 구조를 읽기 전용으로 조사한 결과다. 코드는 수정하지 않았다.

표의 **확인**은 코드에서 직접 본 사실, **추측**은 코드 사실에서 유추한 판단이다. 경로는 저장소 루트 기준이며 `api/`는 `apps/commerce-api/src/main/java/com/loopers/`의 줄임이다.

## 조사 결과

**1. 주문 확정**

| 질문 | 답 | 근거 | 구분 |
|---|---|---|---|
| 상태 값 목록 | `DRAFT, PAYMENT_PENDING, CONFIRMED, PAYMENT_FAILED` 4개. 과제가 말하는 UNKNOWN은 주문이 아니라 결제 시도(PaymentAttempt)의 상태 | `api/domain/order/Order.java:28-30`, `api/domain/payment/PaymentAttempt.java:33-39` | 확인 |
| 전이 코드 위치 | 엔티티 메서드는 `startPayment()` 하나뿐 (DRAFT→PAYMENT_PENDING). CONFIRMED·PAYMENT_FAILED 전이는 엔티티가 아니라 QueryDSL 조건부 UPDATE `finishIfPaymentPending`이 담당하며 `WHERE status = PAYMENT_PENDING` 가드 | `Order.java:91-97`, `api/infrastructure/order/OrderRepositoryImpl.java:64-72` | 확인 |
| confirmedAt 필드 | 없음. Order 필드는 userId·status·paymentMethod·items·paidAmount, 시간 필드는 BaseEntity의 createdAt·updatedAt·deletedAt뿐 | `Order.java:40-56`, `modules/jpa/src/main/java/com/loopers/domain/BaseEntity.java:25-32` | 확인 |
| updatedAt으로 대신하는가 | 사실상 그렇다. 확정 UPDATE가 `updatedAt = ZonedDateTime.now()`를 직접 세팅하므로 지금 "확정 시각"에 가장 가까운 값은 updatedAt. Clock 빈을 쓰지 않아 테스트에서 고정 불가 | `OrderRepositoryImpl.java:69` | 확인 |
| 최초 CONFIRMED 구분 가능? | 반쯤 가능. 결제 시도 단위로는 `settleIfOpen`이 0행이면 false 반환으로 "이미 처리됨"을 안다. 그러나 주문 단위 UPDATE의 반환 행수는 받지 않고 버린다. 그래서 "이 호출이 주문을 처음 CONFIRMED로 만들었다"는 신호는 현재 코드에 없다 | `api/domain/payment/PaymentResultService.java:42-46`(시도 문지기), `:49`(반환값 폐기) | 확인 |
| DDL 파일 | flyway·sql 스키마 없음. jpa.yml의 local/test 프로파일이 `ddl-auto: create` | `modules/jpa/src/main/resources/jpa.yml` | 확인(에이전트) |

초보자용 설명: 이 코드는 "엔티티 객체를 바꾸고 저장"하는 방식이 아니라 "조건이 맞는 행만 UPDATE하고 바뀐 행 수를 본다"는 방식으로 중복을 막는다. 행 수가 1이면 내가 처음 바꾼 것이고 0이면 누군가 이미 바꾼 것이다. 주문 쪽만 이 행 수를 안 보고 있다.

## 과제 요구사항과 비교해 바꾸거나 새로 만들어야 할 것

아래는 조사 결과와 과제 문서를 대조한 목록이다. 설계 결정이 아니라 "현재 없거나 어긋나는 것"의 목록이다.

**commerce-api (발행 쪽)**

1. **kafka 모듈 의존 추가.** `:modules:kafka` 의존과 `kafka.yml` import가 모두 없어 지금은 발행 자체가 불가능하다.
2. **confirmedAt 저장.** Order에 컬럼이 없다. `finishIfPaymentPending`의 `WHERE PAYMENT_PENDING` 가드 덕분에 같은 UPDATE 안에서 세팅하면 중복 callback이 덮어쓰지 못하는 구조는 이미 갖춰져 있다. 시각 소스(Clock 빈 vs `now()`)는 결정 필요.
3. **"주문이 처음 CONFIRMED가 됐다"는 신호.** `PaymentResultService.java:49`에서 버리는 반환 행수를 받아 1일 때만 발행 조건으로 삼아야 한다. 현재 `applyFinal`의 boolean은 시도 기준이라 주문 기준과 다를 수 있다.
4. **after-commit 발행 메커니즘.** Spring 이벤트 사용 선례가 0건이다. 기존 선례인 `TransactionSynchronization` 직접 등록 방식과 `@TransactionalEventListener` 중 택일해야 한다. 어느 쪽이든 payload(orderId, confirmedAt, items)는 TX B 안에서 미리 만들어야 한다. items 재료는 OrderItem의 productId·quantity로 충분하다.
5. **producer 계약.** 현재 KafkaTemplate이 `<Object,Object>` + JsonSerializer다. key를 orderId 문자열로 고정하고 send 결과(topic·partition·offset)를 관찰하는 코드가 새로 필요하다. 전용 template을 둘지는 설계 사항.
6. **ArchUnit 영향.** 발행기를 `infrastructure`에 두고 포트 인터페이스를 `domain`이나 `application`에 두면 기존 3규칙과 충돌하지 않는다. `domain`의 `PaymentResultService`가 Kafka 클래스를 직접 참조하면 ArchUnit은 막지 않지만 기존 계층 의도와 어긋난다.

**modules/kafka (설정)**

7. `kafka.yml:21` `value-serializer` → `value-deserializer` 수정. 과제가 명시한 항목이다.
8. `kafka.yml:23` `enable-auto-commit` → `enable.auto.commit` 표기 수정. 과제가 "ConsumerConfig 실제 값 확인"을 요구한다.
9. `acks` 명시. 현재 없음.
10. **record listener factory 신설.** 과제 예시의 `orderActivityKafkaListenerContainerFactory`에 해당. batch=false, MANUAL_IMMEDIATE, concurrency 1, `CommonContainerStoppingErrorHandler`, `<String, byte[]>`. 기존 `BATCH_LISTENER_DEFAULT`는 그대로 둔다.
11. **테스트용 fetch 설정.** fetch.min.bytes·fetch.max.wait.ms가 Java 상수라 프로파일로 못 바꾼다. 새 factory에서 작은 값을 쓰고 이유를 남겨야 한다.
12. admin의 `kafka:9092` 주소는 호스트 실행 시 해석 불가다. 토픽을 코드로 만들면 문제가 된다.

**commerce-streamer (소비 쪽)**

13. **레이어 신설.** domain·application·infrastructure 패키지가 없다. 리포지터리는 JpaConfig 스캔 범위 때문에 `com.loopers.infrastructure` 아래여야 한다.
14. **엔티티 2개와 유일 제약.** 소비 완료 기록(eventId·orderId 유일)과 상품 구매 활동(orderId·productId 유일). 과제는 DB 제약으로 동시 소비를 막으라고 요구한다.
15. **트랜잭션 handler 별도 빈.** streamer에 `@Transactional`이 0건이다. 완료 기록과 모든 품목을 한 TX로 묶고, consumer가 commit 후 ack해야 한다.
16. **실제 consumer.** `order-events` 토픽, 별도 groupId, 새 factory 지정. demo listener는 기능이 아니므로 대체·유지 여부 결정.
17. `application.yml:17` name을 `commerce-streamer`로 수정. 지금은 client-id가 `commerce-api`로 나간다.
18. **`src/test` 신설.** 테스트가 0건이며 과제는 `:apps:commerce-streamer:check`를 요구한다.

**테스트 인프라**

19. **Kafka Testcontainers fixture 신설.** 클래스가 없다. MySQL fixture 패턴(static 블록 + `System.setProperty("spring.kafka.bootstrap-servers", ...)`)을 따르는 것이 기존 컨벤션에 맞다.
20. **의존성 전이 수정.** `testcontainers:kafka`를 `testFixturesApi`로 바꾸거나 각 앱에 `testImplementation`으로 추가해야 fixture를 쓸 수 있다. commerce-api에도 `testFixtures(":modules:kafka")`가 필요하다.
21. 과제의 partition·consumer group 실험, offset 미커밋 재전달 실험, listener 실패 경로 실험은 모두 새로 작성해야 한다. 기존에 재사용할 Kafka 테스트가 없다.

## 설계 전에 결정이 필요한 것

- eventId를 컬럼으로 저장할지, `order-confirmed:v1:{orderId}`로 유도할지.
- confirmedAt을 Clock 빈으로 찍을지. 현재 벌크 UPDATE는 `now()`를 직접 써서 테스트에서 시각을 고정할 수 없다.
- after-commit 발행을 기존 `TransactionSynchronization` 방식으로 갈지, `ApplicationEventPublisher` + `@TransactionalEventListener`를 새로 도입할지.
- 새 listener factory를 `modules/kafka`에 둘지 streamer 안에 둘지.
- 이전 POINT 확정 주문은 confirmedAt이 null로 남는다. 과제는 소급 발행을 금지하므로 null 허용 컬럼이어야 한다.
