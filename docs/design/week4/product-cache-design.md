# 상품 목록 캐시 설계 (W4)

> **튜닝이 끝난 상품 목록 한 경로에 Redis cache-aside를 붙인다. 낡음은 표시 필드에만, 시간 상한(TTL)까지만 허용한다.**

고객 `GET /api/v1/products`의 `latest`·`price_asc` 목록이 대상이다. 키·무효화 표·실패 시나리오 상세는 [AI용 상세](product-cache-design.ai.md), 측정 원자료는 [baseline](product-list-baseline.md)에 있다.

## 핵심 결정

| 결정 | 이유 |
|---|---|
| 캐시 대상은 `latest`·`price_asc` 목록이다. `likes_desc`와 상세는 제외한다 | 좋아요순은 좋아요마다 순서가 바뀌고 이미 튜닝으로 약 1.9ms다 |
| `likeCount`는 캐시에 넣지 않고, hit마다 카운터 테이블에서 읽는다 | 좋아요는 가장 잦은 쓰기라 넣으면 hit율이 무너진다 |
| 그 카운터 조회가 삭제된 상품을 걸러 내는 확인을 겸한다 | 무효화가 실패해도 삭제된 상품이 응답에 나가지 않는다. 빠진 id가 있으면 캐시를 버리고 DB로 읽는다 |
| 무효화는 관리자 쓰기 commit 뒤에 목록 영역 전체를 지운다 | 조합(브랜드·정렬·페이지·크기)이 많아 일부만 지우면 빠뜨리기 쉽고, 쓰기는 드물다 |
| 무효화 실패는 삼키고 TTL(기본 60초)이 방어한다 | DB는 이미 commit되어 관리자 응답을 실패로 바꾸지 않는다 |
| Redis 오류는 miss로 취급하고 DB로 우회한다. 연결 200ms, 명령 300ms 안에서 끊는다 | Redis 장애가 DB 장애나 오류 응답으로 번지지 않게 하려고 |
| 캐시 포트는 쓰는 쪽(application)이 소유하고 infrastructure가 구현한다 | 도메인 서비스는 캐시를 모른다 |

## 흐름

```
조회(latest|price_asc)
 ├ 캐시 조회 (Redis 오류 → miss로 취급)
 │   ├ hit : 카운터 테이블에서 좋아요 수 조회(SQL 1개)
 │   │        ├ 모든 id에 행 있음 → 캐시 값 + 좋아요 수를 조합해 반환
 │   │        └ 빠진 id 있음(삭제됨) → 캐시를 버리고 miss 경로로
 │   └ miss: DB 조회(SQL 4개) → 반환 직전 캐시 저장(실패는 무시)
 └ likes_desc → 캐시 없이 DB
```

## 허용하는 낡음

| 장면 | 허용 |
|---|---|
| 무효화 실패, 이전 조회의 늦은 채움, Redis 장애 중 변경 | 이름·가격·브랜드명·총 개수·순서가 TTL까지 낡을 수 있다 |
| 삭제 비노출, 좋아요 수, 주문 금액·재고·결제 판단 | 허용하지 않는다 |

## 결과

| 항목 | 값 |
|---|---|
| 요청당 SQL | miss 4개 → hit 1개 |
| 브랜드 7 `price_asc` p50 | DB-only 2.0~4.3ms, hit 0.65~1.1ms |
| 영역 비우기 | 키 1,000개 1.6ms, 10,000개 11ms |
| Redis 중단 중 | 약 620ms (조회·저장 timeout 각 300ms + DB) |

## 알려진 한계

- 지연만 보면 DB 튜닝으로 충분했다. 캐시의 이득은 DB 부하(SQL 4 → 1)이고, 대가는 무효화·장애 처리·표시 낡음이다.
- Redis 명령 timeout은 호출자의 대기만 끊는다. 중단 중 보낸 저장은 복구 직후 실행될 수 있다(값은 저장 시점의 DB 결과이고 TTL이 있다).
- timeout 설정은 공용 `modules/redis`라 다른 앱에도 적용된다(현재 다른 앱은 Redis를 쓰지 않는다).
- 동시 요청 제한, stampede 완화, 깊은 페이지 키 상한은 하지 않았다.
