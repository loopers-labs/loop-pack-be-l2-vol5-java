# 상품 조회 SQL·인덱스 개선 설계 (W4)

> **조회 계약을 바꾸지 않고 상품 목록의 병목을 줄인다. 방법은 측정으로 고른다.**

브랜드 필터 + 가격순 목록(A)과 브랜드 없는 좋아요순 목록(B)이 대상이다. 캐시는 범위 밖이다(별도 문서). 후보 비교표와 구현 세부는 [AI용 상세](product-query-design.ai.md), 측정 원자료는 [baseline](product-list-baseline.md)에 있다.

## 핵심 결정

| 결정 | 이유 |
|---|---|
| 정렬·필터·응답 계약과 OFFSET 페이지는 그대로 둔다 | 개선이 응답을 바꾸지 않았음을 체크섬 8개로 확인하기 위해서 |
| A는 `(brand_id, deleted_at, price, id DESC)` 인덱스로 교체한다 | 정렬(`filesort`)이 사라지고 count는 인덱스만으로 끝난다. 상품이 몰린 브랜드에서 3.6ms에서 1.5ms |
| 전역 가격순 인덱스는 채택하지 않는다 | 브랜드 없는 목록은 빨라지지만 count 계획이 바뀌어 오히려 느려진다 |
| B는 좋아요 카운터 테이블(`product_like_counts`)에서 id를 먼저 고른 뒤 상품을 조회한다 | 14.6~16.3ms에서 1.8~1.9ms. `products.like_count` 컬럼은 좋아요가 상품 행을 잠가 주문·삭제와 경쟁한다 |
| 카운터 테이블을 `likeCount`의 단일 출처로 쓴다 | 정렬 키와 표시 값이 같고, 좋아요 수 조회가 집계에서 PK 조회로 바뀐다 |
| 옵티마이저 힌트(`STRAIGHT_JOIN`)는 쓰지 않는다 | 분포가 바뀌면 오히려 해롭고 유지가 어렵다 |

## 결과

| 요청 | 합계 p50 (전 → 후) |
|---|---|
| A 브랜드 7 `price_asc` | 1.2 → 1.2ms (균등 seed는 편차 안) |
| A, 브랜드에 5,000개 쏠림 | 3.6 → 1.5ms |
| **B 브랜드 없는 `likes_desc`** | **15 → 1.9ms** |

## 좋아요 카운터의 동작

- 좋아요 등록·취소가 카운터 행만 원자적으로 ±1 한다(상품 행은 건드리지 않는다).
- 행은 노출 중인 상품만 가진다. 상품을 만들 때 0으로 만들고, 삭제할 때 지운다.
- 삭제된 상품에 좋아요가 남아도 읽기에서 무시한다.

## 알려진 한계

- 브랜드를 지정한 `likes_desc`는 브랜드 크기에 비례한다(5,000개 쏠림에서 약 4.5ms).
- 저장소를 거치지 않고 상품을 직접 INSERT하면 카운터 행이 없어 `likes_desc`에서 빠진다. 새 Facade가 `createCount`를 빠뜨리는 것은 테스트로만 잡는다.
- 쓰기 비용, 깊은 페이지, 수백만 건 규모, HTTP 전체 지연은 측정하지 않았다.
- 인덱스 교체로 브랜드 삭제 시 갭 잠금이 닿는 이웃이 직전 브랜드에서 다음 브랜드로 바뀐다(영향 크기는 같다).
