# 주문 쿠폰 할인 설계 (W1)

> **구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않는다.**

모호한 쿠폰 요구를 테스트와 코드로 옮길 수 있는 약속으로 바꾼 기록이다. 제품 코드는 바꾸지 않았다. 불변식 표와 오류 계약 상세는 [AI용 상세](order-discount-contract.ai.md)에 있다.

## 핵심 결정

| 결정 | 이유 |
|---|---|
| 오류는 HTTP 의미(형식 400, 대상 없음 404, 상태 충돌 409)까지만 구분하고, 원인은 메시지로 전한다 | 원인마다 전용 코드를 만들면 코드가 끝없이 늘고 REST 의미와 어긋난다 |
| 남의 주문·쿠폰은 403이 아니라 404로 응답한다 | 리소스가 존재한다는 사실을 숨긴다 |
| 확정 시 할인 금액과 쿠폰 id를 주문에 스냅샷으로 저장한다 | 재계산하면 쿠폰 정책이 바뀔 때 확정 금액이 바뀐다 |
| `POST /orders/{id}/discount` 한 번으로 검증·계산·저장을 서버가 한 트랜잭션에서 처리한다 | 호출 순서와 부분 실패의 복잡도를 서버가 흡수하고, 멱등도 한 경계에서 보장한다 |

## 약속과 가정

- **확인된 약속:** 확정 전에 본인 쿠폰을 적용할 수 있다. 확정된 금액은 바뀌지 않는다.
- **임시 가정:** 쿠폰은 주문당 한 장, `finalAmount = originalAmount - discountAmount`, 같은 요청은 같은 결과(멱등), 만료는 요청 시작 시각 기준.
- 금액 계산 방식이나 가정이 틀리면 영향받는 지점은 AI용 상세의 임시 판단 표에 적어 두었다.

## 제품 담당자에게 남은 질문

| 질문 | 답에 따라 달라지는 것 |
|---|---|
| 적용 후 확정 전에 쿠폰이 만료되면 확정을 막는가 | 확정 단계의 오류 응답 |
| 주문이 취소·실패하면 쿠폰을 되돌려 주는가 | 쿠폰 사용 상태 저장 방식 |
| 운영자가 구매자 대신 적용할 수 있는가 | 호출 권한 |
| 할인이 원금보다 크면 0원으로 막는가, 적용을 거부하는가 | 0원 성공 vs 오류 |
| 적용한 쿠폰을 확정 전에 교체·해제할 수 있는가 | 주문의 쿠폰 슬롯 변경 가능 여부 |

## API

| 요청 | 결과 |
|---|---|
| `POST /api/v1/orders/{orderId}/discount` `{couponId}` | 200 `{orderId, originalAmount, discountAmount, finalAmount}` |
| 형식 오류·필드 누락 | 400 |
| 없는 주문·쿠폰, 타인의 주문·쿠폰 | 404 |
| 이미 확정된 주문 | 409 |

## 알려진 한계

- "가장 큰 할인 쿠폰 자동 선택" 제안은 근거가 없어 거절했고, 요청이 `couponId`를 명시하는 것으로 한정했다.
- 만료, 단일 쿠폰, 0원 처리의 외부 오류 표현은 질문이 답을 얻은 뒤 정한다.
