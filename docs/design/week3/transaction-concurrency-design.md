## 1. 전제와 현재 코드의 갱신 유실 지점

### 1-1. 실행 환경

| 항목 | 값 | 영향 |
|---|---|---|
| DB | MySQL 8.0, InnoDB | 행 잠금, MVCC, 갭·next-key 잠금 |
| 격리 수준 | 설정한 곳이 없어 기본값 **REPEATABLE READ** | InnoDB에서 일반 SELECT는 트랜잭션의 스냅샷을 읽는다. 잠금 읽기(`FOR UPDATE`·`FOR SHARE`)와 UPDATE는 최신 commit 값을 읽는다 (아래 이식성 주의) |
| 영속성 | `open-in-view: false`, Hibernate 기본 UPDATE | **바뀌지 않은 컬럼까지 모든 컬럼**을 UPDATE한다 (`@DynamicUpdate` 없음) |
| 커넥션 | 풀 크기 10(local·test), 획득 대기 3초 | 잠금을 기다리는 요청도 커넥션을 쥔다 |
| 트랜잭션 경계 | Facade의 `@Transactional`, 도메인 Service에는 없음 | 호출이 프록시를 거치는 Facade가 시작점이다 |

InnoDB는 PostgreSQL의 REPEATABLE READ와 달라서 **갱신 유실을 감지해 거절하지 않는다.** 두 번째 UPDATE는 앞 트랜잭션이 commit할 때까지 기다린 뒤, 자기가 읽은 낡은 값으로 덮어쓴다.

**이식성 주의 (DB 고유 동작에 기대는 범위)**: `FOR UPDATE`가 잠금이 풀릴 때까지 기다린 뒤 *그 시점에 commit된 최신 값*을 읽는 것은 READ COMMITTED를 쓰는 DB 대부분에서 같은 보편적 동작이다. InnoDB RR만의 특이점은 두 가지다.

- 같은 트랜잭션에서 일반 SELECT는 스냅샷, 잠금 읽기는 최신 값을 봐서 **한 행이 두 값으로 보일 수 있다.**
- 잠금 읽기가 오류 없이 최신 값을 돌려준다. PostgreSQL RR에서는 다른 트랜잭션이 바꾼 행을 `FOR UPDATE`로 만나면 `could not serialize access`로 rollback되어 재시도가 필요하다.

이 설계는 다음 두 가지만 전제하고, InnoDB RR의 특이점에는 정합성을 기대지 않는다.

1. 대상 행은 트랜잭션에서 **처음 읽을 때부터 잠금 조회**로 읽는다. 잠금 없이 읽은 값으로 판단하면 판단과 잠금 사이에 값이 바뀔 수 있다(check-then-act, DB와 무관). JPA에서는 영속성 컨텍스트 때문에 함정이 하나 더 있다 (2-2).
2. 잠금을 얻은 뒤 읽은 값은 앞선 트랜잭션이 commit한 값이다. READ COMMITTED를 쓰는 DB와 InnoDB RR에서 같다.

1을 지키면 한 트랜잭션에서 같은 행이 두 값으로 보이는 InnoDB RR의 장면이 코드에 나타나지 않는다.

### 1-2. 현재 코드의 경쟁 지점

| 지점 | 현재 코드 | 반례 |
|---|---|---|
| 재고 | `OrderFacade.confirm` → `ProductService.getAllActiveByIds`(잠금 없는 SELECT) → `product.decreaseStock` → 변경 감지 UPDATE | 재고 5를 두 요청이 읽고 각각 4를 저장 → 성공 2 / 재고 4 |
| 잔액 | `UserService.get`(잠금 없음) → `user.payPoint`·`chargePoint` | 충전과 결제가 같은 잔액을 읽고 한쪽이 덮어씀 |
| 주문 상태 | `orderService.getMine`(잠금 없음) → `ensureConfirmable` → `confirm` | 같은 주문을 두 번 확정하면 둘 다 DRAFT로 읽고 재고·잔액이 두 번 차감됨 |
| 삭제 플래그 | 상품 전체 컬럼 UPDATE | 브랜드 삭제가 `deleted_at`을 기록한 뒤, 낡은 스냅샷을 가진 확정이 `deleted_at = null`로 덮어써 삭제된 상품이 되살아남. 반대 순서에서는 삭제가 재고를 되돌림 |
| 가격 수정 | `AdminProductFacade.update` | 가격 수정 UPDATE가 `stock` 컬럼까지 써서 주문 차감을 지움 |
| 브랜드 삭제 | `hasActiveProducts` 확인 후 `brand.delete()` | 확인과 삭제 사이에 상품이 등록됨 (D-16이 남긴 한계) |

**핵심 관찰**: 경쟁은 재고·잔액만이 아니라 *같은 행을 쓰는 모든 경로*에서 생긴다. 한 유스케이스만 잠그면 나머지 경로가 우회로가 된다.

## 2. 보호 대상과 잠금 규칙

### 2-1. 판단 기준

**모든 쓰기 경로가 최신 값 기준의 배타 잠금(X) 아래에서 계산해야 한다.**

- 비관적 잠금(`FOR UPDATE`로 읽고 엔티티로 쓰기)과 조건부 갱신(현재 값을 읽는 원자적 UPDATE)은 둘 다 이 기준을 만족하므로 섞을 수 있다.
- 잠금 없이 읽은 엔티티로 전체 컬럼을 쓰는 경로가 하나라도 남으면 기준을 깨뜨린다.
- 낙관적 잠금은 InnoDB에서 `UPDATE … WHERE version = ?`도 행 잠금을 기다린 뒤 0행으로 실패하므로 "기다리지 않는 방식"이 아니다.

### 2-2. 유스케이스별 전략

전역 잠금 순서: **주문 → 브랜드 → 상품(id 오름차순) → 사용자**

잠금 순서는 처리 속도를 바꾸지 않는다. 한 트랜잭션이 여러 자원을 잡을 때 서로 순환하지 않도록 정하는 규칙이다. 지금은 주문과 브랜드를 함께 잡는 유스케이스가 없다.

| 유스케이스 | 시작점(Facade) | 잠금 (순서대로) |
|---|---|---|
| 주문 확정 | `OrderFacade.confirm` | 주문 X → 상품 X(`IN … ORDER BY id FOR UPDATE`, 한 번에) → 사용자 X |
| 브랜드 일괄 삭제 | `AdminBrandFacade.delete` | 브랜드 X → 그 브랜드의 미삭제 상품 X(id 오름차순) |
| 브랜드 수정 | `AdminBrandFacade.update` | 브랜드 X |
| 상품 등록 | `AdminProductFacade.create` | 브랜드 S(`FOR SHARE`) |
| 포인트 충전 | `PointFacade.charge` | 사용자 X |
| 관리자 상품 수정·삭제·재고 설정 | `AdminProductFacade.update`·`delete`·`changeStock` | 상품 X |
| 주문 생성·좋아요·고객 조회 | `OrderFacade.create` 등 | 없음 (MVCC 스냅샷, 확정에서 다시 판단) |

**최초 로드 규칙**: 트랜잭션에서 대상 엔티티를 처음 읽는 조회가 잠금 조회여야 한다. 근거는 두 겹이다.

- **check-then-act (DB와 무관)**: 잠금 없이 읽은 값으로 판단하면, 판단한 뒤 잠금을 잡기 전에 다른 트랜잭션이 값을 바꿀 수 있다. 판단은 잠금을 쥔 뒤 읽은 값으로 해야 한다.
- **영속성 컨텍스트 (JPA 추가 함정, `LockedReadStaleEntityTest`로 확인)**: 영속성 컨텍스트는 트랜잭션마다 하나(`open-in-view: false`)이며 같은 트랜잭션 안에서 엔티티를 1차 캐시에 보관한다. 잠금 없이 먼저 읽은 엔티티를 나중에 잠금 조회하면, DB는 최신 행을 주지만 Hibernate는 이미 관리 중인 객체를 그대로 돌려주고 새로 읽은 컬럼 값은 버릴 수 있다. 낡은 값에 변경을 더하면 전체 컬럼 UPDATE가 최신 값을 덮는다. 트랜잭션이 끝나 컨텍스트가 닫히면 낡은 엔티티는 다음 트랜잭션으로 넘어가지 않는다. 실험에서 DB에는 최신 재고 3이 있었지만, 먼저 읽은 객체를 돌려받아 재고 5가 그대로였다.

이 규칙은 *잠금 조회 전용 Repository·Service 메서드*(예: `getForUpdate`)로 경로를 제한하고, 경쟁 테스트로 확인한다.

**확정의 사용자 조회**: 현재는 사용자 → 상품 순으로 읽지만 사용자 처리를 상품 뒤로 옮긴다. 사용자 조회는 필터가 존재를 보장해 실패하지 않으므로 오류 우선순위 계약은 바뀌지 않는다.

### 2-3. 교착 분석

교착은 두 트랜잭션이 각자 둘 이상의 잠금을 **서로 다른 순서로** 잡을 때만 생긴다.

- 잠금을 둘 이상 잡는 유스케이스는 **주문 확정과 브랜드 삭제 둘뿐**이다. 나머지는 잠금이 하나이거나 없다.
- 확정 vs 확정: 둘 다 상품을 id 오름차순으로 한 번에 잡고 사용자를 마지막에 잡는다. 같은 사용자의 두 주문도 순환하지 않는다.
- 확정 vs 브랜드 삭제: 둘 다 상품을 id 오름차순으로 잡는다. 삭제는 *그 브랜드의 상품 행만* 잠그므로 다른 브랜드의 확정은 기다리지 않는다.
- 주문과 브랜드: 확정은 브랜드를 잡지 않고 삭제는 주문을 잡지 않으므로 둘이 엇갈릴 일이 없다. 확정이 나중에 브랜드를 잠가야 한다면 주문을 읽어야 품목·상품·브랜드를 알 수 있으므로 "주문 먼저" 순서가 읽기 순서와도 맞다.
- 삭제 vs 상품 등록: 둘 다 브랜드 행을 먼저 잡는다. 브랜드 행이 문지기라서 상품 INSERT가 삭제의 갭 잠금과 엇갈릴 일이 없다.
- 확정·삭제 vs 충전·관리자 상품 변경: 상대가 잠금을 하나만 잡으므로 순환할 수 없다.

**남는 위험**

1. 상품을 품목 순서대로 하나씩 잠그면 순서가 깨진다. 반드시 정렬된 `IN` 조회 하나로 잡는다.
2. 브랜드 삭제의 상품 잠금(`brand_id`로 시작하는 보조 인덱스 범위, RR)은 next-key·갭 잠금을 잡는다. 실측(`LockBehaviorCharacterizationTest`): 같은 브랜드의 상품 수정·등록과 **다음 브랜드(id가 바로 뒤)의 상품 등록**이 삭제가 끝날 때까지 기다린다. 직전 브랜드나 먼 브랜드의 등록, 다른 브랜드 상품 수정, 일반 조회는 기다리지 않는다. (W4에서 인덱스를 `(brand_id, deleted_at, price, id DESC)`로 바꾸기 전에는 대기하는 이웃이 **직전** 브랜드였다. 새 행이 같은 브랜드·가격 행들 맨 앞에 놓이도록 바뀌어 이웃이 뒤바뀌었고 영향의 크기는 같다.) 순환이 아니라 삭제 한 건 동안의 불필요한 대기다. 확정의 `IN` 조회는 기본 키로 찾은 행만 잠가 인접 상품과 등록을 막지 않는다.
3. 나중에 추가되는 경로가 전역 순서를 어기면 교착이 생긴다. 이 표를 규칙으로 유지한다.
4. 가장 큰 비용은 교착보다 **커넥션 점유**다. 한 상품에 요청이 몰리면 대기 요청이 풀을 비워 무관한 요청이 커넥션 획득 대기 3초를 넘길 수 있다.

### 2-4. 대기와 교착의 처리

- InnoDB는 교착을 즉시 감지해 한쪽을 rollback한다. 잠금 대기 초과는 `innodb_lock_wait_timeout`(기본 50초)을 따른다.
- 교착·대기 초과는 **기술 오류**로 집계하고 `OUT_OF_STOCK`·`INSUFFICIENT_POINT`로 바꾸지 않는다. 이 둘은 복구 방법이 다르다 (D-28).
- 대기 한도는 기본 50초이며 이번 범위에서는 바꾸지 않는다. 실측 결과와 적용 방법은 D-28과 7장에 있다. 커넥션 획득 대기가 3초라서, 잠금을 기다리는 요청이 풀을 비우면 무관한 요청도 3초 뒤 실패할 수 있다는 점이 한계다.

## 3. 흐름

표기: `Controller → Facade(@Transactional, 프록시 진입점) → Service → Repository → SQL`. 요청 하나가 트랜잭션 하나다. Facade 안의 Service·Repository 호출은 같은 트랜잭션에 참여하며, 실패를 감싸는 `REQUIRES_NEW`는 쓰지 않는다.

### 3-1. 브랜드 일괄 삭제

`DELETE /api-admin/v1/brands/{brandId}`

```
AdminBrandController → AdminBrandFacade.delete(brandId)   ← @Transactional 시작
   ├ BrandService.getForUpdate(brandId)        브랜드 X, 없거나 삭제됐으면 NOT_FOUND
   ├ ProductService.getAllActiveByBrandForUpdate(brandId)   미삭제 상품 X (ORDER BY id)
   ├ products.forEach(Product::delete)         soft delete
   └ brand.delete()
   ← 정상 반환이면 commit, 예외면 전부 rollback
```

| 항목 | 결정 |
|---|---|
| 삭제 방식 | 엔티티를 조회해 `delete()` (변경 감지). 행동·콜백(`updatedAt`)·영속성 컨텍스트가 어긋나지 않는다 (D-23) |
| 대상 없음 | 브랜드가 없거나 이미 삭제됐으면 기존 `NOT_FOUND` |
| 연결 상품 없음 | 정상 처리 (브랜드만 삭제) |
| 재고 0 상품 | 포함 |
| 다른 브랜드·상품 | 변경하지 않는다 |
| 과거 주문 | 품목에 상품명·단가를 복사해 두었고 상품 행을 참조하지 않으므로 그대로 조회된다 (D-20). 주문 행을 삭제하지 않는다 |
| 접근 | 일반·식별 없는 요청은 기존 관리자 접근 규칙(403)으로 거절하고 DB를 바꾸지 않는다 |
| 순서 | 상품 → 브랜드 순으로 `delete()`하지만 모두 같은 트랜잭션이라 관찰 순서는 의미가 없다 |

**삭제 후 고객·관리자 동작**

| 동작 | 결과 |
|---|---|
| 고객 상품 목록·상세 | 제외 (기존 `deletedAt is null` 조건) |
| 새 좋아요 | 상품이 없는 것으로 거절 (`NOT_FOUND`) |
| 내 좋아요 목록 | 제외 (기존 단일 쿼리, D-17) |
| 기존 좋아요 취소 | 유지 (상품을 조회하지 않고 항상 성공) |
| 새 주문 생성 | 상품이 없는 것으로 거절 (`NOT_FOUND`) |
| 삭제 전에 만든 DRAFT 확정 | 확정 시 상품을 다시 확인해 `PRODUCT_UNAVAILABLE` (주문 당시 상품명으로 안내) |
| 관리자 상품 수정·재고 변경 | 삭제된 상품이라 거절 (`NOT_FOUND`) |
| 고객 브랜드 상세 | 삭제된 브랜드라 `NOT_FOUND` |

**중간 실패**: 상품마다 별도 commit하지 않고 일부 성공 응답도 만들지 않는다. 예외가 Facade 밖으로 전달되면 브랜드와 모든 상품의 변경이 취소된다. 메서드 안에서 예외를 잡아 정상 반환하는 코드를 두지 않는다.

### 3-2. 주문 확정 (week2 4-1을 잠금 단계로 갱신)

`POST /api/v1/orders/{orderId}/confirm`

| 단계 | 하는 일 | 잠금 | 실패 시 |
|---|---|---|---|
| 1 | 본인 주문 조회 (`userId`로 한정) | 주문 X | `NOT_FOUND` |
| 2 | 주문이 DRAFT인지 확인 | (주문 X 보유) | `ORDER_ALREADY_CONFIRMED` |
| 3 | 품목 상품 일괄 조회 (id 오름차순, 삭제·없음 확인) | 상품 X | `PRODUCT_UNAVAILABLE` |
| 4 | 품목마다 `decreaseStock(qty)` | (상품 X 보유) | `OUT_OF_STOCK` |
| 5 | 사용자 조회 후 `payPoint(total)` | 사용자 X | `INSUFFICIENT_POINT` |
| 6 | `order.confirm(PaymentResult)` | — | (상태 재검증) |
| 7 | 변경된 엔티티 저장 (변경 감지) | commit에서 잠금 해제 | 예외 시 전체 rollback |

- 오류 우선순위는 week2와 같은 단계 순서다. 이미 확정된 주문이 재고 부족으로 보이지 않게 2단계를 앞에 둔다.
- 주문 행을 먼저 잡으므로 같은 주문의 동시 확정은 상품 잠금 경쟁에 들어가기 전에 직렬화된다. 두 번째 요청은 기다린 뒤 CONFIRMED를 보고 기존 계약대로 `ORDER_ALREADY_CONFIRMED`로 거절된다.
- 4·5단계에서 예외가 나면 3단계까지의 변경이 모두 취소된다.
- 확정되지 못한 주문은 DRAFT, 재고와 잔액은 변경 전 그대로여야 한다.
- 결제액은 주문 합계(주문 당시 단가 스냅샷)다 (D-21).

### 3-3. 같은 행을 바꾸는 다른 경로

| 경로 | 같은 행 | 규칙 |
|---|---|---|
| 포인트 충전 `PointFacade.charge` | 사용자 | 사용자 X로 읽은 뒤 `chargePoint`. 확정의 결제와 같은 잠금에 참여한다 |
| 관리자 재고 설정 `changeStock` | 상품 | 상품 X로 읽은 뒤 최종 수량으로 교체. 확정의 차감과 직렬화된다 |
| 관리자 상품 수정 `update` | 상품 | 상품 X. 전체 컬럼 UPDATE가 재고를 덮어쓰지 못하게 한다 |
| 관리자 상품 삭제 `delete` | 상품 | 상품 X |
| 브랜드 수정 `update` | 브랜드 | 브랜드 X. 전체 컬럼 UPDATE가 삭제 표시를 되살리지 못하게 한다 |
| 상품 등록 `create` | 브랜드(읽기) | 브랜드 S. 삭제(X)와는 직렬화하고, 등록끼리는 동시에 진행한다 |

관리자 재고 설정은 "최종 수량으로 교체"이므로 먼저 commit한 주문 차감을 지우는 것이 아니라, **잠금 순서대로 뒤에 적용**된다. 설정이 뒤에 오면 설정값이 최종이고, 앞에 오면 주문이 설정값에서 차감한다. 어느 쪽이든 성공한 업무 결과와 일치한다.

## 4. 반례 점검

과제가 요구한 반례를 설계에 대조한다. 구현 후 테스트로 확인한다.

| 반례 | 현재 위험 | 설계의 대응 |
|---|---|---|
| 자기 호출 | `delete`가 같은 객체의 `@Transactional` 메서드를 호출하면 경계가 적용되지 않음 | 경계는 외부에서 호출되는 Facade 진입 메서드에만 둔다. 내부 헬퍼에는 붙이지 않는다 |
| 예외 삼키기 | 상품 하나가 실패해도 catch 후 계속하면 프록시가 정상 종료로 판단 | 상품 삭제·차감 중 예외를 catch하지 않는다 |
| 독립 commit | 상품마다 `REQUIRES_NEW`를 쓰면 앞 상품이 따로 commit | `REQUIRES_NEW`·`NESTED`를 쓰지 않는다. Facade 하나의 물리 트랜잭션만 쓴다 |
| 빠진 잠금 대상 | 재고만 잠그면 잔액·주문 상태·삭제 플래그가 남음 | 2-2 표가 대상 전체를 열거한다. 상품 수정·재고 설정·충전·브랜드 수정이 모두 참여한다 |
| 잠금 전 로드 | 잠금 없이 먼저 읽은 엔티티는 나중에 잠가도 낡은 상태일 수 있음 | 첫 조회를 잠금 조회로 하고, 그 경로를 전용 메서드로 제한한다 |
| 잠금 조회와 변경이 다른 트랜잭션 | 잠금 조회 직후 트랜잭션이 끝나면 판단이 보호되지 않음 | 잠금 조회는 항상 Facade의 `@Transactional` 안에서만 호출한다 |
| 전역 `synchronized` | 모든 상품을 직렬화하고 프로세스가 다르면 보호되지 않음 | 쓰지 않는다 |
| flush와 commit 혼동 | flush 후 같은 엔티티를 읽은 값은 commit의 증거가 아님 | rollback 확인은 서비스 트랜잭션 종료 후 새 경계에서 재조회한다 |

## 5. 검증 설계

### 5-1. 원칙

- 원인 설명용 **대조군**과 개선된 **실제 서비스 검증**을 구분한다. 대조군의 통과는 실제 주문의 정합성 증거가 아니다.
- 데이터는 worker 시작 전에 commit한다. 테스트 전체를 부모 트랜잭션으로 감싸지 않고, `@AfterEach`에서 `DatabaseCleanUp`으로 정리한다.
- 실제 서비스 worker는 **시작만 맞추고** 각 요청이 독립 트랜잭션으로 실제 Facade·Repository·MySQL을 통과한다. 잠금 구간에 장벽이나 sleep을 넣지 않는다.
- 요청별 결과를 **성공 / 업무 거절 / 기술 오류**로 수집한다. 예외를 출력만 하고 버리지 않으며, 모든 worker가 끝난 뒤 새 조회로 DB를 확인한다.
- 대기·future에 제한 시간을 두고, timeout을 업무 거절로 세지 않는다. `finally`에서 대기를 풀고 executor를 정리한다.
- 기존 MySQL fixture(`MySqlTestContainersConfig`, `DatabaseCleanUp`)를 쓴다. 메모리 DB와 repository mock은 증거로 쓰지 않는다.
- **짧은 요청은 겹침이 확률적이다.** 관리자 수정·삭제는 읽기 한 번과 쓰기 한 번이라 확정보다 먼저 끝나는 경우가 많다. 실측에서 잠금을 빼도 반복 20번 중 0~4번만 실패했다(`AdminWriteConcurrencyTest`). 그래서 실제 요청끼리 경쟁시키는 테스트와 별도로, **테스트 트랜잭션이 대상 행의 잠금을 쥔 채 동시에 commit 되는 변경(재고 차감, 삭제)을 미리 수행**하고 서비스 요청이 모두 시작한 뒤 잠금을 푸는 결정적 테스트를 둔다(`AdminWriteStaleOverwriteTest`, `HeldRowLock`). 서비스가 처음 읽을 때 잠그지 않았다면 풀리기 전에 이미 낡은 값을 읽고 풀린 뒤 덮어쓴다. 잠그면 풀릴 때까지 기다렸다가 최신 값을 읽는다.
- 이 방식은 "시작만 맞춘다"는 원칙의 예외다. 서비스 코드의 잠금 구간에는 장벽이나 sleep 이 없고 잠금을 쥐는 쪽은 테스트 트랜잭션이지만, 요청이 읽기를 마칠 시간을 주려고 테스트에 고정 대기(300ms)를 둔다. 이 대기는 잠금이 있는 구현의 결과에는 영향이 없고, 대기가 모자라면 *잠금이 빠진 구현을 놓칠 수만* 있다.

### 5-2. 대조군 (제품 구현이 아님)

테스트 소스에서 독립된 트랜잭션 두 개가 commit된 재고 5를 잠금 없는 SELECT로 읽는다. 두 값이 5임을 확인한 뒤 쓰기를 허용하고, 각자 읽은 값에서 1을 뺀 **상수 4**를 조건·version 없이 저장한다.

- 기대: `성공 2 / 최종 재고 4`, `2 + 4 ≠ 5`. 불변식 위반이 *재현됐음*을 assertion으로 확인하며 실패를 방치하지 않는다.
- 최소 두 worker·connection을 확보하고, 읽기·쓰기 완료에 제한 시간을 둔다. timeout이나 SQL 오류는 재현으로 세지 않는다.
- post-read 장벽은 대조군 안에만 둔다. `stock = stock - 1` SQL은 이 예제와 다르므로 대조군으로 쓰지 않는다.

| 관리자 재고 설정 vs 확정 | 같은 상품에 재고 설정 1개와 확정 5개를 동시에 실행 | 확정은 모두 성공, 재고는 15~20(설정이 잠금 순서의 어디에 오느냐). 설정 전 값(10 이하)으로 남지 않음. 재고 설정은 절대값을 쓰므로 확정과의 경쟁만으로는 잠금 누락이 드러나지 않는다 |
| 관리자 수정·삭제·재고 설정이 동시에 commit 된 변경을 덮는지 (`AdminWriteStaleOverwriteTest`) | 테스트 트랜잭션이 상품·브랜드 행을 잠그고 재고 차감 또는 삭제를 수행한 채, 서비스 요청을 줄 세운 뒤 풀어 줌 | 재고 차감은 유지(수정·삭제 뒤에도 9), 삭제는 되살아나지 않고 요청은 `NOT_FOUND`. 확정은 최신 재고(20)에서 차감, 삭제된 상품은 `PRODUCT_UNAVAILABLE` |
| 브랜드 삭제 vs 확정 | 같은 브랜드 상품의 확정과 삭제를 동시에 실행 | 확정이 먼저면 삭제 후 DRAFT가 아닌 CONFIRMED 주문이 유지, 삭제가 먼저면 `PRODUCT_UNAVAILABLE`. 상품이 되살아나지 않음 |

집계식 (요청 결과와 DB의 주문·품목·잔액으로 함께 확인한다):

- 수량: 초기 재고 − 성공 주문의 품목 수량 합 = 최종 재고
- 잔액: 초기 잔액 + 성공 충전액 합 − 성공 결제액 합 = 최종 잔액
- 집계: 성공 + 업무 거절 + 기술 오류 = 전체 요청

"최종 재고가 음수가 아니다"만 확인하지 않는다. 모든 요청을 거절하거나 성공을 집계에서 빼먹은 코드도 그 조건을 만족하기 때문이다. 포인트 경쟁은 재고를 충분히 두어 잔액 보호의 실패를 재고 부족이 가리지 않게 한다.

### 5-4. 실패 주입

- 운영 코드에 실패용 API·sleep·공개 스위치를 만들지 않는다.
- 테스트 구성에서 Hibernate `StatementInspector`(또는 동등한 저장 경계)로 N번째 `update products`/`update users` 문장에서 예외를 던진다. 앞의 변경 SQL이 실제로 DB에 전송된 뒤에 실패하므로 rollback이 의미를 가진다.
- 구현 시 이 방식이 동작하는지 먼저 확인하고, 안 되면 대안을 보고한다. 앞 단계까지 전부 mock하는 방식은 쓰지 않는다.
- HTTP 연결은 브랜드 일괄 삭제와 주문 확정의 대표 사례로 확인하고, 같은 수량 규칙의 모든 경계값을 모든 계층에 반복하지 않는다.

## 6. 설계 결정 기록

번호는 week2의 D-22에서 이어진다.

### D-23. 브랜드 삭제는 연결 상품을 함께 soft delete하고, 엔티티 조회 후 `delete()`로 처리한다

- **상황**: week2는 연결 상품이 있으면 삭제를 거절했다. week3는 브랜드와 연결된 미삭제 상품(재고 0 포함)을 함께 고객의 사용 대상에서 제외해야 한다.
- **결정**: 한 트랜잭션에서 브랜드를 잠금 조회하고, 그 브랜드의 미삭제 상품을 잠금 조회해 각 `delete()`를 호출한 뒤 브랜드를 삭제한다. 물리 삭제·DB cascade는 쓰지 않는다.
- **근거**: 주문 품목은 상품명·단가를 복사해 두었으므로 상품 행을 지우지 않아도 과거 주문이 유지된다. 행을 남기고 사용 대상에서 제외하는 방식이 참조 보존의 첫 번째 선택이다 (D-5). 엔티티 조회 방식은 기존 `BaseEntity.delete()`의 멱등성과 `updatedAt` 갱신을 그대로 쓰고, 영속성 컨텍스트와 DB가 어긋날 일이 없다.
- **비용**: 상품 수만큼 UPDATE가 나가고 상품이 많은 브랜드에서는 트랜잭션과 잠금 시간이 길어진다. 이 규모를 가정하지 않는 로컬 실습이라 허용한다.
- **재검토 조건**: 브랜드당 상품 수가 커져 잠금 시간이 문제가 되면 먼저 `hibernate.jdbc.batch_size`로 UPDATE를 묶는 것을 검토한다(현재는 꺼져 있다. 상품 INSERT는 `IDENTITY` 전략이라 묶이지 않고, 공유 설정이라 이번 범위에 넣지 않았다). 그래도 부족하면 JPQL bulk UPDATE를 검토한다. 이때는 엔티티 콜백을 우회하고 영속성 컨텍스트 정리(flush/clear) 판단이 필요하다.
- **기각한 대안**: JPQL bulk UPDATE(엔티티 행동·`updatedAt` 우회, 컨텍스트 정리 필요), DB cascade(업무 결과를 DB 설정에 맡김), 상품마다 별도 트랜잭션(중간 실패 시 일부만 반영).

### D-24. 같은 행을 쓰는 모든 경로가 한 규칙에 참여하고, 대상은 처음 읽을 때 잠근다

- **상황**: Hibernate의 전체 컬럼 UPDATE 때문에 업무상 다른 필드를 바꾸는 요청끼리도 서로를 덮어쓴다 (1-2).
- **결정**: 2-1의 판단 기준을 따른다. 주문 확정, 충전, 관리자 상품 수정·삭제·재고 설정, 브랜드 수정·삭제가 모두 대상 행을 배타 잠금으로 읽는다. 잠금 조회는 전용 메서드로 제한한다.
- **근거**: 전체 컬럼 UPDATE에서는 재고를 잠근 확정이라도 가격 수정이 재고를 덮어쓴다. 보호의 단위는 유스케이스가 아니라 *행*이다.
- **비용**: 단순 수정에도 잠금 조회가 필요하고 관리자 수정이 확정을 잠깐 기다리게 한다. 잠금 조회 메서드를 빠뜨린 경로가 우회로가 된다.
- **재검토 조건**: 상품의 컬럼이 늘어 수정과 재고가 독립적인 규칙이 되면 `@DynamicUpdate`나 재고 분리를 검토한다.
- **기각한 대안**: `@DynamicUpdate`만 적용(재고 설정·삭제·확정의 판단 경쟁은 남고 규칙이 두 가지가 됨).

### D-25. 격리 수준은 MySQL 기본 REPEATABLE READ를 유지하고, 쓰기 경로는 비관적 잠금을 쓴다

- **상황**: InnoDB의 RR은 갱신 유실을 감지하지 않는다. 대안으로 격리 수준 변경, 낙관적 잠금, 조건부 갱신이 있다.
- **결정**: 격리 수준을 바꾸지 않고, 모든 쓰기 경로(2-2)를 `FOR UPDATE`(상품 등록은 `FOR SHARE`)로 보호한다. 읽기 전용 경로는 MVCC 스냅샷을 그대로 쓴다.
- **근거**:
  - MySQL의 기본 격리 수준을 그대로 쓰고 필요한 곳에만 `FOR UPDATE`를 붙이는 방식이 가장 흔한 패턴이다. 설정이나 트랜잭션별 격리 수준 지정이 코드 밖 지식을 요구하지 않는다.
  - 정합성은 "처음 읽기가 잠금 읽기"(JPA 근거)와 "잠금 후 읽은 값은 commit된 값" 두 가지 위에 선다 (1-1). InnoDB 고유 장면(한 트랜잭션에서 같은 행이 두 값으로 보임)은 첫 번째 규칙을 지키면 나타나지 않는다.
  - 기존 도메인 검증(`Stock`, `PointBalance`)과 오류 계약을 그대로 쓴다.
  - 읽기 요청은 X 잠금에 막히지 않아 브랜드 삭제 중에도 카탈로그 조회가 멈추지 않는다.
- **비용**: 대기 중에도 커넥션을 점유하고, 잠금 순서를 어기면 교착이 생긴다. 규율(최초 로드 규칙)에 의존한다. **이식성**: PostgreSQL RR로 옮기면 잠금 대기 뒤 직렬화 오류가 나므로 재시도 장치가 필요하다.
- **재검토 조건**: 재고 차감만 하는 짧은 트랜잭션(선착순 API 등)이 생기거나 확정 오류 계약을 "구매 불가" 하나로 합치면 재고에 조건부 갱신을 다시 검토한다. 포인트 규칙이 계속 단순하고 경쟁이 잦아지면 포인트에도 다시 검토한다.
- **기각한 대안**:
  - 낙관적 잠금: 재고처럼 요청이 몰리는 곳에서 재시도가 폭증하고, 가격 수정 같은 무관한 변경과 거짓 충돌하며, 확정이 마지막 단계에서 충돌하면 앞 작업을 버리고 처음부터 다시 해야 한다. InnoDB에서는 version UPDATE도 행 잠금을 기다리므로 "기다리지 않는다"는 이점이 없다. 재시도는 별도 bean의 새 트랜잭션이어야 해 구조도 늘어난다.
  - 재고의 조건부 갱신: `stock >= ? AND deleted_at IS NULL`의 0행은 "삭제"와 "부족" 두 원인이라, 오류 우선순위 계약을 지키려면 다시 읽어야 한다. 이 재조회는 갱신과 원자적이지 않아(그 사이 상태가 바뀔 수 있고, InnoDB RR에서는 일반 SELECT가 스냅샷이라 모순된 값까지 줄 수 있다) 원인 구분에 결국 잠금 읽기가 필요하다. 그러면 비관적 잠금과 구조가 같아진다.
  - SERIALIZABLE: 직렬화 실패(교착·직렬화 오류)가 일상적으로 생기고 재시도가 필요해 "기술 오류 0"을 지킬 수 없다. InnoDB에서는 일반 SELECT가 공유 잠금이 되어 S→X 승격 교착으로 나타난다(가설).
  - READ COMMITTED 전역 변경: 서비스 전체 정책 변경이며 `modules` 공유 설정에 영향이 간다. 읽고 판단한 뒤 쓰는 사이의 경쟁도 이것만으로는 해결하지 못해 잠금은 여전히 필요하다.
  - 쓰기 경로만 READ COMMITTED 명시: MySQL에서 흔한 패턴이 아니고 트랜잭션마다 격리 수준 전환이 든다. 읽는 쪽이 "왜 여기만 RC인가"를 따로 이해해야 한다.

### D-26. 포인트는 비관적 잠금으로 보호하고, 조건부 갱신은 비교한 대안으로 남긴다

- **상황**: 충전과 결제는 동시에 일어날 가능성이 낮다. 조건부 갱신(`UPDATE users SET point_balance = point_balance - ? WHERE id = ? AND point_balance >= ?`)도 적합 조건 ①(행 하나의 조건 하나) ②(0행의 원인이 하나) ③(갱신 뒤 엔티티 상태가 거의 불필요)을 만족한다.
- **결정**: 사용자 행을 `FOR UPDATE`로 읽은 뒤 `user.chargePoint`·`payPoint`로 판단한다. 결제는 상품 잠금 뒤 마지막에 잡는다.
- **근거**: 두 방식 모두 최신 값 기준의 X 잠금 아래에서 계산해 경쟁 안전성은 같다. 경쟁이 드물어 성능 차이도 없다. 남는 차이는 다음이다.
  - 비관적 잠금은 잔액 규칙(잔액 ≥ 결제액, 충전액 > 0, 범위 초과)이 `PointBalance`·`Money` 한 곳에 남고, 프로젝트 관례(규칙은 모델에)를 바꾸지 않으며, 일일 한도·이력 같은 읽고 판단하는 규칙을 코드로 확장하기 쉽다.
  - 조건부 갱신은 구조적으로 안전하고 다른 컬럼과 간섭하지 않으며 `User` 이중 조회가 사라진다. 대신 `@PreUpdate`를 우회해 `updated_at`을 직접 써야 하고, 같은 트랜잭션의 1차 캐시가 낡으며, `@Modifying(clearAutomatically)`가 앞서 읽은 `Order`를 분리할 수 있고, 잔액 판정이 SQL로 옮겨 가 테스트의 보호 범위가 DB 통합 테스트로 좁아진다.
- **비용**: "처음 읽기가 잠금 읽기여야 한다"는 규율에 의존한다. `User`를 일반 조회로 먼저 읽는 경로가 생기면 낡은 잔액으로 판단한다. 확정에서 `User` 이중 조회가 남는다 (D-21 그대로).
- **재검토 조건**: 포인트 규칙이 계속 단순하고 충돌이 잦아지면 조건부 갱신을 다시 본다.
- **기각한 대안**: 조건부 갱신(위), 사용자 `@Version` + 충전만 낙관적 재시도(InnoDB에서 충전 UPDATE도 행 잠금을 기다리므로 얻는 것이 없고 재시도 장치만 늘어남).

### D-27. 전역 잠금 순서는 주문 → 브랜드 → 상품(id 오름차순) → 사용자이고, 상품 등록은 브랜드를 공유 잠금한다

- **상황**: 잠금을 둘 이상 잡는 유스케이스는 확정과 브랜드 삭제다. 여러 상품을 잡을 때와 종류가 다른 자원을 잡을 때 순서가 일관돼야 교착을 피한다.
- **결정**:
  - 같은 종류의 여러 행은 id 오름차순 `IN … ORDER BY id`로 *한 번에* 잠근다.
  - 종류가 다른 자원은 주문 → 브랜드 → 상품 → 사용자 순이다.
  - 상품 등록은 브랜드를 `FOR SHARE`로 읽어 삭제(X)와 직렬화하고, 등록끼리는 동시에 진행한다.
- **근거**: 순환 대기가 생기려면 서로 다른 순서가 필요하다 (2-3). 브랜드 행이 문지기라서 삭제와 등록 사이의 "삭제 후 미삭제 상품이 남는" 경쟁이 닫히고, 상품 INSERT가 삭제의 갭 잠금과 엇갈리지 않는다.
- **비용**: 새 경로는 이 순서를 지켜야 한다. RR의 보조 인덱스 범위 잠금 때문에 같은 갭을 향한 INSERT가 잠깐 기다릴 수 있다.
- **실측**: 잠금을 적용하기 전에는 삭제 1개와 등록 4개를 동시에 실행한 20회 중 8회에서 삭제된 브랜드 아래에 미삭제 상품 4개가 남았다(week2 D-16이 넘긴 한계의 재현). 공유 잠금을 적용하자 20회 모두 남지 않았고, 일반 조회로 되돌리면 다시 실패한다. 공유 잠금 대신 배타 잠금으로 바꾸면 "등록끼리 기다리지 않는다" 테스트가 5초 제한 시간을 넘겨 실패한다.
- **재검토 조건**: 잠금을 둘 이상 잡는 유스케이스가 늘어나면 순서 표를 갱신하고 교착 테스트를 추가한다. 주문과 브랜드를 함께 잡는 유스케이스가 생겨도 이 순서(주문 먼저)를 그대로 따른다.
- **기각한 대안**: 상품 등록의 `FOR UPDATE`(같은 브랜드의 등록끼리 서로 기다림), 품목 순서대로 하나씩 잠그기(순서가 요청마다 달라 교착).

### D-28. 교착·잠금 대기 초과는 기술 오류로 두고, 업무 거절로 바꾸지 않는다

- **상황**: 경쟁에서 실패한 요청이 재고 부족인지, 잔액 부족인지, DB가 중단시킨 것인지 구분돼야 한다.
- **결정**: `OUT_OF_STOCK`·`INSUFFICIENT_POINT`는 잠금 후 현재 상태를 판단한 결과에만 쓴다. 교착·대기 초과·커넥션 획득 실패는 기술 오류(`INTERNAL_ERROR` 계열)로 전파하고 테스트가 별도로 집계한다. 재시도는 하지 않는다.
- **근거**: 업무 거절과 기술 실패는 복구 방법이 다르다. 기술 오류를 품절로 바꾸면 운영 원인을 잃고, 테스트의 "기술 오류 0" 기대값이 의미를 잃는다.
- **비용**: 드문 교착이 사용자에게 500으로 보일 수 있다.
- **대기 한도 (실측)**: 기술 오류로 전파되는 잠금 대기 초과는 기본 50초 뒤에 나타난다. MySQL에서 JPA 힌트로는 유한한 대기를 줄 수 없고(`lock.timeout=0`만 NOWAIT로 동작, 그 외 값은 무시), 세션 변수로만 가능하다(7장). 이번 범위에서는 설정을 바꾸지 않고 한계로 둔다.
- **재검토 조건**: 운영에서 교착이 관찰되면 새 트랜잭션에서 횟수·대기 한도를 둔 재시도를 검토한다.
- **기각한 대안**: 모든 실패를 `OUT_OF_STOCK`으로 변환, 무제한 재시도.

### D-29. 실패는 테스트 구성의 저장 경계에서 주입한다

- **상황**: rollback은 최소 한 번의 실제 변경 SQL이 나간 뒤 다음 단계가 실패해야 검증된다. 앞 단계를 mock하면 DB rollback을 볼 수 없다.
- **결정**: 테스트에서만 Hibernate `StatementInspector`(`FailingStatementInspector`)로 지정한 접두사의 N번째 변경 문장에 예외를 던진다. 서비스 트랜잭션 종료 후 영속성 컨텍스트를 거치지 않는 `JdbcTemplate`으로 새로 읽는다. 등록은 `@SpringBootTest(properties = "spring.jpa.properties.hibernate.session_factory.statement_inspector=…")`로 해당 테스트 클래스에만 한다.
- **실측 (브랜드 일괄 삭제, 구현 완료)**: 동작을 확인했다. 첫 `update products`에서 실패시키면 그 앞에 `update brands`가 실제로 전송되어 있었고(inspector 기록으로 assertion), 예외는 Facade 밖으로 전달되었으며, 브랜드·상품이 모두 변경 전 상태로 남았다. 예외는 감싸져 나올 수 있어 원인 사슬에 주입한 예외가 있는지로 확인한다.
- **실측 (주문 확정)**: 확정의 잠금 SQL이 `orders` → `products`(`in (…) order by id`) → `users` 순서로 `for update`를 붙여 나가는 것을 SQL 기록으로 확인했다. 변경 SQL의 전송 순서도 `orders` → `products` → `users`라서, 사용자 UPDATE에서 실패시키면 재고 UPDATE가 이미 전송된 상태가 된다. 이 순서는 영속성 컨텍스트에 엔티티가 들어온 순서를 따르므로, 사용자를 상품보다 먼저 읽는 옛 순서에서는 재고 UPDATE가 나가기 전에 실패해 rollback 검증이 비어 있었다.
- **배치와의 관계**: 현재 `hibernate.jdbc.batch_size`가 꺼져 있다. 나중에 켜면 같은 SQL의 UPDATE가 묶여 "N번째 상품 UPDATE"라는 지점이 사라질 수 있으므로, 실패 지점을 *첫 번째* 상품 UPDATE로 두고 앞선 변경 SQL이 나갔는지 기록으로 확인한다.
- **근거**: 운영 코드를 건드리지 않고 실제 SQL 전송 뒤에 실패할 수 있다. 테스트 메서드의 자동 rollback과 구분하려고 테스트를 부모 트랜잭션으로 감싸지 않는다.
- **비용**: Hibernate 내부 확장점에 의존하며 문장 문자열 매칭이 느슨할 수 있다.
- **재검토 조건**: 확장점이 동작하지 않으면 repository 구현을 테스트 설정에서 감싸는 방식을 보고하고 정한다.
- **기각한 대안**: 운영 코드의 실패용 스위치·sleep, Facade·Service mock.

## 7. 열린 항목

| 항목 | 확인 방법 |
|---|---|
| ~~잠금 대기 한도를 짧게 두는 방법~~ | **실측 완료, 설정은 적용하지 않음**. JPA 표준 힌트 `jakarta.persistence.lock.timeout`은 MySQL 8.0에서 `0`(`for update nowait`로 즉시 `LockTimeoutException`)만 의미가 있고, 그 외 값(예: 500)은 SQL에 아무 절도 붙지 않아 무시된다(보유자가 풀 때까지 기다림). 유한한 대기는 MySQL 세션 변수 `innodb_lock_wait_timeout`으로만 가능하며, 줄이면 그 시간 뒤 `PessimisticLockException`(근본 원인 "Lock wait timeout exceeded")으로 실패한다. 적용 방법 후보는 jdbc-url의 `sessionVariables=innodb_lock_wait_timeout=N` 또는 풀의 `connection-init-sql`이다. 운영 튜닝이며 `modules` 공유 설정이라 이번 범위에 넣지 않았다 |
| ~~Hibernate가 MySQL 8.0에서 `PESSIMISTIC_READ`를 `for share`로 생성하는지~~ | **확인됨**. 상품 등록의 브랜드 조회가 `... where id=? and deleted_at is null for share`로 나가고, 삭제의 브랜드 조회는 `for update`로 나간다 |
| ~~`IN … ORDER BY id FOR UPDATE`의 실제 잠금 범위와 실행 계획~~ | **행동으로 확인**. 앱 계정은 `performance_schema.data_locks`를 읽을 수 없어(권한 거부) 별도 세션이 잠금 대기를 1초로 줄이고 문장을 시도해 막히는지로 관찰했다. `EXPLAIN`: 삭제의 상품 조회는 `idx_products_brand_id`(W4에서 `idx_products_brand_price_id`로 교체, `type=ref`), 확정의 `IN` 조회는 `PRIMARY`(`type=range`). 범위는 2-3의 실측과 같다 |
| ~~`StatementInspector`로 변경 문장 실패 주입이 되는지~~ | **확인됨** (D-29 실측). 주문 확정도 같은 장치로 확인: 재고 UPDATE가 전송된 뒤 첫 `update users`에서 실패시키면 재고·잔액·상태·결제 결과가 모두 변경 전으로 돌아간다 |
| ~~갭 잠금의 영향(이웃 브랜드 상품 등록 대기)~~ | **실측 완료**. 삭제 중 이웃 브랜드 한쪽(W4 인덱스 교체 이후 다음 브랜드)의 상품 등록만 기다린다(2-3). 영향은 삭제 한 건 동안으로 제한되어 한계로만 기록한다 |

이 문서의 성능·잠금 범위에 관한 서술 중 위 표에서 취소선으로 표시하지 않은 것은 *실측 전 가설*이며, 실측하지 않은 항목을 검증됐다고 쓰지 않는다. 잠금 범위의 실측은 InnoDB 8.0 동작이므로 MySQL 버전을 바꾸면 `LockBehaviorCharacterizationTest`로 다시 확인한다.
