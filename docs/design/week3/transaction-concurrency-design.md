# 트랜잭션 경계와 동시성 제어 설계 (W3)

> **함께 바뀌어야 할 상태를 하나의 트랜잭션으로 묶고, 같은 행을 바꾸는 모든 경로를 같은 잠금 규칙에 참여시킨다.**

브랜드 일괄 삭제, 중간 실패 rollback, 주문 확정의 재고·포인트 경쟁을 다룬다. 잠금 순서 표, 교착 분석, 검증 시나리오 상세는 [AI용 상세](transaction-concurrency-design.ai.md)에 있다. 주문 확정의 결제는 W5에서 PG로 바뀌었다([pg-payment-design.md](../week5/pg-payment-design.md)).

## 핵심 결정

| 결정 | 이유 |
|---|---|
| 격리 수준은 MySQL 기본(REPEATABLE READ)을 유지하고, 쓰기 경로는 `FOR UPDATE`로 읽는다 | InnoDB는 갱신 유실을 감지하지 않아 덮어쓴다. 설정 변경 없이 흔한 패턴으로 막는다 |
| 대상 행은 트랜잭션에서 처음 읽을 때부터 잠금 조회로 읽는다 | 잠금 없이 읽은 값으로 판단하면 잠그기 전에 바뀐다. JPA는 먼저 읽은 낡은 엔티티를 그대로 돌려준다 |
| 같은 행을 쓰는 모든 경로가 한 규칙에 참여한다(주문 확정, 충전, 관리자 수정·삭제, 브랜드 수정·삭제) | 전체 컬럼 UPDATE라 가격 수정이 재고를, 삭제가 복원을 덮어쓴다. 보호 단위는 유스케이스가 아니라 행이다 |
| 전역 잠금 순서는 주문 → 브랜드 → 상품(id 오름차순) → 사용자다. 상품은 정렬한 `IN` 조회 한 번으로 잡는다 | 서로 다른 순서로 잡을 때만 교착이 생긴다 |
| 상품 등록은 브랜드를 공유 잠금(`FOR SHARE`)으로 읽는다 | 브랜드 삭제와 직렬화되어 삭제된 브랜드 아래 상품이 남는 경쟁이 닫히고, 등록끼리는 기다리지 않는다 |
| 브랜드 삭제는 연결 상품(재고 0 포함)을 함께 soft delete한다 | 주문 품목이 상품명·단가를 복사해 두어 과거 주문이 유지된다 |
| 교착·잠금 대기 초과는 기술 오류로 두고 `OUT_OF_STOCK` 등 업무 거절로 바꾸지 않는다 | 복구 방법이 달라 원인을 잃으면 안 된다 |
| 낙관적 잠금, 조건부 갱신, 격리 수준 변경은 채택하지 않았다 | 재시도 폭증, 오류 원인 구분 불가, 서비스 전체 정책 변경 때문에 |

## 흐름

```
브랜드 삭제   브랜드 X → 그 브랜드의 미삭제 상품 X → 상품 delete → 브랜드 delete   (한 트랜잭션, 실패하면 전부 rollback)
주문 확정    주문 X → 상품 X (id 오름차순, 한 번에) → 사용자 X → 재고·포인트 차감
상품 등록    브랜드 S → 상품 저장
```

## 검증

- 실제 MySQL로 요청 결과를 성공 / 업무 거절 / 기술 오류로 나눠 세고, 재고·잔액을 집계식으로 확인한다.
- rollback은 테스트에서만 Hibernate `StatementInspector`로 N번째 변경 SQL에 예외를 던져 확인한다.
- 잠금 범위는 InnoDB 동작이라 `LockBehaviorCharacterizationTest`로 기록한다.

## 알려진 한계

- 가장 큰 비용은 교착보다 커넥션 점유다. 한 상품에 요청이 몰리면 대기 요청이 풀을 비워 무관한 요청이 3초 뒤 실패할 수 있다.
- 잠금 대기 한도는 기본 50초이며 바꾸지 않았다(JPA 힌트로는 유한 대기를 줄 수 없다).
- 브랜드 삭제는 다음 브랜드의 상품 등록을 삭제 한 건 동안 기다리게 한다(갭 잠금).
- 새 경로가 전역 순서를 어기거나 잠금 조회를 빠뜨리면 우회로가 생긴다. 규율과 경쟁 테스트에 의존한다.
- PostgreSQL로 옮기면 잠금 대기 뒤 직렬화 오류가 나므로 재시도가 필요하다.
