# R04. 좋아요순 상품 목록 조회 개선

[전체 요구사항](../total_requirement.md) · 작업 브랜치: `volume-3/r04-like-sort-index` · PR 대상: `volume-3/main`

상태: 구현·검증 완료([결과](result.md)). 최종 check: test 241건, slowTest 17건 통과. R03 병합 후 main 기준으로 리베이스했다. [PR #18](https://github.com/corinB/loop-pack-be-l2-vol5-java/pull/18) 병합 완료.
기준 항목: 분석 항목 2(좋아요순 정렬 인덱스 부재와 매 요청 `COUNT`).

## 1. 목적

상품 목록의 좋아요순 정렬이 활성 상품 전체를 읽고 정렬하지 않도록 하고, 페이지 요청마다 반복되는 전체 개수 계산 비용을 줄인다.

## 2. 현재 동작과 변경점

| 구분 | 현재 코드에서 확인한 동작 | 요구하는 변경 |
|---|---|---|
| 좋아요순 정렬 | `infrastructure/query/mall/QueryDslProductQueryDao`가 `product_like_counts`를 LEFT JOIN하고 `coalesce(like_count, 0) desc, id desc`로 정렬 | 인덱스를 사용해 필요한 페이지만 읽도록 개선 |
| 다른 정렬 | 최신순·가격순은 `products`의 `idx_products_deleted_brand_created`, `idx_products_deleted_brand_price` 인덱스 사용 | 유지 |
| 전체 개수 | 목록 요청마다 `products`·`brands` 조인 `COUNT` 실행 | 비용을 줄이는 방식 선택. 응답의 페이지 정보 계약은 유지 |
| 좋아요 수 저장 | R03에서 결정한 방식(집계 테이블·갱신 시점)을 따름 | R03 결과를 전제로 설계 |

## 3. 포함·제외 범위

**포함**

- 좋아요순 목록(브랜드 필터 유무 모두)의 조회 경로·인덱스·스키마 변경.
- 목록 `COUNT` 처리 방식 변경.
- 변경 전후 `EXPLAIN`과 실행 SQL 비교.

**제외**

- 좋아요 집계 방식 자체의 재설계(R03에서 결정).
- 최신순·가격순 정렬 동작 변경, 상품 상세 조회 변경.
- 외부 캐시 서버 도입.

## 4. 규칙

- 좋아요순 정렬 결과는 기존과 같다. 좋아요 수 내림차순, 같으면 상품 ID 내림차순이며, 집계 행이 없는 상품은 0으로 취급한다.
- 삭제된 상품·삭제된 브랜드의 상품은 목록과 개수에서 제외한다.
- 목록 응답의 `page`·`size`·`totalElements` 등 기존 페이지 필드의 의미를 바꾸지 않는다. 바꿔야 한다면 트레이드오프에서 사용자와 합의한다.

## 5. 시나리오와 기대 결과

| 시나리오 | 사전 상태 | 실행 | 기대 결과 | 유지되어야 할 상태 |
|---|---|---|---|---|
| 좋아요순 정렬 | 좋아요 수가 다른 상품·동점 상품·집계 없는 상품 | 좋아요순 목록 조회 | 기존과 같은 순서 | 삭제 상품 제외 |
| 브랜드 필터 | 여러 브랜드의 상품 | 브랜드 지정 좋아요순 조회 | 해당 브랜드만 같은 규칙으로 정렬 | 다른 정렬 결과 |
| 실행 계획 | 대량 상품 fixture | `EXPLAIN` | 좋아요순이 인덱스를 사용하고 전체 정렬(filesort)이 없음 | 최신순·가격순 계획 |
| 좋아요 반영 | 좋아요 등록·취소 후 R03 방식의 반영 완료 | 좋아요순 조회 | 반영된 값으로 정렬 | 반영 지연 허용 범위(R03 결정) |
