# R06. repository 저장 경로 개선

[전체 요구사항](../total_requirement.md) · 작업 브랜치: `volume-3/r06-save-flush` · PR 대상: `volume-3/main`

상태: 문서 준비. 트레이드오프 문답 전이며 채택안은 없다. R03 병합이 필수 선행 조건이다.
기준 항목: 분석 항목 4(repository 저장마다 재조회·`saveAndFlush`).

## 1. 목적

도메인 모델과 JPA 엔티티를 분리한 구조는 유지하면서, 저장할 때마다 엔티티를 다시 조회하고 즉시 flush하는 비용을 줄인다.

## 2. 현재 동작과 변경점

| 구분 | 현재 코드에서 확인한 동작 | 요구하는 변경 |
|---|---|---|
| 브랜드 저장 | `infrastructure/persistence/mall/repository/BrandRepositoryImpl.save`가 브랜드 `findById` 후, 연결 상품마다 `findById` + `saveAndFlush` | 상품 수에 비례하는 조회·flush 횟수 감소 |
| 주문 저장 | `infrastructure/persistence/ordering/repository/OrderRepositoryImpl.save`가 기존 주문을 `join fetch` 쿼리로 다시 조회한 뒤 `saveAndFlush` | 이미 읽은 엔티티의 재조회 제거. 주문 기록 id·생성 시각 반영 필요성 검토 |
| 기타 repository | 상품·지갑·사용 기록 등 같은 패턴 사용 여부 | 구현 시 전체 목록을 확인해 같은 기준 적용 |

## 3. 포함·제외 범위

**포함**

- repository 구현의 재조회·flush 시점 변경과 공통 기준 정리.
- 브랜드 일괄 삭제·주문 확정 등 저장 경로의 쿼리 수 전후 비교.
- R01·R02 롤백·동시성 테스트 회귀 확인.

**제외**

- 도메인 모델과 JPA 엔티티의 통합.
- bulk UPDATE로 삭제 판단을 SQL에 옮기는 방식([R01 저장 단위](../../week3/r01-brand-bulk-delete/trade_off/04-save-unit.md)에서 미채택).
- 주문 확정 잠금 방식 변경(R05).

## 4. 규칙

- 도메인 계층은 Spring·JPA 타입에 의존하지 않는다(ArchUnit 규칙 유지).
- 저장 결과로 반환하는 도메인 객체는 id·생성 시각 등 DB가 채우는 값을 기존과 같이 포함한다.
- flush를 늦추더라도 제약 위반·롤백 결과는 기존과 같아야 한다. 오류가 드러나는 시점이 바뀌는 경우 `result.md`에 기록한다.
- 같은 트랜잭션 안에서 JDBC로 변경을 읽는 코드가 없어야 한다(R03 완료 조건).

## 5. 시나리오와 기대 결과

| 시나리오 | 사전 상태 | 실행 | 기대 결과 | 유지되어야 할 상태 |
|---|---|---|---|---|
| 브랜드 일괄 삭제 | 상품 N개를 가진 브랜드 | 삭제 | 브랜드·상품 모두 삭제 상태, 조회·flush 횟수가 N에 비례하지 않음 | R01 결과 계약 |
| 삭제 중 실패 | 일부 상품 반영 후 저장 경계에서 오류 | 삭제 | 전체 롤백 | R01 롤백 테스트 기대값 |
| 주문 확정 저장 | 확정 가능한 주문 | 확정 | 주문 기록 id·생성 시각이 결과에 포함 | R02 결과 계약 |
| 신규 저장 | 새 브랜드·상품·주문 | 생성 | id가 채워진 도메인 반환 | 기존 생성 API 응답 |

## 6. 완료 조건

- 대표 저장 경로의 변경 전후 실행 SQL·쿼리 수를 `result.md`에 기록한다.
- R01·R02 관련 테스트와 기존 저장 테스트가 기대값 변경 없이 통과한다.
- `./gradlew :apps:commerce-api:check`가 통과한다.

## 7. 미정 사항

트레이드오프 문답으로 결정한다. 아래는 후보 목록이며 채택을 의미하지 않는다.

- flush 시점: 저장마다 즉시 / 트랜잭션 종료 시 / IDENTITY 채번이 필요한 경우만 즉시.
- 재조회 방식: 커스텀 `@Query` 재조회 유지 / 영속성 컨텍스트 1차 캐시를 쓰는 `findById`·`em.find` / 로드한 엔티티를 매퍼에서 추적.
- 브랜드 저장에서 상품 엔티티를 한 번에 로드하는 방식(`IN` 조회 등).
