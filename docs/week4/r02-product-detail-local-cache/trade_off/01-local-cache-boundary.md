# 01 로컬 캐시와 변경 경계

## 사용자 선택

처음에는 LinkedHashMap 기반 LRU를 선택했지만 [참고 글](https://agongstory.tistory.com/116)을 검토한 뒤 Caffeine으로 변경했다.
사용자는 전체 상세 응답 캐시, 모든 영향 쓰기의 commit 후 무효화·늦은 채움 방지, JMeter CLI 실제 측정까지 승인했다.

제출 시 사용자는 Caffeine 로컬 캐시를 이번 구현의 최종 선택으로 확정했다. Redis는 이번에 도입하지 않는다.
단일 JVM에서 반복하는 상품 상세 조회의 DB 호출을 줄이는 범위로 선택했다.

Caffeine은 순수 LRU가 아니라 [W-TinyLFU](https://github.com/ben-manes/caffeine/wiki/Efficiency)를 사용한다.
용량 기반 교체와 [expireAfterWrite](https://github.com/ben-manes/caffeine/wiki/Eviction)를 사용하며,
만료된 항목의 논리적 사용 중단과 실제 메모리 정리 시점은 구분한다. 용량 테스트는 유지보수 후 확인한다.
기존 Spring Boot BOM이 관리하는 Caffeine 의존성을 사용한다.

## 선택 근거와 비용

[실제 결과](../result.md)에서 같은 JAR의 Caffeine OFF/ON을 비교해 DB 호출 감소를 확인했다.
애플리케이션 메모리에 상세 응답을 보관하므로 별도 캐시 서버를 설치·운영할 필요가 없고,
별도 캐시 인프라 운영 비용을 추가하지 않는다. 애플리케이션 메모리와 무효화 처리 비용은 남는다.

이 선택은 여러 JVM 사이의 캐시 공유나 외부 SQL 변경 전파를 지원하지 않는다.
Redis 성능과 직접 비교한 실험도 없다. 이번 측정으로 확인한 범위는 단일 JVM의 반복 상세 조회다.

## 경계 선택

- QueryDao 데코레이터에서 Caffeine API를 명시적으로 사용한다. 애노테이션만으로 TX 순서와 늦은 채움이 해결됐다고 가정하지 않는다.
- 데코레이터는 `@Primary`이며 원본 DAO를 명시적 qualifier로 주입해 자기 주입·프록시 우회를 막는다.
- 기존 TX 내부에서는 우회한다. 미커밋 조회·과거 snapshot을 전역 로컬 캐시에 게시하지 않는다.
- 불변 View만 저장한다. 관리형 JPA 엔티티·HTTP 포장·사용자별 정보를 저장하지 않는다.
- 기본 OFF, 용량 1000개, TTL 30초다. OFF/ON은 동일 JAR의 설정만 바꿔 비교한다.
- 기존 목록 COUNT 캐시는 별도 정책이며 이 작업으로 변경하지 않는다.

## 무효화와 늦은 채움

application 이벤트는 기존 쓰기 TX에서 발행한다. infrastructure의 동기 AFTER_COMMIT 리스너가 무효화한다.
특히 주문 재고는 파사드 TX, 좋아요 수는 관계 commit뿐 아니라 flush·전체 재집계 commit 뒤에도 처리한다.
브랜드 bulk 삭제는 상품 엔티티 콜백으로 감지하지 않고 브랜드 이벤트를 처리한다.

로컬 캐시에 단일 무효화 세대를 둔다. lookup과 세대 캡처를 잠금 안에서 수행하고 원본은 잠금 밖에서 읽는다.
재진입 후 세대가 같을 때만 저장한다. 무효화는 같은 잠금 안에서 세대를 올리고 항목을 제거한다.
브랜드 캐시 항목이 0개여도 세대를 올려 진행 중인 miss의 옛 브랜드 결과를 막는다.
관계없는 상품 변경으로도 진행 중인 조회의 저장이 생략될 수 있어 안전성 대신 추가 miss 비용을 감수한다.
이미 유효한 다른 상품 캐시는 유지한다. 동일 키의 동시 miss 병합은 이 단계에서 추가하지 않는다.

## 측정과 한계

단일 JVM의 애플리케이션 쓰기만 즉시 전파한다. 외부 SQL 변경과 여러 JVM 사이의 캐시 전파는 지원하지 않는다.
주문 판단은 기존 DB 규칙을 사용한다. TTL만으로 모든 변경·장애의 전역 최신성 상한을 주장하지 않는다.

기존 API를 중단하지 않고 전용 API 18081/관리 포트 18082에서 100개 고정 활성 상품을 순환 조회한다.
OFF/ON × 1명/10명 × 2회, 조건별 워밍업 20초/본 측정 60초/램프업 5초다.
1회차 OFF→ON, 2회차 ON→OFF로 시간 순서 영향을 완화하지만 DB·OS·JIT 상태와 단일 장비 편차는 남는다.
캐시 통계와 DB load 수는 기존 Prometheus 경로로 관측하고 SQL 로그는 별도 검증 때만 활성화한다.
