## 이번 증분의 목표와 범위

2026-10-16 사용자가 다음 개선 진행과 추가 설명 기록을 요청했다. 직전 측정에서 초당 좋아요 변경 2회/10회에 같은 버전의 추가 계산이 40/105회 발생했고, 별도 8명 동시 조회는 3회 모두 같은 목록을 8번 계산했다. 이번 증분은 이 중복 원본 조회를 줄이는 것이다. 사용자 후속 답변으로 **다른 요청의 계산은 최대 500ms 기다리고 초과하면 기존 DB 조회로 우회**하기로 했다.

Redis + DB 버전 방식, TTL 60초, 캐시 대상·payload·최신성·삭제 보호, 기존 업무 트랜잭션·비관적 잠금은 유지한다. 좋아요 카운터·인덱스·SQL 재작성·Redis 분산 락·백그라운드 갱신은 범위 밖이다.

### 처리 순서와 책임

1. `ProductQueryService`가 기존 비대상/OFF/외부 TX 우회를 유지하고 DB 버전을 확인한다.
2. 최초 Redis GET이 hit이면 반환한다. GET 오류는 기존처럼 DB 직접 조회하고 추가 SET을 하지 않는다.
3. miss이면 `ProductListSingleFlight`에서 해당 버전의 리더를 정한다. 합치기 OFF면 종전 snapshot/SET 경로다.
4. 리더만 Redis를 재확인하고 여전히 비었으면 기존 `ProductListReader`의 RR snapshot을 읽는다. 실제 snapshot 버전으로 Redis에 저장한다.
5. 대기자는 같은 결과를 공유하거나 대기 초과/상한 초과 시 DB로 우회한다. 대기 중 DB 연결·트랜잭션·업무 잠금을 보유하지 않는다.
6. 리더의 정상·예외 종료 모두 자기 future만 조건부 제거하고 슬롯을 반환한다. 한 대기자의 timeout은 공유 future를 취소하거나 제거하지 않는다.

DB 실패는 원래 실패 의미를 전파한다. SET 실패는 성공한 DB 결과를 유지한다. 대기자 인터럽트는 플래그를 복구하고 기술 실패로 종료하며 추가 DB 작업을 시작하지 않는다.

초기 lookup 7의 리더가 실제 snapshot 8을 읽을 수 있다. 이 경우 7그룹에 snapshot 8을 공유하고 Redis에는 8키로 저장한다. 독립적인 8그룹과 계산이 겹칠 수 있어 **모든 부하에서 실제 snapshot 버전당 계산이 반드시 1회라고 보장하지 않는다.** 500ms도 follower 대기 상한일 뿐 리더 DB SQL이나 API 전체 실행 상한이 아니다.

진행 중 64개 상한은 리더의 map/슬롯 수만 제한한다. 대기자 수나 DB 우회 동시성 전체의 상한은 아니며, SQL 자체가 오래 걸리는 경우 해당 리더 항목은 실제 종료 때까지 남는다. 이번 증분은 DB 부하 제한기나 분산 single-flight를 구현한 것이 아니다.

### 비교 방법

- 같은 MySQL 8.0·Redis 7.4, 상품 10,000개·좋아요 46,955개·노출 상품 9,812개의 재현 seed를 사용한다.
- DB-only / 기존 캐시 / 요청 합치기를 추가한 캐시를 같은 실행에서 비교한다. 모든 모드는 DB 버전 쓰기를 유지한다.
- 각 조건은 10회 준비 조회 후 50ms 간격 조회 200회, 좋아요 변경 0/20/100회다. 읽기 worker 4개·writer 1개로 실행 순서를 뒤집은 두 라운드, 총 조회 3,600회·쓰기 720회다.
- 별도로 고정된 새 버전에 8명이 동시 출발하는 burst를 OFF/ON 각 3회, 총 48회 조회한다. 서버 안에 인위적인 지연이나 barrier는 넣지 않는다.
- 최초 GET 기준 hit율과 리더 재확인, 결과 공유, snapshot/SET 및 DB 직접 우회 비용을 분리한다. 정상 timeout도 집계 수·지연에 포함하며 성능 합격선을 만들지 않는다.
- 전체 DTO·정렬·페이지·반환 버전, 실제 SQL 수·쓰기 버전 증가·최종 DB, 마지막 별도 변경 후 최신 응답을 검사한다. 시간은 계측 비용 포함 로컬 관찰값이며 운영 최대 처리량·최적 TTL의 증거가 아니다.

혼합 실험의 lookup→snapshot 버전 변경은 모두 0회였다. 이 관찰이 실제 운영에서 버전 전환 중 중복이 불가능하다는 증명은 아니다. 자연 부하에서 timeout·상한 우회가 관찰되지 않았으므로 그 경계는 결정적 단위 테스트로 별도 검증했다.

고정된 새 버전의 8명 burst는 3회 모두 **snapshot·SET·비싼 집계 8→1회**, 추가 계산 7→0회였다. 개선 경로는 리더 1명·공유 7명, DB 우회 0회다. 회차별 HTTP p95는 **111.20→51.62ms, 99.32→52.99ms, 94.62→51.33ms**였다. 표본이 회차별 8개라 이 p95는 사실상 최댓값이며 운영 p95로 일반화하지 않는다.

### 해석과 남은 일

1. **중복 집계 감소는 확인했다.** 초당 2회 변경에서 집계 50%, 10회에서 약 33% 감소했다. hit율은 오히려 소폭 낮지만 miss가 결과를 공유하므로 실제 원본 비용은 줄었다. 재확인 7회도 불필요한 계산을 피했다.
2. **모든 조건이 빨라진 것은 아니다.** 초당 10회 변경의 p95는 약 11.5% 줄었지만, 2회에서는 약 2.4ms 늘었다. 2회 조건의 리더 snapshot/집계 시간도 늘었다. 기존 miss 전체와 개선 후 리더는 표본 구성이 다르므로 이 평균만으로 SQL이 느려진 원인을 단정하지 않는다. 공유 대기나 새로운 쓰기 락 때문이라고 단정하지도 않는다. 쓰기 p95 역시 개선되지 않았다. 단일 로컬 실행의 두 라운드만으로 원인을 확정할 수 없다.
3. **필요한 첫 집계는 남는다.** 10회 변경에서도 200개 버전의 최초 집계 200회는 필요했고 SELECT는 DB-only의 800회보다 많은 1,000회다. hit의 버전 조회와 리더의 재확인 GET 비용도 남는다. 중복 계산을 줄였다고 캐시가 모든 부하에서 최선이라고 판단하지 않는다.
4. 당시 다음 후보였던 **첫 miss의 좋아요순 집계 SQL·실행계획**은 [좁은 순위 집계 TDD](product-like-ranking-tdd-log.md)에서 개선·검증했다. [TTL 다중 주기·키 수·메모리 비교](product-list-cache-ttl-memory.md) 후 2026-10-16 사용자 승인으로 이번 과제는 TTL 60초 유지·서버 시작 워밍 미도입을 선택했다. 브랜드 필터 없는 좋아요순 첫 페이지를 요청 시 채우는 [정책 결정](../week2/commerce-policy-decisions.md#w4-캐시-설계의-선택과-미정-질문)이며, 필수 작업의 미완료 표시가 아니다. 여러 서버의 합치기·실제 홈 요청 비중·운영 최적값은 별도 검토 대상이고, 좋아요 수 별도 저장·payload 분리나 신선도 정책 변경은 도입하지 않았다.
