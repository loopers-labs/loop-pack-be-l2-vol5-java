# 옵티마이저는 왜 조인 순서를 바꿨나 (브랜드 + likes_desc)

`product-query-brand-index.md` 에서 `(brand_id, deleted_at)` 인덱스를 더한 뒤 큰 브랜드의 좋아요순 조회가 약 41ms → 6ms 가 됐다. 그때는 실행 계획의 `filtered` 값만 보고 원인을 추정했다. 이 문서는 **옵티마이저 트레이스로 그 추정을 확인하고, 불리한 분포에서도 같은 일이 생기는지** 잰 결과다.

- 실험 코드: `apps/commerce-api/src/test/java/com/loopers/experiment/OptimizerPlanExperiment.java`
- 실행: `RUN_EXPERIMENT=true ./gradlew :apps:commerce-api:test --tests '*OptimizerPlanExperiment'`
- 원본 출력: `build/experiment/optimizer-plan.md`, 트레이스 전문 `build/experiment/optimizer-trace/*.json`
- 실행일: 2026-10-16, MySQL 8.0 Testcontainers, **한 번 실행한 결과**

## 1. 실험 방법

| 항목 | 내용 |
|---|---|
| 데이터 | 기본 seed + 큰 브랜드 + 중간 브랜드 seed (상품 33,000개, `product-query-seed.md` 5절) |
| 장면 | 브랜드 7(94개) · 101(18,824개, 좋아요 고르게) · **102(2,823개, 좋아요 0 · 1개뿐)** 의 likes_desc 첫 페이지 |
| 인덱스 전후 | 같은 DB 에서 `(brand_id, deleted_at)` 인덱스를 떼고(외래 키를 위해 `brand_id` 단일 인덱스를 둠) 붙여 비교 |
| 강제 비교 | 인덱스 후 상태에서 두 조인 순서를 `JOIN_ORDER` 힌트로 각각 강제. 실행 계획으로 의도한 테이블에서 출발하는지 확인 |
| 기록 | 실행 계획 · `EXPLAIN ANALYZE` · 옵티마이저 트레이스 · SQL 만 50회 실행한 지연. 계획이 달라도 결과 순서가 같은지 매번 확인 |

브랜드 102 는 **필터(브랜드)와 정렬 키(좋아요 수)가 연관된 분포**다. 이 브랜드의 상품은 모두 좋아요 순서의 맨 뒤에 몰려 있어, 좋아요 순서로 훑으면 다른 브랜드 상품 약 2.4만 개를 먼저 지나야 한다.

두 조인 순서는 다음과 같다.

| 이름 | 순서 | 특징 |
|---|---|---|
| 브랜드 먼저 | 상품(브랜드 인덱스) → 좋아요 수(PK) → 정렬 → 20개 | 브랜드 상품 수만큼 읽고 정렬한다 |
| 좋아요 순서 | 좋아요 수 인덱스를 큰 순서로 → 상품(PK)에서 브랜드 · 삭제 확인 → 20개 차면 멈춤 | 정렬이 없고 일찍 멈출 수 있지만, 맞는 상품이 드물면 오래 훑는다 |

## 2. 결과 (SQL p50, ms)

| 브랜드 | 인덱스 전 (선택된 계획) | 인덱스 후 (선택된 계획) | 강제: 좋아요 순서 | 강제: 브랜드 먼저 |
|---|---|---|---|---|
| 7 (94개) | 1.06 (브랜드 먼저) | 0.81 (브랜드 먼저) | 4.91 | 0.87 |
| 101 (18,824개) | **27.85 (브랜드 먼저)** | **0.64 (좋아요 순서)** | 0.54 | 26.43 |
| 102 (2,823개, 좋아요 0 · 1) | 5.35 (브랜드 먼저) | 4.59 (브랜드 먼저) | **16.84** | 4.57 |

인덱스 후에는 세 브랜드 모두 옵티마이저가 두 계획 중 실제로 빠른 쪽을 골랐다. 결과 순서는 모든 장면에서 같았다.

## 3. 트레이스가 보여 준 비교

옵티마이저는 조인 순서마다 **"끝까지 조인했을 때의 비용 + 정렬이 필요하면 정렬 비용"** 을 추정해 비교한다(트레이스의 `considered_execution_plans`, `sort_cost`). 비용 단위는 옵티마이저 내부 값이다.

| 장면 | 브랜드 먼저 (추정 행 · 비용) | 좋아요 순서 (비용) | 선택 |
|---|---|---|---|
| 브랜드 101 · 인덱스 전 | 1,655행, 조인 3,358 + 정렬 1,655 = **5,013** | 28,949 | 브랜드 먼저 |
| 브랜드 101 · 인덱스 후 | 16,128행, 조인 13,562 + 정렬 16,128 = **29,690** | **28,360** | 좋아요 순서 |
| 브랜드 102 · 인덱스 후 | 2,823행, 조인 3,370 + 정렬 2,823 = **6,193** | 32,932 (비용으로 탈락) | 브랜드 먼저 |

### 3.1 인덱스 전: 행 수를 11배 적게 추정했다
- 인덱스 전에는 `brand_id` 인덱스만 있어 `brand_id = 101` 은 16,553행으로 추정했다.
- `deleted_at is null` 에는 통계가 없어 **10%로 어림**했다(`filtered` 10.0).
- 그래서 브랜드 먼저의 결과를 **1,655행**으로 봤지만 실제는 **18,824행**이었다.
- 적게 본 만큼 조인 비용과 정렬 비용도 작게 나와(5,013), 좋아요 순서(28,949)보다 훨씬 싸 보였다. 실제로는 1.8만 행을 조인 · 정렬해 27.85ms 가 걸렸다.

### 3.2 인덱스 후: 추정이 맞아지자 비교가 뒤집혔다 — 단 4.5% 차이로
- `(brand_id, deleted_at)` 인덱스로 두 조건을 인덱스 범위로 함께 추정해 **16,128행**(실제 18,824에 가까움)이 됐다.
- 행 수가 10배 커지자 브랜드 먼저의 조인 · 정렬 비용이 29,690 으로 올라, 좋아요 순서(28,360)보다 **약 4.5% 비싸졌다.** 그래서 좋아요 순서가 선택됐다.
- 그런데 실제 차이는 4.5%가 아니라 **약 40배**(26.43ms vs 0.64ms)다. 좋아요 순서 계획은 22행만 읽고 멈췄는데, **이 "일찍 멈추는" 효과는 조인 순서 비교의 비용에 들어 있지 않았다.** 좋아요 순서의 28,360 은 좋아요 수 33,020행을 끝까지 훑는다고 보고 계산한 값이다.
- 트레이스의 `reconsidering_access_paths_for_index_ordering`(정렬을 피할 인덱스를 LIMIT 기준으로 다시 고려하는 단계)는 이미 좋아요 순서가 선택된 뒤에 "인덱스가 순서를 제공한다, 계획 변경 없음"으로만 나왔다.

### 3.3 브랜드 102: 함정을 피한 이유는 "보수적인 계산"
- 좋아요 순서의 비용을 끝까지 훑는 것으로 계산하므로(32,932), 맞는 상품이 드문 브랜드에서는 크게 비싸 보여 탈락했다.
- 실제로 좋아요 순서를 강제하면 좋아요 수 24,454행을 훑고 16.84ms 가 걸렸다(브랜드 먼저 4.59ms 의 약 3.7배).
- 옵티마이저가 이 브랜드의 좋아요 분포를 알아서 피한 것이 아니다. **일찍 멈추는 이득을 계산에 넣지 않는 방식 덕분**에 이번에는 맞는 쪽을 골랐다.

## 4. 앞선 설명을 고친다

`product-query-brand-index.md` 에서는 "실제에 가까운 행 수를 알게 되자, 좋아요 수 인덱스 순서로 읽다가 20개에서 멈추는 계획이 더 싸다고 판단했다"고 적었다. 트레이스로 보면 **절반만 맞다.**

- 맞은 것: 원인은 `deleted_at is null` 의 행 수 추정이 바뀐 것이다 (10% 어림 → 인덱스 범위 추정).
- 틀린 것: 옵티마이저는 "20개에서 멈춘다"를 계산에 넣지 않았다. 브랜드 먼저 계획의 추정 비용이 커져 **끝까지 훑는 좋아요 순서보다 근소하게 비싸졌을 뿐**이다. 41ms → 6ms 의 대부분은 계산에 없던 조기 종료에서 나왔다.

## 5. 판단

1. **이 개선은 보장된 성능이 아니다 (판단 유지, 근거 보강).** 두 계획의 추정 비용 차이는 4.5%였다. 브랜드 비율, 삭제 비율, 통계 갱신 시점이 조금만 달라져도 다시 브랜드 먼저(약 26ms)로 돌아갈 수 있다.
2. **힌트로 계획을 고정하지 않는다.** 이 측정에서 브랜드마다 빠른 계획이 달랐다.
   - 좋아요 순서로 고정하면 브랜드 7 은 약 6배(4.91 vs 0.81ms), 브랜드 102 는 약 3.7배 느려진다.
   - 브랜드 먼저로 고정하면 브랜드 101 이 약 40배 느려진다.
3. **추정을 정확하게 해 주는 인덱스가 옵티마이저의 판단을 바꿨다.** 이번 측정 범위에서는 인덱스 후의 선택이 세 브랜드 모두 최선이었다. 다만 그 비교도 LIMIT 의 조기 종료를 반영하지 않으므로, 계획이 바뀌었을 때 알아챌 수 있도록 운영에서는 느린 쿼리 · 실행 계획 변화를 관찰하는 쪽이 맞다고 본다(이번에는 구현하지 않음).

## 6. 한계

- 한 번 실행한 결과이며, 동시 요청이 없는 상태의 SQL 지연이다.
- 브랜드 비율이 경계(두 계획의 추정 비용이 같아지는 지점)를 넘나드는 데이터는 따로 만들지 않았다.
- MySQL 8.0 기준이다. 비용 모델은 버전에 따라 다를 수 있다.
- 비용 숫자는 옵티마이저 내부 단위라 실제 시간과 비례하지 않는다.
