# W4 캐시 읽기·좋아요 변경 혼합 실험

[캐시 구현 기록](product-list-cache-tdd-log.md) · [캐시 설계](../week2/commerce-policy-decisions.md#w4-캐시-설계의-선택과-미정-질문)

이 문서는 11:41 전체 검사 당시의 첫 혼합 실험을 보존한다. 이후 같은 테스트에 [버전별 중복 채움·시간 계측](product-list-cache-diagnostics.md), [요청 합치기 전후 비교](product-list-single-flight-tdd-log.md), [좁은 좋아요 순위 집계 후 재검사](product-like-ranking-tdd-log.md)를 추가했다. **현재 테스트의 생성 파일은 `apps/commerce-api/build/reports/week4/product-list-single-flight-comparison.json`**이다. `product-list-cache-diagnostics.json`은 중간 진단 증분 당시의 출력이며, 아래 고정 증거·SQL 2/4/1회·과거 수치는 덮어쓰지 않는다. 현재 비어 있지 않은 무필터 좋아요순의 DB-only/직접 계산 miss/hit는 3/5/1회다.

## 목표와 사전 조건

2026-10-16 사용자가 승인한 다음 증분이다. TTL은 **60초로 고정**하고, 캐시 읽기 경로 OFF/ON에서 조회와 좋아요 변경이 섞일 때의 정확성·비용을 비교한다. 운영 코드·캐시 기본 설정·업무 계약·트랜잭션·락은 바꾸지 않는다. OFF도 DB 버전 증가는 수행하므로 **DB 버전 도입 전후 비용 비교는 아니다.**

새 `ProductListCacheMixedLoadIntegrationTest`는 테스트 소유 MySQL·Redis와 수동 001~008 SQL, 기존 1만 상품 seed를 사용한다. `RequestSqlProbe`는 요청별 실제 JDBC 실행을 구분하는 테스트 도구다. 도구 단위 테스트에서 관찰·예외 전달·동시 요청 분리를 검증하고 실제 HTTP 측정에 연결한다. 이미 구현된 서비스의 측정이므로 업무 Red를 인위적으로 만들지 않는다.

| 조건 | 고정값·검증 방법 |
| --- | --- |
| 조회 | 브랜드 필터 없는 `GET /api/v1/products?sort=likes_desc&page=0&size=20` |

고정 지연·hit율을 합격선으로 두지 않는다. 모든 예정 요청을 끝내고 최종 상태를 확인한 뒤 실행 증거를 저장한다. Future·executor·HTTP 요청은 유한 시간 제한을 두며 테스트 소유 자원만 정리한다.

## 해석의 경계

- 읽기 중 변경이 커밋될 수 있으므로 두 DTO 중 하나라는 검사는 일관성 증거다. 매 응답의 최신성 증명은 아니며 기존 결정적 경합 테스트와 마지막 쓰기 후 조회로 보완한다.
- 쓰기 worker가 1개이므로 여러 쓰기 간 버전 행 경합·처리량 시험은 아니다.
- TTL 만료 여러 주기·5/30/60초 비교는 이 당시 실험의 범위가 아니며, 이후 [키 수·메모리와 함께 측정](product-list-cache-ttl-memory.md)을 완료했다. 메모리 제한 하의 퇴거 부하와 운영 최적 TTL은 여전히 검증 범위가 아니다.
- miss 이유는 빈 GET만 보고 추정하지 않는다. 이번에는 통제한 초기 채움·버전 변화·기간을 함께 기록한다.
- 실제 홈 호출·접근 분포는 미확인이다. 결과를 모든 API나 운영 전체 성능으로 일반화하지 않는다.

## 테스트 작성·실행 과정

- `RequestSqlProbeTest`: no-op 구현에서 8개 중 7개 실패(Red), 실제 실행·예외·요청 ID·동시 수집·세션 경계를 구현한 뒤 8개 통과(Green). 최초 method reference의 컴파일 모호성은 도구 테스트 작성 오류로 수정했으며 업무 Red로 세지 않는다.
- 혼합 테스트는 이미 구현된 서비스에 대한 후속 측정이다. 같은 데이터·계약을 유지하며 테스트를 통과시키기 위한 생산 코드 변경은 하지 않는다.
- 첫 통합 실행은 Docker가 꺼져 초기화에 실패했다. 이때 측정은 시작되지 않았으며 성능·정확성 결과로 쓰지 않는다.
- 초기 TTL이 준비 구간과 실제 측정 기간보다 길었는지 검사한다. 실행 시작 때 보고서를 `completed=false`로 초기화하고 성공·실패와 시각을 저장해 과거 성공 파일을 이번 실행으로 오인하지 않는다.

## 실행 결과

**혼합 부하 실험을 두 번 완료했다.** 아래 수치는 전체 검사 안에서 재실행한 **2026-10-16 11:37:48~11:39:57 KST**의 보고서(`completed=true`)다. 첫 성공 실행은 11:34:14~11:36:23 KST였으며, 서로 다른 실행의 분위수를 섞지 않는다.

환경은 Java 21.0.10·MySQL 8.0.46·Redis 7.4 이미지·로컬 Docker Engine 28.5.2다. 수동 스키마 001~008과 동일 seed를 사용했다. 각 조건·모드의 두 라운드 원시 조회 **400개를 합쳐** nearest-rank p50/p95를 다시 계산했다. 구간별 분위수의 평균이 아니다. 총 측정 조회 **2,400개**, 실제 좋아요 변경 **480개**는 모두 HTTP 200·정확성 검사 통과이며 SQL 실패·Redis invalid/GET 오류/SET 오류는 0이다. 준비·정리·마지막 별도 변경은 이 표본에 포함하지 않는다.

### 조회 비용: 좋아진 부분과 나빠진 부분

| 좋아요 변경 빈도 | ON hit / miss | hit율 | HTTP p50: OFF → ON | HTTP p95: OFF → ON | 목록 집계 횟수: OFF → ON | SELECT 횟수: OFF → ON |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 없음 | 400 / 0 | 100% | 49.68 → 10.03ms | 59.76 → 14.76ms | 400 → 0 | 800 → 400 |
| 초당 2회 | 321 / 79 | 80.25% | 49.98 → 9.19ms | 53.21 → 89.43ms | 400 → 79 | 800 → 637 |
| 초당 10회 | 103 / 297 | 25.75% | 50.15 → 52.53ms | 59.46 → 65.81ms | 400 → 297 | 800 → 1,291 |

- **변경 없음:** 미리 채운 결과를 재사용하여 중앙값·p95·DB 집계를 모두 줄였다.
- **초당 2회 변경:** 중앙값과 비싼 집계는 줄었지만 p95는 나빠졌다. hit율 80%만 보고 모든 요청이 빨라졌다고 평가할 수 없다.
- **초당 10회 변경:** 중앙값·p95가 모두 나빠지고 SELECT는 61.4% 증가했다. 집계가 줄어도 hit의 버전 SELECT와 miss의 4회 SELECT를 합친 호출 부담은 늘었다. 관측한 조회 지연 기준으로 개선이 없었으며, 세부 지연 원인까지 분리해 증명한 것은 아니다.

각 조회의 SQL도 검증했다. OFF는 SELECT 2회·목록 집계 1회, ON hit는 SELECT 1회·집계 0회, ON miss는 SELECT 4회·집계 1회다. 관찰된 요청 ID 집합이 실제 표본 ID 집합과 같고, 각 쓰기의 버전 UPSERT도 정확히 1회다.

### 쓰기 지연·요청 공급 확인

| 변경 빈도 | 쓰기 HTTP p50: OFF → ON | 쓰기 HTTP p95: OFF → ON | 버전 SQL execute p95: OFF → ON |
| --- | ---: | ---: | ---: |
| 초당 2회 | 10.95 → 26.37ms | 15.03 → 35.96ms | 0.355 → 1.441ms |
| 초당 10회 | 10.34 → 10.30ms | 13.74 → 15.60ms | 0.387 → 0.480ms |

OFF도 같은 버전 쓰기를 수행한다. 위 차이를 DB 버전 도입 전후 비용이나 순수 잠금 대기로 해석하지 않는다. writer가 1개이므로 여러 쓰기의 공통 행 경합을 측정한 것도 아니다. 관찰된 쓰기 지연 증가의 세부 원인은 별도 프로파일링 없이 단정하지 않는다.

조회의 예정 도착→완료 p95는 변경 없음에서 63.55→19.01ms, 초당 2회에서 57.53→91.19ms, 초당 10회에서 60.24→68.22ms다. 읽기 시작 지연 p95는 모든 조건에서 5.03~5.10ms, 구간별 실제 완료 조회율은 19.973~20.080회/초였다. 고정 공급 부하를 처리한 지연 비교이며 **최대 처리량 시험이 아니다.**

### TTL과 다음 판단

모든 ON 구간은 시작 키의 남은 TTL보다 짧게 끝났다. 이번 miss를 TTL 만료 문제로 보고 TTL만 늘리는 것은 맞지 않는다. 현재 구조에서는 변경 커밋으로 버전이 바뀌면 옛 키의 TTL이 남아 있어도 새 버전 키를 조회한다. 당시에는 같은 버전의 중복 채움 여부를 구분할 버전별 lookup·store 추적이 더 필요했고, 이 진단은 다음 증분에서 수행했다.

이번 결과로 TTL·신선도 계약·캐시 적용 범위는 바꾸지 않았다. 당시 후속 과제였던 miss 중복 채움과 원본 집계 비용은 [12:07 후속 검사](product-list-cache-diagnostics.md)에서 측정했고, 이후 [한 JVM의 요청 합치기](product-list-single-flight-tdd-log.md)와 [좁은 순위 집계](product-like-ranking-tdd-log.md)를 구현·검증했다. [TTL 다중 만료 주기·키 수·메모리 비교](product-list-cache-ttl-memory.md)도 완료했다. 실제 홈 호출·운영 읽기/쓰기 비율, 운영 다중 writer 부하, 여러 서버의 중복 계산 제어는 미확인·미구현이며 payload 분리와 워밍도 도입하지 않았다. 이들을 과제의 새 필수 합격선으로 만들지 않는다.

이 실험은 고정 간격 HTTP·동시 읽기·요청별 SQL 계측을 포함한다. 이전 순차 DB-only/miss/hit 측정의 약 3ms hit와 직접 비교해 성능 회귀라고 단정하지 않는다. 위 표의 동일 실험 OFF/ON끼리 비교한다.

## 실행·복구 이력과 증거

- 최초 도구 단위 테스트 8개·ArchUnit 1개·관련 Checkstyle은 통과했지만, 실제 혼합 테스트는 Docker 연결 불가로 Spring 초기화에 실패했다.
- Docker 앱 실행 후 backend가 `exit status 2`로 종료했고, 공식 재시작도 잔류 UI 프로세스 때문에 timeout이었다. 이후 **사용자 승인으로 확인된 Docker Desktop/Helper 프로세스 4개만 강제 종료·재실행**하여 엔진을 복구했다. 기존 데이터·볼륨 삭제, Docker 초기화, prune은 하지 않았다.
- 복구 뒤 측정 도구 8개와 혼합 통합 테스트 1개가 통과했다. 생산 코드·설정·기존 기대값을 변경하지 않고 실행했다.
- 전체 회귀도 **11:41 KST, 76개 스위트·696개 테스트 통과**, 실패·오류·skip 0, Checkstyle XML 11개·위반 0, ArchUnit 통과, **BUILD SUCCESSFUL·종료 코드 0**으로 완료했다. 신규 도구 8개와 혼합 테스트 1개를 포함한다. [최신 검사](../week2/commerce-completion-checklist.md#최신-통합-검사)와 고정 증거 JSON의 스위트별 집계를 대조할 수 있다.

```shell
./gradlew :apps:commerce-api:test --tests '*RequestSqlProbeTest' --tests '*ProductListCacheMixedLoadIntegrationTest' --console=plain
./gradlew :apps:commerce-api:check --rerun-tasks --console=plain
```

당시 생성 보고서는 `apps/commerce-api/build/reports/week4/product-list-cache-mixed-load.json`이었다. 12개 구간의 요청별 원시 표본·SQL 템플릿·지표·최종 상태 검사는 [고정 증거 JSON](evidence/product-list-cache-mixed-load-2026-10-16.json)에 보존한다. 현재 테스트는 문서 첫머리에 적은 후속 비교 파일을 생성하므로 과거 실행 확인에는 이 고정 증거를 사용한다. Spring 초기화 자체가 실패하면 이전 생성 파일이 남을 수 있으므로 `completed=true`뿐 아니라 보고서 시각과 해당 실행의 테스트 XML도 함께 확인한다. 최신 전체 검사 상태는 [완료 체크리스트](../week2/commerce-completion-checklist.md#최신-통합-검사)를 따른다.
