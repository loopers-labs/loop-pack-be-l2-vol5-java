# 상품 조회 쿼리 개선 기록

| 쿼리 | 핵심 판단 |
| --- | --- |
| [좋아요순](01-likes.md) | 상품 행의 쓰기 경합·카운트 정합성 관리 부담을 피하려고 비정규화 대신 조회 시 집계와 조인 순서 개선을 선택했다. |
| [최신순](02-latest.md) | 인덱스를 사용해도 100만 행을 읽었다. 필터 뒤에 정렬 순서를 배치해 21행에서 멈추게 했다. |
| [가격순](03-price.md) | 최신순 인덱스로는 가격 정렬을 제거할 수 없어 가격순 전용 인덱스를 추가했다. |
| [목록 N+1 개선](04-n-plus-one.md) | 상품별 부가 조회를 묶어 SQL과 서버 내부 반복 처리 비용을 줄였다. 무필터 좋아요순 20개 기준 SQL 63 → 6회. |

## 측정 기준

2026-10-14 서울 EC2, 상품 100만 개·좋아요 69만 개 기준이다. 기본 요청은 `GET /api/v1/products?sort={sort}&page=0&size=20`. 브랜드 1은 상품 5,000개, 브랜드 601은 333개다.

API 시간은 순차 3회 평균이다. 최신순·가격순·브랜드별 좋아요순은 워밍업 3회, N+1 비교는 5회 후 측정했다. 좋아요순 최초 측정에는 배포 직후 요청이 포함되어 단계 간 조건이 완전히 같지는 않다. 현재 revision 캐시가 포함된 API의 성능값은 아니다.

일반 EXPLAIN은 로컬 MySQL 8.0.46에서 당시 쿼리를 재구성한 기록이고, EC2 EXPLAIN ANALYZE와 별도 실행이다. `experiments/` 원본 링크는 Git 추적에서 제외한 로컬 자료이며, 제출용 핵심 계획·수치·판단은 각 문서에 담았다.
