# 상품 (brand_id, deleted_at) 인덱스 적용 결과

`product-query-like-count.md` 4절에서 "동기화 책임 없이 시도할 수 있는 후보"로 남긴 인덱스의 측정이다. 비교 대상은 같은 문서의 "후" 값이다.

- 실행일: 2026-10-15, 같은 실험 코드 · 같은 seed(큰 브랜드 포함), **한 번 실행한 결과**
- 결과: 아홉 장면 모두 응답이 기대 결과와 일치. 전체 회귀(`:apps:commerce-api:check`) 테스트 272건 실패 0

## 1. 변경

```java
@Table(name = "product", indexes = @Index(name = "idx_product_brand_deleted", columnList = "brand_id, deleted_at"))
```

- 고객 조회의 조건(`brand_id = ? and deleted_at is null`)과 같은 순서다. 보조 인덱스에는 PK가 들어 있어 `count(p.id)` 를 인덱스만으로 센다.
- `brand_id` 가 맨 앞이라 MySQL이 외래 키에도 이 인덱스를 쓴다. 전에 외래 키용으로 자동 생성되던 `brand_id` 단일 인덱스는 더 이상 만들어지지 않는다(실행 계획의 후보 키에서 사라짐). 상품 쓰기에 드는 인덱스 수는 그대로이고, 열이 하나 늘었다.

## 3. 실행 계획의 변화

브랜드 101 · likes_desc 는 **조인 순서가 뒤집혔다.** 좋아요 수 인덱스를 큰 순서로 읽으면서 상품을 PK로 찾아 브랜드 · 삭제 여부를 확인하고, 22행을 읽은 뒤 20개를 채워 멈춘다.

```
전: 브랜드 상품 18,824개 → 좋아요 수 행 조인 → 정렬 → 20개              (32.2ms)

후:
-> Limit: 20 row(s)                                                       (actual time=0.042)
    -> Nested loop inner join                                             (rows=20)
        -> Covering index scan on plc1_0 using idx_product_like_count_count (reverse)  (rows=22)
        -> Filter: ((p1_0.brand_id = 101) and (p1_0.deleted_at is null))
            -> Single-row index lookup on p1_0 using PRIMARY (id=plc1_0.product_id)  (loops=22)
```

브랜드 7 · likes_desc 는 그대로 브랜드 상품을 먼저 찾는다(94개). 찾는 인덱스만 FK 인덱스에서 새 인덱스로 바뀌었다.

건수 SQL 은 모든 브랜드 장면에서 `Covering index lookup` 으로 바뀌었다. 전체 목록의 건수는 `Covering index skip scan` 이다.

## 4. 관찰

1. **노린 효과인 건수 SQL은 줄었다.** 큰 브랜드에서 약 8~9ms → 약 3~6ms. 테이블을 읽지 않고 인덱스만으로 센다.
2. **큰 브랜드 · 좋아요순은 노리지 않은 효과로 약 41ms → 약 6ms가 됐다.** (아래 원인 설명은 옵티마이저 트레이스로 일부 고쳤다 → `optimizer-plan.md` 4절)
   - 원인은 새 인덱스로 직접 빨라진 것이 아니라 **옵티마이저의 판단 변화**다. 전에는 `deleted_at is null` 을 통계 없이 10%로 어림했다(EXPLAIN `filtered` 10.0). 새 인덱스에 `deleted_at` 이 들어가면서 조건에 맞는 행 수를 인덱스로 추정하게 됐다(14,995행, 상품 PK로 찾을 때의 `filtered` 50.0).
   - 그래서 좋아요 수 인덱스 순서로 읽다가 20개에서 멈추는 계획이 더 싸다고 판단했다.
   - 이 인덱스(`idx_product_like_count_count`)는 비정규화 측정 때 만들어 두었지만 쓰이지 않던 것이다(`product-query-like-count.md` 관찰 3).
3. **이 계획은 데이터 분포에 기대고 있다.**
   - 브랜드 101은 전체 상품의 약 2/3라서, 좋아요 많은 순으로 훑으면 금방 20개가 찬다.
   - 상품이 적은 브랜드(7)에서는 옵티마이저가 브랜드 상품을 먼저 찾는 계획을 골랐다. 이것도 맞는 판단이다.
   - 위험한 경우는 **중간 크기이면서 인기 상품이 적은 브랜드**다. 좋아요 순서로 훑는 계획이 골라지면, 20개를 채우기까지 많은 행을 읽을 수 있다. 이 장면은 재지 않았다.
4. 큰 브랜드의 `latest` · `price_asc` 는 p50이 3~6ms 줄었다. 대부분 건수 SQL의 감소분이다. 목록 SQL은 한 번 잰 EXPLAIN ANALYZE 기준으로 1~4ms 늘었으나, 한 번 측정이라 차이를 판단하지 않는다.
5. 전체 목록(브랜드 필터 없음)은 차이가 측정 오차 범위다. 이 인덱스는 브랜드 조건이 있어야 쓰인다.

## 5. 판단

- 인덱스는 유지한다. 대가는 상품 쓰기 시 인덱스 열 하나다(외래 키 인덱스를 대신하므로 인덱스 수는 같다). 건수 SQL은 모든 브랜드 장면에서 줄었다.
- 큰 브랜드 · 좋아요순의 개선은 **옵티마이저가 고른 계획에 기대는 결과**라서, 보장된 성능으로 기록하지 않는다. 계획이 바뀌어 느려지는 장면이 실제로 보이면 그때 힌트나 쿼리 분리를 검토한다. 힌트를 미리 넣으면 작은 브랜드에서 반대로 느려진다.
