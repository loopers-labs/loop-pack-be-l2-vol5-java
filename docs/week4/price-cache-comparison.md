# 가격순: 캐시 없음·로컬·Redis 비교

브랜드 7의 가격순 첫 20개와 그 상품들의 좋아요 수·내 좋아요 여부를 조회한다. 목록 항목에는 `isLiked`가 있고 공통 캐시에는 없다. 인덱스 측정 때와 같은 상품 페이지가 대상이며, 응답은 `items`, `page`, `size`다. 총상품수를 세거나 반환하는 작업은 포함하지 않는다.

## 조회 범위와 현재 코드

| 항목 | 비교 조건 |
| --- | --- |
| 인덱스 | 기존 상품 인덱스 유지 |
| 데이터 | 상품 100,000건을 복사한 실험 DB |
| 요청 | brandId=7, sort=price_asc, page=0, size=20, X-USER-ID=95 |
| 캐시 값 | 상품 20개의 ID·이름·가격·생성 시각 |
| DB에서 합성/확인 | 브랜드·현재 좋아요 수·사용자·내 좋아요 여부, hit의 상품 삭제 여부 |
| 응답 | 상품 목록과 page·size |

local·benchmark 프로필은 캐시가 켜져 있고 provider 생략/redis는 Redis를 사용한다. `local` 프로필 이름이 로컬 캐시를 뜻하지는 않는다. 로컬 캐시는 `provider=local`이다. 현재 Redis는 과제 학습 구현이며 운영 도입 결정과 구분한다.

## 비교한 다섯 경우

기존 인덱스를 유지한 Java 앱의 실제 HTTP API를 호출했다. 캐시 없음은 로컬·Redis의 공통 기준이므로 다섯 경우다. 시간은 요청부터 응답 본문을 받을 때까지이며 SQL 한 개의 실행 시간이 아니다.

| 경우 | 1차 중앙값(ms) | 2차 중앙값(ms) | 3차 중앙값(ms) | SELECT 수 |
| --- | ---: | ---: | ---: | ---: |
| 캐시 없음 | 10.051 | 10.273 | 10.028 | 5 |
| 로컬 miss | 8.491 | 8.607 | 8.467 | 5 |
| 로컬 hit | 10.695 | 10.021 | 10.063 | 5 |
| Redis miss | 10.334 | 9.762 | 10.872 | 5 |
| Redis hit | 12.494 | 10.823 | 11.123 | 5 |

주 측정은 `X-USER-ID: 95`를 보내는 목록이다. 사용자·관계 테이블도 원본에서 복사하고, seed 규칙으로 계산한 사용자 95의 하트가 매 응답과 같은지 확인했다. 각 경우는 워밍업 100회 뒤 200회를 측정했다. 세 번 반복하며 앱 실행 순서를 바꿨다. 모든 GET의 상품·가격·순서·좋아요·브랜드·page·size가 독립 기대값과 같았다. p95와 원시 표본은 [측정 JSON](measurements/100k-price-cache-providers-personal.json), [상세 기록](implementation-log.md#price-cache-providers)에 둔다.

로컬 miss가 hit보다 짧게 나온 결과는 측정 순서·JVM 워밍업·준비용 수정 API의 영향을 분리하지 못했다. miss가 본질적으로 더 빠르다고 결론 내리지 않는다. 단일 호스트·순차 요청·별도 JVM의 작은 차이로 보편적인 우열이나 개선 배율을 확정하지 않는다.

## SQL을 실행한 건가, 앱을 실행한 건가?

```text
Python 스크립트
  → GET /api/v1/products?brandId=7&page=0&size=20&sort=price_asc
  → 실행 중인 Java 앱
  → DB / 로컬 캐시 / Redis 경로
  → 응답 본문 수신까지 시간 측정
  → 기대 응답과 비교
```

SQL은 앱 안에서 실행된다. 시간 측정이 끝난 뒤 별도 대표 요청의 MySQL 로그에서 실행 SQL과 계획을 수집했다. 데이터 복사·검증용 SQL과 API 요청 중 SQL은 구분한다.

## Redis hit·miss를 어떻게 만들고 확인했나?

miss는 동일 이름·가격의 관리자 PUT을 완료해 캐시를 비운 다음 GET을 보냈다. 준비용 PUT 시간은 GET 시간에 포함하지 않았다.

```text
관리자 PUT 완료 → commit 후 캐시 삭제
  → GET 시간 측정 시작
  → 브랜드 확인 → Redis GET에 값 없음
  → DB 가격순 상품 20개 → Redis 저장
  → DB 좋아요 카운터 → 사용자 확인·페이지의 내 좋아요 여부 → 응답
```

hit는 같은 요청으로 미리 채운 뒤 변경·삭제 없이 반복 GET을 보냈다. Redis에 있는 목록을 읽고 현재 활성 상품 ID·좋아요 수를 DB에서 확인했다.

| 실제 DB 조회 | 캐시 없음/miss | hit |
| --- | :---: | :---: |
| 브랜드 확인 | O | O |
| 가격순 상품 페이지 | O | — |
| 캐시 상품의 활성 ID 확인 | — | O |
| 상품별 좋아요 카운터 | O | O |
| 활성 사용자 확인 | O | O |
| 페이지의 내 좋아요 여부 | O | O |
| 합계 | 5 | 5 |

사용자 헤더가 있는 정상 비어 있지 않은 측정 요청의 SQL이며, 모든 대표 요청에서 상품 총수 COUNT가 없었다. hit는 상품 페이지 조회를 활성 ID 확인으로 대체한다. **SQL 수가 같아도 각 쿼리가 하는 일이 다르다.** 원본 JSON의 hit/miss는 통제한 조건 이름이며, 개별 GET마다 Redis hit 로그를 수집한 것은 아니다. 시간 측정 후 대표 요청의 SQL로 경로를 확인했다.

## 헤더 없는 조회도 구분해 확인

로그인 측정이 끝난 같은 JVM에서 헤더 없이 워밍업 100회/측정 200회 GET을 보냈다. 모든 하트는 false이고 사용자·개인 관계 SQL은 없었다. 아래는 세 반복의 중앙값이다. 로그인보다 나중에 실행했으므로 두 표의 차이를 개인화 쿼리 두 개의 순수 비용으로 빼서 계산하지 않는다.

| 경우 | 1차(ms) | 2차(ms) | 3차(ms) | SELECT 수 |
| --- | ---: | ---: | ---: | ---: |
| 캐시 없음 | 6.412 | 6.469 | 6.180 | 3 |
| 로컬 hit | 6.728 | 6.279 | 6.688 | 3 |
| Redis hit | 7.744 | 6.821 | 8.613 | 3 |

## 가격 변경 후 데이터 확인과 GET·PUT 시간은 왜 다른가?

실제 가격을 원래 값과 1 낮은 값으로 번갈아 바꾸고, 변경 1회 뒤 GET 10회를 보냈다. GET마다 전체 응답을 기대값과 비교했다. 가격 변경으로 페이지 순서가 바뀌는 장면은 실제 관리자 PUT을 사용하는 통합 테스트로도 확인했다. [쉽게 읽는 가격 변경 흐름](cache-basics.md#가격-변경-흐름을-예로-읽기).

GET 시간은 조회 API 전체, PUT 시간은 DB 수정·commit 후 캐시 삭제·응답까지다. 시간 자체가 정합성을 증명하지 않으며 캐시 삭제만의 순수 비용도 아니다. 중앙값은 가운데 표본, p95는 95% 지점의 지연이다. 변경 1회/조회 10회는 실험 패턴이며 실제 서비스의 변경 빈도나 hit rate가 아니다.

## "앱 두 대"는 무슨 뜻인가?

한 컴퓨터에서 같은 백엔드를 A(18082)와 B(18084)로 실행하고 같은 실험 DB를 사용했다. 먼저 둘의 캐시를 채운 뒤 A에서 가격을 변경하고 각 앱을 다시 조회했다. 요청을 자동 분배하는 구성은 실험하지 않았다.

| 저장소 | A에서 변경한 뒤 B의 조회 |
| --- | --- |
| 로컬 | B의 캐시가 지워지지 않아 옛 가격이 남았다. |
| Redis | 공유 키가 삭제돼 B도 새 가격을 읽었다. |

로컬에 다른 앱의 캐시를 지우는 기능은 없다. Redis 결과는 정상 변경 후 순차 조회의 검증이며 DEL 실패·늦은 채움에서도 즉시 최신이라는 뜻은 아니다. 예시 숫자 대신 실제 응답 비교 결과는 [원본](measurements/100k-price-cache-providers-personal.json)의 two_processes에 남겼다.

## 같은 조건과 실행 방법

캐시 내용·TTL 300초·브랜드/삭제 확인·좋아요 합성을 공유한다. 로컬은 Caffeine의 불변 DTO·최대 1,000개 엔트리(실험 상한), Redis는 JSON을 사용한다. 저장·변경 후 삭제·복구 책임도 비용이다. JVM RSS는 전체 앱 메모리이고 Redis MEMORY USAGE는 키 메모리이므로 캐시 메모리의 동등한 비교나 월 요금으로 해석하지 않는다.

```bash
python3 scripts/compare-week4-price-cache-providers.py \
  --jar apps/commerce-api/build/libs/commerce-api-a083b48.jar \
  --user-id 95 \
  --output docs/week4/measurements/100k-price-cache-providers-personal.json
```

JAR는 현재 빌드에 맞춘다. 재실행 시 기존 원본을 덮어쓰지 않도록 새 출력 경로를 쓴다. benchmark MySQL·Redis와 18082~18085 포트가 필요하다. 다른 벤치마크와 겹치지 않게 실행하며 자신이 만든 복제 DB·권한·키·프로세스만 정리한다.

| 모드 | 설정 |
| --- | --- |
| 캐시 없음 | commerce.cache.price.enabled=false |
| 로컬 | enabled=true, provider=local |
| Redis | enabled=true, provider=redis |

캐시 없음 설정은 변경 후 DEL도 끈다. 같은 DB에 캐시 사용 앱과 DB-only 쓰기 앱을 혼합 배포하는 설정으로 사용하지 않는다.

## 보조 확인: Redis에서 목록을 받는 비용

같은 연결·Jackson 설정과 상품 20개 형식을 쓰는 별도 Java 프로그램에서 GET과 JSON 변환을 나눴다. HTTP 앱의 요청 중간에 삽입한 계측은 아니다. JSON은 1771바이트다.

| 구간 | 중앙값(ms) | p95(ms) |
| --- | ---: | ---: |
| Redis GET → 문자열 수신 | 0.541~0.720 | 0.770~2.669 |
| JSON → 상품 목록 | 0.046~0.061 | 0.078~0.173 |
| GET 시작 → 변환 완료 | 0.591~0.794 | 0.834~2.780 |

독립 JVM 세 개에서 각각 워밍업 1,000회 뒤 1,000회 측정했다. 범위는 세 반복 통계의 최솟값~최댓값이다. GET에는 클라이언트 대기·통신·Redis 처리·문자열 변환이 포함되므로 순수 네트워크 시간이라고 부르지 않는다. 측정 3,000회가 원본 페이지와 같았다. 별도 실험의 시간을 기존 API 시간에서 빼거나 네트워크가 전체 성능 차이의 원인이라고 단정하지 않는다.
