# 인덱스를 맞췄는데도 정렬이 남았던 이유

> W4 Technical Writing. 실습 노트의 인덱스를 우리 실제 쿼리에 그대로 옮겼더니 정렬이 사라지지 않았다. 무엇이 달랐는지, 무엇을 바꿨는지, 그리고 그 개선을 어디까지 주장할 수 있는지를 적는다.

## 상황

고객 상품 목록 `GET /api/v1/products?brandId=7&sort=price_asc`는 브랜드 7의 상품을 가격 오름차순으로 20개 돌려준다. 좋아요 수도 함께 보여 준다. 실제로 나가던 SQL은 이랬다.

```sql
SELECT p.*, COUNT(l.id)
FROM products p LEFT JOIN likes l ON l.product_id = p.id
WHERE p.deleted_at IS NULL AND p.brand_id = 7
GROUP BY p.id
ORDER BY p.price, p.id DESC
LIMIT 0, 20;
```

인덱스는 `(brand_id)` 하나였다. 상품 1만 개(브랜드 100개, 브랜드당 100개)와 좋아요 9만 행에서 실행 계획은 `Using where; Using temporary; Using filesort`였고, `EXPLAIN ANALYZE`로 보면 브랜드 7의 상품 100개와 그 좋아요 948행을 전부 읽은 뒤 정렬해서 20개를 남겼다.

## 개념: 정렬이 사라지는 조건

B-Tree 인덱스는 키 순서로 정렬된 목록이다. `(brand_id)` 인덱스의 실제 항목은 PK가 붙은 `(brand_id, id)`라서, 브랜드 7 구간 안은 id 순서로 놓여 있고 가격은 뒤죽박죽이다. 가장 싼 20개가 구간 끝에 있을 수도 있으니 끝까지 읽을 수밖에 없다.

`=` 조건 열 다음에 ORDER BY 열을 **같은 순서·같은 방향**으로 두면, DB는 그 구간을 앞에서부터 읽다가 LIMIT만큼 모이면 멈춘다. 정렬 단계가 필요 없다. 실습 노트에서는 `(brand_id, price, id)`로 `Handler_read_next`가 1,000에서 19로 줄었다.

## 그대로 옮겼더니

삭제 조건까지 넣어 `(brand_id, deleted_at, price, id)`를 만들었다. 실행 계획은 이 인덱스를 골랐지만(`ref`, `const,const`) **`Using temporary; Using filesort`가 그대로 남았다.** 읽은 상품도 99개 — 거의 그대로였다.

차이는 두 가지였다.

1. **JOIN + GROUP BY.** 좋아요 수를 같은 쿼리에서 세느라 상품마다 좋아요를 붙이고 `GROUP BY p.id`로 묶는다. 옵티마이저는 이 집계를 임시 테이블에서 하고, 그 결과를 다시 정렬했다. 인덱스가 준 가격 순서는 집계 단계에서 버려진다.
2. **정렬 방향.** 우리 계약은 동률을 최신순(`id DESC`, P-09)으로 정렬한다. 실습 쿼리는 `id ASC`였다. 인덱스의 마지막 열이 오름차순이면 `price ASC, id DESC`를 그대로 읽어 낼 수 없다.

하나씩 확인했다. 좋아요를 빼고 상품만 고르는 쿼리로 바꾸자 임시 테이블은 사라졌지만 `Using filesort`는 남았다(2번). 인덱스를 `(brand_id, deleted_at, price, id DESC)`로 바꾸자 정렬이 사라지고 `Handler_read_key 1`, `Handler_read_next 19` — 정확히 20개만 읽었다.

## 판단: 쿼리를 정렬별로 나눈다

latest·price_asc는 좋아요 수가 정렬에 필요 없다. 그래서 ① 인덱스 순서로 상품 20개를 먼저 고르고 ② 그 20개의 좋아요만 `product_id IN (…) GROUP BY`로 센다. 좋아요 읽기는 948행에서 185행으로 줄었고, 응답 JSON은 개선 전과 같았다.

likes_desc는 그대로 두었다. 정렬 기준이 집계 결과라 "20개를 먼저 고르고 센다"로 바꾸면 "전체 후보 중 좋아요 많은 순"이라는 의미가 깨진다. 이 쿼리는 1만 개 상품과 9만 행 좋아요를 전부 읽는다(DB 30 ms). 인덱스로 줄일 수 없는 비용이라, 목록 캐시를 붙인 근거가 됐다 — hit에서는 PK 20건 확인으로 바뀌어 p50이 약 24 ms에서 5 ms가 됐다.

## 얻은 것, 생긴 비용, 주장하지 않는 것

- **줄인 것**: price_asc 한 요청이 읽는 행 — 상품 100 → 20, 좋아요 948 → 185. 정렬·임시 테이블 제거.
- **생긴 것**: 요청당 SQL이 3개에서 4개로 늘었다(좋아요 집계를 따로 보냄). 인덱스 하나만큼 쓰기·저장 비용. 삭제 조건이 없는 관리자 조회는 이 인덱스로 정렬을 피하지 못한다 — 인덱스는 테이블이 아니라 쿼리별 계약에 맞춘다.
- **주장하지 않는 것**: HTTP 응답이 빨라졌다는 말. 같은 측정이 실행마다 2~3배 흔들렸고(p50 4.4 ms ↔ 15.6 ms), 1만 행에서는 DB 시간이 1 ms 미만이라 차이가 잡음에 묻혔다. 브랜드당 상품이 1만 개쯤 되면 "100개 읽고 정렬"과 "20개 읽고 멈춤"의 차이가 시간으로도 보일 것이라 예상하지만, 그 규모는 재지 못했다.

실습 노트의 결론("인덱스가 정렬을 없앤다")은 맞았다. 다만 그 결론은 **그 쿼리**에 대한 것이었다. 같은 인덱스도 JOIN·집계·정렬 방향이 다른 실제 쿼리에서는 다르게 읽힌다. 실행 계획은 축약 쿼리가 아니라 API가 실제로 보내는 SQL로 봐야 한다.
