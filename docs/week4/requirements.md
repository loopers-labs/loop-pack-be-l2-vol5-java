## 완화하지 않는 기존 계약

조회를 빠르게 하려고 아래를 바꾸면 성능 개선으로 세지 않는다. 원문: "기존 조건을 빼서 빨라지는 제안 … 은 수정합니다."

| 기존 규칙 | 내용 | 이번 주에 걸리는 자리 |
|---|---|---|
| `PRODUCT-005` · `COMMON-006` | 고객 목록 · 상세는 삭제되지 않은 상품만. 삭제된 것은 404 | 인덱스 열 순서, 캐시에 담긴 삭제 상품 |
| `PRODUCT-010` · `011` | `brandId` 필터, 정렬 `LATEST` · `PRICE_ASC` · `LIKES_DESC`, 기본 `LATEST` | 쿼리 재작성 |
| `PRODUCT-012` | 어느 정렬이든 마지막 기준은 `id` 내림차순 | `PRICE_ASC` 는 `price ASC, id DESC` — **방향이 섞인다.** 인덱스 방향을 맞출 때 지운다 |
| `COMMON-008` | `page`(0부터) · `size`(기본 20, 최대 100), 응답은 `hasNext`. 총 개수 없음 | 커서 방식으로 바꾸지 않는다 |
| `PRODUCT-007` · `013` · `LIKE-008` | 응답에 브랜드(id · 이름)와 좋아요 수. 좋아요 수는 **관계를 세어** 얻고 따로 저장하지 않는다 | 좋아요 수를 저장하지 않는다는 W2 원문을, W4 원문이 선택 심화(카운터 비정규화)로 연다. 고를지는 Q-6 |
| `PRODUCT-008` | 응답에 요청자의 `liked`. **같은 조회 쿼리 안에서** 얻는다 | 공용 캐시와 충돌한다(Q-4) |
| Q-2 (W2) | 고객 응답에는 재고 수량이 아니라 품절 여부만 | 캐시 payload |
| `ORDER-012` 등 | 주문 확정은 DB 의 상품 · 재고 · 포인트를 잠가 읽는다 | 캐시 값으로 주문을 판단하지 않는다(`CACHE-009`) |

## SEED — 측정용 데이터

측정 데이터는 실제 스키마(JPA 엔티티가 만든 `brand` · `product` · `product_like`)의 필수 값과 관계를 지킨다.
측정용 별도 모델을 만들지 않는다 — 개선한 SQL 이 실제 API 에서 쓰이지 않게 된다.

| ID | 규칙 | 출처 |
|---|---|---|
| `SEED-001` | 살아 있는 상품이 10,000 개 이상이다 | 원문 |
| `SEED-002` | 같은 seed 를 몇 번이든 같은 데이터로 다시 만든다. 난수는 고정 seed 로 시작하고, 시각은 `NOW()` 가 아니라 고정 기준일에서 계산한다 | 원문 + 정함 |
| `SEED-003` | 브랜드 · 가격 · 좋아요 수가 한 값에만 몰리지 않는다. 좋아요 0 개 · 동점 · 인기 상품을 포함한다 | 원문 |
| `SEED-004` | 데이터는 세 벌이다. **A(균등, 상품 1만)** 는 검산, **B(쏠림, 상품 100만)** 가 판단 기준, **B-small(B 와 같은 분포, 상품 10만)** 은 규모에 따른 결론의 민감도 확인이다 | 정함 |
| `SEED-007` | 캐시 · 장애 테스트(Testcontainers)는 seed 가 아니라 장면마다 필요한 작은 데이터로 돈다 | 정함 |
| `SEED-005` | seed 는 `.sql` 파일과 저장 프로시저로 저장소에 남긴다(`docs/week4/seed/`) | 정함 |
| `SEED-006` | 공유 DB 의 데이터나 다른 과제의 인덱스를 지우지 않는다. 격리된 실습 DB 에서만 돌린다 | 원문 |

### A · 균등 — 원문 예시 그대로

```
상품 순번 i = 1..10,000
브랜드 순번 = (i % 100) + 1
가격 = ((i * 37) % 100000) + 100
```

| 확인 | 기대 |
|---|---|
| 상품 수 · 가격 합계 | 10,000 · 472,685,000 |
| 브랜드 순번 7 의 상품 수 · 가격 합계 | 100 · 4,647,200 |

원문 예시가 정하지 않은 값은 정했다(`정함`). 확인 쿼리는 `docs/week4/seed/02_check_uniform.sql`.

| 값 | 정한 것 | 확인 |
|---|---|---|
| id | 브랜드 id = 브랜드 순번, 상품 id = 상품 순번 | 원문의 "순번을 실제 ID 와 매핑" 을 같은 값으로 |
| 재고 | `(i × 7) % 50` — 0 이 섞여 품절이 생긴다 | — |
| 좋아요 수 | `i % 1000 = 0` 이면 300(인기 10 개), `i % 4 = 0` 이면 0, 나머지는 `(i × 13) % 20`. 사용자 id 1 ~ 300 이 순서대로 누른다 | 좋아요 78,000 개, 0 개인 상품 2,490 개, 최대 300. 동점이 많다 |
| 가격 동점 | **없다.** 37 과 100,000 이 서로소라 1 만 개의 가격이 모두 다르다 | 서로 다른 가격 10,000 개. 가격 동점은 B 와 별도의 작은 자료로 본다(원문 "동점이 생기는 작은 별도 자료") |

**쓰는 이유**: 원문이 검산값을 주므로 **seed 를 맞게 만들었는지** 확인할 수 있는 유일한 데이터다.
**판단에 쓰지 않는 이유**: 모든 브랜드가 100 개라 브랜드 필터 뒤의 정렬이 늘 가볍고, 테이블 전체가 메모리에 들어간다(B 의 "왜 1 만이 아닌가").

### B · 쏠림 — 판단 기준

**규모**: 살아 있는 상품 100 만 개 이상, 좋아요 약 500 만 개.

| 왜 1 만이 아닌가 | |
|---|---|
| 메모리 | 상품 1 만 행은 수 MB 라 버퍼 풀(MySQL 기본 128 MB)에 전부 들어간다. 계획이 나빠도 메모리에서 끝나 좋은 계획과 차이가 측정 잡음에 묻힌다. 100 만 행 · 좋아요 500 만 행은 버퍼 풀을 넘는다 |
| 계획 | 작은 테이블에서는 옵티마이저가 전체 스캔을 싸다고 본다. 규모가 커져야 생기는 계획 문제가 재현되지 않는다 |
| 쏠림 | 1 만이면 가장 큰 브랜드도 수천 개라 그 정렬이 가볍다 |

**뒤집을 조건**: B 와 B-small 의 결론이 다르면 규모에 민감하다는 뜻이다 — 결론에 그 경계를 적고, 필요하면 규모를 더 늘려 다시 잰다.
더 늘리지 않는 이유는 노트북 Docker 의 적재 시간 · 디스크다.

| 축 | 목표 (생성 뒤 확인 쿼리로 검증) | 근거 |
|---|---|---|
| 브랜드 크기 | 브랜드 1,000 개. 순위 k 의 브랜드가 상품의 `(1/k) / H₁₀₀₀` 를 가진다(Zipf, s = 1). 브랜드 id = 순위 | 소수 브랜드가 상품을 독점하는 것이 일반적이다. 브랜드 필터 + 가격순의 비용은 **그 브랜드의 상품 수**가 정하므로, 큰 브랜드가 없으면 병목이 재현되지 않는다 |
| 측정 대상 브랜드 | 큰 브랜드 `1`, 중간 브랜드 `100`, 작은 브랜드 `1000` | 같은 인덱스도 대상 행 수에 따라 계획과 성능이 달라진다. 셋을 따로 재야 "큰 브랜드에서만 이득" 같은 결과를 구분한다 |
| 상품 id 와 브랜드 | 같은 브랜드의 상품이 id 구간으로 뭉치지 않게 id 순서를 섞는다 | 실제 등록은 여러 브랜드가 시간순으로 섞여 들어온다. 뭉치면 브랜드 필터가 기본키 범위 읽기처럼 싸게 보인다 |
| 가격 | 로그정규(중앙값 13,000 원, σ = 0.6)를 3,000 ~ 60,000 원으로 자르고 100 원 단위로 반올림 | 저가에 몰리고 고가가 드문 것이 일반적이다. 100 원 단위라 **가격 동점이 자연히 생겨** `PRODUCT-012` 의 `id` 보조 정렬을 시험한다 |
| 재고 | 0 ~ 99, 약 1% 가 0(품절) | 품절 여부가 응답에 있다(W2 Q-2) |
| 좋아요 | 인기 순위 r 의 상품이 `⌊C / r^0.85⌋` 개, `C = (0.78 × 상품 수)^0.85`. 상위 1% 가 30% 이상, 0 개인 상품 20% 이상이 되게 고른 값이다 | 소수 인기 상품이 반응을 독점한다. 인기 상품이 낀 페이지만 느린 현상은 평균이 아니라 p99 에서 보이므로, 꼬리를 일부러 만든다. 순위가 낮을수록 같은 값이 많아 동점도 생긴다 |
| 인기와 브랜드 · id 의 관계 | 인기 순위는 상품 id · 브랜드와 무관한 순열로 배정한다 | id 와 인기가 같이 움직이면 `LATEST` 와 `LIKES_DESC` 가 같은 순서가 되어 정렬별 비용을 구분하지 못한다 |
| 사용자 | 좋아요를 누르는 사용자 id 20 만 개. 한 상품 안에서 사용자가 겹치지 않는다 | `LIKE-001` 의 유니크 제약. 사용자 테이블이 없으므로 id 만 만든다. 사용자가 적으면 한 사람이 수천 개를 누르는 비현실적인 데이터가 된다 |
| 삭제 상품 | 상품마다 12% 확률로 삭제, 그리고 삭제 브랜드의 상품 전부 | `deleted_at IS NULL` 이 실제로 행을 거르게 해야 인덱스 열 순서를 시험할 수 있다. 삭제가 0 이면 그 조건은 공짜처럼 보인다 |
| 삭제 상품의 좋아요 | 삭제된 상품에도 좋아요가 남아 있다 | W2 `LIKE-005` · `006` — 삭제 전에 누른 좋아요는 남는다. 집계가 그 행을 읽고 버리는 비용까지 재야 한다 |
| 삭제 브랜드 | 브랜드 `300` · `700` 은 삭제되어 있고, 그 상품도 전부 삭제되어 있다 | W3 의 "삭제된 브랜드 아래 살아 있는 상품 없음" 불변식을 seed 도 지킨다. 측정 대상과 겹치지 않는 중하위 브랜드를 골랐다 |
| 시각 | `created_at` 은 고정 기준일에서 id 순으로 증가 | `SEED-002`. `LATEST` 는 `id DESC` 라 시각이 정렬에 쓰이지 않지만, 실행 시점에 따라 값이 바뀌면 결과 비교의 체크섬이 흔들린다 |
| 재현 | 난수 대신 `CRC32(태그 + id)` 로 값을 만든다 | `RAND(seed)` 는 한 문장 안에서 행을 읽는 순서가 바뀌면 값도 바뀐다. id 의 해시는 순서와 무관하다 |

**적재 시간**: B-small 4 초, B 12 분 24 초(Apple Silicon 노트북 · Docker · 버퍼 풀 128 MB). B 는 유니크 인덱스 `(user_id, product_id)` 의 중복 검사가 무작위 사용자 순서로 버퍼 풀 밖의 페이지를 읽고, binlog(`ROW`)에 행마다 한 번 더 쓴다.
다시 만드는 일이 잦아지면 세션의 `sql_log_bin = 0` · `unique_checks = 0`, 또는 보조 인덱스를 지웠다가 적재 뒤 다시 만드는 것으로 줄인다.

**기대값** (`03_seed_skewed.sql` 의 `CALL seed_skewed(상품 수)` 뒤 `04_check_skewed.sql`). MySQL `CRC32` 와 같은 함수로 미리 계산했다(`python3 docs/week4/seed/05_expected_skewed.py 상품수`).
좋아요 수 · 가격은 부동소수 계산이라 경계에서 1 정도 어긋날 수 있다.

| 확인 | B (`1150000`) | B-small (`115000`) |
|---|---|---|
| 상품 · 살아 있는 상품 · 삭제율 | 1,150,000 · 1,011,285 · 12.06% | 115,000 · 100,990 · 12.18% |
| 브랜드 `1` 상품 · 살아 있는 상품 | 153,631 · 135,186 | 15,363 · 13,450 |
| 브랜드 `100` | 1,537 · 1,345 | 153 · 136 |
| 브랜드 `1000` | 154 · 129 | 15 · 13 |
| 삭제 브랜드 아래 살아 있는 상품 | 0 | 0 |
| 좋아요 합계 · 상위 1% 비중 · 0 개 비율 · 최대 | 4,911,926 · 0.49 · 0.22 · 114,781 | 462,316 · 0.458 · 0.22 · 16,213 |
| 살아 있는 상품 가격 최소 · 최대 · 중앙값 · 서로 다른 값 | 3,000 · 60,000 · 13,000 · 364 | 3,000 · 60,000 · 13,000 · 350 |

**분포 모수의 출처는 `정함` 이다.** 우리 서비스의 실제 분포 자료가 없다.
쏠림을 일부러 만드는 이유는 옵티마이저가 분포를 균일하다고 가정하기 때문이다 — 쏠린 데이터에서 추정과 실제가 벌어지는 것을 보려면 불균형이 있어야 한다.

**뒤집을 조건**: 실제 분포(브랜드별 상품 수, 상품별 좋아요 수)를 알게 되면 그 분포로 바꾸고 다시 측정한다.
B 의 결과가 모수(예: Zipf 지수)를 조금 바꿨을 때 결론이 뒤집힐 만큼 민감하면, 결론에 그 민감도를 함께 적는다.

### 실행 환경

| 항목 | 정한 것 | 근거 |
|---|---|---|
| 적재 방식 | `.sql` 의 저장 프로시저를 MySQL Workbench 또는 CLI 로 실행 | `SEED-005`. 측정하는 사람이 같은 자리에서 `EXPLAIN ANALYZE` 까지 돌린다 |
| 적재 단위 | 행마다 `INSERT` 하지 않고, 숫자 열(재귀 CTE · 교차 조인)에서 `INSERT ... SELECT` 로 집합 단위로 넣는다. 프로시저는 그 문장의 순서만 묶는다 | 행 단위 루프는 100 만 건에 수십 분이 걸린다 |
| 구문 구분자 | 프로시저 정의는 `DELIMITER $$` 로 감싼다 | Workbench · CLI 는 `;` 로 문장을 끊으므로 본문에 `;` 가 있는 프로시저는 구분자를 바꿔야 한다. `DELIMITER` 는 클라이언트 명령이라 JDBC 로는 실행되지 않지만, seed 를 테스트가 쓰지 않으므로(`SEED-007`) 걸리지 않는다 |
| 스키마 | JPA 엔티티가 만든 스키마 위에 적재한다 | 스키마의 출처가 엔티티다(마이그레이션 도구가 없다) |
| **스키마 재생성 주의** | local 프로파일은 `ddl-auto: create` 라 앱을 띄울 때마다 테이블을 다시 만든다. 측정 순서는 "앱으로 스키마 생성 → seed → `ddl-auto: none` 으로 앱 실행" 이다 | 이것을 놓치면 앱 재시작으로 seed 가 사라지고, 빈 테이블의 측정이 개선처럼 보인다 |
| 인덱스 | 비교 후보는 `.sql` 로 적용 · 제거한다. 채택한 것은 엔티티의 `@Index` 에도 반영한다 | 엔티티와 실제 스키마가 어긋나지 않게 한다 |

## QUERY — 조회 SQL · 인덱스 개선

| ID | 규칙 | 출처 | 기대 |
|---|---|---|---|
| `QUERY-001` | 측정 요청을 고정한다: `GET /api/v1/products?brandId={대상}&sort=PRICE_ASC&page=0&size=20` | 원문 + 정함 | 새 `limit` 계약을 만들지 않는다. 대상 브랜드는 B · B-small 의 큰 · 중간 · 작은 브랜드와 A 의 브랜드 순번 7 |
| `QUERY-002` | 개선 전(기준선)에 같은 요청의 응답 · 요청당 SQL 수 · `EXPLAIN` · `EXPLAIN ANALYZE` · 반복 지연을 기록한다 | 원문 | 캐시를 끈 상태로 잰다 |
| `QUERY-003` | 개선 전후의 **결과가 같다**: 정렬된 상품 id · 가격 · 좋아요 수 · `hasNext` | 원문 | 결과가 바뀌면 성능 개선으로 세지 않는다. 체크섬을 쓰면 직렬화 필드 · 순서를 고정하고, 불일치는 실제 값을 찾아 확인한다 |
| `QUERY-004` | 비교에 남길 것: 사용 key · 접근 경로, 예상 / 실제 rows · loops, 정렬 단계, 요청당 SQL 수, 준비 실행 수 · 측정 표본 수, 지연의 p50 · p95 · p99 | 원문 | 특정 인덱스 이름 · `Using index` · "몇 배" 를 정답으로 고정하지 않는다 |
| `QUERY-005` | `LIKES_DESC` 는 **전체 후보**를 좋아요 수로 정렬한 뒤 페이지를 고른다 | 원문 | "20 개를 먼저 고르고 그 안에서 정렬" 로 바꾸지 않는다 |
| `QUERY-006` | 좋아요 수를 상품마다 반복 조회한다면 목록 단위로 줄인다 | 원문 | 현재는 한 SQL 의 `LEFT JOIN` + `GROUP BY` 라 반복 조회가 없다. 반복이 없다는 것을 요청당 SQL 수로 확인해 기록한다 |
| `QUERY-007` | 지연은 k6 로 잰다(`docs/week4/load/measure.sh`). 워밍업 40 VU · 30 초를 버린 뒤, 동시성 1 · 10 · 40 · 80 VU 를 단계마다 30 초 잰다 | 정함 | 워밍업은 횟수가 아니라 시간으로 한다 — JIT 의 최적화 컴파일은 호출이 대략 1 만 번 쌓여야 들어간다. 40 은 커넥션 풀 크기, 80 은 풀을 넘겨 **커넥션 대기가 생기는 단계**다 |
| `QUERY-009` | 단계마다 요청당 SQL 수와 커넥션 대기를 함께 남긴다 | 정함 | 요청당 SQL 수 = MySQL `Com_select` 증가량 ÷ 요청 수. 커넥션 대기 = Hikari `hikaricp_connections_acquire_seconds` 의 증가량(평균) · 최대. 앱 코드를 바꾸지 않고 앱 밖에서 읽는다 |
| `QUERY-010` | 버퍼 풀이 빈 상태(MySQL 재시작 직후)의 20 회를 따로 기록한다(`COLD=1`) | 정함 | 데이터가 버퍼 풀보다 크게 만든 이유가 디스크 읽기다. 데운 상태만 재면 그 비용이 사라진다. 판단의 기준은 데운 상태이고, 차가운 상태는 함께 적는다. **재시작만으로는 차가워지지 않는다** — MySQL 8 은 종료 때 버퍼 풀 페이지 목록을 저장하고(`innodb_buffer_pool_dump_at_shutdown`) 시작 때 다시 읽는다. 그래서 저장을 끄고 `ib_buffer_pool` 파일을 지운 뒤 재시작한다. **한계**: Docker on Mac 에서는 VM 의 OS 파일 캐시가 남아(InnoDB 기본 `fsync` 는 OS 캐시를 거친다) 디스크 읽기가 재현되지 않았다. 차가운 상태와 데운 상태가 거의 같았다 |
| `QUERY-011` | 측정할 때 앱은 `ddl-auto=none` 으로 띄운다 | 정함 | local 프로파일의 `create` 가 seed 를 지운다 |
| `QUERY-008` | 측정 전 `ANALYZE TABLE` 로 통계를 갱신한다. 갱신하지 않은 상태도 한 번 기록한다 | 정함 | W3 에서 통계가 틀어진 순간 계획이 바뀌는 것을 봤다. 두 상태를 구분해 적는다 |

## CACHE — 한 조회 경로의 캐시

| ID | 규칙 | 출처 | 기대 |
|---|---|---|---|
| `CACHE-001` | 목록 또는 상세의 공통 조회 한 경로에 Redis cache-aside 를 붙인다 | 원문 | 어느 경로인지, 담는 단위는 Q-2 |
| `CACHE-002` | miss: DB 의 올바른 결과를 읽어 유효 시간과 함께 저장한다. hit: 같은 조건의 응답을 반환하고 비싼 원본 쿼리 · 집계를 줄인다 | 원문 | 같은 입력에서 DB 조회 · miss · hit 의 결과가 같다 |
| `CACHE-003` | 키는 필터 · 정렬 · 페이지 · 크기 · 응답 형식을 구분한다 | 원문 | — |
| `CACHE-004` | 사용자별 필드(`liked`)를 공용 캐시에 담지 않는다 | 원문 · 보안 | 다른 사용자의 좋아요 여부가 보이지 않는다. 합성 방법은 Q-4 |
| `CACHE-005` | 캐시 내용에 영향을 주는 **모든** 기존 쓰기 경로가 캐시에 반영된다. 가격 수정만 새 서비스로 우회하지 않고 기존 관리자 API 에 연결한다 | 원문 | 대상: 상품 등록 · 수정 · 삭제 · 재고 변경, 브랜드 수정 · 일괄 삭제, 좋아요 등록 · 취소(좋아요 수를 담는다면), 주문 확정(재고 · 품절을 담는다면) |
| `CACHE-006` | 장애 · 동시 채움이 없는 정상 변경이 끝난 뒤 시작한 순차 조회는 변경된 결과를 반환한다 | 원문 | — |
| `CACHE-007` | 변경이 rollback 되면 존재하지 않는 새 결과를 게시하지 않는다 | 원문 | — |
| `CACHE-008` | 삭제된 상품 · 다른 사용자 정보는 캐시를 통해서도 노출되지 않는다 | 원문 | 신선도 정책의 대상이 아니다. 오래된 표시를 허용하더라도 이것은 허용하지 않는다 |
| `CACHE-009` | 주문 확정은 캐시를 읽지 않는다. Redis 장애만으로 결제 · 재고 처리를 우회하지 않는다 | 원문 | — |
| `CACHE-010` | Redis 오류는 제한된 시간만 기다리고 DB 결과로 우회한다. DB 까지 실패하면 빈 목록 · 가격 0 으로 감추지 않고 기존 오류 계약을 따른다 | 원문 | 대기 한도는 Q-7 |
| `CACHE-011` | `@Transactional` + 캐시 삭제나 TTL 만으로 모든 경쟁 · 장애에서 최신성을 보장한다고 주장하지 않는다. 장애 중 허용할 신선도와 복구 조건을 따로 정한다 | 원문 | 정책은 Q-5 |
| `CACHE-012` | 공유 Redis 에 `FLUSHALL` 을 실행하거나 다른 작업의 컨테이너를 중단하지 않는다. 장애 실험은 테스트가 실제로 연결한 Redis 만 대상으로 한다 | 원문 | — |
| `CACHE-013` | 최신성 실험에서 어떤 Redis 연결(master · replica)을 읽었는지 적는다. replica 지연을 애플리케이션 최신성 보장으로 오인하지 않는다 | 원문 | 기본 연결은 `REPLICA_PREFERRED`, 별도 master 연결이 있다 |

### 확인할 장면

실제 애플리케이션 · MySQL · Redis 가 연결된 테스트로 확인한다. 캐시 동작을 전부 Mock 으로 대체하지 않는다(원문, 그리고 "테스트 더블을 두지 않는다").
순서가 중요한 장면은 테스트 훅 · 래치로 통제하고, 기다림에는 유한한 timeout 을 둔다.

| 장면 | 확인할 결과 | 출처 |
|---|---|---|
| 같은 입력의 DB 조회 · miss · hit | 상품 · 정렬 · 페이지 결과 일치, hit 에서 선택한 비싼 DB 조회 감소 | 원문 |
| 관리자 가격 수정 commit 후 재조회 | 새 가격과 목록 순서 반영, 과거 주문 금액 유지 | 원문 |
| 캐시에 담긴 상품 · 브랜드 일괄 삭제 | 해당 상품이 고객 결과에서 제외, 다른 브랜드와 과거 주문 유지 | 원문 |
| 캐시 내용에 영향을 주는 나머지 쓰기 | `CACHE-005` 의 대상마다 조회 반영 | 원문 |
| DB 변경 rollback | 변경 전 결과 유지, 새 데이터로 오인할 캐시 없음 | 원문 |
| commit 뒤 캐시 무효화 실패 | DB 의 commit 은 유지(실패 응답으로 바꾸지 않음), Q-5 의 정책대로 표시 · 복구 뒤 원본 일치 | 원문 |
| 이전 조회의 늦은 캐시 채움 | 이전 DB 결과 읽기 → 관리자 변경 commit → 이전 결과 캐시 저장 → 새 조회. 오래된 재삽입을 결정적으로 재현하고 Q-5 의 정책 결과 확인 | 원문 |
| Redis 중단 · 재시작 | 제한된 대기 뒤 DB 결과 반환, 재시작 뒤 정확한 재채움. 실험 자원 정리 | 원문 |

## 물을 질문

**측정으로 답할 질문**은 판단 기준을 함께 적는다. 측정이 끝나면 질문을 결정으로 옮기고 근거를 설계 기록에 적는다.

| # | 질문 | 출처 | 답을 정하는 것 | 판단 기준 |
|---|---|---|---|---|
| ~~Q-1~~ | ~~**SQL · 인덱스 개선만으로 충분한가**~~ → **충분하다**(`PRICE_ASC` · `LATEST`). 21 개를 먼저 고르는 쿼리 + `(brand_id, deleted_at, price, id DESC)` 로 브랜드 `1` 의 p50 이 1,621 → 1.0 ms, 동시 요청 80 의 실패 335 → 0. 근거는 설계 2.1 ~ 2.3 | 측정 | B 의 큰 브랜드에서 개선 전후 `EXPLAIN ANALYZE` · 읽은 행 · p50 · p95 · p99, 결과 일치 | 개선 뒤 p95 가 50 ms 이하이고, 동시 요청을 늘려도 DB 커넥션 대기가 생기지 않으면 "충분". 그래도 캐시는 원문이라 붙이되, 이득이 작다고 적는다 |
| ~~Q-2~~ | ~~**캐시를 어느 경로에, 어떤 단위로 담는가**~~ → **가격순 · 최신순 목록의 첫 페이지(크기 20)만, 브랜드별과 전체 목록.** 페이지 응답 단위로 담는다. 인기순은 순서가 좋아요 수라 담지 않고, 다음 페이지 · 다른 크기는 원본으로 간다. 첫 페이지만이라 쓰기 하나가 무효화할 키가 최대 4 개다. "요청이 첫 페이지에 몰린다" 는 가정(정함)이고, 다음 페이지의 비중이 크게 측정되면 늘린다. **측정 결과 hit 는 SQL 개선 뒤의 원본보다 빠르지 않았다(같거나 20 ~ 28% 느림) — 판단 기준을 넘지 못했고, 과제 필수라 유지한다.** 근거 설계 4 · 4.8 절 | 측정 + 선택 |
| ~~Q-3~~ | ~~**캐시 패턴**~~ → **목록은 cache-aside.** 원본이 DB 이고 쓰기가 드문 값(이름 · 가격 · 품절 · 순서)이라 지우고 다시 채운다. write-through 는 목록의 순서 · 페이지 경계를 쓰기 때 계산해야 하고, write-behind 는 원본이 캐시가 되어 맞지 않는다. 자주 바뀌고 쌓이는 값(좋아요 수)은 지우는 방식이 맞지 않아 담지 않는다 | 원문 + 선택 |
| ~~Q-4~~ | ~~**`liked` 를 어떻게 합성하는가**~~ → **hit · miss 모두 마지막에 원본에서 한 쿼리로 붙인다** — 좋아요 수와 `liked` 를 함께, 살아 있는 상품만. 목록 요청의 SQL 은 hit 1 개 · miss 2 개가 되어 W2 `PRODUCT-008` 을 고쳤다 | 정함(W2) → 바꿨다 |
| ~~Q-5~~ | ~~**장애 중 표시 신선도 정책**~~ → **브랜드별 세대 번호 + TTL 60 초 + 꺼낼 때 삭제 상품 재확인.** 읽는 쪽이 DB 를 읽기 전에 세대를 읽고 그 세대의 키에 저장해 늦은 채움을 막는다. 커밋 뒤 세대 올리기가 실패하면 이름 · 가격 · 품절 표시 · 순서가 최대 60 초 옛 값이다. 삭제된 상품은 좋아요를 붙이는 쿼리가 걸러 무효화가 실패해도 보이지 않는다(`CACHE-008`). 주문은 캐시를 보지 않는다(`CACHE-009`). 근거 설계 4 절 | 정함 |
| ~~Q-6~~ | ~~**`LIKES_DESC` 를 무엇으로 빠르게 하는가**~~ → **이번 주에는 비정규화하지 않는다.** 쿼리 구조 개선(L2)으로 2 배 안팎 줄었지만 큰 브랜드는 동시 요청 40 에서 5.9 초 · 80 에서 55% 실패 — 해결은 카운터 비정규화이고 선택 심화라 캐시 뒤로 미룬다. ### 측정의 한계 (먼저 적어 둔다)

- 노트북 한 대에서 Testcontainers · Docker 로 돌린다. 절대값이 아니라 **같은 환경에서의 전후 비교**만 의미가 있다.
- 동시 요청은 테스트 스레드로 만든 통제된 부하다. 운영 부하가 아니다.
- seed B 의 분포는 실제 자료가 아니라 원리를 옮긴 것이다(SEED 의 뒤집을 조건).
