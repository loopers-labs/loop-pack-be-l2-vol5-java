# W4 상품 조회와 Redis 캐시 채점 기준

2026-10-12에 제공된 [과제 원문](assignment-original.md)을 이번 주 평가 기준으로 사용한다. 목표는 기존 상품 조회의 병목을 줄이면서 변경·캐시 장애 뒤에도 기존 업무 계약을 지키는 것이다. 원문과 이 정리가 다르게 해석되면 원문을 우선한다.

이번 체크리스트는 **8개 항목**이다. W3의 9개 항목 통과 결과를 이번 주 완료로 이어받지 않는다. 기존 2·3주차 모델·API·삭제·소유권·주문 계약은 유지하고, 새 요구와 관련 회귀를 함께 평가한다. 이 파일은 채점 기준이며 구현 정책을 확정하거나 현재 프로젝트의 완료를 판정하는 문서는 아니다.

| 번호 | 원문의 체크 항목 | 충족 여부를 확인할 증거 |

채점할 때 각 항목은 충족·부분 충족·미충족·확인 불가로 구분하고 코드·문서·실행 결과를 근거로 붙인다. 원문에 없는 숫자 배점이나 성능 목표를 임의로 만들지 않는다. 설계 계획과 실제 구현, 테스트 작성과 실행 성공, 로컬 검증과 제출 완료를 구분한다.

## 설계에 정할 내용

기존 [전체 설계](../week2/commerce-erd-draft.md)에 다음을 추가하거나 수정한다. 실제 업무 계약과 미정 선택은 구분한다.

- 브랜드 필터·세 정렬·기존 페이지와 동점 기준·오류·응답 필드.
- 측정할 브랜드 필터+가격순 목록 요청과 요청당 SQL 수·좋아요 조회 비용.
- 목록 또는 상세 중 캐시할 공통 조회 한 경로, 재사용할 필드와 제외하거나 분리할 사용자별 정보.
- 해당 응답에 영향을 주는 모든 쓰기 경로와 DB 트랜잭션·캐시 변경의 경계.
- Redis 오류의 대기 제한·DB 우회, 표시 데이터의 허용 신선도·복구 조건.

AI 대안 검토에는 실제 SQL·실행 계획·요청당 SQL 수를 사용한다. 조건을 빼서 빨라지는 변경, 개인화 정보를 공용 키에 저장하는 변경, TTL만으로 변경 직후 최신성을 보장한다는 설명은 받아들이지 않는다.

## SQL과 인덱스 비교의 필수 조건

1. 격리된 실습 DB에 상품 **10,000개 이상**과 실제 관계·필수 값을 준비한다. 같은 seed를 재현할 수 있어야 하며 브랜드·가격·좋아요 수를 분산한다. 좋아요 0개·동점·인기 상품과 가격 동점 자료도 확인한다.
2. **브랜드 필터+price_asc의 기존 첫 페이지 요청**을 고정하고 실제 파라미터·기본값·페이지 크기를 적는다. 성능 측정을 위해 새 limit 계약으로 바꾸지 않는다.
3. 캐시 없이 개선 전후의 응답·요청당 SQL 수·EXPLAIN·EXPLAIN ANALYZE·반복 지연 시간을 비교한다. 사용 key·접근 경로·예상/실제 rows·loops·정렬 단계·준비 실행 수·측정 표본 수·지연 분포를 남긴다.
4. 실제 삭제·브랜드 노출·필터·정렬·조회 열에 맞는 인덱스 또는 쿼리 개선을 적용한다. 좋아요가 상품별 반복 조회라면 목록 단위로 줄인다. 이미 반복 조회가 아니라면 존재하지 않는 문제를 전제로 구조를 강제로 바꾸지 않는다.
5. 같은 seed와 입력에서 **정렬된 ID·가격·좋아요 수·페이지 정보**를 비교한다. 체크섬을 쓰면 직렬화 필드와 순서를 고정하고, 불일치한 실제 값을 확인한다. 결과가 달라진 실행은 성능 개선의 성공으로 세지 않는다.
6. seed와 인덱스 SQL은 기존 migration·fixture 방식에 맞춰 저장한다. 공유 DB 데이터나 다른 과제의 인덱스를 삭제해 비교하지 않는다.

원문의 seed 공식·브랜드 개수·합계는 구성 예시다. 특정 index 이름, Using index 표시, 특정 향상 배수, SQL 호출 수의 고정 목표는 정답이 아니다. 실제 병목·개선 결과·정확성과 측정 한계를 판단한다.

## 캐시의 정확성과 변경 책임

선택한 목록 또는 상세의 **공통 조회 한 경로**에 cache-aside를 연결한다. miss는 올바른 DB 결과를 유효 시간과 함께 저장하고, hit는 같은 조건의 결과를 반환하며 비싼 원본 조회를 줄인다.

키는 선택한 응답에 영향을 주는 필터·정렬·페이지·크기·응답 형식을 구분한다. 개인별 필드는 공용 payload에서 제외하거나 실제 사용자 경계를 분리한다. 매번 비싼 원본 조회를 모두 수행하고 사용하지 않는 캐시만 채우는 것은 hit 개선이 아니다.

변경 책임은 선택한 payload를 기준으로 추적한다. 기존 상품 생성·수정·삭제, 브랜드 변경·일괄 삭제, 좋아요 등록·취소, 관리자 재고 변경·주문 확정 등 응답에 영향을 주는 경로를 빠뜨리지 않는다. 가격 변경만 별도 새 서비스로 우회한 검증으로 기존 관리자 API 연결을 대신하지 않는다.

| 상황 | 지켜야 할 계약 |
| --- | --- |
| 장애·동시 채움이 없는 정상 변경 완료 뒤 새로 시작한 순차 조회 | 변경된 결과를 반환한다. TTL 만료까지 이전 값을 반환하는 것으로 정상 완료를 판단하지 않는다. |
| DB 변경 rollback | 변경 전 결과를 유지하고, 커밋되지 않은 새 결과를 게시하지 않는다. |
| commit 후 무효화 실패 또는 이전 조회의 늦은 채움 | 실제 DB commit 사실을 유지한다. 사전에 정한 표시 신선도·방지·만료·복구 정책과 복구 완료 조건을 검증한다. |
| 모든 장면에서의 필수 보호 | 삭제 대상 비노출·소유권을 유지하고 주문 금액·재고·포인트 판단은 기존 DB 규칙으로 처리한다. 표시 신선도 선택을 이유로 이 계약을 완화하지 않는다. |

장애 중 표시 가격·설명 등의 일시적 오래된 값을 허용한다면 대상 필드와 허용 조건, 만료·무효화 재처리 또는 원본 우회 조건, 복구 완료 판정을 정하고 테스트한다. 정상 순차 조회와 장애 상황의 기준을 섞지 않는다. TTL 또는 `@Transactional`과 캐시 삭제의 조합만으로 모든 경쟁·장애에서 최신성이나 전역 시간 상한을 보장한다고 쓰지 않는다.

payload 축소·원본 합성 또는 삭제·접근 가능 여부의 권위 확인으로 필수 계약을 보호할 수 있다. 이런 DB 확인 비용도 hit 측정에 포함한다. **hit의 DB 호출 0회는 필수가 아니다.**

## 필수 변경과 장애 재현

실제 애플리케이션·MySQL·Redis를 연결하여 다음 8개 장면을 확인한다. 전부 mock인 캐시 테스트만으로 완료 처리하지 않는다.

| 장면 | 확인할 결과 |
| --- | --- |
| 같은 입력의 DB-only·miss·hit | 상품·정렬·페이지 결과 일치와 hit의 비싼 DB 조회 감소 |
| 기존 관리자 가격 수정 commit 후 재조회 | 새 가격과 필요한 목록 순서 반영, 과거 주문 금액 유지 |
| 캐시된 상품의 삭제와 브랜드 일괄 삭제 | 해당 상품 제외, 다른 브랜드·과거 주문 유지 |
| 나머지 영향 쓰기 | 영향에 맞는 결과 반영. 좋아요 수를 담았다면 등록·취소 포함 |
| DB 변경 rollback | 변경 전 결과와 올바른 캐시 상태 유지 |
| commit 후 캐시 무효화 실패 | DB commit 사실 보존, 허용한 표시 신선도와 복구 후 원본 일치 |
| 이전 조회의 늦은 캐시 채움 | 오래된 재삽입을 결정적으로 재현하고 선택한 정책의 결과 확인 |
| Redis 중단·재시작 | 제한된 대기 후 DB 응답, 복구 후 정확한 재채움 |

무효화 실패와 늦은 채움은 테스트 훅·래치로 순서를 통제한다. 예를 들어 `이전 DB 결과 읽기 → 관리자 변경 commit → 이전 결과 캐시 저장 → 새 조회`를 만든다. 단순 동시 시작만으로 늦은 채움을 재현했다고 하지 않는다. 이 장면에서도 삭제·다른 사용자 정보·주문 판단은 보호하며 유한한 timeout과 worker 정리를 적용한다.

Redis 장애 실험에서는 다음을 확인한다.

- 실제 사용하는 template·연결·직렬화·대기 시간과 읽기 endpoint를 기록한다. 기본 REPLICA_PREFERRED 및 별도 master 연결을 확인하고 replica lag를 최신성 보장으로 오인하지 않는다.
- 장애 전에 miss→hit의 원본 호출 감소와 복구 절차를 확인한다.
- 실제 연결된 모든 읽기 endpoint를 중단한다. master와 replica를 모두 읽는다면 둘 다 중단한다. Testcontainers와 Compose 대상을 혼동하지 않는다.
- DB가 정상이고 통제한 부하를 감당하는 조건에서 기존 정상 응답·대기 시간·캐시 오류를 확인한다. DB까지 실패하면 빈 목록·가격 0으로 감추지 않고 기존 오류 계약을 따른다.
- 동일 Redis를 재시작하여 연결과 새 조회·정확한 재채움을 확인한다. 자신이 시작한 실험 자원만 정리하고 공유 Redis FLUSHALL이나 다른 작업의 컨테이너 중단을 하지 않는다.

## 선택 사항과 미정 정책

다음 선택은 원문만으로 임의 확정하지 않는다. 구현 전에 기존 설계와 함께 결정한다.

| 선택할 것 | 평가할 기준 |
| --- | --- |
| 목록 또는 상세 | 공통 조회 한 경로면 충분하며 선택 이유와 실제 비용 감소를 확인 |
| payload·키·TTL | 공통/개인화 경계와 조회 조건을 유지하고 선택한 유효 시간을 적용 |
| 인덱스 또는 쿼리 개선 | 실행 계획·결과 동일성·반복 측정에 근거해 선택 |
| 무효화·늦은 채움 대응 | 필수 보호 계약을 유지하면서 표시 신선도·복구 정책을 구체화 |
| Redis endpoint·대기 제한 | 실제 연결과 유한한 대기·DB 우회·복구를 측정하고 검증 |

**DB revision은 선택 가능한 예시이지 필수 구조가 아니다.** 채택한다면 영향 쓰기와 revision을 같은 DB 트랜잭션으로 변경하고, 현재 revision을 DB에서 확인하며, miss의 결과와 revision은 일관된 DB 읽기로 얻는다. 오래된 결과를 새 revision 키에 저장하지 않아야 한다. 모든 영향 쓰기의 참여·잠금 순서·rollback을 유지하고, hit의 DB 조회와 공통 revision 행 경합 비용도 측정한다. TTL은 옛 키 정리 수단으로 구분한다.

좋아요 카운터 비정규화, 목록·상세 모두 캐시, 데이터 쏠림·깊은 페이지 비교, stampede 완화는 선택 심화다. 추가한다면 중복·동시 변경·정합성을 확인한다. 이벤트·배치 집계 시스템, 특정 인덱스 구조, 특정 테스트 클래스명은 필수로 만들지 않는다.

## 실행과 제출

관련 테스트 이름은 실제 구현에 맞춘다. 다음은 원문의 예시이며 테스트 수 0이나 연결 실패를 통과로 세지 않는다.

```bash
./gradlew :apps:commerce-api:test --tests '*ProductQuery*Test'
./gradlew :apps:commerce-api:test --tests '*ProductCache*Test'

# 현재 Java 프로젝트의 최종 검사
./gradlew :apps:commerce-api:check
```

제출물은 변경 코드·테스트, 재현 seed·인덱스 변경, 실행 계획·결과 비교, 갱신 설계 문서와 기술 글이다. PR에는 병목·선택 방법·정확성·장애 결과와 측정 환경·표본의 한계를 짧게 적는다. 체크리스트 충족과 기술 글·PR의 실제 제출은 별도로 확인한다.

## 채점 진행 원칙

- 문서에 적었다는 사실만으로 실행·개선 완료를 인정하지 않는다. 실제 코드와 결과를 대조한다.
- 테스트가 통과해도 필요한 장면이 빠졌거나 기대값이 약해졌다면 해당 항목을 충족으로 세지 않는다.
- 표시 신선도의 선택지를 강제로 한 가지 정답으로 바꾸지 않는다. 선택하지 않은 심화 기능으로 감점하지 않는다.
- 평가 요청에서는 문제와 수정 방향을 알려 주고, 구현 요청이 있을 때 합의한 범위에서 수정한다.
- 이번 기준 저장은 현재 프로젝트의 W4 채점 결과가 아니다. 다음 평가부터 위 8개 항목으로 확인한다.
