## 3. 개선 전 기준선

### 요청당 SQL 수

상품 목록 1회, 브랜드 일괄 조회 1회, 상품별 좋아요 COUNT 20회로 **요청당 조회 SQL은 22회**였다.<br>

```sql
SELECT p.id, p.brand_id, p.created_at, p.deleted_at,
       p.name, p.price, p.stock, p.updated_at
FROM products p
LEFT JOIN brands b ON b.id = p.brand_id
WHERE p.deleted_at IS NULL AND b.id = 7
ORDER BY p.price, p.id
LIMIT 20;
```

```sql
SELECT b.id, b.created_at, b.deleted_at, b.name, b.updated_at
FROM brands b
WHERE b.id IN (7);
```

```sql
SELECT COUNT(l.id)
FROM likes l
WHERE l.product_id = 5406;
```

### EXPLAIN

실측 지연을 수집한 뒤, 같은 SQL을 MySQL에서 `EXPLAIN`과 `EXPLAIN ANALYZE`로 확인했다.<br>
`EXPLAIN`의 `rows`와 `filtered`는 실제 실행 결과가 아니라 옵티마이저의 추정치다.<br>
`rows`는 읽을 것으로 예상한 행 수이고, `filtered`는 그중 조건을 통과할 것으로 예상한 비율이다.

#### 상품 목록 조회

계획은 SQL에 적힌 순서와 달리 브랜드 `b`를 먼저 찾고, 그 브랜드 ID로 상품 `p`를 조회한다.

| 테이블 | 접근 방식 | 사용 key | 예상 rows·filtered | Extra |
| --- | --- | --- | ---: | --- |
| `b` (브랜드 조인) | `const` | `PRIMARY` | 1·100% | `Using index; Using filesort` |
| `p` (상품) | `ref` | `FKa3a4mpsfdf4d2y6r8ra3sc8mv` | 17,440·10% | `Using where` |

`b`는 `b.id = 7`을 기본 키로 한 번 찾는 `const` 접근이다.<br>
`p`는 브랜드 ID 인덱스로 연결되는 `ref` 접근이며, 예상 조회 행은 17,440개다.<br>
`filtered=10%`를 적용하면 삭제 조건을 통과할 행은 약 1,744개로 추정된다.

상품 조회에 사용한 key는 브랜드 ID 인덱스라 `p.price, p.id` 순서를 제공하지 않는다.<br>
따라서 `Using filesort`가 표시되고 별도 정렬 단계가 필요하다.<br>
표시가 `b` 행의 `Extra`에 붙어 있어도 정렬 대상은 브랜드가 아니라 상품이다.

#### 브랜드 일괄 조회

기준 요청은 브랜드 `7`로 필터링되고, 반환된 상품 20개의 브랜드 ID도 모두 `7`이다.<br>
따라서 `findAllByIds`에 전달되는 중복 제거 ID는 `[7]`이며 실제 SQL 조건은 `b.id IN (7)`이다.<br>
메서드는 여러 브랜드 ID를 한 번에 받을 수 있지만, 이 측정 요청에서는 브랜드 한 건을 조회한다.

| 테이블 | 접근 방식 | 사용 key | 예상 rows·filtered | Extra |
| --- | --- | --- | ---: | --- |
| `b` (브랜드) | `const` | `PRIMARY` | 1·100% | — (`NULL`) |

`id=7`이 기본 키와 일치하므로 옵티마이저는 브랜드 행 한 건을 `const`로 찾는다.<br>
예상 행은 1개이고 필터 통과율은 100%다. `Extra`는 `NULL`로, 이 조회에 별도의 정렬이나 필터 연산이 표시되지 않았다.<br>
브랜드 필터가 없는 목록에서는 페이지에 포함된 여러 브랜드 ID가 `IN (...)`에 전달될 수 있다.

#### 좋아요 COUNT

좋아요 수 SQL은 `product_id`만 조건으로 지정한다.<br>
선택된 유니크 인덱스는 `(user_id, product_id)` 순서라 검색 조건이 인덱스의 첫 컬럼부터 시작하지 않는다.

| 테이블 | 접근 방식 | 사용 key | 예상 rows·filtered | Extra |
| --- | --- | --- | ---: | --- |
| `l` (좋아요) | `range` · skip scan | `uk_like_user_product(user_id, product_id)` | 504,460·100% | `Using where; Using index for skip scan` |

MySQL은 `user_id`의 인덱스 값 범위를 건너뛰며 각 범위에서 `product_id`를 찾는 skip scan을 선택했다.<br>
`Using index for skip scan`은 이 접근 방식이 인덱스를 이용한다는 표시이고, `Using where`는 조회 조건을 적용한다는 표시다.

`rows=504,460`은 인덱스에서 찾아낼 것으로 예상한 행 수이지 좋아요 개수나 COUNT 결과가 아니다.<br>
아래 `EXPLAIN ANALYZE`에서 확인한 실제 행 수와 비교하면 추정과 실제 사이의 차이를 볼 수 있다.

### EXPLAIN ANALYZE

`EXPLAIN ANALYZE`는 쿼리를 실제 실행하므로 연산자별 실제 행 수와 소요 시간도 보여준다.<br>
상품 목록 조회 표는 데이터가 흐르는 순서대로, 인덱스 조회부터 `LIMIT`까지 정리했다. 시간 단위는 밀리초다.

#### 상품 목록 조회

| 연산자 (아래에서 위로) | 예상 rows | 실제 rows | loops | 실제 시간 |
| --- | ---: | ---: | ---: | ---: |
| 상품 인덱스 조회 (`brand_id=7`) | 17,440 | 10,000 | 1 | 1.86–71.5 ms |
| 삭제 조건 필터 | 17,440 | 10,000 | 1 | 1.88–71.9 ms |
| `price, id` 정렬 | 17,440 | 20 | 1 | 72.7–72.7 ms |
| `LIMIT 20` | 20 | 20 | 1 | 72.7–72.7 ms |

실제 실행에서는 브랜드 `7`의 상품 10,000개를 인덱스에서 읽었고, 모두 `deleted_at IS NULL` 조건을 통과했다.<br>
이 ANALYZE 출력에서 삭제 조건 필터의 예상 행 수는 17,440개이고 실제 행 수는 10,000개다.<br>
앞 절의 1,744개는 일반 EXPLAIN의 `rows × filtered` 환산값이며, 이 표는 ANALYZE의 TREE 출력에 표시된 예상 행 수를 기록했다.<br>
정렬 단계는 이 10,000개를 입력받아 가격과 ID 기준의 상위 20개를 반환했다.

최상위 `LIMIT`까지 걸린 시간은 72.7 ms다.<br>
각 상위 연산자의 시간에는 하위 연산자 실행이 포함되므로 표의 시간을 합산해 전체 시간으로 계산하지 않는다.

#### 브랜드 일괄 조회

| 연산자 | 예상 rows | 실제 rows | loops | 실제 시간 |
| --- | ---: | ---: | ---: | ---: |
| 브랜드 조회 (`id=7`) | 1 | 1 | 1 | 기준 출력에 없음 |

실제 실행계획은 브랜드 행 한 건을 반환했다.<br>
`const` 조회라 결과 행을 실행 전에 가져오며, 저장된 기준 출력에는 개별 소요 시간이 남아 있지 않다.

#### 좋아요 COUNT

| 연산자 (아래에서 위로) | 예상 rows | 실제 rows | loops | 실제 시간 |
| --- | ---: | ---: | ---: | ---: |
| 복합 인덱스 skip scan (`product_id`) | 504,460 | 상품별 0~10 | 1 | 기준 출력에 없음 |
| COUNT 집계 (`COUNT(l.id)`) | 1 | 1 | 1 | 첫 실행 25.5 ms |

skip scan의 실제 행 수는 상품마다 달랐고, 옵티마이저 추정치 504,460개와 큰 차이가 있었다.<br>
이 추정치를 실제 좋아요 수로 해석하면 안 된다. COUNT 집계는 일치하는 좋아요가 없어도 결과 한 행을 반환하고 값은 `0`이다.<br>
목록 조회는 상품마다 COUNT SQL을 별도로 실행하므로 기준 요청에서는 이 조회가 20회 반복된다.

좋아요 20회 조회의 요청당 비용은 단일 VU 반복 측정의 Performance Schema 전후 차이로 확인했다.<br>
준비 3회와 실측 1,000회를 포함한 1,003개 요청의 기존 집계다.

| 측정 요청 수 | COUNT 호출 수 | 누적 DB 실행 시간 | 요청당 좋아요 조회 시간 (평균) |
| ---: | ---: | ---: | ---: |
| 1,003회 | 20,060회 | 101,000.601 ms | 100.699 ms |

요청당 평균은 누적 DB 실행 시간을 1,003으로 나눈 값이다.<br>
단건 ANALYZE의 25.5 ms와 위 집계는 별도 측정이며, 이 DB 실행 시간은 아래 k6의 HTTP 지연과 측정 범위가 다르다.

### 실행계획 기준 개선 판단

현재 측정 요청(`brandId=7&page=0&size=20&sort=price_asc`)에서 확인한 판단이다.

| 조회 | 판단 | 근거 |
| --- | --- | --- |
| 상품 목록 | 개선 후보 | 20개를 반환하지만 상품 10,000개를 읽고 `price, id`로 정렬했다. |
| 브랜드 일괄 조회 | 현재 요청에서는 추가 개선 근거 없음 | 브랜드 ID 한 개를 기본 키로 한 번 조회해 한 행을 반환했다. |
| 좋아요 COUNT | 개선 후보 | 상품마다 COUNT를 실행해 요청당 20회 발생했고, `product_id` 조건에 복합 인덱스 skip scan을 사용했다. |

브랜드 조회 판단은 브랜드 필터가 있는 이 요청에 한정한다. 필터가 없는 요청은 페이지에 여러 브랜드가 포함될 수 있으므로 별도 측정 없이 같은 판단을 적용하지 않는다.

### 반복 HTTP 지연 (k6)

SQL 상세 로그와 Hibernate 통계를 끈 API에 k6로 같은 요청을 보냈다. 단일 VU가 준비 3회 후 1,000회를 실행했다. `noConnectionReuse=true`로 요청마다 새 연결을 열었다.

모든 응답에서 `200 OK`, `meta.result=SUCCESS`, 상품 20개와 기준 체크섬을 확인했다. 준비 요청을 뺀 1,000개 응답의 지연 분포다.

| 실측 표본 | 최소 | 평균 | p50 | p95 | p99 | p99.9 | 최대 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000회 | 152.468 ms | 164.350 ms | 159.484 ms | 186.122 ms | 283.177 ms | 352.625 ms | 373.309 ms |

지연 분포는 최소·평균·p50·p95·p99·p99.9·최대 값을 기록한다.<br>
p99.9는 저장된 실측 1,000개 원본 표본에서 계산했다. 현재 표본 수에서는 상위 극소수 요청에 민감한 참고 지표로 해석한다.

측정 시간은 k6 `response.timings.duration`이며 요청 전송·서버 대기·응답 수신 시간을 포함하고 TCP 연결 수립 시간은 포함하지 않는다.<br>
단일 VU·동시성 1 결과이므로 높은 동시 부하의 지연을 나타내지는 않는다.

#### 동시 VU 참고 측정

같은 요청·DB·응답 체크섬에서 실측 1,000회를 유지하고 VU당 준비 요청을 3회씩 실행했다.

| VU | 실측 표본 | 최소 | 평균 | p50 | p95 | p99 | p99.9 | 최대 | HTTP 실패율 | 응답 검증 통과율 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1,000 | 152.468 ms | 164.350 ms | 159.484 ms | 186.122 ms | 283.177 ms | 352.625 ms | 373.309 ms | 0% | 100% |
| 10 | 1,000 | 346.916 ms | 395.258 ms | 371.398 ms | 586.954 ms | 661.000 ms | 680.595 ms | 715.004 ms | 0% | 100% |
| 100 | 1,000 | 1,084.315 ms | 3,429.975 ms | 3,377.774 ms | 4,682.444 ms | 4,989.746 ms | 5,164.483 ms | 5,215.069 ms | 1.7% | 98.3% |

지연 통계는 각 VU의 저장된 원본 표본에서 집계했다. 표의 지연 분포·HTTP 실패율·응답 검증 통과율은 준비를 제외한 실측 1,000회 기준이다.<br>
지연 분포에는 실패 응답의 소요 시간도 포함한다.

100 VU의 실측 요청은 HTTP 200이 983회, HTTP 500이 17회였다. 정상 응답 983개는 모두 기준 응답 검증을 통과했다.<br>
준비 요청에서도 HTTP 500이 24회 발생해, 준비 포함 1,300회 중 총 41회가 실패했다. API 로그에서 Hikari 연결 풀 한계에 도달한 것을 확인했다.

10 VU는 요청 오류와 응답 불일치가 없었지만 Performance Schema 호출 수가 예상과 달랐다. 따라서 SQL 호출 수·비용 비교 기준은 단일 VU 측정으로 둔다.
