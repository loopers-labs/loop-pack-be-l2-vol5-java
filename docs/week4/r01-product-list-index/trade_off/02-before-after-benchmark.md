# JMeter·실행 계획 전후 비교

[← 전체 선택 현황](total_trade_off.md) · [첫 실행 안내](../jmeter-guide.md)

## 사용자 결정

| 항목 | 채택 | 다른 선택지 |
|---|---|---|
| 데이터 규모 | 상품 100만 개 | 10만 개·1만 개 |
| HTTP 대상 | 전체 최신순·전체 가격순·브랜드별 가격순 | 6종 전체 또는 변경 2종만 |
| 동시 부하 | 1명과 10명을 별도로 측정 | 1명만 또는 10명·50명 |
| 실행 역할 | 사용자가 JMeter 직접 실행 | Codex가 실제 부하까지 실행 |
| 실행 계획 | Codex가 목록·COUNT SQL의 EXPLAIN·EXPLAIN ANALYZE 수집·분석 | HTTP 수치만 비교 |

위 선택은 2026-10-16 대화로 확인했다. 사용자는 JMeter를 처음 사용하므로 설치 확인·파일 열기·1건 시험부터 안내한다.
이후 사용자 선택으로 각 실행의 warm-up 20초·본 측정 60초를 확정했고, 시간 단축 요청에 따라 반복은 3회에서 2회로 줄였다.
ramp-up 5초와 요청 timeout 등 세부 재현 조건은 [실행 조건](04-jmeter-run-settings.md)에 기록한다.

## 비교 경계

- 전후 모두 `page=0&size=20`, 같은 seed·브랜드 ID·쿼리·삭제 조건·응답 열을 유지한다.
- 인덱스 2개 외에 쿼리·캐시·페이지·업무 로직을 함께 바꾸지 않는다.
- 무필터 COUNT 캐시는 실험에서만 끄고 좋아요 집계를 중지해 측정 중 조건을 고정한다. 운영 정책의 변경이 아니다.
- 초기 스키마는 현재 전체 모델로 별도 준비한다. 측정 실행은 `ddl-auto=none`, SQL 출력은 끄고 로그·연결 풀을 동일하게 맞춘다.
- JMeter는 3종을 각각 실행해 HTTP 지연 분포·처리량·오류율·표본 수를 남긴다. warm-up 결과를 측정 표본에 섞지 않는다.
- 결과는 `.jtl` 원본과 HTML 보고서·실행 조건을 보존한다. 전체 응답 일치 검증은 별도로 수행한다.
- 실제 애플리케이션이 실행한 SQL을 확보하고 바인딩·전체 Projection을 보존해 계획을 분석한다. 현재 DAO 코드를 SQL로 옮긴 자료는 실캡처와 구분한다.
- EXPLAIN은 key·접근 경로·예상 rows, EXPLAIN ANALYZE는 실제 rows·loops·시간·정렬 단계를 비교한다. 요청당 SQL 수도 관측한다.
- EXPLAIN 노드 시간을 모두 더해 HTTP 지연으로 해석하거나, 반복 표본 없는 한 번의 DB 시간을 JMeter 결과로 대신하지 않는다.
- 단순 배수·filesort 유무를 미리 성공으로 정하지 않는다. 좋아요순 등 이번 부하 대상 밖의 목록 계약은 관련 회귀로 확인한다.

## 도구 선택과 한계

JMeter GUI에서 준비한 파일을 열고 소량 요청을 확인한 뒤, 실제 부하는 준비된 CLI 명령으로 실행하고 HTML 보고서를 본다.
이는 초보자도 실행 순서를 따라가면서 반복 측정을 재현하기 위한 방법이다.
[Apache JMeter 실행 안내](https://jmeter.apache.org/usermanual/get-started.html)와
[테스트 계획 구성](https://jmeter.apache.org/usermanual/test_plan.html)을 기준으로 후속 파일·명령을 준비한다.

현재 전용 스키마 `week4_r01_index_benchmark`에 실제 100만 상품 적재·검증을 완료했다.
기존 `loopers` 테이블은 이전 모델이 포함돼 있어 실험 데이터로 사용하지 않는다.
기존 R04 자료의 스키마·수기 SELECT·1회 수치를 이번 앱/JMeter 전후 결과로 옮겨 적지 않는다.
