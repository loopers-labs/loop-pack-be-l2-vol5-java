# JMeter 기준선 실행 설정

[← 전체 선택 현황](total_trade_off.md) · [전후 비교 경계](02-before-after-benchmark.md) · [첫 실행 안내](../jmeter-guide.md)

상태: **첫 CLI 측정이 최신순 10명에서 timeout으로 중단됐다.** 아래는 확정 설정이며 부분 결과는 result.md에 보존한다.
Codex가 도구·JMX·실행 스크립트와 사전 확인을 준비하고 사용자가 본 측정을 직접 실행한다.
이후 사용자가 실행 주체를 변경해 Codex에 after CLI 전체를 위임했다. [12개 실제 결과](../baseline/jmeter-after/README.md)를 별도 보존한다.

## 확정한 대상과 시간

| 시나리오 속성 | 실제 HTTP 요청 |
|---|---|
| `latest` | `GET /api/v1/products?sort=latest&page=0&size=20` |
| `price` | `GET /api/v1/products?sort=price_asc&page=0&size=20` |
| `brand7` | `GET /api/v1/products?brandId=7&sort=price_asc&page=0&size=20` |

| 항목 | 채택 값 |
|---|---|
| 동시 사용자 | 1명·10명을 각각 실행 |
| 한 run | 같은 시나리오·동시 수로 워밍업 20초 → 본 측정 60초 |
| 반복 | 각 시나리오·동시 수 조합을 2회 |
| 본 측정 수 | 3개 시나리오 × 2개 동시 수 × 2회 = 12개 |
| 워밍업 결과 | 각 run마다 별도 JTL로 저장하고 본 측정에서 제외 |
| ramp-up | 5초, 워밍업과 본 측정에 각각 적용 |
| 연결 / 응답 timeout | 3,000ms / 30,000ms |

각 본 측정의 60초에는 ramp-up 설정 5초가 포함된다. 이는 실행을 완만하게 시작하기 위한 구현 선택이며,
목표 동시 수가 유지되는 구간을 60초 확보한다는 뜻은 아니다. 스레드 시작·진행 중인 요청의 완료 시점에 따라 실제 표본 구간도 달라진다.

사용자의 시간 단축 요청에 따라 반복을 3회에서 2회로 줄였다. 설정 시간 합계는 `12 × (20 + 60) = 960초`, 16분이다.
JMeter 프로세스 시작·종료와 보고서 생성 등을 포함하면 한 번의 변경 전 전체 실행은 **약 17~20분**으로 예상한다.
이 시간은 실측 완료 시간이 아니며 요청 종료 지연·실행 환경에 따라 더 길어질 수 있다.
각 run의 표본 수는 시간과 응답 속도에 따라 결정되므로 같은 요청 수를 보장하지 않는다.

## 실행 순서와 부하 해석

| 반복 | 시나리오 순서 |
|---|---|
| 1회차 | `latest` → `price` → `brand7` |
| 2회차 | `price` → `brand7` → `latest` |

각 시나리오에서 1명 run을 마친 뒤 10명 run을 실행한다. 모든 run은 자기 워밍업 JTL과 본 측정 JTL을 따로 가진다.
시나리오 순환은 항상 같은 요청이 먼저 실행되는 영향을 조금 분산하기 위한 선택이다.
무작위 순서는 아니며, 동시 수의 순서는 고정이므로 워밍업·실행 순서의 편향을 없앤다고 보장하지 않는다.
앱·DB 프로세스와 데이터는 전체 실행 동안 유지하고 run 사이에 재시작·초기화하지 않는다.

각 스레드는 응답을 받은 뒤 즉시 다음 요청을 보내는 **closed-loop** 방식이다. think time과 목표 TPS 제한은 두지 않는다.
서버가 느려지면 같은 스레드의 다음 요청도 늦어져 요청 유입률이 낮아질 수 있다.
따라서 결과는 동시 1명·10명에서 관찰한 지연·처리량·오류율로 해석하고,
일정 TPS에서의 지연이나 실제 서비스의 독립적인 요청 도착·수용 한계로 일반화하지 않는다.

시나리오·동시 수·반복별로 Samples, 오류율, 평균, p50·p95·p99, 처리량과 실제 시간을 보존한다.
서로 다른 시나리오나 동시 수를 섞어 평균내지 않고 2회 결과의 편차도 함께 본다.
표본이 적은 p99나 오류가 발생한 실행은 그 조건을 함께 기록한다.

## 환경과 응답 확인

- 도구는 Apache JMeter **5.6.3 공식 ZIP**으로 고정하고 같은 배포의 공식 SHA-512와 다운로드 파일을 대조한다. 기존 Java 21을 사용한다.
- MySQL은 같은 전용 DB의 상품 100만 개를 사용한다. 변경 전은 기존 보조 인덱스 4개, 변경 후는 기존 4개와 새 전체 최신순·가격순 2개의 6개 상태다.
- 버퍼 풀은 기본 **128MiB (`134217728` bytes)** 를 유지한다. DB 주요 설정·앱/DB 버전·연결 풀·로그 조건을 전후 기록하고 임의로 튜닝하지 않는다.
- 조회 앱은 `local`, 전용 DB URL, `ddl-auto=none`, `scheduler.like-count.enabled=false`, `query.product-count-cache.ttl=0s`로 실행한다.
- 본 측정용 앱의 SQL·바인딩 로그는 끈다. 실제 SQL 캡처와 실행 계획 확인은 별도 앱 기동 구간에서 수행하고 본 측정과 섞지 않는다.
- seed·데이터 변경·인덱스 변경·Gradle 검사 등 다른 무거운 작업을 동시에 실행하지 않는다.

준비 단계에서 세 실제 HTTP 요청의 응답을 각각 저장하고 정렬된 상품 ID·가격·좋아요 수·페이지 정보를 검증한다.
그 기준 응답 파일로 시나리오마다 1명·1회 **`validation=full` smoke 확인**을 통과한 뒤 본 측정을 시작한다.
full 검증은 상품 목록과 페이지 결과를 기준값과 대조하는 절차이며 측정 표본에 넣지 않는다.
워밍업·본 측정은 **`validation=light`** 로 HTTP 상태와 최소 응답 형태를 확인해 반복 검증 비용을 줄인다.
light만으로 모든 상품 필드·정렬·페이지 결과가 같다고 주장하지 않고 full smoke·실제 HTTP 검증 근거를 함께 보존한다.
오류가 있으면 원인을 해결한 뒤 해당 조합을 다시 실행하고 이전 오류 원본을 덮어쓰지 않는다.

GUI는 JMX 열기와 소량 요청 확인에 사용하고, 본 측정은 CLI로 실행한다.
무거운 Listener와 전체 응답 저장을 끄고 JTL·JMeter 로그·HTML 보고서·실행 인자와 버전을 보존한다.
이 선택은 [Apache JMeter 실행 안내](https://jmeter.apache.org/usermanual/get-started.html)와
[부하 도구의 자원 사용을 줄이는 공식 권장 사항](https://jmeter.apache.org/usermanual/best-practices.html#lean_mean)에 따른다.

## 매개변수와 보존 경계

JMX는 실행별 값을 속성으로 받되, 이번 기본 실행에서는 다음 값을 사용한다. `price`는 JMX 시나리오 이름이며 API의 `sort` 값은 `price_asc`다.

| JMeter 속성 | 기본 실행 값·용도 |
|---|---|
| `scenario` | `latest` / `price` / `brand7` 중 하나 |
| `threads` | `1` 또는 `10` |
| `rampup` | `5`초 |
| `duration` | 워밍업 `20`초, 본 측정 `60`초 |
| `loops` / `scheduler` | `-1` / `true`, 지정 시간 동안 반복 |
| `host` / `port` | `localhost` / `18080`, 로컬 조회 앱 |
| `connectTimeout` / `responseTimeout` | `3000` / `30000`ms |
| `validation` | 사전 smoke `full`, 워밍업·본 측정 `light` |
| `expectedFile` | 세 시나리오의 확인된 기준 응답을 모은 JSON 파일 절대 경로 |

실행 래퍼는 `WarmupSeconds=20`, `DurationSeconds=60`, `Repetitions=2`, `RampUpSeconds=5`를 기본으로 매핑한다.
설정 오입력을 잡기 위해 동시 수는 1·10만, 시간·반복 수는 정수 범위만 허용한다.
래퍼의 허용 범위는 워밍업 1~120초, 본 측정 1~600초, 반복 1~10회, ramp-up 1~30초다.
이 범위는 입력 검증용이며 이번에 합의한 기본값을 바꿔 측정해도 같은 비교 조건으로 간주한다는 뜻은 아니다.
짧은 도구 점검·smoke 결과는 이름과 실행 인자를 본 측정과 구분해 남긴다.

워밍업 JTL을 본 측정에 합치지 않고, 각 시나리오·동시 수·반복·전후 구분별 원본을 새 경로에 저장한다.
JMeter 종료 코드만으로 성공을 판정하지 않고 JTL의 실제 표본 수·실패 여부도 확인한다.
첫 CLI 실행의 실제 표본·오류율은 result.md에 기록하며, 전체 미실행 조합이나 개선 배수를 추정해 채우지 않는다.

## 실시간 GUI 추가 선택

첫 CLI 실행 중단 뒤 사용자가 실시간 UI로 확인하기를 요청했다.
[GUI 안내](../jmeter-ui-guide.md)의 전용 JMX는 같은 HTTP·light 검증·30초 응답 timeout으로
20초 워밍업과 60초 본 측정을 순차 실행한다. 본 측정의 Aggregate Report만 화면에 표시한다.
한 조합씩 사용자가 Start를 누르며 JTL을 구분 저장한다. GUI 표의 표시 비용이 있으므로 CLI와 GUI 표본을 합치지 않는다.
DB·인덱스·서버 설정은 변경하지 않는다. GUI 로딩 확인은 부하 측정 실행으로 기록하지 않는다.
