## 3. 후속 JMeter·인덱스 추가

사용자는 직접 JMeter 본 측정을 실행하며 warm-up 20초·본 측정 60초를 선택했다.
가독성 개선과 시간 단축 요청에 따라 반복은 3회에서 2회로 줄였다. 본 측정 12개, 예상 약 17~20분이다.
3종 요청 × 동시 1명/10명을 각각 측정한다. ramp-up 5초는 각 실행 시간에 포함한다.
사용자가 기존 4개 상태에서 측정한 다음 새 인덱스 2개를 적용하고, 같은 조건의 응답·계획·JMeter 결과를 비교한다.
SQL 캡처와 부하 측정은 분리하며, JMeter 결과가 모이기 전에는 전체 성능 개선 검증을 완료로 표시하지 않는다.

## 4. 유지할 경계와 검사

Hibernate DDL은 Runner보다 먼저 실행된다. 최초 schema 생성 전에 실제 대상 URL·빈 스키마를 확인한다.
JDBC 의존은 Jdbc 클래스로 제한하며 일반 업무 쓰기와 JPA 트랜잭션에 fixture 작업을 섞지 않는다.
기존 공유 DB·인덱스·컨테이너를 삭제하지 않는다. 실제 SQL은 전체 Projection·JOIN·삭제 조건·동점 기준을 보존한다.

실제 대량 적재에서 최초 600초 제한보다 실행이 길어지는 것을 확인했다. 재실행 전 seed 트랜잭션 제한을
3,600초로 늘리고, 상품·좋아요 INSERT SELECT에 PK 순서를 명시한다. 데이터 공식·건수·기존 인덱스와
적재·검증의 단일 트랜잭션 경계는 유지한다. 최초 실행 결과와 재실행 결과는 별도로 기록한다.
ApplicationRunner 전환과 이 보완 뒤 모듈 check는 284건, 실패·오류·skip 0으로 통과했다.
첫 실행은 검증 단계의 TransactionTimedOutException으로 실패했고 전체 롤백 뒤 대상 5개 테이블의 0건을 확인했다.
이후 승인 계획에 없던 버퍼 풀 1GiB 변경과 재실행을 진행했으나 사용자 지적으로 재실행을 중단했다.
버퍼 풀은 원래 128MiB로 원복했고 확장·축소 완료 상태를 확인했다. 이 실행을 기준선으로 사용하지 않는다.
재실행 프로세스 종료 뒤 MySQL 백그라운드 롤백이 남았으나, 후속 확인에서 남은 트랜잭션 0개와 대상 5개 테이블 0건을 확인했다.
버퍼 풀 크기를 실제 지연의 주원인으로 확정하지 않으며, 추가 DB 전역 설정 변경은 현재 범위에 포함하지 않는다.

2026-10-16 추가 지시에 따라 다음 적재 전에 INSERT 6개의 EXPLAIN과 FORMAT=TREE를 수집했다.
사전 상태와 계획 원문은 [사전 확인](baseline/seed-preflight.txt), [EXPLAIN SQL](baseline/seed-explain-before.sql),
[실행 계획](baseline/seed-explain-before.txt), [해석](baseline/seed-explain-review.md)에 보존한다.
버퍼 풀은 128MiB, 실제 테이블은 비어 있지만 이전 통계는 남아 있어 추정 rows를 실제 건수로 해석하지 않는다.
**계획을 사용자에게 설명하고 명시적인 적재 승인을 받기 전에는 seed를 실행하지 않는다.**
사용자가 버퍼 풀 포함 다른 설정 유지·3,600초 제한·ID순·한 번 적재를 명시적으로 승인했다.
적재 직전 롤백 완료·5개 테이블 0건·버퍼 풀 128MiB를 재확인하고, 13:07 KST에 같은 JAR로 실행을 시작했다.
이번 실행에서는 DB 전역 설정을 변경하지 않으며 실행 전후 주요 설정을 읽기 전용으로 대조한다.
승인한 실행은 191.086초에 정상 종료했다. 내부 검증·커밋 뒤 별도 검증 SQL에서도 전수 공식·관계·집계 불일치가 모두 0이었다.
기존 데이터 재실행은 INSERT 전에 brands의 기존 데이터를 감지해 거절했고, 건수와 합계를 유지했다.
seed 완료 시점에는 이후 조회 확인이 미진행이었다. 현재 추가로 확인한 HTTP·JMeter 사전 결과는 아래 항목과 result.md를 따른다.
버퍼 풀 포함 주요 전역 설정 11개는 사전 확인 전후에도 동일했다.
