# 변경 전 JMeter 첫 본 측정 · timeout으로 중단한 부분 기준선

[진행 결과](../../result.md) · [필터링한 실행 요약](summary.json)

사용자가 2026-10-16 **13:57:36~14:01:20 KST**에 실행한 결과다.
전체 최신순의 1회차 동시 10명 본 측정에서 응답 timeout이 발생해 wrapper가 후속 실행을 중단했다.
실패를 포함한 변경 전 부분 기준선으로 보존하며, 계획한 **12개 본 측정 전체를 완료한 결과가 아니다.**

## 실행 조건

- 대상: `GET /api/v1/products?sort=latest&page=0&size=20`.
- 실제 요청 설정: 시나리오 3종 × 동시 1명·10명 × **2회**, 총 12개 본 측정 예정.
- 각 조합은 워밍업 20초 → 본 측정 60초, 각각 ramp-up 5초. 연결/응답 timeout은 3,000/30,000ms다.
- 워밍업·본 측정 모두 `validation=light`이며, 스레드가 응답 뒤 다음 요청을 보내는 closed-loop 방식이다.
- 실행 스크립트 기준 커밋 `07b47bde4ca5c71f8c38818db122c2f65b79c176`, 앱은 `commerce-api-98da9d2.jar`.
- JMeter 5.6.3, Java 21.0.10, MySQL 8.0.46. 앱은 `local`, SQL·바인딩 로그를 끈 측정 모드다.

설정한 시간에는 ramp-up이 포함되며 진행 중인 요청이 나중에 끝날 수 있다.
아래 평균은 JTL의 `elapsed`로 계산한 클라이언트 응답 시간이며 JVM 기동·보고서 생성 시간은 포함하지 않는다.

서버가 실제로 요청 처리를 마친 시각이나 그 최종 지연을 뜻하지 않는다.

## 실패 원인과 후속 확인

확정된 실패 이유는 JMeter가 30초 동안 응답을 받지 못한 것이다. DB 쿼리 timeout이나 HTTP 5xx로 확정하지 않는다.
전체 최신순은 `created_at DESC, id DESC`지만 기존 인덱스에는 그 앞에 미지정 `brand_id`가 있어 전체 정렬을 직접 제공하지 못한다.
목록 읽기·정렬, TTL 0s로 매번 실행되는 COUNT와 동시 요청 경합이 병목 후보이며 실행 계획으로 확인한다.
설정상 local 커넥션 풀 최대값은 40이고 연결 획득 제한은 3초다. 30초라는 수치만으로 풀 부족을 원인으로 쓰지 않는다.
사용자는 부분 기준선을 유지한 채 기존 4개에 전체 최신순·가격순 인덱스 2개를 추가하기로 했다.
가격순·브랜드별·2회차를 측정한 것으로 채우거나 미측정 조합의 개선율을 제시하지 않는다.

네 단계 모두 JMeter CLI 종료 코드는 0이었다. wrapper는 마지막 JTL의 `success=false` 10건을 확인해
`Failed`로 중단했다. 본 측정 두 단계의 HTML도 생성됐지만 HTML 생성·CLI 0만으로 성공으로 판정하지 않는다.
워밍업 표본은 본 측정에 합산하지 않았다.

## 중단 범위와 환경 확인

- 본 측정 2개를 시도해 1개는 실패 없이 끝났고 1개는 timeout을 포함했다.
- `price`·`brand7`의 1회차와 모든 시나리오의 2회차, 총 10개 본 측정은 시작하지 않았다.
- 전후 DB snapshot은 상품 **1,000,000개**, 좋아요 **2,597,980개**, 버퍼 풀 **134,217,728 bytes(128MiB)** 로 일치했다.
- 상품 인덱스는 PRIMARY와 기존 보조 인덱스 4개뿐이며 새 전체 최신순·가격순 인덱스는 없다.
- 전후 비교한 전역 설정 11개는 동일했고 사후 확인 오류는 없었다. 실제 값은 `summary.json`에 보존했다.

이 결과만으로 가격순·브랜드별 가격순이나 2회차 성능을 설명하지 않는다.
동시 1명 본 측정도 6건뿐이므로 꼬리 분위수나 서비스 전체의 성능으로 일반화하지 않는다.
`light` 검증은 전체 응답 필드·정렬·페이지 동일성을 단독으로 증명하지 않으며,
변경 후 자료가 아직 없으므로 인덱스 개선 효과로 해석하지 않는다.
