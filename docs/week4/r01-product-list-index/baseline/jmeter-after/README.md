## 대응 가능한 변경 전 비교

[변경 전 부분 기준선](../jmeter-before-first/README.md)은 최신순 1회차의 1명·10명 두 조건만 남아 있다.
아래 역시 변경 후 **1회차**와 대응시켰다. 가격순·브랜드 조건 및 2회차에는 변경 전 측정이 없다.

| 최신순 1회차 | 표본 전 → 후 | 평균 ms 전 → 후 | 전체 req/s 전 → 후 | 오류율 전 → 후 |
|---|---:|---:|---:|---:|
| 동시 1명 | 6 → 439 | 10,845.667 → 132.533 | 0.091927 → 7.432741 | 0% → 0% |
| 동시 10명 | 30 → 2,417 | 25,443.867 → 237.728 | 0.383000 → 40.838740 | 33.333% → 0% |

변경 전 10명에서는 30건 중 10건이 30,007~30,017ms에 `Read timed out`으로 종료됐다.
이 실패 표본은 클라이언트 timeout으로 관측이 끝난 값이며 실제 서버 처리 완료 시간이 아니다.
따라서 25,443.867ms는 timeout을 포함한 관측 평균이다. 성공한 20건만의 평균은 23,158.450ms,
성공 처리량은 0.255333 req/s다. 성공 평균도 실패한 느린 요청을 제외하므로 오류율과 함께 해석해야 한다.
변경 후에는 실패가 없어 전체 평균·처리량과 성공 평균·처리량이 같다.

변경 전 1명은 6개 표본뿐이다. 변경 전 p95/p99는 1명에서 15,065ms, 10명에서 30,017ms로
모두 해당 실행의 최댓값과 같아 꼬리 지연을 일반화하기 어렵다. 이 자료로 안정적인 개선 배수를 확정하지 않는다.

## 재현 조건과 반복 편차

- `latest`: 전체 최신순, `price`: 전체 가격 오름차순, `brand7`: 브랜드 7의 가격 오름차순이다. 모두 첫 페이지·20개다.
- JMeter 5.6.3 CLI, Java 21.0.10, MySQL 8.0.46, 동시 사용자 1명/10명, 반복 2회다.
  각 조건에서 워밍업 20초를 별도 저장한 뒤 본 측정 60초를 수행했고 램프업은 5초다.
  연결 timeout은 3초, 응답 timeout은 30초이며 측정 중 `light` 검증을 사용했다.
- 요청 사이 대기 시간을 추가하지 않은 고정 사용자 방식이다. req/s는 JTL의 첫 요청 시작부터 마지막 응답 종료까지의
  실제 관측 구간을 분모로 계산했으며, CLI 실행 시간이나 예정된 60초로 나누지 않았다. 워밍업은 본 측정에서 제외했다.
- 1회차는 `latest → price → brand7`, 2회차는 `price → brand7 → latest` 순서이며 조건마다 1명 다음 10명을 실행했다.
  두 반복 모두 최신순 1명 평균은 132.533/131.348ms로 비슷했으나 10명은 237.728/263.526ms였다.
  가격순 평균은 1명 124.419/161.592ms, 10명 227.456/271.912ms로 2회차가 높았다.
  브랜드 7은 1명 30.930/16.541ms, 10명 25.511/20.881ms로 2회차가 낮았다.
  같은 조건에서도 편차가 있어 각 반복의 원본 지표를 유지한다.
- 전용 스키마 `week4_r01_index_benchmark`에서 상품 1,000,000건·좋아요 2,597,980건,
  버퍼 풀 134,217,728바이트(128MiB)를 유지했다. 변경 후 측정 시작·종료의 기존 인덱스 4개와 신규 인덱스 2개가 동일하다.
  변경 전후 스냅샷의 데이터 건수·버퍼 풀과 전역 설정 11개도 일치한다. 개별 값은 [요약](summary.json)에 보존했다.
- 전후 API JAR는 `commerce-api-98da9d2.jar`, SHA-256은
  `47A6839167CD1C0E2F459040E2B76572BB19C792E8701F180CBC033089883FCA`로 같다.
  JMX·기대 응답·결과 속성 파일의 해시도 같다. `local` 프로필·18080 포트에서 DDL/seed/좋아요 집계를 끄고,
  COUNT TTL은 `0s`, SQL·바인딩 로깅은 끈 상태다.
- 변경 전 PowerShell은 `5.1.26100.9711`, 변경 후는 `7.6.5`다. 같은 Java/JMeter를 실행했지만 셸 버전 차이는 남는다.
  변경 전은 13:57:36~14:01:20 KST, 변경 후는 14:38:37~14:57:46 KST로 실행 시각도 다르다.
  순차 실행과 인덱스 적용, 실행 순서에 따른 캐시·시스템 상태 영향을 완전히 제거하지 못했다.
- `light` 검증만으로 모든 응답 필드의 동일성이 증명되지는 않는다. [별도 full 응답 검증](../http-after/README.md)을 함께 확인한다.
  SQL 단발 `EXPLAIN ANALYZE` 시간과 이 HTTP 부하 지표도 구분한다.
