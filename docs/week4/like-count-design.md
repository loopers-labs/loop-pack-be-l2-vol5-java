# 좋아요 수 비정규화 설계

## 1. 배경

- `likes(product_id)` 인덱스로 브랜드 목록의 좋아요 전체 스캔은 사라졌다(`product-query-index.md`).
- 그러나 브랜드 필터 없는 전체 목록은 그대로 약 180~200ms였다. 첫 페이지 20개를 위해 **9,412개 상품의 좋아요 수를 매번 임시 테이블로 집계**하는 단계(약 140~170ms)가 남았고, 인덱스로는 줄일 수 없다.
- `latest` · `price_asc` 는 정렬 키가 좋아요 수와 무관하므로 "20개를 먼저 고르고 그 20개만 집계"로 바꿀 수 있다. 하지만 `likes_desc` 는 정렬 키가 좋아요 수 자체라 후보 전체를 먼저 세야 한다. 세 정렬 모두 집계를 없애려면 좋아요 수를 미리 저장해야 한다.

## 2. 저장 위치와 행 생성

### 2.1 별도 테이블 `product_like_count`

| 항목 | 값 |
|---|---|
| 엔티티 | `domain/product/ProductLikeCount` (소유 도메인: product) |
| 열 | `product_id` (유니크 `uk_product_like_count_product`), `like_count` |
| 인덱스 | `idx_product_like_count_count (like_count, product_id)` |

| 후보 | 판단 |
|---|---|
| `product.like_count` 열 | 브랜드 + 좋아요순을 `(brand_id, like_count, id)` 인덱스 하나로 처리할 수 있다. 그러나 `product` 행은 재고 차감 · 관리자 수정이 비관적 잠금으로 잡는 행이라(3주차 설계 4.2), 좋아요 증감이 주문 확정과 같은 행 잠금을 두고 경쟁한다. 변경 감지가 모든 열을 다시 쓰므로 관리자 수정이 카운터 값을 덮어쓰지 않게 매핑을 따로 막아야 한다 |
| **별도 테이블 (채택)** | 좋아요는 카운터 행만 잠가 주문 · 관리자 경로와 잠금이 겹치지 않는다. `Product` 엔티티가 카운터를 갖지 않아 덮어쓰기 문제가 없다. 대가: 정렬 키(카운터)와 필터 키(`product.brand_id`)가 다른 테이블이라 **브랜드 + 좋아요순 복합 인덱스를 만들 수 없다.** 이 비용은 측정으로 확인한다(5절) |

### 2.2 상품을 만들 때 0 으로 함께 만든다

`ProductService.create` 가 같은 트랜잭션에서 상품과 좋아요 수 행을 만든다. 모든 상품이 행을 가진다.

| 후보 | 판단 |
|---|---|
| **상품 생성 때 (채택)** | 모든 상품이 행을 가져 조회가 inner join 이고, 증감이 항상 있는 행을 갱신한다. 대가: 상품 생성 경로가 행 하나를 더 쓰고, 기존 데이터는 한 번 채워야 한다(backfill) |
| 첫 좋아요 때 upsert | 상품 생성 경로를 건드리지 않는다. 그러나 좋아요 0 인 상품은 행이 없어 `coalesce` 로 정렬해야 하고, `INSERT … ON DUPLICATE KEY UPDATE` 는 행이 없을 때 갭 잠금을 잡아 동시 요청에서 교착이 날 수 있다 |

- backfill: `INSERT INTO product_like_count … SELECT p.id, COUNT(l.id) FROM product p LEFT JOIN likes l … GROUP BY p.id` (seed 파일에 같은 문장)
- 테스트가 엔티티를 직접 저장해 만든 상품은 행이 없으므로, 테스트 준비도 생성 입구(`ProductService.create`)를 쓰거나 행을 함께 만든다.

## 3. 증감과 동시성

### 3.1 불변식

**좋아요 수 = 그 상품의 관계 수.** 관계가 실제로 생겼을 때만 +1, 실제로 지워졌을 때만 −1 한다. 상품이 삭제된 뒤의 취소(LIK-03)도 −1 이다.

### 3.2 원자적 갱신 (채택)

```
등록: 관계 조회 → 없으면 insert → (insert 했으면) UPDATE … SET like_count = like_count + 1 → commit
취소: DELETE … WHERE user_id = ? AND product_id = ? → (지운 행이 1이면) UPDATE … SET like_count = like_count - 1 → commit
```

- 관계 변경과 카운터 갱신은 한 트랜잭션(`LikeFacade`)이라 같이 commit 되거나 같이 rollback 된다.
- **"실제로 반영됐는지"는 미리 읽은 결과가 아니라 DB가 알려 주는 결과로 판단한다.** 등록은 유니크 키가 둘 중 하나만 성공시키고, 취소는 DELETE 의 영향 행 수로 판단한다(늦게 온 취소는 앞의 commit 을 기다린 뒤 0행).
- 카운터는 읽지 않고 한 문장으로 갱신해 갱신 유실이 없다. 행 잠금은 UPDATE 부터 commit 까지이므로 **UPDATE 를 트랜잭션의 마지막 쓰기로 둔다.** 응답용 좋아요 수 조회(PK 한 건)만 그 뒤에 온다.
- 잠금 순서는 관계 행 → 카운터 행으로 등록 · 취소가 같다. 주문 · 관리자 경로는 카운터를 잡지 않아 새 교착 경로가 없다.

| 후보 | 판단 |
|---|---|
| **원자적 갱신 (채택)** | 잠금 구간이 UPDATE~commit 으로 가장 짧고, 경쟁에서 진 쪽은 기다렸다가 그대로 성공한다. 대가: 같은 사용자의 동시 등록에서 늦은 쪽이 유니크 키 위반을 받는다(3.3) |
| 카운터 행 비관적 잠금 | 확인과 반영이 잠금 안이라 중복 예외가 없다. 대가: 같은 상품의 좋아요가 확인 · insert · 증감 전체 동안 한 줄로 선다 |
| 낙관적 잠금 | 잠금 구간은 원자적 갱신과 같지만 진 쪽이 처음부터 다시 실행한다. 쓰기가 한 행에 몰리는 카운터에서는 재시도가 몰린다(3주차 실험의 "재고가 남았는데 한도 초과") |

### 3.3 같은 사용자의 동시 등록: 다시 실행

- 늦은 쪽은 앞 트랜잭션의 commit 을 기다린 뒤 유니크 키 위반으로 rollback 된다. 카운터도 함께 rollback 되어 정합성은 지켜지지만, 멱등 계약(LIK-02)상 오류로 내보내면 안 된다.
- `LikeRetrier` 가 등록 유스케이스 전체를 새 트랜잭션으로 다시 실행한다. 다시 실행하면 관계가 보여 아무것도 바꾸지 않고 성공한다. 정책은 기존 `~Retrier` 와 같다(총 3회, 50ms부터 지수 백오프 최대 200ms, 지터).
- **다시 실행 대상은 이 관계의 유니크 키 위반만이다.** Spring 은 이 위반을 일반 `DataIntegrityViolationException` 으로 알리므로(실측), `LikeRepositoryImpl.save` 가 제약 이름이 `uk_likes_user_product` 인 경우만 `DuplicateKeyException` 으로 바꾸고 `LikeRetrier` 는 그것만 다시 실행한다. NOT NULL 위반 같은 다른 무결성 위반은 다시 실행하지 않는다.

| 후보 | 판단 |
|---|---|
| **다시 실행 (채택)** | 기존 `~Retrier` 와 같은 방식이다. 드문 경우(따닥 클릭)에만 비용을 낸다 |
| `INSERT IGNORE` | 예외 없이 0행을 받는다. 대가: 네이티브 SQL이 늘고, 중복 외의 오류도 경고로 바꿔 삼킨다 |

## 4. 조회

### 4.1 좋아요 수 행을 inner join 한다

| 조회 | 변경 |
|---|---|
| 상품 목록 · 상세 (`ProductRepositoryImpl`) | `likes` outer join + GROUP BY → `product_like_count` inner join. 집계가 사라진다 |
| `likes_desc` 정렬 | `like_count desc, product_id desc`. 동점 기준은 상품 식별자 역순으로 기존 계약과 같다 |
| 내 좋아요 목록 (`LikeRepositoryImpl`) | 상품별 상관 서브쿼리 count → `product_like_count` join |
| 등록 · 취소 응답의 좋아요 수 (`LikeFacade`) | 관계 count → 좋아요 수 행. 없는 상품은 0 (LIK-03 응답 계약) |

## 5. 측정

`product-query-like-count.md` 에 기록했다. 요약하면 다음과 같다.

- 전체 목록 p50: 약 180~205ms → **약 8~23ms**
- 브랜드 7(상품 94개) p50: 약 5~7ms → 약 5~6ms
- 상품 18,824개 브랜드의 `likes_desc` p50 약 41ms. 브랜드 상품 전부를 읽어 정렬하며, 비용이 브랜드 크기에 비례한다(2.1에서 감수한 비용).

## 7. 한계

- **카운터 행 하나에 같은 상품의 좋아요가 한 줄로 선다.** 잠금 구간을 줄였을 뿐 직렬화는 없어지지 않는다. 인기 상품 하나에 초당 수백 건이 몰리면 행을 여러 개로 나눠 합산하거나(sharded counter) 이벤트로 모아 늦게 반영하는 구조가 필요하다. 이번 범위에서는 측정하지 않았다.
- 브랜드 + 좋아요순은 브랜드 상품 수에 비례한다. 더 줄여야 하면 `brand_id` · 삭제 여부를 카운터 테이블에도 복사해 `(brand_id, like_count, product_id)` 인덱스를 둘 수 있지만, 브랜드 일괄 삭제 · 상품 삭제 때 카운터 테이블도 함께 갱신하는 책임이 생긴다.
- 좋아요 수 행이 없는 상품에 증감이 오면 불변식이 깨진 것으로 보고 예외를 낸다. 운영 데이터에는 backfill 이 먼저 필요하다.
