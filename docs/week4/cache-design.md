# 상품 목록 캐시 설계

Redis cache-aside 를 상품 목록 한 경로에 붙인다. 측정 근거는 `product-query-*.md`, 앞선 조회 개선은 `like-count-design.md` · `product-query-brand-index.md` 를 따른다.

## 1. 대상 선택: 목록 vs 상세

| 기준 | 목록 | 상세 |
|---|---|---|
| 원본 비용 (p50) | 브랜드 7 약 5ms, 전체 약 9~24ms, 큰 브랜드 약 6~23ms | 약 2.8ms, 대부분 DB 밖 (`product-query-detail.md`) |
| hit 로 줄이는 것 | 정렬 · 조인 · 건수 SQL | 거의 없음. hit 도 Redis 왕복 · 역직렬화가 듦 |
| 무효화 범위 | 넓음 (아래 2.1 로 좁힘) | 키 하나 |

**목록을 캐시한다.** 상세는 줄일 원본 비용이 측정상 거의 없어, 캐시를 붙이면 무효화 책임만 는다.

- **캐시 측정 뒤 보완:** 상세의 원본 비용에는 `EXPLAIN` 에 보이지 않는 커넥션 · 트랜잭션 · 왕복 비용 약 1.5~2ms가 있었다(`product-query-cache.md` 관찰 4). 상세를 캐시해도 이득은 2ms 미만으로 추정되어 판단은 같다.

## 2. 범위와 키

### 2.1 첫 페이지 · 기본 크기만

- 대상: `GET /api/v1/products?[brandId=]&sort=&page=1&size=20` (기존 계약의 첫 페이지 · 기본 크기). 그 밖의 요청은 캐시를 거치지 않고 DB 로 간다.
- 키 수 상한: (브랜드 수 + 전체 1) × 정렬 3. 지금 데이터로 최대 306개.
- 첫 페이지에 요청이 몰린다는 것은 **가정**이다. 실서비스 분포가 없어 hit 율은 측정하지 않았다.
- 응답의 `totalCount` · `totalPages` 도 담으므로, 2페이지 이후 상품의 생성 · 삭제도 첫 페이지를 바꾼다(3.3 무효화 대상에 포함).

### 2.2 저장 내용과 키 형식

| 항목 | 값 |
|---|---|
| 저장 내용 | 첫 페이지의 `ProductView` 목록 + 전체 건수 (JSON). 사용자별 필드는 응답에 없어 공용 캐시에 섞일 정보가 없다 |
| 데이터 키 | `product-list:v1:{범위}:ver={범위 버전}:sort={정렬}`. 범위는 `brand={id}` 또는 `all`. `v1` 은 저장 형식 버전 |
| 버전 키 | `product-list:version:{범위}` (`…:brand=7`, `…:all`) |
| TTL | 데이터 키 60초(`product-list-cache.ttl-seconds`, 테스트에서 줄여 만료를 확인). 버전 키는 TTL 없음 |

## 3. 무효화

### 3.1 범위 버전을 올린다

| 후보 | 판단 |
|---|---|
| 영향 키 삭제 | 읽기가 Redis 1회로 가장 빠르다. 그러나 변경 전에 DB 를 읽은 조회가 삭제 *뒤에* 옛 값을 같은 키에 다시 넣으면(늦은 채움) TTL 까지 옛 값이 남는다 |
| **범위 버전 올리기 (채택)** | 키에 버전을 넣고 commit 뒤 버전을 `INCR` 한다. 늦은 채움은 *옛 버전 키*에만 들어가 이후 조회에 보이지 않는다. 대가: 읽기마다 버전 조회로 Redis 왕복 1회 추가, 버전 키 관리 책임 |
| TTL 만 | 정상 변경 직후 순차 조회의 최신성(필수 요건)을 지키지 못한다 |

품절 표시는 정상 상황에서 최신이어야 한다는 요구(5절)가 채택 근거다. 성능은 쓰기 쪽이 비슷하고 읽기 쪽은 오히려 왕복이 하나 는다.

### 3.2 버전 단위: 브랜드 + 전체

상품 하나의 변경이 영향을 주는 첫 페이지는 **그 상품의 브랜드 목록 3개(정렬별) + 전체 목록 3개** 다. 쓰기 한 번에 브랜드 버전과 전체 버전을 하나씩 올린다.

| 후보 | 판단 |
|---|---|
| 전역 버전 하나 | 상품의 브랜드를 몰라도 된다. 그러나 어느 브랜드의 변경이든 모든 첫 페이지가 함께 사라져, 브랜드 · 상품이 늘수록 hit 율이 떨어진다 |
| **브랜드 + 전체 (채택)** | 바뀐 브랜드와 전체만 무효화한다. 대가: 쓰기 경로가 상품의 브랜드 식별자를 알아야 한다 → `Product.getBrandId()` (2주차 D-36 에 단서 추가) |

전체 목록 키는 어떤 상품이 바뀌어도 무효화된다. 피할 수 없으며, 상품이 많아질수록 전체 목록의 hit 율은 브랜드 목록보다 낮다.

### 3.3 무효화하는 쓰기

| 쓰기 | 위치 | 올리는 버전 |
|---|---|---|
| 상품 생성 · 수정 · 삭제 | `AdminProductFacade` | 그 상품의 브랜드, 전체 |
| 관리자 재고 변경 — **품절 여부가 뒤집힐 때만** | `AdminProductFacade` | 그 상품의 브랜드, 전체 |
| 주문 확정의 재고 차감 — **품절이 된 상품이 있을 때만** | `OrderFacade` | 품절이 된 상품들의 브랜드, 전체 |
| 브랜드 수정 · 일괄 삭제 | `BrandFacade` | 그 브랜드, 전체 |

- 캐시에는 재고 수량이 아니라 품절 여부(`stock == 0`)가 담긴다. 10 → 9 같은 차감은 응답을 바꾸지 않으므로 무효화하지 않는다. 품절 판단의 기준은 `Product.isSoldOut()` 하나로 두고 응답 DTO 도 이를 쓴다.
- **좋아요 등록 · 취소는 무효화하지 않는다.** 좋아요 수와 `likes_desc` 순서는 TTL(60초) 동안 오래된 값일 수 있다(5절).
- 브랜드 생성은 상품이 없는 브랜드라 목록을 바꾸지 않는다.

### 3.4 commit 뒤에 올리고, 실패는 기록해 다시 올린다

- 쓰기 경로가 `ProductListCache` 를 **명시적으로 호출**하고, 구현은 진행 중인 트랜잭션이 있으면 commit 뒤로 미룬다. rollback 된 변경은 버전을 올리지 않는다.

| 후보 | 판단 |
|---|---|
| **명시 호출 (채택)** | 무효화하는 곳이 코드에 보인다. 빠뜨림은 "모든 쓰기 경로가 무효화를 부르는가" 테스트로 막는다 |
| 도메인 이벤트 + `@TransactionalEventListener(AFTER_COMMIT)` | 결합이 낮다. 그러나 트랜잭션 없이 발행된 이벤트는 기본 설정에서 버려지고, 프로젝트에 없던 개념이 생긴다 |

- **`INCR` 실패:** DB 는 이미 commit 됐으므로 쓰기 응답은 성공이다. 실패한 범위(브랜드 id · 전체)를 메모리 집합에 기록하고 몇 초 간격으로 다시 `INCR` 한다. 버전은 여러 번 올려도 해가 없어 중복 처리가 필요 없다.

| 후보 | 판단 |
|---|---|
| 기록만 + TTL 상한 | 가장 단순. 품절 표시가 최대 TTL 동안 틀릴 수 있다 |
| **메모리 기록 + 주기 재처리 (채택)** | 일시 장애가 끝나면 몇 초 안에 바로잡는다. 앱이 재시작되면 기록을 잃지만 TTL 이 남은 오차를 막는다 |
| DB 기록(outbox) + 배치 | 유실이 없지만 테이블 · 배치가 생긴다. 이번 조회 최적화의 선행조건으로 두지 않는다 |
| 즉시 재시도 | 장애 중에는 실패를 반복하며 관리자 · 주문 응답만 늦춘다 |

### 3.5 버전 키가 없을 때

- 처음 기동하거나 그 범위에 쓰기가 없었으면 버전 키가 없다. **현재 시각(ms)으로 `SETNX`** 해 만든다.
- 0 이나 1 로 만들면, 키가 유실됐다 다시 생길 때 예전 데이터 키(`ver=1`)와 번호가 겹쳐 옛 값을 읽을 수 있다.
- 현재 시각으로 만들면 예전 버전(처음 만든 시각 + 그동안 올린 횟수)보다 크다. 단, 버전을 올린 횟수가 그동안 흐른 밀리초보다 많으면 겹칠 수 있다. 무효화는 관리자 작업 · 품절 전환이라 그 빈도에 이르지 않는다고 본다.
- 무효화할 때 버전 키가 없어도 같은 방식으로 만든 뒤 올린다. `INCR` 은 없는 키를 1 로 만들기 때문이다.

## 4. 읽기

### 4.1 순서

```
ProductFacade.getProducts (트랜잭션 없음)
  1. 첫 페이지 · 기본 크기가 아니면 → DB
  2. 범위 버전 읽기 (master)              ─ 실패하면 → DB, 캐시에 쓰지 않음
  3. 데이터 키 읽기 (기본 연결)           ─ hit 이면 반환 / 실패하면 → DB, 캐시에 쓰지 않음
  4. miss → DB 조회 (여기서 읽기 트랜잭션 시작)
  5. 2에서 읽은 버전의 데이터 키에 TTL 과 함께 저장 ─ 실패해도 결과는 반환
```

- **버전 키는 master 에서 읽는다.** 기본 연결은 `REPLICA_PREFERRED` 다. 관리자 변경 → master `INCR` → 직후 조회가 아직 복제되지 않은 replica 에서 옛 버전을 읽으면 옛 페이지가 나가, 정상 순차 조회의 최신성이 깨진다.
- **데이터 키는 기본 연결로 읽어도 된다.** 키에 버전이 있어 replica 에 아직 없으면 miss 일 뿐 옛 값을 돌려주지 않는다. 새 버전 키에는 `INCR` 이후(commit 이후)에 DB 를 읽은 결과만 들어간다.
- **버전을 읽은 뒤에 DB 를 읽는다.** REPEATABLE READ 는 트랜잭션의 첫 읽기 시점 스냅샷을 쓴다. 캐시 확인 전에 같은 트랜잭션에서 무언가를 읽었다면, 새 버전을 읽고도 옛 스냅샷으로 새 버전 키를 채울 수 있다. 그래서 캐시 확인을 트랜잭션 밖(`ProductFacade`)에 둔다.

### 4.2 Redis 장애

- 캐시용 Redis 연결은 commerce-api 안에 따로 두고 **명령 대기 한도를 100ms** 로 둔다. 공통 모듈(`modules/redis`)은 batch · streamer 도 쓰므로 바꾸지 않는다(2주차 D-37 과 같은 기준). Lettuce 기본값은 60초라, 그대로면 Redis 가 멈출 때 목록 요청도 멈춘다.
- Redis 오류는 miss 와 구분해 기록하고 DB 로 우회한다. DB 오류는 빈 목록으로 숨기지 않고 기존 오류 응답을 따른다.
- Redis 가 완전히 멈추면 조회도 DB 로 가므로 옛 값은 노출되지 않는다. 옛 값이 노출되는 경우는 **`INCR` 만 실패하고 조회는 성공하는 부분 장애** 이며, 3.4 의 재처리와 TTL 이 막는다.
- 우회하는 동안 hit 로 끝나던 요청까지 DB 로 간다. 이번에는 작은 통제 부하에서 우회와 결과를 확인한다.

## 5. 허용 신선도

| 데이터 | 정상 상황 (변경 완료 뒤 시작한 순차 조회) | 장애 · 경쟁 |
|---|---|---|
| 가격 · 이름 · 브랜드 정보 · 상품 존재(생성 · 삭제) · 목록 순서 | 최신 (3.3 무효화) | `INCR` 실패 시 재처리까지, 최대 TTL 60초 |
| 품절 여부 | 최신 (뒤집힐 때 무효화) | 위와 같음. 초과 판매는 주문 확정의 DB 재고 잠금이 막으므로 영향은 "구매 가능해 보였으나 확정에서 품절 거절" |
| 좋아요 수 · `likes_desc` 순서 | 최대 TTL 60초 오래될 수 있음 | 같음 |
| **삭제 상품 비노출 · 주문 금액 · 재고 · 포인트 판단** | 신선도 선택 대상이 아님. 주문 확정은 캐시를 쓰지 않고 DB 를 따른다 | 같음 |

TTL 60초는 가정한 값이다. 좋아요 수가 1분 늦는 것은 화면용으로 허용하고, 키 306개가 1분마다 miss 나도 원본 비용(수~수십 ms)으로 DB 부하가 작다는 판단이다. 실서비스라면 hit 율 · miss 비용을 지표로 보고 조정한다.

## 7. 검증 계획

| 장면 | 확인할 결과 |
|---|---|
| 같은 입력의 DB-only · miss · hit | 결과 일치, hit 에서 목록 · 건수 SQL 0회 |
| 첫 페이지 · 기본 크기가 아닌 요청 | 캐시를 거치지 않음 |
| 관리자 가격 수정 commit 후 재조회 | 새 가격과 `price_asc` 순서 반영, 다른 브랜드 캐시는 유지, 확정한 주문의 금액 유지 |
| 상품 생성 · 삭제, 브랜드 수정 · 일괄 삭제 | 영향 범위 반영, 다른 브랜드와 과거 주문(상태 · 금액, 판매 여부 false) 유지 |
| 재고 변경 · 주문 확정 | 품절이 뒤집힐 때만 무효화 |
| 좋아요 등록 · 취소 | 무효화하지 않음. TTL 동안은 이전 좋아요 수 · 순서, 만료 뒤에는 DB 와 같은 수 · 순서 |
| DB 변경 rollback | 버전이 오르지 않고 변경 전 결과 유지 |
| 모든 쓰기 경로 | 무효화를 부르는지 (빠뜨림 방지) |
| 늦은 채움 | 래치로 "이전 조회의 DB 읽기 → 변경 commit · 버전 증가 → 이전 조회의 저장 → 새 조회" 를 만들고 새 조회가 최신인지 |
| `INCR` 실패 | 쓰기는 성공, 재처리 뒤 최신 반영 |
| Redis 중단 · 재시작 | 대기 한도 안에 DB 결과 반환, 재시작 뒤 다시 채움 |
| Redis 장애 중 주문 확정 | 캐시와 무관하게 DB 규칙대로 재고 · 포인트를 반영하고 성공, 품절 표시는 재처리 뒤 반영 |
| 측정 | hit · miss 지연을 기존 측정과 같은 방식으로 비교 |

## 8. 한계

- 첫 페이지 집중 · TTL 60초는 가정이다.
- 전체 목록 키는 모든 상품 변경에 무효화된다.
- 버전이 오르면 그 범위의 정렬 3개가 동시에 miss 난다. 키가 적어 요청 합치기 같은 동시 miss 대책은 두지 않는다.
- 재처리 기록은 메모리라 앱 재시작 때 사라진다(최대 TTL 동안 오래된 값).
