# 4주차 설계: 상품 목록 조회의 병목과 캐시

과제 1절이 설계 문서에 정하라고 한 다섯 항목과, 근거 문서의 위치를 정리한다.

## 1. 조회 계약 (바꾸지 않고 유지한 기존 계약)

`GET /api/v1/products` (2주차 설계 6.1 · 6.2)

| 항목 | 계약 |
|---|---|
| 브랜드 필터 | `brandId` 선택. 없으면 전체, 없는 브랜드면 빈 목록 (D-24) |
| 정렬 | `sort` = `latest`(기본, 생성 시각 desc) · `price_asc` · `likes_desc`. **동점은 모두 상품 식별자 desc.** 모르는 값은 기본값으로 바꾸지 않고 400 |
| 페이지 | `page` 는 1부터(기본 1), `size` 는 1~100(기본 20). 범위를 벗어나면 400 |
| 대상 | 삭제되지 않은 상품만. 브랜드 일괄 삭제 시 상품도 함께 삭제됨 (3주차 2.3) |
| 응답 | `items[id, name, price, likeCount, soldOut, brand{id, name}]`, `page`, `size`, `totalCount`, `totalPages`. 재고 수량은 내보내지 않고 품절 여부만 |
| `likes_desc` | 전체 후보에서 정렬한 뒤 페이지를 선택한다 (애플리케이션에서 일부만 정렬하지 않음) |

4주차 변경(인덱스 · 좋아요 수 비정규화 · 캐시) 전후로 이 계약의 결과가 같은지를 측정 실험이 seed 규칙으로 계산한 기대 결과와 비교해 매번 확인했다.

## 2. 측정 대상

| 항목 | 값 |
|---|---|
| 고정한 요청 | 브랜드 필터 + `price_asc` 의 첫 페이지 (`brandId=7&sort=price_asc&page=1&size=20`). 같은 브랜드의 `latest` · `likes_desc`, 브랜드 필터 없는 전체, 상품 2만 개 브랜드(101)도 함께 측정 |
| 데이터 | 재현 seed: 상품 1만 개(삭제 588) · 브랜드 100 · 사용자 1,000 · 좋아요 100,163 (+ 큰 브랜드 상품 2만 개) — `product-query-seed.md` |
| 기록 | 요청당 SQL 수, 실제 SQL 의 `EXPLAIN` · `EXPLAIN ANALYZE`, 준비 50회 뒤 200회의 지연 분포, 결과 일치 여부 |
| 좋아요 조회 비용 | 요청당 SQL 은 2개로 N+1 은 없었다. 비용은 좋아요 전체 스캔(→ 인덱스)과 후보 전체 집계(→ 비정규화)였다 |

## 3. 캐시 범위

목록 첫 페이지(`page=1`, `size=20`)만, 범위(브랜드 · 전체) × 정렬 3. 사용자별 필드는 응답에 없다. → `cache-design.md` 1 · 2절

## 4. 변경 책임

상품 생성 · 수정 · 삭제, 브랜드 수정 · 일괄 삭제는 항상, 재고 변경 · 주문 확정은 품절 여부가 바뀔 때만 commit 뒤 범위 버전을 올린다. 좋아요는 무효화하지 않고 TTL 안에 반영한다. → `cache-design.md` 3절

## 5. 장애 계약

캐시 전용 연결의 대기 한도 100ms, Redis 오류는 DB 로 우회(DB 오류는 숨기지 않음), 무효화 실패는 메모리 기록 후 재처리, 데이터별 허용 신선도. 주문 확정은 캐시를 쓰지 않는다. → `cache-design.md` 4 · 5절
