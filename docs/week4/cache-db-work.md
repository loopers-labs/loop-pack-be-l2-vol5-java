# 캐시가 덜어 주는 DB 일: 가격순·인기순 비교

가격순과 인기순에 같은 Redis 캐시를 붙였는데 결과가 갈렸다. 가격순은 응답 시간이 줄지 않았고, 인기순은 크게 줄었다. 차이가 어디서 나는지 보려고 응답 시간 대신 **요청 하나가 DB에 시키는 일**(읽은 행·문장 실행 시간)을 쟀다. 결론은 hit가 아니라 **캐시가 없을 때의 원본 비용**이 갈랐다는 것이다.

가격순·인기순 목록에서 어떤 항목을 얼마나 늦게 반영해도 되는지는 [design.md의 캐시별 최신성 표](design.md#cache-freshness)에 정리했다.

## 조회 범위와 측정 조건

| 항목 | 조건 |
| --- | --- |
| 원본 데이터 | `loopers_benchmark_100k`(seed-week4-100k.py). 상품 100,000개(활성 96,990), 브랜드 100개(활성 98, 브랜드마다 상품 1,000개), 사용자 200명, 좋아요 관계 628,186개, 카운터 100,000행(상품당 0~150, 평균 6.3) |
| 990개 조건 | 원본을 임시 DB로 그대로 복사. 브랜드 7의 상품 1,000개 중 활성 990개 |
| 87,390개 조건 | 같은 복사본에서 ID 1~90,000의 brand_id만 7로 바꿈. 가격·삭제 여부·좋아요·카운터는 그대로라 브랜드 7의 활성 상품이 87,390개가 됨(전체 상품 수는 10만 그대로) |
| 요청 | `GET /api/v1/products?brandId=7&page=0&size=20&sort=price_asc` 또는 `sort=popular`, `X-USER-ID: 95`. 매 응답을 seed로 계산한 기대값(순서·가격·좋아요 수·isLiked)과 대조 |
| 캐시 상태 | 원본 = 해당 캐시를 끈 앱, hit = 키를 채운 뒤 연속 조회, miss = 조회마다 직전에 키 삭제 |
| 반복 | 순차 단일 클라이언트. 990개는 준비 100·측정 200회, 인기순 87,390개는 준비 10·측정 50회, 가격순 87,390개는 준비 100·측정 200회. 앱 실행 순서를 바꿔 3회 |
| 지표 | 읽은 행·DB 시간 = 측정 구간의 `performance_schema` 문장 통계 합 ÷ 요청 수(임시 DB 스키마만, SELECT·SET·COMMIT 포함). DB CPU = 같은 통계의 문장 CPU 시간. API = 클라이언트가 잰 응답 시간 중앙값 |
| 환경 | 한 노트북의 MySQL 8.0.46(buffer pool 128MiB)·Redis 7.0.15·앱 1개(JDK 21, 힙 512MB, 커넥션 풀 40). 네 경우 모두 같은 JAR(SHA-256 앞 16자리 `86a54ef466f84927`) |

87,390개 조건은 실제 분포라기보다 다른 값은 그대로 두고 **브랜드 7의 크기만 키운** 실험용 데이터다. "조회 조건에 걸리는 행이 늘 때 원본과 hit가 어떻게 변하나"를 보기 위한 조건이다.

## 네 경우의 결과

| 경로 | 브랜드 7 | 원본: 읽은 행 / DB / API | hit: 읽은 행 / DB / API | hit의 DB 감소 |
| --- | ---: | --- | --- | ---: |
| 가격순 | 990개 | 54 / 1.11~1.13ms / 8.9ms | 54 / 1.09~1.10ms / 10.2~10.4ms | 2~3% |
| 가격순 | 87,390개 | 42 / 1.32ms / 9.0~9.1ms | 42 / 1.11~1.13ms / 10.1~10.2ms | 15~16% (약 0.2ms) |
| 인기순 | 990개 | 2,056 / 2.33~2.36ms / 11.3ms | 56 / 1.05~1.08ms / 10.3~10.5ms | 54~55% |
| 인기순 | 87,390개 | 174,856 / 84.2~84.5ms / 98.0~99.8ms | 56 / 1.13~1.16ms / 12.7~13.1ms | 98.6~98.7% |

범위는 세 번 반복한 값의 최솟값~최댓값이다. 읽은 행은 요청 하나의 모든 SELECT 합이다. 가격순 87,390개에서 행이 적은 것은 그 첫 페이지에 사용자 95의 좋아요가 없어서다.

hit는 네 경우 모두 DB 약 1.1ms다. 캐시 값을 꺼내 쓰는 일은 데이터 크기와 무관하다. 차이는 원본에서 났다.

- 브랜드가 88배 커질 때 가격순 원본의 DB 시간은 약 0.2ms 늘었다.
- 같은 88배에서 인기순 원본의 DB 시간은 약 36배(2.3 → 84ms) 커졌다.

## 원본과 hit는 각각 무엇을 읽나?

요청 하나의 문장을 나눠 보면, 원본과 hit에 **공통으로 남는 문장**이 있다. 공통 캐시에 넣지 않은 값이라 hit여도 DB에서 읽는다(3회 평균).

| 공통 문장 | 읽은 행 | DB |
| --- | ---: | ---: |
| 브랜드 확인 | 1 | 약 0.10ms |
| 사용자 확인 | 1 | 약 0.12ms |
| 좋아요 수(카운터, 20개) | 20 | 약 0.14ms |
| 내 좋아요 여부(20개) | 0~14 | 약 0.23ms |
| 트랜잭션 SET·COMMIT 5개 | 0 | 약 0.24ms |
| 합계 | 22~56 | 약 0.83ms |

원본과 hit가 **다른 부분**은 "화면에 보여 줄 상품 20개를 정하는 일" 하나뿐이다.

- **캐시가 없을 때(원본)**: DB가 직접 "어떤 20개를, 어떤 순서로 보여 줄지"를 정한다.
- **hit일 때**: 20개와 순서는 캐시가 이미 알고 있다. DB는 "그 20개가 아직 삭제되지 않았는지"만 확인하거나, 그 20개의 정보만 읽는다.

| 경로 | 브랜드 7 | 캐시가 없을 때: 20개를 정하는 일 | hit일 때: 이미 정해진 20개 확인 |
| --- | ---: | --- | --- |
| 가격순 | 990개 | 가격순 인덱스의 브랜드 7 칸을 앞에서 20개 읽고 멈춤 → 20행 · 0.31ms | 캐시가 준 20개 ID가 아직 살아 있는지 확인 → 20행 · 0.27ms |
| 가격순 | 87,390개 | 위와 같음 → 20행 · 0.50ms | 위와 같음 → 20행 · 0.29ms |
| 인기순 | 990개 | 브랜드 7 상품 전부의 좋아요 수를 보고 줄 세운 뒤 20개 고름 → 2,000행 · 1.32ms<br>그 20개 상품 정보 읽기 → 20행 · 0.19ms | 캐시가 준 20개 ID의 상품 정보만 읽기 → 20행 · 0.21ms |
| 인기순 | 87,390개 | 같은 줄 세우기 → 174,800행 · 83.1ms<br>20개 상품 정보 읽기 → 20행 · 0.25ms | 20개 상품 정보만 읽기 → 20행 · 0.22ms |

가격순은 "20개를 정하는 일" 자체가 인덱스 덕분에 이미 20행이라, hit가 대신 하는 확인 작업과 크기가 같다. 인기순은 "20개를 정하는 일"이 브랜드 상품 전체를 줄 세우는 일이라, hit가 그 일을 통째로 건너뛰는 만큼 차이가 난다.

### 가격순은 왜 줄지 않았나?

가격이 상품 인덱스 `(brand_id, deleted_at, price, created_at DESC, id DESC)`에 있어서, 원본도 브랜드 7 칸을 앞에서부터 20개 읽고 멈춘다. hit가 대신 하는 활성 ID 확인도 20행이다. 둘이 거의 같은 일을 하니 hit가 피해 가는 비용이 없다. 공통 문장(약 0.83ms) 위에 0.2~0.3ms 차이만 남고, API는 Redis 왕복·JSON 변환이 더해져 hit가 1ms쯤 느렸다.

### 인기순은 왜 크게 줄었나?

정렬 기준인 좋아요 수가 상품 인덱스에 없고 `product_like_count`에 있다. 좋아요가 가장 많은 20개를 알려면 브랜드 7의 활성 상품과 그 카운터를 모두 보고 정렬해야 한다(990개 → 2,000행, 87,390개 → 174,800행). hit는 저장한 20개 ID로 상품만 읽어 이 문장을 통째로 건너뛴다.

| | 가격순 | 인기순 |
| --- | --- | --- |
| 순서 기준 | 가격 (상품 인덱스 안) | 좋아요 수 (다른 테이블) |
| 좋아요 수를 읽는 이유 | 화면에 보여 주려고 | 순서를 정하려고 |
| 좋아요 수를 읽는 개수 | 고른 20개 | 후보 전부 |
| 브랜드가 커지면 원본 | 20행 그대로 | 브랜드 상품 수에 비례 |

## 데이터가 많아지는 것과 조건에 걸리는 행이 많아지는 것

원본을 키우는 것은 테이블 전체 크기가 아니라 **조회 조건에 걸리는 행 수**다. 이 조회에서는 브랜드 7의 활성 상품 수다.

| 상황 | 브랜드 7 상품 | 인기순 원본이 읽는 양 |
| --- | --- | --- |
| 전체가 늘어도 브랜드 수가 같이 늘어 브랜드 7은 그대로 | 그대로 | 크게 변하지 않음(브랜드 인덱스로 브랜드 7 칸만 읽음) |
| 브랜드 수는 그대로, 브랜드마다 상품이 늘어남 (1만 → 10만 건) | 99 → 990 | 10배 |
| 브랜드 7에만 몰림 (이번 쏠림 조건) | 990 → 87,390 | 약 88배 |

- 4주차의 1만 → 10만 건 확장은 브랜드 100개를 유지했으므로 "브랜드마다 상품이 늘어난" 경우다.
- 데이터 전체가 buffer pool(128MiB)보다 커지면 같은 행도 디스크에서 읽을 수 있어 시간이 늘 수 있다. 이 경우는 재지 않았다.
- 브랜드 필터가 없는 목록은 조건에 걸리는 행이 곧 전체 활성 상품이라 전체 데이터와 함께 커진다.

## 그래서 캐시는 어디에 두나?

- **같은 20개를 보여줘도, 가격순은 인덱스로 바로 고를 수 있었고 인기순은 전체 후보의 좋아요 수를 비교해야 했다. 캐시가 대신하는 일의 크기가 달라서 효과도 달랐다.**
- 캐시를 붙일지 판단할 때 **원본이 조건에 걸리는 행을 몇 개 읽는지와, 그 수가 브랜드 크기를 따라 늘어나는 양상**을 먼저 확인한다. 실제로 붙일지는 같은 키의 재사용 빈도, miss 비용, 허용할 지연도 함께 본다. 가격순은 990개·87,390개 모두 상품 20행에서 멈췄고, 인기순은 2,000행에서 174,800행이 됐다. 한 시점의 응답 시간만 보면 두 경로가 10ms 안팎으로 비슷해 이 차이가 가려진다.
- 가격순은 원본이 구조상 20행에서 멈춰 캐시 이득이 데이터 규모로 생기지 않았고 API 응답 시간도 개선되지 않았다. 이번 조건에서는 운영 적용을 뒷받침할 이득이 작아, 운영 적용 시 캐시 없는 DB 조회를 우선 검토한다(요청량·환경이 달라지면 다시 판단한다, [ADR 0021](../adr/0021-price-page-cache-aside-with-after-commit-eviction.md)).
- 인기순은 원본이 조건에 걸리는 행에 비례해 캐시를 둔다. 대가로 순위는 TTL 60초 동안 재사용해 늦게 반영하고, 현재 좋아요 수와 내 하트는 매번 DB에서 읽는다([ADR 0025](../adr/0025-popular-page-snapshot-with-ttl.md)).
- 이 비교는 인기순 원본을 DB 정렬로 개선한 뒤의 코드로 다시 쟀다. 원본을 싸게 만들면 캐시의 몫이 줄어든다. 인기순 원본을 DB 정렬로 바꾸기 전에는 990개 브랜드의 hit 감소가 74~76%였고 지금은 54~55%다. 큰 브랜드에서는 여전히 원본이 비싸 캐시의 몫이 크다.

### 히트율과 hit 한 번이 아끼는 양은 다르다

조건에 걸리는 행 수가 바꾸는 것은 **히트율이 아니다**.

| 구분 | 무엇으로 정해지나 | 이번 측정에서 |
| --- | --- | --- |
| 히트율 | 같은 키로 요청이 얼마나 자주 오는지, TTL(가격순 300초·인기순 60초), 키를 얼마나 자주 지우는지 | 운영 히트율은 재지 않았다. 브랜드 크기와는 무관하다 |
| hit 한 번이 아끼는 양 | 캐시가 없을 때 원본이 하는 일 | 가격순은 약 0.2ms로 거의 없고, 인기순은 990개 약 1.3ms에서 87,390개 약 83ms로 커졌다 |

```text
hit로 절감한 원본 DB 작업 ≈ 히트율 × hit 한 번이 아끼는 양
```

이 식은 hit로 피한 원본 작업만 센다. 캐시의 전체 이득을 말하려면 miss의 추가 비용(키가 빈 순간 겹친 계산 포함)과 저장·무효화 비용을 함께 빼야 한다.

가격순은 히트율이 높아도 hit 한 번이 아끼는 양이 거의 없어 이번 조건에서 이득이 작았다. 인기순은 아끼는 양이 크고, 이번 실험에서는 브랜드가 클수록 더 커졌다. 1분에 같은 요청이 100번 온다면 두 정렬의 히트율은 비슷하지만, 줄어드는 DB 일은 크게 다르다.

### 만료까지 포함한 지속 조회

위 식은 순간의 hit만 본다. 스레드 20개가 150초 동안 계속 요청하고 TTL 60초가 저절로 끝나게 한 지속 조회에서는, 만료 순간의 겹친 계산까지 포함한 요청당 DB 시간이 87,390개 브랜드에서 캐시 없음 884~886ms → Redis 1.50~1.52ms, 990개 브랜드에서 3.17~3.59ms → 1.18~1.30ms였다. 처리량은 각각 21 → 약 1,150 요청/초, 약 930 → 약 1,170 요청/초였다. 만료 순간의 비용까지 넣어도 인기순 캐시의 이득은 유지됐다([캐시 스탬피드](cache-stampede.md#지속-조회에서-본-만료-순간), [41절](implementation-log.md#popular-sustained)).

## 만료 순간: 키가 비면 무슨 일이 생기나?

원본이 커지는 경로는 키가 비는 순간도 위험하다(자세한 내용은 [캐시 스탬피드](cache-stampede.md)). 키를 지운 직후 스레드 N개를 함께 출발시켜, 원본 순위 계산이 몇 번 일어나는지 셌다.

| 데이터 | 상태 | 동시 | 순위 재계산 / 묶음 | 실패 | p50 |
| --- | --- | ---: | ---: | ---: | ---: |
| 990개 (변경 전 코드) | 키 삭제 직후 | 20 | 9~20 (평균 13.9) | 0 | 68.8~73.0ms |
| 990개 (변경 전 코드) | 키 삭제 직후 | 80 | 8~22 (평균 15.1) | 0 | 108.7~126.8ms |
| 87,390개 (변경 전 코드) | 캐시 없음 | 20 | — | 271 / 300 | 8,177~12,339ms |
| 87,390개 (변경 전 코드) | 키 삭제 직후 | 20 | — | 175 / 200 | 6,736~15,492ms |
| 87,390개 (변경 후 코드) | 캐시 없음 | 20 | 20 | 0 / 300 | 973~988ms |
| 87,390개 (변경 후 코드) | 키 삭제 직후 | 20 | 20 | 0 / 300 | 966~1,009ms |
| 87,390개 (변경 후 코드) | 키가 차 있음 | 20 | 0 | 0 / 300 | 28~35ms |

- 키가 비면 첫 저장 전까지 들어온 요청이 각자 원본을 계산한다.
- 변경 전 코드는 요청마다 브랜드 상품 87,390개를 엔티티로 올려 앱에서 정렬했다. 동시 20에서 앱 메모리(힙 512MB)가 부족해 500·무응답이 났고, 이후 키가 찬 요청까지 실패하거나 앱이 종료됐다.
- 그래서 likes_desc·popular의 원본을 DB가 정렬해 한 페이지 ID만 읽도록 바꿨다([ADR 0026](../adr/0026-likes-ranking-sorted-in-database.md)). 바꾼 뒤 같은 조건의 실패는 0이 됐지만, 키가 빈 순간 동시 20 요청의 p50은 약 1초였다. 실패는 없어졌지만 만료 순간 지연은 남았다.
- 계산이 긴 큰 브랜드에서는 키가 빈 순간 들어온 20개 요청이 모두 각자 계산한다. 같은 키의 계산을 하나로 합치는 처리(single-flight)는 아직 없다.

## 한계

- 순차 측정과 동시 20·80 묶음까지다. 지속 부하·최대 처리량·서버 전체 CPU는 재지 않았다.
- 앱·MySQL·Redis가 한 노트북의 CPU를 나눠 쓴다. 절대값보다 같은 환경의 비교로 읽는다.
- 쏠림 조건은 한 브랜드만 키운 실험용 데이터다. 전체 데이터가 buffer pool보다 커지는 경우는 재지 않았다.
- 같은 조건 비교의 원본 JSON은 현재 로컬에 보관한다.
