# 캐시 스탬피드: 키가 비는 순간 몰린 요청

캐시 스탬피드는 캐시 키가 비는 순간 몰린 요청들이 한꺼번에 원본(DB)으로 가는 현상이다. 첫 요청이 원본을 계산해 저장하기 전까지 들어온 요청은 모두 miss가 되어 같은 계산을 각자 한다.

```text
평소:   요청 100개 → 캐시 hit → 순위 재계산을 건너뜀 (상품·좋아요 수·하트 조회는 남음)

키가 비는 순간 (TTL 만료, 또는 상품 추가·삭제로 키 삭제):
  요청 1  → miss → DB에서 순위 계산 시작 ...
  요청 2  → miss → DB에서 같은 계산 시작 ...   ← 요청 1이 저장하기 전이라 또 miss
  요청 3  → miss → DB에서 같은 계산 시작 ...
  ...
  요청 1이 저장 → 그 뒤 요청부터 hit
```

원본 계산이 비쌀수록 겹친 요청마다 DB 일이 커지고, 계산이 오래 걸려 첫 저장이 늦을수록 겹치는 요청 수가 늘어난다. 이 문서는 인기순 캐시(TTL 60초)에서 이 현상을 측정한 기록이다. 가격순은 원본이 인덱스로 20행만 읽어 키가 비어도 겹친 계산의 비용이 작다([캐시가 덜어 주는 DB 일](cache-db-work.md)).

## 어떻게 쟀나

| 항목 | 조건 |
| --- | --- |
| 요청 | `GET /api/v1/products?brandId=7&page=0&size=20&sort=popular`, `X-USER-ID: 95` |
| 동시 요청 | 스레드 N개를 barrier로 함께 출발시킨 한 묶음. 도착 시점까지 같게 강제하지는 않는다 |
| 상태 | 캐시 없음(인기순 캐시를 끈 앱), 키 삭제 직후(묶음 직전에 키 삭제), 키가 찬 상태(묶음 직전에 키 채움) |
| 다시 계산한 수 | 묶음 동안 브랜드 전체를 읽는 순위 계산 문장이 실행된 횟수(`performance_schema`) |
| 실패 | HTTP 500, 30초 무응답, 연결 끊김 |
| 데이터 | 상품 10만 건. 브랜드 7이 990개인 경우와, ID 1~90,000을 브랜드 7로 바꿔 87,390개로 만든 경우 |
| 환경 | 한 노트북의 MySQL·Redis·앱 1개(커넥션 풀 40). 매 성공 응답을 seed 기대값과 대조 |

## 결과

### 브랜드 7 = 990개 (앱에서 정렬하던 코드)

| 상태 | 동시 | 다시 계산한 수 / 묶음 | 실패 | p50 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 캐시 없음 | 20 | 19~20 | 0 | 72.9~75.6ms | 125.4~144.5ms |
| 캐시 없음 | 80 | 79~80 | 0 | 189.5~211.8ms | 274.2~287.2ms |
| 키 삭제 직후 | 20 | 9~20 (평균 13.9) | 0 | 68.8~73.0ms | 101.9~112.8ms |
| 키 삭제 직후 | 80 | 8~22 (평균 15.1) | 0 | 108.7~126.8ms | 161.7~175.9ms |
| 키가 찬 상태 | 20·80 | 0 | 0 | 31.8~74.4ms | 43.5~177.2ms |

키가 비면 첫 저장 전까지 들어온 요청이 각자 계산했다. 계산이 짧아(요청 하나 DB 약 4.6ms) 동시 80에서도 평균 15번 정도에서 멈췄고, 실패는 없었다.

### 브랜드 7 = 87,390개 (현재 코드, DB에서 정렬)

| 상태 | 동시 | 다시 계산한 수 / 묶음 | 실패 | p50 |
| --- | ---: | ---: | ---: | ---: |
| 캐시 없음 | 20 | 20 | 0 / 300 | 973~988ms |
| 키 삭제 직후 | 20 | 20 | 0 / 300 | 966~1,009ms |
| 키가 찬 상태 | 20 | 0 | 0 / 300 | 28~35ms |

계산 하나가 약 1초로 길어, 첫 저장 전에 20개 요청이 모두 원본에 들어갔다. 키가 빈 순간에는 캐시가 없는 것과 같은 일을 했다. 실패는 없지만 그 순간의 응답은 p50 약 1초다. 허용 응답 시간을 정하지 않았으므로 이 지연을 받아들일지는 따로 판단한다.

원본을 앱 정렬에서 DB 정렬로 바꾼 이유와 변경 전 결과는 [ADR 0026](../adr/0026-likes-ranking-sorted-in-database.md)에 둔다.

## 지속 조회에서 본 만료 순간

### 왜 지속 조회가 필요했나

앞의 측정은 모두 조각이었다. 87,390개 브랜드 기준으로 정리하면 이렇다.

| 조각 | 측정값 | 출처 |
| --- | --- | --- |
| hit 하나 | DB 1.13~1.16ms | [36절](implementation-log.md#likes-db-sorted-page), 순차 요청 |
| 캐시 없음(원본) 하나 | DB 84.2~84.5ms | 36절, 순차 요청 |
| miss 하나 | DB 85.1~86.3ms (원본 계산 + 캐시 저장) | 36절, 순차 요청 |
| 키가 빈 순간 동시 20 요청 | 20번 겹쳐 계산, p50 약 1초 | [36절](implementation-log.md#likes-db-sorted-page), 위 결과 |

실제 요청 흐름에서는 이 조각들이 섞인다. hit가 이어지다 60초마다 키가 만료되고, 그 순간 몰린 요청들이 겹쳐 계산한다. hit로 아낀 것보다 만료 순간에 겹쳐 쓴 것이 더 크면 캐시를 둬도 전체로는 손해일 수 있다. 예를 들어 TTL이 1초라면 매초 스레드 20개가 각자 약 84ms짜리 계산을 해서, 모든 요청이 계산하는 캐시 없음과 큰 차이가 없다. 그래서 "hit가 싸다"만으로는 "캐시가 이득이다"를 말할 수 없고, 만료를 포함한 흐름 전체로 확인했다. 결론을 뒤집으려는 측정이라기보다, 이미 낸 결론이 실제에 가까운 조건에서도 유지되는지 확인하는 마무리 검증이다.

### 결과

키를 일부러 지우지 않고 스레드 20개가 150초 동안 계속 요청해, TTL 60초가 저절로 두 번 끝나게 했다([41절](implementation-log.md#popular-sustained)).

| 데이터 | 경우 | 처리량(요청/초) | 실패 | p50 / p95 / p99(ms) | 요청당 DB 실행 시간 | 150초 동안 순위 재계산 |
| --- | --- | ---: | ---: | --- | ---: | ---: |
| 87,390개 | 캐시 없음 | 21.0 | 0 | 971~974 / 1,298~1,320 / 1,424~1,439 | 884~886ms | 3,153~3,165 (모든 요청) |
| 87,390개 | Redis | 1,147~1,154 | 0 | 16.0 / 24.4~24.6 / 30.8~32.2 | 1.50~1.52ms | 40 |
| 990개 | 캐시 없음 | 921~938 | 0 | 19.3~20.7 / 29.7~33.0 / 37.0~48.6 | 3.17~3.59ms | 138,150~140,597 (모든 요청) |
| 990개 | Redis | 1,160~1,182 | 0 | 15.5~15.9 / 24.0~26.6 / 31.6~43.1 | 1.18~1.30ms | 20~32 |

- 87,390개 브랜드에서 가장 느린 40개 요청(= 재계산 40번)은 세 회차 모두 59초·120초, 곧 TTL이 끝난 두 순간에 몰려 있었다. 응답은 약 0.5~1초였다.
- 그래도 이 40개는 전체 약 17만 3천 개 중 일부라 p95·p99에 드러나지 않았고, 요청당 DB 시간은 만료 비용을 포함해 캐시 없음의 약 1/590이었다.
- 즉 겹친 계산은 실제로 생기지만, 60초에 한 번 그 순간 들어온 요청 몇 개가 기다리는 비용이다. 백분위수만 보면 보이지 않으므로 최댓값이나 시간대별 기록으로 본다.

## 지금 상태

같은 계산이 여러 번 겹치는 것은 남아 있다. 막는 처리는 넣지 않았다([ADR 0025 한계 3](../adr/0025-popular-page-snapshot-with-ttl.md)).

## 막는 방법과 지금 넣지 않은 이유

| 방법 | 어떻게 | 걸리는 점 |
| --- | --- | --- |
| 한 번만 계산(single-flight) | 같은 키는 첫 요청만 계산하고 나머지는 그 결과를 기다린다 | 앱 하나 안에서만 막는다. 앱이 여러 대면 대마다 한 번씩 계산한다. 기다리는 요청은 그동안 요청 스레드를 쥔다 |
| Redis 락 | 락을 잡은 요청만 계산하고 나머지는 잠깐 기다렸다 캐시를 다시 본다 | 락을 잡은 요청이 죽거나 늦으면 나머지가 기다리거나 결국 각자 계산한다. 락 만료 시간·재시도 간격을 정해야 하고 Redis 왕복이 늘어난다 |
| 만료 전에 미리 갱신 | TTL이 끝나기 전에 한 요청이 미리 다시 계산한다 | 아무도 안 보는 브랜드 키도 갱신할 수 있다. 갱신 시점 판단이 들어간다 |
| 옛 값을 주며 뒤에서 갱신 | 만료돼도 옛 순위를 보여 주고 하나만 다시 계산한다 | 순서 지연이 60초보다 길어질 수 있다. 백그라운드 실행과 실패 처리가 필요하다 |

모든 방법이 "기다림"이나 "더 늦은 값" 중 하나를 대가로 치르고, 상태(락·진행 중 계산·갱신 시점)를 하나 더 관리하게 한다. 지금은 넣지 않았다.

- 겹친 계산의 비용은 브랜드 키마다 60초에 한 번, 키가 비는 순간에만 생긴다. 990개 브랜드의 계산은 요청 하나에 DB 약 2.3ms다.
- 87,390개처럼 계산이 긴 브랜드에서는 겹친 20번이 DB에 부담이 될 수 있다. 다만 동시 부하에서 DB CPU가 실제로 차는지는 재지 않았다.

## 다시 볼 조건

- 지속 부하에서 키가 비는 순간 DB CPU나 커넥션 대기가 눈에 띄게 오르면 막는 처리를 넣는다. 인기순은 순서 지연을 이미 허용했으므로, 넣는다면 "옛 값을 주며 뒤에서 갱신"이 정책과 가장 잘 맞는다.
- 앱 서버가 한 대이고 계산이 짧으면 한 번만 계산(single-flight)이 가장 단순하다.
- 넣은 뒤에는 같은 조건(87,390개, 키 삭제 직후 동시 20)에서 다시 계산한 수가 20번에서 줄어드는지 잰다.
