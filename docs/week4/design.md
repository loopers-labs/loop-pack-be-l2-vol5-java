# 4주차 설계 문서 — 캐시를 붙이기 전에 병목 증명하기

> **요약**
> 1. 상품 조회(목록·상세)를 빠르게 만들기 전에, 바뀌면 안 되는 **조회 계약**을 정하고 인수 테스트(RestAssured)로 고정한다 — 최적화는 "같은 결과"를 전제로만 인정한다.
> 2. 재현 가능한 1만 건 seed에서 브랜드 필터 + 가격순 목록의 SQL 수·실행 계획·지연을 **측정해 병목을 증명**한 뒤 인덱스·쿼리를 개선하고, 전후 결과가 같은지 비교한다.
> 3. 그다음 한 조회 경로에 Redis 캐시를 붙이며, 응답을 바꾸는 **모든 쓰기 경로의 무효화 책임**과 Redis 장애·오래된 캐시에서의 동작을 정한다.

2·3주차 설계(`docs/week2/design.md`, `docs/week3/design.md`)를 그대로 이어받는다. 이 문서는 이번 주에 **바뀌거나 새로 정한 것**만 적는다. 측정·캐시·장애 섹션은 해당 단계를 진행하면서 채운다.

## 1. 이번 주 범위 — 사실과 결정

| 구분 | 내용 |

## 2. 상품 조회 계약 — 최적화 전후로 바뀌면 안 되는 것

### 목록 `GET /api/v1/products`

| 항목 | 계약 |
|---|---|
| 필터 | `brandId`(선택). 없으면 전체 브랜드. |
| 정렬 `sort` | 기본 `latest`. 셋 다 동점일 때 `name ASC, id ASC`로 순서를 고정한다. |
| | `latest` = `createdAt DESC, name ASC, id ASC` |
| | `price_asc` = `price ASC, name ASC, id ASC` |
| | `likes_desc` = `좋아요 수 DESC, name ASC, id ASC` — **전체 후보를 정렬한 뒤** 페이지를 자른다(페이지 안에서만 정렬하지 않는다). |
| 페이지 | `page` 기본 0(0부터 시작), `size` 기본 20. 1·2페이지 사이에 빠지거나 겹치는 상품이 없어야 한다. |
| 비노출 | 삭제된 상품은 목록·상세·전체 건수에서 모두 빠진다. 브랜드 삭제는 연결 상품을 함께 삭제하므로(3주차) 삭제된 브랜드의 상품도 보이지 않는다. |
| 없는 브랜드 | 존재하지 않거나 삭제된 `brandId` → **200 + 빈 목록**(404가 아니다). 쿼리가 필터만 걸기 때문에 생긴 현재 동작을 계약으로 명시한다. |
| 응답 필드 | 상품마다 `id, name, price, remainingStock, brand{id, name}, likeCount`. 페이지 정보 `page, size, totalElements, totalPages`. |
| `likeCount` | 현재 유효한 좋아요 관계(User–Product)의 수. 취소는 관계 행을 삭제한다(`LikeService.cancel`). 카운터 열이 아니라 관계에서 집계한다(2주차 결정). |
| 반영 시점 | 쓰기가 commit된 뒤 새로 시작한 조회는 변경된 값을 본다. **예외: `likeCount`와 `likes_desc` 순서는 최대 60초 늦게 반영될 수 있다**(캐시 도입으로 이번 주 변경 — 6번 섹션). |
| 오류 | 잘못된 `sort` → 400, `page < 0` → 400, `size < 1` → 400, **`size > 100` → 400 (이번 주 추가 — 2주차 design.md 8번 섹션 계약표의 `GET /products` 행을 이 내용으로 대체)**. |

### 상세 `GET /api/v1/products/{productId}`

목록과 같은 응답 필드. 없거나 삭제된 상품은 404.

### 결정: `size` 상한 100, 넘으면 400

- **발견**: `ProductV1Controller.toPageable()`은 `size >= 1`만 확인해서 `size=100000` 같은 요청도 받았다. 한 요청이 읽고 정렬하고 직렬화하는 양을 요청자가 무제한으로 정할 수 있었다 — 이번 주 주제(조회 비용)와 직결된다.
- **상한값**: 고객용 목록 API에서 흔한 값(GitHub `per_page` 100, Stripe `limit` 100)을 따른다. 상품 목록 화면은 보통 20~60개를 보여주므로 정상 요청을 막지 않는다. Spring Data의 기본 `max-page-size` 2000은 프레임워크의 최소 안전장치라 고객용 목록에는 크다.
- **넘었을 때 400 vs 조용히 낮추기**: 조용히 낮추면 클라이언트는 깨지지 않지만 요청한 것과 다른 결과를 받았다는 걸 모른다. 프로젝트의 400 기준("요청자가 입력을 바꾸면 해결되는가")에 맞고, 기존 `size < 1` 처리와도 일관되므로 400.
- **계약 변경**: `size > 100`을 보내던 클라이언트는 깨진다. 이 프로젝트에는 외부 클라이언트가 없어 실제 영향은 없지만 기존 계약을 좁히는 변경이다.

## 3. 인수 조건과 인수 테스트

### 왜 인수 테스트인가

이번 주 작업(인덱스·쿼리·캐시)은 **겉의 동작은 그대로 두고 속을 바꾸는 일**이다. 그래서 최적화 **전에** 현재 계약을 사용자가 관찰하는 결과(HTTP 응답)로 고정하고, 이후 모든 변경에서 같은 테스트가 계속 통과하게 한다. 캐시가 붙으면 조회 결과를 바꾸는 **모든 쓰기 API**가 엮이므로, 범위는 상품 조회 하나가 아니라 "이번 주 변경이 깨뜨릴 수 있는, 사용자가 보는 결과" 전체다.

### 인수 조건 — 버그의 네 방향

| 종류 | 의미 | 예 |
|---|---|---|
| ① 반영돼야 하는데 안 됨 | 오래된 값이 보인다 | 관리자가 가격·이름을 바꿨는데 고객은 이전 값을 본다. 브랜드 이름, 좋아요 등록·취소, 재고 |
| ② 바뀌면 안 되는데 바뀜 | 과거 기록이 흔들린다 | 가격을 바꿨더니 어제 주문의 금액도 바뀐다 |
| ③ 보이거나 되면 안 되는데 됨 | 노출·권한 위반 | 삭제 상품이 목록에 보이거나 주문된다 |
| ④ 순서·페이지가 흔들림 | 같은 조건에서 다른 결과 | 동점 순서가 매번 다르다, 페이지 사이에 상품이 빠지거나 겹친다, 전체 건수가 다르다 |

①은 캐시가 직접 깨뜨리는 조건이고, ②③은 표시 신선도와 바꿀 수 없는 계약이다(삭제된 상품이 캐시에 남아 있어도 주문은 DB 기준으로 거절한다). ④는 인덱스·쿼리 변경이 가장 직접 깨뜨리는 조건이다.

### 시나리오

| # | 시나리오 | 종류 |
|---|---|---|
| A1 | 브랜드 필터 있음/없음 × 정렬 3종 × 페이지: 기대 순서, 동점 순서, 페이지 사이 누락·중복 없음, `totalElements`·`totalPages`. seed에는 가격 동점이 없으므로 **동점 순서는 여기서 작은 데이터로 확인**한다 | ④ |
| A2 | 삭제 상품·삭제된 브랜드의 상품은 목록·상세·전체 건수에서 빠진다. 없거나 삭제된 `brandId`는 200 + 빈 목록 | ③ |
| A3 | 관리자 가격·이름 수정 → 목록·상세·`price_asc` 순서에 반영 | ① |
| A4 | 관리자 상품 등록 → 목록에 나타난다 / 삭제 → 사라진다 | ①③ |
| A5 | 브랜드 이름 변경 → 상품 목록·상세의 브랜드명에 반영 | ① |
| A6 | 브랜드 삭제 → 그 브랜드의 상품은 사라지고 다른 브랜드는 그대로 | ①③ |
| A7 | 좋아요 등록·취소 → 좋아요 수와 `likes_desc` 순서에 반영 (**최대 60초 지연 허용** — 6번 섹션 계약 변경) | ① |
| A8 | 주문 확정·관리자 재고 변경 → `remainingStock`에 반영 | ① |
| A9 | 주문 후 가격 변경 → 내 주문의 금액은 그대로 | ② |
| A10 | 삭제된 상품으로 주문 생성 → 404 | ③ |
| A11 | 오류 계약: 잘못된 `sort`, `page < 0`, `size < 1`, `size > 100` → 400 | ④ |

### 인수 테스트가 다루는 범위와 다루지 않는 범위

인수 테스트는 요청을 **하나씩 순서대로** 보내므로 "변경이 끝난 뒤 새로 시작한 조회"만 검증한다. 아래는 순서를 통제하거나 내부를 봐야 하므로 통합 테스트의 몫이다(실습 문서: 정상 순차 조회의 조건과 장애 정책을 섞지 않는다).

- 요청당 SQL 수, 캐시 hit에서 원본 호출이 줄었는지
- DB 변경 rollback 시 새 값이 노출되지 않는지
- commit 뒤 캐시 무효화 실패
- 늦게 끝난 이전 조회의 캐시 재삽입(래치로 순서 고정)
- Redis 중단·재시작

### 구현 방식

- RestAssured로 `RANDOM_PORT`에 실제 HTTP 요청을 보낸다. 시나리오는 given/when/then으로 읽히게 API 호출을 헬퍼(Steps)로 감싼다.
- 데이터는 가능한 한 관리자 API로 준비한다. 사용자는 생성 API가 없으므로(2주차: 회원가입 범위 밖) 저장소로 직접 넣는다.
- 기존 E2E 테스트(`TestRestTemplate`/`MockMvc`)는 그대로 둔다. 다시 쓰는 건 범위 밖이다.
- 위치: `apps/commerce-api/src/test/java/com/loopers/acceptance/` — `ProductQueryAcceptanceTest`(A1·A2·A11), `ProductChangeAcceptanceTest`(A3~A8), `OrderContractAcceptanceTest`(A9·A10).

### 결정: 관리자 API는 테스트 전용 인증 수단으로 호출한다

- **발견**: `AdminBoundaryConfig`는 `/api-admin/**`에 `hasRole("ADMIN")` 규칙만 두고 **인증 수단을 정하지 않았다**(이 프로젝트는 실제 인증이 범위 밖). 그래서 실제 HTTP로는 모든 관리자 요청이 403이다. 기존 관리자 E2E는 MockMvc의 `user("admin")`으로 SecurityContext를 직접 채워 우회해 왔다.
- **비교**: (A) 테스트에만 같은 권한 규칙 + Basic 인증 + 테스트용 관리자 계정을 운영 체인보다 먼저 적용 / (B) RestAssuredMockMvc로 기존 E2E와 같은 방식 — HTTP 계층을 거치지 않음 / (C) 운영 코드에 인증 추가 — 범위 밖이고 계약 변경.
- **결정 A** (`AcceptanceTestSecurityConfig`): 인수 테스트는 "사용자가 관찰하는 결과"를 보므로 실제 HTTP를 거치는 쪽을 택했다. 관리자를 어떻게 인증하는지는 원래 정해지지 않은 부분이라, 그 부분만 대체하는 건 기존 E2E의 `user("admin")`과 같은 수준의 우회다. `@TestConfiguration`이라 다른 테스트의 컨텍스트에는 들어가지 않는다.
- **감수하는 것**: 운영 `AdminBoundaryConfig` 자체는 인수 테스트에서 실행되지 않는다. 테스트 체인은 CSRF도 끈다(Basic 인증 무상태 호출). "ADMIN이 아니면 403" 규칙은 기존 관리자 E2E가 계속 검증한다.

### 검증 — 테스트가 실제로 계약 위반을 잡는가

일부러 계약을 깨뜨리고 실패하는지 확인했다(확인 후 원복).

| 변이 | 결과 |
|---|---|
| `size > 100` 검사 제거 | `size=101` 테스트 실패 — 잡음 |
| `price_asc` 동점 기준 `name ASC, id ASC` → `id DESC` | **처음엔 통과 — 놓침** |

처음 데이터는 가격 동점이 두 개(apple·cherry)였고 나중에 등록된 apple의 id가 더 컸다. 동점이 둘이면 가능한 순서도 둘뿐이라, 이름순은 id 정순·역순 중 하나와 반드시 겹친다 — 동점 기준이 id로 바뀌어도 테스트가 통과한다. **동점이 셋이고 이름순이 id 정순과도 역순과도 다른 데이터**(등록 순서 melon·lemon·mango)로 테스트를 추가한 뒤, `price_asc`·`likes_desc`의 동점 기준을 id로 바꾼 변이가 4개 테스트에서 실패하는 것을 확인했다.

## 4. 측정 대상과 기준선

### 재현 seed

`seed` 프로필(`--spring.profiles.active=local,seed`)로 띄우면 Hibernate가 스키마를 만든 직후 `seed/product-seed.sql`이 실행된다. `local`의 `ddl-auto: create` 때문에 재시작하면 데이터가 지워지므로, 매번 같은 데이터로 다시 채우는 방식을 택했다.

| 항목 | 값 |
|---|---|
| 브랜드 | 100개. 브랜드 100은 일괄 삭제가 끝난 상태(브랜드·상품 모두 삭제) |
| 상품 | 10,000개. 브랜드 = `(i % 100) + 1`, 가격 = `((i * 37) % 100000) + 100`(가격 중복 없음), 등록 시각 = 기준 + i분 |
| 삭제 상품 | 999개 = 브랜드 100 전체 + `i % 11 = 0`(브랜드와 무관하게 흩어짐). 측정 대상 브랜드 7에도 9개 섞여 있음 |
| 사용자 / 좋아요 | 500명 / 168,317건. 인기 상품(500개) 10개, 0~49개 구간에 동점 다수, 0개 상품 3,457개 |
| 검증값 | 전체 10,000개·가격 합 472,685,000, 브랜드 7은 100개·4,647,200 (실습 문서 값과 일치 확인) |

생성 방식은 교차 조인으로 순번을 만든 뒤 `INSERT … SELECT` 한 번씩이다. 행 단위 프로시저는 느리고, 재귀 CTE는 기본 재귀 한도(1000)를 올려야 하며, CSV + `LOAD DATA`는 1만 건에는 과하다. 실행 시간은 약 5.7초다.

### 측정 대상

브랜드 필터 + `price_asc` 첫 페이지(`brandId=7&sort=price_asc&page=0&size=20`). 나머지 조합은 같은 seed로 기준선만 기록한다.

**요청당 SQL 수와 좋아요 조회 비용** (코드 기준 — 측정에서 확인한다)

| 요청 | SQL | 좋아요 조회 비용 |
|---|---|---|
| 목록 `latest`·`price_asc` | 4개: 페이지 조회, count, 브랜드 `IN`, 좋아요 `GROUP BY … IN(페이지의 상품 id)` | 페이지에 담긴 상품(최대 `size`개)만 집계 |
| 목록 `likes_desc` | 4개. 단 페이지 조회 자체가 `product LEFT JOIN likes … GROUP BY p.id` | **필터를 통과한 후보 전체**의 좋아요를 집계한 뒤 정렬 |
| 상세 | 3개: 상품, 브랜드, 좋아요 count | 상품 1개 |

브랜드·좋아요는 2주차에 이미 일괄 조회로 바꿔 N+1이 없다. 그래서 이번 병목은 SQL 개수보다 **SQL 한 개가 읽고 정렬하는 양**일 가능성이 높다 — 측정으로 확인한다.

### 측정 방법과 조건

| 항목 | 정한 것 |
|---|---|
| 실행 계획 | `ANALYZE TABLE` 후 `EXPLAIN`(사용 key·접근 경로·예상 rows·Extra)과 `EXPLAIN ANALYZE`(실제 rows·loops·정렬 단계·actual time). API가 실제로 실행하는 SQL(로그에서 확인)을 대상으로 하고, 축약 쿼리만 따로 튜닝하지 않는다. |
| 요청당 SQL 수 | `show-sql` 로그로 한 요청의 SQL을 센다. |
| HTTP 지연 | 준비 실행 50회 → 측정 300회, **순차 실행(동시 요청 1)**. p50·p95·p99·max를 기록한다. 평균 하나로 요약하지 않는다. |
| 캐시 | hit와 miss는 다른 경로이므로 따로 측정한다(캐시 단계). |
| 환경 | 로컬 PC, Docker MySQL 8.0(`docker/infra-compose.yml`), 같은 seed·같은 인덱스 상태. 절대값은 이 환경에서만 의미가 있고, 전후 **비교**에 쓴다. |

동시 부하(처리량·연결 풀 대기)는 이번 필수 범위가 아니므로 측정하지 않는다 — 결과의 한계로 적는다.

### 측정 전 가설 (측정 후 확인·반박)

- `idx_product_brand_id(brand_id)`는 브랜드 범위 탐색만 줄인다. 찾은 N개마다 테이블 본체를 다시 읽고, N개 전체를 filesort한 뒤 20개만 쓴다 — `LIMIT`이 재조회·정렬을 줄이지 못한다.
- `(brand_id, price, name, id)` 또는 `(brand_id, deleted_at, price, name, id)`면 정렬 없이 앞에서부터 읽다가 멈출 수 있다. 엔티티 전체를 읽으므로 둘의 차이는 "삭제된 행을 몇 개 읽고 버리느냐"다.
- `(:brandId IS NULL OR p.brand_id = :brandId)`는 MySQL이 매 실행 최적화하고 Connector/J가 값을 채워 보내므로 상수 접기로 무해할 가능성이 높다 — `EXPLAIN`으로 확인한다.
- `likes_desc`는 정렬 키가 집계 값이라 product 인덱스로 받칠 수 없다.

### 결과 동일성 확인

인수 테스트는 작은 데이터로 돈다. 1만 건 seed에서의 결과 동일성은 따로 확인한다 — 기준선 측정 때 응답의 `(id, price, likeCount)` 목록과 페이지 정보를 파일로 떠두고, 개선 후 같은 요청의 결과와 비교한다.

## 5. 인덱스·쿼리 개선

측정 원본: `docs/week4/measurements/` (`baseline-*`, `after-likes-index-*`). 조건은 4번 섹션과 같다. 서버가 실제로 받은 SQL은 `performance_schema.events_statements_history_long`에서 확인했다.

### 기준선 — 측정 대상 요청의 해부 (`brandId=7&sort=price_asc&page=0&size=20`, HTTP p50 54.65ms)

| SQL | 실행 계획 | 실제 시간 |
|---|---|---|
| 상품 페이지 조회 | `idx_product_brand_id`로 100행 → 삭제 걸러 91행 → `Using filesort`(상위 20개만 유지) | 약 1.5ms |
| count | 같은 인덱스로 100행 → 91 | 약 0.3ms |
| 브랜드 `IN (7)` | PK | 무시할 수준 |
| **좋아요 집계 `product_id IN (20개)`** | `Covering index scan on likes using UK(user_id, product_id)` — **168,317행을 읽고 84행만 남김** | **약 35.7ms** |

### 가설 대조 — 측정이 판단을 바꿨다

| 측정 전 가설 | 결과 |
|---|---|
| `brand_id` 인덱스는 탐색만 줄이고 filesort가 남는다 | 맞음 — 다만 브랜드당 상품 100개라 정렬은 1.5ms 수준 |
| `(:brandId IS NULL OR …)`는 상수 접기로 무해하다 | 맞음 — 서버는 `(7 is null or brand_id=7)`을 받았고 계획은 `ref const`. `brandId`가 없으면 `(null is null or brand_id=null)` → 전체 스캔 |
| 요청당 SQL: 목록 4개, 상세 3개 | 맞음 |
| 병목은 상품 쪽 정렬일 것 | **틀림 — 병목은 좋아요 집계(35.7ms)였다.** `likes`의 UK가 `(user_id, product_id)`라 `product_id`는 두 번째 열이고, `product_id`로 탐색을 시작할 수 없어 인덱스 전체를 읽었다(맨 앞 열부터 규칙). 상세의 좋아요 count는 같은 인덱스로도 skip scan(사용자 494개마다 건너뛰며 탐색)이 잡혀 2ms였지만, 목록의 `IN (20개)` 집계에는 옵티마이저가 그 방식을 고르지 않았다. |

### `likes` 테이블의 접근 경로

| 기능 | 조건 | 필요한 맨 앞 열 |
|---|---|---|
| 좋아요 중복 확인·취소, 중복 방지 제약 | `user_id = ? AND product_id = ?` | 순서 무관 |
| 내 좋아요 목록 | `user_id = ?` | `user_id` |
| 상세 좋아요 수, 목록 좋아요 집계, `likes_desc` 조인 | `product_id = ? / IN / ON l.product_id = p.id` | `product_id` |

두 방향이 모두 있으므로 인덱스는 두 개가 필요하다.

### 결정: `UK(user_id, product_id)` 유지 + `idx_likes_product_id(product_id)` 추가

| 대안 | 판단 |
|---|---|
| **A. UK 유지 + `(product_id)` 추가** | 채택 |
| B. UK를 `(product_id, user_id)`로 뒤집고 `(user_id)` 추가 | 인덱스 수는 같지만, 업무 규칙을 담은 제약을 성능 때문에 바꾸게 되고, 계약에 없던 "내 좋아요 목록" 순서(지금은 UK를 따라 `product_id` 오름차순)가 바뀔 수 있다 |
| C. `(product_id, user_id)` 추가 | `product_id` 경로는 모두 개수만 센다 — `user_id`까지 담을 이유가 없고 인덱스만 커진다 |

- **UK와 일반 인덱스의 차이**: 조회 경로로서는 같은 B-Tree다. 다른 점은 UK는 업무 규칙(중복 좋아요 방지)을 DB가 보장한다는 것, 키가 지정 열만으로 유일해 PK를 키에 붙이지 않는다는 것(`innodb_index_stats`: `user_id,product_id`까지), 삽입마다 중복 검사가 필요해 change buffer를 못 쓴다는 것. 규칙은 UK가, 조회 방향은 각 인덱스가 맡는다.
- **단일 열 인덱스에도 PK가 붙는다**: `innodb_index_stats`에서 `idx_likes_product_id`는 `product_id` → `product_id,id`로 나온다. 그래서 `count(l.id)`도 인덱스만으로 끝난다(Covering).
- **감수하는 것**: 좋아요 등록·취소마다 인덱스 하나를 더 갱신한다. 저장 공간 289페이지(UK 481, PK 673페이지 대비).

### 보류: 좋아요 수 비정규화 카운터 (`product.like_count`)

- **검토한 내용**: 전체 `likes_desc`는 인덱스 후에도 요청마다 좋아요 15만 행을 세서 상위 20개를 고른다. 순위는 요청이 아니라 좋아요 등록·취소 때만 바뀌고 목록 조회가 훨씬 잦으므로, 좋아요 수를 상품 행에 열로 두고 바뀔 때 ±1 하면 읽기에서 집계가 사라지고, 정렬 키가 열이 되어 `(brand_id, like_count, …)` 인덱스로 정렬까지 받칠 수 있다.
- **새로 생기는 책임**: 관계와 카운터를 같은 트랜잭션에서, 관계가 **실제로** 추가·삭제됐을 때만 ±1(중복 요청에 카운터만 움직이면 안 됨), 동시 갱신은 원자적 UPDATE(3주차 갱신 유실), 좋아요가 상품 행을 쓰게 되어 3주차의 "상품 행 쓰기는 같은 잠금에 참여" 규칙 안으로 들어오고 인기 상품 행이 경합 지점이 된다.
- **보류 근거**: 발제 — "현재 필요한 개선이 쿼리 조정으로 충분하다면 카운터나 조회용 테이블을 추가할 이유는 없다", 카운터 비정규화는 선택 심화. 측정 대상의 병목(좋아요 집계)과 브랜드 필터 `likes_desc`는 인덱스로 0.1~0.9ms가 됐다.
- **다시 꺼낼 조건**: 전체 `likes_desc`가 주 사용 경로가 되거나, 좋아요 증가로 이 요청이 허용 지연을 넘을 때. 남은 비용이 좋아요 전체 건수에 비례한다는 점은 알고 보류한다.

### 보류: 상품 쪽 복합 인덱스

측정 원본: `docs/week4/measurements/product-index-candidates.txt`. 100만 행 데이터는 `scale-seed.sql`, 쓰기 측정은 `scale-writes.sql`로 재현한다.

후보는 "정렬을 인덱스 순서로 받쳐 filesort를 없애는" 네 개다.

| 후보 | 열 | 받치는 요청 |
|---|---|---|
| c1 | `(brand_id, deleted_at, price, name)` | 브랜드 필터 + `price_asc` |
| c2 | `(brand_id, deleted_at, created_at DESC, name)` | 브랜드 필터 + `latest` |
| c3 | `(deleted_at, price, name)` | 전체 + `price_asc` |
| c4 | `(deleted_at, created_at DESC, name)` | 전체 + `latest` |

**1만 행([A])**: 각 후보는 **정확히 한 가지 요청 모양**의 filesort만 없앤다. 정렬 3종 × 브랜드 필터 유무를 모두 받치려면 인덱스 4개가 필요하고, `likes_desc`는 정렬 키가 집계 값이라 어느 상품 인덱스로도 받칠 수 없다. 측정 대상의 상품 정렬은 1.5ms로, HTTP 27.8ms의 약 5%다.

**100만 행으로 키워본 결과([B]~[E])** — 데이터: 브랜드1 50만 건(삭제 10만), 브랜드7 5,051건(삭제 0), 전체 삭제 10%. Windows Docker 측정이라 편차가 크다. 절대값이 아니라 배율로 읽는다.

| 쿼리 | 기존 인덱스만 | 후보 4개 |
|---|---|---|
| 브랜드1 latest / price_asc | 3,403 / 3,295ms | 0.2 / 0.5ms |
| 브랜드1 500페이지 | 3,508ms | 33ms |
| 브랜드7 price_asc | 86ms | 0.5ms |
| 전체 latest / price_asc | 940 / 833ms | 0.2 / 0.5ms |
| 브랜드1 count | 3,033ms | 1,249ms |
| **전체 count** | 374ms | **4,604ms (악화)** |

- **부작용 — 다른 쿼리가 느려진다**: c3만 켜면 전체 latest 873 → 5,779ms, 전체 count 260 → 5,088ms. c4만 켜면 전체 price_asc 790 → 4,140ms. 옵티마이저가 `deleted_at is null` 범위를 좁히려고 새 인덱스를 고른 뒤, 행마다 본체를 다시 읽는다.
- **count가 악화된 원인([E])**: 통계는 `ANALYZE` 직후라 최신이었다. 옵티마이저는 `(null is null or brand_id=null)`을 `deleted_at is null`로 접었지만(`SHOW WARNINGS`로 확인), 접은 뒤에도 c3를 커버링으로 판정하지 않아 90만 행을 본체 재조회했다(`Using index condition`, 4.6s). 브랜드 절을 뺀 같은 의미의 쿼리는 커버링으로 241ms다.
- **count는 인덱스로 근본 해결이 안 된다**: 목록과 count는 WHERE가 같다. 하지만 목록은 인덱스 순서로 읽다가 20개를 찾으면 멈추고, count는 조건에 맞는 행을 끝까지 센다. InnoDB는 MVCC 때문에 행 수를 따로 저장하지 않는다.
- **쓰기 비용([D], 2만 건)**: 후보 4개를 추가하면 등록 0.3~0.5s → 8.9~14.8s, 가격 수정 0.2~0.5s → 3.3~6.7s, 재고 변경 0.2s → 0.5~2.9s다. 재고 변경은 인덱스 열을 바꾸지 않는데도 느려졌다. 버퍼 풀(128MB) 압박으로 추정하지만 검증하지는 않았다.
- **나중에 추가하는 비용([C])**: 100만 행 기준 인덱스 하나 생성에 12~15초가 걸린다. 크기는 c1/c2 59.7MB, c3/c4 50.7MB다. 동시 트래픽이 없는 상태에서 측정한 값이다.
- 제외한 측정값: c1만 켠 상태의 브랜드1 latest 77초. 실행 계획이 기준선과 같아 I/O 잡음으로 보고 제외했다.

**결정: 이번 주에는 상품 쪽 복합 인덱스를 추가하지 않는다.**

- 병목이 아니다. 측정 대상에서 상품 정렬은 1.5ms이고, 남은 27.8ms 중 대부분은 DB 밖에 있다.
- 캐시가 어떻게 동작하든 결론은 같다. 캐시가 매번 무효화되는 최악의 경우에도 이 쿼리는 1.5ms다. 캐시가 잘 맞으면 쿼리 실행 횟수가 줄어 0.5ms로 줄이는 이득은 더 작아진다.
- 미리 넣으면 비용이 생긴다. 모든 쓰기가 인덱스 4개를 갱신해야 하고, 다른 쿼리가 오히려 느려지는 계획 회귀가 실제로 확인됐다. 반면 나중에 추가하는 비용은 인덱스 하나에 약 15초다.

**다시 꺼낼 조건**

- 상품 목록 관련 쿼리 하나가 **단독으로 p95 100ms**를 넘으면 다시 검토한다. 평균은 상품이 몰린 브랜드 하나의 지연을 가린다. 위 측정에서 같은 쿼리가 작은 브랜드에서는 86ms, 상품이 몰린 브랜드에서는 3.4s였다.
- **count부터 본다.** 같은 데이터에서 목록보다 count가 먼저, 더 크게 느려진다(100만 행에서 목록 0.5ms, count 1~3s).
- 전체 상품 수보다 **브랜드별 상품 쏠림**이 먼저 이 조건을 건드린다. 한 브랜드의 대량 등록만으로도 그 브랜드 페이지가 조건을 넘을 수 있다.
- 다시 검토할 때는 이번 측정처럼 후보를 하나씩 켜서, 다른 요청 모양의 계획이 회귀하는지까지 확인한 뒤 추가한다.

**count 처리 방식** — 캐시하면 "삭제 직후 전체 건수 반영"(A4, `ProductChangeAcceptanceTest`)이라는 조회 계약이 바뀐다. 멘토링(10/14) 답변: 목록의 전체 건수는 실시간성을 엄격하게 잡지 않아도 되며, 불일치를 허용해도 된다.

- **건수 하나가 두 가지 일을 하고 있다.** 하나는 페이징(`totalPages`, 마지막 페이지 판단)이고, 다른 하나는 화면에 표시하는 상품 수다. 페이징용은 목록과 반드시 맞아야 한다. 같은 응답 안에서 목록은 3개인데 `totalElements`가 4이면 빈 페이지가 생긴다. 표시용은 정확하지 않아도 된다. 일정 건수를 넘으면 "1k", "2k"처럼 근사해서 보여줘도 된다.
- 그래서 느린 count는 캐시로 가릴 문제가 아니라 **응답 계약(요구사항)에서 풀 문제**로 본다. 예를 들어 표시용 건수에 상한을 두면 건수가 아무리 늘어도 세는 비용은 그 상한까지만 든다.
- **이번 주 결정: count를 따로 캐시하지 않는다.** 측정 대상의 count는 0.3ms로 재검토 기준(p95 100ms)에 한참 못 미친다. 응답 계약 변경도 이번 주 범위 밖이다. `totalElements`는 지금처럼 목록과 같은 시점의 정확한 값으로 유지하고, A4는 그대로 둔다. 목록 응답을 통째로 캐시할 경우에도 목록과 건수는 한 응답 안에서 같은 시점 값이어야 한다.

## 6. 캐시 범위

### 결정: 상세와 목록 모두, 목록은 "id 순서"와 "상품 내용"을 나눠 저장한다

과제는 한 조회 경로를 요구하지만, 측정 대상이 목록(`brandId=7&sort=price_asc`)이라 상세만 캐시하면 재측정에서 측정 대상이 바뀌지 않는다. 그래서 목록까지 포함한다. 이득이 가장 큰 곳은 인덱스로도 줄이지 못한 전체 `likes_desc`(약 95ms)다.

목록 응답을 통째로 하나의 값으로 저장하지 않는다. 쓰기 경로를 "무엇을 바꾸는가"로 나누면 다음과 같다.

| 쓰기 | 빈도 | A. 어떤 상품이 어떤 순서로 (id 목록·페이지 정보) | B. 각 상품의 내용 |
|---|---|---|---|
| 관리자 상품 등록·수정·삭제 | 드묾 | ✔ | ✔ |
| 관리자 브랜드 수정 | 드묾 | | ✔ (브랜드명) |
| 관리자 브랜드 삭제 | 드묾 | ✔ | ✔ |
| 관리자 재고 변경 | 드묾 | | ✔ |
| **주문 확정** | 잦음 | | ✔ |
| **좋아요** | 가장 잦음 | `likes_desc` 순서만 (TTL로 허용) | `likeCount` (TTL로 허용) |

- A를 **즉시** 바꾸는 쓰기는 드문 관리자 작업뿐이다. 재고는 `latest`·`price_asc` 순서를 바꾸지 않는다.
- B는 잦은 쓰기에 바뀌지만 언제나 **상품 하나 단위**다.
- 목록 응답 하나를 통째로 저장하면 그 안에 상품 20개의 재고가 들어 있어 주문 확정마다 지워야 한다. 주문된 상품이 들어 있는 목록 키(정렬·필터·페이지·size 조합)를 하나하나 찾을 수 없으니 목록 캐시 전체를 버리게 되고, 주문이 잦아지면 적중률이 0에 가까워진다.

### 키와 값

| 키 | 값 | 쓰는 곳 |
|---|---|---|
| `product:list:v{버전}:{brandId 또는 all}:{sort}:{page}:{size}` | `ids`, `totalElements` (`page`·`size`는 키에 있고 `totalPages`는 계산한다) | 목록 |
| `product:{id}` | `id`, `name`, `price`, `remainingStock`, `brandId`, `likeCount` | 상세, 목록 |
| `brand:{id}` | `id`, `name` | 상세, 목록 |

- **목록 조회**: 목록 키에서 id를 꺼낸다 → 상품 키를 `MGET` → 없는 상품만 DB에서 일괄 조회해 채운다 → 브랜드 키도 같은 방식 → id 순서대로 조립한다.
- **id와 `totalElements`는 한 키에 함께 저장한다.** 한 응답 안에서 목록과 건수가 같은 시점 값이어야 하기 때문이다(5번 섹션 count 결정 — 목록 3개에 `totalElements` 4면 빈 페이지가 생긴다).
- **목록 키에 버전을 넣는 이유**: 순서를 바꾸는 쓰기가 생기면 어떤 목록 키가 영향을 받는지 하나하나 찾을 수 없다. 키를 지우는 대신 버전(`INCR`)을 올려 이전 목록 키 전체를 읽히지 않게 하고, 남은 키는 TTL로 사라지게 한다. 순서를 바꾸는 쓰기는 드문 관리자 작업뿐이라 목록 캐시 전체가 비는 비용을 감수한다.
- **브랜드를 상품 키에서 분리한 이유**: 상품 키에 브랜드명을 넣으면 브랜드 이름 변경 때 그 브랜드의 상품 키를 모두 지워야 한다(100만 행 시나리오에서 50만 개). 상품 키 전체에 공통 버전을 두는 방법도 검토했지만, 브랜드 수정 한 번에 모든 브랜드의 상품 캐시가 비고 조회마다 버전을 읽는 왕복이 늘어난다. 브랜드별 버전은 상세 요청(`/products/{id}`)이 브랜드를 모르는 상태라 키를 만들 수 없다. 브랜드 키를 분리하면 무효화는 `brand:{id}` 하나이고, 조회 비용은 한 페이지의 브랜드 몇 개를 `MGET`하는 것뿐이다 — DB 조회가 이미 상품과 브랜드를 따로 읽어 붙이는 구조와 같다.
- **응답에 사용자별 필드가 없다**: "내가 좋아요했는지" 같은 필드가 없어 모든 사용자가 같은 캐시 값을 써도 다른 사용자 정보가 섞이지 않는다.

### TTL 60초와 필드별 신선도

| 필드 | 쓰기 후 반영 | 근거 |
|---|---|---|
| 이름, 가격, 재고, 브랜드명, 목록 구성·순서·건수 | **commit 뒤 즉시** (무효화) | 재고·가격의 정확성은 주문 트랜잭션이 보장한다(주문 생성은 DB에서 가격 스냅샷, 확정은 상품 행 락 후 재고 차감). 화면은 바뀌면 바로 지운다. |
| `likeCount`, `likes_desc` 순서 | **최대 60초 늦게** (무효화하지 않음) | 가장 잦은 쓰기라 무효화하면 캐시가 계속 비어 DB로 요청이 몰린다. 다른 사용자는 실제 좋아요 수를 모르므로 지연을 알아챌 수 없고, 누른 본인은 보통 화면에서 먼저 반영(낙관적 UI)한다. |

TTL은 두 가지 일을 한다. ① 좋아요 수의 지연 한도. ② 무효화 실패·늦은 채움 같은 장애 상황에서 **틀린 재고·가격이 보일 수 있는 최대 시간**(8번 섹션). 30초도 검토했지만, 재고·가격은 평소 즉시 무효화되어 TTL과 무관하고, 좋아요 1분 지연은 허용 범위이며, 짧을수록 적중률이 떨어져 DB 조회가 늘어난다.

**계약 변경 — 좋아요 반영 지연**: 2번 섹션의 `likeCount`와 `likes_desc` 계약, 3번 섹션의 A7("좋아요 등록·취소 → 좋아요 수와 `likes_desc` 순서에 반영")은 **즉시 반영**을 전제로 했다. 이를 "최대 60초 안에 반영"으로 바꾼다. 검증은 둘로 나눈다.
- **A7 (인수 테스트)**: 좋아요 뒤 Redis를 비우고(= TTL 만료를 흉내) 다시 조회해 반영을 확인한다. 60초를 실제로 기다리지 않고 "캐시가 만료되면 반영된다"를 확인한다.
- **통합 테스트**: 좋아요 뒤에도 `product:{id}` 키가 남아 있는지 확인한다. "좋아요는 캐시를 지우지 않는다"는 의도한 규칙이라, 나중에 무효화가 추가되어 적중률이 조용히 무너지는 것을 막는다.

### 캐시하지 않는 것

- **count 단독 캐시**: 5번 섹션. 목록 키 안에 id와 함께 저장될 뿐, 따로 캐시하거나 주기적으로 갱신하지 않는다.
- **주문 생성·확정이 읽는 상품**: 정확성의 기준이므로 항상 DB에서 읽는다(`OrderFacade`는 `ProductService`를 직접 쓴다).
- **관리자 조회**: 관리자는 방금 바꾼 값을 바로 봐야 하고 호출 빈도가 낮다.

## 7. 변경 책임 — 상품 응답을 바꾸는 쓰기 경로

모든 무효화는 **commit이 성공한 뒤** 실행한다. commit 전에 지우면 그 사이 다른 조회가 아직 바뀌지 않은 값을 읽어 다시 채우고, 롤백되면 지울 이유가 없었기 때문이다.

| 쓰기 경로 | 바뀌는 응답 | commit 뒤 무효화 |
|---|---|---|
| 관리자 상품 등록 | 목록 구성·건수 | 목록 버전 올리기 |
| 관리자 상품 수정 (이름, 가격) | 상품 내용, `price_asc`·동점 순서 | `product:{id}` DEL + 목록 버전 올리기 |
| 관리자 상품 삭제 | 목록 구성·건수, 상세 404 | `product:{id}` DEL + 목록 버전 올리기 |
| 관리자 재고 변경 | `remainingStock` | `product:{id}` DEL |
| 주문 확정 | `remainingStock` | 주문에 담긴 상품마다 `product:{id}` DEL |
| 관리자 브랜드 수정 | `brand.name` | `brand:{id}` DEL |
| 관리자 브랜드 삭제 (연결 상품 일괄 삭제) | 목록 구성·건수, 상세 404 | 목록 버전 올리기 + `brand:{id}` DEL + 삭제된 상품마다 `product:{id}` DEL |
| 좋아요 등록·취소 | `likeCount`, `likes_desc` 순서 | 없음 — TTL 60초로 늦게 반영 (6번 섹션) |

- **브랜드 삭제에서 지울 상품 id**: commit 뒤에 브랜드 id로 "삭제되지 않은 상품"을 조회하면 이미 모두 삭제돼 0개가 나온다. 그래서 id는 트랜잭션 안에서 확보한다. `ProductService.deleteAllByBrandId()`가 이미 그 상품들을 락으로 읽어 삭제하므로, 삭제한 id 목록을 돌려주게 한다. 상품이 많으면 DEL을 묶어서 보낸다.
- **주문 생성(DRAFT)**: 재고·가격을 바꾸지 않으므로 무효화하지 않는다.

## 8. 장애 계약

**원칙: 정답은 DB, Redis는 언제 사라져도 다시 만들 수 있는 사본이다. Redis의 실패가 요청의 실패가 되지 않는다.** 대신 틀린 값이 보일 수 있는 시간에 상한(TTL 60초)을 둔다. 재고·가격이 틀리게 보여도 주문은 DB 기준이라 틀린 금액이 결제되거나 재고가 초과 판매되지 않는다(6번 섹션).

| 상황 | 동작 | 사용자가 보는 것 |
|---|---|---|
| 조회 중 Redis 실패 (타임아웃·연결 끊김) | **재시도하지 않고** DB에서 읽어 응답한다. 같은 요청 안에서 첫 실패 이후의 Redis 호출(남은 GET·MGET·채우기 SET)은 건너뛴다 | 정상 응답 (조금 느림) |
| 쓰기 commit 뒤 DEL·버전 올리기 실패 | 쓰기 요청은 **성공**으로 응답한다(DB가 이미 정답). 실패한 키를 WARN 로그로 남긴다 | 최대 60초 동안 이전 값 |
| 쓰기 트랜잭션 롤백 | 무효화하지 않는다(commit 뒤에만 실행) | 캐시 그대로 — DB도 그대로라 맞다 |
| 늦은 채움 (DEL 뒤 이전 조회가 옛 값을 SET) | 막지 않는다 | 최대 60초 동안 이전 값 |
| Redis 재시작 | 이 프로젝트의 Redis는 AOF가 켜져 있어(`docker/infra-compose.yml`) 재시작해도 캐시가 **복원**된다. 중지 중 무효화에 실패한 값도 함께 돌아오지만, 만료 시각이 절대 시각으로 저장되어 남은 수명은 원래 TTL 안이다. 데이터가 없는 키는 miss → DB에서 다시 채운다. 같은 키의 동시 miss는 막지 않는다(아래 보류) | 정상 응답. 중지 중 무효화 실패분은 최대 60초 이전 값 |
| replica 복제 지연·단절 | 아래 "읽기는 replica" 참고 | 보통 1ms 미만, 단절 시 최대 60초 이전 값 |

### 결정: Redis 명령 타임아웃 50ms, 연결이 끊기면 즉시 거절, 조회 재시도 없음

- **발견**: `RedisConfig`의 Lettuce 설정에는 타임아웃이 없어 기본값 **60초**가 적용된다. 또 기본 설정은 연결이 끊기면 명령을 거절하지 않고 재연결까지 대기열에 쌓는다. 그대로 캐시를 붙이면 Redis가 멈췄을 때 조회 하나하나가 최대 60초 멈춘다 — 폴백 코드가 있어도 사실상 장애다.
- **재시도 없음**: 조회에서 캐시를 놓친 대가는 DB 한 번(측정 대상 약 2ms)이다. Redis가 완전히 멈춘 상황에서 재시도는 모든 요청의 대기를 두 배로 만들 뿐이다.
- **50ms**: 평소 Redis 조회는 1ms 미만이라 정상 상태에서 타임아웃에 걸리지 않을 만큼 여유를 두고, 장애 때 요청마다 더해지는 지연은 측정 대상 HTTP 시간(27.8ms) 수준으로 제한한다.
- **한 요청 안에서 첫 실패 이후 건너뛰기**: 타임아웃은 명령 하나마다 적용되는데 목록 요청은 Redis 명령을 여러 번(목록 키 GET → 상품 MGET → 브랜드 MGET → 채우기 SET) 보낸다. 건너뛰지 않으면 Redis가 멈춘 동안 요청 하나가 150~250ms 늦어진다.

### 보류: 서킷 브레이커

- **검토한 내용**: 최근 실패가 많으면 한동안 Redis를 부르지 않고 바로 DB로 가는 장치(Resilience4j 등).
- **보류 근거**: Redis가 **꺼진** 경우는 "연결이 끊기면 즉시 거절" 설정만으로 대기 없이 DB로 간다(과제의 Redis 중지 시나리오). 서킷 브레이커가 실제로 필요한 건 Redis가 응답 없이 **느려지거나 멈추는** 경우인데, 이번 주 범위의 장애 모양이 아니다. 들이면 임계치·열림 시간·반열림 상태 설정과 그 전이 테스트가 생기고, Redis가 복구된 뒤에도 열려 있는 동안 캐시를 쓰지 않는다.
- **다시 꺼낼 조건**: Redis 타임아웃이 반복해서 관측될 때 — 원인이 장애든 캐시 조회 증가로 인한 부하든 같다. 원인이 부하라면 서킷 브레이커와 별개로 Redis 확장(replica 추가, 클러스터)도 함께 검토한다. 서킷 브레이커는 부하를 줄이는 장치가 아니라 "제대로 응답하지 못하는 Redis를 매번 기다리는 손해"를 없애는 장치다.

### 보류: 캐시 스탬피드 방지

- **검토한 내용**: 같은 키에 동시 miss가 몰리면 모두 DB로 간다. Redis 재시작 직후와, 인기 키의 TTL 만료 순간(키마다 60초에 한 번) 생긴다. 키별 락(`SET NX`)으로 한 요청만 DB로 보내고 나머지는 기다리게 할 수 있다.
- **보류 근거**: 측정 대상 목록의 DB 비용은 약 2ms라 동시 miss가 몰려도 금방 끝난다. 가장 비싼 키는 전체 `likes_desc`(약 95ms)로, 초당 100건이면 만료 순간 약 10개가 동시에 실행되는 수준이다. 막으려면 락을 잡은 요청이 죽을 때, 기다리는 시간의 상한, Redis 장애 때 락 자체의 실패를 새로 다뤄야 하고 각각 테스트가 필요하다. 과제의 실패 시나리오에도 들어 있지 않다.
- **다시 꺼낼 조건**: 비싼 키(전체 `likes_desc` 등)의 만료 순간 DB 동시 실행이 관측되거나, Redis 재시작 직후 DB 부하가 문제가 될 때.

### 결정: 캐시 읽기는 replica에서 (기존 `REPLICA_PREFERRED` 유지)

- **복제 지연**: DEL과 SET은 master로 가고 복제는 비동기라, DEL 직후 replica에서 이전 값을 읽을 수 있다. 보통 1ms 미만이라 영향이 작다고 판단했다.
- **복제 단절**: master–replica 연결이 끊기면 replica는 기본 설정(`replica-serve-stale-data yes`)으로 이전 데이터를 계속 내준다. DEL은 전달되지 않지만, replica도 만료 시각이 지난 키는 읽기에서 없는 것으로 응답하므로 이전 값은 **최대 TTL 60초**로 제한된다 — DEL 실패와 같은 상한이다.
- 그래서 6번 섹션의 "commit 뒤 즉시"는 정확히는 **"commit 뒤 복제 지연 이내"**다.
- **감수하는 것 — 테스트로 확인할 수 없다**: 테스트 컨테이너(`RedisTestContainersConfig`)는 Redis 한 대를 master와 replica로 함께 쓰므로 복제 지연이 재현되지 않는다. 복제 지연·단절의 동작은 위 설명과 Redis 문서에 근거한 판단으로 남는다.

## 9. 캐시 결과 — 같은 결과, 측정으로 잡은 결함

측정 원본: `docs/week4/measurements/after-cache-latency.txt`. 조건은 4번 섹션과 같다(캐시 hit와 miss는 따로 측정).

**결과 동일성**: 기준선 스냅샷 39개 요청이 캐시 miss 상태와 hit 상태 모두에서 완전히 일치한다.

**요청당 SQL**: 목록 miss 4 / hit 0, 상세 miss 3 / hit 0. 목록 hit 중 상품 키 하나만 빠지면 그 상품만 읽는 2개(상품 `IN`, 좋아요 `IN`).

| HTTP p50 / p95 (ms) | 캐시 없음 | miss | hit |
|---|---|---|---|
| **측정 대상** brand7 price_asc | 27.81 / 34.14 | 33.22 / 49.78 | **6.30 / 8.23** |
| brand7 latest | 26.48 / 31.31 | 32.00 / 47.63 | 6.08 / 8.15 |
| brand7 likes_desc | 26.98 / 33.86 | 32.46 / 44.86 | 6.27 / 9.19 |
| 전체 price_asc | 33.87 / 40.10 | 39.59 / 49.51 | 6.33 / 8.53 |
| 전체 latest | 35.72 / 42.89 | 41.04 / 51.48 | 6.39 / 8.50 |
| **전체 likes_desc** | 95.51 / 106.92 | 98.38 / 113.11 | **6.22 / 8.44** |
| 상세 | 21.85 / 28.15 | 25.40 / 32.15 | 3.88 / 4.87 |

- miss는 캐시 없음보다 약 5ms 느리다 — Redis 왕복 5~6번(버전·목록 조회, 목록·상품 저장, 브랜드 조회·저장, 로컬 왕복 약 0.9ms)의 값이다. 평균이 캐시 없음과 같아지는 손익분기 적중률은 약 20%다.
- 운영 환경의 같은 데이터센터 안 왕복(보통 0.1~0.5ms)이면 miss 비용은 더 작다. 이 수치는 Windows Docker 포트 포워딩을 포함한 로컬 값이다.

### 측정이 잡은 결함: 캐시 채우기가 요청마다 Redis 연결을 새로 맺었다

| 저장 방식 | miss 요청당 새 연결 | 측정 대상 miss p50 |
|---|---|---|
| 파이프라인(`executePipelined`) | master 약 9 + replica 약 6 | 75.56ms — 연속 요청에서 임시 포트 고갈로 측정 중단 |
| 키마다 `SET EX` 차례로 | 0 | 54.23ms — 왕복 약 25번 |
| **Lua 스크립트 한 번(`EVAL`)** | 0 | **33.22ms** — 저장 왕복 1번 |

- **원인**: Spring Data Redis의 파이프라인은 공유 연결이 아니라 전용 연결이 필요하다. 연결 풀이 없으니 호출마다 master·replica에 연결을 맺고 닫았다. 기능 테스트는 결과만 확인하므로 통과했고, 재측정에서만 드러났다.
- **고친 방법**: 원인이 "전용 연결이 필요한 기능"이었으므로 파이프라인을 쓰지 않는다. 먼저 가장 단순한 순차 저장으로 연결 문제를 없앤 뒤 측정했고, 손익분기 적중률이 약 56%로 높아 저장을 스크립트 한 번으로 줄였다(약 20%). 연결 풀(`commons-pool2`)은 의존성과 풀 크기 설정이 늘어 택하지 않았다.
- **회귀 방지**: `RedisProductCacheTest` — 여러 키를 저장해도 새 연결이 생기지 않음(이전 코드에서는 15개로 실패함을 확인), 상품 20개 저장이 스크립트 호출 1번.
