# 커머스 API 설계 — 4주차 · 조회 최적화와 캐시

요구사항 명세(`docs/week4/requirements.md`)의 규칙과 질문을 바탕으로, 측정한 것과 그것으로 정한 것을 적는다.
2 · 3 주차 설계는 `W2` · `W3` 으로 가리킨다.

## 1. 상품 목록의 병목

측정 요청은 `QUERY-001` 이다 — `GET /api/v1/products?brandId={1 · 100 · 1000}&sort=PRICE_ASC&page=0&size=20`, 데이터는 seed B.
측정 스크립트(k6 · `EXPLAIN ANALYZE` 비교 · 응답 스냅숏)와 원시 결과는 저장소에 두지 않는다. 본문의 `results/…` · `snapshots/…` 는 각 숫자가 나온 측정의 이름이다.

### 1.1 기준선

k6 (`results/c-baseline-*`):

| 브랜드 (살아 있는 상품) | 동시 요청 | 초당 처리 | p50 | p99 | 실패 | 커넥션 획득 대기(평균) |
|---|---|---|---|---|---|---|
| `1` (25,201) | 1 | 22 | 44 ms | 73 ms | 0 | 0.7 ms |
| | 10 | 15 | 670 ms | 930 ms | 0 | 1.5 ms |
| | 40 | 65 | 515 ms | 2,138 ms | 0 | 0.1 ms |
| | 80 | 77 | **1,022 ms** | 1,543 ms | 0 | **509 ms** |
| `100` (981) | 1 | 265 | 3.5 ms | 7.2 ms | 0 | 0 |
| | 80 | 1,682 | 44 ms | 126 ms | 0 | 21 ms |
| `1000` (194) | 1 | 434 | 2.1 ms | 4.5 ms | 0 | 0 |
| | 80 | 4,809 | 15 ms | 51 ms | 0 | 6 ms |

- **큰 브랜드에서 동시성을 늘려도 처리량이 늘지 않는다.** 1 → 80 에서 초당 22 → 77 건이고, 같은 동시성에서 작은 브랜드는 4,809 건이다.
- **80 에서 커넥션 풀 앞에 줄이 선다.** 풀 40 개를 이 조회가 쥐어 커넥션을 얻는 데만 평균 509 ms 를 기다렸다. 대기 한도(3 초) 안이라 실패는 없었다.
- **같은 쿼리가 작은 브랜드에서는 수 ms 다.** 비용이 브랜드의 상품 수에 비례한다. 균등한 seed A 로는 보이지 않는다.
- 요청당 SQL 은 1 개다. N+1 은 없다(`QUERY-006`).

**버퍼 풀이 빈 상태**는 브랜드 `1` 의 p50 이 150 ms 로 데운 상태(44 ms)의 3 배였다(`QUERY-010`, `results/c-baseline-cold-*`). 판단은 데운 상태로 한다.
데운 상태의 시간은 디스크 대기가 아니라 **행을 붙이고 묶는 CPU 작업**이다.

### 1.2 무엇이 시간을 쓰는가

브랜드 `1` 의 `EXPLAIN ANALYZE`(174 ms, `results/sql-c-0-current.txt`):

```
Limit 21
└ Sort: price, id DESC (21 개만 남김)                             ← 5. 여기서야 21 개
  └ Group aggregate: count(distinct l.id), max(liked)   25,201 행  ← 4. 전부 묶음
    └ Nested loop left join (ml: 내 좋아요)             100,654 회  ← 3. 좋아요 행마다 찾음
      └ Nested loop left join (l: 좋아요)               100,654 행  ← 2. 좋아요를 붙여 불어남
        └ Sort: p.id …                                  25,201 행
          └ Index lookup idx_product_brand_id            25,201 행  ← 1. 전부 읽음
```

- **집계가 `LIMIT` 보다 먼저다.** 상품마다 좋아요 수를 확정하려면 그 상품의 행을 모두 봐야 하고, `GROUP BY p.id` 의 순서(id)와 `ORDER BY` 의 순서(가격)가 달라
  전부 묶은 뒤 따로 정렬한다. 화면에 필요한 21 개를 고르기 위해 25,201 개 상품의 좋아요 100,654 개를 센다.
- **`PRICE_ASC` 의 순서에는 좋아요 수가 필요 없다.** 좋아요 수는 보여 줄 21 개에만 있으면 된다.
- **`liked` 를 좋아요 행마다 찾는다.** 상품당 한 번이면 될 일을 100,654 번 한다.
- **인덱스에 가격이 없다.** `idx_product_brand_id (brand_id, deleted_at)` 로 찾은 뒤 행마다 기본키로 본 행을 읽는다.
  `EXPLAIN` 의 `possible_keys` 도 이 인덱스 하나뿐이었다.
- 예상 행 수 48,960, 실제 25,201 — 통계 추정이 2 배 어긋난다.

## 2. 개선 후보와 예측

**예측은 측정 전에 적는다.** 결과가 예측을 확인하는지 뒤집는지가 선택의 근거다.

| 후보 | 바꾸는 것 | 예측 (브랜드 `1`) | 예측이 틀렸다고 볼 결과 |
|---|---|---|---|
| ① 인덱스만 | `(brand_id, deleted_at, price, id DESC)` 추가. 쿼리는 그대로 | **거의 줄지 않는다.** 집계가 정렬보다 먼저라 인덱스 순서로 읽다가 멈출 수 없다. 옵티마이저가 새 인덱스를 고르더라도 브랜드의 상품을 모두 읽고 좋아요를 붙여 묶는 일은 그대로다 | 기준선의 절반 아래로 떨어진다 |
| ② 쿼리만 | 파생 테이블이 가격순 21 개의 `id` 를 먼저 고르고, 좋아요 수와 `liked` 는 그 21 개에 대해서만 구한다. 인덱스는 그대로 | **절반쯤 준다.** 좋아요 조인과 집계(2 ~ 4 단계)가 사라진다. 그러나 가격이 인덱스에 없어 브랜드의 상품을 모두 읽고 정렬하는 일(1 단계)은 남는다 | 수 ms 로 떨어지거나, 기준선보다 느리다 |
| ③ 둘 다 | ② + ①의 인덱스. 파생 테이블이 인덱스만으로 `id` 를 고른다(커버링, 지연 조인) | **브랜드 크기와 무관하게 1 ms 안팎.** 인덱스를 가격순으로 21 항목 읽고 멈춘다. 정렬도 집계도 21 개 규모다 | 브랜드 `1` 이 `1000` 보다 수십 배 느리다 |
| ③′ 둘 다, `id` 오름차순 인덱스 | ③ 에서 인덱스를 `(brand_id, deleted_at, price, id)` 로 | **③ 보다 느리다.** `ORDER BY price ASC, id DESC` 의 방향이 인덱스와 어긋나 가격 동점을 정리하려고 브랜드의 인덱스 항목 전체를 정렬한다. 본 행은 읽지 않으므로 ② 보다는 빠르다 | ③ 과 같다 |

③′ 을 따로 재는 이유는 `PRODUCT-012`(동점은 `id` 내림차순)가 인덱스 방향을 정하기 때문이다. 방향을 맞추지 않으면 인덱스가 있어도 정렬이 남는지를 확인한다.

### 2.1 결과

`EXPLAIN ANALYZE` 7 회의 중앙값이다(`results/sql-c-*.txt`). 후보마다 인덱스를 만들고 `ANALYZE TABLE` 한 뒤 재고, 다음 후보 전에 지웠다.
측정 전에 테이블과 인덱스를 한 번씩 훑어 버퍼 풀을 데웠다. 좋아요 수는 모든 후보가 같은 방식으로 붙인다.

| 후보 | 브랜드 `1` | `100` | `1000` | 옵티마이저가 고른 것 | 예측과 비교 |
|---|---|---|---|---|---|
| 기준선 | 186 ms | 6.3 ms | 1.1 ms | `idx_product_brand_id` | — |
| ① 인덱스만 | **207 ms** | 5.6 ms | 1.4 ms | 새 인덱스 `idx_product_brand_price` | 맞았다 — 줄지 않았다. 옵티마이저가 새 인덱스를 골랐지만 집계가 앞에 있어 순서를 쓰지 못하고, 같은 25,201 행을 읽어 100,654 행을 묶었다 |
| ② 쿼리만 | 243 ms (56 ~ 356) | 3.6 ms | 0.4 ms | `idx_product_brand_id` | **브랜드 `1` 에서 틀렸다 — 줄지 않았다.** 조인 · 집계는 사라졌지만 가격을 보려고 25,201 개 상품의 본 행을 기본키로 읽었고, 버퍼 풀(128 MB) 에 다 들지 않는 행을 읽느라 회차마다 흔들렸다. 작은 브랜드는 예측대로 절반 아래로 줄었다 |
| ③ 둘 다 | **0.33 ms** | 0.23 ms | 0.19 ms | 새 인덱스, 커버링 · 정렬 없음 | 맞았다 — 인덱스를 21 항목 읽고 멈췄다. 브랜드 크기와 무관하다 |
| ③′ 둘 다, `id` 오름차순 | 5.2 ms | 0.35 ms | 0.22 ms | 새 인덱스, 커버링 + 정렬 | 맞았다 — 본 행은 읽지 않았지만 방향이 어긋나 25,201 항목을 정렬했다. 작은 브랜드는 정렬할 항목이 적어 ③ 과 거의 같다 |

- **인덱스도 쿼리도 혼자서는 큰 브랜드를 줄이지 못했다.** 병목이 "어떻게 찾느냐" 가 아니라 "몇 개를 읽고 묶느냐" 였기 때문이다. 쿼리가 21 개를 먼저 고르는 모양이 되고, 그 순서를 인덱스가 줄 때 비로소 21 개에서 멈췄다.
- **인덱스의 방향이 동점 규칙을 따라야 한다.** ③ 과 ③′ 의 차이는 `id DESC` 하나다. `PRODUCT-012` 를 바꾸면 인덱스도 바꿔야 한다.
- **결과가 같다.** 기준선과 ② · ③ 의 쿼리가 브랜드 3 개 × 사용자 5 명에서 같은 행을 돌려줬다. 앱에 넣은 뒤에는 응답 스냅숏 180 개로 다시 비교한다.

**고른 것: ③.** 브랜드 크기와 무관하게 1 ms 아래이고, 기존 계약(요청당 SQL 1 개, 페이지 번호, 동점 규칙)을 하나도 바꾸지 않는다.

**대가**: 인덱스가 하나 늘어 상품의 등록 · 가격 수정 · 삭제가 인덱스 하나를 더 고친다. 가격 수정은 인덱스 안에서 항목의 위치를 옮긴다(2.5 에서 쟀다).
**뒤집을 조건**: 상품 쓰기가 측정 가능한 수준으로 느려지면 기존 `idx_product_brand_id` 를 새 인덱스로 대신할 수 있는지 본다 —
새 인덱스의 앞 두 열이 같아 브랜드 삭제의 벌크 UPDATE(W3 2.2)도 쓸 수 있다. 다만 브랜드 필터 + `LATEST` 는 기존 인덱스의 `(brand_id, deleted_at, id)` 순서를 쓰므로, 지우기 전에 그 정렬을 함께 잰다.

**모든 후보가 지켜야 하는 것**: 같은 입력에 같은 결과(`QUERY-003`). 정렬된 id · 가격 · 좋아요 수 · `liked` · 품절 · `hasNext` 를
기준선의 응답 스냅숏(`snapshots/c-baseline.jsonl`)과 비교한다. 정렬 3 종 × 브랜드 `1` · `100` · `1000` · 전체 × 페이지 0 · 1 · 5 × 사용자 5 명.

**고르는 방법**: 후보는 먼저 SQL 수준(`EXPLAIN` · `EXPLAIN ANALYZE`)에서 비교하고, 고른 하나를 애플리케이션에 넣어 k6 와 스냅숏으로 확인한다.
후보마다 코드를 바꿔 부하 측정을 하는 것은 SQL 수준에서 차이가 분명하지 않을 때만 한다.

### 2.2 애플리케이션에 넣은 결과

`ProductViewQueryImpl.findPage` 의 `PRICE_ASC` · `LATEST` 를 ③ 의 구조로 바꾸고, `ProductEntity` 에 `idx_product_brand_price (brand_id, deleted_at, price, id DESC)` 를 더했다.
`LIKES_DESC` 는 기존 집계 쿼리 그대로다(3 절에서 다룬다).

**결과가 같다.** 바꾸기 전에 지금 동작을 고정하는 테스트를 더했다(`ProductV1ApiE2ETest.ListPaging` — 가격 동점이 페이지 경계에 걸칠 때, 목록의 좋아요 수와 `liked`,
가장 싼 상품이 삭제됐을 때, `hasNext` 의 경계). 응답 스냅숏 180 개(정렬 3 종 × 브랜드 `1` · `100` · `1000` · 전체 × 페이지 0 · 1 · 5 × 사용자 5 명)가
기준선과 하나도 다르지 않았다(`snapshots/c-baseline.jsonl` · `c-after.jsonl`). 사용자 5 명 중 3 명은 각 브랜드의 가격순 첫 페이지에 좋아요를 누른 사람이라 `liked = true` 도 비교한다.

**남은 것**: 브랜드 필터 없는 목록은 이 인덱스를 쓰지 못한다(2.4).

### 2.3 Q-1 — SQL · 인덱스 개선만으로 충분한가

**충분하다.** 측정 전에 정한 기준(개선 뒤 p95 50 ms 이하, 동시 요청을 늘려도 커넥션 대기가 생기지 않음)을 넘는다 —
동시 요청 80 에서도 p99 41 ms 이고, 풀 크기 이내에서는 커넥션 대기가 없다.
그래서 이 경로에 캐시를 붙여 줄일 수 있는 것은 1 ms 안팎이다. 캐시는 원문(`CACHE-001`)이라 붙이되, **어느 경로에 붙일지(Q-2)는 아직 무거운 `LIKES_DESC` 와 함께 정한다.**

**뒤집을 조건**: 요청 분포가 측정과 달라 같은 첫 페이지에 요청이 몰리거나, 실제 운영 DB 가 이 노트북보다 느려 p95 가 기준을 넘으면 이 경로의 캐시 이득을 다시 잰다.

**이 절이 다루지 않는 것**: `LIKES_DESC` 는 순서가 좋아요 수로 정해져 먼저 자를 수 없다(`QUERY-005`). 같은 방법이 통하지 않으므로 따로 다룬다.
`LATEST` 는 브랜드 필터와 함께 같은 구조를 쓰므로 ③ 의 효과를 함께 확인한다.
### 2.4 브랜드 없는 목록

`brandId` 는 선택 값이라 브랜드 없는 목록(메인 화면의 전체 상품)도 계약에 있는 조회다. 측정 요청(`QUERY-001`)은 아니지만 가장 자주 불릴 수 있다.
복합 인덱스는 왼쪽 열부터 쓰므로 `brand_id` 로 시작하는 인덱스는 이 조회에 쓰이지 않는다.

| 정렬 | 개선 전 (SQL, 3 회 중앙값) | 원인 | 개선 후 (5 회 중앙값) |
|---|---|---|---|
| 최신순 | 166 ms | 옵티마이저가 기본키를 거꾸로 읽다 21 개에서 멈추는 대신 `idx_product_brand_price` 를 건너뛰며 훑었다(`Index skip scan … rows=1.01e+6`, 예상 57 만) | `idx_product_alive_latest (deleted_at, id)` — 0.64 ms |
| 가격순 | 186 ms | 같은 skip scan 으로 살아 있는 상품 101 만 개를 읽고 정렬 | `idx_product_alive_price (deleted_at, price, id DESC)` — 0.34 ms |
| 인기순 | 4,119 ms | 115 만 개마다 좋아요를 센다 | 인덱스로 풀리지 않는다. 카운터의 몫(3.2) |

(`results/sql-c-all-*`) 새 인덱스를 넣은 뒤에도 브랜드 있는 조회는 브랜드 인덱스를 골랐고, 응답 스냅숏 180 개가 기준선과 같았다.

| 최신순에 고를 수 있는 것 | 속도 | 대가 |
|---|---|---|
| 힌트 `FORCE INDEX (PRIMARY)` | 0.21 ms | 쓰기 비용이 없다. 대신 분포에 기댄다 — 삭제 상품이 늘거나 최근 상품이 몰아서 삭제되면 기본키를 거꾸로 읽으며 그 구간을 모두 지나야 하는데, 힌트가 계속 강제한다 |
| **인덱스 `(deleted_at, id)`** (고른 것) | 0.64 ms | 상품 쓰기마다 인덱스 하나를 더 고친다. 삭제 비율 · 위치와 무관하게 살아 있는 구간만 읽는다 |

둘 다 기준(p95 50 ms) 안이라 분포에 무너지지 않는 쪽을 골랐다. 통계가 틀어져 옵티마이저가 다른 인덱스를 고르는 위험은 남는다 — `EXPLAIN` 으로 보고 `ANALYZE TABLE` 로 바로잡는다.
**대가**: `product` 의 인덱스가 다섯 개(기본키 · 브랜드 최신순 · 브랜드 가격순 · 전체 최신순 · 전체 가격순)가 됐다. 쓰기 비용은 2.5 에서 쟀다.

### 2.5 인덱스의 쓰기 비용

4 주차에 더한 인덱스 셋(브랜드 가격순 · 전체 최신순 · 전체 가격순) 을 빼고 넣으며 같은 쓰기를 쟀다(`results/write-cost.txt`).
연산마다 2,000 번을 한 트랜잭션에서 실행한 뒤 되돌렸다. 버퍼 풀(128 MB) 보다 데이터가 커 인덱스 페이지를 읽는 일이 섞여 편차가 크다 — 배율과 자릿수로만 읽는다.

| 쓰기 | 갱신되는 4 주차 인덱스 | 4 주차 인덱스 없음 | 있음 | 한 번당 더해진 것 |
|---|---|---|---|---|
| 상품 등록 | 3 개 | 0.009 ~ 0.021 ms | 0.021 ~ 0.023 ms | 약 0.01 ms |
| 가격 수정 | 가격이 든 2 개(자리 이동) | 0.012 ~ 0.022 ms | 0.05 ~ 0.17 ms | 0.04 ~ 0.15 ms |
| 상품 삭제(`deleted_at`) | **3 개 모두** — 모든 인덱스가 `deleted_at` 을 든다 | 0.019 ~ 0.033 ms | 0.12 ~ 0.14 ms | **약 0.1 ms (4 ~ 7 배)** |
| 재고 변경(주문 확정) | 없다 | 0.013 ~ 0.015 ms | 0.013 ~ 0.020 ms | 없다 |

**유지한다.** 한 번당 더해진 비용이 1 ms 아래이고, 영향을 받는 쓰기는 관리자 기능이라 드물다. **가장 잦은 쓰기인 주문 확정의 재고 차감에는 비용이 없다** — `quantity` 를 든 인덱스가 없다.
**가장 큰 대가는 브랜드 일괄 삭제다.** 한 문장으로 그 브랜드의 상품 행을 모두 고치고(W3 2.2), 행마다 인덱스 셋을 함께 고친다.
가장 큰 브랜드 `1`(25,201 개) 의 일괄 삭제 문장을 트랜잭션 안에서 실행하고, 문장이 끝난 뒤 그 브랜드의 상품 하나에 주문 확정과 같은 `SELECT … FOR UPDATE` 를 보냈다(`results/bulk-delete-c.txt`):

| | 4 주차 인덱스 없음 | 있음 |
|---|---|---|
| 일괄 삭제 문장 | 1.05 ~ 1.22 초 | 1.08 ~ 1.53 초 |
| 되돌리기(rollback) | 0.54 ~ 0.59 초 | 1.37 초 |
| 그동안 주문의 잠금(앱의 대기 한도 3 초) | 얻음 | 얻음(되돌리기가 끝날 때까지 1.2 ~ 1.6 초) |

- 잠금은 커밋까지 이어진다. 문장 앞쪽에서 잠긴 상품의 주문은 **문장이 끝날 때까지** 기다린다 — 가장 큰 브랜드에서 1 ~ 1.5 초로, 앱의 대기 한도(3 초) 안이다.
  위의 한 번당 배율(4 ~ 7 배)보다 문장 전체의 차이가 작은 것은 행을 찾고 고치는 일이 인덱스와 무관하게 들기 때문이다.
- 삭제가 실패해 되돌리면 인덱스 셋을 되돌리느라 2 ~ 3 배 걸린다.
- 측정의 한계: 주문 대기는 되돌리는 동안 잰 것이다. 커밋하는 경우의 대기는 "그 상품이 잠긴 뒤 문장이 끝날 때까지" 로, 위 문장 시간에서 추론했다.

**인덱스는 유지한다.** 가장 큰 브랜드의 일괄 삭제도 주문의 대기 한도 안에 끝난다.
**뒤집을 조건**: 브랜드가 커져 일괄 삭제 문장이 대기 한도(3 초)에 가까워지면 — 이 측정으로는 상품 5 만 ~ 7 만 개 — 삭제를 묶음으로 나눠 묶음마다 커밋한다.
다만 이것은 W3 의 "브랜드와 상품을 함께 삭제" 를 한 트랜잭션에서 여러 트랜잭션으로 바꾸는 계약 변경이라(중간에 실패하면 일부만 삭제된 상태가 보인다) 그때 먼저 정한다.
상품 쓰기가 측정 가능하게 느려지면 `idx_product_brand_id` 를 `idx_product_brand_price` 로 대신할 수 있는지 먼저 본다(브랜드 최신순의 계획을 함께 잰다).
**필터 · 정렬이 늘 때**: 인덱스는 거르는 조건 × 정렬의 조합마다 하나씩 필요해 조합이 늘면 쓰기 비용과 관리가 함께 는다.
조합이 늘면 인덱스를 더하기 전에 ① 후보가 적은 조합(작은 브랜드 — 브랜드 `1000` 은 인덱스 없이 1.1 ms)은 정렬을 받아들이고 큰 조합만 인덱스로 맡을지, ② 목록 조회를 검색 엔진으로 옮길지를 먼저 본다.

## 3. 인기순과 좋아요 수

### 3.1 인기순(`LIKES_DESC`)은 먼저 자를 수 없다

순서가 좋아요 수로 정해지므로 브랜드의 모든 상품의 좋아요를 세야 21 개를 고를 수 있다(`QUERY-005` — 전체 후보에서 정렬한 뒤 페이지).
기존 쿼리에서 바꿀 수 있는 것은 **무엇을 붙여서 묶느냐** 뿐이다. SQL 수준 비교(`results/sql-c-L*.txt`, 5 회 중앙값):

| 후보 | 브랜드 `1` | `100` | `1000` | |
|---|---|---|---|---|
| L0 기존(상품 · 브랜드 · 좋아요를 붙여 묶음) | 180 ms | 5.8 ms | 1.4 ms | |
| L1 좋아요를 먼저 상품별로 묶어 붙임 | 1,123 ms | 1,084 ms | 1,025 ms | 브랜드와 무관하게 좋아요 491 만 행을 묶는다. 탈락 |
| L2 상품마다 좋아요를 세고 상위 21 개만 붙임 | 65 ms | 2.6 ms | 0.77 ms | 채택. 남은 비용은 브랜드의 상품 2 만 5 천 개마다 세기 |

L2 를 넣은 뒤 응답 스냅숏 180 개가 기준선과 같았다. k6, 브랜드 `1` 기준선 → L2(`results/c-baseline-*` · `c-v1-likes-*`):

| 동시 요청 | 초당 처리 | p50 | p99 | 실패 |
|---|---|---|---|---|
| 1 | 7.9 → 15 | 124 → 63 ms | 168 → 114 ms | 0 → 0 |
| 40 | 21 → 53 | 1,874 → 708 ms | 2,290 → 1,197 ms | 0 → 0 |
| 80 | 22 → 53 | 3,619 → 1,485 ms | 4,353 → 1,992 ms | 7 → 0 |

**큰 브랜드의 인기순은 동시 요청에서 느리다** — 초당 53 건에서 늘지 않고 p50 이 1.5 초다. 세는 일이 CPU 작업이라 동시 요청이 그것을 나눠 쓰며 함께 느려진다.
커버링 인덱스는 이미 쓰고 있다 — 남은 비용은 본 행 읽기가 아니라 세는 횟수다. 브랜드 없는 전체 인기순은 115 만 개를 세서 훨씬 무겁다(2.4, 3.2).

### 3.2 Q-6 — 좋아요 수를 카운터로 비정규화한다. 배치로 갱신하는 Sorted Set 은 두지 않는다

**좋아요를 요청마다 세는 비용이 두 곳에서 측정됐고, 원인이 하나다.**

| 측정 | 비용 |
|---|---|
| 인기순(3.1 · 2.4) | 브랜드 `1` 은 동시 요청 80 에서 초당 53 건 · p50 1.5 초. 전체 인기순은 동시 요청 80 에서 470 건 중 390 건 실패 |
| 인기 상품의 상세(5) | 좋아요 11 만 개를 세느라 상품 하나가 MySQL CPU 를 채운다(초당 898 건) |

카운터는 둘 모두에서 세기를 행 하나 읽기로 바꾼다. 원문의 선택 심화(카운터 비정규화)다.

**카운터 뒤** (응답 스냅숏 180 개가 기준선과 같다 — `snapshots/c-after.jsonl`):

| 요청 | 카운터 전 (`results/c-v1-*`) | 카운터 후 (`results/c-now-*`) |
|---|---|---|
| 인기 상품 상세 · 동시 요청 80 | 898 /s · 1,000 건당 MySQL CPU 1,468 | **8,619 /s · 27** — 평범한 상품(8,388 /s · 22) 과 같아졌다 |
| 브랜드 `1` 인기순 · 동시 요청 1 | p50 63 ms | p50 21 ms |
| 브랜드 `1` 인기순 · 동시 요청 80 | 53 /s · p50 1,485 ms | 58 /s · p50 1,371 ms · 실패 0 |
| 전체 인기순 · 동시 요청 1 · 80 | p50 1,268 ms · 470 건 중 390 건 실패 | p50 611 ms · 383 건 실패(`results/c-counter-join-likes-all.txt`) |

상세의 핫키는 풀렸고, 인기순은 요청 하나가 2 ~ 3 배 빨라졌지만 동시 요청에서는 그대로다.

**구조**: 카운터는 상품 행이 아닌 별도 테이블 `product_like_count (product_id, like_count)` 에 둔다.
상품 행에 두면 좋아요가 주문 확정의 상품 잠금과 다툰다(W2 3.3 — 확정은 상품 행을 잠근다).
별도 테이블이면 둘은 다른 행을 잠근다 — 좋아요의 상품 확인(`requireAvailable`)은 잠그지 않는 읽기이고, 좋아요가 잠그는 것은 관계 행과 카운터 행뿐이다.
관계 행이 **실제로 생기고 지워질 때만** 같은 트랜잭션에서 증감한다 — `INSERT IGNORE` 가 넣지 않은 중복 좋아요, 지운 행이 없는 취소는 카운터를 바꾸지 않는다(`LIKE-002` · `003` 멱등).
좋아요가 0 인 상품은 행이 없고 0 으로 읽는다.

**대가**: 같은 상품의 좋아요가 카운터 행 하나에서 줄을 선다 — 읽기의 세기 비용을 쓰기의 경합으로 바꾼다. 인기 상품일수록 좋아요도 몰린다.
관계 행과 카운터, 두 곳이 같은 사실을 들게 되므로 동시 좋아요 · 취소 뒤에 둘이 같은지 테스트로 확인한다(원문의 "중복 · 동시 변경과 정합성").
**뒤집을 조건**: 인기 상품의 좋아요 응답에 카운터 행 대기가 보이면, 증감을 트랜잭션 밖의 비동기 집계로 옮긴다(카운터가 잠깐 늦는 것을 받아들인다).

**인기순이 여전히 무너지는 이유**: 카운터로 바뀐 것은 상품마다 하는 일(세기 → 기본키 한 번)뿐이다.
거르는 조건(브랜드 · 삭제 여부)은 `product` 에, 정렬 기준(좋아요 수)은 카운터에 있어 한 인덱스로 정렬된 순서를 읽을 수 없고,
**후보 전체를 읽고 정렬한다** — 브랜드 `1` 은 25,201 개를 읽고 카운터를 25,201 번 찾은 뒤 21 개를 자른다(SQL 27 ms, `results/sql-c-Lc-likes-counter.txt`). 전체 인기순은 101 만 개다.

21 개 근처에서 멈추려면 거르는 조건과 정렬 기준이 한 인덱스에 있어야 한다. 고를 수 있는 것:

| 선택지 | 맡는 요청 | 대가 |
|---|---|---|
| 카운터에 `(like_count, product_id)` 인덱스 · 카운터에서 출발해 상품을 기본키로 찾으며 삭제를 거름 | **전체** 인기순(거르는 조건이 삭제 여부 하나) | 좋아요마다 이 인덱스도 갱신된다. 좋아요 0 인 상품은 카운터 행이 없어, 좋아요 있는 상품으로 페이지가 차지 않으면 지금 쿼리로 대신한다. 삭제 상품이 상위에 몰리면 그만큼 더 읽는다 |
| 카운터에 `brand_id` · 삭제 여부를 두고 `(brand_id, like_count, product_id)` 인덱스 | 브랜드 인기순 | 같은 사실(브랜드 · 삭제 여부)을 두 테이블이 든다 — 상품 등록 · 삭제 · 브랜드 일괄 삭제가 카운터도 고쳐야 한다 |
| `product` 에 `like_count` | 둘 다 | 좋아요가 주문 확정의 상품 잠금과 다툰다. 가장 잦은 쓰기마다 `product` 인덱스가 갱신된다 |
| Redis Sorted Set | 둘 다 | 아래 — 배치 갱신은 `CACHE-006` 을 어긴다 |

**전체 인기순은 카운터 인덱스로 푼다** — 첫 번째 선택지. 카운터에 `(like_count, product_id)` 인덱스를 두고, 브랜드 조건이 없는 인기순은
카운터에서 좋아요가 1 이상인 상품을 인덱스 순서로 읽으며 상품을 기본키로 찾아 삭제를 거른다. 페이지가 차면(`limit` 개) 그대로 쓰고,
차지 않으면(좋아요 있는 상품이 이 페이지에서 끝남) 지금의 쿼리로 대신한다 — 좋아요가 1 이상인 상품은 언제나 0 인 상품보다 앞이므로 페이지가 찼다면 결과가 같다.
데이터가 적은 서비스 초기에는 첫 페이지도 대신하는 쪽으로 간다.

옵티마이저는 살아 있는 상품을 57 만으로 추정(실제 101 만)하고, `LIMIT 21` 이면 카운터 인덱스를 따라 일찍 멈출 수 있다는 것을 비용에 안정되게 넣지 못한다.
**통계가 샘플링이라 다시 계산할 때마다 흔들린다** — InnoDB 는 인덱스 통계를 페이지 20 개(`innodb_stats_persistent_sample_pages`)로 추정한다.
쓰기 없이 같은 데이터에 `ANALYZE TABLE` 을 세 번 연달아 돌리자 카운터 인덱스의 서로 다른 값 추정(`n_diff_pfx01`)이 624 · 312 · 1,926 으로 6 배 흔들렸다. 좋아요 수가 쏠려 있어(대부분 0 ~ 몇 개, 소수가 수만 개) 어느 페이지가 뽑히느냐에 따라 달라진다.
**재계산은 저절로도 일어난다** — `innodb_stats_auto_recalc` 가 켜져 있어 테이블 행의 약 10% 가 바뀌면 백그라운드에서 다시 샘플링한다.
카운터는 좋아요마다 갱신되는 가장 잦은 쓰기라, 89 만 행이면 약 9 만 번 변경마다(좋아요가 초당 20 건이면 약 75 분마다) 통계가 다시 뽑히고 배포 없이도 계획이 바뀔 수 있다.
힌트는 인덱스 이름이 아니라 조인 순서만 고정한다. 이 순서가 나빠지는 것은 좋아요 상위 상품이 대부분 삭제됐을 때이고, 그때도 삭제된 상위 상품 수만큼만 더 읽는다. `product` 에서 출발하는 길은 늘 전체를 읽는다.
| 계획을 안정시키는 방법 | 대가 |
|---|---|
| 샘플 페이지를 늘린다(`STATS_SAMPLE_PAGES`) | `ANALYZE` 가 느려지고, 흔들림이 줄 뿐 없어지지 않는다 |
| 자동 재계산을 끈다(`STATS_AUTO_RECALC = 0`) | 데이터가 바뀌어도 통계가 따라가지 않는다 |
| **조인 순서 힌트** (고른 것) | 통계와 무관하게 계획이 고정된다. 다른 계획이 더 나아져도 따라가지 않는다 |

**뒤집을 조건**: MySQL 버전이 바뀌어 옵티마이저가 통계 재계산에도 카운터에서 출발하면 힌트를 뺀다(`ANALYZE TABLE` 을 여러 번 돌린 뒤 `EXPLAIN` 으로 확인). 삭제된 상품이 좋아요 상위에 쌓이면 삭제 때 카운터 행을 지운다.
**대가**: 좋아요마다 이 인덱스도 갱신된다 — 카운터 행 하나를 고치던 쓰기에 인덱스 항목 하나의 이동이 더해진다.
카운터 증가 한 문장만 보면 0.01 ms 에서 0.02 ~ 0.05 ms 로 2 ~ 5 배지만, **좋아요 전체(관계 행 `INSERT IGNORE` + 카운터 증가)** 로는 0.18 ~ 0.35 ms 에서 0.33 ~ 0.68 ms 로 늘었다(`results/write-cost.txt`, 범위가 겹친다).
관계 행이 인덱스 셋을 고치는 비용이 더 크다. 받아들인다. **뒤집을 조건**: 좋아요 응답의 지연이 이 인덱스 때문에 보이면, 랭크 인덱스를 빼고 전체 인기순을 다른 방법(쓰기 뒤에 갱신하는 사본)으로 옮긴다.

**브랜드 인기순의 속도는 이번 주에 풀지 않는다.** 원문에서 인기순은 정렬 의미(전체 후보에서 정렬한 뒤 페이지, 28 행)가 필수이고 그 의미는 지켜진다(응답 스냅숏 · 기존 테스트).
속도의 측정 · 개선 대상은 브랜드 필터 + 가격순이고(15 행), 브랜드 인기순의 속도는 선택 심화 밖이다.
카운터로 가장 큰 브랜드의 인기순은 요청 하나가 3 배 빨라졌지만(63 → 21 ms), 동시 요청 80 에서는 초당 58 건 · p99 2.2 초로 느리다. 실패는 없다.
**뒤집을 조건**: 브랜드 인기순이 실제로 쓰이는 화면이 되거나, 큰 브랜드의 인기순이 커넥션 풀을 고갈시키는 것이 보일 때 — 위 표의 브랜드 카운터 인덱스나 실시간 Sorted Set 중에서 고른다.

**배치로 갱신하는 Sorted Set 은 두지 않는다 — `CACHE-006` 을 지키지 못한다.**
원문은 "장애 · 동시 채움이 없는 정상 변경 완료 뒤 시작한 순차 조회는 변경된 결과를 반환" 하라고 한다. 좋아요 뒤 인기순을 다시 보면 바뀐 순서가 나와야 하는데,
배치로 주기마다 다시 만들면 그 주기 동안 옛 순서가 보인다. 순서가 늦어도 된다고 정하는 것은 원문 필수 계약을 정함으로 덮는 것이라 고르지 않는다.

| Sorted Set 의 갱신 | `CACHE-006` | 대가 |
|---|---|---|
| 배치(주기마다 원본에서 다시 만듦) | 어긴다 | — |
| 좋아요 커밋 뒤 `ZINCRBY` | 정상 경로에서 지킨다 | 좋아요 쓰기마다 Redis 쓰기가 더해지고, 실패 · 어긋남의 정책(재시도, 원본에서 다시 맞추기)과 장애 중 신선도(Q-5 와 같은 형식)를 따로 정해야 한다. 사본과 원본을 맞추는 일이 하나 더 생긴다 |

전체 인기순은 카운터 인덱스로 이미 동시 요청을 견디므로 Sorted Set 이 맡을 것은 브랜드 인기순뿐이고, 그 속도는 이번 주 범위가 아니다.
**뒤집을 조건**: 인기순 순서가 늦어도 되는 계약(예: "인기순은 몇 분마다 갱신")이 생기면 배치 사본으로 간다 — 원본은 카운터, 임시 키에 채운 뒤 `RENAME`, Redis 장애 때는 원본으로 우회, 삭제 상품은 읽을 때 거른다.

### 3.3 좋아요 수를 붙이는 비용과 인덱스

카운터(3.2) 전에는 목록의 좋아요 수를 셀 수밖에 없었다. 그래서 페이지에 인기 상품이 끼면 그만큼 셌다.
캐시 hit 뒤에 20 개의 좋아요 수와 `liked` 를 한 쿼리로 붙인다고 할 때(`SELECT product_id, COUNT(*), MAX(user_id = ?) … WHERE product_id IN (…) GROUP BY product_id`):

| 페이지 | 읽은 좋아요 | 인덱스 `(product_id)` | 인덱스 `(product_id, user_id)` |
|---|---|---|---|
| 평범한 상품 20 개 | 64 | 0.1 ms | 0.05 ms |
| 인기 상품 1 개 포함 (평범한 19 개 + 1 위 상품, 만든 경우) | 114,842 | 45 ms | 20 ms |
| 인기 상위 20 개 (실제 페이지가 아니라 전체 상위 20 개를 모아 만든 최악의 경우) | 503,554 | **7,429 ms** | **87 ms** |

`(product_id)` 에는 `user_id` 가 없어 `liked` 를 위해 50 만 행의 본 행을 읽었고, 옵티마이저는 `GROUP BY` 순서를 맞추려 인덱스 전체(491 만)를 훑었다.
`(product_id, user_id)` 에서는 20 개 상품의 범위만 커버링으로 읽는다. 남은 87 ms 는 50 만 개를 세는 비용이고 인덱스로는 줄지 않는다(3.2 의 카운터 몫).

**고른 것: `(product_id)` 를 `(product_id, user_id)` 로 교체한다.** 같은 열로 시작하므로 기존 쓰임을 모두 대신하고, 인덱스 수가 늘지 않아 좋아요 쓰기 비용이 그대로다.
**대가**: 인덱스가 넓어져(160 MB) 많이 세는 경로가 느려진다. 가격순(21 개만 셈)은 차이가 없었다. 인기순은 3.2 의 카운터로 풀 경로라 이 손실을 받아들인다.
좋아요 데이터는 상품 id 로만 정해져 브랜드 분포와 무관하므로, 이 표의 수치는 브랜드 분포를 바꿔도 같다.
**뒤집을 조건(닿았다)**: 카운터(3.2) 뒤 좋아요 수를 세는 쿼리가 없어져, 이 인덱스를 첫 열 `product_id` 로 읽는 쿼리가 남지 않았다 — `liked` 는 `(user_id, product_id)` 유니크 인덱스로 찾는다.
지우면 좋아요 쓰기마다 고치는 인덱스가 셋에서 둘로 준다. 카운터를 다시 세어 맞추는 일(seed 의 마지막 단계)만 이 인덱스를 쓴다.

## 4. 목록 캐시

### 4.1 무엇을 캐시하나

| 값 | 캐시 | 이유 |
|---|---|---|
| 상품 id · 이름 · 가격 · 품절 · 브랜드 id · 이름, 페이지 순서, `hasNext` | 담는다 | 관리자의 등록 · 수정 · 삭제와 품절 전환에만 바뀐다. 드물게 바뀌어 지우고 다시 채우는 비용이 작다 |
| 좋아요 수 | **담지 않는다** | 가장 잦은 쓰기다. 담으면 좋아요마다 무효화해야 하고, 요청이 몰리는 인기 상품일수록 캐시가 비어 있다. TTL 로 옛 수를 허용하는 것은 "정상 변경 뒤 순차 조회는 최신" (`CACHE-006`) 을 어긴다 |
| `liked` | **담지 않는다** | 사용자마다 다르다(`CACHE-004`) |
| 재고 수량 | 담지 않는다 | 고객 응답에 없다(W2 Q-2). 재고 판단은 주문 확정이 DB 를 잠가 한다(`CACHE-009`) |

좋아요 수와 `liked` 는 hit · miss 모두 마지막에 한 쿼리로 붙인다 — 20 개 상품에 대해 좋아요 수(`(product_id, user_id)` 커버링, 3.3) 와
`liked`(`(user_id, product_id)` 유니크)를 구하고, **살아 있는 상품만** 돌려준다. 캐시에 남은 상품이 그사이 삭제됐으면 여기서 빠진다(`CACHE-008`).

### 4.2 어느 요청을 캐시하나

**가격순 · 최신순의 첫 페이지(크기 20) 만, 브랜드별과 전체 목록.** 인기순 · 다음 페이지 · 다른 크기는 원본으로 간다.

| 고를 수 있는 것 | 키 수 | 쓰기 하나가 무효화할 키 | |
|---|---|---|---|
| 모든 페이지 | 브랜드 × 정렬 × 페이지 × 크기 | 그 브랜드와 전체 목록의 모든 페이지 — 몇 개인지 모른다 | 가격 하나가 바뀌면 순서가 밀려 페이지 경계가 모두 바뀐다 |
| 순서(id 목록) · 내용(상품별) 분리 | 순서 키 + 상품 키 | 이름 · 품절은 상품 키 하나, 가격은 그 브랜드의 가격순 순서까지 | hit 에 Redis 왕복이 둘 |
| **첫 페이지만** | 브랜드당 2 + 전체 2 | **최대 4 개** | 깊은 페이지는 재사용이 적어 담아도 hit 가 드물다 |

**전제(정함)**: 요청이 첫 페이지에 몰린다. 실제 분포 자료가 없다.
**뒤집을 조건**: 다음 페이지의 요청 비중이 크게 측정되면 담는 페이지를 늘린다. 그때 무효화 범위가 페이지 수만큼 커지므로 순서 · 내용 분리를 함께 본다.

인기순을 담지 않는 이유: 순서 자체가 좋아요 수라 좋아요마다 무효화해야 한다. 큰 브랜드의 인기순 비용은 캐시가 아니라 카운터 비정규화가 푼다(3.2).

### 4.3 키와 무효화 방식

| 키 | 값 |
|---|---|
| `product:list:v1:brand={id\|all}:sort={정렬}` | 첫 페이지의 공용 내용(JSON), TTL 60 초 |

**읽는 순서**: 키를 찾는다 → 없으면 DB 에서 읽어 그 키에 저장한다. hit 의 Redis 왕복은 1 번이다.
**무효화**: 쓰기가 커밋되면 그 브랜드와 전체 목록의 키를 정렬마다 **지운다**(`DEL` 한 번).
첫 페이지만 담으므로(4.2) 쓰기 하나가 건드릴 키를 정확히 안다 — 그 브랜드와 `all` 의 정렬 수만큼이다.

| 무효화 방식 | 맞는 경우 | 이 목록에서 |
|---|---|---|
| **삭제** | 쓰기가 건드릴 키를 정확히 알고, 늦은 채움을 TTL 동안 받아들일 수 있다 | 고른 것 |
| 갱신(write-through, `@CachePut`) | 쓰기만으로 새 값을 계산할 수 있고 miss 가 비싸다(좋아요 카운터의 `+1`) | 상품 하나의 수정은 첫 페이지 20 개를 돌려주지 않는다. 새 값을 만들려면 목록 쿼리를 다시 구현해야 한다. 동시 수정이면 put 순서가 커밋 순서와 뒤바뀔 수 있다 |
| revision(쓰기가 범위의 revision 을 올리고, 읽기는 현재 revision 의 키만 읽는다) | 쓰기가 건드릴 키를 모르거나 많고, 장애 중에도 늦은 채움을 구조로 막아야 한다 | 늦은 채움은 막지만 hit 마다 revision 확인이 하나 더(DB 에 두면 DB 조회, 원문의 예시), 옛 키가 TTL 까지 메모리를 차지. Redis 에만 두면 revision 키를 잃었을 때 옛 키를 새것으로 읽는다 |

**revision 을 고르지 않는 이유는 둘이다.** ① **필요 없다** — 첫 페이지만 담아 지울 키를 정확히 알고(`DEL` 한 번), revision 이 구조로 막는 늦은 채움은 Q-5 가 TTL 동안 받아들였다.
② **비용이 있다(측정)** — 평소에는 거의 없지만, 품절이 몰리는 순간 주문 확정이 revision 행 하나에서 줄을 선다. 표시 신선도를 위해 주문 처리량을 거는 구조다.

기능으로 넣지 않고 SQL 수준에서 쟀다. seed B 에 주문 확정 모양의 트랜잭션(상품 행 `FOR UPDATE` → 갱신 → 커밋, 상품은 무작위)을 동시에 보내고,
같은 트랜잭션에서 전체 범위(`all`) revision 행 하나를 올리는 비율만 바꿨다(mysqlslap, 트랜잭션 4,000 개씩 2 회, `READ-COMMITTED`, 커밋마다 로그 flush). 초당 트랜잭션, 괄호는 락을 기다린 트랜잭션 비율 · 평균 대기:

| 동시 | 올리지 않음 | 1% 가 올림 | 10% 가 올림 | 매번 올림 |
|---|---|---|---|---|
| 1 | 414 ~ 446 | 387 ~ 433 | 397 ~ 440 | 397 ~ 434 |
| 10 | 1,838 ~ 2,176 | 1,559 ~ 1,636 (0%) | 1,850 ~ 1,862 (4% · 2 ms) | 680 ~ 737 (100% · 11 ms) |
| 40 | 4,153 ~ 4,281 | 3,449 ~ 4,087 (0.3%) | 2,212 ~ 2,831 (9% · 52 ~ 72 ms) | 613 ~ 723 (100% · 52 ~ 61 ms) |
| 80 | 4,496 ~ 5,008 | 4,820 ~ 5,249 (0.4% · 4 ~ 6 ms) | 2,594 ~ 2,670 (10% · 144 ms) | 706 ~ 719 (100% · 106 ms) |

- 매번 올리면 동시 요청과 무관하게 초당 약 700 건에서 멈춘다 — 모든 쓰기가 행 하나에서 커밋만큼씩 줄을 선다. 동시 80 에서 1/7 이다.
- 이 목록에서 revision 을 올릴 쓰기는 관리자 수정과 마지막 재고를 판 확정뿐이라 평소는 1% 쪽이고, 차이는 측정의 흔들림 안이다.
  한정 판매처럼 품절이 몰리면 10% 쪽으로 가서, 동시 80 의 처리량이 절반이 되고 기다린 트랜잭션은 평균 144 ms 를 기다린다.
- 읽기 쪽: revision 조회(기본키 2 행)의 DB 실행 시간은 0.033 ms 다. 4.8 의 요청당 DB 시간(hit · miss 모두)에 더하면 손익분기 히트율이 브랜드 `1` 은 0% 그대로, `100` 은 79 → 88%, `1000` 은 40 → 66% 가 된다.
  앱에서는 이 조회가 DB 왕복 하나라 응답 시간에는 실행 시간보다 크게 더해진다.

**삭제의 대가 — 늦은 채움**: 변경 전 DB 를 읽은 요청이 무효화 뒤에 저장하면 옛 값이 살아 있는 키에 들어가 **그 저장 시점부터 TTL(60 초)** 동안 보인다(Q-5).
늦은 저장이 커밋 뒤 언제 일어날지는 정할 수 없으므로(느린 쿼리, GC 멈춤) 커밋 기준의 전역 상한은 없다.
읽기 · 커밋 · 무효화 · 늦은 저장이 이 순서로 겹쳐야 일어나고, 관리자 쓰기는 드물다. `CACHE-006` 은 동시 채움이 없는 순차 조회만 요구하므로 이 창은 그 밖이다.
**뒤집을 조건**: 첫 페이지 밖까지 담아 쓰기가 건드릴 키를 모르게 되거나(4.2), 늦은 채움으로 인한 옛 값을 받아들일 수 없게 되면 revision 으로 간다.
그때 revision 은 원문의 예시처럼 **DB 에 두고 읽을 때 DB 에서 확인한다** — Redis 에만 두면 그 키를 잃었을 때 옛 값을 새것으로 읽는다.
범위를 브랜드별 행으로 나눠도 전체 목록은 모든 쓰기가 바꾸므로 `all` 행은 남는다 — 그때는 전체 목록을 revision 밖(삭제 + TTL)에 두고 브랜드 목록만 revision 으로 지키는 쪽을 함께 본다.
지연 이중 삭제(커밋 뒤 지우고 잠시 뒤 한 번 더)는 창을 줄일 뿐 닫지 못하므로 그 사이의 선택지다.

**`@Cacheable` · `@CacheEvict` 를 쓰지 않는 이유**: 무효화가 시작되는 곳이 도메인이다 — 주문 확정 안에서 품절이 뒤집혔는지, 어느 브랜드인지는 `ProductService` 만 안다(4.6).
어노테이션은 붙은 메서드의 인자로 키를 정하므로 응용 계층의 메서드에서는 지울 브랜드를 표현할 수 없고, 도메인에 붙이면 스프링 캐시가 도메인으로 들어온다.
커밋 뒤 실행(`transactionAware`), Redis 오류 우회(`CacheErrorHandler`), 서킷 브레이커와 무효화의 연결, hit 뒤 좋아요 붙이기를 위한 빈 분리도 각각 따로 맞춰야 한다.
어노테이션의 쓰기는 기본이 **커밋 전**이다 — `@CacheEvict` 가 커밋 전에 지우면 그 사이 옛 DB 를 읽은 요청이 다시 채우고(늦은 채움), `@CachePut` 이 커밋 전에 쓰면 롤백된 값이 캐시에 남는다(`CACHE-007`).
커밋 뒤로 미루려면 `RedisCacheManager` 의 `transactionAware()` 가 필요하고, 그래도 `@CachePut` 은 동시 수정의 쓰기 순서가 커밋 순서와 뒤바뀔 수 있다. 지금은 커밋 뒤 리스너가 같은 일을 한다(4.6).
**뒤집을 조건**: 상품 상세처럼 키가 메서드 인자로 정해지고 바꾸는 쪽이 그 키를 직접 아는 캐시를 둘 때는 어노테이션으로 둔다.

**연결**: 읽기 · 쓰기 모두 master 연결이다. 무효화 직후의 조회가 replica 에서 아직 지워지지 않은 키를 읽으면 옛 값이 보인다(`CACHE-013`).
**Redis 오류**: 읽기 · 쓰기 오류는 경고만 남기고 원본 결과를 돌려준다(`CACHE-010`). 읽기가 실패해도 저장을 시도하므로 장애 동안 요청 하나가 Redis 를 최대 두 번(약 400 ms) 기다린다(4.7).

### 4.4 어디에 두나

cache-aside 와 좋아요 붙이기는 `ProductFacade.findPage`(응용 계층)에, Redis 는 `RedisProductListingCache`(infrastructure)에 있다.
"첫 페이지만 · 좋아요는 원본에서 · 삭제 상품 재확인" 은 이번 주에 정한 판단이라, Redis 코드 안이 아니라 응용 계층에 드러나게 둔다.
응용 계층은 캐시를 `ProductListingCache` 포트로만 안다.

**SQL 수**: 캐시를 거치지 않는 요청 1 개, hit 1 개(좋아요 붙이기), miss 2 개(공용 목록 + 좋아요 붙이기). W2 `PRODUCT-008` 을 고쳤다.

### 4.5 확인한 것 (읽기 경로)

`ProductCacheE2ETest` — 실제 MySQL · Redis 컨테이너, 가짜 객체 없음.

| 장면 | 결과 |
|---|---|
| 같은 요청의 miss 와 hit | 응답이 같고, 페이지 키 1 개가 생긴다 |
| hit 가 실제로 캐시에서 나오나 | 첫 요청 뒤 앱을 거치지 않고 DB 의 가격을 바꿔도 다음 응답은 옛 가격 — 원본을 다시 읽지 않았다 |
| 다른 사람이 채운 캐시 | 각자의 `liked` 만 보인다 |
| hit 에서 좋아요 | 가격은 캐시의 값, 좋아요 수는 즉시 반영 |
| 캐시하지 않는 요청 | 인기순 · 2 페이지 · 크기 10 은 키를 만들지 않는다 |
| 캐시에 남은 상품이 삭제됨 | hit 에서도 보이지 않는다 |

### 4.6 무효화

**목록을 바꾸는 쓰기는 커밋 뒤에 그 브랜드와 전체 목록의 키를 지운다.** 쓰기 하나에 `DEL` 한 번이다.

| 쓰기 | 이벤트를 내는 곳 | 조건 |
|---|---|---|
| 상품 등록 · 수정 · 삭제 | `ProductService` | 항상 |
| 재고 조정 | `ProductService.adjustStock` | **품절 여부가 뒤집힐 때만**(0 → 양수, 양수 → 0) |
| 주문 확정의 재고 차감 | `ProductService.deductStock` | **차감 뒤 0 일 때만**. 확정마다 올리면 판매가 잦은 브랜드의 캐시가 늘 빈다 |
| 브랜드 수정 · 일괄 삭제 | `BrandService` | 항상 |
| 좋아요 | — | 목록 캐시에 좋아요가 없다(4.1) |

**어떻게**: 도메인 서비스가 포트 `ProductListingEvents.changed(brandId)` 로 알리고, 인프라의 구현이 이를 Spring 이벤트 `ProductListingChanged` 로 발행한다. 응용 계층의 `ProductListingInvalidation` 이 `@TransactionalEventListener(AFTER_COMMIT)` 으로 받아 포트의 `invalidate` 를 부른다.

| 고를 수 있는 것 | 대가 |
|---|---|
| **도메인 서비스가 포트로 알림 · 응용 계층이 커밋 뒤 처리** (지금) | 도메인은 "이 브랜드의 목록이 바뀌었다" 는 사실만 알리고, 어떻게 전하는지(Spring 이벤트)는 인프라가 정한다 — 도메인이 spring-context 를 모르는 것을 ArchUnit 이 지킨다. "커밋 뒤" 라는 트랜잭션의 의미는 응용 계층에만 있다. 포트 하나와 구현 하나가 더 있다. 비동기 · 아웃박스(4.7 의 뒤집을 조건)로 옮길 때는 인프라 구현만 바꾼다 |
| Facade 가 직접 무효화 | 품절이 뒤집혔는지는 도메인만 안다 — Facade 가 알려면 서비스가 그 사실을 돌려줘야 하고, 주문 확정은 `OrderConfirmation` 을 거쳐 품목마다 돌려줘야 한다 |
| 트랜잭션 안에서 바로 무효화 | rollback 되어도 키가 지워져 있다. 해는 없지만(다음 요청이 miss 일 뿐) **커밋 전에 지우면 그 사이 옛 DB 를 읽은 요청이 키를 옛 값으로 다시 채워** 무효화가 없던 것이 된다 |

이벤트가 트랜잭션 밖에서 나오면(테스트에서 서비스를 바로 부를 때) `@TransactionalEventListener` 는 아무 일도 하지 않는다. 운영의 쓰기는 모두 Facade 의 트랜잭션 안이다.

**무효화가 실패하면**: 커밋은 이미 끝났으므로 응답을 실패로 바꾸지 않는다. 경고만 남기고, 옛 키는 TTL(60 초)에 사라진다 — 그동안 이름 · 가격 · 품절 표시 · 순서가 옛 값이다(Q-5).
삭제된 상품은 꺼낼 때 다시 걸러 이 동안에도 보이지 않는다(`CACHE-008`).

**확인한 것** (`ProductCacheE2ETest`):

| 장면 | 결과 |
|---|---|
| 관리자 가격 수정 커밋 뒤 재조회 | 두 목록의 키가 지워지고, 브랜드 목록과 전체 목록 모두 새 가격 · 바뀐 순서 |
| 상품 등록 | 다음 조회에 나온다 |
| 상품 삭제 · 브랜드 일괄 삭제 | 키가 지워진다(화면만 보면 꺼낼 때의 재확인이 가려 구분되지 않아 키를 본다) · 전체 목록에서 빠진다 |
| 브랜드 이름 수정 | 다음 조회에 새 이름 |
| 재고 0 → 5 · 5 → 3 | 앞은 품절이 풀리고, 뒤는 키가 그대로다 |
| 주문 확정이 마지막 재고를 팖 | 다음 조회에서 품절 |
| rollback | 키가 그대로이고 캐시는 변경 전 가격 |

### 4.7 장애

**무효화 실패 — 다시 시도하지 않고, TTL 이 상한이다.** 리스너가 한 번 지우고, 실패하면 오류 로그를 남긴다. 실패는 서킷 브레이커를 연다(아래).
리스너는 쓰기 요청의 스레드에서 돈다. 재시도를 두면 Redis 가 응답 없이 멈춘 동안 그 시간이 쓰기 응답에 그대로 더해진다 —
3 번(사이에 50 · 100 ms) 시도하면 관리자 수정 하나가 약 850 ms 걸렸다. 무효화를 부르는 쓰기에는 **주문 확정**(마지막 재고를 팔 때)도 있어, 사용자의 결제 응답이 Redis 상태에 묶인다.
재시도가 줄여 주는 것은 "잠깐 끊긴 Redis" 의 옛 값 시간뿐이고, Q-5 는 이미 무효화 실패에 TTL 60 초를 상한으로 받아들였다. 옛 값은 목록 표시에만 남고 주문은 캐시를 보지 않는다(`CACHE-009`).

| 고를 수 있는 것 | 무효화 실패로 옛 값이 보이는 시간(커밋 기준, 늦은 채움은 4.3) | 대가 |
|---|---|---|
| **TTL 만** (지금) | 60 초 | 없다. 장애 중 쓰기 응답이 Redis 를 기다리지 않는다 |
| 재시도 + TTL | Redis 가 잠깐 끊긴 경우 수백 ms. 계속 실패하면 60 초 | 실패하는 동안 쓰기 요청(주문 확정 포함)의 응답이 재시도 횟수 × 대기 한도만큼 늦어진다 |
| 아웃박스(같은 트랜잭션에 "무효화 필요" 기록 → 실패분을 주기적으로 처리) | 재시도 주기 | 테이블 · 스케줄러 · 정리, 쓰기마다 INSERT 하나 |
| 읽을 때마다 DB 의 revision 확인 | 0 | hit 마다 DB 조회, 목록을 바꾸는 쓰기가 revision 행 하나에서 줄을 선다(4.3 측정 — 품절이 몰리면 동시 80 의 주문 확정 처리량이 절반) |

**뒤집을 조건**: 표시 가격이 1 분 늦는 것을 받아들일 수 없게 되면(정해진 시각에 바뀌어야 하는 타임 세일 등) 아웃박스로 간다.

**리스너는 동기다.** 커밋 직후 같은 요청 스레드에서 돈다 — 응답이 돌아왔다면 무효화도 끝났으므로 "정상 변경 뒤 순차 조회는 최신"(`CACHE-006`) 이 응답 시점에 선다.
비동기로 옮기면 응답은 빨라지지만 응답과 무효화 사이에서 옛 값이 보인다. 리스너는 예외를 던지지 않는다 — 던지면 이미 커밋된 요청이 실패로 응답된다.
**뒤집을 조건**: 무효화가 느려져 쓰기 응답에 체감될 때 비동기로 옮기고, `CACHE-006` 의 범위를 "응답 뒤 무효화가 끝난 다음" 으로 다시 정한다.

**Redis 대기 한도 — 200 ms, 연결이 끊긴 것을 알면 즉시 실패(Q-7).** `RedisConfig`(공용 모듈)의 Lettuce 기본 명령 타임아웃은 60 초다.
그대로 두면 Redis 가 응답하지 않는 동안 캐시를 거치는 모든 조회가 60 초씩 요청 스레드를 쥐고, 스레드가 차면 **캐시와 무관한 요청까지 멈춘다** — 3 주차의 "느린 쿼리가 풀을 쥐어 무관한 요청까지 실패" 와 같은 구조다.
`datasource.redis.command-timeout`(기본 200 ms) 으로 명령 · 연결 타임아웃을 두고, 끊긴 동안의 명령은 기다리지 않고 거절한다(`REJECT_COMMANDS`).
200 ms 는 정상 hit(1 ms 미만)의 수백 배 여유이면서, 장애 동안 Redis 명령 하나가 기다리는 상한이다(`정함`). 캐시 대상 조회는 읽기 · 저장 두 명령이라 요청 하나에 약 400 ms 까지 더해진다.
**뒤집을 조건**: 정상 상태의 Redis p99 가 이 값에 가까워져 우회가 잦아지면 늘린다.

**Redis 가 실패하면 5 초 동안 건너뛴다(서킷 브레이커, Q-7).** 대기 한도만으로는 부족했다 — Redis 를 응답 없이 멈춘 채(`docker pause`, 연결은 열려 있어 즉시 거절이 일어나지 않는다)
캐시 대상 요청을 보내면 요청마다 읽기 · 저장 두 명령이 한도(200 ms)를 다 기다려, 처리량이 원본의 1/30 로 떨어졌다. 원문은 "캐시 실패 때 DB 가 정상이고 통제한 부하를 감당하는 조건에서 기존 정상 응답" 을 요구한다.
`RedisProductListingCache` 가 읽기 · 저장에서 Redis 오류를 만나면 그때부터 5 초 동안 Redis 를 건드리지 않고 원본으로 간다. 5 초가 지나면 다음 요청이 다시 시도한다.
**무효화도 건너뛴다.** 창 안의 무효화는 Redis 를 건드리지 않고 실패로 돌아가고, 무효화의 실패도 창을 연다. 장애 중 쓰기 응답에 더해지는 Redis 대기는 창을 여는 처음 한 번(최대 200 ms)뿐이다.
대가는 창 안에서 커밋된 쓰기의 옛 키가 Redis 가 살아난 뒤 TTL 까지 남는 것이다 — 무효화 실패와 같은 상한(Q-5)이다. Redis 가 데이터를 잃고 재시작했다면 옛 키도 없다.
**뒤집을 조건**: 장애 뒤의 옛 값을 줄여야 하면(타임 세일 등) 실패분을 아웃박스로 모았다가 브레이커가 닫힐 때 지운다 — 쓰기 응답이 Redis 를 기다리는 방향으로는 돌아가지 않는다.

**옛 값이 보이는 크기.** 무효화를 못 한 쓰기 하나가 남기는 옛 값과, 그런 쓰기가 얼마나 자주 생기는지로 나눠 본다. 늦은 채움(4.3)은 따로다.

- **언제 보이나**: 목록을 바꾸는 쓰기의 무효화가 ① `DEL` 실패이거나 ② 브레이커가 열린 창 안이라 건너뛰어졌고, ③ 옛 키가 Redis 에 남아 있을 때. 창 안에서는 이 서버가 캐시를 읽지 않으므로 옛 값은 **창이 닫힌 뒤** 보인다. Redis 가 데이터를 잃고 재시작했다면 옛 키가 없어 보이지 않는다.
- **한 번의 크기**: 그 브랜드와 전체 목록의 첫 페이지(정렬마다)가 **커밋 뒤 최대 60 초** 옛 이름 · 가격 · 품절 표시 · 순서다. 옛 키는 커밋 전에 저장됐으므로 커밋 뒤 60 초 안에 만료된다. 삭제된 상품은 이 동안에도 보이지 않고(`CACHE-008`), 주문은 캐시를 보지 않는다(`CACHE-009`).
- **얼마나 자주**: (목록을 바꾸는 쓰기의 초당 수) × (브레이커가 열려 있던 시간) + (Redis 가 정상일 때 `DEL` 이 실패한 수). 둘 다 이 환경에서 잴 수 없는 운영의 값이다.
  예를 들어 목록을 바꾸는 쓰기가 초당 0.1 건(관리자 수정과 마지막 재고를 판 확정)이고 Redis 가 한 달에 10 분 멈추면, 한 달에 약 60 번 각각 최대 60 초다(`정함`, 가정한 값).
  한정 판매처럼 품절이 몰리는 시간에 장애가 겹치면 그 시간의 쓰기 수만큼 늘어난다 — revision 의 쓰기 경합(4.3)이 커지는 조건과 같다.
- **운영에서 세는 것**(Micrometer, `/actuator/prometheus`):

  | 메트릭 | 뜻 |
  |---|---|
  | `product.listing.cache.invalidation{result=deleted}` | 지웠다 |
  | `product.listing.cache.invalidation{result=failed}` | `DEL` 이 실패했다(그리고 브레이커를 열었다) |
  | `product.listing.cache.invalidation{result=skipped}` | 브레이커가 열린 창 안이라 건너뛰었다 |
  | `product.listing.cache.breaker.opened` | 닫힌 브레이커가 열렸다. 열린 동안 겹친 실패는 한 번으로 센다 |

  무효화는 목록을 바꾸는 쓰기마다 한 번이므로 세 결과의 합이 그 쓰기 수다. **옛 값을 남긴 쓰기의 비율** = (`failed` + `skipped`) / 합. 브레이커가 열려 있던 시간은 열림 횟수 × 5 초가 하한이다.
  `ProductCacheOutageE2ETest` 가 Redis 를 멈춘 채 쓰기 · 조회를 섞어 네 값이 각각 한 번씩 오르는 것을 확인한다.
- **뒤집을 조건**: 옛 값을 남긴 쓰기의 비율이 1% 를 넘거나(`정함`), 장애 뒤 품절이 판매 중으로 보이는 문의가 생기면 위의 아웃박스로 간다. revision(4.3)도 이 비율로 다시 본다 — 장애가 잦아 옛 값이 자주 남는데 아웃박스로도 줄지 않을 때다.

k6, 브랜드 `1` 가격순 첫 페이지(캐시 대상), Redis 를 멈춘 채로(`results/c-outage-redis-rerun-*` · `c-outage-breaker-*`):

| 동시 요청 | Redis 정상(hit) | Redis 멈춤, 대기 한도만 | Redis 멈춤, 서킷 브레이커 |
|---|---|---|---|
| 1 | 596 /s · p50 1.4 ms | 2.4 /s · p50 416 ms | **367 /s · p50 2.2 ms** |
| 80 | 5,928 /s · p99 44 ms | 193 /s · p99 435 ms | **4,005 /s · p99 77 ms** |

실패는 모두 0 이다. 브레이커가 열린 동안은 모든 요청이 원본으로 가므로 처리량은 원본의 처리량(4.8 의 캐시 밖)이 된다. Redis 를 되살리면 5 초 안에 다시 캐시를 채웠다.
같은 측정을 처음 했을 때 대기 한도만으로 요청이 한 줄로 서서 초당 1.67 건에 머문 적이 있었으나(`c-outage-redis-*`), 같은 명령을 네 번 다시 돌려도 재현되지 않아 원인을 이 설계의 근거로 쓰지 않는다.

| 고를 수 있는 것 | 대가 |
|---|---|
| 대기 한도만 | 장애 동안 캐시 대상 요청마다 약 400 ms 를 기다리고, 그 시간 동안 요청 스레드를 쥔다 |
| **실패 한 번에 일정 시간 건너뛰기** (고른 것) | 의존성 없이 `AtomicLong` 하나. 일시적인 실패 한 번에도 5 초 동안 캐시를 쓰지 않는다 — 원본이 정확하므로 틀린 응답은 없다. 창이 끝난 순간 들어온 요청은 모두 다시 시도한다(각자 최대 400 ms 한 번) |
| 실패율 기반 · 반열림(Resilience4j 등) | 최근 N 번의 실패 비율로 열고, 창이 끝나면 일부 요청만 시험한다. 의존성이 늘고 상태 지표를 얻는다 |

**뒤집을 조건**: 운영에서 일시적인 네트워크 흔들림으로 브레이커가 자주 열려 캐시 이득을 잃으면 실패율 기반 · 반열림으로 바꾼다.
**남는 위험**: 브레이커가 열린 동안 캐시 대상 요청은 모두 원본으로 간다. 원본이 싸서(4.8) 지금은 견디지만, 트래픽이 원본의 처리 한계를 넘는 규모에서는 Redis 장애가 DB 장애로 번진다 — 그때는 원본 쪽의 여유(복제본, 속도 제한)를 함께 본다.

**스탬피드는 완화하지 않는다(Q-8).** 키가 비는 순간 몰린 요청이 모두 원본을 읽는 일이다. 원본이 싸서 키가 비어 있는 시간이 몇 ms 뿐이다.
브랜드 `1` 의 키를 지운 직후 동시에 요청을 보내 원본 쿼리 수와 지연을 쟀다(3 회, `results/c-stampede.tsv`):

| 동시 요청 | 문장 수(hit 의 좋아요 쿼리 포함) | 원본 목록 쿼리(추정) | p99 | 실패 |
|---|---|---|---|---|
| 40 | 46 ~ 47 | 약 6 | 7 ~ 11 ms | 0 |
| 80 | 86 ~ 90 | 약 6 ~ 10 | 7 ~ 15 ms | 0 |

처음 몇 요청만 원본을 읽고 나머지는 그사이 채워진 키를 읽었다. 측정의 한계: 요청을 `curl` 프로세스로 띄워 완전히 같은 순간에 출발하지 않는다.
**뒤집을 조건**: 원본이 다시 비싸지거나(인덱스로 풀리지 않는 필터 · 정렬), 한 키에 몰리는 이벤트가 생기면 완화를 넣는다 —
같은 키의 진행 중인 원본 조회를 나눠 쓰기(인스턴스 하나 안), Redis 락(인스턴스 사이), 만료 전 미리 갱신 중에서 고른다. `@Cacheable(sync = true)` 는 인스턴스 하나 안에서만 막는다.

**확인한 것**

`ProductCacheFailureE2ETest` — 실패 주입. 테스트 설정이 실제 Redis 캐시를 감싸 `invalidate` 를 정한 횟수만큼 실패로 돌려주거나 `save` 직전에 멈춘다.
규칙도 저장도 흉내 내지 않고 실패 시점 하나만 만든다(W3 2.5 와 같은 예외).

| 장면 | 결과 |
|---|---|
| 무효화가 실패 | 응답 200(커밋 유지), DB 는 새 가격, 조회는 옛 가격, 옛 키의 TTL 이 1 ~ 60 초, 만료(키 삭제로 앞당김) 뒤 첫 조회가 DB 와 같다 |
| 늦은 채움: 이전 조회가 옛 값을 읽고 저장 직전에 멈춤 → 관리자 수정 커밋 → 늦게 저장 | 늦은 저장이 살아 있는 키에 들어가 **이후 조회는 옛 가격**, 그 키의 TTL 이 1 ~ 60 초, 만료(키 삭제로 앞당김) 뒤 첫 조회가 DB 와 같다 |

`ProductCacheOutageE2ETest` — 이 테스트만의 Redis 컨테이너(고정 포트, 영속화 끔)를 실제로 멈추고(`docker pause`) 재시작한다. 공용 Redis 는 건드리지 않는다(`CACHE-012`).

| 장면 | 결과 |
|---|---|
| Redis 중단 중 캐시 대상 조회 | 2 초 안에 200, 값은 멈춘 동안 바뀐 원본 |
| Redis 중단 중 인기순(캐시 밖) | 0.5 초 안에 200 |
| Redis 중단 중 관리자 수정 | 무효화를 포함해 2 초 안에 200, DB 에 반영 |
| Redis 중단 중 브레이커가 열린 뒤 관리자 수정 | 무효화가 Redis 를 기다리지 않아 300 ms 안에 200, DB 에 반영 |
| Redis 재시작(데이터 유실) | 다시 연결되어 원본과 같은 값으로 다시 채운다 |
| Redis 가 응답 없이 멈춘 동안 스레드 20 개가 6 초 동안 캐시 대상 조회를 계속 보냄 | 요청마다 Redis 를 기다리지 않아 스레드마다 50 건 넘게 처리된다(대기 한도만으로는 스레드마다 약 14 건) |

### 4.8 캐시가 얼마나 줄였나

k6, 같은 seed B · 같은 요청(`QUERY-001`). 같은 시각에 **캐시 밖(크기 19)** 과 **캐시 hit(크기 20)** 를 쌍으로 쟀다(`results/c-now-*`). 좋아요 수는 카운터(3.2) 에서 읽는다.

| 브랜드 | 동시 요청 | 캐시 밖 | 캐시 hit |
|---|---|---|---|
| `1` | 1 | 812 /s · p50 1.05 ms | 596 /s · p50 1.37 ms |
| | 80 | 5,725 /s · p99 51 ms | 5,928 /s · p99 44 ms |
| `100` | 1 | 801 /s · p50 0.98 ms | 749 /s · p50 1.15 ms |
| | 80 | 6,167 /s · p99 52 ms | 5,823 /s · p99 46 ms |
| `1000` | 1 | 917 /s · p50 0.93 ms | 673 /s · p50 1.24 ms |
| | 80 | 5,525 /s · p99 67 ms | 3,981 /s · p99 71 ms |
| 전체 | 1 | 818 /s · p50 1.05 ms | 464 /s · p50 1.66 ms |
| | 80 | 6,369 /s · p99 42 ms | 6,070 /s · p99 35 ms |

실패는 모두 0, 요청당 SQL 은 모두 1 개다.

**캐시 hit 는 응답을 줄이지 못했다 — 동시 요청 1 에서 7 ~ 43% 느렸고, 80 에서는 p99 만 조금 낮았다.** Q-2 의 기준("hit 이 개선된 SQL 보다 의미 있게 빨라야 한다")을 넘지 못했다.

| | 캐시 밖 | 캐시 hit |
|---|---|---|
| DB | 21 개 고르기 + 상품 · 브랜드 붙이기 + 좋아요 수 · `liked` | 20 개의 좋아요 수 · `liked` · 삭제 재확인 |
| Redis | 없다 | 왕복 1 번 + JSON 변환 |

**hit 에 DB 조회가 하나 남는다** — 좋아요 수 · `liked` · 삭제 재확인(`CACHE-004` · `008`, 원문의 "권위 확인을 유지하고 그 비용도 hit 측정에 포함").
SQL 과 인덱스를 고친 뒤 원본은 인덱스 21 항목을 읽고 끝나, 캐시가 덜어 줄 일이 고르기와 붙이기뿐이다. 쿼리 하나의 고정 비용(커넥션 · 파싱 · 전송)은 남고, Redis 왕복과 JSON 변환이 더해진다.

**손익분기 히트율을 계산했다.** 동시 요청 1 로 같은 요청을 300 번씩 순서대로 보내, 원본(크기 19) · hit · miss(요청마다 키를 지운 크기 20) 의 응답 시간과
**요청당 DB 실행 시간**(`performance_schema` 의 문장 실행 시간 합 ÷ 요청 수) 을 쟀다(`results/c-now-breakeven.tsv`).

| 브랜드 | | 원본 | hit | miss | hit 가 아끼는 것 | miss 의 손해 | 손익분기 히트율 |
|---|---|---|---|---|---|---|---|
| `1` | 응답 p50 | 3.54 ms | 4.43 ms | 5.20 ms | −0.89 ms | 1.66 ms | **없음** |
| | DB 시간 | 1.36 ms | 0.85 ms | 1.29 ms | **0.51 ms (38%)** | −0.06 ms | **0%** — 어느 히트율이든 이득 |
| `100` | 응답 p50 | 3.06 ms | 3.18 ms | 5.31 ms | −0.12 ms | 2.25 ms | 없음 |
| | DB 시간 | 0.88 ms | 0.80 ms | 1.18 ms | 0.08 ms (9%) | 0.30 ms | **79%** |
| `1000` | 응답 p50 | 3.37 ms | 4.12 ms | 4.65 ms | −0.75 ms | 1.28 ms | 없음 |
| | DB 시간 | 0.91 ms | 0.83 ms | 0.96 ms | 0.08 ms (8%) | 0.05 ms | **40%** |

손익분기 히트율 = miss 의 손해 ÷ (hit 가 아끼는 것 + miss 의 손해). 응답 시간에는 `curl` 의 연결 비용이 세 경우에 똑같이 들어 있다.

- **응답 시간으로는 히트율 100% 에서도 이득이 없다.** hit 가 원본보다 느리므로 손익분기가 없다.
- **DB 의 일로는 큰 브랜드에서만 분명하다.** 브랜드 `1` 은 hit 하나가 DB 시간의 38% 를 덜고 miss 는 손해가 없다 — 고르기가 2 만 5 천 항목의 인덱스 구간에서 일어나 원본에서 차지하는 몫이 크다.
  작은 브랜드는 아끼는 것이 8 ~ 9% 라 히트율이 40 ~ 79% 를 넘어야 이득이다.
- 같은 쌍의 k6 요청 1,000 건당 MySQL CPU 도 같은 방향이다 — 브랜드 `1` 은 동시 요청 1 · 80 에서 hit 가 21 · 34% 적고, 작은 브랜드는 차이가 없거나 동시 요청 80 에서 hit 가 더 많았다.
  높은 동시성에서는 앱 · MySQL · k6 가 한 노트북의 CPU 를 다투어 대기 · 스레드 전환이 섞이므로, 쿼리의 비용은 DB 실행 시간으로 비교한다.

**판단**: 캐시가 덜어 주는 것은 응답 시간이 아니라 DB 의 일이고, 그것도 원본에서 고르기가 차지하는 몫만큼이다. 이 경로에서는 큰 브랜드의 첫 페이지에만 이득이 분명하다.
과제의 필수(한 조회 경로의 cache-aside)라 유지하고, 정확성(4.5 ~ 4.7)은 모두 확인했다.
**캐시의 이득은 "히트율" 이 아니라 "히트율 × hit 하나가 아끼는 원본 비용" 이 miss 의 손해를 넘느냐로 정해진다.** 기준선(브랜드 `1` 의 원본 44 ms, 동시 요청 80 에서 1 초)이었다면 같은 구성으로 크게 이겼을 것이다.

**측정의 한계**: 앱 · MySQL · Redis · k6 가 한 노트북의 CPU 를 나눠 쓴다. Redis 까지 같은 CPU 를 쓰는 캐시 쪽에 불리하고, 운영처럼 Redis 가 별도 장비면 차이가 줄 수 있다.
`localhost` 라 네트워크 전송이 빠져 있다. **실제 히트율은 재지 않았다** — "요청이 첫 페이지에 몰린다" 는 Q-2 의 가정이다.

**뒤집을 조건 — 캐시가 이득이 되는 때**:
- 원본이 다시 비싸질 때: 필터 · 정렬 조건이 늘어 인덱스 하나로 21 개를 고를 수 없는 조회가 생기면 그 조회에 둔다.
- DB 가 병목일 때: 앱 서버가 늘어 DB CPU 가 먼저 차면, hit 가 덜어 주는 DB 의 일이 의미를 갖는다. 운영의 히트율을 재서 위 손익분기와 비교한다.
- hit 에서 DB 조회를 없애야 할 만큼 DB 가 차면, 좋아요 수 · `liked` 를 Redis 사본으로 옮긴다. 정상 변경 뒤 최신(`CACHE-006`)을 지키려면 배치가 아니라 쓰기 뒤에 함께 갱신하는 사본이어야 한다. 삭제 재확인은 원문이 신선도 정책의 대상이 아니라고 하므로 원본에 남긴다.

캐시는 DB 가 매번 하던 계산을 미리 만든 결과로 바꾸고, 그것을 꺼내 쓰는 비용을 앱에 넘긴다(동시 요청 1 의 요청당 앱 CPU 가 hit 에서 14 ~ 82% 많았다).
앱은 늘리기 쉽고 DB 원본은 하나이므로 **스케일아웃해서 DB 가 먼저 찰 때** 이 이동이 이득이 된다. 그때도 커넥션 수(앱 한 대당 풀 40 개 × 대수)와 잠금 경합(같은 상품의 확정)은 캐시로 풀리지 않는다.

## 5. 핫키 — 인기 상품의 상세

"원본이 싸다" 는 평균적인 상품의 이야기다. 요청이 몰리는 인기 상품은 좋아요가 많아 원본이 비싸다.
상세(`findAliveById`)가 좋아요를 조인해 묶던 쿼리였고, 목록과 같은 방식(좋아요는 커버링 인덱스로 세고 `liked` 는 유니크 인덱스로 확인)으로 바꿨다. 결과는 기존 쿼리와 같았다.

k6 (`results/c-baseline-detail-*` · `c-v1-detail-*`, 인기 상품 867325 · 평범한 상품 942306, 브랜드 · 정렬 칸은 상세에 쓰이지 않는다):

| 상품 | 동시 요청 | 처리량 | p50 | p99 | MySQL CPU |
|---|---|---|---|---|---|
| 1 위 (좋아요 114,781 개), 개선 전 | 1 | 43 /s | 23 ms | 26 ms | 89% |
| | 80 | 359 /s | 219 ms | 376 ms | **1,246%** |
| 1 위, 개선 후 | 1 | 113 /s | 8.6 ms | 13 ms | 75% |
| | 80 | **898 /s** | 85 ms | 184 ms | **1,317%** |
| 평범 (좋아요 3 개) | 80 | 8,152 ~ 9,796 /s | 7 ~ 8 ms | 31 ~ 38 ms | 약 240% |

- 개선 전에는 **상품 하나의 상세가 MySQL CPU 를 모두 썼고**, 동시 요청 10 에서 이미 처리량이 초당 350 건에서 멈췄다. 같은 엔드포인트의 평범한 상품과 27 배 차이 난다.
- 쿼리 개선으로 2.5 배 늘었지만 여전히 MySQL 이 차고 평범한 상품의 1/9 이다. 요청마다 좋아요 11 만 개를 세는 일이 남기 때문이다 — **카운터(3.2) 가 지금 해야 하는 조건에 가까워졌다.**
- 상세를 캐시해도 좋아요 수를 담으면 인기 상품일수록 좋아요가 잦아 늘 무효화되고, 빼면 hit 에도 세야 한다. 원본을 싸게 하는 것(카운터)이 먼저고, 그 뒤 값마다 자리를 나눈다 — 이름 · 가격은 오래 캐시, 좋아요 수는 카운터, `liked` · 품절은 원본.

이 측정이 카운터를 고른 근거 중 하나다(3.2).

**카운터 뒤** (`results/c-now-detail-*`):

| 상품 | 동시 요청 | 처리량 | p50 | p99 | MySQL CPU | 1,000 건당 |
|---|---|---|---|---|---|---|
| 인기 (좋아요 114,781 개) | 80 | **8,619 /s** | 7.2 ms | 41 ms | 235% | 27 |
| 평범 (좋아요 3 개) | 80 | 8,388 /s | 7.5 ms | 44 ms | 187% | 22 |

**상세는 캐시하지 않는다.** 원본이 기본키 · 유니크 인덱스로 한 행씩 찾는 일뿐이라, 이 환경의 최대 처리량에서도 MySQL 은 코어 2 개 정도만 썼다 — 병목은 DB 가 아니었다(앱 · k6 가 먼저 CPU 를 채웠다).
캐시를 두어도 hit 에 좋아요 수 · `liked` · 삭제 확인의 조회가 남아(4.8) 덜어 줄 것은 상품 · 브랜드 행 두 개뿐이다. 원문에서도 목록 · 상세 모두의 캐시는 선택 심화다.
**뒤집을 조건**: 이벤트처럼 한 상품에 조회가 몰려 MySQL CPU 가 차는 것이 보일 때(요청당 비용으로 이 환경에서 초당 수만 건 이상).
그때는 상세 캐시와 함께 hit 에 남는 조회를 줄이는 정책을 정한다 — 좋아요 수는 쓰기 뒤에 함께 갱신하는 Redis 사본(카운터의 사본)을 읽는다 — 짧은 TTL 이나 배치 사본은 `CACHE-006` 을 어긴다. 시작 시각을 아는 이벤트면 미리 채우고 이벤트 동안 만료시키지 않는다(스탬피드).

## 6. 측정의 한계

- **분포는 정함이다.** 가장 큰 브랜드가 상품의 2.5%(25,201 개)이고 1 만 개를 넘는 브랜드가 3 개다. 실제 분포를 알면 바꾼다(SEED 의 뒤집을 조건).
  결론을 숫자보다 **"브랜드 크기에 비례하던 비용을 크기와 무관하게 만들었다"** 로 읽는다.
- **한 노트북**에서 앱 · MySQL · Redis · k6 가 CPU 를 나눠 쓴다. 절대값이 아니라 같은 환경의 전후 비교만 의미가 있다. `localhost` 라 네트워크 전송이 빠져 있다.
- **버퍼 풀**(128 MB) 보다 데이터가 크다. 같은 쿼리도 직전에 무엇을 읽었는지에 따라 페이지를 디스크(Docker VM 의 OS 캐시)에서 읽어 흔들린다 — SQL 비교 전에 테이블과 인덱스를 한 번씩 훑어 데웠다.
  버퍼 풀이 빈 상태(`QUERY-010`)의 브랜드 `1` 기준선은 p50 150 ms 로 데운 상태(44 ms)의 3 배였다.
- **`EXPLAIN ANALYZE` 의 첫 줄**은 바깥 쿼리가 상수 한 행으로 끝나면 SELECT 절 서브쿼리의 시간을 담지 않는다. 상세 쿼리가 0.0001 ms 로 나와 `SHOW PROFILES` 로 다시 쟀다.
- **CPU** 는 1 ~ 2 초마다 잰 평균이라 흔들린다. `docker stats` 가 코어 수(1,200%)를 넘는 값을 보이기도 했다.

**측정하지 않은 계약 밖의 것** — 들어오면 다시 잰다:
- 가격 범위 필터: 가격순은 지금 인덱스로 21 개에서 멈추지만, 최신순 · 인기순은 범위 안의 상품을 모두 읽는다. 범위 값이 키에 들어가 목록 캐시는 효과가 없다.
- 가격 높은순: 동점 규칙(`id DESC`) 때문에 가격 인덱스를 어느 방향으로 읽어도 맞지 않는다. 전용 인덱스를 두거나 정렬마다 동점 규칙을 정한다.
  관리자 목록의 높은순 · 재고순이 지금 이 상태다(관리자 화면이라 두었다).

## 7. 기각한 선택지

설계 중 검토했고 측정으로 기각한 선택지다. 그럴듯해 보여 다시 제안되기 쉬워 근거와 함께 둔다.

| 선택지 | 기각한 근거 |
|---|---|
| 인덱스만 더한다 | 집계가 정렬보다 앞에 있으면 인덱스의 순서를 쓰지 못한다. 인덱스만 더한 후보는 기준선보다 느렸다(2.1) |
| 쿼리만 고친다 | 큰 브랜드는 가격을 보려고 본 행을 모두 읽어 줄지 않았다(2.1) |
| 브랜드 없는 최신순은 기본키 그대로 둔다 | 옵티마이저가 브랜드 인덱스를 skip scan 해 101 만 개를 읽는다(2.4) |
| 브랜드 없는 최신순을 힌트(`FORCE INDEX`)로 고정한다 | 삭제 비율 · 위치에 따라 무너진다(2.4) |
| 목록 캐시로 응답을 빠르게 한다 | SQL 개선 뒤 hit 는 같거나 느리다. 응답 시간으로는 손익분기 히트율이 없다. 캐시가 하는 일은 DB 의 일을 앱으로 옮기는 것이다(4.8) |
| 좋아요 수를 목록 캐시에 담는다 | 좋아요마다 무효화하거나 옛 수를 보여야 한다. 담아도 `liked` 때문에 hit 의 왕복이 원본과 비슷해진다(4.1, 4.8) |
| 좋아요 수를 Redis 카운터 · Sorted Set 만으로 둔다 | 순서를 Redis 에만 두면 장애 때 다시 계산할 원본이 4 초다. DB 카운터를 원본으로 둔다. 배치로 갱신하는 사본은 `CACHE-006` 을 어긴다(3.2) |
| 전체 인기순을 옵티마이저에 맡긴다 | 같은 데이터에서 통계를 다시 계산하자 출발점이 뒤집혀 1,000 배 느려졌다(3.2) |
| Redis 장애는 대기 한도만으로 견딘다 | 요청마다 한도를 다 기다려 처리량이 1/30 이 된다(4.7) |
| 스탬피드를 미리 막는다 | 원본이 싸서 키가 비는 시간이 몇 ms 이고, 동시 80 에서도 p99 15 ms 안이었다(4.7) |
| 인기 상품 20 개 묶음(87 ms)을 페이지 비용으로 쓴다 | 실제 페이지가 아니라 만든 최악의 경우다. 실제 페이지는 12 ms(3.3) |
| MySQL 재시작으로 버퍼 풀을 비운다 | 종료 때 페이지 목록을 저장해 시작 때 되살린다(`QUERY-010`) |
