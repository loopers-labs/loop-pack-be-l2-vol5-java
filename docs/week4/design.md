# 커머스 API 설계 — 4주차 · 조회 최적화와 캐시

요구사항 명세(`docs/week4/requirements.md`)의 규칙과 질문을 바탕으로, 측정한 것과 그것으로 정한 것을 적는다.
2 · 3 주차 설계는 `W2` · `W3` 으로 가리킨다.

## 1. 상품 목록의 병목

측정 요청은 `QUERY-001` 이다 — `GET /api/v1/products?brandId={1 · 100 · 1000}&sort=PRICE_ASC&page=0&size=20`, 데이터는 seed B.
측정 자료는 `docs/week4/load/results/` 에 있다.

### 1.1 기준선

| 브랜드 (살아 있는 상품) | 동시 요청 | 초당 처리 | p50 | p99 | 실패 | 커넥션 획득 대기(평균) |
|---|---|---|---|---|---|---|
| `1` (135,186) | 1 | 0.6 | 1,621 ms | 1,796 ms | 0 | 0.7 ms |
| | 10 | 4.1 | 2,440 ms | 2,634 ms | 0 | 1.4 ms |
| | 40 | 4.4 | 8,849 ms | 12,813 ms | 0 | 0.8 ms |
| | 80 | 13.5 | 3,015 ms | 12,478 ms | **335 / 495** | **2,549 ms** |
| `100` (1,345) | 1 | 136 | 7 ms | 11 ms | 0 | 0 |
| | 80 | 613 | 124 ms | 320 ms | 0 | 62 ms |
| `1000` (129) | 1 | 778 | 1.2 ms | 2.6 ms | 0 | 0 |
| | 80 | 4,078 | 17 ms | 61 ms | 0 | 8 ms |

- **큰 브랜드에서 동시성을 늘려도 처리량이 늘지 않는다.** 1 → 40 에서 초당 0.6 → 4.4 건이고, 요청마다 길어질 뿐이다.
- **80 에서 커넥션 풀이 고갈된다.** 풀 40 개를 이 조회가 모두 쥐어 나머지가 `connection-timeout` 3 초에 실패했다(68%).
  이 단계의 p50 이 40 보다 낮은 것은 실패한 요청이 3 초에 끝나 끌어내렸기 때문이다.
- **같은 쿼리가 작은 브랜드에서는 수 ms 다.** 비용이 브랜드의 상품 수에 비례한다. 균등한 seed A 로는 보이지 않는다.
- 같은 측정을 한 번 더 돌려 재현했다(브랜드 `1`, 80 에서 실패 339 / 499).
- 요청당 SQL 은 1 개다. N+1 은 없다(`QUERY-006`).

**버퍼 풀이 빈 상태**는 데운 상태와 거의 같았다(브랜드 `1` p50 1,227 ms). Docker 의 OS 파일 캐시가 남아 디스크 읽기가 재현되지 않았다(`QUERY-010`).
그래서 1 초가 넘는 시간은 디스크 대기가 아니라 **행을 붙이고 묶는 CPU 작업**이다.

### 1.2 무엇이 시간을 쓰는가

브랜드 `1` 의 `EXPLAIN ANALYZE`(1,446 ms):

```
Limit 21
└ Sort: price, id DESC (21 개만 남김)                              ← 5. 여기서야 21 개
  └ Group aggregate: count(distinct l.id), max(liked)   135,186 행  ← 4. 전부 묶음
    └ Nested loop left join (ml: 내 좋아요)             643,300 회  ← 3. 좋아요 행마다 찾음
      └ Nested loop left join (l: 좋아요)               643,300 행  ← 2. 좋아요를 붙여 불어남
        └ Sort: p.id …                                  135,186 행
          └ Index lookup idx_product_brand_id            135,186 행, 693 ms  ← 1. 전부 읽음
```

- **집계가 `LIMIT` 보다 먼저다.** 상품마다 좋아요 수를 확정하려면 그 상품의 행을 모두 봐야 하고, `GROUP BY p.id` 의 순서(id)와 `ORDER BY` 의 순서(가격)가 달라
  전부 묶은 뒤 따로 정렬한다. 화면에 필요한 21 개를 고르기 위해 135,186 개의 좋아요를 센다.
- **`PRICE_ASC` 의 순서에는 좋아요 수가 필요 없다.** 좋아요 수는 보여 줄 21 개에만 있으면 된다.
- **`liked` 를 좋아요 행마다 찾는다.** 상품당 한 번이면 될 일을 643,300 번 한다.
- **인덱스에 가격이 없다.** `idx_product_brand_id (brand_id, deleted_at)` 로 찾은 뒤 행마다 기본키로 본 행을 읽는다(693 ms).
  `EXPLAIN` 의 `possible_keys` 도 이 인덱스 하나뿐이었다.
- 예상 행 수 288,114, 실제 135,186 — 통계 추정이 2 배 어긋난다.

## 2. 개선 후보와 예측

**예측은 측정 전에 적는다.** 결과가 예측을 확인하는지 뒤집는지가 선택의 근거다.

| 후보 | 바꾸는 것 | 예측 (브랜드 `1`) | 예측이 틀렸다고 볼 결과 |
|---|---|---|---|
| ① 인덱스만 | `(brand_id, deleted_at, price, id DESC)` 추가. 쿼리는 그대로 | **거의 줄지 않는다.** 집계가 정렬보다 먼저라 인덱스 순서로 읽다가 멈출 수 없다. 옵티마이저가 새 인덱스를 고르더라도 135,186 행을 읽고 643,300 행을 묶는 일은 그대로다 | 1 초 아래로 떨어진다 |
| ② 쿼리만 | 파생 테이블이 가격순 21 개의 `id` 를 먼저 고르고, 좋아요 수와 `liked` 는 그 21 개에 대해 SELECT 절 서브쿼리로 구한다. 인덱스는 그대로 | **절반쯤 준다.** 좋아요 조인과 집계(2 ~ 4 단계)가 사라진다. 그러나 가격이 인덱스에 없어 135,186 행을 읽고 정렬하는 일(1 단계 693 ms)은 남는다 | 100 ms 아래로 떨어지거나, 1 초가 넘게 남는다 |
| ③ 둘 다 | ② + ①의 인덱스. 파생 테이블이 인덱스만으로 `id` 를 고른다(커버링, 지연 조인) | **브랜드 크기와 무관하게 수 ms.** 인덱스를 가격순으로 21 항목 읽고 멈춘다. 정렬도 집계도 21 개 규모다 | 브랜드 `1` 이 `1000` 보다 수십 배 느리다 |
| ③′ 둘 다, `id` 오름차순 인덱스 | ③ 에서 인덱스를 `(brand_id, deleted_at, price, id)` 로 | **③ 보다 느리다.** `ORDER BY price ASC, id DESC` 의 방향이 인덱스와 어긋나 가격 동점을 정리하려고 브랜드의 인덱스 항목 전체를 정렬한다. 본 행은 읽지 않으므로 ② 보다는 빠르다 | ③ 과 같다 |

③′ 을 따로 재는 이유는 `PRODUCT-012`(동점은 `id` 내림차순)가 인덱스 방향을 정하기 때문이다. 방향을 맞추지 않으면 인덱스가 있어도 정렬이 남는지를 확인한다.

### 2.1 결과

`EXPLAIN ANALYZE` 5 회의 중앙값이다(`docs/week4/load/compare.sh`, 결과 `results/sql-*.txt`). 후보마다 인덱스를 만들고 `ANALYZE TABLE` 한 뒤 재고, 다음 후보 전에 지웠다.

| 후보 | 브랜드 `1` | `100` | `1000` | 옵티마이저가 고른 것 | 예측과 비교 |
|---|---|---|---|---|---|
| 기준선 | 1,716 ms | 8.7 ms | 0.94 ms | `idx_product_brand_id` | — |
| ① 인덱스만 | **2,443 ms** | 15.3 ms | 0.99 ms | 새 인덱스 `idx_product_brand_price` | 맞았다 — 줄지 않았다. **오히려 느려졌다.** 옵티마이저가 새 인덱스를 골랐지만 집계가 앞에 있어 순서를 쓰지 못하고, 더 넓은 인덱스로 같은 135,186 행을 읽었다 |
| ② 쿼리만 | 176 ms | 2.5 ms | 0.48 ms | `idx_product_brand_id` | **틀렸다 — 예측(절반)보다 10 배 줄었다.** 조인 · 집계가 사라지고, 남은 정렬은 상위 21 개만 유지하는 정렬(`limit input to 21 row(s) per chunk`)이라 가벼웠다. 135,186 행을 읽는 일은 그대로 남아 브랜드 크기에 비례한다 |
| ③ 둘 다 | **0.42 ms** | 0.36 ms | 0.35 ms | 새 인덱스, 커버링 · 정렬 없음 | 맞았다 — 인덱스를 21 항목 읽고 멈췄다(`Covering index lookup … rows=21`). 브랜드 크기와 무관하다 |
| ③′ 둘 다, `id` 오름차순 | 23.7 ms | 0.55 ms | 0.34 ms | 새 인덱스, 커버링 + 정렬 | 맞았다 — 본 행은 읽지 않았지만 방향이 어긋나 135,186 항목을 정렬했다 |

- **인덱스만으로는 아무것도 얻지 못했다.** 병목이 "어떻게 찾느냐" 가 아니라 "몇 개를 묶느냐" 였기 때문이다. 쿼리가 21 개를 먼저 고르는 모양이 된 뒤에야 인덱스의 순서가 쓰였다.
- **인덱스의 방향이 동점 규칙을 따라야 한다.** ③ 과 ③′ 의 차이(0.42 → 23.7 ms)는 `id DESC` 하나다. `PRODUCT-012` 를 바꾸면 인덱스도 바꿔야 한다.
- **결과가 같다.** 기준선과 ② · ③ 의 쿼리가 브랜드 3 개 × 사용자 5 명에서 같은 행을 돌려줬다. 앱에 넣은 뒤에는 응답 스냅숏 180 개로 다시 비교한다.

**고른 것: ③.** 브랜드 크기와 무관하게 1 ms 아래이고, 기존 계약(요청당 SQL 1 개, 페이지 번호, 동점 규칙)을 하나도 바꾸지 않는다.

**대가**: 인덱스가 하나 늘어 상품의 등록 · 가격 수정 · 삭제가 인덱스 하나를 더 고친다. 가격 수정은 인덱스 안에서 항목의 위치를 옮긴다.
**뒤집을 조건**: 상품 쓰기가 측정 가능한 수준으로 느려지면 기존 `idx_product_brand_id` 를 새 인덱스로 대신할 수 있는지 본다 —
새 인덱스의 앞 두 열이 같아 브랜드 삭제의 벌크 UPDATE(W3 2.2)도 쓸 수 있다. 다만 브랜드 필터 + `LATEST` 는 기존 인덱스의 `(brand_id, deleted_at, id)` 순서를 쓰므로, 지우기 전에 그 정렬을 함께 잰다.

**모든 후보가 지켜야 하는 것**: 같은 입력에 같은 결과(`QUERY-003`). 정렬된 id · 가격 · 좋아요 수 · `liked` · 품절 · `hasNext` 를
기준선의 응답 스냅숏(`docs/week4/load/snapshots/baseline.jsonl`)과 비교한다. 정렬 3 종 × 브랜드 `1` · `100` · `1000` · 전체 × 페이지 0 · 1 · 5 × 사용자 2 명.

**고르는 방법**: 후보는 먼저 SQL 수준(`EXPLAIN` · `EXPLAIN ANALYZE`)에서 비교하고, 고른 하나를 애플리케이션에 넣어 k6 와 스냅숏으로 확인한다.
후보마다 코드를 바꿔 부하 측정을 하는 것은 SQL 수준에서 차이가 분명하지 않을 때만 한다.

### 2.3 Q-1 — SQL · 인덱스 개선만으로 충분한가

**충분하다.** 측정 전에 정한 기준(개선 뒤 p95 50 ms 이하, 동시 요청을 늘려도 커넥션 대기가 생기지 않음)을 넘는다 —
동시 요청 80 에서도 p99 38 ms 이고, 풀 크기 이내에서는 커넥션 대기가 없다.
그래서 이 경로에 캐시를 붙여 줄일 수 있는 것은 1 ms 안팎이다. 캐시는 원문(`CACHE-001`)이라 붙이되, **어느 경로에 붙일지(Q-2)는 아직 무거운 `LIKES_DESC` 와 함께 정한다.**

**뒤집을 조건**: 요청 분포가 측정과 달라 같은 첫 페이지에 요청이 몰리거나, 실제 운영 DB 가 이 노트북보다 느려 p95 가 기준을 넘으면 이 경로의 캐시 이득을 다시 잰다.

**이 절이 다루지 않는 것**: `LIKES_DESC` 는 순서가 좋아요 수로 정해져 먼저 자를 수 없다(`QUERY-005`). 같은 방법이 통하지 않으므로 따로 다룬다.
`LATEST` 는 브랜드 필터와 함께 같은 구조를 쓰므로 ③ 의 효과를 함께 확인한다.
## 3. 인기순과 좋아요 수

### 3.1 인기순(`LIKES_DESC`)은 먼저 자를 수 없다

순서가 좋아요 수로 정해지므로 브랜드의 모든 상품의 좋아요를 세야 21 개를 고를 수 있다(`QUERY-005` — 전체 후보에서 정렬한 뒤 페이지).
기존 쿼리에서 바꿀 수 있는 것은 **무엇을 붙여서 묶느냐** 뿐이다. SQL 수준 비교(`results/sql-L*.txt`, 5 회 중앙값):

| 후보 | 브랜드 `1` | `100` | `1000` | |
|---|---|---|---|---|
| L0 기존(상품 · 브랜드 · 좋아요를 붙여 묶음) | 914 ms | 7.9 ms | 0.98 ms | |

| L2 상품마다 좋아요를 세고 상위 21 개만 붙임 | 358 ms | 3.6 ms | 0.55 ms | 채택. 상품 쪽은 새 인덱스로 본 행 없이 19 ms, 나머지는 13 만 번 세기 |

| 40 | 3.5 → 6.6 | 10,762 → 5,851 ms | 12,682 → 8,761 ms | 0 → 0 |
| 80 | 13.2 → 13.4 | 3,011 → 3,107 ms | 15,550 → 11,420 ms | 362 → 265 / 480 |

**큰 브랜드의 인기순은 동시 요청을 견디지 못한다.** 세는 일이 CPU 작업이라 동시 요청이 그것을 나눠 쓰며 함께 느려진다.
커버링 인덱스는 이미 쓰고 있다 — 남은 비용은 본 행 읽기가 아니라 세는 횟수다.

### 3.2 Q-6 — 이번 주에는 비정규화하지 않는다

원본이 동시 요청 10 에서 1 초를 넘으므로 Redis 만으로는 고르지 않는다(Q-6 의 기준) — 캐시가 비는 순간마다 위의 실패가 되살아난다.
해결은 좋아요 수를 미리 저장하는 것(카운터 비정규화)이고, 원문의 선택 심화다. 필수인 캐시를 먼저 하고 미룬다.

**하게 되면**: 카운터는 상품 행이 아닌 별도 테이블 `product_like_count (product_id, brand_id, like_count)` 에 두고 `(brand_id, like_count DESC, product_id DESC)` 로 정렬한다.
상품 행에 두면 좋아요가 주문 확정의 상품 잠금과 다툰다. 관계 행이 실제로 생기고 지워질 때만 같은 트랜잭션에서 증감한다(`LIKE-002` · `003` 멱등).
같은 카운터가 목록의 좋아요 수(3.3 의 87 ms)도 없앤다.
**뒤집을 조건(지금 하는 조건)**: 인기순이 실제로 쓰이는 화면이 되거나, 큰 브랜드의 인기순 요청이 커넥션 풀을 고갈시키는 것이 운영에서 보일 때.

### 3.3 좋아요 수를 붙이는 비용과 인덱스

목록의 좋아요 수는 저장하지 않고 셀 수밖에 없다(3.2). 그래서 페이지에 인기 상품이 끼면 그만큼 센다.
캐시 hit 뒤에 20 개의 좋아요 수와 `liked` 를 한 쿼리로 붙인다고 할 때(`SELECT product_id, COUNT(*), MAX(user_id = ?) … WHERE product_id IN (…) GROUP BY product_id`):

| 페이지 | 읽은 좋아요 | 인덱스 `(product_id)` | 인덱스 `(product_id, user_id)` |
|---|---|---|---|
| 평범한 상품 20 개 | 64 | 0.1 ms | 0.05 ms |
| 인기 상품 1 개 포함 (평범한 19 개 + 1 위 상품, 만든 경우) | 114,842 | 45 ms | 20 ms |
| 인기 상위 20 개 (실제 페이지가 아니라 전체 상위 20 개를 모아 만든 최악의 경우) | 503,554 | **7,429 ms** | **87 ms** |

`(product_id)` 에는 `user_id` 가 없어 `liked` 를 위해 50 만 행의 본 행을 읽었고, 옵티마이저는 `GROUP BY` 순서를 맞추려 인덱스 전체(491 만)를 훑었다.
`(product_id, user_id)` 에서는 20 개 상품의 범위만 커버링으로 읽는다. 남은 87 ms 는 50 만 개를 세는 비용이고 인덱스로는 줄지 않는다(3.2 의 카운터 몫).

**고른 것: `(product_id)` 를 `(product_id, user_id)` 로 교체한다.** 같은 열로 시작하므로 기존 쓰임을 모두 대신하고, 인덱스 수가 늘지 않아 좋아요 쓰기 비용이 그대로다.
**대가**: 인덱스가 넓어져(160 MB) 많이 세는 경로가 느려진다 — 같은 시점에 번갈아 잰 인기순 L2 가 355 · 362 → 385 · 412 ms(약 10%).
가격순(21 개만 셈)은 차이가 없었다. 인기순은 3.2 의 카운터로 풀 경로라 이 손실을 받아들인다.
**뒤집을 조건**: 카운터를 도입해 목록과 인기순이 더 이상 좋아요를 세지 않으면, `liked` 는 `(user_id, product_id)` 유니크 인덱스로 충분하므로 `(product_id)` 로 되돌릴 수 있는지 본다.

## 4. 목록 캐시

### 4.1 무엇을 캐시하나

| 값 | 캐시 | 이유 |
|---|---|---|
| 상품 id · 이름 · 가격 · 품절 · 브랜드 id · 이름, 페이지 순서, `hasNext` | 담는다 | 관리자의 등록 · 수정 · 삭제와 품절 전환에만 바뀐다. 드물게 바뀌어 지우고 다시 채우는 비용이 작다 |
| 좋아요 수 | **담지 않는다** | 가장 잦은 쓰기다. 담으면 좋아요마다 무효화해야 하고, 요청이 몰리는 인기 상품일수록 캐시가 비어 있다. TTL 로 옛 수를 허용하는 것은 "정상 변경 뒤 순차 조회는 최신" (`CACHE-006`) 을 어긴다 |
| `liked` | **담지 않는다** | 사용자마다 다르다(`CACHE-004`) |
| 재고 수량 | 담지 않는다 | 고객 응답에 없다(W2 Q-2). 재고 판단은 주문 확정이 DB 를 잠가 한다(`CACHE-009`) |

좋아요 수와 `liked` 는 hit · miss 모두 마지막에 한 쿼리로 붙인다 — 20 개 상품에 대해 좋아요 수(`(product_id, user_id)` 커버링, 3.3) 와
`liked`(`(user_id, product_id)` 유니크)를 구하고, **살아 있는 상품만** 돌려준다. 캐시에 남은 상품이 그사이 삭제됐으면 여기서 빠진다(`CACHE-008`).

### 4.2 어느 요청을 캐시하나

**가격순 · 최신순의 첫 페이지(크기 20) 만, 브랜드별과 전체 목록.** 인기순 · 다음 페이지 · 다른 크기는 원본으로 간다.

| 고를 수 있는 것 | 키 수 | 쓰기 하나가 무효화할 키 | |
|---|---|---|---|
| 모든 페이지 | 브랜드 × 정렬 × 페이지 × 크기 | 그 브랜드와 전체 목록의 모든 페이지 — 몇 개인지 모른다 | 가격 하나가 바뀌면 순서가 밀려 페이지 경계가 모두 바뀐다 |
| 순서(id 목록) · 내용(상품별) 분리 | 순서 키 + 상품 키 | 이름 · 품절은 상품 키 하나, 가격은 그 브랜드의 가격순 순서까지 | hit 에 Redis 왕복이 둘 |
| **첫 페이지만** | 브랜드당 2 + 전체 2 | **최대 4 개** | 깊은 페이지는 재사용이 적어 담아도 hit 가 드물다 |

**전제(정함)**: 요청이 첫 페이지에 몰린다. 실제 분포 자료가 없다.
**뒤집을 조건**: 다음 페이지의 요청 비중이 크게 측정되면 담는 페이지를 늘린다. 그때 무효화 범위가 페이지 수만큼 커지므로 순서 · 내용 분리를 함께 본다.

인기순을 담지 않는 이유: 순서 자체가 좋아요 수라 좋아요마다 무효화해야 한다. 큰 브랜드의 인기순 비용은 캐시가 아니라 카운터 비정규화가 푼다(3.2).

### 4.3 키와 세대 번호

| 키 | 값 |
|---|---|
| `product:list:v1:gen:brand={id\|all}` | 그 범위의 세대 번호. 없으면 0 |
| `product:list:v1:brand={id\|all}:sort={정렬}:gen={세대}` | 첫 페이지의 공용 내용(JSON), TTL 60 초 |

**읽는 순서**: 세대를 읽는다 → 그 세대의 키를 찾는다 → 없으면 DB 에서 읽어 **처음 읽은 세대의 키에** 저장한다.
세대를 DB 보다 먼저 읽으므로, 읽는 동안 변경이 커밋되어 세대가 올라가면 늦게 끝난 요청은 옛 세대의 키에 쓴다. 새 세대를 보는 요청은 그 키를 읽지 않는다 — **늦은 채움이 구조로 막힌다.**

세대는 키를 지우는 대신 쓰는 이유: 지우기는 "읽는 중에 지우고, 그 뒤에 옛 값을 쓴다" 를 막지 못한다.

**연결**: 읽기 · 쓰기 모두 master 연결이다. 세대를 replica 에서 읽으면 복제 지연 동안 옛 세대를 봐 늦은 채움 방지가 깨진다(`CACHE-013`).
**Redis 오류**: 세대를 읽지 못하면 캐시를 건너뛰고 원본으로 간다. 읽기 · 쓰기 오류는 경고만 남기고 원본 결과를 돌려준다(`CACHE-010`).

### 4.4 어디에 두나

cache-aside 와 좋아요 붙이기는 `ProductFacade.findPage`(응용 계층)에, Redis 는 `RedisProductListingCache`(infrastructure)에 있다.
"첫 페이지만 · 좋아요는 원본에서 · 삭제 상품 재확인" 은 이번 주에 정한 판단이라, Redis 코드 안이 아니라 응용 계층에 드러나게 둔다.
응용 계층은 캐시를 `ProductListingCache` 포트로만 안다.

**SQL 수**: 캐시를 거치지 않는 요청 1 개, hit 1 개(좋아요 붙이기), miss 2 개(공용 목록 + 좋아요 붙이기). W2 `PRODUCT-008` 을 고쳤다.

### 4.5 확인한 것 (읽기 경로)

`ProductCacheE2ETest` — 실제 MySQL · Redis 컨테이너, 가짜 객체 없음.

| 장면 | 결과 |
|---|---|
| 같은 요청의 miss 와 hit | 응답이 같고, 페이지 키 1 개가 생긴다 |
| hit 가 실제로 캐시에서 나오나 | 첫 요청 뒤 앱을 거치지 않고 DB 의 가격을 바꿔도 다음 응답은 옛 가격 — 원본을 다시 읽지 않았다 |
| 다른 사람이 채운 캐시 | 각자의 `liked` 만 보인다 |
| hit 에서 좋아요 | 가격은 캐시의 값, 좋아요 수는 즉시 반영 |
| 캐시하지 않는 요청 | 인기순 · 2 페이지 · 크기 10 은 키를 만들지 않는다 |
| 캐시에 남은 상품이 삭제됨 | hit 에서도 보이지 않는다 |

### 4.6 무효화

**목록을 바꾸는 쓰기는 커밋 뒤에 그 브랜드와 전체 목록의 세대를 올린다.** 쓰기 하나에 세대 키 둘(`INCR`)이다.

| 쓰기 | 이벤트를 내는 곳 | 조건 |
|---|---|---|
| 상품 등록 · 수정 · 삭제 | `ProductService` | 항상 |
| 재고 조정 | `ProductService.adjustStock` | **품절 여부가 뒤집힐 때만**(0 → 양수, 양수 → 0) |
| 주문 확정의 재고 차감 | `ProductService.deductStock` | **차감 뒤 0 일 때만**. 확정마다 올리면 판매가 잦은 브랜드의 캐시가 늘 빈다 |
| 브랜드 수정 · 일괄 삭제 | `BrandService` | 항상 |
| 좋아요 | — | 목록 캐시에 좋아요가 없다(4.1) |

**어떻게**: 도메인 서비스가 `ProductListingChanged(brandId)` 를 내고, 응용 계층의 `ProductListingInvalidation` 이 `@TransactionalEventListener(AFTER_COMMIT)` 으로 받아 포트의 `invalidate` 를 부른다.

| 고를 수 있는 것 | 대가 |
|---|---|
| **도메인 서비스가 이벤트 · 응용 계층이 커밋 뒤 처리** (지금) | 도메인이 `ApplicationEventPublisher`(spring-context) 를 안다. ArchUnit 이 막는 것은 spring-tx · JPA · Spring Data · 웹이라 규칙 안이다. "커밋 뒤" 라는 트랜잭션의 의미는 응용 계층에만 있다 |
| Facade 가 직접 무효화 | 품절이 뒤집혔는지는 도메인만 안다 — Facade 가 알려면 서비스가 그 사실을 돌려줘야 하고, 주문 확정은 `OrderConfirmation` 을 거쳐 품목마다 돌려줘야 한다 |
| 트랜잭션 안에서 바로 무효화 | rollback 되어도 세대가 올라 있다. 해는 없지만(다음 요청이 miss 일 뿐) **커밋 전에 지우면 그 사이 옛 DB 를 읽은 요청이 새 세대의 키를 옛 값으로 채운다** |

이벤트가 트랜잭션 밖에서 나오면(테스트에서 서비스를 바로 부를 때) `@TransactionalEventListener` 는 아무 일도 하지 않는다. 운영의 쓰기는 모두 Facade 의 트랜잭션 안이다.

**무효화가 실패하면**: 커밋은 이미 끝났으므로 응답을 실패로 바꾸지 않는다. 경고만 남기고, 옛 키는 TTL(60 초)에 사라진다 — 그동안 이름 · 가격 · 품절 표시 · 순서가 옛 값이다(Q-5).
삭제된 상품은 꺼낼 때 다시 걸러 이 동안에도 보이지 않는다(`CACHE-008`).

**확인한 것** (`ProductCacheE2ETest`):

| 장면 | 결과 |
|---|---|
| 관리자 가격 수정 커밋 뒤 재조회 | 브랜드 목록과 전체 목록 모두 새 가격 · 바뀐 순서 |
| 상품 등록 | 다음 조회에 나온다 |
| 상품 삭제 · 브랜드 일괄 삭제 | 세대가 오른다(화면만 보면 꺼낼 때의 재확인이 가려 구분되지 않아 세대를 본다) · 전체 목록에서 빠진다 |
| 브랜드 이름 수정 | 다음 조회에 새 이름 |
| 재고 0 → 5 · 5 → 3 | 앞은 품절이 풀리고, 뒤는 세대가 그대로다 |
| 주문 확정이 마지막 재고를 팖 | 다음 조회에서 품절 |
| rollback | 세대가 그대로이고 캐시는 변경 전 가격 |
