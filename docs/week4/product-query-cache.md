# 상품 목록 첫 페이지 캐시 측정

`cache-design.md` 의 캐시를 붙인 뒤의 측정이다. 비교 대상(DB 만)은 `product-query-brand-index.md` 의 "후" 값이다(같은 실험 코드 · 같은 seed, 다른 실행).

- 실험 코드: `ProductQueryExperiment` (`RUN_EXPERIMENT=true`)
- 실행일: 2026-10-16, MySQL 8.0 · Redis 7.0 단일 노드 Testcontainers, **한 번 실행한 결과**
- 결과: 아홉 장면 모두 miss · hit 응답이 seed 규칙으로 계산한 기대 결과와 일치. hit 의 SQL 은 모든 장면에서 0개

## 1. 측정 방법

| 구분 | 방법 |
|---|---|
| hit | 같은 요청을 반복. 준비 50회 뒤 200회 |
| miss | 요청마다 그 범위의 버전을 올려 캐시를 버림. **버전을 올리는 시간은 측정에서 뺌.** 준비 50회 뒤 200회 |
| Redis 무응답 | 실험 전용 Redis 컨테이너를 일시정지한 상태에서 요청. 요청마다 대기 한도(100ms)를 기다려 표본을 줄임(준비 5회 뒤 50회). 큰 브랜드를 더한 뒤(상품 3만 개)에 재므로, 같은 상태 · 같은 표본 수로 Redis 정상 때의 miss 를 바로 앞에 재서 비교 |

miss 한 번에는 버전 읽기(master) · 데이터 읽기 · DB 조회(SQL 2개) · 저장이 들어 있다.

## 3. 관찰

1. **hit 는 장면과 관계없이 약 1ms다.** 원본 비용이 클수록 효과가 크다. 전체 · likes_desc 약 24ms → 약 1ms, 큰 브랜드 약 23ms → 약 1ms.
2. **miss 는 DB 만 읽을 때와 차이가 측정 오차 수준이다.** 버전 읽기 · 데이터 읽기 · 저장으로 Redis 왕복이 셋 늘지만, 이번 실행에서는 DB 쪽 흔들림보다 작았다. 장면에 따라 miss 가 DB 만보다 조금 빠르게 나온 것은 서로 다른 실행의 차이로 보고 해석하지 않는다.
3. **Redis 가 응답하지 않으면 요청마다 약 108~110ms 가 늘어난다. 원본 비용과 관계없이 일정하다.**
   - 같은 데이터 상태에서 정상 miss 와 비교한 차이다. 대기 한도 100ms와 약 8~10ms의 고정 비용으로 이루어진다. 고정 비용은 timeout 예외 생성, 스택 트레이스를 포함한 경고 로그, Lettuce 의 timeout 타이머 처리로 추정한다(나눠 재지 않음).
   - 처음 측정에서 전체 · likes_desc 의 "원인 모를 35ms" 는 **비교 기준을 잘못 잡은 것**이었다. 무응답 장면은 큰 브랜드를 더한 뒤라 상품이 3만 개였다. 이 상태의 전체 · likes_desc 원본은 약 24ms(1만 개)가 아니라 약 52ms였다.
   - 대기 한도가 없었다면(Lettuce 기본 60초) 요청이 그만큼 멈췄을 것이다.
   - 무응답 동안 모든 목록 요청이 DB 로 간다. 이번 측정은 한 스레드의 통제된 부하라 DB 부하 증가는 재지 않았다.
4. **상세 측정의 해석을 고친다.** `product-query-detail.md` 에서는 상세 p50 약 2.8ms를 "대부분 DB 밖 비용"이라고 봤다. 그런데 DB 를 거치지 않는 목록 hit 가 약 1ms였다. 그러므로 상세 2.8ms 중 약 1.5~2ms는 **SQL 실행 시간이 아니라 커넥션 획득 · 트랜잭션 · DB 왕복 비용**으로 봐야 한다. `EXPLAIN ANALYZE` 의 실행 시간(거의 0)에는 이 비용이 보이지 않는다. 상세에 캐시를 붙이면 약 2.8ms → 약 1ms 수준의 이득이 있었을 것으로 추정한다(미측정). 다만 절대값으로 2ms 미만이라, 목록을 고른 판단(`cache-design.md` 1절)은 바꾸지 않는다.

## 4. 판단

- 목록 첫 페이지 캐시는 원본 비용이 큰 장면(전체 · 큰 브랜드)에서 p50 을 약 20배 이상 줄였다. 원본이 작은 장면(브랜드 7)에서도 약 5ms → 약 1ms다.
- 대가는 다음과 같다.
  - **무효화 책임:** 6개 쓰기 경로(`cache-design.md` 3.3)
  - **허용 신선도:** 좋아요 수는 TTL 60초까지 오래된 값 허용, 장애 시 품절 표시가 재처리까지 늦을 수 있음
  - **Redis 무응답 때의 지연:** 요청마다 약 100ms 추가
- DB 쿼리 개선만으로 충분했는가: DB 만으로도 모든 장면이 p50 25ms 이하였다. **캐시가 없어도 응답 시간 목표를 크게 넘지는 않았을 것**이다. 캐시의 이득은 응답 시간보다 **반복 요청이 DB 에 주는 부하를 덜어 주는 쪽**에 있다고 본다. 부하 측정은 하지 않았다.

## 5. 한계

- 한 번 실행한 결과이며, 동시 요청이 없는 상태의 지연이다. DB 부하 · 커넥션 풀에 대한 효과는 재지 않았다.
- hit 율은 재지 않았다. 실서비스의 요청 분포가 없다.
- Redis 는 단일 노드라 replica 지연, 네트워크 왕복이 있는 원격 Redis 의 hit 지연은 재지 않았다.
- Redis 무응답은 일시정지(timeout)만 재현했다. 연결 거부처럼 즉시 실패하는 장애는 재지 않았다.
- 무응답 비교용 정상 miss(전체 · likes_desc)는 p99 · 최대가 약 650ms로 튀었다. 큰 seed 직후 버퍼 풀이 덜 데워졌고 준비 요청이 5회뿐이라 p50 만 비교에 쓴다.
