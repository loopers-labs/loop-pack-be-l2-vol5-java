# TTL 5·30·60초와 캐시 키·메모리 비교

2026-10-16 사용자 요청에 따른 **측정 기록**이다. 실제 적용 TTL 60초·캐시 방식·조회 계약·트랜잭션·락은 변경하지 않았다. W4-CACHE-12 중 남아 있던 TTL 다중 주기와 키 수/메모리 비교를 완료했다. 실행 전 고정한 조건·실측 결과와 이후 사용자 승인으로 확정한 선택을 구분해 기록한다. 전체 증분의 현재 상태는 [완료 체크리스트](../week2/commerce-completion-checklist.md#최신-통합-검사)를 따른다.

## 메모리 수치의 의미

- `STRLEN` 합계는 저장된 JSON 문자열의 바이트 수다.
- `MEMORY USAGE` 합계는 관찰된 키·값과 관련 할당 비용을 포함한다. Redis 서버의 기본 메모리 전체를 TTL별 캐시 비용으로 나누지 않는다. [Redis MEMORY USAGE](https://redis.io/docs/latest/commands/memory-usage/)
- `INFO memory`의 `used_memory`, `used_memory_dataset`, `used_memory_rss`는 **세 namespace가 함께 있는 Redis 프로세스 전체**의 참고값이다. 키가 만료되어도 메모리 할당자가 OS에 즉시 반환하지 않을 수 있으므로 RSS 감소와 키 만료를 혼동하지 않는다. `maxmemory`와 `evicted_keys`도 확인한다. [Redis INFO](https://redis.io/docs/latest/commands/info/)
- SCAN부터 각 키의 측정까지는 원자적인 스냅샷이 아니다. 중복과 도중 만료를 처리하며 최대값은 **표본 중 최대**다. 관찰 명령이 만료된 키 정리에 영향을 줄 수 있고 전체 관찰 소요시간을 별도로 기록한다. [Redis SCAN](https://redis.io/docs/latest/commands/scan/)

## 실행과 변경 범위

신규 측정은 실제 TTL 여러 주기를 기다리므로 일반 회귀에서 별도 태그 `ttl-measurement`로 분리한다. 기존 테스트의 실행·기대값은 제거하지 않는다. 전용 실행과 일반 회귀의 결과는 합쳐서 한 번의 전체 검사라고 표현하지 않는다.

테스트용 메모리 관찰 도구·단위 테스트, 실제 앱 측정 하네스, Gradle의 전용 테스트 실행과 본 기록만 추가했다. 측정 직후에는 60초 유지 제안으로 남겼고, 이후 2026-10-16 사용자 승인으로 이번 과제의 선택을 확정했다. 기존 설정을 유지하는 결정이므로 적용 설정 변경은 없다.

### 적중률과 재계산

각 셀은 **hit / 전체 요청 (적중률), 집계 SQL 재실행 횟수**다. miss마다 집계 1회, 전체 SELECT 5회이며 hit는 버전 SELECT 1회였다. single-flight의 재확인 GET 때문에 발생한 miss 카운터 2회를 요청 2건으로 계산하지 않았다.

| TTL | 변경 없는 지속 조회 | 변경 없는 드문 조회 | 좋아요 초당 약 2회 변경 |
| --- | --- | --- | --- |
| 5초 | 1,911 / 1,950 (98.00%), 39회 | 0 / 9 (0%), 9회 | 1,560 / 1,950 (80%), 390회 |
| 30초 | 1,943 / 1,950 (99.64%), 7회 | 4 / 9 (44.44%), 5회 | 1,560 / 1,950 (80%), 390회 |
| 60초 | 1,946 / 1,950 (99.79%), 4회 | 6 / 9 (66.67%), 3회 | 1,560 / 1,950 (80%), 390회 |

지속/드문 조회의 miss는 각 장면 최초 채움 1회와 같은 버전의 자연 만료였다. 변경 장면의 miss는 각 TTL에서 최초 채움 1회와 버전 전환 389회였다. **버전이 0.5초마다 바뀌면 세 TTL 모두 다음 버전에 다시 계산하므로, TTL을 늘려도 이 miss는 줄지 않았다.** 세 장면을 임의 비중으로 합쳐 운영 적중률로 표시하지 않는다.

전체 SELECT는 지속 조회에서 2,106 / 1,978 / 1,966회, 드문 조회에서 45 / 29 / 21회, 변경 조회에서 각각 3,510회였다(5 / 30 / 60초 순서).

### HTTP 시간과 실제 진행 속도

단위는 ms이며 `p50 / p95`다. 사전 준비는 제외하되 각 장면 최초 miss와 실제 재계산은 포함했다.

| TTL | 지속 조회 | 변경 조회 |
| --- | --- | --- |
| 5초 | 8.32 / 12.83 | 4.95 / 36.53 |
| 30초 | 8.16 / 12.25 | 4.72 / 37.63 |
| 60초 | 8.18 / 12.01 | 4.87 / 37.50 |

30초와 60초의 지속 조회 차이는 추가 hit **3건 / 1,950건(약 0.154%p)**다. 큰 지연 개선으로 해석하지 않는다. 변경 조회의 지연도 TTL만으로 개선됐다고 볼 근거가 없다. 서로 다른 시점에 실행한 지속/변경 장면 사이의 지연 차이를 TTL 효과로 해석하지 않는다. 드문 조회는 조건당 9건뿐이므로 원시 시간은 보존하되 p95를 운영 지연 근거로 제시하지 않는다.

지속 조회는 195.064초에 TTL별 9.997회/초, 변경 조회는 195.358초에 TTL별 9.982회/초·쓰기 1.996회/초였다. 목표 속도에 근접했지만 정확한 등간격 실행은 아니다. 변경 조회의 예정 시각 대비 지연 p95는 약 136~139ms, 최대 약 428ms였다. HTTP 시간에는 대기 중인 스케줄 지연·부모의 증거 수집·메모리 관찰·보고서 쓰기를 포함하지 않는다. 따라서 이 수치를 부하 한계나 사용자 대기 전체 시간으로 주장하지 않는다.

### 키 수와 메모리

아래는 **변경 장면의 5초 간격 관측 최대값**이다. 첫 페이지 한 종류·이번 payload·초당 약 2개의 새 버전 캐시 채움 조건에 한정된다. `KiB = 1,024 bytes`다.

| TTL | 전체 키 최대 | 현재 / 옛 버전 키(최대 표본) | 키 할당 메모리 합계 최대 | JSON payload 합계 최대 |
| --- | ---: | --- | ---: | ---: |
| 5초 | 10 | 1 / 9 | 31,920 B (31.17 KiB) | 28,290 B |
| 30초 | 60 | 1 / 59 | 191,520 B (187.03 KiB) | 169,740 B |
| 60초 | 120 | 1 / 119 | 383,040 B (374.06 KiB) | 339,480 B |

변경이 없는 두 장면은 TTL별 최대 1키·3,192 B였다. 변경 장면은 키 하나당 같은 3,192 B였고, 실제 JSON은 버전 숫자 길이를 포함해 2,827~2,829 B였다. 60초는 30초보다 약 **187.03 KiB**를 더 보관했지만 이 장면의 추가 hit는 0건이었다.

이 구조에서 보유 키 수는 대략 `초당 캐시가 채워진 새 버전 수 × TTL`에 비례한다. 모든 쓰기마다 반드시 캐시가 채워지는 것은 아니며, 좋아요 외에도 같은 목록 버전을 올리는 상품·브랜드·재고 등의 변경이 영향을 준다. 이번 수치를 운영 메모리 상한으로 일반화하지 않는다.

세 namespace를 함께 담은 Redis 프로세스의 장면 중 `used_memory`는 1,259,504~1,954,088 B, `used_memory_dataset`은 248,512~877,320 B, RSS는 15,343,616~15,736,832 B였다. 이 값에는 Redis 기본 비용과 연결 등이 섞여 있으므로 TTL별 캐시 메모리로 나누지 않는다. `maxmemory=0`이고 eviction 0이어서 메모리 제한 하의 퇴거 성능을 검증한 실험도 아니다. 한 namespace 관찰 소요시간의 최대는 5/30/60초에서 약 51/97/155ms였으며, 관찰 비용도 일정 지연에 영향을 주었다.

### 요청 중단 후 자연 만료

모든 HTTP를 중단한 뒤 DEL·외부 SET 없이 관찰했다. 종료 직후 표본은 이미 일부 키가 만료된 시점이므로 위 최대값과 다르다.

| 중단 후 관찰 시점 | 5초 TTL 키 | 30초 TTL 키 | 60초 TTL 키 |
| --- | ---: | ---: | ---: |
| 0초 | 9 | 59 | 118 |
| 5초 | 0 | 49 | 109 |
| 30초 | 0 | 0 | 59 |
| 61초 | 0 | 0 | 0 |

61초에는 세 namespace의 키 할당 메모리 합계도 0 B였다. Redis RSS는 15,736,832 B로 유지됐다. **키가 만료됐다는 사실과 프로세스가 OS에 메모리를 반환했다는 사실은 다르다.** 최종 DB는 상품 10,000개·좋아요 46,955개·버전 390·alice의 대상 좋아요 0개로 별도 확인했고, 실험 앱 JVM 세 개도 정상 종료했다.

## 확정한 선택과 운영 확인

**2026-10-16 사용자 승인으로 이번 과제에서는 TTL 60초 유지를 선택했다.** 브랜드 필터 없는 좋아요순 첫 페이지(`page=0,size=20`)의 Redis + DB 버전 캐시를 유지하며, 서버 시작 워밍은 도입하지 않고 요청 시 채운다. 이는 미완료 필수 작업이 아니라 선택한 구현 범위다. [정책 결정](../week2/commerce-policy-decisions.md#w4-캐시-설계의-선택과-미정-질문)을 따르며, 운영 최적값을 입증했다는 뜻은 아니다. 실제 적용 설정은 바꾸지 않았다.

| 선택 | 이번 근거·트레이드오프 |
| --- | --- |
| 60초 유지 선택 | 변경 없는 지속/드문 조회에서 재계산이 가장 적어 기존 설정을 유지한다. 이번 한 종류의 첫 페이지에서 30초 대비 추가 키 메모리 약 187 KiB를 쓰는 비용을 수용했다. 다만 지속 조회 이득은 작고 운영 최적값은 아니다. |
| 30초로 단축하는 대안 | 변경이 빈번한 구간에서는 같은 hit율로 옛 키 메모리를 절반으로 줄였다. 반대로 선택한 드문 조회에서는 60초보다 재계산이 2회 늘었다. 실제 변경 빈도가 높거나 메모리 제약이 커지면 검토할 수 있다. |
| 5초로 단축하는 대안 | 변경 장면의 옛 키 보유량은 가장 작았다. 그러나 이번 드문 조회에서는 재사용이 0회였고 지속 조회도 재계산이 가장 많았다. 현재 근거만으로 우선 선택하지 않는다. |

짧은 TTL은 **버전 변경으로 생기는 miss를 해결하는 방법이 아니라 옛 버전 메모리를 줄이는 방법**이다. TTL은 허용할 오래된 표시 시간을 뜻하지 않는다. 변경 완료 뒤 새 요청의 최신성은 기존 DB 버전 계약으로 유지한다.

운영 환경에서 선택을 재검토하려면 실제 홈 요청의 대상 비율·방문 간격·모든 영향 쓰기의 빈도·서버 수·메모리 예산이 필요하다. 이 미확인 항목 때문에 이번 과제의 TTL 선택을 보류하지 않는다. 서버 시작 워밍은 추가 효과와 기동 비용이 검증되지 않아 이번에는 미도입을 선택했고, 다른 페이지 캐시·주기적 순위 갱신도 이번 범위에 추가하지 않는다.

첫 전용 실행은 실제 DTO 동등성 검사에는 통과했으나 JSON 객체 필드 순서까지 해시에 반영한 **측정 도구 오류**로 첫 조회에서 실패했다. [실패 기록](evidence/product-list-cache-ttl-hash-failure-2026-10-16.json)을 보존했다. 객체 필드만 재귀 정렬하고 배열 순서·전체 DTO·SQL 기대값은 유지한 뒤 전체 실험을 처음부터 다시 실행했다. 실패 표본은 위 정상 완료 통계에 섞지 않았다.

일반 742개 회귀와 전용 장시간 측정 1개는 서로 다른 실행이다. 이를 한 번의 전체 `check`에서 743개가 통과한 것으로 표시하지 않는다. 이번 실측 완료는 운영 최적값 확정이나 과제 제출 완료를 뜻하지 않는다.
