# 인기순: 목록 캐시와 상품 캐시 나누기 (시도 후 되돌림)

> 이 구조는 구현하고 측정한 뒤 되돌렸다. hit에서 DB 일이 줄지 않았고, 공유로 이득을 낼 가격순 목록은 캐시하지 않기로 했기 때문이다. 현재 코드에는 상품 캐시가 없다. 아래는 시도한 구조와 측정 기록이다([ADR 0027](../adr/0027-popular-product-cache.md)).

목록 캐시에는 상품 ID(순서)만 두고, 상품 정보는 상품 ID로 상품 캐시에서 다시 읽는다. 상품 캐시는 상품마다 키가 하나라 여러 목록과 화면이 같은 키를 쓴다. 그래서 상품 캐시의 히트율이 올라간다.

인기순은 이미 목록에 ID만 저장하고 있어 이 구조와 가장 가깝다. hit에서 상품 정보를 DB에서 다시 읽던 부분을 상품 캐시로 바꿨다. 가격순은 바꾸지 않았다.

## Redis에 저장하는 것

```text
목록 캐시 (TTL 60초, 브랜드마다 1개)
  popular:brand:7  →  [9207, 407, 707, ... 20개 ID]          ← 순서만

상품 캐시 (TTL 300초, 상품마다 1개)
  product:9207  →  {id, brandId, name, price, createdAt}
  product:407   →  {id, brandId, name, price, createdAt}
  ...
```

좋아요 수와 하트(내가 좋아요를 눌렀는지)는 어느 캐시에도 저장하지 않는다. 재고와 삭제 여부도 저장하지 않는다. 실제 키 앞에는 환경별 prefix가 붙는다(`commerce:popular-page:v1:benchmark`, `commerce:product:v1:benchmark` 등).

## 조회 흐름

### 예시 1: 목록 캐시와 상품 캐시가 모두 hit (평소 대부분의 요청)

```text
GET /api/v1/products?brandId=7&sort=popular   (X-USER-ID: 95)

① Redis  목록 캐시 GET popular:brand:7
         → [9207, 407, 707, ...] hit

② DB     20개가 아직 살아 있는지 확인
         SELECT id FROM product WHERE brand_id=7 AND id IN (20개) AND deleted_at IS NULL
         → 20개 모두 있음                       ← 삭제 상품은 캐시에 맡기지 않고 DB로 확인

③ Redis  상품 캐시 MGET product:9207, product:407, ... (20개를 한 번에)
         → 20개 모두 있음                       ← 이름·가격은 DB에서 읽지 않음

④ DB     좋아요 수 20개 (카운터)               ← 항상 현재 값
⑤ DB     사용자 95의 하트 20개                 ← 사용자마다 다름

⑥ 응답: 순서는 ①, 이름·가격은 ③, 좋아요 수는 ④, 하트는 ⑤
```

### 예시 2: 목록은 hit, 상품 캐시는 일부 miss

상품 407의 가격이 방금 바뀌어 `product:407` 키가 지워진 상태다.

```text
① 목록 캐시 hit → [9207, 407, 707, ...]
② DB 활성 확인 → 20개 모두 있음
③ 상품 캐시 MGET → 19개 hit, 407만 없음
   └→ DB    SELECT * FROM product WHERE id IN (407)     ← 없는 상품만 DB에서 읽음
   └→ Redis SET product:407 (새 가격, TTL 300초)         ← 다음 요청부터 hit
④⑤ 좋아요 수, 하트 → DB
⑥ 응답: 407은 바뀐 가격으로 보인다
```

### 예시 3: 목록 캐시 miss (60초가 지났거나 상품이 추가·삭제됨)

```text
① 목록 캐시 GET → 없음
② DB  순위 계산: 브랜드 7의 활성 상품과 카운터를 정렬해 ID 20개만 받음   ← 비싼 일
③ 상품 캐시 MGET 20개 → 있는 것은 그대로, 없는 것만 DB에서 읽고 SET
④⑤ 좋아요 수, 하트 → DB
⑥ Redis SET popular:brand:7 = [새 순위 20개] (TTL 60초)
⑦ 응답
```

순위는 다시 계산해도, 상품 정보는 상품 캐시에 남아 있으면 그대로 쓴다.

## 변경이 일어날 때

```text
관리자가 상품 407 가격 수정
  → DB 수정 commit
  → commit 뒤 DEL product:407          ← 그 상품 키 하나만
  → 목록 캐시(순서)는 그대로 둠        ← 순서는 60초 지연 허용

좋아요 등록·취소
  → DB 관계 + 카운터 갱신
  → 캐시를 지우지 않음                 ← 좋아요 수는 매번 DB에서 읽음

상품 삭제
  → DEL popular:brand:7 + DEL product:{id}
  → 키 삭제가 실패해도 ② 활성 확인에서 빠짐
```

각 항목을 얼마나 늦게 반영해도 되는지는 [design.md의 캐시별 최신성 표](design.md#cache-freshness)에 정리했다. 상품 캐시의 이름·가격은 정상일 때 지연 없이 반영하고, 키 삭제 실패·늦은 채움에서만 최대 300초 옛 값이 남을 수 있다.

## 기존 인기순 hit와 바뀐 점

|            | 기존 인기순 hit                              | 상품 캐시를 켠 hit     |
| ---------- | -------------------------------------------- | ---------------------- |
| 삭제 확인  | DB에서 상품 20개의 **전체 행**을 읽으며 확인 | DB에서 **ID만** 확인   |
| 이름·가격  | 그 전체 행에서 사용                          | **상품 캐시**에서      |
| Redis 왕복 | 1번 (목록)                                   | 2번 (목록 + 상품 MGET) |

DB로 가는 문장 수는 같다. 상품을 읽는 문장이 "20개 전체 행 읽기"에서 "ID만 확인"으로 바뀐다. 이 차이가 실제로 DB 일을 줄이는지는 아래에서 쟀다. 상품 캐시는 상품마다 키가 하나라, 이후 가격순 목록이나 상세 화면이 같은 캐시를 쓰면 같은 키를 더 많이 재사용한다. 이번에는 인기순만 바꿨으므로 그 공유 효과는 측정하지 않았다.

## 측정: 상품 캐시를 끈 경우와 켠 경우

같은 JAR(SHA-256 앞 16자리 `af4b4432c6e09653`)·같은 실행기로 상품 캐시만 끄고 켜서 비교했다. 데이터·요청·반복·지표 조건은 [캐시가 덜어 주는 DB 일](cache-db-work.md)과 같다. 브랜드 7·첫 20개·`X-USER-ID: 95`, 순차 요청, 990개는 준비 100·측정 200회, 87,390개는 준비 10·측정 50회, 앱 실행 순서를 바꿔 3회다. hit는 목록 키와 상품 키가 모두 찬 상태, miss는 조회마다 목록 키만 지운 상태다(상품 키는 남아 있다).

### 요청 하나의 DB 작업

| 브랜드 7 | 경우 | 상품 캐시 끔: SELECT / 읽은 행 / DB / API | 상품 캐시 켬: SELECT / 읽은 행 / DB / API |
| ---: | --- | --- | --- |
| 990개 | hit | 5 / 56 / 1.04~1.24ms / 10.3~11.1ms | 5 / 56 / 1.13~1.18ms / 10.8~11.0ms |
| 990개 | miss | 6 / 2,056 / 2.77~2.93ms / 13.8~14.0ms | **5** / 2,036 / 2.55~2.70ms / 12.9~13.4ms |
| 87,390개 | hit | 5 / 56 / 1.11~1.16ms / 12.8~13.2ms | 5 / 56 / 1.21~1.26ms / 13.3~13.8ms |
| 87,390개 | miss | 6 / 174,856 / 77.1~77.7ms / 90.8~92.4ms | **5** / 174,836 / 76.7~77.1ms / 89.1~90.2ms |

### 바뀐 문장만 보면

| 경우 | 상품 캐시 끔 | 상품 캐시 켬 |
| --- | --- | --- |
| hit | 상품 20개 전체 행 조회: 20행 · 0.22ms | 상품 20개 활성 ID 확인: 20행 · 0.27~0.32ms |
| miss | 순위 계산 + 상품 20개 전체 행 조회(20행 · 0.20~0.26ms) | 순위 계산만. 상품 정보는 상품 캐시에서 |

### 해석

- **hit에서는 DB 일이 줄지 않았다.** 상품 캐시를 켜도 삭제 상품을 숨기려고 ID 확인 문장이 남는다. 이 문장은 브랜드 인덱스만 읽는 커버링 조회로 SQL 실행은 약 0.05ms, 기존 전체 행 조회도 PK로 20행을 읽어 약 0.11ms다(EXPLAIN ANALYZE). `performance_schema`로 잰 MySQL 문장 실행 시간은 두 문장 모두 0.2~0.3ms였고, 읽는 컬럼을 줄인 차이는 이 범위에서 드러나지 않았다. API 지연 개선도 확인하지 못했다(hit API 10.3~11.1ms → 10.8~11.0ms). 문장 실행 시간이 EXPLAIN ANALYZE보다 큰 이유와, 상품 캐시 MGET이 API 시간에서 차지한 몫은 따로 나눠 재지 않았다.
- **miss에서는 문장 하나가 빠졌다.** 순위를 다시 계산해도 상품 정보는 상품 캐시에 남아 있어 상품 조회 문장(약 0.2ms)이 사라졌다. 990개 브랜드에서 DB 약 0.2ms, API 약 1ms 줄었다. 87,390개 브랜드에서는 순위 계산(약 75ms)에 비해 작아 차이가 거의 보이지 않았다.
- 정리하면 이 구조의 이득은 **DB 문장을 없앨 수 있을 때** 생긴다. 인기순 hit는 삭제 확인 문장을 없앨 수 없어 이득이 없었고, miss는 상품 조회 문장을 없애 작은 이득이 있었다. 상품 정보가 넓은 행이거나, 여러 목록·상세가 같은 상품 키를 공유해 상품 조회 문장 자체가 사라지는 경로에서 효과가 커질 수 있다. 이 공유 효과는 아직 재지 않았다.


## 당시 설정과 코드 (되돌림)

- 설정: `commerce.cache.product.enabled`(local·benchmark 기본 true), `commerce.cache.product.ttl-seconds`(기본 300), `commerce.cache.product.prefix`. 상품 캐시는 인기순 캐시가 켜진 읽기 트랜잭션에서만 쓴다. 끄면 기존 인기순 hit와 같다.
- 코드: `ProductQueryService`의 인기순 경로, `ProductCache`·`CachedProduct`(domain), `RedisProductCache`(infrastructure, MGET), `ProductChanged`·`ProductCacheInvalidator`(commit 뒤 DEL).
- 테스트: `PopularProductCacheIntegrationTest` 5건 — hit에서 상품 정보를 DB 대신 캐시에서 읽는지, 수정 시 그 상품 키만 지우는지, 두 키 삭제가 모두 실패해도 삭제 상품이 보이지 않는지, 손상 값은 DB로 대신하고 다시 채우는지, 좋아요 수는 현재 값인지.

되돌릴 때 위 설정·코드·테스트를 모두 지웠다. 측정 실행기의 `--product-cache` 옵션은 당시 측정을 재현하는 방법으로 남겨 두었으며, 현재 코드에서는 설정이 없어 효과가 없다.
