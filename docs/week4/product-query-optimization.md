# W4 1단계: 상품 목록 SQL·인덱스 개선

이 문서는 2026-10-15 SQL·인덱스 개선 단계의 기록이다. 대상은 기존 `GET /api/v1/products`의 고객 가격순·최신순 조회이며, Controller·API 계약·업무 모델·변경 트랜잭션과 락은 유지했다. Redis와 로컬 캐시는 이 단계에 추가하지 않았다. [개선 전 기준선](product-query-baseline.md)의 동일 seed와 고정 요청으로 비교했다.

아래 수치와 후보 선택은 당시 기록으로 보존한다. 이후 무필터 최신순·가격순은 [페이지 한정 집계](global-list-query-optimization.md), 무필터 좋아요순은 [좁은 순위 집계](product-like-ranking-tdd-log.md)로 추가 개선했고, 선택한 좋아요순 첫 페이지의 [Redis 구현·검증](product-list-cache-tdd-log.md)도 진행했다. 현재 전체 상태는 [완료 체크리스트](../week2/commerce-completion-checklist.md)를 따른다.

## 테스트 우선 순서

1. 기존 조회에 페이지 경계를 넘는 동일 가격·생성 시각 상품 25개를 추가한다. 최신순·가격순 모두 ID 내림차순, 20개+5개+범위 밖 빈 페이지, 전체 개수·모든 응답 필드·좋아요 0/1/2의 정확한 매핑을 검사한다.
2. ID순으로 먼저 페이지를 선택하면 빠지는 오래된 상품에만 좋아요를 부여한다. `likes_desc`가 전체 후보의 좋아요 순위를 먼저 계산하는지 검사한다.
3. 10,000개 seed에서 고정 브랜드의 세 정렬·page 0~5, 무브랜드의 세 정렬 첫 페이지, 고정 브랜드 가격순의 size 1/20/100을 실제 HTTP로 검사한다. 페이지 크기 증가에 비례해 애플리케이션 SQL 수가 늘지 않아야 한다.
4. 생산 변경 전에 테스트를 실행한다. 기존 구현에서 통과하는 회귀를 억지로 실패시키지 않는다. 최적화는 이 Green을 유지하는 리팩터링으로 진행한다.
5. 쿼리만·인덱스만·둘을 조합한 후보의 실제 SQL·바인딩·실행 계획·동일 응답·반복 지연을 비교한다. 고정 밀리초나 향상 배수를 합격 조건으로 만들지 않는다.
6. 채택한 변경으로 상품·브랜드·좋아요·주문 관련 회귀, Checkstyle, ArchUnit과 필요 시 실제 수동 DDL 적용을 확인한다.

## 비교한 후보와 선택

- A: 기존 상품/좋아요 join·group 쿼리 + 기존 인덱스.
- B: A에 `(brand_id, deleted_at, price ASC, id DESC)` 인덱스만 추가.
- C: 고객 가격순·최신순의 projection에서 좋아요를 상관 count 서브쿼리로 조회하고 전체 like join·group 제거. 기존 인덱스 유지.
- D: C와 후보 인덱스 조합.

이 단계에서 좋아요순·관리자 목록·내 좋아요·상세 조회는 기존 집계 쿼리를 유지했다. C는 Hibernate HQL의 select 서브쿼리를 사용한다. 좋아요 0개는 count 0으로 반환하고 상품·브랜드·좋아요는 같은 목록 SQL에서 읽는다. 실제 DB가 서브쿼리를 몇 번 평가하는지는 실행 계획으로 확인하며, SQL 문법만으로 반환 20개에 한정된다고 가정하지 않는다.

페이지 상품과 좋아요 일괄 집계를 별도 SQL로 나누는 대안도 검토했다. 당시 고정 브랜드 요청에서 C가 충분한 개선을 보여 그 대안은 추가하지 않았다. 별도 SQL의 네트워크 왕복·ID 순서 복원·읽기 시점 조립을 늘리지 않기 위해서다. 무필터 요청에서 추가 병목을 확인한 뒤 적용한 분리 조회는 위의 페이지 한정 집계 기록과 구분한다.

**D를 채택했다.** 기존 Controller → application → domain 저장소 약속 → infrastructure 의존을 유지한다. 이 단계의 생산 Java 변경은 `ProductQueryRepositoryImpl` 한 파일이며, 인덱스는 [007 추가 SQL](../../apps/commerce-api/src/main/resources/db/schema/007-product-brand-price-index.sql)로 제공한다. 001~006과 기존 인덱스는 삭제·교체하지 않는다. 이 인덱스 증분은 기존 DB에 007만 별도로 적용하며, 후속 스키마를 포함한 현재 적용 순서는 [운영 안내](../week2/commerce-schema-operations.md)를 따른다.

이 단계에서는 읽기 서비스와 저장소의 `@Transactional(readOnly = true)`를 유지했다. 상품·브랜드·좋아요 값은 한 목록 SQL에서 읽고 기존 전체 개수 쿼리는 별도로 유지했으며, 새로운 DB 락·변경 트랜잭션·별도 좋아요 조회는 추가하지 않았다. readOnly 자체가 격리 수준을 정하는 것은 아니며 count와 목록 사이의 일관성은 기존 실행 환경의 격리 설정을 따른다. 삭제와 겹친 조회의 새 정책도 이 단계에서 임의로 확정하지 않았다.

## 실제 전후 비교

2026-10-15 21:18~21:19 KST, Java 21.0.10·MySQL 8.0.46·전용 로컬 컨테이너에서 같은 seed v1과 요청을 비교했다. 생산 변경 전의 작업 시작 HEAD는 `9904a5f`다. [원시 비교 증거](evidence/product-query-comparison-2026-10-15.json)에 8회 측정의 실제 SQL·바인딩·EXPLAIN·EXPLAIN ANALYZE·응답·전체 표본·인덱스와 소스 hash를 보존한다.

```http
GET /api/v1/products?brandId=1007&sort=price_asc&page=0&size=20
```

각 쿼리 버전에서 기존 인덱스 → 후보 추가 → 후보 제거 → 후보 추가 순서로 2라운드 비교했다. DDL 변경 후 ANALYZE를 실행했다. 각 구간은 준비 5회·측정 20회이며 **8개 구간 모두 HTTP 200·SUCCESS, 20개 품목의 여섯 필드·순서·totalElements=99·totalPages=5가 동일**, 요청당 SELECT는 2회였다.

| 후보 | 목록 본문에서 실제 확인한 DB 작업 | HTTP p50 1차 / 2차 | HTTP p95 1차 / 2차 |
| --- | --- | --- | --- |
| A 기존 | 상품 99행, 좋아요 lookup 99 loops, 조인 459행 → 99개 임시 집계·정렬 | 5.248 / 4.300 ms | 6.504 / 4.761 ms |
| B 인덱스만 | A와 같은 기존 인덱스 선택·집계·정렬. 후보 인덱스가 본문 계획을 개선하지 못함 | 4.800 / 4.396 ms | 5.772 / 4.694 ms |
| C 쿼리만 | 상품 99행 정렬, 반환 대상 좋아요 lookup 20 loops. 전체 임시 집계 제거 | 4.818 / 4.064 ms | 5.396 / 4.829 ms |
| D 조합 · 채택 | `idx_product_brand_price`로 상품 20행, 좋아요 lookup 20 loops. 임시 집계·별도 정렬 제거 | 4.517 / 3.712 ms | 5.116 / 4.888 ms |

전체 개수 쿼리는 여전히 기존 `idx_product_brand_deleted`로 99행을 읽는다. 따라서 **요청 전체의 상품 읽기가 모두 20행이 됐다거나, SQL 수가 줄었다는 의미가 아니다.** DB 내부의 상관 서브쿼리 20 loops도 애플리케이션이 SQL 20개를 보내는 N+1과 다르다.

### 비용·한계와 버린 대안

- D의 선택 근거는 동일 결과와 반복 확인된 **집계 범위·목록 스캔·정렬 작업 감소**다. B는 시간 수치가 일부 작아도 실행 계획이 같아 인덱스 단독 효과로 해석하지 않는다.
- HTTP p50은 낮아졌지만 워밍·실행 순서·작은 표본의 영향이 있다. A 자체도 1차보다 2차가 빨랐고, 2차 p95는 D가 A보다 약간 높았다. 일정 개선율·운영 처리량·지연 상한을 보장하지 않는다.
- 고정 브랜드 가격순 첫 페이지의 성능 증거다. 무브랜드·최신순은 결과 회귀를 검사했지만 각 경로의 성능 향상 수치는 측정하지 않았다. 깊은 offset·큰 브랜드·운영 분포·동시 부하는 별도 측정 대상이다.
- 서브쿼리는 반환 대상의 좋아요 관계를 실제로 센다. 매우 인기 있는 상품의 집계 비용이나 전역 `likes_desc`의 전체 집계 비용이 사라지는 것은 아니다.
- 새 인덱스는 저장 공간과 상품 등록·가격/삭제 변경의 인덱스 유지 비용을 늘린다. 쓰기 처리량은 이번 실험에서 측정하지 않았다. 브랜드 최신순 인덱스·좋아요 카운터·캐시는 근거 없이 함께 추가하지 않았다.
- Hibernate HQL select 서브쿼리에 의존하는 기술 선택이다. 표준 JPQL만으로의 이식성은 제한된다. 페이지+별도 일괄 집계 대안은 추가 왕복과 결과 조립을 늘리므로 이번에는 구현하지 않았다.

## 재현

기본 실행은 001~007을 적용한 현재 구현을 측정하고 `build/reports/week4/product-query-current.json`을 만든다. 비교 모드는 전용 DB에 001~006을 적용한 뒤 테스트가 007을 추가·제거하며 각 구간 결과를 별도 파일로 남긴다. 테스트가 만든 후보 인덱스만 `finally`에서 제거하며 공유 DB에는 연결하지 않는다.

```shell
# 현재 코드에서 인덱스 유무 비교. 매번 테스트를 실제 실행한다.
W4_QUERY_LABEL=after W4_COMPARE_BRAND_PRICE_INDEX=true \
./gradlew :apps:commerce-api:test \
  --tests 'com.loopers.application.product.ProductQueryBaselineTest' \
  --rerun-tasks --console=plain
```

`W4_QUERY_LABEL`은 **파일 이름용 표식이지 이전 쿼리로 바꾸는 스위치가 아니다.** A/B를 재현하려면 기존 쿼리 버전의 실제 소스를 사용해야 한다. 이번 비교는 생산 파일 변경 전에 A/B, 변경 후 C/D를 실행했으며 보고서의 SQL·sourceSha256으로 구분한다. seed hash는 모두 `912f7bbcfcce8ce19e47ead734a658a6ace998999c495cacf20fac65f0106197`이다. 이전 생산 소스는 `15c250d8...`, 새 소스는 `f46f73f1...`로 전체 hash를 증거에 남겼다.

## TDD·검증 기록

첫 실행은 Docker 비실행으로 컨텍스트 초기화에서 실패했다. 업무 assertion의 실패나 TDD Red로 세지 않는다.

- 테스트 우선: 페이지 경계 2건과 전역 인기순 반례 1건을 추가한 후 생산 변경 전 **2개 스위트·11개 테스트와 Checkstyle test 통과**. 기존 동작을 지키는 회귀는 처음부터 Green이었다.
- 쿼리 리팩터링: 새 projection과 공통 페이지 실행 함수를 적용한 뒤 같은 **11개 테스트·Checkstyle main/test 통과**. 기존 기대값을 변경하지 않았다.
- 인덱스 Red: 실제 수동 스키마에서 `idx_product_brand_price`의 컬럼 순서 검사를 추가하고 실행해 **1개 테스트가 인덱스 부재로 실패**함을 확인했다. 파일 누락·환경 실패가 아닌 assertion 실패다.
- 인덱스 Green: 007을 실제 적용하고 컬럼·ASC/DESC, 기존 데이터/인덱스 보존·중복 적용 실패의 무변경을 검사했다. 기존 스키마 검증을 포함한 `CommerceSchemaIntegrationTest` **32개 통과**.
- 21:23 KST 최종 전체 검사: `./gradlew :apps:commerce-api:check --rerun-tasks --console=plain` **BUILD SUCCESSFUL·종료 코드 0**. **62개 스위트·559개 테스트, 실패·오류·skip 0**. ArchUnit 포함, Checkstyle XML 11개 위반 0. 기존 계약·검사 규칙을 삭제하거나 완화하지 않았다.
- 최종 001~007 스키마의 기본 실행에서도 상품 20행·좋아요 lookup 20 loops·정렬 제거를 재확인했다. 세션 기본 격리 조회 결과는 REPEATABLE-READ, HTTP p50 3.721ms·p95 4.190ms였다. 이는 별도 전체 검사 프로세스 안의 재검증이며 위 A/B/C/D 비교 표에 섞어 향상률을 계산하지 않는다.

이 단계로 SQL·인덱스 개선을 완료했다. 당시 다음 작업으로 남겼던 캐시 대상·payload·TTL·정상 변경·장애 복구 정책과 Redis TDD는 이후 [캐시 구현·검증 기록](product-list-cache-tdd-log.md)으로 이어졌다. 이 문서의 과거 검사 결과만으로 현재 W4 전체 완료나 PR 제출 완료를 대신하지 않으며, 현재 상태는 위의 완료 체크리스트에서 구분한다.
