# 가격순: 상품 쏠림·동시 조회 확인

브랜드 7의 가격순 첫 20개와 그 상품들의 좋아요 수·내 좋아요 여부를 조회한다. 목록 항목에는 `isLiked`가 있고 공통 캐시에는 없다. 주 측정은 `X-USER-ID: 95`를 보내는 목록이다. 사용자·관계 테이블도 원본에서 복사하고, seed 규칙으로 계산한 사용자 95의 하트가 매 응답과 같은지 확인했다. 총상품수 COUNT를 포함하지 않는다. 한 브랜드의 상품이 많거나 캐시가 빈 순간에 요청이 겹쳐도 같은 페이지를 올바르게 반환하는지 확인한다.

## 무엇을 바꿨나

원본 10만 건을 두 실험 DB로 복사했다. 기존 인덱스·상품 가격·삭제 상태·좋아요 카운터를 유지하고 쏠림 DB에서만 ID 1~90,000의 brand_id를 7로 바꿨다. 이는 분포를 만드는 SQL이며 새 브랜드 변경 API를 만든 것이 아니다.

| 조건 | 전체 상품 | 브랜드 7의 활성 상품 |
| --- | ---: | ---: |
| 일반 | 100,000 | 990 |
| 상품 쏠림 | 100,000 | 87,390 |

위 건수는 데이터 준비 시 확인한 조건이다. API는 items·page·size만 반환하며 요청 중 총상품수를 세지 않는다. 기대 상품·순서·가격·좋아요 수·isLiked·브랜드는 seed 규칙으로 독립 계산한다.

사용자 95는 일반 첫 페이지에서 12개를 좋아요했고, 쏠림 첫 페이지에서는 좋아요한 상품이 없었다. 두 페이지의 하트는 각각 12개 true/8개 false와 20개 false로 검증했다. 모든 사용자·좋아요 분포를 대표하는 조건은 아니다.

## 한 명씩 조회한 결과

각 경우는 워밍업 100회 뒤 200회 측정하고 세 번 반복했다. 앱 실행 순서와 hit/miss 순서를 바꿨다. 시간은 GET부터 응답 본문 수신까지이고 miss 준비용 수정은 시간 밖이다.

| 경우 | 일반 중앙값(ms) | 상품 쏠림 중앙값(ms) |
| --- | ---: | ---: |
| 캐시 없음 | 9.472~9.702 | 9.830~12.408 |
| 로컬 miss | 8.859~9.703 | 8.386~9.710 |
| 로컬 hit | 8.572~10.371 | 8.770~10.561 |
| Redis miss | 9.762~10.739 | 10.581~11.935 |
| Redis hit | 9.461~11.235 | 9.803~12.560 |

범위는 세 반복의 중앙값 중 최솟값~최댓값이다. 일반·쏠림 모두 기존 가격순 인덱스로 페이지를 선택한다. 별도 대표 GET의 SQL은 모든 모드에서 5개이고 총상품수 COUNT는 없었다. hit는 가격순 페이지 선택을 활성 ID 확인으로 대체한다. 작은 차이를 보편적인 개선 배율로 해석하지 않는다.

## 20명이 함께 조회한 결과

Python 스레드 20개를 barrier에서 함께 출발시켜 한 앱에 GET을 보냈다. 준비용 3묶음 뒤 10묶음×20요청을 측정하고 세 번 반복했다. 실제 도착/SQL 시작 시점까지 같게 강제하지 않았고 지속 부하·최대 처리량 실험은 아니다. DB 연결 풀 최대 크기는 benchmark의 기존 40이다.

| 시작 상태 | 일반 p95(ms) | 상품 쏠림 p95(ms) |
| --- | ---: | ---: |
| 캐시 없음 | 35.042~48.154 | 35.426~42.583 |
| 로컬 / 시작 시 빈 캐시 | 34.794~53.387 | 34.661~58.934 |
| 로컬 / 미리 채운 캐시 | 36.582~38.460 | 39.404~69.939 |
| Redis / 시작 시 빈 캐시 | 40.767~61.760 | 34.777~49.017 |
| Redis / 미리 채운 캐시 | 31.125~44.668 | 36.083~45.696 |

빈 캐시는 묶음 시작 전에 지웠다는 뜻이다. 앞 요청이 채운 뒤 뒷 요청이 hit할 수 있으므로 전부 miss라고 세지 않는다. 채운 캐시는 같은 페이지를 미리 조회한 상태다.

시간 측정 뒤 별도 20요청 묶음의 MySQL 로그에서 실제 상품 페이지 SELECT 수를 셌다. 아래는 1차/2차/3차다.

| 경우 | 일반 페이지 재조회 횟수 | 쏠림 페이지 재조회 횟수 |
| --- | ---: | ---: |
| 캐시 없음 | 20 / 20 / 20 | 20 / 20 / 20 |
| 로컬 / 빈 캐시 | 7 / 8 / 3 | 4 / 7 / 4 |
| 로컬 / 채운 캐시 | 0 / 0 / 0 | 0 / 0 / 0 |
| Redis / 빈 캐시 | 10 / 11 / 11 | 6 / 8 / 10 |
| Redis / 채운 캐시 | 0 / 0 / 0 | 0 / 0 / 0 |

모든 별도 동시 묶음에서 총상품수 COUNT는 0번이었다. 빈 캐시에는 같은 페이지를 DB에서 반복 조회하는 일이 남았다. 채운 캐시도 브랜드·활성 ID·좋아요 카운터·사용자·개인 관계의 DB 확인이 있어 20요청에 100 SELECT가 실행됐다. SQL 로깅이 경쟁 시점에 영향을 줄 수 있어 이 별도 횟수를 시간 표본의 정확한 hit rate로 바꾸지 않는다.

## 해석과 실행

이 실험과 일반 데이터 비교를 함께 본 최종 판단은 [design.md의 가격순 캐시 결론](design.md#price-cache-choice)을 따른다.

브랜드 상품 수가 많다는 사실만으로 첫 20개 조회가 그만큼 많은 행을 읽는 것은 아니다. 읽기 속도와 함께 같은 결과·실행 계획·변경 반영을 확인한다. 이 범위의 결과로 모든 최악 상황·실제 운영 hit rate·Redis 장애와 쏠림이 겹치는 상황까지 검증했다고 설명하지 않는다. 동시 miss를 한 번으로 합치는 기능은 구현하지 않았다.

```bash
python3 scripts/measure-week4-price-cache-skew.py \
  --jar apps/commerce-api/build/libs/commerce-api-a083b48.jar \
  --user-id 95 \
  --output docs/week4/measurements/100k-price-cache-skew-personal.json
```

JAR는 현재 빌드에 맞추고 재실행 시 새 출력 경로를 쓴다. 다른 benchmark와 겹치지 않게 실행한다. 측정 GET 12,000개의 결과가 독립 기대값과 같고 오류는 0이었다. 원본 데이터·인덱스를 보존했으며 복제 DB·권한·키·직접 시작한 앱을 정리했다. [원본](measurements/100k-price-cache-skew-personal.json), [상세 기록](implementation-log.md#price-cache-skew).
