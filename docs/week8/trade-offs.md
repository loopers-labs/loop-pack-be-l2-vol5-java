# 쿠폰 설계 결정 기록

이 문서는 구현 전 대화에서 검토한 T01~T32의 선택·기각 이유를 보존하는 기록이다.
현재 구현 지시는 [현재 설계](design.md), 실제 실행 여부는 [검증 매핑](verification-plan.md)과 [구현 현황](completed/README.md)을 따른다.

| 현재 결정 | 반영 위치 |
|---|---|
| 인스턴스별 Java Semaphore, 전체 공유 한도 없음 | C04·YAML 양수 설정·기본 닫힘 |
| DB 슬롯과 마지막 캠페인 잠금, 발급 결과가 원본 | C01~C02·복합 FK·DB 시각·같은 TX |
| 기존 결과 우선·불변 혜택·본인 전체 목록 | C02~C03·쿠폰 ID/시각/혜택 보존 |
| 종료 불명 보류·수동 확인·지정 실행 복구 | C04·같은 DB의 원 세션 소멸·TX 부재·정합성 |
| Redis는 수용이 아닌 누적 집계 | C05·준비/0 구분·원자 중복 방지·DB 재집계·UUID fence |
| 고객·관리자 HTTP를 마지막에 연결 | C06 대상 검증과 전체 검사 실패 모듈의 환경 재실행 확인 완료 |

아래의 ‘아직 구현하지 않음’, ‘추천’, ‘다음 논의’는 **해당 대화 시점의 기록**이다.
이전 전역 Redis Set/Lua 수용 조건은 T24의 인스턴스별 선택으로 대체됐다. 후속 누적 집계 추가는 그 수용 정책을 되돌린 것이 아니다.
오래된 대안을 현재 명세로 적용하거나 미확인 실험을 완료 근거로 사용하지 않는다.
별도 역사 사본을 늘리지 않고 이 경로의 고유한 논의 기록을 그대로 보존한다.

## T25 · coupon Redis 목록과 분산락 · 후속 A 확정

사용자는 A(coupon 경로에서 Redis 제외)를 선택했다. 진행 중 캠페인+사용자 목록·완료 사용자 목록·해당 조합의 Redis 분산락도 추가하지 않는다.
서버별 Semaphore는 현재 처리 여력, DB 사용자 유일 제약은 중복 업무 효과, 슬롯 잠금/유일 제약과 캠페인 갱신은 총량을 보호한다.
같은 사용자 요청 둘이 DB에 진입할 수 있으며 제약 충돌 시 실패 TX를 rollback한 뒤 기존 결과를 새 TX에서 확인한다.
기존 다른 기능의 Redis 사용은 유지한다.

## T26 · 행사 시작·종료 판단 · 질문 21-B 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 관리자 active 전환 + 최초 startedAt 기록 | 수동 운영이 단순함 | 정해진 시각의 자동 시작/종료가 없음 |
| B · startsAt/endsAt + active를 요청 시 검사 | 스케줄러 없이 기간 밖 신규 발급 거절 | 시각 권위·경계·진행 중 요청·기간 변경 정책 설계 필요 |

사용자 확정 21-B: 캠페인에 시작/종료 시각을 저장하고 active와 함께 발급 가능 여부를 판단한다.
기존 쿠폰은 기간 종료 뒤에도 반환한다. 슬롯 준비 완료 조건과 기존 총량/혜택 불변 정책은 유지한다.
시각 권위와 마지막 검증/진행 중 요청 마감 기준은 이후 T28/23-A와 T29/24-A로 확정했다.
직전 제안한 일반 필드 길이/숫자 범위에는 사용자 확정 답변이 없으므로 추천 상태로 유지한다.

## T27 · 슬롯 재확인 초기 수치 · 질문 22-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 최초 포함 최대 4회·간격 50ms·예산 200ms | permit 점유와 응답 대기를 짧게 제한하는 출발점 | 일시 경합도 503이 될 수 있음 |
| B · 최초 포함 최대 5회·간격 100ms·예산 500ms | 같은 요청에서 슬롯 획득/최종 상태 확인 기회가 늘어남 | permit 점유·추가 DB 조회·지연 증가 |

사용자 확정 22-A: A 수치를 측정 전 초기값으로 사용한다. 기존 19-B의 쓰기 전 한정 재확인 정책은 유지한다.
같은 로컬 permit 안에서 빈 결과 TX 종료 뒤 기다리고 이미 INSERT한 발급 TX는 재실행하지 않는다.
예산/최대 횟수 중 하나라도 소진하면 새 시도를 시작하지 않는다. 품절 미확정이면 COUPON_SLOT_BUSY이며 확정 품절과 구분한다.
200ms는 실행 중 SQL 취소/DB 종료/전체 HTTP deadline의 보장이 아니다. 이미 시작한 작업의 실제 종료 확인과 permit 반환 규칙을 유지한다.

## T28 · 캠페인 시각의 권위 · 질문 23-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · DB 시각 | 여러 인스턴스가 같은 쓰기 DB의 시각으로 판단 | DB 시각 조회·시간대/정밀도 매핑 필요 |
| B · 각 앱 서버 시각 | 앱에서 시간 조회/테스트가 간단함 | 서버 간 시계 차이와 마감 판정 불일치를 관리해야 함 |

사용자 확정 23-A: DB 시각을 기준으로 한다. 앱/고객 접수 시각은 발급 가능 기간의 최종 판단 권위가 아니다.
잠금 대기 전 SQL 시작 시각을 잠금 획득 뒤 시각으로 오해하지 않도록 최종 캠페인 잠금 뒤 별도 DB 시각 조회를 설계한다.
UTC/정밀도/시작·끝 포함 여부는 구체 제안과 사용자 확정을 구분한다.

## T29 · 마감 직전 접수된 요청 · 질문 24-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 마지막 캠페인 검증 시점 기준 | DB에서 최종 확인한 기간 안의 발급만 승인 | 마감 전 접수 요청도 대기 후 마감이면 거절 |
| B · 서버 접수 시점 기준 | 기간 안에 접수한 요청을 종료 후에도 처리 가능 | 접수 시각 보존·마감 후 처리·중간 비활성 정책 추가 |

사용자 확정 24-A: 마지막 캠페인 잠금 획득 뒤 DB 시각과 현재 조건으로 판단한다.
이때 마감이면 앞선 미커밋 슬롯 변경/쿠폰 INSERT/카운터를 전체 rollback한다. 접수 시각으로 발급 권리를 예약하지 않는다.
마감 전에 마지막 검증을 통과했다면 commit이 종료 시각을 넘어 완료되는 것은 허용한다. commit 완료 시각까지 기간 안임을 보장하는 계약으로 해석하지 않는다.
기존 발급 완료 결과 조회는 기간과 관계없이 유지한다.

## T30 · 시작 후 행사 기간 변경 · 질문 25-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 시작 후 시작/종료 시각 고정 | active만 바꾸는 운영 규칙·기간 판단이 단순함 | 기간 연장은 새 캠페인으로 준비 |
| B · 종료 전 종료 시각 연장 허용 | 운영 중 연장 가능 | 발급과 같은 캠페인 잠금·연장 가능 시점 검증 필요 |

사용자 확정 25-A: 시작 후 startsAt/endsAt를 고정한다. 기존 총량/혜택 고정·active 전환 정책을 유지한다.
기본안은 DB 시각이 저장된 startsAt에 도달한 것을 시작으로 판단한다. active=false/실제 발급 0이어도 고정 정책을 우회하지 않는다.

## T31 · 수동 복구 대상 지정 · 질문 26-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 실행 ID 목록 지정 | 운영자가 확인한 대상만 선택적으로 복구 | 대상 ID 수집·개별 결과 확인 필요 |
| B · 복구 가능한 실행 전체 정리 | 한 번의 호출로 가능한 대상 처리 | 호출 시 대상 범위가 넓어짐 |

사용자 확정 26-A: 실행 ID를 지정하고 각 처리 결과를 반환한다. 현재 인스턴스/boot의 종료 확인된 미반환 handle만 반환한다.
이미 반환/미등록/이전 boot/종료 불명 실행은 카운트를 증가시키지 않는다. 관리자 지정 자체는 DB 종료 증거가 아니다.
recover 이후에도 닫힘을 유지하고 open은 별도 검증/명령이다. 여러 ID 중 종료 확인된 항목만 처리하는 개별 결과 기본안은 질문 27에 포함한다.

## T32 · 세부 계약 기본값 · 후속 마무리 요청 반영

사용자 선택 1~26의 주요 방향을 유지하면서 필드 범위/시간 구간/응답 필드/복구 관찰 계약을 [설계](design.md)의 세부 계약 기본안으로 구체화했다.
사용자는 별도 A/B 응답 대신 설계를 마무리하고 나머지는 구현하며 정하도록 요청했다. 기존 기본안을 마무리 기준으로 채택하며 개별 27-A 선택으로 기록하지 않는다.
추가 허용 범위는 도메인 레이어 우선 구현과 최소 필요 테스트다. API/DB/수용 기능까지 구현하라는 요청으로 확대하지 않는다.
구현 방식의 실효값은 실제 DB/드라이버/TX manager 검증 대상이며 문서 채택을 구현/실험 성공으로 기록하지 않는다.

## T24 · 전체 한도를 없애고 서버별 Java Semaphore 사용 · 최신 사용자 B 확정

사용자는 A(Redis 전역 한도 + 인스턴스 Semaphore)와 B(전역 한도 없이 인스턴스 Semaphore만) 중 B를 명시적으로 선택했다.
추가로 최대 동시 한도는 YAML에서 변경할 수 있게 요청했다. 이 결정이 아래 Redis 관련 과거 선택보다 우선한다.

| 항목 | 현재 결정 |
|---|---|
| 수용 범위 | 인스턴스별, 모든 캠페인 신규 발급이 같은 singleton Semaphore 사용 |
| 최대값 | YAML `coupon.admission.max-concurrency`, 초기 3·양수 정수 검증 |
| 반영 시점 | 시작 시 한 번 읽고 설정 변경은 인스턴스 재시작 시 적용 |
| 초과 요청 | 로컬 tryAcquire 실패 시 즉시 429 |
| 반환 | DB TX/실행 종료 확인 후 같은 로컬 permit handle을 한 번 반환 |
| DB 정합성 | 사전 슬롯·실제 쿠폰 INSERT·마지막 issuedCount 갱신·사용자 중복을 그대로 보호 |
| Redis | 쿠폰 수용 Set/Lua/SREM 제외, 기존 캐시 등 다른 기능은 유지 |
| 합계 | A=3/B=5이면 합계 8 가능·전역 C 보장 없음 |
| 관리자 제어 | 기존 선택을 인스턴스별로 유지·종료 불명은 해당 인스턴스 닫힘 |

원문 과제의 Redis 전역 수용 조건과 다른 사용자 설계다. 원문을 구현/검증했다고 주장하지 않는다.
8번의 Redis 반환 실패 정책·13번의 coupon Redis 1초 설정은 현재 경로에서 불필요해졌다.
9번의 boot/실행 UUID는 필요하면 로그/로컬 추적 ID로 유지하며 Redis permit token으로 쓰지 않는다.
10번의 고정 서버 설정 선택은 현재 YAML의 인스턴스별 최대값으로 이어진다. 런타임 조정 API는 요청하지 않았다.
이후 18-A/19-B/20-A도 확정했다. 현재 설계는 [최신 설계](design.md), 이전 Redis 상세는 [이전 기록](history/redis-admission-design.md)을 따른다.

| 19-B | T22 | 쓰기 전 슬롯 획득/상태 제한 재확인 | 대기 예산/간격/횟수·최종 판정 실험 |
| 20-A | T23 | 로그·운영자 확인 기반 수동 복구·DB 실행 이력 추가 없음 | 실제 process/DB 종료 근거와 운영 실험 |
| 후속 A | T25 | coupon Redis 진행 중/완료 목록과 분산락 제외 | 중복 요청은 DB 유일 제약·새 TX 기존 결과 조회 |
| 21-B | T26 | startsAt/endsAt + active를 요청 시 판단 | 기간 변경·정밀도/표현·경계 포함 여부 |
| 22-A | T27 | 슬롯 재확인 최초 포함 최대 4회·간격 50ms·예산 200ms | 실제 경합·조회 시간·예산 소진 검증 |
| 23-A | T28 | 쓰기 DB 시각을 권위로 사용 | 마지막 잠금 뒤 DB 시각 조회·UTC/정밀도 매핑 |
| 24-A | T29 | 마지막 캠페인 검증 시 마감 판단·통과 뒤 늦은 commit 허용 | 대기 중 마감 rollback·기존 쿠폰 유지 검증 |
| 25-A | T30 | 시작 후 시작/종료 시각 고정·active만 전환 | 시작 판단 기본안·기간 고정 검증 |
| 26-A | T31 | 복구할 실행 ID 목록 지정·개별 결과 반환 | 현재 boot/종료 근거·중복 반환 방지 |

첫 대화의 세 번째 질문은 T07에 해당한다. T03을 선택한 것으로 해석하지 않는다.

## 원문 조건·초기 설계 기록 · Redis 전역 항목은 T24로 변경

아래 표와 T01~T23은 논의 경위를 보존한다. Redis 전역 수용과 관련된 이전 고정/추천 표현을 현재 지시로 해석하지 않는다.
DB 규칙·고객 API·동기 발급·명시적 종료 확인 등 변경하지 않은 조건은 유지한다.

| 주제 | 과제 계약 | 이번에 확장하지 않는 범위 |
|---|---|---|
| 수용 방식 | 빈자리에서 동기 발급·초과 429 | 대기실·Kafka 비동기 발급·무제한 queue |
| 수용 저장소 | 실행마다 고유 token·공유 Redis Set·Lua | JVM Semaphore만으로 전체 C 보장 |
| DB 원본 | 총량·사용자 중복·발급 수/쿠폰 원자성 | Redis 수용을 실제 발급 성공으로 취급 |
| 연결 | master template·String serializer | replica count 기반 승인 |
| 장애 | 불확실한 수용은 503·DB 신규 발급 시작 금지 | local fallback·다른 queue 우회 |
| 반환 | 실행/TX 종료 확인 뒤 자기 token 제거 | HTTP timeout·TTL만으로 회수 |
| 재개 | 기본 닫힘·명시적 열기·오류 후 자동 재개 금지 | PONG만으로 재개·자동 failover 보장 |
| 중복 응답 | 기존 쿠폰은 자리 없이 200·같은 ID | 품절/비활성 때문에 기존 결과 거절 |

위 조건을 바꾸려면 과제 자체의 계약 변경이다. 아래 선택지와 섞지 않는다.

## T01 · 쿠폰 책임을 어디에 둘까?

| 후보 | 이점 | 비용 |
|---|---|---|
| 독립 coupon Context | 발급 규칙/저장/수용 조율의 소유권이 선명함 | 순수 도메인 검사 대상·패키지 추가 필요 |
| 기존 shopping Context | 기존 사용자 활동 구조를 활용함 | 좋아요/구매 활동과 쿠폰 발급의 책임 구분 필요 |

사용자 확정: 독립 coupon Context.
구현할 때 `DomainPurityArchitectureTest`의 패키지 목록에 실제 신규 도메인을 추가해야 한다.
현재 목록은 mall/shopping/ordering/pay/shared다. 새 패키지가 자동으로 순수성 검사를 받는다고 가정하지 않는다.
기존 계층 순서와 순수 Java domain·JPA Entity 분리는 유지한다.

## T02 · 마지막 쿠폰을 어떻게 보호할까?

| 후보 | 이점 | 비용 |
|---|---|---|
| 캠페인 행 비관적 잠금 | 중복/활성/잔여 확인과 증가를 한 흐름으로 설명하기 쉬움 | 같은 캠페인의 발급 TX가 직렬화됨 |
| 조건부 발급 수 증가 | DB에서 한도 조건과 변경을 한 번에 판단 | 변경 0행의 원인 분류·JPA 상태 동기화 필요 |
| 낙관적 버전과 제한 재시도 | 경합이 적을 때 명시적 사전 잠금이 없음 | 인기 행사에서 충돌/재시도 부하와 재시도 경계 증가 |

최초 사용자 선택은 캠페인 행 비관적 선잠금이었다. 이후 사전 슬롯 제안과 추가 S01-A 선택으로 이 범위를 변경했다.
현재는 개별 DB 슬롯에서 발급을 준비하고 같은 TX 마지막에 캠페인을 잠가 현재 활성/한도 확인과 issuedCount 증가를 수행한다.
같은 사용자에게 이미 쿠폰이 있다면 비활성/품절보다 기존 결과를 먼저 반환한다.
DB 유일 제약은 잠금 선택과 관계없이 유지한다. 잠금 대기/병목도 측정하며 처리량 개선을 미리 주장하지 않는다.
캠페인에 대한 공통 잠금을 없앤 선택은 아니다. FK/실제 flush가 이를 앞당기지 않는지 검증한다. 기존 JPA 쓰기 규칙은 유지한다.

## T03 · 중복의 빠른 조회와 동시 충돌은 어떻게 나눌까?

| 후보 | 이점 | 비용 |
|---|---|---|
| 사전 조회 + TX 재검사 + 유일 제약 | 완료 중복은 Redis 장애 중에도 즉시 기존 결과 반환 | 최초 발급에 조회가 추가됨 |
| TX 안에서만 중복 조회 | DB 진입 흐름이 단순함 | Redis 앞 조회가 없으면 완료 중복도 수용 거절 영향을 받음 |

과제 흐름에는 첫 번째 방식이 맞는다. 선택할 세부는 사전 조회의 구현/연결 비용과 예외 처리 경계다.
추천: QueryDao의 저장 결과 조회를 재사용하고, 동시 충돌 후에는 실패 TX가 끝난 뒤 별도 조회한다.
유일 제약 위반도 정확한 `(campaignId,userId)` 제약인지 식별한다. 기존 쿠폰을 찾지 못하면 성공으로 꾸미지 않는다.
실행 token 재확인과 쿠폰 업무 멱등성은 별개이며, 같은 사용자+캠페인을 실행 token으로 재사용하지 않는다.

## T04 · 처리 자리와 업무 TX의 경계를 어디에 둘까?

| 후보 | 이점 | 비용 |
|---|---|---|
| TX 없는 조율 facade + 별도 TX 빈 | Redis 대기 동안 DB 연결을 점유하지 않고 TX 완료 뒤 반환 가능 | 종료 확인/실패 조율 책임이 필요 |
| 전체 facade를 하나의 TX로 감쌈 | 메서드 구조가 짧아 보임 | 수용 대기도 DB TX 안으로 들어가고 반환이 실제 commit보다 빠를 수 있음 |

사용자 확정 6-A: 기존 PG 조율과 같은 별도 Spring 빈의 공개 `@Transactional` TX 진입점 구조를 활용한다.
조율 facade에서 TransactionTemplate로 직접 업무 TX를 여는 대안은 선택하지 않았다.
성공 응답뿐 아니라 rollback 완료·commit 결과 불명/종료 불명을 나눠 종료 증거를 정의한다.
단순 `finally`가 실행됐다는 이유로 항상 반환하지 않는다. 정상 종료를 확인한 경우만 자기 token을 반환한다.
구체 종료 신호는 실제 Spring TX 구성에서 정하고 검증한다. 이 문서는 아직 구현 방식을 확정하지 않는다.

## T05 · capacity와 거절 안내를 어떻게 정할까?

| 후보 | 이점 | 비용 |
|---|---|---|
| 서버의 고정 C | 부하 실험/운영 설명이 쉬움 | 처리 여력 변화에 즉시 대응하지 못함 |
| 운영 중 C 변경 | 실제 자원 여력에 맞게 조정 가능 | 인스턴스별 설정 불일치·축소 시 기존 점유 처리 정의 필요 |

사용자 확정 10-A: C는 신뢰하는 서버 설정으로 고정하며 초기 실험은 3이다. 값 변경은 설정 후 재시작으로 반영한다.
C는 코드 상수가 아니고 HTTP 입력으로 받지 않는다. 동적 C 변경 endpoint는 추가하지 않는다.
C=3은 필수 실험값이며 모든 환경의 최적값이라고 주장하지 않는다. 재시작 후에도 수용은 기본 닫힘이다.
키는 전체 신규 발급 경로가 공유하고 캠페인별 C=3으로 잘못 분산하지 않는다.
실행 token 형식은 사용자 확정 9-B인 `<bootUUID>:<executionUUID>`를 따른다. 키/설정 속성 이름은 아직 미정이다.
429 재시도 간격 안내는 가능하지만 재시도 시각의 성공/쿠폰 예약을 약속하지 않는다.
짧은 backoff/jitter는 재폭주를 완화하나 Redis 원자 수용만으로 엄격한 도착순 공정성이 보장되지는 않는다.

## T06 · Redis command timeout을 어디에 설정할까?

| 후보 | 이점 | 비용 |
|---|---|---|
| 기존 수동 factory에 명시 timeout 추가 | 실제 Lettuce builder에 적용됨을 확인하기 쉬움 | 기본/다른 template에 대한 영향 검토 필요 |
| 쿠폰용 전용 factory 추가 | 기존 cache client 설정과 분리 가능 | 연결/빈/설정 관리 중복 |

현재 `RedisConfig`는 수동 `LettuceClientConfiguration.builder()`를 쓰고 `RedisProperties`에 timeout이 없다.
추천: 기존 master 연결을 우선 재사용하면서 명시 timeout의 적용 범위를 설계한다.
Spring Boot 속성만 추가해 적용됐다고 주장하지 않는다. 수치와 최종 설정 위치는 미정이다.
timeout은 명령이 Redis에서 실행되지 않았다는 증거가 아니다. 수용 응답 유실은 닫힘/DB 시작 금지로 처리한다.
Lua는 검증/자리 판단만 수행하며 DB 발급이나 긴 루프를 넣지 않는다. 원자 실행은 오류 시 쓰기 rollback을 뜻하지 않는다.

## T07 · 로컬 수용 열기와 복구는 어떻게 운영할까?

| 후보 | 이점 | 비용 |
|---|---|---|
| 시작 시 닫힘 + 로컬 관리자 명령 | 명시적인 재개 절차와 오류 후 닫힘을 설명하기 쉬움 | 명령 권한/실행 확인 필요 |
| 설정 파일/환경 변경 후 재시작 | 별도 운영 API를 줄일 수 있음 | 재시작 자체를 안전 증거로 착각하기 쉬움·다른 실행 확인 필요 |

사용자 확정: 앱 실행 중 로컬 관리자 명령으로 수용을 제어한다. 설정 변경/재시작을 기본 열기 방식으로 삼지 않는다.
사용자 확정 5-A: 로컬 관리자 명령은 HTTP API로 전달한다. endpoint/응답·재개 조건은 [설계](design.md)에서 구체화한다.
공개 관리 화면이나 실제 인증 시스템으로 확장하지 않는다. 기존 관리자 fixture를 쓰면 접근 계약을 명시한다.
열기 직전에 기존 해당 실행·DB 작업 종료, 실제 쿠폰 결과, 비활성 token 정리 범위를 확인해야 한다.
재시작·PONG·빈 Set만으로는 이 조건을 만족하지 않는다. DB 결과/종료 불명은 수용을 닫아 둔다.
반환 실패는 쿠폰 성공 사실을 취소하지 않으며 미확인 점유를 복구 대상으로 남긴다.
이 설계는 가용성을 낮출 수 있다. lease/fencing/자동 failover는 이번 준비/기본 실험 범위에 넣지 않는다.

## T08 · 저장된 혜택과 목록을 어떻게 모델링할까?

| 후보 | 이점 | 비용 |
|---|---|---|
| 발급 당시 혜택을 쿠폰에 snapshot | 캠페인 변경 뒤에도 발급된 결과가 안정적임 | 일부 정보 중복 저장 |
| 조회 시 현재 캠페인 혜택 조인 | 중복 저장이 적음 | 과거 쿠폰의 혜택 의미가 바뀔 수 있음 |

사용자 확정 4-B: 발급 완료 정보에 혜택 설명과 정액 할인 금액을 각각 snapshot으로 저장한다.
설명 문자열만 저장하는 안 대신 두 필드를 분리했다. 실제 할인 적용/할인 유형 확장은 구현 범위에 추가하지 않는다.
금액의 유효 범위/저장 타입, 설명 길이, 이름 snapshot 포함 여부는 아직 미정이다.
목록은 기존 QueryDao·QueryDSL 조회 구조를 따르고 본인 조건을 DB 조회에 포함한다.
초기 목록의 페이지 정책·응답 구조는 별도 확정한다. 안정된 정렬과 타인 결과 미노출은 고정 요구사항이다.

## T09 · 경쟁/장애를 어떻게 재현할까?

| 후보 | 이점 | 비용 |
|---|---|---|
| 실제 Redis/MySQL + 제한된 test barrier/실패 주입 | 실제 점유·TX 효과를 분리 관찰 가능 | 실행 수명주기·deadline·정리 설계 필요 |
| mock 결과만 검증 | 빠르고 분기 확인이 쉬움 | 공유 슬롯·실제 rollback·연결 장애 증명 불가 |

추천: 실제 저장소 검증을 중심에 두고 mock은 작은 분기 검증에만 사용한다.
기존 Redis fixture는 static 시작/전역 property/가변 이미지이므로 장애 제어 수명주기에 맞는지 먼저 확인한다.
새 장애 fixture가 필요하면 이미지 고정·각 테스트의 명시적 소유/종료를 검토한다. 기존 fixture를 일괄 변경하지 않는다.
수용량 실험과 DB 총량 실험을 분리한다. 자세한 절차는 [검증 계획](verification-plan.md)을 따른다.

## T10 · 캠페인 잠금 대기를 얼마나 허용할까? · 질문 7-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 짧은 명시적 잠금 대기 제한 | 특정 캠페인 지연이 처리 자리를 오래 점유하는 것을 줄임 | 일시적 경합도 실패/재요청으로 돌아올 수 있음 |
| B · 기존 DB 기본 대기 유지 | 짧은 경합을 기다려 같은 요청에서 완료할 가능성 | Redis 자리와 DB 연결을 더 오래 점유할 수 있음 |

사용자 확정 7-A: 짧은 명시적 잠금 대기 제한. 구체 초 값과 MySQL/JPA에 실제로 적용하는 경계는 별도 확인/실험 후 확정한다.
클라이언트 시간 초과만으로 TX 종료/token 반환을 판단하지 않는다.
DB rollback과 실행 종료가 확인된 잠금 실패는 품절·Redis 자리 없음·수용 불확실과 다른 오류로 분류한다.
정상 rollback이면 자리는 반환할 수 있지만 미확인 상태는 유지한다. 잠금 실패 자체를 Redis 수용 장애로 바꾸지 않는다.

## T11 · 자기 token 반환 실패에 재시도를 붙일까? · 질문 8-A 확정

고정 조건: 쿠폰 commit 확인 시 발급 사실을 유지하고 반환 실패는 수용 닫힘으로 처리한다.
실패를 숨기거나 재시도 성공만으로 자동 재개하지 않는다.

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 한 번 시도 후 실패는 수동 복구 | 응답 지연/재시도 분기 감소·관찰이 단순함 | 짧은 통신 장애도 운영 복구가 필요할 수 있음 |
| B · 닫힘 처리 후 자기 SREM만 제한적으로 추가 1회 | 일시 오류에서 남은 token을 줄일 가능성 | 응답 지연·대기/종결 분기 증가, 명시적 재개는 여전히 필요 |

사용자 확정 8-A: 반환 1회 시도 후 실패는 수용 닫힘/수동 복구. 자동 SREM 추가 재시도를 두지 않는다.
발급 TX/쿠폰 생성도 재시도하지 않으며 타 token/Set 전체를 삭제하지 않는다.
commit된 최초 발급 201/기존 결과 200은 저장된 사실로 결정하고 운영 점유 오류와 구분한다.
관리자의 확인 후 복구에서 같은 자기 token을 다시 SREM하는 것은 원래 실행의 자동 재시도와 구분한다.

## T12 · 실행 token에 인스턴스 소유 정보를 넣을까? · 질문 9-B 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 실행 UUID만 저장하고 로그/실행 registry로 연결 | Redis token 형식이 단순함 | 재시작 후 소유 범위를 찾으려면 별도 관찰 정보가 필요 |
| B · boot UUID와 실행 UUID를 결합 | 같은 실행 인스턴스의 token을 구분하기 쉬움 | token 길이/관찰 필드 증가·이전 boot 추적 필요 |

사용자 확정 9-B: `<bootUUID>:<executionUUID>`. bootUUID는 앱 시작마다, executionUUID는 실행마다 서버가 생성하며 고객이 입력하지 않는다.
소유 범위 식별은 종료 증거가 아니다. 오래된 boot token도 살아 있는 DB 작업 여부를 확인하지 않고 삭제하지 않는다.
재시작 뒤 token 복구 절차/관찰 근거는 별도 구체화한다. 사용자+캠페인을 실행 token으로 쓰는 것은 대안이 아니다.

## T13 · 보유 목록에 페이지를 둘까? · 질문 11-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 본인 전체 목록 | 작은 로컬 캠페인에서 계약/조회가 단순함 | 보유량이 늘면 응답량도 증가 |
| B · 시각/ID cursor 목록 | 응답량 제한·최신순 이어보기 가능 | cursor 형식/size/경계 검증과 테스트 추가 |

사용자 확정 11-A: 본인 전체 목록을 `(issuedAt DESC, couponId DESC)`로 반환한다. cursor/size/total 페이지 계약을 추가하지 않는다.
응답량이 보유량만큼 늘어나는 비용을 수용한다. 본인 조회 조건과 빈 목록 응답은 유지한다.

## T14 · 복구와 열기 명령을 분리할까? · 질문 12-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · recover와 open 분리 | 정리 결과를 닫힘 상태에서 확인한 뒤 별도 명시적 열기 가능 | 운영 호출이 두 번 필요 |
| B · 한 관리자 명령에서 검증/정리/열기 | 운영 호출이 한 번 | 단계별 실패/중단 결과와 재호출 의미를 함께 설계해야 함 |

사용자 확정 12-A: recover와 open을 분리한다. recover 성공 뒤에도 수용은 닫힘이며 open에서 조건을 다시 확인한다.
진행 중 실행·미종결 DB 작업·출처/종료 불명 token이 있으면 정리/열기를 거절한다.
관리자가 요청했다는 사실 자체를 종료/신뢰 증거로 간주하지 않는다. 세부 증거/오류 응답은 별도 설계한다.

## T15 · Redis 명령 대기의 초기값 · 질문 13-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 명령 대기 1초 | 수용 확인 불가/반환 장애를 빠르게 관찰 | 순간적인 지연도 닫힘/수동 복구로 이어질 수 있음 |
| B · 명령 대기 3초 | 짧은 지연을 기다려 응답받을 여유 | Redis 장애에서 요청 대기가 길어짐 |

사용자 확정 13-A: 로컬 첫 실험의 명령 대기 초기값은 1초다. 측정으로 조정할 출발값이며 성능 보장이 아니다.
수치는 명령 대기 한도이며 전체 HTTP/접속/DB 수행 시간의 합산 제한을 뜻하지 않는다.
기존 수동 master client builder에 실제 timeout을 명시하는 방식을 우선 설계한다. 다른 API 영향과 적용을 검증한다.
수용/반환 timeout은 Redis 미실행 증거가 아니며 기존 닫힘/불확실 처리 규칙을 유지한다.

## T16 · DB 잠금 대기의 초기 목표값 · 질문 14-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 캠페인 잠금 대기 1초 | 캠페인 지연으로 슬롯/연결을 오래 점유하는 것을 줄임 | 일시적 경합도 잠금 실패가 될 수 있음 |
| B · 캠페인 잠금 대기 3초 | 같은 요청에서 잠금을 얻을 여유 | 슬롯/연결 점유와 사용자 대기가 길어짐 |

사용자 확정 14-A: 마지막 캠페인 카운터 행의 잠금 대기 초기 목표는 1초다.
SKIP LOCKED 슬롯을 1초 기다린다는 뜻이 아니다. 실제 MySQL 설정/취소와 rollback 경계를 검증해야 한다.
이 값이 전체 TX/HTTP의 절대 종료 시간을 보장한다고 주장하지 않는다. 기존 API의 대기 설정은 일괄 변경하지 않는다.
미확인 작업을 시간 경과만으로 반환하지 않는다. 구현 시 선택한 시간이 실효값이 아니면 조정 근거를 사용자에게 제시한다.

## T17 · 오류 코드의 구체성 · 질문 15-A 확정

기존 `ApiErrorMapper`는 재고 부족 등 상태 충돌을 409로 매핑한다. coupon도 품절/비활성은 409를 제안한다.
현재 공통 `ApiResponse.meta.errorCode`는 범용 ErrorType의 코드 문자열을 사용한다.

| 후보 | 이점 | 비용 |
|---|---|---|
| A · coupon 경로는 업무별 오류 코드 | 품절/비활성/수용량/잠금 실패를 client가 명확히 구분 | coupon 전용 매핑/코드 정의 필요 |
| B · 기존처럼 범용 HTTP 오류 코드 | 기존 표현과 가장 유사함 | 같은 HTTP 상태 안의 다른 원인은 메시지 등에 의존 |

사용자 확정 15-A: coupon 경로에 업무별 오류 코드를 제공하며 기존 공통 응답 구조와 다른 API의 오류 응답은 유지한다.
원문에 명시한 429/503 구분은 고정이다. 품절/비활성/슬롯 경합/잠금 실패/수용 불확실을 별도 코드로 분류한다.
세부 코드/매핑은 [설계](design.md)의 표를 따른다. 예상하지 못한 DB 예외를 업무 거절로 숨기지 않는다.

## T18 · 사전 DB 발급 슬롯과 카운터 · 추가 S01-A 확정

사용자는 사전 슬롯의 목적을 총량의 행 단위 보호와 캠페인 잠금 경합 완화 둘 다로 답했다.
제안 A(저장 issuedCount를 같은 TX 마지막에 갱신)와 B(발급 수를 조회 시 산출) 중 A를 선택했다.

- `coupon_slots`를 총량만큼 미리 준비하고 실제 발급 결과는 `coupons`에 INSERT한다.
- `UNIQUE(slot_id)`와 `UNIQUE(campaign_id,user_id)`를 함께 유지한다.
- 슬롯 변경·쿠폰 INSERT·캠페인 카운터는 한 TX이며 최종 활성/한도 거절도 전체 rollback이다.
- 최초 T02의 캠페인 선잠금을 개별 슬롯 → 마지막 캠페인 카운터 잠금 순서로 변경한다.
- 잠금 구간 축소가 목표지만 카운터 공통 행 경합·FK 검사·JPA SQL 순서는 실제로 확인한다.
- 슬롯 수/totalQuota 일치와 준비 완료 후 활성화를 보장한다. 행 생성/상태 변경의 원자성도 검증한다.
- Redis의 현재 처리 자리는 그대로 필요하며 DB 발급 슬롯은 정상 발급 후 반환하지 않는다.

S01-A는 당시 질문 13~15와 별도 선택이었다. 이후 해당 질문도 13-A/14-A/15-A로 확정했다.

## T19 · 미발급 슬롯 선택 · 질문 16-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · SKIP LOCKED로 잠긴 슬롯을 건너뜀 | 다른 비어 있는 슬롯을 고를 기회·행 대기 감소 | 빈 결과를 곧바로 품절로 처리할 수 없음 |
| B · 첫 미발급 슬롯의 잠금을 제한 시간 동안 기다림 | 선택/대기 흐름이 비교적 단순함 | 뒤의 빈 슬롯이 있어도 앞선 행을 기다릴 수 있음 |

사용자 확정 16-A: SKIP LOCKED로 잠긴 슬롯을 건너뛴다. 잠금 획득/해제만으로 엄격한 선착순을 보장하지 않는다.
빈 결과는 기존 쿠폰 재확인과 최신 발급 수/한도에 따라 기존 결과·품절·일시 슬롯 경합을 구분한다.
실제 SELECT/인덱스/잠금 범위를 검증한다. 빈 결과 응답/조회 경계의 구체 제안은 설계 문서를 따른다.

## T20 · 행사 시작 후 변경 정책 · 질문 17-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 시작 후 총량/혜택 고정, 활성 여부만 전환 | 사전 슬롯 수와 총량 일치·혜택 snapshot 원본이 단순함 | 운영 중 수량/혜택 변경은 새 캠페인으로 처리 |

비활성 후 재활성도 같은 슬롯/총량/카운터/발급 결과를 보존한다. 수량/혜택 변경은 새 캠페인으로 준비한다.
실제 할인 적용/전체 캠페인 관리 CRUD는 추가하지 않는다. 기존 coupon snapshot은 유지한다.

## T21 · FK로 슬롯/캠페인 관계를 보호할까? · 질문 18-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 슬롯을 경유하는 DB FK | 쿠폰이 실제 슬롯과 그 캠페인에 속함을 DB에서 보호 | 복합 FK/인덱스·실제 잠금 검증 필요 |
| B · ID만 저장하고 애플리케이션에서 관계 검사 | DDL/매핑이 단순함 | 외부/잘못된 쓰기의 잘못된 참조를 DB가 막지 못함 |

사용자 확정 18-A: `coupons(slot_id,campaign_id)` → `coupon_slots(id,campaign_id)` → `coupon_campaigns(id)`로 관계를 보호한다.
coupon에서 campaign으로 직접 FK를 중복 추가하는 대신 슬롯 경유로 일치를 보호하는 안이다.
실제 FK 검사/슬롯 상태 UPDATE/flush가 공통 캠페인 잠금을 앞당기지 않는지 검증해야 한다.

## T22 · 슬롯을 당장 못 골랐을 때 기다릴까? · 질문 19-B 확정

16-A는 SKIP LOCKED 선택이며 빈 결과 이후 응답/대기 정책까지 확정한 것은 아니다.

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 최신 상태 확인 뒤 여전히 경합이면 즉시 503 | 빠른 실패·자리 점유 시간을 줄임 | 잠시 뒤 품절/발급 가능이 확정돼도 사용자가 다시 요청해야 함 |
| B · 쓰기 전 슬롯 획득/상태만 제한된 시간 안에서 재확인 | 다른 TX 종료 뒤 실제 품절/빈 슬롯을 같은 요청에서 확인할 기회 | 로컬 permit 유지·응답 대기·추가 조회 증가 |

사용자 확정 19-B: 쓰기 전 슬롯 획득/상태만 유한 시간/횟수 안에서 재확인한다.
확정된 품절은 즉시 종료한다. B도 전체 대기 예산/횟수 한도를 두며 무한 재시도/queue를 추가하지 않는다.
재확인은 미발급 쓰기가 없던 빈 결과 경로에 한정하고, 쿠폰 INSERT/발급 효과가 발생한 TX를 재실행하지 않는다.
현재 T24에서는 같은 로컬 permit을 유지하며 새 HTTP 실행에 공유하지 않는다. 기다리는 동안 TX/연결을 계속 잡는 방식은 피한다.
예산이 끝나도 품절이 확정되지 않으면 503 `COUPON_SLOT_BUSY`다. 원문의 5/8 실험과 구분 검증을 함께 설계한다.
A를 선택하면 첫 응답의 일시 503과 이후 실제 소진을 확인한 409가 다를 수 있음을 계약/실험에 명시해야 한다.

## T23 · 앱 재시작 뒤 이전 실행 복구의 범위 · 질문 20-A 확정

| 후보 | 이점 | 비용 |
|---|---|---|
| A · 현재 boot 실행 추적 + 이전 boot는 운영자가 근거를 확인해 수동 복구 | 별도 실행 이력 테이블/쓰기 추가 없음·로컬 실험 범위에 맞음 | 이전 실행과 DB 종료 근거를 운영 절차로 확인해야 함 |
| B · 실행 이력도 DB에 영속화 | 재시작 뒤 실행 정보/저장 상태를 조회할 수 있음 | 별도 모델/TX·이력 저장 실패와 미완료 기록의 해석 필요 |

사용자 확정 20-A: 로그/로컬 추적과 운영자 확인으로 복구하며 별도 DB 실행 이력 모델/쓰기는 추가하지 않는다.
어느 안이든 종료를 모르면 닫힘을 유지하고 TTL/이전 boot/관리자 입력만으로 강제 회수하지 않는다.
현재 T24에서는 이전 process와 해당 DB 작업 종료·실제 쿠폰 결과·정리할 정확한 로컬 실행/permit 범위를 확인한 후에만 수동 정리/재개한다.
운영 절차는 현재 설계에 기록한다. 실제 근거 수집/DB 종료 확인은 구현·통제 실험에서 검증하며 자동 재개/다중 인스턴스 failover 보장을 추가하지 않는다.
