# 8주차 실험 기록 — 쿠폰을 단계별로 설계하며 측정하기

DB에서 정합성을 확보하고 행 잠금과 조건부 UPDATE를 비교했다. DB에 요청이 집중되는 문제를 관찰해 Redis 수량·중복 판단을 적용했다. 각 단계의 부하·응답·자원 사용량과 남은 문제를 기록한다. 설계는 [design.md](design.md)를 따른다.

실험별 실행 조건과 측정 범위를 함께 기록한다. “DB까지 가지 않음”은 **DB 발급 TX에 진입하지 않음**을 뜻하며, 사용자 확인·기존 결과 조회는 남는다. Redis 수량 판단 비교와 요청별 시간 분해는 각각의 계측 조건으로 해석한다.

### 숫자를 세는 기준

| 이름 | 정의 | 어디서 세나 |
| --- | --- | --- |
| **RPS(보낸 속도)** | k6가 1초에 새로 시작하는 발급 요청 수. 앞 요청이 느려져도 정해진 속도로 시작한다(실제 사용자도 서버가 느리다고 덜 누르지 않는다) | 설정값. 실제로 보낸 수는 응답 기록에서 따로 센다 |
| **TPS(초당 발급)** | 구간의 201 응답 수 ÷ 구간 초. 1초에 실제로 발급(commit)된 쿠폰 수. 409·200은 넣지 않는다 | k6 응답 기록. DB 발급 수와 201 수가 같은지 매번 대조한다 |
| **한계 X** | RPS를 올려도 TPS가 더 오르지 않는 지점. RPS가 X를 넘으면 그 차이만큼 매초 요청이 쌓인다 | 한계 찾기 실험 |
| **DB까지 간 요청** | 실행된 UPDATE 문 수(`Com_update`). 실험 중 UPDATE는 발급의 조건부 UPDATE뿐이라, DB에서 한도 판단까지 간 요청 수로 읽는다(0건 갱신 = 409도 센다) | MySQL 전역 카운터, 0.5초마다 |
| **쿠폰 저장 시도** | 실행된 INSERT 문 수(`Com_insert`). 유일 제약 위반으로 실패한 저장도 센다 | MySQL 전역 카운터, 0.5초마다 |

**정합성과 응답 대응은 나눠 판정한다.** 실험 도구는 DB 정합성(발급 수 = 쿠폰 행 = 서로 다른 사용자, 한도 이하)을 지키지 못하면 실패로 끝낸다. 처음에는 "DB 발급 수 = 성공 응답 받은 사용자 수"도 같은 검사에 넣었다. 그런데 클라이언트(k6, 15초 제한)가 먼저 포기해도 이미 실행 중인 서버 TX는 끝까지 진행되므로, 2-4 분산락처럼 DB는 맞는데 응답만 못 받은 사용자가 생긴다. 이것은 정합성 위반이 아니라 재려는 현상이라 2-5 측정 뒤부터 **실패로 보지 않고 `correctness.issuedWithoutSuccessResponse`(DB에 쿠폰이 있는데 그 사용자가 201·200을 받지 못한 수)로 센다.** DB 정합성 검사는 바꾸지 않았다. 그 전 실행(2-4)은 이 검사에서 실패로 끝났다.

**부하 종료와 서버 작업 종료를 구분한다.** 2-5 측정 뒤부터 도구는 k6가 끝나도 표본을 계속 모으고, Hikari 사용 중 0·Tomcat 사용 중 1 이하(표본 요청 자신)·쿠폰 수 변화 없음이 3초 이어질 때 서버 작업이 끝난 것으로 본다(`drain`). 최대 120초(`COUPON_LOAD_DRAIN_SECONDS`)까지 기다리고, 넘으면 `drained=false`로 남긴다. 그 전 실행은 k6 종료 직후 관찰을 멈췄다.

TPS만 보면 거절이 쓰는 DB 처리량이 보이지 않는다. 600/s 1단계에서 매진 뒤 1초에 약 700건의 응답(대부분 409)이 DB를 거쳐 끝났다. "DB까지 간 요청"은 1단계 첫 측정 뒤에 추가한 지표다.

### 합격선

같은 PC에서 k6·앱·MySQL이 CPU를 나눠 쓰므로 "몰려도 평소 값 그대로"는 기준으로 삼지 않았다. 사람이 느리다고 느끼지 않는 정도를 기준으로 했다(0.1초 이하는 즉시, 1초 이하는 흐름이 끊기지 않음).

| 항목 | 합격선 | 이유 |
| --- | --- | --- |
| 정합성 | 한도 초과·중복 0건 | 예외 없음 |
| 상품 조회 p95(쿠폰이 몰리는 중) | 100ms 이하, 실패 0건 | 평소 약 10ms의 10배까지는 즉시로 느껴진다 |
| 못 받은 사람(409) p95 | 100ms 이하 | 결과를 바꿀 수 없으니 빨리 알려 준다 |
| 받은 사람(201) p95 | 1초 이하 | 받는 사람은 조금 기다려도 된다 |
| 서버 오류·타임아웃 | 0건 | |
| 회복 | 매진 뒤 5초 안에 위 기준으로 돌아옴 | |

판정 부하는 **600/s(한계 X의 2배)**, 쿠폰 5,000장이다. 1200/s(4배)는 k6도 정해진 만큼 보내지 못해 측정이 흔들리므로 관찰용으로만 둔다.

## 1단계: 요청 → RDB

구조: 한 TX에서 한도 확인·발급 수 증가·쿠폰 저장. UNIQUE(campaign_id, user_id)로 1인 1매. 마지막 쿠폰 경쟁을 막는 두 방식을 비교했다.

- **잠금(ROW_LOCK)**: 캠페인 행 `FOR UPDATE` → 기존 쿠폰 확인 → 앱에서 한도 확인·증가 → 저장
- **조건부 UPDATE(CONDITIONAL_UPDATE)**: 기존 쿠폰 확인 → `UPDATE … WHERE issued_count < total_quota` → 저장. 따닥은 UNIQUE에서 만나고, rollback 뒤 다시 읽어 200

**초 단위로 본 매진 전후 (300/s·600/s)**

- 매진 전: 초당 발급은 잠금 약 170~230건, 조건부 약 210~300건에서 더 오르지 않았다. 그동안 Hikari 대기는 계속 160, 발급·상품 p95가 매초 늘었다(600/s 잠금은 7초대까지).
- 매진 뒤 **조건부**: 밀린 요청이 빠지자 409 응답이 10ms대로 돌아왔다(300/s는 매진 2초 뒤, 600/s는 약 12초 뒤).
- 매진 뒤 **잠금**: 300/s는 약 8초 뒤 회복했다. **600/s는 실험이 끝날 때까지(매진 뒤 약 18초) 회복하지 못했다.** Hikari 대기 160, 409 p95 약 3초, 상품 p95 약 3초가 계속됐다.
- 해석(요청별 잠금 보유 시간은 직접 재지 않았다): 두 방식 모두 거절할 요청도 캠페인 행 잠금을 거친다. 잠금 방식은 잠금을 얻은 뒤 기존 쿠폰 조회·한도 확인을 하고 rollback하므로 요청마다 잠금을 쥔 채 DB를 더 오간다. 조건부는 기존 쿠폰·캠페인 조회를 잠금 없이 먼저 하고, 잠금은 UPDATE 한 문장부터 rollback까지만 쥔다. 한계 찾기 400/s에서 행 잠금 평균 대기도 잠금 168ms, 조건부 125ms였다.

### 1단계에서 보인 문제

1. **한 캠페인 행 앞에 한 줄로 선다.** 처리량이 약 300/s에서 멈추고, 그 이상 온 요청은 커넥션 풀·톰캣 큐에서 수 초를 기다린다.
2. **쿠폰과 무관한 API까지 느려진다.** 상품 조회가 10ms → 수 초. 같은 커넥션 풀과 톰캣 스레드를 쓰기 때문이다.
3. **매진 뒤에도 모든 요청이 DB까지 간다.** 600/s 조건부는 보낸 19,475건 중 14,292건(73%)이 매진 뒤 요청이었고, 결과가 정해진 거절을 위해 DB 연결을 잡았다.
4. **거절도 로그를 남긴다.** 409마다 WARN 로그가 남아 40초에 최대 약 119MB.

정합성(한도·1인 1매·따닥·rollback)은 DB만으로 지켜졌다. 문제는 **정확성이 아니라 대기와 피해 범위**다.

- 상품 조회 실패·Hikari 연결 획득 실패는 0건. Hikari 대기는 세 번 모두 최대 160.

- 쿠폰 INSERT가 5,000보다 조금 많은 것(5,005~5,017)은 따닥이 유일 제약에서 만나 실패한 저장이다.
- 600/s·1200/s에서는 InnoDB 행 잠금 대기 횟수가 UPDATE 수와 같았다(18,007·19,553). UPDATE마다 앞 요청의 잠금을 기다렸다.
- 회복: 300/s는 매진 약 2초 뒤 409가 10~30ms로 돌아왔다. **600/s는 실험이 끝날 때까지(매진 뒤 약 19초) 돌아오지 못했다**(마지막 초 409 p95 848ms). 1-2의 600/s 조건부(약 12초 뒤 회복)와 다르다. 같은 조건에서도 회복 시간이 흔들린다.

| 정합성 | 0건 | 0건 | 통과 |

## 2단계: 요청 → Redis 발급 판단 → RDB

구조: Redis Lua가 남은 수·통과한 사용자로 먼저 판단하고 통과한 요청만 1단계의 DB 발급 TX로 보낸다. 매진·종료는 DB에 가지 않는다. 같은 사용자의 뒤 요청은 앞 요청이 끝나기 전이면 409 "처리 중"이다([ADR 0068](../adr/0068-judge-coupon-issue-in-redis-before-db.md)). 실행마다 캠페인을 만든 뒤 관리자 준비 API로 판단 정보를 채운다. Redis 7.0.15 컨테이너를 같은 PC에서 함께 돌렸다.

### 2-0. 거를 곳은 왜 Redis인가 — 앱 메모리와 비교

**질문:** 1단계에서 결과가 정해진 요청은 DB 앞에서 걸러야 한다는 것을 확인했다. 그 거르는 곳이 왜 앱 메모리가 아니라 Redis여야 하나? 2단계의 효과(매진 뒤 DB UPDATE 0)는 Redis여서 얻은 것인가, DB 앞에서 걸러서 얻은 것인가?

이 비교는 2-1~2-3을 실행한 뒤에 따로 실행했다. Redis를 고르는 근거라서 2단계 맨 앞에 둔다.

판단 규칙은 그대로 두고, 판단 정보를 둘 곳만 바꿨다. `commerce.coupon.issue-gate.store=LOCAL`이면 `LocalCouponIssueGate`가 Lua와 같은 규칙(수량·중복·R/A 예약·확인·보상)을 이 앱의 메모리에서 캠페인별 잠금으로 처리한다. 기본값은 REDIS다.

#### 서버 두 대 — 테스트로 확인

`CouponIssueGateTwoServersTest`는 실제 앱을 두 대 띄우지 않고 판단 객체 두 개로 서버 1·2를 흉내 낸다. 앱 메모리 객체는 각자 자기 메모리를 가지고, Redis 객체 두 개는 같은 Redis를 본다. 두 서버를 같은 DB 값(남은 2장, 발급자 없음)으로 준비한 뒤 A·C는 서버 1, B는 서버 2로 동시에 보낸다.

| 남은 2장, A·B·C 동시 요청 | A (서버 1) | B (서버 2) | C (서버 1) | 통과 |
| --- | --- | --- | --- | ---: |
| 앱 메모리 | 통과 | 통과 | 통과 | **3** |
| Redis | 셋 중 둘 통과, 하나 매진 | | | 2 |

```text
앱 메모리   서버 1: 2장 남음 → A 통과(1장) → C 통과(0장)
            서버 2: 2장 남음 → B 통과(1장)        ← 서버 1이 2장을 쓴 걸 모른다
Redis       두 서버가 같은 "2장 남음"을 본다 → 두 명만 통과, 한 명 매진
```

같은 사용자도 마찬가지다. A가 서버 1에서 통과한 뒤 다시 누른 요청이 서버 2로 가면, 앱 메모리의 서버 2는 A를 몰라서 또 통과시킨다. Redis에서는 서버 2도 A의 기록을 보고 처리 중으로 거른다.

원인은 **앱 메모리는 서버끼리 남은 수와 사용자 기록을 공유하지 않는다**는 것이다. 최종 한도와 중복은 DB 조건부 UPDATE·UNIQUE가 막는다. 그래서 셋째 통과자는 DB에서야 거절되고, 앞에서 거르려던 요청이 DB까지 간다. 이 테스트는 판단 계층만 본다. HTTP·DB를 포함한 두 서버의 부하 실험은 하지 않았다.

#### 서버 한 대 — 부하 실험

같은 조건(600/s·40초·5,000장·상품 조회 20/s·매 50번째 동시 두 요청, Hikari 40, Tomcat 200)에서 저장소만 바꿔 각 1회 실행했다. 계측(JDBC timing)은 켜지 않았다.

| 지표 | 앱 메모리 | Redis |
| --- | ---: | ---: |
| 실제 보낸 발급 요청 | 13,351 | 14,468 |
| 201 / 200 / 409 / 409 진행 중 | 5,000 / 30 / 8,250 / 71 | 5,000 / 19 / 9,367 / 82 |
| 발급 수 = 쿠폰 행 = 서로 다른 사용자 | 5,000 | 5,000 |
| 마지막 신규 발급 | 29.8초 | 27.9초 |
| 201 p95 | 8,330ms | 8,072ms |
| 상품 조회 p95 / 실패 | 7,398ms / 0 | 7,298ms / 0 |
| 매진 뒤 요청 / 그 DB UPDATE | 7,455 / 0 | 8,695 / 0 |
| 매진 뒤 응답 p50 / p95 | 11ms / 2,902ms | 9ms / 2,916ms |
| DB UPDATE / INSERT | 5,000 / 5,000 | 4,965 / 4,993 |
| Hikari 대기 최대 / 획득 실패 | 160 / 0 | 160 / 0 |
| Tomcat 사용 중 최대 | 200 | 200 |
| 행 잠금 평균 대기 / 동시 대기 최대 | 210.7ms / 38 | 199.1ms / 38 |

**관찰:** 서버 한 대에서는 두 저장소의 결과가 거의 같다. 둘 다 매진 뒤 DB UPDATE가 0이고 정합성 위반이 없다. 매진 전 대기(Hikari 160·Tomcat 200·행 잠금 약 200ms)도 같은 모양이다. 수치의 작은 차이는 실제 보낸 요청 수가 다르고 각 1회 실행이라 우열로 보지 않는다. 이번 Redis 실행의 201 p95(8,072ms)는 [2-1](#2-1-매진까지-쿠폰-5000장-각-40초)의 7,138ms와 다르다. 같은 조건의 다른 실행 사이에도 이 정도 차이가 있다.

**확인한 것:** 2단계의 효과는 "DB 앞에서 결과가 정해진 요청을 거른 것"에서 나왔다. 서버 한 대라면 앱 메모리로도 같은 효과를 얻는다. Redis가 필요한 이유는 속도가 아니라, **서버가 여러 대일 때 모두가 같은 남은 수·사용자 기록을 봐야 하기 때문**이다. 이는 위의 두 서버 테스트로 확인했다.

### 2-1. 매진까지 (쿠폰 5,000장, 각 40초)

| 속도 | 보낸 수 | 201 / 200 / 409 / 409 처리 중 | 매진 시각 | 201 p95 | 409(매진 뒤) p50 / p95 | 상품 p95 | DB UPDATE 수 | 매진 뒤 DB UPDATE | 앱 로그 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 300/s | 11,493 | 5,000 / 3 / 6,393 / 97 | 23.1초 | 3,687ms | 5 / 225ms | 3,114ms | 4,924 | 0 | 38.3MB |
| **600/s** | 16,539 | 5,000 / 5 / 11,439 / 95 | 24.5초 | 7,138ms | 6 / 1,492ms | 6,570ms | 4,938 | 0 | 68.1MB |
| 1200/s | 27,522 | 5,000 / 3 / 22,422 / 97 | 23.6초 | 6,954ms | 9 / 880ms | 6,343ms | 4,945 | 0 | 133.0MB |

- 정합성: 세 번 모두 발급 수 = 쿠폰 행 = 서로 다른 사용자 = 201 수 = 5,000. 실험 뒤 Redis는 남은 수 0, 통과한 사용자 5,000으로 DB와 같았다.
- 따닥 쌍은 `201+409(처리 중)` 95~97쌍, `200+201` 3~5쌍, 매진 뒤 `409+409`. 두 장 발급은 없었다.
- **DB UPDATE가 보낸 요청 수가 아니라 쿠폰 수만큼으로 줄었다.** 600/s에서 1단계 18,007 → 4,938. 매진 뒤 DB UPDATE는 세 번 모두 0. 5,000보다 조금 적은 것은 0.5초 표본 구간 밖(시작 직후·끝)의 실행이 빠진 값이라 근사다. 쿠폰 INSERT도 4,958~4,978로 같은 이유의 근사다.
- 1200/s는 1단계(21,254건)보다 많이 보냈다(27,522건). 거절 응답이 빨라져 k6 가상 사용자가 덜 묶였다.
- 상품 조회 실패·Hikari 연결 획득 실패는 0건.

**초 단위로 본 매진 전후 (600/s)**

- 매진 전(0~24초): 초당 발급 약 160~240건. Hikari 대기 160, 톰캣 스레드 200이 계속 찼고, 발급 p95가 매초 늘어 7초대, 상품 p95도 6초대까지 갔다. 1단계와 같은 모습이다.
- 매진 뒤: 약 2초 만에(26초부터) 409가 7~40ms로 돌아왔고 Hikari 대기가 0이 됐다. 300/s·1200/s도 매진 1~3초 뒤 같은 상태가 됐다.
- 해석: Redis는 실행된 요청의 수량·중복을 빠르게 판단한다. 그러나 통과한 요청이 DB 완료까지 톰캣 스레드를 점유하므로, 스레드가 포화되면 아직 Redis를 실행하지 못한 요청도 앞에서 기다린다. DB는 약 220/s로 5,000장을 저장했다. 이 실험에서는 Redis 예약 완료 시각을 따로 재지 않았다. (처음에는 "Redis가 5,000명을 약 8초 만에 통과시킨다"고 적었는데, 이는 5,000 ÷ 600으로 계산한 값이지 측정값이 아니고, 동기 경로의 스레드 한도와도 맞지 않아 고쳤다.)

### 2단계 채점 (600/s)

| 항목 | 합격선 | 1단계 | 2단계 | 판정 |
| --- | --- | --- | --- | --- |
| 정합성 | 0건 | 0건 | 0건 | 통과 |
| 상품 조회 p95 | 100ms 이하, 실패 0 | 5,543ms | 6,570ms | 불합격 |
| 409 p95 | 100ms 이하 | 4,040ms(매진 뒤) | 1,492ms(매진 뒤, 밀린 요청이 빠지는 약 2초 포함) | 불합격 |
| 201 p95 | 1초 이하 | 6,034ms | 7,138ms | 불합격 |
| 서버 오류·타임아웃 | 0건 | 0건 | 0건 | 통과 |
| 회복 | 매진 뒤 5초 안 | 19초 안에 안 됨 | 약 2초 | **통과** |

### 2단계에서 보인 문제

1. **통과한 n명(5,000)이 DB 처리량(약 220/s)보다 빨리 들어온다.** 매진 전 구간은 1단계와 같은 한 줄 서기다. Redis는 "누가 받을지"는 빨리 정하지만 DB 저장 속도는 그대로다.
2. **통과한 요청이 스레드·커넥션을 붙잡아 다른 요청까지 기다린다.** 매진 전에는 상품 조회가 1단계보다 나아지지 않았다(같은 PC에 Redis가 더해진 영향도 섞여 있다).
3. 거절 로그는 1단계와 비슷하게 남는다(600/s 68MB, 1200/s 133MB).

## 2-2. 시간대별 기록 읽기 — 600/s에서 대기가 쌓이고 풀리는 과정

600/s·40초·5,000장 실험의 시간대별 JSON(DB 조건부 UPDATE, Redis 판단 → DB)으로 커넥션 대기·상품 조회 지연·매진 후 회복을 살펴봤다.

### 먼저 읽는 법

원본의 `timeline.s = 10`은 시작 후 **10초 이상 11초 미만** 구간이다. 신규 발급 완료 수와 응답 p95는 그 구간에 **응답이 끝난 요청** 기준이다. 그 초에 새로 도착한 요청 수를 뜻하지 않는다. Hikari 대기는 해당 초의 수집 표본 중 최대값이다. DB UPDATE는 0.5초 간격 누적 카운터의 차이로 계산한 근사여서 신규 발급 완료 수와 정확히 일치하지 않을 수 있다. 관찰 누락을 대기 0으로 해석하지 않는다.

### Redis를 추가한 실험의 실제 흐름

| 시작 후 구간 | 신규 발급 완료(201) | DB UPDATE 근사 | Hikari 대기 최대 | 상품 조회 p95 |
| --- | ---: | ---: | ---: | ---: |
| 0~1초 | 127 | 143 | 0 | 300ms |
| 1~2초 | 163 | 159 | 159 | 982ms |
| 5~6초 | 201 | 199 | 160 | 3,467ms |
| 10~11초 | 227 | 227 | 160 | 5,780ms |
| 18~19초 | 237 | 239 | 160 | 6,853ms |
| 24~25초 | 21 | 1 | 158 | 5,326ms |
| 25~26초 | 0 | 0 | 157 | 1,247ms |
| 26~27초 | 0 | 0 | 0 | 52ms |
| 27~28초 | 0 | 0 | 0 | 11ms |

- **1~2초에는 이미 커넥션 대기가 관찰된다.** 대기 최대 159, 상품 조회 p95 982ms다. 기록 해상도만으로 그 초 내부에서 무엇이 먼저 증가했는지는 알 수 없다.
- **발급이 진행되는 동안 대기가 지속된다.** 5~6초, 10~11초, 18~19초 모두 Hikari 대기 최대 160이며 상품 p95는 수 초까지 늘었다. 이 실험 전체에서 Hikari 사용 중 최대 40·Tomcat 사용 중 최대 200·DB 행 잠금 동시 대기 최대 38도 기록됐다. 이 세 최댓값이 같은 순간의 상태였다고 단정하지 않는다.
- **마지막 신규 발급 응답은 약 24.5초다.** 24~25초에는 새 발급 21건이 끝났고, 다음 구간에는 새 발급이 없는데도 이전 요청의 응답 지연이 남았다.
- **26~27초에는 Hikari 대기가 0이고 상품 p95도 52ms로 내려온다.** 27~28초에는 상품 p95 11ms다. 쿠폰을 모두 저장한 뒤에도 남은 거절 요청을 DB 발급 UPDATE까지 보내지 않은 효과와 일치하는 관찰이다.

### DB만 사용한 실험과 비교

동일한 27~28초 구간에서 DB만 사용한 실험은 신규 발급 0건인데도 UPDATE 670회·Hikari 대기 최대 159·상품 p95 1,967ms였다. Redis 실험은 신규 발급 0건·UPDATE 0회·Hikari 대기 0·상품 p95 11ms였다. DB 실험의 마지막 201은 약 20.9초, Redis 실험은 약 24.5초이므로 각자의 매진 후 경과 시간은 다르다. 동일 PC의 별도 실행 각 1회이며, 통제된 운영 성능의 우열 확정으로 확대하지 않는다.

### 확인한 것과 아직 모르는 것

**확인:** Redis를 추가해 매진 뒤 발급 UPDATE와 대기를 줄였다. 그러나 매진 전에는 Hikari 대기와 상품 응답 지연이 함께 지속됐다. 이를 다음 실험에서 줄일 대상으로 삼을 수 있다.

**미확인:** 원본에는 1초 단위 Hikari 대기·응답 지연·UPDATE 집계가 있지만, **Tomcat 사용량·Hikari 사용 중·DB 행 잠금 대기의 시간대별 값과 개별 요청의 커넥션 획득/잠금/실행 시간은 보존돼 있지 않다.** 따라서 “DB 잠금 → 커넥션 부족 → Tomcat 포화”의 정확한 시작 순서나 요청별 지연 비중을 확정할 수 없다. 0.5초마다 표본을 수집했다는 사실과 모든 원시 표본을 JSON으로 보존했다는 것은 구분한다.

다음으로 커넥션 획득·점유와 SQL 호출 시간을 구분해 지연이 발생하는 구간을 확인한다. 이후 유입 속도·진행 중 실행 수·대기 위치를 조절할 후보를 비교하며, 발급량·거절률·상품 조회 지연을 함께 평가한다.

## 2-3. 요청별 시간 분해 — Redis 이후 커넥션 획득과 DB 작업

### 목적·조건

REDIS_SYNC 경로에서 **커넥션을 얻기까지와 얻은 뒤 어디에 시간이 쓰이는지** 측정했다. Redis 판단·동기 DB 발급을 사용하며 유입·동시 실행 제한과 대기열은 적용하지 않은 조건이다.

- 기존과 같은 목표 600/s·40초·쿠폰 5,000장·상품 조회 20/s·매 50번째 동시 두 요청·Hikari 최대 40/최소 30·Tomcat 최대 200.
- 같은 PC의 격리된 MySQL 8.0·Redis 7.0.15·실제 API 별도 JVM·k6. Kafka·worker는 기동하지 않음.
- 계측 단위 검사 뒤 30/s·4초·40장의 짧은 실제 앱 검사로 계측·정합성 확인.
- 본측정 1회, 이어서 HTTP와 서버를 요청 ID로 연결한 본측정 1회. 각각 다른 실행이며 반복 평균으로 합치지 않았다. 아래 상세 표는 요청 ID 연결 실행이다.
- 계측은 테스트 전용 classpath에서만 기동한다. 일반 제품 API에는 계측용 조회 경로를 등록하지 않는다. 추가 계측 비용이 있으므로 과거 비계측 실행과의 지연 차이를 성능 회귀나 설정 우열로 읽지 않는다.

### 재현

```bash
# Java 21과 로컬 Testcontainers Docker endpoint 설정 후 실행
COUPON_LOAD_MODE=REDIS_SYNC COUPON_LOAD_STAGES=600:40 COUPON_LOAD_QUOTA=5000 \
COUPON_LOAD_LABEL=week8-redis-jdbc-correlated-600 COUPON_LOAD_JDBC_TIMING=true \
./gradlew :apps:commerce-api:experimentTest --tests '*CouponLoadExperimentTest' --rerun

python3 scripts/analyze-week8-jdbc-timing.py \
  build/week8-redis-jdbc-correlated-600.json \
  --output build/week8-redis-jdbc-correlated-600-analysis.json
```

### 지표의 경계

- **HTTP 시간:** k6가 관찰한 요청 전송·응답 대기·응답 수신 시간이다. k6의 blocked·DNS·연결 설정 시간은 이 duration에 포함하지 않는다([k6 공식 지표 정의](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)).
- **서버 처리 시간:** 실험 servlet filter 진입부터 chain 반환까지. 작업 스레드 배정 이전과 네트워크 응답 구간은 직접 측정하지 않는다.
- **커넥션 획득:** 요청 안의 `getConnection()` 호출 시간 합계. 신규 발급은 사용자 조회·기존 쿠폰 조회·발급 TX를 거쳐 요청당 실제 3번 획득했다. 아래 837ms는 한 번의 획득 시간이 아니다.
- **커넥션 점유:** 획득 완료부터 close 완료까지의 합. SQL·commit/rollback 시간이 포함된다. SQL 시간을 점유 시간에 다시 더하지 않는다.
- **조건부 UPDATE 시간:** JDBC execute 호출 시간으로 DB 행 잠금 대기·드라이버·네트워크·실제 실행을 포함한다. 단일 요청의 순수 행 잠금 시간은 아니다.
- **HTTP − 서버:** 같은 requestId로 연결해 요청별 차이를 낸 뒤 집계했다. 별도 p95끼리 빼지 않았다. 이 차이에는 filter 바깥과 네트워크가 포함되며 이를 전부 Tomcat queue 시간으로 부르지 않는다. 응답 완료와 filter 반환의 겹침 때문에 작은 음수 차이가 나올 수도 있다.

### 요청 흐름 위에서 측정 시간을 읽기

아래는 **새 쿠폰 발급에 성공한 요청 5,000건**을 기준으로 설명한다. 기존 쿠폰이 있거나 Redis에서 거절된 요청은 중간에 응답하므로 별도 흐름이다.

먼저 서로 다른 두 자원을 구분한다.

| 이름 | 역할 | 지금 설정 |
| --- | --- | --- |
| Tomcat 작업 스레드 | 요청 하나를 맡아 필터·Controller·Service 코드를 실행한다. DB 연결이나 잠금을 기다리는 동안에도 그 요청을 담당한다 | 서버 한 대에서 최대 200개. 처음부터 항상 200개가 있는 것은 아님 |
| HikariCP의 DB 커넥션 | 서버 코드가 DB에 SQL을 보낼 때 빌리는 연결이다. 사용한 뒤 풀에 반환해 다음 요청이 다시 쓴다 | 최대 40개 |

**요청은 먼저 Tomcat 작업 스레드를 배정받고, 그 스레드가 DB 작업이 필요해질 때 HikariCP에서 커넥션을 빌린다.** 스레드 배정과 DB 커넥션 획득은 다른 단계다.

#### 전체 흐름: ① 스레드 배정 전 → ② 배정받아 처리 → ③ 응답 수신

```text
클라이언트가 쿠폰 발급 요청을 보냄
  ↓
① 요청이 서버에 도착하고 담당 Tomcat 작업 스레드를 배정받는 과정
   · 요청 전송·서버 도착 등도 포함한다.
   · Tomcat은 요청을 처리할 작업 스레드를 배정한다.
   · 사용할 작업 스레드가 없으면 배정 전에 기다릴 수 있다.
   · 현재 설정의 “최대 200개 중 요청을 맡을 하나를 배정받음”이 여기다.
  ↓ 담당 작업 스레드가 생김
② 배정받은 Tomcat 스레드가 서버 코드를 진행하는 과정
   · 처리 시간을 재는 코드 → Controller → Service 등을 같은 스레드가 진행한다.
   · HikariCP에서 연결을 기다리거나 DB 잠금을 기다릴 수도 있다.
   · 기다리는 동안에도 담당 Tomcat 스레드는 다른 요청을 맡지 못한다.
  ↓ 서버가 응답을 작성함
③ 응답이 클라이언트에 전달되어 수신되는 과정
  ↓
클라이언트가 결과를 받음
```

①의 “200개 중 하나를 배정받는다”는 것은 요청을 담당할 **작업 스레드**를 얻는다는 뜻이다. 아직 **DB 커넥션 40개 중 하나를 얻은 것은 아니다.** HikariCP는 ② 안에서 등장한다.

#### “필터”와 “스톱워치”가 뜻하는 것

**“계측 필터”는 이번 실험에서 요청 처리 시간을 재려고 추가한 코드**다. 원래 업무가 수행되는 별도의 서버나 대기 장소를 뜻하지 않는다.

필터는 Controller로 요청을 넘기기 전과, 아래 처리가 끝나 돌아온 뒤에 코드를 실행할 수 있는 장치다. 인증 확인·로그 기록 등에도 쓴다. 이번에는 시간을 재는 코드를 넣은 실험용 필터를 사용했다.

**“스톱워치”는 실제 시계나 별도 서버가 아니라, 시작·종료 시각의 차이를 계산하는 코드를 비유한 말**이다.

```text
Tomcat 작업 스레드를 배정받음
  ↓
[계측 필터] 시작 시각을 기록함       ← “스톱워치 켬”
  ↓
Controller → Service → Redis·DB 작업 → 응답 생성
  ↓
[계측 필터] 종료 시각을 기록함       ← “스톱워치 끔”

종료 시각 − 시작 시각 = 필터 안에서 보낸 시간
```

필터가 별도의 스레드를 받는 것이 아니다. **이미 배정받은 Tomcat 스레드가 필터 코드도 실행한다.** 이 계측에는 Hikari·DB에서 기다린 시간도 포함되므로 “CPU가 실제 계산한 시간”과는 다르다. 필터 진입 전 Tomcat 스레드 배정 대기는 재지 못한다.

#### ② 안을 자세히 보기: HikariCP는 어디에 있나

아래 전체를 요청을 맡은 Tomcat 스레드가 진행한다. 현재 코드는 Redis보다 먼저 DB에서 사용자와 기존 쿠폰을 확인한다.

```text
② 담당 Tomcat 스레드로 요청 처리 시작
  ↓
계측 필터: 시작 시각 기록
  ↓
Controller → CouponFacade
  ↓
사용자 확인
  → HikariCP에 DB 커넥션을 요청함                 [첫 번째 획득]
     · 빈 연결이 있으면 빌림
     · 모두 사용 중이면, 담당 Tomcat 스레드가 기다림
  → 연결을 얻은 뒤 사용자 SELECT
  → 연결 반환
  ↓
기존 쿠폰 확인
  → HikariCP에서 DB 커넥션을 빌림                 [두 번째 획득]
     · 여기서도 빈 연결이 없으면 기다릴 수 있음
  → 기존 쿠폰 SELECT
  → 연결 반환
  → 이 예시는 기존 쿠폰이 없으므로 다음으로 진행
  ↓
Redis에서 남은 수·종료·사용자 중복 판단
  → 이 예시는 통과했으므로 DB 발급으로 진행
  ↓
DB 발급 트랜잭션
  → HikariCP에서 DB 커넥션을 빌림                 [세 번째 획득]
     · 연결을 얻기 전: 커넥션 획득 대기
  → 기존 쿠폰 재확인·캠페인 조회
  → 조건부 UPDATE
     · 다른 요청이 같은 캠페인 행을 수정 중이면 DB 행 잠금 대기
     · 이때는 이미 커넥션을 빌린 상태이므로
       Tomcat 스레드와 DB 커넥션을 함께 점유함
  → 쿠폰 INSERT → commit
  → 연결 반환
  ↓
Redis 예약 확정 → Controller에서 201 응답 생성
  ↓
계측 필터: 종료 시각 기록
  ↓
이후 Tomcat 스레드는 다음 요청을 처리할 수 있게 됨
```

HikariCP가 새 작업 스레드를 배정하는 것은 아니다. **Tomcat 스레드가 HikariCP에 “SQL을 보낼 DB 연결을 빌려 달라”고 요청한다.** 반환한 연결은 풀에서 재사용하며 요청마다 DB 연결을 완전히 끊는다는 뜻은 아니다.

두 대기를 구분하면 다음과 같다.

| 기다리는 곳 | 이미 얻은 것 | 아직 기다리는 것 |
| --- | --- | --- |
| ① Tomcat 작업 스레드 배정 전 | 해당 요청을 담당할 작업 스레드는 아직 없음 | 요청을 처리할 작업 스레드 |
| ② HikariCP 커넥션 획득 | 담당 Tomcat 작업 스레드 | SQL을 보낼 DB 커넥션 |
| ② DB 행 잠금 | 담당 Tomcat 작업 스레드 + 빌린 DB 커넥션 | 같은 캠페인 행을 수정할 차례 |

#### 측정한 숫자를 ①·②·③에 붙이면

```text
① 스레드 배정 전 과정 등
  ↓
② 서버 필터 안에서 사용자 조회 → Redis → DB 발급 → 응답 생성
   └ 평균 1.065초를 직접 측정함
  ↓
③ 응답 전달·수신 과정 등

클라이언트가 기다린 전체 시간 ① + ② + ③ = 평균 6.576초
그중 서버 필터 안에서 직접 잰 ②          = 평균 1.065초
두 값의 차이, 즉 남은 시간                = 평균 5.511초
```

**5.511초는 ①과 ③ 등을 합친 나머지 시간**이다. 각각 몇 초인지 따로 재지는 않았다. 따라서 “Tomcat 스레드를 기다리는 데만 5.511초가 걸렸다”고 말할 수는 없다. 실제 응답 전송은 ② 끝부분과 겹칠 수 있어서 위 그림은 경계를 이해하기 위한 단순화다. 전체 시간은 k6의 HTTP duration 기준이며 최초 DNS·연결 설정 시간은 제외한다.

②에서 직접 잰 1.065초를 다시 나누면 다음과 같다.

```text
② 서버 필터 안에서 보낸 시간: 평균 1.065초
│
├─ 커넥션을 얻기까지 걸린 시간의 합계: 평균 0.837초
│    첫 번째 획득 + 두 번째 획득 + 세 번째 획득
│    같은 Tomcat 스레드가 각 연결을 기다린 시간 등이 들어간다.
│    한 번에 0.837초를 기다렸다는 뜻은 아니다.
│
├─ 연결을 받은 뒤 반환할 때까지의 점유 시간 합계: 평균 0.225초
│    │
│    ├─ 조건부 UPDATE 호출: 평균 0.206초
│    │    행 잠금 대기·실제 실행·통신 등이 포함된다.
│    └─ SELECT·INSERT·commit·그 밖의 연결 점유 시간
│
└─ 나머지 서버 처리: 평균 0.003초
     Redis 호출·애플리케이션/JPA 처리 등 여러 비용의 합
```

**0.837 + 0.225 + 0.003 ≈ 1.065초**다. UPDATE 0.206초는 점유 시간 0.225초 안에 이미 들어 있어 다시 더하지 않는다. 위 분해는 요청 순서대로 한 번씩 실행되는 세 단계가 아니라, 요청 안에서 발생한 같은 종류의 시간을 합쳐 보여준 것이다.

이번에 직접 확인한 것은 **② 안의 커넥션 획득 대기와 DB 작업 비용**이다. 여기에 전체 HTTP 시간과 ② 사이에도 큰 차이가 남았고 Tomcat 포화가 함께 관찰됐다. ①의 스레드 배정 전 대기가 유력한 설명이지만, ①·③의 세부 비중까지 분리한 결과는 아니다.

### 요청별 평균 — 연결 실행의 실제 값

단위는 ms다. 서버 처리 시간은 커넥션 획득 + 점유 + 나머지 서버 시간으로 나눌 수 있다. 조건부 UPDATE는 점유 시간의 부분집합이다.

| 요청 | 수 | HTTP 전체 | filter 안 서버 처리 | 커넥션 획득 합계 | 커넥션 점유 합계 | 조건부 UPDATE | HTTP − 서버 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 새 발급 201 | 5,000 | 6,576.1 | 1,065.4 | 837.1 | 225.1 | 205.9 | 5,510.6 |
| 기존 결과 200 | 14 | 5,618.9 | 1,033.7 | 1,020.6 | 10.5 | 0.0 | 4,585.2 |
| 거절 409(진행 중 포함) | 8,952 | 1,161.1 | 108.3 | 85.0 | 20.6 | 0.0 | 1,052.7 |
| 상품 조회 200 | 676 | 3,916.6 | 184.6 | 160.7 | 23.4 | 0.0 | 3,731.9 |

새 발급에서는 INSERT 평균 1.5ms, SELECT 합계 평균 5.3ms, commit/rollback 합계 평균 4.6ms였다. **UPDATE 호출 205.9ms가 연결을 얻은 뒤의 점유 225.1ms 대부분을 차지했다.** MySQL 표본 구간의 행 잠금 대기 평균도 205.7ms, 동시 대기 최대 38였다. 두 평균은 집계 대상·경계가 달라 정확히 빼서 잠금 외 실행 시간을 계산할 수 없지만, 캠페인 행 경합이 큰 비용이라는 해석을 뒷받침한다.

#### 표 읽는 법 — 쿠폰 요청 하나가 겪는 일

5,000장 행사여도 발급 수를 적는 칸은 `coupon_campaign`의 한 줄(`issued_count`)뿐이다. 모든 새 발급이 이 한 줄을 +1 해야 하고, 한 요청이 바꾸는 동안(commit 전까지) 다른 요청은 기다린다. 그래서 발급은 한 명씩 차례로 일어난다.

```text
사용자가 "쿠폰 받기"를 누름 (k6가 요청 전송 시작)
 1. 서버에 도착했지만 비어 있는 톰캣 작업 스레드(최대 200개)를 기다림   ┐ HTTP − 서버 (5,510.6ms)
                                                                         ┘  + k6↔서버 오가는 시간
 2. 톰캣 스레드가 요청을 맡음 ─────────────────────────────────────────┐
 3. HikariCP 커넥션 풀(최대 40개)에서 빈 DB 커넥션을 기다림   837.1ms   │
 4. 커넥션을 잡고:                                                       │ filter 안 서버 처리
    - issued_count +1을 하려는데 앞 요청이 바꾸는 중이라 기다림          │ (1,065.4ms)
      → 차례가 와서 +1 (조건부 UPDATE)                         205.9ms   │
    - 쿠폰 INSERT, commit                                                │
    (커넥션을 잡고 있던 시간 합계                              225.1ms)  │
 5. 결과 정리 ─────────────────────────────────────────────────────────┘
사용자가 201 응답을 받음 (k6가 응답을 끝까지 읽음)              HTTP 전체 6,576.1ms
```

| 표의 이름 | 뜻 |
| --- | --- |
| HTTP 전체 | k6 실험에서 잰 시간. k6가 요청을 보내기 시작해 응답을 끝까지 받을 때까지(`response.timings.duration`: 보내기 + 기다리기 + 받기). TCP 연결 맺기는 빠진다 |
| filter 안 서버 처리 | 톰캣 스레드가 요청을 맡아 계측 filter에 들어온 뒤부터 끝날 때까지 |
| 커넥션 획득 합계 | HikariCP 커넥션 풀에서 빈 커넥션을 기다린 시간. 40개가 모두 쓰이는 중이면 줄을 선다(최대 3초 뒤 실패) |
| 커넥션 점유 합계 | 커넥션을 잡고 있던 시간. 그 안에서 SQL과 commit을 한다 |
| 조건부 UPDATE | 점유 시간 중 `issued_count`를 +1 하는 SQL 하나. 대부분 앞 요청의 행 잠금을 기다리는 시간이다 |
| HTTP − 서버 | HTTP 전체에서 filter 안 처리를 뺀 나머지. 톰캣 스레드를 기다린 시간과 k6↔서버 오가는 시간이 섞여 있다 |

**오가는 시간**은 요청·응답 바이트가 k6와 서버 사이를 이동하고 k6가 응답을 끝까지 읽는 시간이다. 이 실험은 k6와 앱이 같은 PC에서 `127.0.0.1`로 통신해 보통 1ms 미만이다. 다만 부하가 크면 k6도 같은 CPU를 나눠 써서 늦게 보내거나 늦게 읽는 지연이 섞일 수 있다. 그래서 HTTP − 서버의 대부분은 톰캣 스레드 대기일 가능성이 높지만, 둘을 따로 재지는 않았다.

줄줄이 막히는 순서로 읽으면 다음과 같다. 이는 표와 맞는 설명이며 시간 순서를 직접 기록한 결과는 아니다.

1. `issued_count` 한 줄 때문에 발급이 한 명씩 진행된다.
2. 기다리는 요청이 커넥션을 쥔 채로 기다려 커넥션 40개가 찬다.
3. 커넥션을 못 잡은 요청이 톰캣 스레드를 쥔 채로 기다려 스레드 200개가 찬다.
4. 새로 도착한 요청은 스레드를 받지 못해 서버 입구에서 기다린다.
5. 상품 조회도 같은 톰캣 스레드·커넥션 풀을 써서 같이 느려진다.

#### 커넥션 풀은 DB를 지키는 쪽이다

HikariCP는 앱 쪽에 있는 DB 커넥션 풀이다. 앱과 MySQL 사이의 연결을 미리 열어 두고 돌려 쓰며, 이 실험에서는 최대 40개(`maximum-pool-size: 40`)를 쓴다.

```text
요청 1,000개 동시 도착
   ↓
[앱] HikariCP: DB 연결은 최대 40개까지만
   ├ 40개 → DB로 감
   └ 나머지 → 앱 안에서 기다림 (3초를 넘기면 실패)
   ↓
[DB] 동시에 받는 연결은 최대 40개
```

- 풀이 없으면 요청마다 DB 연결을 열어, MySQL 연결 한도(`max_connections`)를 넘기거나 DB의 CPU·메모리가 바닥날 수 있다. 흔히 말하는 "DB가 터진다"는 이런 경우다. 실무에서는 앱 서버 여러 대의 풀 크기 합이 DB 한도를 넘거나, 무거운 쿼리가 몰려 DB CPU가 꽉 차는 경우가 많다.
- 풀은 DB로 가는 연결 수를 제한하고, 넘친 요청을 앱 안에서 기다리게 한다.
- 이번 실험에서 DB는 멈추지 않았다. DB가 받은 연결은 최대 40개였고 행 잠금 동시 대기는 최대 38, 커넥션 획득 실패(3초 초과)는 0건이었다.
- 대신 기다림이 앱 쪽으로 밀려났다. 커넥션을 못 받은 요청이 톰캣 스레드를 쥔 채 기다려 스레드가 찼고, 상품 조회까지 느려졌다. 같은 한 줄에 몰리는 경합은 DB를 멈추게 하기보다 줄을 길게 만들었다.

**풀을 키우면 나아질까 — 아직 재지 않은 질문.** DB 안에서는 `issued_count` 한 줄을 한 번에 한 요청만 바꾼다. 그래서 풀을 80으로 늘려도 DB 안에서 잠금을 기다리는 연결만 늘고 발급 속도는 그대로일 수 있다는 가설이 있다. 반대로 커넥션 대기(837.1ms)가 줄어 스레드가 덜 막힐 가능성도 있다. 어느 쪽인지는 같은 조건에서 풀 크기만 40 → 80으로 바꾼 비교로 확인할 수 있다.

**40은 측정으로 고른 값이 아니다.** `modules/jpa/src/main/resources/jpa.yml`의 `datasource.mysql-jpa.main` 설정(`maximum-pool-size: 40`, `minimum-idle: 30`, `connection-timeout: 3000`)에 있는 값이다. 프로젝트를 시작할 때의 첫 커밋(`Initial commit`)부터 있었고 그 뒤로 바뀌지 않았다. 부하 도구(`CouponLoadExperimentTest`)도 같은 값을 `--datasource.mysql-jpa.main.maximum-pool-size=40`으로 넘긴다. 이번 단계에서 풀 크기를 근거로 정한 적은 없다.

**HikariCP 문서의 풀 크기 기준.** [About Pool Sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)은 다음을 말한다.

- 풀 크기는 "얼마나 크게"가 아니라 "얼마나 작게"의 문제다. 몇십 개 이하의 작은 풀을 권하고, 100개도 대개 과하다고 본다. 소개한 Oracle 실험에서는 연결 수를 2048에서 96으로 줄이는 것만으로 응답 시간이 약 100ms에서 약 2ms로 줄었다. CPU 코어는 한 번에 한 스레드만 실행하므로, 코어보다 많은 연결은 번갈아 실행하는 비용을 늘린다.
- 출발점 공식은 `연결 수 = (코어 수 × 2) + 유효 디스크 수`이며, 이 값 근처에서 부하 테스트로 조정한다. 이 실험의 MySQL은 2코어 VM에서 실행돼 공식으로는 5개 안팎이 출발점이다. 공식은 정답이 아니라 부하 테스트를 시작할 값이며, 40이 너무 큰지는 재지 않았다.
- 이상적인 상태는 풀이 커넥션을 기다리는 스레드로 가득 찬 상태이며, 풀 크기는 사용자 수가 아니라 DB가 감당할 수 있는 만큼으로 정한다. 커넥션 대기 자체는 풀이 의도한 동작이다. 이번 실험에서 문제가 된 것은 그 기다림이 상품 조회와 함께 쓰는 톰캣 스레드를 붙잡았다는 점이다.
- 긴 트랜잭션과 아주 짧은 트랜잭션이 섞인 시스템이 가장 조정하기 어렵고, 풀을 둘로 나누는 것을 해법으로 든다. 락 대기로 길어진 쿠폰 발급과 짧은 상품 조회가 같은 풀을 쓰는 지금이 이 경우에 가깝다.

이 문서가 작은 풀을 권하는 근거는 DB의 CPU·디스크이며, 같은 행 하나의 잠금 경합을 직접 다루지는 않는다. 풀을 키워도 발급이 빨라지지 않는다는 위 추론과 방향은 같지만, 이 실험의 결과로 확인한 것은 아니다.

#### 어디를 늘려도 한 줄 앞에서 기다린다 — 표에서 이어지는 추론

```text
톰캣 스레드를 늘리면 → 늘어난 스레드가 HikariCP 커넥션을 기다린다
커넥션 풀을 늘리면   → 늘어난 커넥션이 DB 행 잠금을 기다린다
결국 모두            → issued_count 한 줄 앞에서 기다린다
```

새 발급 요청 하나가 톰캣 스레드를 쥔 1,065.4ms 중 커넥션 대기 837.1ms와 UPDATE 205.9ms(대부분 행 잠금 대기)가 대부분이다. 스레드와 커넥션은 일하기보다 기다리며 붙잡혀 있었다. 그래서 스레드·풀을 늘리면 기다리는 위치만 앞뒤로 옮겨지고, 발급 속도의 상한은 그 한 줄을 한 요청씩 바꾸는 속도로 남는다고 본다. 이는 표의 숫자와 맞는 추론이며 스레드·풀 크기를 실제로 바꿔 확인한 결과는 아니다.

남는 방향은 두 가지다.

1. 줄 맨 앞을 빠르게 한다. 한 줄을 바꾸는 시간을 줄이거나, 그 한 줄에 몰리지 않게 한다.
2. 줄을 세우는 위치를 바꾼다. 스레드·커넥션을 쥔 채 기다리지 않게, 처리할 수 있는 만큼만 들여보낸다. 처리 속도는 그대로지만 다른 기능이 같이 느려지는 것을 막는다.

상품 조회는 자체 SELECT 합계가 평균 10.6ms인데 HTTP 평균은 3,916.6ms였다. filter 안에서도 커넥션 획득 평균 160.7ms를 기다렸다. 또한 HTTP−filter 차이가 커서 상품 지연을 상품 SQL 자체만으로 설명할 수 없다. 상품 평균은 실험 전체이며 조용해진 매진 후 구간도 포함한다.

### 이번 관찰의 결론과 다음 후보

**직접 확인한 것:** 신규 발급 요청의 커넥션 획득 대기가 크고, 연결을 얻은 뒤에는 조건부 UPDATE 호출이 주요 비용이다. 상품 조회에도 커넥션 획득 대기가 생겼다. Tomcat은 포화되고, 같은 요청을 클라이언트에서 기다린 전체 시간과 서버 코드 안에서 직접 잰 시간 사이에도 큰 차이가 있다.

**해석:** 같은 캠페인 행 경합으로 연결 반환이 늦어지고, Hikari 대기와 작업 스레드 점유가 커져 요청 처리 경로 앞쪽에도 대기가 누적되는 설명과 일치한다. filter 바깥 시간에 Tomcat 대기가 크게 기여했을 가능성이 높지만, 네트워크·커넥터 큐와의 세부 비중을 직접 분리한 것은 아니다.

**이번에 입증하지 않은 것:** 풀을 늘리면 좋아진다는 결론, 특정 제한값·장치의 효과, 다중 서버·장애 시 처리량이나 공정성이다. rate limit·동시 실행 제한·bulkhead·입장 대기열·분산락·Kafka의 채택은 아직 결정하지 않았다.

다음 비교는 **발급 경로로 들어오는 속도/진행 중 요청 수를 조절하거나, 대기를 HTTP 밖으로 옮겼을 때 공유 자원의 대기와 상품 지연이 줄어드는지**를 확인하는 방향이다. 분산락으로 DB 앞에서 대기시키는 경우 Tomcat 점유가 남는지, bulkhead로 DB 자원만 분리했을 때 공용 HTTP 스레드 대기가 남는지도 함께 고려한다. 어떤 장치든 실제 발급 TPS·거절률·대기 시간·매진 시간·다른 API 영향으로 평가한다.

### 정합성·관찰 범위

연결 실행은 발급 요청 13,966건(201 5,000·200 14·409 8,952), 상품 676건을 실제로 시작·완료했다. 목표 600/s만큼 전부 시작한 것은 아니며 k6 VU 상한과 같은 PC의 자원 경쟁 영향을 받는다. 발급 수 = 쿠폰 행 = 서로 다른 발급 사용자 = 201 = 5,000, 상품 실패·커넥션 획득 실패 0이다. 계측 원본 14,642건이 k6 응답과 requestId·status 기준으로 전부 1:1 대응함을 검사했다. 각 실행은 1회 관찰이며 운영 최적값을 정한 결과가 아니다.

## 2-4. DB 앞에서 들어가는 수를 묶으면 — 분산락·세마포어 (기다리기 / 바로 거절)

**질문:** 2-3에서 요청이 커넥션·행 잠금을 쥔 채 기다리는 것을 봤다. DB 발급 TX 앞에서 기다리게 하면(분산락 1개, 세마포어 N개) DB는 보호되는가? 그 기다림 동안 톰캣 스레드는 어떻게 되는가? "기다리면 톰캣 스레드를 쥔다"는 추론을 확인한다.

**조건:** REDIS_SYNC에서 Redis 판단을 통과한 뒤, DB 발급 TX에 들어가기 전에 자리를 기다린다(`commerce.coupon.issue-limit.mode`). 분산락은 Redisson `RLock`(캠페인당 1개, watchdog), 세마포어는 Redisson `RSemaphore`(캠페인당 3자리)다. 서버의 최대 대기는 60초, 넘으면 예약을 돌리고 거절한다. 측정 당시 이 거절은 503이었고, 측정 뒤 429로 바꿨다(아래 "응답 코드"). k6의 요청 제한은 15초라 서버가 기다리는 동안 k6가 먼저 포기할 수 있다. 나머지 조건(600/s·40초·5,000장·상품 조회 20/s·매 50번째 동시 두 요청, Hikari 40, Tomcat 200)은 2-0의 Redis 실행과 같고 각 1회다. 비교 기준은 같은 날 실행한 2-0의 Redis(제한 없음) 결과다.

| 지표 | 제한 없음 | 분산락 (1개) | 세마포어 (3개) |
| --- | ---: | ---: | ---: |

**DB 정합성은 지켰다.** 한도 초과·중복 발급이 없고 발급 수 = 쿠폰 행 = 서로 다른 사용자다. 실험 도구가 실패로 끝난 것은 그와 별개인 **응답 대응 검사(DB 발급 수 = 201 받은 사용자 수)** 때문이다. k6가 먼저 포기해도 이미 실행 중인 서버 TX는 끝까지 진행되므로, 발급됐는데 응답을 받지 못한 사용자가 생겼다. 결과를 먼저 저장한 뒤 검사하도록 도구를 바꿔 숫자를 남겼다.

**관찰 범위의 한계:** 도구는 k6가 끝나면 표본 수집을 멈춘다. 분산락 실행의 마지막 앱 표본은 Tomcat 사용 중 200·커넥션 사용 중 1로, 관찰이 끝날 때도 서버는 처리 중이었다. 그래서 분산락의 저장 시각·발급 수·"응답 못 받은 사용자" 수는 최종값이 아니라 관찰 종료 시점의 값이다.

**관찰**

- **DB는 보호됐다.** 분산락은 행 잠금 대기 0, Hikari 대기 0, 사용 중 커넥션 최대 3이다. 세마포어도 행 잠금 평균 대기가 199ms에서 4ms로 줄었다.
- **톰캣 스레드는 세 조건 모두 200이다.** 기다림이 DB 안에서 락·세마포어 앞으로 옮겨졌을 뿐, 기다리는 요청은 여전히 스레드를 쥐었다.
- **상품 조회는 나아지지 않았다.** 분산락에서는 오히려 15초 시간 초과로 377건이 실패했다. 세마포어도 p95가 7,298ms에서 9,104ms로 늘었다.
- **발급 속도가 줄었다.** 분산락은 TX 전체(조회 포함)를 한 줄로 세워 초당 약 80~90장에 그쳤다. 40초 안에 5,000장을 채우지 못했고 부하가 끝난 뒤에도 저장이 이어졌다. 세마포어 3개는 약 150~170장으로 제한 없음보다 조금 느렸다.
- **발급됐는데 응답을 못 받은 사용자가 생겼다.** 서버가 최대 60초 기다리는 동안 k6는 15초에 포기했고, 서버는 그 뒤에 발급을 끝냈다. 분산락 3,282명, 세마포어 37명이다.

**확인한 것:** "기다리면 톰캣 스레드를 쥔다"는 추론이 측정과 맞았다. DB 앞에서 기다리게 하면 DB 안의 줄(행 잠금·커넥션 대기)은 사라지지만 톰캣 스레드는 그대로 묶이고, 같은 스레드를 쓰는 상품 조회도 보호되지 않는다. 한 줄로 세우는 범위가 넓어지면(분산락) 발급 속도도 떨어진다.

**한계**

- 각 1회 실행이다. 실제 보낸 요청 수가 조건마다 크게 다르다(k6 VU가 응답을 기다리느라 묶였다).
- 서버 대기 60초와 k6 제한 15초가 달라 "발급됐는데 응답 못 받음"이 커졌다. 대기 시간을 클라이언트보다 짧게 두면 이 수는 줄고 503이 늘 것으로 보지만 재지 않았다.
- 세마포어에서 Hikari 대기 86이 남은 이유는 분리하지 않았다(자리 앞의 사용자 확인·기존 쿠폰 조회와 상품 조회 등).
- 세마포어 자리 수는 3만 쟀다.

#### 바로 거절하면 (대기 0초)

기다리면 스레드가 묶였다. 그렇다면 자리가 없을 때 기다리지 않고 바로 거절하면 어떻게 되는가? 세마포어 3자리에 대기 시간을 0초로 두고 같은 조건으로 1회 실행했다. 측정 당시 거절은 503이었다.

먼저 테스트(`CouponIssueSemaphoreFailFastIntegrationTest`)로 장면을 확인했다. 쿠폰 10장에 1·2·3번이 자리를 쥔 동안 4번이 오면 바로 거절된다. 이때 쿠폰은 7장 남아 있었다. 1·2·3번이 끝난 뒤 온 5번은 쿠폰을 받는다. 먼저 온 4번은 쿠폰이 없고 나중에 온 5번은 있다.

- **다른 기능의 피해는 크게 줄었지만 목표에는 못 미쳤다.** 상품 조회 p95가 7,298ms에서 454ms로 세 조건 중 가장 낮았지만, 합격선(100ms 이하)은 넘지 못했다. 발급 응답도 빠르다. Tomcat 최대 200이 순간값인지 계속된 포화인지는 표본으로 따로 계산하지 않았다.
- **선착순은 크게 깨졌다.** 40초 내내 쿠폰이 남아 있었는데 22,088건이 자리 없음으로 거절됐다. 발급이 끝까지 이어졌으므로 거절된 요청마다 그보다 나중에 시작해 쿠폰을 받은 요청이 있다.
- **발급도 느렸다.** 40초에 2,063장으로 5,000장을 채우지 못했다. 자리 3개로 동시에 들어가는 수를 묶었고, Hikari 대기 151도 남았다. 느린 이유를 더 나누지는 않았다(자리 앞의 사용자 확인·기존 쿠폰 조회가 커넥션을 두고 경쟁했을 가능성).
- k6는 거절된 요청을 다시 보내지 않는다. 실제 사용자는 다시 누르므로 거절이 요청을 더 늘릴 수 있다.
- "그 뒤에 시작한 요청"의 순서는 k6 응답 시각 − 응답 시간으로 추정한 시작 시각이다. 서버의 공통 접수 순번을 직접 기록한 지표는 아니다. 대기열의 공정성을 볼 때는 접수 순번을 남겨 비교한다.

**응답 코드:** 측정 뒤 자리 없음 거절(바로 거절, 기다리다 시간 초과)을 503에서 **429**로 바꿨다. 표준이 의도한 거절에 429를 요구하는 것은 아니고(503도 일시적 과부하를 뜻할 수 있다), 이 프로젝트의 구분 정책이다. 의도한 거절과 장애(Redis·자리 확인 불가 503)를 상태 코드로 구분하고, 5xx를 서버 오류로 세는 합격선·모니터링에서 의도한 거절을 장애로 집계하지 않기 위해서다. 자리 확인 자체가 안 되면 503을 유지한다. 위 측정의 거절 수는 응답 문구로 셌으므로 코드 변경과 무관하다.

**확인한 것(두 방식을 합쳐서):** DB 앞에서 들어가는 수를 묶으면 DB 안의 줄은 줄어든다. 하지만 기다리게 하면 톰캣 스레드가 묶여 다른 기능이 느려지고, 바로 거절하면 다른 기능은 지키지만 먼저 온 사람이 떨어지고 나중 사람이 받는다. 둘 다 "선착순으로 받되 다른 기능을 지킨다"를 동시에 만족하지 못했다(바로 거절도 상품 조회 목표 100ms는 넘지 못했다). 또 Redisson `RLock`은 FIFO 락이 아니어서 기다리는 순서도 보장하지 않는다. 그래서 권리는 바로 정하고, 기다림은 요청 밖에 보관하는 방식(대기열)을 다음 후보로 본다.

## 2-5. Redis를 DB 조회보다 먼저 보게 하면 — Lua 앞 DB 조회 제거

### 왜 바꿨나

REDIS_SYNC는 요청마다 DB에서 사용자 확인과 기존 쿠폰 조회를 한 뒤 Redis Lua로 판단했다. 그래서 매진 뒤처럼 결과가 정해진 요청도 DB를 두 번 거쳤다. "이미 받았는가"는 Redis 사용자 기록(준비 때 DB 발급자를 A로 채움)이 판단할 수 있으므로 기존 쿠폰 조회는 같은 일을 두 번 하는 것이다. 사용자 확인은 Redis가 대신할 수 없어, Redis를 통과한 요청만 하도록 옮겼다([ADR 0075](../adr/0075-judge-in-redis-before-any-db-lookup.md)).

```text
바꾸기 전: [DB 사용자 확인] → [DB 기존 쿠폰 조회] → [Redis 판단] → [DB 발급 TX]
바꾼 뒤:                                         [Redis 판단] → [DB 사용자 확인] → [DB 발급 TX]
                                                   매진·종료·이미 받음은 여기서 끝
```

### 앞의 실험을 다시 돌리지 않는 이유

2-0~2-4는 바꾸기 전 구조(Lua 앞 DB 조회 2번)의 기록으로 보존한다. 각 실험의 결론이 이 변경에 영향을 받는지 따져, 새 구조로는 기준 측정 한 번만 했다.

| 실험 | 다시 하나 | 이유 |
| --- | --- | --- |
| 1단계 (DB만) | 아니요 | Redis를 쓰지 않는 DB_ONLY는 바꾸지 않았다 |
| 2-0 앱 메모리 vs Redis | 아니요 | "서버 여러 대라서 Redis"는 판단 정보를 둘 곳의 문제라 Lua 앞 조회와 무관하다 |
| 2-1·2-3 Redis → DB, 시간 분해 | **새 구조로 한 번** | 매진 뒤 요청이 DB에 가지 않게 되어 숫자가 달라질 수 있다. 아래가 그 결과다 |
| 2-4 분산락·세마포어 | 아니요 | "기다리면 스레드가 묶이고 바로 거절하면 선착순이 깨진다"는 DB 앞에서 들어가는 수를 묶는 방식의 성질이다. 통과한 요청이 DB 한 줄 앞에서 기다리는 구조는 그대로다. 다만 2-4의 정확한 TPS·커넥션 대기·상품 지연 수치를 지금 구조에 그대로 적용할 수는 없다. 수치로 비교하려면 같은 코드 단계에서 다시 재야 한다 |

**한계:** 1회 실행이다. 커넥션 획득 실패 1건이 500으로 응답된 원인(Hikari 3초 초과)은 기록했지만, 예외 응답 코드를 바꾸지는 않았다.

## 2-6. DB 저장을 요청 밖으로 — 작업 큐(Redis Stream) + Worker 1개

### 왜 이걸 했나

2-4·2-5에서 남은 문제는 통과한 요청이 DB 저장이 끝날 때까지 톰캣 스레드·커넥션을 쥐고 기다린다는 것이었다. DB 앞에서 들어가는 수를 묶으면 기다리게 할 때 스레드가 묶이고, 바로 거절하면 선착순이 깨졌다. 그래서 받을 사람은 접수 순간에 정하고, DB 저장은 HTTP 요청이 끝난 뒤 Worker가 하도록 옮겼다.

```text
요청 → Redis Lua 한 번: 중복 확인 + 남은 수 차감 + 사용자 기록(R) + Stream에 작업 등록
        ├ 통과 → 202 PENDING (DB에 가지 않음, 톰캣 스레드 반환)
        └ 매진·종료 → 409
Worker(앱 안 스케줄 스레드 1개) → 작업을 꺼냄 → 사용자 확인 → DB 조건부 UPDATE + INSERT(접수 시각 기준)
                               → 예약 확정(R→A) → 처리 완료(XACK)
상태 조회 GET /api/v1/coupon-campaigns/{campaignId}/issues/me → ISSUED / PENDING / CANCELLED / NONE
```

정책(구현 전에 정함): 202 + 상태 조회, 종료 직전 접수는 종료 뒤 처리돼도 발급(접수 시각으로 판단), 확정 거절(없는 사용자·DB 매진·비활성·없는 캠페인)은 취소 기록 + 예약 보상 + 처리 완료, 일시 오류·결과 불명은 처리 완료하지 않고 다시 처리, Worker는 앱 안 1개.

### 조건

2-5와 같다(QUEUE, 600/s·40초·5,000장·상품 조회 20/s·매 50번째 동시 두 요청, Hikari 40, Tomcat 200). Worker는 한 번에 최대 10건을 가져와 한 건씩 처리한다. 요청별 JDBC 계측은 켜지 않았다. 부하 종료 뒤 서버 작업이 끝날 때까지 기다렸다(`drain`). 1회 실행이다.

### 결과

| 지표 | REDIS_SYNC (2-5) | QUEUE |
| --- | ---: | ---: |
| 실제 보낸 발급 요청 | 14,491 | 24,482 |
| "받음" 응답 | 201 5,000 | 202 5,100 (따닥 두 번째 100 포함) |
| "받음" 응답 p95 | 8,109ms | **3ms** |
| 매진 뒤 409 p95 | 2ms | 1ms |
| **상품 조회 p95 / 실패** | 7,336ms / 0 | **12ms / 0** |
| Hikari 대기 최대 / 사용 중 최대 | 160 / 40 | **0 / 2** |
| Tomcat 사용 중 최대 | 200 | **8** |
| 행 잠금 평균 대기 | 206.4ms | **0** |
| 마지막 "받음" 응답 | 28.4초 | **8.3초** |
| 5,000장 모두 저장 | 28.7초 | **52.8초** |
| DB 초당 발급 (대략) | 180~200 | 약 95 |
| 접수 → DB 저장 p50 / p95 / 최대 | - (응답이 곧 저장 완료) | 25.6초 / 42.5초 / 44.1초 |

정합성: 발급 수 = 쿠폰 행 = 서로 다른 사용자 = 5,000, 한도 초과·중복 0. 발급됐는데 성공 응답(201·200·202)을 받지 못한 사용자 0. 실험 뒤 작업 큐는 5,000건, 처리 완료 전 작업 0. 서버 작업은 부하 종료(40.3초) 뒤 53.5초에 끝났다.

**관찰**

- **톰캣 스레드가 묶이지 않았다.** "받음" 응답이 3ms 안에 끝나 Tomcat 사용 중 최대가 8이었다. DB 커넥션 대기와 행 잠금 대기도 0이다.
- **상품 조회가 합격선 안으로 들어왔다.** p95 12ms로 처음으로 100ms 이하를 만족했다. 평소 값(약 10ms)과 비슷하다.
- **선착순은 접수 순간에 정해졌다.** 5,000명이 8.3초 만에 "받음"을 들었고, 그 뒤 요청은 모두 매진이다. 바빠서 거절된 요청은 없다.
- **대신 쿠폰함에 들어오기까지 오래 걸린다.** Worker 1개가 한 건씩 저장해 초당 약 95장, 5,000장을 모두 저장하는 데 52.8초가 걸렸다. 동기 경로(28.7초)보다 느리다. 접수부터 저장까지 p95가 42.5초다.
- Worker가 동기 경로보다 느린 이유는 따로 재지 않았다. 한 건마다 사용자 확인·발급 TX·Redis 확정·처리 완료를 차례로 하고, 커넥션을 두 번 얻으며, DB에 동시에 들어가는 실행이 하나뿐이라 같이 할 수 있는 조회도 줄을 서는 것으로 본다(해석).
- 거절 응답 19,382건이 WARN 로그를 남겨 앱 로그가 약 116MB였다.

**확인한 것:** 기다림을 요청 밖(작업 큐와 Worker)으로 옮기자 톰캣 스레드가 묶이지 않았고, 다른 기능(상품 조회)이 처음으로 합격선을 지켰다. 선착순도 접수 순간에 정해진다. 남은 문제는 **쿠폰함 반영 시간**이다. Worker 1개의 저장 속도가 동기 경로의 절반쯤이라, 접수는 빨라졌지만 실제 발급 완료는 늦어졌다.

**한계:** 1회 실행이다. 응답 시간 목표의 의미가 바뀌었다. 동기 경로의 201은 발급 완료, 여기의 202는 접수다. "발급 완료 1초 이하" 합격선을 접수 시간으로 바꿔 통과로 보지 않는다. 접수부터 저장까지의 허용 시간은 아직 정하지 않았다. 접수→저장 시간은 앱 시계로 남긴 발급 시각(접수 시각)과 INSERT 시각의 차이이며, commit 시각과는 조금 다를 수 있다.

## 2-7. Worker 묶음 저장 — 가져온 작업 10건을 한 TX로

### 왜 이걸 했나

2-6에서 접수부터 쿠폰함 반영까지 p95 42.5초로, 목표(p95 10초 이내)를 넘었다. 목표는 사용자가 접수 결과("접수됨·발급 처리 중")를 본 뒤 쿠폰함으로 이동하는 사이에 저장이 끝나면 된다고 보고 정했다(design.md 7절). 행 잠금·커넥션 대기가 0이었으므로 느린 원인은 경쟁이 아니라 작업 한 건마다 드는 고정 비용(TX 시작·commit, 커넥션 획득, 사용자 확인 따로)으로 봤다. Worker를 늘리면 같은 캠페인 행의 잠금 경쟁을 다시 만들 수 있어, Worker는 하나로 두고 가져온 작업을 한 TX로 저장했다(`commerce.coupon.issue-queue.worker.save-in-batch=true`, 한 번에 최대 10건).

묶음 TX 안에서는 확정 거절(없는 사용자·DB 매진 등)을 예외가 아니라 작업별 결과로 받는다. 예외가 나면 TX가 rollback 대상이 되어 다른 작업의 저장까지 되돌리기 때문이다. 같은 이유로 사용자 확인은 `@Transactional` 서비스 대신 저장소 조회로 한다. 묶음 TX가 실패로 확정되면 한 건씩 처리로 넘기고, 결과를 모르면 모두 다시 처리한다.

### 조건

2-6과 같다(QUEUE, 600/s·40초·5,000장, Worker 1개). 바꾼 것은 저장 방식(한 건씩 → 10건 묶음) 하나다. 1회 실행이다.

### 결과

| 지표 | 한 건씩 (2-6) | 10건 묶음 |
| --- | ---: | ---: |
| 202 p95 | 3ms | 3ms |
| 상품 조회 p95 / 실패 | 12ms / 0 | 12ms / 0 |
| Tomcat 사용 중 최대 / Hikari 사용 중 최대 | 8 / 2 | 5 / 1 |
| 행 잠금 대기 | 0 | 0 |
| DB 초당 발급 (대략) | 약 95 | **약 170~200** |
| 5,000장 모두 저장 | 52.8초 | **29.3초** |
| 접수 → DB 저장 p50 / p95 / 최대 | 25.6초 / 42.5초 / 44.1초 | **11.6초 / 20.0초 / 20.8초** |

정합성: 발급 수 = 쿠폰 행 = 서로 다른 사용자 = 5,000, 한도 초과·중복 0, 응답 못 받은 발급 0, 처리 완료 전 작업 0. 서버 작업은 부하 종료(40.3초) 뒤 41.5초에 끝났다.

**관찰**

- **저장 속도가 약 2배가 됐다.** 5,000장을 29.3초에 모두 저장해 동기 경로(2-5, 28.7초)와 비슷해졌다. 다른 기능 보호(상품 p95 12ms, Tomcat 최대 5)는 그대로다.
- **목표에는 아직 못 미친다.** 접수 → 저장 p95가 20.0초다. 5,000명이 8.3초 만에 접수되는데 저장은 초당 약 180장이라, 늦게 접수된 사람일수록 앞의 작업이 다 저장되기를 기다린다.
- 대략으로 계산하면, 접수가 끝나는 8.3초 전후로 저장도 거의 따라잡아야 p95 10초 안에 든다. 그러려면 초당 약 350장 이상이 필요하다(추론, 재지 않음).

**확인한 것:** 작업마다 드는 고정 비용을 묶어 나누자 저장 속도가 동기 경로 수준으로 올라왔다. 하지만 목표(p95 10초)에는 아직 약 2배 더 빨라져야 한다.

**한계:** 1회 실행이다. 묶음 크기는 10만 쟀다. 묶음 안에서도 쿠폰마다 조건부 UPDATE를 한 번씩 하므로 같은 캠페인 행을 묶음 크기만큼 갱신한다.

## 2-8. 묶음 안에서도 한 줄은 한 번만 — 발급 수 한 번에 +N, 쿠폰 INSERT 한 문장

### 왜 이걸 했나

2-7에서 저장 속도는 초당 약 180장으로 올랐지만 접수 → 저장 p95는 20.0초로 목표(10초)를 넘었다. 묶음 TX 안에서도 쿠폰마다 `issued_count`를 한 번씩 갱신하고(같은 행을 묶음 크기만큼), 사용자 확인·기존 쿠폰 확인·INSERT도 쿠폰마다 따로 보냈다. 실무에서 흔한 "쓰기를 묶기"를 따르되, DB가 마지막 한도 방어선이라는 원칙은 유지했다.

- 사용자 확인과 기존 쿠폰 확인을 묶음 전체에 대해 각각 조회 한 번으로 한다.
- 새로 줄 쿠폰이 모두 한도 안이면 발급 수를 한 번에 올린다: `issued_count + N <= total_quota`일 때만 `+N`(활성·종료 조건 포함, 종료는 묶음에서 가장 늦은 접수 시각으로 판단). 한 번에 못 올리면 쿠폰마다 조건부 UPDATE로 나눠, 들어갈 수 있는 만큼만 발급한다.
- 쿠폰은 여러 행을 INSERT 문 하나로 넣는다. JPA는 IDENTITY 키라 묶어 보내지 못해 이 부분만 JDBC로 보낸다(같은 TX의 연결, UTC 시각).

### 조건

2-7과 같다(QUEUE, 600/s·40초·5,000장, Worker 1개). 묶음 크기 10과 50을 각 1회 실행했다. 첫 50건 실행은 27초 이후 PC가 약 400초 멈춰 요청이 한꺼번에 시간 초과·503으로 끝나 결과에서 뺐고(별도 보관), 다시 실행했다.

### 결과

| 지표 | 2-7 묶음 TX (10건, 쿠폰마다 UPDATE·INSERT) | 묶음 UPDATE (10건) | 묶음 UPDATE (50건) |
| --- | ---: | ---: | ---: |
| 202 p95 | 3ms | 3ms | 3ms |
| 상품 조회 p95 / 실패 | 12ms / 0 | 14ms / 0 | 14ms / 0 |
| Tomcat 사용 중 최대 / Hikari 사용 중 최대 | 5 / 1 | 2 / 1 | 4 / 1 |
| DB UPDATE 문 수 | 4,985 | **495** | **99** |
| 5,000장 모두 저장 | 29.3초 | **14.3초** | **10.3초** |
| DB 초당 발급 (대략) | 약 180 | **약 340** | 접수 속도(약 600)를 따라감 |
| 접수 → DB 저장 p50 / p95 / 최대 | 11.6초 / 20.0초 / 20.8초 | **3.7초 / 5.6초 / 5.9초** | **1.0초 / 1.4초 / 1.5초** |

정합성(두 실행 모두): 발급 수 = 쿠폰 행 = 서로 다른 사용자 = 5,000, 한도 초과·중복 0, 응답 못 받은 발급 0, 처리 완료 전 작업 0. 서버 작업은 부하 종료 뒤 약 1.3초 안에 끝났다.

**관찰**

- **목표를 만족했다.** 접수 → 저장 p95가 10건 묶음 5.6초, 50건 묶음 1.4초로 모두 10초 안이다.
- **같은 행을 갱신하는 횟수를 줄인 효과가 컸다.** UPDATE 문이 약 5,000번에서 495번(10건), 99번(50건)으로 줄며 저장 속도가 2배 이상 올랐다. 50건 묶음은 저장이 접수(마지막 202 8.3초)를 거의 따라잡아, 지연이 주로 접수 속도에 달렸다.
- **동기 경로보다 빨리 모두 저장했다.** 5,000장 저장 완료가 10.3~14.3초로 REDIS_SYNC(28.7초)보다 빠르다. 다른 기능 보호(상품 p95 14ms, Tomcat 최대 2~4)는 그대로다.
- 행 잠금 대기는 0이다. Worker가 하나라 같은 행을 두고 경쟁하는 실행이 없다.

**확인한 것:** 기다림을 요청 밖으로 옮긴 뒤(2-6), 남은 병목은 Worker가 같은 행을 쿠폰마다 갱신하는 비용이었다. 묶음당 한 번만 갱신하자 DB 한도 방어를 유지한 채 목표 안에 들어왔다.

**한계와 대가:** 각 1회 실행이다. 묶음이 클수록 묶음 TX 하나가 실패할 때 다시 처리할 작업도 많고, 한도에 닿는 마지막 묶음은 쿠폰마다 나눠 처리한다. 묶음 크기를 무엇으로 둘지는 정하지 않았다. 실험의 접수 속도(600/s)와 수량(5,000)에서의 결과이며, 접수가 더 빠르거나 수량이 더 많으면 다시 봐야 한다.

## 2-9. 유입 올려 보기 — 1,000/s·1,500/s (작업 큐, 묶음 10건)

### 왜 이걸 했나

판정 부하 600/s는 DB 단계의 한계 X(약 300/s)의 2배로 정한 값이다(1-1). 그때 800/s 이상을 보내지 못한 것은 응답이 수 초로 늘어 k6 VU(상한 1,500)가 요청 하나에 오래 묶였기 때문이다. 이후 "이 PC로는 600/s가 한계"로 확인 없이 가정하고 있었다. 작업 큐에서는 접수가 수 ms로 끝나 같은 VU로 더 보낼 수 있을 수 있어, 목표 유입을 실제로 보냈는지부터 확인했다. 부하 도구가 k6 요약의 실제 송신량과 `dropped_iterations`(VU가 모자라 시작하지 못한 요청 수)를 결과에 남기게 했다.

### 조건

2-8의 마지막 설계(QUEUE, Worker 1개, 묶음 10건, +N·여러 행 INSERT)와 같다. 5,000장, 40초. 유입만 1,000/s, 1,500/s로 바꿨다. 각 1회 실행.

| 상품 조회 p95 / 실패 | 14ms / 0 | 14ms / 0 | 19ms / 0 |
| 5,000장 모두 저장 | 14.3초 | 16.3초 | 17.7초 |
| **접수 → 저장 p95** | **5.6초** | **10.7초** | **13.5초** |

정합성: 세 조건 모두 발급 5,000, 쿠폰 행 5,000, 서로 다른 사용자 5,000, 한도 초과·중복 0.

**관찰**

- **목표 유입을 모두 보냈다.** 시작하지 못한 요청은 0이고, VU는 상한(1,500)의 약 1/3만 썼다. 응답이 짧아져 VU가 오래 묶이지 않았다. 600/s가 이 PC의 한계라는 가정은 이 구조에서는 맞지 않았다. 더 높은 유입은 아직 재지 않았다.
- **입구는 버텼다.** 1,500/s에서도 접수 p95 10ms, Tomcat 최대 14, 상품 조회 p95 19ms였다.
- **늦어진 곳은 저장이다.** 유입이 커질수록 접수가 더 빨리 끝나고(매진 8.3초 → 3.3초), 그 뒤 Worker 하나가 5,000건을 비우는 시간은 비슷했다(모두 저장 14~18초). 그래서 접수 → 저장 p95가 5.6초 → 13.5초로 늘어 10초 목표를 넘었다.

**해석**

이 범위에서 유입이 늘어 생긴 문제는 입구(Tomcat·Redis 판단)가 아니라 **저장 속도**다. 대기열·rate limit처럼 입구를 줄이는 장치의 근거는 이 결과에서 나오지 않는다. 저장 쪽(묶음 크기·Worker 구성)이 먼저 검토 대상이다. 별도 소비 앱(Kafka 등)으로 옮기는 것만으로 DB 저장이 빨라진다는 근거는 이 결과에 없다. 1회 실행이고, 1,500/s보다 높은 유입에서 입구가 어떻게 되는지는 모른다.

### 앞 단계의 600/s 결과와의 관계

더 높은 유입을 잴 수 있게 된 것은 구조가 바뀌어 응답이 짧아졌기 때문이다. 앞 단계의 결과를 다시 잴 필요는 없다.

- **앞 단계 구조는 600/s도 이미 버거웠다.** DB만 쓸 때 한계는 약 300/s였고(1-1), Redis 판단·분산락·세마포어도 통과한 요청이 행 앞에서 스레드·커넥션을 쥐고 기다렸다. 이 구조들은 응답이 수 초라 서버도 k6도 더 받을 수 없었다. 유입을 올렸다면 같은 문제가 더 커졌을 뿐, 다음 단계로 넘어간 판단은 바뀌지 않는다.
- **부하를 600/s로 고정한 것은 비교 방법이다.** 모든 단계를 같은 부하로 재야 차이를 구조 때문이라고 말할 수 있다.
- **틀렸던 것은 "이 PC로는 600/s가 한계"라는 일반화다.** 1-1에서 확인한 것은 "DB만 구조에서는 응답이 느려 k6가 더 보내지 못한다"였고, 구조가 바뀐 뒤 다시 확인하지 않았다.
- **바뀌는 것은 마지막 구조의 평가다.** 2-6~2-8의 600/s 결과(접수 3ms, 저장 p95 5.6초)는 그대로 맞다. 2-9는 유입이 더 늘면 저장이 목표를 넘는다는 것을 더했다.

DB에 쿠폰이 쌓이는 속도 자체는 크게 달라지지 않았다. 조건이 다른 실험을 대략 비교한 것이지만, DB만 쓸 때 초당 발급은 약 360에서 더 오르지 않았고(1-1 조건부), 작업 큐에서 5,000장을 저장하는 데는 14~18초(초당 약 300~350)가 걸렸다. 바뀐 것은 이 속도를 **요청이 스레드를 쥔 채 기다리느냐, Worker가 뒤에서 기다리느냐**다. 그래서 유입을 올리자 입구는 버텼지만 접수 → 저장 시간이 늘었다.

## 2-10. 유입이 클 때 묶음 50건 — 저장 쪽의 싼 손잡이부터

### 왜 이걸 했나

2-9에서 유입이 늘자 접수 → 저장 p95가 10초를 넘었다. 저장 쪽을 바꾸는 손잡이 중 가장 싼 것은 묶음 크기다(설정 하나). 600/s에서는 50건 묶음이 p95 1.4초였다(2-8). Worker 수를 늘리거나 저장을 별도 앱으로 옮기기 전에, 50건 묶음이 높은 유입에서도 충분한지 확인했다.

### 조건

2-9와 같다(QUEUE, Worker 1개, +N·여러 행 INSERT, 5,000장, 40초). 묶음 크기만 50. 각 1회 실행.

### 결과

| 지표 | 1,000/s 묶음 10 (2-9) | **1,000/s 묶음 50** | 1,500/s 묶음 10 (2-9) | **1,500/s 묶음 50** |
| --- | ---: | ---: | ---: | ---: |
| 시작하지 못한 요청 | 0 | 0 | 0 | 0 |
| 접수(202) p95 | 4ms | 6ms | 10ms | 20ms |
| Tomcat 사용 중 최대 | 5 | 3 | 14 | 27 |
| 상품 조회 p95 / 실패 | 14ms / 0 | 16ms / 0 | 19ms / 0 | 31ms / 0 |
| 5,000장 모두 저장 | 16.3초 | **11.8초** | 17.7초 | **14.7초** |
| 접수 → 저장 p50 | 6.5초 | 3.7초 | 8.4초 | 6.7초 |
| **접수 → 저장 p95** | 10.7초 | **6.2초** | 13.5초 | **11.0초** |

정합성: 두 실행 모두 발급 5,000, 쿠폰 행 5,000, 서로 다른 사용자 5,000, 한도 초과·중복 0, Hikari 획득 실패 0.

**관찰**

- **1,000/s에서는 50건 묶음으로 10초 목표 안에 들어왔다**(10.7초 → 6.2초).
- **1,500/s에서는 줄었지만 목표를 넘었다**(13.5초 → 11.0초).
- 1,500/s에서는 매진(3.3초)까지 5,000건이 들어오므로, p95를 10초 안에 두려면 저장이 대략 초당 500건 이상이어야 한다(계산). 이번 실행은 5,000장을 14.7초에 저장했다.
- 같은 50건 묶음인데 저장 완료가 600/s 10.3초(2-8), 1,000/s 11.8초, 1,500/s 14.7초로 유입이 클수록 늦었다. 같은 PC에서 k6·앱이 더 많은 요청(매진 뒤 409 포함)을 처리하며 CPU를 나눠 쓴 영향일 수 있다(추론, 따로 재지 않음).
- 1,500/s 묶음 50에서 접수 p95·상품 p95·Tomcat이 묶음 10보다 높았다. 1회 실행이라 차이의 원인은 단정하지 않는다.

**해석**

묶음 크기는 1,000/s까지는 충분한 손잡이였다. 1,500/s에서 목표를 넘은 남은 차이는 Worker 한 개의 저장 속도다. 다음 손잡이는 Worker 수(같은 캠페인 행의 잠금 경쟁 확인 필요) 또는 더 큰 묶음이다. 저장을 별도 앱으로 옮기는 것만으로 이 차이가 줄어든다는 근거는 아직 없다.

## (1·2단계 직후 기록) 다음 검토: Redis를 통과한 요청의 DB 대기

> 1·2단계를 마친 시점의 계획이다. 이후 2-3(시간 분해)부터 2-9까지 이 질문을 이어서 다뤘다.

1·2단계 부하 실험은 완료했다. 다음 질문은 **수량 필터를 통과한 요청이 DB를 기다리며 자원을 점유하는 문제를 어떻게 줄일 것인가**다. 기존 측정에서 매진 뒤 UPDATE는 사라졌지만, 매진 전 Hikari 대기와 다른 API 지연은 남았다.

분산락·동시 실행 제한·입장 대기열을 각각 어떤 문제에 적용할지 비교한다. 입장 대기열은 순번을 주고 HTTP를 종료한 뒤 빈자리만큼 입장시키는 방식이며, 저장 작업을 쌓는 작업 큐와 구분한다. Kafka를 다음 단계로 미리 정하지 않는다.

### 후속 비교의 실행 조건

비교 모드는 `DB_ONLY`와 `REDIS_SYNC`다. 처리량 제어 후보는 600/s·40초·5,000장을 기준으로 비교하고, 선택한 방법 외의 부하·풀·스레드 조건을 맞춘다.

```bash
COUPON_LOAD_MODE=DB_ONLY COUPON_LOAD_STAGES=600:40 COUPON_LOAD_QUOTA=5000 \
COUPON_LOAD_LABEL=week8-db-followup \
./gradlew :apps:commerce-api:experimentTest --tests '*CouponLoadExperimentTest' --rerun

COUPON_LOAD_MODE=REDIS_SYNC COUPON_LOAD_STAGES=600:40 COUPON_LOAD_QUOTA=5000 \
COUPON_LOAD_LABEL=week8-redis-followup \
./gradlew :apps:commerce-api:experimentTest --tests '*CouponLoadExperimentTest' --rerun
```

Java 21과 로컬 Testcontainers Docker endpoint 설정이 필요하다. 두 조건 모두 MySQL·Redis를 실행하고 Kafka·consumer는 기동하지 않는다. 환경 변수는 Gradle 입력이 아니므로 `--rerun`을 사용한다. 위 명령은 비교 실행 예시다. 요청별 시간 분해 결과는 2-3의 REDIS_SYNC 실행에서 얻었다.
