8주차 쿠폰 발급 설계

선착순 쿠폰을 대기열로 받는다. 줄은 Redis, 판정은 Redis Lua 1회, 쿠폰 생성은 Kafka 뒤 consumer가 한다. 세마포어(동시 처리 자리 수 C)는 11-12에 뺐다. 결정의 이유와 숫자는 docs/week8/plan.md에 있다.

1. 전체 구조

  • 발급 API는 판정(Redis Lua 1회)과 outbox 기록까지만 하고 202를 준다.
  • 쿠폰을 실제로 만드는 건 commerce-streamer의 consumer다. 다른 프로세스라 커넥션 풀·스레드가 나뉜다.
  • 입장 속도는 모든 서버가 Redis 카운터 하나로 센다. 서버를 늘려도 초당 50명(측정 전 임시값)을 넘지 않는다.

2. 사용자 흐름

  • 다음 조회 시점은 화면이 아니라 서버가 정한다(pollAfterMs). 같은 순간에 몰리지 않게 jitter를 섞는다.
  • 품절이면 줄을 지우고, 기다리던 사람은 다음 조회에서 SOLD_OUT을 받는다.

3. 실패 처리: 되돌리지 않고 앞으로 채운다

  • Set에서 빼는 경로는 없다. 두 곳이 서로 빠진 걸 채우기만 한다.
  • 같은 행을 여러 번 채워도 UNIQUE가 하나만 남긴다. 채우는 쪽끼리 겹쳐도 꼬이지 않는다.
  • Redis 데이터가 사라진 것은 캠페인 상태 키가 없는 것으로 알아챈다. 복구 동안은 503이다.
  • consumer 재시도가 다 실패한 메시지(DLT)는 관리자 재처리 API로 다시 보낸다.

4. consumer 트랜잭션

  • 발급 수를 바꾸는 경로가 consumer 하나뿐이라, 3주차 재고처럼 비관적 잠금(SELECT … FOR UPDATE)을 쓰지 않고 조건부 UPDATE 한 문장으로 끝낸다.
  • UPDATE를 맨 뒤에 둬서 캠페인 행 잠금을 쥐는 시간을 가장 짧게 한다.
