# 쿠폰 발급에서 총량, 처리 자리, 집계를 나눈 이유

이 글은 C01~C05 구현과 C06 검증을 정리한 글이다. HTTP·독립 JVM 두 개의 검증과 전체 검사 실패 모듈의 환경 재실행을 확인했다.
최종 확인 상태는 [구현 현황](README.md)을 따른다. 성능 수치를 측정한 글이 아니라 정합성과 실패 경계를 설명한다.

## 쿠폰이 남았다는 사실과 지금 처리할 수 있다는 사실

쿠폰 100장이 남아 있어도 서버가 100개의 발급을 동시에 처리할 수 있다는 뜻은 아니다.
발급 총량은 캠페인의 업무 규칙이고, 처리 자리는 인스턴스가 동시에 수행할 발급 실행 수다.

| 구분 | 보호 대상 | 구현 |
|---|---|---|
| 발급 총량 | 준비한 수량보다 많은 쿠폰이 확정되지 않음 | DB 슬롯·쿠폰·issuedCount, 같은 TX |
| 사용자 중복 | 한 캠페인에서 같은 사용자의 쿠폰 한 장 | DB 유일 제약, 롤백 뒤 기존 결과 조회 |
| 처리 자리 | 해당 인스턴스의 동시 발급 실행 수 | 시작 시 구성하는 singleton Semaphore |
| 누적 집계 | 확정된 발급을 Redis에서 중복 없이 셈 | SET과 Lua, DB 기준 재집계 |

한 인스턴스가 C=3이고 다른 인스턴스도 C=3이면 합계 6개를 처리할 수 있다. 현재 선택은 전역 C가 아니라 인스턴스별 C다.
따라서 Redis 누적 집계를 총량 판단이나 수용 승인에 사용하지 않는다. 서버가 늘어날 때 합산 수용량이 늘어나는 것도 현재 설계의 특성이다.

## 슬롯을 잡아도 발급은 아직 끝나지 않는다

캠페인 활성화 전에 총량만큼 AVAILABLE 슬롯을 만든다. 발급 TX는 기존 쿠폰을 먼저 확인하고, 미발급이면
`FOR UPDATE SKIP LOCKED`로 슬롯 하나를 선택한다. 슬롯을 얻지 못했다고 곧바로 품절을 뜻하지는 않는다.
다른 TX가 잠시 모든 잔여 슬롯을 잡고 있을 수 있기 때문이다.

빈 결과 TX가 끝난 뒤 기존 쿠폰과 현재 캠페인 상태를 다시 확인한다. 품절이 확정되지 않은 경합만 동일 permit 안에서
최초 포함 최대 4회, 50ms 간격, 200ms 예산으로 재확인한다. 예산은 새 획득 TX를 시작할지 결정하는 기준이다.
이미 시작한 SQL이나 전체 HTTP 요청이 200ms 안에 강제 종료된다는 뜻은 아니다. INSERT 이후의 업무 TX는 재실행하지 않는다.

슬롯 선택 뒤 쿠폰을 저장하고, 마지막에 캠페인의 현재 행을 잠근다. 현재 행의 상태·기간·잔여 수량을 검증하고
발급 수를 증가시킨다. 슬롯의 실제 UPDATE도 캠페인 잠금 뒤로 두었다. FK를 지원하는 인덱스 변경이 공통 부모 잠금을
예상보다 먼저 잡는 장면을 피하기 위한 SQL 순서다. 쿠폰·슬롯·카운터 중 하나라도 실패하면 같은 TX 전체가 롤백된다.

DB 제약도 함께 둔다. `(campaign_id, user_id)`는 한 사용자 한 장을, `slot_id`는 슬롯 하나에 쿠폰 한 장을 보장한다.
`coupons(slot_id, campaign_id)`가 `coupon_slots(id, campaign_id)`를 참조해 다른 캠페인의 슬롯을 연결할 수 없게 했다.
동시 중복 충돌이 나면 해당 TX의 롤백이 끝난 뒤 새 TX에서 기존 쿠폰을 조회한다. 품절·비활성·마감이 뒤따라도 이미 저장된 결과를 우선 반환한다.

## 마감 판정은 잠금을 얻은 뒤의 DB 시각으로 한다

요청 접수 시에는 기간 안이었더라도 캠페인 잠금을 기다리는 동안 마감될 수 있다.
그래서 최종 판정은 마지막 캠페인 잠금을 얻은 뒤 같은 TX에서 새로 읽은 쓰기 DB 시각을 사용한다.
조건은 `startsAt <= dbNow < endsAt`이다. 대기 전 시각을 최종 판정에 재사용하지 않는다.

최종 검증 시 이미 마감이면 앞선 쿠폰 INSERT까지 롤백한다. 반대로 마감 전에 최종 검증을 통과했다면 commit이 마감 뒤에
완료되는 것은 허용한다. 이 구간의 의미를 정해 놓아야 마감 시각과 실제 완료 시각을 혼동하지 않는다.

## HTTP 종료만 보고 permit을 돌려주지 않는다

Java Semaphore는 개수만 관리한다. 누가 획득했는지, 그 실행이 끝났는지는 별도로 기록해야 한다.
실행 handle은 원래 Semaphore에만 한 번 반환되며, 획득하지 못한 요청이나 모르는 실행 ID가 permit을 늘릴 수 없다.

발급에는 쓰기 TX만 있는 것이 아니다. 중복 충돌 뒤 조회나 빈 슬롯 뒤 상태 확인도 별도 TX다.
각 TX의 `afterCompletion` 관찰과 facade의 프록시 반환·후속 조회 종료를 함께 확인한 뒤 permit을 반환한다.
HTTP timeout이나 클라이언트 연결 종료는 DB 작업 종료의 증거가 아니다.

COMMITTED·ROLLED_BACK이 확인되면 정상 종료 절차를 진행하지만 UNKNOWN, 완료 신호 부재, TX 생성·통신 오류는 성공이나 롤백으로 추정하지 않는다.
그 실행의 permit을 보류하고 해당 인스턴스의 신규 수용을 닫는다. 일반 업무 거절을 모두 불명 상태로 취급하지도 않는다.

복구는 지정한 현재 boot의 실행만 처리한다. 애플리케이션 실행 종료와 원 DB 세션 소멸·TX 부재를 확인하고,
쿠폰과 ISSUED 슬롯의 양방향 대응 및 카운터를 대조한다. 원 세션의 `Sleep`은 종료 증거가 아니다.
복구 확인 쿼리의 TX 프록시 진입 자체가 실패해도 해당 ID는 보류하고 다음 ID의 확인을 계속한다.

재시작해서 registry가 비었다고 이전 DB 작업이 끝난 것은 아니다. 새 인스턴스는 닫힘으로 시작한다.
일반 재시작은 이전 로그의 DB 세션 목록과 운영자의 프로세스 종료 확인을 요구하고, 서버가 세션 종료와 DB 정합성을 다시 검사한다.
최초 배포는 이전 실행이 없다는 명시적 운영 확인을 별도로 받는다. 새 Semaphore에 이전 boot의 permit을 더하지 않는다.

## Redis에서 미준비와 0건을 구분한다

Redis 집계는 단일 SET에 준비 표식 `__ready__`와 쿠폰 ID를 저장한다. 준비 표식이 없다면 미준비·유실이고,
표식만 있다면 실제 0건이다. 준비된 집계의 값은 `SCARD - 1`이다.

record Lua는 준비 상태를 확인하고 `SADD`로 쿠폰 ID를 반영한다. 동일한 ID의 동시 호출은 집계 증가를 한 번만 만든다.
접근 실패를 empty나 0으로 숨기지 않는다. 활성 집계에는 TTL을 두지 않는다.

집계 호출은 DB 발급 facade가 정상 반환해 commit과 permit 반환이 확인된 뒤 수행한다.
Redis가 실패하면 쿠폰·DB 발급 수·이미 확정된 고객 응답은 유지하고 캠페인·쿠폰 ID와 재집계 필요 로그를 남긴다.
다만 commit 뒤 이 호출 전에 프로세스가 종료되면 누락이 생긴다. 메모리 호출만으로 영속 전달이나 DB와 Redis 간 exactly-once를 보장하지 않는다.

## 재집계에서 늦은 교체 명령을 막는다

재집계는 캠페인 행 잠금을 유지한 상태로 확정 쿠폰 ID를 읽고 DB issuedCount와 개수가 맞는지 확인한다.
Redis 임시 SET을 완성한 뒤 활성 키로 원자 교체한다. 미커밋 발급은 마지막 캠페인 잠금에서 기다리므로,
재집계가 잠금을 해제한 뒤 commit하고 새 ID를 반영한다. 늦게 도착한 이전 commit의 ID는 이미 snapshot에 있어 중복 증가하지 않는다.

하지만 Redis 명령 timeout은 서버에 제출한 명령의 취소가 아니다. 옛 publish가 timeout된 뒤 DB 잠금이 풀리고,
새 발급 반영이나 새 재집계가 성공한 다음 옛 `RENAME`이 실행되면 최신 집계를 덮어쓸 수 있다.

이를 막기 위해 캠페인별 UUID fence를 둔다. 새 build와 모든 record 호출이 fence를 바꾸고,
publish Lua는 자기 token이 현재 fence와 같을 때만 준비 상태·개수를 확인한 뒤 `RENAME`한다.
미준비·중복 record도 이전 publish를 무효화한다. 불필요한 재집계 거절은 생길 수 있지만 최신 결과를 옛 snapshot으로 덮어쓰지 않는다.
임시 build만 TTL 60초를 사용하고 활성 집계와 fence는 TTL·cleanup 대상에서 제외한다.

실제 Lua 회귀는 옛 stage를 준비한 뒤 새 record·새 rebuild 또는 미준비 상태의 record를 실행하고,
옛 publish가 거절되는지 확인한다. 실제 네트워크에서 모든 지연 패턴을 재현했다고 주장하는 시험은 아니다.

## 검증으로 말할 수 있는 범위

C01~C05는 실제 MySQL의 제약·잠금·시간 판정과 실제 Redis의 중복·유실·오류·재집계 경합을 단계별로 확인했다.
C04의 마지막 재검증은 20건이었고 이전 미변경 37건의 성공 근거를 유지했다. C05는 신규 11건과 아키텍처 8건, 총 19건이 성공했다.

C06의 고객·관리자 HTTP 9건과 독립 OS 프로세스 두 개의 시험 1건은 대상 검증을 통과했다.
전체 검사 중 Docker API 400으로 실패한 batch·test-pg는 사용자 PowerShell의 임시 API 버전 설정으로 재실행해 해결했다.
기존 UP-TO-DATE 결과를 포함한 최신 XML 635건은 실패·오류·skip 0이다. 단일 clean 실행 635건의 결과라는 뜻은 아니다.
세부 근거는 [구현 현황](README.md#전체-검사-결과의-범위)에 있다. 처리량 개선이나 전역 수용 한도, 실제 인증,
영속 이벤트 전달은 검증한 보장 범위에 포함하지 않는다.
