# W8 쿠폰 발급과 현재 수용량 제어 기준

2026-11-08 제공된 [과제 원문](assignment-original.md)과 [학습 자료 원문](learning-original.md)을 첨부 그대로 보존한다. 이 문서의 아홉 항목과 아래 검증 예시는 **당시 BASIC 발제**를 추적한다.

## 멘토 공지에 따른 판정

2026-11-12 공유된 멘토 공지에 따라 BASIC 세마포어는 처리량 제한을 이해하는 실험으로 마쳐도 된다. 실제 쿠폰 발급은 BASIC의 동기 발급·즉시 거절 방식과 대기열·예약을 포함한 다른 방식을 모두 인정한다. **고객 API가 네 번째 요청에 429를 반환해야 하는지는 선택한 계약에 따른다.** 두 방식의 고객 API를 모두 구현할 의무는 없다.

| 처리 자리가 모두 찼고 배정할 쿠폰이 남은 상황 | 채점할 실행 결과 |
| --- | --- |
| BASIC 동기 발급 | 세 실행이 자리를 점유하는 동안 네 번째 요청은 429를 받고 DB 발급에 진입하지 않는다. 자리 반환 뒤 재신청하면 발급받을 수 있다. |
| 대기열·예약 방식 | 네 번째 고객의 대기 접수를 허용한다. 대기가 늘어도 실제 발급 실행 수가 설계한 상한을 지키는지, 자리가 난 뒤 접수 건을 약속한 방식으로 처리하는지 확인한다. 대기 접수·쿠폰 한 장 확보·발급 완료는 각각 응답이 약속한 사실과 저장 결과를 대조한다. |

이 프로젝트에서는 MySQL 예약 커밋 후 네 번째 고객에게 `202 WAITING`으로 한 장 확보를 알린다. 자리가 나면 서버가 고객 재신청 없이 같은 예약에서 한 장을 발급하고, 완료 후 재요청에는 `200 ISSUED`와 같은 couponId를 반환한다. **이 흐름에서 W8-C04~06은 작업자의 동시 발급 상한, 자리 반환·재사용, 중복 처리 후 실제 쿠폰 수로 평가한다.** 정확한 선착순을 약속한 설계라면 어떤 시점의 순서를 보장하는지와 그 순서의 실행 결과를 확인한다. [고객 API 계약](../week2/commerce-api-contract.md#w8-쿠폰-예약-응답) · [테스트 기대값](../week2/commerce-tdd-plan.md#w8-쿠폰-예약과-복구-테스트)

각 방식에서 실제 쿠폰 발급·본인 보유 목록, 캠페인 총량, 사용자당 한 장, 처리량 제한과 장애 시 결과를 확인한다. W7까지의 상품·주문·PG·Outbox·구매 활동은 유지한다. 아래 W8-C01~09는 원문 Checklist의 순서에 붙인 추적용 ID이며 표의 확인 증거는 BASIC 실험 기준이다. 별도 배점·최소 테스트 개수·성능 합격선은 제공되지 않았으며 임의로 추가하지 않는다. [구현 체크리스트](implementation-checklist.md)

## BASIC 동기 발급에서 DB의 총량·중복·원자성

기존 결과 사전 조회는 빠른 반환 경로일 뿐 동시성 보호를 대신하지 않는다. 실제 발급 TX에서 조건·한도·중복을 다시 확인하고, 발급 수 증가와 보유 쿠폰 insert를 함께 commit/rollback한다. 잠금 또는 조건부 변경 등으로 마지막 수량을 보호하며 (campaignId, userId) 유일 제약을 둔다.

동시 중복은 기존 couponId를 반환하고 발급 수를 늘리지 않는다. DB 유일 제약 충돌을 처리하는 방식이라면 실패 TX의 rollback 뒤 새 TX에서 기존 결과를 확인한다. 연결 오류나 다른 제약 오류를 모두 중복 성공으로 바꾸지 않는다.

DB 총량 실험은 Redis 용량을 충분히 두거나 DB 발급 handler를 직접 동시 호출한다. 원문의 예시인 **총 5장·서로 다른 8명 → 발급 5·품절 3·실제 쿠폰 5·issuedCount 5**에서 품절 3명은 실제 DB 경쟁의 결과여야 한다. Redis에서 먼저 429로 거절된 요청을 포함하지 않는다. 예시 수치와 테스트 이름 자체를 유일한 정답으로 강제하지 않는다.

## BASIC 동기 발급에서 Redis 수용·반환의 경계

POST 발급의 처리 순서는 **기존 결과 조회 → 없으면 Redis 수용 → 수용 확인 후 실제 DB 발급 TX → TX·발급 실행 종료 확인 → 자기 token 반환**이다. 응답 유실 뒤의 재요청은 저장된 쿠폰 결과로 수렴해야 한다. GET 본인 보유 목록은 Redis 처리 자리를 획득하지 않고 DB에서 조회한다.

- Set에는 서버가 실행마다 만든 고유 token을 저장한다. 고객 입력·사용자 ID·couponId를 실행 소유권으로 대체하지 않는다.
- 같은 token 확인·Set 크기 확인·빈자리 추가를 한 Lua 실행으로 처리한다. SCARD와 SADD를 별도 round-trip으로 나누지 않는다.
- 같은 token 재확인은 동일한 실행 안에서만 허용된다. 수용 응답이 불확실하면 DB 발급을 시작하지 않는다.
- capacity는 서버 설정이며 신규 발급 경로가 공유하는 전용 키를 사용한다. 기존 캐시 키와 섞지 않는다.
- 전용 master template qualifier는 `redisTemplateMaster`다. 실제 선언 타입·primary endpoint·String serializer·script 반환 1/0과 예외를 검증한다. replica count로 승인하지 않는다.
- Spring Data Redis script 실행 API를 사용하고 unchecked cast로 실행 오류를 숨기지 않는다. 클라이언트 command timeout을 제한하며 그 값과 실제 연결 대상은 설계·실행 증거로 확인한다.
- Lua의 원자 실행을 오류 시 전체 rollback으로 해석하지 않는다. 입력·키 타입을 먼저 검증하고 변경 범위를 작게 유지한다.
- 반환은 자기 token만 제거한다. Set 전체 삭제·무조건 카운터 감소로 다른 실행의 자리를 지우지 않는다.
- 클라이언트 HTTP 종료나 timeout은 하위 DB 종료 증거가 아니다. 작업이 끝났는지 불명확하면 자리를 재사용하지 않는다.

## BASIC 동기 발급에서 장애·보수적 재개

Redis 접근 실패·불확실한 수용 응답에는 신규 DB 발급을 시작하지 않는다. W4 표시 캐시처럼 DB로 무제한 우회하거나 local count·queue로 수용 제한을 대체하지 않는다. 이미 저장된 본인 결과의 조회는 DB가 정상이면 유지한다.

**로컬 신규 수용은 기본 닫힘과 명시적 열기를 둔다.** Redis 장애·상태 유실 확인 뒤에는 신규 수용을 닫고, 연결 복구·PONG만으로 다시 열지 않는다. 모든 해당 발급 실행·DB 작업의 종료와 실제 쿠폰 결과를 확인한 다음 자기 범위의 비활성 token만 정리하고 명시적으로 재개한다. 종료가 불명확하면 닫힌 상태를 유지한다.

반환 Redis 호출에 실패해도 이미 커밋한 쿠폰·issuedCount를 되돌리지 않는다. 반환 실패를 이유로 반드시 HTTP 503을 반환한다고 새 계약을 만들지 않으며, 해당 응답은 구현 전에 별도로 정한다. token을 TTL로 자동 회수하지 않는다. 시간 경과는 기존 실행의 취소나 쓰기 차단 증거가 아니다.

필수 장애 실험은 로컬 발급 인스턴스의 통제된 중단·재개다. 감지하지 못한 Redis 상태 손실·다중 인스턴스 자동 장애 전환·lease/fencing까지 보장하는 분산 semaphore로 표현하지 않는다.

## BASIC 실험의 관찰 기준

| 장면 | 확인할 결과 |
| --- | --- |
| 실제 동시 수용 C=3 | 캠페인 발급 한도를 충분히 두어 품절이 수용 실험을 가리지 않게 함. 서로 다른 세 사용자 요청을 획득 뒤·DB TX 전 barrier에서 유지. token 3개 중 네 번째는 429·DB 발급 진입 0·쿠폰 0 |
| 한 자리 재사용 | 한 실행의 실제 commit·종료·반환 뒤 네 번째가 재요청해 실제 발급. 나머지도 종료한 후 실제 쿠폰 수·issuedCount·token 0 확인 |
| 자기 token 반환 | 같은 token 두 번 반환·모르는 token 반환에도 다른 활성 token 보존 |
| 정상·동시 중복·사용자 격리 | 같은 couponId와 업무 효과 1, 다른 사용자 목록 비노출. 기존 결과는 수용 거절·장애와 분리 |
| 실제 SQL 후 실패 | issuedCount 증가 뒤 쿠폰 insert 실패로 전체 rollback, 종료 확인 뒤 자리 반환 |
| DB commit 뒤 응답 유실 | 저장된 쿠폰 유지, 재요청에서 같은 결과·추가 발급 0 |
| 실제 Redis 중단 | 앱이 사용하는 endpoint의 중단을 확인. 신규 503·DB 신규 효과 0, 기존 목록·완료 결과 유지 |
| 반환 실패·재개 | 쿠폰 보존·수용 닫힘, 종료·실제 결과 확인 뒤 자기 남은 점유만 복구. Redis 재접속만으로 열리지 않음 |
| timeout·TTL | 활성 실행이 끝나지 않았는데 연결 종료·시간 경과만으로 자리가 반환되거나 다른 실행에 재사용되지 않음 |

barrier·future·자원 종료에는 deadline을 둔다. 네 요청이 모두 즉시 끝나 차례로 성공한 결과, mock Redis나 thread-local count만으로 C=3 동시 수용을 검증했다고 하지 않는다. 반환과 rollback은 실제 DB·Redis 상태로 확인한다.

## 실행·제출과 범위

원문의 테스트 클래스 이름과 명령은 예시다. 현재 구현 이름에 맞는 관련 테스트·영향 범위의 회귀·Java Checkstyle·ArchUnit을 실행한다. 다음은 현재 프로젝트의 검사 명령 예시다.

```shell
./gradlew :apps:commerce-api:check
```

공통 모듈 변경이 streamer 등 다른 앱에 영향을 주면 해당 검사도 확인한다. W7 과거 전체 통과 기록을 이번 실행으로 합산하지 않는다. 테스트 0건·skip·연결 실패를 성공으로 표시하지 않고 실제 실행 범위·건수·실패/오류/skip·종료 결과를 남긴다. 자신의 격리 DB·Redis·요청 실행만 마지막에 정리하며 사용자 DB·기존 cache·topic/group·컨테이너·볼륨을 일괄 삭제하지 않는다.

제출물은 캠페인 준비 코드, 선택한 발급 방식과 본인 목록 API, DB 정합성과 처리량 제한을 보여 주는 코드·테스트, PR·기술 글이다. BASIC 방식은 Redis 수용·Lua 코드로, 대기열·예약 방식은 실제 발급 동시 수와 대기 건의 처리 결과로 설명한다. PR에 발급 총량·현재 점유·중복 결과·장애 대응과 재개 조건을 남긴다. 제출 의무를 임의의 열 번째 기능 항목으로 추가하지 않는다.

BASIC 발제는 사용자 대기실·비동기 worker를 범위 밖에 두었다. 멘토 추가 공지에 따른 선택 설계는 예약된 고객을 서버 작업자가 발급한다. 쿠폰 사용/할인·환불·알림·전체 캠페인 CRUD, W7 주문 이벤트·Outbox·구매 활동과의 연결은 선택 설계에도 추가하지 않는다.
