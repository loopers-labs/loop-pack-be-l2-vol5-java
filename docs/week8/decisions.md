# 8주차 결정 기록

> 설계 대화에서 합의한 결정과 근거, 버린 대안을 남긴다. 7주차 결정을 가리킬 때는 `W7 D-xx`로 쓴다.

## 이번 주의 목표

행사 쿠폰 발급 요청이 한꺼번에 몰린다. 발급 한도를 DB가 지켜도, 모든 요청이 DB 연결을 잡고 기다리면 주문·상품 조회까지 느려진다.
그래서 실제 발급 앞에 "지금 동시에 실행할 수 있는 자리"를 두고, 자리가 없으면 바로 거절한다. **쿠폰이 남아 있는 것과 지금 처리할 자리가 있는 것은 다르다.**

## 불변식

| ID | 불변식 | 지키는 곳 | 깨지면 생기는 일 |
|---|---|---|---|
| INV-801 | 캠페인의 발급 수는 총 한도를 넘지 않고, 실제 발급된 쿠폰 수와 같다 | `CouponIssuer` TX: 캠페인 행 비관적 락, `CouponCampaign`의 판단, 발급 수 증가와 쿠폰 insert를 한 TX에 | 한도 초과 발급(되돌릴 수 없음), 또는 수량만 줄고 쿠폰은 없는 상태 |
| INV-802 | 한 사용자는 한 캠페인에서 쿠폰을 최대 한 장 갖는다. 다시 요청하면 같은 couponId를 받는다 | `(campaign_id, user_id)` unique, 위반 시 새 TX에서 기존 쿠폰 조회 | 버튼 두 번에 쿠폰 두 장 |
| INV-803 | 동시에 DB 발급 경로에 들어간 신규 발급 실행은 C개를 넘지 않는다 | Redis Set + Lua 한 번(확인+추가), 실행마다 다른 token | 몰린 요청이 DB 연결을 다 잡아 다른 기능까지 느려짐 |
| INV-804 | 자리 반환은 업무 결과(쿠폰, 발급 수)를 바꾸지 않고, 자기 token만 지운다 | `SREM` 자기 token, 반환 실패해도 쿠폰 유지 | 남의 자리를 지워 초과 수용, 또는 발급된 쿠폰을 취소 |
| INV-805 | 수용 상태를 확인할 수 없으면 신규 DB 발급을 시작하지 않고, 사람이 확인하기 전에는 다시 열지 않는다 | 메모리 수용 표시(기본 닫힘), Redis 오류·timeout 시 닫기, TTL 없음 | Redis 장애 때 제한을 우회하거나, 남은 실행과 새 실행이 겹침 |
| INV-806 | 발급된 쿠폰의 혜택은 발급 순간의 값으로 남고, 사용자는 자기 쿠폰만 본다 | 발급 때 혜택을 쿠폰 행에 복사, 목록은 요청자 ID로만 조회 | 캠페인 변경이 받은 쿠폰을 바꾸거나 남의 쿠폰이 보임 |

## 두 한도

### D-1. 총 발급 한도와 사용자당 한 장은 DB가, 동시 처리 자리는 Redis가 지킨다

| | 총 발급 한도 (예: 100장) | 동시 처리 수용량 (예: 3자리) |
|---|---|---|
| 뜻 | 캠페인에서 나갈 수 있는 쿠폰 수 | 지금 이 순간 함께 실행 중인 발급 수 |
| 발급 한 건이 끝나면 | 남은 수가 줄고 **돌아오지 않는다** | 자리가 **다시 빈다** |
| 비유 | 오늘 준비한 음식 100인분 | 테이블 3개 |
| 지키는 곳 | DB (원본, 지워지지 않음) | Redis (잠깐만 의미 있는 상태) |

- **근거**: 총 한도를 Redis에 두면, Redis가 죽거나 데이터를 잃었을 때 "몇 장 나갔는지"가 사라져 한도를 넘겨 발급할 수 있다. 이미 나간 쿠폰은 되돌릴 수 없다. "지금 몇 명 앉아 있나"는 잃어도 다시 확인할 수 있는 상태라 Redis에 둔다.
- **함께 지킬 것**: 자리를 반환할 때 발급 수를 줄이지 않는다. 발급 수를 지금 실행 수로 세지 않는다.

## Redis 장애

### D-2. 자리를 확인할 수 없으면 신규 발급을 닫는다 (fail-closed)

- **결정**: Redis 접근 실패나 불확실한 응답이 오면 신규 발급을 시작하지 않고 503으로 거절한다. 이미 받은 쿠폰 조회와 보유 목록은 DB로 계속 제공한다.
- **근거**: 자리 제한은 DB와 다른 기능(같은 연결 풀을 쓰는 주문·상품 조회)을 지키는 문이다. Redis가 죽는 때는 대개 요청이 몰리는 때이기도 하다. 그때 자리 확인을 건너뛰면 보호가 가장 필요한 순간에 보호를 없앤다.
- **4주차 상품 캐시와 다른 이유**: 그 캐시는 빠르게 하려는 장치라, Redis가 죽으면 DB로 우회해도 결과가 같다(fail-open). 이번 Redis는 제한을 지키는 장치라, 우회하면 제한 자체가 사라진다. 같은 Redis 장애라도 그 Redis가 맡은 책임에 따라 대응이 갈린다.

## 자리 잡기와 반환

### D-3. 자리 확인과 추가는 Lua script 한 번으로 한다

- **결정**: "같은 token이 이미 있는지 → 현재 Set 크기 → 빈자리면 추가"를 Redis 안에서 한 번에 실행한다. `SCARD`와 `SADD`를 애플리케이션에서 두 번 호출하지 않는다.
- **근거**: 명령 하나하나는 원자적이어도 "세고 → 판단하고 → 앉는다"는 흐름은 쪼개져 있다(check-then-act). 2자리가 찬 상태에서 두 요청이 둘 다 `SCARD = 2`를 보고 각자 `SADD`하면 4자리가 된다. 3주차 DB의 "조회 후 갱신" 경쟁과 같은 모양이다.
- **Lua의 범위**: Lua는 실행 도중 다른 명령이 끼어들지 못하게 할 뿐, 중간 오류를 되돌려 주지 않는다. 스크립트는 자리 판단과 token 기록만 짧게 하고, 실제 발급은 DB TX에서 한다.

### D-4. 자리 주인은 사용자가 아니라 실행이다. 서버가 실행마다 token을 만들고, 반환은 자기 token만 지운다

- **결정**: 서버가 요청 실행마다 새 token을 만들어 Set에 넣는다. 사용자 ID·couponId·고객이 보낸 키를 쓰지 않는다. 반환은 `SREM key 자기token`만 한다.
- **사용자 ID를 넣으면**: 같은 사용자가 버튼을 두 번 누르면 HTTP 실행은 2개인데 Set에는 `user-7` 하나만 들어간다. 자리를 덜 세고, 먼저 끝난 실행의 `SREM user-7`이 아직 도는 실행의 자리까지 지운다. Lua의 "같은 token이면 수용" 줄 때문에 두 번째 실행은 자리를 세지도 않고 통과한다.
- **카운터(INCR/DECR)를 쓰지 않는 이유**: 늦게 온 반환이 남의 자리를 하나 더 뺀다. token Set이면 늦은 반환은 자기 이름표만 찾으니, 이미 없으면 아무 일도 일어나지 않는다. token이 반환 쪽의 fencing 역할을 한다(W7 PR 한계의 "TX-2에 차수 확인 없음"과 대비된다).
- **개수 구분**: 버튼을 두 번 누르면 자리는 2개, 쿠폰은 1장이다. 자리는 Redis token이, 쿠폰은 DB `(campaign, user)` unique가 센다.

### D-5. token에 TTL을 걸지 않는다. 남은 자리는 사람이 확인한 뒤 지운다

- **TTL을 버린 이유**: 실행이 TTL(예: 3초)을 넘는 때는 DB가 느리거나 락 대기가 길 때, 즉 DB가 이미 힘든 때다. TTL은 token만 지우고 실행을 멈추지 못한다. 그 틈에 새 요청이 들어오면 자리 3개에 실행 4개가 DB를 쓴다. W7 relay의 임대가 끝난 뒤 원래 relay가 늦게 결과를 기록하던 문제와 같은 구조다(lease와 fencing은 다른 문제).
- **재개 순서**:
  1. 신규 수용을 닫는다. 확인하는 동안 새 token이 섞이지 않게 하기 위해서다.
  2. 남은 token의 실행과 DB 작업이 끝났는지, 실제 쿠폰과 발급 수가 맞는지 확인한다.
  3. 자기 범위(죽은 서버)의 token만 지운다. token에 서버 식별자를 넣어 범위를 구분한다.
  4. 수용을 다시 연다.
  - 확인할 수 없으면 닫힌 채로 둔다.
- **받아들이는 비용**: 장애 뒤 자리가 남아 있는 동안 처리량(가용성)이 줄어든다.

### D-6. Redis가 대답해도(PONG) 자동으로 다시 열지 않는다

- **근거**: Redis가 재시작돼 Set이 비면 0자리로 보이지만, 그 전에 자리를 잡은 실행은 앱 서버에서 계속 DB를 쓰고 있다. Redis가 잃은 건 장부일 뿐이고 실행은 그대로다. 바로 열면 자리 3개에 실행 6개가 될 수 있다. `PONG`은 "대답한다"는 뜻이지 "장부가 정확하다"는 뜻이 아니다.
- **결정**: Redis 오류를 한 번이라도 보면 닫는다. 연결이 돌아와도 사람이 D-5 순서로 확인한 뒤에만 연다.

### D-7. 열림/닫힘 표시는 서버 메모리에 두고, 켜질 때 기본값은 닫힘이다

- **결정**: 표시를 발급 서버의 메모리에 둔다. 서버가 켜지면 닫힌 상태로 시작하고, 명시적으로 열어야 발급을 받는다. Redis 오류를 보면 그 자리에서 닫는다.
- **근거**:
  - 닫기는 절대 실패하면 안 된다. 메모리 변수를 바꾸는 건 실패하지 않는다. DB `UPDATE`는 DB가 느리거나 연결이 바닥나면 실패할 수 있고, 그러면 열린 채 남는다.
  - 이 문은 DB를 지키려고 있다. 매 요청마다 표시를 DB에서 읽으면, DB가 힘들 때 문 확인부터 느려진다.
  - 재시작한 서버는 기본값 덕분에 닫혀 있다. "자동으로 다시 열지 않는다"가 따로 코드 없이 지켜진다.
- **받아들이는 비용 (휘발성)**: 표시는 서버마다 따로다. 서버가 재시작되면 다시 열어야 하고, 서버가 여러 대면 서버마다 열어야 하며, 오류를 직접 보지 못한 서버는 열린 채 남는다. 이번 장애 실험은 로컬 발급 서버 한 대 기준이고, 여러 서버의 자동 전환까지 안전하다고 주장하지 않는다(과제 범위).
- **버린 대안**: Redis에 저장(표시를 지켜야 할 때가 바로 Redis가 죽은 때다). DB에 저장(여러 서버가 판단을 공유하지만 닫기가 실패할 수 있고 매 요청 DB 조회가 늘어난다). 둘을 섞는 방식(닫기는 메모리, 열기는 공유 저장소)은 여러 서버가 될 때 다시 꺼낸다.

## DB 발급

### D-8. 마지막 한 장은 캠페인 행의 비관적 락으로 지키고, 판단은 도메인 모델이 한다

- **결정**: 발급 TX는 캠페인 행을 `SELECT … FOR UPDATE`로 읽는다. `CouponCampaign`이 활성 여부와 잔여 수를 판단하고 발급 수를 1 올린다. 같은 TX에서 보유 쿠폰을 insert한다. 캠페인 행을 바꾸는 다른 경로(비활성화 등 준비 코드)도 모두 같은 락으로 읽는다.
- **근거**:
  - 프로젝트 원칙상 불변식(`issued_count ≤ total_quota`, 비활성이면 발급 안 함)은 도메인 모델이 지킨다.
  - 애플리케이션이 판단해도 안전한 조건은 "판단에 쓴 값이 스냅샷이 아닌가"다. `FOR UPDATE`로 읽은 값은 내 TX가 끝날 때까지 아무도 못 바꾸므로, 그 값으로 판단해도 commit 시점까지 참이다. 3주차 관리자 상품 수정 버그처럼 한 경로라도 일반 SELECT로 읽고 덮어쓰면 깨진다.
  - 비관적 락의 약점(인기 행 하나에 대기가 몰림)은 앞단의 Redis 자리(최대 C개)가 줄여 준다. 이 행을 기다리는 TX도 최대 C개다.
- **중복 사용자**: `(campaign_id, user_id)` unique가 마지막 방어선이다. 위반되면 발급 수 증가도 같은 TX라 함께 rollback된다. 그 TX를 버리고 새 TX에서 기존 쿠폰을 조회해 200으로 같은 couponId를 돌려준다. 이 unique 위반이 아닌 오류(연결 오류, 다른 제약)는 성공으로 바꾸지 않는다.
- **앞단 조회의 역할**: 자리를 잡기 전 기존 쿠폰 조회는 이미 끝난 사람을 빨리 돌려보내는 지름길이다. "없음"을 봤다는 사실로 중복을 막지는 못한다(check-then-act). Redis가 닫혀도 이미 받은 사람이 200을 받는 것도 이 순서 덕분이다.
- **버린 대안**: 조건부 UPDATE(`WHERE issued_count < total_quota`). 한 번의 왕복으로 끝나지만 규칙 일부가 SQL로 가고, 0행일 때 품절과 비활성을 구분하려면 다시 조회해야 한다.

## 응답

### D-9. 품절·비활성은 409, 자리 없음은 429, 수용 상태 모름은 503. `ErrorType`에 429·503을 추가한다

| 상황 | 코드 | 근거 |
|---|---|---|
| 처음 발급 | 201 | |
| 이미 받은 사용자 | 200, 같은 couponId | D-8 |
| 없는 캠페인 | 404 | |
| 품절·비활성 | 409 `CONFLICT` | 요청자가 입력을 바꿔도 안 풀리고, 캠페인 상태가 바뀌어야 해결된다 |
| 자리 없음 | 429 `TOO_MANY_REQUESTS` | 지금 처리할 자리가 없다. 발급 성공이나 나중 발급을 약속하지 않는다 |
| 수용 닫힘·Redis 오류 | 503 `SERVICE_UNAVAILABLE` | 신규 발급을 받을 수 없다(D-2, D-7) |

- **정책 변경**: CLAUDE.md의 "ErrorType 네 가지로만 매핑"을 여섯 가지로 고쳤다(사용자 확인). `ErrorType`은 `apps/commerce-api` 안이라 공용 모듈 규칙과 무관하다.
- **보류**: `Retry-After` 헤더는 이번 범위에서 빼고 PR "남은 한계"에 적는다. 재시도 예정 시각은 발급을 약속하지 않는다.

### D-10. 반환이 실패해도 쿠폰과 응답은 그대로 두고, 수용을 닫는다

- **결정**: DB 발급이 commit된 뒤 자기 token 반환(`SREM`)이 실패하면,
  - 쿠폰을 취소하거나 발급 수를 되돌리지 않는다.
  - 사용자에게는 201과 쿠폰을 그대로 응답한다. 업무 결과는 성공이고, 자리 반환은 내부 정리다.
  - Redis 오류를 봤으니 그 자리에서 신규 수용을 닫는다(D-2, D-7).
  - 반환하지 못한 token 값을 로그에 남긴다. 관리자는 D-5 순서로 그 token만 지우고 다시 연다. 이 token의 실행은 응답까지 끝난 것이 확실하다.
- **근거**: 반환 실패를 발급 실패로 응답하면 사용자는 쿠폰이 없는 줄 안다. 쿠폰을 되돌리면 "자리 반환이 업무 결과를 바꾸지 않는다"가 깨진다.

## 운영 진입점

### D-11. 수용 열기·닫기·남은 token 정리는 HTTP 없이 빈 메서드로만 둔다

- **결정**: `CouponAdmission` 같은 빈에 `open()`, `close()`, `releaseLeftover(token)`을 둔다. HTTP 주소는 만들지 않고, 테스트와 로컬 실행 코드에서만 부른다. W7 `OutboxResume`(W7 D-15)과 같은 모양이다.
- **근거**: 운영 설정의 `/api-admin/**`은 로그인 수단이 없어 모든 요청이 403이다(관리자 인증은 테스트 설정에만 있다). HTTP로 만들면 운영에서 아무도 못 부르거나, 막지 않으면 인증 없이 아무나 수용을 열고 남의 token을 지울 수 있다. 그러면 D-5의 "확인한 뒤에만 연다"를 우회하는 뒷문이 된다.
- **받아들이는 비용**: 서버는 기본 닫힘(D-7)이라, 로컬에서 손으로 발급해 보려면 먼저 코드로 `open()`을 불러야 한다. 테스트는 준비 단계에서 연다.

## 검증

### D-12. 세 실행은 "자리 획득 직후, DB 발급 TX 전"에 붙잡는다. 이음매는 DB 발급을 맡은 별도 빈이다

- **왜 붙잡아야 하나**: 네 요청을 그냥 동시에 보내면 각 실행이 수 ms 만에 끝나, 네 번째가 들어올 때 이미 빈자리가 있다. 네 명 모두 201이 나와도 최대 동시성을 넘긴 게 아니다. 세 실행이 자리를 쥔 채 멈춰 있는 상태에서 네 번째를 보내야 한다.
- **구조**: 흐름은 `CouponIssueFacade`(기존 쿠폰 조회 → 자리 획득 → 발급 → 반환)가 맡고, DB 발급 TX(락, 한도 판단, insert)는 별도 빈 `CouponIssuer`가 맡는다. `@Transactional`을 걸려면 어차피 다른 빈이어야 한다.
- **테스트**: `CouponIssuer`를 감싼 테스트 빈이 `issue()` 입구에서 latch로 기다린다. W7 `SwitchableLedger`(W7 D-11)와 같은 방식이다. 대기에는 deadline을 두고, 실패하면 자기가 붙잡은 실행을 풀고 정리한다.
- **순서**:
  1. 사용자 3명이 요청하고, 각 실행이 이음매에서 멈춘다.
  2. token 3개를 확인한다.
  3. 4번째 사용자 요청은 429다. 그 사용자는 DB 발급 경로에 들어가지 않았고 쿠폰도 없다.
  4. 하나를 풀어 발급, 종료, 반환을 확인한다.
  5. 4번째 사용자가 다시 요청하면 201이다.
  6. 나머지를 풀고 token 0개, 실제 쿠폰 수, 발급 수를 확인한다.

### D-13. Redis 장애 테스트는 테스트 전용 Redis 컨테이너를 실제로 멈춘다

- **근거**: 공용 Redis 컨테이너(`modules/redis` testFixtures)는 JVM 전체가 같이 쓴다. 그걸 내리면 다른 테스트가 깨지고, `modules/*`는 수정 금지다.
- **방법**: W6 C-3(DB 정지 실험)과 같다.
  - 전용 컨테이너를 띄우고 `@DynamicPropertySource`로 `datasource.redis.*`를 덮어쓴다. 시스템 프로퍼티보다 우선한다.
  - 실제로 그 컨테이너에 붙었는지 연결 주소로 확인한다.
  - `docker pause`가 아니라 `docker stop`으로 멈춘다. pause는 소켓을 남겨 요청이 끝없이 기다린다.
  - 다시 켜도 주소가 같도록 고정 host 포트에 묶는다.

## Redis 연결

### D-14. 수용 판단은 master에만 붙는 전용 연결로 하고, command timeout을 500ms로 둔다

- **부딪힌 점**: 공용 `RedisConfig`(`modules/redis`, 수정 불가)는 timeout을 정하지 않아 Lettuce 기본값 60초가 적용된다.
  - Redis가 꺼져 연결이 거절되면 바로 실패한다.
  - 대답만 없는 경우(네트워크 단절, 바쁜 Redis)에는 요청마다 60초를 기다린다.
  - 그러면 요청 스레드가 발급에 다 묶여 주문·조회까지 멈춘다. 오류로 판정되지 않으니 fail-closed(D-2)도 60초 동안 작동하지 않는다.
- **결정**: `apps/commerce-api`에 수용 전용 Redis 설정을 둔다.
  - 공용 `RedisProperties`에서 master 주소만 가져와 master에만 붙는 연결을 만든다. replica에서 읽은 수로 자리를 승인할 길이 구조적으로 없다.
  - 이 연결에만 command timeout 500ms를 건다. Redis 명령은 보통 1ms 안에 끝난다.
  - String serializer로 전용 템플릿(예: `admissionRedisTemplate`)을 만든다. 수용 판단과 반환은 이 템플릿만 쓴다.
- **과제 문장과 다른 점**: 과제는 `redisTemplateMaster` 주입을 권한다. 그 목적(primary에서 읽기, 같은 serializer)은 지키되, timeout 때문에 전용 연결을 둔다. PR에 적는다.
- **timeout이 나면**: 불확실한 수용 응답이다. Lua가 이미 실행돼 token이 들어갔는지 알 수 없다.
  - DB 발급을 시작하지 않고 503으로 거절한다.
  - 수용을 닫는다(D-2, D-7).
  - 그 token 값을 로그에 남긴다. 남아 있다면 관리자가 D-5 순서로 지운다.

## 처리량

### D-17. C의 상한은 서버 한 대의 커넥션 풀 중 쿠폰 몫이고, 값은 그 안에서 측정으로 정한다

- **상한**: 커넥션 풀은 서버마다 있고 모든 기능이 같이 쓴다. C는 Redis에서 전체 기준으로 세므로, 로드밸런서가 C개를 한 서버로 몰아줄 수 있다. 그래서 C는 "서버 한 대의 풀 − 다른 기능의 피크 사용량 − 여유분"을 넘지 않는다. 피크는 HikariCP 지표(`hikaricp_connections_active`, `hikaricp_connections_pending`)로 본다. 쿠폰 쪽 효율만 보면 C는 계속 커지는 쪽으로 간다 — C를 키운 만큼 다른 기능의 커넥션이 준다(벌크헤드).
- **값**: 그 안에서 C를 늘려 가며 잰다(`experiment/CouponThroughputExperimentTest`).
  - 처리량은 `1 ÷ 락 쥔 시간`이 정한다. 관측 처리량과 이 천장이 거의 같았다(22.0 대 21.8, 36.1 대 36.2/s).
  - C를 1 → 3 → 6 → 12로 늘리면 락 대기 평균이 4 → 64 → 150 → 189ms로 늘었다. 늘린 C는 대부분 줄 서기로 바뀐다.
  - C가 풀보다 크면 커넥션 대기도 생겼다(C=12, 테스트 풀 10: TX 시작 전 대기 약 18 → 60ms).
  - 락 쥔 시간의 60~70%가 commit이었다. C가 클수록 commit이 짧아진 이유(group commit 추정)는 확인하지 않았다.
- **C=3**: 운영 풀 40의 약 7.5%이고, 테스트 풀 10 안에도 들어간다.
- **측정 환경**: 로컬 Windows Docker testcontainers, 회차당 40장. 절대값보다 경향을 본다.

### D-18. 기존 쿠폰 조회는 자리 앞(과제 흐름 A)에 둔다. 거절당한 요청도 DB를 한 번 읽는 비용을 알고 고른다

- **결정**: 순서는 그대로 "기존 쿠폰 조회 → 자리 → 발급"(A)이다. 이미 받은 사용자는 자리를 쓰지 않고 바로 200을 받고, Redis가 닫혀도 200을 받는다(D-8, INV-802).
- **알게 된 비용**: 문은 자기 뒤만 지킨다. 조회가 문 앞에 있어서 429로 거절될 요청도, 재시도할 때마다 DB SELECT를 한 번씩 한다.
  - C=1에서 재시도 트래픽이 있으면 처리량이 절반이었다(23.3 → 12.7/s). 커넥션 대기, 락 안 작업, commit이 모두 길어졌다(`CouponThroughputExperimentTest`).
- **비교 (`CouponPrecheckOrderExperimentTest`, C=3, client 32, 429면 약 1ms 뒤 재시도)**: B는 테스트에서만 만든 "자리 → 조회 → 발급" 순서다.

  | | A (조회 → 자리) | B (자리 → 조회) |
  |---|---|---|
  | 사전 SELECT 수 (신규 40명) | 862~1,008 | 40 |
  | 신규 발급 처리량 | 20.6~23.3/s | 27.0~33.2/s (1.2~1.6배) |
  | 섞인 부하에서 이미 받은 사용자 지연 | 평균 36~38ms | 평균 282~398ms (약 10배), p95 약 1초 |

- **언제 바꾸나**:
  - **B**: 오픈 직후처럼 거의 모든 요청이 신규이고, DB 보호가 이미 받은 사용자의 응답보다 중요할 때.
  - **A 유지**: 이미 받은 사용자의 재요청이 많을 때(새로고침, 응답 유실 뒤 재시도), Redis 장애 중에도 그들에게 200을 줘야 할 때.
  - **품절 뒤**: A든 B든 락까지 들어가서야 품절을 안다. 바뀌지 않는 "품절" 사실을 문 앞에 두는 편이 낫다(보류).
  - **어느 쪽이든**: 재시도 자체를 줄이는 `Retry-After`·backoff·Gateway rate limit을 함께 쓴다(D-9에서 보류).
- **실제 앱에서 확인한 한계 (`docs/week8/load-test/`, local 풀 40)**:
  - 발급 VU = C(거절이 거의 없음): 커넥션 사용 최대는 C + 2였고, 다른 기능(`GET /api/v1/coupons`) p95는 C≤24에서 14~15ms로 그대로였다. D-17과 같은 모양이다.
  - 발급 VU 200(429가 초당 약 390~510건): **C=1이든 3이든 풀 40이 꽉 차고 대기가 87~160까지 쌓였다.** 신규 발급은 9.7~9.8/s로 거절이 없을 때의 절반 이하였고, 다른 기능 p95는 286~442ms로 약 30배 느려졌다.
  - 즉 A에서는 **요청이 몰리는 바로 그 순간에 동시 처리 제한이 커넥션 풀을 지키지 못한다.** 거절될 요청이 문 앞 조회로 커넥션을 쓰기 때문이다.
  - 덤: 429마다 스택이 붙은 WARN 로그가 남아 단계마다 앱 로그가 약 200MB 쌓였다. 거절이 많을 때는 로그도 비용이다.
- **결정 유지와 이유**: 과제 흐름(A)과 INV-802(Redis가 닫혀도 이미 받은 사용자는 200)를 지키고, 이 한계를 PR과 글에 그대로 적는다.
- **해결 방안 (다음 작업)**: A를 유지하면서 문 앞 조회의 비용을 줄인다. 이미 받은 사용자 목록을 Redis에도 두고(발급 commit 뒤 기록), 문 앞에서는 Redis만 본다.
  - 거절 경로가 DB에 닿지 않는다. 이미 받은 사용자는 여전히 자리 없이 200을 받는다.
  - Redis 기록은 지름길일 뿐이다. 기록이 빠져도 최종 판단은 발급 TX 안의 재검사와 DB unique가 한다(D-8).
  - Redis가 닫히면 문 앞 조회를 DB로 돌릴지(지금의 A), 503으로 막을지는 그때 정한다.
