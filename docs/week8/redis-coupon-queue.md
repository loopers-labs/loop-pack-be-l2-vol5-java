# Redis 대기열 쿠폰 발급

MySQL은 비관적 캠페인 행 잠금과 유일 제약으로 쿠폰 발급 총량과 사용자별 중복을 보호한다. Redis는 발급할 신청과 작업 소유·재시도 정보를 관리한다. 발급 결과는 Redis에 저장하지 않으며 본인 쿠폰 목록을 MySQL에서 조회한다.

## 신청과 쿠폰 확인

```http
POST /api/v1/coupon-campaigns/{campaignId}/issue-requests
X-USER-ID: {userId}
```

- 이미 발급된 쿠폰이 있으면 Redis 대기열을 거치지 않고 HTTP 200과 기존 `couponId`를 반환한다. Redis가 장애 상태이거나 대기열이 가득 찬 경우에도 DB가 정상이면 확인할 수 있다.
- 신규 신청은 대기열에 등록하고 HTTP 202로 접수를 알린다. 202는 발급 성공을 의미하지 않는다. 같은 캠페인·사용자의 대기 또는 처리 중 신청은 중복으로 등록하지 않는다.
- 대기 중 신청이 100건이면 신규 신청은 HTTP 429로 거절한다. 거절된 요청은 자동 재접수하지 않는다.
- Redis의 영속화·복제 설정과 장애 상황에 따라 접수된 신청이 유실될 수 있다. 202가 접수 보존을 보장하지 않는다.

```http
GET /api/v1/coupons
X-USER-ID: {userId}
```

발급 여부는 본인 쿠폰 목록에서 확인한다. 목록에 쿠폰이 없다면 아직 대기·처리 중이거나 발급되지 않았을 수 있다. 쿠폰이 없는 사실만으로 신청 유실이나 실패를 판단할 수 없다. 번호표별 상태 조회 API는 제공하지 않는다. 결과가 확인되지 않으면 잠시 후 목록을 확인하고 필요할 때 다시 신청할 수 있다.

로컬 서버가 `localhost:8080`에 실행 중이고 캠페인 1과 사용자 42가 실제 존재한다고 가정하면:

```sh
curl -i -X POST -H 'X-USER-ID: 42' http://localhost:8080/api/v1/coupon-campaigns/1/issue-requests
curl -i -H 'X-USER-ID: 42' http://localhost:8080/api/v1/coupons
```

캠페인과 사용자 ID는 실제 로컬 데이터의 값으로 변경한다. 기존 데이터는 자동으로 삭제하거나 초기화하지 않는다.

## 처리 모델

- Spring JVM마다 작업자 스레드 하나가 실행된다. 서버 N개가 정상 동작하면 최대 N개 발급 작업이 동시에 실행되므로 DB 수용량을 측정해야 한다.
- 정원 100은 같은 Redis 키 접두사를 사용하는 모든 캠페인의 대기 중 신청을 합친 수다. 작업자가 이미 꺼내 처리 중인 신청은 별도로 센다.
- 대기 신청은 Redis Set에 저장한다. 임의의 요청을 꺼내므로 도착·등록·처리·발급 순서와 최대 대기 시간은 보장하지 않는다. Lua로 대기열 용량과 같은 캠페인·사용자의 중복 등록을 원자적으로 확인한다.
- 작업자는 신청을 꺼낼 때 처리 소유자를 기록한다. 처리가 끝나면 자신의 소유권을 확인하고 신청·사용자 인덱스·처리 중 기록을 원자적으로 정리한다. 쿠폰 발급 결과는 MySQL에 남고 Redis에는 보관하지 않는다.
- 발급 전에 기존 쿠폰을 확인하고, 발급 트랜잭션은 캠페인 행 잠금 후 수량 증가와 쿠폰 저장을 함께 처리한다. 유일 제약은 동시 중복 발급을 방어한다.
- MySQL 데드락(1213)·잠금 대기 시간 초과(1205)는 롤백이 확인된 경우에만 최초 시도 후 최대 세 번을 1·2·4초 간격으로 재시도한다. 횟수와 다음 시도 시각을 Redis에 기록해 수동 복구 후에도 유지한다. 기다리는 동안 해당 서버의 작업자는 같은 신청을 보유한다.
- DB 연결·권한 오류 또는 트랜잭션 결과가 불명확하면 신청을 보존하고 해당 JVM의 작업자와 신규 접수를 닫는다. 기존 작업 종료 및 DB 결과를 확인한 다음 [수동 복구 절차](coupon-queue-recovery.md)를 따른다.
- 품절 확인 시 Redis의 캠페인 상태를 갱신해 이후 신규 신청을 거절한다. 100번째 발급 커밋과 Redis 품절 표시는 하나의 트랜잭션이 아니며, 품절을 확인하기 전 추가 접수가 가능하다. 최종 발급 한도는 MySQL이 보호한다.
- Redis 오류나 불명확한 응답을 감지한 JVM은 작업과 신규 접수를 멈춘다. Redis 연결 복구만으로 자동 재개하지 않는다. 다른 JVM의 접수까지 한 번에 중단하는 전역 제어는 아니며 이미 진행 중인 요청은 영향받을 수 있다.
- 각 JVM은 Redis 접수 판정·등록과 수용 중단의 완료 순서를 조율한다. 중단이 완료된 뒤에는 접수 허용 상태로 새 Redis 명령을 시작하지 않는다. 이미 시작한 명령은 중단을 기다리는 동안 등록될 수 있고, HTTP 응답은 중단 후 도착할 수 있다. Redis 응답 유실이나 시간 초과 시에는 이미 전송된 명령이 나중에 실행될 수도 있어 실제 등록 여부를 확정할 수 없으므로 503으로 처리하고 수동 확인한다.
- 접수 Redis 명령을 JVM별로 직렬화하므로 명령이 느려지면 뒤에 들어온 접수와 중단 완료도 기다릴 수 있다. 처리량 영향은 부하 테스트로 확인해야 한다.
- 대기 신청 기록은 남았지만 Redis 대기 Set에 해당 신청이 없다면, 같은 사용자가 재신청할 때 불일치를 감지하고 그 JVM의 접수를 닫는다. 감지는 재신청 시점에 발생하며 유실된 신청을 자동 복원하지 않는다.
- 접수 전에 사용자와 기존 쿠폰을 MySQL에서 확인하므로 대기열에 거절되는 요청에도 DB 조회가 발생한다. 쿠폰 목록을 자주 조회하는 경우에도 DB 조회 부하가 발생한다.

## 설정

| 설정 | 기본값 | 의미 |
| --- | --- | --- |
| `coupon.queue.capacity` | `100` | 대기 중 신청 최대 건수 |
| `coupon.queue.key` | `coupon:{issue}:queue` | 공통 Redis 키 접두사 |
| `coupon.queue.worker.enabled` | `true` | 해당 JVM의 작업자 실행 여부 |
| `coupon.queue.open-on-start` | `false` | 확인된 local/test 실습에서 명시적으로 신규 접수·작업자 시작 |
| `coupon.queue.worker.poll-delay-ms` | `250` | 대기열이 비었거나 재시도할 때 기다리는 시간 |
| `datasource.redis.master-timeout-ms` | `500` | Redis master 연결·명령 대기 시간 |

서버마다 같은 Redis와 같은 키 접두사를 사용해야 공통 대기열이 된다. 접두사의 `{issue}`는 여러 키를 동일한 Redis Cluster 슬롯에 두기 위한 태그다. Redis Cluster에서 접두사를 변경할 때도 같은 형식의 해시 태그를 포함해야 한다.

## 이전 버전에서 전환

이전 버전은 완료 결과를 Redis에 보관하므로 새 버전과 같은 접두사로 혼용하지 않는다. 신규 접수를 멈추고 모든 작업자와 기존 DB 작업을 종료해 대기·처리 중 신청을 확인한 다음 별도의 새 접두사로 시작한다. 기존 결과와 미처리 신청의 자동 이관이나 삭제는 제공하지 않는다. 기존 데이터를 임의로 삭제하지 않는다.

## 장애 복구

신청을 꺼내거나 정리한 결과가 불명확하거나 DB 결과가 불명확하면 처리 중 기록이 남을 수 있다. 단순 시간 초과로 자동 회수하거나 자동 재개하지 않는다. 기존 작업자의 종료와 DB 작업 결과를 확인하고 [수동 복구 절차](coupon-queue-recovery.md)를 따른다.
