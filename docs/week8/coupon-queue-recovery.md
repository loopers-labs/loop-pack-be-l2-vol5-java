# 쿠폰 대기열 처리 중 요청 수동 복구

작업자가 Redis에서 신청을 꺼내면 내부 신청 기록과 처리 소유자를 남긴다. 프로세스가 중단되거나 Redis 응답이 유실되면 해당 신청은 자동 회수하지 않는다. 기존 DB 작업이 살아 있을 수 있기 때문이다.

아래는 로컬 실습용 절차다. 공개 HTTP 복구 API는 제공하지 않는다. Redis 접속 호스트, 포트, DB 번호와 키 접두어는 실제 애플리케이션 설정을 확인한다. 예시는 기본 접두어 `coupon:{issue}:queue`를 사용한다. Redis 또는 DB 작업 결과가 불명확하면 신청을 그대로 보존한다.

요청을 꺼낸 결과나 DB 결과가 불명확해 작업자가 멈추면 그 JVM은 신규 신청을 `503`으로 거절한다. 다른 JVM은 계속 동작할 수 있으며, Redis 연결 복구만으로 멈춘 작업자는 재개되지 않는다.

## 1. 기존 작업과 DB 결과 확인

Redis master에 접속하는 `redis-cli`에서:

```redis
HGETALL coupon:{issue}:queue:processing
HGET coupon:{issue}:queue:requests <requestId>
SCARD coupon:{issue}:queue:waiting
```

`processing`의 필드는 내부 요청 ID, 값은 실행별 소유자다. 신청 기록에는 캠페인 ID, 사용자 ID, 처리 상태, 소유자와 재시도 정보가 있다. 내부 요청 ID는 사용자에게 노출하는 번호표가 아니라 운영 복구용 식별자다. 로그의 `workerId`는 처리 소유자의 앞부분과 대조할 수 있다.

- 해당 소유자의 서버 및 작업이 실제로 종료됐는지 확인한다. 단순 시간 초과만으로 종료를 추정하지 않는다.
- 해당 MySQL 트랜잭션이 커밋 또는 롤백으로 종료됐는지 확인한다. 결과가 불명확하면 복구하지 않는다.
- 캠페인과 사용자의 MySQL 발급 결과를 확인한다. Redis 상태만 보고 쿠폰 수량을 되돌리지 않는다.
- 신청 기록 자체가 유실됐다면 아래 명령으로 복구할 수 없다. 장애 로그, MySQL 발급 결과, 이용 가능한 Redis 백업을 대조한다. 자동 복원 기능은 없다.

운영자는 확인 결과에 따라 완료된 작업의 **기록을 정리**하거나, 처리가 필요한 신청을 **재등록**한다. DB 발급 결과는 Redis에 다시 저장하지 않는다.

## 2. 종료가 확인된 신청 정리

DB에 발급이 완료됐거나, 작업 종료와 DB 결과를 확인하고 더 이상 재처리하지 않기로 결정한 신청만 정리한다. 프로젝트 루트에서 아래 인자를 실제 값으로 바꿔 실행한다. `<requestId>`와 `<owner>`는 현재 Redis 값이며, 마지막 값은 신청의 캠페인 ID와 사용자 ID를 콜론으로 연결한 값이다.

```text
redis-cli -h <master-host> -p <port> -n <db> --eval \
  apps/commerce-api/src/main/resources/redis/queue-complete.lua \
  'coupon:{issue}:queue:requests' \
  'coupon:{issue}:queue:processing' \
  'coupon:{issue}:queue:users' \
  , '<requestId>' '<owner>' '<campaignId>:<userId>'
```

`1`은 해당 신청을 정리했거나 관련 기록이 이미 없는 경우다. Redis 데이터 유실로 기록이 사라진 것과 이전 정리가 성공한 것은 이 반환값만으로 구분할 수 없으므로, 반드시 기존 작업과 DB 결과를 먼저 확인한다. `-1`은 상태·소유자 등 불일치이므로 Redis와 DB를 다시 확인한다. 명령 응답이 유실되면 재실행 전에 현재 기록을 확인한다. 쿠폰 발급 여부는 본인 쿠폰 목록이나 MySQL에서 확인한다.

## 3. 처리가 필요한 신청 재등록

기존 작업 및 DB 결과를 확인한 뒤 재처리할 수 있는 신청만 대기열에 다시 넣는다. 재시도 횟수와 다음 시도 시각은 유지된다.

```text
redis-cli -h <master-host> -p <port> -n <db> --eval \
  apps/commerce-api/src/main/resources/redis/queue-retry.lua \
  'coupon:{issue}:queue:waiting' \
  'coupon:{issue}:queue:requests' \
  'coupon:{issue}:queue:processing' \
  , '<requestId>' '<owner>' 100
```

- `1`: 해당 신청이 대기열에 등록됐거나 이미 대기 Set에 등록되어 있고 처리 중 소유자 기록은 없다.
- `0`: 대기열이 가득 차 처리 중 기록을 유지한다. 빈자리가 난 뒤 다시 확인한다.
- `-1`: 신청 상태·소유자가 달라졌거나 `WAITING` 기록과 실제 대기 Set·처리 중 기록이 일치하지 않는다. Redis와 DB를 다시 읽고 조사한다.

첫 번째부터 세 번째까지의 DB 시도가 예약된 뒤 지연 시각이 기록되기 전에 중단됐다면, 수동 재등록 시 Redis 시각을 기준으로 각각 1·2·4초를 보수적으로 기다린다. 이미 저장된 재시도 시각이 더 늦다면 그 시각을 유지한다. DB 작업 전에 예약한 횟수는 실제 DB 작업이 시작되지 않았더라도 보수적으로 사용된 것으로 남을 수 있다.

네 번째 시도 후 결과가 불명확하다면 재시도 횟수가 소진됐다는 이유만으로 실패를 확정하지 않는다. 작업과 DB 결과를 먼저 확인한다. 발급이 완료됐거나 안전하게 처리 종료를 결정할 수 있을 때만 위 정리 절차를 사용한다. 계속 불명확하면 닫힌 상태로 유지한다.

## 4. 작업자 재시작

영향받은 작업과 DB 트랜잭션의 종료·결과를 확인한 다음, 로컬 실습에서는 `--coupon.queue.open-on-start=true`를 명시하여 해당 JVM을 수동으로 재시작한다. 옵션 없이 시작하면 기본적으로 닫혀 있다. 이 옵션을 자동 재시작 설정에 상시 지정하면 수동 확인 없이 열릴 수 있으므로 사용하지 않는다. 새 JVM은 남은 처리 중 신청을 자동 재등록하지 않는다. 확인되지 않은 작업이 있다면 열지 않는다.

대기열이 가득 차 재등록할 수 없다면 확인된 기존 대기 신청을 먼저 처리해 자리가 생긴 뒤 해당 신청을 재등록한다. 다른 신청을 임의로 삭제하지 않는다.
