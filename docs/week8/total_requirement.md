## 현재 적용하는 사용자 변경 · 원문과 구분

후속 설계 논의에서 사용자가 Redis 전체 한도를 없애고 인스턴스별 Java Semaphore만으로 처리 여력을 제한하는 B를 선택했다.
추가로 최대 동시 발급 수를 YAML에서 변경하도록 요청했다. 아래 원문 요약과 충돌하는 수용/Redis 항목은 이 변경과 [현재 설계](design.md)를 우선한다.

- 현재 동시 한도는 인스턴스별이다. 전체 인스턴스 합계 C 보장을 요구하지 않는다.
- `coupon.admission.max-concurrency: 3`을 초기 YAML 값으로 두고 각 인스턴스 시작 시 한 번 읽는다. 변경은 재시작 시 적용한다.
- 0/음수/잘못된 형식은 시작 시 거절한다. 요청마다 Semaphore를 만들거나 HTTP 입력으로 한도를 받지 않는다.
- 한 인스턴스의 신규 발급 경로 전체가 singleton Semaphore를 공유한다. tryAcquire 실패는 즉시 429다.
- 기존 완료 쿠폰은 permit 없이 반환한다. DB TX/실행 종료 확인 뒤 획득한 permit을 한 번만 반환한다.
- Redis 실행 Set/Lua·전역 token 반환·Redis 장애를 근거로 한 신규 발급 차단은 현재 coupon 경로에서 제외한다.
- 기존 다른 기능의 Redis 사용/연결은 유지한다. Redis 1초 수용 설정 선택은 현재 coupon 경로에 적용하지 않는다.
- 기존 로컬 관리자 제어/기본 닫힘·명시적 열기는 인스턴스 단위로 유지한다. DB 종료 불명은 자기 permit을 유지하고 해당 인스턴스를 닫는다.
- 사전 DB 슬롯·마지막 issuedCount 갱신·실제 쿠폰 INSERT의 한 TX, 사용자/슬롯 유일 제약은 유지한다.
- 검증은 실제 인스턴스별 C와 여러 인스턴스의 합계를 구분한다. 원문 Redis C 검증을 완료했다고 기록하지 않는다.
- 후속 A 선택으로 coupon 진행 중/완료 사용자 Redis 목록과 캠페인+사용자 Redis 분산락도 추가하지 않는다. 중복 효과는 DB 제약으로 보호한다.
- 21-B로 캠페인 startsAt/endsAt와 active를 요청 시 함께 판단한다. 스케줄러 없이 기간 밖 신규 발급을 거절하며 기존 쿠폰은 보존/조회한다.
- 22-A로 쓰기 전 슬롯 재확인은 최초 포함 최대 4회·간격 50ms·예산 200ms를 초기값으로 사용한다. 전체 HTTP/실행 중 DB 작업의 강제 종료 보장이 아니다.
- 23-A/24-A로 쓰기 DB 시각·마지막 캠페인 검증 시점에 기간을 판단한다. 이때 마감이면 전체 rollback하며, 마감 전 검증을 통과한 TX의 마감 후 commit은 허용한다.
- 25-A로 시작 후 시작/종료 시각도 고정한다. 26-A로 수동 복구는 실행 ID 목록을 지정하고 각 결과를 반환하며 종료 확인/닫힘 유지 조건은 보존한다.

### 구현에 연결한 현재 계약

- 신규 발급은 동기 처리하며 DB 쿠폰·슬롯·issuedCount가 원본이다. Redis 장애로 확정 쿠폰을 취소하지 않는다.
- `POST /api/v1/coupon-campaigns/{campaignId}/issues`는 헤더에서 확인한 사용자만 사용하고 최초 201·기존 결과 200이다.
- `GET /api/v1/coupons`는 본인 전체 목록을 발급 시각·ID 내림차순으로 반환한다. 저장 혜택과 기존 결과는 마감·품절·닫힘 뒤에도 유지한다.
- 쿠폰 업무 거절 409, 포화 429, 닫힘·종료 불명·일시 경합 503을 구분하며 예약이나 향후 발급 성공을 약속하지 않는다.
- 로컬 관리자 fixture는 상태·닫기·종료 확인·지정 복구·개방을 분리한다. 빈 registry나 요청 필드만으로 원 세션 종료를 추정하지 않는다.
- C05 Redis 누적 집계는 발급 ID 중복 반영을 막고 미준비와 0을 구분한다. DB 기준 재집계와 UUID fence로 지연된 옛 publish를 차단한다.
- 영속 전달·자동 누락 재시도 저장소는 추가하지 않는다. commit 뒤 process 종료 누락은 대조·통제된 재집계 대상이다.

[설계](design.md)와 [API·운영 안내](completed/operations.md)가 실제 경계·경로·입력을 정의한다.
아래 최초 원문 중 변경되지 않은 총량·사용자 중복·데이터 보존 조건은 계속 유효하다.
원문의 quota=5/사용자 8명 실험 등 근거가 아직 없는 항목은 검증 매핑에서 별도로 유지한다.

## 원문 과제 요약 · 변경 전 계약 기록

이하 내용은 최초 과제의 원문 요약을 보존한 역사 구간이다. Redis Set/Lua 전역 C·Redis 장애 시 신규 발급 차단 등 현재 변경과 충돌하는 조건은 실행 지시가 아니다. 적용 여부는 위 현재 계약과 설계·검증 매핑을 따른다. 원문 자체의 고유 학습·검증 요구를 지우지 않기 위해 같은 파일 안에 보존한다.

## 범위와 서로 다른 한도

| 대상 | 의미 | 보호 경계 |
|---|---|---|
| 발급 총량 | 캠페인에서 발급 가능한 누적 쿠폰 수 | DB TX·잠금 또는 조건부 변경 |
| 현재 처리 자리 | 신규 발급 경로 전체에서 진행 중인 실행 최대 C개 | 공유 Redis Set·Lua |
| 사용자 중복 | 캠페인마다 사용자당 한 장 | DB 유일 제약과 기존 결과 반환 |

발급 실행이 끝나면 자리만 반환한다. 발급된 쿠폰을 삭제하거나 issuedCount를 감소시키지 않는다.
요청률·처리량·동시성·지연을 구분하고 rate limit을 동시성 제한으로 대신하지 않는다.

포함: 작은 캠페인 fixture/로컬 준비 코드, 동기 쿠폰 발급, 본인 보유 목록, 수용·반환·장애/재개 검증.
제외: 캠페인 관리 화면/전체 CRUD, 대기실·순번·비동기 worker, 쿠폰 사용/할인·알림, 실제 인증/공개 배포.
기존 7주차까지의 기능은 유지하고 주문 이벤트/구매 활동을 쿠폰에 불필요하게 연결하지 않는다.

## 데이터·사용자·API

- 캠페인: ID·이름·발급 가능 여부·총 발급 한도·현재 발급 수.
- 보유 쿠폰: 쿠폰 ID·사용자·캠페인·발급 시각·고정 혜택 정보. 실제 할인은 적용하지 않는다.
- 기존 로컬 사용자 식별/관리자 테스트 설정을 유지한다. 별도 userId 입력으로 타인 발급/조회를 허용하지 않는다.
- 목록은 발급 시각 내림차순·couponId 내림차순 등 안정적인 순서와 본인 결과만 보장한다.

| API/결과 | 계약 |
|---|---|
| `POST /api/v1/coupon-campaigns/{campaignId}/issues` | 현재 사용자의 발급 |
| `GET /api/v1/coupons` | 현재 사용자의 보유 목록 |
| 최초 발급 | HTTP 201·저장된 couponId |
| 동일 사용자·캠페인 기존 발급 | HTTP 200·같은 couponId |
| 품절/비활성 | 업무 거절, 기존 API 규칙에 맞춰 코드·상태 명시 |
| 처리 자리 없음 | HTTP 429 |
| 수용 상태 확인 불가 | HTTP 503 |

기존 쿠폰은 캠페인이 품절/비활성이 된 뒤에도 반환한다. 429·503은 발급 예약/성공 약속이 아니다.

## DB 불변식

1. 발급 가능 여부·잔여 한도 확인, issuedCount 증가, 쿠폰 insert는 같은 TX다.
2. 모든 실행에서 `issuedCount <= totalQuota`, `(campaignId, userId)` 유일 제약을 유지한다.
3. 마지막 쿠폰은 잠금/조건부 변경으로 보호하고 insert 실패 시 발급 수 증가도 rollback한다.
4. 사전 조회가 없었어도 TX 안에서 중복을 재검사한다. 중복은 발급 수를 늘리지 않고 기존 결과를 반환한다.
5. 충돌 예외를 처리하면 실패한 TX를 rollback한 뒤 새 TX에서 기존 쿠폰을 확인한다.
6. 연결 오류·다른 제약 오류를 중복 성공으로 숨기지 않는다.

## Redis 수용과 반환

기존 쿠폰 조회 → 없을 때 Redis 수용 → 확정 수용된 실행만 DB 발급 TX → 실행/TX 종료 확인 → 자기 token 반환.

- 전용 Set 키를 신규 발급 경로 전체가 공유한다. C는 신뢰하는 서버 설정이고 HTTP 입력이 아니다.
- token은 서버가 실행마다 생성한다. 사용자+캠페인·couponId·고객 요청 키와 구분하고 다른 실행이 공유하지 않는다.
- 동일 token 확인·SCARD·빈자리 SADD는 한 Lua 실행이다. 애플리케이션의 두 round-trip으로 나누지 않는다.
- 같은 token 재확인은 동일 실행 안에서만 사용한다. 수용 응답 불확실 시 DB 발급을 시작하지 않는다.
- 반환은 `SREM permitsKey ownToken`이며 반복/모르는 token 반환이 다른 점유에 영향을 주지 않는다.
- 이미 완료된 중복은 자리 없이 반환한다. 아직 완료되지 않은 동시 중복 HTTP 실행은 각각 자리를 쓸 수 있다.
- DB 성공/확정 거절/rollback 뒤 실행 종료를 확인해야 반환한다. HTTP 종료/timeout은 종료 증거가 아니다.
- DB 결과·작업 종료 불명 시 점유를 유지한다. 반환 실패 때문에 이미 발급한 쿠폰을 취소하지 않는다.

## 연결·장애·보수적 재개

- `modules/redis` 설정을 확인하고 `redisTemplateMaster`의 실제 선언 타입·String serializer로 script를 실행한다.
- replica count로 승인하지 않는다. command timeout을 제한하며 실제 애플리케이션 endpoint로 장애를 만든다.
- Redis 접근 실패/불확실 응답은 신규 발급 503·신규 DB 발급 시작 금지다. 로컬 count/무제한 queue로 우회하지 않는다.
- DB가 정상이라면 기존 본인 목록·완료 결과 조회는 유지한다.
- 로컬 수용은 기본 닫힘과 명시적 열기를 둔다. 오류/상태 유실 후 건강 확인만으로 자동으로 다시 열지 않는다.
- 신규 수용을 닫고 해당 실행·DB 작업 종료와 실제 쿠폰 결과를 확인한 뒤 자기 범위의 비활성 token만 정리해 연다.
- 종료 불명확 시 닫힘을 유지한다. TTL/시간 경과로 활성 자리를 자동 회수하지 않는다.
- 보장 범위는 로컬 인스턴스의 통제된 장애·재개다. 미감지 상태 손실/다중 인스턴스 자동 failover 안전성을 주장하지 않는다.

## 필수 검증

| 장면 | 기대 결과 |
|---|---|
| 정상 발급·본인 목록 | 쿠폰 1·issuedCount 1·같은 ID·타인 미노출 |
| 순차/동시 같은 사용자·캠페인 | 같은 쿠폰 하나·발급 수 증가 한 번 |
| 마지막 수량 경쟁 | 총량 초과 0·품절과 수용량 거절 구분 |
| 발급 수 증가 뒤 insert 실패 | 전체 rollback·종료 후 자리 반환 |
| commit 뒤 응답 유실 | 재요청에서 기존 쿠폰·추가 발급 0 |
| 실제 Redis 중단 | 신규 발급 503·신규 DB 효과 0·기존 목록 유지 |
| 반환 실패·복구 | 쿠폰 유지·수용 닫힘·확인 후 명시적 재개 |
| 반복/모르는 token 반환 | 다른 활성 token 보존 |

C=3 실험은 실제 Redis에서 세 요청을 획득 직후/DB TX 전에 barrier로 유지한다.
활성 token 3개에서 네 번째는 429·DB 발급 경로 미진입·쿠폰 없음이어야 한다.
한 실행을 완료/반환한 뒤 네 번째 사용자가 재요청해 발급되고, 모두 종료 후 token 0을 확인한다.
barrier/대기에는 deadline을 두고 실패 시 자기 실행만 해제/정리한다. mock/local count로 대체하지 않는다.

DB 총량 검증은 충분한 Redis 수용량 또는 DB handler 직접 경쟁으로 분리한다.
총 5장·서로 다른 8명 참여 시 성공 5·품절 3·쿠폰 5·issuedCount 5다. Redis 거절은 품절에 세지 않는다.
TTL 시간 경과만으로 점유가 사라지지 않는 것도 확인한다.

실제 MySQL/Redis fixture를 재사용하고 자기 테스트 자원만 정리한다.
연결 오류·skip·0건은 성공이 아니다. 관련 회귀·Checkstyle·ArchUnit과 PR 마무리 전체 검사를 유지한다.
