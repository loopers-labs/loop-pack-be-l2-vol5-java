원문 과제(`ref/week8/assignment.md`, 학습 자료 `ref/week8/study.md`)를 구현과 테스트의 기준으로 쓸 수 있게 정리한 문서다.
W7 명세(`docs/week7/requirements.md`)의 규칙 ID 와 출처 구분을 그대로 쓰고, 이번 주에 생긴 것만 적는다.

| | |

## 출처 구분

W2 의 표기(`원문`, `정함`, `선택`, `보안`, `범위`, `질문`)를 그대로 쓴다.

## 규칙 ID

W7 의 갈래에 넷을 더한다. `EXP` 는 W7 번호를 이어 쓴다.

| 접두사 | 다루는 것 |
|---|---|
| `CPN` | 캠페인과 쿠폰의 계약, 발급과 목록 API |
| `ISS` | DB 가 지키는 발급 총량, 사용자당 한 장, 원자성 |
| `ADM` | Redis 의 현재 처리 자리(수용과 반환) |
| `FLT` | Redis 장애, 수용 닫기, 재개 |

## 세 가지 수

이번 주의 규칙은 아래 셋을 섞지 않는 데서 나온다.

| 수 | 지키는 곳 | 실행이 끝나면 |
|---|---|---|
| 발급 총량(`issuedCount <= totalQuota`) | DB | 줄지 않는다 |
| 사용자당 발급 수(한 장) | DB 유일 제약 | 줄지 않는다 |
| 현재 발급 실행 수(최대 C) | Redis | 자기 자리를 반환한다 |

같은 사용자가 두 번 누르면 HTTP 실행은 둘이고 쿠폰은 하나다. 앞의 것은 `ADM` 이, 뒤의 것은 `ISS` 가 센다.

## ISS: DB 의 발급 총량과 중복

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `ISS-001` | 발급 가능 여부와 남은 한도 확인, 발급 수 증가, 쿠폰 insert 를 한 TX 에서 한다 | 원문 | |
| `ISS-002` | 어떤 실행 순서에서도 `issuedCount <= totalQuota` 이고 `issuedCount` 는 실제 쿠폰 수와 같다 | 원문 | 동시 경쟁 뒤 두 값이 같고 한도 이하 |
| `ISS-003` | 마지막 한 장을 둘이 동시에 가져가지 못하게 한다. 수단은 잠금이나 조건부 변경이다 | 원문, 질문(Q-2, 수단) | |
| `ISS-004` | `(campaignId, userId)` 유일 제약을 둔다. 먼저 조회해서 없었다는 사실만으로 중복을 막았다고 보지 않는다 | 원문 | |
| `ISS-005` | 쿠폰 insert 가 실패하면 발급 수 증가도 rollback 한다 | 원문 | 쿠폰 0, 발급 수 그대로 |
| `ISS-006` | 중복이면 발급 수를 늘리지 않고 기존 쿠폰을 돌려준다. 유일 제약 위반을 받으면 그 TX 를 rollback 한 뒤 새 TX 에서 기존 쿠폰을 읽는다. 연결 오류나 다른 제약 위반을 중복 성공으로 바꾸지 않는다 | 원문 | 동시에 같은 사용자 둘이 와도 쿠폰 1, 발급 수 1 |

## ADM: Redis 의 현재 처리 자리

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `ADM-001` | 발급 경로는 기존 쿠폰 조회, 자리 획득, DB 발급 TX, 자리 반환 순서다. 기존 쿠폰이 있으면 자리를 잡지 않고 돌려준다 | 원문 | |
| `ADM-002` | 자리는 Redis Set 에 실행 token 을 넣어 잡는다. token 은 서버가 실행마다 만들고 사용자 ID, 요청 키, `couponId` 와 다르다. 두 실행이 같은 token 을 쓰지 않는다 | 원문 | |
| `ADM-003` | token 존재 확인, Set 크기 확인, 추가를 Lua 스크립트 한 번으로 한다. `SCARD` 와 `SADD` 를 두 번의 호출로 나누지 않는다 | 원문 | |
| `ADM-004` | 수용량 C 는 서버 설정이고 HTTP 로 받지 않는다. 쿠폰 발급 전용 키를 쓰고 캐시 키와 섞지 않는다 | 원문 | |
| `ADM-005` | 자리가 없으면 429 `COUPON_BUSY` 와 `Retry-After` 를 준다. 429 는 발급 성공이나 나중 발급의 약속이 아니고, `Retry-After` 의 시각에 자리가 있다는 약속도 아니다 | 원문, 정함(Q-4, W5 `PAYMENT_BUSY` 는 그대로. `Retry-After`) | 429 뒤 그 사용자의 쿠폰 0, DB 발급 경로 진입 0, `Retry-After` 있음 |
| `ADM-006` | 자리를 얻었다고 발급된 것이 아니다. 품절, 비활성, 중복, 오류는 DB 가 판정하고 응답은 DB 결과를 따른다 | 원문 | |
| `ADM-007` | DB 의 commit 이나 rollback 과 실행 종료를 확인한 뒤 자기 token 만 `SREM` 으로 반환한다. 반환해도 발급 수를 줄이지 않는다. 같은 반환을 두 번 하거나 모르는 token 을 반환해도 다른 자리는 그대로다 | 원문 | |
| `ADM-008` | client timeout 이나 연결 종료만으로 반환하지 않는다. token 에 TTL 을 두어 시간이 지나면 자리를 비우지 않는다 | 원문 | 시간이 지나도 활성 token 이 남는다 |
| `ADM-009` | 수용 판단은 master 연결(`redisTemplateMaster`)로 한다. 기본 연결(`REPLICA_PREFERRED`)이 읽은 값으로 판단하지 않는다 | 원문 | |
| `ADM-010` | 같은 사용자의 동시 요청은 각자 자리를 차지할 수 있다. DB 효과는 하나다(`ISS-006`) | 원문 | |
| `ADM-011` | 발급 TX 에서 품절을 한 번 본 서버는 그 캠페인의 신규 발급을 자리 획득 없이 409 `COUPON_SOLD_OUT` 으로 거절한다. 기존 쿠폰 조회는 그 앞에 그대로 둔다(`CPN-004`) | 정함 | 자리가 모두 차 있어도 품절 뒤 요청은 429 가 아니라 409 |

## FLT: 장애와 재개

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `FLT-001` | Redis 접근 실패, timeout, 해석할 수 없는 응답이면 신규 발급을 시작하지 않고 503 이다. 로컬 count 나 다른 queue 로 우회하지 않는다 | 원문 | DB 신규 효과 0 |
| `FLT-002` | Redis 장애 중에도 DB 가 정상이면 보유 목록과 기존 쿠폰의 200 응답은 그대로다 | 원문 | |
| `FLT-003` | 반환 호출이 실패해도 발급한 쿠폰과 발급 수를 되돌리지 않는다 | 원문 | |
| `FLT-004` | Redis 장애나 상태 유실을 확인하면 신규 수용을 닫고 자동으로 열지 않는다. 연결 복구나 `PONG` 만으로 열지 않는다. 로컬 실행은 닫힌 상태로 시작하고 명시적으로 연다 | 원문, 질문(Q-3, 닫힘 상태의 위치와 여는 수단) | |
| `FLT-005` | 열기 전에 진행 중이던 발급 실행과 DB 작업이 모두 끝났는지, 실제 쿠폰 결과가 어떤지 확인하고 자기 범위의 남은 token 만 정리한다. 끝났는지 모르면 닫아 둔다 | 원문 | |
| `FLT-006` | 이 방식은 로컬 단일 인스턴스의 통제된 장애와 재개까지만 보장한다. 감지하지 못한 Redis 상태 손실과 다중 인스턴스 장애 전환을 안전하다고 주장하지 않는다 | 원문, 범위 | |

## EXP: 실험

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `EXP-015` | 수용 제한 없이 동시 요청 수를 1 에서 256 까지 올리며 처리량, 지연, 커넥션 풀의 사용과 대기, 바쁜 워커 스레드, CPU, 행 잠금 대기를 잰다. 발급 구간(한도를 크게 두어 측정 중 품절되지 않음)과 품절 구간(이미 품절된 캠페인)을 따로 잰다. knee 는 최대 처리량의 90% 에 처음 닿는 동시 요청 수로 정하고, C 는 knee 로 둔다. 그 지점에서 먼저 바닥나는 자원을 `ISS-003` 수단의 근거로 쓴다 | 정함 | 설계 문서에 측정값, 병목 자원, knee 와 C |
| `EXP-016` | 쿠폰 발급이 몰릴 때 다른 기능이 받는 영향을 잰다. 다른 API 는 DB 만 쓰는 것(포인트 잔액 조회)과 Redis 캐시를 쓰는 것(상품 목록) 하나씩을 일정한 속도로 부른다. 같은 부하로 다섯 번 돌린다: 다른 API 만, 수용 제한 없는 쿠폰 부하와 함께, 수용 제한(C)을 둔 쿠폰 부하와 함께. 수용 제한을 둔 실행은 429 뒤 클라이언트의 재시도 방식을 바꿔 세 번 돌린다: 바로 다시 보냄, `Retry-After` 만큼 기다림, `Retry-After` 에 지터를 섞어 기다림. 429 로 거절되는 요청이 쓰는 워커 스레드, 커넥션, Redis 호출도 함께 본다 | 정함 | 실행별 다른 API p99 와 실패율, 커넥션 풀 대기, `tomcat.threads.busy`. 판정: `Retry-After` 와 지터를 지키는 실행에서 다른 API p99 가 기준 실행의 2 배 이내다. 넘으면 막는 자원이 다른 것이므로 설계를 다시 본다 |
| `EXP-017` | 실제 Redis 에 C=3 을 두고, 서로 다른 세 사용자의 실행을 자리 획득 뒤 DB TX 전에 barrier 로 붙잡는다. 활성 token 3 을 확인하고 네 번째를 보낸다. 한 실행을 끝내 반환을 확인한 뒤 네 번째가 다시 요청한다. barrier 는 deadline 을 두고 실패 시 자기가 시작한 실행을 정리한다 | 원문 | 네 번째 첫 요청은 429, 쿠폰 0. 다시 요청하면 201. 모두 끝나면 활성 token 0, 쿠폰과 발급 수 4 |
| `EXP-018` | 자기 token 을 두 번 반환하고, 모르는 token 을 반환한다 | 원문 | 다른 활성 token 이 그대로다 |
| `EXP-019` | DB 한도 경쟁. Redis 자리를 충분히 두거나 DB 발급을 직접 동시에 불러, 한도 5 에 서로 다른 8 명이 DB 발급에 참여한다. Redis 에서 거절된 요청을 품절에 세지 않는다 | 원문 | 발급 5, 품절 3, 쿠폰 5, 발급 수 5 |
| `EXP-020` | 쿠폰 결과 장면: 정상 발급과 본인 목록, 같은 사용자 재요청, 같은 사용자 동시 발급, 발급 수 증가 뒤 insert 실패, commit 뒤 응답 유실 후 재요청 | 원문 | `CPN-004`, `CPN-007`, `ISS-005`, `ISS-006` 의 관찰값. 실패한 실행도 끝나면 자리를 반환한다 |
| `EXP-021` | 애플리케이션이 실제로 쓰는 Redis endpoint 를 내린다. 다시 올린 뒤 `FLT-004`, `FLT-005` 의 절차로만 연다. 반환 실패 장면도 만든다 | 원문 | 장애 중 신규 발급 503, DB 신규 효과 0, 기존 목록 유지. 반환 실패 뒤 쿠폰 유지, 수용 닫힘, 확인 뒤 남은 점유 정리 |

### 원문 체크리스트와 규칙

| 원문의 체크 | 규칙 |
|---|---|
| 정상 발급 결과를 본인 보유 목록에서 조회하고 다른 사용자 결과를 노출하지 않는다 | `CPN-003`, `CPN-007`, `EXP-020` |
| 한도, 사용자 중복, 발급 수와 쿠폰 insert 를 DB 에서 원자적으로 보호한다 | `ISS-001` ~ `ISS-006`, `EXP-019` |
| 처리 자리 반환이 발급된 쿠폰이나 총량을 되돌리지 않는다 | `ADM-007`, `FLT-003` |
| 실제 Redis 의 원자 연산으로 C=3 에서 유지 중인 세 실행과 네 번째 거절을 확인한다 | `ADM-003`, `EXP-017` |
| 실행 종료 뒤 자기 token 만 반환하고 새 요청이 그 자리를 재사용한다 | `ADM-007`, `EXP-017`, `EXP-018` |
| 동일 업무의 중복 효과와 동시에 진행 중인 HTTP 실행 수를 구분한다 | `ADM-010`, `ISS-006` |
| Redis 장애에서 신규 발급을 우회하지 않고 기존 DB 결과 조회는 유지한다 | `FLT-001`, `FLT-002`, `EXP-021` |
| timeout 과 TTL 만으로 활성 자리를 재사용하지 않으며 확인 후 명시적으로 재개한다 | `ADM-008`, `FLT-004`, `FLT-005` |
| 관련 기능, 회귀, lint, ArchUnit 을 실행하고 자기 테스트 자원을 정리한다 | 전체 |

## 범위 밖

사용자 대기실, 비동기 worker, 쿠폰 사용과 할인 적용, 알림, 실제 인증, 다중 인스턴스 장애 전환(원문).
요청 도착 순서의 공정성(선착순). 발급 순서는 Redis 가 자리를 내준 순서와 DB 잠금을 얻은 순서이고, 사용자가 요청한 순서와 같다고 약속하지 않는다(정함).
사용자별 요청 제한, 앱 앞의 rate limit. 협조하지 않는 클라이언트가 429 를 무시하고 다시 보내는 장면은 `EXP-016` 에서 재고, 막는 방법은 설계 문서의 고르지 않은 선택지에 둔다(정함).
