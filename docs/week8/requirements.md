## 세 가지 수

| 수 | 정하는 곳 | 끝까지 지키는 곳 |
|---|---|---|
| 발급 총량 | Redis 예약 집합 크기 | DB 조건부 update(`ISS-002`) |
| 사용자당 한 장 | Redis 예약 집합 | DB 유일 제약(`ISS-004`) |
| 동시에 DB 에 쓰는 실행 수(C) | 워커의 consumer 스레드 수 | 같음 |

Redis 가 빠르게 정하고, DB 가 느리게 기록하며, Redis 가 상태를 잃은 경우에만 DB 가 최종 판정을 한다. 요청 경로에는 DB 쓰기가 없다. 주문, 결제, 이벤트, 구매 활동(W2 ~ W7)은 그대로 두고 쿠폰에 연결하지 않는다(원문).

| `CPN-008` | 발급된 쿠폰은 사용자, 캠페인, `couponId`, `issueNumber`, 발급 시각, 혜택 정보를 DB 에 남긴다. 캠페인이 끝나거나 품절돼도 지우지 않는다 | 원문, 정함 | |

## RSV: Redis 예약

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `RSV-001` | 접수는 캠페인마다 Redis 의 예약 집합 하나로 정한다. 이 사용자가 이미 있는지, 집합 크기가 한도에 닿았는지, 없으면 다음 번호로 추가하는 것을 Lua 하나로 한다. 세 판단 사이에 다른 요청이 끼지 않는다. 명단에는 캠페인을 만들 때 준비 표식을 넣고, 표식이 없으면 받지 않는다 | 공지, 정함 | 같은 사용자 동시 요청 둘이면 번호 하나 |
| `RSV-002` | `issueNumber` 는 Redis 가 그 캠페인의 요청을 받아들인 순서다. 1 부터 시작하고 가장 큰 번호 + 1 로 매긴다. 취소(`PUB-002`)와 유실 복구 뒤에는 빈 번호가 생길 수 있고, 유실 복구 창(`FLT-008`) 안에서는 같은 번호가 두 사용자에게 갈 수 있다. 번호는 순서를 말할 뿐 쿠폰의 identity 가 아니다 | 정함 | 유실 없는 실행에서 한도 N 이면 번호 1 ~ N 이 정확히 한 번씩 |
| `RSV-003` | 한도와 발급 가능 여부는 DB 의 캠페인에서 읽어 프로세스에 캐시하고 Lua 에 인자로 준다. 캠페인은 만든 뒤 바뀌지 않으므로 캐시를 갱신하지 않는다. 함께 넘기는 DB 발급 수는 유실 감지(`FLT-008`)의 하한이라 뒤처져도 되고, 대사가 주기마다 갱신한다 | 정함 | 접수 요청마다 DB 읽기가 없다. 하한이 뒤처진 동안 유실 오탐이 없다 |
| `RSV-005` | 요청 경로에는 자리 제한이 없다. 예약은 Redis 가 받는 만큼 받는다. 처리량 제한은 워커에 있다(`WRK-002`) | 공지, 실험 | 한도 안에서는 요청이 몰려도 429 가 없다 |

## PUB: 발행

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `PUB-001` | 예약이 되면 캠페인 ID, 사용자 ID, `issueNumber`, 예약 시각을 담은 메시지를 보내고, broker 의 확인(`acks=all`)을 받은 뒤 202 를 돌려준다 | 정함 | 202 를 받았으면 메시지가 broker 에 있다 |
| `PUB-002` | 발행 결과는 셋이다. 확인을 받으면 202. 확인이 제한 시간 안에 오지 않으면(Unconfirmed) producer 가 메시지를 아직 쥐고 있어 뒤늦게 닿을 수 있으므로 예약은 남기고 503 이다. 다시 요청하면 같은 번호로 200 `PENDING` 이고, 메시지가 끝내 안 갔으면 대사(`RCN-001`)가 보낸다. producer 가 포기한 실패(Rejected. 직렬화 실패, 없는 토픽, 크기 초과, `delivery.timeout.ms` 만료)는 메시지가 없는 것이 확실하므로 예약을 지우고 503 이다. 지우는 것도 실패하면 예약은 남고 503 이며 대사가 메운다 | 정함 | Unconfirmed 503 뒤 예약은 남고 재요청은 같은 번호다. Rejected 503 뒤 예약이 없고 재요청은 새로 접수된다 |
| `PUB-003` | 메시지 키는 사용자 ID 다. 캠페인 하나의 메시지가 파티션 전부에 흩어져 consumer 수만큼 병렬로 기록되고, 같은 사용자의 메시지(원본과 대사의 재발행)는 한 파티션에 차례로 쌓인다. 순번은 Redis 가 정하므로 기록 순서는 결과를 바꾸지 않는다 | 정함(Q-12) | 캠페인 하나의 기록 처리량이 C 에 비례한다. 같은 사용자의 두 메시지가 동시에 DB 에 들어가지 않는다 |
| `PUB-004` | broker 가 느리거나 죽어도 다른 기능의 스레드를 빼앗지 않는다. ack 대기 상한(timeout 500ms)과 동시에 ack 를 기다릴 수 있는 요청 수의 상한(로컬 bulkhead 128, 차면 기다리지 않고 예약 없이 503)을 둔다. circuit breaker 는 두지 않는다. 상한값은 `EXP-022` 로 정했다 | 정함 | broker 가 느린 동안 쿠폰 접수 503 이 늘어도 다른 API p99 는 그대로다 |

## WRK: 워커

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `WRK-001` | 워커는 commerce-api 안의 consumer 다. 쿠폰 발급 전용 consumer group 을 쓴다 | 정함 | |
| `WRK-002` | 동시에 DB 에 쓰는 실행 수는 consumer 스레드 수 C 다. C 는 서버 설정이고 HTTP 로 받지 않는다 | 원문, 정함 | DB 발급 TX 의 동시 수가 C 를 넘지 않는다 |
| `WRK-003` | 쿠폰은 메시지의 `issueNumber` 와 예약 시각을 그대로 기록한다(`ISS-001`). TX 의 단위는 `WRK-011` 이다 | 정함 | |
| `WRK-004` | DB 가 중복이라 하면(`ISS-006`) 그 메시지는 이미 처리된 것이므로 로그만 남기고 넘어간다. 같은 메시지를 두 번 받아도 쿠폰은 하나다 | 정함 | 메시지 재전달 뒤 쿠폰 1, 발급 수 1 |
| `WRK-005` | DB 가 품절이라 하면(`ISS-002`) 로그와 지표에 남기고 넘어가며 다시 시도하지 않는다. 그 사용자가 Redis 명단에 있으면 Redis 가 받아들인 것을 DB 가 거절한 것이라 예약 집합과 DB 가 어긋났다는 뜻이고, 그 캠페인의 유실 복구(`FLT-008`)를 시작한다. 명단에 없으면(DLT 리플레이가 정상 품절에 닿음) 시작하지 않는다 | 정함 | 지표에 그 수가 남는다. 복구 뒤 쿠폰 없는 `PENDING` 이 없다 |
| `WRK-006` | DB 연결 오류 같은 인프라 실패는 같은 메시지를 다시 시도한다. 건너뛰지 않고 offset 을 넘기지 않는다 | 정함 | DB 가 돌아오면 밀린 메시지가 순서대로 처리된다 |
| `WRK-007` | 같은 파티션의 메시지는 받은 순서대로 처리한다. DB 의 쿠폰 생성 순서가 `issueNumber` 순서와 같다고 약속하지 않고, 어긋나는 비율을 잰다(`EXP-024`) | 정함(Q-12) | |
| `WRK-008` | 워커는 서버 설정(`coupon.issue.worker.auto-startup`)으로 켜고 끈다. 끈 동안 접수는 받고 기록만 멈추며, 메시지는 broker 에 남는다 | 정함, 실험 | 끈 채 접수한 사용자는 202 와 `PENDING` 이고, 켜면 순서대로 쿠폰이 된다 |
| `WRK-009` | 다시 해도 같을 실패(읽을 수 없는 메시지, 없는 캠페인, 비활성 캠페인, 그 외 도메인 거절)는 재시도 없이 DLT(`coupon-issues.dlt`)로 보내고 offset 을 넘긴다. 같은 파티션의 다른 메시지가 그 뒤에 막히지 않는다. DLT 로 보내는 것 자체가 실패하면 넘기지 않는다 | 정함 | 그런 메시지 뒤의 정상 메시지는 기록된다. 재시도 지표 0, DLT 지표 1 |
| `WRK-010` | DLT 의 메시지는 원본 위치(topic, partition, offset)를 키로 로그 테이블에 PENDING 으로 적는다. 운영자가 조회하고 골라서 원본 토픽에 다시 보내면 REPLAYED 가 되고 워커가 다시 기록한다. 읽을 수 없는 payload 는 다시 보낼 수 없어 PENDING 으로 남는다 | 정함 | 다시 보낸 메시지의 쿠폰이 생기고 로그가 REPLAYED 다 |
| `WRK-011` | 워커는 poll 묶음(최대 50)을 캠페인별 연속 구간으로 나눠 구간마다 TX 하나로 기록한다. 쿠폰 insert N 과 `issued_count += N` 조건부 update 하나다. 구간에 중복이나 품절, 다시 해도 같을 실패가 섞이면 TX 를 되돌리고 그 구간을 건별로 다시 기록한다(`WRK-004`, `WRK-005`, `WRK-009` 가 그대로 맡는다). 건별로 풀다 DLT 감이 나오면 그 앞까지만 offset 을 넘기고 뒤는 다음 poll 에 다시 받는다 | 정함 | 묶음 셋은 쿠폰 셋, 발급 수 3. 중복이나 품절이 섞여도 쿠폰은 늘지도 빠지지도 않는다. 가운데의 나쁜 메시지만 DLT 로 가고 앞뒤는 기록된다 |

## ISS: DB 가 끝까지 지키는 것

워커의 TX 가 따른다. 요청 경로에서는 실행되지 않는다.

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `ISS-001` | 발급 가능 여부와 남은 한도 확인, 발급 수 증가, 쿠폰 insert 를 한 TX 에서 한다 | 원문 | |
| `ISS-002` | 어떤 실행 순서에서도 `issuedCount <= totalQuota` 이고 `issuedCount` 는 실제 쿠폰 수와 같다 | 원문 | 워커가 다 비운 뒤 두 값이 같고 한도 이하 |
| `ISS-003` | 마지막 한 장을 둘이 동시에 가져가지 못하게 한다. 수단은 조건부 변경이다 | 원문, 정함 | |
| `ISS-004` | `(campaignId, userId)` 유일 제약을 둔다. Redis 예약 집합이 막았다는 사실만으로 중복을 막았다고 보지 않는다 | 원문 | |
| `ISS-005` | 쿠폰 insert 가 실패하면 발급 수 증가도 rollback 한다 | 원문 | 쿠폰 0, 발급 수 그대로 |
| `ISS-006` | 중복이면 발급 수를 늘리지 않는다. 유일 제약 위반을 받으면 그 TX 를 rollback 한다. 연결 오류나 다른 제약 위반을 중복으로 바꾸지 않는다 | 원문 | 같은 사용자 메시지 둘이어도 쿠폰 1, 발급 수 1 |

## RCN: 대사

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `RCN-001` | 10 초마다 활성 캠페인마다 Redis 예약 집합과 DB 쿠폰을 대조한다. 워커가 비어 있을 때(topic 전체 lag 0)만 대조하고, 밀려 있으면 하한과 지표만 갱신한다. 누락은 번호로 고른다. 지난 실행 때 본 최대 번호 이하인데 그 사용자의 쿠폰이 DB 에 없는 번호다. 그 사용자의 메시지를 다시 보낸다 | 정함(Q-14) | 메시지를 잃은 예약이 큐가 빈 뒤 다음 대사에 쿠폰이 된다. 정상 부하에서 재발행 수 0 |
| `RCN-002` | 캠페인마다 밀린 수(Redis 예약 수 − DB 발급 수), `WRK-005` 의 수, 워커가 밀려 대사를 건너뛴 주기 수를 지표로 낸다 | 정함 | |
| `RCN-003` | 대사는 쿠폰을 직접 만들지 않는다. 메시지를 다시 보내고 워커가 기록한다. 워커의 `WRK-004` 가 있어 같은 예약을 두 번 보내도 쿠폰은 하나다. 다시 보낸 메시지의 예약 시각은 대사 시각이다 | 정함 | 다시 보낸 접수의 쿠폰 `issued_at` 은 대사 시각이다 |

## FLT: 장애

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `FLT-001` | Redis 접근 실패, timeout, 해석할 수 없는 응답이면 접수하지 않고 503 이다. DB 로 우회해 접수하지 않는다. timeout 은 Lua 가 이미 적용됐을 수 있다. 그러면 예약만 남고 메시지가 없는 `FLT-004` 와 같은 상태라 재요청은 같은 번호로 `PENDING` 이고 `RCN-001` 이 메운다 | 원문, 실험 | 장애 중 DB 쓰기 0. timeout 뒤 재요청은 새 번호를 받지 않는다 |

| `FLT-005` | Redis 가 예약 상태를 잃어도 202 를 받은 사용자의 쿠폰은 잃지 않고, 잃은 명단으로 새로 202 를 주지 않는다. 명단이 통째로 사라지면 준비 표식이 같이 사라져 첫 요청에서 닫힌다. 꼬리만 사라지는 경우(재시작, failover)는 설계 11.1 의 뒤집을 조건이다. 202 는 broker 확인 뒤에만 주므로(`PUB-001`) 그 메시지는 broker 에 있고 워커는 Redis 와 무관하게 기록한다 | 정함 | 유실 뒤 복구를 거치면 202 받은 사용자 전원에게 쿠폰이 있다 |
| `FLT-006` | 워커의 인프라 실패는 `WRK-006` 이다. 밀린 메시지는 broker 에 남고 사용자는 202 상태 그대로다 | 정함 | |
| `FLT-007` | 이 방식은 로컬 단일 인스턴스와 Redis 한 대까지 보장한다. 다중 인스턴스에서 예약 집합은 공유되므로 그대로 동작하지만, 캠페인 캐시(`RSV-003`)는 인스턴스마다 따로 생긴다 | 범위 | |
| `FLT-008` | Redis 가 상태를 잃은 것을 알면(요청 경로의 준비 표식 없음이나 `ZCARD < DB 발급 수`, 워커의 `WRK-005`) 그 캠페인의 접수를 닫고(503), 닫은 시점까지 broker 에 있던 메시지를 워커가 다 기록한 뒤, DB 쿠폰으로 예약 집합을 다시 만들고, 그 뒤에 연다. 재구성 전에 열면 빈 집합이 한도만큼 다시 받아들여 DB 가 품절로 거절하는 사용자가 생기므로 열기는 재구성이 끝났을 때만 받는다. 관리자가 `POST /api-admin/v1/coupon-campaigns/{id}/recover` 로 같은 절차를 시작할 수 있고, 부르면 즉시 닫힌다 | 정함 | 유실 뒤 바로 보낸 접수는 503. 복구 뒤 접수는 번호가 이어진다 |
