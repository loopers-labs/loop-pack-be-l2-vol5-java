# 요구사항 명세서 (W8): 받는지는 Redis 가 정하고, 쿠폰은 DB 가 뒤따라 기록한다

원문 과제(`ref/week8/assignment.md`, 학습 자료 `ref/week8/study.md`)와 그 뒤의 공지를 구현과 테스트의 기준으로 쓸 수 있게 정리한 문서다.
W7 명세(`docs/week7/requirements.md`)의 규칙 ID 와 출처 구분을 그대로 쓰고, 이번 주에 생긴 것만 적는다.

| | |
|---|---|

| 공지 | 원문의 Redis semaphore 는 처리량 제한을 이해하기 위한 기본 예제다. 그 이해가 끝났으면 쿠폰 발급은 어떤 방식이어도 된다. 발급이 가능한데 처리량 제한 때문에 실패를 돌려주지 않는 것, 공정한 선착순을 기대한다 |
| 이 문서가 하는 일 | 1부: 기본 예제로 처리량 제한을 실험해 확인한 것. 2부: 그 결과 위에 세운 발급 방식의 계약, 각 저장소가 지킬 것, 장애, 실험으로 증명할 것 |
| 이 문서가 하지 않는 일 | 테이블 구조, 키 이름, 설정값, C 와 묶음 크기의 근거. 설계 문서(`docs/week8/design.md`)에 적는다 |

## 1부. 처리량 제한 실험 (원문의 기본 예제)

원문의 방식(요청 앞 Redis Set 세마포어, 자리 없음 429, 장애 시 닫힘과 명시적 재개)을 구현하고 측정했다. 확인한 것은 아래다. 수치와 방법은 설계 문서 1부에 있다.

| ID | 확인한 것 | 출처 |
|---|---|---|
| `EXP-015` | 수용 제한 없이 동시 요청을 1 에서 256 까지 올리면 처리량은 동시 4 에서 최대의 90% 에 닿고 그 뒤 늘지 않는다. 막는 자원은 캠페인 행 잠금이다. 상한은 로컬에서 초당 600 ~ 890 건이다 | 실험 |
| `EXP-016` | C 를 두면 쿠폰이 몰려도 다른 API 의 p99 가 기준의 2 배 안에 있다. 429 를 받은 클라이언트가 바로 다시 보내면 거절 자체가 자원을 쓰고, `Retry-After` 와 지터를 지키면 몰림이 풀린다 | 실험 |
| `EXP-017` ~ `EXP-019` | 실제 Redis 에서 C=3 의 세 실행과 네 번째 거절, 자기 token 만 반환, DB 한도 경쟁에서 발급 5 와 품절 3 | 실험 |
| `EXP-020` | Redis 처리량은 클라이언트 모양이 정한다. 같은 Lua 가 연결 1 에서 17,513/s, 연결 50 에서 138,889/s, 연결 1 에 파이프라인 256 이면 199,196/s. Lua 하나의 서버 비용은 4.5µs. `io-threads 4` 는 6%. 복제는 초당 12 만 쓰기에서 지연 0, `WAIT 1` 은 연결 50 에서 25 만/s | 실험 |
| `EXP-021` | 멈춤은 기본 설정에서 보이지 않는다. 95 만 ZSET 의 `ZRANGE 0 -1` 143ms, `DEL` 155ms, `UNLINK` 0, 1 초 Lua 는 1 초, 5 초 넘는 Lua 는 그때부터 BUSY. p50 은 거의 안 움직이고 `latency-monitor-threshold` 기본 0. AOF `always` 는 fsync 가 루프 한 바퀴마다 묶여 연결 50 에서 39,200/s, 연결 1 에서 2,718/s | 실험 |
| 같은 행 잠금 | 같은 캠페인 행을 갱신하는 TX 는 동시 수를 올려도 초당 1,600 commit 에 머물고 group commit 이 묶이지 않는다. 다른 행이면 동시 16 에서 8,900 이다 | 실험 |
| Redis 명령 비용 | `SADD` 5.8µs, 자리 획득 Lua 7.8µs, 초당 96,000 번. 요청 경로의 Redis 사용은 그 30% 였다 | 실험 |
| timeout 은 모름이다 | 명령이 timeout 뒤에 실행될 수 있다. 같은 token 으로 다시 물어야 결과가 정해진다 | 실험 |
| 소켓 줄서기 | 캐시와 쿠폰이 같은 Lettuce 소켓을 쓰면 큰 응답 뒤에 작은 명령이 기다린다 | 실험 |

이 방식은 DB 상한을 넘는 요청을 429 로 돌려보낸다. 쿠폰이 남아 있어도 그렇다. 공지가 기대하는 두 가지(남았으면 실패를 주지 않는 것, 선착순)를 이 구조로는 만들 수 없어서 2부로 간다. 1부의 코드(Set 세마포어, 닫힘과 재개)는 제품 경로에 두지 않는다(Q-9).

## 2부. 발급 방식

### 세 가지 수

| 수 | 정하는 곳 | 끝까지 지키는 곳 |
|---|---|---|
| 발급 총량 | Redis 예약 카운터 | DB 조건부 update(`ISS-002`) |
| 사용자당 한 장 | Redis 예약 집합 | DB 유일 제약(`ISS-004`) |
| 동시에 DB 에 쓰는 실행 수(C) | 워커의 스레드 수 | 같음 |

Redis 가 빠르게 **정하고**, DB 가 느리게 **기록하며**, Redis 가 상태를 잃은 경우에만 DB 가 최종 판정을 한다. 요청 경로에는 DB 쓰기가 없다.

### 바뀌는 기존 계약

없다. 주문, 결제, 이벤트, 구매 활동(W2 ~ W7)은 그대로 두고 쿠폰에 연결하지 않는다(원문).

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `PUB-001` | 예약이 되면 캠페인 ID, 사용자 ID, `issueNumber`, 예약 시각을 담은 메시지를 보내고, broker 의 확인(`acks=all`)을 받은 뒤 202 를 돌려준다 | 정함(Q-11) | 202 를 받았으면 메시지가 broker 에 있다 |
| `PUB-002` | 발행 결과는 셋이다. 확인을 받으면 202. 확인이 제한 시간 안에 오지 않으면(Unconfirmed) producer 가 메시지를 아직 쥐고 있어 뒤늦게 닿을 수 있으므로 예약은 남기고 503 이다. 다시 요청하면 같은 번호로 200 `PENDING` 이고, 메시지가 끝내 안 갔으면 대사(`RCN-001`)가 보낸다. producer 가 포기한 실패(Rejected. 직렬화 실패, 없는 토픽, 크기 초과, `delivery.timeout.ms` 만료)는 메시지가 없는 것이 확실하므로 예약을 지우고 503 이다. 지우는 것도 실패하면 예약은 남고 503 이며, 대사가 메운다 | 정함(Q-11) | Unconfirmed 503 뒤 그 사용자의 예약은 남고 재요청은 같은 번호다. ### ISS: DB 가 끝까지 지키는 것

워커의 TX 가 따른다. 요청 경로에서는 실행되지 않는다.

| ID | 규칙 | 출처 | 관찰값 |
|---|---|---|---|
| `ISS-001` | 발급 가능 여부와 남은 한도 확인, 발급 수 증가, 쿠폰 insert 를 한 TX 에서 한다 | 원문 | |
| `ISS-002` | 어떤 실행 순서에서도 `issuedCount <= totalQuota` 이고 `issuedCount` 는 실제 쿠폰 수와 같다 | 원문 | 워커가 다 비운 뒤 두 값이 같고 한도 이하 |
| `ISS-003` | 마지막 한 장을 둘이 동시에 가져가지 못하게 한다. 수단은 조건부 변경이다 | 원문, 정함(Q-2) | |

| ~~Q-15~~ | ~~Redis 상태 유실을 어떻게 알고 어떻게 복구하는가~~ | 감지: 프로세스는 캠페인 캐시로 DB 의 발급 수를 알고(`RSV-003`) Lua 에 넘긴다. 예약 집합 크기가 그보다 작으면 집합이 줄어든 것이므로 유실이다. 복구: 닫기 → 워커 lag 0 → DB 쿠폰(사용자, `issueNumber`)으로 `ZADD` → 열기(`FLT-008`). 1부의 "닫힌 채 시작하고 명시적으로 연다" 를 그대로 쓰되, 열기 전 할 일이 "진행 중 실행 확인" 이 아니라 "DB 로 재구성" 이라 자동화할 수 있다. AOF `always` 는 처리량 때문이 아니라(`EXP-021` 에서 연결 50 에 39,200/s) fsync 시간이 요청 지연에 붙고, 빈 인스턴스 교체와 eviction 은 어차피 못 막아 복구 절차가 그대로 필요해서 두지 않는다. **뒤집을 조건**: 복구에 걸리는 시간(닫힌 동안의 503)이 허용치를 넘고 디스크 fsync p99 가 1ms 안일 때 | `FLT-005`, `FLT-008` |

## 범위 밖

쿠폰 사용과 할인 적용, 알림, 실제 인증, 다중 인스턴스 장애 전환(원문).
Gateway rate limit 과 사용자 대기실. 지금 구조는 한도 안의 요청을 모두 접수하므로 대기실이 필요 없고, 한도 밖은 409 다. 뒤집을 조건: 접수 요청 자체가 Redis 상한(초당 약 96,000 번)에 닿거나, 어뷰저를 입구에서 걸러야 할 때(정함).
DLT. 워커의 인프라 실패는 재시도하고, 업무 거절(중복, 품절)은 기록하고 넘어가므로 격리할 메시지가 없다. 뒤집을 조건: 메시지 자체가 읽히지 않는 경우가 생길 때(정함).
