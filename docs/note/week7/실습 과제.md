## 💻 Implementation Quest

> **주문 확정과 전달할 사실을 함께 남기고, 중단 뒤 같은 구매 활동으로 수렴시킵니다.**
>

6주차의 OrderConfirmed 계약·Kafka producer·구매 활동 consumer와 실제 MySQL·Kafka 테스트 기반을 유지합니다. 변경할 부분은 **확정 후 직접 발행을 Outbox 기록과 단일 relay로 교체**하는 경계입니다.

| 유지할 것 | 이번에 추가·교체할 것 |
| --- | --- |
| PG 결과 검증·예약 소비·CONFIRMED | 같은 확정 TX의 Outbox insert |
| stable eventId·orderId·confirmedAt·items | 변경되지 않는 key·payload 영속 저장 |
| Kafka topic·소비 group·구매 활동 | 단일 polling relay·전송 상태 |
| 소비 중복 방지·DB TX·ack | 발행 중단·재시작·기존 누락 복구 검증 |

별도 결제수단·새 주문 도메인·범용 saga·CDC 플랫폼·다중 relay는 필수 범위가 아닙니다.

### 🧭 1. 바꿀 트랜잭션을 먼저 표시하기

기존 PG 결과 적용 경계에서 **최초 SUCCESS의 내부 확정**을 찾습니다. 새 주문을 insert하는 코드가 아니라 기존 미완료 주문을 확정하는 코드입니다.

```
TX 밖: 기존 PG 거래를 조회·검증
DB TX: 기존 시도·주문·예약 확인
       → 최초 성공 반영 + 예약 소비 + confirmedAt
       → 같은 OrderConfirmed Outbox PENDING
       → 함께 commit
TX 밖: relay가 나중에 Kafka 발행
```

W6의 after-commit 직접 send를 제거하거나 이 경로에서 호출되지 않게 교체합니다. 직접 send와 relay를 의도치 않게 병행하지 않습니다. callback·reconcile은 계속 같은 결과 적용 경계를 사용합니다.

### 📮 2. Outbox 모델과 로컬 원자성

다음 의미를 담는 최소 모델을 만듭니다. 클래스·테이블·패키지 이름은 기존 설계와 ArchUnit 규칙에 맞게 정합니다.

| 데이터 | 규칙 |
| --- | --- |
| eventId | W6의 동일 확정 사건 ID, DB 유일 제약 |
| orderId·eventType·schemaVersion | 원본 주문과 계약 연결 |
| messageKey·payload | W6와 동일, 생성 뒤 변경 금지 |
| status | 최초 PENDING, broker 확인 후 PUBLISHED |
| createdAt·publishedAt | 기록 시각과 발행 확인 저장 시각 구분 |
| attemptCount·nextAttemptAt·lastError | 재시도·지연·실패 관찰 |

Outbox insert와 주문 확정·예약 소비·PG 성공 사실 저장은 **같은 데이터 소스의 같은 로컬 TX**에 둡니다. 별도 `REQUIRES_NEW`나 after-commit insert로 나누지 않습니다.

- PENDING·UNKNOWN·확정 FAILED는 OrderConfirmed Outbox를 만들지 않습니다.
- 같은 거래의 중복 callback·reconcile은 Outbox도 하나만 남깁니다.
- Outbox 실패가 발생하면 최초 성공 반영·예약 소비도 rollback합니다.
- 원래 미완료 주문·이전 시도·예약은 TX 직전 상태로 남습니다. 기존 주문 행을 0개로 만드는 것이 기대 결과가 아닙니다.
- 외부 PG SUCCESS는 로컬 rollback과 무관하게 남을 수 있습니다. 같은 거래 재조회로 성공 반영을 재시도하고 create는 추가하지 않습니다.
- Java·Kotlin · 같은 TX에 두는 범위의 의사코드

  5주차 결과 적용 handler에 Outbox 기록을 추가하는 위치입니다. 실제 오류·잠금·저장 방식은 기존 구현을 유지합니다.

    ```
    applyVerifiedSuccess(observation):
      DB TX:
        시도·주문·예약 잠금과 관찰 일치 검증
        이미 같은 SUCCESS이면 기존 결과 반환
        예약을 한 번 소비
        주문 CONFIRMED와 PG 성공 사실 저장
        최초 confirmedAt과 고정 eventId 결정
        저장 품목에서 immutable OrderConfirmed 생성
        동일 eventId Outbox PENDING insert
      commit
    ```

  Outbox 저장에 필요한 serialization이 실패한 경우도 같은 TX의 실패로 다룹니다. relay가 현재 상품 정보를 재조회해 payload를 다시 만들지 않습니다.


### 🚚 3. 단일 Relay 구현

한 번에 **한 relay 실행 흐름**만 활성화합니다. scheduler·수동 실행이 겹치지 않게 하고, 다른 인스턴스에서 같은 relay를 동시에 켜지 않는 로컬 실행 설정을 정합니다. 여러 프로세스의 소유권 문제를 메모리 flag로 해결했다고 주장하지 않습니다.

1. 재시도 시간이 된 PENDING을 작은 묶음으로 안정된 순서에서 찾습니다.
2. 대상 eventId와 저장 payload로 시도를 시작하고 필요한 시도 정보를 남깁니다.
3. 주문 확정 TX 밖에서 같은 topic·key·payload를 send합니다.
4. 실제 broker 성공 확인 뒤 별도 DB TX에서 해당 행을 PUBLISHED로 바꿉니다.
5. 실패·timeout이면 동일 행을 재시도 대상으로 유지하고 다음 시각·오류를 기록합니다.

DB 조회·상태 변경 TX와 외부 전송 대기를 분리합니다. 단일 relay의 직렬 실행을 기본으로 두고, 무제한 future 병렬 생성이나 tick 중첩으로 범위를 넓히지 않습니다. PENDING 조회에는 상태·다음 시각·정렬 조건에 맞는 인덱스를 검토합니다.

**전송 확인**은 send 호출이 예외 없이 반환했다는 뜻이 아니라 producer future의 성공입니다. `acks`는 broker 확인을 받을 수 있는 설정을 선택하고 W6의 단일 broker 한계를 유지합니다.

| 결과 | Outbox 처리 |
| --- | --- |
| broker 성공 확인 + 상태 TX 성공 | PUBLISHED·publishedAt |
| 전송 실패 | PENDING·다음 재시도·오류 |
| timeout·응답 유실 | 같은 사건 PENDING, 수신 0회라고 단정하지 않음 |
| broker 성공 뒤 상태 TX 실패 | PENDING이 남아 같은 사건 재발행 가능 |

로컬 대기를 중단해도 하위 send가 나중에 성공할 수 있습니다. 늦은 callback이 상태를 임의 변경하지 않게 하고, 상태 변경 책임을 relay의 한 경계에 둡니다. 오류 메시지에는 카드·비밀·불필요한 전체 payload를 남기지 않습니다.

### 🛠 4. 재시도·운영 재개

실패 뒤 즉시 무한 반복하지 않도록 전송 대기 시간·한 번의 처리 개수·재시도 간격을 정합니다. 테스트에서는 시간을 통제하거나 짧은 유한 대기로 검증하고 운영 값을 무조건 같은 수준으로 두지 않습니다.

- broker 장애가 회복되면 **기존 PENDING**을 다시 처리합니다.
- 반복되는 영구 오류는 원인과 eventId를 노출합니다. 별도 BLOCKED 상태로 분리했다면 미해결 상태로 목록에 남기고 복구 후 같은 행을 재개하는 경로를 둡니다.
- 전송 횟수·PENDING 수·가장 오래 기다린 시각을 SQL이나 간단한 구조화 로그로 확인합니다. 새 모니터링 서버는 필수가 아닙니다.
- PUBLISHED를 소비 완료로 표시하지 않습니다. consumer lag·오류·실제 구매 활동을 따로 확인합니다.
- 이번 과제에서는 미발행·격리 행을 자동 삭제하지 않습니다. 보존·정리 정책과 dedup 기록 보존의 관계를 짧게 정리합니다.

재개는 로컬에서 대상 eventId를 명시해 relay 한 회차를 실행하는 작은 운영 진입점이나 테스트 도구로 충분합니다. 이 진입점은 로컬에서만 사용하며 공개 관리자 API로 노출하지 않습니다.

### 🧩 5. 새 격리 실행에서 W6 누락 상태를 재현하고 복구하기

W6에서 남긴 **두 사례의 재현 코드·고정 입력·관찰 기록**을 가져옵니다. W6의 임시 DB가 종료돼도 시작할 수 있어야 합니다. 이번 검증은 역사적 원본 행의 복원이 아니라, **W6 누락 상태 재현 → 같은 실행 안에서 복구**입니다.

1. 테스트가 새 격리 MySQL·Kafka·로컬 PG fixture의 수명주기를 소유합니다. 준비 단계에서는 보존한 W6 테스트 구성 또는 W6 revision 실행물로 **실제 주문 확정·after-commit 직접 발행 경로**를 실행합니다.
2. 기존 주문 API와 로컬 PG로 두 합성 주문을 확정합니다. 첫 주문은 검증한 PG SUCCESS의 내부 확정 commit 뒤 send 직전에서 멈추고, 둘째는 실제 발행·소비를 끝냅니다. 두 주문 모두 CONFIRMED·예약 소비가 있고 Outbox는 아직 없으며, 첫 주문의 구매 활동만 0인지 새 DB 조회로 확인합니다.
3. 두 주문의 실제 `orderId, eventId, confirmedAt, items`와 PG 거래 식별자를 기록합니다. W6 기록과는 별도인 **이번 재현 실행의 사건**입니다. 이후 복구가 끝날 때까지 DB·broker·PG 상태를 초기화하거나 `@AfterEach` 정리를 사이에 실행하지 않습니다.
4. 직접 발행을 중단하고 같은 DB에 W7의 Outbox 저장 구조·복구 경로·단일 relay를 연결합니다. 준비 상태를 만들려고 SUCCESS를 직접 삽입하거나 W7 Outbox 행을 삭제하지 않으며, 제품의 운영용 우회 스위치도 만들지 않습니다.
5. 대상 두 주문의 저장된 확정 사실에서 **기존 eventId·confirmedAt·품목 그대로** Outbox가 없을 때만 한 행씩 추가합니다. 이미 있으면 내용 일치를 확인합니다. 원본 사실 부족·충돌에는 추측하지 않고 오류를 드러냅니다.
6. relay와 기존 consumer를 실행합니다. 미발행 사례에는 빠졌던 구매 활동이 생기고, 이미 소비된 사례에는 재발행이 와도 활동 행·수량이 늘지 않는지 확인합니다. 같은 대상의 두 번째 복구도 Outbox·구매 효과를 늘리지 않아야 합니다. 모든 확인 뒤에만 자신이 만든 자원을 정리합니다.
- 공통 · 준비와 복구의 PG 호출 수를 나눠 읽기

    ```
    준비: W6 실제 확정 경로로 합성 주문 A·B 생성
          A = commit 후 send 전 중단 / B = 발행·소비 완료
          이번 실행의 주문·거래·eventId·confirmedAt·items 기록
          PG create 누적 횟수 C와 외부 거래 수 T 기록
    복구: 같은 DB에서 A·B의 저장 사실 → 없는 Outbox 추가 → relay
          PG create = C, PG 조회·callback 추가 호출 = 0
          외부 거래 수 = T, 주문 재확정·예약 추가 소비 = 0
          A의 구매 활동 정상 생성 / B의 구매 활동 불변
    ```

  로컬 PG의 새 거래는 **재현 상태 준비**에서만 필요합니다. 두 주문을 각 한 번 시작한 최소 사례라면 C=2, T=2입니다. 복구 시작 직전 기준값을 기록하고 이후 증가가 0인지 확인합니다. 복구를 위해 새 결제를 만드는 것은 허용하지 않습니다.


실제 W6 원본 DB를 별도로 보존한 경우에는 준비 1–3을 다시 수행하지 않고, 보존한 사건 사실을 검증한 뒤 같은 복구 경로를 적용할 수 있습니다. 이 경우만 원본 사건의 복구라고 부릅니다. 두 방식 모두 이전 POINT 주문 전체를 자동 소급하지 않고, 대상 두 사례만 확인합니다.

### 🔬 6. 두 중단 구간을 검증하기

먼저 relay 없이 실제 DB의 로컬 원자성을 확인한 뒤 실제 broker·consumer를 연결합니다.

| 장면 | 확인할 결과 |
| --- | --- |
| Outbox insert 전후 실패, 확정 TX rollback | 기존 미완료 주문·예약 유지, 새 Outbox 0, 추가 PG create 0 |
| 같은 거래 결과 재적용 | 주문 CONFIRMED·예약 소비·Outbox 각 한 번 |
| commit 후 relay 실행 전 중단 | 주문·Outbox PENDING 존재, 구매 활동 아직 없음 |
| relay 재생성 후 실행 | 저장 행에서 이벤트를 찾아 정상 구매 활동 |
| broker 확인 뒤 PUBLISHED 저장 전 중단 | 같은 Outbox PENDING 유지, 재시작 후 같은 사건 재발행 |

중단 hook은 **그 단계가 완료된 뒤 다음 단계를 못 가게** 둡니다. 예를 들어 broker 확인 뒤 중단 실험에서는 실제 send 성공 metadata를 확보하고 PUBLISHED 저장을 수행하지 않습니다. 예외를 던진 테스트를 OS 강제 종료 시험으로 표현하지 않습니다.

재시작은 relay 객체·실행 흐름을 새로 만들되 같은 DB·Kafka·eventId를 유지합니다. 중단 뒤 테스트가 Outbox 상태를 직접 PENDING으로 덮어써 복구 조건을 만들어서는 안 됩니다.

### 🔗 7. 실제 주문부터 구매 활동까지 한 번에 확인

한 E2E 실행에서 기존 주문 API와 로컬 PG fixture, 실제 DB·Kafka, 실제 구매 활동 consumer를 연결합니다. 별도의 가짜 handler로 업무 완료를 대신하지 않습니다.

1. 기존 API로 합성 주문을 만들고 PG SUCCESS를 내부 확정 경로에 적용합니다.
2. 확정 주문·예약 소비·같은 eventId의 Outbox 한 행을 확인합니다.
3. relay의 첫 broker 확인 뒤 PUBLISHED 저장 전에 중단합니다.
4. 같은 Outbox에서 relay를 재시작해 다시 발행합니다.
5. consumer가 같은 사건을 처리한 뒤 DB의 상품별 구매 사실을 확인합니다.

| 관찰 | 품목이 상품 7×2, 상품 8×1인 한 주문의 기대 |
| --- | --- |
| 주문·PG 거래 | 같은 확정 주문·외부 거래 각각 1 |
| Outbox | 동일 eventId 1행, 최종 PUBLISHED |
| Kafka | 같은 eventId의 별도 record 2개 이상 관찰 가능 |
| consumer | 같은 사건의 수신 2회 이상 |
| 완료 이벤트 | 같은 orderId·eventId의 완료 기록 1 |
| 구매 활동 | 상품별 2행, 수량 2·1 유지 |
| 재고·포인트 | 예약 추가 소비·반환 없음, PG 주문 포인트 추가 차감 없음 |

중단 실험에서는 **첫 발행과 재발행의 실제 broker 기록**을 관찰해 두 번을 확인합니다. 애플리케이션의 send 호출 횟수만 세지 않습니다. W6의 동일 offset 재전달과 달리, 여기서는 같은 eventId가 별도 offset으로 기록될 수 있습니다.

- Java·Kotlin · E2E 테스트 경계

  W6의 실제 DB·Kafka fixture와 consumer를 재사용합니다. 한 테스트 실행이 자원 준비·consumer 시작·API 호출·relay 중단·재시작·결과 조회를 소유하면 상태를 맞추기 쉽습니다.

    - 기존 MySQL 8.0 fixture와 실제 broker를 producer·consumer·admin 모두에 연결합니다.
    - 테스트 의존성 또는 별도 application context로 실제 consumer를 로드할 수 있습니다. 제품 runtime에 commerce-api→commerce-streamer 의존성을 새로 만들지 않습니다.
    - 실제로 사용하는 listener factory·parser·handler를 명시적으로 연결하고 두 애플리케이션의 전체 component scan 충돌을 피합니다.
    - 테스트 자동 rollback 안에 모든 절차를 넣지 않습니다. relay·consumer가 다른 TX에서 볼 수 있도록 실제 commit을 확인합니다.
    - 고유 topic·group·합성 주문을 사용하고, 실행 중인 consumer와 경쟁하며 DB를 초기화하지 않습니다.
    - 마지막에는 자신이 만든 consumer·broker·HTTP fixture 등만 정리합니다. 다른 작업이 쓰는 공유 DB·broker를 일괄 종료하지 않습니다.

### 🧪 8. 회귀와 제출

기존 W5의 중복 callback·reconcile·재고 예약·소유권·이전 POINT 사실과 W6의 소비 멱등성·listener 실패 정책을 보호합니다. 영향 없는 모든 테스트 계층에서 같은 시나리오를 반복할 필요는 없습니다.
