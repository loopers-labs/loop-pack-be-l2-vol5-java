# 사용자 여정의 증거로 사고를 복구하기
> **프로세스가 응답하는 것과, 사용자의 일이 끝난 것은 다릅니다.**

<aside>
🎯

**Summary**

</aside>

상품을 고르고 결제한 사용자는 주문 결과를 기다립니다. 주문이 확정된 뒤에는 구매 활동과 주간 랭킹으로도 이어집니다. 어느 경계에서 멈췄는지 구분하지 못하면 재시작이나 재시도가 오히려 중복 결제를 만들 수 있습니다.

이번에는 실제 누적 서비스에 작은 결제 사고를 주입하고, **같은 주문의 외부 거래와 내부 상태를 연결해 복구**합니다. 관측 신호를 모으는 이유, 경쟁 가설을 가르는 방법, 조치의 중단 조건과 복구 범위를 배웁니다.

- **관측**: 로그·지표·추적이 답하는 질문을 구분합니다.
- **업무 기준**: health와 주문 종결·미확인 상태를 따로 봅니다.
- **진단**: 원인 추측과 그 추측을 검증하는 증거를 분리합니다.
- **복구**: 새 결제 없이 기존 거래를 조회해 같은 주문을 마무리합니다.
- **종료**: 확인한 기능·실패·복구와 아직 확인하지 않은 위험을 구분합니다.

## 🛍 어디까지 끝났다고 말할 수 있는가

```
상품 조회 → 주문·재고 확보 → PG 거래 → 내부 주문 확정
                                      → Outbox → Kafka → 구매 활동
                                                        → 주간 랭킹 공개

쿠폰 발급 → DB 쿠폰 저장 → 본인 쿠폰 목록
```

쿠폰 발급은 별도의 사용자 기능입니다. 이번 과정에서는 쿠폰을 PG 할인에 적용하지 않았으므로 Redis 쿠폰 수용 실패를 곧바로 결제 미확인의 원인이라고 설명하지 않습니다.

각 경계의 성공은 다음 경계까지 보장하지 않습니다. PG 성공은 내부 주문 확정을, Outbox 발행 완료는 소비 완료를, 구매 활동 저장은 랭킹 공개를 자동으로 뜻하지 않습니다.

| 관찰 | 알 수 있는 것 | 아직 모르는 것 |
| --- | --- | --- |
| health UP | 설정한 상태 검사 통과 | 특정 주문 종결 |
| PG SUCCESS | 외부 거래의 최종 성공 | 내부 TX 반영 |
| 주문 CONFIRMED | 내부 결제·예약 적용 | 소비 활동 도착 |
| Outbox PUBLISHED | broker 발행 확인 | consumer DB commit |
| Batch COMPLETED | 실행 metadata의 완료 | 요청 기간·공개본의 업무 정확성 |

## 🔭 관측 가능성과 모니터링

> **관측 가능성**은 외부로 드러난 신호로 시스템 내부 상태를 추론하는 능력입니다. **모니터링**은 정한 신호를 수집하고 정상 기준에서 벗어났는지 감시하는 활동입니다.
>

대시보드가 많아도 “이 주문은 결제가 됐는가”에 답하지 못하면 필요한 관측이 빠져 있습니다. 먼저 사용자가 겪은 증상과 판단할 질문을 정합니다.

### 🧾 로그·지표·추적의 다른 역할

| 신호 | 주로 답하는 질문 | 한계 |
| --- | --- | --- |
| 로그 | 이 주문에서 무슨 일이 일어났나 | 한 사건이 전체 빈도를 말하지 않음 |
| 지표 | 미확인·지연·오류가 얼마나 늘었나 | 집계만으로 특정 주문을 찾기 어려움 |
| 추적 | 요청이 어떤 경계를 지나 어디서 기다렸나 | 전파·수집하지 않은 구간은 보이지 않음 |

로그에는 주문·결제 시도·외부 거래를 연결할 식별자를 남깁니다. 비동기 이벤트에는 eventId, 배치에는 snapshotId를 사용합니다. 이 값들은 업무 사건을 잇는 열쇠이지 그 자체로 결제 성공의 증거는 아닙니다.

traceId는 한 추적의 문맥입니다. 나중에 실행한 reconcile이나 배치는 다른 trace가 될 수 있으므로 traceId만으로 동일 업무를 판단하지 않습니다. Kafka 같은 경계를 지나 추적을 연결하려면 실제 문맥 전달·계측이 필요합니다. 로그에 traceId라는 글자만 붙인 것을 분산 추적 구현으로 보지 않습니다.

### 🔒 많이 남기는 것의 비용

orderId·userId처럼 계속 늘어나는 값을 metric label로 넣으면 시계열 수가 크게 늘어납니다. 지표는 유한한 상태·결과 분류를 쓰고 개별 식별자는 접근 제한된 로그·상태 기록에서 찾습니다.

카드 정보·인증 헤더·비밀키·개인정보는 진단 편의를 위해 출력하지 않습니다. 원문 보존은 비밀값까지 무차별 저장하라는 뜻이 아닙니다. 필요한 합성 식별자와 허용한 필드만 처음부터 기록합니다.

## 📏 Health, SLI, SLO

**Liveness**는 프로세스가 살아 있는지, **readiness**는 트래픽을 받을 준비가 됐는지 판단하는 용도로 사용할 수 있습니다. 무엇을 포함하는지는 실제 health 설정에 달려 있습니다.

> **SLI**는 서비스 수준을 나타내는 측정값이고, **SLO**는 정해진 기간·대상에서 지키려는 목표입니다.
>

“주문 10건”만 쓰면 분모가 모호합니다. 입력 오류로 거절된 요청까지 포함하는지, 수락한 서로 다른 주문인지, 언제까지 완료를 기다리는지 정해야 합니다.

이번 실험에서는 **유효한 PG 결제 요청을 수락한 고정 주문 집합**을 분모로 삼습니다. 최종 성공·최종 실패·처리 중·결과 미확인을 구분하고, 정한 관찰 시점의 수를 셉니다. 최종 실패도 종결 상태일 수 있지만 성공률의 성공으로 세지는 않습니다.

```
정상 주문 집합: 성공 10 / UNKNOWN 0 / PG 성공 거래 10
장애 주문 집합: 성공  7 / UNKNOWN 3 / PG 성공 거래 10
같은 집합 복구: 성공 10 / UNKNOWN 0 / PG 성공 거래 10
복구 중 PG create 추가: 0
```

이 통제 실험은 10건의 결과입니다. 이 수치만으로 월간 99.9% SLO나 운영 처리량을 달성했다고 주장하지 않습니다. 실제 SLO에는 측정 기간·지연 한도·제외 규칙과 대표적인 트래픽 근거가 필요합니다.

## 🧪 같은 증상, 다른 원인

고객에게는 모두 “결제 확인 중”으로 보여도 원인은 다를 수 있습니다.

| 가설 | 예상 관찰 | 구분하는 근거 |
| --- | --- | --- |
| PG가 아직 처리 중 | 권위 조회도 PENDING | 동일 거래의 실제 최종 상태 |
| PG 성공 응답을 잃음 | PG SUCCESS, 내부 UNKNOWN, 생성 응답 timeout | adapter 결과·동일 거래 조회·내부 상태 |
| 성공 조회 뒤 내부 TX 실패 | PG SUCCESS, 적용 시도와 DB rollback | 조회 성공 로그·TX 실패·예약/Outbox 상태 |

PG SUCCESS와 내부 UNKNOWN만으로 두 번째와 세 번째 가설을 완전히 구분할 수는 없습니다. 둘 다 이 조합을 만들기 때문입니다. 외부 응답 경계의 결과와 내부 적용 시도까지 확인해야 합니다.

장애 주입 코드를 알고 있어도 관측 증거가 같은 결론을 지지하는지 확인합니다. 숨은 원인을 맞히는 게임이 아니라, 주입자의 기억 없이도 진단 가능한 시스템을 만드는 실험입니다.

## 🧯 완화와 복구

**완화(mitigation)**는 새 피해나 영향을 줄이는 조치이고, **복구(recovery)**는 이미 영향을 받은 업무를 올바른 상태로 돌리는 일입니다.

| 조치 | 용도 | 주의할 점 |
| --- | --- | --- |
| 새 테스트 주문 중단 | 영향 범위를 고정 | 기존 미확인 주문은 남음 |
| 같은 거래 조회·조정 | 기존 주문 종결 | 권위·금액·주문 일치 필요 |
| 프로세스 재시작 | 일시적인 실행 상태 회복 가능 | 외부 거래는 없어지지 않음 |
| 코드 rollback | 코드 회귀 완화 | DB·PG 사실이 과거로 돌아가지 않음 |

이번에는 실험의 새 입력을 멈추고 증거를 보존한 뒤 W5의 기존 reconcile 경로를 사용합니다. DB 상태를 직접 바꿔 성공으로 표시하지 않습니다.

### 💳 결제 재시도와 조회 재시도

응답 timeout은 PG 거래가 없다는 뜻이 아닙니다. UNKNOWN에 create를 다시 보내면 중복 결제가 생길 수 있습니다.

같은 계정 범위·주문·금액·거래를 조회해 확인하고 기존 결과 적용 경계로 수렴시킵니다. 조회 0건·복수 거래·금액 불일치·계속 PENDING이면 중단 조건에 따라 미확인 상태를 보존합니다. 성공 수를 맞추려고 새 거래를 만들거나 강제로 CONFIRMED를 저장하지 않습니다.

## 🧱 상태와 효과를 함께 대사하기

**대사(reconciliation)**는 서로 다른 경계에 저장된 같은 업무 사실을 맞춰 차이를 찾고, 허용한 규칙으로 해소하는 일입니다.

복구 후에는 주문 상태만 보지 않습니다. 동일한 주문 집합의 PG 거래·예약·Outbox·구매 활동을 맞춥니다.

- PG create 횟수와 거래 수가 복구 중 늘지 않았는가?
- 이미 확보한 재고를 성공 적용 때 다시 차감하지 않았는가?
- UNKNOWN 동안 예약을 잘못 반환하지 않았는가?
- 각 확정 주문의 Outbox 사실이 있고 각 주문·상품 활동이 한 번인가?
- PG 결제 복구가 포인트 잔액이나 쿠폰 발급을 바꾸지 않았는가?

메시지 발행 횟수는 재시도로 늘 수 있습니다. 이것과 PG 거래 중복·업무 활동 중복을 같은 수로 취급하지 않습니다.

## 📊 복구된 사실과 주간 랭킹

구매 활동이 늦게 저장됐다고 이미 공개한 snapshot이 자동으로 바뀌어서는 안 됩니다. W9의 frozen input과 새 revision 규칙으로 결과를 설명합니다.

또한 주간 소속은 **내부에 처음 저장한 confirmedAt**입니다. 사고 뒤 주문이 처음 확정되면서 주 경계를 넘었다면 그 저장된 시각이 속한 주로 집계합니다. 임의로 PG 요청 시각을 대신 넣지 않습니다. 이미 확정된 주문의 이벤트만 늦었다면 원래 confirmedAt의 주로 들어갑니다.

선택한 사고를 같은 주 안에서 복구하고 새 snapshot으로 집계하면, 실제 복구 주문의 구매 수량이 API에 반영됐는지 확인할 수 있습니다. 이 연결은 전체 배치 장애나 모든 기간의 데이터 정확성을 증명하지는 않습니다.

## 🗂 재현 가능한 사고 기록

정상·장애·복구는 동일한 시나리오의 상태를 이어야 합니다. 단계 사이에 DB나 테스트 PG 거래를 초기화하면 같은 주문 복구가 아닙니다.

작은 실험은 한 테스트 lifecycle에서 상태를 유지하는 방법이 단순합니다. 여러 프로세스를 사용한다면 동일한 DB·거래 저장소·식별자를 유지한다는 근거가 필요합니다. 세 개의 독립 실행 로그에 같은 이름을 붙이는 것으로 대신할 수 없습니다.

기록에는 시각·단계·대상 주문 집합·상태·관찰한 외부 거래·조치·결과를 남깁니다. 새 실행은 새 증거 위치를 사용하고 실패한 실행도 보존합니다. 파일 checksum은 기록이 바뀌지 않았는지 확인할 뿐 내용이 참인지 자동으로 증명하지 않습니다.

## 📓 Runbook과 사후 분석

**Runbook**은 특정 증상에서 안전하게 판단하고 조치하기 위한 절차입니다. 명령 모음보다 전제·중단 조건·결과 확인이 중요합니다.

| 구간 | 담을 내용 |
| --- | --- |
| 시작 | 사용자 증상·대상 기능·영향 주문 |
| 진단 | 먼저 보존할 기록·경쟁 가설·구분 질의 |
| 조치 | 권한·범위·한도·중단 조건 |
| 복구 | 같은 ID의 상태·효과·후속 결과 |
| 재진입 | 실패 상태 보존·안전한 다음 조회 |
| 후속 | 원인·빠진 방어·검증 가능한 개선 |

사후 분석은 개인을 비난하기보다 실패 조건과 부족한 방어를 찾습니다. “모니터링 강화”보다 “미확인 주문의 나이와 개수가 정한 한도를 넘으면 같은 거래 조회 절차로 연결한다”처럼 확인할 수 있는 개선을 씁니다. 한도는 실제 업무 기대와 측정 근거로 정합니다.

### 💭 선택을 설명하기

- health가 UP인데도 사용자는 왜 실패를 겪었나요?
- 두 가설이 같은 관찰을 예측할 때 어떤 신호를 더 찾았나요?
- 어떤 식별자는 metric이 아니라 로그에 남겨야 하나요?
- 재시작과 새 결제를 먼저 하지 않은 이유는 무엇인가요?
- 복구한 주문과 아직 검증하지 않은 기능을 어떻게 구분했나요?
