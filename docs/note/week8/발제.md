## 🎟 쿠폰 발급 행사에서 서로 다른 두 한도

이번에 소개하는 **쿠폰 발급**은 캠페인의 쿠폰을 한 사용자에게 부여하고 보유 목록에 남기는 기능입니다. 쿠폰을 주문 할인에 적용하거나 환불하는 기능과는 구분합니다.

| 한도 | 예시 | 작업이 끝나면 |
| --- | --- | --- |
| 발급 총량 | 캠페인에서 총 100장 | 발급된 쿠폰 수가 줄어들지 않음 |
| 동시 처리 수용량 | 현재 발급 실행 최대 3개 | 끝난 실행의 자리는 반환 가능 |
| 시간당 요청 제한 | 1초 동안 최대 20회 | 다음 시간 구간의 정책에 따름 |

쿠폰 한 장을 정상 발급한 뒤 처리 슬롯을 돌려줬다고 쿠폰 재고가 한 장 늘어나면 안 됩니다. 반대로 이미 발급된 누적 100장을 현재 동시 작업 수로 세면 행사가 끝난 뒤에도 처리 자리가 영원히 차 있습니다.

사용자가 “발급” 버튼을 두 번 누르는 경우에도 **두 HTTP 실행**과 **한 번의 쿠폰 부여**는 다른 개수입니다. 어떤 개수를 제한하고 어떤 효과의 중복을 막는지 이름부터 구분해야 합니다.

## 🌊 요청이 도착하는 속도와 끝나는 속도

초당 100건이 도착하고 초당 20건을 끝낼 수 있다면, 전부 보관할 때 미완료 작업은 초당 약 80건씩 늘어납니다. queue가 생겼을 뿐 처리 능력이 늘어난 것은 아닙니다.

```
도착 100건/초 → [계속 늘어나는 대기] → 완료 20건/초
```

| 관찰값 | 뜻 | 흔한 혼동 |
| --- | --- | --- |
| 요청률 | 단위 시간에 들어온 요청 | 실제 완료 처리량과 같다고 봄 |
| 처리량 | 단위 시간에 끝낸 작업 | 동시 연결 수와 같다고 봄 |
| 동시성 | 지금 함께 실행 중인 작업 수 | 누적 성공 수와 같다고 봄 |
| 지연 | 한 요청이 결과까지 기다린 시간 | CPU 실행 시간만 포함한다고 봄 |

평균적으로 초당 20건을 처리하고 한 건이 0.2초 머문다면 안정된 흐름에서 평균 진행 중 작업 수는 약 4개입니다. 하지만 이 평균식이 안전한 최대 수용량을 자동으로 정해 주지는 않습니다. 지연 분포·DB 연결·잠금 경합·다른 API의 자원 사용까지 확인해야 합니다.

PG 응답이 평소보다 열 배 느려졌는데 초당 요청률이 그대로라면 진행 중 호출이 쌓일 수 있습니다. **Rate limit과 동시 작업 제한은 서로 다른 보호 장치**입니다.

**Bulkhead(격벽)**는 한 기능의 자원 고갈이 다른 기능으로 번지지 않도록 실행 자원을 분리하는 방식입니다. 예를 들어 쿠폰 발급이 몰려도 주문·상품 조회가 사용할 실행 자원을 남겨 두는 것입니다. 쿠폰 동시 수용을 3개로 제한해도 모든 API가 같은 DB 연결 풀을 공유한다면 자원 격리가 보장되지는 않습니다. 이번 과제는 수용 제한을 구현하며, 별도 풀이나 라이브러리 도입까지 요구하지 않습니다.

## 🚦 받을 것인가, 기다리게 할 것인가

> **Admission control**은 새 작업을 지금 시스템 안으로 받아 책임질지 결정하는 경계입니다. **Backpressure**는 하류의 처리 여력에 맞춰 상류의 유입·실행을 줄이도록 피드백하는 개념입니다.
>

| 선택 | 사용자에게 약속하는 것 | 비용 |
| --- | --- | --- |
| 즉시 거절 | 이번 실행은 받지 않음 | 재시도 안내·공정성 고민 |
| 빈자리에서 즉시 실행 | 수용된 요청의 처리를 시작 | 동시 실행·종결·자리 반환 |
| 제한된 queue | 정해진 양만 보관해 나중 실행 | 대기 상태·유실·취소·worker 복구 |
| 사용자 대기실 | 입장 순서·안내 제공 | 토큰·순번·polling/SSE·별도 UX |

거절이 항상 나쁜 것도, 대기열이 항상 좋은 것도 아닙니다. 사용자가 수분을 기다려도 괜찮은 행사와 빠른 실패를 원하는 API의 선택은 다를 수 있습니다. 무제한 queue는 처리할 수 없는 약속을 계속 늘릴 뿐입니다.

이번 과제는 **빈자리에서 동기 발급하고 초과 요청을 거절**하는 작은 경계를 사용합니다. 발급 결과와 보유 목록까지 완성하고, 사용자 대기 순번·비동기 worker는 필수로 추가하지 않습니다.

### 🛑 거절 응답도 부하를 만든다

모든 사용자가 같은 시각에 즉시 재시도하면 다시 폭주할 수 있습니다. 재시도 간격 안내와 client의 backoff·jitter가 도움이 됩니다. 다만 재시도 예정 시각은 **쿠폰 확보나 성공 예약**이 아닙니다.

정확한 선착순을 약속하려면 요청 도착 시각·동점·다중 서버의 관찰 순서를 정의해야 합니다. Redis 원자 수용만으로 전 세계 도착 순서의 공정성이 자동 보장되지는 않습니다.

## 🪑 Semaphore와 현재 점유

> **Semaphore**는 동시에 사용할 수 있는 자리를 정해 두고 실행 전에 획득하고 끝난 뒤 반환하는 동기화 방식입니다.
>

수용량 C가 3이라면 진행 중 발급 실행이 3개일 때 다음 실행은 시작하지 않습니다. 여기에서 슬롯을 식별하는 내부 **permit token**은 한 실행이 어떤 자리를 맡았는지 구분합니다.

| 식별자 | 역할 |
| --- | --- |
| 사용자·캠페인 | 누구에게 어떤 쿠폰을 부여하는가 |
| 보유 쿠폰 ID | 실제 발급된 결과 한 건 |
| 실행 token | 현재 한 발급 실행이 점유한 자리 |

실행 token은 사용자 인증이나 쿠폰 자체가 아닙니다. 고객에게 token을 만들어 보내게 하거나, 같은 token을 다른 실행이 재사용하게 하지 않습니다.

같은 JVM의 semaphore만으로는 다른 프로세스의 실행 수를 알 수 없습니다. 공유 Redis의 Set에 활성 token을 보관하면 여러 client가 같은 점유를 확인할 수 있습니다. 다만 Redis 장애·상태 유실까지 포함한 보장은 별도의 조건이 필요합니다.

## ⚛️ 마지막 자리를 원자적으로 결정하기

현재 token 수가 2이고 최대가 3입니다.

```
A: SCARD → 2 → 빈자리 있음
B: SCARD → 2 → 빈자리 있음
A: SADD token-A
B: SADD token-B
결과: 4개
```

각 Redis 명령이 원자적이어도 **확인과 추가를 나눈 전체 판단**은 원자적이지 않습니다.

> **Redis Lua script**는 Redis 안에서 여러 명령과 판단을 하나의 실행으로 묶습니다. 스크립트 실행 사이에 다른 client의 명령이 끼어들지 않도록 처리됩니다.
>
- 공통 · 수용 결정의 최소 의사코드

    ```
    검증: 내부 실행 token과 설정된 capacity
    현재 token 수가 capacity 이상이면 거절
    그렇지 않으면 이 token 추가 후 수용
    ```

  반환은 이 실행의 token만 제거합니다. Set 전체 삭제나 무조건 카운터 감소로 다른 실행의 자리를 지우지 않습니다.


Lua의 원자 실행은 SQL 트랜잭션의 모든 성질을 뜻하지 않습니다. 실행 중 오류가 나도 앞선 쓰기가 자동 rollback된다고 가정하지 않습니다. 입력·키 타입 검증을 먼저 하고 변경 범위를 작게 유지합니다.

긴 루프나 외부 업무를 스크립트에 밀어 넣으면 Redis의 다른 요청도 기다립니다. 스크립트는 수용 판단·token 기록에 집중하고 실제 쿠폰 발급은 DB 트랜잭션에서 처리합니다.

## 🗄 Redis 수용과 쿠폰 DB 원본의 역할

| Redis가 책임지는 것 | DB가 책임지는 것 |
| --- | --- |
| 현재 실행 자리의 원자적 수용 | 캠페인 발급 한도 |
| 자기 token 반환 | 사용자별 중복 발급 방지 |
| 점유를 모를 때 새 수용 거절 | 보유 쿠폰과 실제 발급 수의 원자성 |

```
쿠폰 요청
  → 기존 보유 결과 확인
  → Redis 처리 자리 획득
  → DB TX: 캠페인 조건·잔여 한도·중복 확인 + 실제 발급
  → TX가 끝난 뒤 자기 처리 자리 반환
  → 저장된 쿠폰 결과 응답
```

Redis에서 자리를 얻었다고 발급이 성공한 것은 아닙니다. DB에서 마지막 쿠폰이 먼저 발급되거나 사용자 중복이 확인될 수 있습니다. 이때 DB의 업무 결과에 따라 응답하고 실행이 끝났다면 자리를 돌려줍니다.

발급 수 증가와 보유 쿠폰 insert가 다른 TX라면 중간 실패로 수량만 줄거나 쿠폰만 늘어날 수 있습니다. 3주차의 잠금·조건부 변경·유일 제약을 적용할 위치입니다.

이미 발급된 쿠폰은 Redis와 무관한 DB 사실입니다. Redis 장애 때도 DB가 정상이라면 본인 보유 목록과 같은 완료 결과를 조회할 수 있습니다. 장애를 핑계로 다른 사용자 결과를 노출하거나 없는 쿠폰을 성공으로 응답하지 않습니다.

## 🔓 언제 자리를 반환해도 되는가

정상 성공·확정 거절·rollback 후 실행이 끝났다면 자기 token을 제거할 수 있습니다. 그러나 HTTP 연결이 끊겼거나 timeout을 관찰했다고 하위 DB 작업이 반드시 끝난 것은 아닙니다.

| 장면 | 주의할 점 |
| --- | --- |
| DB commit 완료 | 쿠폰은 남고 처리 자리만 반환 |
| DB rollback 완료 | 쿠폰 추가 없음, 처리 자리 반환 |
| client 연결 종료 | 서버 작업이 계속될 수 있음 |
| DB 결과·종료 불명 | 끝났다고 추측해 자리 재사용하지 않음 |
| 반환 Redis 호출 실패 | 쿠폰을 되돌리지 않고 남은 점유·오류를 확인 |

### ⏲ TTL로 자리를 자동 반환하면?

3초가 지나 token을 지웠는데 원래 작업이 5초 뒤에도 DB를 변경하고 있다면 새 요청과 겹칩니다. token TTL은 실제 작업을 취소하지 않습니다.

시간이 지나면 소유권을 넘기는 lease와 오래된 실행의 쓰기를 거절하는 fencing은 서로 다른 문제입니다. 모든 저장 경계에서 이를 강제하는 작업자 시스템은 이번 범위를 넘어섭니다.

이번 동기 발급에서는 자동 TTL 회수로 진행 중 실행을 덮지 않습니다. 중단 때문에 남은 자리는 보수적으로 유지하고, **새 수용을 닫은 상태에서 기존 실행·DB 작업이 끝났음을 확인한 뒤** 복구합니다. 편리한 자동 회복을 줄이는 대신 보장을 설명하기 쉬운 경계를 선택합니다.

## 🔌 Redis를 믿고 읽을 수 없는 순간

> **Fail-closed**는 필요한 권위 상태를 확인할 수 없을 때 새 작업을 허용하지 않는 선택입니다.
>

4주차 상품 표시 캐시는 원본 DB로 우회할 수 있었습니다. 여기에서 Redis를 못 읽었다고 “현재 점유 0”으로 취급하면 수용량 제한을 우회합니다. 같은 Redis 장애라도 기능의 책임에 따라 fallback이 달라집니다.

현재 점유는 primary의 원자 연산으로 다룹니다. 복제가 지연될 수 있는 replica의 count를 기준으로 새 자리를 승인하지 않습니다. 시작 저장소의 기본 Redis 연결은 `REPLICA_PREFERRED`이므로 전용 master 연결의 실제 사용을 확인합니다.

Redis의 연결 복구나 PONG은 기존 token 상태가 정확하다는 증거가 아닙니다. 재시작·복제 전환·데이터 유실 시 이전 점유가 빠질 수 있습니다. 이런 상태를 자동으로 빈자리로 해석하지 않고 운영 재개 조건을 확인합니다.

## 🔬 무엇을 함께 관찰해야 하는가

| 관찰 | 확인할 것 |
| --- | --- |
| 수용·거절 수 | 지금 처리할 수 없는 요청을 거절했는가 |
| 활성 token 수 | 진행 중 실행과 현재 점유가 맞는가 |
| 실행·DB 종료 | 자리를 너무 일찍 반환하지 않았는가 |
| 실제 쿠폰 수·발급 수 | 한도·중복·rollback이 맞는가 |
| 본인 보유 목록 | 사용자가 실제 결과를 확인할 수 있는가 |
| Redis 장애·복구 | 우회 수용 없이 알려진 상태에서 재개했는가 |

용량 3을 검증할 때 작업이 즉시 끝나면 네 요청 모두 차례로 통과할 수 있습니다. 이것은 최대 동시성 초과가 아닙니다. **세 실행을 슬롯 획득 뒤 잠시 유지한 상태**에서 네 번째의 판단을 확인해야 합니다.

DB 발급 총량 테스트와 Redis 동시 수용 테스트도 분리합니다. Redis 거절 때문에 DB 경쟁에 참여하지 못한 요청을 “쿠폰 품절 처리”라고 세면 한도 검증이 되지 않습니다.

### 💭 선택을 설명하기

- 쿠폰이 남아 있는데 요청을 거절해야 하는 이유는 무엇일까요?
- queue가 없으면 어떤 복구 책임이 줄고 어떤 사용자 경험을 포기할까요?
- 중복 업무 결과와 중복 HTTP 실행을 어떻게 구분했나요?
- Redis 장애 때 보유 쿠폰 조회는 되지만 신규 발급은 닫는 이유는 무엇일까요?
- 자동 TTL 회수 대신 보수적 재개를 선택한 비용은 무엇일까요?
