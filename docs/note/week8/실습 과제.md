## 💻 Implementation Quest

> **실제 쿠폰을 발급하되, 지금 처리할 자리와 발급 가능한 총량을 따로 지킵니다.**
> 

7주차까지의 상품·주문·PG·이벤트·구매 활동을 유지하고 **쿠폰 발급과 본인 보유 목록**을 추가합니다. 빈 처리 자리에서 동기 발급하고 초과 요청은 거절합니다. 사용자 대기실·비동기 worker·쿠폰 사용/할인 적용·알림은 이번 구현 범위가 아닙니다.

### 🎟 1. 쿠폰 규칙과 API

이번에 처음 도입하는 캠페인은 “정해진 쿠폰을 정해진 수량만 발급하는 행사”입니다. 작은 로컬 캠페인 fixture 또는 로컬 관리자 준비 코드로 시작합니다. 별도 캠페인 관리 화면이나 전체 CRUD는 필요하지 않습니다.

| 규칙 | 이번 계약 |
| --- | --- |
| 캠페인 | ID·이름·발급 가능 여부·총 발급 한도·현재 발급 수 |
| 쿠폰 설명 | 예: 5,000원 할인권이라는 고정 혜택 정보. 실제 할인 적용은 구현하지 않음 |
| 사용자별 제한 | 같은 캠페인에서 사용자당 한 장 |
| 발급 완료 | DB에 사용자·캠페인·쿠폰 ID·발급 시각·혜택 정보가 저장됨 |
| 종료된 행사·품절 | 신규 발급 거절. 이미 발급된 쿠폰은 보존 |
| 동시 처리 수용량 | 쿠폰 신규 발급 경로 전체의 활성 실행 최대 C개 |

| API | 동작 |
| --- | --- |
| `POST /api/v1/coupon-campaigns/{campaignId}/issues` | 현재 사용자의 쿠폰 발급 |
| `GET /api/v1/coupons` | 현재 사용자의 보유 쿠폰 목록 |

클라이언트가 별도 userId를 보내 다른 사용자에게 발급하거나 조회하지 못하게 합니다. 기존 로컬 사용자 식별과 관리자 테스트 설정을 유지하며 실제 인증·공개 배포로 확대하지 않습니다.

최초 발급은 HTTP 201, 같은 사용자·캠페인의 기존 발급 결과는 HTTP 200과 같은 couponId를 반환합니다. 보유 목록은 발급 시각 내림차순·couponId 내림차순 등 안정된 순서를 정하고 본인 결과만 반환합니다.

**품절/비활성**은 업무 거절, **처리 자리 없음**은 HTTP 429, **수용 상태 확인 불가**는 HTTP 503으로 구분합니다. 품절/비활성 오류 코드와 HTTP 상태는 기존 API 오류 규칙에 맞춰 명시합니다. 429·503을 쿠폰 발급 성공이나 나중 발급 보장으로 표현하지 않습니다.

### 🧱 2. DB에서 발급 총량과 중복 보호

캠페인의 발급 가능 여부·잔여 한도 확인, 발급 수 증가, 보유 쿠폰 insert를 같은 TX에서 처리합니다.

- `issuedCount <= totalQuota`를 모든 실행에서 지킵니다.
- `(campaignId, userId)` 유일 제약으로 같은 사용자의 두 장 발급을 막습니다.
- 잠금·조건부 변경 등 3주차의 방식으로 마지막 쿠폰 경쟁을 보호합니다.
- 발급 수만 증가한 뒤 쿠폰 저장이 실패하면 전체 rollback합니다.
- 중복이면 발급 수를 다시 증가시키지 않고 기존 쿠폰을 반환합니다.
- 캠페인이 품절·비활성으로 바뀐 뒤에도 이미 받은 같은 쿠폰 결과는 그대로 조회됩니다.

기존 쿠폰을 빠르게 조회해 반환할 수 있지만 **먼저 조회한 결과가 없었다는 것만으로 동시 중복을 막을 수는 없습니다.** TX 안의 재검사와 DB 제약을 유지합니다.

동시 충돌의 DB 예외를 다룬다면 실패한 TX를 rollback한 뒤 기존 쿠폰을 새 TX에서 확인합니다. 연결 오류·다른 제약 오류를 전부 중복 성공으로 바꾸지 않습니다.

### 🪑 3. Redis의 현재 처리 자리

Redis Set에 **현재 발급 실행 token**을 저장합니다. token은 서버가 실행마다 생성하며 고객의 요청 키·사용자 ID·couponId와 구분합니다. 서로 다른 실행이 같은 token을 공유하지 않습니다.

```
기존 쿠폰 조회 → 있으면 기존 결과 반환
       ↓ 없으면
Redis 자리 획득
       ↓ 수용됐을 때만
실제 DB 발급 TX
       ↓ 실행·TX 종료 확인
자기 token 반환 → 저장된 업무 결과 응답
```

수용량 C는 신뢰하는 서버 설정이며 HTTP 입력으로 받지 않습니다. 전용 키 이름을 사용하고 동일한 쿠폰 발급 경로가 같은 키를 참조하게 합니다. 캐시 키와 섞지 않습니다.

**필수 Lua 경계**는 같은 실행 token의 존재 확인·현재 Set 크기 확인·빈자리 추가입니다. `SCARD`와 `SADD`를 애플리케이션의 두 round-trip으로 분리하지 않습니다.

- 공통 · Lua 수용 로직 예시
    
    실제 호출에서는 수용 기능이 열린 상태인지와 Redis 상태의 신뢰 조건을 별도로 확인합니다. 이 예시는 정상 Redis에서 한 키의 자리 경쟁을 보호하는 작은 로직입니다.
    
    ```lua
    local capacity = tonumber(ARGV[1])
    local token = ARGV[2]
    if not capacity or capacity < 1 or capacity % 1 ~= 0
        or not token or token == '' then
      return redis.error_reply('invalid admission input')
    end
    if redis.call('SISMEMBER', KEYS[1], token) == 1 then
      return 1
    end
    if redis.call('SCARD', KEYS[1]) >= capacity then
      return 0
    end
    redis.call('SADD', KEYS[1], token)
    return 1
    ```
    
    같은 token 결과 재확인은 동일한 실행 안에서만 의미가 있습니다. 다른 HTTP 실행에 기존 token을 넘겨 두 실행이 한 자리를 공유하게 하지 않습니다. 수용 응답이 불확실하면 DB 발급을 시작하지 않습니다.
    
    반환은 `SREM permitsKey ownToken`처럼 자기 token만 제거합니다. 같은 반환을 반복해도 다른 실행의 자리가 지워지지 않아야 합니다.
    

Lua가 성공했다고 실제 쿠폰이 만들어진 것은 아닙니다. DB가 품절·중복·오류를 판단하며, 실행이 끝나면 처리 자리만 반환합니다. **정상 발급 뒤 슬롯을 돌려줄 때 issuedCount를 감소시키지 않습니다.**

이미 발급된 중복 요청은 DB의 기존 결과를 반환하므로 새 실행 자리가 필요 없습니다. 동시에 도착한 미완료 중복 요청은 각 HTTP 실행이 별도 자리를 차지할 수 있지만, DB 발급 효과는 하나입니다. 이번에 제한하는 것은 일반 workId의 접수 이력이 아니라 **현재 실행 수**입니다.

### 🔌 4. 연결과 장애 경계

두 트랙의 기존 Redis 설정에서 수용 판단은 전용 master 연결을 사용합니다. 기본 `REPLICA_PREFERRED` 연결의 읽은 count를 별도 수용 판단으로 쓰지 않습니다.

- Java·Kotlin · Redis 연결과 script 실행
    - `modules/redis`의 `RedisConfig`와 `RedisProperties`를 읽고 실제 primary 주소·serializer를 확인합니다.
    - master template qualifier는 `redisTemplateMaster`입니다. Java/Kotlin의 기존 선언 타입에 맞춰 주입하고 unchecked cast로 실행 오류를 숨기지 않습니다.
    - script는 `apps/commerce-api/src/main/resources/redis/` 등 기존 구조에 맞춰 두고 Spring Data Redis script 실행 API로 호출합니다.
    - 키·token은 현재 String serializer에 맞춥니다. script 결과 1·0과 예외·timeout을 구분합니다.
    - 클라이언트 command timeout을 제한합니다. 실제 테스트 대상 주소를 확인해 엉뚱한 Compose Redis를 내려 장애를 만들었다고 하지 않습니다.

**Redis 접근 실패·불확실한 수용 응답에는 신규 DB 발급을 시작하지 않습니다.** local count·다른 무제한 queue로 우회하지 않습니다. DB가 정상인 경우 기존 보유 목록·이미 완료된 결과 조회는 유지합니다.

DB commit/rollback과 실행 종료를 확인한 뒤 자기 token을 반환합니다. 단순 client timeout이나 HTTP 연결 종료만으로 반환하지 않습니다. 반환 호출이 실패해도 이미 발급한 쿠폰을 취소하거나 발급 수를 되돌리지 않습니다.

**짧은 재개 규칙**: Redis 장애·상태 유실을 확인하면 신규 수용을 닫고 자동으로 다시 열지 않습니다. 로컬 실행은 기본 닫힘 설정과 명시적 열기를 두고, 오류 후 건강 확인만으로 열지 않게 합니다. 모든 해당 발급 실행·DB 작업의 종료와 실제 쿠폰 결과를 확인한 다음, 자기 범위의 비활성 token만 정리하고 수용을 다시 엽니다. 종료가 불명확하면 닫힌 상태를 유지합니다.

이 보수적 방법은 장애 때 자리가 남아 가용성이 줄어들 수 있습니다. token을 TTL로 지워 살아 있는 이전 실행과 겹치게 만들지는 않습니다. 이번 기본 실험은 로컬 발급 인스턴스의 통제된 장애·재개이며, 감지하지 못한 Redis 상태 손실이나 다중 인스턴스 자동 장애 전환까지 안전한 분산 semaphore라고 주장하지 않습니다.

### 🔬 5. 현재 수용량과 자리 반환 검증

실제 Redis에 C=3을 설정하고 캠페인 발급 한도는 이 실험을 가리지 않게 충분히 둡니다.

1. 서로 다른 세 사용자의 실제 발급 요청을 보냅니다.
2. Redis 획득 직후·DB TX 시작 전에 barrier를 두어 세 실행을 유지합니다.
3. 활성 token 3개를 확인한 상태에서 네 번째 사용자의 요청을 보냅니다.
4. 네 번째는 429이며 해당 사용자의 DB 발급 경로에 진입하지 않고 쿠폰도 없습니다.
5. 한 실행을 진행시켜 DB 발급·종료·반환을 확인합니다.
6. 네 번째 사용자가 다시 요청하면 빈자리에 들어가 실제 쿠폰을 받습니다.
7. 나머지 실행도 종료해 실제 쿠폰·issuedCount와 활성 token 0을 확인합니다.

이 실험은 네 요청이 모두 바로 끝나는 테스트와 다릅니다. barrier 대기는 deadline을 두고 실패 시 자신이 시작한 실행을 해제·정리합니다. thread-local count나 mock Redis 결과만으로 실제 공유 수용량 검증을 대체하지 않습니다.

자기 token 반환을 두 번 수행하거나 모르는 token을 반환해도 다른 활성 token이 사라지지 않는지 확인합니다. 같은 token을 가진 두 업무 실행을 만들어 “중복 수용이 안전하다”고 주장하지 않습니다.

### 🧪 6. 쿠폰 결과·중복·장애 검증

| 장면 | 핵심 기대 |
| --- | --- |
| 정상 발급·본인 목록 | 쿠폰 1·issuedCount 1, 자기 목록에서 같은 ID |
| 동일 사용자·캠페인 재요청 | 같은 couponId, 추가 발급·발급 수 증가 0 |
| 동시 동일 사용자 발급 | 실제 DB 효과 1, 별도 사용자 목록에 노출 없음 |
| 마지막 수량 경쟁 | 한도 초과 0, 품절과 수용량 거절을 구분 |
| 발급 수 증가 뒤 insert 실패 | 쿠폰·발급 수 전체 rollback, 종료 뒤 자리 반환 |
| DB commit 뒤 응답 유실 | 같은 사용자 재요청에서 기존 쿠폰, 추가 발급 0 |
| 실제 Redis 중단 | 신규 발급 503·DB 신규 효과 0, 기존 본인 목록 유지 |
| 반환 실패·복구 | 쿠폰 유지, 수용 닫힘, 확인 후 자기 남은 점유 복구 |

DB 한도 테스트에서는 충분한 Redis 용량으로 실제 DB 경쟁에 참여시키거나 DB 발급 handler를 직접 동시 호출해 해당 불변식을 검증합니다. 예를 들어 총 5장에 서로 다른 8명이 DB 발급에 참여하면 발급 5·품절 3·실제 쿠폰 5·issuedCount 5가 됩니다. Redis에서 먼저 거절된 요청을 품절 3에 포함하지 않습니다.

Redis 중단 테스트는 **실제 application이 사용하는 endpoint**를 내려 확인합니다. 복구 시 PONG만 보고 재개하지 말고 위의 짧은 재개 규칙을 적용합니다. TTL 시간 경과만으로 기존 활성 자리가 자동 반환되지 않는지도 확인합니다.

- Java·Kotlin · 관련 검사 예시
    
    테스트 이름은 직접 작성한 코드에 맞춥니다. 기존 실제 MySQL·Redis fixture를 재사용하고 생성한 자원만 정리합니다.
    
    ```bash
    ./gradlew :apps:commerce-api:test --tests '*CouponIssueIntegrationTest'
    ./gradlew :apps:commerce-api:test --tests '*CouponAdmissionTest'
    ./gradlew :apps:commerce-api:test --tests '*CouponRedisFailureTest'
    
    # Java: 기존 Checkstyle·ArchUnit·관련 회귀
    ./gradlew :apps:commerce-api:check
    
    # Kotlin
    ./gradlew :apps:commerce-api:ktlintCheck :apps:commerce-api:check
    ```
    
    테스트 0건·skip·연결 실패는 성공이 아닙니다. 장애로 Redis 상태를 잃었다고 신규 수용 성공으로 바꾸거나, 다른 작업의 cache·DB·컨테이너를 일괄 삭제하지 않습니다.
    

설계에서 “쿠폰 5장과 처리 자리 3개”의 차이를 먼저 정하고 AI에 중복 발급·동시 마지막 자리·반환 실패 반례를 질문합니다. 필요한 변경과 기대 결과를 작게 나누고, 실제 DB·Redis 상태로 채택 여부를 판단합니다.

**제출**: 캠페인 준비 코드·실제 쿠폰 발급/목록 API, DB 정합성·Redis 수용 코드와 Lua, 관련 테스트, PR과 기술 글. PR에는 발급 총량·현재 점유·중복 결과·장애 거절의 대표 결과와 보수적 재개 조건을 짧게 남깁니다. W7 주문 이벤트·구매 활동은 불필요하게 쿠폰에 연결하거나 변경하지 않습니다.

### 실습 추가 공지
발제자료의 세마포어는 여러분들이 처리량 제한에 대한 이해와 구현을 가장 쉽게 따라해볼 수 있도록 만든 BASIC 샘플이에요.
하지만, 열정넘치는 여러분은 처리량 제한에 걸려 쿠폰 발급이 가능한 상황인데도 실패를 반환하는 고객경험을 결코 만들고 싶지 않겠죠, 또한 정말 공정한 선착순 쿠폰 발급은 어떻게 설계해야할까에 대한 고민도 많이 하고 있는 것 같아요.
우리 발제의 BASIC 샘플은 처리량 제한에 대한 이해를 위해 실험해보는 수준으로 끝내도 괜찮습니다.
처리량 제한에 대한 이해가 완벽하다면, 쿠폰 발급에 대한 구현은 어떠한 방식이어도 좋습니다.

- [ ]  정상 발급 결과를 본인 보유 목록에서 조회하고 다른 사용자 결과를 노출하지 않는다.
- [ ]  한도·사용자 중복·발급 수와 쿠폰 insert를 DB에서 원자적으로 보호한다.
- [ ]  처리 자리 반환이 발급된 쿠폰이나 총량을 되돌리지 않는다.

### 🪑 수용과 반환

- [ ]  실제 Redis의 원자 연산으로 C=3에서 유지 중인 세 실행과 네 번째 거절을 확인했다.
- [ ]  실행 종료 뒤 자기 token만 반환하고 새 요청이 그 자리를 재사용한다.
- [ ]  동일 업무의 중복 효과와 동시에 진행 중인 HTTP 실행 수를 구분한다.

### 🔌 장애와 회귀

- [ ]  Redis 장애에서 신규 발급을 우회하지 않고 기존 DB 결과 조회는 유지한다.
- [ ]  timeout·TTL만으로 활성 자리를 재사용하지 않으며 확인 후 명시적으로 재개한다.
- [ ]  관련 기능·회귀·lint·ArchUnit을 실행하고 자기 테스트 자원을 정리했다.

> 

자신의 구현·실험에서 의미 있었던 주제 하나를 저장소 Markdown·Issue·블로그로 씁니다.

### 💭 주제 예시

- 쿠폰이 남아 있는데도 요청을 거절해야 했던 이유
- 발급 총량과 처리 자리를 나눠 설계한 방법
- 동기 발급과 비동기 대기열 중 선택한 이유
- 마지막 자리를 Redis Lua로 보호하며 알게 된 원자성의 범위
- 같은 사용자의 두 요청과 하나의 쿠폰을 구분한 방법
- Redis 장애에서 신규 발급과 보유 목록이 다르게 동작하는 이유
- TTL 자동 회수 대신 보수적 재개를 선택한 비용
- AI가 제안한 fallback이 수용 제한을 우회했던 장면
- 그 밖에 이번 학습에서 설명하고 싶은 주제

### 📝 작성 기준

- **상황·예시**: 실제 요청·점유·쿠폰 결과 중 중요한 장면을 보여 줍니다.
- **개념**: 수용량·원자성·멱등성·fail-closed 중 중요한 개념을 자신의 말로 설명합니다.
- **판단·이유**: 선택한 수용·반환·재개 정책과 이번 실험의 한계를 구분합니다.
