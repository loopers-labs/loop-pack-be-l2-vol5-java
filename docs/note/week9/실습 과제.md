# 9주차 실습 · 중단된 배치를 이어서 같은 랭킹 만들기

Tag: BE_L2, round9, task

## 💻 Implementation Quest

> **실제 구매 활동으로 주간 랭킹을 만들고, 중단 뒤 같은 입력·같은 작업을 이어 갑니다.**
> 

W6·W7의 상품 구매 활동을 입력으로 사용합니다. W8 쿠폰 발급은 유지하지만 구매 점수에 섞지 않습니다. `commerce-batch`에 주간 job을 만들고, `commerce-api`에서 **완성된 주간 랭킹**을 조회하도록 연결합니다.

### 📊 1. 주간 결과와 조회 계약

| 항목 | 이번 계약 |
| --- | --- |
| 기간 | UTC 월요일 00:00부터 다음 월요일 00:00 전까지 |
| 주간 소속 | 활동의 최초 주문 confirmedAt |
| 점수 | 상품별 구매 quantity 합, 정수 |
| 순서 | 점수 내림차순, 동점이면 productId 오름차순 |
| 입력 원본 | W6·W7 consumer가 남긴 orderId·productId별 구매 활동 |
| 공개 | 기간별 하나의 완성된 snapshot |

`GET /api/v1/rankings/weekly?periodStart=2026-08-17&limit=10`을 추가합니다. 날짜·월요일 기준을 검증하고 limit은 양수·최대 100 등 명시한 범위를 적용합니다. 응답에 periodStart·periodEnd·snapshotId·입력 고정 시점과 상품별 점수·순위를 포함합니다.

공개본이 없으면 `NOT_PUBLISHED`와 빈 items, 구매가 없었던 완성본이면 `PUBLISHED`와 해당 snapshotId·빈 items로 구분할 수 있습니다. 내부 stage나 임의의 이전 주를 요청한 주의 결과로 반환하지 않습니다.

삭제·비노출 상품은 기존 고객 공개 조건으로 제외합니다. **저장된 계산 순위는 유지**하므로 제외된 상품 때문에 1·3위처럼 간격이 있을 수 있음을 계약에 명시합니다. 공개 조건을 적용한 뒤 limit을 적용하고 현재 이름 등 표시 정보는 기존 상품 조회 규칙으로 연결합니다. 과거 활동·점수 행은 지우지 않습니다.

### 🧊 2. 실제 입력을 고정하기

`snapshotId`와 기간·revision을 정하고, 해당 주의 실제 구매 활동을 **변경하지 않는 입력 묶음**으로 만듭니다. 개념상 다음 데이터가 필요하며 실제 테이블·클래스 구성은 설계에 맞게 정합니다.

| 저장 단위 | 목적·유일성 |
| --- | --- |
| snapshot 정보 | snapshotId·기간·revision·상태·입력 고정 시점·건수·checksum |
| snapshot 입력 | snapshotId·orderId·productId별 quantity·confirmedAt |
| 점수 stage | snapshotId·productId별 계산 중 절대 점수 |
| 완성 ranking | snapshotId·productId별 점수·계산 순위 |
| 공개 pointer | periodStart별 공개 snapshotId |

기존 DB의 일관된 읽기에서 원본 활동을 가져와 snapshot 입력과 manifest를 함께 commit합니다. 작은 실습 데이터에서는 하나의 로컬 TX로 고정할 수 있습니다. 여러 페이지를 읽는다면 **같은 일관된 읽기 시점과 안정된 정렬**을 유지해야 합니다. `max(id)`만으로 commit 시점까지 고정했다고 가정하지 않습니다.

- 입력 고정이 실패하면 반쪽 snapshot을 계산 대상으로 사용하지 않습니다.
- 완성된 입력은 재시작할 때 다시 복사하거나 추가하지 않습니다.
- W6의 같은 주문 이벤트에 상품이 여러 개 있으면 모든 품목을 포함합니다. eventId만으로 두 번째 상품을 중복 제거하지 않습니다.
- source의 소비 중복은 W6 DB 경계에서 처리되며 배치 입력도 orderId·productId의 유일성을 지킵니다.
- 이미 존재하는 snapshotId의 기간·입력·revision이 다르면 덮어쓰지 않고 충돌로 처리합니다.

### 🧩 3. Job과 Step 연결

`weeklyRanking` job은 **입력 고정 → 상품별 점수 계산 → 완성본 공개**로 나눕니다. 식별 parameter는 `periodStart, snapshotId` 등 실제 업무를 구분하는 값으로 고정합니다.

- Java·Kotlin · 기존 Batch 기반에서 확인할 것
    
    두 트랙 `commerce-batch`에 DemoJobConfig·DemoTasklet·DemoJobE2ETest와 Spring Batch 의존성이 있습니다. 랭킹 job·입력 fixture·API는 이번에 만듭니다.
    
    - DemoJobConfig의 `RunIdIncrementer`는 새 작업 예시이며 실패 작업 재시작에 그대로 적용하지 않습니다.
    - Demo tasklet의 `ResourcelessTransactionManager`는 DB 점수·checkpoint의 원자성을 제공하지 않습니다. 실제 DB transaction manager를 연결합니다.
    - 영속 JobRepository와 결과 writer가 같은 DB TX에 참여하도록 설정합니다. 매 실행 새 메모리 repository를 만들지 않습니다.
    - 기존 local/test의 Batch schema 초기화 설정은 최초 테스트 DB 준비에 사용합니다. 첫 실행과 재시작 사이에 Batch metadata를 비우거나 새 DB를 만들지 않습니다.
    - `spring.batch.job.name`이 자신의 job을 선택하도록 하고, 테스트에서는 자동 실행과 명시적 launch가 겹치지 않게 합니다.
    - reader의 job parameter는 step scope 등 실제 실행에 바인딩합니다.

첫 Step이 성공한 뒤 계산 Step에서 실패하면 재시작은 기존 입력을 유지한 채 실패한 계산을 이어 갑니다. 완료한 입력 고정 Step을 무조건 다시 실행하도록 설정하지 않습니다.

- 공통 · 먼저 세 상품으로 DB chunk 재시작 연결하기
    
    랭킹 계산 전에 **§6의 구매 활동을 고정한 snapshot에서 상품 7·8·9를 읽는 작은 연결 예시**로 reader 상태와 DB commit을 확인합니다. 점수·순위·공개 API의 정답 구현은 아닙니다. 아래 `ranking_snapshot_input(snapshot_id, product_id, …)`는 §2에서 직접 만든 frozen 입력 테이블의 예시 이름이므로 자신의 이름에 맞춥니다.
    
    두 고정 starter는 Spring Boot 3.4.4와 관리되는 Spring Batch 5.2.2를 사용합니다. 아래 예시는 이 버전의 `JdbcCursorItemReaderBuilder`와 `JobLauncher`를 사용합니다. 자신의 의존성을 바꿨다면 먼저 실제 해석 버전을 확인합니다.
    
    ```bash
    ./gradlew :apps:commerce-batch:dependencyInsight --dependency spring-batch-core --configuration runtimeClasspath
    ```
    
    기존 `commerce-batch` 테스트에서 다음만 연결합니다.
    
    - `@SpringBootTest(properties = "spring.batch.job.enabled=false")`로 자동 실행을 끄고, 기존 실제 MySQL fixture의 `mySqlMainDataSource`와 그 DB를 사용하는 Spring의 `PlatformTransactionManager` bean, `JobRepository, JobLauncher, JobExplorer`를 주입합니다. Kotlin은 properties에 배열 문법을 사용합니다.
    - starter의 primary DataSource와 같은 transaction manager를 사용하는 Boot의 JDBC JobRepository를 그대로 주입합니다. 별도 `@EnableBatchProcessing`·메모리 repository·`ResourcelessTransactionManager`를 추가하지 않습니다. 별도 Batch용 DataSource/transaction manager를 설정했다면 이 예시에서는 writer와 repository가 같은 DB TX를 쓰도록 먼저 맞춥니다. `JdbcTemplate`도 같은 DataSource를 전달받아야 합니다.
    - 테스트 시작 시 한 번만 §6 입력을 snapshotId=`probe-1`로 고정하고 아래 **테스트 확인용 테이블**을 빈 상태로 준비합니다. 제품의 점수 테이블·새 업무 도메인이 아니며 API에서 읽지 않습니다.
    
    ```sql
    CREATE TABLE batch_restart_probe (
      snapshot_id VARCHAR(64) NOT NULL,
      product_id BIGINT NOT NULL,
      PRIMARY KEY (snapshot_id, product_id)
    ) ENGINE=InnoDB;
    ```
    
    기본 동기 JobLauncher를 사용해 한 테스트 메서드 안에서 최초 실패와 재실행을 이어 갑니다. 두 실행 사이에는 입력·확인 행·Batch metadata·MySQL을 초기화하지 않습니다. 테스트 전체에 자동 rollback을 걸지 말고, 첫 chunk가 별도 DB 조회에서 보이는지 확인합니다. 기존 local/test의 Batch schema 초기화는 처음 DB를 준비할 때만 사용합니다.
    
- Java · 실제 Reader·Writer와 같은 parameter로 다시 실행
    
    테스트의 작은 helper 메서드입니다. `Job/JobParameters`는 Batch core, builder는 `core.job.builder`·`core.step.builder`, reader builder는 `item.database.builder`, `ItemProcessor`는 `item`, `JdbcTemplate`는 Spring JDBC의 타입입니다.
    
    ```java
    Job probe(JobRepository repo, PlatformTransactionManager tx,
              DataSource ds, JobParameters params, boolean failOnNine) {
        String snapshot = Objects.requireNonNull(params.getString("snapshotId"));
        var reader = new JdbcCursorItemReaderBuilder<Long>()
            .name("purchaseProductProbe").saveState(true)
            .dataSource(ds)
            .sql("select distinct product_id from ranking_snapshot_input "
                + "where snapshot_id = ? order by product_id")
            .preparedStatementSetter(ps -> ps.setString(1, snapshot))
            .rowMapper((rs, n) -> rs.getLong("product_id"))
            .build();
        var jdbc = new JdbcTemplate(ds);
        var step = new StepBuilder("probeProducts", repo)
            .<Long, Long>chunk(2, tx)
            .reader(reader)
            .processor((ItemProcessor<Long, Long>) id -> {
                if (failOnNine && id == 9L) {
                    throw new IllegalStateException("before third product");
                }
                return id;
            })
            .writer(items -> {
                for (Long id : items) {
                    jdbc.update("insert into batch_restart_probe "
                        + "(snapshot_id, product_id) values (?, ?)", snapshot, id);
                }
            })
            .build();
        return new JobBuilder("purchaseInputProbe", repo).start(step).build();
    }
    ```
    
    주입받은 bean을 위 메서드에 전달합니다. `probe(...)` 호출마다 새 reader·step·job 객체를 만들지만 이름과 식별 parameter는 같습니다.
    
    ```java
    var params = new JobParametersBuilder()
        .addString("snapshotId", "probe-1", true).toJobParameters();
    var first = launcher.run(probe(repo, tx, ds, params, true), params);
    // 여기서 FAILED, 확인 행 7·8, 저장된 reader 위치 2를 먼저 검사
    var second = launcher.run(probe(repo, tx, ds, params, false), params);
    // 같은 JobInstance, 다른 JobExecution, COMPLETED와 확인 행 7·8·9 검사
    ```
    
- Kotlin · 같은 연결과 재실행
    
    ```kotlin
    fun probe(
        repo: JobRepository, tx: PlatformTransactionManager,
        ds: DataSource, params: JobParameters, failOnNine: Boolean,
    ): Job {
        val snapshot = requireNotNull(params.getString("snapshotId"))
        val reader = JdbcCursorItemReaderBuilder<Long>()
            .name("purchaseProductProbe").saveState(true)
            .dataSource(ds)
            .sql("select distinct product_id from ranking_snapshot_input " +
                "where snapshot_id = ? order by product_id")
            .preparedStatementSetter { ps -> ps.setString(1, snapshot) }
            .rowMapper { rs, _ -> rs.getLong("product_id") }
            .build()
        val jdbc = JdbcTemplate(ds)
        val step = StepBuilder("probeProducts", repo)
            .chunk<Long, Long>(2, tx)
            .reader(reader)
            .processor(ItemProcessor<Long, Long> { id ->
                check(!(failOnNine && id == 9L)) { "before third product" }
                id
            })
            .writer { items ->
                items.forEach { id ->
                    jdbc.update("insert into batch_restart_probe " +
                        "(snapshot_id, product_id) values (?, ?)", snapshot, id)
                }
            }
            .build()
        return JobBuilder("purchaseInputProbe", repo).start(step).build()
    }
    ```
    
    ```kotlin
    val params = JobParametersBuilder()
        .addString("snapshotId", "probe-1", true).toJobParameters()
    val first = launcher.run(probe(repo, tx, ds, params, true), params)
    // 여기서 FAILED, 확인 행 7·8, 저장된 reader 위치 2를 먼저 검사
    val second = launcher.run(probe(repo, tx, ds, params, false), params)
    // 같은 JobInstance, 다른 JobExecution, COMPLETED와 확인 행 7·8·9 검사
    ```
    

**확인할 관찰값**: 첫 실행 뒤 `JobExplorer.getStepExecution(jobExecutionId, stepExecutionId)`로 `probeProducts`의 영속 ExecutionContext를 다시 읽습니다. 위 이름의 reader는 `purchaseProductProbe.read.count=2`가 마지막 성공 chunk 위치이며 확인 테이블에는 상품 7·8만 있어야 합니다. 재실행은 동일 JobInstance의 새 JobExecution이고 writer는 상품 9 한 건만 추가해 최종 세 행이 됩니다. reader의 메모리 값이나 로그만 비교하지 않습니다. 실패 스위치는 parameter가 아니며 `run.id`·현재 시각도 추가하지 않습니다.

이 작은 예시의 INSERT·유일 키는 앞의 두 상품을 잘못 다시 썼을 때 오류가 드러나게 합니다. 실제 랭킹 writer에는 아래의 절대 점수·멱등성 설계를 적용합니다. 입력 고정·점수 계산·완성본 공개와 연결 검증은 그대로 자신의 과제입니다. 참고: [Boot 3.4.4의 Batch 의존성](https://github.com/spring-projects/spring-boot/blob/v3.4.4/spring-boot-project/spring-boot-dependencies/build.gradle), [Batch 5.2.2 reader 설정](https://docs.spring.io/spring-batch/docs/5.2.2/api/org/springframework/batch/item/database/builder/JdbcCursorItemReaderBuilder.html).

### ♻️ 4. 상품별 Reader·Processor·Writer

reader는 고정 입력의 **서로 다른 productId**를 오름차순으로 읽습니다. 상품 하나가 chunk item 하나입니다.

processor는 해당 snapshot·상품의 quantity 합을 계산하고, writer는 `(snapshotId, productId)`에 **절대값을 upsert**합니다. 같은 입력을 다시 처리해도 `score = total`로 수렴해야 합니다. `score += total`로 두 번 더하지 않습니다.

| 경계 | 확인할 것 |
| --- | --- |
| Reader | 유일하고 안정된 sort key, 영속 재시작 상태 |
| Processor | 현재 활동 DB가 아니라 같은 frozen snapshot에서 계산 |
| Writer | 상품별 유일 키·절대 점수, 실제 DB TX 참여 |
| Chunk | 결과와 reader checkpoint의 같은 commit 경계 |

기존 활동을 한 번씩 증분 합산하는 방식을 선택해도 되지만 그 경우 활동별 적용 기록과 점수 증가가 같은 TX여야 합니다. 절대값 쓰기와 증분 쓰기를 섞지 않습니다.

- Java · Chunk Step 연결 예시
    
    `ProductScore`와 reader·processor·writer는 직접 작성한 구성 요소입니다. 실제 DB용 `transactionManager`를 주입합니다.
    
    ```java
    return new StepBuilder("calculateWeeklyScores", jobRepository)
        .<Long, ProductScore>chunk(2, transactionManager)
        .reader(productIdReader)
        .processor(weeklyScoreProcessor)
        .writer(scoreWriter)
        .build();
    ```
    
- Kotlin · Chunk Step 연결 예시
    
    ```kotlin
    return StepBuilder("calculateWeeklyScores", jobRepository)
        .chunk<Long, ProductScore>(2, transactionManager)
        .reader(productIdReader)
        .processor(weeklyScoreProcessor)
        .writer(scoreWriter)
        .build()
    ```
    
    chunk=2는 아래 작은 재시작 실험의 값입니다. 실제 데이터의 최적 처리량을 측정한 값이라는 뜻은 아닙니다.
    

### 🚪 5. 완성본만 공개하기

계산 Step이 완료된 뒤 snapshot의 모든 상품 점수와 예상 상품 수를 확인하고 `score DESC, productId ASC`로 순위를 만듭니다. 내부 상태 이름은 자유롭게 정하되, **완성 조건과 공개 pointer 변경은 하나의 DB TX에서 보호**합니다.

- 계산 중·계산 실패에는 기존 공개 pointer와 API 결과를 유지합니다.
- 공개 TX 중 오류가 나면 새 pointer나 일부 ranking만 노출하지 않습니다.
- 같은 snapshot의 공개 단계를 다시 수행해도 결과가 늘거나 순위가 바뀌지 않습니다.
- 기간별 revision은 명시적으로 증가시킵니다. 같은 기간의 동시 계산은 기본 범위에서 직렬로 실행합니다.
- 이미 더 새 revision이 공개돼 있다면 오래된 실행으로 pointer를 되돌리지 않습니다. 조건부 갱신·현재 pointer 검증으로 보호합니다.

API는 pointer와 그 snapshot의 ranking을 일관되게 조회합니다. 예를 들어 한 query에서 pointer를 join하면 읽는 도중 서로 다른 snapshot의 행을 섞는 일을 피할 수 있습니다.

**공개 TX commit과 최종 Batch metadata 저장은 같은 순간이라고 가정하지 않습니다.** 공개된 완성본이 있는데 JobExecution이 실패·미완료로 남으면 기존 snapshot·pointer를 먼저 확인합니다. 재실행된 공개 단계는 같은 결과로 수렴하며 이미 공개한 정상 결과를 임의 삭제하지 않습니다.

### 🔬 6. 작은 입력으로 재시작 확인

| 43 | 7 | 3 | 2026-08-18T01:00:00Z |
| 44 | 9 | 5 | 2026-08-19T01:00:00Z |

정상 결과는 **상품 7: 5점·1위, 상품 9: 5점·2위, 상품 8: 1점·3위**입니다. 원본 구매 활동은 4행이고, reader item은 상품 7·8·9의 3개입니다. 같은 주문의 두 품목을 잃지 않았는지와 동점 순서를 함께 확인합니다.

1. snapshot 입력을 고정하고 chunk=2로 시작합니다.
2. 상품 7·8의 점수 5·1과 reader 위치가 실제 commit된 것을 확인합니다.
3. 세 번째 item인 상품 9를 처리하기 직전에 한 번 실패시킵니다.
4. 첫 JobExecution FAILED, 같은 JobInstance, 마지막 checkpoint와 stage 2행, 기존 공개본 유지를 확인합니다.
5. 같은 식별 parameter·같은 DB metadata로 새 JobExecution을 시작합니다.
6. 완료된 입력과 첫 두 상품을 다시 계산하지 않고 상품 9부터 이어서 완료하는지 확인합니다.
7. 완성 ranking과 API 결과를 정상 한 번 실행한 결과와 비교합니다.

실패 여부를 제어하는 테스트 설정은 새 식별 parameter로 만들지 않습니다. 실패 뒤 reader·job 실행 객체를 새로 만들어도 같은 metadata에서 이어져야 합니다. 실제 reader의 저장 key·위치를 관찰하고 항상 `reader.index`라는 이름이라고 가정하지 않습니다.

입력 checksum은 orderId·productId 순서로 정렬한 `orderId, productId, quantity, confirmedAt`을, 결과 checksum은 rank 순서의 `productId, score, rank`를 직렬화해 계산합니다. 필드 사이 TAB·행 사이 LF·마지막 LF 등 규칙을 고정하고 UTC 시각을 같은 형식으로 씁니다. 실행 ID·실행 시각은 결과 내용 비교에서 제외하고 snapshot의 소속 증거로 따로 기록합니다.

정상 실행과 재시작의 checksum뿐 아니라 위의 기대 점수·순위도 assert합니다. 비교용 정상 실행은 별도 snapshot/DB 격리로 만들고, 재시작 대상의 stage·Batch metadata를 지워 정상 실행으로 위장하지 않습니다.

### 🔗 7. 실제 이벤트 입력과 늦은 구매 연결

고정 fixture만 읽는 job으로 끝내지 않습니다. 한 연결 테스트에서 기존 PG 주문 확정→Outbox relay→실제 Kafka→구매 활동을 만든 뒤, 그 **실제 DB 활동을 snapshot으로 고정해 job과 랭킹 API까지** 확인합니다. ID·시각은 테스트 clock과 생성한 주문에 맞춰 기대값을 계산합니다.

- W7의 같은 이벤트를 다시 발행해도 원본 구매 활동과 랭킹 점수가 늘지 않습니다.
- snapshot 고정 뒤 같은 주의 늦은 구매가 도착해도 현재 입력·재시작 결과는 바뀌지 않습니다.
- 해당 주의 새 revision snapshot을 명시적으로 만들어 늦은 구매를 포함한 재계산을 수행합니다.
- 새 결과 공개 전에는 이전 revision, 공개 후에는 새 revision이 일관되게 보입니다.
- 구간 시작은 포함하고 끝은 제외합니다. 빈 주간 결과·아직 미공개·삭제 상품 제외도 API에서 구분합니다.

늦은 구매도 원래 주에 속합니다. 기존 snapshot을 이어 가는 재시작과, 늦은 구매를 포함한 새 revision의 재계산을 구분해 확인합니다.
