## 📬 업무 호출을 이벤트로 바꾸는 이유

주문이 확정될 때마다 구매 활동 저장·통계 갱신·알림을 모두 주문 서비스에서 호출한다고 생각해 봅니다. 기능이 늘수록 주문 서비스가 후속 기능의 구현과 실패를 알아야 합니다. 통계 저장이 잠시 느리다는 이유로 이미 성공한 결제를 실패로 돌려야 할까요?

> **이벤트(event)**는 이미 일어난 사실을 이름과 데이터로 표현한 것입니다. **커맨드(command)**는 특정 주체에게 어떤 작업을 수행하라는 요청입니다.
>

| 표현 | 의미 | 실패를 해석할 때 |
| --- | --- | --- |
| ConfirmOrder | 주문을 확정해 달라는 요청 | 아직 주문이 확정되지 않았을 수 있음 |
| OrderConfirmed | 주문이 확정됐다는 사실 | 후속 소비 실패가 과거 확정을 취소하지 않음 |
| RecordPurchaseActivity | 구매 활동을 기록하라는 요청 | 수행할 책임과 완료 결과를 정해야 함 |

이벤트를 사용하면 발행자는 후속 소비자의 내부 구현을 덜 알 수 있습니다. 하지만 **시간적 결합과 실패를 없애는 것이 아니라 전달 지연·중복·누락을 다뤄야 하는 경계로 옮깁니다.** 메시지 시스템을 붙였다고 모든 작업이 자동으로 완료되지는 않습니다.

이번에 새로 다루는 **상품 구매 활동**은 “어느 확정 주문에서 어떤 상품을 몇 개 구매했는가”라는 영속 사실입니다. 주문을 또 결제하거나 재고를 다시 차감하는 작업이 아닙니다. 당장은 DB에서 확인하고, 이후 이 사실을 모아 주간 랭킹을 만듭니다.

## 🏠 프로세스 안의 이벤트와 프로세스 밖의 메시지

Spring의 application event는 같은 애플리케이션 안에서 발행자와 listener를 분리할 수 있습니다. Kafka는 프로세스 밖의 broker에 기록을 남겨 별도 consumer가 읽도록 연결합니다.

| 방식 | 실행·저장 경계 | 주의점 |
| --- | --- | --- |
| 일반 메서드 호출 | 호출자의 흐름에서 직접 실행 | 협력 대상과 실패가 직접 연결됨 |
| 기본 application event | 기본 설정에서는 같은 스레드의 listener 실행 | 발행 자체가 비동기·영속 저장을 뜻하지 않음 |
| 비동기 listener | executor의 별도 실행 | 프로세스 종료 때 미완료 작업이 남을 수 있음 |
| Kafka 메시지 | broker에 기록하고 consumer가 별도로 읽음 | 발행 확인·보존·소비 위치·중복 정책이 필요 |

`@TransactionalEventListener`는 listener 실행 시점을 트랜잭션 단계에 연결합니다. 기본은 `AFTER_COMMIT`이며, 트랜잭션이 없으면 기본적으로 실행하지 않습니다. 일반 `@EventListener`를 붙였다는 이유로 commit 이후에만 실행되는 것은 아닙니다.

### 🕳 commit 이후에도 남는 빈틈

```
주문 확정 DB commit
        ↓ 프로세스가 여기에서 멈출 수 있다
Kafka로 OrderConfirmed 전송
        ↓
consumer가 구매 활동 저장
```

commit 전에 보내면 나중 DB rollback으로 **실제로 확정되지 않은 주문의 이벤트**가 남을 수 있습니다. commit 뒤 보내면 확정과 발행 사이에 **누락 구간**이 남습니다. `@Async`나 after-commit annotation만으로 이 두 시스템을 하나의 원자적 작업으로 만들 수 없습니다.

이번 주는 commit 이후 직접 발행을 연결하고 이 한계를 관찰합니다. 다음 주에는 같은 업무 변경과 **Outbox라는 전달할 사실의 DB 기록**을 묶어 개선합니다. 이번 주에 Outbox를 미리 구현할 필요는 없습니다.

## 🗂 Kafka에 남는 것은 소비해도 사라지지 않는 로그

> **Topic**은 관련 기록을 담는 논리적 이름이고, **partition**은 그 topic을 나눈 순서 있는 로그입니다. **Offset**은 한 partition 안에서 기록의 위치를 나타냅니다.
>

```
topic: order-events
  partition 0: [offset 0] [offset 1] [offset 2] ...
  partition 1: [offset 0] [offset 1] ...
```

서로 다른 partition의 offset 10은 같은 시점이나 전역 순서를 뜻하지 않습니다. 하나의 record를 특정하려면 `topic + partition + offset`을 함께 봅니다.

consumer가 읽어도 record를 즉시 삭제하지 않습니다. 보존 기간·크기 등의 정책에 따라 로그가 유지되고, consumer group마다 진행 위치를 관리합니다. 따라서 다른 그룹이 같은 데이터를 독립적으로 읽거나 보존 범위 안에서 다시 읽을 수 있습니다.

반대로 **영원히 보관되는 DB**라고 생각하면 안 됩니다. retention을 지나 삭제된 record는 단순 offset 되돌리기로 되살릴 수 없습니다. compacted topic의 key별 보존 정책도 일반 이벤트 로그와 목적이 다릅니다.

## 🔑 Key로 순서와 분산의 기준을 고르기

Producer는 record의 topic·key·value를 지정합니다. key는 어떤 업무를 같은 partition에 모을지 정하는 데 사용합니다.

| 후보 key | 모이는 단위 | 고려할 비용 |
| --- | --- | --- |
| orderId | 같은 주문의 사건 | 주문 내부 순서를 연결하기 쉬움 |
| productId | 같은 상품의 사건 | 인기 상품에 부하 집중 가능 |
| 무작위 값 | 매번 다른 단위 | 같은 업무의 순서 연결이 어려움 |
| null | partitioner의 무키 정책 | 항상 순번대로 분산된다고 가정할 수 없음 |

같은 partitioner·직렬화·partition 수에서 같은 key는 같은 partition으로 연결됩니다. partition 수를 늘리거나 분배 방식을 바꾸면 매핑이 달라질 수 있으므로 “같은 key는 영원히 같은 partition”이라고 말하지 않습니다.

Kafka의 순서 보장은 **partition 안의 로그 순서**입니다. consumer가 받은 뒤 별도 executor에 무제한 병렬 제출하면 업무 완료 순서는 달라질 수 있습니다. 한 주문의 이벤트를 같은 key로 보낸 것과 애플리케이션이 그 순서대로 결과를 적용하는 것은 별도 조건입니다.

이번 주문 확정 이벤트는 `orderId`를 key로 사용합니다. 한 이벤트가 여러 상품을 포함하므로 품목마다 key를 바꾼 별도 주문 확정 이벤트로 쪼개지 않습니다.

## 👥 Consumer group과 Rebalance

> **Consumer group**은 같은 topic을 분담해서 읽는 소비자들의 논리적 묶음입니다. 일반적인 group 구독에서는 한 partition을 동시에 한 group member에게 배정합니다.
>

| partition 2개, 같은 group | 안정된 배정 이후의 의미 |
| --- | --- |
| consumer 1개 | 한 consumer가 두 partition 담당 |
| consumer 2개 | 둘이 partition을 나누어 담당 |
| consumer 3개 | 적어도 하나는 담당 partition 없음 |

consumer 수를 늘린다고 partition 수를 넘어 같은 partition을 동시에 분담하지는 못합니다. 반면 **다른 group**은 각자 같은 로그를 읽습니다. 구매 활동 저장과 별도 분석이 각각 모든 이벤트를 받아야 한다면 group을 분리할 수 있습니다.

**Rebalance**는 구성원 참여·이탈이나 partition 변화 등에 따라 배정을 다시 정하는 과정입니다. 시작 직후 화면 한 번으로 배정이 끝났다고 판단하지 않습니다. 실험에서는 실제 assignment가 목표 조건에 도달할 때까지 유한하게 기다립니다.

Spring listener의 `concurrency=3`은 그 컨테이너 안의 consumer 수를 늘리는 설정입니다. 애플리케이션을 두 인스턴스 띄우면 총 member 수는 더 늘어날 수 있습니다. 인스턴스 수·스레드 수·partition 수를 혼동하지 않습니다.

## 📍 읽은 위치와 완료한 위치

| 값 | 뜻 | 알 수 없는 것 |
| --- | --- | --- |
| consumer position | 다음 poll에서 읽을 현재 위치 | 이전 record의 DB 저장 성공 |
| committed offset | group이 재시작 시 이어 갈 다음 위치 | 외부 DB와 원자적으로 완료됐는지 |
| log end offset | partition 로그의 끝 다음 위치 | 소비 업무가 모두 성공했는지 |

offset `n`의 record를 완료했다면 일반적으로 `n + 1`을 commit합니다. “마지막 처리 record의 offset”과 “다음에 읽을 offset”은 한 칸 차이가 납니다.

**Lag**는 로그 끝과 소비 진행 위치의 차이를 보는 지표입니다. committed offset 기준 lag가 0이어도 업무 처리 전에 commit한 구현이라면 DB 효과가 빠질 수 있습니다. 업무 결과까지 확인해야 하는 이유입니다.

### ⚖️ 언제 commit할 것인가

| 소비 정책 | 순서와 중단 시 결과 |
| --- | --- |
| **At-most-once · 최대 한 번** | offset commit → DB 저장. 그 사이에 멈추면 다시 읽지 않아 처리가 누락될 수 있습니다. |
| **At-least-once · 최소 한 번** | DB 저장 → offset commit. 그 사이에 멈추면 같은 record를 다시 읽어 처리가 중복될 수 있습니다. |

이 비교는 **broker에 기록된 record를 소비하는 경계**를 설명합니다. 보존된 record를 계속 재처리할 수 있다는 전제가 필요하며, 아직 발행하지 못한 주문 이벤트의 누락까지 해결하지는 않습니다.

**Exactly-once**는 정한 처리 경계에서 같은 입력의 결과가 정확히 한 번 반영되는 보장을 뜻합니다. Kafka 안의 트랜잭션 처리와 별도 MySQL의 업무 효과는 서로 다른 경계입니다. 뒤에서 producer의 보장과 consumer의 DB 중복 방지를 나누어 살펴봅니다.

두 순서의 위험이 다릅니다. 이번에는 **DB 저장 후 offset commit**을 선택하고, 재전달은 허용하되 DB의 같은 구매 효과는 한 번만 남깁니다.

`enable.auto.commit=false`는 consumer의 주기적 자동 commit을 끄는 설정입니다. 애플리케이션의 `commitSync`, Spring의 ack mode·error handler, 이미 요청해 둔 commit까지 모두 금지하는 설정은 아닙니다.

## 📨 Producer의 성공과 업무의 성공

> **acks**는 producer가 전송 성공을 판단할 때 broker의 어떤 확인을 기다리는지 정합니다.
>

| 설정 | 기다리는 확인 | 비용과 한계 |
| --- | --- | --- |
| `acks=0` | broker 확인을 기다리지 않음 | broker 수신 성공 여부를 확인하지 못함 |
| `acks=1` | leader의 기록 확인 | 복제 전 leader 장애의 유실 위험 |
| `acks=all` | 현재 ISR의 기록 확인 | 복제·최소 ISR 설정과 함께 판단 |

**Replica**는 partition의 복제본이고, **ISR**은 현재 동기화 조건을 충족하는 replica 집합입니다. `min.insync.replicas`는 `acks=all` 쓰기에 필요한 최소 ISR 수를 제한합니다. 복제 수 1의 로컬 broker에서 `acks=all`을 켰다고 다중 broker 장애 내구성을 증명한 것은 아닙니다.

**Idempotent producer**는 broker로의 전송 재시도 중 생길 수 있는 중복을 줄이는 producer 프로토콜입니다. 애플리케이션이 동일 업무를 새 record로 두 번 send하거나 consumer가 MySQL을 두 번 변경하는 것까지 자동으로 막지는 않습니다. 관련 acks·retry·in-flight 설정의 호환 조건도 함께 확인합니다.

Kafka transaction으로 Kafka record와 consumer offset을 함께 다루는 보장과 **별도 MySQL 변경**의 보장은 구분해야 합니다. “Kafka가 exactly-once이므로 DB 중복 방지는 필요 없다”는 결론은 성립하지 않습니다.

## 🧾 이벤트의 신원과 업무 효과를 함께 보호하기

전송 재시도마다 새 eventId를 만들면 같은 사실이 매번 새 사건처럼 보입니다. 주문 확정의 최초 시점과 stable eventId를 정하고, 재전달에서도 동일하게 유지합니다.

| 데이터 | 보호할 의미 |
| --- | --- |
| eventId | 같은 논리적 확정 이벤트 식별 |
| orderId | 같은 주문의 확정 사실 식별 |
| confirmedAt | 실제 최초 확정 시점 |
| items | 확정 당시 상품별 수량 |
| schemaVersion | payload 해석 계약 |

카드 정보·PG 비밀·불필요한 개인정보는 구매 활동 소비에 필요하지 않습니다. 현재 상품 가격을 다시 조회해 과거 이벤트 금액을 바꾸거나, 소비 시각을 주문 확정 시각으로 저장하지 않습니다.

### 🧱 중복 제거만 먼저 저장하면?

```
처리 완료 eventId 저장 → 프로세스 중단 → 구매 활동 저장 못 함
재전달 → 이미 처리했다며 건너뜀 → 업무 누락
```

반대로 구매 활동을 저장하고 별도 TX에서 중복 기록을 만들면 그 사이에 멈췄을 때 중복 효과가 생깁니다. **업무 효과와 중복 방지 기록을 같은 DB 트랜잭션에 넣는 것**이 핵심입니다.

- Java·Kotlin · 구매 활동 소비의 의사코드

  완성 코드가 아니라 원자적으로 보호할 범위를 보여 줍니다.

    ```
    consume(event):
      형식·버전·양수 수량·식별 관계 검증
      DB TX:
        같은 eventId 또는 orderId의 완료 기록 확인
        같은 사실이면 효과 추가 없이 완료
        식별자나 payload가 충돌하면 실패
        중복 방지 기록 + 모든 품목의 구매 활동 저장
      DB commit이 성공한 뒤에만 ack
    ```

  동시 소비에서는 조회만으로 중복을 막을 수 없습니다. DB 유일 제약으로 경쟁을 보호합니다. JPA 유일 제약 예외가 발생한 TX 안에서 예외를 삼키고 정상 commit하려 하지 않습니다. rollback 뒤 별도 TX에서 기존 사실의 일치를 확인하는 등 사용한 저장 방식에 맞는 경계를 정합니다.


같은 eventId에 다른 수량을 보내는 것은 정상 재전달이 아닙니다. 무조건 `INSERT IGNORE`로 숨기면 계약 위반을 놓칩니다. 같은 주문을 다른 eventId로 다시 보낸 경우도 새 구매로 더하지 않도록 **업무의 자연 키**를 함께 보호합니다.

## 🚧 Listener의 예외는 어디까지 전달되는가

listener에서 DB 오류가 발생했는데 catch한 뒤 ack하면 broker 입장에서는 처리 완료입니다. catch하지 않아도 error handler가 일정 횟수 뒤 기록만 남기고 정상 복귀하면 offset이 진행될 수 있습니다.

| 확인할 경계 | 질문 |
| --- | --- |
| DB handler | commit 전에 오류가 나면 모든 품목·중복 기록이 rollback되는가? |
| listener | 실패한 record를 acknowledge하지 않는가? |
| error handler | 재시도 소진 뒤 skip·recover·stop 중 무엇을 하는가? |
| offset | 실제 group의 committed offset이 실패 record를 지나갔는가? |

Spring Kafka에서 `commitRecovered=false` 하나만으로 “실패 record는 절대 commit되지 않는다”라고 말하지 않습니다. handler 자체의 recovered commit과, handler 정상 복귀 후 컨테이너의 `ackAfterHandle` 동작은 구분됩니다.

이번 범위에서는 오류 record를 성공 처리하지 않고 **소비 중단과 원인 노출 후 복구·재시작**하는 정책도 충분합니다. 무한한 빠른 재시도는 장애를 증폭할 수 있습니다. DLQ를 선택한다면 그곳으로 옮긴 사실과 업무 완료를 구분하고 이후 처리를 정해야 합니다.

## 🔬 재전달을 실제로 관찰하기

중복 handler 호출 테스트는 DB 멱등성 확인에 유용하지만 Kafka 재전달을 증명하지는 않습니다. 실제 broker에 남은 같은 record를 **같은 group의 새 consumer가 다시 읽는지** 확인해야 합니다.

1. 대상 record의 실제 topic·partition·offset `n`을 producer 결과에서 얻습니다.
2. 첫 consumer가 구매 활동을 DB에 commit합니다.
3. target offset을 commit하지 않고 consumer를 종료합니다.
4. 같은 group의 새 consumer가 같은 위치를 다시 읽습니다.
5. DB 효과는 늘지 않고, 완료 뒤 committed offset이 `n + 1`로 진행합니다.

`position`이 증가한 것과 committed offset이 증가한 것은 다릅니다. 종료 동작도 사용한 API 계약을 확인합니다. 자동 commit을 끄고 미리 요청한 commit이나 종료 시 commit하는 사용자 callback이 없는 통제 consumer를 사용하면, OS 강제 종료 없이도 이 구간을 관찰할 수 있습니다.

이 실험은 **DB 효과 뒤 offset 미커밋 상태에서의 재전달**을 증명합니다. 모든 OS 장애·broker 장애·네트워크 분할을 시험했다는 뜻은 아닙니다.
