## 💻 Implementation Quest

> **기존 상품 조회의 병목을 줄이고, 변경·캐시 장애 뒤에도 같은 업무 결과를 반환합니다.**
>

2·3주차의 상품·브랜드·좋아요 조회와 관리자 변경, 주문 구현에서 이어갑니다. Product 모델이나 조회 Controller를 별도로 다시 만들지 않습니다. **조회 SQL·인덱스 개선과 한 조회 경로의 Redis cache-aside**를 구현합니다.

### 📐 1. 기준선과 설계

기존 설계 문서에 다음 항목을 짧게 추가합니다.

| 항목 | 정할 것 |
| --- | --- |
| 조회 계약 | 브랜드 필터, `latest/price_asc/likes_desc`, 기존 페이지·동점 정렬·오류·응답 필드 |
| 측정 대상 | 브랜드 필터+가격순 목록 하나, 요청당 SQL 수와 좋아요 조회 비용 |
| 캐시 범위 | 목록 또는 상세의 공통 조회 한 경로, 재사용할 필드와 제외할 사용자별 정보 |
| 변경 책임 | 해당 응답을 바꾸는 모든 기존 쓰기 경로, TX와 캐시 갱신·무효화 경계 |
| 장애 계약 | Redis 오류의 제한된 대기·DB 우회, 표시 데이터의 허용 신선도·복구 조건 |

AI에 실제 SQL·계획·요청당 SQL 수를 주고 병목과 대안을 비교하게 합니다. 기존 조건을 빼서 빨라지는 제안, 개인화 필드를 공용 키에 저장하는 제안, TTL만으로 변경 직후 최신성을 주장하는 제안은 수정합니다.

### 🧪 2. 기존 조회의 SQL·인덱스 개선

1. 격리된 실습 DB에 **상품 10,000개 이상**과 실제 모델에 필요한 브랜드·좋아요·필수 값을 준비합니다. 같은 seed를 다시 만들 수 있게 하고, 브랜드·가격·좋아요 수가 한 값에만 몰리지 않게 합니다.
2. 브랜드 필터+`price_asc`의 기존 첫 페이지 요청을 고정합니다. 실제 페이지 파라미터·기본값·페이지 크기를 적습니다. 새 `limit` 계약으로 교체하지 않습니다.
3. 캐시 없이 응답·SQL 수·`EXPLAIN`·`EXPLAIN ANALYZE`·반복 지연 시간을 기록합니다.
4. 실제 삭제·브랜드 노출 조건, 필터·정렬·조회 열에 맞는 인덱스 또는 쿼리 개선을 적용하고 같은 입력으로 비교합니다.
5. 좋아요 수를 상품마다 반복 조회한다면 목록 단위 집계·조회로 줄입니다. `likes_desc`는 전체 후보에서 정렬한 뒤 페이지를 선택해야 합니다.

**남길 비교**: 사용 key·접근 경로, 예상/실제 rows·loops·정렬 단계, 요청당 SQL 수, 준비 실행·측정 표본 수와 지연 분포. 특정 index 이름·`Using index` 문자열·몇 배 향상 수치를 정답으로 고정하지 않습니다.

**결과 비교**: 같은 seed에서 정렬된 ID·가격·좋아요 수와 페이지 정보를 비교합니다. 체크섬을 쓰면 직렬화 필드·순서를 고정하고 불일치한 실제 값을 확인합니다. 인덱스 전후 결과가 바뀌면 성능 개선으로 세지 않습니다.

- 공통 · 작은 재현 seed의 구성 예시

  다음은 기존 모델에 맞춰 fixture를 만들 때 사용할 분포 예시입니다. 제공된 SQL 파일이나 실제 스키마 이름이 아닙니다. 외래 키·필수 이름·재고·삭제 상태·좋아요 관계는 자신의 모델에서 함께 준비합니다.

    ```
    상품 순번 i = 1..10,000
    브랜드 순번 = (i % 100) + 1
    가격 = ((i * 37) % 100000) + 100
    전체 상품 count = 10,000 / price 합계 = 472,685,000
    브랜드 순번 7: count = 100 / price 합계 = 4,647,200
    ```

  순번은 생성한 실제 ID와 매핑합니다. 서로 다른 사용자–상품 좋아요 관계를 재현 가능하게 넣고, 0개·동점·인기 상품을 포함합니다. 가격순은 동점이 생기는 작은 별도 자료도 확인합니다.


인덱스 SQL·seed는 저장소에 남기되 이미 있는 migration·fixture 방식을 활용합니다. 성능 비교를 위해 공유 DB의 데이터나 다른 과제의 인덱스를 삭제하지 않습니다.

### 🚄 3. 한 조회 경로에 cache-aside 연결

선택한 목록 또는 상세의 공통 조회에 Redis 캐시를 붙입니다.

- **miss**: DB의 올바른 결과를 읽어 유효 시간과 함께 저장합니다.
- **hit**: 같은 조회 조건의 응답을 반환하고 비싼 원본 쿼리·집계 호출을 줄입니다.
- **키**: 필터·정렬·페이지·크기·응답 형식을 구분합니다. 개인별 필드는 공용 캐시에서 제외하거나 실제 사용자 경계를 분리합니다.
- **변경**: 가격 수정만 새 서비스로 우회하지 말고 기존 관리자 API에 연결합니다. 상품 생성·수정·삭제, 브랜드 변경·일괄 삭제, 좋아요·재고 등 캐시 내용에 영향을 주는 경로를 빠뜨리지 않습니다.
- **보존**: 삭제 대상·다른 사용자 정보가 캐시를 통해 노출되지 않아야 합니다. 주문 확정은 기존 DB의 주문·상품·재고·포인트 규칙을 사용합니다.

**장애·동시 채움이 없는 정상 변경 완료 뒤 시작한 순차 조회는 변경된 결과를 반환**해야 합니다. 변경이 rollback되면 존재하지 않는 새 결과를 게시하지 않습니다. DB 변경과 Redis 삭제 사이의 실패·늦은 재삽입은 별도 장면으로 재현하고, 표시 데이터에 허용할 신선도와 복구 정책을 정합니다. `@Transactional + cache.delete` 또는 TTL만으로 모든 경쟁·장애에서 최신성을 보장한다고 하지 않습니다.

예를 들어 장애 중 상품 설명·표시 가격의 일시적 오래된 값을 허용한다면 대상 필드, 만료·무효화 재처리 또는 원본 우회 조건, 복구 완료 판정을 적고 그 정책을 테스트합니다. 정상 순차 조회의 조건과 장애 정책을 섞지 않으며, 단순 TTL로 모든 요청에 적용되는 전역 시간 상한을 주장하지 않습니다.

**완화하지 않는 기존 계약**: 2·3주차에서 삭제 상품은 고객 조회·새 주문에서 제외했고 자신의 좋아요·주문·포인트만 다뤘습니다. 이 비노출·소유권과 주문 금액·재고·포인트 판단은 표시 신선도 선택의 대상이 아닙니다. 캐시 payload를 필요한 공통 부분으로 줄이고 민감한 필드는 원본에서 합성하거나, 삭제·접근 가능 여부의 권위 확인을 유지합니다. 이 확인의 비용도 hit 측정에 포함합니다.

- 설계 예시 · 권위 있는 조회 revision으로 오래된 캐시 구분하기

  한 가지 가능한 방법이며 이 구조를 반드시 복제할 필요는 없습니다.

    1. 선택한 공통 조회의 결과가 바뀌는 DB 트랜잭션에서 단조 증가하는 revision도 함께 변경합니다.
    2. 독자는 DB의 현재 revision을 확인하고 그 revision에 대응하는 캐시만 읽습니다. 현재 revision 자체를 검증 없이 Redis에 캐시하지 않습니다.
    3. miss에서 결과와 revision은 같은 일관된 DB 읽기 경계로 얻습니다. 이전 결과를 새 revision의 키에 저장하지 않습니다.
    4. 늦게 끝난 이전 조회가 예전 revision의 키를 채워도 이후 독자는 새 revision의 키를 사용합니다. TTL은 옛 키의 정리 수단입니다.
    5. 삭제·브랜드·좋아요 등 선택한 payload를 바꾸는 모든 쓰기가 revision에 참여해야 합니다. 고정된 잠금 순서와 기존 rollback 규칙을 유지합니다.

  이 방식도 hit에서 DB 조회가 하나 남고 공통 revision 행의 쓰기 경합이 생깁니다. 캐시로 줄인 비싼 목록·집계 쿼리와 새 비용을 따로 측정합니다. 이미 시작한 조회와 변경이 겹친 경우는 그 조회가 읽은 DB 시점의 결과로 설명하고, 변경 완료 후 새로 시작한 요청과 구분합니다.


revision 방식은 장애 중에도 강한 표시 최신성이 필요한 경우의 선택지입니다. 다른 방법은 정한 표시 신선도·복구 정책과 위의 필수 계약을 확인합니다. 모든 조회를 항상 DB로 수행한 뒤 사용하지 않는 캐시를 채우는 것은 cache hit 개선이 아닙니다. 반대로 DB 호출 0회만을 위해 기존 비노출·소유권·주문 계약을 포기하지 않습니다.

### 🛠 4. 변경·실패·복구 확인

실제 애플리케이션·MySQL·Redis가 연결된 테스트로 아래 경계를 확인합니다. 캐시 동작을 전부 Mock으로 대체한 테스트만으로 마무리하지 않습니다.

| 장면 | 확인할 결과 |
| --- | --- |
| 동일 입력의 DB-only·miss·hit | 상품·정렬·페이지 결과 일치, hit에서 선택한 비싼 DB 조회 감소 |
| 관리자 가격 수정 commit 후 재조회 | 새 가격과 필요한 목록 순서 반영, 과거 주문 금액 유지 |
| 캐시에 담긴 상품·브랜드 일괄 삭제 | 해당 상품이 고객 결과에서 제외, 다른 브랜드와 과거 주문 유지 |
| 캐시 내용에 영향을 주는 나머지 쓰기 | 영향 범위에 맞게 조회 반영. 좋아요 수를 담았다면 등록·취소 포함 |
| DB 변경 rollback | 변경 전 결과 유지, 새 데이터로 오인할 캐시 없음 |
| commit 뒤 캐시 무효화 실패 | DB의 실제 commit 사실 유지, 허용한 표시 신선도 정책과 복구 뒤 원본 일치 확인 |
| 이전 조회의 늦은 캐시 채움 | 오래된 재삽입을 결정적으로 재현하고 선택한 방지·만료·복구 정책의 결과 확인 |
| Redis 중단·재시작 | 제한된 대기 뒤 DB 결과 반환, 재시작 뒤 정확한 캐시 재채움 |

무효화 실패와 늦은 채움은 테스트 훅·래치로 순서를 통제합니다. 예를 들어 **이전 DB 결과 읽기 → 관리자 변경 commit → 이전 결과 캐시 저장 → 새 조회** 순서를 만들어 확인합니다. 이후 선택한 정책이 오래된 표시를 허용하는 조건과 복구 완료 조건을 실제로 만족하는지 검증합니다. 삭제·다른 사용자 정보·주문 판단은 이 장면에서도 보호합니다. 기다림은 유한한 timeout을 두고 모든 worker를 정리합니다.

캐시 실패 때 DB가 정상이고 통제한 부하를 감당하는 조건에서 상품 조회는 기존 정상 응답을 반환합니다. DB까지 실패했다면 빈 목록·가격 0으로 감추지 말고 기존 오류 계약을 따릅니다. Redis 장애만으로 주문의 결제·재고 처리를 우회하지 않습니다.

- 공통 · 기존 Redis 설정에서 읽을 파일
    - Java: `modules/redis/src/main/java/com/loopers/config/redis/RedisConfig.java`
    - Kotlin: `modules/redis/src/main/kotlin/com/loopers/config/redis/RedisConfig.kt`
    - 공통: `modules/redis/src/main/resources/redis.yml`, `docker/infra-compose.yml`

  기본 연결은 `REPLICA_PREFERRED`이고 별도 master 연결이 있습니다. 사용하는 template·연결·직렬화와 대기 시간을 확인합니다. 최신성 실험에서 어떤 endpoint를 읽었는지 적고, replica lag를 애플리케이션 최신성 보장으로 오인하지 않습니다.

- 공통 · Redis 장애 실험의 준비와 정리

  테스트가 실제 연결하는 Redis를 대상으로 합니다. Testcontainer를 사용하면 해당 컨테이너를 중단·재시작하고, Compose를 사용하면 연결 설정이 그 서비스들을 가리키는지 확인합니다. 둘을 혼용해 엉뚱한 Redis를 중단하지 않습니다.

    1. cache miss→hit로 원본 호출 감소를 확인합니다.
    2. 테스트의 모든 읽기 endpoint를 중단합니다. master와 replica를 쓴다면 둘 다 중단합니다.
    3. DB 정상 상태에서 조회 응답·대기 시간·캐시 오류를 확인합니다.
    4. 동일 Redis를 다시 시작하고 연결 가능 여부와 새 조회·재채움을 확인합니다.
    5. 자신이 시작한 실험 자원만 종료·정리합니다.

  장애 시작 전에 복구 절차를 준비합니다. 공유 Redis에 `FLUSHALL`을 실행하거나 다른 작업의 컨테이너를 중단하지 않습니다.


    ```bash
    # Java: 기존 Checkstyle 설정 포함
    ./gradlew :apps:commerce-api:check
    
    # Kotlin
    ./gradlew :apps:commerce-api:ktlintCheck :apps:commerce-api:check
    ```

  선택된 테스트의 실행 건수·실패·skip·종료 결과를 확인합니다. 테스트 0개나 연결 실패를 성능 개선의 성공으로 세지 않습니다.


**제출**: 변경 코드·테스트, 재현 seed·인덱스 변경, 실행 계획·결과 비교, 갱신한 설계 문서와 기술 글. PR에는 병목·선택한 방법·정확성 및 장애 결과와 측정 환경·표본의 한계를 짧게 적습니다.

**선택 심화**: 좋아요 카운터 비정규화, 목록·상세 모두 캐시, 데이터 쏠림·깊은 페이지 비교, stampede 완화. 추가한 구조가 있다면 중복·동시 변경과 정합성도 확인합니다. 이벤트·배치 기반 집계 시스템을 이번 주 필수로 만들지는 않습니다.

## ✍️ Technical Writing Quest

> **측정 결과가 설계 선택을 어떻게 바꿨는지 설명합니다.**
>

자신의 조회·캐시 구현에서 의미 있었던 주제 하나를 저장소 Markdown·Issue·블로그로 씁니다.

### 💭 주제 예시

- 인덱스가 있는데도 느렸던 SQL의 실제 병목
- 복합 인덱스의 열 순서를 결정한 이유
- 좋아요 수의 N+1과 전체 정렬을 구분한 과정
- 비정규화를 선택하거나 미룬 이유
- 관리자 변경과 캐시 무효화 사이에서 발견한 실패
- 캐시 hit에 DB 확인이 남는 설계의 이득과 비용
- Redis 장애 후 원본 조회가 늘어난 결과
- AI의 최적화 제안에서 발견한 계약 변화
- 그 밖에 이번 학습에서 설명하고 싶은 주제

### 📝 작성 기준

- **상황·예시**: 실제 SQL·계획·작은 비교 결과 중 하나로 문제를 보여 줍니다.
- **개념**: 인덱스·집계·캐시·정합성 중 핵심 개념을 자신의 말로 설명합니다.
- **판단·이유**: 선택한 방법, 줄인 비용, 새로 생긴 비용과 확인하지 않은 한계를 구분합니다.
