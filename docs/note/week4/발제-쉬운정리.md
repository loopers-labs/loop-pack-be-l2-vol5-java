# 4주차 발제 쉬운 정리

> 원문: `발제.md`. 백엔드 입문자용으로 풀어 쓴 요약입니다. 기술 용어는 원어를 유지하고, 처음 나올 때 한 줄 설명을 붙였습니다.

## 1. 한 줄 요약 / 이번 주 핵심 질문

**한 줄 요약**: 같은 결과를 더 적은 비용으로 읽고, 복사본(캐시)이 오래됐을 때 어떻게 동작할지까지 설계한다.

**핵심 질문**
1. 느리다는 말을 숫자로 어떻게 증명하나? (측정)
2. 인덱스는 무엇을 줄여 주고, 어떻게 확인하나?
3. 조회 구조(N+1, 좋아요 집계, 페이지)에서 숨은 비용은 무엇인가?
4. 캐시는 무엇을 재사용하고, 언제 낡은 값이 되나?
5. 관리자 변경이나 Redis 장애가 나도 정확성과 가용성을 지킬 수 있나?

## 2. 섹션별 핵심 개념

### 2-1. 측정: 먼저 "어디가 느린지" 나눠 본다

Redis부터 붙이지 않습니다. 한 요청이 실제로 하는 일을 쪼개 봅니다.

| 관찰 | 가능한 원인 | 먼저 확인할 것 |
| --- | --- | --- |
| SQL 하나가 오래 걸림 | 많은 행 탐색, 정렬·집계 | 그 SQL의 실행 계획과 실제 행 수 |
| SQL은 짧은데 수십 개 실행 | N+1, 반복 조회 | 요청 1회당 SQL 수 |
| DB는 빠른데 HTTP가 느림 | 연결 대기, 외부 호출, 직렬화 | 구간별 시간, 연결 풀 |
| 같은 집계를 반복 수행 | 재사용 가능한 계산 | 요청 분포, 허용 가능한 신선도 |
| 캐시 hit인데도 느림 | Redis 대기, 큰 payload, 네트워크 | 캐시 시간·크기, DB 호출 여부 |

- **latency(지연 시간)**: 요청 하나가 끝나는 시간. 식당에서 "내 주문이 나오기까지" 걸린 시간.
- **throughput(처리량)**: 일정 시간에 처리한 요청 수. "한 시간에 몇 테이블을 소화했나".
- 평균 하나만 보면 일부 요청의 긴 대기를 놓칩니다.

**비교 가능한 기준선 만들기**
1. 기존 API의 필터·정렬·페이지·응답 필드를 고정한다.
2. 같은 데이터, 같은 DB 버전, 같은 인덱스 상태를 쓴다.
3. 준비 실행과 측정 실행을 구분하고, 표본 수와 동시 요청 수를 적는다.
4. SQL 수, 실행 계획, 결과, 지연을 함께 비교한다.

고정하지 않으면 비교가 깨지는 조건: 데이터 양과 분포, 페이지 위치와 정렬, DB·앱 준비 상태(버퍼 풀, 연결 생성), 응답 필드와 삭제 조건, 캐시 hit/miss(경로가 달라 따로 측정).

> **주의**: 빨라졌다는 주장에는 "같은 결과를 반환한다"는 전제가 있습니다.
> - 정렬된 상품 ID·가격·좋아요 수와 페이지 정보를 직접 비교합니다. 결과가 크면 직렬화 형식을 고정한 체크섬을 보조로 씁니다.
> - JSON 필드 순서나 시간 필드 차이를 업무 결과 차이로 오인하지 않습니다. 체크섬이 다르면 실제로 다른 행·필드를 찾아야 합니다.
> - 측정 데이터는 실제 스키마의 필수 필드·관계를 지켜야 합니다. 실험용 별도 Product 모델을 만들면, 개선한 SQL이 실제 API에서 쓰이지 않을 수 있습니다.

### 2-2. 인덱스

**인덱스**: 책 뒤의 "찾아보기"처럼, 검색 키를 정렬해 두고 필요한 행을 빨리 찾게 하는 보조 자료구조(InnoDB는 B-Tree 계열). 대신 쓰기(삽입·수정·삭제) 때 같이 관리해야 해서 저장 공간과 쓰기 비용이 늘어납니다.

기준 쿼리(열 순서를 설명하는 축약 예시. 실제 쿼리는 기존 삭제·노출 조건을 유지):

```sql
SELECT id, brand_id, name, price
FROM products
WHERE brand_id = 7
ORDER BY price ASC, id ASC
LIMIT 20;
```

**후보 인덱스 비교** (두 개를 무조건 다 만들라는 뜻이 아니라 비교용 예시입니다. 겹치는 인덱스가 이미 있으면 중복 비용을 검토)

| 후보 | 기대 역할 | 남는 비용 |
| --- | --- | --- |
| `(brand_id)` | 브랜드에 해당하는 행 탐색 | 가격 정렬, 다른 열 읽기 |
| `(brand_id, price, id)` | 브랜드 범위 안에서 가격·ID 순으로 읽기 | name 등 인덱스 밖 열 읽기 |
| `(price, brand_id)` | 가격 순 탐색에 쓰일 가능성 | 특정 브랜드만 찾으려면 많은 행을 건너뜀 |

**복합 인덱스**: 여러 열을 묶은 인덱스. 전화번호부가 "성 → 이름" 순으로 정렬된 것과 같습니다. `(brand_id, price)`는 브랜드로 묶고 그 안에서 가격순입니다. 성을 모르고 이름만으로 찾기 어려운 것과 같은 이치로, 가격만으로 찾는 요청은 같은 이득을 못 얻습니다.

- 왼쪽 열부터 이어지는 조건이 인덱스 탐색에 잘 맞습니다.
- `WHERE a=? AND b=?`를 `b=? AND a=?`로 적어도 인덱스 열 순서는 바뀌지 않습니다.
- 앞쪽 열의 범위 조건은 뒤쪽 열의 정렬·탐색 기여를 제한할 수 있습니다.
- `ASC/DESC`가 섞이면 인덱스 방향과 스캔 방향을 함께 확인합니다.
- 최종 선택은 통계·분포·조회 열과 옵티마이저의 비용 판단에 달려 있습니다.
- **cardinality(카디널리티)**: 서로 다른 값의 개수. **selectivity(선택도)**: 조건이 행을 얼마나 적게 남기는가. "고유값 많은 열을 앞에" 라는 공식은 없고, 쿼리의 조건 조합을 기준으로 판단합니다.

**Covering index**: 쿼리에 필요한 값을 인덱스만 읽고 얻는 경우. 가게에서 진열대(인덱스)만 보고 끝나고, 창고(테이블)까지 안 가도 되는 상태. `(brand_id, price, id)`가 있어도 `name`까지 반환하면 자동으로 covering이 아닙니다.

**추가 정렬**: `Using filesort`는 인덱스 순서만으로 정렬을 못 해서 따로 정렬한다는 뜻입니다. 이름에 file이 있어도 꼭 디스크 정렬은 아닙니다. 또 추가 정렬이 항상 나쁜 것도 아닙니다. 좁힌 몇 행을 정렬하는 비용이 큰 인덱스를 계속 유지하는 비용보다 작을 수 있습니다.

### 2-3. EXPLAIN 읽는 법

- `EXPLAIN`: 옵티마이저가 "이렇게 하겠다"고 예상한 계획.
- `EXPLAIN ANALYZE`(MySQL 8.0.18 이후): 문장을 **실제로 실행**해 예상과 실제(반복 수, 행 수, 시간)를 비교. 격리된 실습 데이터의 SELECT에만 사용합니다.

```sql
SELECT VERSION();
ANALYZE TABLE products;   -- 통계 갱신
EXPLAIN
SELECT id, brand_id, name, price FROM products
WHERE brand_id = 7 ORDER BY price, id LIMIT 20;

EXPLAIN ANALYZE
SELECT id, brand_id, name, price FROM products
WHERE brand_id = 7 ORDER BY price, id LIMIT 20;
```

실제 테이블·열·삭제 조건에 맞춰 쓰고, API가 실행하는 SQL과 따로 노는 축약 쿼리만 튜닝하지 않습니다.

| 읽을 항목 | 질문 |
| --- | --- |
| 접근 경로·사용 key | 전체 탐색인가, 인덱스 탐색인가? |
| 예상 rows vs 실제 rows | 분포를 잘 추정했는가? |
| loops | 적은 행을 아주 많이 반복해서 읽지 않는가? |
| filter·sort·aggregate | 어디서 행을 줄이고 정렬·집계하는가? |
| actual time | 하위 작업 포함 시간인가, 반복당 평균인가? |

- 전통 표 형식(`key/type/Extra`)과 `ANALYZE`의 트리 형식은 표현이 다릅니다. 트리에 없는 열을 억지로 찾거나, 모든 노드 시간을 합해 HTTP 시간이라고 하지 않습니다.
- `Using index`는 "인덱스만으로 값을 읽었다"는 뜻이지, "인덱스를 썼다"와 같지 않습니다.
- 예상과 실제 rows가 크게 다르면 통계와 데이터 쏠림을 봅니다. 인덱스가 안 골라졌다고 바로 힌트로 강제하지 말고, **실제로 읽는 양과 비용이 줄었는지**를 확인합니다.

### 2-4. 조회 구조: N+1, 좋아요 집계, 페이지네이션

**N+1**: 목록 1번 조회 뒤, 항목 수(N)에 비례해 추가 쿼리가 붙는 현상. 식당에서 메뉴 20개를 시키고 계산을 20번 따로 하는 것과 같습니다.

```
목록 1회
  상품 20개 조회 1회
  각 상품의 좋아요 COUNT 20회
  각 상품의 브랜드 조회가 추가될 수도 있음
```

각 COUNT에 인덱스가 있어도 네트워크 왕복과 반복 호출 비용은 남습니다.

**좋아요 집계: 방법을 바꾸면 책임도 옮겨진다**

| 방법 | 얻는 것 | 주의할 것 |
| --- | --- | --- |
| 목록 ID를 모아 한 번에 집계 | 상품별 반복 COUNT 감소 | 페이지를 먼저 정한 뒤 집계하면 좋아요순 전체 정렬에는 못 씀 |
| DB에서 집계·정렬 후 페이지 선택 | 전체 후보의 좋아요순 의미 유지 | JOIN·GROUP BY·정렬 비용 |
| 좋아요 수를 별도 열로 유지 | 읽을 때 반복 집계 감소 | 등록·취소·중복 요청·동시 갱신과 카운터 정합성 |
| 별도 조회용 집계 결과 | 읽기 목적에 맞춘 구조 | 갱신 경계·지연·복구 책임 |

- **비정규화**: 계산·결합한 값을 읽기 편하게 중복 저장하는 선택(계산해 둔 점수를 따로 적어 두는 메모). 좋아요 관계와 카운터를 같은 트랜잭션에서 갱신할 수도 있으므로 비정규화가 곧 지연 반영은 아닙니다. 반대로 JOIN을 썼다고 잘못된 격리·중복 관계까지 해결되지는 않습니다.
- 좋아요가 **진짜로 추가됐을 때만 +1, 실제 취소됐을 때만 -1**. 재요청마다 카운터를 바꾸면 관계 수와 어긋납니다. 3주차의 트랜잭션·동시성 판단이 여기에도 적용됩니다.
- 쿼리 조정으로 충분하면 카운터나 조회용 테이블을 추가할 이유가 없습니다. 별도 이벤트·배치 동기화를 이번 조회 최적화의 선행조건으로 만들지 않습니다.

**페이지네이션: 빨리 읽기 vs 계약 바꾸기**
- `OFFSET`은 앞의 결과를 건너뛰는 비용이 있어 깊은 페이지가 느립니다.
- **커서 방식**(마지막 `(price, id)` 뒤에서 시작)은 대안이지만, 임의 페이지 이동이 안 되고 응답 계약이 달라집니다.
- 동점에서 결과가 흔들리지 않도록 기존 동점 정렬 기준을 유지합니다.
- 좋아요순 전체 정렬을 "20개 먼저 읽고 애플리케이션에서 정렬"로 바꾸지 않습니다.
- JOIN으로 행이 늘 때 상품 중복·페이지 크기·전체 건수가 달라지는지 확인합니다.
- 비용 개선을 이유로 페이지 번호 API를 설명 없이 커서 API로 교체하지 않습니다.

### 2-5. 캐시: cache-aside, 키, TTL, 무효화

**캐시**: 원본에서 읽거나 계산한 결과를 다시 쓰려고 저장해 둔 복사본. 자주 쓰는 책을 책상 위에 꺼내 둔 것과 같습니다.

**Cache-aside**: 앱이 먼저 캐시를 보고, 없으면 DB에서 읽어 캐시에 채웁니다.

```
조회 → 캐시 확인
        ├─ hit  → 저장된 복사본 반환
        └─ miss → DB 조회 → 캐시 저장 → 반환
```

캐시의 가치는 "Redis를 썼다"가 아니라 **비싼 읽기를 얼마나 줄였는가**입니다. 재사용이 거의 없는 페이지까지 다 저장하면 키 수와 무효화 비용만 늡니다.

**키는 "응답을 구분하는 조건"**

```
예시: products:v1:brand=7:sort=price_asc:page=0:size=20
```

키 구성 예시이며, 실제 페이지 시작값·파라미터는 기존 API를 따릅니다.

| 빠진 구분 | 생길 수 있는 오류 |
| --- | --- |
| 브랜드·필터 | 다른 조건의 목록 반환 |
| 정렬·페이지·크기 | 같은 키에 다른 순서·구간 저장 |
| 응답 형식 버전 | 배포 전후 직렬화 계약 충돌 |
| 사용자별 정보 | 다른 사용자의 좋아요 여부·개인 정보 반환 |

- 공통 상품 정보와 "내가 좋아요했는지"는 재사용 범위가 다릅니다. 사용자별 필드를 공용 캐시에 섞지 않거나 별도로 합성합니다.
- 키에 `v1`을 붙이는 것만으로 DB 변경을 감지하지는 못합니다.

**TTL과 무효화**
- **TTL**: 캐시 항목의 유통기한. **invalidation(무효화)**: 못 믿게 된 복사본을 지우거나 쓰지 않게 하는 작업.

| 방식 | 효과 | 한계 |
| --- | --- | --- |
| TTL | 오래된 항목이 무기한 남는 것을 제한 | 변경 즉시 최신을 보장하지 않음 |
| 변경 후 삭제 | 다음 miss에서 원본 재조회 | 삭제 실패, 경쟁 중 재삽입 가능 |
| 새 버전의 키 | 데이터 세대 분리 | 현재 버전을 어디서 읽는지에 따라 같은 불일치가 남음 |
| 쓰면서 캐시 갱신 | 정상 경로의 후속 조회 가속 | DB·Redis 간 부분 실패와 순서 문제 |

- 읽을 때마다 TTL을 연장하면 자주 읽히는 오래된 값이 계속 남을 수 있습니다. Spring Data Redis의 TTL과 TTI(time-to-idle)는 다른 정책이므로, 이번 설계에서 무엇을 쓰는지 확인합니다.
- TTL 30초라고 "변경 후 30초 안에 모든 요청이 최신"이라고 단정할 수 없습니다. 오래된 DB 읽기가 늦게 끝나 새 TTL로 캐시에 들어가거나, 지연된 복제본에서 다시 채워질 수 있습니다. **만료 기준, 원본 읽기, 진행 중인 요청**까지 알아야 상한을 설명할 수 있습니다.

**Spring에서의 구현 선택**

| 방법 | 적합한 경우 | 직접 확인할 책임 |
| --- | --- | --- |
| `@Cacheable / @CacheEvict` | 단순한 메서드 단위 캐시 | key, CacheManager, TTL 설정, 프록시·오류 처리·TX 순서 |
| `RedisTemplate` | 실패 분기와 키·직렬화를 명시할 때 | 조회·저장·만료·삭제, 타입 변환, 타임아웃 |

- `@Cacheable`은 기본 프록시 방식이라 같은 객체 내부 호출에는 적용되지 않을 수 있습니다.
- `@CacheEvict`의 메서드 실행 후 삭제가 항상 DB commit 이후라는 뜻이 아니므로 트랜잭션과 캐시 설정의 실제 경계를 확인합니다.

### 2-6. 관리자 변경과 캐시 불일치 (commit 뒤 삭제의 실패 창)

관리자가 가격을 바꾸면 상세만이 아니라 가격순 목록의 구성·위치도 달라질 수 있습니다.

| 변경 | 캐시가 담았다면 검토할 결과 |
| --- | --- |
| 상품 가격·이름 변경 | 상세, 검색·정렬된 목록 |
| 상품 생성·삭제 | 목록 구성·전체 건수, 상세의 존재 여부 |
| 브랜드 변경·일괄 삭제 | 브랜드 정보, 연결 상품의 노출 |
| 좋아요 등록·취소 | 좋아요 수·정렬·사용자별 표시 |
| 재고 변경·주문 확정 | 응답에 포함한 재고 정보 |

- **캐시 범위를 작게 고르면 무효화 책임도 작아집니다.** 목록 전체 응답을 캐시했다면 관련 키 하나만 지우는 것으로 충분한지 검토합니다.
- 전용 캐시 영역을 통째로 비우는 방법은 작은 실습에서 가능하지만, 요청이 전부 miss가 되는 비용을 기록해야 합니다. 공유 Redis 전체를 비우는 것은 별개의 문제입니다.

**commit 뒤 삭제에도 남는 실패 창**

```
정상: DB 가격 12,000 commit → 캐시 삭제 성공 → 다음 조회 12,000
실패: DB 가격 12,000 commit → 캐시 삭제 timeout → 캐시에 10,000 잔존
경쟁: 조회 A가 DB 10,000 읽음 → 변경 commit·캐시 삭제 → A가 10,000 저장
```

- 삭제를 먼저 해도 commit 전에 다른 조회가 이전 DB 값을 채울 수 있습니다.
- `@Transactional` 하나나 한 메서드 안의 두 호출이 MySQL과 Redis를 원자적으로 만들지 않습니다.
- 3주차의 commit 경계를 이용해 **성공한 DB 변경 뒤** 무효화할 수 있지만, after-commit 실행도 외부 호출 실패를 없애지 못합니다. DB가 이미 commit됐다면 캐시 오류 때문에 "DB까지 rollback됐다"고 응답해서는 안 됩니다.

| 요구하는 신선도 | 필요한 판단 |
| --- | --- |
| 정상 변경 후 순차 조회가 최신 | 영향 캐시와 commit 이후 무효화 경로 확인 |
| 일시적 오래된 표시 허용 | 허용 필드·조건·복구·만료 정책 명시 |
| 오래된 값을 절대 쓰면 안 됨 | 원본 재확인, 권위 있는 버전 검증, 또는 캐시 대상 제외 |

- **주문 확정은 DB에 보존한 주문 금액과 기존 상품 상태·재고 규칙을 사용**합니다. 캐시의 오래된 값으로 구매를 확정하지 않습니다.
- 이번 최적화를 이유로 주문 단가의 기존 결정 시점을 바꾸거나, 삭제된 상품을 사용할 수 있게 되살리지 않습니다.
- 버전 방식을 택한다면 현재 버전은 업무 변경과 같은 권위 경계에서 바뀌어야 합니다. Redis의 `currentVersion` 포인터가 낡으면 새 키 전략에서도 예전 데이터를 읽습니다. DB에서 버전·사용 가능 여부를 확인하면 안전하지만 hit에도 DB 비용이 남으므로, 무엇을 줄였는지 정직하게 측정합니다.
- 원문 Redis 설정: 기본 연결은 `REPLICA_PREFERRED`, 별도 master 연결은 `MASTER`. 무효화 직후 replica의 옛 값을 읽을 수 있으니 순차 최신성 실험에서는 읽기 연결을 명시합니다. 연결 선택이 DB·Redis의 원자성을 대신하지는 않습니다.

### 2-7. Redis 장애 시 fallback과 stampede

**fallback**: 캐시가 죽었을 때 원본(DB)으로 우회하는 것. DB가 정상이고 실험 부하를 감당할 때 가능합니다. 캐시 오류를 빈 목록이나 가격 0으로 바꾸는 것은 우회가 아닙니다.

```java
public ProductView find(long productId) {
    try {
        var cached = cache.find(productId);
        if (cached.isPresent()) {
            return cached.get();
        }
    } catch (CacheUnavailableException e) {
        metrics.cacheReadFailure();   // 캐시 읽기 실패는 기록만 하고 DB로 진행
    }

    ProductView result = readRepository.find(productId);
    try {
        cache.save(productId, result);
    } catch (CacheUnavailableException e) {
        metrics.cacheWriteFailure();  // 캐시 쓰기 실패가 응답을 막지 않음
    }
    return result;
}
```

완성 구현이 아니라 경계 예시입니다(CachePort, ReadRepository, DTO, 오류 타입, 키, TTL은 실제 설계에서 정의). 전체를 `catch (Exception)`으로 감싸 빈 상품을 반환하면 DB 오류·존재하지 않는 상품·구현 결함까지 감춰집니다. 캐시 장애와 원본 조회 실패를 구분하세요. (원문에는 같은 흐름의 Kotlin 예시도 있습니다.)

**장애 대비 체크 포인트**
- 캐시 연결·명령의 대기 시간을 제한한다.
- miss와 Redis 오류를 구분해 관찰한다.
- DB 조회 오류를 정상 빈 결과로 숨기지 않는다.
- 복구 때 오래된 항목이 다시 쓰이는지 확인한다.
- 테스트가 실제로 연결한 endpoint를 중단한다. 별도 Testcontainer가 살아 있으면 Compose 중단은 그 테스트의 장애가 아니다.
- 캐시가 내려가면 hit로 끝나던 요청도 DB로 갑니다. 이로 인해 DB 연결 대기까지 늘면 기능적 fallback만으로는 부족합니다. 동시 요청 제한·부하 축소는 다음 판단이고, 이번에는 작은 통제 부하에서 우회와 결과를 먼저 확인합니다.

**Cache stampede**: 인기 항목의 캐시가 만료되는 순간 요청이 한꺼번에 DB로 몰리는 현상(문 열자마자 손님이 한꺼번에 계산대로 몰리는 장면). 대안은 요청 합치기, 만료 시점 분산 등입니다. 여러 서버에 걸친 분산 잠금까지 모든 캐시에 먼저 도입할 필요는 없습니다.

## 3. 자주 하는 오해 vs 올바른 이해

| 오해 | 올바른 이해 |
| --- | --- |
| 느리면 일단 Redis부터 붙인다 | 먼저 SQL 수·실행 계획·읽은 행으로 병목을 나눠 본다 |
| 평균 응답 시간만 보면 된다 | 평균은 일부 요청의 긴 대기를 가린다 |
| 빨라졌으면 성공이다 | 같은 결과를 반환한다는 전제가 있어야 한다 |
| 인덱스는 많을수록 좋다 | 쓰기 비용과 공간이 늘고, 겹치는 인덱스는 중복 비용이다 |
| 고유값 많은 열을 앞에 두면 된다 | 공식이 없다. 쿼리의 조건·정렬 조합과 실제 분포로 판단 |
| WHERE 조건 순서를 바꾸면 인덱스 순서도 바뀐다 | 인덱스 열 순서는 그대로다 |
| `Using index`는 인덱스를 썼다는 뜻 | 인덱스만으로 값을 읽었다는 뜻(covering) |
| `Using filesort`는 항상 디스크 정렬이고 실패다 | 꼭 디스크는 아니며, 작은 정렬은 오히려 이득일 수 있다 |
| 인덱스가 안 골라지면 힌트로 강제한다 | 먼저 실제 읽는 양과 비용이 줄었는지 확인한다 |
| 쿼리 하나의 시간을 다 합치면 HTTP 시간이다 | 노드 시간은 하위 작업 포함/반복당 평균일 수 있어 단순 합산 금지 |
| 20개 읽은 뒤 앱에서 정렬해도 좋아요순이다 | 전체 후보 기준 정렬이 아니라 의미가 달라진다 |
| OFFSET이 느리면 커서 API로 바꾸면 된다 | 임의 페이지 이동과 응답 계약이 바뀌므로 설명 없이 교체 금지 |
| 카운터/조회용 테이블/이벤트 동기화를 미리 만든다 | 쿼리 조정으로 충분하면 추가하지 않는다 |
| 캐시를 쓰면 무조건 빨라진다 | 재사용이 적으면 키·무효화 비용만 늘어난다 |
| 키에 `v1`을 붙이면 변경이 감지된다 | 버전 접두사는 DB 변경을 감지하지 못한다 |
| TTL 30초면 30초 안에 모두 최신이다 | 늦게 끝난 오래된 읽기나 지연 복제본이 다시 채울 수 있다 |
| `@Transactional`로 DB와 Redis가 원자적이다 | 원자적이지 않다. after-commit 삭제도 실패할 수 있다 |
| 캐시 삭제가 실패하면 전체를 rollback한다 | DB가 이미 commit됐다면 캐시 오류로 rollback 응답을 주지 않는다 |
| `@Cacheable`은 어디서나 동작한다 | 프록시 방식이라 같은 객체 내부 호출은 가로채지 못한다 |
| 캐시 값으로 주문 금액을 확정해도 된다 | 주문은 DB에 보존한 금액과 기존 상품·재고 규칙을 쓴다 |
| Redis 장애 시 `catch (Exception)`으로 빈 값 반환 | DB 오류까지 감춰진다. 캐시 장애만 분리해 DB로 우회 |
| fallback만 있으면 장애 대비가 끝난다 | 모든 요청이 DB로 몰려 연결 대기가 늘 수 있다 |

## 4. 최종 체크리스트: "무엇을 개선했다고 말할 것인가"

| 장면 | 확인할 결과 |
| --- | --- |
| 인덱스 전후 | 같은 업무 결과, 계획·읽은 행·시간의 변화 |
| cache miss/hit | 동일 입력에서 응답 일치, 실제 원본 호출 감소 |
| 정상 관리자 변경 | 선택한 캐시와 영향 범위의 최신 값 반영 |
| 무효화 실패·경쟁 | 오래된 값의 재현, 허용 범위 또는 방지 장치, 복구 결과 |
| Redis 장애·재시작 | 제한된 대기와 DB 우회, 복구 후 정확한 재채움 |

**작업 전 점검**
- [ ] 기존 필터·정렬·페이지·응답 필드와 삭제·노출 조건 등 보존할 계약을 먼저 적었다.
- [ ] 관찰한 병목(요청당 SQL 수, 실행 계획)에서 시작했고, "Redis를 붙여 줘"로 시작하지 않았다.
- [ ] 개선 전후가 같은 데이터·조건·결과인지 비교했다(필요하면 체크섬 보조).
- [ ] 불필요한 구현(카운터, 조회용 테이블, 이벤트·배치 동기화, 분산 잠금)을 선행하지 않았다.
- [ ] 쿼리 개선만으로 충분했는지, 캐시를 추가해 운영 책임이 얼마나 늘었는지 함께 기록했다.
- [ ] 작은 변경을 구현하고, 관련 테스트·기존 lint·ArchUnit으로 확인했다.

**AI에게 요청할 때 (원문 검토 예시)**
> "브랜드 필터·가격순·기존 페이지 계약을 유지한다. 이 SQL 계획과 요청당 SQL 수에서 먼저 줄일 비용은 무엇인가? 캐시한다면 관리자 변경·브랜드 삭제·다른 사용자 조회에서 어떤 반례가 생기는가?"
