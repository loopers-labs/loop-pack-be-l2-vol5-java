# 💻 Implementation Quest

> **상품 조회 성능을 개선하고, 데이터 변경과 캐시 장애에도 기존 업무 규칙을 지킨다.**

2·3주차에 구현한 상품·브랜드·좋아요 조회, 관리자 변경, 주문 기능을 개선합니다. 새로운 Product 모델이나 조회 Controller를 만들지 않고, **기존 조회 SQL·인덱스를 최적화하고 한 조회 경로에 Redis Cache-Aside를 적용**합니다.

## 🎯 0. 완료 기준

과제를 시작하기 전에 다음 목표를 확인합니다.

- [ ] 기존 API의 필터·정렬·페이지·응답·오류 계약을 유지한다.
- [ ] SQL·인덱스 개선 전후의 실행 계획, 조회 비용, 응답 시간을 비교한다.
- [ ] 한 조회 경로에 캐시를 적용하고, 캐시 hit에서 비싼 원본 조회를 줄인다.
- [ ] 데이터 변경·롤백·캐시 실패·Redis 장애 상황에서 정합성과 복구 정책을 검증한다.
- [ ] 코드·테스트·측정 결과·설계 문서·기술 글을 제출한다.

## 1. 기준선과 설계

기존 설계 문서에 아래 항목을 간단히 정리합니다.

| 항목 | 확인할 내용 |
|---|---|
| 조회 계약 | 브랜드 필터, `latest/price_asc/likes_desc`, 페이지·동점 정렬·오류·응답 필드 |
| 측정 대상 | 브랜드 필터 + 가격순 목록, 요청당 SQL 수, 좋아요 조회 비용 |
| 캐시 범위 | 목록 또는 상세 조회 중 하나, 캐시할 필드와 제외할 사용자별 정보 |
| 변경 경로 | 캐시 결과에 영향을 주는 모든 쓰기 경로와 트랜잭션 경계 |
| 장애 정책 | Redis 오류 시 DB 우회, 허용할 데이터 신선도와 복구 조건 |

AI를 활용해 실제 SQL·실행 계획·요청당 SQL 수를 분석하고 최적화 대안을 비교할 수 있습니다.

단, 다음 사항은 반드시 직접 검토합니다.

- 기존 조회 조건을 제거해 결과가 달라지는 최적화
- 사용자별 데이터를 공용 캐시에 저장하는 설계
- TTL만으로 변경 직후의 최신성이 보장된다는 주장

## 2. 기존 조회의 SQL·인덱스 개선

### 2.1 데이터와 기준선 준비

1. 격리된 실습 DB에 상품 10,000개 이상을 준비합니다.
2. 실제 모델에 필요한 브랜드·좋아요·필수 필드를 구성합니다.
3. 같은 seed를 반복 생성할 수 있게 하고, 브랜드·가격·좋아요 수에 다양한 값과 동점이 생기도록 합니다.
4. 기존 API의 브랜드 필터 + `price_asc` 첫 페이지 요청을 고정합니다. 실제 페이지 파라미터·기본값·페이지 크기를 기록합니다.
5. 캐시 없이 응답 결과, SQL 수, `EXPLAIN`, `EXPLAIN ANALYZE`, 반복 측정한 지연 시간을 기록합니다.

새로운 `limit` 계약을 만들거나 기존 API의 페이지 처리 방식을 임의로 바꾸지 않습니다.

### 2.2 쿼리와 인덱스 개선

- 실제 삭제·브랜드 노출 조건, 필터·정렬·조회 열에 맞춰 인덱스 또는 쿼리를 개선합니다.
- 좋아요 수를 상품마다 반복 조회한다면 목록 단위 집계·조회로 줄일 수 있는지 검토합니다.
- `likes_desc`는 전체 후보의 정렬 결과에서 페이지를 선택해야 한다는 의미를 유지합니다.

### 2.3 개선 결과 비교

개선 전후에 다음 항목을 비교합니다.

- 사용 인덱스와 접근 경로
- 예상·실제 rows, loops, 정렬 단계
- 요청당 SQL 수
- 준비 실행 여부, 측정 표본 수, 응답 시간 분포
- 정렬된 상품 ID·가격·좋아요 수·페이지 정보

결과가 달라졌다면 성능 개선으로 인정하지 않습니다. 체크섬을 사용한다면 비교 필드와 직렬화 순서를 고정하고, 불일치한 실제 값도 확인합니다.

**특정 인덱스 이름, `Using index` 문자열, 몇 배 향상 같은 수치를 정답으로 고정하지 않습니다.** 실제 실행 계획과 측정 결과를 근거로 판단합니다.

### 2.4 재현 가능한 seed와 인덱스 관리

다음은 seed를 구성하는 예시이며, 실제 스키마나 제공된 SQL 파일을 의미하지 않습니다.

```text
상품 순번 i = 1..10,000
브랜드 순번 = (i % 100) + 1
가격 = ((i * 37) % 100000) + 100
전체 상품 수 = 10,000
전체 가격 합계 = 472,685,000
브랜드 순번 7의 상품 수 = 100
브랜드 순번 7의 가격 합계 = 4,647,200
```

실제 ID와 순번을 매핑하고, 외래 키·필수 이름·재고·삭제 상태·좋아요 관계를 함께 준비합니다. 좋아요가 없는 상품, 인기 상품, 동점 가격도 포함합니다.

인덱스 SQL과 seed는 저장소에 남기되 기존 migration·fixture 방식을 활용합니다. 공유 DB의 데이터나 다른 과제의 인덱스를 삭제하지 않습니다.

## 3. 한 조회 경로에 Cache-Aside 적용

상품 목록 또는 상세 조회 중 **공통 조회 경로 하나**를 선택합니다.

### 3.1 캐시 동작

| 상황 | 동작 |
|---|---|
| Cache miss | DB에서 올바른 결과를 조회하고 유효 시간과 함께 저장 |
| Cache hit | 캐시 결과를 반환하고 비싼 원본 조회·집계 비용 감소 |
| 데이터 변경 | 영향을 받는 캐시를 무효화하거나 선택한 정책에 따라 갱신 |
| Redis 장애 | 제한된 시간 내 DB 우회 또는 기존 오류 계약에 따른 처리 |

### 3.2 캐시 키와 데이터 범위

- 브랜드 필터·정렬·페이지·페이지 크기·응답 형식을 키에 반영합니다.
- 사용자별 정보는 공용 캐시에서 제외하거나 적절하게 사용자 경계를 분리합니다.
- 필요한 공통 필드만 캐시하고, 민감한 정보는 원본에서 조회하거나 합성할 수 있습니다.
- 캐시 hit의 성능을 측정할 때 남아 있는 DB 확인 비용도 포함합니다.

### 3.3 기존 변경 경로 연결

가격 수정만 별도 서비스로 처리하지 말고 기존 관리자 API와 연결합니다.

캐시 내용에 영향을 주는 다음 경로를 빠뜨리지 않습니다.

- 상품 생성·수정·삭제
- 브랜드 변경·일괄 삭제
- 좋아요 등록·취소
- 캐시에 포함된 재고 등 기타 데이터 변경

**캐시 무효화는 DB 트랜잭션과 별개의 실패 가능성이 있습니다.** `@Transactional`과 `cache.delete`를 함께 사용하거나 TTL을 설정했다는 사실만으로 모든 장애·경쟁 상황의 정합성이 보장되지는 않습니다.

### 3.4 반드시 유지할 업무 계약

캐시를 적용해도 다음 규칙은 완화할 수 없습니다.

- 삭제 상품은 고객 조회와 새 주문에서 제외합니다.
- 사용자별 좋아요·주문·포인트는 소유권을 지킵니다.
- 주문 금액·재고·포인트 판단은 기존 DB 기반 규칙을 따릅니다.
- 캐시를 통해 삭제 대상이나 다른 사용자의 정보가 노출되어서는 안 됩니다.

표시용 상품 설명·가격의 일시적인 오래된 값은 정책에 따라 허용할 수 있지만, 주문·재고·포인트의 정확성을 표시 데이터의 신선도 정책과 혼동하지 않습니다.

### 3.5 정합성 및 신선도 기준

정상 변경과 장애 상황을 구분해 검증합니다.

- **정상 변경:** 장애나 동시 캐시 채움이 없는 상황에서, 변경 완료 후 시작한 조회는 변경된 결과를 반환해야 합니다.
- **롤백:** 변경 전 결과를 유지하고, 롤백된 데이터가 새 결과로 캐시에 게시되지 않아야 합니다.
- **무효화 실패:** DB 변경이 실제로 커밋되었다는 사실을 유지하고, 허용한 표시 신선도 정책과 복구 조건을 검증합니다.
- **늦은 캐시 채움:** 이전 조회가 오래된 결과를 나중에 저장하는 상황을 재현하고, 선택한 방지·만료·복구 정책을 검증합니다.

장애 중 오래된 표시 데이터를 허용한다면 대상 필드, 만료·재처리·원본 우회 조건, 복구 완료 판정을 정의합니다. 정상 변경의 보장과 장애 시의 허용 범위를 하나로 섞지 않습니다.

## 4. 변경·장애·복구 검증

실제 애플리케이션·MySQL·Redis가 연결된 테스트로 검증합니다. 캐시 동작을 모두 Mock으로 대체한 테스트만으로 완료하지 않습니다.

### 4.1 필수 테스트 시나리오

| 장면 | 검증할 결과 |
|---|---|
| DB-only·cache miss·cache hit | 상품·정렬·페이지 결과 일치, hit에서 비싼 DB 조회 감소 |
| 관리자 가격 수정 후 재조회 | 새 가격과 목록 순서 반영, 과거 주문 금액 유지 |
| 상품·브랜드 일괄 삭제 | 삭제 대상은 고객 결과에서 제외되고 다른 브랜드·과거 주문은 유지 |
| 좋아요 등 나머지 쓰기 | 캐시 결과에 영향을 주는 변경이 반영됨 |
| DB 변경 rollback | 변경 전 결과 유지, 롤백된 데이터가 캐시에 남지 않음 |
| 커밋 후 캐시 무효화 실패 | DB 커밋 사실 유지, 정한 신선도·복구 정책 충족 |
| 이전 조회의 늦은 캐시 채움 | 오래된 재삽입을 재현하고 선택한 방지·복구 정책 검증 |
| Redis 중단·재시작 | 제한된 대기 후 DB 결과 반환, 복구 후 정상 조회와 캐시 재채움 |

### 4.2 경쟁 상황 재현

테스트 훅·래치 등으로 실행 순서를 통제합니다. 예를 들어 다음 순서를 만듭니다.

1. 이전 조회가 DB에서 결과를 읽습니다.
2. 관리자 변경이 커밋됩니다.
3. 이전 조회가 오래된 결과를 캐시에 저장합니다.
4. 새 조회를 실행하고 선택한 정책의 결과를 확인합니다.

테스트 대기는 유한한 timeout을 사용하고, 종료 시 모든 worker를 정리합니다.

Redis 오류 시 DB가 정상이고 통제된 부하를 감당할 수 있다면 상품 조회는 기존 정상 응답을 반환해야 합니다. DB까지 실패했다면 빈 목록이나 가격 0으로 오류를 감추지 않고 기존 오류 계약을 따릅니다. Redis 장애를 이유로 주문의 결제·재고 처리를 우회하지 않습니다.

### 4.3 Redis 장애 실험

테스트 환경이 실제 애플리케이션이 연결하는 Redis를 대상으로 하는지 먼저 확인합니다.

1. cache miss → cache hit으로 원본 조회 감소를 확인합니다.
2. 사용하는 Redis endpoint를 중단합니다. master와 replica를 모두 사용한다면 둘 다 확인합니다.
3. DB 정상 상태에서 응답·대기 시간·캐시 오류를 확인합니다.
4. 같은 Redis를 다시 시작하고 연결·조회·재채움을 확인합니다.
5. 자신이 시작한 실험 자원만 정리합니다.

Testcontainer를 사용한다면 해당 컨테이너를 중단·재시작하고, Compose를 사용한다면 실제 연결 설정이 그 서비스를 가리키는지 확인합니다. 두 환경을 혼용해 엉뚱한 Redis를 중단하지 않습니다.

공유 Redis에 `FLUSHALL`을 실행하거나 다른 작업의 컨테이너를 중단하지 않습니다. 장애 실험 전에 복구 절차를 준비합니다.

### 4.4 기존 Redis 설정 확인

- Java: `modules/redis/src/main/java/com/loopers/config/redis/RedisConfig.java`
- Kotlin: `modules/redis/src/main/kotlin/com/loopers/config/redis/RedisConfig.kt`
- 공통: `modules/redis/src/main/resources/redis.yml`, `docker/infra-compose.yml`

기본 연결은 `REPLICA_PREFERRED`이고 별도 master 연결이 있습니다. 실제로 사용하는 template·연결·직렬화·대기 시간을 확인합니다. 최신성 실험에서는 어떤 endpoint를 읽었는지 기록하고, replica lag를 애플리케이션의 최신성 보장으로 오인하지 않습니다.

### 5.3 선택 심화

필수 과제를 완료한 뒤 필요에 따라 확장합니다.

- 데이터 쏠림과 깊은 페이지 비교

# ✍️ Technical Writing Quest

> **측정 결과가 설계 선택을 어떻게 바꿨는지 설명합니다.**

이번 과제의 조회·캐시 구현에서 의미 있었던 주제 하나를 선택해 저장소 Markdown·Issue·블로그에 작성합니다.

## 주제 예시

- 인덱스가 있는데도 느렸던 SQL의 실제 병목
- 복합 인덱스의 열 순서를 결정한 이유
- 좋아요 수의 N+1과 전체 정렬을 구분한 과정
- 비정규화를 선택하거나 미룬 이유
- 관리자 변경과 캐시 무효화 사이에서 발견한 실패
- 캐시 hit에 DB 확인이 남는 설계의 이득과 비용
- Redis 장애 후 원본 조회가 늘어난 결과
- AI의 최적화 제안에서 발견한 계약 변화

## 작성 기준

1. **상황과 근거:** 실제 SQL·실행 계획·측정 결과 중 하나로 문제를 보여 줍니다.
2. **개념 설명:** 인덱스·집계·캐시·정합성 중 핵심 개념을 자신의 말로 설명합니다.
3. **설계 판단:** 선택한 방법과 이유를 설명합니다.
4. **비용과 한계:** 줄어든 비용, 새로 생긴 비용, 확인하지 못한 한계를 구분합니다.

실제로 측정하지 않은 수치나 검증하지 않은 결과를 사실처럼 작성하지 않습니다.
