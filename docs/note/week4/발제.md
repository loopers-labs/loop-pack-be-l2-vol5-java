## 🔎 상품 목록이 느리다는 말에서 시작하기

브랜드별 가격순 목록을 여는 데 오래 걸립니다. 상품이 많아서일 수도 있지만, 상품마다 브랜드와 좋아요 수를 따로 조회해서일 수도 있습니다. Redis를 추가하기 전에 **한 요청이 실제로 하는 일**을 나눠 봅니다.

| 관찰 | 가능한 원인 | 먼저 확인할 것 |
| --- | --- | --- |
| SQL 한 개가 오래 걸림 | 많은 행 탐색, 정렬·집계 | 해당 SQL의 계획과 실제 행 수 |
| SQL은 짧지만 수십 개 실행 | N+1, 반복 조회 | 요청 한 번의 SQL 수와 호출 경로 |
| DB 시간은 짧은데 HTTP가 느림 | 연결 대기, 외부 호출, 변환·직렬화 | 구간별 시간과 연결 풀 |
| 반복 요청에서 같은 집계 수행 | 재사용 가능한 계산 | 요청 분포와 허용 신선도 |
| 캐시 hit도 느림 | Redis 대기, 큰 payload, 네트워크 | 캐시 시간·크기와 DB 호출 여부 |

**지연 시간(latency)**은 요청 하나가 끝나는 시간이고, **처리량(throughput)**은 일정 시간 동안 처리한 요청 수입니다. 동시 요청을 늘려 처리량이 오르다가 대기가 쌓이면 지연이 급격히 커질 수 있습니다. 평균 하나만 보면 일부 요청의 긴 대기를 놓칩니다.

### 📏 비교 가능한 기준선

1. 기존 API의 필터·정렬·페이지와 응답 필드를 고정합니다.
2. 같은 데이터·DB 버전·인덱스 상태를 사용합니다.
3. 준비 실행과 측정 실행을 구분하고 표본 수·동시 요청 수를 적습니다.
4. SQL 수·계획·결과·지연을 함께 비교합니다.

| 고정할 조건 | 바꾸면 비교가 달라지는 이유 |
| --- | --- |
| 데이터 양과 분포 | 한 브랜드에 몰린 데이터와 균등 분포의 비용이 다름 |
| 페이지 위치와 정렬 | 첫 페이지와 깊은 페이지가 읽는 양이 다름 |
| DB·애플리케이션 준비 상태 | 버퍼 풀, JIT, 연결 생성의 비용이 섞임 |
| 응답 필드·삭제 조건 | 더 적은 정보를 반환하거나 삭제 상품을 포함하면 다른 기능 |
| 캐시 hit/miss | 서로 다른 경로이므로 별도로 측정해야 함 |

측정용 데이터는 실제 스키마의 필수 필드와 관계를 만족해야 합니다. 실험을 위해 별도 Product 모델을 만들면 개선한 SQL이 실제 API에서 쓰이지 않을 수 있습니다.

> **빨라졌다는 주장에는 같은 결과를 반환한다는 전제가 있습니다.**
>

정렬된 상품 ID·가격·좋아요 수와 페이지 정보를 직접 비교할 수 있습니다. 결과가 크다면 직렬화 형식을 고정한 체크섬을 보조로 사용합니다. JSON 필드 순서나 시간 필드가 달라진 것을 업무 결과 차이로 오인하지 않습니다. 체크섬 불일치 때는 실제 다른 행·필드를 찾아야 합니다.

## 📚 인덱스는 어떤 일을 줄이는가

> **인덱스**는 검색 키를 정렬된 구조로 유지해 필요한 행을 찾는 비용을 줄이는 보조 자료구조입니다.
>

InnoDB의 일반적인 인덱스는 B-Tree 계열 구조입니다. 테이블 전체를 차례로 읽는 대신 키를 따라 범위를 좁힐 수 있습니다. 대신 삽입·수정·삭제할 때 인덱스도 관리하므로 저장 공간과 쓰기 비용이 늘어납니다.

아래 SQL은 열 순서를 설명하는 축약 예시입니다. 실제 쿼리에는 기존 삭제·브랜드 노출 조건과 응답에 필요한 조회를 유지합니다.

```sql
SELECT id, brand_id, name, price
FROM products
WHERE brand_id = 7
ORDER BY price ASC, id ASC
LIMIT 20;
```

### 🧱 단일 인덱스와 복합 인덱스

```sql
CREATE INDEX idx_products_brand ON products(brand_id);
CREATE INDEX idx_products_brand_price_id ON products(brand_id, price, id);
```

두 인덱스를 무조건 함께 추가하라는 지시가 아닙니다. 후보를 비교하는 예시이며, 겹치는 인덱스가 이미 있다면 중복 비용을 검토합니다.

| 후보 | 위 쿼리에서 기대하는 역할 | 남을 수 있는 비용 |
| --- | --- | --- |
| `(brand_id)` | 브랜드에 해당하는 행 탐색 | 가격 정렬, 행의 다른 열 읽기 |
| `(brand_id, price, id)` | 브랜드 범위 안에서 가격·ID 순서로 읽기 | name 등 인덱스 밖의 열 읽기 |
| `(price, brand_id)` | 가격 순서 탐색에 이용될 가능성 | 특정 브랜드만 찾으려면 많은 행을 건너뛸 수 있음 |

복합 인덱스는 **정렬된 전화번호부의 분류 순서**처럼 생각할 수 있습니다. `(brand_id, price)`는 브랜드별로 묶고 그 안에서 가격순으로 놓습니다. 가격만으로 찾는 요청이 브랜드로 먼저 좁히는 요청과 같은 이득을 얻는 것은 아닙니다.

- 왼쪽 열부터 이어지는 조건은 일반적인 인덱스 탐색에 잘 맞습니다.
- SQL의 `WHERE a=? AND b=?`를 `WHERE b=? AND a=?`로 적는다고 인덱스 열 순서가 바뀌지는 않습니다.
- 앞쪽 열의 범위 조건은 뒤쪽 열이 정렬·탐색에 기여하는 방식을 제한할 수 있습니다.
- `ASC/DESC`가 섞이면 인덱스 방향과 스캔 방향을 함께 확인합니다.
- 실제 선택은 통계·분포·조회 열과 옵티마이저 비용 판단에 달려 있습니다.

**카디널리티(cardinality)**는 서로 다른 값의 수를 뜻하고, **선택도(selectivity)**는 조건이 전체 중 얼마나 적은 행을 남기는지를 판단하는 데 쓰입니다. 고유값이 많은 열을 무조건 앞에 놓는 공식은 없습니다. 브랜드 동등 조건과 가격 정렬을 함께 쓰는 쿼리는 그 조합을 기준으로 판단합니다.

### 🗂️ Covering index와 추가 정렬

**Covering index**는 쿼리에 필요한 값을 인덱스만으로 읽을 수 있는 경우입니다. `(brand_id, price, id)`가 있어도 `name`까지 반환하는 위 쿼리를 자동으로 covering이라고 부를 수는 없습니다.

전통적인 `EXPLAIN`의 `Using index`는 인덱스만으로 필요한 값을 읽는 경우를 나타내며, “어떤 인덱스든 사용했다”와 같은 뜻이 아닙니다. `Using filesort`는 인덱스 순서만으로 해결하지 못한 추가 정렬을 뜻합니다. 이름에 file이 있다고 반드시 디스크 정렬인 것은 아닙니다.

추가 정렬이 항상 실패도 아닙니다. 좁힌 행 몇 개를 정렬하는 비용이 큰 인덱스를 계속 유지하는 비용보다 작을 수 있습니다.

## 🧪 실행 계획을 읽는 순서

`EXPLAIN`은 옵티마이저가 예상한 접근 방법을 보여 줍니다. MySQL 8.0.18 이후의 `EXPLAIN ANALYZE`는 **실제로 문장을 실행**해 예상과 실제 반복·행 수·시간을 비교합니다. 이 과정에서는 격리된 실습 데이터의 SELECT에 사용합니다.

- SQL · 현재 조회의 계획 확인

  아래 예시를 실제 테이블·열·삭제 조건에 맞춥니다. API가 실행하는 SQL과 별개의 축약 쿼리만 튜닝하지 않습니다.

    ```sql
    SELECT VERSION();
    ANALYZE TABLE products;
    EXPLAIN
    SELECT id, brand_id, name, price
    FROM products
    WHERE brand_id = 7
    ORDER BY price, id
    LIMIT 20;
    
    EXPLAIN ANALYZE
    SELECT id, brand_id, name, price
    FROM products
    WHERE brand_id = 7
    ORDER BY price, id
    LIMIT 20;
    ```


| 읽을 항목 | 질문 |
| --- | --- |
| 접근 경로·사용 key | 전체 탐색인가, 인덱스 탐색인가? |
| 예상 rows와 실제 rows | 데이터 분포를 잘 추정했는가? |
| loops | 적은 행을 아주 많이 반복해서 읽고 있지 않은가? |
| filter·sort·aggregate | 어디에서 행을 줄이고 정렬·집계하는가? |
| actual time | 하위 작업을 포함하는 시간인지, 반복당 평균인지? |

전통적인 표 형식의 `key/type/Extra`와 `ANALYZE`의 트리 형식은 다른 표현입니다. 트리에 없는 열을 억지로 찾거나 모든 노드 시간을 합산해 HTTP 시간이라고 하지 않습니다.

예상 rows와 실제 rows가 크게 다르면 통계와 데이터 쏠림을 봅니다. 인덱스가 선택되지 않았다는 이유만으로 힌트를 강제하기 전에 **실제로 읽는 양과 비용이 줄었는지**를 확인합니다.

## ❤️ 좋아요 수와 페이지 조회의 숨은 비용

상품 20개를 읽은 뒤 각 상품의 브랜드·좋아요 수를 별도 조회하면 목록 한 번에 여러 SQL이 실행됩니다.

```
목록 1회
  상품 20개 조회 1회
  각 상품의 좋아요 COUNT 20회
  각 상품의 브랜드 조회가 추가될 수도 있음
```

이처럼 한 조회 뒤 연관 데이터 수에 비례한 추가 조회가 붙는 현상을 **N+1**이라고 합니다. 각 COUNT에 인덱스가 있어도 네트워크 왕복과 반복 호출 비용은 남습니다.

### 🧮 집계를 옮기면 책임도 옮겨진다

| 방법 | 얻는 것 | 주의할 것 |
| --- | --- | --- |
| 목록 ID를 모아 한 번에 집계 | 상품별 반복 COUNT 감소 | 이미 페이지를 정한 뒤 집계하면 좋아요순 전체 정렬에는 사용할 수 없음 |
| DB에서 집계·정렬 후 페이지 선택 | 전체 후보의 좋아요순 의미 유지 | JOIN·GROUP BY·정렬 비용 |
| 좋아요 수를 별도 열로 유지 | 읽을 때 반복 집계 감소 | 등록·취소·중복 요청·동시 갱신과 카운터 정합성 |
| 별도 조회용 집계 결과 | 읽기 목적에 맞춘 구조 | 갱신 경계·지연·복구 책임 |

**비정규화**는 계산하거나 결합한 값을 읽기 편하게 중복 저장하는 선택입니다. 좋아요 관계와 카운터를 같은 트랜잭션에서 갱신할 수도 있으므로 비정규화가 반드시 지연 반영을 뜻하지는 않습니다. 반대로 조인을 썼다는 사실만으로 잘못된 격리·중복 관계까지 해결되지는 않습니다.

좋아요 관계가 진짜로 추가됐을 때만 +1, 실제 취소됐을 때만 -1 해야 합니다. 재요청마다 카운터를 바꾸면 관계 수와 달라집니다. 3주차의 트랜잭션·동시성 판단이 여기에도 적용됩니다.

현재 필요한 개선이 쿼리 조정으로 충분하다면 카운터나 조회용 테이블을 추가할 이유는 없습니다. 별도 이벤트·배치 동기화 구현을 이번 조회 최적화의 선행조건으로 만들지 않습니다.

### 📄 페이지를 빨리 읽는 것과 계약을 바꾸는 것

`OFFSET`은 앞의 결과를 건너뛰는 비용이 있어 깊은 페이지가 느려질 수 있습니다. 마지막 `(price, id)` 뒤에서 시작하는 커서 방식은 대안이지만, 임의 페이지 이동과 응답 계약이 달라집니다.

- 동점에서 결과가 흔들리지 않도록 기존 동점 정렬 기준을 유지합니다.
- 좋아요순 전체 정렬을 “20개를 먼저 읽고 애플리케이션에서 정렬”로 바꾸지 않습니다.
- JOIN으로 행이 늘어날 때 상품 중복·페이지 크기·전체 건수가 달라지는지 확인합니다.
- 비용 개선을 위해 페이지 번호 API를 설명 없이 커서 API로 교체하지 않습니다.

## 🚄 캐시가 재사용하는 것은 무엇인가

> **캐시**는 원본에서 읽거나 계산한 결과를 다시 사용하기 위해 저장한 복사본입니다.
>

**Cache-aside**에서는 애플리케이션이 먼저 캐시를 보고, 없으면 DB에서 읽어 캐시에 저장합니다.

```
조회 → 캐시 확인
        ├─ hit  → 저장된 복사본 반환
        └─ miss → DB 조회 → 캐시 저장 → 반환
```

캐시의 가치는 Redis를 썼다는 사실이 아니라 **비싼 읽기를 얼마나 줄였는가**입니다. 재사용이 거의 없는 페이지를 모두 저장하면 키 수와 무효화 비용만 늘 수 있습니다.

### 🔑 키는 응답을 구분하는 조건이다

```
예시: products:v1:brand=7:sort=price_asc:page=0:size=20
```

위 문자열은 키 구성 예시이며 실제 페이지 시작값·파라미터는 기존 API를 따릅니다.

| 빠진 구분 | 생길 수 있는 오류 |
| --- | --- |
| 브랜드·필터 | 다른 조건의 목록 반환 |
| 정렬·페이지·크기 | 같은 키에 다른 순서·구간 저장 |
| 응답 형식 버전 | 배포 전후 직렬화 계약 충돌 |
| 사용자별 정보 | 다른 사용자의 좋아요 여부·개인 정보 반환 |

공통 상품 정보와 “내가 좋아요했는지”는 재사용 범위가 다릅니다. 사용자별 필드를 공용 캐시에 섞지 않거나 별도로 합성합니다. 이름에 `v1`을 붙이는 것만으로 DB 변경을 감지하지는 못합니다.

### ⏳ TTL과 무효화

**TTL**은 캐시 항목이 만료되기까지의 수명입니다. **무효화(invalidation)**는 더 이상 믿을 수 없는 복사본을 지우거나 사용 대상에서 제외하는 작업입니다.

| 방식 | 효과 | 한계 |
| --- | --- | --- |
| TTL | 오래된 항목이 무기한 남는 것을 제한 | 변경 즉시 최신 값을 보장하지 않음 |
| 변경 후 삭제 | 다음 miss에서 원본 재조회 | 삭제 실패·경쟁 중 재삽입 가능 |
| 새 버전의 키 | 다른 데이터 세대 분리 | 현재 버전을 어디서 읽는지에 따라 동일한 불일치가 남음 |
| 쓰면서 캐시 갱신 | 정상 경로의 후속 조회 가속 | DB·Redis 사이의 부분 실패와 순서 문제 |

읽을 때마다 TTL을 연장하면 자주 읽히는 오래된 값이 계속 남을 수 있습니다. Spring Data Redis의 TTL과 TTI(time-to-idle)는 다른 정책입니다. 이번 설계에서 어떤 동작을 쓰는지 확인합니다.

TTL을 30초로 두었다고 “DB 변경 후 반드시 30초 안에 모든 요청이 최신”이라고 단정할 수도 없습니다. 오래된 DB 읽기가 늦게 완료돼 새 TTL로 캐시에 들어가거나, 지연된 복제본에서 다시 채워질 수 있습니다. **만료 기준·원본 읽기·진행 중인 요청**까지 알아야 상한을 설명할 수 있습니다.

## 🔄 관리자 변경과 캐시는 한 저장소가 아니다

관리자가 가격을 바꾸면 상세만 달라지는 것이 아닙니다. 가격순 목록의 구성과 위치도 달라질 수 있습니다. 브랜드 이름 변경·브랜드 일괄 삭제·상품 생성·좋아요·재고 변경도 응답 필드에 따라 영향을 줍니다.

| 변경 | 캐시가 담았다면 검토할 결과 |
| --- | --- |
| 상품 가격·이름 변경 | 상세, 검색·정렬된 목록 |
| 상품 생성·삭제 | 목록 구성·전체 건수, 상세의 존재 여부 |
| 브랜드 변경·일괄 삭제 | 브랜드 정보, 연결 상품의 노출 |
| 좋아요 등록·취소 | 좋아요 수·정렬·사용자별 표시 |
| 재고 변경·주문 확정 | 응답에 포함한 재고 정보 |

**캐시 범위를 작게 고르면 무효화 책임도 작아집니다.** 상품 목록 전체 응답을 캐시하기로 했다면 관련 키 하나만 지우는 것으로 충분한지 검토합니다. 전용 캐시 영역을 통째로 비우는 방법도 작은 실습에서는 가능하지만, 요청이 모두 miss가 되는 비용을 기록해야 합니다. 공유 Redis 전체를 비우는 것은 별개입니다.

### ⚠️ commit 뒤 삭제에도 남는 실패 창

```
정상: DB 가격 12,000 commit → 캐시 삭제 성공 → 다음 조회 12,000
실패: DB 가격 12,000 commit → 캐시 삭제 timeout → 캐시에 10,000 잔존
경쟁: 조회 A가 DB 10,000 읽음 → 변경 commit·캐시 삭제 → A가 10,000 저장
```

삭제를 먼저 해도 commit 전에 다른 조회가 이전 DB 값을 채울 수 있습니다. `@Transactional` 하나나 메서드 안의 두 호출이 MySQL과 Redis를 원자적으로 만들지는 않습니다.

3주차에 배운 commit 경계를 이용해 **성공한 DB 변경 뒤** 캐시를 무효화할 수 있습니다. 그러나 after-commit 실행도 외부 호출 실패를 없애지 못합니다. DB가 이미 commit됐다면 캐시 오류 때문에 DB까지 rollback됐다고 응답해서는 안 됩니다.

| 요구하는 신선도 | 필요한 판단 |
| --- | --- |
| 정상 변경 후 순차 조회가 최신 | 영향 캐시와 commit 이후 무효화 경로 확인 |
| 일시적 오래된 표시 허용 | 허용 필드·조건·복구·만료 정책 명시 |
| 오래된 값을 절대 사용하면 안 됨 | 원본 재확인, 권위 있는 버전 검증 또는 캐시 대상 제외 |

가격을 보여 주는 조회와 주문 확정의 금액 판단은 다른 책임입니다. **주문 확정은 DB에 보존한 주문 금액과 기존 상품 상태·재고 규칙을 사용**하며 캐시의 오래된 값으로 구매를 확정하지 않습니다. 이번 최적화를 이유로 주문 단가의 기존 결정 시점을 바꾸거나 삭제된 상품을 사용할 수 있게 되살리지 않습니다.

버전 방식을 택한다면 현재 버전은 업무 변경과 같은 권위 경계에서 바뀌어야 합니다. Redis의 `currentVersion` 포인터가 낡으면 새 키 전략에서도 예전 데이터를 읽습니다. DB에서 버전·사용 가능 여부를 확인하는 방법은 안전성을 높이지만 hit에도 DB 비용이 남습니다. 무엇을 줄였는지 정직하게 측정해야 합니다.

## 🛠️ Spring에서 캐시 경계를 구현하기

| 방법 | 적합한 경우 | 직접 확인할 책임 |
| --- | --- | --- |
| `@Cacheable / @CacheEvict` | 비교적 단순한 메서드 단위 캐시 | key, CacheManager, TTL 설정, 프록시·오류 처리·TX 순서 |
| `RedisTemplate` | 실패 분기와 키·직렬화를 명시할 때 | 조회·저장·만료·삭제, 타입 변환, 타임아웃 |

`@Cacheable`은 기본 프록시 방식에서 외부 호출을 가로챕니다. 같은 객체 내부 호출에 적용된다고 가정하지 않습니다. `@CacheEvict`의 메서드 실행 후 삭제가 항상 DB commit 이후라는 뜻도 아니므로 트랜잭션과 캐시 설정의 실제 경계를 확인합니다.

- Java · 캐시 실패를 원본 조회와 분리하는 흐름 예시

  완성 구현이 아닌 경계 예시입니다. CachePort·ReadRepository와 응답 DTO, 오류 타입·키·TTL은 실제 설계에서 정의합니다. 캐시 내용의 신선도·노출 검증은 별도로 필요합니다.

    ```java
    public ProductView find(long productId) {
        try {
            var cached = cache.find(productId);
            if (cached.isPresent()) {
                return cached.get();
            }
        } catch (CacheUnavailableException e) {
            metrics.cacheReadFailure();
        }
    
        ProductView result = readRepository.find(productId);
        try {
            cache.save(productId, result);
        } catch (CacheUnavailableException e) {
            metrics.cacheWriteFailure();
        }
        return result;
    }
    ```

  전체 메서드를 `catch (Exception)`으로 감싸 빈 상품을 반환하면 DB 오류·존재하지 않는 상품·구현 결함도 감춰집니다. 캐시 장애와 원본 조회 실패를 구분합니다.

- Kotlin · 캐시 실패를 원본 조회와 분리하는 흐름 예시

  Java 예시와 같은 미완성 경계 설명입니다. 프로젝트에 제공된 상품 조회 함수가 아닙니다.

    ```kotlin
    fun find(productId: Long): ProductView {
        val cached = try {
            cache.find(productId)
        } catch (e: CacheUnavailableException) {
            metrics.cacheReadFailure()
            null
        }
        if (cached != null) return cached
    
        val result = readRepository.find(productId)
        try {
            cache.save(productId, result)
        } catch (e: CacheUnavailableException) {
            metrics.cacheWriteFailure()
        }
        return result
    }
    ```


두 트랙의 Redis 설정은 기본 연결에 `REPLICA_PREFERRED`, 별도 master 연결에 `MASTER`를 사용합니다. 무효화 직후 replica의 옛 값을 읽을 가능성을 고려해야 합니다. 순차 최신성 실험에서는 선택한 읽기 연결을 명시합니다. 연결 선택은 DB·Redis의 원자성을 대신하지 않습니다.

## 🚧 Redis가 멈추면 어디까지 유지되는가

Redis 장애 때 DB가 정상이고 실험 부하를 감당한다면 **원본 조회로 우회**할 수 있습니다. 우회는 캐시 오류를 빈 목록이나 가격 0으로 바꾸는 것이 아닙니다.

- 캐시 연결·명령의 대기 시간을 제한합니다.
- miss와 Redis 오류를 구분해 관찰합니다.
- DB 조회 오류는 정상 빈 결과로 숨기지 않습니다.
- 복구 때 오래된 항목이 다시 사용되는지 확인합니다.
- 테스트가 실제로 연결한 endpoint를 중단합니다. 별도 Testcontainer가 살아 있으면 Compose 중단은 그 테스트의 장애가 아닙니다.

캐시가 내려가면 hit로 끝나던 요청까지 DB로 갑니다. 이것이 DB 연결 대기까지 증가시키면 기능적인 fallback만으로는 충분하지 않습니다. 동시 요청 제한·부하 축소는 다음 판단이지만, 이번에는 작은 통제 부하에서 우회와 결과를 먼저 확인합니다.

**Cache stampede**는 같은 항목의 miss가 한꺼번에 발생해 원본 조회가 몰리는 현상입니다. 요청 합치기, 만료 시점 분산 등이 대안입니다. 여러 서버에서의 분산 잠금까지 모든 캐시에 먼저 도입할 필요는 없습니다.

## 🧭 무엇을 개선했다고 말할 것인가

| 장면 | 확인할 결과 |
| --- | --- |
| 인덱스 전후 | 같은 업무 결과, 계획·읽은 행·시간의 변화 |
| cache miss/hit | 동일 입력에서 응답 일치, 실제 원본 호출 감소 |
| 정상 관리자 변경 | 선택한 캐시와 영향 범위의 최신 값 반영 |
| 무효화 실패·경쟁 | 오래된 값의 재현, 허용 범위 또는 방지 장치, 복구 결과 |
| Redis 장애·재시작 | 제한된 대기와 DB 우회, 복구 후 정확한 재채움 |

AI에는 “Redis를 붙여 줘”보다 보존할 계약과 관찰한 병목을 먼저 줍니다.

> **검토 예시:** “브랜드 필터·가격순·기존 페이지 계약을 유지한다. 이 SQL 계획과 요청당 SQL 수에서 먼저 줄일 비용은 무엇인가? 캐시한다면 관리자 변경·브랜드 삭제·다른 사용자 조회에서 어떤 반례가 생기는가?”
>

설명 가능한 대안을 고른 뒤 작은 변경을 구현하고 관련 테스트·기존 lint·ArchUnit으로 확인합니다. 같은 결과를 내는 데 DB 쿼리 개선만으로 충분했는지, 캐시를 추가한 만큼 운영 책임이 늘었는지 함께 기록합니다.
