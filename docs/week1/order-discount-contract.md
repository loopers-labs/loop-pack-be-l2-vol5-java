# 주문 할인(쿠폰 적용) 계약 설계 문서 — Week 1

## 1. 기준 문장

> "구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 합니다."


## 2. 확인된 사실 (2개)

| # | 사실 |
|---|---|
| 사실 1 | 구매자는 **주문이 확정되기 전에** 자신이 보유한 쿠폰을 주문에 적용할 수 있다. |
| 사실 2 | 주문이 확정된 이후에는, 그 시점에 계산된 할인 금액이 **이후 정책·가격 변화에도 변경되지 않는다.** |

## 3. 실습 장면의 조건 (4개)

| # | 조건 |
|---|---|
| 조건 1 | 한 주문에 보유 쿠폰을 **한 장만** 적용한다. |
| 조건 2 | 최종 금액은 원금에서 할인액을 뺀 값이다. (`finalAmount = originalAmount - discountAmount`) |
| 조건 3 | 같은 요청을 다시 보내면 **이전 결과를 그대로 재사용**한다. |
| 조건 4 | 쿠폰 만료 여부는 **요청이 시작된 시각**을 기준으로 판단한다. |

## 4. 관찰 테스트 결과 — `ContractClassificationTest`

기존 `GET /api/v1/examples/{id}`를 4가지 입력으로 실제 호출해 관찰한 값. 코드: [`ContractClassificationTest.java`](../../apps/commerce-api/src/test/java/com/loopers/interfaces/api/ContractClassificationTest.java) (`./gradlew :apps:commerce-api:test --tests 'com.loopers.interfaces.api.ContractClassificationTest'`로 재현 가능, 전체 assertion 통과 확인됨).

| 입력 | HTTP status | `meta.result` | `errorCode` | `data` 유무 |
|---|---|---|---|---|
| 정상 숫자 ID | `200 OK` | `SUCCESS` | `null` | 있음 |
| 숫자가 아닌 ID (`abc`) | `400 BAD_REQUEST` | `FAIL` | `"Bad Request"` | 없음 |
| 존재하지 않는 숫자 ID | `404 NOT_FOUND` | `FAIL` | `"Not Found"` | 없음 |
| 미매핑 URL | `404 NOT_FOUND` | `FAIL` | `"Not Found"` | 없음 |

**핵심 관찰**: 존재하지 않는 숫자 ID(비즈니스 로직에서 `CoreException(ErrorType.NOT_FOUND)`를 던지는 경로, [`ExampleService.java:18`](../../apps/commerce-api/src/main/java/com/loopers/domain/example/ExampleService.java))와 미매핑 URL(스프링 라우팅 실패, `NoResourceFoundException`을 [`ApiControllerAdvice.java:106`](../../apps/commerce-api/src/main/java/com/loopers/interfaces/api/ApiControllerAdvice.java)가 처리하는 경로)은 **내부 원인이 완전히 다름에도 불구하고, 클라이언트에게 보이는 응답은 `status`/`meta.result`/`errorCode`/`data` 4가지 필드 모두 동일**하다. 유일하게 다른 값은 `meta.message`의 텍스트뿐이며, 이는 클라이언트가 분기 처리에 쓸 수 있는 값이 아니다.

→ 즉 **현재 예시 API는 "리소스 없음"과 "경로 없음"을 구분하지 않고 하나의 `NOT_FOUND` 계약으로 합쳐서 응답한다.**

## 5. 제품 담당자에게 물을 질문

## 6. 여섯 불변식(INV)과 반례

| 규칙 ID | 출처 구분 | 규칙 | 깨지는 입력(반례) | 기대 결과 | 책임 후보 |
|---|---|---|---|---|---|
| INV-001 | 제품 약속 | 구매자는 **자신이 보유한** 쿠폰만 주문에 적용할 수 있다. (기준 문장의 "보유 쿠폰") | 다른 사용자 소유의 `couponId`로 적용 요청 | 실패 응답 (소유자 불일치). 주문 존재 자체는 노출하지 않는다 | 할인 적용 처리 흐름 — 요청자와 주문 주인이 같은지 확인 |
| INV-002 | 실습 조건 | 한 주문에는 보유 쿠폰을 **한 장만** 적용할 수 있다. | 이미 쿠폰이 적용된 주문에 다른 쿠폰을 또 적용 시도 | 요청 거부, 기존 적용 쿠폰 유지 | API 요청 형식(쿠폰을 한 개만 받음) + 주문 객체(이미 쿠폰이 붙었는지 확인) |
| INV-003 | 실습 조건 | `finalAmount = originalAmount - discountAmount` 이며, 할인액은 **0 이상 원금 이하**다. | `discountAmount > originalAmount`가 되는 쿠폰 적용 시도 | 할인액을 원금까지만 적용해 `finalAmount = 0` (전액 할인 허용). 초과분 소멸 여부는 5절 질문 3으로 확인 | 주문 객체 — 금액 계산 |
| INV-004 | 제품 약속 | 주문이 확정된 이후에는 쿠폰 상태·정책이 바뀌어도 `finalAmount`가 변하지 않는다. | 확정 후 쿠폰이 취소/만료되거나 할인 정책이 변경된 상태에서 같은 주문 재조회 | 최초 확정 시점의 `finalAmount` 그대로 반환 | 주문 객체 — 확정 시점 금액을 따로 저장해 보존 |
| INV-005 | 실습 조건 | 동일한 요청(같은 주문·쿠폰 조합)을 다시 보내도 쿠폰이 중복 차감되지 않고 같은 결과를 반환한다. | 같은 `orderId`+`couponId`로 연속 2회 요청 | 두 번째 요청도 첫 번째와 동일한 응답, 쿠폰 사용 횟수는 1회만 차감 | 할인 적용 처리 흐름 — 같은 요청인지 판단해 첫 결과를 되돌려줌 |
| INV-006 | 실습 조건 | 쿠폰 만료 여부는 **요청이 시작된 시각**을 기준으로 판단한다. | 만료 1초 전에 요청이 시작되었으나 처리 도중 만료 시각을 지난 경우 | 만료로 처리하지 않고 정상 적용 (적용 요청과 확정 사이에 만료되는 경우는 이 규칙의 범위 밖 — 5절 질문 4로 확인) | 쿠폰 객체 — 유효 기간 확인 |

## 7. 외부 계약과 내부 경계

### 기본 API 모양
PDF가 제시한 W2 기본 장면을 그대로 따른다. 다르게 설계하지 않았다.

- **method / path**: `POST /api/v1/orders/{orderId}/discount`
- **request**: `{ "couponId": Long }`
- **success 응답**: 기존 `ApiResponse.success(data)` 포맷 유지, `data = { orderId, originalAmount, discountAmount, finalAmount }`
- **error 응답**: 기존 `ApiResponse.fail(errorCode, message)` 포맷 유지 (`meta.result=FAIL`)
- **사용자 식별**: `X-USER-ID` 요청 헤더로 구매자를 식별한다고 **이번 실습 범위에서 가정**한다 (강의 자료 p.3의 소유권 반례가 `X-USER-ID`를 전제로 서술됨). 현재 코드베이스(`ExampleV1Controller` 등)에는 인증/식별 로직이 관찰되지 않는다. 인증 수단(세션/토큰 등) 선택은 개발팀이 정할 기술 결정으로 보고, **누가 호출할 수 있는지**라는 정책만 5절 질문 2로 남긴다.

### 결정 1 — 오류를 구분하는 방식
- **선택**: 쿠폰 적용의 실패는 원인별로 `errorCode`를 세분화한다 (예: `COUPON_NOT_FOUND`, `COUPON_ALREADY_USED`, `COUPON_EXPIRED`, `ORDER_NOT_FOUND` 등 개별 코드).
- **버린 대안**: 지금 예시 API처럼 모든 "없음" 상황을 `ErrorType.NOT_FOUND` 하나로 합쳐서 응답한다.
- **버린 이유**: 4절에서 실제로 확인했듯, 현재 방식은 "쿠폰이 없는지 / 주문이 없는지 / 경로가 틀렸는지"를 클라이언트가 전혀 구분할 수 없다. 조회만 하는 예시 API에서는 이 모호함이 큰 문제가 아니지만, 쿠폰 적용은 실패 원인마다 사용자에게 다른 안내(재시도 가능/불가능, 다른 쿠폰 선택 유도 등)가 필요할 가능성이 높아 구분이 필요하다고 판단했다.

### 결정 2 — snapshot과 재계산
- **선택**: 주문 확정 시점에 `finalAmount`를 스냅샷으로 저장하고, 이후 조회는 재계산 없이 저장된 값을 그대로 반환한다.
- **버린 대안**: 조회할 때마다 쿠폰·주문 정보를 다시 읽어 매번 재계산한다.
- **버린 이유**: 재계산 방식은 기준 문장의 "확정된 할인 금액은 나중에 바뀌지 않아야 한다"(사실 2, INV-004)와 정면으로 충돌한다. 쿠폰이 사후에 취소되거나 할인 정책이 바뀌면 재계산 결과가 달라져 확정 금액이 흔들리게 된다.

### 결정 3 — 호출 순서를 숨길 책임 경계
- **선택**: "쿠폰 검증 → 금액 계산 → 확정 저장"의 순서는 **할인 적용 처리를 맡은 한 곳**이 전담하고, HTTP 요청을 받는 컨트롤러는 이 순서를 모른 채 메서드 하나만 호출한다. (기존 예시 코드가 쓰는 구조와 같은 방식)
- **버린 대안**: 컨트롤러가 쿠폰 조회와 주문 저장을 직접 순서대로 호출한다.
- **버린 이유**: 호출 순서(검증이 계산보다 먼저 와야 함 등)가 컨트롤러까지 드러나면, 이후 검증 단계가 추가되거나 순서가 바뀔 때마다 컨트롤러 코드도 같이 고쳐야 해 책임 경계가 무너진다. 기존 예시 코드도 컨트롤러가 세부 순서를 모르는 구조라 일관성도 유지된다.
