# 설계 문서

이 문서는 **주문에 쿠폰을 적용하는 기능의 요구사항을 구체화하고, 이후 구현과 테스트의 기준을 세우기 위한 설계 문서**다.
“주문에 쿠폰을 적용할 수 있어야 해요.”라는 짧은 기획 문장에서 출발해, 쿠폰의 소유권, 주문 확정 이후 할인 금액의 보존, 같은 요청이 반복될 때의 처리처럼 구현 전에 판단해야 할 내용을 정리한다.

요구사항은 **확인된 사실, 실습을 위한 임시 조건, 제품 담당자에게 확인할 질문**으로 구분하고 각각의 근거를 기록한다.
이를 바탕으로 지켜야 할 규칙과 그 규칙을 시험할 반례, 기대 결과, 책임 후보를 구체화한다.
개발자나 AI가 이후 이 문서를 읽고 사용자 응답, 저장 데이터, 권한과 처리 책임을 일관되게 구현하고 검증할 수 있도록 하는 것이 목적이다.
답변받지 못한 제품 질문은 미확정으로 남기고, 근거 없는 도구 제안은 보류 또는 거절과 그 이유를 기록한다. 이 내용을 확정된 제품 정책으로 취급하지 않는다.

**목표:** 쿠폰 요구에서 확인된 사실, 임시 조건, 제품 질문을 나누고 구현 가능한 경계를 설계한다.

**문서 간 참조:** 확인된 사실은 `FACT-001`, 실습 조건은 `COND-001`, 제품 질문은 `Q-001`, 도구 제안은 `SUG-001`, 설계 결정은 `DEC-001` 형식의 고정 ID로 참조한다. 다른 문서에서는 이 문서의 경로와 ID를 함께 적는다. 항목의 순서가 바뀌어도 ID를 유지하고, 삭제한 ID는 다른 항목에 재사용하지 않는다. `INV-001`부터 `INV-006`까지는 문서·테스트·지표와 W2에서도 같은 규칙을 가리키며, 다른 의미로 바꾸어 재사용하지 않는다.

## 관찰 테스트 결과

아래는 기존 예시 조회 API와 미매핑 URL의 응답을 관찰한 기록이다. 쿠폰 적용 기능의 구현 결과를 검증한 표는 아니다.
HTTP status, `meta.result`, `meta.errorCode`, `data` 유무를 검증했다.
아래 값은 [ContractClassificationTest](../../apps/commerce-api/src/test/java/com/loopers/interfaces/api/ContractClassificationTest.java)의 assertion과 동일하다.

| 입력 | HTTP status | `meta.result` | `meta.errorCode` | `data` 유무 |
| --- | ---: | --- | --- | --- |
| 정상 숫자: 존재하는 ID | 200 | `SUCCESS` | 없음 (`null`) | 있음 (조회한 예시 객체) |
| 숫자가 아닌 `abc` | 400 | `FAIL` | `Bad Request` | 없음 (`null`) |
| 존재하지 않는 숫자 ID | 404 | `FAIL` | `Not Found` | 없음 (`null`) |
| 미매핑 URL | 404 | `FAIL` | `Not Found` | 없음 (`null`) |

## 확인된 사실 2개

아래는 사용자가 제공한 과제 안내에 명시된 규칙이다. 현재 코드에 구현되어 있는지를 확인한 결과와는 구분한다.

출처: 제공된 과제 안내의 `INV-001 · 주문 소유권`, `INV-004 · 확정 결과 보존`.

| 참조 ID    | 규칙 ID | 확인된 사실 |
|----------| --- | --- |
| FACT-001 | INV-001 | 구매자는 자신이 소유한 주문만 변경할 수 있다. 다른 `X-USER-ID`로 같은 주문을 요청하면 주문의 존재를 노출하지 않고 거절한다. |
| FACT-002 | INV-004 | 주문 확정 이후에는 확정된 할인 금액이 변경되지 않는다. 이후 할인 정책이 바뀌더라도 이미 저장된 주문의 확정 금액을 유지한다. |

## 실습 장면의 조건 4개

출처는 사용자가 제공한 과제 안내의 “주문 처리에서 함께 지켜야 할 네 규칙”이다.
해당 네 규칙을 이 문서의 실습 조건으로 분류하며, 실제 제품 전체에 적용되는 정책인지까지 확정한 것은 아니다.

| 참조 ID | 규칙 ID | 실습 조건 |
| --- | --- | --- |
| COND-001 | INV-002 | 주문 확정 전에 구매자가 보유한 쿠폰을 한 주문에 최대 한 장 적용할 수 있다. |
| COND-002 | INV-003 | `finalAmount = originalAmount - discountAmount`이며, `0 <= discountAmount <= originalAmount`를 만족한다. |
| COND-003 | INV-005 | 같은 주문과 쿠폰으로 다시 요청하면 저장된 결과를 반환하며, 할인을 중복해서 적용하지 않는다. |
| COND-004 | INV-006 | 쿠폰 만료 여부는 요청 시작 시각을 기준으로 판단한다. |

확인 필요: 요청 시작 시각이 만료 시각과 정확히 같은 경우의 허용 여부는 제공된 문장만으로 확정하지 않는다.

## 도구 제안 검토 기록

질문 내용을 반복한 항목은 제외하고, 근거 없이 기능을 추가하거나 처리 기준을 단정할 수 있는 제안만 기록한다.

| 제안 ID | 관련 질문 | 도구가 제시한 정책 후보 | 출처·근거 | 판정 | 이유 |
| --- | --- | --- | --- | --- | --- |
| SUG-001 | Q-004 | 시스템이 쿠폰 한 장을 추천하거나 자동 선택하고, 선택 기준을 안내한다. | 사용자의 쿠폰 선택 질문을 AI가 구체화한 선택지. 추천·자동 선택 기능에 대한 제품 근거는 없음. | 보류 | 한 장 적용 규칙만으로 추천·자동 선택 기능까지 필요한 것은 아니다. 불필요한 기능 확장을 막기 위해 제품 담당자 확인 전에는 추가하지 않는다. |
| SUG-002 | Q-005 | 요청 시작 시각이 쿠폰 만료 시각과 정확히 같으면 만료로 처리한다. | AI가 검토 방법을 설명하며 든 예시. COND-004에는 등호 처리 기준이 없음. | 보류 | 설명용 예시만으로 사용 가능 여부를 결정하지 않는다. 경계 시각의 허용 여부는 Q-005의 답변으로 확인한다. |

## 외부 계약과 내부 경계

### 외부 계약

과제에서 제시한 method·path, 쿠폰 ID 요청, 주문·금액 응답 구성을 사용한다.

| 항목 | 계약 |
| --- | --- |
| method · path | `POST /api/v1/orders/{orderId}/discount` |
| 사용자 식별 | 필수 `X-USER-ID` 헤더: 비어 있지 않은 문자열. 실습용이며 운영 인증을 대신하지 않는다. |
| request | `application/json`, 본문 `{"couponId": 201}`. `orderId`·`couponId`는 양의 정수(`Long` 범위). 금액은 서버가 계산한다. |
| success | `200 OK`, `meta.result = SUCCESS`. `meta.errorCode`·`meta.message`는 생략한다. |
| 성공 데이터 | `data`에 `orderId`, `originalAmount`, `discountAmount`, `finalAmount`를 반환한다. |
| error meaning | `meta.result = FAIL`, `meta.errorCode`·`meta.message`를 반환하고 `data`는 생략한다. status·오류 의미는 아래 표를 따른다. |
| 재요청 | 소유권 확인 후 저장된 성공 결과를 반환한다(`INV-005`). 이후 확정·만료됐어도 재계산하지 않는다. |

### 오류 계약

아래 업무 코드·매핑은 **새 설계**다. 기존 예시 API의 `Bad Request`·`Not Found` 같은 관찰 결과는 변경하지 않는다.

| HTTP status | `meta.errorCode` | 발생 상황 | 외부 응답의 의미 |
| ---: | --- | --- | --- |
| 400 | `INVALID_REQUEST` | 필수 헤더·본문·값 누락, 잘못된 ID 형식·범위 | 요청 형식이나 필수 값을 수정해야 한다. |
| 404 | `ORDER_NOT_FOUND` | 없는 주문 또는 다른 사람의 주문 | 두 경우 모두 같은 코드와 메시지: `주문을 찾을 수 없습니다.` |
| 404 | `COUPON_NOT_AVAILABLE` | 없는 쿠폰 또는 본인이 보유하지 않은 쿠폰 | 보유 쿠폰을 찾을 수 없다. 두 경우를 외부에서 구분하지 않는다. |
| 409 | `ORDER_ALREADY_CONFIRMED` | 이미 확정된 주문에 새로운 쿠폰 적용 요청 | 현재 주문 상태에서는 새로 적용할 수 없다. |
| 409 | `COUPON_EXPIRED` | 신규 요청의 시작 시각이 쿠폰 만료 시각보다 늦음 | 만료된 쿠폰이므로 적용할 수 없다. **정확히 같은 시각은 미정이다.** |
| 500 | `INTERNAL_ERROR` | 예상하지 못한 서버 오류 | 서버가 정상적으로 처리하지 못했다. 내부 상세는 숨긴다. |

| 주의할 상황 | 처리 기준 |
| --- | --- |
| 업무 판단 순서 | 형식 검증 후, 소유권 확인 → 저장된 동일 요청 결과 확인 → 신규 적용 검증 순서를 따른다. |
| 서버 계산 결과가 금액 범위를 벗어남 | 요청에 금액이 없으므로 곧바로 사용자 입력 오류인 `400`으로 분류하지 않는다. 잘못된 결과를 저장·성공 반환하지 않고 원인에 맞게 처리한다. |
| 현재 코드와의 차이 | W2에서 입력 검증과 업무 오류 매핑을 추가·검증해야 한다. 현재 공통 예외 처리만으로 위 응답이 보장되지는 않는다. |

### 내부 경계에 관한 세 결정

| 결정 ID | 선택 | 버린 대안 | 선택 이유 |
| --- | --- | --- | --- |
| DEC-001 | **오류 구분:** HTTP status + 업무 오류 코드. API 계층이 내부 실패를 외부 계약으로 변환한다. | 모든 실패를 `400`과 같은 메시지로 반환 | 요청 형식·자원 접근·상태 문제를 구분한다. 단, 주문 존재를 숨기는 경우는 같은 응답을 쓴다. |
| DEC-002 | **결과 보존:** 적용 결과와 확정 결과의 snapshot을 구분해 저장한다. | 조회·재요청마다 최신 정책으로 재계산 | 확정 금액과 동일 요청 결과가 바뀌면 `INV-004·005`를 위반한다. |
| DEC-003 | **처리 순서:** `OrderDiscountFacade`가 호출 순서와 트랜잭션을 맡는다. | 컨트롤러가 여러 서비스를 직접 순서대로 호출 | 절차 중복을 막고, 내부 순서 변경이 외부 API에 영향을 주지 않게 한다. |

### snapshot 저장 기준

snapshot은 **계산 당시의 결과를 나중에도 그대로 사용할 수 있도록 저장한 값**이다.

| 구분 | 저장할 내용 | 사용·변경 기준 | 관련 규칙 |
| --- | --- | --- | --- |
| 쿠폰 적용 결과 | 주문·쿠폰 식별값, 적용 당시 원금·할인액·최종 금액 | 동일 요청에 그대로 반환. 추가 효과를 만들지 않는다. | INV-005 |
| 주문 확정 결과 | 확정 시 정해진 금액 | 정책 변경 후에도 재계산하거나 덮어쓰지 않는다. | INV-004 |

### 내부 책임과 호출 순서

#### 구성요소별 책임

| 구성요소 | 맡는 책임 |
| --- | --- |
| 요청 진입 계층 | 서버 요청 시작 시각을 한 번 확보한다. |
| 컨트롤러 | 요청 형식을 검증하고 Facade의 적용 기능 하나를 호출한다. 내부 검증·저장 순서는 알지 않는다. |
| `OrderDiscountFacade` | 도메인·저장소 호출 순서와 트랜잭션을 조율한다. |
| 도메인 | 소유권·쿠폰 조건·금액 규칙을 검증하고 계산한다. |
| 저장소 | 데이터 조회·저장을 담당한다. |

| 호출 계약 | 내용 |
| --- | --- |
| 설계 이름 | `OrderDiscountFacade.applyDiscount` — 새로 구현할 이름이며 현재 존재하는 코드가 아니다. |
| 전달값 | `userId`, `orderId`, `couponId`, `requestedAt` |
| 컨트롤러가 알아야 할 것 | 위 기능의 입력과 결과. 내부 서비스 호출 순서는 Facade 안에 숨긴다. |

#### 처리 순서

| 순서 | 처리 | 결과·다음 동작 |
| ---: | --- | --- |
| 0 | 요청 진입 시각 확보, 요청 형식 검증 | 서버가 확보한 `requestedAt`과 검증된 입력을 Facade로 전달한다. |
| 1 | 주문 조회·소유권 확인 | 없거나 타인의 주문이면 동일한 `ORDER_NOT_FOUND` 응답으로 종료한다. |
| 2 | 같은 주문·쿠폰의 성공 결과 조회 | 있으면 **저장된 결과를 반환하고 종료**한다. 없으면 신규 적용 검증으로 진행한다. |
| 3 | 신규 적용 조건 검증 | 주문 확정 여부·쿠폰 보유 여부·한 장 제한·만료 여부를 확인한다. 만료 판단에는 `requestedAt`을 사용한다. |
| 4 | 금액 계산·범위 검증 | `INV-003`의 계산식과 범위를 만족하는지 확인한다. |
| 5 | 적용 결과·관련 상태 변경 저장 | 하나의 트랜잭션으로 저장하고, 저장 성공 후 결과를 반환한다. |
