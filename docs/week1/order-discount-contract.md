# [W1] 주문 쿠폰(할인) 설계

## 1. 기준 문장
> 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 합니다.
> (출처: 1주차 실습 · 모호한 쿠폰 요구를 구현 가능한 설계로 바꾸기 - 기준문장)

문장에 직접 적힌 약속. 그대로 지키고, 불변식과 성공 조건에 반영한다.

## 7. 외부 계약과 내부 경계

### 7.1 외부 계약 — 기본 장면

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| method · path | `POST /api/v1/orders/{orderId}/discount` | 주문에 종속된 하위 자원에 대한 상태 변경이므로 POST. 주문 ID는 자원의 위치이니 URL. |
| 사용자 식별 | `X-USER-ID` 요청 헤더 | 본문에 `userId`를 받으면 요청자가 자기 신원을 스스로 주장하게 된다. 신원은 요청 파라미터가 아니라 요청의 맥락이므로 헤더로 분리한다. |
| request | `{ "couponId": 200 }` | C-01(한 주문에 한 장)이라 단수 필드다. 배열이나 우선순위 필드를 미리 넣지 않는다. |
| success | `200 OK` — `data`에 `{ orderId, originalAmount, discountAmount, finalAmount }` | INV-003의 등식을 요청자가 응답만으로 검산할 수 있는 최소 집합. 생성이 아니라 기존 주문의 상태 변경이므로 `201`이 아니다. |
| error meaning | 7.2 표 | 상태 코드만이 아니라 **요청자의 다음 행동**까지 계약에 포함한다. |

**명세의 기본 장면과 다른 부분**
응답 본문을 날것의 `{ orderId, ... }`로 두지 않고, 이 저장소에 이미 있는 `ApiResponse` 봉투(`meta` + `data`)의
`data` 안에 넣는다. 필드 이름(주문·원금·할인·최종 금액)과 method·path·request는 명세 그대로다.
이유는 문서 앞머리의 관찰이다 — 기존 `/api/v1/examples`가 이미 `meta.result` / `meta.errorCode` / `data` 형태로 답하고 있어서,
주문 할인만 다른 봉투를 쓰면 요청자가 **엔드포인트마다 다른 성공·실패 판정 규칙**을 알아야 한다.
계약의 일관성이 필드 하나를 줄이는 것보다 크다고 봤다.

### 7.2 실패의 의미 — 요청자의 다음 행동

`errorCode` 값은 이미 존재하는 `ErrorType`(`BAD_REQUEST` / `NOT_FOUND` / `CONFLICT`)의 코드를 그대로 쓴다.
새 열거 상수를 추가하지 않아도 세 가족이 전부 표현된다.

| 상황 | status | errorCode | 요청자의 다음 행동 | 관련 규칙 |
| --- | --- | --- | --- | --- |
| 주문 없음 **또는** 주문 소유자 다름 | `404` | `Not Found` | 주문 목록에서 다시 확인한다. 두 경우를 구분해 알려주지 않는다. | INV-001 |
| 이미 확정된 주문 | `409` | `Conflict` | 확정 주문은 되돌릴 수 없다. 다음 주문에 쓴다. | INV-002 |
| 이미 다른 쿠폰이 적용됨 | `409` | `Conflict` | 기존 쿠폰을 해제한 뒤 재시도한다. | INV-002 / Q-01·Q-03 |
| 쿠폰 없음 **또는** 쿠폰 보유자 다름 | `404` | `Not Found` | 보유 쿠폰 목록에서 다시 고른다. | INV-001 |
| 쿠폰 기간 만료 | `400` | `Bad Request` | 다른 쿠폰을 고른다. 보낸 값을 고치면 되는 실패다. | INV-006 |
| 같은 (주문, 쿠폰) 재요청 | `200` | — | 추가 행동 없음. 첫 결과를 그대로 받는다. | INV-005 |

**`403`이 아니라 `404`인 이유:** `403`은 "그 주문은 있는데 네 것이 아니다"를 알려준다.
INV-001의 가장 작은 반례가 바로 "남의 `X-USER-ID`로 요청했을 때 존재를 노출하지 않고 거절하는가"이므로,
존재 여부를 감추는 쪽을 택했다. 단, 이때 **서버 로그에는 소유권 위반으로 남긴다** — 요청자에게 감추는 것과
운영자에게 감추는 것은 다른 문제다.

**만료를 `400`, 주문 없음을 `404`로 나눈 이유:** 관찰 표의 3번과 4번은 기계 판독 값이 전부 같아서
요청자가 "ID를 다시 찾을지, 경로를 고칠지" 코드로 판단할 수 없었다. 같은 실수를 반복하지 않는다.
`400`은 "네가 보낸 값을 고쳐라", `404`는 "대상을 다시 찾아라", `409`는 "대상의 상태가 허락하지 않는다"로
서로 다른 행동을 지시한다.

**아직 정해지지 않은 것:** Q-01(재적용 시 기존 쿠폰이 유지인지 교체인지)의 답이 "교체"로 오면
세 번째 줄은 `409`가 아니라 `200`이 된다. 답을 받기 전까지는 **덜 파괴적인 쪽**(거절)으로 둔다.
거절을 나중에 교체로 푸는 것은 가능하지만, 교체로 열어둔 계약을 거절로 조이는 것은 이미 나간 응답을 되돌리는 일이다.


### 7.3 내부 경계 — 이 API가 감추는 것

요청자가 아는 것은 "`couponId`를 보내면 최종 금액이 온다" 하나다. 아래 순서는 계약이 아니다.

```
가격 확정 → 쿠폰 조회 → 소유·만료 판정 → 할인액 계산 → 등식 검증 → 스냅샷 고정
```

| 계층 | 책임 | 책임이 아닌 것 |
| --- | --- | --- |
| `OrderV1Controller` | HTTP를 도메인 입력으로 옮긴다. `X-USER-ID`·`orderId`·`couponId`를 꺼내고, 결과를 `ApiResponse`에 담는다. | 소유권·만료·금액 판정. 컨트롤러가 `if (order.getUserId() != userId)`를 쓰기 시작하면 규칙이 HTTP 계층으로 샌다. |
| `OrderDiscountService` | 요청 시작 시각을 한 번 읽고(INV-006), 소유자 조건을 **조회 조건에 함께 걸어** 주문·쿠폰을 가져오고, 트랜잭션 경계와 재요청 판정(INV-005)을 맡는다. | 할인액 계산. 금액 등식. |
| `Order` | 확정 여부와 중복 적용을 스스로 판정하고(INV-002), 계산된 할인액이 `0 ≤ discountAmount ≤ originalAmount`인지 검증한 뒤 값으로 보관한다(INV-003, INV-004). | 쿠폰 종류별 계산식. 정액인지 정률인지 `Order`는 모른다. |
| `Coupon` | 주어진 시각 기준으로 자신이 쓸 수 있는지 답한다 (`isUsableAt(requestedAt)`). | "지금"이 언제인지 스스로 정하지 않는다. 시각은 밖에서 받는다. |
| `DiscountPolicy` | 원금과 쿠폰으로 할인액 하나를 계산한다. | 저장, 주문 상태, 응답 형태. |

경계를 이렇게 그은 기준은 **"쿠폰 정책이 바뀌면 몇 곳을 고치는가"**다.
정률 쿠폰이 추가되면 `DiscountPolicy` 안쪽만 바뀌고 컨트롤러·서비스·응답 스키마는 그대로다.

## 8. 세 결정과 버린 대안

### 8-1. 오류를 구분하는 방식

- **결정** — 실패를 **가족 단위**로 나눈다. 입력을 고치면 되는 실패(`400`) / 대상을 다시 찾아야 하는 실패(`404`) /
  대상의 상태가 허락하지 않는 실패(`409`). 기존 `CoreException` + `ErrorType`을 그대로 쓰고,
  어떤 불변식이 걸렸는지는 `INV-00x`로 **로그와 지표에만** 남긴다.
- **버린 대안** — 불변식마다 예외 클래스 하나씩 (`OrderNotOwnedException`, `CouponExpiredException`,
  `DiscountAlreadyAppliedException` …). 규칙과 예외가 1:1이라 추적이 쉬워 보였다.
- **선택 이유** — 요청자가 오류로부터 얻어야 하는 것은 "어떤 규칙을 어겼는가"가 아니라 **"다음에 무엇을 하면 되는가"**다.
  7.2 표에서 서로 다른 행동을 지시하는 것은 세 가지뿐이고, 예외 클래스를 여섯 개로 늘려도 요청자의 행동은 세 갈래 그대로다.
  규칙이 하나 늘 때마다 클래스가 하나 늘고, 그 클래스가 응답 코드와 묶이면 **도메인 타입이 HTTP 계약에 고정**된다.
- **이 결정이 틀리면 바뀌는 것** — 같은 `409` 안에서 복구 절차가 실제로 갈리면(예: "확정됨"은 재시도 불가,
  "다른 쿠폰 적용됨"은 해제 후 재시도 가능) 그때 `meta.message`가 아니라 기계 판독 가능한 하위 코드를 추가한다.
  status와 예외 계층은 건드리지 않는다.

### 8-2. snapshot 과 재계산

- **결정** — 할인 적용 시점의 `originalAmount` / `discountAmount` / `finalAmount`와 판단 근거(적용 쿠폰, 적용 시각)를
  **값으로 고정 저장**한다. 이후 조회는 저장된 값을 읽기만 한다.
- **버린 대안** — 주문을 조회할 때마다 현재 쿠폰 정책으로 다시 계산한다. 저장 필드가 줄고 정책 변경이 즉시 반영된다.
- **선택 이유** — 재계산은 과거에 확정된 금액을 나중에 바꿔버린다. (F-02와 INV-004를 어긴다.)
  10% 쿠폰으로 9,000원에 확정한 주문이, 쿠폰 정책이 20%로 바뀐 뒤 조회하면 8,000원으로 보이는 것은
  결제·정산·고객 문의의 기준이 사라진다는 뜻이다. 저장 공간이 아니라 불변식 때문에 스냅샷이다.
- **이 결정이 틀리면 바뀌는 것** — "현재 값이 곧 계약"인 화면(실시간 견적 등)에서는 스냅샷이 오히려 틀린 답이다.
  그런 화면이 생기면 **확정 전 견적**과 **확정된 주문**을 다른 경로로 분리한다. 이 API는 후자로 남는다.

### 8-3. 호출 순서를 숨길 책임 경계

- **결정** — `order.applyDiscount(coupon, requestedAt)` 하나 뒤에 7.3의 여섯 단계를 전부 둔다.
  호출자가 넘기는 것은 쿠폰과 시각뿐이고, 판정과 계산과 고정은 안에서 끝난다. 작은 인터페이스, 깊은 모듈.
- **버린 대안** — 애플리케이션 계층에서 조회 → 검증 → 계산 → 저장을 차례로 조립한다.
  각 단계가 밖에서 보여 흐름을 읽기 쉽고, 단계별로 갈아끼우기 좋다.
- **선택 이유** — 조립 방식이면 **순서 자체가 계약이 된다.** 새 호출부가 생길 때마다 "검증을 계산 앞에 불러야 한다"를
  사람이 기억해야 하고, 한 곳이라도 순서를 빠뜨리면 INV-002·INV-003이 조용히 깨진다.
  불변식은 호출 규율이 아니라 타입 안에서 지켜져야 한다. 시각만 밖에서 주입하는 것은 테스트에서 만료 경계를
  고정해야 하기 때문이고(INV-006), 그 외에는 밖으로 내보내지 않는다.
- **이 결정이 틀리면 바뀌는 것** — C-01을 철회해 복수 쿠폰이 허용되면 적용 순서 정책이 이 메서드 **안으로** 들어온다.
  시그니처는 `applyDiscounts(coupons, requestedAt)`로 넓어지지만 호출부가 아는 것은 여전히 늘지 않는다.

요청자는 **ID를 다시 찾아야 하는지, 경로를 고쳐야 하는지**를 코드로 구분할 수 없다.
