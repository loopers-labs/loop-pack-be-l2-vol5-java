# 주문 할인(쿠폰) 계약 — Week 1

## 1. 기준 문장

> 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고,
> 확정된 할인 금액은 나중에 바뀌지 않아야 합니다.

- 출처: Loopers Week 1 과제 Guide (기준 문장으로 제시됨)

## 2. 사실 · 조건 · 질문

### 2-1. 확인된 사실 (제품 약속) — 문장이 직접 보장하는 것

| ID | 내용 | 문장 근거 |
|---|---|---|
| F1 | 쿠폰 적용은 주문 확정 **이전**에만 가능하다 | "주문 확정 전에 … 적용할 수 있고" |
| F2 | 확정 시점에 결정된 할인 금액은 이후 어떤 시점에도 바뀌지 않는다 | "확정된 할인 금액은 나중에 바뀌지 않아야" |

### 2-2. 실습 조건 — 문장에 없어서 이번 실습 장면에서 임시로 정한 것

| ID | 내용 | 이렇게 정한 이유 |
|---|---|---|
| C1 | 확정 전 한 주문에는 보유 쿠폰 한 장만 적용한다 | 중복 적용 규칙이 문장에 없음. 가장 단순한 경계 선택 |
| C2 | `finalAmount = originalAmount - discountAmount`이며, 할인액은 0과 원금 사이다 | 초과·음수 시 동작이 미정의. 금액 경계를 닫아 계산을 판정 가능하게 함 |
| C3 | 주문과 쿠폰은 `X-USER-ID`로 식별되는 계정에 귀속되며, 자신이 소유한 주문만 바꿀 수 있다 | 기준 문장의 "**보유** 쿠폰"이 소유 개념을 직접 뒷받침 |
| C4 | 같은 주문·쿠폰 재요청은 저장된 결과를 돌려주고 효과를 늘리지 않는다 | 네트워크 재시도가 흔한 환경에서 중복 요청 규칙이 미정의. 멱등으로 고정 |

### 2-3. 제품 질문 — 실제 제품 담당자에게 물을 것

| ID | 질문 | 답에 따라 달라지는 것 |
|---|---|---|
| Q1 | "주문 확정"은 결제 완료 시점인가, 주문 생성 시점인가? | **저장 데이터** — 할인 금액 스냅샷을 저장하는 시점이 달라짐 |
| Q2 | 확정 후 부분 취소·환불이 발생하면 할인 금액은 쿠폰으로 보상하나, 금액으로 보상하나? | **저장 데이터** — F2 불변 보장에 예외 레코드가 필요한지가 달라짐 |
| Q3 | 쿠폰 유효(만료) 판정의 기준 시각은 적용 요청 시점인가, 주문 확정 시점인가? | **사용자 응답** — 같은 요청이 성공(200)이 되거나 거절(400)이 됨 |
| Q4 | 쿠폰 적용으로 0원 주문이 되는 것을 허용하는가? | **사용자 응답** — 허용 시 그대로 확정, 불허 시 100% 할인 쿠폰 적용이 거절됨 |
| Q5 | 타인 주문에 접근했을 때 주문의 존재를 알려줘도 되는가? | **권한** — 노출 허용이면 403, 비노출이면 404로 응답이 달라짐 |

### 2-4. 도구(AI) 제안의 처리

이 문서 작성에 AI 도구를 사용했다. 도구가 제안했으나 출처(기준 문장·Guide·관찰)가
없는 항목은 제품 정책으로 바로 채택하지 않고 아래와 같이 처리했다.

| 도구 제안 | 처리 | 이유 |
|---|---|---|
| Long 범위를 초과하는 숫자 ID는 400으로 취급된다 | **보류** | 2026-09-10 실행으로 관찰된 사실이나, Guide의 네 입력에 없어 관찰 표에서 제외. 참고 기록으로만 남김 |
| 확정된 주문에 적용 시도 시 409 CONFLICT | **채택(실습 한정)** | 기존 `ErrorType.CONFLICT`가 존재해 시스템 규약과 정합. 제품 정책 확정은 Q1 답변 이후 |

작성자 자신의 아이디어였던 "쿠폰에 제품/카테고리별 적용 대상 제한"은 기준 문장·Guide에
근거가 없어 이번 장면의 범위 밖으로 **보류**했다 (도구 제안이 아니므로 위 표에서 제외).

## 3. 관찰 표 — `ContractClassificationTest`의 네 HTTP 입력

2026-09-10, `./gradlew :apps:commerce-api:test --tests 'com.loopers.interfaces.api.ContractClassificationTest'`
실행으로 관찰한 값이며, 테스트의 assertion과 동일하다.

| 입력 | HTTP status | meta.result | errorCode | data 유무 | 분류 |
|---|---|---|---|---|---|
| 정상 숫자 ID (`/api/v1/examples/{존재하는 id}`) | 200 | SUCCESS | 없음 | 있음 | Fact |
| 숫자가 아닌 ID (`/api/v1/examples/abc`) | 400 | FAIL | Bad Request | 없음 | Fact |
| 존재하지 않는 숫자 ID (`/api/v1/examples/999999`) | 404 | FAIL | Not Found | 없음 | Fact |
| 미매핑 URL (`/api/v1/no-such-resource`) | 404 | FAIL | Not Found | 없음 | Fact |

관찰의 핵심: ① 성공/실패 모두 `meta + data` 봉투가 유지된다 (미매핑 URL조차).
② "없는 리소스"와 "없는 경로"는 외부에서 구분 불가능한 동일 404다 — 이 성질이
INV-001의 "존재를 노출하지 않는 404" 결정을 뒷받침한다.

## 4. 여섯 규칙 (INV-001..006)과 반례

번호는 W2 이후 문서·테스트·지표에서 같은 뜻으로 재사용하며, 의미를 바꿔 재사용하지 않는다.

| 규칙 ID | 출처 구분 | 규칙 | 깨지는 입력 (반례) | 기대 결과 (외부 응답) | 책임 후보 |
|---|---|---|---|---|---|
| INV-001 | 실습 조건 (C3) | 구매자는 자신이 소유한 주문만 바꾼다 | 다른 `X-USER-ID`로 같은 주문에 할인 적용 요청 | 404 — 주문 존재를 노출하지 않고 거절 (관찰 표 ②) | application (파사드의 소유권 검증) |
| INV-002 | 실습 조건 (C1) | 확정 전 한 주문에는 보유 쿠폰 한 장만 적용한다 | 쿠폰이 적용된 주문에 다른 쿠폰으로 재요청 | 409 — 기존 적용 유지, 교체는 해제 후에만 | domain (주문의 쿠폰 적용 규칙) |
| INV-003 | 실습 조건 (C2) | `finalAmount = originalAmount - discountAmount`, `0 <= discountAmount <= originalAmount` | 원금보다 할인액이 큰 쿠폰 적용 요청 | 400 — 적용 거절, 주문 금액 무변화 | domain (금액 계산) |
| INV-004 | 제품 약속 (F2) | 주문 확정 뒤 할인 금액은 바뀌지 않는다 | 할인 정책을 10%→20%로 변경한 뒤 확정 주문 재조회 | 200 — 정책 변경 전 저장된 `finalAmount` 그대로 응답 | domain + 저장 (확정 시점 스냅샷) |
| INV-005 | 실습 조건 (C4) | 같은 주문·쿠폰 재요청은 저장된 결과를 돌려주고 효과를 늘리지 않는다 | 동일 `orderId`+`couponId`로 연속 2회 요청 | 200 — 두 응답의 금액 동일, 할인은 1회만 반영 | application (멱등 처리) |
| INV-006 | 제품 질문 (Q3의 잠정 답) | 만료 여부는 요청 시작 시각으로 판단한다 | 요청 시작 시엔 유효했으나 처리 중 만료되는 쿠폰 | 200 — 요청 시작 시각 기준으로 적용 성공 | domain (유효성 판정의 기준 시계) |

## 5. 외부 계약과 내부 경계

### 5-1. 외부 계약 (W2 기본 장면)

Guide의 기본 장면을 그대로 채택한다 (차이 없음).

- **method · path**: `POST /api/v1/orders/{orderId}/discount`
- **사용자 식별**: `X-USER-ID` 요청 헤더
- **request**: `{ "couponId": <쿠폰 ID> }`
- **success (200)**: `ApiResponse` 봉투의 `data`에 주문 ID, `originalAmount`, `discountAmount`, `finalAmount`
- **error meaning**:
  - 400 `Bad Request` — 형식 오류(숫자가 아닌 ID 등) 및 규칙 위반(INV-003 금액 경계, 만료 쿠폰)
  - 404 `Not Found` — 주문/쿠폰이 없거나, 내 소유가 아님 (INV-001, 존재 비노출)
  - 409 `Conflict` — 주문 상태와 충돌 (확정된 주문에 적용 시도 F1, 이미 다른 쿠폰 적용 INV-002)

응답 봉투는 관찰 표에서 확인된 기존 `ApiResponse<T>` 규약(meta + data)을 따른다.

### 5-2. 내부 경계의 세 결정 (버린 대안과 이유)

| 결정 | 선택 | 버린 대안 | 이유 |
|---|---|---|---|
| 오류를 구분하는 방식 | 상태 코드(400/404/409) + 기존 `ErrorType` 코드와 메시지로 구분 | 사유별 커스텀 에러 코드 체계(`EXPIRED_COUPON` 등) 신설 | 관찰 표에서 확인된 기존 규약만으로 세 오류가 구분됨. 코드 체계 신설은 관찰 근거 없는 확장 |
| snapshot과 재계산 | 확정 시점에 `discountAmount`/`finalAmount`를 저장(스냅샷)하고 이후 재계산하지 않음 | 조회 시마다 현재 정책으로 재계산 | 재계산은 정책 변경 시 INV-004(확정 결과 보존)를 구조적으로 위반함 |
| 호출 순서를 숨길 책임 경계 | 파사드가 소유권 검증→유효성 판정→적용→저장을 한 유스케이스로 캡슐화, 외부에는 요청 1회만 노출 | 검증 API와 적용 API를 분리해 클라이언트가 순서대로 호출 | 클라이언트에 순서가 노출되면 순서 위반·중간 상태 경합이 가능해져 INV-005 멱등 보장이 어려움 |

## 6. 규칙이 깨지면 (영향 추적)

| 항목 | 깨질/답변될 경우 영향 |
|---|---|
| C1 (쿠폰 1장) | INV-002 폐기, 5-1 request가 단수 → 복수(`couponIds`) 구조로 변경, INV-003 재검토 |
| C4 (멱등) | INV-005 폐기 시 중복 할인 방지 책임이 클라이언트로 이동 — 5-2 세 번째 결정 재검토 |
| Q1 답변 (확정 = 주문 생성) | 쿠폰 적용 구간이 사라져 F1 재정의, INV-004 스냅샷 시점 변경 |
| Q3 답변 (판정 = 확정 시점) | INV-006 재정의, 적용 성공 후 확정 시 거절되는 새 오류 케이스가 5-1에 추가 |
| Q4 답변 (0원 주문 불가) | INV-003 하한이 `0 <`로 변경, 100% 할인 쿠폰 적용이 400으로 거절됨 |
| Q5 답변 (존재 노출 허용) | INV-001 기대 결과가 404 → 403으로 변경, 관찰 표 ②의 근거 효력 상실 |
