# 주문 쿠폰 적용 · 설계 기록

## 1. 기준 문장

> 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 한다.

## 2. 사실과 실습 조건

| 분류 | 내용 | 규칙 |
| --- | --- | --- |
| 사실 | 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있다 | INV-001, UC-01 시작 조건 |
| 사실 | 확정된 할인 금액은 이후에도 유지된다 | INV-004 |
| 실습 조건 | 한 주문에는 쿠폰 한 장만 적용한다 | INV-002 |
| 실습 조건 | `finalAmount = originalAmount - discountAmount` | INV-003 |
| 실습 조건 | 같은 요청은 첫 결과를 재사용한다 | INV-005 |
| 실습 조건 | 만료는 요청 시작 시각으로 판단한다 | INV-006 |

## 3. 담당자가 답할 질문과 임시로 둔 판단

임시로 둔 판단은 답을 기다리는 동안 선택한 것이며 구현에 들어간다. 판단이 없는 행은 이번 범위에서 다루지 않는다.

| 번호 | 질문 | 임시로 둔 판단 | 답에 따라 바뀌는 것 |
| --- | --- | --- | --- |
| Q-01 | 운영자도 다른 사람의 주문에 쿠폰을 적용할 수 있는가? | — (범위 밖) | 권한 — 누가 어느 주문을 바꿀 수 있는가 |
| Q-02 | 이미 사용한 쿠폰은 다시 쓸 수 없는가? | 쓸 수 없다 (보유 쿠폰이 아니다) | 데이터 — 쿠폰의 사용 상태가 갖는 의미 |
| Q-03 | 쿠폰 사용 불가 사유를 요청자에게 구분해 알려주는가? | 구분하지 않는다 — 없음·미보유·만료·이미 사용 모두 다음 행동이 "다른 쿠폰 선택"으로 같다 | 사용자 응답 — 실패 행 수와 오류 코드 |
| Q-04 | 할인액이 원금보다 크면 전액 할인인가, 거절인가? | 원금까지로 제한한다 (전액 할인) | 사용자 응답 — 성공인지 실패인지 |
| Q-05 | 확정 전에 적용한 쿠폰을 구매자가 바꾸거나 해제할 수 있는가? | 없다. 한 번 적용하면 확정까지 유지된다 | 데이터 — 주문의 쿠폰이 변경 가능한 값인지 |

### 도구가 제안했으나 채택하지 않은 것

| 제안 | 처리 | 이유 |
| --- | --- | --- |
| 쿠폰 소유권을 별도 규칙(INV-007)으로 추가 | 거절 | 기준 문장의 "보유"로 이미 표현되며, 규칙은 INV-001~006으로 고정한다 |
| 확정 사건의 대안으로 "결제 완료" | 거절 | 이번 범위에 결제가 없고 출처가 없다 |

## 4. 용어

### 주문 상태

| 상태 | 의미 | 진입 |
| --- | --- | --- |
| `DRAFT` | 구매자가 구성 중인 주문. 판매자에게 이행 의무가 없다 | 초기 상태 |
| `PLACED` | 판매자에게 이행 의무가 생긴 주문. 품목·배송지 등 내용이 바뀌지 않는다 | 확정 성공 시 |

### 확정 (사건)

구매자의 제출로 주문을 `DRAFT`에서 `PLACED`로 바꾼다.

### 보유 쿠폰

요청자에게 발급되었고 아직 사용되지 않은 쿠폰.

### 만료

쿠폰의 유효 기간이 끝난 상태. 만료 여부를 판단하는 시각은 요청 시작 시각이다 (INV-006).

### 금액

- `originalAmount` — 주문 품목 합계
- `discountAmount` — 쿠폰이 만든 할인액
- `finalAmount` — `originalAmount - discountAmount`

## 5. 액터와 사용 장면

```
UC-01: 주문에 쿠폰 적용
주 사용자: 구매자
시작 조건: 요청자가 소유한 주문이며 상태가 `DRAFT`다
시작 사건: 구매자가 couponId를 지정해 적용을 요청한다
성공 결과: 주문에 쿠폰이 적용되고 할인액·최종 금액이 기록되어 반환된다
실패 결과: 주문 없음 / 주문 소유자 다름 / 주문이 확정됨 / 주문에 이미 쿠폰이 적용됨 / 쿠폰 사용 불가
종료 조건: 이후 주문이 `PLACED`가 되면 기록된 할인액·최종 금액은 정책·가격 변화에도 바뀌지 않는다
```

## 6. 불변식

| 번호 | 출처 | 규칙 | 깨지는 입력 | 기대 결과 | 책임 후보 |
| --- | --- | --- | --- | --- | --- |
| INV-001 | 제품 약속 | 구매자는 자신이 소유한 주문만 바꾼다 | 주문 소유자가 아닌 `X-USER-ID`로 적용 요청 | 거절되며 주문 존재가 드러나지 않는다 → 404 `ORDER_NOT_FOUND` | 주문 조회 (소유자 확인), HTTP 변환 (존재 미노출) |
| INV-002 | 실습 조건 | `DRAFT` 주문에는 보유 쿠폰이 최대 한 장 적용된다 | 쿠폰이 적용된 주문에 다른 쿠폰 적용 요청 | 거절되며 기존 적용이 유지된다 (Q-05) → 409 `COUPON_ALREADY_APPLIED` | 주문 (할인 적용) |
| INV-003 | 실습 조건 | `finalAmount = originalAmount - discountAmount`, `0 ≤ discountAmount ≤ originalAmount` | 원금 10,000원 주문에 할인액 12,000원짜리 쿠폰 | 할인액 10,000원, 최종 금액 0원 (Q-04) → 200 | 주문 (할인 계산) |
| INV-004 | 제품 약속 | `PLACED` 주문의 할인액·최종 금액은 이후 바뀌지 않는다 | 10% 정책으로 `PLACED` → 정책을 20%로 변경 | 저장된 할인액이 확정 당시 값 그대로 | 주문 (확정 시 금액 고정) |
| INV-005 | 실습 조건 | 같은 주문·쿠폰 재요청은 저장된 결과를 돌려주고 효과를 늘리지 않는다 | 같은 주문·쿠폰으로 적용 요청 두 번 | 두 번째 응답이 첫 번째와 같고 할인액이 누적되지 않는다 → 200, 같은 본문 | 주문 (이미 적용된 쿠폰 판별) |
| INV-006 | 실습 조건 | 만료 여부는 요청 시작 시각으로 판단한다 | 시작 시각엔 유효, 처리 중 만료되는 쿠폰 | 성공 → 200 | 요청 수신 경계 (시각 고정), 쿠폰 (만료 판정) |

## 7. 기존 동작 관찰 · Example API

| 입력 | status | `meta.result` | `meta.errorCode` | `meta.message` | `data` |
| --- | --- | --- | --- | --- | --- |
| `GET /api/v1/examples/{테스트에서 저장한 ID}` | 200 | `SUCCESS` | `null` | `null` | 있음 |
| `GET /api/v1/examples/abc` | 400 | `FAIL` | `BAD_REQUEST` | `파라미터 exampleId 값 abc 잘못됨` | `null` |

| `GET /api/v1/not-mapped` | 404 | `FAIL` | `NOT_FOUND` | `존재하지 않는 요청입니다.` | `null` |

## 8. 인터페이스

### 요청

```
POST /api/v1/orders/{orderId}/discount
X-USER-ID: {요청자 식별자}
Content-Type: application/json

{ "couponId": 42 }
```

### 성공 응답 · 200

```json
{
  "meta": { "result": "SUCCESS", "errorCode": null, "message": null },
  "data": {
    "orderId": 1001,
    "couponId": 42,
    "originalAmount": 30000,
    "discountAmount": 3000,
    "finalAmount": 27000
  }
}
```

같은 `orderId`·`couponId` 재요청도 200이며 본문이 같다 (INV-005).

### 실패 응답

본문 형식은 공통이며 `data`는 항상 `null`이다.

```json
{
  "meta": { "result": "FAIL", "errorCode": "ORDER_NOT_FOUND", "message": "..." },
  "data": null
}
```

| 실패 의미 | 조건 | HTTP | `meta.errorCode` | 요청자의 다음 행동 | 근거 |
| --- | --- | --- | --- | --- | --- |
| 문법 오류 | `orderId`가 숫자가 아님, `couponId` 누락·비숫자 | 400 | `INVALID_REQUEST` | 입력 수정 | 관찰 2행 |
| 대상 주문 없음 | 주문이 없거나 요청자 소유가 아님. 두 경우 status·errorCode·message가 모두 같아야 한다 | 404 | `ORDER_NOT_FOUND` | 주문 재조회 | INV-001 |
| 주문 확정됨 | 주문 상태가 `PLACED` | 409 | `ORDER_ALREADY_CONFIRMED` | 없음 (적용 불가) | UC-01 시작 조건 |
| 이미 쿠폰 적용됨 | 주문에 다른 쿠폰이 적용되어 있음 | 409 | `COUPON_ALREADY_APPLIED` | 없음 (Q-05에 따라 바뀔 수 있음) | INV-002 |
| 쿠폰 사용 불가 | 쿠폰 없음 · 미보유 · 만료 · 이미 사용 | 422 | `COUPON_UNUSABLE` | 다른 쿠폰 선택 | Q-03에 따라 행이 나뉠 수 있음 |
| 처리기 없음 | 매핑되지 않은 경로 | 404 | 현재 `NOT_FOUND` | 경로 수정 | 관찰 4행 |

### 현재 동작과 다른 점

| 항목 | 현재 (Example API) | 이 설계 | 이유 |
| --- | --- | --- | --- |
| `meta.errorCode`의 의미 | HTTP reason phrase (`Not Found`) | 안정된 업무 코드 (`ORDER_NOT_FOUND`) | status가 같은 실패(없는 주문 404 vs 없는 경로 404, 확정됨 409 vs 이미 적용 409)를 요청자가 구분해 다음 행동을 고를 수 있어야 한다. 결정 1 참고 |
| `meta.message`의 내용 | 파라미터 이름·값 노출 | 404는 없음·타인 소유가 같은 문장 | INV-001. message가 다르면 주문 존재가 새어 나간다 |
| 422 사용 | starter `ErrorType`에 없음 | `COUPON_UNUSABLE`에 422 | 입력 형식은 맞지만 업무 규칙으로 처리할 수 없는 경우를 400과 분리한다. W2에서 `ErrorType` 추가가 필요하다 |

## 9. 결정과 버린 대안

| 결정 | 선택 | 버린 대안 | 이유 |
| --- | --- | --- | --- |
| 오류를 구분하는 방식 | 실패 의미마다 안정된 업무 코드 하나를 `meta.errorCode`에 두고 HTTP로 변환한다. 요청자의 다음 행동이 같으면 하나로 합친다 | (a) 불변식마다 오류 타입을 일대일로 만든다 (b) 현재 동작처럼 `errorCode`에 reason phrase를 두고 status로만 구분한다 | (a) 규칙이 늘면 타입이 함께 늘고 HTTP 응답이 도메인 타입에 묶인다. (b) 같은 status를 가진 실패를 요청자가 message 문자열로 구분해야 한다. 요청자에게 필요한 건 다음 행동을 고를 정보뿐이다 |
| snapshot과 재계산 | 확정 시 할인액·최종 금액을 저장하고 이후 다시 계산하지 않는다 | 조회할 때마다 현재 정책으로 재계산한다 | INV-004. 재계산은 정책이 바뀌면 확정된 금액을 바꾼다. 재계산은 `DRAFT` 견적에는 맞을 수 있으나 이 범위에 조회가 없다 |
| 호출 순서를 숨길 책임 경계 | 쿠폰 검증·할인 계산·금액 기록을 주문의 한 책임 안에서 한 번에 끝낸다. 요청자는 `couponId`만 넘긴다 | 요청자가 가격 조회 → 쿠폰 조회 → 계산 → 저장 순서를 직접 조합한다 | 순서를 아는 곳이 늘면 정책 변경이 그만큼 퍼지고, 저장을 빼먹거나 두 번 계산하는 경로가 생긴다 (INV-004, INV-005) |
