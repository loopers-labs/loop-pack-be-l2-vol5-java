# 모호한 쿠폰 요구를 구현 가능한 설계로 바꾸기

## 1. 기존 API 관찰값

### 1.1 기존 E2E 기준선

`ExampleV1ApiE2ETest`는 다음 세 경우를 확인한다.

| 입력 | 기대 HTTP status | 확인하는 내용 |
| --- | --- | --- |
| 정상 숫자 ID | 2xx 성공 | 응답 `data`의 ID·이름·설명 |
| 숫자가 아닌 ID `나나` | `400 BAD_REQUEST` | HTTP status |
| 존재하지 않는 숫자 ID `-1` | `404 NOT_FOUND` | HTTP status |

### 1.2 추가 관찰값

`ContractClassificationTest`의 네 실제 HTTP 요청으로 아래 관찰값을 기록한다.  
관찰값은 현재 동작을 재현하는 기준일 뿐, 다음 쿠폰 적용 API의 제품 정책으로 자동 승격하지 않는다.

| 입력 | HTTP status | `meta.result` | `meta.errorCode` | `data` |
| --- | ---: | --- | --- | --- |
| 존재하는 숫자 ID | `200 OK` | `SUCCESS` | 없음 (`null`) | 있음 |
| 숫자가 아닌 ID (`abc`) | `400 BAD_REQUEST` | `FAIL` | `Bad Request` | 없음 (`null`) |
| 존재하지 않는 숫자 ID | `404 NOT_FOUND` | `FAIL` | `Not Found` | 없음 (`null`) |
| 미매핑 URL | `404 NOT_FOUND` | `FAIL` | `Not Found` | 없음 (`null`) |

`errorCode`는 `ErrorType`이 `HttpStatus.getReasonPhrase()`를 그대로 사용하므로 위 문자열로 응답한다.

관찰 결과, 존재하지 않는 리소스와 미매핑 URL은 현재 동일한 `404 NOT_FOUND`와 `Not Found` 오류 코드로 응답한다.

## 2. 요구사항 분류

기준 문장: "구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 한다." 출처는 1주차 실습 발제문이 제시한 기준 문장이다.  
2.1의 `FACT-001`·`FACT-002`는 이 한 문장을 둘로 나눈 것이며, 2.2의 `COND-001`~`COND-004`는 같은 발제문의 실습 장면 조건이다.

이 문서는 확인된 제품 약속, 실습 장면의 조건, 제품 담당자에게 확인할 질문, 설계 결정을 구분해 기록한다.

| 구분 | 과제 용어 | 의미 |
| --- | --- | --- |
| 확인된 제품 약속 | `FACT` | 제품 담당자와 확인된 약속으로, 반드시 지킨다. |
| 실습 장면의 조건 | `COND` | 이번 실습에서 반드시 지키는 조건이며, 실제 제품 정책으로 일반화하지 않는다. |
| 제품 질문 | `Q` | 제품 담당자에게 확인할 미정의 동작이다. |
| 설계 결정 | `DEC` | 학습자가 선택한 계약·책임 경계·대안이다. |

### 2.1 확인된 제품 약속

| ID | 확인된 사실 |
| --- | --- |
| `FACT-001` | 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있다. |
| `FACT-002` | 확정된 할인 금액은 이후에도 유지된다. |

위 두 문장만 현재 확인된 제품 약속으로 취급한다.  

### 2.2 실습 장면의 조건

| ID | 조건 |
| --- | --- |
| `COND-001` | 한 주문에는 쿠폰 한 장만 적용한다. |
| `COND-002` | `finalAmount = originalAmount - discountAmount`로 계산한다. |
| `COND-003` | 같은 요청을 다시 보내면 기존 결과를 재사용한다. |
| `COND-004` | 쿠폰 만료 여부는 요청 시작 시각을 기준으로 판단한다. |

위 조건은 이번 실습에서 반드시 지키되, 실제 서비스의 영구적인 제품 정책으로 일반화하지 않는다.

### 2.3 학습자가 정할 것

| 구분 | 항목 | 상세 위치 |
| --- | --- | --- |
| 미해결 제품 질문 | 실제 제품 담당자에게 물을 질문 3~5개 | 아래 제품 질문, `Q-001`~`Q-004` |
| 설계 결정 | 오류를 구분하는 방식 | 4.4절, `DEC-001` |
| 설계 결정 | snapshot과 재계산 | 5.1절, `DEC-002` |
| 설계 결정 | 호출 순서를 숨길 책임 경계 | 5.2절, `DEC-003` |

#### 제품 질문 (Open Questions)

미해결 제품 질문은 실제 제품 담당자에게 묻고 3~5개로 남긴다.  
답이 달라졌을 때 사용자 응답, 저장 데이터, 권한 중 하나가 달라지는 것만 남긴다.  
`출처` 열은 질문이 어디서 나왔는지를 가리킨다. 답 자체는 모두 미정이며, 받기 전에는 제품 정책으로 취급하지 않는다.  
`Q-*`의 답은 이후 `INV-*`와 `DEC-*`의 세부 계약을 정하는 입력이다. 다만 `FACT`·`COND`만으로 확정된 규칙과 결정까지 답을 기다리지는 않는다.

| ID | 출처 | 질문 | 답에 따라 달라지는 것 |
| --- | --- | --- | --- |
| `Q-001` | `FACT-001` | 주문 할인을 적용할 수 있는 주체는 구매자 본인뿐인가,<br/>운영자가 구매자를 대신해 적용할 수도 있는가? | **권한**<br/>구매자 본인만 허용할지, 운영자 역할에도 대리 적용 권한을 줄지에 따라 할인 적용을 허용할 요청자가 달라진다. |
| `Q-002` | `FACT-001`<br/>`COND-002` | 할인액이 주문 금액과 같거나 클 때 최종 금액 0원을 허용하는가?<br/>주문 금액을 초과한 할인액은 주문 금액까지만 적용하는가, 쿠폰 적용을 거절하는가? | **사용자 응답 + 저장 데이터**<br/>0원 결제 허용 여부와 초과 할인 처리에 따라 성공·실패 응답이 달라진다. 상한 적용 또는 거절에 따라 저장할 할인 결과도 달라진다. |
| `Q-003` | `FACT-002` | 쿠폰 적용 후 주문 확정 전에 상품 가격이 내려가면, 쿠폰 적용 시점의 주문 금액·할인 금액을 유지할 것인가,<br/>변경된 주문 금액을 기준으로 할인 금액을 다시 정할 것인가? | **사용자 응답 + 저장 데이터**<br/>유지하면 적용 시점의 금액으로 확정한다. 다시 계산하면 주문 확정 전 할인액과 최종 금액이 바뀐다. |
| `Q-004` | `COND-001` | 한 주문에 쿠폰이 이미 적용된 상태에서, 다른 쿠폰의 적용 요청은 교체로 처리할 것인가, 거절로 처리할 것인가? | **사용자 응답 + 저장 데이터**<br/>이 질문 하나의 답으로 결정된다. 거절이면 기존 할인 결과를 유지하고 실패를 알린다. 교체면 기존 할인 결과를 새 쿠폰의 결과로 바꾼다. |

### 2.4 도구 제안 검토

도구가 먼저 제안한 제품 동작만 기록한다. 도구 제안은 `FACT`나 `COND`로 바로 채택하지 않으며, 이번 문서에서 제품 답이 필요하면 `Q`로 옮긴다.  
출처가 없거나 이번 범위에서 다루지 않으면 보류하거나 거절한다.

| 도구 제안 | 관련 출처 | 처리 | 이유 |
| --- | --- | --- | --- |
| 운영자가 구매자를 대신해 쿠폰을 적용 | `FACT-001` | `Q-001`로 보류 | `FACT-001`은 구매자만 언급한다. 운영자 대리 적용 허용 여부는 제품 답이 필요하다. |
| 원금 초과 할인 시 0원 결제를 허용하거나, 원금까지만 할인하거나, 쿠폰 적용을 거절 | `FACT-001` · `COND-002` | `Q-002`로 보류 | 계산식은 정해졌지만 최종 금액 0원과 원금 초과 할인 처리 정책은 정해지지 않았다. |
| 쿠폰 적용 후 상품 가격이 바뀌어도 적용 시점의 주문 금액과 할인 금액을 유지 | `FACT-002` | `Q-003`으로 보류 | `FACT-002`는 확정 후 금액만 정한다. 확정 전 가격 변경은 제품 답이 필요하다. |
| 이미 적용된 쿠폰 대신 다른 쿠폰을 적용 | `COND-001` | `Q-004`로 보류 | `COND-001`은 한 주문에 쿠폰이 하나라고만 정한다. 기존 할인을 교체할지 거절할지는 제품 답이 필요하다. |
| 별도의 멱등성 키로 같은 요청을 식별 | `COND-003` | 설계에서 결정 | `COND-003`은 반복 요청의 결과 재사용을 정한다. 별도 멱등성 키를 둘지는 그 조건을 구현하는 기술 선택이며, 제품 정책으로 채택하지 않는다. |
| 쿠폰 적용 후 만료되어도 주문 확정까지 할인 결과를 유지 | `COND-004` | 보류 | `COND-004`는 적용 요청의 시작 시각만 정한다. 주문 확정 전 만료의 효과는 이번 쿠폰 적용 API 범위에서 정하지 않는다. |
| 할인 방식·최소 주문 금액을 정함 | 없음 | 보류 | 정액·정률·상한·최소 주문 금액에 대한 `FACT`·`COND` 근거가 없다. |
| 무료 배송 쿠폰을 제공 | 없음 | 보류 | 무료 배송 쿠폰을 제공한다는 `FACT`·`COND` 근거가 없다. |

## 3. 불변식

어떤 실행 경로를 거쳐도 성공한 상태에서 항상 참이어야 하는 관계다.  
class 이름이 아니라 관찰 가능한 상태 관계로 쓰고, 각 규칙에 깨지는 입력을 하나 이상 붙인다.

| 규칙 ID | 출처 | 규칙                                                                                                                                    | 깨지는 입력 | 기대 결과                                                                                                                                                          | 책임 후보 |
| --- | --- |---------------------------------------------------------------------------------------------------------------------------------------| --- |----------------------------------------------------------------------------------------------------------------------------------------------------------------| --- |
| `INV-001` | `FACT-001`<br/>`Q-001` | 주문의 구매자 또는 `Q-001`의 답으로 허용된 운영자만, 해당 주문의 구매자가 보유한 쿠폰을 적용할 수 있다.                                                                       | ① 구매자가 `U1`인 주문에 `X-USER-ID: U1`로, `U2`가 보유한 쿠폰 `C2`의 적용을 요청<br>② 구매자가 `U1`인 주문에 운영자 권한이 없는 `X-USER-ID: U2`로, `U1`이 보유한 쿠폰 `C1`의 적용을 요청 | ① 할인은 적용되지 않고 `404/FAIL/COUPON_NOT_APPLICABLE/data: null`을 반환한다.<br>② 할인은 적용되지 않고 `404 / FAIL / ORDER_NOT_FOUND / data: null`을 반환한다.<br/>주문 존재 은닉을 위한 외부 응답이다. | 주문은 구매자와 운영자 권한을, 쿠폰은 보유자를 검증한다. |
| `INV-002` | `COND-001`<br/>`Q-004` | 확정 전 한 주문에 동시에 유효한 할인은 최대 하나다.                                                                                                        | 쿠폰 `C1`을 적용한 주문에 쿠폰 `C2` 적용 요청 | `C1`과 `C2`가 동시에 유효하지 않다.<br/>교체인지 거절인지는 `Q-004`의 답으로 정한다.                                                                                                      | 주문이 할인 자리를 하나만 보유한다. |
| `INV-003` | `COND-002`<br/>`Q-002` | 저장되는 할인 결과는 `finalAmount = originalAmount - discountAmount`를 만족하고, `discountAmount`와 `finalAmount`는 음수가 아니다. 이는 음수 금액 저장을 막는 범위 규칙이다. | 원금 `10,000`인 주문에 할인액 `15,000`이 계산되는 요청 | 음수 최종 금액인 결과는 저장되지 않는다. 최종 금액 0원을 성공으로 허용할지와 원금을 초과해 계산된 할인액을 상한 처리할지 거절할지는 `Q-002`의 답으로 정한다.                                                                  | 쿠폰(계산)과 금액 값 객체(범위 검사) |
| `INV-004` | `FACT-002`<br/>`Q-003` | 확정된 주문의 확정 시점 금액 snapshot(`originalAmount`, `discountAmount`, `finalAmount`)은 이후 정책과 가격 변화에도 동일하다.                                    | 주문 확정 후 쿠폰 할인율을 10%에서 20%로 바꾸고 같은 주문을 조회 | 저장된 세 금액이 확정 시점에 굳은 값과 같다.                                                                                                                                     | 확정 시 잠기는 할인 결과 기록 |
| `INV-005` | `COND-003` | 동일 요청의 반복은 할인 효과를 한 번만 남긴다. 주문 확정 후 재전송도 기존 성공 결과를 재사용한다.                                                                             | 쿠폰 적용 성공 후 주문을 확정하고, 같은 요청을 재전송 | `409 ORDER_ALREADY_CONFIRMED`가 아니라 첫 성공 응답과 같은 `200 / SUCCESS / data`를 반환하며 할인액이 누적되지 않는다. 이 API에서 동일 요청은 권한을 통과한 같은 `orderId`와 `couponId` 조합으로 판단한다.                                     | 주문 ID·쿠폰 ID와 첫 할인 결과를 보관하는 할인 결과 기록 |
| `INV-006` | `COND-004` | 만료 판단의 기준 시각은 요청 시작 시각이며, 그 시점에 유효했던 쿠폰은 처리 중 만료되더라도 적용된다.                                                                            | 쿠폰 만료 1초 전에 요청을 시작했지만 처리 중 만료 시각을 지나는 요청 | 요청 시작 시점에는 유효하므로 쿠폰 적용에 성공한다. 처리에 걸린 시간에 따라 결과가 갈리지 않는다.                                                                                                       | 요청 시작 시각을 주입받는 만료 판정 |

출처에 `Q`가 포함된 규칙은 제품 답변에 따라 갱신한다.

### 책임 후보 선택 이유

| 규칙 ID | 선택한 책임 후보 | 선택 이유 |
| --- | --- | --- |
| `INV-001` | 주문과 쿠폰 | 주문 구매자는 주문의 속성이고, 쿠폰 보유자는 쿠폰의 속성이다. 두 값을 각각 확인해야 주문 구매자가 보유한 쿠폰만 적용된다. 운영자 대리 적용은 `Q-001`의 답에 따라 주문 또는 별도 권한 정책이 추가로 판단한다. |
| `INV-002` | 주문 | 적용된 쿠폰의 개수는 주문 할인 상태다. 주문이 할인 자리를 하나만 가지면 한 장 제한을 주문 상태로 유지할 수 있다. |
| `INV-003` | 쿠폰과 금액 값 객체 | 할인액을 계산하는 규칙은 쿠폰의 성질이므로 쿠폰이 맡는다. 금액 값 객체는 계산 결과가 만들어질 때 범위를 검사해 음수 최종 금액이 저장되지 않게 한다. |
| `INV-004` | 할인 결과 기록 | 확정 후 값을 유지하려면 쿠폰이나 상품 가격을 다시 읽지 않고, 확정 시점의 `originalAmount`, `discountAmount`, `finalAmount`를 복사해 보관해야 한다. |
| `INV-005` | 할인 결과 기록 | 주문 ID·쿠폰 ID와 첫 할인 결과를 함께 보관해야 재요청에 기존 결과를 돌려줄 수 있다. |
| `INV-006` | 만료 판정 지점 | 판정 시각을 요청 시작 시각으로 받으면 처리 시간과 무관하게 만료 여부를 판단할 수 있다. |

## 4. 외부 계약

이번 실습은 과제가 제시한 기본 장면을 그대로 따른다. `POST /api/v1/orders/{orderId}/discount`로 `couponId`를 요청하고, 성공하면 주문 ID·원금·할인액·최종 금액을 응답한다.  
이 기본 장면이 구체화하지 않은 사용자 식별은 4.1에서 `X-USER-ID` header로 정한다. method·path·요청 본문·성공 응답은 기본 장면과 다르게 정한 부분이 없다.

### 4.1 요청 계약

새 할인 적용의 전제 조건은 요청자가 구매자이거나 `Q-001`의 답으로 허용된 운영자이고, 요청한 쿠폰은 주문 구매자가 보유하며, 주문이 아직 확정되지 않은 상태다.  
확정된 주문의 새 적용 요청은 실패하며 그 응답은 4.3에 있다. 이미 성공한 동일 요청의 재전송은 4.2의 결과 재사용 규칙을 따른다.

| 항목 | 계약                                  |
| --- |-------------------------------------|
| method | `POST`                              |
| path | `/api/v1/orders/{orderId}/discount` |
| 사용자 식별 | header [`X-USER-ID`]                |
| request | `couponId`                          |

전체 요청 모양은 다음과 같다.

```
POST /api/v1/orders/{orderId}/discount
X-USER-ID: {사용자 식별자}

{ "couponId": "{쿠폰 식별자}" }
```

사용자 식별은 header `X-USER-ID`로 한다. 이는 요청자가 주문의 구매자인지 확인하는 권한 검증용 값이다.  
`Q-001`의 답으로 운영자 대리 적용을 허용하면 이 헤더만으로 역할을 표현할 수 없으므로, 운영자 권한을 전달·검증하는 방식도 함께 바뀐다.  
`X-USER-ID`는 요청자 권한 검증용 값이다. 권한을 통과한 뒤 같은 `orderId`와 `couponId` 조합을 보낸 요청은 동일 요청으로 판정하며, 할인 결과 기록이 첫 성공 결과를 보관한다.

### 4.2 성공 응답

성공 응답의 최상위 구조는 기존 ApiResponse 형식을 유지한다.  
meta에는 처리 결과를, data에는 주문 ID·원금·할인액·최종 금액을 담는다. HTTP status는 200 OK다.

```
{
  "meta": { "result": "SUCCESS", "errorCode": null, "message": null },
  "data": {
    "orderId": "...",
    "originalAmount": 10000,
    "discountAmount": 2000,
    "finalAmount": 8000
  }
}
```

세 금액은 쿠폰 적용 시점에 계산한 결과로 응답한다. 따라서 요청자가 `INV-003`을 스스로 검산할 수 있다.

이미 쿠폰이 적용된 주문에 다시 요청해도 같은 응답 형식이다.  
동일 요청을 다시 보내면 첫 결과를 재사용한다(`INV-005`). 주문이 그 뒤 확정되었더라도, 이미 성공한 동일 요청이면 첫 성공 결과를 반환한다.  
이미 다른 쿠폰이 적용된 주문에 새 쿠폰을 요청하는 경우의 응답과 저장 방식은 `Q-004`의 답으로 정한다.

### 4.3 오류 의미

`errorCode`는 API 실패를 가리키는 안정된 식별자로 설계한다.  
`message`는 사람이 읽는 설명이며 계약이 아니다. 클라이언트는 `errorCode`로만 분기한다.

#### 오류를 나누는 방식

동일 요청의 결과 재사용은 오류가 아니라 기존 성공 결과를 반환하는 정상 흐름이다. (`INV-005`)

1절에서 관찰한 기존 API의 입력 형식 오류 `meta.errorCode`는 `Bad Request`다.  
이는 현재 동작의 관찰값이며, 이번 쿠폰 적용 API는 기존 공통 오류를 전환하지 않고 입력 형식 오류를 `INVALID_REQUEST`로 별도 변환한다.  
따라서 기존 Example API의 `Bad Request` 응답은 바뀌지 않는다. 기술 실패는 공통 5xx 처리로 넘긴다.

| 구분 | 상황 | status | `meta.result` | `errorCode` | `data` | 요청자가 할 수 있는 일 |
| --- | --- | ---: | --- | --- | --- | --- |
| 입력 형식 오류 | 요청 본문을 해석하거나 검증할 수 없음 | `400` | `FAIL` | `INVALID_REQUEST` | 없음 (`null`) | 요청 본문을 고친다. |
| 주문 식별 실패 | 주문 없음 | `404` | `FAIL` | `ORDER_NOT_FOUND` | 없음 (`null`) | 주문 목록으로 돌아간다. |
| 권한 위반 | 주문은 존재하지만 요청자에게 적용 권한이 없음 | `404` | `FAIL` | `ORDER_NOT_FOUND` | 없음 (`null`) | 주문 목록으로 돌아간다. |
| 주문 상태 위반 | 기존 성공 기록이 없는 요청으로 이미 확정된 주문에 적용 시도 | `409` | `FAIL` | `ORDER_ALREADY_CONFIRMED` | 없음 (`null`) | 할인 없이 진행하거나 문의한다. |
| 쿠폰 적용 불가 | 쿠폰 사용 불가 | `404` | `FAIL` | `COUPON_NOT_APPLICABLE` | 없음 (`null`) | 다른 쿠폰을 고른다. |

위 실패 응답에서 `meta.result`는 `FAIL`이고 `data`는 `null`이다. 부분 성공을 두지 않는다는 뜻이다.  
`message`는 표에 넣지 않았다. 사람이 읽는 설명일 뿐 계약이 아니므로 문구는 구현 시점에 정한다.

`ORDER_NOT_FOUND`는 외부 응답의 의미다. 내부에서는 주문이 실제로 없을 수도 있고, 주문은 있지만 요청자에게 적용 권한이 없을 수도 있다.  
두 내부 원인은 구분해 판단하되, 요청자에게는 모두 "이 주문을 찾을 수 없다"로 보이게 한다.

두 곳에서 서로 다른 실패를 하나의 `errorCode`로 합쳤다.

- **소유자 다름을 `ORDER_NOT_FOUND`로**
  - 내부의 권한 위반을 주문 없음과 같은 외부 응답으로 묶는 선택이다. (`DEC-001`)
  - 이는 소유자 다름이 주문 없음이라는 뜻이 아니다.
  - `403 ORDER_FORBIDDEN`처럼 권한 위반을 별도 응답하면 주문이 존재한다는 사실이 요청자에게 드러날 수 있으므로, 이번 계약에서는 그 정보를 숨긴다.
- **없는 쿠폰, 남의 쿠폰, 만료된 쿠폰을 `COUPON_NOT_APPLICABLE`로**
  - 없는 쿠폰과 남의 쿠폰은 위와 같은 이유로 합쳤다. 
  - 만료된 쿠폰은 요청자 본인의 것이라 숨길 정보가 없지만, 이번 잠정 계약에서는 오류 코드를 미리 쪼개지 않는다. 
  - 제품 요구가 생기면 `COUPON_EXPIRED` 등으로 나눈다. 코드 체계는 쪼갤 수 있는 형태로 두었다.

할인액이 주문 금액과 같거나 클 때의 성공·실패와 오류 의미는 `Q-002`의 답을 받은 뒤 정한다.

### 4.4 오류를 구분하는 방식 (DEC-001)

오류 코드를 정할 때 두 단계를 거쳤다.

1. **표현 방식**
   - 기존 방식은 `Not Found`, `Bad Request`처럼 HTTP reason phrase를 `errorCode`로 쓰고, 자세한 원인은 `message` 문구로 전달한다.
   - 선택한 방식은 `INVALID_REQUEST`, `ORDER_NOT_FOUND`, `ORDER_ALREADY_CONFIRMED`, `COUPON_NOT_APPLICABLE`처럼 실패 원인을 가리키는 안정된 `errorCode`를 둔다.

2. **묶는 범위**
   - 원인마다 `COUPON_NOT_FOUND`, `COUPON_NOT_OWNED`, `COUPON_EXPIRED`처럼 모두 나눌 수 있다.
   - 권한 위반도 `ORDER_FORBIDDEN`으로 따로 응답할 수 있다.
   - 이번 계약은 주문 존재 노출을 막기 위해 소유자 다름을 `ORDER_NOT_FOUND`로 묶고, 쿠폰 관련 원인은 `COUPON_NOT_APPLICABLE`로 묶는다. 이는 확인된 제품 사실이 아니라 외부 계약의 선택이다.

오류 코드 수와 소유 경계의 수는 같지 않다. 이 유스케이스가 응답을 조합하지만, 코드의 의미와 추가·변경 판단은 다음 경계가 맡는다.

| 소유 경계 | 오류 코드 | 소유하는 의미 |
| --- | --- | --- |
| 쿠폰 적용 API 인터페이스 | `INVALID_REQUEST` | 요청 본문을 해석하거나 형식을 검증할 수 없음.<br/>기존 공통 오류의 `Bad Request`와 달리 이번 API에서만 별도 변환한다. |
| 주문 | `ORDER_NOT_FOUND`, `ORDER_ALREADY_CONFIRMED` | 주문 조회 가능 여부와 주문 상태.<br/>소유자 다름을 `ORDER_NOT_FOUND`로 감추는 외부 응답 정책도 포함한다. |
| 쿠폰 | `COUPON_NOT_APPLICABLE` | 쿠폰의 존재·보유·유효성처럼 적용 가능 여부 |

`ApplyCouponToOrder` 유스케이스는 위 판단 결과를 HTTP 응답으로 조합할 뿐, 새로운 업무 오류 의미를 직접 소유하지 않는다.

- **선택** — `errorCode`를 실패 원인을 가리키는 안정된 식별자로 새로 설계한다. 입력 형식 오류에는 `INVALID_REQUEST`를 사용하고, `message`는 계약에서 제외해 사람이 읽는 설명으로만 둔다.
- **버린 대안** — 기존처럼 `HttpStatus`의 reason phrase를 `errorCode`로 쓰고, 실패의 구분은 `message` 문구로만 드러낸다.
- **이유**
  - 버린 쪽은 클라이언트가 분기하려면 `message` 문자열을 읽어야 한다.
  - 문구를 다듬거나 다국어를 넣는 순간 계약이 깨지고, `404` 하나에 주문 없음과 쿠폰 사용 불가가 섞여 요청자가 다음 행동을 고를 수 없다.
  - 비용은 코드 목록을 관리하고 오류 타입을 확장해야 한다는 점이다.
  - 무엇을 합치고 무엇을 나눌지는 코드 체계와 별개의 판단이므로, 주문 없음과 소유자 다름은 합친 채로 두고 제품 요구가 생기면 다시 본다.

## 5. 내부 경계

외부 계약은 요청자에게 결과와 오류 의미만 드러낸다. 할인 결과를 언제 보존할지와 어떤 규칙을 어디에서 지킬지는 이 경계 안에서 정한다.

### 5.1 snapshot과 재계산 (DEC-002)

- **선택**
  - 동일 요청 재사용을 위해 쿠폰 적용 결과는 별도 기록으로 보관한다.
  - 주문을 확정할 때는 `originalAmount`, `discountAmount`, `finalAmount`를 주문의 확정 snapshot으로 남기고, 이후에는 그 값을 그대로 반환한다.
- **버린 대안**
  - 확정된 주문을 조회할 때마다 현재 쿠폰 정책과 상품 가격으로 금액을 다시 계산한다.
- **이유**
  - 확정 후 할인 금액이 바뀌지 않아야 한다는 `FACT-002`를 지키려면, 확정된 결과는 당시의 값으로 보존해야 한다.
  - 이는 상품 가격과 쿠폰 정책에서 계산한 값을 주문에 복사하는 의도적인 반정규화다.
  - 상품 가격과 쿠폰 정책은 앞으로 발생할 주문 계산의 기준이고, 확정 snapshot은 이미 끝난 거래의 기준이다.
  - 가격이나 정책이 바뀌어도 과거 거래를 다시 계산하지 않는다.


  중복 금액을 보관하므로 저장 공간과 일관성 관리 비용은 생긴다. 그러나 금액을 조회 때마다 다시 계산해 과거 주문 금액이 바뀌는 비용보다 작다.  
  확정 금액의 정정이 필요해지면 snapshot을 현재 정책으로 조용히 덮어쓰지 않고, 제품 요구로 정한 별도 변경 기록을 남긴다.

  적용 결과 기록은 확정 snapshot과 다르다. `INV-005`의 동일 요청 재사용을 위한 기록이며,  
  확정 전 가격이 변했을 때 그 값을 확정 snapshot에 그대로 복사할지 확정 시 다시 계산할지는 `Q-003`의 답으로 정한다.  
  어느 경우든 확정 후에는 확정 snapshot만 변하지 않는다. 쿠폰 만료는 `COND-004`에 따라 적용 요청 시작 시각에 판단한다.

### 5.2 호출 순서를 숨길 책임 경계 (DEC-003)

- **선택**
  - 쿠폰이 보유자·계산 규칙을, 주문이 구매자·상태 규칙을, 할인 결과 기록이 굳은 값과 요청 식별을 갖는다.
  - 운영자 대리 적용을 허용하면 권한 정책이 역할 검증을 추가로 맡는다. 유스케이스는 조회 순서와 트랜잭션 경계만 관리한다.


  유스케이스는 4.2의 결과 재사용과 4.3의 오류 은닉 의미를 지키도록 내부 호출을 조합한다. 어떤 조회·검증을 먼저 수행하는지는 외부 계약으로 노출하지 않는다.

#### 검사 순서

주문 존재 → 요청자 권한 확인 → 기존 성공 기록(동일 요청 재사용) → 확정 여부 → 쿠폰 적용 가능 → 금액 계산 순으로 판정한다.

- 요청자 권한 확인보다 확정 여부를 먼저 보면 남의 확정된 주문에 `409 ORDER_ALREADY_CONFIRMED`가 나가 그 주문의 존재가 드러나고 4.3의 은닉이 깨진다.
- 재사용 판정보다 확정 여부를 먼저 보면 확정 후 재전송이 `409`로 막혀 4.2의 결과 재사용과 `INV-005`가 깨진다.

| 책임 | 지키는 규칙 |
| --- | --- |
| 쿠폰 | 쿠폰 보유자 검증, 할인액 계산과 만료 판정 (`INV-001`, `INV-003`의 계산, `INV-006`) |
| 금액 값 객체 | 할인액과 최종 금액의 범위 검사 (`INV-003`의 경계) |
| 주문 | 주문 구매자 검증, 한 장 제한 (`INV-001`, `INV-002`) |
| 권한 정책 | 운영자 대리 적용 역할 검증 (`Q-001`의 답에 따라 `INV-001`) |
| 할인 결과 기록 | 확정 금액의 보존, 동일 요청 식별 기준의 보관 (`INV-004`, `INV-005`) |
| 유스케이스 | 조회 순서, 트랜잭션 경계 |

주문은 쿠폰에게서 `discountAmount`라는 결과만 받고 계산 방식은 모른다.

`INV-003`이 두 책임에 걸친 것은 의도한 것이다. 계산은 쿠폰이 하고, 범위 검사는 금액 값 객체가 따로 맡는다.  
"어떤 실행 경로를 거쳐도"라는 불변식의 조건을 특정 구현의 올바름에 기대지 않기 위해 남긴 방어선이다.

유스케이스는 어떤 불변식도 직접 소유하지 않는다. 규칙은 도메인이 지키고 유스케이스는 조립만 한다는 뜻이며, 유스케이스에 규칙이 올라오기 시작하면 경계가 무너지고 있다는 신호로 읽는다.

- **버린 대안**
  - 주문이 쿠폰을 직접 알고 `order.applyCoupon(coupon)`으로 스스로 할인한다.
- **이유**
  - 버린 쪽은 규칙이 주문 한 곳에 모여 지키기 쉽다. 그러나 주문이 쿠폰의 계산 규칙까지 알게 되어 쿠폰 정책 변경이 주문으로 번진다.
  - 쿠폰은 주문 금액이라는 값 하나만 받으므로 주문 타입을 알지 않는다.
  - 쿠폰이 품목 구성이나 주문자 등급을 알아야 하는 종류가 생기면 이 경계는 무너지며, 그때는 주문과 쿠폰을 함께 받는 별도 정책 객체가 필요하다.
  - 비용은 유스케이스가 조회 순서와 트랜잭션 경계를 관리해야 한다는 점이다.
  - 대신 주문과 쿠폰은 서로의 호출 방식을 알 필요가 없고, 외부 계약에는 성공·실패 결과만 드러난다.

## 부록 A. 요구사항에서 유스케이스를 해석한 흐름

이 문서는 ‘쿠폰 사용’이라는 모호한 요구사항에서 시작한다. 먼저 확인된 사실과 실습 장면의 조건을 분리하고, 답이 필요한 부분은 제품 질문으로 남긴다.

그 과정에서 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 적용되어 확정된 할인 금액은 이후에도 유지되어야 한다는 사실을 확인했다.  
따라서 이 요청은 쿠폰의 유효 여부만 판단하는 일이 아니라, 쿠폰을 근거로 주문의 할인액과 최종 금액을 결정하고 그 결과를 보존하는 일이다.

이 문서에서는 이를 `ApplyCouponToOrder`(주문에 쿠폰을 적용한다) 유스케이스로 본다.  
쿠폰은 소유·만료·할인 가능 여부를 판단하는 협력 대상이고, 주문은 할인 결과가 반영되고 확정 후에도 보존되는 변경의 중심이다.  
애플리케이션 유스케이스는 주문과 쿠폰을 조회한 뒤 각 규칙을 조합하여 주문에 할인 결과를 적용한다.
