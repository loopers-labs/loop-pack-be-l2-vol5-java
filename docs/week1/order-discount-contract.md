# 주문 할인 · 중단한 학습 설계

현재 구현할 계획이 아니라 요구사항·불변식·API·설계 판단을 연결했던 학습 기록이다.
2026-11-17 문서 정리에서 반복 본문과 빈 실행 양식을 압축했다. 질문 17개와 아래 미확인 상태는 보존한다.
8주차의 쿠폰 **발급**과 별개이며 주문 할인 적용·실제 로그인·HTTP 관찰·테스트 구현을 완료했다는 뜻이 아니다.
예전 분할 경로는 저장소 밖 학습 자료의 링크를 위해 짧은 연결 안내로만 유지한다.

<a id="purpose"></a>
## 1. 목적·출처·범위

구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고 확정된 할인 금액은 이후에도 유지되어야 한다.
제품 약속, 실습 조건, 학습자가 선택한 설계를 구분한다. 질문을 선택한 사실은 정책의 답을 확인한 사실과 다르다.
출처 없는 추가 정책 제안은 사용자 확인 결과 없으며, 합성 금액·상황을 실제 정책으로 확정하지 않는다.

## 3. 제품 질문 17개와 영향

### UC-001 · 주문에 쿠폰 적용

사용자가 검토한 쿠폰 적용 유스 케이스다. 세부 흐름과 상태는 후속 단계에서 필요한 만큼 구체화한다.

| 항목 | 내용 |
|---|---|
| ID | UC-001 |
| 이름 | 주문에 쿠폰 적용 |
| 액터 | 구매자 |
| 목적 | 주문에 할인을 적용하고 할인 후 금액을 확인한다. |
| 시작 사건 | 구매자가 주문과 쿠폰을 선택해 적용을 요청한다. |
| 기본 조건 | 주문 확정 전이며, 구매자가 보유한 쿠폰이어야 한다. |
| 기본 흐름 | 적용 가능 여부 확인 → 할인 금액·최종 금액 계산 → 적용 결과 전달 |
| 성공 결과 | 구매자가 적용 결과와 금액을 확인한다. |
| 실패 결과 | 구매자에게 적용하지 못한 이유를 알려준다. |
| 처리 후 저장 상태 | 미확인. 결과 저장 여부에 대한 답변이 필요하다. |
| 미확정 분기 | 교체·취소·만료 처리와 같은 요청의 구체적인 판단 기준 |

기본 조건은 P-001 제품 약속에 근거한다. 만료나 금액 제한의 구체적인 처리 방식은 답변을 받은 뒤 보완한다. 성공·실패 후 저장 상태나 세부 분기를 이 표만으로 확정하지 않는다.

| INV-003 · A-002 | 최종 금액 = 원금 - 할인 금액. 10,000-1,000=9,000이며 8,000은 위반 | 할인 계산. 금액 범위·자료형·통화는 미확인 |
| INV-004 · P-002 | 확정된 할인 1,000원을 정책 변경으로 2,000원으로 바꾸지 않는다. | 확정 결과 저장/조회. 확정·저장 시점과 세부 항목은 미확인 |
| INV-005 · A-003 | 같은 요청으로 판별된 재요청은 최초 결과를 재사용한다. 임의 재계산으로 결과가 바뀌면 위반 | 요청 식별·이전 결과. 동일 요청 기준·실패 포함 여부는 미확인 |
| INV-006 · A-004 | 만료를 처리 시각이 아닌 요청 시작 시각으로 판단한다. 11:59:59 시작을 12:00:01 처리 이유로 만료시키면 위반 | 사용 가능 여부. 만료 시각과 정확히 같을 때는 미확인 |

<a id="boundaries"></a>
## 6. 경계와 충돌

만료가 12:00:00이면 11:59:59 시작은 만료 전, 12:00:01 시작은 만료 후다. 정확히 12:00:00은 A-004/Q1의 답이 필요하다.
만료 후라는 판단만으로 오류 응답·저장 상태를 정하지 않는다.
같은 성공 요청을 쿠폰 만료 후 또는 주문 확정 후 다시 보내는 경우, 결과 재사용과 신규 적용 제한의 우선순위가 미확인이다.
두 경우 모두 같은 요청이라고 판별됐다는 전제이며 만료/확정만으로 재요청 실패를 확정하지 않는다.

<a id="api"></a>
## 7. 외부 API 설계

과제 지정 형태는 POST /api/v1/orders/{orderId}/discount, 본문은 couponId다. 두 ID는 필수 양의 정수이며 상한은 미정이다.
누락·문자·0·음수·소수의 형식 오류와 대상의 존재 여부를 구분한다.
서버가 검증한 로그인 정보로 요청자를 식별하고 본문의 userId를 신뢰하지 않는 안을 선택했다.
세션/토큰 방식과 추가 호출 권한은 미정이며 현재 프로젝트의 fixture 식별 구현으로 대체 확정하지 않는다.

성공은 200 OK, meta.result=SUCCESS와 data의 orderId/originalAmount/discountAmount/finalAmount를 반환하는 설계다.
설명용 예시는 orderId=100, couponId=200, 금액 10,000-1,000=9,000이다.
숫자 JSON 예시는 통화·자료형·소수 처리·허용 범위를 확정하지 않는다. 성공 시 오류 필드 포함 여부도 미정이다.
예상 금액 계산인지 결과 저장 완료인지, 주문/할인 확정을 보장하는지는 미확인이다.

| 상황 | HTTP·meta.errorCode | meta.message·다음 행동 |
|---|---|---|
| 입력 형식 오류 | 400 · INVALID_REQUEST | 요청 정보를 확인해 주세요. / 입력 수정 |
| 없는 주문 | 404 · ORDER_NOT_FOUND | 존재하지 않는 주문입니다. / 주문 확인·재선택 |
| 없는 쿠폰 | 404 · COUPON_NOT_FOUND | 존재하지 않는 쿠폰입니다. / 쿠폰 확인·재선택 |
| 소유하지 않은 쿠폰 | 403 · COUPON_NOT_APPLICABLE | 사용할 수 없는 쿠폰입니다. / 보유 쿠폰 재선택 |
| 확정 주문 신규 적용 | 409 · ORDER_ALREADY_CONFIRMED | 확정된 주문에는 쿠폰을 새로 적용할 수 없습니다. / 신규 적용 중단 |

공통 실패는 meta.result=FAIL, 위 code/message, data=null이다. 해당 요청의 신규 쿠폰 적용을 수행하지 않는다.
소유권 실패는 타인 정보 대신 사용 불가만 알린다. 여러 오류의 검사 순서, 만료·교체의 구체 응답은 미정이다.
기존 성공 재요청을 신규 적용 오류로 간주하지 않는다. 같은 요청 기준·성공/실패 재사용·정책 변경·만료/확정 후 우선순위가 미확인이다.
HTTP와 오류 코드 연결은 학습자의 설계 선택이며 실제 API 관찰 결과가 아니다.

## 8. 설계 결정과 비용

| 결정 | 선택·버린 대안·이유 | 감수한 비용·남은 확인 |
|---|---|---|
| DEC-001 오류 구분 | 코드+안내 문구. 문구만 제공하는 안 대신 문구 변경에도 프로그램 분기 기준을 유지 | 코드 의미 관리 필요. 미확인 상황과 다중 오류 우선순위는 확정하지 않음 |
| DEC-002 확정 금액 | snapshot 저장. 현 정책 재계산은 확정 금액이 변할 수 있어 기각 | 저장·조회 비용. 요청 즉시 저장한다는 뜻은 아니며 시점/세부 저장 항목 미정 |
| DEC-003 조율 책임 | 서버 내부 서비스가 조회·검증·계산·저장 순서를 조율. 화면이 단계별로 호출하는 안의 누락·변경 부담을 피함 | 모든 판단을 서비스에 몰지 않고 상태·계산·저장 책임에 나눔. 순서·저장 시점 미정 |

서비스가 흐름, 주문이 적용 상태, 쿠폰이 사용 가능 여부, 계산부가 금액 관계, 결과 저장부가 확정 snapshot을 맡는 책임 후보다.
각 책임이 반드시 별도 클래스라는 뜻은 아니다. 안내 문구·저장 위치·내부 조회 순서를 바꿔도 코드·확정 금액·응답·재요청 약속을 보존해야 한다.
