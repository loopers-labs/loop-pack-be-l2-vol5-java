# 커머스 정책 선택과 설계 검토

[전체 설계](commerce-erd-draft.md) · [API 계약](commerce-api-contract.md) · [TDD 계획](commerce-tdd-plan.md)

미정 정책 P01~P07과 책임·의존·저장 방식의 대안 검토를 모은다. 아래 제안은 구현 완료나 사용자 승인 기록이 아니다. 정책을 확정하거나 변경하면 관련 API 계약과 테스트 기대값도 함께 갱신한다.

## 구현 전에 확인할 정책 선택

[API 계약](commerce-api-contract.md)의 경로 자체는 더 이상 미정이 아니다. 아래는 과제에서 허용한 선택이나 명시하지 않은 세부 동작에 대한 **검토용 제안**이며, 사용자가 확인하기 전에는 확정 정책으로 승격하지 않는다. 관련 기능 구현 전에 선택한 안과 이유를 갱신한다. 순수 재고 규칙의 TDD처럼 이 선택에 영향받지 않는 작업은 먼저 진행할 수 있다.

| ID | 확인할 선택 | 초안의 제안·대안과 영향 |
| --- | --- | --- |
| P01 | 중복 주문 품목 합산 또는 거절 | 합산안을 제안한다. productId별로 각 양수 수량을 합쳐 한 항목으로 저장하고 합산 범위를 검사한다. 거절을 선택하면 `400 DUPLICATE_ORDER_ITEM`로 전체 생성 실패. 어느 쪽이든 확정 시 저장된 상품별 총수량으로 재고를 검사한다. |
| P02 | 가격 0 허용 여부와 입력 범위 | 원 단위 정수·1원 이상, 이름 공백 제거 후 1~100자로 제안한다. 0원 허용을 선택하면 가격 검증과 무료 주문의 결제액 0 기대값을 함께 반영한다. |
| P03 | 실습 사용자·관리자와 DB 행 연결 | 미리 준비한 fixture 매핑과 관리자 권한, 초기 잔액 0을 제안한다. 문자열 `X-USER-ID` 사용은 이미 확정이다. 자동 회원 생성·별도 인증 기능은 추가하지 않는다. |
| P04 | 중복 좋아요·없는 관계 취소·반복 삭제 | 중복 좋아요와 이미 없는 관계 취소는 200·현재 결과, 이미 삭제된 상품/브랜드의 DELETE는 200·기존 삭제 결과를 제안한다. 없는 상품·브랜드 행은 404다. 다른 응답을 선택해도 관계 수·재고·주문이 추가 변경되면 안 된다. |
| P05 | 상품 PUT의 변경 가능 필드와 관리자 조회 | name·price만 수정하고 brandId·stockQuantity 입력은 400을 제안한다. 관리자 조회는 삭제 행을 포함하고 고객 조회는 제외한다. 브랜드 불변·삭제 대상 수정 거절은 확정 규칙이다. |
| P06 | 목록·응답의 세부 계약 | [API 계약](commerce-api-contract.md)의 page/size 기본값·범위·동률 기준·빈 페이지 처리·응답 필드·오류 매핑을 제안한다. 과제의 세 정렬 이름과 브랜드 필터 지원은 확정이다. |
| P07 | 충전·주문 생성의 반복 요청 | 별도 멱등 키 요구가 없으므로 각 성공 요청을 새 충전·새 주문으로 처리하는 안을 제안한다. 클라이언트 자동 재전송을 전제하지 않는다. 주문 확정 재요청의 기존 결과 반환은 이미 확정이다. |

동시성 제어의 구체적인 잠금·조건부 갱신 방식은 주문 확정 구현 전에 비교한다. 설계 계약은 중복 차감·재고와 잔액의 음수·부분 반영을 허용하지 않으며 구현 편의를 위해 이 기대값을 완화하지 않는다.

## AI와 설계 다듬기: 책임·의존·대안 검토

아래는 책임 중복과 의존에 대한 검토 기록이다. **현재 초안에서 채택한 설계 제안과 그 이유**를 남기며, 업무 정책 확정이나 실제 구현 완료를 뜻하지 않는다. 구현 뒤 드러난 근거로 대안을 바꾸면 관련 계약·테스트 기대값의 영향도 함께 기록한다.

| 검토 질문 | 비교한 대안 | 초안의 선택·이유와 주의점 |
| --- | --- | --- |
| 관리자·주문 서비스가 각각 재고 부족을 검사하면 중복되지 않는가? | 각 서비스가 직접 수량 계산 / Product가 재고 상태 규칙 관리 | Product에 최종 재고 설정·차감 유효성을 둔다. 애플리케이션은 호출 순서를 조율하며 비음수·삭제 상태 검사를 서로 다르게 구현하지 않는다. |
| Order가 상품·사용자 조회와 저장까지 맡아야 하는가? | Order가 전체 결제 처리 / 애플리케이션이 도메인을 조율 | 애플리케이션이 트랜잭션·조회·소유권·재요청 분기를 조율하고 Product·User·Order는 각자의 상태를 변경한다. 한 주문의 원자성을 엔티티별 저장으로 쪼개지 않는다. |
| Brand가 상품 전체를 가지고 있어야 삭제를 판단할 수 있는가? | Brand에 상품 컬렉션 로딩 / 도메인 서비스의 미삭제 상품 존재 조회 | 도메인 서비스가 저장소 인터페이스로 존재 여부를 조회한다. 전체 로딩을 피하고 재고0도 같은 조건으로 판단한다. 동시 등록과 삭제의 경합은 저장 전략으로 별도 보장한다. |
| 상품 삭제 시 실제 행을 지우는가? | 물리 삭제와 FK 재설계 / deleted_at 논리 삭제 | 상품·브랜드는 논리 삭제를 제안한다. 기존 주문·좋아요 FK를 유지하면서 과거 주문 조회와 남은 본인 관계 취소가 가능하다. 대신 작업별 미삭제 조건이 필요하며 모든 조회에 공통 필터를 강제하면 안 된다. |
| 좋아요 취소도 상품처럼 논리 삭제해야 하는가? | 관계 행 보존·재활성화 / 관계 행 실제 삭제 | 좋아요 이력 요구가 없으므로 관계 행 삭제를 제안한다. UNIQUE(user_id,product_id)와 재등록·관계 집계가 단순해진다. 상품 삭제 시 관계를 함께 지우는 규칙은 추가하지 않는다. |
| 상품 조회의 좋아요 수를 별도 컬럼으로 관리할까? | 상품 카운터 동시 갱신 / 관계 집계 | 과제에 따라 관계에서 집계한다. 중복 등록·재취소로 개수가 변하지 않는다. 정렬은 집계 후 페이지 처리하고 성능 검토 없이 캐시 컬럼을 추가하지 않는다. |
| 과거 주문 조회에 현재 상품명·가격을 사용할까? | 현재 상품과 결합해 표시 / OrderItem 스냅샷 | 생성 스냅샷을 선택한다. 가격 변경·상품 삭제와 무관하게 합의한 주문 금액을 보존한다. 현재 재고·판매 가능 여부는 DRAFT 확정에서 따로 확인한다. |
| 애플리케이션이 JPA 저장소 구현에 직접 의존해도 되는가? | infrastructure 구현 직접 참조 / domain 저장소 인터페이스 참조 | 인터페이스를 선택하고 구현은 infrastructure에 둔다. 현재 ArchUnit 규칙과 계층 의존 방향을 유지한다. 실행 시 저장소 호출 방향과 코드 의존 방향을 구분한다. |
| 동시 확정은 트랜잭션 선언만으로 충분한가? | 단순 읽기·저장 / 비관적 잠금 / 버전·조건부 갱신 | 잠금 또는 조건부 갱신이 필요하다는 설계 요구만 확정한다. 전략은 구현 전에 경합 테스트·락 순서·재시도 기준을 비교해 선택하며 Product·User·Order 및 관리자 변경 경로에 일관되게 적용한다. |
