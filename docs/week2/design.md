# 기능 설계 문서

## 1. 버드뷰

```
고객 ── 상품·브랜드 조회 / 좋아요 / 포인트 / 주문 ─┐
                                                 ├─ commerce-api ─→ DB
관리자 ── 브랜드·상품 CRUD / 재고 변경 / 주문 조회 ─┘   고객·관리자 API 구분
```

- **고객과 관리자의 API를 구분한다.** 같은 상품을 다루더라도 입력·권한·응답 필드가 다르다.
- **DB는 하나를 공유한다.** 관리자의 변경·삭제가 고객 조회에 바로 반영되어야 한다.

## 2. 도메인 관계

### 2.1 관계도

```
Brand 1 ── N Product ── 재고
User  1 ── N Like N ── 1 Product
User  1 ── N Order 1 ── N OrderItem ── 상품 식별자 · 수량 · 주문 시점 스냅샷(상품명·단가)
User  1 ── 0..1 Point ── 잔액 (행은 첫 충전 때 생김)
Order ── 품목 금액 합계 / 포인트 결제액 · 결제 시각 (결제 결과는 주문 상태가 대신함)
```

관계도의 선은 업무 관계를 나타낸다. 모든 선을 객체 참조로 구현하지 않고, 아래 기준으로 객체 참조와 식별자 보관을 나눈다.

### 2.2 참조 방식 판단 기준

| 질문 | 객체 참조 쪽 근거 | 식별자 보관 쪽 근거 |
|---|---|---|
| 상대의 상태가 그 객체의 **불변식**에 필요한가? (살아 있는 동안 계속 지켜야 하는가) | 객체가 자신의 입구(생성·변경)에서 지킴 | - |
| 유스케이스가 **시작될 때 한 번** 확인하면 되는가? | - | 확인하는 시점에만 조회하면 됨 |
| 함께 생성·변경·삭제되는가? | 한 덩어리로 움직임 | 각자 따로 수정·삭제됨 |
| 한쪽을 불러올 때 다른 쪽이 딸려 와도 되는가? | 항상 함께 필요함 | 딸려 오는 것이 부담임 |
| 누가 누구를 알아야 행동할 수 있는가? | 필요한 방향으로만 둠 | - |

객체가 지킬 수 있는 것은 자기 상태가 바뀌는 입구뿐이다. 상대 쪽에서 불변식을 깨는 입구(예: 브랜드 삭제)는 그 입구를 가진 쪽의 규칙이 따로 막아야 한다.

"A가 없으면 B도 없다"는 생명주기에 대한 판단이다. 누가 누구를 참조할지는 "누가 누구의 상태를 알아야 규칙을 지키는가"로 따로 판단한다.

### 2.3 관계별 판단

| 관계 | 판단 | 근거 |
|---|---|---|
| Product → Brand | 객체 참조 | "브랜드 없이 존재할 수 없다"가 Product의 불변식임. 생성 입구는 Product가, 브랜드 삭제 입구는 BRD-02가 지킴 |
| Like → User, Product | 둘 다 식별자 | Like의 불변식에 다른 객체의 상태가 필요하지 않음. 등록 시 상품 삭제 여부 확인(LIK-01)은 시작 시점의 한 번 확인임 |
| Order → OrderItem | Order가 품목을 앎 | 합계·상태 규칙을 Order가 지킴 |
| OrderItem → Order | 참조하지 않음 | OrderItem이 Order의 상태로 판단할 규칙이 없음. 테이블의 `order_id` 는 Order 쪽 단방향 매핑이 관리한다 |
| OrderItem → Product | 식별자 + 스냅샷 | 주문 시점의 값을 보존함 |
| Point → User | 식별자 (`userId`) | 잔액 규칙에 User의 상태가 필요하지 않음 |

#### Product → Brand: 객체 참조

- **근거:** "상품은 브랜드 없이 존재할 수 없다"는 Product의 불변식이다. 이 불변식이 깨지는 입구는 상품 생성과 브랜드 삭제 두 곳이며(BRD-02), Product는 그중 **생성 입구**를 지킨다. 상품을 만들 때 Product가 `Brand` 를 받아 삭제되지 않은 브랜드인지 스스로 확인한다. 브랜드 확인을 빠뜨린 상품이 만들어질 수 없다. 식별자만 보관하면 이 확인을 application이 매번 빠뜨리지 않아야 한다.
- **보조 근거:** 상품은 반드시 하나의 브랜드에 속하고 수정해도 바뀌지 않는다. 생성자에서만 받고 변경 행동을 두지 않는다.
- **감수하는 비용**
  - Product 도메인 테스트마다 Brand 객체가 필요하다.
  - 생성 시점의 확인만 보장한다. 이후 브랜드가 삭제되는 경우는 브랜드 삭제 조건("삭제되지 않은 상품이 남은 브랜드는 삭제할 수 없다")이 막는다.
  - 참조를 따라 목록을 만들면 N+1이 생길 수 있다. 목록 · 상세는 조회 결과 타입(4.5)을 조인 한 번으로 가져오므로 이 참조를 따라가지 않는다.
- **참고:** 상품 목록은 좋아요 수와 `likes_desc` 정렬 때문에 집계가 들어간 전용 조회가 될 가능성이 크다. 따라서 참조 방식은 목록 조회가 아니라 규칙을 기준으로 정한다.

#### Like → User, Product: 둘 다 식별자

- **근거:** Like는 사용자–상품 관계 자체만 표현한다. Like 자신의 규칙에는 User의 상태도 Product의 상태도 필요하지 않다.
  - 같은 사용자–상품 관계의 중복은 (`userId`, `productId`) 유니크 키로 막는다. (LIK-02)
  - 본인 관계만 취소하며, 상품이 삭제되었어도 취소할 수 있다. (LIK-03)
  - 좋아요 수는 관계에서 count로 조회한다.
  - "삭제된 상품에는 새 좋아요를 달 수 없다"(LIK-01)는 Product의 상태가 필요한 유스케이스의 협력이며, 등록 흐름에서 상품을 조회할 때 확인한다.
- **Product → Brand와의 차이:** 상품이 브랜드에 속한다는 것은 Product가 존재하는 동안 계속 지켜야 하는 불변식이라 Product가 Brand를 들고 스스로 지킨다. 반면 LIK-01은 좋아요를 **등록하는 시점에 한 번** 확인하면 되고, 등록된 뒤 상품이 삭제되어도 그 관계는 남는다(LIK-03). 확인하는 시점에만 Product를 조회하면 되므로 참조를 들 이유가 없다.
- **버린 대안:** Product를 객체로 참조한다. 내 좋아요 목록에서 상품 정보에 바로 접근할 수 있지만, 규칙이 아닌 조회 편의 때문에 참조가 생긴다. Product → Brand와 판단 기준이 어긋난다.
- **감수하는 비용:** 내 좋아요 목록에서 상품 정보를 따로 조회해 조합해야 한다.

#### Order → OrderItem: Order가 품목을 앎

- **근거:** "합계 = 품목 금액의 합"(ORD-05), "DRAFT에서만 확정"(ORD-07) 같은 규칙을 Order가 지킨다. 그러려면 Order가 자신의 품목을 알아야 한다.
  - 확정 시 재고 확인(ORD-10)에는 Order가 가진 품목별 총수량이 필요하지만, 재고는 Product가 가진다(2.4). Order 혼자 지킬 수 있는 규칙이 아니라 `domain/order` 의 `~Service` 가 조율한다(4.4).
- **OrderItem은 Order를 모른다.** 주문을 가리키는 필드가 없고, 테이블의 `order_id` 는 Order 쪽 `@JoinColumn` 이 관리한다. OrderItem이 Order의 상태를 보고 판단할 규칙이 없다.
  - 이번 범위의 주문 상태는 DRAFT·CONFIRMED뿐이고 주문 취소가 없다.
  - 품목을 수정하는 API가 없다.
  - 이후 품목 변경이 생기더라도 변경은 Order를 통해서만 하고, Order가 자신의 상태를 확인한다. OrderItem이 Order의 상태를 물어 스스로 막으면 규칙이 두 객체에 나뉜다.
- **JPA 매핑은 단방향 `@OneToMany` + `@JoinColumn(order_id)` 이다.** (구현하며 정함) Order 가 품목을 cascade 로 함께 저장하고, 품목은 `@OrderBy("id asc")` 로 저장 순서대로 읽는다(D-33).
  - **이유:** OrderItem 이 Order 를 알 필요가 없다는 판단(위)과 그대로 맞는다. 품목은 Order 를 통해서만 만들어진다.
  - **버린 대안:** 양방향 `mappedBy` (OrderItem 이 Order 를 참조하게 되어 위 판단과 어긋남), 따로 저장 후 조율 (Order 의 합계 · 합산 규칙을 서비스가 다시 맞춰야 함).

#### OrderItem → Product: 식별자 + 주문 시점 스냅샷

- **근거:** 관리자가 상품의 이름·가격을 바꿔도 이미 만든 주문의 품목 정보와 금액은 바뀌지 않아야 한다. 주문 품목을 조회할 때 상품의 현재 상태 전체가 필요하지 않다.
- **스냅샷 시점:** DRAFT 생성 시점에 상품명·단가를 저장한다.
- **확정 시 가격 확인:** 확정할 때 스냅샷 단가와 상품의 현재 가격이 다르면 확정을 거절한다.
- **가격이 내려간 경우도 거절한다.** 오른 경우만 거절하면 내려간 가격을 스냅샷과 현재 가격 중 무엇으로 결제할지 추가로 정해야 한다. "다르면 거절"로 두어 고객이 본 금액과 결제 금액을 항상 같게 유지한다.
- **비교 대상은 단가뿐이다.** 상품명이 바뀌어도 결제 금액은 달라지지 않으므로 확정을 거절하지 않는다. 주문 품목에는 생성 시점의 상품명이 그대로 남는다.
- **가격 비교는 OrderItem이 한다.** 스냅샷 단가를 가진 쪽이 현재 가격을 받아 비교한다. "가격이 다르면 거절"은 주문의 결제 정책이므로, 인하를 허용하는 식으로 정책이 바뀌어도 Product는 바뀌지 않는다.

| 대안 | 장점 | 비용 |
|---|---|---|
| **가격이 다르면 거절 (선택)** | 고객이 모르는 금액으로 결제되지 않음 | 그 DRAFT는 확정할 수 없어 고객이 주문을 새로 만들어야 함 |
| 현재 가격으로 결제하고 스냅샷 갱신 | 고객이 다시 주문하지 않아도 됨 | 생성 때 본 금액과 결제 금액이 달라짐 |
| 스냅샷 가격으로 결제 | 생성 때 본 금액 그대로 결제 | 관리자가 바꾼 가격이 반영되지 않음 |

- **확인 순서:** 가격·상품 삭제 여부·재고·잔액을 **모두 확인한 뒤** 재고·포인트를 차감한다. (ORD-08~ORD-11)
  - 트랜잭션이 롤백되면 DB 반영은 막을 수 있지만, 메모리의 도메인 객체는 이미 바뀐 상태로 남는다. 모두 확인한 뒤 변경하면 "거절 시 기존 값 유지"를 DB 없이 도메인 테스트로 확인할 수 있다.
  - 이론 문서의 "여러 품목이라면 전체 입력과 필요한 재고·잔액을 확인한 뒤 변경 행동을 호출합니다"와 같은 순서다.
  - 트랜잭션 롤백은 예상하지 못한 실패에서 DB 반영을 막는 보조 수단으로 둔다.
- **거절 후 상태:** 주문은 DRAFT로 남고 재고와 잔액은 바뀌지 않는다.

#### Point → User: 식별자

- **잔액만 저장한다.** 포인트 내역은 이번 범위의 요구가 아니다.
- **사용자 한 명에 Point는 하나다.** `userId` 유니크 키로 보장한다.
- **Point 행이 없으면 잔액은 0원이다.** 행은 첫 충전 때 만든다.
  - "행 없음"과 "잔액 0인 행"이 같은 의미가 되므로, 행이 없을 때 0원 Point로 바꾸는 일은 한 곳에서만 한다.
- **확장 가능성:** 충전·결제 이력이 필요해지면 포인트 내역을 별도로 둔다. 이때 잔액을 따로 저장할지 내역 합계로 계산할지 정해야 하고, 잔액을 따로 저장한다면 잔액과 내역 합계를 일치시킬 책임이 추가된다.
- **알려진 한계:** 첫 충전이 동시에 두 번 들어오면 둘 다 행이 없다고 보고 insert를 시도한다. 유니크 키가 데이터를 지키지만 한쪽 요청은 실패한다.

### 2.4 재고의 책임

**재고는 Product의 필드로 둔다.**

재고를 바꾸는 행동은 두 가지다.

| 행동 | 호출되는 경로 | 지키는 조건 |
|---|---|---|
| 차감 | 주문 확정 | 차감 수량은 양수, 보유량보다 많이 차감할 수 없음, 결과는 0 이상 (PRD-05, PRD-06) |
| 최종 수량 설정 | 관리자 재고 변경 | 삭제되지 않은 상품만, 결과는 0 이상 (PRD-04, PRD-05) |

#### 근거 ① 재고를 Product에 두는 이유

- **함께 생성·삭제되는가:** 그렇다. 재고는 상품 없이 존재하지 않고, 상품이 삭제되면 재고도 사용할 수 없다. 재고만 따로 생기거나 사라지는 경우가 없다.
- **규칙을 지키려면 상대의 상태를 알아야 하는가:** 그렇다. "삭제되지 않은 상품만 재고를 변경한다"(PRD-04)는 상품의 삭제 상태가 필요하다. 같은 객체에 두면 이 규칙이 자기 상태의 검사가 된다.
- **불러올 때 딸려 와도 되는가:** 그렇다. 재고는 숫자 하나이고, 상품을 조회할 때 재고를 얻으려고 추가 조회를 할 필요가 없다.
- **반론:** 변경 이유는 다르다. 이름·가격은 관리자 상품 수정에서, 재고는 주문 확정과 관리자 재고 변경에서 바뀐다. 응집도만 보면 분리할 근거가 된다.
- **그래도 두는 이유:** 이번 범위의 재고 규칙은 "0 이상", "보유량 이하 차감" 정도다. 분리해서 얻는 변경 격리보다 분리했을 때 생기는 비용이 크다.
  - 삭제 여부 확인이 객체 간 협력으로 바뀐다.
  - 상품 조회에 조인이 생긴다.
  - 두 엔티티의 생명주기(생성·삭제)를 맞춰야 한다.
  - 변경 이유가 다르다는 점은 감수하는 비용으로 남긴다.

#### 근거 ② 재고 규칙의 종류와 필드로 두는 이유

| 규칙 | 종류 | 적용되는 행동 |
|---|---|---|
| 재고는 0 이상 | 값의 유효성 | 차감, 최종 수량 설정 (결과 값에 공통 적용) |
| 차감 수량은 양수 | 행동의 입력 조건 | 차감 |
| 보유량보다 많이 차감할 수 없음 | 행동의 입력 조건 (요청 값과 현재 재고의 관계) | 차감 |

- 값의 유효성("0 이상")은 두 행동에 공통이므로, Product 안에서 재고를 바꾸는 행동이 공통으로 거치는 한 곳에서 검사해 중복을 막는다.
- **별도 값 객체로 감싸지 않는 이유:** 이론 문서의 도입 기준은 "의미가 혼동되거나 유효성 검사가 반복되는 곳"이다. 이번 범위에서는 규칙이 세 개이고 Product 안의 한 곳에 모을 수 있어 반복이 생기지 않는다.

#### 버린 대안과 비용

| 대안 | 얻을 수 있던 것 | 포기한 이유 |
|---|---|---|
| 별도 엔티티 (상품 식별자로 연결한 재고 테이블) | 이름·가격 수정과 재고 변경이 서로 다른 행을 바꾼다. 재고 규칙이 늘어나도 Product가 바뀌지 않는다. | 삭제되지 않은 상품만 재고 변경(PRD-04)이 Product 조회와 재고 변경의 협력으로 바뀐다. 상품 조회에 조인이나 추가 조회가 생긴다. 상품을 생성·삭제할 때 재고 행도 함께 생성·삭제해야 하고, 삭제 상태(`deletedAt`)가 두 곳에 생긴다. |
| 값 객체 (Product 안의 재고 타입, 같은 테이블) | 재고 규칙이 한 타입에 모인다. Brand 없이 재고 규칙만 단위 테스트할 수 있다. | 이번 범위의 재고 규칙은 세 개이고, Product 안의 한 곳에 모아 반복을 막을 수 있다. 타입과 JPA 매핑을 추가하는 비용에 비해 얻는 것이 작다. |

- **이 선택의 비용:** Product가 상품 정보(이름·가격·브랜드) 규칙과 재고 규칙을 함께 떠안는다. 상품 정보가 바뀌는 이유와 재고가 바뀌는 이유가 한 클래스에 모인다.

#### 반례 대입 결과

- **삭제된 상품의 재고 변경:** Product의 재고 변경 행동이 자신의 삭제 상태를 확인해 거절한다. 주인이 같으므로 다른 객체를 조회할 필요가 없다.
- **주문 확정의 재고 비교:** Order는 품목별 수량만 알고 재고는 모른다. Order 혼자서는 "재고 충분"(ORD-10)을 판단할 수 없다. 이 협력은 `domain/order` 의 `~Service` 가 조율한다(4.4).
- **테스트에 Brand가 필요한가:** 필요하다. Product가 생성할 때 Brand를 받으므로, 재고 규칙만 테스트할 때도 Brand를 먼저 만들어야 한다. 테스트용 Brand 생성을 한 곳(fixture)에 모아 비용을 줄인다. 값 객체였다면 없었을 비용이다.
- **동시 변경:** 재고와 이름·가격이 같은 행에 있다.
  - JPA(Hibernate)는 기본적으로 변경 감지 시 모든 컬럼을 UPDATE하므로, 관리자의 이름 수정이 그 사이에 확정된 재고 차감을 덮어쓸 수 있다.
  - 같은 상품을 동시에 확정하면 둘 다 같은 재고를 읽고 차감해 초과 판매가 생길 수 있다. 이 문제는 재고를 어디에 두든 생긴다.
  - 과제에 동시성 요구가 없으므로 이번 범위에서는 해결하지 않고 알려진 한계로 남긴다.

#### 다시 검토할 조건

- **재고 규칙이 늘어날 때** (예약 재고, 안전 재고, 입출고 이력) → 값 객체나 별도 엔티티로 분리를 검토한다.
- **동시성을 처리해야 할 때:** 재고를 잠그면 상품 행 전체가 잠겨 이름·가격 수정까지 막힌다. → 잠금 범위를 줄이기 위해 별도 엔티티를 검토한다.
- **재고가 상품 단위가 아니게 될 때** (옵션별, 창고별 재고) → 상품과 재고의 1:1 관계가 깨지므로 별도 엔티티가 필요하다.
- **재고 규칙 테스트에서 Brand를 준비하는 비용이 반복해서 문제가 될 때** → 값 객체를 검토한다.

#### 재고의 입력과 노출

- **상품 생성에서는 재고를 받지 않고 0으로 시작한다.** 재고는 `PUT /api-admin/v1/products/{productId}/stock` 으로만 바꾼다.
  - 재고를 설정하는 입구가 하나뿐이라 재고 규칙(PRD-04, PRD-05)을 한 경로에서만 지키면 된다.
  - **감수하는 비용:** 관리자가 상품을 팔려면 생성과 재고 설정을 두 번 호출해야 한다.
- **고객 응답에는 품절 여부만 내보내고, 수량은 관리자 응답에만 넣는다.**
  - 고객은 살 수 있는지만 알면 된다. 같은 상품이라도 고객과 관리자의 응답 필드가 다르다는 1장의 판단을 따른다.
  - 품절 여부(재고 0)를 판단해 응답을 만드는 일은 조회 결과의 구성이며 응답을 조합하는 쪽이 맡는다(3.1).

### 2.5 삭제 방식

**브랜드와 상품은 논리 삭제한다.** 행을 남기고 삭제 상태를 표시하며, 고객 조회와 새 주문에서 제외한다.

#### 근거

| # | 근거 | 물리 삭제였다면 |
|---|---|---|
| 1 | 삭제된 상품의 좋아요 관계를 본인이 취소할 수 있어야 한다 (LIK-03) | 상품 행이 사라질 때 좋아요 행을 함께 지울지 정해야 하고, 남기면 가리키는 대상이 없는 행이 된다 |
| 2 | 확정된 주문의 품목과 좋아요가 상품 식별자를 가리킨다 | 기존 참조가 깨진다 |
| 3 | 브랜드 삭제 조건이 "삭제되지 않은 상품(재고 0 포함)이 남으면 거절"이다 (BRD-02) | "삭제된 상품"이라는 상태가 없어 조건을 표현할 수 없다 |
| 4 | 관리자는 삭제된 상품이 포함된 과거 주문도 조회한다 | 주문 품목의 상품 식별자로 상품을 더 이상 찾을 수 없다 |

#### 감수하는 비용

- 고객 조회와 새 주문에서 삭제 상태 조건을 빠뜨리면 삭제된 대상이 노출된다. 조건을 빠뜨리지 않을 방법이 필요하다.
  - **조건은 쿼리마다 명시하고, 저장소 테스트가 모든 조회 경로를 확인한다(7.2).** 살아 있는 상품 조회는 `ProductService` 한 곳에 모은다(D-31).
  - **버린 대안:** 엔티티 단위 전역 필터(Hibernate `@SQLRestriction` 등). 조건을 빠뜨릴 수 없지만 쿼리에 보이지 않는 조건이 붙어 읽기 어렵고, 삭제된 행이 필요한 조회가 생기면 막힌다.
- 행이 남으므로 상품명 같은 값에 유니크 제약을 걸 때 삭제된 행까지 고려해야 한다.
- 삭제된 행이 쌓인다. 정리 기준은 이번 범위에서 정하지 않는다.

#### 삭제된 대상의 조회와 복원

- **삭제된 브랜드·상품은 관리자 목록에서도 제외한다.** 복원이 없으므로 목록에서 볼 이유가 적고, 고객·관리자 목록의 조회 조건이 하나로 통일된다.
  - **감수하는 비용:** 잘못 삭제한 대상을 관리자 화면에서 확인할 수 없다.
  - 관리자 주문 조회에서는 삭제된 상품이 포함된 과거 주문도 그대로 보인다. 주문 품목은 주문 시점 스냅샷을 쓴다(2.3).
- **복원 기능은 두지 않는다.** 과제 요구에 없다. BRD-02를 지켜야 하는 입구가 상품 생성과 브랜드 삭제 두 곳으로 유지된다.
  - 복원이 생기면 "삭제된 브랜드에 속한 상품의 복원"처럼 입구가 늘어난다. 그때 BRD-02의 표현을 다시 본다.

### 2.6 사용자

**User는 식별자만 가진 최소 엔티티로 두고, 테스트 데이터(fixture)로 준비한다.** 회원가입 API는 없다.

- **테이블로 두는 이유:** 과제는 "없는 사용자"를 거절하라고 한다. 헤더 값을 그대로 믿으면 이 요구를 지킬 수 없다. 테이블로 두면 존재 확인이 조회 하나로 끝나고, 다른 데이터와 같은 방식으로 관리된다.
- **버린 대안:** 설정 파일에 허용할 사용자 목록을 둔다. 가볍지만 테스트 DB의 데이터와 사용자 목록이 두 곳으로 나뉘고, 사용자를 추가하려면 설정을 바꿔야 한다.
- **감수하는 비용:** 로컬에서 실행할 때 쓸 사용자 데이터가 필요하다. `local` 프로필에서 앱이 뜰 때 사용자가 없으면 2명을 만든다(`LocalUserInitializer`). 실행 코드에 로컬 전용 코드가 섞이는 대신 연결 흐름을 바로 확인할 수 있다.
- **테이블 이름은 `users` 다.** MySQL 키워드와 겹치지 않게 한다.

#### 존재 확인

**`interfaces` 에서 헤더를 읽는 한 곳이 존재까지 확인하고, 컨트롤러는 확인된 사용자만 받는다.**

- 새 API가 생겨도 확인을 빠뜨릴 수 없다.
- **존재 여부를 묻는 메서드를 따로 두고, 거짓이면 `interfaces` 가 `UNAUTHENTICATED` 를 던진다.** 대상 없음 예외(`USER_NOT_FOUND`)를 던지는 조회는 쓰지 않는다.
  - **이유:** 식별 실패의 의미("요청자를 확인할 수 없음")를 `interfaces` 가 정한다. 헤더 누락·형식 오류·없는 사용자(6.1)가 한 곳에서 같은 오류가 된다. `USER_NOT_FOUND` 404는 경로의 `userId` 가 요청자 본인이 아닐 때만 쓴다(6.3).
  - **버린 대안:** `USER_NOT_FOUND` 를 던지는 조회를 쓰고 `interfaces` 가 잡아 `UNAUTHENTICATED` 로 바꾼다. 메서드는 늘지 않지만 예외를 바꿔 던지는 코드가 생기고, 같은 코드가 상황에 따라 401도 404도 되어 읽기 어렵다.
  - **감수하는 비용:** 사용자 조회 메서드가 하나 더 생긴다.
- **호출 경로는 `interfaces` → `UserFacade` → `UserService` 다.** 4.1·4.3의 흐름에 예외를 두지 않는다. 반환값은 존재 여부뿐이라 엔티티가 `interfaces` 로 나가지 않는다(4.4).
  - **버린 대안:** `interfaces` 가 `UserService` 를 직접 호출한다. 가장 단순하지만 4.3 흐름의 예외가 되고, 같은 예외가 다른 곳으로 번질 수 있다.
  - **감수하는 비용:** 전달만 하는 얇은 `UserFacade` 가 생긴다.
- **소유자 조건 조회(6.1)만으로는 부족하다.** 포인트 충전은 Point 행이 없으면 새로 만들기 때문에(2.3), 없는 사용자에게도 포인트가 생긴다.
- **버린 대안:** 각 `~Facade` 가 처음에 확인한다. 필요한 곳에서만 확인할 수 있지만 같은 코드가 반복되고 새 유스케이스에서 빠뜨리기 쉽다.
- **감수하는 비용:** 식별이 필요한 요청마다 사용자 조회가 한 번 더 나간다.
- 헤더를 읽는 곳이 직접 값을 꺼내 검사한다. `ApiControllerAdvice` 에는 헤더 누락 예외(`MissingRequestHeaderException`) 핸들러가 없어, 스프링의 필수 헤더 검사에 맡기면 500이 나간다.

#### 식별이 필요한 API

| 대상 | 식별 |
|---|---|
| 상품 · 브랜드 조회 | **필요 없음.** 누구의 것도 아니다 |
| 좋아요 · 포인트 · 주문 | 필요함. 자신의 것을 다룬다 |

- 식별이 필요한 이유를 "자신의 것을 다루는가"로 설명한다. 상품만 구경하는 요청까지 거절할 이유가 없다.

## 3. 지킬 규칙

### 3.1 분류 기준

| 분류 | 뜻 | 근거 |
|---|---|---|
| 자기 상태의 검사 | 필요한 상태의 주인이 규칙을 지키는 객체 자신이다. 값의 유효성과 행동의 입력 조건을 포함한다. | 이론 문서: "자기 상태의 검사와 유스케이스의 협력을 구분", "공통 값의 유효성과 특정 행동의 입력 조건을 구분" |
| 유스케이스의 협력 | 규칙을 지키려면 다른 객체(또는 같은 종류의 다른 객체들)의 상태가 필요하다. | 이론 문서: "브랜드의 존재는 다른 객체를 조회해야 합니다" |
| 입력 검증 | 요청의 형식(누락, 타입, 표현 범위)만 본다. | 이론 문서: "입력 검증, 객체의 행동, 저장·조회" |
| 조회 결과의 구성 | 거절이 아니라 응답을 만들거나 걸러낸다. | 이론 문서: "조회 결과의 구성: 상품과 브랜드 정보를 조합해 필요한 응답을 만듭니다" |

이 절에는 자기 상태의 검사와 유스케이스의 협력만 둔다. 입력 검증은 API 계약의 대표 오류(6장)에, 조회 결과의 구성은 각 API의 응답·조회 조건(6장)에 적는다.

- **예외: ORD-06.** 조회 결과의 구성이지만 주문 확정의 실패 지점(5.4)으로 함께 다뤄야 해 규칙 목록에 남긴다.

| PRD-02 | 관리자 상품 수정 | 삭제되지 않은 상품만 수정한다 | Product | 자기 상태의 검사 |

| PRD-04 | 관리자 재고 변경 | 삭제되지 않은 상품만 재고를 변경한다 | Product | 자기 상태의 검사 |
| PRD-05 | 관리자 재고 변경 / 주문 확정 | 재고는 0 이상이다 | Product | 자기 상태의 검사 |
| PRD-06 | 주문 확정 | 차감 수량은 양수이고, 보유량보다 많이 차감할 수 없다 | Product | 자기 상태의 검사 |
| LIK-01 | 좋아요 등록 | 삭제되지 않은 상품에만 등록한다 | Product | 유스케이스의 협력 |
| LIK-02 | 좋아요 등록 | 같은 사용자–상품 관계는 하나만 존재한다 | Like | 유스케이스의 협력 (같은 종류의 다른 객체) |
| LIK-03 | 좋아요 취소 | 본인 관계만 취소하며, 상품이 삭제되었어도 취소할 수 있다 | Like | 자기 상태의 검사 |
| PNT-01 | 포인트 충전 | 충전액은 양의 정수다 | Point | 자기 상태의 검사 |
| PNT-02 | 포인트 충전 | 충전 후 잔액이 저장 타입의 표현 범위 안이다 | Point | 자기 상태의 검사 |
| PNT-03 | 주문 확정 | 잔액은 0 이상이다 (0원 허용) | Point | 자기 상태의 검사 |
| ORD-01 | 주문 생성 | 상품이 존재하고 삭제되지 않았다 | Product | 유스케이스의 협력 |
| ORD-02 | 주문 생성 | 품목 수량은 1 이상 999 이하다 | Order (품목 수량, 합산 후 기준이라 `Order.draft` 가 확인) | 자기 상태의 검사 |
| ORD-03 | 주문 생성 | 같은 상품의 품목은 하나로 합산해 저장한다 | Order | 자기 상태의 검사 |
| ORD-04 | 주문 생성 | 주문에는 품목이 하나 이상 있다 | Order | 자기 상태의 검사 |
| ORD-05 | 주문 생성 | 합계는 품목별 수량 × 단가의 합이다 | Order | 자기 상태의 검사 |
| ORD-06 | 주문 확정 | 본인 주문만 확정한다 | Order | 조회 결과의 구성 (소유자 조건 조회) |
| ORD-07 | 주문 확정 | DRAFT 상태에서만 확정한다 | Order | 자기 상태의 검사 |
| ORD-08 | 주문 확정 | 상품이 삭제되지 않았다 | Product | 유스케이스의 협력 |
| ORD-09 | 주문 확정 | 스냅샷 단가와 현재 가격이 같다 | Order / Product | 유스케이스의 협력 |
| ORD-10 | 주문 확정 | 모든 품목의 총수량 기준으로 재고가 충분한지 확인한 뒤 차감한다 | Order / Product | 유스케이스의 협력 |
| ORD-11 | 주문 확정 | 잔액이 결제액 이상이다 | Order / Point | 유스케이스의 협력 |
| ORD-12 | 주문 확정 | 결제 정보를 저장하고 CONFIRMED로 바꾸며, 재고·포인트 차감과 함께 반영된다 | Order / Product / Point | 유스케이스의 협력 |

- **BRD-02:** 상품 생성과 브랜드 삭제는 같은 규칙의 두 입구다. 상품 수정은 PRD-03 때문에 이 규칙을 깨지 않는다. 복원 기능이 생기면 입구가 늘어난다.
- **LIK-02:** 주인은 Like지만 Like 하나는 다른 Like의 존재를 알 수 없어 유스케이스의 협력으로 분류했다.
- **ORD-06:** 소유자까지 조건으로 건 조회로 처리한다(6.1). 타인의 주문은 조회되지 않아 "없는 주문"과 같은 응답이 된다.
- **USR-01:** 다른 유스케이스의 협력 규칙과 달리 `interfaces` 에서 확인한다(2.6). 식별이 필요한 모든 API의 입구에서 같은 확인을 빠뜨리지 않기 위해서다.
- **PRD-06과 ORD-10:** "보유량보다 많이 차감할 수 없음"은 Product 자신의 재고와 요청 수량의 비교라 자기 상태의 검사다. "모든 품목을 확인한 뒤 차감"은 Order의 총수량과 여러 Product의 재고가 필요해 유스케이스의 협력이다.

### 3.3 반례와 기대값

자기 상태의 검사 중 대표 규칙에 반례를 붙인다. 이 표가 도메인 단위 테스트의 입력과 기대값이 된다. 거절하는 경우 **기존 값이 유지되는지**까지 기대값에 포함한다.

| 규칙 ID | 반례 입력 | 기대 결과 |
|---|---|---|
| PRD-06 | 재고 5인 상품에 6 차감 | 거절하고 재고는 5로 유지된다 |
| PRD-06 | 재고 5인 상품에 0 또는 음수 차감 | 거절하고 재고는 5로 유지된다 |
| PRD-06 | 재고 5인 상품에 2 차감 | 재고가 3이 된다 (정상 사례) |
| PRD-06 | 재고 5인 상품에 `canDecrease(5)` | 참 (전량 차감 가능) |
| PRD-06 | 재고 5인 상품에 `canDecrease(6)` | 거짓 |
| PRD-06 | 재고 5인 상품에 `canDecrease(0)` 또는 음수 | 거짓 (예외를 던지지 않는다) |
| PNT-03 | 잔액 1,000에 `canPay(1,000)` / `canPay(1,001)` | 참 / 거짓 |
| PNT-03 | 잔액 0에 `canPay(0)` | 참 (0원 결제 허용) |
| ORD-09 | 스냅샷 단가 1,000원 품목에 현재 가격 1,000원 / 1,200원 / 800원 | 일치 / 불일치 / 불일치 (인하도 거절, 2.3) |
| PRD-05 | 관리자가 최종 재고를 음수로 설정 | 거절하고 기존 재고가 유지된다 |
| PNT-01 | 0원 충전 요청 | 거절하고 기존 잔액이 유지된다 (잔액 0원은 유효하지만 충전 0원은 충전이 아니다) |
| PNT-02 | 충전 후 잔액이 저장 타입의 표현 범위를 넘는 금액 | 거절하고 기존 잔액이 유지된다 |
| ORD-07 | CONFIRMED 주문을 다시 확정 | 거절하고 주문 상태·결제 정보가 그대로 유지된다 |
| ORD-09 | DRAFT 생성 후 상품 가격이 바뀐 상태에서 확정 | 거절하고 주문은 DRAFT로, 재고·잔액은 그대로 유지된다 |
| LIK-03 | 사용자 A가 좋아요한 상품에 사용자 B가 취소 요청 | 성공하지만 A의 관계는 남는다. 취소는 요청자 자신의 관계만 찾는다 |
| ORD-04 | 품목이 비어 있는 주문 생성 | 거절하고 주문이 만들어지지 않는다 |

- **TDD 대상으로 고를 대표 규칙:** PRD-06 (재고 차감). Red에서 "6 차감 거절 + 재고 5 유지"를 먼저 확인하고, 정상 사례(2 차감 → 3)를 함께 둔다. 정상 사례가 없으면 모든 요청을 거절하는 구현도 첫 테스트를 통과한다. `canDecrease` 의 기대값도 같은 사이클에서 다룬다.
- **0원 결제는 허용한다.** `point.canPay(0)` 은 참이다. 합계 0원 주문을 허용하므로(5.2) 거짓이면 0원 주문을 확정할 수 없다. 재고의 0 차감(`canDecrease(0)` 거짓)과 다른 이유는, 0 차감은 의미 없는 요청이지만 0원 결제는 0원 주문 확정에서 실제로 생기는 정상 요청이기 때문이다.
- 유스케이스의 협력에 속한 규칙의 반례는 대표 흐름(5.4)과 API 계약(6장)에 적는다.

## 4. 구조와 의존

기존 layer-first 구조와 명명을 따른다.

### 4.1 계층별 역할

| 계층 | 맡는 일 | 두는 것 | 직접 의존하지 않을 것 |
|---|---|---|---|
| `interfaces` | 고객·관리자의 입력과 응답 변환, 요청자 식별값 추출과 사용자 존재 확인(2.6), 오류의 HTTP 매핑 | `~V1Controller`, `~V1Dto`, `~V1ApiSpec` | `infrastructure` |
| `application` | 유스케이스의 순서와 객체 협력 조율, 응답용 모델 구성 | `~Facade`, `~Info` | `interfaces`, `infrastructure` |
| `domain` | 상태와 규칙, 여러 객체가 얽힌 업무 판단, 필요한 저장 약속 | 엔티티, `~Service`, `~Repository`(인터페이스) | `interfaces`, `application`, `infrastructure` |
| `infrastructure` | 저장 약속의 JPA 구현 | `~RepositoryImpl`, `~JpaRepository` | HTTP 응답 정책, 중복된 업무 규칙 |

`ArchitectureTest` 가 이 의존 방향을 검사한다.

### 4.2 이름 규칙

`application` 과 `domain` 모두에 조율하는 클래스가 있으므로 패키지와 접미사로 구분한다.

| 위치 | 접미사 | 하는 일 |
|---|---|---|
| `application/<기능>` | `~Facade` | 이론 문서의 애플리케이션 서비스. 모델 조회 → 행동 호출 → 저장 → 결과 구성 |
| `domain/<기능>` | `~Service` | 한 엔티티에 자연스럽게 속하지 않는 업무 판단 |

### 4.3 패키지 배치

```
interfaces/api/product        → application/product → domain/product
interfaces/api/admin/product  → application/product → domain/product
infrastructure/product        ─────────────────────→ domain/product
```

- 기능 단위는 `user`, `brand`, `product`, `like`, `point`, `order` 로 나눈다.
- 고객 API와 관리자 API는 `interfaces` 에서 갈라진다. 같은 저장된 상품을 쓰더라도 입력·출력 모델이 다르다(1장).
- 계층 밖의 패키지

  | 패키지 | 두는 것 |
  |---|---|
  | `interfaces/api/auth` | 요청자 식별(`LoginUser`, `LoginUserArgumentResolver`, 2.6) |
  | `interfaces/api` | 공통 응답 · 페이징(`ApiResponse`, `PageQuery`, `PageResponse`), 오류 변환(`ApiControllerAdvice`, `ErrorStatusMapper`) |
  | `support/error` | HTTP를 모르는 오류 코드 약속(`ErrorCode`, `ErrorType`, `CoreException`) |
  | `config` | 관리자 접근(`AdminBoundaryConfig`), 요청자 식별 등록(`WebMvcConfig`), JSON 설정(`CommerceApiJacksonConfig`), 로컬 사용자(`LocalUserInitializer`) |

  - `config` 는 여러 계층을 엮는 설정이라 `ArchitectureTest` 의 계층 규칙 대상이 아니다.

### 4.4 기존 패키지를 따르는 선택

- **저장 약속은 `domain` 의 인터페이스, 구현은 `infrastructure`.** `application` 은 구현체 이름을 모른다. 테스트에서는 DB 없이 fake 구현을 연결할 수 있다.
- **`domain` 의 `~Service` 가 조회·저장과 대상 없음 예외를 맡고, `~Facade` 는 조율과 결과 구성을 맡는다.** `ExampleService` · `ExampleFacade` 와 같은 분담이다.
- **트랜잭션 경계는 `domain` 의 `~Service` 에 둔다.**
- **유스케이스 계약에 따른 확인은 `~Facade` 가 한다.** 도메인 규칙이 아니라 요청을 어떻게 받아들일지에 대한 확인이다.
  - 관리자 필터의 대상 존재 확인: `AdminProductFacade` (`brandId`), `AdminOrderFacade` (`userId`). 고객 쪽은 같은 필터를 조회 조건으로만 쓰므로(D-24) 도메인 서비스에 넣지 않는다.
  - 경로의 `userId` 와 요청자 비교: `LikeFacade` (내 좋아요 목록, 6.1)
- **여러 객체에 걸친 협력은 `domain` 의 `~Service` 가 조율한다.** 주문 확정(ORD-06~ORD-12)이 여기에 해당한다.
  - 서비스는 필요한 모델을 조회하고(아래 "다른 도메인의 대상 조회"), 모두 확인한 뒤 각 객체의 행동을 호출한다. `ExampleService` 와 같은 모양이며 트랜잭션 경계가 이 서비스에 그대로 유지된다.
  - **확인도 변경도 조건 판단은 각 객체가 한다.** 확인 단계에서 서비스는 각 객체의 판단 메서드를 호출하고, 변경 단계에서 행동을 요청한다. 서비스가 값을 꺼내 비교하지 않는다.
    - 재고: `product.canDecrease(수량)` → `product.decrease(수량)` (ORD-10, PRD-06)
    - 잔액: `point.canPay(결제액)` → `point.pay(결제액)` (ORD-11, PNT-03)
    - 가격: 스냅샷 단가를 가진 `orderItem` 이 현재 가격을 받아 비교한다 (ORD-09, 2.3)
    - **변경 메서드는 같은 판단 메서드를 거쳐 거절한다.** 조건식은 판단 메서드 한 곳에만 있다. 확인 단계를 건너뛰고 변경 메서드를 바로 부르는 호출자가 생겨도 규칙이 뚫리지 않는다.
    - **판단 메서드는 `boolean` 을 반환하고, 오류 코드는 서비스가 정한다.** 서비스가 5.3의 순서대로 결과를 보고 처음 실패한 품목과 오류 코드를 고른다. 판단은 객체에, 유스케이스의 실패 표현은 조율하는 서비스에 둔다.
    - **`canDecrease` 는 0 이하 수량에 거짓을 반환한다.** 예외를 던지지 않는다. `decrease` 는 같은 판단을 거치므로 0 이하 수량을 거절한다(PRD-06).
    - **`decrease` 가 거절할 때의 코드는 이유와 관계없이 `OUT_OF_STOCK` 이다.** 조건을 판단 메서드 한 곳에 두려고 이유를 나누지 않았다. 실제 흐름에서는 주문 생성이 수량 1 이상을 먼저 보장하므로(ORD-02) 0 이하 차감은 생기지 않는다.
    - **버린 대안:** 검증 메서드가 예외를 던진다. 오류 코드와 상품 식별자를 객체가 직접 담을 수 있지만, 판단과 오류 표현이 한 메서드에 묶여 확인 순서가 "처음 실패하면 즉시 중단"으로 고정되고 같은 조건을 다른 용도로 쓰기 어렵다.
  - **버린 대안 ①** `~Facade` 가 조율한다. 유스케이스 순서가 한곳에 보이지만 업무 규칙인 재고·잔액 확인이 application에 자리하고, 트랜잭션 경계를 Facade로 올려야 한다.
  - **버린 대안 ②** 서비스는 판단만 하고 조회·저장은 `~Facade` 가 맡는다. DB 없이 확정 규칙을 테스트할 수 있지만 트랜잭션 경계가 Facade로 올라가고 예시 코드와 모양이 달라진다.
  - **버린 대안 ③** `Order` 가 상품·포인트를 받아 직접 차감한다. 이론 문서의 "상품이 사용자 잔액까지 직접 변경하지 않는다" 와 어긋난다.
  - **감수하는 비용:** `domain/order` 의 서비스가 `ProductService` · `PointService` 를 알게 된다. 확정 규칙을 테스트하려면 fake 저장 구현을 연결한 두 서비스가 필요하다.
- **다른 도메인의 대상 조회는 그 도메인의 `~Service` 를 호출한다.** 유스케이스의 협력 규칙은 그 유스케이스를 가진 도메인의 서비스가 조율하고, 다른 도메인의 대상이 필요하면 그 도메인의 서비스에 조회를 요청한다.

  | 규칙 | 조율하는 곳 | 호출하는 곳 |
  |---|---|---|
  | BRD-02 생성 입구 | `ProductService` | `BrandService` (살아 있는 브랜드). Product 생성자가 한 번 더 확인한다 |
  | BRD-02 삭제 입구 | `BrandService` | `BrandRepository` (브랜드에 살아 있는 상품이 있는가, 아래 참고) |
  | LIK-01 | `LikeService` | `ProductService` (살아 있는 상품) |
  | LIK-02 | `LikeService` | `LikeRepository` (기존 관계) + DB 유니크 키 |
  | ORD-01, 스냅샷 | `OrderService` | `ProductService` (살아 있는 상품들) |
  | 주문 확정 (ORD-06~ORD-12) | `OrderService` | `ProductService` (살아 있는 상품들), `PointService` (사용자의 Point) |

  - **이유:** 삭제 필터와 대상 없음 오류(`PRODUCT_NOT_FOUND` 등)가 도메인마다 한 곳에 모인다. 2.5에서 감수한 "삭제 상태 조건을 빠뜨리면 노출된다"는 비용을 호출 지점마다 반복하지 않는다. 행 없음을 0원 Point로 바꾸는 일도 `PointService` 한 곳에 남는다(2.3, 5.3).
  - **트랜잭션:** 호출된 서비스는 Spring 기본 전파(`REQUIRED`)에 따라 호출한 서비스의 트랜잭션에 합류한다. 확정할 때 차감하는 상품도 같은 트랜잭션에서 조회한 엔티티다.
  - **확인 순서:** `ProductService` 가 품목 순서대로 조회하다 처음 만난 없거나 삭제된 상품에서 `PRODUCT_NOT_FOUND` 를 던진다. 5.3의 "ORD-08을 먼저, 처음 실패한 품목을 알린다"와 맞는다.
  - **버린 대안:** 조율하는 서비스가 다른 도메인의 저장 약속을 직접 쓴다. 트랜잭션과 의존은 단순하지만 삭제 필터·대상 없음 오류·0원 Point 변환을 서비스마다 다시 쓴다.
  - **감수하는 비용:** 서비스끼리 의존이 생긴다. 서로를 호출하면 빈 순환 참조로 애플리케이션이 뜨지 않으므로(Spring Boot 2.6부터 기본 금지) 방향을 한쪽으로 유지해야 한다.
  - **대상 없음 오류도 호출된 서비스가 던진다.** 주문 생성·좋아요 등록·주문 확정이 모두 `ProductService` 의 `PRODUCT_NOT_FOUND` 를 그대로 쓴다. 이번 범위에서는 세 유스케이스의 오류가 모두 404로 같다.
  - **다시 검토할 조건:** 유스케이스마다 오류가 달라질 때(예: 확정에서만 삭제된 상품을 409로 알림, D-26). 그때는 `ProductService` 가 살아 있는 상품만 돌려주고 오류는 호출자가 정하는 방식으로 바꾼다. 공유된 예외를 잡아 다른 예외로 바꾸지 않는다(2.6과 같은 이유).
- **브랜드 삭제 입구는 `BrandRepository` 에 질문을 두고, 구현은 `infrastructure` 에서 상품 테이블을 조회한다.** `domain/product` 는 Brand 참조(D-02)와 `BrandService` 호출로 `domain/brand` 를 안다. `BrandService` 가 `ProductService` 나 `ProductRepository` 를 알면 두 패키지가 서로를 아는 순환이 생긴다.
  - `BrandRepository` 에 "이 브랜드에 살아 있는 상품(재고 0 포함)이 있는가"를 묻는 메서드를 두면, `domain/brand` 는 상품 클래스를 import하지 않는다. 의존은 `product → brand` 한 방향만 남는다.
  - **버린 대안:** 브랜드 삭제의 조율을 `domain/product` 로 옮긴다(기능 단위 패키지와 어긋남), `~Facade` 가 조율한다(트랜잭션 경계가 올라감), 순환을 남긴다(두 패키지를 떼어 낼 수 없음).
  - **감수하는 비용:** 브랜드의 저장 약속이 상품 테이블에 대한 질문을 품는다. 상품의 삭제 방식이 바뀌면 `infrastructure/brand` 의 조회도 함께 바꿔야 한다.
  - 패키지 순환을 검사하는 규칙은 두지 않는다. `ArchitectureTest` 는 계층 간 방향만 검사한다.
- **업무 오류 코드를 따로 둔다.** 1주차 결정 1을 이어간다. `domain` 에서 생긴 실패마다 고유한 업무 오류 코드를 붙이고, 그 코드를 HTTP 상태로 바꾸는 일은 `interfaces` 의 변환 지점(`ApiControllerAdvice`)에서 한다.
  - **이유:** `ErrorType` 만 쓰면 "없는 주문"과 "매핑되지 않은 경로"가 같은 404·같은 코드가 된다. 요청자가 주문을 다시 찾아야 할지 쿠폰·상품을 바꿔야 할지 고를 수 없어 메시지 문자열로 분기하게 된다.
  - **감수하는 비용:** 코드 목록을 관리해야 하고, 새 실패를 추가할 때 기존 코드와 의미가 겹치지 않는지 확인해야 한다.
  - **구현:** 모든 코드는 HTTP를 모르는 `ErrorCode` 인터페이스(`support/error`)를 따른다. 업무 코드는 도메인마다 enum으로 두고, 공통 코드인 `ErrorType` 도 같은 인터페이스를 따르며 `HttpStatus` 를 갖지 않는다. `interfaces` 의 `ErrorStatusMapper` 가 코드를 HTTP 상태로 바꾸고, 대응표에 없는 코드는 500이다.
  - **대응표 누락 방지:** `ErrorCode` 를 구현한 모든 enum의 모든 값이 대응표에 있는지 테스트가 확인한다(`ErrorStatusMapperTest`).
  - **버린 대안:** 도메인별 enum이 `HttpStatus` 를 직접 가진다. 코드와 상태가 한 줄에 있어 추가가 쉽지만 도메인이 HTTP에 의존한다.
  - **코드 표기는 enum 이름(`BAD_REQUEST`)으로 통일한다.** 기존 `ErrorType` 은 HTTP reason phrase(`Bad Request`)를 썼다. 1주차 관찰 테스트(`ContractClassificationTest`)의 기대값을 이 계약 변경에 맞춰 바꿨다.
- **엔티티는 `interfaces` 로 나가지 않는다.** `application` 이 `~Info` 로 바꾸고, `interfaces` 가 응답 모델로 바꾼다.
- **엔티티는 `modules:jpa` 의 `BaseEntity` 를 상속한다.** `domain` 에 JPA 애노테이션이 들어오지만 이번 범위에서는 그대로 둔다.
  - `BaseEntity` 의 `deletedAt` 과 멱등한 `delete()` 가 2.5의 논리 삭제 결정에 그대로 쓰인다.
  - 저장 전용 모델을 따로 두면 경계는 엄격해지지만 모델 간 변환과 관리 비용이 생긴다. 패키지 의존 규칙을 지키는 일과 프레임워크를 걷어내는 일은 다른 선택이다.

### 4.5 조회 결과 타입

상품 목록은 상품 · 브랜드 · 좋아요 수 집계를 DB에서 한 번에 가져와야 한다. 엔티티 하나로 표현되지 않으므로 조회 결과 타입이 필요하다.

**조회 결과 타입을 `domain` 에 두고, 기존 `~Repository` 가 그 타입을 반환한다.**

- **반환 타입은 `domain` 의 것이어야 한다.** 인터페이스가 `domain` 에 있어도 `interfaces` 의 DTO를 반환하면 경계가 새어 나간다(4.1).
- **조회 타입은 재고 수량까지 담고, 품절 여부로 바꾸는 일은 응답을 만들 때 한다.** 관리자 응답에는 수량이 그대로 필요하다(2.4).
- **구현한 조회 결과 타입**

  | 타입 | 위치 | 쓰는 곳 | 만드는 곳 |
  |---|---|---|---|
  | `ProductView` | `domain/product` | 고객 상품 목록 · 상세 (좋아요 수 집계 · 브랜드 설명) | `ProductRepository` (QueryDSL, outer join · 동적 정렬) |
  | `ProductWithBrand` | `domain/product` | 관리자 상품 목록 · 상세 (재고 수량 · 브랜드 이름) | `ProductRepository` (JPQL 생성자 조회) |
  | `LikedProduct` | `domain/like` | 내 좋아요 목록 (상품 요약 · 좋아요 시각) | `LikeRepository` (QueryDSL) |
  | `OrderSummary` | `domain/order` | 고객 · 관리자 주문 목록 (품목 개수 · 대표 상품명) | **`OrderService` 가 트랜잭션 안에서 엔티티로 만든다.** `open-in-view` 가 꺼져 있어 트랜잭션 밖에서 품목을 읽을 수 없고, 품목은 설정된 `default_batch_fetch_size` 로 한 번에 불러온다 |

  - 주문 상세와 확정은 조회 결과 타입 대신 품목을 fetch join 으로 함께 읽은 엔티티를 쓴다.
- **버린 대안 ①** 조회 전용 인터페이스를 따로 둔다. 저장과 조회가 나뉘지만 이번 범위의 그런 조회는 위 네 가지뿐이라 구조만 늘어난다.
- **버린 대안 ②** `application` 에 인터페이스를 두고 `infrastructure` 가 구현한다. 조회 모델이 유스케이스 가까이 가지만 `infrastructure` 가 `application` 을 알게 된다.
- **감수하는 비용:** 저장용 메서드와 조회용 메서드가 한 인터페이스에 섞인다.
- **다시 검토할 조건:** 조회 메서드가 늘어나거나, 저장 쪽 변경과 조회 쪽 변경이 서로를 흔들기 시작할 때 조회 전용 인터페이스로 나눈다.

#### 반례 대입: 상품 규칙과 조회 조합을 어디에 두는가

과제가 제시한 질문 "브랜드 응답이 바뀌면 어떤 객체까지 바뀌는가?"를 두 안에 대입한다.

- **A안** Product가 상품 규칙과 함께 브랜드·좋아요 조회, 응답 조합까지 맡는다.
- **B안 (선택)** Product는 자신의 상태와 규칙만 맡는다. 조합은 조회 결과 타입(4.5)이 DB에서 가져오고, `~Facade` 가 `~Info` 로, `interfaces` 가 응답 모델로 바꾼다.

| 변경 | A안에서 바뀌는 곳 | B안에서 바뀌는 곳 |
|---|---|---|
| 브랜드 응답에 필드 추가 (예: 로고) | Product의 조합 코드, 응답 | 조회 결과 타입, `~Info`, 응답 모델. **Product 엔티티는 바뀌지 않는다** |
| 좋아요 수를 카운터 컬럼으로 바꿈 | Product의 좋아요 조회 코드 | `infrastructure` 의 세 조회 구현(상품 목록·상세, 내 좋아요 목록, 좋아요 등록·취소 응답). 조회 결과 타입은 그대로 |
| 고객은 품절 여부, 관리자는 수량 (2.4) | Product에 응답용 메서드가 두 벌 생김 | 고객·관리자 응답 모델이 각자 바꾼다 |
| 재고 규칙 변경 (예: 차감 조건) | Product | Product |

- **결과:** A안은 응답·조회 방식이 바뀔 때마다 상품 규칙을 가진 Product가 함께 바뀐다. 서로 다른 변경 이유가 한 클래스에 모인다(SRP). B안에서 Product가 바뀌는 경우는 상품 규칙이 바뀔 때뿐이다.
- **B안이 치르는 비용:** 브랜드 필드 하나를 추가해도 조회 결과 타입 · `~Info` · 응답 모델 세 곳을 거친다. 조회를 조율하고 모델을 바꾸는 코드가 필요하다.
- **Product → Brand 객체 참조(2.3)와의 관계:** 이 참조는 "브랜드 없이 존재할 수 없다"는 불변식을 지키려고 둔 것이다. 고객·관리자 응답의 브랜드 정보는 이 참조를 따라가 만들지 않고 조회 결과 타입에서 가져온다. 참조를 따라가 응답을 만들기 시작하면 A안의 문제가 되돌아온다.
  - **Product는 Brand를 밖으로 내보내지 않는다.** Brand를 돌려주는 getter를 두지 않아, 참조를 따라가 응답을 만드는 코드가 컴파일되지 않게 한다. 문서와 리뷰로만 지키면 규칙이 깨져도 테스트가 실패하지 않는다.
  - **감수하는 비용:** Product 생성 시 브랜드 확인 외에는 Brand를 쓸 수 없다. 관리자 상품 응답의 브랜드 이름(6.5)도 조회 결과 타입에서 가져와야 한다. 클래스 전체에 getter를 만드는 Lombok 설정을 쓰면 이 필드만 제외해야 한다.

## 5. 대표 흐름: 포인트 충전 → 주문 확정

고객이 포인트를 충전하고, 주문을 만들고, 확정해 결제하는 흐름이다. 여러 객체가 협력하는 흐름이라 대표로 고른다.

**이 문서에서 "확정(confirm)"은 결제를 마치는 것을 뜻한다.** 수령 후의 구매확정과는 다르다. 이번 범위의 주문 상태는 DRAFT·CONFIRMED뿐이고 배송·취소·환불은 없다.

### 5.1 연결 흐름

```
POST /api/v1/points/charge        10,000 충전  → 잔액 10,000
POST /api/v1/orders               DRAFT 생성   → 합계 7,000 (차감 없음)
POST /api/v1/orders/{id}/confirm  확정·결제    → 재고 차감, 포인트 7,000 차감
GET  /api/v1/points               잔액 조회    → 3,000
GET  /api/v1/orders/{id}          주문 조회    → 품목·금액·상태·결제액
```

### 5.2 주문 생성 (DRAFT)

```
생성 요청 → [요청자 식별]              interfaces
          → 살아 있는 상품들 조회        domain/order 의 ~Service → ProductService
          → [확인] ORD-01, ORD-02, ORD-04
          → 같은 상품 품목 합산          ORD-03
          → 스냅샷(상품명·단가) 저장
          → [합계 계산] ORD-05
          → DRAFT 저장 → OrderInfo 구성  ~Facade
```

- **차감하지 않는다.** 재고와 포인트는 확정할 때만 움직인다.
- **같은 상품의 품목은 저장할 때 합친다.** 요청이 두 줄이어도 주문에는 한 품목으로 남는다. 이후의 합계·가격 비교·재고 차감이 상품별로 유일한 품목을 다루게 된다.
  - **버린 대안:** 요청한 모양대로 저장하고 재고 확인만 총수량으로 한다. 요청이 그대로 보이지만 합계·가격 비교·차감이 매번 상품별로 모아 계산해야 한다.
  - **감수하는 비용:** 고객이 보낸 품목 수와 주문 조회의 품목 수가 다를 수 있다.
- 같은 상품이므로 합산한 품목의 단가는 하나로 정해진다. 스냅샷은 같은 시점에 찍힌다.
- **품목은 요청 순서로 저장한다.** 합산한 품목은 그 상품이 요청에서 처음 등장한 위치에 둔다. 읽을 때는 품목 식별자 오름차순으로 읽어 저장한 순서를 그대로 돌려준다.
  - 이 순서가 "처음 실패한 품목"(5.3), 오류 응답의 상품 식별자, 대표 상품명(6.4)의 기준이다. 정렬 기준을 주지 않으면 DB가 돌려주는 순서가 보장되지 않아 기대값이 흔들린다.
- **품목이 비어 있는 주문은 거절한다**(ORD-04). 품목이 없는 주문은 주문으로서 의미가 없다. 0원 상품을 허용하므로 합계가 0원인 주문은 거절하지 않는다. 빈 주문이 만들어지지 않으므로 확정 단계에서 품목이 없는 경우를 다루지 않아도 된다.

### 5.3 주문 확정 (CONFIRMED)

조율은 `domain/order` 의 `~Service` 가 맡는다(4.4).

```
확정 요청 → [요청자 식별]                      interfaces
          ── 확인 단계 ────────────────────────       domain/order 의 ~Service
          → 주문 조회 (소유자 조건 · 품목 함께)    ORD-06
          → DRAFT 인가                          ORD-07
          → 살아 있는 상품들 조회 (품목 순서)      ORD-08   → ProductService
          → orderItem.가격 일치 판단(현재 가격)    ORD-09
          → product.canDecrease(수량)            ORD-10
          → 사용자의 Point 조회 (행 없으면 0원)   → PointService
          → point.canPay(결제액)                 ORD-11
          ── 변경 단계 ────────────────────────
          → product.decrease(수량)    PRD-06   같은 판단을 거쳐 거절함
          → point.pay(결제액)         PNT-03
          → order.확정(결제 정보)     ORD-12
          → 저장 → OrderInfo 구성      ~Facade
```

- **모두 확인한 뒤 모두 변경한다.** 트랜잭션 롤백은 DB 반영만 막고 메모리의 객체는 이미 바뀐 채로 남는다. 모두 확인한 뒤 변경해야 "거절 시 기존 값 유지"를 DB 없이 확인할 수 있다(2.3).
- **확인 순서는 위 순서로 고정한다.** 재고와 잔액이 둘 다 부족하면 **재고 부족**을 알린다.
- **여러 품목의 재고가 부족하면 품목 순서대로 처음 실패한 상품을 알린다.** 순서를 정해 두어야 기대값이 흔들리지 않는다.
- **조건 판단은 각 객체가 한다.** 서비스는 판단 메서드의 결과로 거절 여부와 오류 코드를 정하고, 비교식을 직접 쓰지 않는다(4.4).
- **포인트 행이 없으면 잔액 0원으로 본다**(2.3). 충전한 적이 없는 고객이 결제액이 0원보다 큰 주문을 확정하면 잔액 부족으로 거절된다.
- **충전한 적 없는 고객의 0원 결제는 Point 행을 만들지 않는다.** 잔액이 바뀌지 않으므로 행을 만들 이유가 없다. 행은 여전히 첫 충전 때만 생긴다(2.3).
  - **구분하는 코드가 필요 없다.** `OrderService` 는 Point를 저장하지 않는다. 행이 있는 Point는 같은 트랜잭션에서 조회한 엔티티라 변경 감지로 반영된다. 행이 없는 Point(0원)는 결제액이 0보다 크면 `canPay` 에서 거절되므로, 변경 단계까지 오는 경우는 0원 결제뿐이고 잔액이 바뀌지 않은 채 저장되지 않는다.

### 5.4 실패 지점과 유지되는 것

| 실패 | 규칙 | 유지되는 것 |
|---|---|---|
| 타인의 주문 확정 | ORD-06 | 주문 상태·재고·잔액 그대로 |
| 이미 확정된 주문 | ORD-07 | 기존 결제 정보 그대로 |
| 삭제된 상품 포함 | ORD-08 | DRAFT 유지, 재고·잔액 그대로 |
| 가격이 달라짐 | ORD-09 | DRAFT 유지, 재고·잔액 그대로 |
| 재고 부족 | ORD-10 | DRAFT 유지, 재고·잔액 그대로 |
| 잔액 부족 | ORD-11 | DRAFT 유지, 재고·잔액 그대로 |

확인 단계에서 거절하므로 어떤 실패에서도 재고와 잔액이 바뀌지 않는다. 확인과 변경을 나눈 이유가 이 표다.

### 5.5 확정할 때 저장하는 것

| 값 | 저장하는 이유 |
|---|---|
| 결제액 | 합계는 주문을 만든 시점의 금액이고 결제액은 실제로 차감한 금액이다. 지금은 값이 같지만 할인이 붙으면 갈라진다 |
| 결제 시각 | `BaseEntity.updatedAt` 은 이후 변경으로 덮인다. 언제 결제됐는지는 덮이면 안 되는 값이므로 별도로 둔다 |
| 결제 결과 | 별도 필드를 두지 않고 **주문 상태가 대신한다.** 결제가 실패하면 확정 자체가 거절되므로 저장된 주문에는 성공만 남는다 |

- **결제 수단은 포인트뿐이다.** 수단이 늘어나면 결제 결과를 따로 담을지 다시 검토한다.

## 6. API 계약

### 6.1 공통 규칙

| 항목 | 값 |
|---|---|
| 고객 API | `/api/v1/**`. 좋아요 · 포인트 · 주문은 `X-USER-ID` 헤더로 요청자를 식별한다. 상품 · 브랜드 조회는 식별하지 않는다 (2.6) |
| 식별 실패 | 헤더 누락 · 형식 오류 · 없는 사용자는 모두 `UNAUTHENTICATED` 401 (USR-01) |
| 관리자 API | `/api-admin/v1/**`, ADMIN 역할을 확인한다. 일반·미식별 요청은 403 |
| 응답 | `ApiResponse` (`meta.result`, `data`) |
| 오류 표현 | 업무 오류 코드를 응답에 담고, HTTP 상태로 바꾸는 일은 `interfaces` 에서 한다 (4.4) |
| 소유 자원 | 요청자의 것이 아니면 **없는 대상 오류(404)** 로 응답한다. "없음"과 "타인 것"을 구분하지 않는다 |

**식별 실패는 하나의 응답으로 묶는다.** 헤더 누락, 숫자가 아닌 값, 없는 사용자를 모두 "요청자를 확인할 수 없음"으로 본다.

- **이유:** 사용자 존재 여부가 드러나지 않는다. 아래 소유 자원 원칙과 같은 방향이다.
- **버린 대안:** 누락은 400, 없는 사용자는 404로 나눈다. 기존 코드를 재사용하지만 상품·주문 요청에 404가 나오면 대상이 없는 것처럼 보이고, 사용자 존재 여부가 드러난다.
- **감수하는 비용:** 클라이언트는 헤더를 빠뜨렸는지 잘못 넣었는지 응답만으로 구분할 수 없다.

**소유 자원의 조회·변경**은 소유자까지 조건으로 건 조회로 처리한다. 1주차 `INV-001` 에서 고른 방식을 이어간다.

- 대상: 내 좋아요 목록, 내 잔액, 내 주문 목록·상세, 주문 확정(ORD-06)
- 경로에 `userId` 가 있는 API는 경로 값과 `X-USER-ID` 가 다르면 없는 대상 오류로 응답한다.
- **이유:** 403으로 나누면 "그 사용자·주문이 존재한다"는 사실이 드러난다.
- **감수하는 비용:** 클라이언트는 식별값을 잘못 보냈는지 대상이 없는지 응답만으로 구분할 수 없다.

**페이징**

| 항목 | 값 |
|---|---|
| 파라미터 | `page`, `size` |
| `page` | **1부터 시작**. 기본값 1 |
| `size` | 기본값 20, 최대 100 |
| 응답 | `items`, `page`, `size`, `totalCount`, `totalPages` |

- 외부 계약은 1부터 쓰고, 0부터 시작하는 내부 표현으로 바꾸는 일은 `interfaces` 에서 한 번만 한다.
- `totalPages` 는 서버가 계산해 내려준다. 클라이언트마다 같은 계산을 반복하지 않는다.
- **감수하는 비용:** 전체 개수를 위해 count 쿼리가 한 번 더 나간다.

**잘못된 입력은 400으로 거절한다.** 기본값으로 대체하지 않는다. 없는 정렬 값, `page` 가 1 미만, `size` 가 1 미만이거나 100 초과, 경로 변수에 숫자가 아닌 값이 모두 해당한다.

- **버린 대안:** 기본값·상한으로 대체한다. 화면은 항상 뜨지만 클라이언트가 잘못 보낸 것을 모르고 지나간다.
- **정수 필드에 소수를 보내면 400으로 거절한다.** Jackson은 기본적으로 소수점을 버리고 받아들여(`ACCEPT_FLOAT_AS_INT`), 충전액 1.5가 1원으로 충전되는 식으로 요청과 다른 값이 저장된다. commerce-api에서만 이 설정을 끈다(`CommerceApiJacksonConfig`). 공용 모듈은 다른 앱에도 영향을 주므로 바꾸지 않는다.
- **응답의 시각은 `Asia/Seoul` 한 시간대로 내보낸다.** (로컬 실행으로 발견) 방금 만든 엔티티는 시스템 시간대(`+09:00`)로, DB에서 다시 읽은 엔티티는 JPA 설정(`NORMALIZE_UTC`)에 따라 UTC(`Z`)로 나가, 같은 주문의 `orderedAt` 이 생성 응답과 확정 응답에서 다르게 표기됐다. 같은 순간이지만 클라이언트가 문자열을 비교 · 표시하면 혼란스럽다. `CommerceApiJacksonConfig` 에서 응답 시간대를 고정한다.

**정렬**

| `sort` | 정렬 기준 |
|---|---|
| `latest` (기본값) | 생성 시각 desc, 식별자 desc |
| `price_asc` | 가격 asc, 식별자 desc |
| `likes_desc` | 좋아요 수 desc, 식별자 desc |

- 동률의 보조 기준을 식별자 desc로 고정한다. 보조 기준이 없으면 같은 상품이 두 페이지에 나오거나 어느 페이지에도 나오지 않을 수 있다.

### 6.2 상품 · 브랜드 조회

식별하지 않는다(2.6). `X-USER-ID` 가 없어도 조회할 수 있다.

| method · path | 입력 | 성공 | 대표 오류 |
|---|---|---|---|
| `GET /api/v1/brands/{brandId}` | 경로 변수 | 200, 브랜드 식별자·이름·설명 | `BRAND_NOT_FOUND` 404, `BAD_REQUEST` 400 |
| `GET /api/v1/products` | `brandId`(선택), `sort`, `page`, `size` | 200, 목록 + 페이징 정보 | `BAD_REQUEST` 400 |
| `GET /api/v1/products/{productId}` | 경로 변수 | 200, 상품 상세 | `PRODUCT_NOT_FOUND` 404, `BAD_REQUEST` 400 |

**응답 필드**

| | 목록 | 상세 |
|---|---|---|
| 상품 | 식별자, 이름, 가격, 좋아요 수, 품절 여부 | 좌측과 같음 |
| 브랜드 | 식별자, 이름 | 식별자, 이름, 설명 |

- **재고 수량은 고객 응답에 넣지 않는다.** 품절 여부만 내보낸다 (2.4).
- **좋아요 수는 관계에서 집계한다.** 좋아요가 없는 상품이 빠지지 않도록 outer join으로 세고, `likes_desc` 정렬도 이 집계로 DB에서 처리한다. 애플리케이션에서 조합한 뒤 정렬하면 페이징이 깨진다.

**삭제된 대상**

| 상황 | 결과 |
|---|---|
| 없거나 삭제된 브랜드·상품의 상세 조회 | 없는 대상 오류 (404). 삭제 여부를 구분해 노출하지 않는다 |
| 목록 조회 | 삭제된 상품을 제외한다 |
| `brandId` 필터에 없거나 삭제된 브랜드 | **빈 목록** (200). 고객 쪽 필터는 조회 조건이지 조회 대상이 아니다. 관리자 쪽 필터는 다르게 다룬다(6.5) |

**오류 코드**

| 코드 | HTTP | 상황 |
|---|---|---|
| `BRAND_NOT_FOUND` | 404 | 없거나 삭제된 브랜드 |
| `PRODUCT_NOT_FOUND` | 404 | 없거나 삭제된 상품 |
| `BAD_REQUEST` | 400 | 경로 변수 형식 오류, 잘못된 정렬·페이징 입력 |

### 6.3 좋아요

| method · path | 입력 | 성공 | 대표 오류 |
|---|---|---|---|
| `POST /api/v1/products/{productId}/likes` | 경로 변수 | 200, 상품 식별자 · 현재 좋아요 수 | `UNAUTHENTICATED` 401, `PRODUCT_NOT_FOUND` 404, `BAD_REQUEST` 400 |
| `DELETE /api/v1/products/{productId}/likes` | 경로 변수 | 200, 상품 식별자 · 현재 좋아요 수 | `UNAUTHENTICATED` 401, `BAD_REQUEST` 400 |
| `GET /api/v1/users/{userId}/likes` | 경로 변수, `page`, `size` | 200, 목록 + 페이징 정보 | `UNAUTHENTICATED` 401, `USER_NOT_FOUND` 404, `BAD_REQUEST` 400 |

**등록과 취소는 멱등하다**

| 요청 | 결과 |
|---|---|
| 관계가 없을 때 등록 | 관계를 만들고 성공 |
| **이미 있는 관계를 다시 등록** | 관계를 그대로 두고 성공. 좋아요 수는 늘지 않는다 (LIK-02) |
| 자신의 관계를 취소 | 관계를 지우고 성공 (LIK-03) |
| **없는 관계를 취소** | 성공. 상태가 이미 원하는 모습이다 |

- **이유:** 응답을 받지 못한 클라이언트가 그대로 다시 요청할 수 있다. 화면에 하트가 채워진 상태에서 오류를 띄우지 않아도 된다.
- **버린 대안:** 중복 등록을 409로 거절한다. 중복 요청임을 알 수 있지만 재시도마다 오류 처리가 필요하다.
- **감수하는 비용:** 응답만으로는 이번에 새로 눌렀는지 이미 눌러 둔 것인지 구분할 수 없다.
- 응답에 **현재 좋아요 수**를 담아 화면이 바로 갱신할 수 있게 한다. 성공은 200이며, 기존 `ApiResponse` 를 쓰므로 204를 쓰지 않는다.

**등록과 취소의 조건이 다르다**

| 대상 | 등록 | 취소 |
|---|---|---|
| 없는 상품 | `PRODUCT_NOT_FOUND` | **멱등 성공** (관계가 없으므로 지울 것도 없다) |
| 삭제된 상품 | 거절 (LIK-01) | **가능** (LIK-03) |

- 취소는 상품의 상태를 보지 않고 자신의 관계만 찾는다. 그래서 없는 상품·삭제된 상품에서도 같은 방식으로 동작한다.
- 응답의 좋아요 수도 관계에서 센다. 없는 상품의 취소는 관계가 없으므로 요청한 상품 식별자와 좋아요 수 0을 돌려준다.

- 삭제된 상품에 새 좋아요는 달 수 없지만, 남아 있는 자신의 관계는 취소할 수 있어야 한다. 논리 삭제를 고른 근거 중 하나다(2.5).

**내 좋아요 목록**

| 항목 | 값 |
|---|---|
| 정렬 | 좋아요 시각 desc, 식별자 desc (최근에 누른 순) |
| 페이징 | 6.1의 `page` · `size` 규칙을 따른다 |
| 응답 필드 | 상품 요약(식별자 · 이름 · 가격 · 브랜드 식별자 · 브랜드 이름 · 좋아요 수 · 품절 여부) + 좋아요 시각 |
| 제외 | 삭제된 상품은 목록에서 제외한다 |
| 소유 | 경로의 `userId` 가 `X-USER-ID` 와 다르면 `USER_NOT_FOUND` (6.1) |

**오류 코드**

| 코드 | HTTP | 상황 |
|---|---|---|
| `PRODUCT_NOT_FOUND` | 404 | 없는 상품, 또는 삭제된 상품에 좋아요 등록 |
| `UNAUTHENTICATED` | 401 | 헤더 누락 · 형식 오류 · 없는 사용자 (2.6) |
| `USER_NOT_FOUND` | 404 | 경로의 `userId` 가 요청자 본인이 아님 (요청자는 확인된 상태) |
| `BAD_REQUEST` | 400 | 경로 변수 형식 오류, 잘못된 페이징 입력 |

**알려진 한계:** 같은 사용자–상품의 등록 요청이 동시에 오면 둘 다 관계가 없다고 보고 저장을 시도한다. 유니크 키(LIK-02)가 데이터를 지키지만 한쪽 요청은 실패한다. 포인트 첫 충전과 같은 상황이며 이번 범위에서는 해결하지 않는다.

### 6.4 포인트 · 주문

| method · path | 입력 | 성공 | 대표 오류 |
|---|---|---|---|
| `POST /api/v1/points/charge` | `{ "amount": <정수> }` | 200, 충전 후 잔액 | `UNAUTHENTICATED` 401, `INVALID_CHARGE_AMOUNT` 400, `BALANCE_LIMIT_EXCEEDED` 409, `BAD_REQUEST` 400 |
| `GET /api/v1/points` | - | 200, 잔액 | `UNAUTHENTICATED` 401 |
| `POST /api/v1/orders` | `{ "items": [{ "productId": <정수>, "quantity": <정수> }] }` | 200, 만든 주문 전체 | `UNAUTHENTICATED` 401, `PRODUCT_NOT_FOUND` 404, `EMPTY_ORDER_ITEMS` 400, `INVALID_QUANTITY` 400, `BAD_REQUEST` 400 |
| `POST /api/v1/orders/{orderId}/confirm` | 경로 변수 | 200, 확정된 주문 | `UNAUTHENTICATED` 401, `ORDER_NOT_FOUND` 404, `ORDER_ALREADY_CONFIRMED` 409, `PRODUCT_NOT_FOUND` 404, `PRODUCT_PRICE_CHANGED` 409, `OUT_OF_STOCK` 409, `INSUFFICIENT_POINT` 409 |
| `GET /api/v1/orders` | `status`(선택, 기본 `CONFIRMED`), `page`, `size` | 200, 목록 + 페이징 정보 | `UNAUTHENTICATED` 401, `BAD_REQUEST` 400 |
| `GET /api/v1/orders/{orderId}` | 경로 변수 | 200, 주문 상세 | `UNAUTHENTICATED` 401, `ORDER_NOT_FOUND` 404, `BAD_REQUEST` 400 |

- 성공은 모두 200으로 통일한다. 기존 `ApiResponse` 를 쓰므로 201·204를 따로 쓰지 않는다.
- 주문 조회는 본인 것만 다룬다. 없는 주문과 타인의 주문은 같은 응답이다 (6.1).
- 충전한 적이 없으면 잔액은 0원이다 (2.3).

**포인트 충전**

| 상황 | 코드 | HTTP | 지키는 곳 |
|---|---|---|---|
| `amount` 누락 · 숫자가 아님 · 소수 · 표현 범위 초과 | `BAD_REQUEST` | 400 | 요청 형식 (`interfaces`) |
| `amount` 가 0 이하 | `INVALID_CHARGE_AMOUNT` | 400 | Point (PNT-01) |
| 충전 후 잔액이 표현 범위 초과 | `BALANCE_LIMIT_EXCEEDED` | 409 | Point (PNT-02) |

- **0 이하 거절은 Point 한 곳에서만 한다.** 요청 DTO에서 다시 검사하지 않는다.
  - **이유:** 도메인 거절도 같은 코드(`INVALID_CHARGE_AMOUNT`)와 메시지를 주고 DB를 바꾸기 전에 일어나, DTO에서 먼저 거절해 얻는 이점이 거의 없다. 조건이 두 곳에 있으면 한쪽만 바뀔 위험이 남는다.
  - **구현하며 바뀐 판단:** 처음에는 DTO에서도 검사하기로 했다. Bean Validation(`@Positive`)을 쓰면 실패 코드가 `BAD_REQUEST` 가 되어 계약(`INVALID_CHARGE_AMOUNT`)과 어긋나고, 맞추려면 필드와 코드의 대응을 따로 만들어야 했다.
  - **감수하는 비용:** 0 이하 요청도 Point 조회 한 번을 거친 뒤 거절된다.
- **표현 범위 초과를 409로 두는 이유:** 요청 자체는 형식이 맞고, 현재 잔액과 합쳐질 때 비로소 불가능해진다. 상태 충돌에 가깝다.
- 상한은 별도 정책 값을 두지 않고 저장 타입(`long`)의 표현 범위로 본다. 정책 상한이 생기면 그때 값을 정한다.

**주문 생성**

- 응답은 만든 주문 전체(식별자 · 상태 · 품목 · 합계)를 내려준다. 고객이 조회 API를 한 번 더 부르지 않아도 된다.
- **같은 상품의 품목은 합산되므로 응답의 품목 수가 요청과 다를 수 있다** (5.2).
- 없거나 삭제된 상품이 있으면 `PRODUCT_NOT_FOUND` 로 거절하고 주문을 만들지 않는다 (ORD-01).
- 품목이 비어 있으면 `EMPTY_ORDER_ITEMS` 로 거절한다 (ORD-04).
- 품목 수량이 1 이상 999 이하가 아니면 `INVALID_QUANTITY` 로 거절한다 (ORD-02). **같은 상품을 합산한 뒤의 수량으로 판단한다.** 두 줄로 600개씩 보내면 합산해 1,200개가 되어 거절된다.
  - **요청의 각 줄도 1 이상이어야 한다.** (구현하며 정함) 합산 후만 보면 `5` 와 `-3` 을 보낸 요청이 수량 2 로 받아들여진다. 음수 줄은 요청 자체가 잘못된 것이므로 줄마다 먼저 확인한다.

**주문 확정**

- 응답은 확정된 주문(품목 · 합계 · 상태 · 결제액 · 결제 시각)이다. **남은 잔액은 담지 않는다.** 주문 응답은 주문에 집중하고, 잔액은 잔액 조회 API가 맡는다.
- 확인 순서는 5.3을 따른다. 재고와 잔액이 둘 다 부족하면 `OUT_OF_STOCK` 이 나간다.
- **오류 응답에 문제가 된 상품 식별자를 담는다.** 품목 순서대로 처음 실패한 상품이며(5.3), 고객이 그 품목을 빼고 다시 주문할 수 있다.
  - **표현:** 실패 응답의 `data` 에 `{ "productId": ... }` 로 담는다. 메시지 문자열에 넣으면 클라이언트가 문자열을 해석해야 한다(1주차 결정 1). `CoreException` 이 부가 정보를 들고, `ApiControllerAdvice` 가 이를 `data` 로 내보낸다.
  - `ProductService` 의 `PRODUCT_NOT_FOUND` 는 호출한 유스케이스와 관계없이 항상 상품 식별자를 담는다. 공유된 예외를 잡아 다시 던지지 않기 위해서다(4.4).
- **확정 시 삭제된 상품은 `PRODUCT_NOT_FOUND` 404로 응답한다.** 조회 계약에서도 삭제된 대상을 "없음"으로 다루므로 일관된다(6.2).
  - **감수하는 비용:** 주문을 만들 때는 있던 상품이라 상태가 바뀐 상황에 가깝지만 404로 응답한다. 상태 충돌을 구분해야 할 이유가 생기면 별도 코드로 나눈다.
- 어떤 실패에서도 주문은 DRAFT로 남고 재고·잔액은 바뀌지 않는다 (5.4).

**내 주문 목록 · 상세**

| | 목록 | 상세 |
|---|---|---|
| 필드 | 주문 식별자, 상태, 합계, 결제액, 품목 개수, 대표 상품명, 주문 시각 | 주문 식별자, 상태, 합계, 결제액, 결제 시각, 품목 전체(상품 식별자 · 상품명 · 단가 · 수량 · 금액) |

- 정렬은 주문 시각 desc, 식별자 desc. 페이징은 6.1 규칙을 따른다.
- **`status` 필터를 두고, 생략하면 `CONFIRMED` 만 보여준다.** `DRAFT` 를 주면 확정 전 주문을 볼 수 있다. 없는 값은 400이다(6.1).
  - **이유:** 가격이 바뀌어 확정할 수 없게 된 DRAFT(ORD-09)는 취소 API가 없어 계속 남는다. 기본 목록에서는 결제를 마친 주문만 보여 이런 DRAFT가 섞이지 않게 한다. 상태 컬럼만 보면 되므로 조회가 가볍고 결과가 흔들리지 않는다.
  - **버린 대안:** 목록 조회 때 현재 가격과 비교해 확정할 수 없는 DRAFT를 제외한다. 조회가 상품 가격까지 뒤져야 하고, 가격이 되돌아가면 다시 나타나 `totalCount` 가 흔들린다. 확정 실패 시 새 상태로 바꾸는 방식은 과제의 두 상태를 넘어서고 "실패해도 DRAFT로 남는다"(5.4)와 충돌한다.
  - **감수하는 비용:** `DRAFT` 를 골라 보면 확정할 수 없는 DRAFT도 그대로 나온다. 근본 해결(취소 API, DRAFT 유효 기간)은 이번 범위 밖이다(8.3).
  - 관리자 주문 목록의 `status` 는 생략하면 전체다(6.5). 관리자는 확정 전 주문도 관리 대상이다.
- 대표 상품명은 첫 품목의 상품명으로 한다. 목록에서 품목 전체를 내려주지 않아 조회가 가벼워진다.
- 품목의 상품명·단가는 주문 시점 스냅샷이다. 상품이 이후에 바뀌거나 삭제되어도 주문 내역은 그대로 보인다 (2.3).

#### 입력 범위

| 대상 | 범위 | 규칙 |
|---|---|---|
| 브랜드 이름 | 공백뿐이 아니고 20자 이하 | BRD-03 |
| 브랜드 설명 | 선택. 255자 이하 | BRD-03 |
| 상품 이름 | 공백뿐이 아니고 50자 이하 | PRD-01 |
| 상품 가격 | 0원 이상 1억 원 이하 | PRD-01 |
| 재고 | 0 이상 | PRD-05 |

- **앞뒤 공백을 자르지 않는다.** 길이에는 공백이 포함된다. 공백뿐인 이름은 거절한다.
- **브랜드 설명은 255자 이하다.** 상한이 없으면 컬럼 길이(varchar 255)를 넘는 설명이 DB 오류(500)가 된다. 계약에 범위를 드러내고 다른 필드처럼 도메인에서 거절한다.
- **이름 중복을 허용한다.** 브랜드·상품은 식별자로 구분한다. 논리 삭제된 행과 이름이 겹치는 문제도 생기지 않는다(2.5).
  - **감수하는 비용:** 관리자가 같은 이름의 브랜드를 실수로 두 번 만들 수 있다.
- **가격 0원을 허용한다.** 증정품 같은 상품을 둘 수 있다. 0원 상품만 담은 주문은 합계 0원으로 확정된다(ORD-04 참고).
- **가격 상한을 1억 원으로 둔다.** 품목 수량 상한(999, ORD-02)과 함께 두면 품목 금액의 최대값이 정해져, 합계를 `long` 으로 계산할 때 넘칠 걱정이 없다.

#### 생성과 수정

- **상품 생성에서 재고를 받지 않는다.** 재고는 0으로 시작하고 재고 변경 API로만 바꾼다 (2.4).
- **숫자 필드는 누락되면 0으로 채우지 않고 400이다.** 요청 모델의 숫자 필드를 원시 타입으로 두고 공통 JSON 설정(`FAIL_ON_NULL_FOR_PRIMITIVES`)으로 거절한다. 가격이 빠진 요청이 0원 상품으로 만들어지지 않는다.
- **수정(PUT)은 전체 교체다.** 수정할 수 있는 필드를 모두 보내야 한다.
- **상품 수정 본문에 `brandId` 를 두지 않는다.** 보내도 무시된다. 브랜드는 바꿀 수 없다(PRD-03).
  - 응답에 기존 브랜드가 그대로 담겨 돌아가므로 클라이언트가 바뀌지 않았음을 확인할 수 있다.
- **재고 변경은 최종 수량을 설정한다.** 증감량이 아니다.

#### 삭제

| 상황 | 결과 |
|---|---|
| 삭제되지 않은 브랜드·상품 삭제 | 논리 삭제하고 성공 |
| **이미 삭제된 대상 삭제** | `BRAND_NOT_FOUND` · `PRODUCT_NOT_FOUND` 404 |
| 삭제되지 않은 상품(재고 0 포함)이 남은 브랜드 삭제 | `BRAND_HAS_PRODUCTS` 409 (BRD-02) |
| 삭제된 대상의 조회 · 수정 · 재고 변경 | 404 (BRD-01, PRD-02, PRD-04) |

- **이미 삭제된 대상은 404로 응답한다.** 조회 계약에서 삭제된 대상을 "없음"으로 다루므로 일관된다(6.2).
  - 좋아요 취소를 멱등 성공으로 둔 것과 다르다. 좋아요 취소는 **자기 관계**를 원하는 상태로 맞추는 것이고, 여기는 **대상 자체**를 다루는 것이다.

#### 응답 필드

| 대상 | 필드 |
|---|---|
| 브랜드 | 식별자, 이름, 설명, 생성 시각, 수정 시각 |
| 상품 | 식별자, 이름, 가격, **재고 수량**, 브랜드 식별자 · 이름, 생성 시각, 수정 시각 |
| 주문 목록 | 주문 식별자, 구매자 식별자, 상태, 합계, 결제액, 품목 개수, 대표 상품명, 주문 시각 |
| 주문 상세 | 주문 식별자, 구매자 식별자, 상태, 합계, 결제액, 결제 시각, 품목 전체 |

- **고객 응답과 다른 점:** 재고는 수량 그대로 내보낸다(고객은 품절 여부만). 생성·수정 시각과 구매자 식별자가 들어간다.
- **좋아요 수는 넣지 않는다.** 관리자 요건에 없고, 넣으면 고객 목록과 같은 집계를 관리자 조회에도 돌려야 한다.

#### 목록 조건

| 목록 | 필터 | 정렬 |
|---|---|---|
| 브랜드 | - | 생성 시각 desc, 식별자 desc |
| 상품 | `brandId` | 생성 시각 desc, 식별자 desc |
| 주문 | `userId`(구매자별), `status`(`DRAFT` · `CONFIRMED`) | 주문 시각 desc, 식별자 desc |

- 삭제된 브랜드·상품은 관리자 목록에서도 제외한다 (2.5).
- 관리자 주문 조회는 삭제된 상품이 포함된 주문도 그대로 보인다. 품목은 주문 시점 스냅샷이다 (2.3).
- 없는 `status` 값은 400으로 거절한다 (6.1).
- **관리자 필터에 없는 대상을 주면 404로 응답한다.** `brandId` 에 없거나 삭제된 브랜드는 `BRAND_NOT_FOUND`, `userId` 에 없는 사용자는 `USER_NOT_FOUND` 다.
  - **이유:** 고객 쪽 필터는 조회 조건이지만, 관리자 쪽 필터는 관리할 대상을 지정하는 것이다. 관리자는 대상이 존재하는지 알아도 되고, 잘못 넣은 식별자를 빈 목록으로 지나치지 않아야 한다.
  - **버린 대안:** 모든 필터를 빈 목록으로 둔다(규칙 하나로 설명되지만 관리자의 오타를 알아채기 어렵다). `userId` 만 404로 둔다(같은 관리자 화면에서 `brandId` 와 규칙이 달라진다).
  - **감수하는 비용:** 필터 규칙이 고객·관리자 두 개가 되고, 관리자 필터마다 존재 확인 조회가 한 번 더 나간다.

#### 접근 거절

- ADMIN이 아니거나 식별이 없는 요청은 403이다. 과제가 준 `AdminBoundaryConfig` 가 `response.sendError(403)` 으로 응답하므로 **이 응답만 `ApiResponse` 를 거치지 않는다.** 과제 지원 설정이므로 그대로 두고 차이를 적어 둔다.

#### 오류 코드

| 코드 | HTTP | 상황 |
|---|---|---|
| `INVALID_BRAND_NAME` | 400 | 브랜드 이름이 공백뿐이거나 20자 초과 |
| `INVALID_BRAND_DESCRIPTION` | 400 | 브랜드 설명이 255자 초과 |

## 7. 테스트 경계

테스트는 확인하려는 책임의 경계에 둔다. 모든 규칙을 HTTP부터 반복하면 실행 비용과 실패 원인을 찾는 비용이 커진다. **수량·금액의 경계값은 도메인 테스트에서 확인하고, HTTP 테스트에서 반복하지 않는다.**

### 7.1 경계별로 확인할 것

| 경계 | 방법 | 확인할 것 |
|---|---|---|
| **도메인 모델** | Spring · DB 없는 단위 테스트 | 각 객체가 자기 규칙을 지키는가. 거절 후 기존 값이 유지되는가 |
| **도메인 서비스** | fake 저장 구현을 연결한 테스트 | 여러 객체의 협력, 확인 순서, 요청자 구분 |
| **저장소 · DB** | 실제 DB 통합 테스트. JPA는 `flush()` · `clear()` 후 재조회 | 저장한 값과 관계가 다시 읽히는가. 조회 조건 · 집계 · 정렬 |
| **HTTP** | `@SpringBootTest` + MockMvc + 테스트 DB | 실제 API의 응답 · 오류 코드 · 저장 동작. 입력·접근 거절 시 기존 값 유지 |
| **구조** | `ArchitectureTest`, Checkstyle | 패키지 의존 방향(4.1), 정적 규칙 |

### 7.3 연결 흐름

5.1의 흐름을 HTTP로 이어서 확인한다 (`PointOrderFlowE2ETest`). 앞부분은 관리자 API로 브랜드 · 상품 · 재고를 준비해, "관리자 변경 → 고객 조회"도 같은 흐름에서 확인한다.

```
관리자: 브랜드 · 상품 2개 등록, 재고 설정 → 고객 상품 목록에 보이는가
고객:   잔액 0 → 10,000 충전 → 여러 품목 주문 생성(DRAFT, 차감 없음) → 확정
     → 잔액 조회 3,000 · 내 주문 목록 · 상세(CONFIRMED, 결제액 7,000)
     → 재고: 관리자는 수량(줄어든 값), 고객은 품절 여부
관리자: 구매자별 주문 조회에 CONFIRMED 주문이 보이는가
```

### 7.4 로컬 실행 확인

테스트와 별도로 `local` 프로필로 앱을 실행해 실제 HTTP로 확인했다.

- **준비:** `docker compose -f docker/infra-compose.yml up -d`. 앱이 뜨면 `LocalUserInitializer` 가 사용자 1, 2를 만든다(2.6). 관리자 API는 실제 HTTP로 항상 403이므로(6.5) 브랜드 · 상품은 SQL로 넣는다.
- **확인한 것:** 서버가 `127.0.0.1` 에만 열리는지, 식별 401, 충전 → 주문 생성 → 확정 → 잔액 3,000, 재확정 409, 타인 주문 404, 재고 부족 409와 `data.productId`, 소수 충전 400, 좋아요와 `likes_desc` 정렬, 관리자 API 403
- **수동 확인 순서:** `http/commerce-api/week2-flow.http` (IntelliJ HTTP Client, 위에서부터 순서대로 실행)
- **실행하며 발견한 것:** 같은 주문의 `orderedAt` 이 생성 응답(`+09:00`)과 확정 응답(`Z`)에서 다르게 표기됐다. 테스트는 시각이 비어 있지 않은지만 확인해 놓쳤다. 응답 시간대를 고정하고(D-40) 표기가 같은지 확인하는 테스트를 추가했다.

## 9. AI와 설계 다듬기

초안을 직접 작성한 뒤 AI(Claude)에게 검토를 요청했다. 제품 정책과 최종 선택은 사람이 하고, AI의 지적과 대안은 근거·반례를 확인한 뒤 받아들이거나 버렸다.

### 9.1 검토 질문

> 이 설계에서 책임이 겹치는 부분과 변경에 취약한 의존을 찾아줘. 대안 두 가지의 비용을 비교하고, 결정되지 않은 정책은 먼저 질문해줘.

초안을 다듬는 중에도 절마다 같은 관점(판단 기준의 일관성, 반례 대입)으로 검토를 받았다.

### 9.4 반례 대입: "브랜드 응답이 바뀌면 어떤 객체까지 바뀌는가?"

과제가 제시한 반례는 4.5에서 두 안(Product가 조합 / 조회 결과 타입과 `~Info` 가 조합)에 대입했다. Product는 상품 규칙이 바뀔 때만 바뀌는 쪽을 골랐다(D-15).
