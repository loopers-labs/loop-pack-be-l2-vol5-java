## 3.도메인 관계
| 관계                          | 다중성   | 연결 방식                                              | 필요한 이유                                                                                | 책임 주체                                                                          |
|-----------------------------|-------|----------------------------------------------------|---------------------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| Brand - Product             | 1:N   | 직접(Product가 brandId보유)                             | 브랜드 삭제 시 연결 상품 존재 확인                                                                  | Product                                                                        |
| User - Like - Product       | 1:N:1 | 간접(좋아요 테이블에 User와 Product가 각각 존재)                  | 유저당 상품에 좋아요를 1번만 누를 수 있기 때문(중복방지)                                                     | Like(동일 User-Product 조합 저장을 막는 규칙을 Like 저장 시점에 검증)                             |
| Order - OrderItem - Product | 1:N:1 | 간접                                                 | 한 주문에 여러 상품을 가질 수 있어야함(Order-OrderItem), 주문 시점의 금액과 수량을 독립적으로 기록해야함(OrderItem-Product) | OrderItem(주문할 때 상품의 수량,단가 결정), Product(재고 수량 체크),Order(여러 OrderItem을 묶어 상태 관리) 
| User - Point                | 1:1   | 직접 (Point가 userId 보유)                              | 유저가 취급하는 포인트는 하나이기 때문, 충전이나 차감 시 유효성(0원 이상, 오버플로우 방지)을 지켜야 함                          | Point(포인트 충전과 차감)                                                              
| User - Order | 1:N | 직접 (Order가 userId 보유) | 유저가 여러 건의 주문을 만들 수 있음, 본인 주문만 조회·확정 가능해야 함 | Order(자신의 상태·금액 규칙 관리) + application(본인 소유 여부 검증, 요청자-userId 일치 확인) |


## 4.API 계약 (입력/성공/오류) - method/path/입력/성공/대표 오류와 주요 규칙의 기대값
### 4-1.고객

| Method/Path | 입력 | 성공 결과 | 대표 오류 | 주요 규칙 기대값 |
|---|---|---|---|---|
| GET /api/v1/brands/{brandId} | brandId(path) | 200, 브랜드 상세 | 없거나 삭제된 브랜드 → 404 | 삭제된 브랜드는 조회 불가 |
| GET /api/v1/products | brandId(query, optional), sort(latest/price_asc/likes_desc), page | 200, 상품 목록(브랜드정보+좋아요수 포함) | 잘못된 정렬값 → 400 | 동률 시 id 내림차순으로 순서 고정, 삭제된 상품은 목록 제외 |
| GET /api/v1/products/{productId} | productId(path) | 200, 상품 상세(브랜드정보+좋아요수 포함) | 없거나 삭제된 상품 → 404 | - |

#### 4-2.관리자

| Method/Path | 입력 | 성공 결과 | 대표 오류 | 주요 규칙 기대값 |
|---|---|---|---|---|
| GET /api-admin/v1/brands | page(query) | 200, 브랜드 목록 | 권한 없음 → 403 | 관리자만 접근 가능, 삭제된 브랜드도 포함(삭제 관리가 관리자 역할), 최신순(id 내림차순) |
| POST /api-admin/v1/brands | name 등 브랜드 정보 | 201, 등록된 브랜드 | 정보 유효성 실패 → 400, 권한 없음 → 403 | 이름 필수(공백 불가), 100자 이내 |

| DELETE /api-admin/v1/brands/{brandId} | brandId(path) | 204 | 삭제되지 않은 연결 상품 존재(재고0 포함) → 409, 없거나 이미 삭제됨 → 404 | 연결 상품이 하나라도 남아있으면 거절, 논리 삭제 |
| GET /api-admin/v1/products | brandId(query, optional), page | 200, 상품 목록 | 권한 없음 → 403 | 삭제된 상품도 포함, 최신순(id 내림차순) |
| POST /api-admin/v1/products | brandId, name, price 등 | 201, 등록된 상품 | 브랜드 없음/삭제됨 → 404, 이름·가격 범위 실패 → 400 | 브랜드 존재·미삭제 확인 |
| GET /api-admin/v1/products/{productId} | productId(path) | 200, 상품 상세 | 없음 → 404 | - |
| PUT /api-admin/v1/products/{productId} | productId(path), name, price | 200, 수정된 상품 | 없거나 삭제됨 → 404, 유효성 실패 → 400 | 이름·가격만 수정, 브랜드는 고정(변경 불가), 재고는 별도 API |
| DELETE /api-admin/v1/products/{productId} | productId(path) | 204 | 없거나 이미 삭제됨 → 404 | 논리 삭제, 삭제 후 고객 조회·새 주문·새 좋아요에서 제외 |
| PUT /api-admin/v1/products/{productId}/stock | productId(path), quantity | 200, 변경된 재고 | 음수 → 400, 없거나 삭제됨 → 404 | 0 이상인 최종 수량으로 설정(증감이 아니라 절대값) |

## 5.대표 흐름
### 5-1. 관리자 변경 → 고객 조회
* 근거 문장 "관리자 변경을 고객 조회에 반영하고, 고객·관리자에게 제공할 응답 필드를 구분합니다."

#### 5-1-1. 상품 가격 수정
* 관리자가 상품 가격을 4,000원 → 5,000원으로 수정 요청
→ PUT /api-admin/v1/products/{productId}
→ 관리자 권한 확인 → 가격 유효성 검증 → Product.changePrice(5000) 호출
→ 저장됨

* 고객이 이 상품을 상세 조회
→ GET /api/v1/products/{productId}
→ Product 조회 → 응답에 가격 5,000원이 반영되어 보임

#### 5-1-2. 상품 삭제
* 관리자가 상품을 삭제 요청
→ DELETE /api-admin/v1/products/{productId}
→ 관리자 권한 확인
→ 삭제 처리 

* 고객이 상품 목록을 조회
→ GET /api/v1/products
→ 삭제된 상품은 목록에서 제외되어 응답
→ 새 좋아요 등록 불가  (기존 좋아요는 취소 가능)
→ 새 주문에서 제외

#### 5-1-3. 재고 변경
* 관리자가 재고를 0으로 변경
→ PUT /api-admin/v1/products/{productId}/stock
→ 관리자 권한 확인 → 0 이상인지 검증 → 최종 수량으로 설정

* 고객이 상품 상세 조회 → 재고 0인 상태로 보임

#### 5-1-4. 상품 등록
* 관리자가 새 상품을 등록
→ POST /api-admin/v1/products
→ 관리자 권한 확인
→ 브랜드 존재/미삭제 확인 → 이름·가격 유효성 검증 → 저장

* 고객이 상품 목록을 조회
→ GET /api/v1/products
→ 방금 등록된 상품이 목록에 나타남

### 5-2. 좋아요 등록 · 취소
#### 5-2-1. 고객이 상품 좋아요를 등록
→ POST /api/v1/products/{productId}/likes
→ 삭제된 상품인지 확인
→ 사용자-상품관계 유니크 체크 (상품이 없거나(404) 좋아요가 이미 등록되어있는 경우(401) 거절)
→ 좋아요가 등록됨

#### 5-2-2. 고객이 상품 좋아요를 취소
→ DELETE /api/v1/products/{productId}/likes
→ 사용자 식별 누락/존재하지 않는 상품(401) 요청 거절
→ 본인의 좋아요만 취소 가능(404)
→ 좋아요가 취소됨

### 5-3. 포인트 충전 → 주문 확정
#### 5-3-1. 고객이 포인트를 충전한다.
→ POST /api/v1/points/charge
→ 누락, 잘못된 타입, 표현 범위 초과를 거절
→ 오류 입력 시 기존 잔액 유지
→ 검증 통과 시: 포인트가 충전됨

#### 5-3-2. 고객이 주문을 생성한다.
→ POST /api/v1/orders
→ 상품이 존재하며 삭제되지 않았는지, 수량이 양수인지 확인
→ 생성 시점에는 재고 차감이 없음 (DRAFT 상태로 저장)

#### 5-3-3. 고객이 주문을 확정한다.
→ POST /api/v1/orders/{orderId}/confirm
→ 본인의 주문만 확정 가능
→ 상품 재고 확인 → 부족하면 거절 (DRAFT 유지, 아무것도 차감 안 됨)
→ 재고 충분하면 차감 → 포인트 잔액 확인 → 부족하면 거절
→ 여러 품목 주문시 중복 상품은 합산하거나 거절됨 (총수량 기준 재고 확인)
→ 재고가 차감됨
→ 포인트가 차감됨
→ 주문이 확정됨(CONFIRMED), 결제액 저장

## 6. AI와 설계 다듬기
AI와 설계 다듬기

### 6-1. OrderItem 필요 근거 검증
- 질문: "요구사항에 가격이 바뀐다는 얘기는 없었잖아. 바뀔 수도 있다는 건
  너의 생각 아니야?"
- 검토: AI가 "가격이 나중에 바뀔 수 있어서 unitPrice가 필요하다"고 설명했으나,
  이는 과제 원문에 없는 일반론적 추론이었음을 확인
- 결론: unitPrice 저장 근거를 과제 원문에 명시된 "여러 품목·수량·단가·합계를
  저장한다"는 요구사항 자체로 재정리. AI의 일반론과 실제 요구사항을 구분함.

### 6-2. 관리자 변경→고객 조회 흐름의 범위 판단
- 질문: (브랜드 수정/삭제/등록도 고객에게 반영되는지 설명을 들은 뒤)
  "그렇다면 굳이 안 적어도 되는 거 아니야?"
- 검토: 이미 상품 CRUD(가격수정/삭제/재고변경/등록) 4개 예시로
  "관리자 변경→고객 조회" 패턴을 충분히 보여줬다고 판단
- 결론: 브랜드 관련 흐름은 추가하지 않고 상품 4개 예시로 충분하다고 결정.
  같은 패턴의 반복 추가는 비용 대비 효용이 낮다고 판단.

### 6-3. User-Product 사이의 연결 경로 재검토
- 질문: "유저와 프로덕트 사이에는 주문도 낄 수 있지 않아?"
- 검토: Like(User-Product 직접 매개, 1:1 단순 관계)와
  Order-OrderItem-Product(2단계 매개, 여러 품목을 묶는 복합 관계)가
  서로 다른 목적과 다중성을 가진 별개의 연결임을 확인
- 결론: 두 관계를 도메인 관계 표에 각각 별도 행으로 분리해서 기록

### 6-4. 이벤트스토밍 커맨드/이벤트 색상 구분 오류 반복 검증
- 질문: (여러 이벤트스토밍 이미지를 제시하며) "이렇게 가면 되나?",
  "화살표는 아래로 향해야 되는거야?" 등
- 검토: 포인트/주문/좋아요/상품/브랜드 다이어그램 전반에서
  "~한다"(명령형) 문장이 주황(이벤트) 색으로 잘못 표시된 경우가
  반복적으로 발견됨
- 결론: 커맨드(파랑, 명령형)와 이벤트(주황, 과거형)를 색과 문장 형태
  기준으로 재분리. 조회 결과는 이벤트가 아니라 읽기모델(초록)로 정정.

### 6-5. 소유권 위반 응답을 403에서 404로 정정
- 질문: "고객 식별 수단(1주차 로컬 실습용)을 먼저 확인해줘"
- 검토: 1주차 문서 7.2가 소유권 위반을 404로 정하고 403을 명시적으로 거부했음을 확인
  ("403은 그 주문은 있는데 네 것이 아니다를 알려준다"). 그런데 2주차 초안은
  좋아요 목록·주문 확정·주문 상세에서 403을 쓰고 있어 두 문서가 충돌했음
- 결론: 존재 노출 방지 논거가 더 우선한다고 보고 2주차를 1주차에 맞춰 404로 통일.
  단, `/api-admin/**`의 "권한 없음 → 403"은 그대로 둔다. 이쪽은 소유권이 아니라
  Spring Security가 지키는 역할 경계이고, 관리자 API의 존재 자체는 비밀이 아니다.
  `ErrorType`에는 401(UNAUTHORIZED)만 추가하고 FORBIDDEN은 추가하지 않는다.

- 결론: 브랜드 관련 조건을 상품 관련 조건으로 정정, 확정 실패 시

### 6-7: User의 성격 재확인
이벤트스토밍 단계에서도 User는 "좋아요를 등록한다", "포인트를
충전한다" 등 다른 도메인의 커맨드를 발생시키는 액터로만
등장했고, User 자신의 상태가 변하는 이벤트는 없었음.
이는 User가 재고·가격 같은 자체 도메인 규칙을 갖지 않는다는
판단과 일치하며, 코드에서도 존재 확인용 최소 구조
(Entity + Repository만, 불필요한 Service 계층 제외)로
구현하는 근거가 됨.

### 6-8: 상품 목록의 보조 정렬 기준을 id 내림차순으로 확정
- 질문: "동률일 때 보조 정렬 기준을 어떻게 정했는지, 임의로 정한 거라면
  근거를 남겨달라"
- 검토: 4-1 계약에 "동률 시 id 등"이라고만 적혀 있어 정렬 방향(오름/내림)이
  정해지지 않은 상태였음. 구현에서는 방향을 반드시 골라야 함
- 결론: id 내림차순으로 확정. 근거 두 가지.
    1. latest 정렬과 방향이 일치한다. 최신순은 나중에 등록된 상품이 앞이고
       나중에 등록될수록 id가 크므로, 동률일 때도 최신이 앞에 오는 편이 일관됨
    2. latest 정렬 자체를 결정적으로 만든다. createdAt 이 같은 시각에 기록되면
       1차 정렬만으로는 순서가 정해지지 않는데, id 내림차순이 tie-breaker 로
       작동해 조회 결과가 항상 같은 순서를 보장함
- 영향: price_asc / likes_desc / latest 세 정렬 모두 2차 기준으로 id DESC 를
  적용한다. 페이지 경계에서 항목이 중복·누락되지 않는 것도 이 덕분이다.

### 6-9: 고객 API 경로의 CSRF 보호 해제
- 질문: 좋아요 등록 E2E 가 전부 403 으로 실패하는 원인 확인 요청
- 검토: 관리자 경계 설정에서 CSRF 를 끄지 않아 기본값(활성)이 적용되고 있었음.
  고객 API 가 그동안 조회(GET)뿐이어서 드러나지 않다가, 좋아요 등록·취소라는
  첫 상태 변경 요청에서 문제가 발생
- 결론: /api/** 경로만 CSRF 보호를 해제. 고객 API 는 X-USER-ID 헤더로 식별하는
  stateless 경로라 쿠키를 노린 CSRF 의 대상이 아니기 때문. 쿠키 인증을 쓰는
  관리자 경로(/api-admin/**)의 CSRF 는 그대로 유지한다.

### 6-10: 주문의 미확정 정책 3건 확정
- 질문: 주문 구현 전, 계약에 정해지지 않은 항목 확인 요청
- 검토 및 결론:
    1. 중복 상품 처리 — 계약 표에 "합산 또는 거절(정책 결정 필요)"로 남아 있었음.
       수량 합산으로 확정한다. 합산된 총수량을 기준으로 재고를 확인한다.
       OrderFacadeTest 스켈레톤이 이미 합산을 전제로 작성되어 있어 코드 변경은 없고
       문구만 갱신한다.
    2. 결제액 계산 기준 — 생성 시점 단가로 확정한다. 과제 원문이 OrderItem 에
       "상품 식별자·수량·단가"를 저장하도록 하고, 3장이 Order-OrderItem 의 필요
       이유를 "주문 시점의 금액과 수량을 독립적으로 기록"으로 설명한 것이 곧
       단가 스냅샷을 전제한 서술이었음. 확정 시점 가격을 쓰면 DRAFT 로 담아둔
       사이 관리자가 가격을 바꿨을 때 결제액이 달라지는 문제가 생긴다.
       확정 시점에 재고·포인트는 다시 확인하지만 가격은 재계산하지 않는다.
    3. 주문 상태 — DRAFT / CONFIRMED 두 가지만 둔다. 과제 원문이 명시한 상태가
       이 둘뿐이고 취소·실패 상태는 요구되지 않았다. 확정 실패(재고·포인트 부족)
       시에는 예외만 던지고 상태를 바꾸지 않아 DRAFT 로 남는다.

### 6-11: 관리자 CRUD 의 수정 범위와 삭제 방식 확정
- 질문: 관리자 브랜드/상품 CRUD 와 삭제 경계 구현 요청. 계약에 "수정할 정보"
  라고만 적혀 있어 수정 대상과 삭제 방식이 정해지지 않은 상태였음
- 검토 및 결론:
    1. 브랜드 수정 범위 — 이름만 수정한다. Brand 가 name 외의 속성을 갖지 않기
       때문이다. 100자·공백 검증이 생성자와 중복되지 않도록 검증을 private
       메서드로 빼고 생성자와 changeName 이 함께 재사용한다.
    2. 상품 수정 범위 — 이름과 가격만 수정한다. 브랜드는 고정(변경 불가)이고,
       재고는 PUT .../stock 으로 이미 분리되어 있으므로 제외한다.
    3. 삭제 방식 — 논리 삭제(soft delete)를 택한다. 물리 삭제를 하면 이미 저장된
       주문의 OrderItem 이 가리키는 상품이 사라져 과거 주문 내역을 복원할 수 없고,
       Like 관계도 함께 끊어진다. BaseEntity 가 이미 deletedAt 과 delete() 를
       제공하므로 이를 그대로 쓴다. 주문은 생성 시점 단가를 스냅샷으로 들고 있어
       상품이 삭제되어도 금액 정보는 온전히 남는다(6-10 참조).
    4. 브랜드 삭제 거절 조건 — 삭제되지 않은 연결 상품이 하나라도 있으면 409 로
       거절한다. 재고가 0인 상품도 "삭제되지 않은 상품"이므로 거절 대상에 포함한다.
       재고 0은 품절 상태일 뿐 상품이 사라진 것이 아니기 때문이다.
    5. 삭제된 대상의 취급 — 고객 조회·새 주문·새 좋아요에서 제외하고, 수정·재고
       변경의 대상으로도 사용하지 않는다(모두 404). 다만 관리자 목록 조회에는
       포함한다. 무엇이 삭제되었는지 확인하는 것 자체가 관리자의 역할이기 때문이다.
    6. 중복 삭제 — 이미 삭제된 대상을 다시 삭제하면 404 로 응답한다. 기존
       findActiveBrand / getActiveProduct 가 삭제분을 404 로 다루는 것과 맞춘다.

### 6-12: 관리자 주문 조회의 정렬과 필터 확정
- 질문: 4-6 계약이 "page(query)"와 "전체 주문 목록(구매자별)"이라고만 적고 있어
  정렬 기준과 필터 대상이 정해지지 않은 상태였음
- 검토 및 결론:
    1. 정렬 — 생성일 내림차순(최신순)을 기본으로 한다. 관리자 업무는 "방금 들어온
       주문부터 확인"하는 흐름이 자연스럽고, 고객 상품 목록의 latest 정렬과도
       관례가 일치한다. 구현도 createdAt DESC 하나로 끝난다.
    2. 필터 — "구매자별"이라는 표현을 userId 필터로 해석한다. 관리자가 특정
       구매자의 주문만 골라 볼 수 있어야 한다는 뜻으로 읽었다. userId 를 주지
       않으면 전체 주문을 조회한다.
    3. 상세 조회의 소유권 — 고객 API 는 남의 주문을 404 로 감추지만(6-5),
       관리자 API 는 소유권을 검증하지 않는다. /api-admin/** 의 ROLE_ADMIN 검사가
       이미 접근 경계이고, 모든 구매자의 주문을 보는 것이 이 API 의 목적이다.
    4. 삭제 항목 — 주문에는 삭제 기능이 없으므로 브랜드·상품과 달리 삭제 포함
       여부를 다룰 필요가 없다.
