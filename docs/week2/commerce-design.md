# 커머스 기본 기능 — 설계 문서 (W2)

> 고객·관리자의 요청을 **HTTP → application → domain → repository·DB → 응답**까지 연결하기 위한 설계.
> 구현하며 바뀐 판단은 이 문서에 반영하고, 바뀐 이력과 AI와 설계를 다듬은 기록은 [`design-log.md`](design-log.md)에 남긴다.

- 출처: `docs/note/week2/실습 과제.md`(설계 항목, 기본 기능 구현 조건), `docs/note/week2/발제.md`(버드뷰·구조·도메인 관계 예시)
- 범위: **3. 기본 기능 구현**의 기능과 조건만 다룬다. 사용자 식별·관리자 접근 제한은 `실습 과제.md` 4절이 정한 방식을 따르고, 그 결과로 생기는 요청 계약만 7-0에 적는다. lint·ArchUnit은 이 문서의 설계 대상이 아니다. 동시 요청(같은 주문 동시 확정, 같은 재고·잔액 동시 차감 등)으로 생기는 문제는 이번 설계에서 다루지 않는다.
- 작성 표기: `✏️` 는 직접 채울 칸. 채운 뒤 표기를 지운다.

## 설계 개괄

### 1. 버드뷰

```
고객  ── 상품·브랜드 조회 / 좋아요 / 포인트 / 주문 ─┐
                                           ├─ commerce-api ─→ DB
관리자 ── 브랜드·상품 CRUD / 재고 변경 / 주문 조회 ─┘
```

고객과 관리자는 같은 상품·브랜드를 다루지만 계약이 다르다(고객은 조회, 관리자는 변경). 두 요청은 같은 `commerce-api` 서버 안에서 경로로 구분된다(`/api/v1/**` 고객, `/api-admin/v1/**` 관리자). `User` 엔티티는 고객만 표현한다. 관리자는 엔티티로 저장하지 않고, 관리자 경로를 막는 접근 제한 단계에서 권한으로만 구분한다(P-9). 접근 제한은 4절 지원 설정(`config.AdminBoundaryConfig`: `/api-admin/**`에 `ROLE_ADMIN` 요구, 그 외 403)을 그대로 쓴다.

### 2. 구조와 의존

#### 2-1. 계층 역할

| 계층 | 역할 | 두지 않는 것 |
|---|---|---|
| `interfaces` | 고객·관리자 입력과 응답, HTTP 오류 매핑 | infrastructure 저장 구현 |
| `application` | domain의 행동·저장 약속을 이용한 유스케이스 | controller DTO, infrastructure 구현 |
| `domain` | 상태·규칙, 필요한 repository 약속 | interfaces, application, infrastructure |
| `infrastructure` | repository 약속의 JPA 구현 | HTTP 응답 정책과 중복된 업무 규칙 |


#### 2-2. 허용 의존 방향

```
interfaces/api/{도메인}       → application/{도메인} → domain/{도메인}
interfaces/api/admin/{도메인} → application/{도메인}
infrastructure/{도메인}       ─────────────────────→ domain/{도메인}
```

관리자 전용 `interfaces`가 있어도 `application`/`domain`/`infrastructure`는 고객용과 같은 패키지를 그대로 쓴다(2-3 참고). 
`domain`은 어떤 계층에도 의존하지 않는다.

#### 2-3. 패키지 배치

- 고객용 / 관리자용 코드의 배치: 관리자는 `interfaces.api.admin.{도메인}`만 별도로 두고, `application`·`domain`·`infrastructure`는 고객용과 공유한다(발제.md: "interfaces/api/admin/... → application/..."). 같은 저장된 상품이라도 고객·관리자가 서로 다른 입력·출력 모델을 가질 수 있다는 것은 application/interfaces에서 갈린다는 뜻이다.
- 도메인 패키지 목록: `brand`, `product`, `like`, `user`, `order` — 포인트는 `User`의 잔액이므로 `domain/user`에 둔다. 포인트 API(`/api/v1/points`)의 컨트롤러는 `interfaces/api/point`, 유스케이스는 `application/point`에 두고 `domain/user`를 사용한다.

### 3. 도메인 관계

#### 3-1. 관계도

```
Brand 1 ── N Product
User  1 ── N Like N ── 1 Product
User  1 ── N Order 1 ── N OrderItem ── 상품 식별자·수량·단가
User  1 ── 포인트 잔액
Order ── 품목 금액 합계 / 포인트 결제액·결제 결과
```

(객체 참조로 구현할지 식별자만 보관할지는 조회·변경에 필요한 정보를 보고 정한다 — 3-2 참고)

#### 3-2. 관계별 결정

| 관계 | 카디널리티 | 참조 방식 (객체 참조 / ID 참조) | 이유 |
|---|---|---|---|
| Brand – Product | 1 : N | ID 참조 — `Product`가 `brandId`를 가진다 | 상품의 규칙(이름·가격·재고)은 브랜드 객체 없이 지킬 수 있다. 브랜드 정보 조합은 조회 시점에 application이 한다(결정 2). 브랜드를 객체로 참조하면 브랜드 응답 변경이 상품 모델까지 번진다 |
| User – Like – Product | Like를 통한 N : M | ID 참조 — `Like`가 `userId`·`productId`를 가진다. (`userId`, `productId`) 유일 | 좋아요는 관계 자체가 데이터다(LIK-001). 좋아요 수는 이 관계를 `productId`로 세어 얻는다(LIK-002) |
| User – 포인트 잔액 | — | 별도 엔티티 없이 `User`의 잔액 필드 | 사용자마다 잔액은 하나이고, 사용자가 만들어질 때 0원으로 함께 생긴다(P-5). 별도 엔티티로 두면 "잔액 행이 언제 생기는가"를 따로 관리해야 한다. `User`는 고객만 표현하며 권한 필드를 두지 않는다(P-9, T-6) |
| Order – OrderItem | 1 : N | 객체 참조 — `Order`가 `OrderItem` 목록을 가진다 | 품목은 주문과 함께 만들어지고 확정된다. 합계 계산·상태 전이가 품목과 한 단위로 움직인다 |
| OrderItem – Product | N : 1 | ID 참조(상품 식별자) + 단가·수량은 OrderItem에 저장 | 발제.md가 "OrderItem ── 상품 식별자·수량·단가"라고 명시. T-2(확정 시점 가격)에 따라 확정 시 단가·합계를 현재 가격으로 다시 저장한다 |

`Order`와 `OrderItem`을 제외한 관계는 모두 ID 참조다. 한 요청 안에서 여러 모델이 필요하면 application이 각 repository에서 조회해 조합한다.

#### 3-3. 책임 배치

별도 값 객체(VO)나 도메인 서비스를 처음부터 만들지 않는다. **상태를 가진 엔티티가 자기 규칙을 지키고, 여러 모델이 필요한 순서는 application이 조율**하는 단순한 구조에서 시작한다.

| 책임 | 맡는 객체 | 이유 |
|---|---|---|
| 재고 차감·부족 거절 | `Product` (재고 필드 + 차감 행동) | 재고는 상품의 상태다. 차감 조건(양수 수량, 보유량 이하)을 상품의 행동 안에 두면 주문 확정과 관리자 재고 변경이 검사를 반복하지 않는다 |
| 관리자 재고 변경 (0 이상) | `Product` (재고 설정 행동) | 재고 차감과 같은 상태를 바꾸므로 같은 객체에 둔다(STK-002) |
| 포인트 충전·결제·잔액 부족 거절 | `User` (잔액 필드 + 충전·차감 행동) | 충전의 양수 조건과 잔액 이상 차감 불가는 잔액을 가진 객체가 지킨다(PNT-001~003) |
| 주문 상태 전이 (DRAFT → CONFIRMED) | `Order` (확정 행동) | DRAFT가 아니면 확정할 수 없다는 규칙은 상태를 가진 주문이 판단한다(ORD-003) |
| 주문 합계·결제액 계산 | `Order` | 품목의 수량·단가로 합계를 구하고, 확정 시 결제액(=합계, T-1)을 기록한다 |
| 확정 시 재고·포인트·주문의 협력 | application (`OrderFacade`) | 상품·사용자·주문을 조회해 각 객체의 행동을 순서대로 호출한다. 상품이 포인트를 바꾸거나 주문이 repository를 알지 않는다 |
| 좋아요 중복 방지 | `LikeService`가 기존 관계를 확인 + DB 유일 제약 | 이미 있으면 저장 없이 성공(P-7 멱등). 동시 요청은 (`userId`, `productId`) 유일 제약이 마지막으로 막는다 |
| 좋아요 수 조회 | `Like` repository의 `productId` 기준 개수 조회 | 좋아요 수는 관계에서 조회한다(LIK-002). 상품에 개수 필드를 따로 두지 않는다 |
| 브랜드 삭제 가능 여부 판단 | application(`AdminBrandFacade`)이 연결된 미삭제 상품 존재를 먼저 확인(있으면 상태 충돌) → 없으면 브랜드를 조회(없거나 삭제됨이면 대상 없음)해 `Brand`가 삭제 상태로 바뀐다. 두 단계는 한 트랜잭션 | 발제.md: "관계를 확인하는 일과 데이터를 바꾸는 행동을 구분". 브랜드는 상품 목록을 모르므로 확인은 application이, 삭제 상태 변경은 브랜드가 맡는다(DEL-001). 브랜드 존재는 삭제 단계에서 한 번만 조회한다. 미삭제 상품은 삭제되지 않은 브랜드에만 연결되므로(PRD-001, DEL-001), 상품 확인을 먼저 해도 없거나 삭제된 브랜드가 상태 충돌로 응답받지 않는다 |
| 상품 조회 결과 조합 (브랜드 정보·좋아요 수) | [결정 2](#결정-2-상품-규칙과-조회-조합의-위치) 참고 | |

**별도 객체를 도입할 조건** — 아래 상황이 생기면 그때 분리한다.

| 대상 | 도입 조건 |
|---|---|
| 재고·금액 값 객체 (예: 발제.md의 `Stock`, `Money`) | 같은 검증이 여러 엔티티에 반복되거나, 엔티티의 규칙이 커져 한 객체에서 읽기 어려워질 때 |
| 도메인 서비스 | 한 엔티티에 속하지 않는 업무 규칙이 생길 때(예: 여러 상품·쿠폰에 걸친 할인 계산 — T-1 되돌릴 조건과 연결) |

### 4. 대표 흐름

- 선택한 흐름: **포인트 충전 → 주문 확정**

```
[충전] POST /api/v1/points/charge
  Controller → PointFacade → User 조회 → User 잔액 충전(amount) → 저장

[확정] POST /api/v1/orders/{orderId}/confirm
  Controller → OrderFacade (트랜잭션 시작 — 결정 3)
    → User 조회 (없는 사용자 거절)
    → Order 조회 (본인 소유 확인 — ORD-003, 다른 사용자 주문은 없는 주문과 같은 404)
    → 품목의 삭제되지 않은 Product 일괄 조회
    → Order.confirm(확정 시점 가격)
        DRAFT 확인 (ORD-003) → 모든 품목의 가격 확인, 없으면(삭제된 상품) 거절 (ORD-002)
        → 품목 단가·합계 갱신 (T-2) → 결제액 = 합계 기록, CONFIRMED (ORD-005, T-1)
    → 품목별 Product 재고 차감 (합산된 총수량 — ORD-004, STK-001, T-3)
    → User 잔액 차감 (결제액만큼 — ORD-004)
    → 커밋 (변경 감지로 저장). 중간에 거절되면 전부 롤백
```

- 트랜잭션 경계: 확정 유스케이스 전체(재고 차감 + 포인트 차감 + 주문 상태 변경)를 하나의 트랜잭션으로 묶는다. 여러 도메인을 조율하는 `OrderFacade`에 경계를 둔다 — [결정 3](#결정-3-주문-확정의-트랜잭션-위치) 참고.
- 실패 시 되돌려야 하는 상태: 재고·잔액 부족 등으로 확정이 거절되면 재고·포인트·주문 상태는 모두 시도 이전 값으로 남아야 한다(트랜잭션 롤백, 부분 차감 금지).

## 요구사항과 계약

### 5. 요구사항

`실습 과제.md` 3절의 요구를 세 가지로 나눈다.

#### 5-1. 확정된 사실

| 영역 | 확정된 사실 | 관련 규칙 |
|---|---|---|
| 고객 기능 | 브랜드 상세, 상품 목록·상세, 좋아요 등록·취소·내 목록, 포인트 충전·잔액 조회, 주문 생성·확정·내 목록·상세 | 7-1, 7-2 |
| 관리자 기능 | 브랜드·상품 전체 CRUD, 상품 재고 변경, 주문 목록·상세 | 7-3 |
| 사용자 | 실습용 사용자는 fixture로 준비할 수 있다. 사용자 생성 API는 기능 목록에 없다 | |
| 상품 목록 | 브랜드 필터·페이지 조회, `latest`·`price_asc`·`likes_desc` 정렬, 브랜드 정보·좋아요 수 포함 | LIK-002 |
| 좋아요 | 사용자–상품 관계로 저장하고 중복 관계를 막는다. 좋아요 수는 관계에서 조회한다 | LIK-001~004 |
| 포인트 | 1포인트는 1원. 충전액은 양의 정수, 잔액 0원 허용, 입력 오류 시 기존 값 유지 | PNT-001~003 |
| 주문 상태 | DRAFT는 확정 전, CONFIRMED는 결제를 마친 상태. 생성 시 차감 없음, 확정 시 재고·포인트 차감 | ORD-001~005 |
| 삭제 | 삭제되지 않은 상품이 연결된 브랜드는 삭제 거절. 삭제된 브랜드·상품은 고객 조회·새 주문·수정·재고 변경에서 제외 | DEL-001~003 |
| 조회 반영 | 관리자 변경을 고객 조회에 반영하고, 고객·관리자 응답 필드를 구분한다 | QRY-002 |

#### 5-2. 임시 판단

원문에 근거는 없지만 설계를 진행하기 위해 일단 둔 판단이다. 정책으로 굳히지 않고, 틀렸을 때 바뀌는 범위를 남긴다.

| ID | 임시 판단 | 원문에 근거가 없는 부분 | 틀리면 바뀌는 것 | 되돌릴 조건 |
|---|---|---|---|---|
| T-1 | 결제액은 주문 합계와 같은 값이다. 추후 할인 쿠폰 등 결제액을 바꾸는 정책이 적용될 가능성을 고려했다 | 확정 시 결제액을 저장하라고만 하고 계산식은 없다 | ORD-005, 3-3 "주문 합계·결제액 계산", 7-2 확정·조회 응답 | 할인 쿠폰 등 결제액을 바꾸는 정책이 추가될 때 |
| T-2 | 확정 시점의 상품 가격을 기준으로 한다 | 생성 시 단가·합계를 DRAFT로 저장하지만, 그 뒤 상품 가격이 바뀌면 어느 가격을 쓸지는 없다 | ORD-004(잔액 부족 판단 금액), ORD-005, 3-2 OrderItem–Product 참조 방식 | 생성 시점 가격을 보장해야 한다는 요구(가격 변동 중 주문한 고객 보호 등)가 생기면 |

### 7. API 계약

#### 7-0. 공통 약속

- **요청자 구분**: 좋아요·포인트·주문 API는 "본인·자신"의 데이터만 다룬다(원문 3절). 요청자는 로컬 실습용 식별 헤더 `X-USER-ID`(사용자 ID)로 구분하고, 아래 표에서는 "요청자"로 표기한다. 모든 고객 요청 API는 공통으로 **헤더 누락 → 400**, **없는 사용자 → 404**로 거절하며, 이 두 오류는 7-1·7-2 표의 대표 오류에 반복해 적지 않는다(실습 과제 4절).
- **응답 형식**: 기존 `ApiResponse`를 그대로 쓴다. 성공은 `meta.result = SUCCESS`와 `data`, 실패는 `meta.result = FAIL`, `meta.errorCode`, `meta.message`, `data = null`.
- **성공 상태**: 등록·수정·삭제를 포함해 모두 `200`으로 응답한다. 삭제처럼 돌려줄 값이 없으면 `data = null`.
- **오류 표현**: 1주차 결정 1(`docs/week1/order-discount-contract.md`)을 잇는다. 도메인·application은 HTTP를 모르는 `DomainException`(종류: `INVALID_VALUE`·`NOT_FOUND`·`CONFLICT`)을 던지고, `ApiControllerAdvice`가 이를 기존 `ErrorType`의 `BAD_REQUEST`·`NOT_FOUND`·`CONFLICT`로 바꿔 응답한다([결정 4](#결정-4-도메인-실패-표현)). 같은 분류 안의 원인 차이는 `meta.message`로 전달한다. 새 `ErrorType`은 추가하지 않는다.
- **고객·관리자 응답 필드 구분**(QRY-002): 고객 응답에는 판매에 필요한 값만 둔다. 재고 수량과 등록·수정 시각은 관리자 응답에만 둔다.
- **입력 검증 위치**: 누락·타입 오류는 요청 변환 단계(`ApiControllerAdvice`가 이미 `400`으로 변환)에서, 값의 범위·업무 조건은 도메인 모델에서 거절한다(6절 PNT-001).

| 오류 분류 (6절) | 상황 | HTTP | `ErrorType` |
|---|---|---|---|
| 입력 오류 | 필수 값 누락(요청자 식별 헤더 포함), 타입 오류, 수량·충전액 0 이하, 이름·가격·재고 범위 밖, 잘못된 정렬·페이지 값 | 400 | `BAD_REQUEST` |

### 8. 설계 결정

각 결정은 **선택한 방식 / 버린 대안 / 이유**를 남긴다.

#### 결정 1. 삭제 방식

- **선택한 방식**: soft delete
- **버린 대안**: hard delete
- **이유**: 삭제된 상품은 새로 주문할 수 없지만, 과거 주문 내역에서는 그 상품을 조회할 수 있어야 하기 때문에. 물리 삭제면 행이 사라져 주문 품목이 가리키는 상품을 보여줄 수 없다.
- **적용 범위**: 삭제 제외는 대상을 새로 쓰는 경로(고객 상품·브랜드 조회, 새 주문, 수정, 재고 변경)에만 적용한다. 주문 내역 조회(고객·관리자)는 삭제 여부와 관계없이 품목의 상품을 조회한다(DEL-002, DEL-003).
- **감수하는 점**: 상품명은 `OrderItem`에 저장하지 않으므로, 주문 뒤 상품명이 바뀌면 과거 주문에도 바뀐 이름이 보인다. 금액은 확정 시점 단가를 `OrderItem`에 저장하므로 영향이 없다(3-2).

#### 결정 2. 상품 규칙과 조회 조합의 위치

원문 질문: 상품의 상태·규칙과 조회 결과 조합(브랜드 정보·좋아요 수)을 어디에 둘 것인가?

- **선택한 방식**: `Product`는 자기 상태·규칙(이름·가격·재고, 브랜드 식별자)만 가진다. 고객 상품 조회는 `ProductFacade`(application)가 상품·브랜드·좋아요 수를 각각 조회해 응답 모델(`ProductInfo`)로 조합한다.
- **버린 대안**: `Product`가 `Brand`를 객체로 참조하고 좋아요 수까지 포함해, 상품 모델에서 조회 결과를 만든다.
- **이유**: 반례 "브랜드 응답이 바뀌면 어떤 객체까지 바뀌는가?"를 대입하면 다음과 같다.

  | 변경 | application에서 조합 (선택) | Product에서 조합 (버린 대안) |
  |---|---|---|
  | 브랜드 응답 필드 추가·변경 | `ProductFacade`·`ProductInfo`만 바뀐다 | `Product` 모델과 그 테스트까지 바뀐다 |
  | 고객·관리자 응답 필드 구분 (QRY-002) | Facade·Info를 고객용/관리자용으로 나누면 된다 | 한 모델이 두 응답을 모두 알아야 한다 |
  | 상품 규칙(재고 차감 등) 테스트 | 브랜드·좋아요 없이 `Product`만으로 테스트한다 | 브랜드·좋아요 준비가 필요해진다 |

  상품의 규칙과 화면에 보여줄 조합은 바뀌는 이유가 다르다(발제.md: "상태의 규칙"과 "조회 결과의 구성"은 같은 종류의 요구가 아니다). 3-2에서 `Product`가 `brandId`만 갖기로 한 것과도 맞는다.
- **목록 조회에서 이어지는 결정**: 조합 위치(application)와 정렬·집계 계산 위치(infrastructure 쿼리)를 구분한다.

  **(1) `likes_desc` 정렬과 페이지 조회**

  - 문제: 좋아요 수를 조회한 뒤 Facade에서 붙이면, 페이지를 자르기 전에 좋아요 수로 정렬할 수 없다.
  - 선택: 상품 목록은 `ProductRepository`의 목록 조회 한 번에서 정렬·페이지·좋아요 수 집계를 함께 처리한다. 구현(`ProductRepositoryImpl`)은 이 저장소에 설정된 QueryDSL(`modules/jpa`의 `QueryDslConfig`)로 작성한다.
    - 조건: 삭제되지 않은 상품(DEL-002), 브랜드 필터가 있으면 해당 `brandId`
    - 좋아요 수: `Like`를 `productId`로 왼쪽 조인해 개수를 센다 — 좋아요가 없는 상품은 0 (LIK-002)
    - 정렬: `latest`는 등록 시각 내림차순, `price_asc`는 가격 오름차순, `likes_desc`는 좋아요 수 내림차순. 동률이면 이름 오름차순(P-2), 이름까지 같으면 상품 ID 오름차순
    - 결과: 한 페이지의 상품과 각 상품의 좋아요 수. `Product`에는 좋아요 수 필드가 없으므로, 이 결과(상품 + 좋아요 수)를 담는 조회 모델을 `domain/product`에 둔다. `ProductRepository`가 infrastructure 타입을 반환하지 않게 해 2-2 의존 방향을 지킨다. 구현(`ProductRepositoryImpl`)은 좋아요 저장 모델을 조인한다.
  - 버린 대안: `Product`에 좋아요 수 필드를 두고 등록·취소 때마다 갱신한다. 정렬 쿼리는 단순해지지만, 3-3에서 정한 "상품에 개수 필드를 두지 않는다"와 어긋나고 등록·취소와 개수 갱신이 어긋날 수 있다(동시 요청, 멱등 등록 P-7).
  - 다시 검토할 조건: 좋아요 수 집계 쿼리가 목록 응답 시간을 눈에 띄게 늦출 때.

  **(2) 목록의 브랜드·좋아요 수 조회 횟수**

  - 문제: 상품마다 브랜드와 좋아요 수를 따로 조회하면 쿼리가 상품 수만큼 늘어난다.
  - 선택: 한 페이지 응답을 쿼리 3번 이내로 만든다.

    | 순서 | 조회 | 비고 |
    |---|---|---|
    | 1 | 상품 목록 + 좋아요 수 | (1)의 쿼리 |
    | 2 | 전체 개수 | 페이지 정보용 |
    | 3 | 브랜드 | `ProductFacade`가 페이지의 `brandId`를 모아 한 번에 조회 |

    상품 상세는 상품 1건이므로 상품·브랜드·좋아요 수를 각각 한 번씩 조회한다.
  - 버린 대안: 상품마다 브랜드·좋아요 수를 조회한다. 페이지 크기가 20이면 쿼리가 40번 이상 늘어난다.

#### 결정 3. 주문 확정의 트랜잭션 위치

상황: 주문 확정은 상품 재고 차감, 포인트 차감, 주문 상태 변경이 함께 성공하거나 함께 실패해야 한다(4절 대표 흐름). 이 저장소의 구조는 다음과 같다.

| 구성 | 패키지 | 역할 |
|---|---|---|
| `{Domain}Service` | `domain` | 한 도메인의 repository 조회·저장과 트랜잭션. 여러 엔티티에 걸친 업무 규칙을 담는 도메인 서비스가 아니라, 애플리케이션 서비스에 가까운 역할이다 (`ExampleService`) |
| `{Domain}Facade` | `application` | 여러 Service를 조합해 하나의 유스케이스를 완성한다 (`ExampleFacade`) |

- **선택한 방식**: `OrderFacade`의 확정 메서드에 `@Transactional`을 둔다. `ProductService`·`UserService`·`OrderService`의 메서드는 기본 전파 방식(REQUIRED)으로 Facade의 트랜잭션에 참여한다. 한 도메인만 다루는 유스케이스는 기존처럼 Service에서 트랜잭션을 관리한다.
- **버린 대안**: 도메인별 Service에만 트랜잭션을 둔다(Facade는 트랜잭션 없이 Service를 순서대로 호출).
- **이유**: 대안에서는 각 Service 호출이 끝날 때마다 커밋된다. 재고 차감이 커밋된 뒤 포인트 부족으로 확정이 거절되면 재고만 줄어든 상태가 남는다. 여러 도메인의 변경을 하나로 묶어야 하는 곳은 그 순서를 조율하는 Facade이므로 경계도 Facade에 둔다. `application`이 `domain`에 의존하는 방향이라 2-2 허용 의존 방향도 지킨다.
- **다시 검토할 조건**: 확정 흐름에 외부 결제 등 트랜잭션으로 되돌릴 수 없는 호출이 추가될 때.

#### 결정 4. 도메인 실패 표현

상황: starter의 `CoreException`은 `ErrorType`을 갖고, `ErrorType`은 `HttpStatus`를 갖는다. 도메인이 `CoreException(ErrorType.CONFLICT)`를 던지면 "이 실패는 409다"라는 전송 계층의 결정을 도메인이 내리게 된다. 2-1은 HTTP 오류 매핑을 `interfaces`의 책임으로 정했다.

| 위치 | 구성 | 역할 |
|---|---|---|
| `domain.error` | `DomainException(DomainErrorType type, String message)` | 도메인·application이 던지는 실패. HTTP를 모른다 |
| `domain.error` | `DomainErrorType`: `INVALID_VALUE`, `NOT_FOUND`, `CONFLICT` | 업무상 실패 종류. 6절 분류(입력 오류·대상 없음·상태 충돌)와 같다 |
| `interfaces.api` | `ApiControllerAdvice` | `INVALID_VALUE→400`, `NOT_FOUND→404`, `CONFLICT→409`로 한곳에서 변환 |

- **선택한 방식**: 위 구조. 규칙마다 예외 클래스를 만들지 않고, 원인은 메시지로 구분한다.
- **버린 대안**: starter `ExampleModel`처럼 도메인이 `CoreException(ErrorType)`을 직접 던진다.
- **이유**: 도메인 규칙과 전송 방식은 바뀌는 이유가 다르다. HTTP 대신 배치·이벤트에서 같은 도메인을 써도 HTTP 타입을 끌고 가지 않는다. 도메인 테스트도 상태 코드가 아니라 업무 의미(예: 재고 부족 → `CONFLICT`)를 검증한다. 종류 이름이 HTTP 분류와 거의 1:1이라 겉보기는 비슷하지만 의존 방향이 다르다.
- **지키는 방법**: `ArchitectureTest.domainDoesNotKnowHttp`가 `domain`이 `org.springframework.http`와 `support.error`에 의존하지 않는지 검사한다. starter 예시(`domain.example`)는 기존 방식을 쓰므로 검사에서 제외하고 수정하지 않는다(범위 밖 개편).
- **다시 검토할 조건**: 같은 종류 안에서 요청자가 원인별로 다르게 대응해야 해서 메시지만으로 부족할 때.
