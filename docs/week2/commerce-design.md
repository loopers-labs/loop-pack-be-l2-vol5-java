## 3.도메인 관계
| 관계                          | 다중성   | 연결 방식                                              | 필요한 이유                                                                                | 책임 주체                                                                          |
|-----------------------------|-------|----------------------------------------------------|---------------------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| Brand - Product             | 1:N   | 직접(Product가 brandId보유)                             | 브랜드 삭제 시 연결 상품을 함께 논리 삭제                                                              | Product                                                                        |
| User - Like - Product       | 1:N:1 | 간접(좋아요 테이블에 User와 Product가 각각 존재)                  | 유저당 상품에 좋아요를 1번만 누를 수 있기 때문(중복방지)                                                     | Like(동일 User-Product 조합 저장을 막는 규칙을 Like 저장 시점에 검증)                             |
| Order - OrderItem - Product | 1:N:1 | 간접                                                 | 한 주문에 여러 상품을 가질 수 있어야함(Order-OrderItem), 주문 시점의 금액과 수량을 독립적으로 기록해야함(OrderItem-Product) | OrderItem(주문할 때 상품의 수량,단가 결정), Stock(차감·설정 수량 입력 검증) + ProductRepository(재고 부족 판정과 차감을 조건부 UPDATE 로 처리), Order(여러 OrderItem을 묶어 금액 계산) + OrderRepository(DRAFT→CONFIRMED 전환과 결제액 기록을 조건부 UPDATE 로 처리) 
| User - Point                | 1:1   | 직접 (Point가 userId 보유)                              | 유저가 취급하는 포인트는 하나이기 때문, 충전이나 차감 시 유효성(0원 이상, 오버플로우 방지)을 지켜야 함                          | Point(금액 입력 검증, 첫 충전 생성) + PointRepository(잔액 부족 판정·차감·누적을 조건부 UPDATE 로 처리)                                                              
| User - Order | 1:N | 직접 (Order가 userId 보유) | 유저가 여러 건의 주문을 만들 수 있음, 본인 주문만 조회·확정 가능해야 함 | Order(품목 합산·금액 규칙 관리) + application(본인 소유 여부 검증, 요청자-userId 일치 확인) + OrderRepository(본인·DRAFT 조건의 확정 UPDATE) |


## 4.API 계약 (입력/성공/오류) - method/path/입력/성공/대표 오류와 주요 규칙의 기대값

| GET /api/v1/brands/{brandId} | brandId(path) | 200, 브랜드 상세 | 없거나 삭제된 브랜드 → 404 | 삭제된 브랜드는 조회 불가 |

## 5.대표 흐름
### 5-1. 관리자 변경 → 고객 조회
* 근거 문장 "관리자 변경을 고객 조회에 반영하고, 고객·관리자에게 제공할 응답 필드를 구분합니다."

#### 5-1-1. 상품 가격 수정
* 관리자가 상품 가격을 4,000원 → 5,000원으로 수정 요청
→ PUT /api-admin/v1/products/{productId}
→ 관리자 권한 확인 → 가격 유효성 검증 → Product.changePrice(5000) 호출
→ 저장됨

* 고객이 이 상품을 상세 조회
→ GET /api/v1/products/{productId}
→ Product 조회 → 응답에 가격 5,000원이 반영되어 보임

#### 5-1-2. 상품 삭제
* 관리자가 상품을 삭제 요청
→ DELETE /api-admin/v1/products/{productId}
→ 관리자 권한 확인
→ 삭제 처리 

* 고객이 상품 목록을 조회
→ GET /api/v1/products
→ 삭제된 상품은 목록에서 제외되어 응답
→ 새 좋아요 등록 불가  (기존 좋아요는 취소 가능)
→ 새 주문에서 제외

#### 5-1-3. 재고 변경
* 관리자가 재고를 0으로 변경
→ PUT /api-admin/v1/products/{productId}/stock
→ 관리자 권한 확인 → 0 이상인지 검증 → 최종 수량으로 설정

* 고객이 상품 상세 조회 → 재고 0인 상태로 보임

#### 5-1-4. 상품 등록
* 관리자가 새 상품을 등록
→ POST /api-admin/v1/products
→ 관리자 권한 확인
→ 브랜드 존재/미삭제 확인 → 이름·가격 유효성 검증 → 저장

* 고객이 상품 목록을 조회
→ GET /api/v1/products
→ 방금 등록된 상품이 목록에 나타남

### 5-2. 좋아요 등록 · 취소
#### 5-2-1. 고객이 상품 좋아요를 등록
→ POST /api/v1/products/{productId}/likes
→ 삭제된 상품인지 확인
→ 사용자-상품관계 유니크 체크 (상품이 없거나(404) 좋아요가 이미 등록되어있는 경우(401) 거절)
→ 좋아요가 등록됨

#### 5-2-2. 고객이 상품 좋아요를 취소
→ DELETE /api/v1/products/{productId}/likes
→ 사용자 식별 누락/존재하지 않는 상품(401) 요청 거절
→ 본인의 좋아요만 취소 가능(404)
→ 좋아요가 취소됨

### 5-3. 포인트 충전 → 주문 확정
#### 5-3-1. 고객이 포인트를 충전한다.
→ POST /api/v1/points/charge
→ 누락, 잘못된 타입, 표현 범위 초과를 거절
→ 오류 입력 시 기존 잔액 유지
→ 검증 통과 시: 포인트가 충전됨

#### 5-3-2. 고객이 주문을 생성한다.
→ POST /api/v1/orders
→ 상품이 존재하며 삭제되지 않았는지, 수량이 양수인지 확인
→ 생성 시점에는 재고 차감이 없음 (DRAFT 상태로 저장)

#### 5-3-3. 고객이 주문을 확정한다.
→ POST /api/v1/orders/{orderId}/confirm
→ 본인의 주문만 확정 가능 (없거나 남의 주문이면 404)
→ 한 트랜잭션 안에서 아래 순서로 조건부 UPDATE 를 실행한다. 각 단계는 "확인 후 변경"이 아니라
  WHERE 절에 조건을 둔 UPDATE 한 번이며, 영향 행이 0이면 예외로 전체를 롤백한다
→ 주문: DRAFT 인 본인 주문만 CONFIRMED 로 바꾸고 결제액(생성 시점 단가×수량 합) 기록 (0건이면 409 이미 확정)
→ 포인트: 잔액이 충분할 때만 차감 (0건이면 409 잔액 부족)
→ 상품: 품목을 productId 오름차순으로 돌며, 삭제 여부를 조회로 확인(삭제됨이면 404)한 뒤
  재고가 충분할 때만 차감 (0건이면 409 재고 부족). 중복 상품은 생성 시점에 합산되어 총수량 기준
→ 어느 단계든 실패하면 앞서 나간 UPDATE 까지 전부 롤백되어 DRAFT 유지, 재고·포인트 차감 없음
→ 성공하면 갱신 후 다시 읽은 주문(CONFIRMED, 결제액)을 응답

## 6. AI와 설계 다듬기
AI와 설계 다듬기

### 6-1. OrderItem 필요 근거 검증
- 질문: "요구사항에 가격이 바뀐다는 얘기는 없었잖아. 바뀔 수도 있다는 건
  너의 생각 아니야?"
- 검토: AI가 "가격이 나중에 바뀔 수 있어서 unitPrice가 필요하다"고 설명했으나,
  이는 과제 원문에 없는 일반론적 추론이었음을 확인
- 결론: unitPrice 저장 근거를 과제 원문에 명시된 "여러 품목·수량·단가·합계를
  저장한다"는 요구사항 자체로 재정리. AI의 일반론과 실제 요구사항을 구분함.

### 6-2. 관리자 변경→고객 조회 흐름의 범위 판단
- 질문: (브랜드 수정/삭제/등록도 고객에게 반영되는지 설명을 들은 뒤)
  "그렇다면 굳이 안 적어도 되는 거 아니야?"

  ("403은 그 주문은 있는데 네 것이 아니다를 알려준다"). 그런데 2주차 초안은
  좋아요 목록·주문 확정·주문 상세에서 403을 쓰고 있어 두 문서가 충돌했음

  단, `/api-admin/**`의 "권한 없음 → 403"은 그대로 둔다. 이쪽은 소유권이 아니라
  Spring Security가 지키는 역할 경계이고, 관리자 API의 존재 자체는 비밀이 아니다.
  `ErrorType`에는 401(UNAUTHORIZED)만 추가하고 FORBIDDEN은 추가하지 않는다.

### 6-7: User의 성격 재확인

### 6-8: 상품 목록의 보조 정렬 기준을 id 내림차순으로 확정
- 질문: "동률일 때 보조 정렬 기준을 어떻게 정했는지, 임의로 정한 거라면
  근거를 남겨달라"
- 검토: 4-1 계약에 "동률 시 id 등"이라고만 적혀 있어 정렬 방향(오름/내림)이
  정해지지 않은 상태였음. 구현에서는 방향을 반드시 골라야 함
- 결론: id 내림차순으로 확정. 근거 두 가지.
    1. latest 정렬과 방향이 일치한다. 최신순은 나중에 등록된 상품이 앞이고
       나중에 등록될수록 id가 크므로, 동률일 때도 최신이 앞에 오는 편이 일관됨
    2. latest 정렬 자체를 결정적으로 만든다. createdAt 이 같은 시각에 기록되면
       1차 정렬만으로는 순서가 정해지지 않는데, id 내림차순이 tie-breaker 로
       작동해 조회 결과가 항상 같은 순서를 보장함
- 영향: price_asc / likes_desc / latest 세 정렬 모두 2차 기준으로 id DESC 를
  적용한다. 페이지 경계에서 항목이 중복·누락되지 않는 것도 이 덕분이다.

### 6-9: 고객 API 경로의 CSRF 보호 해제

### 6-11: 관리자 CRUD 의 수정 범위와 삭제 방식 확정
- 질문: 관리자 브랜드/상품 CRUD 와 삭제 경계 구현 요청. 계약에 "수정할 정보"
  라고만 적혀 있어 수정 대상과 삭제 방식이 정해지지 않은 상태였음
- 검토 및 결론:
    1. 브랜드 수정 범위 — 이름만 수정한다. Brand 가 name 외의 속성을 갖지 않기
       때문이다. 100자·공백 검증이 생성자와 중복되지 않도록 검증을 private
       메서드로 빼고 생성자와 changeName 이 함께 재사용한다.
    2. 상품 수정 범위 — 이름과 가격만 수정한다. 브랜드는 고정(변경 불가)이고,
       재고는 PUT .../stock 으로 이미 분리되어 있으므로 제외한다.
    3. 삭제 방식 — 논리 삭제(soft delete)를 택한다. 물리 삭제를 하면 이미 저장된
       주문의 OrderItem 이 가리키는 상품이 사라져 과거 주문 내역을 복원할 수 없고,
       Like 관계도 함께 끊어진다. BaseEntity 가 이미 deletedAt 과 delete() 를
       제공하므로 이를 그대로 쓴다. 주문은 생성 시점 단가를 스냅샷으로 들고 있어
       상품이 삭제되어도 금액 정보는 온전히 남는다(6-10 참조).
    4. 브랜드 일괄 삭제 — 삭제되지 않은 연결 상품을 브랜드와 함께 논리 삭제하고
       204 로 응답한다(3주차 과제로 기존 409 거절에서 변경). 재고가 0인 상품도
       "삭제되지 않은 상품"이므로 삭제 대상에 포함한다. 재고 0은 품절 상태일 뿐
       상품이 사라진 것이 아니기 때문이다. 브랜드·상품 변경은 한 트랜잭션에서
       처리해 중간에 실패하면 전부 취소한다. 상품마다 따로 commit 하거나 일부
       성공을 응답하지 않는다. 기존 주문은 단가 스냅샷을 갖고 있어 영향이 없다.
    5. 삭제된 대상의 취급 — 고객 조회·새 주문·새 좋아요에서 제외하고, 수정·재고
       변경의 대상으로도 사용하지 않는다(모두 404). 다만 관리자 목록 조회에는
       포함한다. 무엇이 삭제되었는지 확인하는 것 자체가 관리자의 역할이기 때문이다.
    6. 중복 삭제 — 이미 삭제된 대상을 다시 삭제하면 404 로 응답한다. 기존
       findActiveBrand / getActiveProduct 가 삭제분을 404 로 다루는 것과 맞춘다.

### 6-13: 주문 확정의 동시성 — 조건부 UPDATE 로 전환
- 질문: 주문 확정이 "조회 → 메모리에서 검사 → 더티체킹 저장"(read-modify-write)이라
  같은 재고·잔액을 동시에 바꾸면 마지막 commit 이 이기는 갱신 유실이 가능했음.
  3주차 과제로 이를 어떻게 막을지 확인 요청
- 검토 및 결론:
    1. 트랜잭션 경계와 처리 순서 — OrderFacade.confirmOrder 하나의 트랜잭션 안에서
       주문(DRAFT→CONFIRMED) → 포인트 차감 → 상품 재고 차감(productId 오름차순) 순으로
       처리한다. 상품을 ID 순으로 고정하는 이유는 서로 다른 주문이 같은 상품들을 반대
       순서로 잠그다 교착에 빠지지 않게 하기 위해서다. 주문·포인트는 요청자별 행이라
       경쟁이 없고, 상품만 여러 구매자가 공유하므로 마지막에 둔다.
    2. 조건부 갱신을 선택한 이유 — 상태·잔액·재고 조건을 WHERE 절에 넣은 UPDATE 한 번으로
       판정과 변경을 원자적으로 처리한다(예: `UPDATE products SET quantity = quantity - ?
       WHERE id = ? AND quantity >= ? AND deleted_at IS NULL`). DB 의 행 잠금이 동시
       요청을 직렬화하고, 영향 행이 0이면 CoreException 으로 전체를 롤백한다. 비관적 락
       (SELECT ... FOR UPDATE)보다 왕복이 적고, 낙관적 락(@Version)처럼 재시도 루프가
       필요 없다. 잠금 구간에 외부 호출이나 대기를 두지 않는다.
       비용: (a) 벌크 UPDATE 는 영속성 컨텍스트를 거치지 않아 응답용 Order 는
       EntityManager.refresh 로 다시 읽는다(SELECT 1회 추가, 컨텍스트 전체는 비우지 않음).
       (b) @PreUpdate 가 돌지 않으므로 updated_at 을 SET 절에서 직접 갱신한다.
       (c) Product 에 @DynamicUpdate 를 두어 더티체킹 UPDATE 가 재고 컬럼을 stale 값으로
       덮어쓰지 않게 한다. (d) 삭제 상품 404 와 재고 부족 409 를 구분하기 위해 상품만
       조회 후 차감한다(SELECT 1회 추가).
    3. 도메인 메서드의 역할 재배치 — Stock.deduct, Point.deduct, Order.confirm 이 메모리에서
       하던 "재고 부족·잔액 부족·DRAFT 아님" 상태 검증과 값 변경은 SQL 조건부 UPDATE 가
       맡는다. 메모리 상태는 조회 시점의 스냅샷이라 동시 요청 아래서는 판정 근거가 될 수
       없기 때문이다. 0 이하 수량·금액 거절, 오버플로 같은 입력 검증은 도메인 정적
       메서드(Stock.validateDeductQuantity, Point.validateDeductAmount 등)로 남겨 Service 가
       UPDATE 전에 호출한다. 각 Repository 의 조건부 UPDATE 메서드 Javadoc 에 어떤 도메인
       규칙을 대신하는지 적어 두었다.
    4. 같은 행을 바꾸는 다른 경로 — 포인트 충전은 `balance = balance + ?`(표현 범위
       초과는 WHERE 로 거르고 0건+행 있음이면 400), 관리자 재고 설정은
       `SET quantity = ? WHERE id = ? AND deleted_at IS NULL`(0건이면 404)의 단일 UPDATE 로
       바꿨다. 이 경로들이 read-modify-write 로 남아 있으면 확정과 섞일 때 다시 갱신
       유실이 생기므로 함께 바꿔 규칙을 우회하지 않게 했다. 포인트 행이 없는 사용자의
       첫 충전은 기존처럼 새 행을 저장한다.
    5. 검증한 것 — OrderConcurrencyTest(실제 MySQL, 클래스 @Transactional 없음, mock 없음,
       worker 마다 독립 트랜잭션, CountDownLatch 로 시작만 동기화):
       - 대조군: 제품 코드가 아닌 순수 SQL 로 두 트랜잭션이 재고 5를 잠금 없이 읽고 각각
         4를 저장 → 둘 다 성공, 최종 재고 4, "성공 2 + 최종 4 ≠ 초기 5"로 갱신 유실 재현
       - 재고 경쟁: 재고 5, 1개씩 사는 주문 8건 동시 확정 → 확정 5, 재고 부족 3,
         기술 오류 0, 최종 재고 0
       - 포인트 경쟁: 잔액 10,000원, 4,000원 주문 3건 동시 확정 → 확정 2, 잔액 부족 1,
         기술 오류 0, 최종 잔액 2,000원, 거절된 주문의 재고 유지
       - 충전과 결제: 잔액 10,000원에서 2,000원 충전과 7,000원 확정 동시 → 둘 다 성공,
         최종 잔액 5,000원
       - 공식: 초기 재고 − 성공 수량 합 = 최종 재고, 초기 잔액 + 성공 충전 − 성공 결제
         = 최종 잔액, 성공 + 업무 거절 + 기술 오류 = 전체 요청. 3회 반복 실행 통과
       - 원자성(OrderFacadeIntegrationTest): 앞선 상품의 재고 UPDATE 가 DB 에 나간 뒤
         다음 상품에서 CHECK 제약으로 실패 → 주문 DRAFT, 결제액 0, 재고, 잔액 전부 원상태
       - 계약 회귀(OrderV1ApiE2ETest): 확정 5건의 상태 코드·메시지 유지, 삭제된 상품이
         포함된 DRAFT 확정은 404

         유니크 제약 위반으로 한쪽이 500 이 된다. 이번 범위 밖이며 처리하지 않았다.
