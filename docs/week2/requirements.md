# commerce-api 요구사항

2주차 과제 문서에서 고객과 관리자에게 제공해야 하는 기능, 결과, 업무 규칙을 추린 것이다. 클래스·패키지·저장 방식·HTTP·테스트 같은 구현 방법에 관한 지시는 제외한다. [설계 문서](./commerce-api-design.md)의 근거는 이 문서의 ID를 가리킨다.

## 요구사항


| 컬럼   | 뜻                                                                          |
| ---- | -------------------------------------------------------------------------- |
| ID   | 요구사항을 가리키는 식별자다. `R-그룹-순번` 형식이며, 한 번 붙인 ID는 바꾸지 않고 새 요구사항은 그룹의 다음 순번을 받는다. |
| 요구사항 | 고객과 관리자에게 제공해야 하는 기능, 결과, 업무 규칙이다.                                         |
| 출처   | 과제 문서에서 이 요구사항이 나온 부분이다.                                                   |


### 사용자와 접근 범위 (`ACCESS`)


| ID          | 요구사항                                                 | 출처                                         |
| ----------- | ---------------------------------------------------- | ------------------------------------------ |
| R-ACCESS-01 | 고객은 브랜드와 상품을 조회하고 좋아요·포인트·주문 기능을 이용할 수 있다.           | 과제 문서 · `3. 기본 기능 구현` — 상품·브랜드·좋아요, 포인트·주문 |
| R-ACCESS-02 | 관리자는 브랜드·상품·재고를 관리하고 구매자들의 주문을 조회할 수 있다.             | 과제 문서 · `3. 기본 기능 구현 > 관리자`                |
| R-ACCESS-03 | 고객은 자신의 좋아요·포인트·주문만 다룰 수 있다.                         | 과제 문서 · `4. 실행·제출` 첫 문단                    |
| R-ACCESS-04 | 관리자 기능은 관리자만 사용할 수 있고 일반 사용자와 식별되지 않은 사용자는 사용할 수 없다. | 과제 문서 · `4. 실행·제출 > 관리자 HTTP 테스트 실행`       |
| R-ACCESS-05 | 식별 정보가 없거나 존재하지 않는 사용자의 고객 요청은 거절한다.                 | 과제 문서 · `4. 실행·제출` 첫 문단                    |
| R-ACCESS-06 | 고객과 관리자에게 제공하는 응답 정보를 구분한다.                          | 과제 문서 · `3. 기본 기능 구현 > 관리자` 표 아래 문장        |

| R-CATALOG-07 | 존재하지 않거나 삭제된 브랜드·상품의 고객 상세 조회는 없는 대상 오류로 처리한다. | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` 하단 조건                                    |
| R-CATALOG-08 | 상품 목록 조건(브랜드 필터, 페이지, 정렬)의 잘못된 입력을 처리한다.       | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` — “잘못된 입력 처리”                            |


### 좋아요 (`LIKE`)


| ID        | 요구사항                                          | 출처                                                     |
| --------- | --------------------------------------------- | ------------------------------------------------------ |
| R-LIKE-01 | 고객은 삭제되지 않은 상품에 좋아요를 등록하고 자신의 좋아요를 취소할 수 있다.  | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` — 좋아요 등록·취소 및 하단 조건 |
| R-LIKE-02 | 같은 고객은 같은 상품에 좋아요를 중복으로 보유할 수 없다.             | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` — “중복 관계 방지”        |
| R-LIKE-03 | 고객은 자신의 좋아요 상품 목록을 조회할 수 있다.                  | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` — 내 좋아요 목록          |
| R-LIKE-04 | 고객은 자신의 좋아요 관계만 조회하고 취소할 수 있다.                | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` — 내 좋아요 목록의 핵심 조건   |
| R-LIKE-05 | 상품의 좋아요 수는 좋아요 관계에서 조회하며, 좋아요를 누른 고객 수를 나타낸다. | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` — “좋아요 수는 관계에서 조회” |
| R-LIKE-06 | 좋아요 등록과 취소 결과는 이후 조회하는 상품의 좋아요 수에 반영된다.       | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` — 내 좋아요 목록의 핵심 조건   |
| R-LIKE-07 | 삭제된 상품에는 새 좋아요를 등록할 수 없고 내 좋아요 목록에도 나타나지 않는다. | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` 하단 조건               |
| R-LIKE-08 | 상품이 삭제된 뒤에도 고객은 남아 있는 자신의 좋아요를 취소할 수 있다.      | 과제 문서 · `3. 기본 기능 구현 > 상품·브랜드·좋아요` 하단 조건               |

## 정책 확인 필요 사항

- **임시 판단**: 확인 전에도 진행할 수 있는 결정이다. 나중에 되돌리기 쉬우므로 임시로 판단해 진행하고, 확인 결과가 다르면 바꾼다.
- **담당자 확인**: 확인 전에는 진행할 수 없는(블로킹되는) 결정이다. 임시로 정하고 진행하면 나중에 되돌리기 힘들기 때문이다. 지금은 과제 환경이라 실제 담당자가 없으므로, 담당자가 아래 판단을 확인해 주었다고 가정하고 진행한다.


| 컬럼      | 뜻                                                                                                                                           |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| ID      | 정책을 가리키는 식별자다. `P-그룹-순번` 형식이며, 그룹은 첫 번째 근거 요구사항의 그룹을 따른다. 한 번 붙인 ID는 바꾸지 않고 새 정책은 그룹의 다음 순번을 받는다. 두 영역으로 나뉘어 있어 한 영역 안에서는 순번이 이어지지 않을 수 있다. |
| 질문      | 요구사항만으로는 답이 하나로 정해지지 않는 제품 동작이다.                                                                                                            |
| 근거 요구사항 | 이 질문이 나온 요구사항의 ID다.                                                                                                                         |
| 질문의 출처  | 과제 문서에서 질문이 생긴 부분과, 과제가 무엇을 정하지 않았는지다.                                                                                                      |
| 선정      | 질문을 고른 쪽이다. `직접`은 작성자가 고른 질문이고, `AI`는 AI가 과제 문서를 다시 읽고 추가한 질문이다.                                                                            |
| 판단      | 질문에 대한 답이다.                                                                                                                                 |
| 판단 근거   | 그렇게 답한 이유다. 근거가 되는 요구사항 ID나 정책 ID를 함께 적는다.                                                                                                  |
