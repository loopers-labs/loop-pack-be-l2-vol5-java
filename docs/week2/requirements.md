# 요구사항 명세서 (W2)

원문 요구사항 표를 구현과 테스트의 기준이 될 수 있는 수준으로 정제한 문서다.
**"무엇을"** 만 적는다. "왜 이렇게" 는 같은 폴더의 설계 기록이 진다.

| | |
|---|---|
| **원문** | Vol5 W2 요구사항 — 🏷 상품·브랜드·좋아요 / 💰 포인트·주문 / 🛠 관리자 |
| **이 문서가 하는 일** | ① 원문이 **비워 둔 값**을 채운다 ② 원문이 **선택지를 준 것**을 고른다 ③ 규칙마다 ID 를 붙여 테스트가 그 ID 로 자기를 설명하게 한다 |
| **이 문서가 하지 않는 일** | 저장 구조·클래스 경계·트랜잭션 범위. 설계 기록의 몫이다 |

## 규칙 ID

`BRAND` · `PRODUCT` · `LIKE` · `POINT` · `ORDER` · `COMMON` 여섯 갈래에 세 자리를 붙인다.

- 번호는 **다시 쓰지 않는다.** 규칙이 사라지면 번호는 비워 두고 다른 규칙에 붙이지 않는다.
  같은 번호가 다른 뜻이 되면 문서와 테스트가 조용히 어긋난다.
- 테스트 이름은 `[PRODUCT-004] 동률이면 id 내림차순으로 정렬한다` 처럼 ID 로 시작한다.
- W1 의 `INV-001`~`INV-006` 은 주문 할인(쿠폰) 계약의 규칙이다. 접두사 체계로 옮기려면
  `DISCOUNT-001`~`006` 이 되며, W1 은 설계만 하고 코드를 만들지 않아 참조하는 테스트가 없으므로
  문서 한 곳만 고치면 된다.

## 출처 구분

| 표기 | 뜻 |
|---|---|
| **원문** | 요구사항 표에 문장으로 있다 |
| **정함** | 원문이 값을 비워 두어 우리가 채웠다. 뒤집혀도 값만 바뀐다 |
| **선택** | 원문이 선택지를 주어 우리가 골랐다 |
| **보안** | 원문에 없지만 그러지 않으면 사고다 |
| **질문** | 아직 답이 없다. 아래 「물을 질문」 |

## LIKE — 좋아요

`POST·DELETE /api/v1/products/{productId}/likes` · `GET /api/v1/users/{userId}/likes`

| ID | 규칙 | 출처 | 깨는 입력 | 기대 |
|---|---|---|---|---|
| `LIKE-001` | 좋아요는 사용자–상품 관계로 저장한다. 같은 관계는 하나만 존재한다 | 원문 | 같은 요청 두 번 | 두 번째도 성공 응답, 관계는 하나 |
| `LIKE-002` | 등록은 멱등이다. 이미 눌렀으면 아무 일도 일어나지 않고 성공이다. **살아 있는 상품에 한해 성립한다** | 선택 | — | 200 |
| `LIKE-003` | 취소는 멱등이다. 누른 적 없어도 성공이다 | 선택 | — | 204 |
| `LIKE-004` | 삭제된 상품에는 좋아요를 등록할 수 없다. **기존 관계가 있어도 마찬가지다** | 원문 + 정함 | 이미 좋아요한 상품이 삭제된 뒤 다시 등록 | 404 |
| `LIKE-005` | 삭제된 상품은 내 좋아요 목록에서 제외한다 | 원문 | — | 목록에 없다 |
| `LIKE-006` | 남아 있는 자기 좋아요 관계는 상품이 삭제되었어도 취소할 수 있다 | 원문 | 삭제된 상품의 기존 관계 취소 | 204 |
| `LIKE-007` | 자기 관계만 조회·취소할 수 있다 | 보안 | 경로 `userId` ≠ 헤더 `X-USER-ID` | 404 (존재를 숨긴다) |
| `LIKE-008` | 상품의 좋아요 수는 관계를 세어 얻는다. 별도로 저장하지 않는다 | 원문 | — | 관계를 지우면 수도 즉시 줄어든다 |

`LIKE-004` 와 `LIKE-006` 은 일부러 비대칭이다 — **삭제된 대상에는 더 쌓지 않되, 치울 수는 있다.**
등록은 없어진 상품에 대한 새 행위라 막고, 취소는 사용자가 자기 데이터를 치우는 것이라 허용한다.
"삭제된 대상은 조작 대상이 아니다" 를 브랜드·상품 전부에서 지켜 온 것과 같은 줄에 선다.

`LIKE-005` 와 `LIKE-006` 을 함께 만족하면 목록에 보이지 않는 관계가 남지만, **아무것도 깨지지 않는다** —
논리 삭제라 상품 행이 그대로 있어서 끊어진 참조가 생기지 않는다 (질문 Q-4 에서 정했다).

## POINT — 포인트 (구현 완료)

`POST /api/v1/points/charge` · `GET /api/v1/points`

| ID | 규칙 | 출처 | 깨는 입력 | 기대 |
|---|---|---|---|---|
| `POINT-001` | 충전액은 양의 정수다 | 원문 | `0` · `-1` · `"abc"` · 누락 | 400 |
| `POINT-002` | 잔액은 0 이상이다. 0원을 허용한다 | 원문 | — | — |
| `POINT-003` | 잔액 합산이 표현 범위를 넘으면 충전을 거절하고 **기존 잔액을 유지한다** | 원문 | 잔액 `Long.MAX_VALUE - 10` 에 11 충전 | 409 `POINT_BALANCE_EXCEEDED`, 잔액 불변 |
| `POINT-004` | 잔액이 바뀌는 모든 순간에 원장 한 줄이 함께 생긴다. 잔액 == Σ원장 == 마지막 줄의 `balanceAfter` | 정함 | — | 충전 3회 후 원장 3줄, 합이 잔액 |
| `POINT-005` | 원장은 append-only 다. 쓴 줄은 고치거나 지우지 않는다 | 정함 | — | 수정·삭제 메서드가 없다 |
| `POINT-006` | 충전 응답은 충전 후 잔액이다. 조회는 저장된 잔액을 읽는다 | 원문 | — | — |
| `POINT-007` | 포인트 레코드가 없는 사용자의 잔액은 0원이다. 첫 충전 때 개설한다 | 정함 | 충전한 적 없는 사용자 조회 | 200, `balance: 0` |

**왜 `balanceAfter` 를 원장에 남기는가.** 흔히 드는 이유("잔액을 O(1) 로 읽으려고")는 우리에게 해당하지 않는다 —
잔액은 `user_point.balance` 에서 읽지 원장을 훑지 않는다. 그 근거로는 중복된 상태일 뿐이다.
진짜 이유는 `POINT-004` 의 등식이다: **같은 숫자에 도달하는 경로가 셋**이고, 셋이 어긋나면 뭔가 잘못된 것이다.
`balanceAfter` 를 빼면 경로가 둘로 줄고 **어긋남을 감지하는 능력이 사라진다.**
append-only 원장에서 틀린 `balanceAfter` 는 손상이 아니라 **증거**다 —
"이 시점에 시스템은 잔액이 X 라고 믿었다" 를 기록하므로 **어느 줄에서 갈라졌는지**를 짚을 수 있다.
`balanceAfter` 는 잔액을 쓰는 것과 **같은 배타 잠금 안에서** 계산돼야 한다. 아니면 두 트랜잭션이 같은 값을 쓴다.
**뒤집을 조건**: 원장에 과거 시각의 줄을 끼워 넣게 되면(정정 기입·배치 소급) 그 뒤 줄들의 `balanceAfter` 가 전부 어긋난다.
그때는 running balance 를 버리고 "정정도 새 줄로 append" 로 간다.

**동시 첫 충전 (Q-5).** 레코드가 없는 사용자에게 충전이 동시에 들어와도 어긋나지 않는다.
배타 잠금은 **없는 행을 잠글 수 없으므로**, 저장소가 **행을 먼저 열고 잠근다** —
`INSERT ... ON DUPLICATE KEY UPDATE` 한 문장으로 열고(중복이어도 배타 락을 잡아 승격이 없다),
그 다음 `FOR UPDATE` 한다. `uk_user_point_user_id` 가 둘 중 하나만 행을 만들게 보장한다.
여는 것과 잠그는 것 사이가 벌어지면 무슨 일이 생기는지는 설계 6.5 에 있다.

충전은 **멱등이 아니므로 둘 다 성공하고 합산되는 것이 맞다** — 두 번 충전은 중복 요청이 아니라 두 번의 충전이다.
중복 요청을 걸러내는 것은 멱등키의 몫이고 범위 밖이다(아래).

이것을 닫은 것은 **명세 이행이 아니라 우리 판단**이다. `POINT-007` 의 출처는 `정함` 이고,
원문은 포인트 레코드의 생애에 대해 말한 바가 없다. 동시성을 원문이 요구한 자리는 `PRODUCT-023` 하나뿐이다.

**우리가 잡으려는 버그를 잡아내는 것이 바로 그 컬럼이다.**

## 비기능 요구사항

**규칙을 여기에 다시 적지 않는다.** 기능 표의 ID 를 갈래별로 가리키는 **색인**이다 —
같은 규칙을 두 곳에 적으면 한쪽만 고쳐지는 날이 온다.
이 절이 있는 이유는 따로다: 기능 표는 "무엇이 맞는가" 로 줄을 세우므로
**"동시에 들어와도 맞는가" · "누가 봐도 되는가" 같은 질문이 표 전체에 흩어진다.**

| 갈래 | 무엇을 요구하나 | 어느 규칙이 지나 |
|---|---|---|
| **동시성** | 같은 자원에 동시에 들어와도 한 번만 반영된다 | `PRODUCT-023` · `LIKE-001` · `ORDER-018` · `BRAND-004` · Q-5(동시 첫 충전) |
| **일관성** | 여러 애그리거트를 건드리는 연산은 전부 되거나 전부 안 된다 | `ORDER-015` · `POINT-004`(잔액 = Σ원장) |
| **성능** | 목록이 상품 수에 비례해 질의를 늘리지 않는다 | `PRODUCT-011` · `012` · `013` · `COMMON-008`(총 개수를 세지 않는다) |
| **보안** | 남의 것은 존재조차 알려주지 않는다. 관리자 전용 값이 고객 응답에 실리지 않는다 | `ORDER-011` · `LIKE-007` · `COMMON-006` · `ORDER-021` · Q-2 |
| **이식성** | 도메인 규칙이 특정 저장 기술을 요구하지 않는다 | 규칙이 아니라 구조의 문제다. 설계 3.11 이 진다 |
| **관측성** | — | **없다.** 로그·지표·추적은 이번 범위 밖이고, 그래서 `ORDER-018` 같은 규칙이 깨졌을 때 **운영 중에 알아차릴 방법이 없다.** 범위를 넓히면 여기가 먼저 필요하다 |

**색인을 만들고 나서야 보이는 것이 있다.** 포인트에는 **동시성 규칙 ID 가 없다.**
`POINT-001`~`007` 은 전부 한 번의 충전이 맞는지를 말하고, 동시 충전이 어긋나지 않아야 한다는 요구는
`POINT-004` 의 등식(잔액 == Σ원장)이 **간접적으로** 지고 있을 뿐이다.
재고(`PRODUCT-023`)나 좋아요(`LIKE-001`)처럼 전용 ID 를 갖지 않았다.
**규칙이 없다는 뜻이 아니라 ID 로 적히지 않았다는 뜻**이고, 그래서 그 테스트는 자기를 ID 로 설명하지 못한다.
`POINT-008` 을 새로 붙이는 것이 맞지만, 번호를 늘리는 결정은 혼자 하지 않는다.

**이 색인에 오르지 못한 갈래가 답이다.** 가용성·처리량·응답시간에 **숫자로 된 목표가 하나도 없다.**
원문이 주지 않았고 우리가 정하지도 않았다 — 지어내면 근거 없는 숫자가 테스트가 된다.
**뒤집을 조건**: 실제 트래픽 수치나 SLO 가 주어질 때. 그때 성능 갈래가 규칙 ID 를 갖는다.

## 우리가 고른 것

원문이 선택지를 준 것들이다.

| 선택 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| 중복 상품 품목 (`ORDER-004`) | **합산** | 거절은 구현이 단순하지만 클라이언트 실수에 가혹하고, "총수량으로 재고 확인" 과 이어지지 않는다 |
| 삭제 방식 (`COMMON-007`) | **논리 삭제** | 물리 삭제는 주문 품목·좋아요의 참조를 깨고, "삭제된 상품의 기존 좋아요는 취소 가능" 을 만족할 수 없다 |
| 좋아요 멱등 (`LIKE-002`·`003`) | **멱등** | 중복 요청을 409로 거절하면 더블클릭·재시도가 오류로 보인다 |
| 복구 제공 여부 | **제공하지 않음** | 요구사항의 관리자 CRUD 에 DELETE 는 있지만 복구는 없다. 실수 삭제는 API 가 아니라 운영 절차(런북)로 되돌린다. 제공하려면 Q-1(삭제된 것을 보는 경로가 없다)을 다시 봐야 하고, 상품 복구에는 "브랜드가 여전히 살아 있는가" 라는 **새 규칙**이 필요하다 |
| 좋아요 취소 방식 (`COMMON-009`) | **실제 삭제** | 논리 삭제로 남기면 `(user_id, product_id)` 유니크 제약 때문에 재등록이 막힌다. 취소 이력이 필요해지면 관계 테이블이 아니라 별도 이벤트 기록으로 남긴다 |

## 물을 질문

| # | 질문 | 무엇이 바뀌나 |
|---|---|---|
| ~~Q-1~~ | ~~관리자 목록 조회에 **삭제된** 브랜드·상품이 보여야 하는가~~ → **보이지 않는다.** 삭제된 것을 보는 경로를 두지 않는다. 그런 파라미터(`includeDeleted=true`)는 **원문에 없는 기능**이고, 그것 하나 때문에 저장소·조회 포트·컨트롤러·응답이 전부 "삭제 여부" 라는 축을 하나씩 더 들게 된다. 두지 않으면 저장소가 **살아 있는 것만 준다**는 규칙이 예외 없이 서고, 관리자 응답에 언제나 false 인 `deleted` 필드도 필요 없다. **뒤집을 조건**: 복구 API 가 생길 때. 무엇을 복구할지 찾으려면 목록에 있어야 한다. 그때도 일상 목록에 파라미터로 섞지 않고 **복구 대상 전용 목록**으로 만든다 — 섞으면 평소에 매번 눈으로 걸러야 한다 | — |
| ~~Q-2~~ | ~~고객에게 재고 수량을 보여주는가~~ → **품절 여부만. 목록·상세 둘 다.** 가르는 선은 "목록이냐 상세냐" 가 아니라 **"누가 보느냐"** 다 — 관리자에게는 수량을 준다. 부족 응답(409)에도 남은 수량을 담지 않는다(주문을 반복해 재고를 이진탐색할 수 있다) | — |
| ~~Q-3~~ | ~~삭제된 브랜드로 상품을 등록하려 하면 400인가 404인가~~ → **400 `BRAND_NOT_AVAILABLE`. 없는 브랜드와 구분하지 않는다** (설계 8.1). 경로가 가리키는 대상이 없으면 404, 요청 본문이 가리키는 참조가 유효하지 않으면 400 | — |
| ~~Q-4~~ | ~~목록에 보이지 않는(삭제된 상품의) 좋아요를 사용자가 취소할 경로가 필요한가~~ → **필요 없다. `DELETE` 는 이미 있고, 화면에는 두지 않는다.** 긴장이라고 적었던 것이 과했다 — 논리 삭제라 상품 행이 그대로 있어서 끊어진 참조가 없다. 물리 삭제였다면 좋아요가 없는 행을 가리키게 되어 진짜 문제였을 것이다. 남은 관계는 목록(`LIKE-005`)에서 빠지고, 좋아요 수(`LIKE-008`)는 살아 있는 상품에 대해서만 보이므로 어떤 숫자에도 들어가지 않는다. 치울 동기가 없는 것을 치우라고 화면을 만들 이유가 없다. 그럼 `LIKE-006` 은 왜 있느냐 — **클라이언트가 낡은 목록을 들고 뒤늦게 취소를 보내는 경우** 때문이다. 404 로 거절하면 재시도 루프에 빠진다. 204 를 주는 것은 `LIKE-003` 멱등의 연장이다. **뒤집을 조건**: "내가 좋아요한 개수" 를 보여주는 화면이 생기면 목록 길이와 숫자가 어긋나므로 정리 경로가 필요해진다 | — |
| ~~Q-5~~ | ~~포인트 레코드는 사용자 생성 시 함께 만드는가~~ **(질문을 다시 썼다)** → ~~동시 첫 충전의 INSERT 경합을 닫을 것인가~~ → **닫는다.** 원래 질문은 답할 수 없었다 — 회원 가입이 범위 밖이라 "사용자 생성" 이라는 사건이 우리 시스템에 없고, "함께 만든다" 는 선택지가 존재하지 않는다. 질문이 틀려서 답이 안 나온 것이지 못 닫을 문제가 아니었다. 회원 가입 없이도 닫힌다 — 행을 먼저 열고 잠근다. 출처는 `보안` (원문에 없지만 그러지 않으면 사고다). 같은 입력이 **타이밍에 따라** 200 이 되기도 500 이 되기도 하는 것은 어느 정책을 고르든 버그이고, 그 500 은 사용자에게 잔액 부족 같은 업무 실패와 구분되지 않는다. 과정은 설계 6.5 | — |
| ~~Q-6~~ | ~~DRAFT 주문이 쌓이는 것을 정리해야 하는가 (만료·취소·개수 제한)~~ → **정리하지 않는다. 범위 밖으로 둔다.** `ORDER-007` 로 접수가 재고도 포인트도 건드리지 않으므로 DRAFT 가 쌓여도 **남에게 해가 없다.** 비용은 목록이 지저분해지는 것과 행 수뿐이다. 반면 만료를 두면 새 규칙이 줄줄이 따라온다 — 만료 시각은 언제인가, 만료된 주문을 확정하면 어떤 코드인가, 누가 돌리는가(스케줄러), 목록에 만료를 보여주는가. 원문에 한 줄도 없는 것에 이만큼을 정하는 것은 과하다. **뒤집을 조건**: 접수가 재고를 **예약**하게 되면 즉시 필요하다. 그 순간부터 쌓인 DRAFT 는 남의 재고를 묶는다 | — |

## 범위 밖

원문에 없고, 이번 구현에서 다루지 않는다.

> **삭제된 브랜드·상품의 복구** · 회원 가입·인증 · 장바구니 · 배송과 배송지 · 주문 취소·환불 · 쿠폰과 할인 · 포인트 사용 외의 적립 ·
> 포인트 만료와 환급 · 결제 수단(PG) · 상품 옵션(SKU) · 카테고리 · 검색 · 리뷰 · 재입고 알림

**충전 멱등(`Idempotency-Key`)** — 따로 적어 둔다. 동시 첫 충전의 경합(Q-5)과 자주 섞이지만 다른 문제다.

동시에 온 두 충전이 별개의 의도인지 같은 요청의 재시도인지 **서버는 구분할 수 없다.**
좋아요는 상태 설정이라 두 번 눌러도 결과가 같은 것이 자연스럽지만(`LIKE-002`), 충전은 **증분**이라 그렇지 않다.
증분을 멱등하게 만들려면 호출자가 "이건 아까 그 요청" 이라고 말해 줘야 하는데, 원문에 없고 보낼 클라이언트도 없다.
그 정보가 없을 때는 **받은 대로 두 번 충전한다** — 임의로 하나를 버리면 진짜로 두 번 충전하려던 사용자의 돈이 사라지고,
그쪽 실수가 훨씬 나쁘다.

반쯤 만들면 없느니만 못하다. 제대로 하려면 같은 키에 다른 본문이 오면 어떻게 하나, 처리 중인 요청과 부딪히면 기다리나 거절하나,
키를 얼마나 보관하나, 저장한 응답을 돌려주나 다시 계산하나를 전부 정해야 한다.
헤더만 받아 두면 클라이언트는 "재시도해도 안전하다" 고 믿는데 실제로는 막히지 않는다.

**누가 발급하는가**: 클라이언트다. 키는 **재시도를 살아남아야** 하는데, 그것을 얻으려고 서버에 한 번 더 물으면
그 요청도 같은 이유로 실패할 수 있다. 요청마다가 아니라 **사용자의 의도가 생긴 순간**(버튼 클릭)에 하나 만들어
그 의도의 모든 재시도가 같은 키를 쓴다.

**우리는 이미 다른 방식을 쓰고 있다** — 서버가 토큰을 먼저 내주는 2단계다.
`POST /orders` 가 `orderId` 를 발급하고 `POST /orders/{id}/confirm` 이 확정한다.
`ORDER-010` 으로 확정은 DRAFT 에만 되므로 **`orderId` 가 멱등키 역할을 한다.**
접수와 확정을 나눈 것이 결제 안전성을 덤으로 준 셈이다. 충전에 그 단계가 없어서 멱등이 아닌 것이다.
충전처럼 단순한 행위에 왕복 두 번은 과하므로, 충전 쪽은 클라이언트 키가 맞는 방식이다.

**붙일 자리**: 원장의 `(user_id, idempotency_key)` 유니크 제약.
`POINT-004`·`005` 로 이미 append-only 원장을 쓰고 있어 별도 저장소가 필요 없다.

**뒤집을 조건**: 결제 수단(PG)이 붙으면 필수다. 돈이 오가면 재시도로 두 번 빠지는 것을 서버가 책임져야 한다.

## 구현 순서

1. **포인트** — 완료 (`POINT-001`~`007`)
2. **브랜드** → **상품·재고** — 주문이 참조할 대상을 먼저 만든다
3. **좋아요** — 상품 목록의 좋아요 수까지
4. **주문** — 접수 → 확정. 포인트 사용(`use`)이 여기서 들어온다
5. **관리자 조회** — 고객 응답과 필드를 가르는 것까지
