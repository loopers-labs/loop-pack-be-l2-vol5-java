# 요구사항 정의서 — 브랜드·상품·좋아요 / 포인트·주문 / 관리자

작성 기준: 「요구사항 정의서 작성 가이드」
원문: 과제 요구사항 표 3개(상품·브랜드·좋아요, 포인트·주문, 관리자) + 기본 삭제 조건 + 요청자 식별 조건(`X-USER-ID` 헤더, → CON-03)
추가 요구(원문 외): 포인트 금액 지정 환불, 운영자의 사용자 포인트 충전·차감. 해당 항목에는 **[추가]** 표시를 붙인다.
설계 피드백 반영: DR-01, DR-06, DR-09, DR-11, DR-19, DR-20 (설계 문서 부록 A). 고친 항목 옆에 `(설계 피드백 DR-xx)` 또는 `(설계 결정 DR-xx)`를 붙였다.

---

## 1. 머리

### 1-1. 용어집

| 용어 | 정의 |
|---|---|
| 브랜드 | 상품이 속하는 단위. 브랜드 정보(→ ASM-03)를 가진다. 상태를 가짐 (→ 3-2) |
| 상품 | 정확히 하나의 브랜드에 속하며 이름·가격·재고를 가진다. 상태를 가짐 (→ 3-2) |
| 가격 | 상품 하나의 값. 단위는 원(= 포인트) |
| 재고 | 상품의 현재 수량. 관리자가 최종 수량으로 설정하고, 주문 확정 시 차감된다 |
| 사용자 | 고객 API의 요청자. `X-USER-ID` 헤더로 식별되며(→ CON-03, ASM-01) fixture로 준비되고 잔액을 가진다 |
| 구매자 | 주문을 만든 사용자를 주문 맥락에서 부르는 말. 별개 개념이 아니라 사용자의 별칭 (설계 피드백 DR-09) |
| 좋아요 | 사용자–상품 관계. 같은 쌍에 대해 최대 하나 |
| 좋아요 수 | 한 상품에 대한 좋아요 관계의 개수. 저장값이 아니라 관계에서 조회한다 |
| 포인트 | 유일한 결제 수단. 1포인트 = 1원 |
| 잔액 | 사용자가 보유한 포인트의 저장값. 0 허용 |
| 충전 | `amount`를 잔액에 더하는 행위 |
| 환불 [추가] | 사용자가 지정한 `amount`를 자신의 잔액에서 빼는 행위. 실제 돈의 이동은 없다 (→ 1-3) |
| 운영자 충전 / 운영자 차감 [추가] | 관리자가 특정 사용자의 잔액에 `amount`를 더하거나 빼는 행위 |
| 표현 범위 | 금액(잔액·충전액·합계)을 저장·표현할 수 있는 정수 범위 (→ ASM-05) |
| 주문 | 사용자가 만든 주문 품목의 묶음. 합계·상태·결제액·결제 결과를 가진다. 상태를 가짐 (→ 3-2) |
| 주문 품목 | 주문 안의 한 줄. 상품·수량·단가·항목 금액 |
| 단가 | 주문 생성 시점의 상품 가격 사본 (→ ASM-10) |
| 항목 금액 | 단가 × 수량 |
| 합계 | 주문 품목의 항목 금액 합 |
| 결제액 | 확정 시 잔액에서 차감된 금액. 확정 후에만 존재 |
| 결제 결과 | 확정 시 차감이 이루어졌다는 기록 (→ ASM-13) |
| 관리자 | 관리자 API의 요청자. `X-USER-ID` 헤더로 식별된 사용자 중 관리자 권한을 가진 자 (→ CON-03, ASM-26, INV-15) |

### 1-2. 행위자

| 행위자 | 리소스별 권한 |
|---|---|
| 고객(사용자) | 브랜드 상세 조회 · 상품 목록/상세 조회 · 좋아요 등록/취소/내 목록 · 포인트 충전/환불/잔액 조회 · 주문 생성/확정/내 목록/상세 |
| 관리자 | 브랜드 CRUD · 상품 CRUD · 재고 변경 · 전체 주문 목록/상세 · 사용자 포인트 충전/차감 [추가] |

### 1-3. 범위 밖

| 개념 | 이유 |
|---|---|
| 배송 | 원문에 언급 없음 |
| 주문 취소 · 부분 취소 · 환불 · DRAFT 주문 삭제/만료 | 원문에 언급 없음. 확정되지 않은 DRAFT는 그대로 남는다. 설계에서도 고려하지 않는다 |
| 주문 수정(품목 추가·삭제·수량 변경) | 원문에 언급 없음 |
| 쿠폰 · 할인 · 배송비 | 원문에 언급 없음. 결제액 = 합계 (ASM-10) |
| 외부 결제(카드 등) | 원문 "포인트만" |
| 환불의 실제 돈 이동(계좌·카드로 돌려주기) | 외부 결제가 없으므로 환불은 잔액 감소까지만이다 |
| 포인트 이력(충전·사용·환불·운영자 조정 기록) · 내역 조회 | 기능으로 제공하지 않지만 **설계에서 고려한다**. 잔액을 단일 저장값으로만 둘지, 변동을 각각 기록으로 남길지는 설계 결정 |
| 충전금 단위 관리 · 포인트 유효기간(일정 일수 후 소멸) | 기능으로 제공하지 않지만 **설계에서 고려한다**. 충전 건을 단위로 식별하고 건마다 만료 시각을 두는 구조가 나중에 들어올 수 있다는 전제로, 잔액을 "충전 건들의 합"으로 볼 수 있는 여지를 남긴다. 소진 순서(FIFO), 만료 배치, 만료 알림은 그때도 별도 판단 |
| 주문 취소에 따른 포인트 되돌림 | 주문 취소가 범위 밖이므로 함께 제외 |
| 사용자 가입 · 로그인 · 인증(자격 증명 검증) 방식 | 원문에 언급 없음. 사용자는 fixture로 준비하고, 요청자 식별은 `X-USER-ID` 헤더로 한다 (CON-03, ASM-01). 헤더 값이 위조되지 않았다고 믿는다 |
| 관리자 권한의 부여 · 회수 · 관리 | 원문에 언급 없음. 관리자 식별은 CON-03 헤더로 하고 판정 기준은 ASM-26에 둔다. 누가 관리자인지는 fixture로 준비 |
| 브랜드 · 상품 복구(삭제 취소) | 원문에 언급 없음 |
| 상품 목록의 브랜드 필터 | 원문에는 있으나 이번 범위에서 제공하지 않기로 판단. 정렬·페이지만 제공 |
| 상품 키워드 검색 | 원문에 언급 없음 |
| 동시 요청 하에서의 불변식 유지(재고·잔액 동시 차감, 브랜드 삭제와 상품 생성의 경합) | 원문에 언급 없음. 이번 범위에서 다루지 않는다. 설계 문서 OQ-02, OQ-03에 열어둠 |

### 1-4. 가정 / 해석

| ID | 원문의 모호한 지점 | 해석 | 근거 / 영향 |
|---|---|---|---|
| ASM-01 | "요청자로 식별한 사용자" — `X-USER-ID` 헤더(CON-03)가 없거나 값이 잘못됐거나 가리키는 사용자가 없을 때의 처리 불명 | 헤더 값이 가리키는 사용자가 존재할 때만 요청자로 식별된다고 본다. 헤더 누락·값 형식 오류·존재하지 않는 사용자는 모두 공통 실패 케이스 `USER_NOT_FOUND`로 본다. **(설계 결정 DR-01: 셋을 합친다. 헤더는 클라이언트가 아니라 시스템이 넣는 값이라 나눌 실익이 없다. 값의 형식은 사용자 ID = Long. 경로·바디의 ID 형식 오류도 같은 결로 해당 `*_NOT_FOUND`)** | 모든 고객 FR의 공통 사전 조건 |
| ASM-02 | "삭제된 브랜드·상품" — 삭제 후에도 참조·취소가 가능하다는 문장 | 삭제는 브랜드·상품의 **상태**다. 삭제된 대상은 "존재하되 삭제됨"으로 도메인에서 구분 가능해야 한다. 물리/논리 저장 방식은 설계에서 정한다 | 3-2 브랜드·상품 상태, FR-LIKE-02, FR-ADMIN-* 조회 |
| ASM-03 | "유효한 브랜드 정보" — 필드와 유효 조건 불명 | 이름을 필수 필드로 본다. 유효 = 이름이 비어 있지 않고 길이 상한 이내. **(설계 결정 DR-11: 상한 100자, 추가 필드 없음)** | INV-14, FR-ADMIN-BRAND-02/04 |
| ASM-04 | "정한 이름·가격 범위 검증" — 값이 없음 | 이름: 비어 있지 않고 길이 상한 이내. 가격: 0 이상 정수, 표현 범위 이내(0원 상품 허용 — 잔액 0 허용과 같은 결). **(설계 결정 DR-11: 이름 상한 200자, 가격은 ASM-05의 표현 범위)** | INV-13, FR-ADMIN-PRODUCT-02/04. 0원 허용이 뒤집히면 가격 > 0으로 변경 |
| ASM-05 | "표현 범위 초과", "잔액 합산 범위" — 범위 값 없음 | 금액은 설계에서 정하는 정수 타입의 범위 안이어야 한다. 잔액·충전액뿐 아니라 주문 합계에도 같은 범위를 적용한다. **(설계 결정 DR-11: 64비트 부호 있는 정수, 0 ~ 9,223,372,036,854,775,807. 재고·수량은 32비트 정수)** | INV-02, FR-POINT-01, FR-ORDER-01 |
| ASM-06 | "중복 관계 방지" — 이미 있는 좋아요를 다시 등록하면 거절인지 무시인지 불명 | 멱등으로 본다. 이미 있으면 새로 만들지 않고 성공, 없는 관계 취소도 변화 없이 성공 | FR-LIKE-01/02. 뒤집히면 `ALREADY_LIKED` / `LIKE_NOT_FOUND` 실패 케이스 추가 |
| ASM-07 | 삭제된 상품과 좋아요의 관계 | 새 등록 거절(`PRODUCT_NOT_FOUND`), 내 목록에서 제외, 남아 있는 관계의 취소는 허용(원문). 상품 삭제 시 기존 좋아요 관계는 지우지 않는다(파생). 삭제된 상품의 좋아요 수는 관계 수 그대로다 | FR-LIKE-01/02/03, FR-ADMIN-PRODUCT-05 |
| ASM-08 | 상품 목록의 정렬 방식, 동률 보조 기준, 잘못된 입력 | 정렬은 `latest` / `price_asc` / `likes_desc` 중 **정확히 하나**만 적용한다. 서로 조합하지 않는다. 지정하지 않으면 `latest`. `latest` = 생성 시각 내림차순, `price_asc` = 가격 오름차순, `likes_desc` = 좋아요 수 내림차순. 동률 보조 기준은 세 정렬 모두 상품 id 내림차순 하나로 통일한다(다른 정렬 기준을 보조로 끌어오지 않음). 허용 목록 밖 정렬값·정렬값 둘 이상 지정·잘못된 페이지 값은 거절 | FR-PRODUCT-01 |
| ASM-09 | "자신의", "본인의" — 소유자가 아닌 리소스에 접근했을 때 | 거절하며 도메인 이름 `NOT_OWNER`로 구분한다. 존재 자체를 숨길지(없는 대상으로 응답)는 설계에서 재검토 가능 **(설계 결정 DR-18: 노출한다)** | FR-LIKE-03, FR-ORDER-02/04. 뒤집히면 해당 실패 케이스 이름이 `*_NOT_FOUND`로 바뀜 |
| ASM-10 | 주문 품목의 "단가"와 확정 시 "결제액"의 관계 | 단가는 생성 시점 상품 가격의 사본. 확정 시 가격을 다시 조회하지 않으며 결제액 = 생성 시 저장된 합계. 이후 관리자의 가격 수정은 기존 주문에 영향 없음 | INV-06, INV-09, FR-ORDER-01/02, FR-ADMIN-PRODUCT-04 |
| ASM-11 | "중복 상품 품목은 합산하거나 거절" | 합산한다. 같은 상품 품목은 수량을 합쳐 한 품목으로 저장하고, 재고 확인은 합산된 총수량으로 한다 | INV-08, FR-ORDER-01/02. 뒤집히면 `DUPLICATE_ORDER_ITEM` 실패 케이스 추가 |
| ASM-12 | 확정 실패 시 주문 상태 — 원문은 "거절"만 있고 실패 상태 없음 | 주문은 DRAFT를 유지하고 재시도 가능. FAILED 상태는 도입하지 않는다(창작) | 3-2 주문 전이, FR-ORDER-02 |
| ASM-13 | "결제액·결과를 저장" — 결제 결과의 내용 불명 | 확정 성공 시에만 기록되며, 포인트 차감이 이루어졌다는 사실(결제액·확정 시각 등)이다. 구체 필드는 설계 | FR-ORDER-02, FR-ADMIN-ORDER-01/02 |
| ASM-14 | 여러 품목 중 일부만 재고가 부족할 때 | 확정은 전부 또는 전무. 하나라도 실패하면 재고·잔액·상태 어느 것도 바뀌지 않는다 | FR-ORDER-02 |
| ASM-15 | 관리자 목록·상세 조회에 삭제된 대상이 포함되는지 | 포함한다. 원문의 제외 규칙은 "고객 조회·새 주문"에만 걸려 있다. 관리자 응답에는 삭제 여부를 표시한다 | FR-ADMIN-BRAND-01/03, FR-ADMIN-PRODUCT-01/03 |
| ASM-16 | "수정 시 브랜드 유지" | 상품 수정은 이름·가격만 대상이며 브랜드는 입력받지 않는다(5층에서 필드 제외). 따라서 브랜드 변경 실패 케이스는 두지 않는다 | INV-11, FR-ADMIN-PRODUCT-04 |
| ASM-17 | 상품 생성 시 재고 입력 여부 | 생성 시 재고를 함께 입력받으며 0 이상 정수여야 한다 | FR-ADMIN-PRODUCT-02. 뒤집히면 생성 시 재고 0 고정 |
| ASM-18 | 이미 삭제된 대상을 다시 삭제하면 | 거절(`*_NOT_FOUND`). 원문 "삭제된 것은 수정·재고 변경의 대상으로 사용하지 않음"과 같은 결로 본다 | FR-ADMIN-BRAND-05, FR-ADMIN-PRODUCT-05 |
| ASM-19 | 관리자 주문 목록 "구매자별" | 필터가 아니라 출력 형태로 본다. 전체 주문을 구매자 단위로 묶어 반환하며, 구매자 필터는 두지 않는다 | FR-ADMIN-ORDER-01. 뒤집히면 구매자 필터 입력과 `INVALID_BUYER_FILTER` 실패 케이스 추가 |

## 2. 기능 요구사항

공통 규칙:
- 행위자가 **고객**인 모든 FR은 사전 조건 "요청자가 식별된 사용자"를 가진다. 위반 시 결과 상태 "변화 없음", 이름 `USER_NOT_FOUND` (ASM-01). 아래에서는 반복하지 않는다.
- 행위자가 **관리자**인 모든 FR은 사전 조건 "요청자가 관리자로 식별된 사용자"를 가진다. 위반 시 결과 상태 "변화 없음", 이름은 요청자를 식별하지 못하면 `USER_NOT_FOUND`, 식별은 됐지만 관리자가 아니면 `NOT_ADMIN` (ASM-26). 지켜야 할 불변식 INV-15. 아래에서는 반복하지 않는다.
- 행위자가 **관리자**인 모든 쓰기 FR의 결과는 이후 고객 조회 FR의 출력에 즉시 반영된다 (ASM-21).
- "없거나 삭제된 대상의 고객 상세 조회는 없는 대상 오류" — 고객 FR에서 "존재하지 않음"과 "삭제됨"은 같은 실패 이름을 쓰며, 클라이언트가 둘을 구분할 필요는 없다(원문).
- 요구사항이 이름을 주지 않은 요청 형식 오류(바디 파싱 불가, 이름 없는 필드의 누락·타입 오류)는 설계의 범용 검증 실패로 처리한다 (설계 문서 4-4 ER-22).

### 2-1. 브랜드 (고객)

#### FR-BRAND-01 브랜드 상세 조회 — `GET /api/v1/brands/{brandId}`
- 행위자: 고객
- 사전 조건: brandId의 브랜드가 존재하고 삭제되지 않음
- 행위: 고객이 브랜드를 조회하면 브랜드 정보가 반환된다
- 결과: 출력 — 브랜드 정보(고객용 필드)
- 실패 케이스:

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 브랜드가 존재하지 않음 | 변화 없음 | `BRAND_NOT_FOUND` |
  | 브랜드가 삭제됨 | 변화 없음 | `BRAND_NOT_FOUND` |
- 지켜야 할 불변식: 없음

### 2-2. 상품 (고객)

#### FR-PRODUCT-01 상품 목록 조회 — `GET /api/v1/products`
- 행위자: 고객
- 사전 조건: 조회 조건(페이지·정렬)이 유효
- 행위: 고객이 조회 조건으로 상품 목록을 조회하면 조건에 맞는 상품이 반환된다
- 결과: 출력 —
    - 대상: 삭제되지 않은 상품만
    - 각 상품에 브랜드 정보와 좋아요 수 포함 (INV-05). 재고는 포함하지 않는다 (설계 결정 DR-22)
    - 페이지: 페이지 번호·크기로 잘라 반환
    - 정렬: `latest`(기본) / `price_asc` / `likes_desc` 중 하나. 조합 불가. 동률이면 상품 id 내림차순 (ASM-08)
    - 브랜드 필터는 제공하지 않는다 (→ 1-3)
- 실패 케이스:

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 정렬값이 허용 목록 밖이거나 둘 이상 지정 | 변화 없음 | `INVALID_SORT` |
  | 페이지 번호·크기가 음수, 0 크기, 타입 오류 | 변화 없음 | `INVALID_PAGE` |

  두 실패를 클라이언트가 구분할 필요는 없다. 설계에서 하나의 입력 오류로 합쳐도 된다.
- 지켜야 할 불변식: INV-05

#### FR-PRODUCT-02 상품 상세 조회 — `GET /api/v1/products/{productId}`
- 행위자: 고객
- 사전 조건: productId의 상품이 존재하고 삭제되지 않음
- 행위: 고객이 상품을 조회하면 상품 정보가 반환된다
- 결과: 출력 — 상품 정보(고객용 필드) + 브랜드 정보 + 좋아요 수. 재고는 포함하지 않는다 (설계 결정 DR-22)
- 실패 케이스:

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 상품이 존재하지 않음 | 변화 없음 | `PRODUCT_NOT_FOUND` |
  | 상품이 삭제됨 | 변화 없음 | `PRODUCT_NOT_FOUND` |
- 지켜야 할 불변식: INV-05, INV-10

### 2-3. 좋아요 (고객)

#### FR-LIKE-01 좋아요 등록 — `POST /api/v1/products/{productId}/likes`
- 행위자: 고객
- 사전 조건: 상품이 존재하고 삭제되지 않음
- 행위: 사용자가 상품에 좋아요를 등록하면 사용자–상품 관계가 저장된다
- 결과: 상태 변화 — 관계 생성. 이미 존재하면 새로 만들지 않고 성공 (ASM-06). 좋아요 수는 관계에서 조회되므로 별도 갱신 없음 (INV-05)
- 실패 케이스:

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 상품이 존재하지 않음 | 변화 없음 | `PRODUCT_NOT_FOUND` |
  | 상품이 삭제됨 (ASM-07) | 변화 없음 | `PRODUCT_NOT_FOUND` |
- 지켜야 할 불변식: INV-04, INV-05

#### FR-LIKE-02 좋아요 취소 — `DELETE /api/v1/products/{productId}/likes`
- 행위자: 고객
- 사전 조건: 상품이 존재함 (삭제 여부는 묻지 않음 — 원문 "남아 있는 자신의 좋아요 관계는 취소할 수 있게")
- 행위: 사용자가 자신의 좋아요를 취소하면 사용자–상품 관계가 삭제된다
- 결과: 상태 변화 — 관계 삭제. 관계가 없으면 변화 없이 성공 (ASM-06)
- 실패 케이스:

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 상품이 존재하지 않음 | 변화 없음 | `PRODUCT_NOT_FOUND` |
- 지켜야 할 불변식: INV-05

#### FR-LIKE-03 내 좋아요 목록 — `GET /api/v1/users/{userId}/likes`
- 행위자: 고객
- 사전 조건: userId가 요청자와 같음. 페이지 값이 유효
- 행위: 사용자가 자신의 좋아요 목록을 조회하면 좋아요한 상품 목록이 반환된다
- 결과: 출력 — 요청자의 좋아요 관계 중 **상품이 삭제되지 않은 것만** (ASM-07). 각 항목에 상품 정보 포함. 정렬은 좋아요 등록 최신순, 페이지 번호·크기로 잘라 반환 (ASM-20)
- 실패 케이스:

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | userId가 요청자와 다름 (ASM-09) | 변화 없음 | `NOT_OWNER` |
  | 페이지 번호·크기가 음수, 0 크기, 타입 오류 | 변화 없음 | `INVALID_PAGE` |
- 지켜야 할 불변식: INV-05

### 2-4. 포인트 (고객)

#### FR-POINT-01 포인트 충전 — `POST /api/v1/points/charge`
- 행위자: 고객
- 사전 조건: `amount`가 존재하고, 정수 타입이며, 양수이고, 표현 범위 안이며, 잔액 + amount도 표현 범위 안
- 행위: 사용자가 amount를 충전하면 잔액에 더해져 저장된다
- 결과: 상태 변화 — 잔액 = 기존 잔액 + amount. 출력 — 충전 후 잔액
- 실패 케이스 (모두 원문 "기존 값 유지"):

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | amount 누락 | 잔액 유지 | `INVALID_AMOUNT` |
  | amount 타입 오류(정수 아님) | 잔액 유지 | `INVALID_AMOUNT` |
  | amount ≤ 0 | 잔액 유지 | `INVALID_AMOUNT` |
  | amount가 표현 범위 초과 | 잔액 유지 | `INVALID_AMOUNT` |
  | 잔액 + amount가 표현 범위 초과 (ASM-05) | 잔액 유지 | `BALANCE_LIMIT_EXCEEDED` |

  입력 오류 4건은 클라이언트가 구분할 필요 없음. 합산 초과는 입력 자체는 유효하므로 구분한다.
- 지켜야 할 불변식: INV-01, INV-02

#### FR-POINT-02 내 잔액 조회 — `GET /api/v1/points`
- 행위자: 고객
- 사전 조건: (공통만)
- 행위: 사용자가 잔액을 조회하면 저장된 잔액이 반환된다
- 결과: 출력 — 요청자의 잔액
- 실패 케이스: 공통 외 없음
- 지켜야 할 불변식: INV-01

#### FR-POINT-03 [추가] 포인트 환불 — `POST /api/v1/points/refund` (ASM-23)
- 행위자: 고객
- 사전 조건: `amount`가 존재하고, 정수 타입이며, 양수이고, 표현 범위 안이며, 잔액 ≥ amount
- 행위: 사용자가 amount를 환불하면 잔액에서 빠져 저장된다
- 결과: 상태 변화 — 잔액 = 기존 잔액 − amount (ASM-24). 출력 — 환불 후 잔액. 실제 돈의 이동은 없다 (→ 1-3)
- 실패 케이스 (모두 잔액 유지):

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | amount 누락·타입 오류·0 이하·표현 범위 초과 | 잔액 유지 | `INVALID_AMOUNT` |
  | 잔액 < amount | 잔액 유지 | `INSUFFICIENT_POINT` |

  입력 오류와 잔액 부족은 클라이언트가 구분해야 한다(수정할 값이 다름).
- 지켜야 할 불변식: INV-01, INV-02

### 2-5. 주문 (고객)

#### FR-ORDER-01 주문 생성 — `POST /api/v1/orders`
- 행위자: 고객
- 사전 조건: 품목이 1개 이상, 각 품목의 상품이 존재하고 삭제되지 않음, 각 수량이 양의 정수
- 행위: 사용자가 품목 목록으로 주문을 생성하면 DRAFT 주문이 저장된다
- 결과: 상태 변화 —
    - 주문 생성, 상태 DRAFT
    - 품목별로 상품·수량·단가(생성 시점 가격 사본, ASM-10)·항목 금액 저장, 합계 저장
    - 같은 상품 품목은 수량을 합산해 한 품목으로 저장 (ASM-11)
    - 재고·잔액 변화 없음 (원문 "생성 시 차감 없음"). 재고 부족 여부는 생성 시 확인하지 않는다 (원문: 확정 시 거절)
    - 출력 — 생성된 주문
- 실패 케이스 (모두 주문이 생성되지 않음):

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 품목이 없음 | 변화 없음 | `EMPTY_ORDER_ITEMS` |
  | 어느 품목의 상품이 존재하지 않거나 삭제됨 | 변화 없음 | `PRODUCT_NOT_FOUND` |
  | 어느 품목의 수량이 0 이하, 누락, 타입 오류 | 변화 없음 | `INVALID_QUANTITY` |

#### FR-ORDER-02 주문 확정 — `POST /api/v1/orders/{orderId}/confirm`
- 행위자: 고객
- 사전 조건: 주문이 존재하고 요청자의 것이며 DRAFT. 모든 품목의 상품이 존재하고 삭제되지 않음. 품목마다 재고 ≥ 수량(합산된 총수량). 잔액 ≥ 합계
- 행위: 사용자가 자신의 DRAFT 주문을 확정하면 재고와 포인트가 차감되고 주문이 CONFIRMED가 된다
- 결과: 상태 변화 —

    - 요청자 잔액 −= 합계
    - 주문에 결제액(= 합계, ASM-10)과 결제 결과(ASM-13) 저장

  | 주문이 DRAFT가 아님 | CONFIRMED 유지 | `ORDER_NOT_DRAFT` |

- 결과: 출력 — 구매자·품목·수량·단가·항목 금액·합계·상태·결제액·결제 결과
- 실패 케이스:

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 주문이 존재하지 않음 | 변화 없음 | `ORDER_NOT_FOUND` |
- 지켜야 할 불변식: 없음

### 2-9. 포인트 (관리자) [추가]

#### FR-ADMIN-POINT-01 [추가] 사용자 포인트 충전 — `POST /api-admin/v1/points/charge` (ASM-23, 설계 피드백 DR-20)
- 행위자: 관리자
- 사전 조건: 바디 `userId`의 사용자가 존재. `amount`가 존재하고, 정수 타입이며, 양수이고, 표현 범위 안이며, 잔액 + amount도 표현 범위 안
- 행위: 관리자가 특정 사용자에게 amount를 충전하면 그 사용자의 잔액에 더해져 저장된다
- 결과: 상태 변화 — 대상 사용자의 잔액 = 기존 잔액 + amount. 사유는 기록하지 않는다 (ASM-25). 출력 — 충전 후 잔액
- 실패 케이스 (모두 잔액 유지):

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 사용자가 존재하지 않음 | 변화 없음 | `USER_NOT_FOUND` |
  | amount 누락·타입 오류·0 이하·표현 범위 초과 | 잔액 유지 | `INVALID_AMOUNT` |
  | 잔액 + amount가 표현 범위 초과 (ASM-05) | 잔액 유지 | `BALANCE_LIMIT_EXCEEDED` |

  여기서 `USER_NOT_FOUND`는 바디 `userId`(대상 사용자)에 대한 것이다. 요청자(관리자) 식별 실패는 공통 규칙에 따르며 이름이 같으므로, 둘은 메시지로 구분한다(설계). `userId` 자체의 누락·타입 오류는 2장 공통 규칙의 범용 검증 실패.
- 지켜야 할 불변식: INV-01, INV-02

#### FR-ADMIN-POINT-02 [추가] 사용자 포인트 차감 — `POST /api-admin/v1/points/deduct` (ASM-23, 설계 피드백 DR-20)
- 행위자: 관리자
- 사전 조건: 바디 `userId`의 사용자가 존재. `amount`가 존재하고, 정수 타입이며, 양수이고, 표현 범위 안이며, 대상 잔액 ≥ amount
- 행위: 관리자가 특정 사용자에게서 amount를 차감하면 그 사용자의 잔액에서 빠져 저장된다
- 결과: 상태 변화 — 대상 사용자의 잔액 = 기존 잔액 − amount. 사유는 기록하지 않는다 (ASM-25). 출력 — 차감 후 잔액
- 실패 케이스 (모두 잔액 유지):

  | 조건 | 결과 상태 | 이름 |
      |---|---|---|
  | 사용자가 존재하지 않음 | 변화 없음 | `USER_NOT_FOUND` |
  | amount 누락·타입 오류·0 이하·표현 범위 초과 | 잔액 유지 | `INVALID_AMOUNT` |
  | 잔액 < amount | 잔액 유지 | `INSUFFICIENT_POINT` |

  잔액을 0까지만 내릴 수 있다. 음수로 만드는 차감은 INV-01 위반이라 허용하지 않는다. `USER_NOT_FOUND`의 의미는 FR-ADMIN-POINT-01과 같다.
- 지켜야 할 불변식: INV-01, INV-02

## 3. 도메인 규칙 / 불변식

### 3-1. 불변식

| ID | 불변식 | 대상 |
|---|---|---|
| INV-01 | 잔액 ≥ 0 | 잔액 |
| INV-02 | 잔액은 표현 범위 안의 정수 | 잔액, 표현 범위 |
| INV-03 | 재고 ≥ 0 | 재고 |
| INV-04 | 같은 사용자–상품 쌍의 좋아요는 최대 하나 | 좋아요 |
| INV-05 | 상품의 좋아요 수 = 그 상품에 대한 좋아요 관계의 개수 | 좋아요 수, 좋아요, 상품 |
| INV-06 | 합계 = Σ 항목 금액, 항목 금액 = 단가 × 수량 | 주문, 주문 품목, 단가, 항목 금액, 합계 |
| INV-07 | 주문 품목의 수량 > 0 | 주문 품목 |
| INV-08 | 한 주문 안에 같은 상품의 주문 품목은 하나 (→ ASM-11) | 주문, 주문 품목 |
| INV-09 | CONFIRMED 주문의 결제액 = 합계 (→ ASM-10) | 주문, 결제액, 합계 |
| INV-10 | 삭제되지 않은 상품은 삭제된 브랜드에 속하지 않는다 | 상품, 브랜드 |
| INV-11 | 상품은 정확히 하나의 브랜드에 속하며 그 브랜드는 바뀌지 않는다 | 상품, 브랜드 |
| INV-12 | 주문은 주문 품목을 1개 이상 가진다 | 주문, 주문 품목 |
| INV-13 | 상품의 이름·가격은 정한 범위 안 (→ ASM-04) | 상품, 가격 |
| INV-14 | 브랜드 정보는 유효 범위 안 (→ ASM-03) | 브랜드 |
| INV-15 | 관리자는 관리자 권한을 가진 사용자다 (관리자 ⊂ 사용자, → ASM-26) (설계 피드백 DR-06) | 관리자, 사용자 |

메모:
- "차감된 포인트 = 결제액", "차감된 재고 = 수량"은 확정 직후에만 말할 수 있는 사후조건이므로 FR-ORDER-02 결과 필드에 두고 여기 두지 않는다.
- INV-10은 FR-ADMIN-BRAND-05의 삭제 조건과 INV-11(브랜드 불변)의 합으로 유지된다. 이 덕분에 고객 상품 조회(FR-PRODUCT-01/02)가 삭제된 브랜드의 상품을 걸러내는 처리를 따로 하지 않아도 된다. 단, 동시 요청 사이의 경합은 범위 밖이다 (→ 1-3).
- INV-15는 설계에서 사용자 애그리거트의 근거로 필요해 올라왔다(DR-06). ASM-26이 이미 말하던 규칙을 불변식으로 승격한 것이다.

### 3-2. 상태 전이

```
주문 상태
  DRAFT       생성됨. 재고·잔액 미차감. 결제액·결제 결과 없음. FR-ORDER-02 가능.
  CONFIRMED   확정됨. 재고·잔액 차감 완료. 결제액·결제 결과 저장됨. 더 이상 전이 없음.

전이
  (FR-ORDER-01 성공) ────────────────────────────────────▶ DRAFT
  DRAFT ──(FR-ORDER-02 성공)────────────────────────────▶ CONFIRMED
  DRAFT ──(FR-ORDER-02 실패: PRODUCT_NOT_FOUND)──────────▶ DRAFT (유지)          ← ASM-12
  DRAFT ──(FR-ORDER-02 실패: INSUFFICIENT_STOCK)─────────▶ DRAFT (유지, 재시도 가능) ← ASM-12
  DRAFT ──(FR-ORDER-02 실패: INSUFFICIENT_POINT)─────────▶ DRAFT (유지, 재시도 가능) ← ASM-12
  CONFIRMED ──(FR-ORDER-02 실패: ORDER_NOT_DRAFT)────────▶ CONFIRMED (유지)
```

```
브랜드 상태
  ACTIVE      삭제되지 않음. 고객 조회 대상. 수정·상품 연결 가능.
  DELETED     삭제됨. 고객 조회·새 상품 생성에서 제외. 수정 불가. 더 이상 전이 없음.

전이
  (FR-ADMIN-BRAND-02 성공) ─────────────────────────────▶ ACTIVE
  ACTIVE ──(FR-ADMIN-BRAND-05 성공)──────────────────────▶ DELETED
  ACTIVE ──(FR-ADMIN-BRAND-05 실패: BRAND_HAS_PRODUCTS)──▶ ACTIVE (유지)
```

```
상품 상태
  ACTIVE      삭제되지 않음. 고객 조회·새 주문·새 좋아요 대상. 수정·재고 변경 가능.
  DELETED     삭제됨. 고객 조회·새 주문·새 좋아요·내 좋아요 목록에서 제외. 수정·재고 변경 불가.
              기존 좋아요 관계·주문 품목의 참조는 유지. 더 이상 전이 없음.

전이
  (FR-ADMIN-PRODUCT-02 성공) ───────────────────────────▶ ACTIVE
  ACTIVE ──(FR-ADMIN-PRODUCT-05 성공)────────────────────▶ DELETED
```

규칙 메모:
- ACTIVE / DELETED는 원문의 "삭제되지 않음 / 삭제됨"에 붙인 이름표다. 저장 방식(플래그, 별도 테이블 등)은 기존 참조와 저장된 주문 정보가 보존되는 범위에서 설계에서 정한다 (ASM-02). (설계: 공통 컬럼 `deleted_at`의 NULL 여부, DR-16)
- 주문의 FAILED 상태, 브랜드·상품의 복구 전이는 원문에 없으므로 그리지 않는다. 그림에 없는 전이는 금지된 전이다.
- 좋아요·사용자·포인트는 상태가 하나이므로 올리지 않는다. 사용자의 관리자 권한 여부(ASM-26)도 이 문서 범위에서는 바뀌지 않으므로 상태로 올리지 않는다.

## 5. 정합성 검사 결과

설계 피드백 반영 후 재검사.

- 불변식 대상·상태 전이 주어 중 용어집에 없는 단어: 없음 (ACTIVE/DELETED는 3-2에서 정의. INV-15의 관리자·사용자는 용어집에 있음)
- 용어집에 있는데 어느 FR·INV·3-2에도 안 나오는 단어: 없음 (구매자 → FR-ADMIN-ORDER-01/02, 결제 결과 → FR-ORDER-02·FR-ADMIN-ORDER, 항목 금액 → INV-06, 표현 범위 → INV-02, 환불 → FR-POINT-03, 운영자 충전/차감 → FR-ADMIN-POINT-01/02, 관리자 → INV-15)
- FR 행위자가 1-2에 없음: 없음 (고객·관리자만 사용)
- FR의 "지켜야 할 불변식"이 3-1에 없음: 없음 (INV-15는 관리자 FR 공통 규칙에서 참조)
- 3-2 전이에 트리거 FR 없음: 없음
- FR 실패 케이스의 결과 상태가 3-2에 없거나 전이가 그림에 없음: 없음 (유지 전이는 모두 그림에 있음)
- 원문에 없는 값·해석이 1-4 없이 들어간 곳: 없음. 설계가 정한 값(길이 상한, 표현 범위, 페이지 기본값·상한, 묶음 순서)은 ASM-03·04·05·20에 `(설계 결정 DR-xx)`로 표시했다. 헤더 이름 `X-USER-ID`는 원문(과제 조건)이므로 CON-03에 두었고, 값의 형식(Long)은 ASM-01에 설계 결정으로 표시했다. 아래는 파생으로 본 것(가정 아님):
    - 사전 조건 위반에서 나온 실패 케이스 전부 (`*_NOT_FOUND`, `INVALID_*`, `INSUFFICIENT_*`, `ORDER_NOT_DRAFT`, `BRAND_HAS_PRODUCTS`, `EMPTY_ORDER_ITEMS`, `NOT_ADMIN`)
    - 주문 생성 시 재고를 확인하지 않는 것 (원문이 재고 부족 거절을 확정에만 붙임)
    - 상품 삭제 시 기존 좋아요 관계를 지우지 않는 것 (원문 "남아 있는 관계 취소 가능"의 전제)
- 관리자 FR의 공통 실패 케이스(`USER_NOT_FOUND` / `NOT_ADMIN`)는 2장 공통 규칙에만 두고 각 FR 표에는 반복하지 않았다. 고객 FR의 `USER_NOT_FOUND`와 같은 방식이다.
- [추가] 기능(환불, 운영자 충전·차감)은 원문 밖이지만 용어집에 새 단어를 셋 넣었을 뿐 새 불변식·상태는 만들지 않았다. 잔액 규칙(INV-01, INV-02)만 그대로 적용된다.
- 설계 피드백으로 바뀐 곳: 용어집 구매자(DR-09), ASM-01(DR-01), ASM-03·04·05·20(DR-11·19), ASM-23·FR-ADMIN-POINT-01/02 경로(DR-20), INV-15(DR-06), CON-04(DR-01·16), 1-3 동시성 범위 밖(OQ-02·03), FR-PRODUCT-01/02 출력에 재고 미포함 명시(DR-22). 새 실패 케이스 이름은 추가되지 않았다.

## 6. 뒤집힐 가능성이 큰 가정

설계 착수 전에 확인하면 좋은 순서:

1. ASM-06 좋아요 멱등 vs 거절 — 테스트 시나리오 개수가 달라진다
2. ASM-11 중복 품목 합산 vs 거절 — 요청 검증 위치가 달라진다
3. ASM-09 `NOT_OWNER` 노출 vs `NOT_FOUND`로 숨김 — 5층 에러 규약에 직접 영향 (설계 결정 DR-18: 노출)
4. ASM-26 관리자 = 권한을 가진 사용자 vs 사용자와 별개의 대상 — 실패 케이스 이름, 용어집 "관리자" 정의, INV-15, fixture 구성이 달라진다
5. ~~ASM-01 헤더 누락·형식 오류·없는 사용자를 하나로 합칠지~~ — 설계 결정 DR-01로 닫힘(합친다. 헤더는 시스템이 넣는 값)
6. ASM-04 가격 0 허용 여부
7. ASM-15 관리자 조회에 삭제 포함 여부 — 관리자 응답 필드 설계에 영향
8. ASM-25 운영자 충전·차감 사유 미기록 — 사유가 필요해지는 순간 포인트 이력이 용어로 들어오고, 1-3의 "설계 고려" 항목 둘(이력, 충전금 단위·유효기간)이 함께 기능으로 올라온다
9. 동시성 비기능 추가 여부 — 추가되면 설계 문서 3-6에 잠금 방식이 들어오고 DR-04·OQ-02·OQ-03이 다시 열린다
