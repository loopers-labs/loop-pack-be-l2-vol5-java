# 2주차 커머스 API ADR

이 문서는 [요구사항 문서](./requirements.md)를 기반으로 구현 과정에서 내린 주요 의사결정을 간략히 모은 기록이다.
각 결정에서 검토한 대안과 비용, 선택 이유와 문제 대응은 [상세 의사결정 기록](./decisions.md)에 정리했다.

## ADR-001. 브랜드와 상품은 논리 삭제한다

- **결정**: Brand와 Product에 삭제 상태를 두고 고객 조회와 새 주문에서 제외한다.
- **이유**: 삭제 이후에도 기존 좋아요와 주문의 참조 및 주문 당시 정보가 유지되어야 한다. (`R-ADMIN-12`~`R-ADMIN-14`, `R-LIKE-08`)
- **재검토 조건**: 삭제 데이터를 실제로 제거하거나 삭제한 이름의 재사용을 금지해야 할 때

## ADR-002. 오류 코드는 HTTP를 모르는 단일 enum으로 관리한다

- **결정**: `CoreException`은 `ErrorCode`를 가지며, HTTP 상태는 interfaces의 `ErrorStatus`가 결정한다.
- **이유**: domain과 application을 HTTP에서 분리하면서 규칙별 오류 코드를 API 계약과 일치시킬 수 있다.
- **재검토 조건**: 오류 코드가 크게 늘어 기능별 파일 분리가 필요할 때

## ADR-003. 0 이하의 재고 차감은 내부 오류로 거절한다

- **결정**: Stock에 0 이하의 차감이 요청되면 `INTERNAL_ERROR`로 거절하고 재고를 유지한다.
- **이유**: 정상적인 주문 수량은 항상 양수이므로 이 호출은 사용자 입력 오류가 아니라 내부 계약 위반이다. (`R-ORDER-06`, `R-ORDER-11`)
- **재검토 조건**: 주문 확정 외에 사용자가 직접 재고를 차감하는 기능이 생길 때

## ADR-004. 주문 확정은 먼저 확인한 실패 조건의 오류를 반환한다

- **결정**: 조건을 확인한 순서대로 첫 오류를 반환하되, 주문 소유권은 항상 가장 먼저 확인한다.
- **이유**: 오류 응답은 하나만 담으며, 소유권을 먼저 확인해야 다른 사용자의 주문 상태가 노출되지 않는다. (`P-ACCESS-02`, `P-ORDER-04`)
- **재검토 조건**: 여러 오류를 함께 반환하거나 특정 오류의 우선순위가 요구될 때

## ADR-006. Repository에는 DIP를 적용하고 domain 객체를 JPA Entity로 사용한다

- **결정**: domain에 Repository 포트를 두고 infrastructure의 JPA 어댑터가 구현하며, domain 객체를 JPA Entity로 함께 사용한다.
- **이유**: application은 저장 기술에서 분리하되, 이번 범위에서는 별도 영속 모델과 변환 코드의 중복을 피한다.
- **재검토 조건**: JPA가 도메인 규칙 표현을 방해하거나 영속 모델과 도메인 모델의 변화 속도가 달라질 때

## ADR-007. 주문 조회 시 품목을 함께 로딩한다

- **결정**: `Order.items`를 EAGER로 매핑하고 목록 조회에서는 batch fetch를 사용한다.
- **이유**: 상세 응답은 품목을 포함하고 요약 응답도 품목 수를 계산한다. OSIV가 꺼져 있어 현재 구조에서 지연 로딩은 응답 변환 중 실패한다. (`R-ORDER-02`, `R-ORDER-14`)
- **재검토 조건**: 품목 컬렉션에 접근하지 않는 요약 조회를 만들거나 품목 조회 비용이 문제가 될 때

## ADR-008. Stock은 VO로 둔다

- **결정**: Stock을 Product가 소유한 VO로 두고 재고 변경은 Product를 통해서만 수행한다.
- **이유**: 재고는 항상 상품의 재고로 다뤄지며 별도 식별이나 추적 요구가 없다. (`R-ORDER-07`, `R-ORDER-08`, `R-ADMIN-08`)
- **재검토 조건**: 창고별 재고나 재고 변경 이력을 상품과 별도로 추적할 때

## ADR-009. Point는 VO로 둔다

- **결정**: Point를 User가 소유한 VO로 두고 충전과 결제는 User를 통해서만 수행한다.
- **이유**: 포인트는 항상 사용자의 잔액으로 다뤄지며 별도 식별이나 추적 요구가 없다. (`R-POINT-01`, `R-POINT-02`, `R-ORDER-11`)
- **재검토 조건**: 충전·사용 이력을 남기거나 한 사용자가 여러 포인트를 가져야 할 때

## ADR-010. OrderItem은 VO로 둔다

- **결정**: OrderItem을 Order가 소유한 VO로 두고 수량 변경 시 새 값으로 교체한다.
- **이유**: 한 주문에는 상품마다 품목이 하나이며 품목별 상태나 독립적인 추적 요구가 없다. (`R-ORDER-15`, `P-ORDER-02`, `P-ORDER-05`)
- **재검토 조건**: 품목별 배송·취소·환불·리뷰 또는 동일 상품의 옵션별 품목이 필요할 때

## ADR-011. PaymentResult는 VO로 둔다

- **결정**: PaymentResult를 Order가 소유한 VO로 두고 주문 확정 시 한 번 생성한다.
- **이유**: 현재 결제는 내부 포인트로만 처리하며 성공 결과의 금액과 시점만 기록하고, 별도 상태나 이력을 추적하지 않는다. (`R-ORDER-11`, `R-ORDER-12`, `P-ORDER-06`)
- **재검토 조건**: 외부 결제 연동, 결제 실패·재시도, 취소·환불 또는 복수 결제 수단이 생길 때
