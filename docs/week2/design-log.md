## 1. AI와 설계 다듬기 기록

초안을 만든 뒤 책임 중복·취약한 의존을 묻고, AI가 낸 대안에 반례를 대입한 결과를 남긴다.

| # | 던진 질문 | AI 지적·대안 | 대입한 반례 | 판단 (채택 / 수정 / 거절) | 이유 |
|---|---|---|---|---|---|
| 1 | starter `ExampleModel`처럼 도메인이 `CoreException(ErrorType)`을 던져야 하나? 도메인이 HTTP를 몰랐으면 한다 | `ErrorType`이 `HttpStatus`를 가지므로 도메인이 전송 계층 결정을 내린다. HTTP를 모르는 `DomainException(DomainErrorType)`을 두고 `ApiControllerAdvice`에서 400/404/409로 바꾸자 | 같은 도메인을 배치·이벤트에서 쓰면 HTTP 타입을 끌고 가는가? 도메인 테스트가 상태 코드를 검증해야 하는가? | 채택 | 도메인 규칙과 전송 방식은 바뀌는 이유가 다르다. ArchUnit `domainDoesNotKnowHttp`로 지킨다(결정 4) |
| 2 | 발제.md의 `Stock`·`PointBalance` 같은 값 객체가 꼭 필요한가? | 예시일 뿐 도입 요구가 아니다. 엔티티가 자기 규칙을 지키는 구조로 시작하고 도입 조건을 남기자 | 같은 검증이 여러 엔티티에 반복되는가? 지금은 재고는 `Product`, 잔액은 `User`에만 있다 | 채택 | 단순한 구조에서 시작하고, 반복·비대화가 생기면 분리한다(T-7, 3-3 도입 조건) |
| 3 | 좋아요 취소의 삭제 방식이 정해지지 않았다 | `BaseEntity.delete()`의 논리 삭제를 쓰면 (`userId`, `productId`) 유일 제약 때문에 다시 좋아요할 수 없다 | 좋아요 → 취소 → 다시 좋아요 | 수정 | 논리 삭제를 버리고 물리 삭제로 정했다. 취소된 관계는 유지할 필요가 없다(P-8) |
| 4 | 결정 1(논리 삭제)의 이유인 "과거 주문 조회"가 계약에서 실현되는가? | 주문 품목에 상품 ID만 있어 삭제 후 상품명을 볼 수 없다. `OrderItem`에 상품명을 저장하거나 삭제된 상품도 조회하자 | 주문 뒤 상품명이 바뀌면 과거 주문에 어떤 이름이 보이는가? | 수정 | 상품명 저장은 거절하고, 주문 내역 조회만 삭제된 상품을 포함해 현재 상품명을 보여준다. 이름이 바뀌어 보이는 것은 감수한다(T-5, DEL-003) |
| 5 | 품목에 삭제된 상품이 있는 주문 확정을 404로 응답해도 되는가? | 경로의 주문은 존재하므로 404는 "주문이 없다"로 읽힌다. 확정할 수 없는 상태이므로 409가 7-0 분류에 맞다 | DRAFT 생성 → 상품 삭제 → 확정 | 채택 | 요청 대상은 있지만 지금 상태로는 처리할 수 없다(P-10) |
| 6 | 고객·관리자를 `User`의 권한 필드로 나눌까, 추상 클래스 상속으로 나눌까? | 관리자에게만 있는 데이터가 없다. 관리자는 엔티티로 두지 않고 요청 권한(`ROLE_ADMIN`)으로 구분하자 | 관리자 로그인이 없으면 관리자 API를 어떻게 호출·테스트하는가? | 채택 | 4절 지원 설정을 연결하고 MockMvc에서 요청마다 관리자 권한을 붙여 실행한다(P-9, T-6) |
| 7 | 전체 설계 검토 | 같은 주문 동시 확정 시 재고·잔액 이중 차감, 같은 재고 동시 차감 시 갱신 손실 등 동시성 문제가 다뤄지지 않았다 | 같은 DRAFT 주문에 확정 요청 두 개가 동시에 들어오면? | 거절 (범위 밖) | 원문 3절이 동시성을 요구하지 않는다. 막지 않는 대신 위험과 되돌릴 조건을 명시했다(T-4) |
| 8 | 상품 목록을 상품 조회 / 좋아요 수 조회 / 브랜드 조회로 나누는 게 낫지 않나? | 좋아요 수를 나중에 붙이면 페이지를 자르기 전에 `likes_desc`로 정렬할 수 없다 | `likes_desc` 2페이지 요청 | 거절 (현재 결정 유지) | 정렬·페이지·집계는 한 쿼리에서, 브랜드는 페이지 단위로 한 번 조회해 조합한다(결정 2) |

## 2. 구현하며 바뀐 판단

| 날짜 | 바뀐 항목 (설계 문서 절·ID) | 이전 판단 | 바뀐 판단 | 계기 |
|---|---|---|---|---|
| 2026-09-18 | 7-3 `GET /api-admin/v1/brands`, 7-0 공통 입력 형식 | 관리자 브랜드 목록의 정렬 기준이 없었다. 관리자 상품·주문, 내 주문 목록은 "최신순"이라고만 적었다 | 정렬을 받지 않는 목록은 모두 등록 시각 내림차순, 같으면 ID 내림차순으로 고정한다 | 관리자 브랜드 목록을 구현하며 순서를 정해야 했다. 같은 시각에 등록된 행이 페이지 경계에서 중복되거나 빠지지 않도록 ID를 보조 기준으로 둔다(P-2와 같은 이유) |
| 2026-09-18 | 3-3 "브랜드 삭제 가능 여부 판단", DEL-001 | application이 연결된 미삭제 상품을 확인한 뒤 브랜드가 삭제 상태로 바뀐다고만 적었다. 첫 구현은 브랜드 존재 확인 → 상품 확인 → 삭제(내부에서 브랜드 재조회)로 브랜드를 두 번 조회했다 | 미삭제 상품 확인(409)을 먼저 하고, 삭제 단계에서 브랜드를 한 번만 조회(404)한다 | 리팩토링에서 중복 조회를 발견했다. 미삭제 상품은 삭제되지 않은 브랜드에만 연결되므로 순서를 바꿔도 없거나 삭제된 브랜드가 409를 받지 않아 응답 계약이 바뀌지 않는다 |
| 2026-09-18 | 4절 대표 흐름(확정), 결정 3 | 상품 조회 → 단가 갱신 → 재고 차감 → 잔액 차감 → 마지막에 `Order.confirm`으로 상태 변경 | `Order.confirm`(DRAFT 확인·가격 확인·단가 갱신·결제액 기록)을 먼저 호출하고 재고·잔액을 차감한다. 전체는 `OrderFacade` 한 트랜잭션 | 구현 중, 이미 확정된 주문을 다시 확정하면 재고 부족 등 다른 사유로 거절될 수 있음을 발견. 상태 확인을 먼저 해야 재확정이 항상 "DRAFT 아님"으로 거절된다. 뒤 단계 실패는 트랜잭션이 되돌리므로 순서를 바꿔도 부분 반영이 없다 |
| 2026-09-18 | 3-3 "좋아요 중복 방지", LIK-001 책임 위치 | application(`LikeFacade`)이 기존 관계를 확인 | 도메인 `LikeService`가 기존 관계를 확인하고, DB 유일 제약이 마지막으로 막는다 | 4절 점검에서 구현(`LikeService.like`)과 문서가 다른 것을 발견해 문서를 구현에 맞췄다. 이 위치를 유지하는 이유: 기존 관계 확인과 저장은 좋아요 한 도메인(한 repository)만 다루고 한 트랜잭션 안에서 함께 일어나야 한다. Facade(`LikeFacade`)에는 상품 삭제 여부·사용자 존재처럼 다른 도메인이 필요한 확인만 둔다 |
| 2026-09-18 | 7-0 요청자 구분·오류 표, 범위, 1절 | 요청자 식별과 관리자 접근 제한은 "4절에서 정한다"며 계약에서 제외 | `X-USER-ID` 헤더로 식별, 누락 400·없는 사용자 404를 모든 고객 API 공통 오류로 둔다. 관리자 경로는 4절 지원 설정(`AdminBoundaryConfig`)을 따른다 | 4절 점검에서 헤더 누락이 500, 좋아요 API가 없는 사용자를 거절하지 않는 문제를 발견. 누락은 7-0의 "필수 값 누락 = 입력 오류" 분류를 따라 새 `ErrorType` 없이 400으로 정했다 |

## 3. 대표 TDD 사례: ORD-003 주문 확정

규칙: **본인의 DRAFT 주문만 확정할 수 있고, 이미 확정된 주문을 다시 확정해도 재고·잔액이 다시 차감되지 않는다.**
고른 이유: 테스트를 쓰는 과정에서 설계 문서 4절의 호출 순서가 바뀌었다. 테스트가 구현만 확인한 것이 아니라 설계 판단을 바꾼 사례다.

| 단계 | 한 일 | 결과 |
|---|---|---|
| Red | `OrderTest`에 "CONFIRMED 주문 재확정 → `CONFLICT`, 결제 정보 유지", "품목 상품 가격을 확인할 수 없으면(삭제됨) → `CONFLICT`, DRAFT 유지"를 작성. 컴파일용 빈 뼈대(`Order`·`OrderItem`·`User`)만 두고 실행 | 도메인 테스트 25건 모두 런타임 실패 |
| 설계 변경 | 재확정 테스트를 쓰다가 4절 원래 순서(재고 차감 → 잔액 차감 → 마지막에 `Order.confirm`)에서는 이미 확정된 주문이 재고·잔액 부족 같은 **다른 사유로 먼저 거절**될 수 있음을 발견 | 상태 확인을 가장 먼저 하도록 순서를 바꿈(2절 이력) |
| Green | `Order.confirm(Map<Long, Long> currentPrices)`가 DRAFT 확인 → 품목 가격 존재 확인(없으면 409) → 단가·합계 갱신 → 결제액 기록·CONFIRMED를 한 번에 수행. `OrderFacade.confirm`은 `@Transactional` 안에서 이를 **먼저** 호출한 뒤 재고·잔액을 차감 | 도메인 25건 통과. E2E `returnsConflict_whenOrderIsAlreadyConfirmed`(잔액 13,000·재고 3 유지), 잔액 부족 시 재고 롤백 테스트 통과 |
| Refactor | Facade 세 곳에 반복된 품목 상품 ID 추출을 `Order.getProductIds()`로 옮김. 품목 입력 누락 검증을 요청 변환 단계로 이동(동작 고정 E2E를 먼저 추가) | 전체 `check` 128건 통과(당시) |
