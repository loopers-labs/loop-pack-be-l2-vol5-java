# ADR-0001 · 주간 구매 랭킹의 입력 고정, 분산 집계와 공개

채택 · 2026-11-20

한 상품의 구매가 여러 주문 구간에 걸쳐도 최종 점수는 그 주의 구매 수량 합과 같아야 한다. 서버가 바뀌거나 청크를 재시도하는 동안에도 고객은 마지막으로 검산을 마친 랭킹을 조회해야 한다.

### 주간 실행은 인스턴스별 스케줄러가 시작한다

C04에서 선택하고 C06에서 구현한 방식은 주문 이벤트를 받으면 주간 실행 요청을 DB에 남기고 별도 실행자가 Job을 시작하는 구조였다. 기준 시각 뒤 주문이 없으면 빈 주차의 공개도 늦어졌다. 현재 Kafka 소비자는 구매 활동을 적재하고, 각 Batch 인스턴스의 스케줄러는 마감된 주차를 찾아 같은 주차·revision의 계획 하나를 공유한다. 각 인스턴스가 담당 주문번호 구간의 Job을 시작하면 JVM 안에서는 Spring Batch Local Partitioning으로 상품을 나눠 계산한다. 이 방식은 빈 주와 중단 중 놓친 주를 처리하는 대신 담당 서버의 생존과 실행권을 DB에서 관리해야 한다. 실행 중인 구간을 인수할 때는 이전 JVM의 종료와 저장된 체크포인트를 확인한다.

### 모든 주문 구간이 한 시점의 구매를 읽는다

구간마다 입력을 고정하면 나중에 시작한 서버만 뒤늦게 도착한 주문을 포함할 수 있다. 주차·revision마다 MySQL `READ COMMITTED`의 단일 `INSERT … SELECT`로 구매를 한 시점에 복사하고, 사본의 주문 경계·건수·체크섬을 같은 트랜잭션에 저장한다. 이 SQL은 구매 원본 행을 잠그지 않고 읽으며 사본에 삽입하는 행에는 배타 잠금을 건다. Kafka 소비자는 주문을 적재할 때 배치와 공통 마감 행을 잠글 필요가 없다. [MySQL 문장별 잠금](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)

대안은 주문의 모든 품목에 같은 마감 번호를 붙이고, 각 서버가 닫힌 번호까지 병렬로 복사하는 방식이다. 닫힌 번호의 구매 행을 그대로 보존하면 재시작해도 같은 입력을 재현할 수 있다. 모든 구매 적재 트랜잭션은 공통 마감 행의 공유 잠금을 커밋까지 유지해야 한다. 공유 잠금끼리는 공존하지만 번호를 15에서 16으로 바꾸려면 배타 잠금이 필요하다. 느린 적재 한 건이 전환을 늦출 수 있고, 전환 중에는 새 적재도 기다릴 수 있다. 매 주문의 조율 비용을 피하기 위해 배치가 주간 복사를 마친 뒤 계산을 시작하기로 했다. 실제 두 JVM 시험에서 고정 뒤 양쪽 구간에 도착한 주문 두 건은 한 구간이 재시작해도 현재 랭킹에서 제외됐고, 다음 명시적 revision에 각각 한 번 들어갔다. [늦은 구매 검증](verification.md#두-jvm에서-고정-후-도착한-실제-구매)

### 구간별 절대 부분합과 읽기 위치를 함께 커밋한다

상품의 최종 점수 한 행에 두 구간이 쓰면 뒤의 값이 앞의 값을 덮는다. 수량을 매번 더하면 같은 청크의 재전달로 점수가 늘어난다. 각 worker는 고정 입력에서 자기 구간의 상품별 수량 합을 구해 `(snapshotId, 주문 구간, productId)`에 저장한다. 같은 키·같은 값은 한 번만 반영하고, 다른 값이면 최초 값을 보존하고 충돌을 기록한다. 부분합과 reader 체크포인트를 한 청크에서 함께 커밋하므로 같은 JobInstance는 마지막 커밋 다음 상품부터 재개한다. 두 JVM에서 2점과 3점을 쓰고 3점을 재전달해도 최종 점수는 5점이었다. 상품 7·8 커밋 뒤 9 처리 직전에 실패한 실행은 9만 다시 처리했다. [점수와 재시작 검증](verification.md)

512개 상품이 두 주문 구간에 모두 등장한 실험에서 1 JVM × 4 workers는 부분 점수 512행, 2 JVM × 2 workers는 1,024행을 썼다. 공개 시간 중앙값 차이 1.083초 중 0.987초가 첫 worker 시작부터 마지막 worker 종료까지의 구간에서 관측됐다. 공통 스냅샷을 유지하면서 서버 간 계산을 상품 ID로 나누면 같은 상품의 부분합을 여러 서버가 쓰는 일을 줄일 수 있다. 이 분할은 아직 구현하지 않았다. 상품 ID 분할이 공개 시간을 줄이는지, 스냅샷 생성이 병목인지는 별도 측정이 필요하다. [성능 측정](benchmark.md)

### 검산한 완성본으로만 주간 공개 포인터를 전환한다

전체 합계만 확인하면 구간별 정답 2·3이 1·4로 잘못 저장돼도 통과한다. 계획한 모든 구간이 완료되고 충돌이 없는지 확인한 뒤, 구간별 부분합과 상품별 최종 점수를 고정 입력에서 구한 수량에 대조한다. 검산 비용과 같은 주차의 공개 잠금 대기를 감수하고, 점수 내림차순·상품 ID 오름차순으로 만든 순위와 완성 기록, 공개 포인터를 한 트랜잭션에 확정한다. 포인터의 revision을 잠금 안에서 비교하므로 이전 계산이 늦게 끝나도 공개본이 역행하지 않는다. 1·4를 주입한 시험에서는 공개가 차단됐고, 새 구간을 계산하는 동안 API는 이전 완성본을 반환했다. [공개 검증](verification.md#같은-상품의-부분-점수)
