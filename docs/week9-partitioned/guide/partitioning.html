두 서버는 왜 주문을 나누고, 서버 안에서는 왜 상품을 나눌까요?

먼저 주문번호로 서버의 담당 범위를 나눠 한 주문의 모든 품목을 같은 서버에 둡니다. 그 안에서는 상품번호로 일을 나눠 같은 상품의 수량을 한 작업이 합산하게 합니다.

이 장의 용어

파티션
한 작업이 책임지고 처리할 데이터 범위입니다. 여기서는 주문번호 범위와 상품번호 범위 두 종류가 있습니다.
로컬 파티셔닝
하나의 자바 프로세스(JVM) 안에서 일감을 여러 작업으로 나눠 처리하는 방식입니다. 여기서 한 작업자(worker)는 배정받은 상품 범위를 계산합니다.
JobInstance
Spring Batch가 같은 논리 작업임을 알아보는 단위입니다. 이 프로젝트에서는 스냅샷 ID와 주문 구간 번호로 한 구간의 작업을 식별합니다.

두 서버가 주문 4건을 맡으면 왜 경계가 90일까요?

이번에는 별도의 설명용 주문 10·20·30·90을 봅니다. 구매 품목 한 행을 한 칸으로 놓고 주문번호 순으로 이어 붙입니다. 한 주문이 차지한 칸의 가운데가 어느 구간에 있는지로 담당을 정합니다. 여기서 무게는 품목 행 수입니다. 한 행에 구매 수량이 10개여도 무게는 1입니다.

가운데를 계산하는 식과 빈 구간 읽기

가운데 위치는 누적 행 − 현재 주문의 행 수 ÷ 2입니다. 여기에 활성 서버 수 N을 곱하고 전체 행 수로 나눈 뒤 소수점 아래를 버리면 임시 구간 번호가 나옵니다. 각 임시 구간의 첫 주문번호 중 두 번째부터가 실제 경계입니다. 경계 번호 자체는 오른쪽 구간에 포함됩니다.

실제 계획은 주문이 있는 구간부터 앞쪽에 붙여 저장한 뒤, 총 N개가 될 때까지 빈 구간을 둡니다. 서버 3대에 주문이 한 건이면 첫 구간이 주문 전체를 맡고 두 구간은 비어 있습니다. 큰 주문 하나를 둘로 쪼개지 않으므로 품목 행 수도 항상 같지는 않습니다.

위의 선택은 각각 새 계획을 만드는 시점을 보여 줍니다. N은 서버 간 주문 구간 수입니다. 각 JVM 안에서 상품을 나누는 로컬 worker 수는 별도 설정이므로, 서버가 2대여도 각자 다른 수의 worker로 자기 구간을 처리할 수 있습니다.

계산 도중 세 번째 서버가 들어오면 경계를 새로 나눌까요?

이번 판본에 저장한 주문 경계와 로컬 분할 기준은 유지합니다. 정상적인 인수 절차를 거쳐 담당 서버가 바뀌어도 스냅샷 ID와 구간 번호가 같으면 같은 JobInstance로 이어집니다. 다음 판본의 계획을 만들 때 가동 중인 서버 수를 다시 셉니다.

구현과 검증 근거

  • ensurePlan의 활성 서버 조회, weights·totals·buckets 계산과 N개 구간 저장
  • 주문 구간별 상품번호를 나누는 구현
  • 로컬 worker를 실행하는 Spring Batch 설정
  • 새 담당자가 같은 JobInstance를 재개한 시험
