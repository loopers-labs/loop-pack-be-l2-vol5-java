# 5주차 결정 상세 — 근거와 검토한 대안

요약은 [`design.md`](design.md)에 있다. 이 파일은 각 결정의 **근거와 버린 대안**, 불변식의 **반례**를 담는다. 번호는 요약과 같다.

## 불변식과 반례

<a id="inv-001"></a>

### INV-001 · 결과 반영은 하나의 트랜잭션
- **규칙:** 결제 시도, 주문, 재고 예약은 결과 반영 트랜잭션(TX B) 하나에서 함께 바뀐다.
- **출처:** 실습 조건 ("성공·반환 상태와 재고 변경을 같은 TX에서 보호")
- **반례:** 결제를 SUCCESS로 commit한 직후, 주문을 바꾸기 전에 서버가 죽는다. 결제는 SUCCESS인데 주문은 PAYMENT_PENDING에 남는다.
- **기대 결과:** 셋 중 하나라도 실패하면 모두 롤백된다. 같은 외부 결과를 다시 조회해 적용할 수 있다.
- **책임:** TX B 경계(application)

<a id="inv-002"></a>

### INV-002 · 전이는 한 번, 효과는 전이에서만
- **규칙:** 결제 시도는 미종결에서 종결로 한 번만 전이한다. 재고 반환과 예약 소비는 그 전이에서만 일어난다.
- **출처:** 실습 조건 + 설계 대화
- **반례 1:** 같은 FAILED가 두 번 들어와 매번 +2를 하면 가용 재고가 5가 아니라 7이 된다.
- **반례 2:** callback과 reconcile의 TX B가 겹쳐서 둘 다 "미종결"로 읽으면 +2가 두 번 일어난다. 같은 밀리초에 올 필요는 없다. 앞의 TX B가 commit하기 전에 뒤의 TX B가 상태를 읽기만 하면 된다. TX B 앞에 수백 ms의 PG 조회가 있어 겹치기 쉽다.
- **기대 결과:** 몇 번, 어떤 순서로, 동시에 들어와도 재고 변화는 한 번이다.
- **책임:** 결제 시도 도메인 클래스가 종결 여부를 검사하고(D-001), 행 락으로 동시 진입을 직렬화한다(D-002).

<a id="inv-003"></a>

### INV-003 · 종결 뒤에 들어온 결과
- **규칙:** 종결된 시도에 같은 결과가 다시 들어오면 아무것도 바꾸지 않는다. 다른 결과가 들어오면 결제, 주문, 재고는 바꾸지 않고 충돌로 기록한다.
- **출처:** 실습 조건 ("종결 뒤 상충하는 응답은 덮어쓰지 않는다") + 설계 대화
- **반례 1:** callback으로 CONFIRMED가 된 뒤 처음 create의 timeout 처리가 늦게 실행되어 UNKNOWN으로 되돌린다.
- **반례 2:** 관리자가 FAILED로 처리한 뒤 PG에서 SUCCESS가 확인됐는데 그냥 무시한다. 고객 돈은 나갔는데 아무 기록도 남지 않는다.
- **기대 결과:** 종결 상태는 유지되고, 충돌은 관리자 확인 목록에 오른다.
- **책임:** 결제 시도 도메인 클래스

<a id="inv-004"></a>

### INV-004 · 미확인은 실패가 아니다
- **규칙:** timeout, 조회 0건, 조회 실패, circuit breaker OPEN은 FAILED의 근거가 아니다. FAILED는 PG 조회로 확인된 FAILED, 효과 0건 확정 거절(`pg-contract.md`의 422 조건), 관리자가 PG 쪽에 거래가 없음을 직접 확인한 경우(D-009)에만 정한다.
- **출처:** 실습 조건 + 설계 대화
- **반례:** OPEN을 FAILED로 처리하면 오탐 한 번에 멀쩡한 결제가 실패가 되고 재고가 풀린다. 나중에 SUCCESS가 확인되면 초과 판매가 된다.
- **기대 결과:** 확인하지 못한 동안 결제 시도와 예약은 그대로 유지되고, 응답은 "현재 상태 + 확인 불가"다.
- **책임:** 결제 시도 도메인 클래스 (상태 전이 메서드가 허용하는 근거를 제한)

<a id="inv-005"></a>

### INV-005 · 재발송 금지
- **규칙:** create는 발송 시작이 DB에 commit된 뒤에만 보낸다. 발송을 시작한 시도에는 어떤 이유로도 create를 다시 보내지 않는다.
- **출처:** 실습 조건
- **반례:** PG 호출 뒤에 기록하면, 호출 직후 서버가 죽었을 때 재시작한 서버가 "보낸 적 없음"으로 판단하고 다시 보낸다. 거래가 2건이 되고 돈이 두 번 나간다.
- **기대 결과:** 실제 create 호출은 시도당 최대 1회다. 기록만 하고 실제로 못 보낸 시도는 UNKNOWN으로 남고 관리자 확인으로 간다. 두 실수 중 되돌릴 수 있는 쪽(결제 미완료)을 고른 것이다.
- **책임:** TX A(application), HTTP client·회복 라이브러리의 숨은 재시도 끄기(infrastructure)

<a id="inv-006"></a>

### INV-006 · 가용 재고와 반환
- **규칙:** `stock_remaining`은 가용 재고다. TX A에서 예약 수량만큼 빼고, FAILED 전이에서 예약 수량만큼 **더한다.** SUCCESS 전이는 바꾸지 않는다. 단, FAILED 전이 시점에 이미 삭제된 상품은 더하지 않는다(D-019).
- **출처:** 실습 조건(5 → 3 → 성공 3 / 실패 5) + 설계 대화
- **반례:** 가용 3(2개 예약 중)일 때 관리자가 2로 바꾼 뒤 FAILED가 오면, "예약 전 값 5로 되돌리기"는 관리자 변경을 지운다. 맞는 값은 4다.
- **기대 결과:** 반환은 상대값 더하기이고, INV-002에 따라 한 번만 일어난다.
- **책임:** `Stock` 값 객체 (기존 `decrease`와 같은 상대 연산)

<a id="inv-007"></a>

### INV-007 · 결제 시도의 주문 참조는 바뀌지 않는다
- **규칙:** 결제 시도의 `order_id`는 생성할 때 정해지고 바뀌지 않는다.
- **출처:** 설계 대화
- **반례:** `order_id`를 바꿀 수 있으면, callback이 잠그지 않고 읽은 주문 번호와 실제로 잠근 주문이 달라져 다른 주문에 결과를 반영할 수 있다.
- **기대 결과:** callback은 잠그지 않고 읽은 `order_id`로 주문을 잠가도 안전하다. 잠그지 않고 읽어도 되는 건 바뀌지 않는 값뿐이고, `status`는 잠근 뒤에 다시 읽는다.
- **책임:** 결제 시도 도메인 클래스 (생성자에서만 설정, setter 없음, `LikeModel`과 같은 방식)

## 결정

| 번호 | 결정 | 근거 | 검토한 대안 |
|---|---|---|---|
| <a id="d-001"></a>D-001 | 종결 여부 검사는 결제 시도 도메인 클래스가 한다 | 새 경로(예: 관리자 처리, D-009)가 생겨도 규칙이 빠지지 않는다. CLAUDE.md "domain 모델이 불변식을 캡슐화한다" | 조건부 UPDATE(`WHERE status IN 미종결`): 동시성은 막지만 규칙이 리포지토리 SQL에 숨는다 |
| <a id="d-002"></a>D-002 | TX B 락 순서: 주문 → 결제 시도 → 상품(id 오름차순). callback은 결제 시도를 잠그지 않고 읽어 `order_id`를 알아낸 뒤 주문부터 잠근다 | 모든 처리가 같은 순서로 잠가야 데드락이 없다(방향은 상관없다). 기존 규칙을 유지하면 TX A와 기존 경로를 바꾸지 않아도 된다 | 결제 시도 먼저: callback은 한 단계 줄지만 기존 규칙과 TX A를 바꿔야 한다 |
| <a id="d-003"></a>D-003 | 재고 예약은 따로 저장하지 않는다. 예약 수량은 `order_item.quantity`, 예약 상태는 `orders.status`(PAYMENT_PENDING 유지 / CONFIRMED 소비 / PAYMENT_FAILED 반환)로 계산한다 | INV-001로 예약 상태와 주문 상태가 항상 함께 바뀐다. 따로 적으면 같은 사실이 두 곳에 남아 어긋날 위험만 생긴다. 2주차 좋아요 수를 관계에서 집계한 것과 같은 원칙. `order_item`은 생성 뒤 바뀌지 않아 더할 수량도 항상 같다 | `product.reserved` 컬럼: 어느 주문의 몇 개인지 구분 못 함. 예약 테이블: 상태가 주문과 중복 |
| <a id="d-004"></a>D-004 | 상품 캐시(`product:{id}`)는 TX A와 FAILED 전이의 commit 뒤에 주문 상품마다 지운다. SUCCESS 전이와 중복·충돌 결과는 지우지 않는다 | 4주차 규칙: 재고가 실제로 바뀌는 commit에서만, commit 뒤에(`ProductCacheInvalidator`) | — |
| <a id="d-005"></a>D-005 | 미뤄진 결제의 회복 경로를 경우별로 나눈다: ⓐ 응답 유실 → 바로 재조회, ⓑ callback 유실 → 스케줄러, ⓒ 서버 재시작 → 고객 reconcile·스케줄러, ⓓ PG에 안 들어감 → 관리자 확인 | 경우마다 계기와 조회 방법이 다르다. 모든 경로가 TX B를 지나므로 겹쳐도 INV-002가 지킨다. 세부와 수치는 `recovery.md` | 고객 reconcile만 / 스케줄러만: 어느 쪽도 ⓓ를 풀지 못한다 |
| <a id="d-006"></a>D-006 | 스케줄러를 둔다. 모든 상품에 같은 목표 시간을 쓴다 | 상품별로 나누면 "인기" 기준과 저장 위치가 새로 필요하다. 실무에서 나눈다면 결제 수단별인데 이번엔 카드뿐이다. 수치는 `recovery.md` | 상품별 목표(인기 5분 / 일반 30분) |
| <a id="d-007"></a>D-007 | 연속 0건이 일정 횟수를 넘으면 관리자 확인 목록에 올리되, 스케줄러 조회는 멈추지 않는다 | 알림과 조회를 분리하면 너무 일찍 넘겨도 놓치는 시도가 없다. 틀려도 싸고 되돌리기 쉬운 결정이라 임시값으로 시작한다 | 넘기면 조회 중단 |
| <a id="d-008"></a>D-008 | 0건이 이어지면 조회 간격을 늘린다. 관리자가 처리하면 미종결 조회는 끝나고 D-013의 감시로 넘어간다 | 실제로 못 보낸 시도는 영원히 0건이라 고정 간격이면 끝없이 쌓인다 | 고정 간격 계속 조회 |
| <a id="d-009"></a>D-009 | 관리자가 PG에 거래가 없음을 직접 확인하면 FAILED 처리하고 예약을 반환한다. 누가 언제 처리했는지 기록한다 | "증거 없음"이 아니라 사람이 만든 증거가 있다(INV-004). 같은 TX B를 지나므로 INV-001~003이 그대로 적용된다 | 끝내지 않음: 시도와 예약이 영원히 남는다 |
| <a id="d-010"></a>D-010 | 충돌은 기록하고 관리자 확인 목록에 올린다 | 자동으로 뒤집으면 그사이 팔린 재고와 부딪힌다. 바로잡는 방법(환불 등)은 사람이 판단하고 과제 범위 밖이다 | — |
| <a id="d-011"></a>D-011 | 충돌은 별도 테이블에 저장한다. 결제 시도(`attempt_id`), 사유, 기록된 결제 상태, PG 관찰 결과(거래 키·상태·금액), 처음/마지막 발견 시각, 처리 시각을 담는다. 로그는 알림·추적용 보조 수단이다 | 우리가 기록한 사실은 계산할 수 있지만(D-003), PG 관찰 결과는 관찰한 순간 적어 두지 않으면 사라진다. 한 시도에 충돌이 여러 번 생길 수 있다 | JOIN으로 계산: 외부 관찰이 DB에 없어 불가. 로그만: 목록 조회·처리 표시·중복 묶기가 안 됨. 결제 시도 행의 컬럼: 두 번째 충돌이 첫 번째를 덮어씀 |
| <a id="d-012"></a>D-012 | 새 관찰과 내용이 같은 충돌 행이 있으면 새 행을 만들지 않는다. 처리 전이면 `last_detected_at`만 갱신하고, 처리 후면 무시한다(로그만 남김). 내용이 다르면 처리 여부와 상관없이 새 행을 만든다. 같은 내용 = 결제 시도, 사유, 기록된 결제 상태, PG 관찰 결과가 모두 같음 | 스케줄러가 같은 충돌을 반복 발견해도 목록이 한 줄이다. 테스트 PG에는 환불 상태가 없어 관리자가 조치해도 PG는 같은 결과를 계속 말하므로, 처리 뒤 같은 관찰은 새 정보가 아니다. 충돌 기록은 결제 시도 행을 잠근 TX B 안에서 쓰므로 동시 발견도 한 행으로 모인다 | 발견할 때마다 새 행: 같은 문제가 수십 줄. 처리 뒤 다시 발견되면 무조건 새 행: 해결한 문제가 계속 다시 올라옴 |
| <a id="d-013"></a>D-013 | 관리자가 FAILED로 처리한 시도는 일정 기간 스케줄러가 계속 조회한다(감시). 늦은 SUCCESS가 발견되면 충돌로 기록한다(D-011). 스케줄러 주기와 별개로 시도마다 다음 확인 시각을 둔다 | 스케줄러는 미종결 시도만 보므로, 없으면 관리자 처리 뒤 늦게 나타난 SUCCESS를 발견할 경로가 없다(PG 기록이 늦게 보일 수 있음). 감시 기간은 짧게 틀리면 "돈은 나갔는데 아무도 모름", 길게 틀리면 조회가 조금 늘 뿐이라 비대칭이다. 그래도 끝을 두는 건 감시가 끝난 뒤에도 고객이 카드 승인 문자로 먼저 알고 문의하는 두 번째 경로가 있기 때문이다(D-014). 수치는 `recovery.md` | 관리자 단건 확인만: 관리자는 이미 "거래 없음"을 확인했으니 다시 누를 계기가 없다 |

PG가 버거운 건 3분 합계가 아니라 순간 몰림이므로 단위를 초로 바꾸면 두 목표가 함께 풀린다. 20의 근거: 테스트 PG에는 한도가 없어 Stripe 공개 한도(조회 엔드포인트 초당 25건)를 빌리고, 같은 엔드포인트를 쓰는 고객 경로(ⓐ·reconcile·관리자)에 초당 5건을 남긴다. 최대 부하 1분 뒤 쌓인 17,000건을 약 14분에 비워 회복 감시 알림 기준(15분, D-035) 안이다. 피크에는 고객 응답을 지키고 밀린 callback은 뒤에 따라잡는 쪽을 택했다. 작업은 스레드 하나로 한 건씩 처리해 DB 커넥션을 한 번에 하나만 쓴다 | 회차당 건수를 줄이기: 순간 몰림은 조금 줄지만 처리량이 더 떨어진다. bulkhead: 동시 실행을 줄이는 장치라 "너무 적게 처리"하는 문제를 풀지 못한다. 피크에도 들어오는 속도(초당 86건)만큼 처리: 고객 경로가 쓸 PG 한도가 남지 않는다 |
