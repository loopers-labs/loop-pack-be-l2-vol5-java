## 중요 보완 · 사용자 승인 후 계획 반영

### 회차 commit 후에도 조회 시작 가능 여부를 다시 확인

회차 시작 때 확인했어도 DB 잠금/commit을 기다리는 사이 30초 예산이 끝나거나 담당자가 실행을 인계할 수 있다. 그대로 PG를 호출하면 기존 만료/인계 정책을 지키지 못할 수 있다.

사용자는 쉬운 설명을 확인한 뒤 “회차 commit 뒤 권한·시간 재확인 보완을 계획에 반영하고 세 관점 재리뷰”를 명시적으로 요청했다. 아래 최소안을 상세 계획에 반영했다.

1. consumeRound commit 성공 후, 현재 실행 ID·완료 상태를 짧은 TX로 다시 확인한다.
2. PG 조회 진입 직전에 단조 시간 기준의 30초 예산도 다시 확인한다.
3. 만료/완료/권한 상실이면 새 PG HTTP를 시작하지 않고 이미 commit한 사용 회차는 유지한다. 옛 실행이 인계받은 새 실행에 표식을 쓰지 않는다.
4. 확인 직후 인계되는 경합까지 완전히 막는 취소 프로토콜은 추가하지 않는다. 이미 시작한 조회의 검증 사실 저장과 기존 snapshot을 통한 진행 보호는 유지한다.

회차 저장 뒤 재확인 DB 조회가 실패한 경우도 PG를 호출하지 않는 기존 DB 확인 실패 정책으로 연결했다. 반영 후 세 관점 재리뷰에서 중요 지적이 해소됐음을 확인했다. 이 문서 반영은 기능 수정이나 검증 완료를 의미하지 않는다.

## 정책 변경 없이 반영한 작은 명시 보완

- 사용자 경험: 수동 대사도 새 회로 차단/계약 오류 사유를 기존 reason 필드에 연결한다. 자동 작업만 상세 사유를 남기고 수동은 LOOKUP_UNAVAILABLE로 뭉뚱그리지 않는다.
- 기술: 실행별 대기 종료 flag/예산 중단 예외를 사용하고, 남은 시간까지만 기다린 뒤 다음 회차에서 조회 없이 종료한다. 동기 Retry의 음수 대기 시간을 종료 신호로 사용하지 않는다. 소진 fallback은 필요한 예외 타입으로 제한한다.
- 기술: 회차 commit 미확인·관찰 저장 실패·상태 확인 실패를 PG 재조회로 반복하지 않는다. 업무 commit 불명확은 새 TX 상태 확인을 먼저 하고, 미완료일 때만 최초 업무 snapshot으로 표시한다. 다른 실행의 최신 snapshot으로 자기 권한을 바꾸지 않는다.

이 항목은 이미 정한 시간 예산·DB 오류 중단·최초 snapshot 정책을 구현할 때의 명시 보완이다. 상세 계획에 기록했고 승인한 중요 보완과 함께 재리뷰를 마쳤다.

### 기능 중요 보완 · 사용자 승인 후 반영

초회 조회 전용 계약은 주문·금액·거래 키만 받았다. 이미 SUCCESS인 거래를 PG가 FAILED라고 조회해도 회로는 정상으로 집계하고 이후 저장 TX에서 TERMINAL_CONFLICT가 드러났다. 생성 전 확정 거절 후 거래가 발견되는 경우도 같았다. 이는 종결 충돌을 제외하기로 한 정책과 달라 HALF_OPEN 회복 판단에도 영향을 줄 수 있었다.

사용자가 최소안을 승인한 뒤 LookupRequest에 caller가 이미 읽은 outcome/rejection을 함께 전달하도록 수정했다. 알려진 종결/존재 충돌은 회로 제외 예외로 보낸다. fallback은 원래 VERIFIED 관찰을 그대로 반환해 기존 저장 TX가 정확한 충돌을 보존한다. DB 처리는 회로 밖을 유지한다.

조회 시작 후 다른 실행의 저장으로 뒤늦게 발견된 충돌은 이미 끝난 PG 표본에 소급 반영하지 않는 한계도 함께 승인받아 집계 문서와 계획에 명시했다. 같은 종결 결과·늦은 PENDING을 충돌로 만들지 않는다.
