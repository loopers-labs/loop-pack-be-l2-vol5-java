# 자동 재확인·실패 분류·수동 전환

[전체 설계 질문](total_trade_off.md) · [요구사항](../requirement.md) · [R01 모델 논의](../../r01-pg-payment-foundation/trade_off/01-payment-attempt-ownership.md)

처음 읽는 개발자는 [현재 구현의 재시도 전략](../../resilience/retry.md)을 먼저 읽는다. PG 조회와 내부 반영의 목적·조건·횟수·시간·중단 후 행동을 나눠 설명한다. 이 문서는 정책 결정 과정의 기록이며 과거 Spring Retry 선택보다 최종 Resilience4j 구현을 따른다.

상태: **2026-10-23 정책 구현·세 관점 기능 리뷰·최종 검증 완료**. 전체 검사 509건과 실제 PG 장애/재시작 실험 14건의 증거·검증 한계는 [결과](../result.md)를 따른다. 아래 논의는 결정 과정이며 현재 클래스와 완료 범위는 [계획](../plan.md)·[리뷰 기록](../review.md)에 연결한다. 원격 PR은 후속 범위다.

## 사용자 결정과 남은 질문

2026-10-21 사용자는 기존 거래를 자동으로 다시 확인하는 방식을 선택했다.
이어 최초 조회 후 추가 재시도 최대 3회, 간격 1초·3초·10초, 지터 ±20%와 아래 실패/수동 전환 기준을 확정했다.
원문의 수동 reconcile 기본 경로에 자동 재확인을 추가하는 사용자 결정이며 원문 파일은 변경하지 않는다.

- 확정: 최초 조회 1회와 추가 재조회 최대 3회, 앞선 확인 종료 후 1초·3초·10초 대기와 각 간격의 지터 ±20%.
- 확정: 아래 분류에 따라 확정 실패는 실패 반영, 일시적 조회 장애/처리 중/빈 조회는 한도 내 재확인, 충돌/설정 오류 등은 즉시 수동 전환한다.
- 확정: 수동 전환은 자동 작업 중단이며 결제 실패가 아니다. 수동 대사와 늦은 callback도 같은 검증·멱등 반영 경계를 사용한다.
- 확정: 정상 실행은 Resilience4j Retry로 처리하고 DB에 진행을 저장한다. 2026-10-22 최신 결정으로 기존 Spring Retry @Retryable 선택을 대체했다. 서버 장애 뒤 자동 재개는 담당자 수동 대사로 변경했다. [실행 방식 결정](06-reconciliation-execution.md)을 따른다.
- 확정: 조회 작업 직전에 사용 횟수를 DB에 기록하고 commit한다. 기록 뒤 HTTP 전에 종료돼도 해당 회차는 소비한 것으로 유지한다. [횟수 기록 결정](07-retry-attempt-accounting.md)을 따른다.
- 후속 확정: R01 [HTTP 설정](../../r01-pg-payment-foundation/trade_off/03-http-client-settings.md)은 연결 1초·연결 풀 대기 1초·응답 대기 2초와 client 자동 retry/redirect 차단이다. [adapter](../../r01-pg-payment-foundation/trade_off/04-adapter-fixture.md)는 관찰/확인 불가 사유를 결과값으로 반환하며 재조회 제어와 회로는 결과 분류에 연결한다.
- 2026-10-22 확정: 첫 자동 조회는 작업 시작 후 바로 실행한다. 명확한 실행기 접수 거절은 100ms 뒤 전달만 1회 재시도하고 재거절은 수동 전환한다. [실행 방식](06-reconciliation-execution.md)을 따른다.
- 2026-10-22 확정: 자동·수동 대사·callback은 하나의 PG 조회 회로를 공유한다. 회로 차단 시 자동 작업은 즉시 수동 전환하며 이미 확보한 회차는 소비한 채 유지한다. 수동/callback은 자동 회차를 소비하지 않는다.
- 2026-10-22 확정: 회로 정상/실패/제외와 4xx 경로별 분류는 [02 집계 문서](02-lookup-circuit-breaker.md)를 따른다. 회로 실패와 재조회 여부는 별도 판단이다.
- 2026-10-22 확정: 자동 작업의 최초 전달 시점부터 대기열·재접수·조회·재시도 대기를 포함한 30초 예산을 적용한다. 만료 뒤 새 조회/추가 대기를 시작하지 않으며 이미 시작한 조회와 검증 결과 저장·반영은 마무리한다.
- 2026-10-22 확정: 저장된 검증 결과의 내부 반영은 확실히 rollback된 MySQL 데드락에만 100ms 뒤 추가 1회 재시도한다. PG 호출·자동 조회 회차·회로 표본을 추가하지 않는다.
- 2026-10-22 확정: 조회 HTTP 오류 중 408·429·500·502·503·504만 예산 내 재조회한다. 나머지 5xx는 회로 실패로 집계하지만 즉시 수동 전환한다. timeout·통신 오류·PENDING·계약상 거래 없음의 기존 재조회 정책도 유지한다.
- 2026-10-22 확정: Retry-After 헤더는 이번 학습 범위에서 해석하지 않는다. 기존 1·3·10초와 지터 ±20%·30초 예산을 유지한다.
- 2026-10-22 확정: 조회 계약 밖 2xx/3xx는 회로 실패로 집계하고 즉시 수동 전환한다. 2xx만으로 결제 성공을 추측하거나 3xx를 따라가지 않는다.
- 2026-10-22 확정: 자동 조회 Retry와 공유 조회 CircuitBreaker는 모두 Resilience4j를 사용한다. 기존 Spring Retry @Retryable 선택은 대체하며 정책과 DB 기록은 유지한다. [연결 논의](03-resilience-library-wiring.md)를 따른다.
- 연결은 Resilience4j @Retry·@CircuitBreaker 애노테이션으로 확정했다. 라이브러리 예외 변환·실행기 연결과 자동 시작 조건의 상세는 미정이다. 회로 수치는 [02](02-lookup-circuit-breaker.md)에서 확정했다.
- R01/R02에 상태·테이블·회차 CAS와 수동 경로가 이미 있다. R03의 추가 사유/필드 필요성은 상세 설계 대상이며 구체적인 의존성 버전·자동 실행은 아직 정하지 않았다. 정책 확정은 구현·검증 완료를 뜻하지 않는다.

## 이미 정해진 안전 조건

- 발송 시작 기록 뒤 PG 결제 생성은 자동 재시도하지 않는다. 응답 유실·서버 오류·재시작도 예외로 삼지 않는다.
- 결제 실패로 종결할 근거는 검증한 PG FAILED 또는 계약에 정확히 맞는 거래 생성 전 확정 거절이다.
- 확정 거절은 HTTP 422, TEST_PG_REJECTED_BEFORE_CREATE, transactionCreated=false, 일치하는 orderId/amount를 함께 검증한다.
- 시간 경과·조회 실패·조회 0건/404·재시도 소진·회로 OPEN은 결제 실패의 근거가 아니다.
- 확정 실패에 따른 재고 복구와 주문/시도 변경은 같은 로컬 TX에서 한 번만 적용한다.
- PG 결과가 확인됐더라도 내부 반영 TX가 실패하면 적용 완료로 기록하지 않는다. 이미 확인한 결제 사실도 반대로 바꾸지 않는다.

| 내부 반영의 영구적 업무 충돌·무결성 문제 | 즉시 수동 확인으로 전환 | PG 결과와 내부 미반영을 함께 보존, 새 결제/임의 재고 복구 금지 |

DB commit 결과가 불명확하면 저장 상태를 먼저 확인하고 공통 멱등 반영 경계를 사용한다.
유일 제약 충돌은 기존 시도·저장 결과를 확인할 경로이며, 모든 DB 예외를 일시적 오류로 묶어 재시도하지 않는다.
관찰 검증은 R01 adapter 경계, 재조회/최종 반영 판단은 application과 도메인에 둔다. 위 코드 목록을 실제 관찰/라이브러리 예외에 연결하는 방식은 상세 설계에서 정한다.

## 조회 HTTP 오류의 재시도 범위 · 확정

HTTP 오류 응답의 재조회 목록은 **408·429·500·502·503·504**로 제한한다. 모든 5xx를 다시 조회하는 안은 채택하지 않았다.

- 500·502·503·504는 일시적인 서버/중계 장애일 수 있으므로 기존 횟수·간격·30초 예산 안에서 다시 조회한다. 일시적 장애라는 보장이나 한도 안에 회복된다는 보장은 아니다.
- 501·505와 그 밖의 5xx는 같은 요청의 반복으로 해결될 것이라 추측하지 않고 즉시 수동 확인으로 넘긴다. **모든 5xx의 회로 실패 집계는 그대로 유지**한다.
- timeout·통신 오류의 재조회, 정상 조회인 PENDING·계약상 거래 없음의 재확인, 다른 4xx/깨진 정상 응답/충돌의 즉시 수동 정책은 유지한다.
- 이 목록은 자동 조회에 적용한다. 수동 대사는 계속 요청당 최대 한 번만 조회하며 callback도 자동 반복 조회를 만들지 않는다. 결제 생성 POST는 재시도하지 않는다.

서버 오류의 의미는 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6)을 참고했다. 위 재조회 목록은 학습용으로 선택한 서비스 정책이다.

### 조회 계약 밖 2xx/3xx · 확정

- PG 조회는 200 응답을 계약으로 삼는다. 202·204 등 다른 2xx나 302 등 3xx를 받으면 계약에 맞지 않는 조회 결과로 분류한다.
- 사용자는 **회로 실패 집계·즉시 수동 전환**을 선택했다. 회로 표본에서 제외하는 안은 채택하지 않았다.
- 해당 응답으로 자동 재조회하거나 결제 성공/실패를 추측하지 않는다. 기존 HTTP client의 redirect 차단도 유지한다.
- 저장된 검증 사실과 차감 재고는 유지한다. 공통 반영이 이미 완료된 상태를 계약 오류로 되돌리지 않는다.
- 생성 POST의 정상 202와 조회의 계약 밖 202는 구분한다. 생성 POST는 이 조회 회로 범위 밖이다.

### Retry-After는 학습 범위에서 미지원 · 확정

사용자는 **고정 간격 유지·헤더 미지원**을 선택했다. 기존 대기와 Retry-After 중 더 긴 시간을 기다리는 안은 채택하지 않았다.

- 자동 재조회는 앞선 확인 종료 후 1·3·10초에 지터 ±20%를 적용하고, 최초 작업 전달부터 30초 예산과 최대 4회 한도를 유지한다.
- 429/503 등에 Retry-After가 있어도 초 단위/날짜 형식을 해석하거나 대기 시간을 덮어쓰지 않는다. 헤더 유무/내용으로 기존 HTTP 분류나 회로 표본을 바꾸지 않는다.
- 현재 테스트 PG는 이 헤더를 보내지 않는다. 헤더 해석·날짜 계산·잘못된 값의 처리와 이를 위한 관찰 필드 확장은 추가하지 않는다.
- 비용은 외부 PG가 지정한 대기 시간을 따르지 못한다는 점이다. 나중에 해당 계약을 가진 PG에 연결한다면 이 정책을 다시 정해야 한다. 이번 학습용 구현의 한계로 기록한다.

헤더의 의미와 형식은 [RFC 9110 · Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)를 참고했다. 미지원 선택은 HTTP 표준의 권장 동작이라는 뜻이 아니라 이 저장소의 학습 범위 결정이다.

## 확정한 횟수·간격과 비용

- 최초 확인 뒤 추가 재조회 최대 3회로 조회 작업은 최대 4회다. 중간에 반영 완료하거나 즉시 수동 전환 사유가 확인되면 남은 재조회를 중단한다.
- 앞선 확인 종료 뒤 1초·3초·10초를 대기하며 각 대기에 지터 ±20%를 적용한다. 각 대기의 범위는 0.8~1.2초·2.4~3.6초·8~12초다.
- 세 대기 시간의 합은 11.2~16.8초다. HTTP 실행·DB 반영·스케줄링 지연이 추가되므로 전체 완료 시간이 이 범위라는 뜻은 아니다.
- 짧은 간격은 빠른 회복에 유리하지만, PG 처리 시간이 길면 매번 PENDING만 보고 수동으로 넘기게 된다.
- 긴 간격은 같은 횟수로 더 긴 처리 지연을 관찰하지만 재고 확보·고객 대기도 길어진다.
- 지터는 여러 시도의 재조회 시점을 흩뜨리며, 장애 해결이나 개별 호출 timeout을 대신하지 않는다.
- PG 학습 시나리오의 완료 시간과 재확인 창을 함께 정한다. 최대 4회의 조회 작업 안에 모든 거래가 완료될 보장은 없다.
- 현재 R02의 gateway.lookup은 저장 거래 키가 있으면 단건, 없으면 주문별 목록 중 한 경로로 HTTP를 한 번 보낸다. R03의 자동 작업 회차·실제 HTTP 호출 수·회로 표본 수를 구분하며 회로 차단/회차 commit 뒤 종료는 HTTP 0회일 수 있다.
- 자동 작업의 최초+추가 3회 외에 HTTP client/library retry가 중첩돼 실제 호출을 늘리지 않도록 구성한다. 실제 HTTP 호출 예산은 조회 흐름과 함께 확정한다.
- 프로세스 재시작으로 횟수를 초기화하지 않는다. 조회 직전 commit한 회차는 사용한 것으로 유지한다. 회로 차단도 이미 확보한 회차는 유지하고 즉시 수동 전환한다. callback/수동 조회는 자동 회차를 소비하지 않는다. [횟수 구분](02-lookup-circuit-breaker.md#카운팅을-읽는-방법)을 따른다.

## 자동 조회의 전체 시간 예산 · 확정

사용자는 **30초 후 추가 자동 조회 중단**을 선택했다. 40초 안은 채택하지 않았다.

- 시작점은 PG 생성 처리가 끝나고 자동 작업을 실행기에 처음 전달하는 시점이다. PG 생성 HTTP를 30초 예산 안에서 다시 호출하거나 재시도하지 않는다.
- 실행기 대기열·명확한 접수 거절 뒤 100ms 재접수·PG 조회·재조회 사이의 대기를 포함한 경과 시간을 본다.
- 예산이 끝나면 새 PG 조회와 추가 대기를 시작하지 않는다. 최대 4회를 채우지 못했어도 미완료라면 수동 확인으로 넘긴다.
- 이미 시작한 조회, 그 결과의 검증·저장·공통 업무 반영은 마무리한다. 따라서 전체 처리를 정확히 30초에 강제 종료하거나 API 응답 시간을 30초로 보장하는 정책이 아니다.
- 만료 직전/후 callback·수동 대사가 완료했다면 최신 완료 상태와 기존 실행 보호를 우선한다. 예산 만료로 완료를 되돌리지 않는다.
- 예산 만료는 결제 실패·재고 반환·새 결제 허용 근거가 아니다. 마지막 검증 결과와 차감 재고·사용 회차를 보존한다.
- 재시작으로 새 자동 예산을 주거나 중단 작업을 자동 재개하지 않는다. 기존 정책대로 담당자가 목록에서 찾아 명시적으로 대사한다.

40초보다 미완료 자동 작업을 일찍 정리하지만, 대기열/조회가 지연되면 조회 횟수가 남아도 자동 확인 기회를 포기하는 비용을 수용했다.
시간 측정·대기 전후 예산 검사와 수동 사유 타입의 구체적인 연결은 상세 구현 계획에서 정한다. 검증한 결과의 내부 반영 재시도는 아래의 별도 정책을 따른다.

## 검증 결과의 내부 반영 재시도 · 확정

사용자는 **100ms 뒤 추가 1회**를 선택했다. 최초 반영까지 합쳐 최대 2회이며, 100ms·300ms 뒤 추가 2회 안은 채택하지 않았다.

- 대상은 PG 결과가 먼저 저장됐고, 주문 확정·재고 반환 등을 처리하는 업무 TX가 **MySQL 데드락으로 확실히 rollback된 경우**다. 새 TX에서 저장된 같은 결과를 다시 반영한다.
- 100ms 대기는 TX와 잠금 밖에서 수행한다. 이 재시도는 PG 생성/조회·자동 조회 회차·회로 표본을 추가하지 않는다.
- 추가 반영도 실패하면 미반영 사실을 보존하고 수동 확인으로 넘긴다. 영구적 무결성 문제·업무 충돌·재고 반환 overflow는 기다리며 반복하지 않고 즉시 수동 처리한다.
- commit 성공 여부가 불명확하면 먼저 새 TX에서 저장 상태를 확인한다. 불명확한 오류를 rollback으로 가정해 이 재시도를 적용하지 않는다.
- 대기 중 callback·수동 대사가 완료하거나 실행을 인계할 수 있다. 기존 공통 멱등 반영과 실행 ID 보호를 유지하며 완료 상태를 되돌리거나 새 실행의 진행을 덮지 않는다.
- 자동 조회 30초 예산이 끝나도 이미 시작한 조회의 검증 결과 저장·업무 반영을 마무리하는 원칙은 유지한다. 내부 반영 재시도는 새 PG 조회를 허용하는 근거가 아니다.

### 2026-10-22 · 대상 DB 오류를 데드락으로 제한

- 사용자는 **MySQL 데드락만 재시도**하는 안을 선택했다. 전체 rollback을 확인한 잠금 대기 timeout까지 포함하는 안은 채택하지 않았다.
- MySQL 데드락은 오류 번호 `1213`·SQLSTATE `40001`로 식별한다. 실제 예외의 원인에서 이 근거를 확인하는 연결은 상세 계획에서 정하며, 일반적인 일시적 예외 타입이나 메시지 문자열만으로 대상을 넓히지 않는다.
- 잠금 대기 timeout·DB 연결 끊김·무결성 오류·재고 반환 overflow는 이 재시도 대상이 아니다. commit 결과가 불명확하면 저장 상태를 먼저 확인하고, 완료하지 못했다면 수동 경로로 남긴다.
- 이 정책은 저장된 PG 결과의 **공통 업무 반영**에 적용한다. 준비 TX·PG 관찰 저장·복구 작업 진행 기록까지 자동으로 재시도하는 정책이 아니다.

일시적 충돌을 한 번 흡수하면서 판별 범위와 추가 부하를 작게 제한하는 선택이다. 대신 회복 가능한 다른 DB 오류도 수동 처리될 수 있다. [MySQL 오류 처리](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)는 데드락의 전체 TX rollback과 잠금 timeout의 기본 SQL 단위 rollback을 구분하며, [오류 코드](https://dev.mysql.com/doc/mysql-errors/8.4/en/server-error-reference.html#error_er_lock_deadlock)도 확인했다. 모든 DB 예외에 일괄 재시도를 적용하지 않는다.

### 2026-10-23 · 내부 반영 재시도의 실제 연결

구현은 `ApplyOrderPaymentFacade` → 별도 `RetryOrderPaymentService` → `ApplyOrderPaymentService` 순서다. Retry 빈의 공개 메서드에 `@Retry(name = "payment-application")`를 붙였고, 그 안에서 업무 TX의 `REQUIRES_NEW` 진입점을 호출한다. 따라서 100ms 대기는 앞선 업무 TX가 끝난 뒤에 수행하며 다음 시도는 새 TX다. 바깥 TX가 활성화된 호출은 거절해 대기 중 잠금을 유지하지 않게 한다.

재시도 대상으로 인정하려면 다음 두 근거가 **함께** 있어야 한다.

1. 같은 SQL 예외에 MySQL 오류 번호 `1213`과 SQLSTATE `40001`이 있다. 중첩 원인·SQL 후속 예외에서도 찾지만 예외 이름이나 메시지만으로 판단하지 않는다.
2. 해당 업무 TX의 `afterCompletion`에서 `STATUS_ROLLED_BACK`을 확인했다. 시도마다 별도 메모리 기록을 만들며 이전 시도의 확인 값을 재사용하지 않는다.

두 근거를 모두 확인한 경우에만 전용 `RolledBackPaymentDeadlockException`을 던진다. 설정은 이 예외만 최초 포함 최대 2회·간격 100ms로 반복한다. 그 밖의 DB/업무 오류·관찰 저장·복구 진행 TX는 반복하지 않는다. 완료 확인이 없거나 `UNKNOWN`이면 코드가 있어도 추가 반영하지 않는 보수적인 경계다.

| 업무 실패 뒤 확인한 내용 | 다음 처리 |
|---|---|
| rollback 확인 + 데드락 코드 일치 | 한도가 남으면 100ms 뒤 새 TX로 반영 |
| rollback 확인 + 다른 오류, 또는 데드락 재시도 소진 | 최초 실행 정보로 실패 표시를 시도하고 새 TX에서 현재 상태 확인 |
| rollback 확인 불가 | 새 TX에서 저장 상태부터 확인. 완료면 그대로 반환, 미완료면 최초 실행 정보로 표시한 뒤 재조회 |
| rollback 확인 불가 + 현재 상태 조회도 실패 | 추가 반영·표시를 추측하지 않고 오류를 반환. 기존 미완료 기록으로 담당자가 확인 |

실패 표시는 처음 확보한 상태·실행 ID·사용 회차를 계속 사용한다. 재시도 중 인계받은 실행이나 완료된 작업을 옛 실패가 덮지 않는다. 새 결제·PG 조회·자동 회차·회로 표본은 늘어나지 않는다. 기능 리뷰는 세 관점 모두 중요 지적 없음이며 관련 검사 결과는 [리뷰 기록](../review.md)에 남긴다.

## 확정한 수동 전환의 의미

수동 전환은 자동 작업을 멈추고 확인이 필요한 대상으로 남기는 것이다. 결제의 최종 실패 상태가 아니다.
미확인이면 재고를 유지하고, 실패는 확인했지만 복구 TX가 실패했다면 미반영 사실을 남겨 같은 복구를 마무리한다.
수동 reconcile은 저장된 검증 종결 결과의 재적용 또는 PG 권위 조회·식별 검증·관찰 저장 뒤 공통 업무 반영을 사용한다. 운영자 입력만으로 성공/실패/재고를 강제 변경하지 않는다. 특히 거래 없는 확정 거절은 먼저 저장한 근거로 재적용한다.
수동 전환 뒤에도 늦은 callback의 검증된 결과를 받아 마무리할 수 있으며 충돌 보존과 종결 상태 보호를 유지한다.
수동 대사는 R02에서 저장 종결 근거 조회 0회/그 외 최대 1회·자동 예산 보존·실행 인계를 구현했다. R03의 자동 실행과의 경합·추가 사유/미확인 표현은 상세 설계 대상이다. 장애 중단 자동 작업을 재시작 시 재개하는 안은 담당자 수동 대사로 대체됐다.
후속 [최소 보완](../../r01-pg-payment-foundation/trade_off/10-learning-scope-completion.md)에서 수동 실행 ID 교체·옛 진행 갱신 차단과 관찰 저장/업무 TX 분리를 확정했다. commerce 지터/다음 실행 예약 정보는 DB에 보존하지 않는다. 정확한 조건식·응답/예산은 후속 설계 대상이다.

## PR 책임

- R01: 결과·관찰 오류·복구 진행 모델과 저장 경계를 구현했다. 당시 설계/검증은 R01 결과를 따른다.
- R02: 기존 거래 조회·공통 결과 적용·수동 reconcile을 연결하고 한 번만 적용되는 업무 효과를 검증한다.
- R03: 자동 재확인 실행·제한/지터·수동 전환·회로와의 결합을 구현하고 재시작/장애 실험으로 확인한다.

현재 실행 방향은 [Resilience4j Retry + DB 진행 기록 + 중단 시 운영 담당자 수동 대사](06-reconciliation-execution.md)다. 이전 Spring Retry @Retryable과 재시작 자동 재개는 각각 후속 결정으로 대체했다.
HTTP client·하위 timeout·결과값 반환과 기존 테이블은 R01/R02 구현을 재사용한다. 자동 조회는 위 30초 예산과 HTTP 목록, 내부 반영은 확실히 rollback된 MySQL 데드락에 100ms 뒤 추가 1회를 적용한다. R03 의존성 버전·추가 사유/필드·라이브러리 예외 변환은 아직 선택하지 않았다. 자동 조회·회로 기능 구현·테스트 완료를 의미하지 않는다.
