# 재확인 횟수 기록과 실행 중단

[설계 질문 목록](total_trade_off.md) · [실행 방식 결정](06-reconciliation-execution.md) · [상태 분리 결정](../../r01-pg-payment-foundation/trade_off/05-payment-attempt-state.md)

상태: **2026-10-23 정책 구현·세 관점 기능 리뷰·최종 검증 완료**. 전체 검사 509건과 실제 PG 장애/재시작 실험 14건의 증거·검증 한계는 [결과](../result.md)를 따른다. 아래 논의는 결정 과정이며 현재 클래스와 완료 범위는 [계획](../plan.md)·[리뷰 기록](../review.md)에 연결한다. 원격 PR은 후속 범위다.

## 구현에서 지키는 순서

`현재 상태 확인 → consume CAS TX commit → 새 TX로 실행 ID·확보 회차·완료 재확인 → PG 조회 직전 30초 재검사 → 공유 회로 조회 → 관찰 저장 → 공통 업무 반영` 순서다. 조회 전에 상태 확인이 끝나므로 DB 대기를 회로 표본에 섞지 않는다.

회차 commit이 반환되기 전에 오류가 나면 PG를 호출하지 않는다. `AutomaticPaymentExecution`은 consume 전에 예정 회차도 기억한다. 중단 처리에서 새 TX로 저장 상태를 읽고, 원래 실행 ID의 이전 회차 또는 미리 기억한 예정 회차와 정확히 일치할 때만 그 보유 값으로 수동 표시한다. 새 소유자의 ID나 임의의 최신 회차를 자기 비교값으로 가져다 쓰지 않는다.

commit 뒤 만료·인계·완료가 확인돼 PG를 호출하지 못해도 소비한 회차는 되돌리지 않는다. 관찰 저장이나 상태 확인이 실패해도 PG 조회용 Retry 예외로 바꾸지 않는다. 확인이 불가능하면 로그와 기존 DB 미완료 기록을 남긴다. 재시작으로 새 자동 예산을 주지 않으며, 수동 대사는 계속 자동 회차를 소비/초기화하지 않는다.

## 사용자 결정

2026-10-21 사용자는 조회 작업 직전에 DB에서 사용 횟수를 기록하는 A를 선택했다.
기록 commit 직후 실제 조회 전에 프로세스가 종료되면 해당 회차를 소비하는 비용을 수용한다.
재시작 후 이미 소비한 회차는 되돌리지 않는다. 후속 결정으로 중단된 자동 실행은 재개하지 않고 담당자 수동 대사로 처리한다. 최초+추가 3회의 자동 예산을 새로 부여하지 않는다.

2026-10-22 후속 결정: 회차 commit 후 회로가 조회를 차단해도 **확보한 회차는 소비한 채 유지하고 즉시 수동 전환**한다. 실제 HTTP 호출은 0회이며 회로 정상/실패 표본에도 넣지 않는다.
수동 대사/callback은 자동 회차를 소비하지 않는다. 실행기 접수와 명확한 거절 뒤 100ms 재접수도 회차를 소비하지 않는다. [회차·HTTP·회로 카운팅 표](02-lookup-circuit-breaker.md#카운팅을-읽는-방법)를 따른다.

계획 리뷰 후 사용자가 승인한 보완: **회차 commit 후 실행 권한/완료 상태를 별도 짧은 TX로 다시 확인하고, PG 조회 직전에 시간 예산을 재검사**한다. 만료·완료·인계 시 HTTP 없이 종료해도 이미 소비한 회차는 유지한다. 옛 실행은 새 소유자의 상태를 바꾸지 않는다. 재확인에 실패하면 PG를 호출하지 않고 기존 DB 확인 실패 정책을 따른다. 확인 직후의 경합까지 완전히 막는 취소 프로토콜은 추가하지 않는다. 이미 시작한 조회의 사실 저장과 진행의 실행 ID 보호를 유지한다. [상세 계획](../plan.md)·[승인/재리뷰 기록](../review.md)을 따른다.

## 판단할 문제

최초 조회+추가 최대 3회의 예산은 DB 진행 기록으로 보존하고 재시작 시 초기화하지 않는다.
다만 DB 기록과 PG HTTP는 하나의 트랜잭션으로 묶을 수 없어 두 동작 사이에 프로세스가 종료될 수 있다.
조회 작업 전 기록과 응답 후 기록의 차이를 비교해 전자를 채택했다.
여기서는 조회 작업의 예산을 비교한다. 주문별 목록/개별 거래 GET의 실제 HTTP 호출 예산은 상세 조회 흐름과 함께 정한다.

## A. 조회 작업 직전에 DB에서 횟수 소비 · 채택

- 필요한 대기가 끝나고 실행할 때 DB에서 남은 예산·종결/수동 상태·실행 권한을 확인하고 해당 회차 사용을 commit한다.
- commit 이후 PG 조회 작업을 수행한다. 기록에 실패하거나 예산이 없으면 해당 조회를 시작하지 않는다.
- PG 조회 오류가 이미 commit한 회차 기록을 rollback하지 않도록 기록 TX와 HTTP 경계를 분리한다.
- 프로세스가 종료되면 이미 소비한 회차는 사용한 것으로 유지한다. 후속 정책에 따라 자동으로 다음 회차를 재개하지 않고 담당자 수동 대사 대상으로 남긴다.
- 실행 권한과 예산을 원자적으로 보호하면 재시작 때문에 조회 작업 예산이 늘어나는 것을 막기 쉽다.
- 비용: 기록 commit 직후 실제 HTTP 이전에 멈추면 PG를 조회하지 못했어도 한 회를 사용한다. 마지막 회차면 수동 확인으로 넘어갈 수 있다.

```text
추가 재조회 1회 사용 기록 commit
→ 실제 조회 직전에 프로세스 종료
→ 재시작 시 추가 재조회 2회가 남은 기록 보존
→ 자동 재개하지 않고 담당자 수동 대사 대상으로 조회
```

## B. 조회 응답을 관찰한 뒤 DB에서 횟수 소비 · 미채택

- 조회 작업의 응답/오류를 관찰한 뒤 사용한 횟수와 다음 진행을 저장한다.
- 시작 전 종료된 작업은 예산을 소비하지 않으며 완료를 관찰한 작업 위주로 셀 수 있다.
- 비용: 조회 후 DB 기록 전에 프로세스가 종료되면 이미 수행한 조회가 기록되지 않는다. 재시작 후 같은 회차를 다시 실행할 수 있다.
- 종료가 반복되면 실제 조회 작업 수가 최초+추가 3회를 넘을 수 있다. 이를 막으려면 실행 중 회차를 별도로 기록하고 재개 규칙을 추가해야 한다.

```text
추가 재조회 1회 실행
→ 사용 기록 저장 전에 프로세스 종료
→ 재시작 시 해당 회차가 미사용으로 보임
```

## 선택 이유와 남은 질문

A는 조회하지 못한 회차가 소비될 수 있다는 비용을 수용하고 재시작 시 남은 예산과 수동 전환 기준을 보수적으로 유지하기 위해 채택했다.
이 결정은 PG 결제 생성 재발송이나 재고 복구를 허용하는 근거가 되지 않는다.
조회 횟수 소진은 조회 자동화를 중단하는 기준이며, 이미 검증된 결과의 내부 반영 예산과 결제 결과를 바꾸지 않는다.
마지막 회차 기록 뒤 조회 전에 종료됐고 재시작 시에도 미확인이라면, 새 회차를 부여하지 않고 수동 확인으로 넘긴다.

- 회로 차단의 확보 회차 소비·즉시 수동 정책은 확정했다. 실제 동시 실행/실패 분기의 CAS 조건은 상세 설계에서 구체화한다.
- 진행 중 회차의 소유권·동시 실행·만료를 어떻게 보호할지.
- 회차의 DB commit 결과가 불명확한 경우 저장 상태를 확인해 중복 소비/실행을 어떻게 막을지.
- 종료 중 도착한 callback과 재시작 복구의 경합에서 다음 조회를 어떻게 중단할지.
- 후속 결정으로 commerce의 지터 값·다음 실행 예약 시각은 저장하지 않는다. 런타임에서 대기하고 종료 뒤 자동 재개하지 않는다. 사용 횟수·실행/진행·최근 시각·오류는 보존한다.

지터/예약 정보 영속화 제외와 수동 실행 ID 교체는 [최소 보완 결정](../../r01-pg-payment-foundation/trade_off/10-learning-scope-completion.md)으로 확정했다. 회로 차단 계수는 위 후속 결정을 따르며 정확한 자동 실행 조건식/추가 필드는 상태 전이·저장 구조·실제 호출 수 검증에 연결한다.
R01의 [복구 진행 기록 저장 경계](../../r01-pg-payment-foundation/trade_off/06-recovery-progress-storage.md)는 별도 pay 작업 모델로 확정했다.
[재고 차감·복구 기록](../../r01-pg-payment-foundation/trade_off/07-stock-adjustment-boundary.md)은 mall의 별도 모델·같은 TX 복구로 후속 확정했다.
R02의 [파사드·TX 경계](../../r02-pg-order-payment/trade_off/01-facade-transaction-boundary.md)는 조율 파사드 + 별도 준비/공통 결과 반영 TX 컴포넌트로 후속 확정했다. 현재 질문 순서는 [R01 목록](../../r01-pg-payment-foundation/trade_off/total_trade_off.md)을 따른다.
