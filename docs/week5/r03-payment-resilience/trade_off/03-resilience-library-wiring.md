# 재시도·서킷브레이커 라이브러리 연결

[결정 목록](total_trade_off.md) · [재확인 정책](01-reconciliation-retry-policy.md) · [회로 집계](02-lookup-circuit-breaker.md) · [작업 실행](06-reconciliation-execution.md)

상태: **2026-10-23 정책 구현·세 관점 기능 리뷰·최종 검증 완료**. 전체 검사 509건과 실제 PG 장애/재시작 실험 14건의 증거·검증 한계는 [결과](../result.md)를 따른다. 아래 논의는 결정 과정이며 현재 클래스와 완료 범위는 [계획](../plan.md)·[리뷰 기록](../review.md)에 연결한다. 원격 PR은 후속 범위다.

## 이번에 바뀐 결정

사용자는 자동 조회 재시도와 서킷브레이커를 **모두 Resilience4j로 통일**하기로 했다. 이전의 Spring Retry `@Retryable` 선택은 이 결정으로 대체한다. Spring Retry와 Resilience4j를 함께 사용하는 안은 채택하지 않았다.

- Resilience4j Retry: 허용된 자동 조회의 반복과 대기를 제어한다.
- Resilience4j CircuitBreaker: 자동·수동 대사·callback이 공유하는 PG 조회 회로다.
- DB: 사용 회차·실행 ID·진행 상태를 계속 보존한다. 라이브러리의 메모리 상태가 이 기록을 대신하지 않는다.

라이브러리를 통일해도 최초 조회＋추가 3회, 1·3·10초와 지터 ±20%, 30초 예산, 조회 직전 회차 commit과 중단 시 수동 대사 정책은 그대로다.

## 경로별 적용 범위

| 경로 | 자동 조회 Retry | 공유 조회 CircuitBreaker |
|---|---|---|
| 최초 confirm이 시작한 백그라운드 자동 조회 | 최대 4회·예산/사유에 따라 조기 중단 | 매 PG 조회에 적용 |
| 고객/관리자 수동 대사 | 적용하지 않음. 저장 종결 재적용은 조회 0회, 그 외 요청당 최대 1회 | 실제 PG 조회에 적용 |
| callback의 권위 조회 | 자동 반복 없음 | 실제 PG 조회에 적용 |
| PG 결제 생성 POST | 적용하지 않음 | 조회 회로 범위 밖 |
| 저장한 종결 근거의 공통 업무 반영 | PG 조회 Retry와 별도인 데드락 추가 1회/100ms 정책 | 조회 회로 범위 밖 |
| 고객 주문 GET·운영 미완료 목록 GET | PG 호출 없음 | PG 호출 없음 |

## 연결에서 지킬 경계

첫 기능은 `PaymentLookupGateway` → `CircuitPaymentLookupGateway`의 공개 `@CircuitBreaker` 진입점 → 기존 HTTP adapter 순서로 연결했다. Resilience4j는 commerce 앱에서 BOM 2.3.0으로 정렬했다. Spring Cloud BOM의 일부 2.2.0과 2.3.0 starter가 섞일 때 생긴 클래스 누락을 해소하고 실제 프록시 검사로 확인했다. 회로 지표·상태 전이 로그와 두 Retry의 기본 지표도 연결했고 실제 Prometheus 응답으로 확인했다.

자동 작업의 한 회차는 **사용 회차 DB commit → 회로를 거친 PG 조회 → 관찰 저장 → 공통 업무 반영**으로 구분한다. 계속 조회할 이유가 있을 때만 정한 간격을 기다린다.

- 회로는 한 번의 PG 조회와 응답 검증 결과를 측정한다. DB 처리·재시도 대기·전체 자동 작업을 회로 표본에 섞지 않는다.
- 조회 요청에 기존 결제 결과·생성 전 거절 사실을 함께 전달해 알려진 종결/존재 충돌을 제외한다. 제외 fallback은 원래 관찰을 복원해 저장 TX가 충돌을 보존하도록 한다. 조회 도중 다른 실행의 저장으로 뒤늦게 발견된 충돌은 표본을 소급 변경하지 않는 승인 한계이며 [집계 문서](02-lookup-circuit-breaker.md)를 따른다.
- Retry가 다시 실행할 때도 현재 상태·실행 ID·남은 횟수/시간을 확인한다. PG 생성이나 이미 끝난 업무를 자동 조회 반복에 넣지 않는다.
- PG adapter의 결과값을 정상·실패·제외로 구분하고, 재조회 여부는 별도로 판단한다. PENDING은 회로 정상이어도 재조회할 수 있고, 계약 오류는 회로 실패여도 즉시 수동이다.
- 라이브러리 교체로 기본 재시도 횟수나 기본 대기 값을 사용하지 않는다. 별도의 HTTP client 재시도도 추가하지 않는다.

## 애노테이션 연결 · 확정

사용자는 **Resilience4j 애노테이션**을 선택했다. API 직접 호출 제안은 채택하지 않았다. Spring Retry의 `@Retryable`로 돌아가는 선택이 아니다.

| 방식 | 이해하는 방법 | 이득·비용 |
|---|---|---|
| API 직접 호출 · 미채택 | 코드에서 Retry로 반복 구간을 감싸고, 내부의 PG 조회만 CircuitBreaker로 감쌈 | 실행 순서와 집계 경계가 드러나지만 연결 코드가 필요함 |
| `@Retry`·`@CircuitBreaker` · 채택 | 별도 메서드에 애노테이션을 붙여 Spring 프록시가 동작을 연결함 | 호출부는 짧아지지만 프록시 호출과 적용 경계를 함께 확인해야 함 |

### 적용할 위치와 지킬 조건

- `@Retry`는 자동 조회 한 회차의 진입점에 둔다. 매번 현재 상태·실행 ID·횟수/시간 예산을 확인하고, 허용한 조회 결과만 추가 시도로 연결한다.
- `@CircuitBreaker`는 PG 조회 전용 진입점에 둔다. 조회 HTTP와 응답 검증 결과를 분류하며 회차 저장·관찰 저장·업무 반영 TX와 재시도 대기는 포함하지 않는다.
- 두 진입점은 별도 Spring 빈의 공개 메서드로 나눠 프록시를 거쳐 호출한다. 같은 객체 안의 직접 메서드 호출로 애노테이션이 적용됐다고 가정하지 않는다.
- 생성 POST에 조회 회로가 적용되지 않도록 조회 진입점을 분리한다. 자동/수동/callback은 같은 조회 회로 이름과 경계를 사용한다.
- adapter의 정상 반환 결과도 정상·실패·제외로 분류해야 한다. 애노테이션만 붙이고 모든 반환을 정상 집계하지 않는다.
- 회로 fallback은 조회 차단/확인 불가를 표현하고 마지막 검증 사실을 유지한다. DB 처리와 수동 전환은 회로 측정 구간 밖의 application 흐름에서 처리한다. 실제 타입·fallback 메서드와 예외 변환은 상세 계획에서 정한다.
- 프록시를 거친 실제 호출로 재시도 횟수·간격·집계 경계를 최소 검증한다. 직접 생성한 객체만 호출한 단위 검사로 애노테이션 적용을 확인했다고 기록하지 않는다.

## 운영 확인 범위 · 확정

사용자는 **기존 조회＋로그＋기본 지표**를 선택했다. 기존 조회/로그만 사용하는 안은 채택하지 않았다. 별도 운영 API나 대시보드는 추가하지 않는다.

| 확인할 내용 | 사용할 수단 |
|---|---|
| 이 주문이 아직 미완료인지, 몇 회 확인했는지, 왜 중단됐는지 | 기존 주문/미완료 조회의 복구 상태·사용 회차·최근 확인 시각·사유 |
| 어느 실행이 언제 조회하고 결과를 저장/반영했는지 | 주문·시도·실행 ID와 회차/결과를 포함한 로그 |
| PG 조회 회로 전체의 상태·성공/실패/차단·재시도 동작 | 기존 Prometheus에 연결한 Resilience4j 기본 지표 |

- 기존 응답 필드와 소유권/관리자 접근 계약을 유지한다. 회로 차단·시간 예산 소진·실행기 접수 거절 등 주요 중단 사유만 기존 사유 필드에서 구분한다. 구체적인 enum 이름은 상세 계획을 따른다.
- 마지막 확인 결제 결과와 복구 진행을 분리한다. 새 중단 사유가 PG FAILED나 주문 실패/재고 반환을 만들지 않는다.
- 회로 상태 전이와 수동 전환·표식 저장 실패를 로그에 남긴다. 카드 원문·PG 응답 원문은 저장하거나 로그에 남기지 않는다.
- 지표에는 회로/Retry 이름과 종류 같은 고정 태그만 사용한다. 주문·시도·실행 ID별 추적은 DB/로그에서 한다.
- Retry의 완료/실패 지표는 재확인 실행의 지표다. 실제 결제 성공률이나 실제 HTTP 호출 수와 같다고 해석하지 않는다. 회차·HTTP·회로 표본은 기존 구분을 유지한다.
- 자동 작업이 수동 전환을 마치고 정상 반환한 경우도 Retry 지표상 정상 종료일 수 있다. 업무 완료 여부는 주문·복구 APPLIED로, 중단 원인은 저장된 사유와 로그로 확인한다. ‘자동 PG 조회 준비’ 로그도 실제 HTTP 전송 횟수를 뜻하지 않는다.
- 기존 Prometheus 경로와 포트를 활용한다. OPEN을 이유로 전체 서비스의 health 상태를 바꾸는 별도 연결은 추가하지 않는다.

버전·의존성 모듈·구체적인 클래스/결과 변환·시간 예산 검사·소진 처리와 최소 검증은 [상세 구현 계획](../plan.md)에서 정한다. 이 문서는 기능 구현이나 검사 통과 기록이 아니다.
