# 자동 재확인 작업의 저장·실행 방식

[설계 질문 목록](total_trade_off.md) · [확정한 재확인 정책](01-reconciliation-retry-policy.md)

상태: **2026-10-23 정책 구현·세 관점 기능 리뷰·최종 검증 완료**. 전체 검사 509건과 실제 PG 장애/재시작 실험 14건의 증거·검증 한계는 [결과](../result.md)를 따른다. 아래 논의는 결정 과정이며 현재 클래스와 완료 범위는 [계획](../plan.md)·[리뷰 기록](../review.md)에 연결한다. 원격 PR은 후속 범위다.

## 실제 연결을 먼저 읽기

1. 최초 confirm의 PG 발송 승자만, 공통 업무 반영 뒤에도 PENDING이면 자동 시작을 요청한다. 같은 confirm 재요청은 READY 작업을 새로 시작하지 않는다.
2. `AutomaticPaymentStateService.claim`이 짧은 TX에서 조건을 확인하고 READY→RUNNING·실행 ID를 commit한다. 시작 가능한 작업이 아니거나 CAS에서 졌다면 전달하지 않는다.
3. `StartAutomaticPaymentRecoveryService`가 최초 전달 직전 단조 시간을 기억하고 전용 실행기에 보낸다. 스레드 2개·대기 2개이며, 대기 중에도 DB 상태는 RUNNING이다.
4. 명확한 접수 거절만 100ms 뒤 같은 ID로 전달을 한 번 더 시도한다. 재거절은 EXECUTOR_REJECTED, 접수 여부가 불명확하면 재전달 없이 DISPATCH_UNCERTAIN으로 수동 표시를 시도한다. 재접수 전 완료·실행 ID·시간을 다시 확인한다.
5. 실행기는 UseCase를 통해 별도 `RecoverAutomaticPaymentService`의 `@Retry` 프록시를 호출한다. 조회 회차를 먼저 commit하고, 새 TX에서 다시 권한/완료를 확인한 다음 PG 조회 직전 시간을 검사한다.
6. PG 조회→검증 관찰 commit→기존 공통 업무 반영 순서다. 허용한 미확인 결과만 다음 조회로 연결한다. 완료·충돌·인계·회로 차단·저장 오류는 반복하지 않는다.

Retry는 최초 포함 최대 4회다. 앞선 회차가 끝난 뒤 1·3·10초에 지터 ±20%를 적용하고, 전체는 최초 전달부터 30초 예산이다. 대기할 시간이 부족하면 남은 시간만 기다린 뒤 종료 표시를 통해 다음 회차를 소비하지 않는다. 이미 시작한 조회는 관찰 저장과 업무 반영을 마무리한다. 자동 반복이 종료돼도 PG 사실·차감 재고·소비 회차는 유지한다.

`payment.recovery.auto-start-enabled`는 기본 true다. test 프로필만 false로 설정해 기존 검사에서 백그라운드 작업과 DB 정리가 겹치지 않게 한다. 자동 컴포넌트를 제거한 것은 아니며 실제 프록시·DB 경계·실행기 용량은 별도 핵심 검사로 확인한다. 현재 검사에서는 긴 대기를 반복하지 않고 이 Retry 이름의 간격을 임시 교체한 뒤 복원한다. 라이브러리 전역 sleep은 바꾸지 않는다.

서버 중단 뒤 자동 회수·lease·재시작 스캔은 추가하지 않았다. 담당자가 기존 목록 GET으로 미완료를 찾고, 명시적 수동 대사 POST로 처리한다. 아래 대안 비교·당시 질문보다 이 실제 연결과 [최신 계획](../plan.md)을 우선한다.

## 최신 사용자 결정 우선

2026-10-21에는 Spring Retry @Retryable + DB 진행 기록을 선택하고, 서버 장애/재시작 뒤 자동 재개는 운영 담당자의 수동 대사로 변경했다. 2026-10-22에는 **재시도·회로 모두 Resilience4j**로 통일해 Spring Retry 선택을 대체했다. DB 기록과 중단 시 수동 대사 정책은 유지한다. [라이브러리 결정](03-resilience-library-wiring.md)을 따른다.
자동 만료/갱신·상시 회수는 보류한다. 현재 장애 복구 정책은 [운영 담당자 조회·수동 대사](../../r02-pg-order-payment/trade_off/06-interrupted-payment-reconcile.md)를 따른다.
후속 [최소 보완 결정](../../r01-pg-payment-foundation/trade_off/10-learning-scope-completion.md)으로 검증 결과 먼저 commit/업무 TX 분리·수동 실행 ID 교체·옛 진행 save 차단·commerce 지터/다음 예약 시각 영속화 제외를 확정했다. 아래 미채택 A/B의 예약 정보 저장을 현재 요구로 해석하지 않는다.

## 2026-10-22 · 첫 조회와 실행기 접수 실패 결정

- 자동 확인 대상의 첫 PG 조회는 **백그라운드 작업 시작 후 바로 실행**한다. 최초 고정 1초 대기안은 채택하지 않았다. 이후 추가 조회의 1·3·10초와 지터 ±20%는 유지한다.
- 실행기가 작업을 **명확히 접수 거절**하면 100ms 뒤 작업 전달만 한 번 재시도한다. 최초 전달까지 합쳐 최대 2번이며 다시 거절되면 수동 확인 필요를 저장한다.
- 이는 PG 생성/조회 재시도가 아니다. 접수 시도만으로 자동 조회 회차를 소비하거나 회로 정상/실패 표본을 만들지 않는다.
- 접수 여부가 불명확한 오류는 위 재전달 대상에서 제외한다. 저장 상태를 확인하고 미완료 상태를 담당자가 확인할 수 있게 남긴다. 이미 접수됐을 수도 있는 작업을 추측해 추가 전달하지 않는다.
- 비용은 접수 재시도 분기와 100ms 대기가 생기는 것이다. 명확한 접수 거절도 즉시 수동 전환하는 안보다 짧은 혼잡을 흡수할 수 있다.
- callback·수동 대사가 먼저 완료하거나 실행을 인계하면 최신 상태/실행 권한을 확인해 남은 자동 조회를 중단한다. PG HTTP가 이미 시작됐다면 검증 사실 저장과 진행 갱신의 권한은 구분한다.
- 자동·수동·callback PG 조회는 [공유 회로](02-lookup-circuit-breaker.md)를 사용한다. 자동 작업은 회로 차단 시 이미 확보한 회차를 유지하고 즉시 수동 전환한다.

## 2026-10-22 · 자동 조회 시작 경로 확정

사용자는 **최초 confirm에서만 자동 조회 시작**을 선택했다. 같은 주문·키의 재요청으로 READY 작업을 시작하는 안은 채택하지 않았다.

- 최초 PG 생성 발송 권한을 얻은 confirm이 PG 호출·관찰 저장·공통 반영을 처리한 뒤, 결과가 여전히 미확인/처리 중이고 작업을 시작할 수 있을 때만 자동 조회를 전달한다.
- 같은 confirm 재요청은 기존 계약대로 현재 상태를 반환한다. 자동 조회 작업을 새로 시작하거나 중단된 작업을 재개하지 않으며, PG 생성 재발송·자동 회차 초기화도 하지 않는다.
- 저장된 종결 결과의 내부 반영 실패나 식별 충돌을 PG 재조회로 해결하려 하지 않는다. 내부 반영의 제한된 재시도/수동 처리와 충돌의 수동 처리 정책을 따른다.
- 전달 전에 callback·수동 대사가 완료하거나 실행을 인계했다면 자동 조회를 시작하지 않는다. 구체적인 대상 검사·CAS 조건은 상세 설계에서 정한다.
- 이 선택으로 최초 PG 호출이 아직 진행 중일 때 재요청이 조회를 시작해 자동 회차를 일찍 소비하는 상황을 피한다. 최초 실행이 전달 전에 중단되면 고객의 confirm 재요청만으로 자동 조회가 복구되지는 않는다.

실행기 크기/대기 용량은 아래 후속 결정으로 확정했다. 위 결정은 구현 완료를 뜻하지 않는다.
실행 권한 저장과 전달 사이에 서버가 종료되면 미완료 DB 기록이 남는 한계를 수용하고, 기존 정책대로 재시작 뒤 운영 목록/수동 대사를 사용한다.

## 2026-10-22 · DB 실행 권한 확보 후 작업 전달 확정

사용자는 **DB 실행 권한 확보 → 백그라운드 작업 전달** 순서를 선택했다. 대기열에 먼저 넣고 작업이 시작될 때 권한을 얻는 안은 채택하지 않았다.

1. 최초 confirm의 자동 조회 대상인지 확인하고, 짧은 DB TX에서 READY→RUNNING 조건부 갱신과 실행 ID 저장을 수행한다.
2. 권한 확보가 commit된 뒤 해당 실행 ID를 담아 백그라운드 실행기에 전달한다. PG HTTP와 대기 동안 DB TX/잠금을 유지하지 않는다.
3. 실제 작업은 현재 상태와 실행 ID를 확인한다. callback 완료·수동 인계 등으로 권한을 잃었다면 남은 자동 조회를 시작하지 않는다.
4. 허용된 PG 조회 직전에 별도의 짧은 TX로 자동 회차 사용을 commit한다. 권한 확보나 대기열 접수만으로는 조회 회차를 소비하지 않는다.

- RUNNING은 실제 PG 조회뿐 아니라 **실행 권한을 확보하고 전달/실행을 기다리는 상태**도 포함한다. RUNNING·사용 횟수 0은 가능한 조합이다.
- 명확한 접수 거절 뒤 100ms 재전달은 같은 실행 ID를 사용하며 새 작업 권한·30초 예산을 부여하지 않는다. 전달 시점의 완료/인계와 늦은 실패 표시는 기존 실행 ID 보호를 유지한다.
- 대기열에서 기다리는 시간도 최초 전달부터 계산하는 30초 예산에 포함한다. 권한 확보 뒤 전달 전 종료되거나 접수 후 서버가 종료되면 담당자가 미완료 목록에서 찾아 수동 대사한다.
- 이 순서로 전달 실패와 실행 진행을 같은 실행 ID로 추적할 수 있다. 대신 RUNNING만 보고 현재 HTTP가 진행 중이라고 해석할 수 없으며, DB commit과 메모리 실행기 전달을 하나의 원자적 작업으로 보장하지 않는다.

실행기의 동시 처리 수·대기 용량은 아래 후속 결정을 따른다. 구체적인 대상 검사/오류 연결은 상세 설계에서 정한다. 자동 회수·lease·영속 큐를 추가하는 결정은 아니다.

## 2026-10-22 · 전용 실행기 동시 2개·대기 2개 확정

사용자는 **전용 스레드 2개·대기 작업 최대 2개**를 선택했다. 스레드 2개·대기 10개 안은 채택하지 않았다. 운영 부하 측정으로 산출한 최적값이 아니라 학습용 초기 설정이다.

- 자동 조회 전용 실행기는 고정 스레드 2개와 용량 2의 대기열을 사용한다. 한 작업은 PG 조회·결과 처리뿐 아니라 1/3/10초 재조회 대기 동안에도 해당 스레드를 사용한다.
- 동시에 실행 중인 작업이 2개이고 대기 중인 작업도 2개라면 새 전달은 접수 거절된다. 기존 정책대로 100ms 뒤 같은 실행 ID의 작업 전달만 한 번 더 시도하고, 다시 거절되면 현재 실행에 한해 수동 전환한다.
- 작업을 호출한 confirm 스레드에서 대신 수행하거나 접수 실패를 숨겨 버리는 정책은 사용하지 않는다. 정한 백그라운드 실행과 명확한 접수 거절 경로를 유지한다.
- 대기열에 있는 동안도 RUNNING이고 자동 조회 30초 예산이 흐른다. 실행 차례가 왔을 때 이미 예산이 끝났다면 새 PG 조회/회차 소비 없이 현재 상태·실행 권한을 확인해 미완료를 수동 전환한다. 대기 중 정확히 30초에 별도 타이머가 처리한다는 뜻은 아니다.
- 작은 용량으로 혼잡·접수 거절·대기 중 예산 소진을 쉽게 실험할 수 있다. 대신 여러 결제가 몰리면 대기 10개 안보다 접수가 일찍 거절되어 수동 확인 대상이 늘 수 있다.

구현할 실행기 빈과 종료 처리·설정 위치는 상세 계획에서 정한다. 이 결정은 자동 실행·실험을 완료했다는 의미가 아니다.

## 판단할 문제

확정한 최초 조회+추가 3회·1/3/10초·지터 ±20% 정책을 정상 실행에 적용하고 장애 중단 기록은 담당자가 확인할 수 있어야 한다.
PG 내부의 자동 거래 완료 방식과 commerce의 자동 재확인 실행 방식은 별개다. 이 문서는 commerce만 비교한다.
재시작으로 횟수가 초기화되거나 callback과 예약 작업이 같은 주문을 중복 반영하지 않도록 설계한다.
업무 결과 반영은 R02의 공통 멱등 경계를 사용한다. 구체적인 저장 필드·잠금/점유 방식은 선택 후 논의한다.

## 사용자 결정 · C. Resilience4j Retry + DB 진행 기록 + 중단 시 수동 대사

2026-10-21 처음에는 @Retryable + DB 기록 + 재시작 후 남은 횟수 재개를 선택했지만, 후속 결정으로 재시작 자동 재개를 담당자 수동 대사로 변경했다.
2026-10-22 최신 결정으로 아래 현재 실행에는 Spring Retry 대신 Resilience4j Retry를 사용한다. 앞선 @Retryable 선택은 당시 기록이다.
앞서 비교한 A/B가 유일한 대안은 아니며, 기존 A 추천을 C 채택으로 대체한다. 주기 조회 스케줄러 도입은 이번 선택에 포함하지 않는다.

- 백그라운드에서 기존 거래 조회를 실행하고 Resilience4j Retry로 최초 조회+추가 최대 3회를 제어한다.
- 앞선 확인 종료 후 1초·3초·10초, 지터 ±20%를 사용자 정의 대기 정책으로 연결한다.
- PG 결과와 내부 반영 진행, 사용한 조회 횟수·재개에 필요한 진행 정보를 commerce DB에 보존한다. 구체적인 컬럼/모델은 후속 설계 대상이다.
- PENDING·빈 조회처럼 정상 응답이어도 재확인이 필요한 결과를 우리 코드가 분류해 재시도 제어에 연결한다. 이를 결제 실패로 저장하지 않는다.
- 한도 소진 후 처리 경계에서 수동 확인 필요를 영속화한다. 즉시 수동 전환 오류도 같은 정책을 따른다. 구체적인 연결 방식은 상세 설계에서 정한다.
- commerce 재시작 자체가 미완료 작업의 PG 조회를 자동 재개하지 않는다. 담당자가 미완료 목록에서 기록을 확인하고 수동 대사로 기존 거래를 조회한다.
- 반영 완료한 작업은 다시 실행하지 않는다. 늦은 callback·수동 대사의 검증된 결과는 공통 멱등 경계에서 처리한다. 수동 대사 요청으로 자동 재시도 예산을 초기화하지 않는다.
- PG 생성 POST에는 Retry를 적용하지 않는다. 이미 확인된 결과의 내부 반영 재시도는 생성 호출을 포함하지 않는다.

### 실행 흐름 예시

```text
PG 결과 확인 필요
→ DB 진행 기록 + 백그라운드 작업 시작
→ 기존 거래 최초 조회
→ 필요하면 1초/3초/10초에 지터를 적용해 추가 재조회
→ 검증된 결과를 공통 TX에서 반영하거나 수동 확인으로 전환

중간에 프로세스 종료
→ 미완료 DB 기록 보존
→ 담당자가 미완료 목록 조회
→ 명시적인 수동 대사로 기존 거래 조회·공통 결과 반영
```

PG HTTP 호출·대기는 DB TX와 잠금 밖에서 수행한다. 결과 반영은 별도의 짧은 TX에서 보호한다.
재시도 라이브러리의 메모리 상태가 영속적인 진행 기록을 대신하지 않는다.
Resilience4j의 Retry 상태도 DB 진행 기록이나 재시작 복구를 대신하지 않는다. 현재 정책은 재시작 자동 재개가 아니라 기록 보존과 수동 대사다.

### 이득·비용

- 반복 호출·대기·소진 후 분기는 라이브러리에 맡기면서 영속적인 업무 사실과 재개 기준은 DB로 유지한다.
- 상시 작업 탐색·재시작 자동 회수 대신 운영 담당자의 기존 수동 대사 경로를 사용한다. 중단 기록은 담당자 처리까지 남을 수 있다.
- 사용자 정의 대기·진행 기록·수동 대사 연결과 동시 실행 조율은 별도로 구현해야 한다.
- 기본 애노테이션만 붙인 구성은 확정한 간격·PENDING 재확인·DB 진행 기록·중단 작업 조회/대사를 모두 충족하지 않는다.

## A. DB에 예약을 기록하고 실행 시간이 된 작업을 주기 조회 · 이전 비교·미채택

- commerce DB에 재확인 진행 정보·사용한 재시도 횟수·다음 실행 시각 등을 기록한다. 실제 컬럼/테이블 구조는 아직 미정이다.
- worker가 실행 시간이 된 대상을 주기적으로 찾아 조회·결과 반영 후 다음 예약 또는 종결/수동 전환을 기록한다.
- DB에 예약이 남으므로 commerce가 재시작해도 미완료 작업을 다시 찾기 쉽다.
- 예약 대상 탐색을 위해 DB를 주기 조회하는 비용과 적절한 인덱스가 필요하다.
- 실제 실행은 예정 시각보다 polling 주기·작업 대기만큼 늦어질 수 있다. 1/3/10초는 정확한 실행 시각 보장이 아니다.
- PG HTTP 동안 DB 트랜잭션/잠금을 유지하지 않도록 점유·조회·반영 경계를 분리해야 한다.
- 여러 worker의 중복 점유 방지와 작업 중 프로세스 종료 시 재개 기준은 추가 설계가 필요하다.

## B. DB에 진행을 기록하고 메모리 타이머로 실행 · 이전 비교·미채택

- DB에 진행/횟수/예정 시각을 저장하고 프로세스의 예약 실행기에 타이머를 등록한다.
- 평상시에는 타이머가 깨우므로 주기적인 DB 대상 탐색을 줄이고 예정 시각에 가깝게 실행하기 쉽다.
- 프로세스가 종료되면 타이머는 사라진다. 시작 시 DB를 읽어 복원하고, DB 저장 후 타이머 등록 전에 멈춘 작업도 회수해야 한다.
- callback 종결과 타이머 취소, 재시작 복원과 기존 실행의 경합을 함께 처리해야 한다.
- 여러 인스턴스를 고려하면 DB 점유·소유권 확인도 필요하다. 메모리 타이머만으로 중복 실행을 막을 수 없다.

이전 비교안도 DB 기록을 기준으로 삼았다. 현재는 기록을 보존해 담당자 수동 대사에 사용하며 A/B의 자동 회수 경로를 도입하지 않는다.

## 선택 후 남은 질문

- 첫 조회 즉시·접수 거절 100ms 뒤 전달 1회 재시도·최초 confirm에서만 시작·DB 실행 권한 commit 후 전달·전용 동시 2개/대기 2개는 확정했다. 정확한 자동 시작 대상 조건·실행기 빈/종료 처리·구체적인 오류 연결은 상세 설계 대상이다.
- 진행 기록은 후속 결정으로 별도 pay 복구 작업 모델에 둔다. 정확한 필드·관계·저장 구조는 후속 설계 대상이다.
- 수동 인계의 실행 ID 조건부 교체·옛 진행 갱신 차단 방향은 확정했다. 정확한 조건식/허용 상태·응답·callback 경합 처리는 상세 설계 대상이며 자동 만료/회수는 도입하지 않는다.
- 조회 직전 회차 사용을 commit하고 재시작 후 되돌리지 않는다. 구체적인 횟수/진행 기록 구조는 후속 설계 대상이다.
- 회로 차단은 이미 확보한 자동 회차 소비·즉시 수동이며 실제 HTTP/회로 표본은 0이다. 내부 반영은 확실히 rollback된 MySQL 데드락에만 100ms 뒤 추가 1회로 확정했다. 실제 예외 변환은 상세 설계 대상이다. [반영 정책](01-reconciliation-retry-policy.md#검증-결과의-내부-반영-재시도--확정)을 따른다.
- 자동 조회는 최초 작업 전달부터 대기열·재접수·조회·재시도 대기를 포함해 30초이며 이미 시작한 조회의 결과 저장/반영은 마무리한다. 수동 대사는 기존 요청당 최대 1회 조회를 유지한다. 백그라운드 실행기·미완료 목록 추가 필드의 필요성은 상세 설계에서 정한다.
- 조회 직전 횟수 소비와 작업 점유를 어떻게 원자적으로 보호할지, commit 결과 불명확 시 저장 기록을 어떻게 확인할지.
- Resilience4j @Retry·@CircuitBreaker 애노테이션 연결은 확정했다. 버전·구체적인 빈·사용자 정의 대기와 소진 처리·DB TX 경계를 상세 계획에서 연결한다.

최초 조회와 추가 3회의 예산은 재시작 시 초기화하지 않는다. 후속 결정으로 [조회 직전 DB 횟수 소비](07-retry-attempt-accounting.md)를 채택했다.
라이브러리의 기본 최대 시도 수를 매번 그대로 재사용하거나, 다른 retry 계층을 중첩해 전역 예산을 늘리지 않는다.

이 선택이 정확히 한 번의 HTTP 조회를 보장하는 것은 아니다. 각 허용 회차에서 같은 거래를 반복 조회할 수 있으며 실제 HTTP 호출 구성·동시 실행 조율은 추가 설계가 필요하다.
반복 조회에서도 주문 확정·재고 복구는 공통 TX/멱등 경계에서 한 번만 반영해야 한다.

후속 결정으로 R01의 [결제 결과·재확인 진행 상태를 분리](../../r01-pg-payment-foundation/trade_off/05-payment-attempt-state.md)했다.
[횟수 소비 시점과 진행 중 종료 회차](07-retry-attempt-accounting.md)는 조회 직전 기록으로 확정했다.
R01의 [복구 진행 기록 저장 경계](../../r01-pg-payment-foundation/trade_off/06-recovery-progress-storage.md)는 별도 pay 작업 모델로 분리하기로 확정했다.
[재고 차감·복구 기록](../../r01-pg-payment-foundation/trade_off/07-stock-adjustment-boundary.md)은 mall의 별도 모델·같은 TX 복구로 후속 확정했다.
R02의 [파사드·TX 경계](../../r02-pg-order-payment/trade_off/01-facade-transaction-boundary.md)는 조율 파사드 + 별도 준비/공통 결과 반영 TX 컴포넌트로 후속 확정했다. 현재 질문 순서는 [R01 목록](../../r01-pg-payment-foundation/trade_off/total_trade_off.md)을 따른다.

참고: [Resilience4j Retry 공식 설명](https://resilience4j.readme.io/docs/retry). 이전 Spring Retry 비교는 당시 선택 기록이며 현재 라이브러리는 위 후속 결정이 우선한다.
