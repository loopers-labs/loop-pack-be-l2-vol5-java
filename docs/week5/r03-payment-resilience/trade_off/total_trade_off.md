# R03 설계 질문·결정 목록

상태: **2026-10-23 정책 구현·세 관점 기능 리뷰·최종 검증 완료**. 전체 검사 509건과 실제 PG 장애/재시작 실험 14건의 증거·검증 한계는 [결과](../result.md)를 따른다. 아래 논의는 결정 과정이며 현재 클래스와 완료 범위는 [계획](../plan.md)·[리뷰 기록](../review.md)에 연결한다. 원격 PR은 후속 범위다.

## 확정한 제약

- 회복 도구는 기존 거래 조회를 제어한다. create 자동 재시도는 허용하지 않는다.
- 조회 실패·회로 차단은 결제의 최종 실패 증거가 아니며, fallback은 저장 상태와 확인 불가를 표현한다.
- 처리 중·결과 미확인에서는 차감 상태를 유지하고, 검증한 확정 실패만 한 번 복구한다.
- 실제 호출 횟수·외부 거래·DB 결과로 검증하며 미실행·skip을 완료로 세지 않는다.
- 사용자 결정으로 최초 조회 후 추가 재조회 최대 3회, 간격 1초·3초·10초와 지터 ±20%를 적용한다. 실패/수동 전환 기준도 01에서 확정했다.
- 정상 실행은 Resilience4j Retry + DB 진행 기록을 사용한다. 기존 Spring Retry @Retryable 선택은 2026-10-22 결정으로 대체했다. 장애/재시작 뒤 자동 재개는 담당자 수동 대사로 변경했다. 자동 만료/회수·주기 조회 스케줄러는 도입하지 않는다.
- 조회 직전 해당 회차 사용을 DB에 commit한다. 기록 뒤 HTTP 전에 종료돼도 소비를 취소하지 않고 남은 예산을 보존한다. 재시작 자동 재개는 하지 않는다.
- 자동·수동 대사·callback PG 조회는 하나의 회로를 공유한다. 생성 POST는 적용 범위 밖이고 저장 종결 근거의 내부 재적용은 OPEN에도 가능하다.
- 자동 작업은 회로 차단 시 즉시 수동 전환한다. 먼저 commit한 회차는 소비한 채 유지하고 실제 HTTP 0회·회로 표본 제외와 구분한다.
- 최초 자동 조회는 작업 시작 후 별도 대기 없이 실행한다. 실행기가 명확히 접수 거절하면 100ms 뒤 전달만 1회 재시도하며 재거절은 수동 전환이다. 전달 자체는 PG 조회/생성·자동 회차 소비가 아니다.
- 자동 조회는 최초 PG 발송 권한을 얻은 confirm에서 PG 처리 뒤에도 미확인/처리 중인 경우에만 시작한다. 같은 confirm 재요청은 현재 상태를 반환하며 READY 작업의 시작·중단 자동 작업 재개·회차 초기화를 하지 않는다. 시작을 놓친 작업은 수동 대사로 처리한다.
- 백그라운드 전달 전에 짧은 DB TX에서 READY→RUNNING과 실행 ID를 commit한다. 대기 중에도 RUNNING이며 권한 확보/접수는 조회 회차를 소비하지 않는다. 작업은 현재 실행 ID를 확인하고 조회 직전에 회차를 따로 commit한다. 전달과 DB 저장 사이의 중단은 수동 대사로 처리한다.
- 학습용 전용 실행기는 고정 스레드 2개·대기 작업 최대 2개다. 재조회 대기 동안도 작업이 스레드를 사용한다. 포화 시 명확한 접수 거절 경로를 사용하며 대기 중도 30초 예산에 포함한다. 실행 차례에 이미 만료됐다면 새 조회 없이 미완료를 수동 전환한다.
- 회로 실패는 timeout·통신 오류·5xx·408·429·잘못된 정상 응답이다. 검증한 SUCCESS/FAILED/PENDING과 계약상 거래 없음은 정상, 다른 4xx·식별 충돌·우리 DB/접수 실패·회로 차단은 집계 제외다. 상세 경로/처리 표는 [02](02-lookup-circuit-breaker.md)를 따른다.
- 조회 HTTP 오류 중 408·429·500·502·503·504만 예산 내 재조회한다. 나머지 5xx는 회로 실패로 집계하지만 즉시 수동 전환한다. timeout·통신 오류·PENDING·계약상 거래 없음의 기존 재조회 정책은 유지한다.
- Retry-After는 학습 범위에서 미지원이다. 기존 1·3·10초＋지터 ±20%와 30초 예산을 유지하며, 외부 PG가 지정하는 대기 시간을 따르지 못하는 한계를 기록한다.
- 조회 계약 밖 2xx/3xx는 회로 실패 집계·즉시 수동 전환이다. 생성 POST의 정상 202와 구분하며 성공 추측·redirect 추적·임의 종결/재고 반환은 하지 않는다.
- 자동 조회 Retry와 공유 조회 CircuitBreaker는 모두 Resilience4j로 통일한다. 횟수·간격·지터·30초 예산·DB 진행 기록 정책은 유지한다. 연결은 Resilience4j @Retry·@CircuitBreaker 애노테이션으로 확정했다. [03](03-resilience-library-wiring.md)을 따른다.
- 운영 확인은 기존 주문/미완료 조회＋로그＋Resilience4j 기본 지표다. 주요 중단 사유를 기존 사유 필드에서 구분하고 기존 Prometheus를 활용한다. 별도 운영 API/대시보드·주문별 지표 태그는 추가하지 않는다.
- 회로의 CLOSED 집계는 건수 기준 최근 10건·최소 5건부터 판단하며 실패율 50% 이상 또는 1초 초과 조회의 느림 비율 50% 이상이면 차단한다. 제외 결과는 정상/실패/느림 표본과 분모에서 뺀다. OPEN은 10초 뒤 새 조회 요청에서 탐색하며 자동 탐색 요청은 만들지 않는다. HALF_OPEN은 집계 대상 2건으로 판단하고 두 건 모두 빠른 정상이어야 복귀한다. HALF_OPEN 진입 후 최대 10초 안에 판정하지 못하면 재차단한다.
- 자동 조회는 PG 생성 처리 뒤 실행기에 처음 전달하는 시점부터 대기열·재접수·조회·재시도 대기를 포함한 30초 예산이다. 만료 뒤 새 조회/추가 대기는 중단하고 미완료는 수동 전환한다. 이미 시작한 조회와 결과 저장·반영은 마무리하므로 강제 종료 시간이 아니다.
- 저장된 검증 결과의 내부 반영은 확실히 rollback된 MySQL 데드락(1213·SQLSTATE 40001)에만 100ms 뒤 추가 1회다. PG 호출·자동 조회 회차·회로 표본은 추가하지 않는다. 잠금 대기 timeout·연결 끊김·영구적 문제/재고 반환 overflow는 재시도 대상이 아니며 commit 결과가 불명확하면 저장 상태부터 확인한다.
- [학습용 최소 보완](../../r01-pg-payment-foundation/trade_off/10-learning-scope-completion.md)으로 관찰 먼저 commit/업무 TX 분리·수동 실행 ID 교체·commerce 지터/예약 정보 영속화 제외를 확정했다. PG의 DB 예정 거래 주기 조회는 commerce 재시작 자동 조회와 별개다.

[재고 차감·복구 기록](../../r01-pg-payment-foundation/trade_off/07-stock-adjustment-boundary.md)은 mall의 별도 모델·같은 TX 복구로 후속 확정했다.
