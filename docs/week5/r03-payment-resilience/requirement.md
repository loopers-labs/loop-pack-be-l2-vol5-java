## 회복 전략

- 실제 HTTP timeout과 create 재시도 차단은 R01부터 적용한다. 이 PR에서 새로 시작하는 항목으로 미루지 않는다.
- 기존 거래는 최초 조회 후 추가 재조회 최대 3회 수행하고, 각 확인 종료 후 1초·3초·10초 대기에 지터 ±20%를 적용한다.
- 첫 자동 조회는 백그라운드 작업 시작 후 바로 실행한다. 실행기가 명확히 접수를 거절하면 100ms 뒤 전달만 1회 재시도하며 재거절은 수동 전환이다. 접수 여부가 불명확하면 재전달하지 않는다. 전달 자체는 조회 회차·PG 호출·회로 표본이 아니다.
- 자동 조회 시작은 최초 PG 발송 권한을 얻은 confirm에서 PG 처리 뒤에도 미확인/처리 중이며 시작 가능한 작업에만 허용한다. 같은 confirm 재요청은 현재 상태를 반환하고 READY 작업을 시작하거나 중단 작업을 자동 재개하지 않는다. 시작 전 중단은 기존 미완료 목록·명시적 수동 대사로 처리한다. 저장 종결 결과의 내부 반영 실패·충돌은 각각의 반영/수동 정책을 따른다.
- 실행기에 전달하기 전에 짧은 DB TX에서 READY→RUNNING과 실행 ID를 commit한다. RUNNING은 대기열에서 기다리는 상태도 포함한다. 권한 확보/접수 자체는 조회 회차를 소비하지 않고, 실제 작업이 현재 실행 ID를 확인한 뒤 조회 직전에 회차를 따로 commit한다. 명확한 접수 거절의 재전달도 같은 실행 ID를 사용한다.
- 자동 조회 전용 실행기는 고정 스레드 2개·대기 작업 최대 2개로 시작한다. 재조회 대기 동안도 스레드를 사용하고, 포화 시 정해진 접수 거절/재전달/수동 전환을 따른다. 대기 시간도 30초 예산에 포함하며 실행 차례에 이미 만료됐다면 새 조회·회차 소비 없이 미완료를 수동 전환한다. 운영 최적값을 검증한 수치가 아니다.
- [확정한 재확인 정책](trade_off/01-reconciliation-retry-policy.md)의 실패/수동 전환 기준을 따른다. R01의 [HTTP 설정](../r01-pg-payment-foundation/trade_off/03-http-client-settings.md)은 연결 1초·연결 풀 대기 1초·응답 대기 2초와 client 자동 retry/redirect 차단이다. 구체적인 재조회 분류는 아래 정책과 [계획](plan.md)·[결과](result.md)를 따른다.
- 자동 조회의 시간 예산은 PG 생성 처리 뒤 실행기에 최초 전달하는 시점부터 30초다. 대기열·100ms 재접수·조회·재시도 대기를 포함한다. 만료 뒤 새 조회/추가 대기를 시작하지 않고 미완료는 수동 전환한다. 이미 시작한 조회와 결과 저장/반영은 마무리하므로 전체 처리를 30초에 강제 종료하는 뜻은 아니다. 최대 4회 미만으로 중단될 수 있다.
- R01 [adapter 결과값 반환 결정](../r01-pg-payment-foundation/trade_off/04-adapter-fixture.md)에 따라 복구 실행기가 재조회할 결과만 Resilience4j Retry 제어에 연결한다. 회로 실패 집계도 반환 결과를 분류하며 통신 장애를 정상 반환이라는 이유로 성공 집계하지 않는다. 실제 애노테이션 연결과 분류 경계는 [계획](plan.md)·[결과](result.md)를 따른다.
- PG HTTP retry 대상은 기존 거래 조회뿐이다. 저장된 검증 결과의 내부 반영은 확실히 rollback된 MySQL 데드락(1213·SQLSTATE 40001)에만 100ms 뒤 새 TX에서 추가 1회 시도한다. PG 호출·자동 조회 회차·회로 표본을 추가하지 않는다. 잠금 대기 timeout·연결 끊김·무결성 문제·재고 반환 overflow는 이 재시도 대상이 아니며, commit 결과가 불명확하면 저장 상태부터 확인한다. 실제 예외 식별과 rollback 확인의 검증 범위는 [결과](result.md)를 따른다.
- 자동·고객/관리자 수동 대사·callback PG 조회는 하나의 circuit breaker를 공유한다. 생성 POST는 회로 범위 밖이며 저장 종결 근거의 내부 재적용은 OPEN에도 가능하다.
- [집계 기준](trade_off/02-lookup-circuit-breaker.md)에 따라 timeout·통신·5xx·408·429·잘못된 정상 응답은 실패 집계, 검증한 SUCCESS/FAILED/PENDING·계약상 거래 없음은 정상 집계다. 나머지 4xx·식별 충돌·우리 DB/실행기 오류·회로 차단은 정상/실패 표본 모두에서 제외한다. 거래 키 조회 404와 목록 경로 자체의 404는 구분한다.
- 회로 실패와 재조회 여부는 별도다. 잘못된 정상 응답은 회로 실패지만 즉시 수동 전환한다. 검증한 FAILED는 회로상 정상이며 공통 업무 TX에서 주문 실패·재고 반환을 처리한다.
- 조회 HTTP 오류 중 재조회 대상은 408·429·500·502·503·504다. 나머지 5xx는 회로 실패 집계를 유지하되 즉시 수동 전환한다. timeout·통신 오류·PENDING·계약상 거래 없음의 기존 재조회 정책과 수동 요청당 조회 최대 1회는 유지한다.
- 학습 범위에서 Retry-After 헤더를 해석하지 않는다. 헤더가 있어도 기존 1·3·10초＋지터 ±20%와 30초 예산을 유지한다. 현재 테스트 PG는 이 헤더를 보내지 않으며 외부 PG의 대기 지시를 따르지 못하는 한계는 남긴다.
- 조회 계약 밖 2xx/3xx(202·204·302 등)는 회로 실패로 집계하고 즉시 수동 전환한다. 2xx를 근거로 결제 성공을 추측하거나 3xx를 따라가지 않으며 저장 사실·차감 재고를 유지한다. 생성 POST의 정상 202는 조회 회로 범위 밖이다.
- 자동 조회 Retry와 공유 조회 CircuitBreaker는 모두 Resilience4j를 사용한다. 2026-10-22 최신 결정으로 기존 Spring Retry @Retryable 선택을 대체했다. `@Retry`와 조회 전용 `@CircuitBreaker`를 별도 Spring 빈의 공개 진입점으로 연결해 DB 처리/대기와 회로 집계를 분리한다. 횟수·대기·30초 예산·DB 기록·수동 전환 정책은 유지하며 [03](trade_off/03-resilience-library-wiring.md)을 따른다.
- CLOSED의 집계는 건수 기준 최근 10건·최소 5건부터 판단하고 실패율 50% 이상 또는 1초 초과 조회의 느림 비율 50% 이상이면 차단한다. 제외 표본은 분모/느림 집계에도 넣지 않는다. 느림 기준은 진행 중 호출을 취소하는 timeout이 아니다.
- OPEN은 10초 뒤 새 조회 요청이 오면 HALF_OPEN 탐색을 허용한다. 별도 자동 탐색 요청은 만들지 않는다. 공유 회로의 집계 대상 탐색 표본 2건으로 판단하고 두 건 모두 정상·1초 이하이면 복귀, 한 건이라도 실패/느림이면 50% 기준에 따라 재차단한다. 제외 결과는 표본을 채우지 않는다. HALF_OPEN 진입 후 최대 10초 안에 판정하지 못하면 재차단한다. 이는 새 PG 호출·진행 중 호출 강제 취소·결제 실패 처리의 근거가 아니다. 수동 요청당 최대 1회 조회는 유지한다.
- 조회 실패·회로 차단의 fallback은 저장된 상태와 확인 불가를 반환한다. 가짜 성공·확정 실패·포인트 대체·임의 재고 복구를 만들지 않는다.
- 회로 OPEN이 이미 발송한 시도를 미발송으로 되돌리지 않으며, 회복 뒤 기존 거래 조회를 재개한다.
- 자동 작업이 회로에 차단되면 확보한 회차는 유지하고 즉시 수동 전환한다. 실제 HTTP는 0회이고 회로 실패 표본을 추가하지 않는다. 수동/callback도 PG를 우회 조회하지 않으며 자동 회차를 소비하지 않는다. 회복 뒤 다음 명시적 대사/후속 callback에서 조회할 수 있지만 중단 자동 작업을 자동 부활시키지 않는다.
- client·retry·자동 재확인·circuit breaker 중첩에서 실제 호출 수와 실패 표본 단위를 확인한다. bulkhead는 필수로 추가하지 않는다.
- 정상 자동 재확인은 Resilience4j Retry로 실행하고 DB에 진행을 기록한다. 소진 후 처리에서 수동 전환을 저장한다. 장애/재시작 뒤 자동 재개는 하지 않고 담당자 수동 대사로 처리한다.
- 사용 횟수·현재 실행/진행·최근 시각·오류는 별도 pay 복구 작업 모델에 저장한다. commerce의 지터·다음 예약 시각·재시작 대기 재개 정보는 영속화하지 않는다. 검증 관찰은 별도 TX로 먼저 commit하고 업무 반영 rollback과 분리하며 저장된 종결 결과는 재적용할 수 있다.
- 실행 권한은 멱등성 키·DB 제약 + 조건부 상태 갱신 + 실행 식별자로 보호한다. 수동 인계는 현재 실행 ID·상태를 조건으로 새 ID를 기록하고 옛 진행 갱신을 차단한다. 자동 만료/회수는 도입하지 않는다. 실제 조건식·응답·bulk/Entity 정합성은 R02 및 R03 계획과 구현을 따른다.
- 사용자 정의 대기·PENDING/빈 조회 판정·미완료 기록 조회·수동 대사 연결은 별도로 구현한다. 자세한 결정은 [실행 방식](trade_off/06-reconciliation-execution.md)을 따른다.
- 조회 작업 직전에 사용 횟수를 DB에 commit한다. 기록 뒤 HTTP 전에 종료돼도 해당 회차는 소비한 것으로 유지한다. [횟수 기록 결정](trade_off/07-retry-attempt-accounting.md)을 따른다.
- 사용자 승인 보완: 회차 commit 뒤 별도 짧은 TX로 현재 실행 ID·RUNNING·확보 회차·완료 상태를 다시 확인하고, PG 조회 진입 직전에 30초 예산을 재검사한다. 만료/완료/인계 시 새 HTTP 없이 소비 회차를 유지하며 새 실행의 상태는 변경하지 않는다. 확인 실패도 새 PG 조회로 우회하지 않는다. 확인 직후 경합까지 막는 취소 프로토콜은 추가하지 않고 이미 시작한 조회의 사실 저장·기존 실행 ID 보호는 유지한다.
- 횟수 기록·실행기·실행 ID 조율·Resilience4j 2.3.0 프록시 연결을 구현하고 실제 Spring/DB 및 독립 JVM에서 검증했다. 한도 도달을 결제 실패나 재고 복구 근거로 쓰지 않는다.
- Resilience4j 의존성·실제 프록시·DB 기록·실서버 실행 연결까지 검증했다. 정책 결정과 실제 증거는 아래 완료 조건 및 결과 문서에서 구분한다.

## 운영 확인 범위 · 확정

- 기존 주문/미완료 조회＋로그＋Resilience4j 기본 지표를 사용한다. 별도 운영 API나 대시보드는 추가하지 않는다.
- 기존 복구 상태·사용 회차·최근 확인 시각·사유 필드를 유지하고, 회로 차단·시간 예산 소진·실행기 접수 거절 등 주요 중단 사유를 구분한다. 고객/관리자 접근·완료/주의 표시 계약은 유지한다.
- 주문별 처리는 시도/실행 ID·회차·결과를 포함한 로그로 추적한다. 카드 원문·PG 응답 원문은 기록하지 않는다.
- 기존 Prometheus에 회로 상태·성공/실패/차단·Retry 기본 지표를 연결한다. 주문/시도/실행 ID를 지표 태그로 쓰지 않고 Retry 지표와 실제 결제 결과·HTTP 수를 구분한다.
- 회로 OPEN을 전체 서비스 health의 DOWN으로 연결하는 별도 설정은 추가하지 않는다. 자세한 범위는 [03](trade_off/03-resilience-library-wiring.md)을 따른다.

## 통합 장애·기존 기능·제출

- R01/R02의 개별 검증을 전제로 외부 거래·DB·controller가 연결된 장애 순서를 결정적으로 재현한다.
- PG 성공 후 내부 commit 실패, 발송 기록 후 프로세스 재생성, callback/대사 동시 적용과 늦은 응답을 검증한다.
- 외부 거래 수·create/lookup 횟수·주문/시도/차감 처리 상태·가용 재고·포인트를 함께 확인한다.
- 과거 POINT 기록·품목·금액, 포인트 충전/조회, 재고 부족/삭제의 PG 미호출을 보존한다.
- 차감 후 삭제 상품의 종결·실패 복구, 관리자 가용 재고 설정의 경쟁, 차감/복구의 캐시 commit/rollback을 확인한다.
- 실제 코드에 연결한 실행 경로·설정·관측 방법과 장기 미확인·자동 완료 한계를 문서에 남긴다.
- 기술 글은 실제 요청/실패 장면, 핵심 개념, 선택 이유·이득·비용·해결하지 못한 상황을 설명한다.

- [x] 최초+추가 3회·1/3/10초·지터 ±20%와 중간 종결/즉시 수동 전환 시 중단을 확인한다. 한도 소진이 결제 실패나 재고 복구를 만들지 않는다.
- [x] Resilience4j Retry의 실제 적용과 DB 진행 기록·재시작 후 미완료 목록 노출·담당자 수동 대사를 검증한다. 재시작이 자동 PG 조회 재개나 최초+추가 3회 초기화를 만들지 않는다.
- [x] 횟수 commit 뒤 HTTP 전에 종료돼도 소비 회차가 되돌아가지 않는다. 재시작 후 미확인 작업은 담당자 확인 대상으로 남고 자동 조회를 추가하지 않는다.
- [x] CLOSED → OPEN → HALF_OPEN → CLOSED 또는 재차단을 통제한 순서로 확인한다.
- [x] OPEN 중 실제 외부 조회가 차단돼도 미완료 결제·차감 재고가 유지되고 회복 후 같은 거래 조회가 재개된다.
- [x] 응답 유실·내부 저장 실패·재시작·동시 결과 적용에서 추가 외부 거래나 중복 확정/복구가 없다.
- [x] 0건·복수 거래·식별/금액 불일치·충돌에서 임의 종결·재결제·재고 복구가 없다.
- [x] 기존 기능·결정된 사용자 경계·캐시 회귀와 전체 check의 실제 실행 건수·실패·skip·종료 결과를 확인한다.
- [x] 서버·worker·실험 자원을 정리하고 상태/트랜잭션 설계·실제 결과·기술 글을 작성한다.
- [x] 기존 조회의 중단 사유·추적 로그·기존 Prometheus의 회로/Retry 기본 지표로 대표 장애를 확인한다.
- [x] 로컬 PR 설명 초안에 대표 효과 수와 미확인 처리 한계를 기록했다. 원격 PR 생성·게시 시점은 후속 요청에서 정한다.
