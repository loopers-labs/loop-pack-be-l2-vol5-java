# PR02 계획과 기능 구현의 세 관점 리뷰

2026-10-22 [상세 계획](plan.md) 초안을 비즈니스·사용자 경험·기술 서브에이전트가 각각 검토했다.
앞의 계획 리뷰 절은 구현 전 검토이며 이후 기능 리뷰는 마지막 절에 구분했다. 파일 수정·테스트 실행을 에이전트에게 맡기지 않았다.

상태: **공통 업무 반영의 중요 보완 승인·반영 및 세 관점 재리뷰·관련 검증 완료**. 계획 리뷰와 이후 기능 리뷰를 아래에 구분해 기록한다.

## 중요 보완 최소안 · 2026-10-22 사용자 승인 및 계획 반영

사용자가 세 가지 보완을 함께 승인했다. 아래는 최초 지적과 승인한 해결 방법이며 [상세 계획](plan.md)에 반영했다.

### 1. 완료된 주문의 늦은 충돌과 미완료를 구분

주문 확정·재고 소비·APPLIED 저장이 끝난 뒤 PG 종결 상충이 기록될 수 있다.
이를 계속 202로 응답하면 호출자가 아직 업무가 진행 중이거나 반복 대사로 해결될 것이라 오해할 수 있다.

업무 반영 완료 여부를 200/202의 기준으로 통일했다.
이미 반영했다면 200과 기존 완료 상태·충돌 주의 표시를 반환하고, 미반영 충돌은 202와 수동 확인 필요를 반환한다.
GET의 조회 성공 200은 유지하며 강제 충돌 해소·환불 API는 추가하지 않는다.

### 2. 실패 표식은 업무 시도 당시 snapshot으로 CAS

callback 실행 A의 업무가 rollback된 뒤 수동 실행 B가 인계받을 수 있다.
A가 실패 후 최신 B를 다시 읽어 expected 값으로 쓰면 CAS라도 B를 수동 필요로 바꿀 수 있다.

업무 시도 직전 또는 해당 업무 TX에서 확인한 작업 상태·실행 ID·사용 회차를 변경 불가능한 비교값으로 실패 기록기에 전달하도록 명시했다.
실패 후 최신 소유자를 새 기준으로 삼지 않는다. 당시 READY였다면 READY/ID 없음/회차 0도 그대로 비교한다.
조건이 바뀌었거나 APPLIED면 예전 실패 기록은 적용하지 않는다.

### 3. 범용 save 제거와 기존 confirm/테스트 이행을 같은 커밋에서 수행

초안은 커밋 2에서 save를 제거하고 커밋 5에서 기존 confirm·POINT 테스트를 전환한다.
그러나 현재 OrderService.confirm과 저장 실패 주입·기존 POINT fixture가 save를 사용하므로 중간 커밋 Green을 유지할 수 없다.

insert/CAS를 먼저 추가하고 최종 save 제거를 confirm 전환 커밋으로 옮겼다.
기존 confirm 전환·관련 테스트/fixture 이행·범용 save 제거를 함께 검증한다. 기존 주문 갱신을 insert로 바꾸거나 임시 POINT facade를 추가하지 않는다.
기반 단계에서도 기존 POINT confirm은 DRAFT만 허용해 새 PG 상태를 POINT로 확정하지 않게 한다.

## 함께 반영한 설명 보완

- 소유권 확인 후 이미 업무 반영 완료라면 claim/인계·PG 조회 없이 저장 상태를 반환하는 빠른 경로를 명시한다. 충돌 표시는 유지한다.
- R02의 202 다음 행동을 예시로 설명한다. GET은 저장 상태만 읽고 실제 재확인은 POST reconcile이며 자동 재조회는 R03이다.
- overflow 수동 처리 예시는 PG 실패 보존→관리자 가용 수량의 원인 해소→저장 근거 재적용(PG GET 0회)을 보여준다.
- 공유 Gateway spy 설정은 doReturn/doAnswer 계열을 사용해 설정 중 실제 HTTP가 실행되지 않게 한다.

기존 save/POINT API는 계획대로 유지하며 실제 PG 요청·상품 서비스 반환·공통 업무 TX·새 API 연결은 후속 범위다.

## 커밋 3 · 준비 TX·재고 선차감·최초 PG 발송 권한

소유권·기존 요청 비교·전역 키 확인 후 주문 CAS 성공자가 같은 TX에서 실제 재고를 차감하고 STARTED 시도·DEDUCTED 차감 기록·READY 복구 작업을 저장한다.
준비 TX는 별도 빈의 REQUIRES_NEW 진입점이며 commit 정상 반환된 최초 실행에만 발송 권한을 준다. 재요청은 기존 시도와 권한 false를 반환한다.
조율 파사드는 CAS 패자와 유일 제약 실패자를 원래 TX 종료 뒤 별도의 읽기 TX에서 재판정한다. 다른 저장 오류는 성공으로 숨기지 않는다.
이번 단계에는 카드 원문·실제 PG HTTP·고객 confirm 전환을 포함하지 않는다. PG 발송 권한은 내부 준비 결과이며 고객 API 응답이 아니다.

| 관점 | 기능 리뷰 결과 |
|---|---|
| 비즈니스 | 중요 결함·누락 없음. 소유권 우선, 동일 요청 비교, 단일 선점·선차감·기록의 원자성, 최초 발송 권한과 후반 실패 rollback이 적절하다. |
| 사용자 경험 | 중요 문제 없음. 같은 요청 재발송 없음, 변경 요청의 정보 노출 없는 409, 타인 주문의 같은 404와 후속 HTTP 범위 구분을 확인했다. |
| 기술 | 중요 수정 없음. 별도 빈의 commit 반환, 경합 패자의 새 snapshot 재판정, 재요청 권한 재생성 차단, 준비 전체 rollback을 확인했다. |

리뷰어는 파일 수정·테스트 실행 없이 기능만 검토했다. 추가 승인이 필요한 중요 수정은 없었다.
최소 신규 통합 시나리오 5건은 동일 주문 동시 준비·재요청, 요청 충돌/소유권, 서로 다른 주문의 전역 키 경합, 재고 부족, 마지막 작업 insert 실패 rollback이다.
기존 ProductServiceTest와 POINT ConfirmOrderIntegrationTest를 함께 실행해 총 24건이 실패·오류·건너뛰기 0건으로 통과했다. 새 계약은 구현 전 컴파일 실패를 확인했고 테스트의 제네릭 타입 추론을 명시해 컴파일을 보완했다.
실제 MySQL·기존 상품 잠금/차감/이벤트를 사용했다. PG 서버 호출 검증과 전체 check는 계획의 후속 단계이며 이번 결과로 완료를 주장하지 않는다.
Checkstyle main/test도 통과했다. 로그는 무시 대상 `build/r02-prepare-{red,green,style}.log`에 남긴다.

## 커밋 4 · 공통 업무 반영·재고 복구·실패 표시

현재 구현은 저장된 PG 결과의 짧은 행 잠금→주문 종결 CAS→PG 성공 기록/재고 반환→차감 기록 종결→작업 APPLIED를 같은 TX로 묶는다.
성공은 추가 차감 없이 완료하고 확정 실패는 현재 가용 수량에 반환한다. 삭제 상태는 보존하며 overflow/내부 실패는 업무 전체를 rollback하고 먼저 commit한 PG 근거는 유지한다.
조율자는 업무 직전 복구 작업의 상태·실행 ID·회차를 불변 snapshot으로 확보하고 rollback 뒤 그 값으로만 APPLICATION_FAILED 표식을 CAS한다. 인계된 새 실행·APPLIED는 덮지 않는다.

| 관점 | 최초 기능 리뷰 결과 |
|---|---|
| 비즈니스 | 중요 보완 1건. 표식 저장만 실패했을 때 새 상태 조회도 차단해 정상 저장 상태를 반환하지 못한다. 나머지 업무 효과와 snapshot CAS는 적절하다. |
| 사용자 경험 | 중요 문제 없음. APPLIED와 결제 성공의 구분, 완료 후 충돌 주의, 실패 근거/차감 유지가 적절하다. 후속 API에서 MANUAL_REQUIRED를 별도로 표시할 것을 확인했다. |
| 기술 | 비즈니스 보완에 동의하며 그 외 중요 수정 없음. 잠금 순서·업무 원자성·실패 당시 비교값·기존 근거 보존을 확인했다. |

### 중요 보완 · 2026-10-22 사용자 승인·반영

수동 표식 UPDATE만 일시 실패한 경우에도 현재 구현은 즉시 예외를 던져 새 상태 조회를 실행하지 않는다. 그 사이 다른 실행이 APPLIED로 마쳤어도 완료를 반환하지 못할 수 있다.
최소 제안은 표식 저장 오류를 로그에 남기고 새 TX의 현재 상태 조회를 한 번 시도하는 것이다. 완료면 완료, 미완료면 확인 필요를 반환하며 조회까지 실패하면 기존 5xx로 처리한다. 재시도·회복 엔진은 추가하지 않는다.
사용자가 “표식 실패 뒤에도 상태 조회하도록 수정”을 선택했다. 즉시 예외를 던지던 분기를 로그 기록으로 바꾸고 새 TX 조회를 계속하도록 반영했다.
완료/미완료 조회 반환과 조회 장애 전파를 다루는 facade 3건이 수정 전에 모두 실패해 문제를 재현했으며, 수정 후 세 건 모두 통과했다.

| 관점 | 승인 보완 재리뷰 |
|---|---|
| 비즈니스 | 보완 해소·새 중요 지적 없음. 완료 우선 반환과 미완료 주의, 조회 실패 시 예외 전파가 적절하다. |
| 사용자 경험 | 보완 해소·새 중요 지적 없음. 저장된 현재 상태를 확인하고 attention과 MANUAL_REQUIRED를 구분한다. |
| 기술 | 보완 해소·새 중요 지적 없음. 새 TX 재조회와 예외 전파가 맞고 기존 snapshot 보호·업무 원자성을 유지한다. |

### 관련 최소 검증 · 완료

## 커밋 5 · 실제 PG 호출·고객 confirm 전환·범용 save 제거

고객 confirm을 준비 저장 → TX 밖 PG 생성 → 관찰 저장 → 공통 업무 반영 → 새 응답 조회 순서로 연결했다. PG 생성은 최초 준비 commit이 정상 반환한 호출만 수행한다. 같은 요청은 재발송하지 않고 저장 결과를 반영·반환한다.
기존 X-USER-ID로 소유권을 먼저 확인하며 다른 고객의 주문은 없는 주문과 같은 404다. 입력은 시도 UUID·합성 카드·선택 테스트 조건이며 금액과 callback URL은 서버가 결정한다. 옵션 오타·문자열/소수의 정수 변환은 400으로 거절하고 카드 원문을 오류·toString에 노출하지 않는다.
응답은 최신 주문의 종결과 복구 작업 APPLIED를 함께 확인해 200/202를 결정한다. 주문 상태와 검증 결과·거절 근거·복구 진행·주의 표시·조회 경로를 구분해 반환한다.

범용 OrderRepository.save와 기존 POINT 결제 조율을 함께 제거했다. 생성은 insert, 기존 PG 주문 변경은 준비/종결 CAS를 사용한다. 과거 POINT는 완료 사실을 가진 신규 fixture로 저장하며 기존 기록·조회·본인 재확정 오류를 유지한다. 새 PG 결제는 포인트를 사용하지 않는다.
기존 재고·스냅샷·SQL rollback·동시성·캐시 검사를 PG 계약으로 이행했고 운영용 POINT 우회 API나 테스트용 production 진입점은 추가하지 않았다.

| 관점 | 커밋 전 기능 리뷰 결과 |
|---|---|
| 비즈니스 | 중요 수정 없음. 최초 발송 권한·선차감·미확인 유지·포인트 사용 0·과거 POINT 보호가 적절하다. |
| 사용자 경험 | 중요 수정 없음. 완료 기준의 200/202·주의 표시·같은 요청 재사용·타인 404·카드 비노출이 일관된다. |
| 기술 | 중요 수정 없음. HTTP 밖 TX 경계·관찰 선저장·공통 반영·최신 응답 조회와 범용 save 제거를 확인했다. |

세 리뷰어는 기능 코드만 검토했고 파일 수정·테스트 실행은 하지 않았다. 추가 사용자 승인이 필요한 중요 수정은 없었다.

### 독립 서버 실연결 · 완료

기존 로컬 DB와 분리한 `payment-lab-verification` MySQL 포트 13316을 다시 사용했다. 두 상태만 있던 orders.status에 증분 `007`을 한 번 적용하고 PG 8081·commerce 8080/관리 8082를 별도 JVM으로 validate 기동했다. 기존 DB·볼륨은 초기화하지 않았다.

| 실제 입력·상황 | 확인한 결과 |
|---|---|
| 정상 성공 조건, callback DROP, 재고 5에서 2 주문 | confirm 202·PAYMENT_PENDING·재고 3. 같은 요청을 반복해도 PG 거래 1건·추가 차감 없음. PG는 이후 SUCCESS지만 commerce 관찰은 PENDING을 유지한다. |
| REJECT_BEFORE_CREATE, 재고 5에서 2 주문 | confirm 200·PAYMENT_FAILED, outcome=FAILED/rejection=NO_EFFECT, 작업 APPLIED·재고 5·RESTORED. 동일 요청 반복에도 PG 거래 0건·추가 반환 없음. |
| 기존 POINT 주문 42 및 포인트 사용 | 기존 7000·PAID·POINT·원래 시각 유지. 새 두 주문의 결제 기록 없음, 전체 USE 0건. |

현재 PG 생성 응답은 항상 PENDING이다. 정상 거래의 최종 성공을 commerce로 가져오는 callback·대사까지 검증했다고 표현하지 않는다. 이 연결과 통합 장애 실험은 예정된 후속 단계다.
실연결 검사 중 NO_EFFECT를 outcome으로 비교한 검증 스크립트 오류는 실제 모델의 FAILED 결과/NO_EFFECT 거절 근거를 나누어 확인하도록 바로잡았다. 기능 수정은 없었다.
실험의 PG·commerce JVM과 전용 MySQL은 종료했고 데이터는 보존했다. 증거는 무시 대상 `build/r02-confirm-live-{summary.json,effects.log,adjustments.log}`와 기동 로그에 있다. JMeter 사용자 변경·두 원문은 유지했다.

## 커밋 6 · 고객·관리자 결제 조회·미완료 목록

기존 주문 조회에 결제 시도·복구 작업을 QueryDSL projection으로 연결했다. 주문 품목은 기존 일괄 조회를 유지한다. 주문 생성/과거 POINT/PG 대기·완료를 구분하고, 결제 결과·거절·충돌과 복구 진행·사용 회차·조회 시각·이유를 별도로 반환한다. 카드·원문·테스트 조건은 선택하지 않는다.
고객 단건은 주문 ID와 헤더 사용자 ID를 같은 조회 조건에 넣는다. 과거 POINT도 본인만 읽을 수 있고 타인·없는 주문은 같은 404다. 주문 관리자 단건·목록과 새 `GET /api-admin/v1/payments/incomplete`는 기존 resolver의 사용자 존재 확인 후 1번 fixture만 허용한다. 그 외 유효 사용자는 403이다. 상품 등 다른 관리자 API는 변경하지 않았다.
미완료 목록은 PAYMENT_PENDING 또는 MANUAL_REQUIRED 또는 결과 충돌을 포함한다. 정상 완료·POINT·아직 결제를 시작하지 않은 DRAFT는 제외하며, 완료 후 늦은 충돌은 포함한다. 목록과 총수는 같은 조건을 사용하고 기존 생성 시각/ID 내림차순·page/size 계약을 유지한다. GET은 저장 상태만 읽고 PG 호출·재고·복구 진행 변경을 하지 않는다.

| 관점 | 최초 기능 리뷰 |
|---|---|
| 비즈니스 | 중요 보완 1건. 관리자 응답의 조회 링크가 고객 경로여서 타인 주문에서 404가 된다. 나머지 조회·접근·목록 범위는 적절하다. |
| 사용자 경험 | 같은 관리자 링크 문제를 확인했다. 고객/관리자 경로를 구분해야 제공된 링크를 그대로 따라갈 수 있다. |
| 기술 | 같은 문제를 확인했다. LEFT JOIN·고객 조건·목록/개수 조건·조회 전용 경계에는 그 외 중요 지적이 없다. |

### 중요 보완 · 2026-10-22 사용자 승인·반영

사용자는 “관리자 조회 경로 분리”를 선택했다. 고객 응답은 `/api/v1/orders/{id}`, 관리자 단건·목록·미완료 응답은 `/api-admin/v1/orders/{id}`를 반환하도록 바꿨다. 시도 없는 주문의 링크는 null을 유지한다.
관리자가 다른 고객의 PG 주문을 미완료 목록에서 읽고 안내된 URL을 그대로 따라가는 HTTP 검사는 수정 전 404로 실패했다. 이를 승인 수정의 재현으로 남겼다.
세 관점 재리뷰에서 모두 관리자 링크 문제 해소·새 중요 지적 없음으로 확인했다. 리뷰어는 파일 수정·테스트 실행 없이 기능만 검토했다.

## 커밋 7 · 단일 조회 수동 대사·실행 인계

고객과 관리자 POST 대사를 같은 유스케이스에 연결했다. 짧은 준비 TX에서 본인/관리자 접근을 먼저 확인하고, 이미 업무 완료인 주문은 조회·인계 없이 반환한다. 미완료 READY는 claim, RUNNING/MANUAL_REQUIRED는 기존 상태·실행 ID·회차를 비교해 새 실행으로 인계한다. CAS 패자는 최신 응답만 읽는다.
저장된 SUCCESS/FAILED/생성 전 거절과 충돌은 추가 조회 없이 공통 업무 반영으로 보낸다. 다른 경우에는 현재 실행 조건으로 조회 시작 시각만 먼저 commit하고 PG를 TX 밖에서 최대 한 번 조회한다. 새 결제를 만들거나 자동 사용 회차를 소비·초기화하지 않는다. 검증 관찰은 별도 commit하고 기존 공통 업무 TX를 재사용한다.
PENDING/확인 불가는 현재 실행 조건으로 MANUAL_REQUIRED와 사유를 저장한다. 이전 실행의 늦은 갱신은 새 실행을 덮지 않는다. 공통 반영에도 준비 당시의 수동 실행 snapshot을 전달해, 업무 실패 후 최신 실행을 다시 읽어 비교값으로 삼지 않게 했다. 기존 confirm/callback용 진입점은 직전 capture 방식을 유지한다.
최신 상태로 완료 200·미완료 202를 판정하며 고객은 고객 URL, 관리자는 구매자 ID와 관리자 URL을 받는다. 수동 표식 저장만 실패하면 로그를 남기고 최신 상태를 확인한다. DB 조회까지 실패하면 오류를 전파한다. callback·자동 조회·회로는 이번 범위에 추가하지 않았다.

| 관점 | 커밋 전 기능 리뷰 |
|---|---|
| 비즈니스 | 중요 지적 없음. 접근 우선·저장 근거 재적용·조회 최대 1회·예산 보존·옛 실행 보호가 적절하다. |
| 사용자 경험 | 중요 지적 없음. 완료 빠른 반환·미완료 수동 상태와 사유·200/202·고객/관리자 경로를 구분한다. |
| 기술 | 중요 지적 없음. 짧은 CAS/시각 commit·TX 밖 HTTP·관찰 선저장·수동 snapshot 전달과 새 상태 조회가 맞다. |

세 리뷰어는 파일 수정·테스트 실행 없이 기능만 검토했다. 추가 승인이 필요한 중요 수정은 없었다.
새 계약의 구현 전 컴파일 실패를 확인한 뒤 저장 종결 재적용 2건, 예산 4회 유지와 단일 조회 3건, 조회 중 인계 뒤 늦은 진행 차단 1건을 실제 MySQL로 검증했다. 성공 반영 후 늦은 충돌은 완료+주의를 유지하며 인계/조회 없이 반환하는 것도 같은 사례에서 확인했다.
기존 공통 반영 facade 3건과 수동 실행 비교값 보존 1건, 고객/관리자 HTTP 1건을 함께 실행해 기능 11건·ArchUnit 8건 모두 실패·오류·건너뛰기 0건으로 통과했다. Checkstyle main/test도 통과했다. HTTP는 타인 404·관리자 거절·헤더 누락·고객 202·관리자 완료 200·조회 URL·완료 재요청의 추가 조회 없음으로 한정했다. 기존 기준은 완화하지 않았다.
로그는 무시 대상 `build/r02-reconcile-{red,green,http-green}.log`에 남긴다. 전체 check와 별도 서버의 callback/재시작 통합 실험은 PR 마무리에 수행한다.

## 커밋 8 · 동기 callback 권위 확인·공통 반영

`POST /api/v1/payments/callback`을 요청 안의 동기 흐름으로 연결했다. 입력은 문자열 providerOrderId/transactionKey/status이며 고객/관리자 헤더를 요구하지 않는다. 등록된 단일 시도·주문·STARTED를 확인하고 저장 거래 키와 다른 알림은 409, 미등록은 404, 잘못된 입력은 400으로 거절한다. 거절된 알림으로 저장 결과를 오염시키지 않는다.
PG 조회는 저장 거래 키를 사용하며 미결합이면 저장된 providerOrderId로 조회한다. 알림 키 자체를 조회·결합의 권위로 쓰지 않고, 검증한 조회 키와 알림 키가 일치해야 관찰을 저장한다. 본문 status는 형식만 검사하고 결제 판단에는 쓰지 않는다.
TX 밖 권위 조회 → 관찰 별도 commit → 기존 공통 업무 TX → 새 완료 상태 조회 순서다. 응답은 고객 주문 상세 없이 completed/attentionRequired만 반환하며 200은 업무 반영 완료, 202는 미완료다. 중복·늦은 결과 충돌도 기존 주문/재고 멱등 경계를 사용한다.
callback은 실행을 claim/인계하거나 자동 회차를 소비하지 않는다. 요청 초기에 확보한 실행 snapshot을 공통 반영에 전달해 조회 중 수동 인계가 발생해도 늦은 업무 실패 표식이 새 실행을 덮지 못하게 했다. callback 접수 큐·별도 실행기·자동 송신 재시도는 추가하지 않았다.

| 관점 | 커밋 전 기능 리뷰 |
|---|---|
| 비즈니스 | 중요 지적 없음. 알림과 권위 결과 구분·키 검증·관찰 선저장·중복 효과 차단·초기 실행 보호가 적절하다. |
| 사용자 경험 | 중요 지적 없음. 본문과 다른 조회 결과도 신뢰하며 미완료/완료 응답과 고객 상세 비노출을 구분한다. |
| 기술 | 중요 지적 없음. 짧은 대상 확인·TX 밖 HTTP·관찰 commit·초기 snapshot 공통 반영과 최신 응답 조회가 맞다. |

리뷰어는 파일 수정·검사 실행 없이 기능만 검토했다. 추가 사용자 승인이 필요한 중요 수정은 없었다.
구현 전 새 HTTP 검사 8건 모두 실패하는 것을 확인했다. 첫 구현 검사 16건 중 14건이 통과했고, MANDATORY repository spy의 실패 주입을 TX 밖에서 설정한 검사와 그 미완료 stubbing의 후속 검사가 실패했다. 주입 설정을 TX 안으로 옮긴 뒤 callback 8건 중 7건이 통과했다. 남은 동시성 검사는 실제 처리 후 차감 기록을 TX 밖에서 스트림으로 재조회해 실패했으며, 재조회만 TX 안으로 옮겨 해당 1건도 통과했다. 기능·검사 기준은 변경하지 않았다.
중복 제외 callback HTTP/MySQL 8개 시나리오와 ArchUnit 8건이 최종 실패·오류·건너뛰기 0건이며 Checkstyle main/test도 통과했다. 본문과 다른 권위 결과, 키 미결합/불일치, 입력·미등록 거절, 조회 불가, 중복/동시 반환 1회, 종결 충돌, 새 실행과 성공 근거 보존만 확인했다.
로그는 무시 대상 `build/r02-callback-{red,green,recheck,concurrency-recheck}.log`에 남긴다. 별도 PG/commerce 프로세스의 실연결·장애·재시작 통합 실험과 필수 전체 check는 커밋 9에서 수행한다.

## 커밋 9 · 실제 PG 통합·장애/재시작·필수 전체 검사

기능 코드 `73bc6cf`의 두 JAR를 빌드하고 PG/commerce 전체 check를 수행했다. PG 25건·commerce 407건, 총 432건이 실패·오류·건너뛰기 0건으로 통과했다. Checkstyle·ArchUnit·기존 slow/example 검사와 포인트/캐시 회귀를 포함한다. 이후 변경은 검증 기록과 문서뿐이다.

독립 PG/commerce JVM과 실험 전용 MySQL에서 대표 실험 10개를 추가 확인했다. 같은 키 동시 confirm, callback 먼저/늦은 생성 응답, 생성 응답 유실 뒤 실패, 관리자 가용 수량 변경, 삭제 상품 반환, PG 성공 뒤 내부 반영 rollback, commerce/PG 강제 종료·재시작과 수동 인계, 거래 생성 전 거절, callback 송신 timeout 뒤 실제 완료, 반환 overflow 후 수동 복구를 통과했다.
정확한 옵션·주문 ID·최종 상태/재고/거래/주문 기록 수는 [결과](result.md), 재현 절차는 [verification](verification.md)에 남긴다. 새 실험 주문의 포인트 USE는 0건이고 과거 POINT 기록·JMeter 사용자 변경·원문을 보존했다.

중요한 기능 수정이 필요한 문제는 발견되지 않았다. 기능 변경 없는 문서·검증은 별도 서브에이전트 리뷰 대상에서 제외하는 기존 사용자 규칙을 따랐다. 기존 기능 커밋의 세 관점 리뷰·중요 수정 승인 기록은 그대로 유지한다. 자동 4회 실행이나 회로 검증을 완료했다고 기록하지 않는다.
