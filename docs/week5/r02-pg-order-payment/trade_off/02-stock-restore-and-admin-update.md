# 재고 복구와 관리자 재고 설정

[결정 목록](total_trade_off.md) · [요구사항](../requirement.md) · [재고 상태](../../states/stock.md)

상태: **복구 실패 시 수동 처리 채택·내부 공통 반영 TX 구현·API 연결 전**. 2026-10-22 사용자 선택을 기록한다.

## 이미 정한 재고의 의미

관리자가 설정하는 수량은 현재 판매할 수 있는 가용 재고다. 실패한 주문의 수량은 그때의 가용 재고에 더한다.

예를 들어 재고 5에서 주문 수량 2를 차감하면 3이다. 이후 관리자가 가용 재고를 10으로 바꾸고 결제가 실패하면,
10에 2를 더해 12로 복구한다. 과거 값 5로 덮어쓰지 않는다. 이 의미는 기존 요구사항이며 새 선택 사항이 아니다.
재고 증감·관리자 설정은 상품 잠금으로 보호하고, 같은 주문의 실패를 반복 반영해 추가로 수량을 더하지 않는다.

## 이번에 정한 것: 복구 수량을 저장할 수 없을 때

현재 Stock과 상품 재고 컬럼은 int다. 관리자가 최대값 근처로 가용 재고를 설정한 뒤 주문 수량을 반환하면 범위를 넘을 수 있다.

| 대안 | 처리 | 이득 | 비용 |
|---|---|---|---|
| 복구 실패 시 수동 처리 · 채택 | 안전한 덧셈으로 초과를 확인하고 업무 반영 TX 전체를 rollback한다. 저장된 PG 실패는 보존하고 수동 확인 대상으로 남긴다. | 기존 관리자 설정 계약·재고 타입을 유지하고 별도 반환 예정량 집계를 만들지 않는다. | 담당자가 원인을 해소한 뒤 같은 결과를 다시 반영해야 한다. |
| 관리자 설정을 미리 제한 · 미채택 | 미완료 주문의 반환 예정 수량을 집계해, 모두 반환해도 한도를 넘지 않는 값만 설정하도록 한다. | 이 원인의 복구 실패를 미리 줄인다. | 미완료 수량 집계·상품별 경쟁 처리와 관리자 입력 정책 변경이 추가된다. |

학습용 최소안으로 첫 번째를 선택했다. 숫자가 넘쳐 음수가 되거나 최대값으로 잘려 일부 수량만 복구되는 처리는 허용하지 않는다.

## 실패와 재처리

- PG의 검증한 FAILED/NO_EFFECT는 앞선 관찰 TX에 이미 저장됐으므로 업무 rollback으로 지우지 않는다.
- 업무 TX의 실제 상품 수량·차감 기록·주문 처리 완료·작업 적용 완료는 함께 rollback한다. 일부 품목만 복구 완료로 남기지 않는다.
- 실제 재고를 돌려놓지 못했으므로 차감 기록은 DEDUCTED이고, 주문의 실패 처리 완료나 작업 APPLIED로 표시하지 않는다.
- 업무 반영 실패를 수동 확인 대상으로 남긴다. 기존 복구 작업 모델을 사용하며, 별도 재고 복구 worker나 오류 작업 플랫폼은 추가하지 않는다.
- 담당자가 가용 수량 등 실패 원인을 해소한 뒤 저장된 실패 근거를 다시 적용한다. 이 때문에 새 결제를 생성하거나 PG를 다시 조회할 필요는 없다.
- 사용자에게 보일 응답, 수동 사유 기록의 TX 경계·실행 ID 조건, 일시 DB 장애의 분류는 후속 공통 반영/API 설계에서 정한다.

상품 삭제 후에도 이미 차감한 주문 수량을 처리하되 삭제를 해제하지 않는 정책은 유지한다.
캐시 변경 알림은 실제 상품 변경 TX의 commit/rollback과 함께 처리한다. 구체적인 공통 반영 잠금 순서는 별도 설계 대상이다.

## 필요한 최소 확인 · 검증 완료

- 관리자 재고를 10으로 설정한 뒤 수량 2의 실패 복구 결과가 12이며 반복 반영으로 늘어나지 않는지 확인한다.
- int 한도 초과 시 전체 업무 rollback·PG 실패 보존·처리 완료 아님을 확인한다.
- 원인 해소 후 같은 저장 결과로 한 번만 복구하고 추가 PG 생성이 없는지 확인한다.

R02의 관련 MySQL 검사와 최종 별도 서버 실험에서 위 경계를 확인했다. 실제 주문 47은 10+2=12, 주문 48은 삭제 유지·반환, 주문 54는 한도 초과 rollback 후 수동 원인 해소·재적용을 통과했다. 전체 검사 432건도 통과했으며 [실제 결과](../result.md)를 따른다.
