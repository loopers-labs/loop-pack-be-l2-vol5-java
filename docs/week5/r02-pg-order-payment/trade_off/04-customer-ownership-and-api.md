# 고객 주문 소유권과 API 경계

[결정 목록](total_trade_off.md) · [요구사항](../requirement.md) · [전체 요구사항](../../total_requirement.md)

상태: **고객 소유권·타인 주문 404·1번 관리자 fixture 채택·구현 전**.
2026-10-22 사용자 선택을 기록한다.

## 원문과 현재 코드의 차이

원문은 본인 주문의 확정·상세 조회·대사를 요구한다. 기존 코드는 주문 생성/목록에 X-USER-ID를 사용하지만,
주문 상세·확정은 orderId만으로 처리한다. 기존 관리자 URL 분리도 관리자 권한 검증을 뜻하지 않는다.
원문이 전제한 소유권이 이미 구현됐다고 기록하지 않는다.

## 선택: 기존 X-USER-ID로 주문 소유자 비교

사용자는 현재 접근 방식을 그대로 유지하는 대신, 기존 학습용 헤더로 소유권을 비교하는 최소안을 선택했다.
기존 리졸버의 양수 사용자 ID·사용자 존재 검증을 재사용하고, 요청 userId와 저장된 주문의 userId가 같은지 확인한다.
헤더는 학습용 사용자 식별 입력이다. 실제 로그인·Spring Security·별도 인증 시스템을 추가하는 결정은 아니다.

| 고객 API | 적용할 규칙 |
|---|---|
| POST /api/v1/orders/{orderId}/confirm | 헤더 사용자 소유의 주문만 처리한다. 준비 CAS·차감·발송 전에 소유권을 확인한다. |
| GET /api/v1/orders/{orderId} | 헤더 사용자 소유의 주문·결제 상태만 반환한다. 과거 POINT 주문도 같은 규칙을 적용한다. |
| POST /api/v1/orders/{orderId}/payment/reconcile | 헤더 사용자 소유의 시도만 조회·반영한다. 실행 인계·PG 조회 전에 소유권을 확인한다. |

고객 주문 목록의 기존 사용자 조건은 유지한다. 헤더 누락/형식 오류의 400과 없는 사용자 404도 기존 계약을 따른다.
과거 POINT 주문의 금액·품목·PAID 사실은 유지하며, 본인 요청의 재확정은 기존 재확정 오류를 유지한다.
상세/확정의 기존 호출자는 새로 헤더를 보내야 한다. 이는 사용자가 승인한 고객 API 계약 변경이다.

## 선택: 타인 주문은 없는 주문과 같은 404

| 대안 | 의미 | 장단점 |
|---|---|---|
| 없는 주문과 같은 404 · 채택 | 존재하지 않거나 본인 소유가 아니면 같은 ORDER_NOT_FOUND·메시지로 응답한다. | 다른 고객 주문의 존재를 드러내지 않고 기존 오류를 활용한다. 호출자는 없는 주문과 타인 주문을 구별하지 못한다. |
| 403 · 미채택 | 주문이 있지만 접근할 수 없음을 구분한다. | 거절 이유를 명확히 알 수 있으나 주문 존재 여부를 구분할 수 있고 오류 매핑이 추가된다. |

사용자는 404를 선택했다. 없는 주문과 타인 주문은 HTTP 상태·업무 오류 코드·메시지를 같게 처리한다.
타인 주문의 상태·기존 결제 결과·멱등 키 충돌 정보를 먼저 반환하지 않는다.
거절된 고객 요청은 주문 선점·재고 변경·PG 생성/조회·복구 작업 인계를 일으키지 않는다.
고객 입력 형식 오류 간의 상세 우선순위, 202/200 응답 DTO와 조회 DAO 계약은 후속 설계에서 정한다.

2026-10-22 계획 리뷰 보완으로 처리 응답의 200/202는 업무 반영 완료 여부로 구분하기로 승인했다.
이미 반영 완료한 주문은 늦은 PG 충돌이 있어도 200·기존 완료 상태·주의 표시이며 미반영 충돌만 202다.
GET은 저장 상태 조회 성공인 200을 유지한다. DTO·경로와 검증 계획은 [상세 계획](../plan.md)을 따른다.

## 별도 경계

- 주문 관련 관리자 조회·미완료 목록·운영자 대사는 아래의 1번 관리자 fixture 검사를 적용한다.
- PG callback은 고객 헤더로 본인 확인하는 API가 아니다. 기존 제공자 계정/거래·주문·금액 검증 및 권위 조회 경계를 따른다.
- 고객 입력 X-USER-ID와 PG가 사용하는 고정 제공자 계정 X-USER-ID:135135를 같은 사용자 신원으로 취급하지 않는다.
- 재시도 라이브러리는 PR03에서 확정한다. 현재 Resilience4j나 Spring Retry 의존성/적용 코드는 없으며 이번 결정으로 도입하지 않는다.

### 관리자·운영 담당자 접근 문답 · 1번 관리자 fixture 채택

관련 범위는 주문 관리자 조회·미완료 목록·운영자 대사다. 다른 고객의 주문을 확인·처리할 수 있어 고객 소유권 검사와 구분한다.
사용자는 기존 1번 사용자를 관리자 fixture로 지정하고 이 경로에서 X-USER-ID=1을 확인하는 최소안을 선택했다.
관리자 URL만 분리하고 권한 검사 없이 유지하는 안은 채택하지 않았다.
기존 사용자 존재 검증도 유지한다. 1번 이외 사용자가 관리자 경로에서 주문 상태를 읽거나 대사 효과를 일으키지 못하게 한다.
1번 사용자는 관리자 경로에서 다른 고객 주문도 조회·처리할 수 있지만, 고객 경로에서는 여전히 본인 주문만 처리한다.
운영자 대사는 고객용 reconcile의 소유권 검사를 우회하지 않고 별도 관리자 진입점에서 공통 유스케이스를 사용한다.
정확한 관리자 목록/대사 URL과 거절 오류 매핑은 상세 계획에 명시한다. 실제 로그인·역할 테이블을 추가하지 않으며 상품 등 다른 기존 관리자 API 변경은 이번 선택에 포함하지 않는다.

## 필요한 최소 확인 · 진행 상황

- 완료: 본인의 PG/과거 POINT 주문 상세에 같은 소유권 규칙을 적용했고 관련 DAO/HTTP 검사로 확인했다.
- 완료: confirm/상세/reconcile의 타인 404, GET의 PG/재고/진행 변경 없음, 거절된 대사의 인계/조회 없음.
- 완료: 헤더 누락 400·본인 POINT 재확정 오류·기존 데이터 보존을 확인했다.
- 완료: 1번 관리자의 타인 조회/대사·다른 사용자 403·GET 효과 0건·관리자 링크를 따른 200과 수동 대사의 관리자 URL.
