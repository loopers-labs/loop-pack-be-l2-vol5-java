# 미완료 작업 조회·운영 담당자 수동 대사

[설계 질문 목록](total_trade_off.md) · [자동 만료 논의 보류](../../r01-pg-payment-foundation/trade_off/09-recovery-lease.md) · [공통 결과 반영 TX](01-facade-transaction-boundary.md)

상태: **수동 복구·실행 ID 교체·저장 관찰 재적용 방향 채택·상세 계약 설계 전·구현 전**.

## 사용자 결정과 변경 범위

2026-10-21 사용자는 자동 실행 권한 만료 논의를 보류하고 운영 담당자가 장애로 중단된 작업을 찾아 수동 대사하는 방식을 선택했다.
정상 실행 중 @Retryable의 최초 조회+추가 3회·1/3/10초·지터 ±20%는 유지한다.
서버 장애 뒤 미완료 작업을 자동으로 이어가는 이전 결정은 담당자 수동 대사 경로로 변경한다.
DB의 시도·작업·사용 횟수·재고 처리 기록은 보존한다. 재시작을 이유로 새 PG 결제를 만들거나 자동 재시도 예산을 초기화하지 않는다.
고정 lease·갱신형 lease·상시 자동 회수 스케줄러는 이번 방향에 도입하지 않는다.
후속 [최소 보완 결정](../../r01-pg-payment-foundation/trade_off/10-learning-scope-completion.md)으로 수동 요청이 미완료 작업의 실행 ID를 조건부 교체하고 옛 실행의 진행 갱신을 차단한다. 이미 저장한 신뢰할 종결 결과가 미반영이면 이를 재적용하며, 항상 PG 재조회부터 요구하지 않는다.

## 조회와 처리의 구분

- 담당자는 미완료 결제/복구 작업을 조회한다. 목록에는 처리 중·결과 미확인·재시도 소진·내부 반영 미완료 및 장애 중단 의심 기록을 포함할 수 있어야 한다.
- 확인한 PG 결과·복구 진행·사용 횟수·마지막 실행/갱신 시각·오류 등 판단에 필요한 정보를 제공한다. 정확한 필드·필터·목록 경로·페이지 계약은 미정이다.
- DB의 실행 중 표시나 오래된 시각만으로 프로세스가 확실히 종료됐다고 단정하지 않는다. 정상 실행 중인 작업도 미완료 목록에 있을 수 있다.
- 목록/주문 GET은 조회 전용으로 유지한다. 조회 API 자체가 결제 생성·자동 재시도·재고 복구를 발생시키지 않는다.
- 고객 대사는 POST /api/v1/orders/{orderId}/payment/reconcile에서 본인 주문만 처리한다. 운영자 대사는 별도 관리자 진입점을 사용하고 내부 공통 대사 유스케이스를 재사용한다. 정확한 관리자 URL은 상세 계획에서 정한다.
- 2026-10-22 결정으로 주문 관리자 조회·미완료 목록·운영자 대사에 X-USER-ID=1인 기존 관리자 fixture를 확인한다. 다른 고객 주문 처리도 허용하지만 실제 로그인·역할 테이블은 추가하지 않는다. [접근 결정](04-customer-ownership-and-api.md)을 따른다.

## 수동 대사 흐름

```text
담당자가 미완료 목록 조회
→ 처리할 주문을 정해 수동 대사 요청
→ 짧은 DB TX에서 미완료 상태·현재 실행 ID를 조건으로 새 실행 ID 기록
→ 저장된 검증 종결 결과가 미반영이면 해당 사실 사용
  그 외에는 TX 밖에서 기존 PG 거래 조회·식별/금액/계정 검증
  새로 검증한 관찰은 별도 짧은 TX에서 먼저 commit
→ 공통 결과 반영 TX
```

- SUCCESS면 주문을 확정하고 이미 차감한 재고를 유지한다.
- 검증된 FAILED 또는 계약에 맞는 생성 전 확정 거절이면 같은 결과 반영 TX에서 mall 재고와 복구 완료 기록을 함께 갱신한다.
- PENDING·0건·404·조회 장애는 미완료/확인 필요를 유지한다. 복수 거래·불일치·종결 충돌은 사실을 보존하며 임의 종결하지 않는다.
- 담당자 입력만으로 성공/실패나 재고를 강제 변경하지 않는다. 권위 조회·검증과 공통 멱등 결과 반영을 사용한다.
- 검증·저장된 생성 전 확정 거절은 거래가 없으므로 저장 사실을 재적용한다. 이후 404/빈 목록으로 거절을 새로 추론하지 않는다. callback 본문이나 운영자 입력은 검증된 저장 근거를 대신하지 않는다.
- 자동 조회 한도는 자동 실행의 예산이다. 수동 대사는 명시적인 별도 확인 요청이며 자동 @Retryable 예산을 새로 부여하지 않는다. 아래 결정에 따라 PG 조회는 요청당 최대 1회다. HTTP 제한은 R01 설정을 재사용하며 반복 요청 제한의 세부는 상세 설계에서 정한다.
- 이미 반영 완료된 주문에 같은 요청이 들어오면 기존 상태를 보호한다. callback·수동 요청의 동시 적용도 추가 확정/복구를 만들지 않는다.
- 권한 확인 후 이미 업무 반영 완료라면 실행 claim/인계·PG 조회 없이 200과 저장 상태를 반환한다. 늦은 충돌 주의는 그대로 보여주며 미반영 충돌의 202와 구분한다.

## 실행 권한과 중단 작업 처리 결정

### 2026-10-22 수동 요청의 조회 범위 문답 · 최대 1회 채택

저장된 검증 종결 결과가 미반영이면 PG 조회 없이 재적용하는 원칙은 이미 확정했다.
사용자는 그 외의 수동 요청에서 최대 한 번 PG 조회하고 미완료면 202로 응답하는 안을 선택했다.
응답 대기를 줄이고 후속 확인은 다음 명시적 대사에 맡긴다. 한 요청 안에서 여러 차례 조회·대기하는 안은 채택하지 않았다.
저장된 종결 결과 재적용은 PG 조회 0회다. 조회할 때는 거래 키가 있으면 키 조회, 없으면 주문별 조회 중 한 경로를 사용한다.
자동 재조회 예산 초기화·새 PG 생성은 금지한다. 이 수동 조회 때문에 자동 사용 회차를 증가시키지 않으며 최근 수동 조회 시각·진행 기록의 구체적인 저장 방식은 상세 계획에 명시한다.
PENDING/미확인 응답은 수동 확인이 필요한 상태로 남기며 새로운 자동 대기 작업을 시작하지 않는다.

자동 lease를 생략해도 정상 실행 중 작업과 수동 요청의 경합을 보호해야 한다.
멱등성 키·DB 제약과 원자적 조건부 상태 갱신으로 진행·권한을 보호하고 실행 식별자로 이전 실행의 늦은 갱신을 막는다. 명시적 비관적 잠금 조회를 필수로 두지 않는다.
수동 요청은 미완료 작업의 기존 실행 ID·상태를 조건으로 새 실행 ID를 기록해 기존 자동 진행 권한을 무효화한다. 중단 RUNNING도 인계할 수 있어야 하며 경쟁에서 진 요청은 최신 상태를 확인한다. 옛 실행은 진행/회차를 갱신하지 못하고 일반 save도 이를 우회하지 못하게 한다. 허용 상태·조건식·응답은 아래 커밋 7 구현 기록과 상세 계획을 따른다.
이미 발송된 PG 조회가 완료될 수 있다는 점과 새 조회/진행 변경의 권한을 구분해 설계한다.

## 이득·비용·검증

- 이득: 자동 만료/갱신·재시작 자동 회수를 이번 학습 범위에서 제외하고 기존 수동 대사 경로를 중심으로 복구할 수 있다.
- 비용: 중단 작업은 담당자가 확인할 때까지 미완료로 남고 재고도 확보된 상태를 유지한다. 목록과 최근 처리 정보를 신뢰할 수 있게 보존해야 한다.
- 대표 검증: 프로세스 종료 후 기록 보존·목록 노출·재시작 자동 create/lookup 재개 없음·수동 대사로 검증 결과 반영.
- 대표 검증: 목록 GET의 무효과, 동시/반복 수동 대사와 callback의 확정/복구 한 번, 미확인 상태의 재고 유지.
- 대표 검증: 실행 ID 교체 뒤 옛 실행의 늦은 진행 save 차단, 거절 사실 저장 뒤 업무 반영 rollback/재시작 시 저장된 근거로 한 번 복구.

## 커밋 7에서 연결한 범위

고객 `POST /api/v1/orders/{id}/payment/reconcile`와 관리자 `POST /api-admin/v1/orders/{id}/payment/reconcile`를 구현했다. 본문 없이 기존 X-USER-ID를 사용한다. 상태·실행 ID·사용 회차가 같은 작업만 새 실행으로 인계하고 자동 사용 회차는 유지한다.
수동 조회 직전의 lastCheckedAt 갱신도 실행 ID·회차 CAS로 commit한다. 이전 실행이 이미 보낸 PG 조회를 마칠 수는 있지만 늦은 진행·실패 표시는 인계자의 상태를 바꾸지 못한다. 수동 실패 표시는 준비에서 얻은 실행 snapshot을 공통 업무 반영에 전달해 보호한다.
관련 기능 11건·ArchUnit 8건·Checkstyle·세 관점 리뷰를 통과했다. 이후 최종 전체 검사 432건과 별도 JVM 실험을 마쳤다. 주문 50은 실제 조회 도중 commerce를 종료한 뒤 RUNNING·실행 ID·회차·시각 보존, 미완료 목록 GET의 무효과, 수동 POST 인계 후 한 번의 완료를 확인했다. 주문 51은 PG 재시작 후 같은 거래의 완료를 대사했다. 새 frontend·운영 화면·자동 lease는 추가하지 않았다. [실제 결과](../result.md)와 [리뷰 기록](../review.md)을 따른다.
