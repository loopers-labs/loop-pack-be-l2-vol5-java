# callback 처리 시점

[결정 목록](total_trade_off.md) · [공통 결과 반영](03-common-result-application.md) · [수동 대사](06-interrupted-payment-reconcile.md)

상태: **요청 안의 동기 처리 구현·관련 검증·세 관점 기능 리뷰 완료**. 2026-10-22 사용자 선택을 기록한다.

## 이미 정한 원칙

callback은 알림이며 본문의 status만으로 주문이나 재고를 바꾸지 않는다.
기존 주문·시도에 연결된 거래를 PG에 권위 조회하고 주문·거래 키·금액·제공자 계정 범위를 검증한다.
새로 확인한 관찰을 먼저 별도 commit한 뒤 공통 업무 TX를 호출한다. PG HTTP는 DB TX 밖이다.
고객/관리자용 사용자 헤더 검사는 callback 처리에 적용하지 않는다.

## 선택과 비용

| 대안 | 흐름 | 이득 | 비용 |
|---|---|---|---|
| 요청 안에서 동기 처리 · 채택 | callback 요청에서 권위 조회·관찰 commit·공통 반영 후 응답한다. | 별도 callback 작업 실행기를 만들지 않고 처리 경계를 따라가기 쉽다. | 조회가 지연되면 응답도 지연된다. PG의 송신 timeout 이후 우리 처리가 끝날 수도 있다. |
| 접수 후 별도 실행기 · 미채택 | 접수 응답 후 별도 실행기에서 권위 조회·관찰 저장·반영한다. | callback 접수 응답을 빨리 돌려줄 수 있다. | 실행 대기·거절·중단 경계를 추가로 처리해야 한다. 접수 응답 자체가 최종 처리 보장은 아니다. |

사용자는 요청 안의 동기 처리를 선택했다. commerce에 별도 callback 접수 큐·실행기를 추가하지 않는다.
동기 요청 전체를 @Transactional로 감싸지 않는다. 권위 조회는 TX 밖, 관찰 저장과 공통 업무 반영은 각각 짧은 별도 TX다.
callback 응답 전달 여부가 결제 결과의 증거를 대신하지 않는다.
검증 실패·확인 불가·중단은 임의 성공/실패를 만들지 않으며 기존 기록과 수동 대사로 확인한다.
PG의 callback 송신은 이미 best-effort 1회다. 이번 선택으로 callback outbox·자동 발송 재시도를 추가하지 않는다.
정확한 응답 코드·중복/미등록 거래 처리와 오류 매핑은 상세 계획에서 명시한다.

## 커밋 8의 연결

알림의 세 문자열을 검증하고 등록된 단일 시도·주문·STARTED를 확인한다. 미등록 404·저장 거래 키와 다른 알림 409에서는 PG를 호출하거나 결과를 변경하지 않는다.
저장 키가 없으면 알림 키를 그대로 조회 키로 삼지 않고 저장된 providerOrderId로 조회한다. 검증한 PG 거래 키와 알림 키가 일치한 뒤 관찰을 저장한다. 고객/관리자 사용자 헤더 없이 고정 PG adapter의 계정·주문·금액 검증을 재사용한다.
callback은 claim·인계·회차 소비를 하지 않는다. 조회 전의 작업 snapshot을 공통 반영에 전달해 조회 중 수동 인계 뒤의 늦은 실패 표식을 차단한다. 최신 업무 완료 여부로 200/202를 반환하며 응답은 completed/attentionRequired 두 값뿐이다.

## 관련 검증 완료

- 완료: 실제 callback controller에서 본문 대신 권위 조회 결과로 관찰 저장·공통 반영한다.
- 완료: 중복 callback/수동 대사가 실제 확정·반환을 추가하지 않는다. 조회 실패는 결제 실패로 만들지 않고 PG 성공 근거도 업무 rollback에서 보존한다.
- 완료: callback HTTP/MySQL 8건·ArchUnit 8건·Checkstyle·세 관점 기능 리뷰. 중요 지적은 없다.
- 완료: 별도 PG/commerce 프로세스에서 callback 먼저 도착·늦은 생성 응답의 종결 보호, PG 송신 timeout 뒤 실제 commerce 저장 완료를 확인했다. 전체 검사 432건과 프로세스 재시작 실험도 통과했다. [실제 결과](../result.md)를 따른다.
