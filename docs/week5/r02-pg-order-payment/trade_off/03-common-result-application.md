# 공통 결과 반영의 중복 방지

[결정 목록](total_trade_off.md) · [트랜잭션 경계](01-facade-transaction-boundary.md) · [재고 복구](02-stock-restore-and-admin-update.md)

상태: **결과 반영 주문 CAS·내부 공통 TX 구현·callback/대사 API 연결 전**. 2026-10-22 사용자 선택을 기록한다.

## 정할 문제

callback과 수동 대사가 같은 결제 실패를 동시에 확인할 수 있다. 두 경로가 모두 재고 2를 반환하면 한 주문에서 4가 복구되는 오류다.
검증 결과를 먼저 저장하는 정책은 유지하고, 공통 업무 반영에서 실제 효과를 한 번만 적용할 경계를 정한다.
준비 단계의 DRAFT→PAYMENT_PENDING CAS는 이미 선택했지만, 이번 질문은 결과를 반영하는 단계다.

| 대안 | 처리 방식 | 이득 | 비용 |
|---|---|---|---|
| 결과 반영도 주문 상태 CAS · 채택 | PAYMENT_PENDING일 때만 CONFIRMED/PAYMENT_FAILED로 갱신한 실행이 나머지 업무를 진행한다. | 준비 단계와 같은 조건부 갱신 방식으로 적용 권한을 판단한다. | bulk 갱신 후 JPA 객체 정합성과 갱신 실패 시 최신 상태 확인이 필요하다. |
| 결과 반영은 주문 행 잠금 · 미채택 | 공통 TX에서 주문을 잠근 뒤 대기/종결 상태를 확인하고 필요한 업무만 진행한다. | 읽은 상태를 기준으로 순차 처리하기 쉽다. | 주문 준비 CAS와 결과 반영의 조율 방식이 달라지고 주문 잠금 구간이 추가된다. |

사용자는 결과 반영도 주문 CAS로 조율하기로 선택했다. 별도 SELECT FOR UPDATE로 주문을 선점하는 안은 채택하지 않았다.
준비의 DRAFT→PAYMENT_PENDING과 반영의 PAYMENT_PENDING→종결은 서로 다른 CAS이며, 각각 해당 TX의 다른 변경과 함께 commit한다.
다음 원칙을 따른다.

- 저장된 PG 결과와 충돌 표시를 공통 TX에서 결제 시도 행을 짧게 잠가 확인한다. 실제 상품 재고를 변경할 때의 기존 잠금도 유지한다.
- 주문 기록·실제 상품 수량·차감 기록·복구 작업 적용 완료를 같은 업무 TX에서 commit/rollback한다.
- 먼저 바꾼 주문 상태도 그 TX의 일부다. 재고 복구가 실패하면 주문 상태까지 함께 rollback되고 처리 완료로 노출되지 않는다.
- PG HTTP·관찰 저장 commit은 이 업무 TX 전에 끝낸다. 업무 반영 중 PG를 호출하지 않는다.
- 중복 요청은 이미 반영한 상태를 반환하고 추가 주문 기록·차감·복구를 만들지 않는다. 경합에서 진 실행은 오래된 객체로 업무를 계속하지 않는다.
- 이미 충돌한 관찰은 임의 성공/실패로 새 업무를 적용하지 않는다. 이미 반영한 뒤 늦게 상충 관찰이 도착해도 과거 업무를 자동 반전하지 않는다.
- 결제 시도·주문·상품·차감 기록의 일관된 접근 순서, 지연 충돌의 수동 표시와 구체 DAO/TX 계약은 상세 설계에서 확정한다.

R01의 재고 기록 version 검증과 주문 기록 유일 제약도 유지한다. 이번 선택을 모든 DB 잠금을 없애는 것으로 해석하지 않는다.

## 계획 리뷰 보완 · 2026-10-22 사용자 승인

업무 rollback 뒤 실패 표시를 저장할 때는 실패한 업무 시도 직전 또는 해당 TX에서 확보한 작업 상태·실행 ID·사용 회차를 그대로 비교한다.
실패 후 최신 실행을 읽어 기준으로 삼으면 인계받은 새 실행을 덮을 수 있다. 당시 READY/ID 없음/회차 0도 모두 비교하고 조건이 바뀌면 실패 표시를 건너뛴다. APPLIED를 되돌리지 않는다.

이미 업무 반영 완료한 주문에 늦은 PG 충돌이 기록돼도 기존 업무를 보호하고 200·기존 완료 상태·주의 표시로 응답한다.
미반영 충돌만 202·수동 확인 필요로 구분한다. 구체 구현 순서와 대표 경합 검증은 [상세 계획](../plan.md)을 따른다.

## 구현과 후속 진입 경로 확인

내부 공통 UseCase의 중복 성공/실패 반영·실패 근거 보존·재고 overflow 후 재적용·옛 실패 표시 차단을 실제 DB로 확인했다. [리뷰 기록](../review.md)에 최소 검사와 사용자 승인 보완을 남겼다.
표식 저장만 실패해도 새 TX에서 현재 상태를 확인하고, 이미 완료했다면 완료 상태를 우선 반환한다. 상태 조회까지 실패하면 오류를 전파한다.
아래 실제 callback/수동 대사 HTTP 진입 검증은 해당 API 연결 후 진행한다.

- 같은 실패의 동시 callback/수동 대사에서 복구 수량이 한 번만 증가하는지 확인한다.
- 성공 결과의 중복 적용이 주문 기록을 추가 생성하지 않는지 확인한다.
- 일부 품목 복구 실패 시 전체 업무 rollback과 먼저 저장한 PG 근거 보존을 확인한다.
