# 5주차 부하 측정 — 설계한 규칙과 회복이 어디까지 버티나

과제 범위 밖에서 한 측정이다. 확인하려는 가설은 하나다.

> 부하가 아무리 커져도 우리 시스템은 **느려지거나 거절될 뿐, 틀린 결과를 만들지 않는다.**

그래서 두 가지를 같이 본다.
1. **어디서부터 느려지거나 거절되나** — k6 응답 시간·실패율, DB 커넥션 풀, Tomcat 스레드
2. **끝난 뒤 규칙이 지켜졌나** — `invariants.sql`의 "규칙이 깨진 상태" 쿼리가 모두 0건

## 단계

PG 장애를 하나씩만 넣는다 — 원인을 분리하기 위해서다. 먼저 장애 없는 기준선을 잰다.

| 단계 | 테스트 PG 상태 | 확인할 것 | 대비한 회복 경로 | 상태 |
|---|---|---|---|---|
| 0 | 정상: create 바로 202, 1초 뒤 callback, 조회 SUCCESS | 우리 시스템만의 한계 | — | **완료** |
| 1 | callback 안 옴 | 회복 작업이 미종결을 다 회수하나 | 스케줄러(ⓑ) | **완료** |
| 2 | create 응답 3초 지연(timeout 2초를 넘김) | UNKNOWN이 쌓이고 고객 응답이 얼마나 늘어나나 | 바로 재조회(ⓐ) | **완료** |
| 3 | 조회 5xx → 도중에 정상으로 복구 | 회로가 열리고 상태가 유지되며, 복구 뒤 다시 회수되나 | circuit breaker, D-044 | **완료** |

단계 1~3은 VU 100, 1분이다(단계 0에서 VU 100부터 처리량이 더 오르지 않았다). 단계마다 앱을 새로 띄워 스키마·seed·회로 상태를 초기화한다(`run-stage.sh`).

## 실행 순서

```bash
# 1) 인프라 (kafka는 쓰지 않으므로 끈다)
docker compose -f docker/infra-compose.yml up -d && docker stop kafka-ui kafka

# 2) 테스트 PG (WireMock standalone, 18080)
docs/week5/load-test/pg-stub/pg-stub.sh start
docs/week5/load-test/pg-stub/pg-stub.sh stage 0          # 단계를 바꾸면 받은 요청 기록도 비운다

# 3) 앱 — seed 프로필로 상품 1만 개(재고 각 100)·사용자 500명(포인트 1,000,000). 띄울 때마다 스키마를 새로 만든다
./gradlew :apps:commerce-api:bootRun --args='--spring.profiles.active=local,seed --spring.jpa.show-sql=false --server.tomcat.mbeanregistry.enabled=true'

# 4) 측정 — VU마다 1분, 지표를 1초마다 기록
docs/week5/load-test/run-ladder.sh 0 10 50 100 200

# 5) 회수가 끝나면 규칙 확인 (위 6개가 모두 0, 4번은 pg-stub.sh count와 같아야 한다)
docker exec -i docker-mysql-1 mysql -uapplication -papplication loopers < docs/week5/load-test/invariants.sql
docs/week5/load-test/pg-stub/pg-stub.sh count
```

### 테스트 PG의 한계
WireMock은 상태를 기억하지 못한다. 그래서 거래 키에 금액을 넣어(`TEST-TX-{주문 식별자}-{금액}`) 단건 조회가 키에서 금액을 꺼내 답한다. **키를 모르는 목록 조회(UNKNOWN 결제)는 금액을 알 수 없어 빈 목록**으로 답한다 — 단계 2에서 UNKNOWN은 실제 PG와 달리 0건으로 남는다.

(왼쪽: 첫 측정, 오른쪽: D-047 반영 뒤 재측정. 확정 경로는 바꾸지 않았으므로 차이는 측정 회차·JVM 예열에 따른 편차로 본다.)

- **DB 커넥션 풀이 먼저 바닥난다.** VU 50부터 40개가 모두 쓰이고 대기가 생긴다. VU 100부터 처리량이 더 오르지 않고 응답 시간만 VU에 비례해 늘어난다(리틀의 법칙: 200 ÷ 초당 86건 ≈ 2.3초).
- PG 호출은 트랜잭션 밖이고 OSIV도 꺼져 있다. 그래도 결제 한 건이 트랜잭션을 여러 번 쓴다(주문 생성, TX A, 수락 기록, 응답용 조회, callback 저장).
- 첫 측정 VU 200의 실패 2건은 커넥션을 3초 안에 얻지 못한 500이다. 롤백돼 결과는 틀어지지 않았다. 그중 1건은 create를 보낸 뒤 수락 기록을 저장하지 못해 REQUESTED로 남았다(회복 작업 대상).

### 회복 작업이 따라잡나 — 측정이 찾은 결함과 고친 결과

| | D-034 (회차당 100건) | D-047 (초당 20건 상한, 밀린 게 없을 때까지 계속) |
|---|---|---|
| 부하 직후 밀린 callback | 17,080건 | 21,180건 |
| 실제 처리 속도 | 3분에 100건 | **초당 약 13.3건** (상한 20은 한 번도 걸리지 않음) |
| 다 비우는 데 | 약 8.5시간 (추정) | **약 26.5분** (실측, `results/stage0-drain.csv`) |

- 회차당 상한은 깨어날 때 초당 약 50건을 몰아 보내고 178초를 쉬었다. PG 부담(순간 최대)은 크고 처리량은 작았다 → 상한의 단위를 초로 바꿨다(D-047).
- 바꾼 뒤 속도를 막은 건 상한이 아니라 **한 건씩 차례로 처리하는 구조**다. 한 건마다 PG 조회 → TX B → 일정 기록 → 수신함 정리를 차례로 해 약 75ms가 든다.
- 26.5분은 회복 감시 알림 기준(15분, D-035)을 넘는다. 이번 부하는 VU 200을 1분 동안 계속 넣은 극단적인 경우다. 병렬 처리·트랜잭션 합치기는 보류했다(`design.md` 8번).

### 규칙
두 측정 모두 `invariants.sql` 6개 **0건**. 재측정에서 결제 21,580건이 모두 CONFIRMED로 끝났고, 테스트 PG가 받은 create 21,580건 = 결제 시도 21,580건, 충돌 0건, 회복 처리 실패 0건.

## 단계 1~3 결과 (2026-10-23, VU 100 · 1분)

| 단계 | 처리량(건/초) | 확정 p50 / p95 (ms) | 실패 | 부하 뒤 결과 | 규칙 6개 |
|---|---|---|---|---|---|
| 1 callback 안 옴 | 88.9 | 770 / 1,362 | 0 | 5,371건 모두 CONFIRMED. 회복 작업이 **270초에 회수(초당 약 19.9건)** | 0건, create 5,371 = 시도 5,371 |
| 2 create 3초 지연 | **40.0** | **2,201 / 3,361** | 0 | 2,482건 모두 UNKNOWN, 재고 유지, 실패 처리 0 | 0건, create 2,482 = 시도 2,482 (**재발송 0**) |
| 3 조회 5xx → 복구 | 106.0 | 659 / 1,080 | 0 | 장애 중 상태 유지, 복구 뒤 6,406건 모두 CONFIRMED | 5개 0건, create 수 대조는 확인 못 함(아래) |

### 단계 1 — callback 없이도 회수한다
- 수신함이 비어 있어 회복 작업은 "다음 확인 시각이 지난 미종결"만 조회한다. 결제 시작 1분 뒤부터 대상이 되고, 상한 20에 거의 닿았다.
- 단계 0의 초당 13건보다 빠른 이유: 수신함이 없으면 묶음마다 수신함 행 500개를 읽고 행마다 결제 시도를 찾는 조회가 없다. **수신함 처리 비용이 회수 속도를 깎는다**는 뜻이다.
- 회수 구간은 DB의 확정 시각(최초 → 마지막)으로 구했다. 30초 단위 기록은 관찰을 늦게 시작해 남지 않았다.

### 단계 2 — 응답을 잃어도 실패로 처리하지 않는다
- 확정 요청마다 create timeout(2초)을 기다리고 바로 재조회까지 해 응답이 2.2초로 늘고 처리량이 절반이 됐다. Tomcat 스레드는 최대 110, DB 커넥션 대기는 최대 60이었다.
- 2,482건 모두 UNKNOWN으로 남고 재고를 유지했다. 뒤늦게 온 callback 2,482통도 수신함에서 모두 처리됐다(목록 조회 0건 → 0건 횟수만 증가).
- 테스트 PG 한계: 실제 PG라면 목록 조회로 거래를 찾아 확정됐을 것이다. 여기서는 빈 목록이라 UNKNOWN에 머문다.

### 단계 3 — 회로가 PG를 보호하고, 복구 뒤 다시 회수한다
```
11:33  부하 끝. 수신함 6,406통
11:36  회차 시작 — 조회 20건 실패 → 회로 OPEN
11:36~11:43  6,406건을 모두 "물어보지 못함"으로 처리(재시도로 미룸). 그동안 PG에 간 조회는 62건뿐
             (처음 20건 + 30초마다 탐색 3건). 상태·재고는 그대로
11:43  테스트 PG를 정상으로 되돌림
11:46  다음 회차 — 탐색 성공 → 회로 CLOSED → 8.7분 동안 6,406건 모두 확정(초당 약 12건), 포기(GAVE_UP) 0
```
- **회로가 없었다면** 회복 작업이 실패할 조회 6,406건을 그대로 보냈을 것이다. 회로 덕분에 PG 호출은 1%(62건)였다.
- **측정이 찾은 결함과 수정**: 처음 측정에서는 회차가 3,000건만 조회하고 끝났고 나머지 2,360건은 한 번도 조회되지 않았다(`results/stage3-before-fix/`). 회차 도중 시각이 흐르게 둔 탓에, 회차가 재시도 간격(3분)보다 길어지자 먼저 실패한 행이 같은 회차 안에서 다시 차례가 됐다. 수신함은 오래된 순으로 500개씩 읽는데 그 500개가 전부 이번 회차에 이미 처리한 결제라 건너뛰었고, 묶음이 비었다고 판단해 회차를 끝냈다. 판단·기록 시각을 회차 시작 시각 하나로 고정해 고쳤다(재현 테스트: `PaymentRecoveryJobTest` "뒤쪽 결제가 굶지 않는다"). 정상 PG에서는 처리한 결제가 바로 확정돼 드러나지 않는, **실패가 반복되는 장애에서만** 나타나는 결함이었다.
- **create 수 대조를 확인하지 못한 이유**: PG 규칙을 정상으로 바꾸면 테스트 PG의 요청 기록이 지워져서, 바꾸기 직전에 create 수를 남기게 했다. 그런데 0으로 기록됐다. 처음 측정에서 멈춘 관찰 스크립트가 바로 끝나지 않고 새 측정 도중 먼저 규칙을 바꿔 기록을 지웠을 가능성이 크지만 확인할 수 없었다. 결제 시도 6,406건 모두 한 번씩 확정됐고 재발송 경로는 단계 0·1·2와 같다.

## 정리
- **가설은 버텼다.** 정상·callback 없음·create 지연·조회 장애 네 상황 모두 규칙 위반 0건이다. 부하와 장애는 "느려짐"(커넥션 대기, 응답 2초대)과 "늦게 끝남"(회수 수 분~수십 분)으로만 나타났다.
- **먼저 바닥나는 자원은 DB 커넥션 풀(40)이다.** VU 50부터 대기가 생기고 VU 100부터 처리량이 초당 86~106건에서 멈춘다.
- **측정으로 결함 두 개를 찾아 고쳤다.** 회차당 상한이 만든 처리 지연(D-047)과, 장애 중 회차가 길어질 때 뒤쪽 결제가 굶는 문제다. 둘 다 단위·통합 테스트로는 드러나지 않았다.
- 남은 한계: 회복 작업이 한 건씩 처리해 초당 12~20건이 상한이다(병렬화 보류, `design.md` 7번).
