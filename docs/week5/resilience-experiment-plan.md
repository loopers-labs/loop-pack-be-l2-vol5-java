# PG 조회 장애 실험 — retry·서킷 브레이커·fallback

결제는 PG에서 성공했는데, 우리 서버가 결과를 조회하는 GET이 실패하는 사건 하나를 따라가며 retry·서킷 브레이커·fallback을 하나씩 붙였다. 회차마다 **질문 → 처음 생각 → 확인한 것 → 정한 것** 순서로 적는다.

이 문서는 실험과 판단의 기록이다. 최종 결정은 [ADR 0031](../adr/0031-pg-lookup-retry-circuit-breaker-and-fallback.md), 구현과 전체 검사 결과는 [구현 기록](implementation-log.md)에 둔다.

## 실험 조건

모든 회차는 같은 주문 하나로 시작한다. **재고 5개 상품을 3개 주문**하고 confirm까지 끝낸 상태다.

```text
confirm
  TX A   가용 재고 5 → 2, 주문 PAYMENT_PENDING, 예약 RESERVED, 결제 시도 REQUESTED
  POST   PG에 거래 1건 생성
  TX B   생성 응답 기록 → 결제 시도 PENDING

reconcile (고객의 결제 확인)
  DB에서 주문·결제 시도를 읽는다
  GET    PG에 기존 거래를 조회한다
  TX B   검증한 결제 결과·관찰 이력을 저장한다
  TX C   저장된 SUCCESS·FAILED를 주문·예약·재고에 반영한다
         이미 결과를 저장했다면 GET·B 없이 C부터 복구한다
```

- 가짜 PG(`FakePaymentServer`)는 테스트가 띄우는 실제 HTTP 서버다. 요청마다 응답 코드·지연을 예약할 수 있다. 예: `replyNext(503, "")`는 다음 요청 하나에만 503을 돌려준다.
- 셀 값은 **PG가 받은 GET 수, 결제·주문·예약 상태, 가용 재고**다. 회로를 볼 때는 회로가 센 실패·성공 표본을, 대기를 볼 때는 소요 시간을 더한다.
- 어느 실험에서든 지키는 기준이 있다. **생성 POST는 다시 보내지 않는다.** 결과를 모르면 결제를 실패로 만들지 않고 재고도 돌려주지 않는다.

## A. retry·fallback

### 1회차 — 조회가 한 번 503이면?

**질문.** PG 거래는 SUCCESS로 바뀌었고, 우리 DB는 아직 PENDING이다. 고객이 결과를 확인했는데 이번 GET만 503이면 어떻게 될까? (retry를 붙이기 전 상황)

| 시점 | PG 거래 | 결제 / 주문 / 예약 | 가용 재고 | GET 누적 |
| --- | --- | --- | --- | --- |
| 장애 설정 직전 | SUCCESS | PENDING / PAYMENT_PENDING / RESERVED | 2 | 0 |
| 첫 reconcile: 503 | SUCCESS | PENDING / PAYMENT_PENDING / RESERVED | 2 | 1 |
| 고객이 다시 누른 reconcile: 정상 | SUCCESS | SUCCESS / CONFIRMED / CONSUMED | 2 | 2 |

POST는 confirm 때 1회뿐이고, 외부 거래도 1건이다. 처음 예상한 값은 모두 맞았다.

**처음 생각과 정리**

| 처음 생각 | 정리 |
| --- | --- |
| 503 = 응답이 안 온 것 | 503은 “지금은 조회를 처리하지 못한다”는 **응답**이다. 답 자체가 안 오는 것은 timeout이다. 둘 다 결제 결과에 대한 정보는 없다 |
| PG까지 실패했다 | 실패한 것은 PG **결제**가 아니라 PG **조회**다. 결제는 SUCCESS 그대로다 |
| 재고가 CONSUMED로 바뀐다 | CONSUMED는 **예약 상태**다. 가용 재고 숫자는 2 그대로다 |
| 다시 POST해도 유니크 칼럼이 막아 준다 | 유니크 제약은 **우리 DB 행**만 막는다. PG로 나간 요청은 못 막는다. 이 테스트 PG는 멱등 키를 받지 않으므로, 중복 결제를 막는 방법은 **POST를 다시 보내지 않는 것**뿐이다 |

- PG는 SUCCESS인데 우리 DB가 PENDING인 것은 이상한 일이 아니다. 우리 DB의 상태는 **마지막으로 PG에게 들은 시점의 기록**이다. 그 차이를 메우는 작업이 reconcile이다.
- reconcile은 고객이 우리 서버에 보내는 요청이고, GET은 그 안에서 우리 서버가 PG에 보내는 조회다.

**다음 질문.** 고객이 두 번 눌러야 하는 일을, 서버가 한 번 더 물어서 끝낼 수 있을까?

### 2회차 — 어떤 실패를 몇 번 다시 물을까?

**질문.** 한 번의 reconcile 안에서 실패한 GET만 다시 시도한다면, 무엇을 몇 번까지 다시 물어야 할까?

`maxAttempts`는 **처음 GET을 포함한 GET의 총 횟수**다. POST는 세지 않는다. 처음에는 “maxAttempts 2 = POST 1 + GET 2”로 셌다가 고쳤다. 성공하거나 다시 물을 필요가 없는 결과를 받으면 남은 횟수를 쓰지 않는다.

| PG 조회 응답 순서 | 최대 1회 | 최대 2회 | 최대 3회 |
| --- | --- | --- | --- |
| 처음부터 정상 | GET 1, 확인 | GET 1, 확인 | GET 1, 확인 |
| 503 → 정상 | GET 1, 미확인 | GET 2, 확인 | GET 2, 확인 |
| 503 → 503 → 정상 | GET 1, 미확인 | GET 2, 미확인 | GET 3, 확인 |
| 계속 503 | GET 1, 미확인 | GET 2, 미확인 | GET 3, 미확인 |

2회에서 3회로 늘리면 얻는 것은 셋째 줄이고, 잃는 것은 넷째 줄의 GET 1회와 대기다. 처음에는 “계속 실패할지를 알아야 정할 수 있다”고 생각했다. 하지만 첫 503을 받은 순간에는 **앞으로 회복될지 미리 알 수 없다.** 그래서 실무에서는 지난 장애 기록(몇 번째에 회복했는지, 끝까지 실패한 비율)으로 정한다. 이 표는 각 상한이 **어떻게 동작하는지** 보여 줄 뿐, 어느 횟수가 좋은지 순위를 매기지 않는다.

**무엇을 다시 물을까**

| GET 결과 | 처음 생각 | 정리 | 이유 |
| --- | --- | --- | --- |
| 503, timeout, 연결 실패 | timeout은 재시도보다 원인 확인? | **제한적으로 재시도** | 대답을 못 들었고, 일시적이면 다시 물을 때 답이 올 수 있다. 계속 쌓이면 그때는 회로가 맡는다 |
| SUCCESS, FAILED | 안 함 | 안 함 | 결과를 알았다. FAILED는 “조회 실패”가 아니라 결제 실패라는 **정상 대답**이다 |
| PENDING | 계속 PENDING이면 다시? | 안 함 | PG가 “처리 중”이라고 **대답한 것**이다. 0.1초 뒤에 물어도 또 PENDING이다. 다시 확인하는 것은 retry가 아니라 **나중의 reconcile**이다 |
| 404, 빈 목록 | 거래가 없으니 POST부터? | 안 함. **POST도 보내지 않음** | “지금 안 보인다”일 뿐 “안 만들었다”는 증거가 아니다 |
| JSON 깨짐 | 재시도 | 즉시 반복하지 않고 원인을 남김 | 응답 형식 변경이나 버그라면 다시 물어도 똑같이 깨진다 |

**retry와 reconcile의 구분** (가장 오래 헷갈린 부분)

> reconcile은 기존 PG 거래를 조회해 우리 기록과 맞추는 작업이다. retry는 그 조회가 일시적으로 실패했을 때 같은 실행 안에서 다시 묻는 것이다.

reconcile은 PENDING뿐 아니라, 생성 응답을 잃어 UNKNOWN인 시도에도 쓴다. retry는 reconcile 바깥의 다른 단계가 아니라 reconcile **안에서** 일어난다.

| 상황 | 답 |
| --- | --- |
| confirm의 POST가 timeout이라 바로 POST를 한 번 더 | 하면 안 됨 (중복 결제) |
| reconcile의 GET이 503이라 0.1초 뒤 GET 한 번 더 | retry |
| PENDING 뒤 10분 동안 callback이 없어 고객이 “결제 확인” | reconcile |
| reconcile의 GET이 PENDING이라 0.1초 뒤 GET 한 번 더 | **의미 없음.** PENDING은 대답을 들은 것 |

**PENDING과 UNKNOWN.** “응답이 안 온다”는 말이 두 뜻으로 섞여 있었다.
- 요청에 대한 답장이 안 옴 → timeout. 생성이면 UNKNOWN, 조회면 retry 대상
- 결과 알림(callback)이 아직 안 옴 → 소식을 기다리는 중. PENDING 그대로

**adapter를 그냥 감싸면 retry가 안 된다.** 처음에는 503이 오면 GET이 2번 나갈 거라고 예상했다. 실제로는 **1번**이다. adapter가 503 예외를 잡아 UNKNOWN **값**으로 돌려주기 때문이다. retry 도구는 기본적으로 예외만 실패로 보므로 “정상으로 끝났다”고 판단한다. 그래서 설정이 아니라 **PG가 실제로 받은 GET 수**로 확인해야 한다. 고칠 방향은 7회차에서 정했다.

### 3회차 — 얼마나 기다리다가 멈출까?

**질문.** 조회 응답이 늦으면, 같은 3회라도 고객의 대기가 크게 늘어난다. 언제 멈추고 fallback으로 가야 할까?

**용어 정리**

| 용어 | 뜻 |
| --- | --- |
| timeout | GET **한 번**을 기다리는 한도. 넘으면 그 GET을 실패로 보고 retry 대상이 된다 |
| maxAttempts | GET을 **몇 번까지** 보낼지 |
| backoff | 재시도 사이에 **쉬는 시간**. 100 → 200처럼 두 배씩 늘리면 지수 백오프 |
| jitter | 쉬는 시간을 **무작위로 조금씩 다르게** 해서, 여러 요청이 같은 순간에 다시 몰리지 않게 하는 것 |
| 예산 | 다음 재시도를 **시작해도 되는지** 판단하는 시간 한도 |

**계산 연습.** GET 한 번이 최대 500ms, backoff가 100·200·400ms라고 가정했다.

| 최대 시도 | 계산상 최대 | 예산 2초라면 |
| --- | --- | --- |
| 1회 | 500ms | 범위 안 |
| 2회 | 500 × 2 + 100 = 1,100ms | 범위 안 |
| 3회 | 500 × 3 + 100 + 200 = 1,800ms | 범위 안 |
| 4회 | 500 × 4 + 100 + 200 + 400 = 2,700ms | 범위 밖 |

계산은 맞았다. 그런데 실제 코드에서는 응답이 계속 늦으면 **2회에서 멈춘다.** GET 한 번에는 응답 대기 500ms 말고도 연결 풀 대기와 연결 시간이 있어서, 한 번의 추정치를 300 + 300 + 500 = **1.1초**로 잡았기 때문이다. 남은 예산이 “가장 긴 쉬는 시간 200ms + 1.1초”보다 적으면 다음 시도를 시작하지 않는다.

**남은 예산이 300ms라면?** 처음에는 “앞의 두 번이 느렸으니 세 번째도 느릴 것”이라서 멈춘다고 답했다. 규칙으로 쓰면 **남은 시간이 GET 한 번의 최대 시간보다 적으면 횟수가 남아도 시작하지 않는다**가 된다. maxAttempts는 채워야 할 횟수가 아니라 상한이다.

**예산이 하지 않는 일.** 예산은 다음 시도를 **시작할지만** 판단한다. 이미 시작한 GET을 남은 시간에 맞춰 끊지는 않는다. 응답 timeout도 “응답 전체 시간”이 아니라 “데이터가 오지 않는 시간”의 한도다. 그래서 1.1초도, 전체 2초도 **반드시 그 안에 끝난다는 보장은 아니다.** 엄격한 종료 시각이 필요하면 따로 구현하고 검증해야 한다.

**backoff를 두는 이유.** 장애 중에 바로 다시 물으면 같은 PG에 요청이 더 몰린다. 처음에는 고정 대기로 횟수를 이해하고, jitter와 동시 부하는 한 번에 넣지 않았다. [AWS의 timeout·retry·backoff 설명](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/).

**fallback은 언제, 무엇을**

| 이번 조회에서 일어난 일 | 처리 |
| --- | --- |
| 재시도할 실패이고 횟수·시간이 남음 | 쉬었다가 다음 GET |
| 재시도 횟수 소진, 또는 예산 부족 | 조회를 멈추고 fallback |
| 다시 물어도 소용없는 실패(형식 오류 등) | 원인을 남기고 fallback |
| 회로 OPEN | PG를 기다리지 않고 바로 fallback |
| SUCCESS·FAILED·PENDING 응답 | 정상 결과. fallback이 아님 |

| 처음 생각 | 정리 |
| --- | --- |
| “나중에 확인하세요”는 이상하다. 실패라고 하고 나중에 돈을 돌려주면? | 실패인지 모르는데 실패라고 하면 틀릴 수 있다. 돌려주려면 취소 API가 필요한데 이번 PG에는 없다. **“결제 결과를 확인하고 있어요”**라고 정직하게 말한다 |
| DB는 어떻게 바꿔야 하나? | 결과를 몰랐으니 **아무것도 바꾸지 않는다.** 결제 시도·주문·예약·재고 그대로 |
| PENDING이 “확인 불가”로 바뀌나? | 바뀌지 않는다. “이번 조회를 못 했다”와 “결제 상태”는 다른 정보다 |

그래서 응답에 `checked` 칸을 두었다. 저장 상태는 그대로 돌려주고, **이번에 PG 대답을 들었는지**만 따로 알린다.

- PG에 물어서 PENDING을 들었다 → `checked: true`
- 물어보지 못했다(retry 소진, 예산 부족, 회로 OPEN) → `checked: false`
- 이미 SUCCESS·FAILED로 끝난 주문 → 다시 묻지 않고 `checked: true`

`checked`는 결제 성공 여부가 아니다.

**아무도 확인하지 않으면?** reconcile을 시작하는 쪽은 고객만이 아니다. callback, 화면의 자동 확인, 배치, 운영자도 있다. 누가 시작하든 안에서 하는 일(GET → 실패면 retry → 결과면 반영)은 같다. 이 회차를 진행할 때는 고객 reconcile과 callback만 있어서, 아무도 확인하지 않으면 PENDING·UNKNOWN이 남았다. 이후 10분이 지난 미완료 시도를 같은 규칙으로 조회하는 배치를 추가했다([ADR 0033](../adr/0033-payment-recovery-batch-for-unfinished-attempts.md)).

**시간만으로 실패 처리하지 않는 이유.** 시간이 지났다는 사실은 결제 결과의 증거가 아니다. 취소 API가 있으면 “취소 요청 → 취소 확인” 뒤에 실패로 만들 수 있지만, 그 취소 응답까지 잃으면 다시 “모름”이다.

### 측정 — 응답 순서별 GET 수와 소요 시간

**무엇을 쟀나.** 현재 설정(최대 3회, backoff 100·200ms, 조회 응답 timeout 500ms, 예산 2초)에서 PG 조회 응답 순서만 바꿨다. 측정 범위는 `ResilientPaymentProvider`의 조회 호출 한 번이다. PG 조회, retry, 쉬는 시간이 들어가고 DB 반영은 들어가지 않는다.

- 장면마다 새 가짜 PG·adapter·회로로 시작했다. 같은 회로로 이어서 재면 앞 실험의 실패가 다음 실험의 차단에 영향을 준다.
- 준비 POST 1회 뒤, warmup 1회를 따로 두고 3회를 쟀다.
- 측정 중 추가 POST는 모두 0회, 외부 거래는 1건이었다.

| PG 조회 응답 순서 | 실제 GET | 소요 시간 (3회) | 반환 | 회로 표본 (실패 / 성공) |
| --- | --- | --- | --- | --- |
| 정상 PENDING | 1 | 1.6~2.3ms | PENDING 확인 | 0 / 1 |
| 503 → PENDING | 2 | 104.8~108.9ms | PENDING 확인 | 1 / 1 |
| 503 → 503 → PENDING | 3 | 316.6~339.1ms | PENDING 확인 | 2 / 1 |
| 503 → 503 → 503 | 3 | 309.6~313.2ms | UNKNOWN (일시적 장애) | 3 / 0 |


**처음 생각과 확인한 것**

- 503 한 번 뒤 PENDING이면 “PENDING은 대답이니까 거기서 끝난다”고 예상했고, 맞았다. GET 2회에서 멈췄다.
- 연속 503은 “요청 비용만 늘어날 것”이라고 예상했다. 실제로 약 310ms와 GET 3회를 쓰고도 결과를 확인하지 못했다. 이때 멈춘 이유는 회로 OPEN이나 예산 부족이 아니라 **최대 3회에 도달**했기 때문이다. 회로는 표본이 3개라 최소 4개에 못 미쳐 CLOSED였다.
- 503 두 번 뒤 정상은, 최대 2회였다면 “확인 불가”로 끝났을 장면이다. 3회째에 PENDING을 확인했다.
- 약 105ms는 GET 한 번의 시간이 아니라 **GET 2회 + 100ms 대기** 전체다. 대부분이 쉬는 시간이다.

**이 측정으로 말할 수 있는 것과 없는 것**

- 말할 수 있는 것: 정해 둔 응답 순서에서 retry가 추가 GET과 대기를 써서 조회를 회복하거나, 비용만 쓰고 멈추는 동작과 그 크기.
- 말할 수 없는 것: **최대 3회가 적절하다는 근거.** 세 번째에 회복하도록 정해 둔 실험을 아무리 반복해도, 실제로 세 번째에 회복하는 빈도는 알 수 없다.
- 로컬 가짜 PG로도 우리 HTTP 호출 시간과 retry 전체 시간은 잴 수 있다. 모르는 것은 **실제 PG의 운영 응답 시간 분포**다.

**다음 질문.** 요청이 한 건이 아니라 계속 들어온다면? 각 요청이 매번 GET 3회와 대기를 쓰며 장애 중인 PG에 계속 요청을 보내야 할까?

## B. 서킷 브레이커

설정: 최근 4개 GET을 보고(COUNT_BASED), 최소 4개가 모이면, 실패율 50% 이상일 때 OPEN. OPEN은 10초, HALF_OPEN에서 시험 2회, OPEN → HALF_OPEN 자동 전환은 끔.

### 4회차 — 언제 OPEN이 될까?

**질문.** GET 결과가 “장애·장애·정상·정상” 순서로 오면 회로는 언제 열릴까?

| 순서 | 이번 GET | 쌓인 표본 | 회로 | 이유 |
| --- | --- | --- | --- | --- |
| 1 | 장애 | 실패 1 | CLOSED | 최소 4개 미달 |
| 2 | 장애 | 실패 2 | CLOSED | 실패율 100%여도 표본 부족 |
| 3 | 정상 | 실패 2, 성공 1 | CLOSED | 아직 표본 부족 |
| 4 | 정상 | 실패 2, 성공 2 | **OPEN** | 4개 충족, 실패율 50% |

처음에는 3번째에서 OPEN이라고 답했다. 3개뿐이라 최소 4개에 못 미치므로, 실패율이 67%여도 판단을 시작하지 않는다.

- **마지막 GET이 정상이어도 열릴 수 있다.** 회로는 그 호출 하나가 아니라 창 안의 결과 전체를 본다.
- **창을 세는 법.** 각 줄은 같은 바구니를 그 시점에 찍은 사진이다. 3번째 줄의 바구니에는 GET 1·2·3이 들어 있고 분모는 3이다. 5번째 GET이 오면 가장 오래된 결과가 빠진다.
- **숫자 하나만 바꿔 보기.** 기준이 75%면 같은 순서도 50%라 CLOSED다. 50% 기준에서 정상·정상·정상·장애는 25%라 CLOSED이고, 다음에 장애가 오면 정상·정상·장애·장애가 되어 OPEN이다. 표현은 “50%가 넘으면”이 아니라 “**50% 이상이면**”이다.

### 5회차 — OPEN은 무엇을 막을까?

**질문.** 회로가 열린 직후 고객 세 명이 reconcile하면?

| 질문 | 처음 생각 | 정리 |
| --- | --- | --- |
| PG가 받는 GET은? | 3번 늘어난다 | **0번.** GET 자체를 보내지 않고 바로 fallback |
| 고객이 받는 응답은? | “닫혀 있다”는 응답 | 회로는 서버 안의 장치라 고객은 모른다. retry 소진 때와 같은 **저장 상태 + `checked: false`**를 받는다. 기다리지 않을 뿐이다 |
| 세 주문의 상태는? | 그대로 | 맞다. OPEN은 “PG에 **못 물어봤다**”이지 결제 실패가 아니다 |
| 3초 뒤 PG가 고쳐지면 GET을 보내나? | 안 보냄 | 안 보낸다. 다만 **정한 10초 동안만** 막는다. 고쳐졌는지는 물어보기 전엔 모른다 |
| 이미 출발한 GET도 끊나? | 아니오 | 아니다. 회로는 **앞으로 나갈 요청**만 정한다. 이미 나간 요청은 timeout이 끊는다 |
| GET에만 달았는데 POST도 막나? | 아니오 | 아니다. 회로는 **감싼 호출만** 막는다 |
| CLOSED에서 동시 GET 수를 제한하나? | 아니오 | 아니다. 동시 개수 제한은 **bulkhead**의 일이다 |

### 6회차 — 언제 다시 닫힐까?

**질문.** OPEN 10초가 지나면 바로 CLOSED가 될까?

처음에는 그렇다고 생각했다. 순서는 항상 **OPEN → HALF_OPEN → CLOSED 또는 OPEN**이다.

- 자동 전환을 꺼 두었기 때문에, 10초가 지난 뒤 **다음 요청이 들어오는 순간** HALF_OPEN이 된다. 그 요청의 GET이 첫 시험이다. 회로가 혼자 PG를 찔러 보지 않고, 시험은 헬스체크가 아니라 **실제 요청**이다.
- HALF_OPEN의 시험 2회 결과로 바로 결정한다.

| 시험 두 번의 결과 | 50% 기준 |
| --- | --- |
| 정상·정상 | CLOSED |
| 장애·정상 | OPEN |
| 정상·장애 | OPEN |
| 장애·장애 | OPEN |

이 설정에서는 장애가 하나라도 섞이면 다시 OPEN이다.

- **주문 하나로 시험할 때의 함정.** 첫 시험에서 그 주문이 SUCCESS로 확정되면, 다음 reconcile은 이미 끝난 주문이라 PG를 부르지 않는다. 그러면 두 번째 시험을 볼 수 없다. 그래서 거래를 PENDING으로 둔 채 회로 회복을 먼저 확인하고, 그 뒤에 SUCCESS로 바꿔 주문 확정을 확인했다. “회로 회복”과 “주문 결제 완료”는 다른 사건이다.
- HALF_OPEN의 시험 GET이 멈춰 있으면, 회로가 아니라 **timeout**이 끊는다.
- 서버를 재시작하면 메모리에 있던 회로는 **CLOSED로 새로** 만들어진다. DB의 결제 시도·예약은 그대로다. 회로는 “최근 분위기”를 적은 메모이고, 결제는 잃으면 안 되는 사실이다.
- **회로가 닫혔다고 응답을 쓸 수 있다는 뜻은 아니다.** 형식이 깨진 응답은 회로에서 실패로 세지 않는다(8회차). 그래서 HALF_OPEN의 시험 응답이 JSON 오류여도 CLOSED로 돌아갈 수 있고, 그 응답 자체는 여전히 확인 불가로 처리된다.

## C. retry와 회로 결합

### 7회차 — 어떤 순서로 감쌀까?

**질문.** retry와 회로를 둘 다 붙일 때, 어느 쪽을 바깥에 둘까?

처음에는 두 순서가 같아 보였다. “503 → 정상”이면 어느 쪽이든 PG가 받는 GET은 2번이다. 다른 것은 **회로가 세는 표본**이다.

| 순서 (바깥 → 안) | PG가 받은 GET | 회로가 센 것 |
| --- | --- | --- |
| retry → 회로 → GET | 2 | 실패 1, 성공 1 (GET마다 한 줄) |
| 회로 → retry → GET | 2 | 성공 1 (묶음의 최종 결과만) |

모든 GET이 503이고 최대 2회, 창·최소 4, 50%라면 다음과 같다.
- retry가 바깥: reconcile 2번(GET 4)에 OPEN
- 회로가 바깥: reconcile 4번(GET 8)에 OPEN

회로가 바깥이면 장애를 늦게 알아채고, retry가 매번 살려 주면 불안정한 PG를 끝내 알아채지 못한다. 그래서 **GET 하나 = 표본 하나**가 되도록 retry를 바깥에 두었다.

**OPEN이면 retry가 당연히 멈출까?** 기본 설정에서는 아니다. 회로가 막을 때 던지는 `CallNotPermittedException`도 retry에게는 그냥 예외라서, 쉬었다가 또 시도한다. PG GET은 0이지만 고객은 헛기다린다. 그래서 **회로가 막은 호출은 retry에서 제외**하도록 설정했다.

**fallback은 어디에?** 안쪽에서 실패를 정상 값으로 바꿔 버리면 retry와 회로가 실패를 못 본다. 그래서 **실패를 판정하고 센 뒤, 맨 바깥에서** 고객에게 줄 응답을 만든다.

```text
fallback (저장 상태 + checked: false)
  └ retry (일시적 장애만, 최대 3회, 예산 안에서만)
      └ 회로 (GET마다 한 표본, 막은 호출은 retry 제외)
          └ PG GET
```

**2회차의 문제를 어떻게 풀까.** RestClient가 503에 예외를 던지고(①), adapter가 그 예외를 잡아 UNKNOWN 값으로 바꾸고(②), 그 바깥의 retry·회로는 바뀐 값만 본다(③). 방법은 두 가지였다.

- **A안**: UNKNOWN에 **이유 라벨**(일시적 장애 / 예상 밖 응답 / 회로 차단)을 붙이고, retry(`retryOnResult`)와 회로(`recordResult`)가 같은 라벨을 보게 한다. adapter의 반환 모양을 유지하고, 실패 이유도 남는다.
- **B안**: 예외가 살아 있는 adapter 안쪽에서 retry·회로를 돌리고 마지막에 값으로 바꾼다. 예외 종류를 세밀하게 다룰 수 있지만 adapter를 둘로 나눠야 한다.

A안을 골랐다.

**어노테이션 대신 직접 감싼 이유.** Spring의 `@Retry`·`@CircuitBreaker`도 기본 순서는 retry → 회로다. 하지만 순서가 aspect 설정에 숨고, 같은 객체 안에서 호출하면 프록시를 거치지 않는 함정이 있다. 순서를 코드에서 바로 읽을 수 있게 `ResilientPaymentProvider`에서 직접 감쌌다. [Resilience4j 기본 순서](https://resilience4j.readme.io/docs/getting-started-3#aspect-order).

### 7회차 이어서 — 정한 순서를 실제 장애로 의심해 보기

위에서는 순서를 표로 계산해 정했다. 여기서는 그 순서와 공유 회로를 세울 때 깔고 있던 가정이 깨지는 장면을 실제로 만들어 본다. 여섯 실험 모두 실제 HTTP 가짜 PG와 `TestPgPaymentAdapter`를 쓰고, 요청은 하나씩 차례로 보낸다. 따로 적지 않으면 설정은 학습값(최대 3회, 창 4, 최소 4, 실패율 50%, OPEN 10초)이고, OPEN 대기가 지나지 않도록 테스트 시계를 멈춘 채 실행했다.

#### ① 거래 하나의 실패가 다른 조회를 막을까

**의심한 가정.** 회로 하나를 두 조회 경로가 공유하는 근거는 "조회가 실패하면 PG 조회 전체에 장애가 있다"였다.

**장면.** PG는 다른 조회에 정상 응답하고, 첫 거래만 조회할 때마다 503이다. 뒤로 정상 거래 30건이 차례로 조회한다. 지금 순서(retry가 바깥)와 학습값 그대로다.

**확인한 것.** 고장 난 거래 하나가 GET 3번을 실패하며 창 네 칸 중 세 칸을 채웠고, 다음 정상 조회 하나에서 75%로 OPEN이 됐다. 나머지 정상 거래 29건은 PG에 묻지 않고 확인 불가를 받았다. 회로는 "PG 조회 전체의 장애"와 "거래 하나의 조회 실패"를 구분하지 못했다. retry를 바깥에 둬서 얻은 "GET 하나 = 표본 하나"가 여기서는 거래 하나의 실패를 세 배로 부풀렸다.

테스트: `PaymentLookupWindowSizeExperimentTest`의 창 4 장면(③의 장면 A와 같은 실행).

#### ② 감싸는 순서를 바꾸면 실제로 달라질까

**질문.** ①을 보고 처음에는 "회로가 바깥이어도 고장 난 거래는 GET 3번을 다 실패하니 같지 않나?"라고 생각했다. PG 입장에서는 같지만, 회로가 바깥이면 retry 묶음 전체를 호출 한 번으로 보고 최종 결과 하나만 기록한다. 위 표의 계산이 실제로도 그런지, 같은 장애에서 순서만 바꿔 돌렸다.

**장면.** 고객 넷이 각자의 거래를 차례로 확인한다. 고객마다 첫 GET은 503, 다시 물으면 정상이라, PG가 받는 GET은 503과 정상이 번갈아 온다(실패율 50%). retry가 바깥인 쪽은 실제 `ResilientPaymentProvider`, 회로가 바깥인 쪽은 같은 판정(일시적 실패, 남은 예산)·설정으로 테스트 안에서만 반대로 감쌌다. 처음에는 회로가 바깥인 쪽에 남은 예산 확인을 빠뜨렸다. 바로 오는 503이라 예산이 모자랄 일은 없었지만, 조건을 맞춘 뒤 다시 돌려 같은 결과를 확인했다.

**예측.** 돌리기 전에 손으로 창을 따라가 적은 값이다.

| 순서 | 회로 | 확인 성공 | 막힘 | PG가 받은 GET |
| --- | --- | --- | --- | --- |
| retry가 바깥 | OPEN | 2 | 2 | 4 |
| 회로가 바깥 | CLOSED | 4 | 0 | 8 |

**결과.** 예측과 같았다.

```text
retry가 바깥 (현재)
고객 A: GET 503 → GET 정상   창: 실패 · 성공                → 확인, CLOSED
고객 B: GET 503 → GET 정상   창: 실패 · 성공 · 실패 · 성공  → 확인, 50% → OPEN
고객 C: GET 0               차단                           → 확인 불가
고객 D: GET 0               차단                           → 확인 불가
회로 표본: 실패 2 · 성공 2, PG가 받은 GET 4

회로가 바깥
고객 A~D: 각자 GET 503 → GET 정상, 묶음 결과 성공 하나씩
창: 성공 · 성공 · 성공 · 성공 → 0%, CLOSED
회로 표본: 실패 0 · 성공 4, PG가 받은 GET 8
```

**해석.** 같은 장애인데 회로가 본 결과가 달랐다. 회로가 바깥이면 retry가 실패를 매번 가려 줘서, PG가 GET 절반을 실패하는 동안에도 실패 표본이 0이었다. 고객 넷은 모두 확인에 성공했지만, 그 대가로 PG는 GET을 두 배 받았고 고객마다 100ms를 더 기다렸다. retry가 바깥이면 실패가 그대로 보여 B의 두 번째 GET에서 OPEN이 됐고, C·D는 PG에 묻지 않고 확인 불가를 받았다.

①과 나란히 놓으면 **GET 하나하나를 센다**는 같은 성질의 양면이다.

| 장면 | retry가 바깥 (현재) | 회로가 바깥 |
| --- | --- | --- |
| 거래 하나만 실패 (①) | 거래 하나 때문에 정상 응답하는 PG 조회까지 막음 | 실패 1개로만 세서 막지 않음 |
| PG 조회 전체가 절반씩 실패 (②) | 실패를 그대로 보고 차단해 PG 부하를 줄임 | 실패를 못 보고 GET을 두 배로 보냄 |

①의 "회로가 바깥" 칸은 처음에 창 계산으로만 적었다. 같은 테스트에 첫 거래만 retry 끝까지 503이고 뒤 정상 거래 3건인 장면을 두 순서로 추가해 돌렸다. retry가 바깥이면 실패 3·성공 1로 OPEN이 되어 정상 거래 2건이 막혔고(GET 4), 회로가 바깥이면 실패 1·성공 3으로 CLOSED가 유지되어 정상 거래 3건을 모두 확인했다(GET 6). 계산과 같았다.

PG 조회 전체가 불안정한 경우를 더 놓치고 싶지 않아서 순서는 retry가 바깥으로 유지했다. 그러면 ①의 단점은 순서가 아닌 다른 손잡이로 줄여야 한다. retry 횟수는 ④, 창 크기는 ③에서 확인했다.

테스트: `PaymentLookupWrapOrderExperimentTest`.

#### ③ 창을 키우면 거래 하나의 실패에 덜 흔들릴까

**질문.** 창과 최소 표본을 함께 4에서 20으로 늘리면, 판단을 시작할 때 ①의 실패 3개는 표본의 15%에 그친다. 대신 PG 조회 전체가 실패할 때도 결과 20개가 쌓여야 판단할 것이다. 먼저 두 설정을 함께 바꿔 비교하고, 이후 최소 표본은 4로 두고 창만 20으로 넓힌 경우를 두 장애에 추가했다.

**예측과 결과.** 돌리기 전에 손으로 계산한 예측과 결과가 모두 같았다.

장면 A — 거래 하나만 계속 실패, 뒤에 정상 거래 30건

| 창 | 최소 표본 | 회로 | 정상 거래 확인 | 정상인데 막힘 | 마지막 창의 실패 표본 |
| --- | --- | --- | --- | --- | --- |
| 4 | 4 | OPEN | 1 | 29 | 3 |
| 20 | 20 | CLOSED | 30 | 0 | 0 |
| 20 | 4 | OPEN | 1 | 29 | 3 |

창 4는 ①과 같이 정상 조회 하나에서 OPEN이 되고, OPEN 10초가 지나지 않는 동안 나머지 29건을 모두 막았다. 테스트 시계를 멈춰 30건이 모두 10초 안에 온 것으로 둔 숫자이며, 실제로는 10초 뒤 HALF_OPEN 시험으로 다시 닫힐 수 있다. 창 20은 표본 20개가 모일 때 실패가 3개(15%)였고, 이후 성공 표본이 실패를 밀어내 마지막 창의 실패는 0이었다.

장면 B — PG 조회 전체가 계속 503

| 창 | 최소 표본 | OPEN이 된 고객 | OPEN까지 PG가 받은 GET | OPEN까지 걸린 시간 (1회 실행) |
| --- | --- | --- | --- | --- |
| 4 | 4 | 2번째 | 4 | 약 0.4초 |
| 20 | 20 | 7번째 | 20 | 약 2.2초 |
| 20 | 4 | 2번째 | 4 | 약 0.4초 |

```text
창 4·최소 4   : 고객 1 GET 3 실패 → 고객 2 첫 GET 실패, 표본 4·100% → OPEN
창 20·최소 20 : 고객 1~6 각자 GET 3 실패(표본 18) → 고객 7 두 번째 GET, 표본 20·100% → OPEN
창 20·최소 4  : 고객 1 GET 3 실패 → 고객 2 첫 GET 실패, 표본 4·100% → OPEN
```

OPEN 뒤 다음 고객은 세 조건 모두 GET 없이 바로 확인 불가를 받았다. 시간은 한 번 실행한 값이며, 대부분 고객마다의 retry 대기(100ms + 200ms)다.

**해석.** 창 20·최소 표본 20은 거래 하나의 실패에 정상 조회 30건을 하나도 막지 않았다. 대신 PG 조회 전체가 실패하는 동안 실패를 겪은 고객은 2명에서 7명으로, PG에 보낸 GET은 4번에서 20번으로 늘었다. 판단을 늦춰 정상 조회를 덜 막는 대신 전체 장애의 차단도 늦어진 결과였다.

창 20·최소 표본 4로 같은 두 장면을 돌리니 창 4·최소 표본 4와 같았다. 거래 하나만 실패하면 첫 정상 조회에서 표본 4개·실패율 75%로 열려 정상 거래 29건이 막혔고, 계속 장애이면 GET 4번의 실패·실패율 100%로 열렸다. 이번 장면에서 정상 조회를 막지 않은 효과는 창을 넓힌 것만이 아니라 최소 표본을 함께 늘린 데서 나왔다.

**이 실험으로 말할 수 없는 것.** 요청을 하나씩 보냈고, 실제 서비스에서는 고객 7명이 차례로 오는 데 걸리는 시간이 트래픽에 달려 있다. 트래픽이 많으면 최소 표본 20도 금방 모이고, 적으면 오래 걸린다. 회로가 열리기 전에 정상 조회가 이어지면 거래 하나의 실패가 창에서 밀려날 수 있지만, 이번 창 4 조건에서는 그 전에 회로가 열렸다. 어느 창과 최소 표본이 맞는지는 실제 조회 수와 함께 봐야 하며, 이번에는 고르지 않았다. 이 비교에서는 시간 기반 창(TIME_BASED)을 다루지 않았다.

테스트: `PaymentLookupWindowSizeExperimentTest`.

#### ④ retry 횟수를 바꾸면 무엇을 얻고 잃을까

**질문.** retry가 도움이 되는지는 다시 물었을 때 회복되느냐에 달려 있고, 회복 시점은 미리 알 수 없다. 그래서 "최대 3회가 맞다"는 증명할 수 없다. 대신 장애 모양을 세 가지로 가정하고, 순서·창 설정은 그대로 둔 채 최대 횟수만 1과 3으로 바꿨다.

**예측과 결과.** 돌리기 전에 손으로 계산한 예측과 결과가 모두 같았다.

| 가정한 장애 모양 | retry 최대 1회 | retry 최대 3회 |
| --- | --- | --- |
| 가끔 끊김: 고객 4명 중 첫 고객의 첫 GET만 503 | 확인 3 · 확인 불가 1, GET 4, CLOSED | 확인 4, GET 5, CLOSED |
| 계속 장애: 모든 GET이 503, 고객 6명 | 4번째 고객에서 OPEN, GET 4, 막힘 2 | 2번째 고객에서 OPEN, GET 4, 막힘 4 |
| 거래 하나만 실패: 첫 거래만 503, 뒤 정상 3건 | 정상 3건 확인, 막힘 0, CLOSED | 정상 1건 확인, 막힘 2, OPEN |

**해석.** retry를 늘리면 가끔 끊김에서는 GET 1번으로 고객 한 명을 살렸고, 거래 하나만 실패할 때는 정상 거래 2건을 막았다. 계속 장애에서는 PG가 받은 GET이 4번으로 같았다. 창 4·최소 4라서 어느 쪽이든 GET 4번째에 열렸고, retry 횟수는 그 GET을 몇 명의 고객이 나눠 쓰느냐만 바꿨다. 어느 장애 모양이 흔한지는 실제 장애 기록이 있어야 알 수 있어, 설정은 3회로 그대로 뒀다.

테스트: `PaymentLookupRetryCountExperimentTest`.

#### ⑤ 실패율 기준과 창 방식을 바꾸면

**질문.** 창 크기 말고도 회로에는 실패율 기준과 창 방식이 있다. 실패율 기준을 50%에서 80%로 높이면 거래 하나가 창 네 칸 중 세 칸(75%)을 채워도 열리지 않는다. 창을 시간(최근 10초)으로 세면 오래된 실패가 저절로 빠진다. 시간 창을 보려고 "새벽" 장면을 더했다. 거래 하나가 실패하고 20분 뒤 정상 거래 셋이 확인한다.

**장면.** 지금(최근 4개·50%), 실패율 80%(최근 4개·80%), 시간 창(최근 10초·최소 4·50%) 세 설정을 네 장면에서 비교했다. `ResilientPaymentProvider`는 개수 기준 창으로 고정돼 있어, 세 설정 모두 테스트 안에서 같은 retry 조건(일시적 실패, 남은 예산)·순서로 감싼 같은 조회 장치로 돌렸다. 장면마다 가짜 PG·회로·테스트 시계를 새로 만들었다. "지금" 칸의 결과는 실제 코드로 돌린 ①·②의 결과와 같아, 테스트 안의 장치가 실제 코드와 같게 동작한다는 확인도 된다.

**예측과 결과.** 12칸 모두 예측과 같았다.

| 장면 | 지금 | 실패율 80% | 시간 창 |
| --- | --- | --- | --- |
| 거래 하나만 실패, 뒤 정상 3건 | 정상 2건 막힘, OPEN | 막힘 0, CLOSED | 정상 2건 막힘, OPEN |
| 조회 전체가 절반씩 실패, 고객 4명 | 고객 2명 막힘, OPEN | 막힘 0, CLOSED, PG 조회 8 | 고객 2명 막힘, OPEN |
| 계속 장애, 고객 6명 | 2번째 고객에서 OPEN | 같음 | 같음 |
| 새벽: 거래 하나 실패 → 20분 뒤 정상 3건 | 정상 2건 막힘, OPEN | 막힘 0, CLOSED | 막힘 0, CLOSED |

**해석.** 실패율 80%는 거래 하나의 실패와 새벽 장면에 강해졌지만, 절반씩 실패하는 PG를 알아채지 못하고 조회를 두 배 보냈다. ②에서 회로를 바깥에 뒀을 때 잃은 것과 같다. 시간 창은 새벽 장면만 고쳤고 나머지는 지금과 같았다.

**이 실험으로 말할 수 없는 것.**
- 시간 창 비교는 두 가지가 함께 바뀌었다. 요청이 짧은 시간에 이어져 10초 창에 그사이 요청이 모두 들어가므로, 창 방식과 함께 창에 들어가는 표본 수도 달라졌다.
- 시간 창이 불리한 장면은 넣지 않았다. 요청이 드물어 10초 안에 표본 4개가 모이지 않는 경우, 실패가 10초보다 띄엄띄엄 이어지는 경우다. 이번 장면에서 잃은 것이 보이지 않았다고 대가가 작다고 할 수는 없다.
- 장애는 모두 바로 오는 503이다. 느린 실패에서 retry 예산·시간이 끼어드는 효과는 보지 않았다.

테스트: `PaymentLookupCircuitSettingsExperimentTest`.

#### ⑥ timeout을 바꾸면

**질문.** timeout은 "얼마나 늦으면 실패로 볼까"의 선이다. 이 선 하나가 retry 횟수(예산 판단에 쓰는 한 번 조회의 추정 시간), 회로가 열리는 시점, 연결을 붙잡는 시간을 함께 움직일 것 같았다.

**장면.** 실제 adapter와 `ResilientPaymentProvider`에 값만 바꿔 넣었다. retry 예산 판단의 추정 시간도 실제 설정처럼 "연결 대기 × 2 + 조회 응답 대기"로 함께 맞췄다. A는 조회 응답 대기 300·500·800ms를 PG 응답 400ms(조금 느린 정상)·2초(많이 느림)에서, 고객 6명이 차례로 확인했다. B는 연결 빌리기 대기 300·500ms를 9회차 장면(PG 400ms, 동시 조회 20개)에서 비교했다. 세 번 돌려 같은 결과였고, 예측과 같았다.

| PG 응답 | 조회 응답 대기 300ms | 500ms (현재) | 800ms |
| --- | --- | --- | --- |
| 조금 느린 정상 400ms | 확인 0, 2번째 고객에서 OPEN. 첫 고객 GET 3번·약 1.2초 | 6명 모두 확인 | 6명 모두 확인 |
| 많이 느림 2초 | 2번째 고객에서 OPEN. 첫 고객 GET 3번·약 1.2초 | 2번째 고객에서 OPEN. 고객 1·2가 GET 2번·약 1.1초씩 | 4번째 고객에서 OPEN. 고객 1~4가 GET 1번·약 0.8초씩 |

| 연결 빌리기 대기 | 확인 성공 (20개 중) | 회로 |
| --- | --- | --- |
| 300ms (현재) | 5 | OPEN |
| 500ms | 10 | OPEN |

**해석.**
- 조회 응답 대기를 줄이면 PG가 정상이어도 조금 느린 응답을 실패로 세서 회로가 열렸다.
- 늘리면 예산 판단의 추정 시간이 길어져 고객당 retry가 줄었다(GET 2번 → 1번). 대신 회로가 열리기 전에 더 많은 고객이 기다렸다. PG가 받은 조회는 어느 쪽이든 4번이었다.
- 연결 빌리기 대기를 늘리면 400ms에 풀린 연결로 5개를 더 확인했지만, 나머지가 500ms에 실패해 회로는 그래도 열렸다.

**이 실험으로 말할 수 없는 것.** 어느 값이 맞는지는 PG의 실제 응답 시간 분포를 봐야 한다. 이 실험은 선을 당기면 무엇이 실패가 되고, 밀면 무엇을 붙잡게 되는지까지 보여 준다.

테스트: `PaymentLookupTimeoutExperimentTest`.

## D. 정책

### 8회차 — 내 정책을 한 장으로

**처음 답과 고친 것**

| 항목 | 처음 답 | 고친 것 |
| --- | --- | --- |
| 재시도 대상 | UNKNOWN·timeout·네트워크 오류는 재시도, PENDING·SUCCESS·FAILED는 안 함 | UNKNOWN은 “확인 못 했다”는 우리 라벨이고 timeout은 그 **이유 중 하나**다. “UNKNOWN이면 재시도”가 아니라 “**이유가 일시적인** UNKNOWN만 재시도”다 |
| 횟수와 시간 | 예산 안에 들어가는 만큼 횟수를 정한다. 예산이 모자라면 timeout | 예산에 들어간다는 이유만으로 횟수를 늘리지 않는다. 추가 회복과 비용을 비교한다. 예산이 모자라면 timeout이 아니라 **다음 시도를 시작하지 않고** fallback이다 |
| fallback | PENDING이면 “진행 중”, UNKNOWN이면 “시간이 걸릴 수 있다” | **PENDING은 fallback이 아니라 정상 결과**다. fallback은 대답을 못 들었을 때뿐이다. 앞은 “물어봤더니 처리 중”, 뒤는 “물어보지 못했다” |
| 회로가 실패로 셀 것 | FAILED, timeout | **FAILED는 빼야 한다.** 정상 FAILED는 PG가 정상적으로 대답한 것이다. 한도 초과 고객이 몰리면 정상 동작하는 PG에 회로가 열린다 |
| 회로 숫자 | 실패율이 절반을 넘으면 닫는다? | 넘으면 닫는 게 아니라 **OPEN(차단)**이다. 창·최소 수가 작으면 빨리 판단하지만 우연에 흔들리고, 크면 안정적이지만 늦게 알아챈다 |
| 시험 | OPEN 동안 계속 요청해서 확인하면? | OPEN은 요청을 안 보내는 상태다. 그동안 계속 확인하면 OPEN의 의미가 없다. 고를 수 있는 것은 OPEN 유지 시간과 HALF_OPEN 시험 수다 |
| 감싸는 순서 | 회로가 retry보다 바깥 | **반대.** 바깥부터 fallback → retry → 회로 → GET. 회로가 바깥일 때의 장점(OPEN이면 retry까지 안 감)은 회로 차단을 retry에서 제외하는 설정으로 얻는다 |

**정한 정책**

| 항목 | 정한 것 | 이유 |
| --- | --- | --- |
| 판단 방법 | UNKNOWN에 이유 라벨. retry와 회로가 같은 라벨을 본다 | 반환 모양을 유지하고, 실패 이유도 남는다 |
| 재시도 대상 | 일시적 장애(timeout, 5xx, 연결 실패)만 | 대답을 못 들었고 곧 회복될 수 있는 것만 다시 물을 가치가 있다 |
| 횟수·시간 | 최대 3회, backoff 100·200ms, 조회 응답 timeout 500ms, 예산 2초 | 학습용 임시값. 선정 근거는 아직 없다 |
| fallback | retry 소진·예산 부족·회로 OPEN일 때. 저장 상태 + `checked: false`, DB 변경 없음 | 물어보지 못한 것은 결제 결과가 아니다 |
| 회로 실패 | 일시적 장애만. SUCCESS·FAILED·PENDING·0건·형식 오류는 성공으로 셈 | 정상 FAILED는 PG가 정상 동작한다는 증거다 |
| 회로 숫자 | 창 4, 최소 4, 실패율 50% 이상, OPEN 10초, HALF_OPEN 2회 | 상태 변화를 관찰하기 쉬운 학습값 |
| 순서 | fallback → retry → 회로 → GET. 회로 차단은 retry에서 제외 | 실패가 숨지 않고, GET마다 세고, OPEN일 때 헛기다리지 않는다 |
| 범위 | 조회 GET 두 경로(거래 키·주문 번호)에 회로 하나. 생성 POST는 감싸지 않음 | 두 조회는 같은 장애를 공유한다. POST는 다시 보내면 거래가 하나 더 생긴다 |

**회로를 어디까지 공유할까.** 주문마다 회로를 만들면 같은 PG의 장애 표본이 흩어진다. 생성 POST와 조회 GET은 실패 특성이 다를 수 있어 따로 둘 후보다. 결제 생성 회로가 있으면 “PG가 지금 결제를 못 받을 게 뻔하면 재고를 잡기 전에 거절”할 수도 있다. 이번에는 만들지 않았다.

**서킷 브레이커는 언제 쓰나.** 외부냐 내부냐보다, **네트워크 너머 다른 프로그램을 부르고, 그게 느려지거나 죽을 때 내 스레드가 묶이고, 대신 줄 응답이 의미 있을 때**다. 결제는 지어낼 값이 없어서 fallback이 “확인 불가, 저장 상태 그대로”다.

## E. 조회가 몰릴 때 — 연결 풀

A~D와 7회차 이어서는 요청을 하나씩 차례로 보냈다. 여기서는 조회가 **동시에 몰릴 때**를 본다. 의심한 가정은 "일시적 실패가 쌓이면 PG에 장애가 있다"이다. 코드에서 본 단서는 두 가지다. HTTP 연결을 빌리지 못한 실패(`ConnectionRequestTimeoutException`)도 `ResourceAccessException`으로 올라와 `TEMPORARY_FAILURE`로 분류되고, 생성용·조회용 RestClient가 HttpClient 하나(같은 주소당 연결 5개)를 함께 쓴다.

공통 조건: PG는 모든 응답을 400ms 뒤 정상으로 돌려준다. 연결 빌리기 대기는 300ms(`connect-timeout`과 같은 값), 조회 응답 대기는 500ms다. 400ms는 연결 대기보다 길고 응답 대기보다 짧아서, PG는 정상인데 우리만 연결을 못 빌리는 장면이 된다. 앞의 5개가 PG에 도착한 것을 확인한 뒤 나머지를 보낸다. 회로의 창은 최근 4개만 기억하므로, 시도 수는 회로 이벤트를 받아 따로 셌다.

### 9회차 — 우리 연결 부족을 PG 장애로 셀까

**처음 생각.** 10개를 보내면 "10개 중 5개 실패라 50%"로 열릴 것 같았다. 실제로는 회로가 결과를 **도착하는 순서대로** 넣는다. 연결을 못 빌린 실패(300ms)가 PG의 정상 응답(400ms)보다 먼저 기록되어, 창의 처음 네 칸이 모두 실패가 된다.

| 시각 | 1~5번 | 6~10번 | 회로 |
| --- | --- | --- | --- |
| 0ms | 연결을 잡고 PG로 감 | 연결을 기다림 | CLOSED |
| 300ms | PG 응답 대기 | 연결을 못 빌려 실패 | 실패 4개째에 OPEN |
| 400ms | 정상 응답 → 확인 | retry가 회로에서 막힘 → 확인 불가 | OPEN |

**결과.** 예측과 같았고, 세 번 모두 같았다.

| 동시 조회 | 확인 성공 | 확인 불가 (회로가 막음) | 회로가 센 시도 | PG가 받은 조회 | PG에 닿지 못한 시도 | 회로 |
| --- | --- | --- | --- | --- | --- | --- |
| 5 | 5 | 0 | 5 | 5 | 0 | CLOSED |
| 10 | 5 | 5 | 10 | 5 | 5 | OPEN |
| 20 | 5 | 15 | 20 | 5 | 15 | OPEN |

**확인한 것.** 회로가 센 실패 수와 "회로가 센 시도 − PG가 받은 조회"가 같았다. PG는 한 번도 실패하지 않았는데, 회로는 우리 연결 부족을 PG 장애로 세고 열렸다. retry는 아무도 살리지 못했다. 이미 출발한 1~5번은 OPEN 뒤에도 정상 응답을 받았다. 회로는 앞으로 나갈 요청만 막고, 이미 나간 요청을 취소하지 않는다.

테스트: `PaymentLookupConnectionPoolExperimentTest`.

### 10회차 — 연결을 못 빌린 결과를 실패로 세지 않으면

**처음 생각.** 빼면 안 될 것 같았다. PG가 느려져서 연결이 오래 묶이면 그것도 연결 부족으로 나타나는데, 빼면 느린 PG를 못 알아챌 것 같았다.

**다시 따져 본 것.** PG가 느리면 연결을 잡고 PG까지 간 요청이 응답 timeout(500ms)으로 끝난다. 이건 PG까지 갔는데 답이 늦었다는 뜻이라 PG 상태를 직접 보여 준다. 연결을 못 빌린 실패는 PG까지 가지도 못해 PG에 대해 아무것도 모른다. 그렇다면 응답 timeout만으로 느린 PG를 알아챌 수 있다.

**장면.** 실제 adapter는 두 실패를 같은 라벨로 돌려줘 밖에서 구분할 수 없다. 그래서 테스트 안에서만 adapter와 같은 HTTP 설정으로 조회하고, 연결 빌리기 timeout만 따로 표시했다. retry 조건·순서·회로 설정은 학습값과 같다. 동시 조회 20개, 세 번 모두 같은 결과였다.

**후보의 정확한 의미.** 연결 부족에 `recordResult`가 false를 반환하므로 회로의 성공 표본에 들어간다. 실패·성공 어느 쪽에도 넣지 않고 표본에서 완전히 제외한 것은 아니다. retry는 연결 부족도 계속 대상으로 삼는다. 아래 결과로 표본에서 완전히 제외하는 정책의 효과까지 검증했다고 볼 수는 없다.

| PG 응답 | 정책 | 확인 성공 | 확인 불가 | 회로 | OPEN 시점 | PG가 받은 조회 |
| --- | --- | --- | --- | --- | --- | --- |
| 정상 400ms | 연결 부족도 셈 (현재) | 5 | 15 (회로가 막음) | OPEN | 약 0.39초 | 5 |
| 정상 400ms | 연결 부족은 성공 표본으로 셈 (후보) | 10 | 10 (retry 소진) | CLOSED | — | 10 |
| 느림 2초 | 연결 부족도 셈 (현재) | 0 | 20 | OPEN | 약 0.31초 | 5 |
| 느림 2초 | 연결 부족은 성공 표본으로 셈 (후보) | 0 | 20 | OPEN | 약 0.50초 | 10 |

**확인한 것.**
- PG가 정상이면 후보는 회로를 열지 않았다. 400ms에 연결이 돌아오자 retry 중 5개가 연결을 잡아 확인이 늘었다. 나머지 10개는 다시 연결을 못 빌렸고, 세 번째 시도는 남은 예산이 모자라 하지 않았다.
- PG가 느리면 후보도 응답 timeout만으로 OPEN이 됐다. 대가로 OPEN이 약 0.2초 늦었고, 그사이 retry가 느린 PG에 조회를 5번 더 보냈다.
- 후보에서도 PG가 정상인데 10명은 확인하지 못했다. 착각은 사라졌지만 연결 5개에 20명이 몰리는 용량 문제는 남았다.

실제 정책은 바꾸지 않았다.

테스트: `PaymentLookupPoolFailureCountingExperimentTest`.

### 11회차 — 조회가 몰리면 결제 생성 POST도 막힐까

**처음 생각.** 생성 POST에는 회로가 없으니 조회 회로가 열려도 POST는 나갈 것 같았다. 하지만 회로는 "보내도 되나"만 판단하고, 연결은 조회와 POST가 같은 풀에서 빌린다.

**장면.** 실제 주문 흐름(MySQL·가짜 PG)에서 조회 20개가 연결 5개를 모두 잡은 순간 다른 주문의 confirm을 실행했다. POST의 연결 빌리기 대기도 300ms다.

**결과.** 결과가 몇십 ms 차이로 갈렸다. 주문을 미리 만들어 confirm 시작 시점을 맞춘 뒤 11번 돌려 8번은 POST가 막혔고 3번은 연결을 잡았다.

| POST가 막힌 경우 (8번) | 결과 |
| --- | --- |
| PG가 받은 POST | 0 |
| confirm 응답 | UNKNOWN, `checked: false`, 약 0.35초 |
| 주문·예약 | PAYMENT_PENDING·RESERVED, 재고 94 |
| 지연을 걷고 reconcile | 조회 0건 → UNKNOWN·예약 그대로 |

POST가 연결을 잡은 3번은 POST가 줄에 늦게 서서, 300ms를 다 기다리기 전에 400ms에 조회 연결이 풀렸다. 정상 PENDING으로 끝났고 confirm은 약 0.75초였다.

**확인한 것.** PG가 정상이어도 조회가 몰리면 생성 POST가 PG에 닿지 못하고, 그 결제는 끝나지 않는 UNKNOWN이 됐다. 이 결과로 [ADR 0034](../adr/0034-close-only-proven-unsent-payments-and-keep-unresolved-pending.md)를 정했다. 이제 연결을 빌리지 못한 생성은 보내지 못한 것이 확실하므로 바로 실패로 닫고 재고를 돌려준다. 위 표는 그 정책 전의 결과다. 당시에는 연결을 못 빌린 POST와 응답만 잃은 POST를 같은 UNKNOWN으로 기록해, 조회 0건이어도 실패 처리·예약 반환을 하지 않았다. 카오스 테스트에서 PG를 내렸을 때 찾은 한계와 결과가 같고, 원인만 다르다. POST가 연결을 빌릴 수 있는지는 연결이 풀릴 때까지의 대기가 한도 300ms 안에 들어오느냐에 따라 갈렸다.

POST가 연결을 잡은 경우는 현재 정책에서 회로가 300ms에 열려 조회 retry를 막았기 때문일 수 있다. 10회차의 후보 정책이라면 조회 retry가 400ms에 연결을 두고 POST와 다툴 것이다. 이 조합은 실험하지 않았다.

테스트: `PaymentCreateConnectionPoolExperimentTest`. 결과가 갈리므로 결과를 고정하지 않고, 각 결과에서 지켜야 할 사실만 확인한다.

### 비고 — bulkhead로 동시 조회 수를 제한하면

5회차에서 "CLOSED에서 동시 GET 수를 제한하는 것은 bulkhead의 일"이라고 정리했는데, 9~11회차가 그 빈칸을 보여 줬다. bulkhead는 한 기능이 자원을 다 써도 다른 기능이 멈추지 않게 자원을 나눠 두는 패턴이다. 연결 풀을 용도별로 나누거나, 한 호출이 동시에 쓸 수 있는 수를 제한하는 방식이 있다.

효과만 테스트 안에서 확인했다. 프로젝트에 Resilience4j Bulkhead 모듈이 없어서 세마포어로 같은 원리를 만들었다. 조회는 동시에 3개까지, 넘치면 기다리지 않고 바로 확인 불가이며, 이 거절은 retry·회로보다 바깥이라 회로와 연결 풀을 거치지 않는다. 11회차와 같은 장면에서 세 번 모두 같은 결과였다.

| | bulkhead 없음 (11회차의 분류 변경 전 기록) | 조회 동시 3개 |
| --- | --- | --- |
| 조회 확인 성공 | 5 | 3 |
| 나머지 조회 | 15개가 300ms 기다린 뒤 실패 | 17개가 바로 확인 불가 |
| 회로 | OPEN | CLOSED, 실패 0 |
| 결제 생성 POST | 대부분 막혀 UNKNOWN | 남은 연결로 나가 PENDING, confirm 약 0.45초 |

조회 확인을 줄이는 대신 이 장면에서 결제 생성에 쓸 연결이 남았다. 생성용 연결을 항상 두 개 예약하는 장치는 아니며, 생성 요청도 함께 몰리는 경우는 확인하지 않았다. 현재 코드는 연결을 빌리지 못한 생성 POST를 NOT_SENT로 실패 처리한다. Resilience4j를 annotation으로 쓰면 기본 순서상 Bulkhead가 가장 안쪽이라, 넘쳐서 거절된 호출이 회로의 실패로 세질 수 있다. 어디에 두느냐가 회로의 판단에 영향을 준다.

구현하지 않았다. retry·회로·timeout 설정만으로는 막지 못하는 문제가 있고, 그건 자원을 나누는 일이라는 것을 확인한 데서 멈췄다.

테스트: `PaymentLookupBulkheadExperimentTest`.

### 비고 — 동시 실행 제한과 풀 분리는 같은 효과일까

**질문과 예측.** 앞의 실험은 공유 풀 앞에서 조회 실행을 3개로 제한했다. 같은 총 연결 한도 5개를 조회 3개·생성 2개로 나누면 POST는 보호되지만, 조회는 풀에서 기다리다 실패해 회로가 열릴 수 있다고 예상했다.

**방법.** `PaymentLookupPoolSeparationExperimentTest`에서 세 조건을 같은 HTTP 경계로 맞춰 다시 비교했다. 실제 `TestPgPaymentAdapter`와 `ResilientPaymentProvider`, 학습용 retry·회로 설정을 사용했다. PG 응답 400ms·연결 풀 대기 300ms, 조회 20건·생성 POST 1건이다. 먼저 각 조건의 조회 연결 5개 또는 3개가 PG에 도착한 것을 확인하고 나머지 조회와 POST를 시작했다. 회로 시계는 고정했다. 주문 DB 처리와 confirm 전체 시간은 측정하지 않았다.

| 항목 | 공유 풀 5개 | 공유 풀 5개·조회 실행 3개 제한 | 조회 풀 3개·생성 풀 2개 |
| --- | --- | --- | --- |
| 조회 확인 | 5 | 3 | 3 |
| PG가 받은 GET | 5 | 3 | 3 |
| 나머지 조회 | 15건 대기 후 확인 불가 | 17건 즉시 거절 | 17건 대기 후 확인 불가 |
| 조회 회로 | OPEN | CLOSED·실패 0 | OPEN |
| 생성 POST | PG 수신 0·NOT_SENT | PG 수신 1·PENDING | PG 수신 1·PENDING |
| 생성 HTTP 호출 시간 | 303~306ms | 403~404ms | 402~404ms |

**결과와 해석.** 세 조건을 세 번씩 실행해 같은 건수와 회로 상태를 확인했다. 풀 분리도 이번 조건에서 POST를 보호했지만, 조회의 연결 대기 실패를 막지는 않았다. 실행 제한은 넘친 조회를 회로 밖에서 바로 거절하고, 풀 분리는 조회용 연결을 기다리게 한다는 차이가 있었다. 두 방식의 조회 확인 건수는 3건으로 같았지만 대기와 회로 상태가 달랐다. 공유 풀의 POST는 시작 시점에 따라 결과가 달라질 수 있으며, 여기서 세 번 막힌 결과를 운영 확률로 해석하지 않는다.

**범위.** 풀 분리는 테스트 안에서만 두 adapter를 각각 조회용·생성용으로 사용했다. 기본 앱 구성은 계속 한 adapter의 공유 풀을 쓴다. 생성 요청도 동시에 몰리는 경우, 다른 연결 배분, PG 자체 장애는 이번 비교에서 확인하지 않았다. 로컬 측정 원본은 `measurements/pool-separation-run-1.txt`부터 `pool-separation-run-3.txt`에 보관하며 Git에는 올리지 않는다.

<a id="policy-selection"></a>

## 아직 확인하지 않은 것

- **설정값 선정.** 감싸는 순서, retry 최대 횟수, 창 크기, 실패율 기준, 창 방식, timeout은 7회차 이어서 ②~⑥에서 하나씩 바꿔 얻고 잃는 것을 비교했다. 값은 고르지 않았고 숫자는 여전히 임시값이다.
- **GET 한 번의 시간과 전체 시간 분리.** 측정은 retry 전체 시간이다. adapter의 GET 한 번 시간과 고객 reconcile 전체 시간(DB 포함)은 따로 재지 않았다.
- **엄격한 시간 상한.** 예산은 재시도 시작만 막는다. 진행 중인 GET을 끊어 전체 2초를 지키는 기능은 없다.
- **동시 부하.** 조회가 몰릴 때의 연결 풀·회로·생성 POST는 E에서 확인했다. jitter 효과, PG가 죽는 순간의 동시 요청, 배치와 고객이 HALF_OPEN 시험을 나눠 쓰는 장면은 확인하지 않았다.
- **느린 호출 비율.** PG가 400ms에 정상 응답하는 장면과 응답 timeout 비교는 이미 확인했다. 응답 timeout 안에 끝나는 느린 호출의 비율로 회로를 여는 설정은 적용·비교하지 않았다.
- **여러 서버.** 회로는 메모리에 있어서 서버마다 따로이고, 재시작하면 CLOSED로 새로 시작한다.
