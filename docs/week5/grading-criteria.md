# W5 테스트 PG 결제와 결과 복구 채점 기준

2026-10-18에 제공된 [과제 원문](assignment-original.md)을 이번 주 평가 기준으로, [학습 자료 원문](learning-original.md)을 개념 설명의 근거로 사용한다. 목표는 기존 포인트 결제를 로컬 테스트 PG로 교체하고, 외부 결과를 주문·재고에 한 번만 반영하는 것이다. 이 정리와 과제 원문이 다르게 해석되면 과제 원문을 우선한다.

공식 체크리스트는 **9개 항목**이다. 이전 주차의 통과 결과를 W5 완료로 이어받지 않는다. 기존 상품·주문·관리자 API, 조회·캐시, DB 정합성·소유권은 유지하되, 이번 과제에서 명시적으로 바꾼 결제·재고·재요청 계약은 새 기준을 적용한다. 이 파일은 평가 기준이며 현재 구현의 완료 판정이나 상세 설계 확정 문서가 아니다.

## 공식 체크리스트와 확인 증거

| 번호 | 원문의 체크 항목 | 충족 여부를 확인할 증거 |
| --- | --- | --- |
| 1 | 미확정 주문의 결제는 PG를 사용하고 포인트를 이중 차감하지 않는다. | 기존·신규 DRAFT의 confirm이 실제 PG 경계로 연결됨. 금액은 저장된 주문에서 결정하고 모든 PG 경로에서 포인트 변화 0. 기존 충전·잔액 API 유지 |
| 2 | 이전 POINT 주문의 결제·품목 사실과 기존 소유권을 보존한다. | 과거 POINT 주문의 수단·금액·결과·당시 품목 조회, 기존 재확정 오류, 다른 사용자 접근 거절과 관리자·고객 조회 회귀 |
| 3 | 생성 수락·처리 중·최종 성공·실패·결과 미확인을 구분한다. | PENDING·UNKNOWN·SUCCESS·FAILED의 의미, 주문과의 상태 전이, 대기 응답 HTTP 202와 조회 경로. 수락·timeout을 완료로 바꾸지 않는 테스트 |
| 4 | 시도·발송·예약이 DB에서 중복을 막고 PG HTTP 동안 잠금을 계속 잡지 않는다. | 주문당 한 시도·요청 일치·발송 권한의 DB 제약과 전이, 동시 confirm의 create 1회, 재시작 뒤 기록 보존, HTTP 구간의 TX·잠금 미보유 |
| 5 | 성공은 추가 차감 없이 확정하고 확정 실패만 예약을 한 번 반환한다. | 호출 전 재고 확보, 성공 시 소비, 확정 실패 시 반환. 중복·동시 적용과 DB rollback 뒤에도 주문·시도·예약이 함께 일치 |
| 6 | timeout·재시작·조회 0건에서 새 결제를 만들거나 예약을 임의 반환하지 않는다. | 거래 생성 후 응답 유실, 발송 기록 후 재시작, 조회 0건의 create 추가 0·예약 유지. HTTP client·프록시·회복 도구의 생성 재시도 차단 |
| 7 | 실제 adapter HTTP 계약과 callback의 권위 조회·식별·금액 검증을 확인했다. | 실제 adapter→로컬 HTTP 서버의 세 요청·응답 계약, 실제 callback controller 경유, 고정 제공자 계정·주문·거래·저장 금액 검증과 조작 알림만으로 성공 처리하지 않음 |
| 8 | 중복·순서 변경·내부 저장 실패와 timeout·회로·조회 복구를 검증했다. | callback-first·lookup-first·동시 적용, 늦은 응답의 상태 퇴행 방지, 외부 성공 후 내부 저장 실패 복구, 실제 timeout·호출 수·회로 전이·수동 reconcile |
| 9 | 관련 회귀·lint·ArchUnit을 실행하고 실험 자원을 정리했다. | 관련 기능 회귀, Checkstyle·ArchUnit의 실제 실행 건수·실패·skip·종료 결과, 유한한 기다림과 자신이 시작한 HTTP 서버·worker 등의 정리 |

각 항목은 **충족·부분 충족·미충족·확인 불가**로 평가하고 코드·테스트·실행 결과의 근거를 붙인다. 원문에 없는 숫자 배점·테스트 개수·성능 목표를 만들지 않는다. 공식 9항목과 별도로 설계 문서·PR·기술 글의 제출 여부를 확인한다.

## 이번 주 확정된 변경과 유지할 계약

| 대상 | W5에서 적용할 기준 |
| --- | --- |
| 기존·신규 미확정 DRAFT | 교체 후 결제를 시작하면 PG를 사용한다. 소유권·품목·양수 수량·저장 금액·삭제·재고 검사를 유지한다. |
| PG 결제 | 포인트를 전혀 차감하지 않는다. PG 장애를 포인트 결제로 우회하지 않는다. |
| 이전 POINT 확정 주문 | 재처리하지 않고 결제수단 POINT·금액·결과·당시 품목을 보존한다. 재확정 요청에는 기존 이미 확정된 상태 오류를 유지한다. |
| 포인트 충전·조회 | 기존 API와 본인 잔액·충전 규칙을 유지하고 주문 결제에서 분리한다. |
| 결제 시도 | 주문당 한 시도만 허용한다. 실패 후 새 시도·새 키에 의한 재결제도 이번 범위에 포함하지 않는다. |
| PG 동일 시도의 재요청 | 이미 종결했다면 저장된 결과를 반환하고 추가 효과를 만들지 않는다. POINT 주문의 재확정 오류와 구분한다. |
| 재고 설정 API | 예약을 제외한 **가용 수량을 최종 설정**한다. 관리자 변경도 같은 재고 행의 보호 규칙을 따르고 기존 예약을 지우지 않는다. |
| 상품 삭제 | 새 조회·새 주문에서 계속 제외한다. 삭제 뒤 새로 시작하는 DRAFT 확정과, 이미 예약을 마친 PAYMENT_PENDING의 결과 처리를 구분한다. |
| 예약 뒤 상품 삭제 | 저장된 품목·금액·예약으로 기존 PG 결과를 마무리한다. 물리 삭제가 참조·반환을 깨뜨리면 종결까지 실제 행 제거를 미룬다. 실패 반환으로 삭제 상품이 재노출되면 안 된다. |
| 기존 조회·캐시 | 기존 계약을 유지한다. 캐시 payload가 가용 재고를 담는다면 예약·반환과 기존 변경·복구 정책을 연결한다. |

환불·정산·사용자 취소·실제 카드 저장·실제 PG 계정·공개 배포는 이번 구현 범위가 아니다. 과거 계약을 유지한다는 이유로 새 PG 결제에 포인트를 계속 차감하거나, 이미 확정된 POINT 주문을 PG로 다시 결제하는 것은 잘못된 변경이다.

## 설계 문서에서 확인할 내용

기존 [전체 설계](../week2/commerce-erd-draft.md), [API 계약](../week2/commerce-api-contract.md), [정책 선택](../week2/commerce-policy-decisions.md), [W5 TDD 계획](../week2/commerce-tdd-plan.md#w5-pg-결제-tdd-계획)을 갱신할 때 다음을 확인한다. 문서 작성만으로 구현이 끝났다고 판단하지 않는다.

프로젝트에서 선택한 저장 구조·시간/회로 초기값과 남은 결정은 정책 문서를, 실제 구현·검증 상태는 [완료 체크리스트의 W5 구분](../week2/commerce-completion-checklist.md#w5-설계-선택과-구현-상태)을 따른다. 그 선택값을 과제 원문의 유일한 정답이나 추가 채점 조건으로 바꾸지 않는다.

- 기존 주문 유스케이스와 결제 경계·PG adapter의 책임, 내부 모델과 외부 JSON·네트워크 오류의 분리.
- 내부 orderId·paymentAttemptKey·providerOrderId·transactionKey의 역할과 DB 보존, 제공자 계정 범위와 생성·조회 매핑의 일관성.
- 주문·결제 시도·발송·예약의 상태와 허용 전이, PENDING과 UNKNOWN의 차이, 종결 결과의 중복·충돌 처리.
- 로컬 TX A, TX 밖 HTTP, 로컬 TX B의 시작·종료와 잠금 순서. 외부 효과가 내부 rollback으로 취소되지 않는다는 점.
- callback·수동 reconcile이 같은 결과 적용 경계를 사용하는 방법, 재시작·내부 저장 실패 뒤 복구 경로.
- timeout·조회 횟수·간격·총 대기 예산, circuit breaker의 실패 조건·최소 표본·대기·탐색 호출 수.
- 기존 POINT 기록·포인트 API·삭제·관리자 재고 설정·관련 캐시에 미치는 영향.
- 응답 유실·외부 성공 후 내부 저장 실패·중복 callback에 대해 AI와 검토한 반례, 선택 이유와 장기 미확인의 비용·한계.

## 로컬 PG와 commerce HTTP 계약

PG 앱이 시작 저장소에 이미 있다는 가정으로 평가하지 않는다. 작은 테스트 HTTP 서버 또는 fixture를 만들고 실제 adapter가 다음 계약대로 통신하는지 확인한다.

| PG 요청 | 필수 입력·응답 |
| --- | --- |
| `POST /api/v1/payments` | `orderId, cardType, cardNo, amount, callbackUrl` 입력. 수락은 HTTP 202와 `transactionKey, orderId, amount, status` 반환 |
| `GET /api/v1/payments/{transactionKey}` | HTTP 200과 같은 거래 필드 반환. 없는 transactionKey는 HTTP 404 |
| `GET /api/v1/payments?orderId={providerOrderId}` | HTTP 200과 같은 거래 객체의 배열 반환. 빈 배열 표현 가능 |
| 공통 헤더·타입 | 세 요청 모두 `X-USER-ID: 135135`. 외부 orderId는 6자 이상 문자열, amount는 원화 정수. 외부 상태는 PENDING·SUCCESS·FAILED |

생성과 조회에는 같은 providerOrderId·제공자 계정 범위를 사용한다. query는 URI builder로 인코딩하고 transactionKey 조회도 연결한다. 실제 메서드·경로·헤더·JSON 타입·금액·응답 매핑을 검증한다. 테스트 PG는 호출자 멱등 키를 받지 않고, 같은 orderId의 새 POST를 중복 제거해 준다고 가정하지 않는다.

카드는 원문의 TEST·합성 번호 같은 실습 값만 사용하고 **합성 카드 번호도 DB·로그에 남기지 않는다.** base URL·callback URL은 로컬 설정으로 고정하며 고객이 임의 외부 주소를 넣게 하지 않는다. 외부 고정 헤더가 내부 고객 식별을 대신하지 않는다.

| commerce 요청 | 필수 동작 |
| --- | --- |
| `POST /api/v1/orders/{orderId}/confirm` | 본인 DRAFT의 PG 시도 시작. paymentAttemptKey·합성 카드 입력을 받고 금액은 저장 주문에서 결정 |
| `GET /api/v1/orders/{orderId}` | 본인 주문·결제수단·시도 상태·최종 결과 조회. 새 결제 생성 없음 |
| `POST /api/v1/orders/{orderId}/payment/reconcile` | 본인의 미완료 시도에 연결된 기존 외부 거래 조회·결과 적용 |
| `POST /api/v1/payments/callback` | providerOrderId·transactionKey·status 알림을 받고 PG를 권위 조회한 뒤 공통 결과 적용 경계 사용 |

대기·미확인 confirm/reconcile은 **HTTP 202와 주문·시도 상태 및 조회 경로**를 반환한다. 같은 PG 시도의 완료 결과는 HTTP 200으로 조회·반환할 수 있다. 소유권·잘못된 입력·상충 시도는 기존 오류 계약에 맞춰 구분한다. 고객·관리자 조회 모두 대기·미확인·최종 결과를 구별한다.

### 효과 없는 확정 거절의 엄격한 조건

`REJECTED_NO_EFFECT`는 고정한 로컬 PG의 **생성 응답**에서 아래 조건을 모두 확인한 경우에만 인정한다.

1. HTTP 422.
2. code가 정확히 `TEST_PG_REJECTED_BEFORE_CREATE`.
3. transactionCreated가 JSON boolean `false`.
4. 응답 orderId·amount가 요청과 일치.
5. fixture가 거래 저장·비동기 처리 예약 전에 종료하고, 이후에도 해당 요청의 거래를 만들지 않는 계약을 실제로 지킴.

이때만 결제 FAILED·예약 한 번 반환으로 연결한다. 거래가 없으므로 transactionKey를 꾸며 저장하지 않는다. timeout, 본문 없는 422, 다른 code의 4xx·5xx, 잘못된 JSON·식별·금액, 일반 조회 404·빈 목록은 효과 0건의 증거가 아니다. 다른 확정 결과가 없는 시도는 UNKNOWN·예약 유지로 남기고 기존 거래를 조회한다.

## DB 경계·발송·재고의 불변 조건

| 단계 | 확인할 책임 |
| --- | --- |
| 로컬 TX A | 주문·상품·입력·재고 검사, 주문별 재고 확보, 시도·예약·결제 대기 상태를 함께 저장. 부족·삭제·잘못된 입력이면 전체 rollback하고 PG 호출 0회 |
| TX 밖 HTTP | 영속적으로 발송 권한을 얻은 실행 하나가 PG POST 호출. PG 생성·조회 동안 DB 트랜잭션·재고 잠금을 계속 보유하지 않음 |
| 로컬 TX B | 검증한 외부 관찰을 주문·시도·예약에 한 번 적용. 성공·반환 상태와 재고 변경이 함께 commit 또는 rollback |

주문당 한 시도와 시도 키의 요청 일치는 **DB 유일 제약·상태 전이**로 보호한다. 메모리 잠금·Set만으로 끝내지 않는다. 같은 키의 다른 주문·금액·요청은 충돌이고, 같은 주문에 새 키를 보내도 두 번째 시도·예약·PG 생성은 허용하지 않는다.

사전 검사 실패로 TX A가 전체 rollback되어 시도 자체가 저장되지 않은 DRAFT와, 이미 만들어진 PG 시도가 최종 실패한 주문은 구분한다. 주문당 한 시도라는 조건을 사전 검사 실패 후의 모든 재요청 금지로 확대하지 않는다.

발송 시작을 영속 기록한 뒤에는 create를 자동 재발송하지 않는다. HTTP client·프록시·회복 라이브러리의 숨은 재시도도 끈다. 발송 기록 직후 실제 HTTP 전에 멈췄다면 외부 거래 0건일 수 있지만, 재시작 뒤 조회 0건을 근거로 새 POST를 허용하지 않는다. **중복 방지와 모든 시도의 자동 완료는 서로 다른 보장**이며, 미완료가 오래 남을 수 있는 한계를 기록한다.

| 검증한 관찰 | 내부 결과의 의미 | 예약·재고 |
| --- | --- | --- |
| 생성 수락 PENDING | 처리 중, 주문 PAYMENT_PENDING | 유지 |
| timeout·응답 유실·조회 불가 | 결과 UNKNOWN, 주문 PAYMENT_PENDING | 유지 |
| SUCCESS | 결제 SUCCESS, 주문 CONFIRMED | 예약 소비, 추가 차감 없음 |
| FAILED 또는 효과 0건 확정 거절 | 결제 FAILED, 주문 PAYMENT_FAILED | 한 번 반환 |
| 조회 0건·복수 거래·식별/금액 불일치 | 미확인·충돌 보존, 새 발송 금지 | 임의 반환 없음 |

표는 상태의 의미를 나타낸다. enum·필드 이름은 같은 의미를 유지하는 범위에서 선택할 수 있다. 이미 종결한 상태는 늦은 PENDING 응답·timeout handler로 되돌리지 않고, 상충하는 최종 결과로 덮어쓰지 않는다.

재고 5개에서 2개를 예약했다면 가용 재고는 3개다. 다른 재고 변경이 없는 조건에서 성공 후에도 3개, 확정 실패 후에는 5개다. 중복 실패로 7개가 되거나 UNKNOWN만으로 5개로 복구되면 잘못된 처리다. 시간 경과만으로 예약을 반환하거나 새 결제를 허용하지 않는다.

## callback·조회·회복 도구

- callback 본문은 확인을 시작하는 알림이다. 본문의 SUCCESS만으로 확정하지 않고, 고정 PG adapter의 조회 결과에서 제공자 계정 범위·providerOrderId·transactionKey·저장 금액을 확인한다.
- 다른 주문·거래·금액은 거절·충돌 기록하며 기존 상태를 바꾸지 않는다. 거래가 복수이면 첫 거래를 임의 선택하지 않는다.
- callback-first·lookup-first·동시 reconcile 모두 같은 결과 적용 경계로 수렴한다. 동일 종결 결과는 추가 효과가 없고, 상충 결과는 덮어쓰지 않는다.
- callback이 없어도 본인의 reconcile API로 복구한다. 조회 0건·PENDING·조회 실패·조회 한도 소진은 새 결제 허용 근거가 아니다.
- timeout은 **실제로 사용하는 request factory·하위 HTTP client의 연결·응답 대기**를 제한한다. Future 대기 종료만으로 하위 HTTP 취소나 PG 취소가 증명됐다고 하지 않는다.
- PG **조회 한 경로에 circuit breaker를 적용**한다. CLOSED→OPEN→HALF_OPEN→회복 또는 재차단, 최소 표본·실패 조건·대기·탐색 호출 수와 OPEN 중 실제 외부 조회 차단을 확인한다. 회로 표본 수를 동시 요청 제한으로 설명하지 않는다.
- 조회 실패·회로 OPEN의 fallback은 저장된 상태·확인 불가를 반환한다. 가짜 성공·금액 0·확정 실패·포인트 대체·예약 반환으로 바꾸지 않는다.
- 조회 횟수·간격·총 대기 예산을 정하고 실제 호출 수를 검증한다. 자동 retry를 넣는다면 조회에만 적용한다. 회로와 중첩하면 어느 호출을 실패 표본으로 세는지 설명한다.
- Resilience4j를 선택하면 기존 Spring Boot 3/JDK 21에 맞는 모듈·버전을 명시한다. annotation 방식은 AOP·자기 호출·실제 proxy 적용을 확인한다. 라이브러리 추가나 설정값의 존재만으로 동작을 인정하지 않는다.

## 필수 검증 장면과 증거

fixture는 거래 수·실제 create/lookup 호출 수·거래 상태를 관찰할 수 있어야 한다. **외부 거래 한 건 생성 → 응답만 유실 → 같은 거래 SUCCESS 조회**를 결정적으로 재현한다. 호출 전에 단순 예외를 던지는 테스트만으로 응답 유실을 검증했다고 하지 않는다.

| 장면 | 핵심 기대값 |
| --- | --- |
| 정상 PG 주문 | 외부 거래 1, 주문 CONFIRMED, 예약 소비 1, 포인트 변화 0 |
| 생성 수락 PENDING | 주문 미확정·예약 유지. 조회 SUCCESS 확인 뒤에만 확정 |
| 효과 전 확정 거절 | 엄격한 422 계약 확인, 외부 거래 0·주문 실패·예약 반환 1. 동일 거절 중복 적용에도 반환 추가 0 |
| 거래 생성 뒤 응답 유실 | 외부 거래 1·UNKNOWN·예약 유지·create 추가 0. 같은 거래 조회로 종결 |
| 같은 주문·시도의 동시 요청 | 시도·예약 각 1, 실제 create 1. 다른 키·불일치 요청에는 추가 효과 없음 |
| callback-first·lookup-first·동시 적용 | 같은 transactionKey·최종 상태. 추가 차감·중복 반환 0. 종결 후 늦은 생성 응답·timeout에도 상태 퇴행 없음 |
| 외부 성공 뒤 내부 저장 실패 | 내부 TX rollback, 같은 거래 재조회로 한 번 확정, create 추가 0. 실패 결과 반영의 rollback도 반환 상태·재고가 함께 복구되어 재적용 가능 |
| 발송 기록 뒤 재시작 | 서비스·클라이언트를 재생성하되 같은 DB·외부 거래 상태 유지. 시도·예약 보존, 자동 재발송 0 |
| 조회 0건·복수 거래·금액/주문 불일치 | 임의 성공·실패·재결제 없음. 미확인·충돌 보존. 다른 거래·계정 범위도 적용하지 않음 |
| timeout·회로 OPEN·복구 | 실제 대기·호출 수 제한, 상태·예약 유지, 회로 전이와 회복 뒤 조회 재개 |
| 기존 기능 보호 | POINT 과거 기록·소유권·포인트 API 유지. 재고 부족 시 PG 0회. 예약 전 삭제와 예약 후 삭제 구분, 관리자 가용 재고 설정·관련 캐시 회귀 |

실제 DB 검증은 기존 **MySQL fixture**를 사용한다. callback도 실제 controller를 거쳐 조작한 본문만으로 성공하지 않는지 확인한다. adapter HTTP 계약 테스트와 업무 순서 테스트는 분리하거나 같은 fixture를 재사용할 수 있다. 모든 조건을 모든 계층에 반복하거나 특정 테스트 클래스명을 사용하는 것은 필수가 아니다.

정상 형식 확인에 무작위 지연·성공 확률을 넣지 않는다. 동시 실행·응답 유실·rollback·재시작은 해당 순서와 최종 DB 상태가 확인되어야 한다. 응답 코드뿐 아니라 **외부 거래 수·발송 횟수·주문·시도·가용/예약 재고·포인트**를 함께 대조한다.

## 직접 선택할 것과 확대하지 않을 범위

| 선택할 것 | 지켜야 할 조건 |
| --- | --- |
| 상태·객체·테이블 분리와 이름 | 원문의 상태 의미, DB 기반 한 시도·발송·예약·결과 적용 보호를 충족 |
| 잠금·조건부 전이 등 구체적 동시성 방법 | 중복 효과 방지와 기존 잠금 규칙 유지, HTTP 구간의 DB TX·잠금 분리 |
| 시도 키 형식·요청 일치 판별 방법 | 다른 주문·금액·요청을 같은 시도로 받아들이지 않음. 카드 번호를 영속화하지 않음 |
| providerOrderId 매핑 | 6자 이상 문자열, 생성·조회에서 같은 안정된 매핑. `LP-ORD-0000000042` 형식 자체는 예시 |
| HTTP client·회복 라이브러리 | 실제 timeout·조회 회로 차단·호출 수 확인. RestClient·Feign·WebClient·Resilience4j 중 특정 제품을 필수로 만들지 않음 |
| timeout·재조회·회로 수치 | 유한한 대기와 호출 수, 선택 이유·검증 결과. 학습 자료의 1초·3회·100/200ms는 예시 |
| PG fixture 구성 | 작은 내부 HTTP 서버 또는 테스트 fixture면 충분. 실제 adapter 형식과 통제된 외부 효과를 검증 |

**수동 reconcile은 기본 복구 경로이고 상시 스케줄러는 선택**이다. 자동 조회 retry 자체도 필수는 아니며 추가한다면 조회에만 제한한다. bulkhead·jitter·별도 PG 프로세스·관리 화면·운영용 callback 서명 체계·운영 모니터링 제품 구축을 새 필수 과제로 만들지 않는다. 다만 실제 HTTP timeout, 조회 한 경로의 circuit breaker, 검증된 권위 조회, 미완료 상태·한계의 기록은 생략할 수 없다.

## 실행·제출과 채점 원칙

다음 테스트 이름은 원문의 예시다. 실제 작성한 이름으로 실행한다.

```bash
./gradlew :apps:commerce-api:test --tests '*PaymentProviderContractTest'
./gradlew :apps:commerce-api:test --tests '*PaymentIntegrationTest'

# 현재 Java 프로젝트의 Checkstyle·ArchUnit·관련 회귀
./gradlew :apps:commerce-api:check
```

실행 건수·실패·skip·종료 결과를 기록한다. 테스트 0건·skip·연결 실패를 성공으로 세지 않는다. 기다림을 유한하게 제한하고 자신이 시작한 HTTP 서버·worker·테스트 자원을 정리한다. 기존 로컬 사용자 식별·관리자 MockMvc와 `127.0.0.1` 실행 범위를 유지하며 실제 비밀정보·카드·공개 배포를 사용하지 않는다.

제출물은 교체 코드·테스트·작은 PG fixture, 갱신한 상태·트랜잭션 설계, PR과 기술 글이다. PR에는 외부 거래 수·발송 횟수·주문·재고·포인트의 대표 결과와 남은 미확인 처리 한계를 적는다.

기술 글은 자신의 구현에서 한 주제를 골라 저장소 Markdown·Issue·블로그 중 하나로 작성한다. **실제 요청·상태 전이·실패 상황**, 관련 **개념을 자신의 말로 설명한 내용**, **선택의 이득·비용·자동 해결하지 못한 상황**을 확인한다. 원문의 주제 예시 중 하나를 반드시 고를 필요는 없다.

- 설계 계획·코드 존재·실제 실행 성공·제출 완료를 구분한다. 문서나 테스트 이름만으로 충족 판정하지 않는다.
- 테스트가 통과해도 필수 장면이 빠졌거나 기대값을 약하게 바꿨다면 해당 항목을 충족으로 세지 않는다.
- 상태·테이블·라이브러리 선택을 한 가지 정답으로 강제하지 않고, 원문에 없는 심화 기능 미구현으로 감점하지 않는다.
- 이전 주차 전체 과제를 다시 제출하도록 요구하지 않되, 이번 변경으로 영향을 받는 기존 계약의 회귀는 확인한다.
- 평가 요청에는 문제·근거·수정 방향을 제시한다. 구현 요청 없이 코드를 변경하지 않는다.
- 이 기준의 저장은 W5 구현 채점 결과가 아니다. 다음 평가에서 위 9개 항목과 제출 준비 상태를 따로 확인한다.
