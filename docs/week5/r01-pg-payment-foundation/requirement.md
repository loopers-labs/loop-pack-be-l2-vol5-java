## 사용자 확정 · 학습용 PG의 실행·저장

- commerce와 별도로 로컬에서 실행하는 작은 테스트 PG를 직접 만든다. commerce adapter는 이 서버에 실제 HTTP로 연결한다.
- 2026-10-21 사용자는 메모리 저장 선택을 철회하고 **DB(MySQL) 저장**으로 변경했다. 메모리 저장은 채택안이 아니다.
- DB 배치는 **기존 MySQL 서버에 PG 전용 스키마 분리**로 확정했다. commerce와 PG의 데이터 접근 경계는 구분한다.
- PG 재시작 후에도 저장된 거래·최종 결과를 같은 키로 조회할 수 있어야 한다. 평상시 재기동이 거래를 지우면 안 된다.
- 원문의 세 HTTP 경로·기본 필드·상태·합성 계정/카드 계약을 유지하고 생성 요청에 학습용 테스트 옵션을 추가한다.
- PG 결제 요청에 프리셋과 필요한 세부 조건을 함께 넣는다. 별도 시나리오 등록 제어 API는 도입하지 않는다. 미지정 조건은 프리셋 값을 유지한다.
- PG는 거래와 적용할 테스트 조건을 DB에 보관해 해당 거래의 자동 처리·응답·조회·callback을 재현한다. 첨부 원문은 수정하지 않고 추가 요청 필드를 사용자 확정 변경으로 구분한다.
- 성공/실패의 실제 거래 결과와 생성 응답의 지연/유실·조회 응답·callback 전달 조건을 구분해 조합한다. 프리셋 없이 축별 조건만 지정하는 안은 철회됐다.
- PG 거래 결과는 설정한 처리 시간에 따라 자동으로 반영한다. 거래 처리 시간과 생성/조회 응답 지연은 분리해 처리 중·응답 timeout을 각각 재현한다.
- commerce의 결제 시도 DB와 PG의 거래 DB는 서로 다른 사실의 원본이다. 직접 데이터 조인이나 같은 로컬 TX로 PG HTTP 경계를 우회하지 않는다.
- 실행 모듈·포트·스키마 이름/권한·스키마 반영·요청 테스트 옵션의 세부 계약/출처·프리셋 목록·재시작 실험 방식은 설계에서 정한다.
- PG는 DB의 예정 시각·결과를 단순 주기 조회해 기한이 지난 PENDING을 종결하고 재시작 뒤에도 처리한다. 재시작 실험용 프로필은 테이블을 보존하며 초기화는 명시 실행한다. 주기·정확한 프로필/필드·초기화 파일은 상세 설계에서 정한다.

## 우리 서비스 확정 · 결제 시도 소유권

- 결제 시도는 pay의 독립 모델·저장소로 두고 내부 orderId로 주문과 연결한다.
- 기존 OrderRecord는 Order의 주문 확정 기록으로 유지하며 결제 진행·실패 기록으로 바꾸지 않는다.
- application이 같은 commerce DB의 로컬 TX에서 주문·결제 시도·재고를 조율한다. 별도 모델이어서 분산 TX가 필요한 것은 아니다.
- 발송/관찰 상태의 정확한 표현·허용 전이·테이블 구성은 후속 문답에서 정한다. 재고 차감·복구 기록의 Context는 mall로 확정했다.
- 정상 자동 재확인은 @Retryable + DB 진행 기록으로 처리한다. 후속 결정으로 장애/재시작 뒤 자동 재개는 운영 담당자 조회·수동 대사로 변경했다. R01은 모델/저장 기반을 설계하고 실행 연결·장애 검증은 R02/R03에서 수행한다.
- [결제 결과·재확인 진행 상태 표현](trade_off/05-payment-attempt-state.md)은 확인한 결제 결과와 복구 진행을 나누는 것으로 확정했다. R01의 실제 enum·필드·허용 조합은 [구현 계획](plan.md)과 [상태 문서](../states/payment.md)를 따른다.
- [복구 진행 기록](trade_off/06-recovery-progress-storage.md)은 별도 pay 복구 작업 모델·저장소로 분리한다. 결제 시도에는 확인한 결제 사실을 두고 작업에는 진행·사용 횟수·재개 정보를 둔다.
- [재고 차감·복구 기록](trade_off/07-stock-adjustment-boundary.md)은 mall의 별도 모델에 둔다. 확정 실패를 반영하는 같은 로컬 TX에서 실제 재고와 복구 기록을 함께 갱신하며 별도 비동기 재고 복구 작업은 두지 않는다.
- application의 조율 파사드와 준비/공통 결과 반영용 TX 컴포넌트를 분리하는 A안을 채택했다. 각 TX 진입점은 별도 Spring 빈이며 PG HTTP·재조회 대기는 TX 밖에 둔다. 정확한 클래스/Context·계약은 R02 상세 설계에서 정한다.
- 복구 작업 실행 권한은 [멱등성 키 + 조건부 상태 갱신 + 실행 식별자](trade_off/08-recovery-claim-coordination.md)로 보호한다. 명시적 비관적 잠금 조회 대신 DB의 원자적 갱신 결과를 확인하고 commit 후 조회한다. 정확한 필드·조건식·bulk/Entity 정합성은 후속 설계에서 정한다.
- [검토 후 최소 보완](trade_off/10-learning-scope-completion.md)에 따라 검증 결과/확정 거절 사실은 기존 pay 시도에 짧은 TX로 먼저 commit하고 업무 반영 TX는 분리한다. 수동 대사는 실행 ID를 조건부 교체해 옛 진행 save를 차단한다. commerce 복구 작업은 사용 횟수·현재 실행/진행·최근 시각·오류를 우선 보존하고 지터/다음 예약 정보는 저장하지 않는다.

## 범위·업무 규칙

- PG 생성 POST, 거래 키 GET, PG용 주문 ID로 목록 GET을 연결하는 외부 경계를 분리한다.
- 세 요청에 합성 계정 `X-USER-ID: 135135`를 사용한다. 문자열 orderId는 6자 이상, 금액은 원화 정수다.
- 생성은 202, 거래 조회는 200, 주문 조회는 거래 배열, 없는 거래 키는 404라는 로컬 계약을 따른다.
- `PENDING/SUCCESS/FAILED`와 최종 결과 미확인 관찰을 구분한다. 수락을 결제 성공으로 매핑하지 않는다.
- 생성 전 거절은 원문에 정한 422·정확한 code·boolean false·요청 orderId/amount 일치가 모두 확인될 때만 효과 0건으로 해석한다.
- timeout·일반 HTTP 오류·잘못된 응답은 효과 0건으로 단정하지 않는다. 조회 404·빈 목록도 생성 전 확정 거절과 구분한다.
- [RestClient + Apache HttpClient 5](trade_off/03-http-client-settings.md)를 명시하고 자동 retry/redirect를 끈다. 연결 1초·연결 풀 대기 1초·응답 대기 2초를 생성/조회 공통 초기값으로 적용한다. 각각의 대기 제한이며 전체 호출의 절대 제한은 아니다. 본문 읽기 정지에도 대기가 제한되는지 실제 HTTP로 검증한다.
- [검증한 관찰 또는 확인 불가 사유를 결과값으로 반환](trade_off/04-adapter-fixture.md)한다. 실제 PG에서 정상·지연·유실·DB 보존을 검증하고, 작은 테스트용 HTTP 서버에서 깨진 JSON/불일치 등 응답을 고정한다. 재조회와 회로는 결과값을 분류해 연결하며 create 재시도는 금지한다.
- 실행형 테스트 PG와 보조 fixture에서 거래 수·create/lookup 횟수와 처리 순서를 관찰·통제할 수 있게 한다.
- 내부 시도 키·PG용 주문 ID·외부 거래 키·금액·상태·발송 사실의 저장 관계를 준비한다.
- 주문당 한 시도와 시도 키 요청 일치, 주문별 재고 차감 수량·처리 상태를 DB에서 보호할 기반을 준비한다.
- [시도 키는 전체 결제 시도에서 전역 유일](trade_off/02-idempotency-request-contract.md)하게 관리한다. 다른 고객의 같은 키도 충돌하며 주문당 한 시도 제약은 별도로 유지한다. 키 형식/DB 비교 규칙은 미정이다.
- 같은 주문·키로 재요청하면 최초 적용한 PG 테스트 조건을 고정 필드로 저장·비교하고 다르면 충돌로 거절한다. 기본값을 채운 실효값이 기준이며 생략/명시와 JSON 순서가 같으면 동등하다. 학습 중 프리셋 기본값은 고정한다. 기존 조건 변경·추가 create/차감은 하지 않으며 정확한 필드/기본값은 미정이다.
- POINT/PG 결제 사실을 구분하면서 과거 POINT 주문·기록의 금액·결과·품목을 보존한다.
- 합성 카드 번호도 영속화·로그 출력하지 않는다. PG/callback 주소는 로컬 설정이며 고객이 임의 주소를 주입하지 못하게 한다.
- 사용자 요청으로 카드 종류/번호는 재요청 비교에서 제외한다. 같은 주문·키·저장 금액·실제 테스트 조건이면 기존 상태를 반환하고 카드가 달라도 새 결제를 만들지 않는다. 카드 기반 HMAC/해시 저장·비밀키 관리는 도입하지 않는다. 카드 형식 검증은 유지하며 원문의 요청 일치 규칙에서 카드 입력을 제외하는 범위 조정으로 기록한다.

## 기존 기능 보호

- 준비 모델·저장 구조를 검증하기 위한 공개 API나 임시 상수 응답을 추가하지 않는다.
- 기존 주문·포인트 API의 동작 전환은 R02에서 처리한다. 과거 주문 기록을 새 결제로 재처리하지 않는다.
- domain은 순수 Java, application은 외부 경계 계약, infrastructure는 HTTP/저장 구현이라는 의존 규칙을 유지한다.
- 모델·테이블 구성, POINT 증분 SQL, 상태와 관찰 타입은 구현 계획·실제 결과에 반영했다. client·timeout 초기값·결과값 반환·검증 분담과 @Retryable 방향·상태 분리는 위 결정을 따른다.

## 요구사항 분석·PR 경계

R01의 산출물은 외부 PG를 호출·해석할 경계와 R02가 사용할 영속 모델이다.
기존 주문 실행을 바꾸지 않은 상태에서도 실제 HTTP 계약, 상태 전이, 저장 제약과 과거 데이터 호환을 독립적으로 검증할 수 있어야 한다.

| 책임 | R01에서 확인할 것 | 후속 PR에서 확인할 것 |
|---|---|---|
| 실행형 테스트 PG·adapter·보조 fixture | PG 거래의 DB 저장/재시작 보존·요청/응답 계약·검증한 관찰·호출 수·실제 timeout | R02의 주문/재고 적용, R03의 조회 회로·retry/fallback |
| 결제 시도·발송 | 상태/식별 관계·허용 전이·요청 일치·DB 제약 | R02의 실제 발송 권한 경쟁·재시작 후 대사 |
| mall 재고 차감·복구 모델 | 주문별 수량·처리 상태·중복 종결 방지의 모델/저장 기반 | R02의 실제 재고 차감·복구 TX·관리자/삭제/캐시 연결 |
| 기존 POINT 호환 | 이전 결제 사실을 해석·보존하고 기존 경로가 계속 동작함 | R02의 PG 전환·새 조회 응답·과거 POINT와의 구분 |

예를 들어 R01의 응답 유실 테스트는 외부 거래 1건·create 1회·결과 미확인 관찰까지 확인한다.
그 관찰로 주문을 대기 상태에 두고 차감 재고를 유지하는 업무 테스트는 R02의 책임이다.
HTTP client 선택·timeout 수치·테이블 구성은 일반적인 설계 선택이며, 그 자체를 원문의 오류로 보지 않는다.

근거 코드:

- [Order](../../../apps/commerce-api/src/main/java/com/loopers/domain/ordering/model/Order.java)는 `confirm()`에서 기록을 생성한다.
- [OrderRecord](../../../apps/commerce-api/src/main/java/com/loopers/domain/ordering/model/OrderRecord.java)는 금액·PAID·시각을 가지며 시도/외부 거래를 표현하지 않는다.
- [JPA 설정](../../../modules/jpa/src/main/resources/jpa.yml)의 local/test는 현재 `ddl-auto: create`다. payment-lab은 validate/명시 SQL로 분리했고 local/test는 유지했다. 마이그레이션 플랫폼은 도입하지 않았다.
- [이전 주문 기록 소유권 결정](../../week3/r02-order-consistency/trade_off/10-order-record-ownership.md)은 주문 확정 기록과 포인트 결제 사실을 구분한 배경이다.

원문이 이미 정한 PENDING/UNKNOWN 재고 유지·확정 거절의 정확한 판정·create 재시도 금지는 다시 미정 정책으로 열지 않는다.
운영용 PG 제품·환불·장기 미확인 자동 완료·스케줄러를 새 필수 요구로 추가하지 않는다.
사용자 추가 조건에 따라 독립 실행하는 DB 저장형 PG는 필수다. 테스트 내부 HTTP fixture는 보조 검증에 사용할 수 있다.

### R02에 넘길 경계 확인

- 가용 재고 5에서 2를 차감해 3이 된 뒤 관리자가 가용 재고를 10으로 설정하고 결제가 실패하면, 원문의 의미상 복구 결과는 12다.
  과거 값 5로 덮어쓰면 관리자 변경이 유실된다. 이는 새 정책 선택이 아니라 가용 수량 설정·주문 수량 반환의 조합에서 도출되는 검증 사례다.
- 현재 [Stock](../../../apps/commerce-api/src/main/java/com/loopers/domain/mall/model/Stock.java)은 int 범위를 사용한다.
  관리자가 최대 수량을 설정한 뒤 미완료 주문 수량을 복구하면 범위를 넘을 수 있으므로 허용 한도·실패 처리의 판단이 필요하다.
- 소유권·관리자 접근 범위는 전체 요구사항에 기록한 R02 질문으로 유지한다.
