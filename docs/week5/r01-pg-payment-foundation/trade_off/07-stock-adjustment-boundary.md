# 재고 차감·복구 기록의 경계

[설계 질문 목록](total_trade_off.md) · [pay 복구 작업 분리 결정](06-recovery-progress-storage.md) · [전체 재고 정책](../../total_requirement.md)

상태: **mall 별도 모델·동일 TX 복구 채택·세부 설계 전·구현 전**.

## 사용자 결정

2026-10-21 사용자는 재고 차감·복구 기록을 mall의 별도 모델로 두고 확정 실패 시 같은 트랜잭션에서 복구하기로 선택했다.
기록 모델 분리와 같은 TX의 동기적 재고 복구를 채택했다. 별도 비동기 재고 복구 worker는 도입하지 않는다.
실제 클래스·품목별/주문별 저장 단위·테이블·정확한 상태/애그리거트 경계는 후속 설계에서 정한다.

## 사용자의 추가 질문

2026-10-21 사용자는 별도 pay 복구 작업을 선택한 뒤 재고 복구도 별도 모델이어야 하는지 질문했다.
기존 요구사항은 이미 주문별 차감 수량·처리 상태의 영속화와 확정 실패 시 한 번 복구를 요구한다.
후속 결정으로 Context는 mall, 실행은 확정 실패 반영 TX 안의 복구로 정했다. 정확한 애그리거트 경계·상태/저장 구조는 아직 미정이다.

## 구분할 책임

| 책임 | 사실/진행 | 현재 결정 |
|---|---|---|
| 결제 시도 | 식별 관계·금액·발송 사실·확인한 결제 결과 | pay의 독립 모델 |
| 결제 복구 작업 | 기존 거래 재확인·결과 반영의 진행·사용 횟수·재개 정보 | 별도 pay 모델·저장소 |
| 주문별 재고 처리 기록 | 어떤 상품을 몇 개 차감했는지·성공으로 사용 확정했는지·실패로 복구했는지 | mall의 별도 모델. 정확한 상태·저장 단위/구조는 미정 |

pay 복구 작업과 mall의 재고 처리 사실은 별도 모델로 관리한다.
실제 복구 수량과 중복 복구 여부는 주문별 재고 처리 기록에서 판단하고 application이 결제 결과와 조율한다.
여기서 상품의 현재 가용 재고와 주문별 차감/복구 기록은 서로 다른 사실이다.

## 확정한 책임 · 차감과 복구를 추적하는 mall 모델

- 주문 식별자와 차감한 품목/수량, 처리 진행을 영속화한다. 실제 이름·품목별/주문별 저장 단위는 미정이다.
- 차감 사실과 복구 여부를 연결해 이미 복구한 수량을 두 번 더하지 못하도록 한다.
- 검증된 PG 실패를 반영할 때 상품 재고 증가와 처리 기록의 복구 완료, 주문/결제 관련 변경을 같은 로컬 TX에서 commit한다.
- 복구 도중 오류면 그 TX를 rollback하고, 기록과 실제 재고가 함께 바뀌었을 때만 복구 완료로 취급한다.
- 성공 시 이미 차감한 수량을 유지하고 해당 주문의 재고 처리를 종결한다. timeout·미확인·수동 전환만으로 복구하지 않는다.
- Context는 mall로 확정했다. ordering은 주문 진행·확정 기록을 소유하고 pay는 결제 사실·복구 작업을 소유한다.
- application 파사드가 각 Context의 서비스를 조율한다. 확정 실패 반영 TX에서 주문/결제·관련 복구 작업·상품 재고·재고 처리 기록을 함께 보호한다.

```text
재고 5개에서 주문 수량 2개 차감
→ 가용 재고 3개 + 주문별 차감 수량 2개 기록

PG 확정 실패
→ 같은 TX에서 재고 +2와 복구 완료 기록
→ 재고 5개

동일 실패 결과 재적용
→ 이미 복구한 기록 확인
→ 재고 5개 유지
```

Context와 같은 TX의 복구는 확정 사항이다. 정확한 저장 구조와 결제 시도·복구 작업의 잠금 순서/관계, 관리자 가용 재고 설정·삭제 상품 처리는 상세 설계에 포함한다.

## 별도 모델과 별도 비동기 작업의 차이

mall 모델을 분리하고 application 파사드가 확정 실패 결과를 반영하는 TX에서 동기적으로 재고를 복구한다.
실제 재고 증가와 기록의 복구 완료를 함께 commit하며, 중간 실패는 같은 TX에서 rollback한다.

별도 worker가 재고를 나중에 복구하는 안은 미채택이다. 이 안은 실패 반영과 재고 복구 사이의 미완료 기간·작업 발행/재개를 추가로 다뤄야 한다.
외부 PG가 이미 확정한 결과와 내부 반영 완료는 구분하며, 내부 복구 TX 실패가 PG 실패 사실을 성공으로 바꾸지 않는다.

후속 결정으로 R02의 [파사드·트랜잭션 경계](../../r02-pg-order-payment/trade_off/01-facade-transaction-boundary.md)는 조율 파사드 + 별도 준비/공통 결과 반영 TX 컴포넌트로 확정했다.
후속 설계 질문의 현재 순서는 [R01 목록](total_trade_off.md)을 따른다.
