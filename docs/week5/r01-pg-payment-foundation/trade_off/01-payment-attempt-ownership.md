# 우리 서비스 결제 시도의 책임·소유권

[전체 설계 질문](total_trade_off.md) · [요구사항](../requirement.md)

## 판단할 문제

우리 서비스는 PG를 호출하기 전에 어떤 주문의 결제를 시작했고 재고를 얼마나 확보했는지 DB에 남겨야 한다.
응답 유실이나 서버 재시작 뒤에도 같은 시도를 찾아 기존 거래를 조회하고, 중복 발송·확정·재고 복구를 막아야 한다.
이번에는 결제 시도를 어느 모델이 소유하고 저장할지부터 정한다. 세부 상태 전이·차감 기록의 소유권·요청 키 규칙은 후속 문답에서 정한다.

현재 [Order](../../../../apps/commerce-api/src/main/java/com/loopers/domain/ordering/model/Order.java)는
확정할 때 [OrderRecord](../../../../apps/commerce-api/src/main/java/com/loopers/domain/ordering/model/OrderRecord.java)를 만들고 자식으로 저장한다.
[기존 애그리거트 결정](../../../week3/r02-order-consistency/trade_off/11-order-record-aggregate.md)에서는 같은 생명주기의 주문 확정 기록을 Order 안에 두었다.
새 결제 시도는 처리 중·결과 미확인·실패도 보존해야 하므로 그 기록과 역할을 구분해 비교한다.

> **채택 — A. pay의 독립 결제 시도 모델**
>
> 2026-10-21 사용자는 주문과 결제 진행을 구분하고 application이 같은 DB TX에서 반영하는 A를 선택했다.
> 결제 시도는 pay에 독립 모델·저장소를 두고 orderId로 연결한다. 기존 OrderRecord와 과거 POINT 사실은 보존한다.
> 별도 저장소와 잠금/변경 조율이 필요하다는 비용을 남긴다. 상태 enum·테이블·차감 기록의 소유권까지 확정한 것은 아니다.

## 대안별 구성

### A. pay의 독립 결제 시도 모델 · 채택

- pay에 결제 시도 모델과 저장소를 두고 내부 orderId로 주문과 연결한다.
- 시도 키·외부 주문/거래 키·발송·결과 상태를 결제 시도의 책임으로 둔다.
- application이 주문·결제 시도·재고를 같은 commerce DB의 로컬 TX에서 조율한다.
- callback·조회·재시작 복구에서 시도를 먼저 찾고 필요한 주문/재고를 함께 검증해 반영할 수 있다.

### B. Order가 소유하는 결제 시도 자식 모델 · 미채택

- ordering의 Order가 결제 시도와 기존 OrderRecord를 서로 다른 자식으로 관리한다.
- 결제 시도의 변경·저장을 Order 루트를 통해 수행해 주문과 시도의 관계를 보호한다.
- 외부 거래/시도 키로 대상 주문을 찾는 조회 경로를 준비하고 주문을 통해 결과를 반영한다.
- Order가 결제 진행·발송 정보까지 소유하므로 모델과 저장/로딩 책임이 커진다.

## 장단점 비교

| 기준 | A. pay의 독립 시도 | B. Order의 자식 시도 |
|---|---|---|
| 책임 | 주문과 외부 결제 진행을 구분 | 주문이 결제 진행까지 함께 소유 |
| 변경 경로 | 시도 저장소와 주문 저장소를 application에서 조율 | Order 루트·저장소를 통해 함께 변경 |
| 불변식 | 시도 자체 규칙은 시도, 주문과의 관계는 application/TX·DB 제약 | 주문과 시도의 관계를 Order에 모으기 쉬움 |
| callback·복구 | 시도를 기준으로 조회·진행 상태 관리 | 시도 식별자로 주문을 찾아 루트를 통해 처리 |
| 비용 | 모델·저장소와 잠금/변경 조율 필요 | Order가 커지고 결제 전용 변경에도 주문을 다뤄야 함 |
| DB 원자성 | 같은 commerce DB의 로컬 TX로 보호 가능 | 같은 commerce DB의 로컬 TX로 보호 가능 |

별도 애그리거트라는 이유로 서로 다른 DB나 분산 트랜잭션을 도입하지 않는다.
어느 안이든 PG HTTP는 로컬 TX 밖에 두며 주문당 한 시도와 결과 적용 한 번의 제약을 지킨다.

## 복구 관점에서 두 안에 공통으로 필요한 사실

- PG 발송 전에 시도·식별 관계·발송 시작·차감 사실을 저장한다. 구체적인 저장/잠금 설계는 아직 미정이다.
- 발송 시작 후 서버가 멈춰도 새 create를 보내지 않고 기존 거래를 조회한다.
- PG 성공/실패 뒤 내부 저장이 실패하면 같은 거래를 다시 조회해 적용한다.
- 종결 반영 뒤 응답만 유실된 재요청은 저장한 결과를 반환하고 추가 효과를 만들지 않는다.
- 발송 기록 뒤 실제 HTTP 이전에 멈추면 외부 거래가 0건일 수 있다. 이 계약에서 재발송 없이 모든 시도의 자동 완료까지 보장하지 않는다.

## 결정 범위·다음 문답

결제 시도의 Context는 pay, 애그리거트는 Order와 독립으로 확정했다.
상태 표현에 앞서 [자동 재확인·수동 전환 정책](../../r03-payment-resilience/trade_off/01-reconciliation-retry-policy.md)을 논의한다.
최초 조회+추가 3회·1/3/10초·지터 ±20%와 실패/수동 전환 기준은 후속 사용자 결정으로 확정했다.
정상 실행은 @Retryable + DB 진행 기록을 유지한다. 이전 재시작 자동 재개는 후속 결정으로 운영 담당자 수동 대사로 변경했다.
[상태 표현](05-payment-attempt-state.md)은 확인한 결제 결과와 복구 진행을 나누기로 후속 결정했다. 정확한 상태값·전이는 아직 미정이다.
후속 결정으로 복구 진행은 별도 pay 작업 모델, 재고 차감·복구 기록은 mall의 별도 모델에 두고 확정 실패 반영 TX에서 복구한다.
application 파사드가 이 모델들을 조율한다. 요청 일치·거래 키 결합·정확한 전이/잠금·조회 경로는 상세 설계에서 정한다.
소유권 선택 자체는 PG 내부 타이머·주기 조회나 commerce 자동 대사 도입을 결정하지 않았다.
commerce 자동 재확인은 위 후속 결정으로 추가됐고 조회 직전 DB 횟수 소비를 채택했다. [최소 보완](10-learning-scope-completion.md)으로 관찰 먼저 commit/업무 TX 분리·수동 실행 ID 교체·commerce 예약 정보 영속화 제외·PG DB 예정 거래 주기 조회를 확정했다. 구체적인 실행기/프록시·조건식/필드·PG 조회 주기는 상세 설계 대상이다.
