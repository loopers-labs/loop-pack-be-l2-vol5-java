# 검토 후 확정한 학습용 최소 보완

[결정 목록](total_trade_off.md) · [R01 요구사항](../requirement.md) · [R02 TX 경계](../../r02-pg-order-payment/trade_off/01-facade-transaction-boundary.md)

상태: **2026-10-21 사용자 확정·구현 전**. 비즈니스·사용자 경험·기술 관점 검토 후 아래 여섯 가지를 채택했다. 기존 선택을 대체하는 범위와 남은 세부 설계를 구분한다.

## 1. 검증 결과를 먼저 commit하고 업무 반영 TX는 분리

흐름은 준비 TX → TX 밖 PG HTTP → 검증 결과 저장 TX → 공통 업무 반영 TX다. 전체 조율 파사드는 긴 TX를 열지 않는다. 각 짧은 TX는 별도 Spring 빈의 공개 진입점으로 둔다는 기존 A안의 원칙을 유지한다.

- 준비 TX는 재고 선차감·주문별 차감 기록·결제 시도·발송 사실을 보호한다.
- 결과 저장 TX는 검증한 PG 관찰과 거래 생성 전 효과 0건 확정 거절의 필요한 사실을 기존 pay 결제 시도에 보존한다. 카드 원문·응답 원문 전체·새 범용 이벤트 저장 모델은 추가하지 않는다.
- PG 생성 응답과 권위 조회 결과가 검증을 통과한 경우에만 관찰을 저장한다. callback 본문은 알림이므로 그 자체를 검증한 관찰로 저장하지 않는다. 거래 결합·종결 충돌·상태 회귀 금지 규칙을 유지한다.
- 저장 commit 뒤 공통 업무 반영 TX에서 저장한 결과를 확인하고 주문 확정 또는 실제 재고 복구·복구 완료 기록·관련 주문/결제/작업 진행을 함께 보호한다. 결과 저장만 성공한 상태는 주문/재고 반영 완료가 아니다.
- 업무 반영이 rollback돼도 먼저 commit한 관찰은 남는다. 신뢰할 수 있는 종결 결과가 저장돼 있고 미반영이면 그 사실을 공통 TX에 재적용할 수 있다. 매번 PG 재조회가 필수인 경로로 한정하지 않는다.
- 특히 정확한 생성 전 확정 거절은 원래 PG 거래가 없으므로 저장한 거절 사실로 재적용한다. 이후의 404·빈 목록으로 같은 거절을 새로 증명하지 않는다. 거래 키도 꾸미지 않는다.
- 결과 저장 전에 프로세스가 종료되거나 저장 commit 여부가 불명확하면 저장 상태를 확인한다. 보존된 근거가 없는 경우 미확인을 유지하며 자동 create 재발송·임의 실패/재고 복구를 하지 않는다. 응답 수신과 DB 기록 사이의 종료 가능성이 사라졌다고 설명하지 않는다.

R01은 관찰/거절 사실의 저장·복원·전이 계약을 준비한다. R02는 결과 저장 TX와 공통 업무 반영 TX의 실제 흐름, R03은 장애·재시작 회귀를 연결한다. 정확한 클래스/메서드·관찰 필드·잠금 순서·내부 반영 재시도 예산은 미정이다.

## 2. 실제 테스트 조건을 고정 필드로 저장·비교

- 프리셋에 기본값과 요청의 세부 조건을 적용한 최초 실효값을 고정된 타입/필드로 확정한다. commerce는 시도에 연결해 보존하고 PG는 전달받아 적용한 조건을 거래와 함께 보존한다.
- 같은 실제 조건이면 기본값 생략/명시·JSON 순서·동등한 프리셋 표현 때문에 충돌하지 않는다. 실제 조건이 다르면 기존 결정대로 충돌이며 최초 조건을 바꾸지 않는다.
- 학습용 프리셋의 기본값은 고정한다. 실행 중 프리셋 편집·버전 관리 플랫폼·범용 JSON 정규화/해시 엔진은 만들지 않는다. 카드 종류/번호도 비교하지 않는다.
- 정확한 프리셋 목록·필드/허용값·시간 기본값·조건 입력 경계는 상세 설계에서 정한다. 고정 필드 저장 방향을 그 목록까지 확정한 것으로 해석하지 않는다.

## 3. PG는 DB의 예정 시각·결과를 단순 주기 조회해 완료

- 자동 종결할 PG 거래에는 예정 시각과 예정 결과를 보존한다. PG 내부 작업이 기한이 지난 PENDING 거래를 찾아 종결하고 이미 종결한 거래를 다시 변경하지 않는다.
- PG 재시작 뒤에도 같은 DB의 미완료 거래를 찾아 처리한다. 거래마다 메모리 타이머를 만들고 기동 시 재예약하는 방식은 채택하지 않는다.
- 거래 처리와 생성/조회 HTTP 응답 지연·유실은 분리한다. PENDING 유지 조건과 생성 전 효과 0건 거절에는 자동 종결을 임의 적용하지 않는다.
- 이 주기 조회는 학습용 PG 내부 처리다. commerce의 재시작 자동 재조회·상시 reconcile 스케줄러를 추가하는 결정이 아니다.
- 주기·한 번의 처리 범위·정확한 저장 필드와 callback 발송 세부 계약은 미정이다. callback 발행 보장 플랫폼을 새 요구로 추가하지 않는다.

## 4. 재시작 실험용 프로필은 테이블 보존, 초기화는 명시 실행

- commerce와 PG의 재시작 보존 실험용 설정에서 기동 시 테이블을 자동 재생성/삭제하지 않는다. 초기 데이터/스키마 준비와 초기화 SQL·명령은 명시적으로 실행한다.
- 프로세스를 실제 종료·재실행해 동일 거래·시도·작업·사용 횟수·차감 기록을 확인한다. 객체 재생성만으로 재시작 보존을 검증했다고 하지 않는다.
- 일반 자동화 테스트의 격리·정리 설정과 보존 실험 설정을 구분한다. 기존 local/test의 create 설정을 보존 실험에 그대로 적용하지 않는다.
- 프로필 이름·구체적인 DDL 설정·초기화 파일 위치·계정/스키마 권한은 상세 설계에서 정한다. 마이그레이션 플랫폼 전체의 도입은 이번 선택에 포함하지 않는다.

## 5. 수동 대사가 실행 ID를 교체하고 옛 진행 갱신을 차단

- 담당자의 명시적 수동 대사 요청이 미완료 작업의 현재 상태·실행 ID를 조건으로 새 실행 ID를 원자적으로 기록한다. 중단 RUNNING도 READY로 자동 회수될 때까지 기다리지 않고 인계할 수 있어야 한다.
- 경쟁 요청 중 같은 이전 실행을 기준으로 갱신한 요청만 인계를 진행한다. 조건부 갱신 실패 시 최신 상태를 확인하며 무조건 덮어쓰지 않는다.
- 옛 실행은 새 조회 회차/진행을 갱신하지 못한다. 일반 save가 최신 실행 ID·횟수·종결/진행 상태를 예전 객체 값으로 되돌리지 않도록 조건부 저장 동작을 설계한다.
- 이미 발송한 GET까지 취소됐다고 가정하지 않는다. 늦은 응답·callback의 검증/업무 반영은 공통 경계에서 종결 충돌·회귀·추가 효과를 막는다.
- 수동 인계로 자동 조회 예산을 초기화하거나 새 PG create를 보내지 않는다. 자동 lease·heartbeat·자동 회수는 도입하지 않는다.
- R01은 실행 ID 교체/조건부 저장 기반, R02는 인계/API 경합, R03은 정상 재조회와 인계 이후 늦은 실행을 검증한다. 정확한 조건식·허용 상태·응답/오류·JPA 정합성 처리는 상세 설계에서 정한다.

## 6. commerce의 지터·다음 예약 시각은 영속화하지 않음

- 별도 pay 복구 작업 모델 선택은 유지한다. 사용 횟수·현재 실행/진행·최근 처리 시각·오류 등 수동 판단에 필요한 사실을 우선 보존한다.
- 정상 @Retryable 실행의 대기 간격과 지터는 런타임에서 계산한다. 적용한 지터 값·다음 실행 예정 시각·재시작 후 대기를 이어갈 예약 정보를 DB에 보존하지 않는다.
- commerce가 종료되면 자동 대기를 이어가지 않고 담당자 수동 대사 대상으로 남긴다. 이미 소비한 회차는 유지한다.
- PG의 자동 완료 예정 시각은 3번에 필요한 별도 사실이므로 저장한다. commerce 예약 정보 제외와 혼동하지 않는다.

## 구현·검증 시 확인할 대표 사례

- 검증한 생성 전 확정 거절 저장 → 재고 복구 TX 실패/rollback → 재시작 → 저장된 거절로 한 번 복구. 추가 create 0회.
- 검증한 SUCCESS 저장 → 주문 확정 TX 실패 → 성공 사실과 미반영 진행 보존 → 같은 사실 재적용.
- 실효 조건이 같은 재요청은 일치, 다른 조건은 충돌. 카드 입력 비교·카드 저장 없음.
- PG PENDING 도중 종료/재시작 → DB의 예정 조건으로 종결. commerce 미완료 작업은 자동 재개하지 않음.
- 수동 인계 뒤 옛 실행의 늦은 진행 save는 거절되며 callback·수동 반영이 추가 주문 확정/재고 복구를 만들지 않음.

위 내용은 확정한 설계와 향후 검증 조건이다. 기능 구현·테스트 실행·완료 기록이 아니다.
