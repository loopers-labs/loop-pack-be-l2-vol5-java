# 결제 결과·재확인 진행 상태 표현

[설계 질문 목록](total_trade_off.md) · [시도 소유권](01-payment-attempt-ownership.md) · [재확인 실행 결정](../../r03-payment-resilience/trade_off/06-reconciliation-execution.md)

상태: **B 채택·상세 전이 설계 전·구현 전**. 아래 이름과 값은 설명용이며 실제 필드/enum/테이블은 확정하지 않는다.

## 사용자 결정

2026-10-21 사용자는 확인한 결제 결과와 복구 진행을 나누어 관리하는 B를 선택했다.
조회 오류나 수동 전환으로 마지막 검증 결과를 덮어쓰지 않고, PG 결과 확인과 내부 업무 반영 완료를 구분한다.
추가 필드·유효 조합/전이 검증이 필요하다는 비용을 수용한다. 정확한 enum 이름·필드·전이표·테이블 분리는 아직 미정이다.
후속 [최소 보완 결정](10-learning-scope-completion.md)으로 검증한 결과/거절 사실은 기존 결제 시도에 짧은 TX로 먼저 commit하고, 주문 확정·재고 복구는 다음 공통 업무 반영 TX에서 처리한다. 먼저 보존한 관찰은 업무 반영 rollback으로 지워지지 않으며, 저장된 종결 결과의 미반영은 PG 재조회 없이 재적용할 수 있다. 관찰 저장 전에 종료되면 미확인 한계는 유지한다.

## 판단할 문제

결제 시도는 pay의 독립 모델이며 정상 @Retryable 실행과 DB 진행 기록, 장애 중단 후 운영 담당자 수동 대사를 지원한다. 재시작 자동 재개는 후속 결정으로 대체됐다.
이제 DB에 남길 결제 사실과 복구 진행을 어떻게 표현할지 정한다.
타임아웃·수동 전환이 이미 확인한 PG 결과를 지우거나 결제 실패로 바꾸지 않도록 해야 한다.

## A. 하나의 상태로 함께 표현 · 미채택

PENDING·UNKNOWN·SUCCESS·FAILED·MANUAL_REQUIRED 같은 값을 하나의 상태로 관리한다.
필드가 적고 단순한 흐름을 한눈에 보기 쉽다. 하지만 수동 전환의 이유와 마지막 확인 결과를 함께 보존하려면 추가 기록이 필요하다.
PG 성공 후 내부 반영 미완료, PG 실패 후 복구 미완료까지 구분하면 SUCCESS_APPLY_PENDING·FAILED_RESTORE_PENDING 같은 조합 상태가 늘어날 수 있다.
이 안도 조합을 충분히 정의하면 구현할 수 있으나, 새 복구 단계가 추가될 때 상태값과 전이가 함께 늘어난다.

## B. 확인한 결제 결과와 복구 진행을 나눔 · 채택

| 구분 | 설명용 값 | 의미 |
|---|---|---|
| 확인한 결제 결과 | 미확인·PENDING·SUCCESS·FAILED | 검증한 PG 사실을 보존. 생성 전 확정 거절은 실패 사유로 별도 구분 |
| 복구 진행 | 자동 진행·수동 확인 필요·반영 완료 | 결과 조회/내부 반영을 이어갈지, 사람의 확인이 필요한지, 업무 반영을 마쳤는지 표현 |

- 발송 시작 사실·거래 키·사용한 횟수·현재 실행/진행·최근 처리 시각·오류 등 필요한 기록을 설계한다. commerce의 지터 값·다음 예약 시각·재시작 대기 재개 정보는 저장하지 않는다. 이 표가 전체 저장 스키마는 아니다.
- PENDING을 확인한 뒤 조회 timeout이 나면 확인한 PENDING은 유지하고 최근 조회 실패를 별도로 기록할 수 있다.
- PG 결과를 확인했어도 주문 확정/재고 복구 TX가 성공하기 전에는 반영 완료로 표시하지 않는다.
- 결제 사실과 복구 진행을 구분하므로 수동 전환이 확인된 결과를 덮어쓰지 않는다.
- 필드와 유효한 조합 검사가 늘어난다. 개별 setter 대신 의미 있는 도메인 행동과 전이 규칙으로 모순된 조합을 막아야 한다.

### 예시

```text
조회 한도 소진
  확인한 결제 결과 = PENDING 또는 미확인
  복구 진행 = 수동 확인 필요

PG 성공 확인 후 주문 확정 DB 오류, 내부 반영 재시도도 소진
  확인한 결제 결과 = SUCCESS
  복구 진행 = 수동 확인 필요

PG 실패 확인 후 재고 복구까지 commit
  확인한 결제 결과 = FAILED
  복구 진행 = 반영 완료
```

설명용 SUCCESS+자동 진행은 기존 결제를 다시 만드는 뜻이 아니다. 확인한 성공 결과의 내부 반영을 이어가는 의미다.
수동 전환 상태에서도 검증된 callback·수동 대사 결과를 공통 멱등 경계로 반영할 수 있다.
종결 충돌은 기존 결과를 덮어쓰지 않고 별도 사유로 보존한다.

## 선택 이유와 남은 질문

B는 이미 확정한 실패/수동 전환 구분과 내부 반영 실패를 표현하기 쉽고, 조회 오류가 결제 사실을 덮어쓰지 않게 할 수 있어 채택했다.
정확한 상태값·허용 조합·발송 사실·내부 반영 표시·저장 경계와 전이표는 후속 설계에서 정한다.
[재시도 횟수 소비 시점](../../r03-payment-resilience/trade_off/07-retry-attempt-accounting.md)은 후속 결정으로 조회 직전 DB 기록/commit을 채택했다.
[복구 진행 기록 저장 경계](06-recovery-progress-storage.md)는 별도 pay 복구 작업 모델로 분리하기로 후속 결정했다.
확인한 결제 사실은 결제 시도, 복구 진행은 복구 작업이 소유하며 application/TX가 두 모델의 유효한 조합을 조율한다.
[재고 차감·복구 기록](07-stock-adjustment-boundary.md)은 mall의 별도 모델·확정 실패 반영 TX 안의 복구로 확정했다.
R02의 [파사드·TX 경계](../../r02-pg-order-payment/trade_off/01-facade-transaction-boundary.md)는 조율 파사드 + 별도 준비/공통 결과 반영 TX 컴포넌트로 후속 확정했다. 현재 질문 순서는 [R01 목록](total_trade_off.md)을 따른다.
callback/자동 작업 경합과 내부 결과 반영 예산은 별도 문답에서 이어간다.
