# PG 응답 해석·최소 HTTP 검증

[설계 질문 목록](total_trade_off.md) · [요구사항 G03/G04/G06/G07](../requirement.md) · [HTTP 호출·시간 제한](03-http-client-settings.md)

상태: **A·테스트 분담 확정·구현 전**. 2026-10-21 사용자가 03과 함께 추천안을 선택했다. 이미 확정된 업무 규칙은 유지한다.

## 판단할 문제

PG가 알려 준 결제 실패와, 통신이 끊겨 결과를 모르는 상황은 서로 다르다. adapter가 이를 어떤 형태로 우리 서비스에 전달할지 정한다.

| 대안 | 전달 형태 | 이득 | 비용 |
|---|---|---|---|
| A. 검증한 관찰 또는 확인 불가 사유를 결과 타입으로 반환 · 채택 | 정상 결과·효과 0건 거절·조회 0건·통신/계약 오류를 구분해 전달 | 테스트에서 반환값으로 확인하기 쉽고 timeout을 결제 FAILED로 잘못 취급할 가능성을 줄임 | 복구 실행기가 재조회 대상인지 판단해 @Retryable 제어에 연결해야 함 |
| B. 정상 관찰은 반환하고 통신/계약 오류는 전용 예외로 전달 · 미채택 | PG FAILED는 정상 관찰이며 timeout 등만 전용 예외 | 일시적 통신 장애를 @Retryable 예외 조건에 직접 연결하기 쉬움 | 값과 예외 두 경로를 이해해야 하며 PENDING/빈 조회는 여전히 별도 재조회 판단이 필요 |

관찰 결과를 반환값으로 확인하기 쉽도록 A를 선택했다. Spring/Apache 예외를 그대로 application 계약에 노출하지 않는다. 외부 JSON DTO는 infrastructure 안에서 변환한다. 예상한 외부 오류를 다루는 선택이며 프로그램 결함까지 모두 catch해 확인 불가로 숨기지 않는다.
PG 결과 검증은 adapter 경계, 주문/시도/실행 권한·최종 반영 판단은 application과 도메인에 둔다. 이름·패키지·record/enum 등 상세 타입은 아직 미정이다.

## 확정한 결과 구분 방향

| PG 관찰 | 전달할 의미 | 기존 확정 정책 |
|---|---|---|
| 필수 값·주문·금액·거래 관계를 검증한 PENDING/SUCCESS/FAILED | 검증한 결제 관찰 | PENDING 차감 유지, SUCCESS 확정, FAILED 한 번 복구 |
| 정확한 생성 전 확정 거절 | 거래 없는 효과 0건 거절 | 422·정확한 code·boolean false·주문/금액 일치가 모두 필요. 거래 키를 꾸미지 않음 |
| 생성 timeout·일반 오류·불완전 응답 | 결과 확인 불가와 사유 | 새 create 없이 기존 거래 조회 |
| 조회 timeout·일시적 5xx | 이번 조회 확인 불가와 사유 | 예산 내 재조회 후 수동 전환. 마지막 검증 결과 유지 |
| 조회 404·빈 목록 | 이번 조회에서 거래 확인 안 됨 | 재조회 대상. 재발송·재고 복구 근거 아님 |
| 복수 거래·주문/금액/기존 거래 키 불일치 | 충돌 사유 | 즉시 수동 확인, 임의 거래 선택·재결합 금지 |
| 조회 인증/설정 오류·잘못된 JSON/필드/상태 | 확인 불가와 계약/설정 오류 사유 | 같은 요청 반복이 도움이 안 되는 경우 즉시 수동 전환 |

필수 문자열 누락/공백·정수가 아닌 금액/허용 범위 초과·알 수 없는 상태·예상과 다른 HTTP 코드를 성공으로 수용하지 않는다. 최초 거래 키는 기대한 주문/금액/제공자 계정 범위 검증 뒤에만 연결하며 연결 후 다른 키로 교체하지 않는다.
정확한 필드별 검증·HTTP/사유 코드 표는 구현 전 상세 설계에서 정한다. 위 표는 기존 [실패 분류 정책](../../r03-payment-resilience/trade_off/01-reconciliation-retry-policy.md)을 보존하는 확정 방향이다.

### @Retryable과의 연결

결과 타입 반환만으로 @Retryable이 재실행되지는 않는다. R03 복구 실행기는 기존 정책상 재조회할 PENDING·빈 조회·일시적 통신 장애를 구분해 재조회 제어용 예외 등으로 연결한다.
횟수는 조회 전에 DB에 commit하고, 관찰/진행 저장을 마친 뒤 TX 밖에서 대기한다. 즉시 수동 전환 사유와 검증한 FAILED는 재조회 제어 예외로 묶지 않는다.
생성 POST에는 @Retryable을 적용하지 않는다. 마지막 검증 결과를 확인 불가 사유로 덮어쓰지 않으며 자동 예산·수동 대사 정책을 바꾸지 않는다.
R03의 회로도 오류가 결과값으로 반환된다는 점을 반영해 실패를 집계해야 한다. 정상 반환이라는 이유만으로 통신 장애를 성공으로 집계하지 않으며 구체적인 회로 연결 방식은 R03에서 정한다.

## 확정한 최소 테스트 분담

- 독립 실행 PG는 DB 저장·자동 완료·요청 프리셋/세부 조건·생성/조회 응답 지연/유실을 재현하는 데 집중한다. 학습용 결제 처리 도구로 유지한다.
- 깨진 JSON·필수 필드 누락·주문/금액 불일치·연결 종료·redirect처럼 adapter 방어를 검증할 응답은 테스트 중에만 실행하는 작은 HTTP 서버로 고정한다. 새로 상시 실행할 앱이나 장애 관리 UI는 만들지 않는다. 테스트 서버 구현 도구는 별도로 무거운 시스템을 도입하지 않는 범위에서 고른다.
- 정상 HTTP 계약과 PG DB 보존은 실제 PG에 연결해 확인한다. 테스트용 서버만 통과한 것으로 독립 실행 PG 요구사항을 완료 처리하지 않는다.
- 테스트 PG는 같은 orderId의 두 POST를 자동 중복 제거하지 않는다. 거래 2건을 확인하는 검증은 commerce의 중복 발송 버그를 가리지 않기 위해 유지한다.
- 유실 후 성공/실패는 고정 조건으로 각각 재현한다. 무작위 성공 확률·성능 벤치마크·별도 테스트 제어 API는 추가하지 않는다.

## 대표 검증 묶음 · 미실행

1. 정상 세 API: 요청 형식과 PENDING/SUCCESS/FAILED의 검증/변환.
2. 효과 0건 확정 거절과 거래 생성 후 응답 유실: PG 거래 수 0/1의 차이, 추가 create 없음. 재고 효과 검증은 R02에서 연결.
3. 조회 404·빈 목록·복수 거래·다른 주문/금액/거래 키: 확인 불가/충돌 구분, 임의 성공 없음.
4. 잘못된 JSON·누락/공백 필드·알 수 없는 상태·잘못된 숫자·일반 4xx/5xx: 확정 실패로 오인하지 않음.
5. 실제 지연/연결 종료: timeout 설정과 숨은 재호출 차단.
6. 같은 orderId의 두 POST는 외부 거래 2건. PG 재시작 후 거래·최종 결과 보존.

독립 PG에 모든 잘못된 응답 기능을 넣지 않고 위 분담으로 검증한다. 테스트용 HTTP 서버의 도구·상세 타입·필드/사유 코드는 아직 미정이며 기능·테스트 완료를 기록한 문서가 아니다.
