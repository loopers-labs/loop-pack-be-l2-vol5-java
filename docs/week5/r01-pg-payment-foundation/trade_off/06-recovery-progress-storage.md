# 복구 진행 기록의 저장 경계

[설계 질문 목록](total_trade_off.md) · [상태 분리 결정](05-payment-attempt-state.md) · [횟수 기록 결정](../../r03-payment-resilience/trade_off/07-retry-attempt-accounting.md)

상태: **B 채택·세부 설계 전·구현 전**. 아래 이름은 설명용이며 실제 클래스·필드·테이블 이름은 미정이다.

## 사용자 결정

2026-10-21 사용자는 복구 진행·사용 횟수·재개 정보를 별도 pay 복구 작업 모델로 분리하는 B를 선택했다.
결제 시도는 확인한 결제 사실을 소유하고, 복구 작업은 재확인/결과 반영의 진행을 관리한다.
application이 같은 commerce DB의 로컬 TX에서 관계·진행을 조율하며 별도 모델/저장소·동시 변경 조율의 비용을 수용한다.
정확한 클래스·테이블·관계/유일성 제약·상태값은 아직 정하지 않았다. 재고 차감/복구의 업무 사실은 후속 결정으로 mall의 별도 모델이 소유한다.
후속 [최소 보완 결정](10-learning-scope-completion.md)으로 검증 관찰은 별도 짧은 TX에서 먼저 보존한다. 복구 작업에는 사용 횟수·현재 실행/진행·최근 처리 시각·오류를 우선 저장하고 commerce의 지터 결과·다음 실행 예약 정보는 영속화하지 않는다. 수동 대사는 실행 ID를 조건부 교체해 옛 진행 갱신을 차단한다.

## 판단할 문제

결제 시도는 pay의 독립 모델이다. 확인한 결제 결과와 복구 진행을 구분하고 사용 횟수·중단 정보를 보존한다. 후속 결정으로 재시작 자동 재개는 담당자 수동 대사로 변경했다.
조회 작업 직전 사용 횟수를 DB에 commit하는 것으로 정했으므로 진행 기록을 어느 모델/저장 경계에서 관리할지 선택한다.
상태를 나누기로 한 결정이 반드시 테이블이나 애그리거트를 분리한다는 뜻은 아니다.

## A. 결제 시도에 복구 진행을 함께 저장 · 미채택

- pay의 결제 시도 안에 확인한 결과와 복구 진행·조회 횟수·대기 단계/재개에 필요한 사실을 각각 구분해 둔다.
- 개념별 필드나 값 객체로 구분할 수 있으며 실제 구성과 저장 컬럼은 이후 설계에서 정한다.
- 시도 하나를 읽어 PG 사실과 자동 재개/수동 전환 여부를 함께 판단할 수 있다.
- 같은 시도의 상태·횟수·종결/수동 전환을 한 저장 경계에서 보호하기 쉽다.
- 비용: 결제 사실과 재확인 진행 변경이 같은 모델/저장 행에 모여 필드·변경 책임과 경합이 늘어난다.

```text
결제 시도
  확인한 결제 결과
  복구 진행
  사용한 조회 횟수
  재개에 필요한 대기 정보
```

## B. 별도 pay 복구 작업 모델로 저장 · 채택

- 결제 시도에는 결제 사실을 두고, 별도 복구 작업 모델을 시도 식별자로 연결한다.
- 복구 작업이 진행·횟수·실행 ID·최근 처리 정보를 관리하며 application이 시도와 작업을 같은 commerce DB의 로컬 TX에서 조율한다. 재시작 후 대기를 이어갈 예약 정보는 저장하지 않는다.
- 복구 작업의 생명주기·저장 구조를 독립적으로 확장하기 쉽다.
- 비용: 모델·저장소·관계/유일성 제약·동시 변경 조율이 추가된다. 시도 종결과 작업 중단을 함께 보호해야 한다.
- 별도 모델을 두는 것만으로 메시지 브로커·분산 TX·상시 스케줄러가 필요한 것은 아니다.

## 선택 이유와 남은 질문

앞서 단순한 저장 경계 때문에 A를 추천했지만 사용자는 B를 선택했다. 복구 작업의 책임과 저장 구조를 결제 사실에서 분리한다.
횟수/실행 권한 확인과 기록은 짧은 로컬 TX로 보호하고 PG HTTP 호출·대기는 TX 밖에서 수행한다.
재시작 후에도 남은 예산과 종결 상태를 보존하며 담당자 수동 대사에서 최신 상태를 확인한다. 자동 재시도를 다시 시작하지 않고 주문 확정·재고 복구는 한 번만 반영한다.

- 정확한 필드·값 객체·상태값·허용 조합/전이표.
- 사용 횟수·실행 ID·진행·최근 처리 시각·오류의 정확한 필드/저장 제약. 지터/예약 정보 저장은 제외한다.
- 수동 대사의 실행 ID 교체 조건·허용 상태·응답과 callback 경합의 구체적인 보호 방식. 자동 lease/회수는 도입하지 않는다.
- 먼저 commit한 검증 결과를 재적용할 입력/저장 계약·내부 반영 실패 기록의 상세. 관찰 저장 TX와 업무 반영 TX 분리는 확정이다.

[재고 차감·복구 기록](07-stock-adjustment-boundary.md)은 mall의 별도 모델·같은 TX 복구로 후속 확정했다.
R02의 [파사드·TX 경계](../../r02-pg-order-payment/trade_off/01-facade-transaction-boundary.md)는 조율 파사드 + 별도 준비/공통 결과 반영 TX 컴포넌트로 후속 확정했다. 현재 질문 순서는 [R01 목록](total_trade_off.md)을 따른다.
구현·테스트는 아직 시작하지 않았다. 실제 저장 구조와 전이 규칙은 후속 설계 후 계획에 연결한다.
