# 학습용 PG의 독립 실행·거래 저장

[전체 설계 질문](total_trade_off.md) · [요구사항](../requirement.md)

## 판단할 문제

사용자는 학습용 PG를 직접 만들고 commerce가 실제 HTTP로 연결하는 구성을 요구했다.
테스트 클래스 안에서만 실행되는 HTTP fixture를 넘어, 로컬에서 별도로 실행할 수 있는 작은 서버가 필요하다.
PG 거래 저장 방식은 사용자가 메모리 선택을 철회하고 DB 저장으로 변경했다.

> **확정 — 독립 실행 테스트 PG·기존 MySQL의 PG 전용 스키마에 거래 저장**
>
> 2026-10-21 사용자 최종 선택이다. 메모리 저장은 채택안이 아니다.
> PG 재시작 뒤에도 거래·결과를 같은 키로 조회한다. 실제 카드·금전·외부 PG 계정은 사용하지 않는다.
> DB 배치는 기존 MySQL 서버 안에 commerce와 구분되는 PG 전용 스키마를 두는 것으로 사용자와 확정했다.

## 저장 방식 비교

| 기준 | DB 저장 · 채택 | 메모리 저장 · 철회 |
|---|---|---|
| 실행 중 생성·조회 | DB에서 거래를 저장·조회 | 프로세스 메모리에서 저장·조회 |
| PG 재시작 | 저장된 거래를 다시 조회 | 거래 초기화 |
| 복구 실험 | commerce와 PG의 재시작을 구분해 검증 가능 | PG를 켜 둔 채 commerce 재시작을 검증 |
| 추가 구성 | DB 연결·테이블·스키마 반영·테스트 데이터 정리 필요 | 저장 구조가 간단함 |

## DB 배치 결정

| 기준 | 기존 MySQL의 PG 전용 스키마 · 채택 | 별도 MySQL 인스턴스 · 미채택 |
|---|---|---|
| 실행 구성 | 기존 서버를 재사용하고 스키마·접근 설정을 분리 | 서버·포트·볼륨 설정 추가 |
| 데이터 경계 | commerce와 PG의 스키마를 구분 | 서버와 스키마를 구분 |
| DB 장애 | MySQL 서버 장애는 두 앱에 함께 영향 | DB 인스턴스별 장애 실험 가능 |
| 이번 선택 | 학습용 기존 인프라를 재사용한다는 사용자 결정 | 이번 구성에서는 추가하지 않음 |

스키마 이름·계정/권한·테이블·프로필 이름과 초기화 SQL/명령의 상세는 아직 정하지 않았다. 후속 [최소 보완 결정](10-learning-scope-completion.md)에 따라 재시작 실험용 프로필은 테이블을 보존하고 초기화는 명시적으로 실행한다.
같은 MySQL을 사용해도 두 앱은 자기 스키마를 대상으로 동작하고 업무 연동은 HTTP를 사용한다.

## 실패 시나리오 제어 결정

**확정 — PG 결제 생성 요청에 프리셋과 필요한 세부 테스트 조건을 함께 보낸다.**
사용자는 별도 제어 API로 사전 등록하는 방식에서 요청에 테스트 조건을 포함하는 방식으로 변경했다.
프리셋을 선택하고 필요한 조건만 변경하는 구성은 유지한다. 축별 직접 설정만 제공하는 안은 채택하지 않는다.
무작위 성공/실패보다 동일한 실패 순서를 재현할 수 있는 구성을 우선한다.

| 기준 | 별도 제어 API로 사전 등록 · 철회 | PG 결제 요청에 테스트 조건 포함 · 채택 |
|---|---|---|
| 사용 | 결제 전에 주문별 시나리오를 따로 등록 | 결제 정보와 테스트 조건을 한 요청에 전달 |
| 장점 | 결제 요청과 시나리오 등록을 구분 | 사전 등록 흐름이 없고 요청만으로 원하는 실험을 재현 |
| 비용 | 등록 API·설정 관리와 추가 요청 필요 | 학습용 추가 필드와 commerce에서 전달할 조건의 출처/범위 설계 필요 |
| 원문 결제 계약 | 기존 결제 생성/조회 형식 유지 | 기본 필드·경로는 유지하고 생성 본문에 학습용 옵션 추가 |

예시는 주문 A의 성공, 주문 B의 확정 실패, 주문 C의 거래 생성 뒤 응답 유실이다.
별도 시나리오 등록·변경 제어 API는 도입하지 않는다. PG는 받은 거래와 적용할 테스트 조건을 DB에 저장하고
그 조건대로 자동 처리·응답·조회·callback을 제공한다. commerce의 주문·재고 상태는 정상 결과 확인 경계를 통해 바뀐다.
원문의 생성 본문에 테스트 조건을 추가하는 것은 사용자 확정 변경으로 기록하며 첨부 원문은 수정하지 않는다.

### 프리셋과 세부 조건

- 자주 사용하는 상황을 프리셋으로 준비한다. 정상 성공·유실 후 성공·유실 후 실패는 출발 예시이며 전체 목록·이름은 아직 정하지 않았다.
- 선택한 프리셋을 기본으로 적용하고 요청에서 지정한 세부 조건을 우선 반영한다. 지정하지 않은 조건은 프리셋 값을 유지한다. 최초 실효 조건을 고정 필드로 저장·비교하며 기본값 생략/명시와 JSON 순서는 동등성에 영향을 주지 않는다. 학습 중 기본값은 고정하고 실행 중 프리셋 편집/버전 관리 기능은 만들지 않는다.
- 거래의 실제 결과와 응답 전달 방식을 구분한다. 성공/실패와 생성 응답의 정상/지연/유실을 조합할 수 있어야 한다.
- 거래 생성 여부·결과/완료 시점·생성 응답·조회 응답·callback 전달 조건을 구분해 설계한다. 정확한 필드·허용값·기본 시간은 미정이다.
- 예를 들어 유실 후 성공 프리셋을 선택한 뒤 callback만 누락으로 바꾸면, 생성 응답과 callback을 못 받아도 조회로 성공을 확인하는 실험이 된다.
- 생성 전 효과 0건 확정 거절이 나중에 거래를 만들지 않는다는 원문 제약 등 조합의 업무 불변식을 유지한다.

프리셋을 고르는 단계 없이 축별 조건만 직접 지정하는 방식은 최종 채택안이 아니다.
요청 일치는 실제 적용 조건을 고정 필드로 저장·비교하는 것으로 확정했다. 정확한 옵션 필드·조건 출처·세부 상태 전이·callback 발생 조건은 아직 정하지 않았다.
`testScenario` 같은 이름은 설명용 예시이며 최종 필드명으로 확정하지 않았다.

## 결제 완료 방식 결정

**확정 — PG가 설정한 처리 시간에 따라 거래를 자동으로 완료한다.**
2026-10-21 사용자는 자동 처리 방식을 선택했다. 별도 완료 API 호출이 있어야만 거래를 종결하는 수동 방식은 기본 동작으로 채택하지 않는다.

- 거래 처리 시간과 생성/조회 HTTP 응답 지연을 서로 구분한다. 응답 대기가 끝나도 PG의 거래 처리는 계속될 수 있어야 한다.
- 예를 들어 commerce 응답 timeout 1초·PG 성공 완료 2초·생성 응답 지연 3초면, commerce가 먼저 timeout을 관찰한 뒤 PG 성공을 조회/콜백으로 확인한다.
- 같은 구성에서 결과를 FAILED로 바꾸면 timeout 후 확정 실패 확인과 재고 복구를 검증한다. 위 수치는 설명용이며 기본값으로 확정하지 않았다.
- 생성 응답을 즉시 PENDING으로 보낸 뒤 거래를 늦게 완료하는 것은 처리 중 테스트다. 실제 응답 timeout은 생성/조회 응답 지연을 따로 설정해 재현한다.
- 생성 전 효과 0건 확정 거절은 나중에 거래를 만들지 않는다. PENDING 유지 등 미완료 시나리오와 자동 성공/실패 시나리오의 세부 규칙은 프리셋 설계에서 정한다.

### PG 자동 작업의 실행·재시작 · DB 주기 조회 채택

이전에는 아래 비교를 보류했으나 2026-10-21 후속 결정으로 DB에 예정 시각·결과를 저장하고 단순 주기 조회하는 안을 채택했다. 상세는 [최소 보완 결정](10-learning-scope-completion.md)을 따른다.

| 기준 | DB에서 예정된 거래를 주기적으로 확인 · 채택 | 거래마다 타이머를 예약하고 재시작 시 복원 · 미채택 |
|---|---|---|
| 동작 | 완료 예정 시점이 지난 PENDING 거래를 찾아 결과 반영 | 생성 시 완료 작업을 예약하고 기동 시 미완료 거래를 다시 예약 |
| PG 재시작 | DB를 확인하는 작업이 다시 실행되면 남은 거래를 찾음 | DB에서 거래를 읽어 예약 작업을 복구하는 절차 필요 |
| 장점 | 저장한 사실을 기준으로 처리하고 재시작 흐름이 단순 | 평상시 주기 조회를 줄일 수 있음 |
| 비용 | 확인 주기의 DB 조회와 처리 지연 | 거래별 예약 관리와 기동/재예약 경계의 구현 필요 |

어느 안이든 종결 거래를 다시 바꾸지 않고 응답 전송·지연과 거래 처리를 분리해야 한다.
여기서 논의하는 것은 학습용 PG 내부의 자동 처리이며, commerce의 상시 reconcile 스케줄러를 추가한다는 결정이 아니다.
사용자는 우리 서비스의 복구 설계도 중요함을 지적했고, 테스트 PG는 요청 조건을 재현하는 학습 도구로 단순화하기로 했다.
내부 작업은 DB 주기 조회로 확정했다. 기한이 지난 PENDING을 종결하고 재기동 뒤에도 남은 거래를 찾는다. PENDING 유지·거래 없는 확정 거절에는 임의 완료를 적용하지 않으며 주기·처리 범위·정확한 필드·callback 세부는 후속 설계 대상이다.

## 구현으로 이어질 요구

- PG 생성·거래 조회·주문별 조회의 경로·기본 필드를 유지하고 생성 요청에 학습용 테스트 조건을 추가한다.
- 같은 orderId의 새 POST를 자동 중복 제거하지 않는다. 호출·거래 수와 결과 상태를 관찰할 수 있어야 한다.
- 성공·실패·처리 중·지연·거래 생성 뒤 응답 유실을 학습에 맞게 통제한다.
- PG의 거래 DB와 commerce의 시도/주문 DB를 서로 다른 사실의 원본으로 다룬다. 직접 조인·공유 TX로 HTTP 경계를 우회하지 않는다.
- PG 재기동 때 거래를 초기화하지 않는다. 의도적인 테스트 데이터 정리와 평상시 기동을 구분한다.
- R01에서는 테스트 PG와 실제 commerce adapter의 연결을 검증하고, 주문 confirm·callback 수신 연결은 R02에서 검증한다.

## 남은 설계 질문

- 독립 실행 모듈·명령·로컬 포트와 실행 방법.
- 확정한 기존 MySQL의 PG 전용 스키마 이름·계정/권한·접근 설정.
- 스키마 반영·초기화·테스트 정리 방식. 기존 commerce의 local/test `ddl-auto: create`를 무심코 재사용하지 않도록 검토한다.
- 프리셋 목록·세부 조건·생성 요청의 테스트 옵션 계약과 commerce에서 옵션을 전달할 경계.
- DB 주기 조회의 간격/처리 범위·세부 결과 전이·callback 발송 방식과 미완료 거래에 적용할 설정.

독립 실행·DB 저장·전용 스키마·요청 프리셋/세부 조건·실효 조건 고정 필드 저장·자동 완료/응답 지연 분리·DB 예정 거래 주기 조회·보존용 실행 프로필과 명시 초기화 방향을 확정했다.
나머지 세부 구현은 아직 결정하지 않았다.
이 문서는 기능 구현·테스트 통과를 의미하지 않는다.
