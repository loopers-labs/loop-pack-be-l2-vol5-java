# 복구 작업 실행 권한 확보

현재의 실행 ID 인계·진행 갱신 조건과 보호 범위는 [멱등성과 동시성 제어 안내](../../resilience/idempotency-and-concurrency.md)에서 설명한다. 아래의 구현 전·미정 표현은 당시 설계 논의의 기록이다.

[설계 질문 목록](total_trade_off.md) · [pay 복구 작업 결정](06-recovery-progress-storage.md) · [조회 횟수 기록 결정](../../r03-payment-resilience/trade_off/07-retry-attempt-accounting.md) · [파사드/TX 결정](../../r02-pg-order-payment/trade_off/01-facade-transaction-boundary.md)

상태: **C·수동 실행 ID 교체 채택·기존 A 철회·구현 전**. 수동 인계 방향은 후속 확정했으며 정확한 필드·상태/응답·갱신 조건식은 미정이다. 자동 lease는 도입하지 않는다.

## 사용자 결정

2026-10-21 처음에는 짧은 비관적 행 잠금 A를 선택했지만, 후속 문답에서 명시적인 비관적 잠금 대신 멱등성 키·조건부 상태 갱신·실행 식별자를 사용하는 C로 변경했다.
멱등성 키와 DB 유일 제약은 중복 생성, 조건부 갱신은 실행 권한 경쟁, 실행 식별자는 늦은 실행의 진행 변경을 제어한다.
자동 만료·회수는 보류하고 장애 중단은 담당자 수동 대사로 처리하는 기존 결정을 유지한다.
변경 범위는 복구 작업 실행 권한이다. 주문/상품 재고의 기존 동시성 제어와 공통 결과 반영 TX의 한 번 적용 보장을 일괄 제거하지 않는다.

## 판단할 문제

자동 재확인의 중복 시작과 운영 담당자 수동 대사 등이 같은 pay 작업에 경합할 수 있다.
단순히 진행 상태를 읽고 각각 @Retryable을 시작하면 같은 작업의 조회 예산을 중복으로 소비할 수 있다.
DB에서 실행 권한을 확보하는 경계와 조회 직전 횟수 기록의 원자성을 설계해야 한다.
이 문서는 작업 실행 권한 확보 방식을 비교하며, 결제 생성의 발송 권한이나 공통 결과 반영의 전체 잠금 순서를 함께 확정하지 않는다.

## C. 멱등성 키 + 조건부 상태 갱신 + 실행 식별자 · 채택

- 동일한 논리 요청/작업의 중복 생성은 멱등성 키·DB 제약으로 보호한다. 결제 시도 키는 후속 결정으로 전역 유일하며 작업 관계의 구체적인 제약은 상세 설계 대상이다.
- 상태를 읽고 무조건 save하는 경로만으로 실행 권한을 판단하지 않는다. DB에서 예상 상태일 때만 실행 상태와 새 실행 식별자를 함께 바꾼다.
- 갱신 행 수 1이면 해당 실행이 권한을 획득한 것이며 commit 뒤 PG 조회를 진행한다. 0이면 현재 상태를 다시 확인하고 중복 실행하지 않는다.
- 이후 진행 갱신에도 현재 실행 식별자가 일치하는 조건을 둔다. 같은 RUNNING 상태가 다시 나타나도 이전 실행이 새 진행을 덮어쓰지 못하게 한다.
- 각 조회 직전 사용 횟수도 실행 권한·예상 회차·남은 자동 예산 조건과 함께 원자적으로 소비하고 commit한다. 정확한 조건식/필드는 상세 설계에서 정한다.
- 명시적인 SELECT FOR UPDATE/PESSIMISTIC_WRITE를 작업 실행 권한 확보의 필수 단계로 두지 않는다. DB UPDATE 자체의 쓰기 잠금·경합까지 없어진다는 뜻은 아니다.
- PG HTTP·재시도 대기는 DB TX 밖에 둔다. 키가 같다는 이유로 기존 PG 생성 POST를 다시 보내지 않는다.
- 실제 구현은 JPA 쓰기 규칙 안에서 설계한다. 조건부 bulk 갱신과 관리 중인 Entity의 정합성·flush/clear·전이 검증 책임은 별도 검토하며 검사 규칙을 완화하지 않는다.

### 원리 설명용 예시

아래 이름과 상태값은 설명용이며 실제 schema/enum은 아직 확정하지 않았다.

```sql
UPDATE payment_recovery_task
SET status = 'RUNNING', execution_id = :newExecutionId
WHERE id = :taskId AND status = 'READY';
```

동시 요청 중 상태 조건을 만족해 갱신·commit한 실행만 진행한다. 작업 재처리 이후의 변경은 execution_id까지 확인해야 한다.
이 예시는 최초 작업 획득의 원리만 보여준다. 후속 [최소 보완 결정](10-learning-scope-completion.md)으로 수동 대사는 미완료 작업의 기존 실행 ID·상태를 조건으로 새 실행 ID를 기록하고 옛 실행의 진행 갱신을 차단한다. 중단 RUNNING도 인계할 수 있어야 한다. 정확한 허용 상태·쿼리·응답은 미정이다.

이득은 별도 잠금 조회 없이 DB의 조건부 쓰기로 승자를 결정할 수 있다는 점이다.
비용은 갱신 결과 확인·실행 식별자 조건·상태 재사용·영속성 컨텍스트 정합성 처리가 필요하다는 점이다.

## A. 짧은 비관적 행 잠금으로 확인·점유 · 이전 선택·철회

- 짧은 TX에서 복구 작업 행을 잠그고, 실행 가능 여부·기존 실행·종결/수동 상태를 확인한다.
- 실행 권한 정보를 저장하고 commit해 행 잠금을 해제한 뒤 조회를 진행한다.
- 다음 실행은 같은 행의 최신 상태를 확인해 이미 유효한 실행이 있으면 중복 시작하지 않는다.
- 이득: 확인과 변경이 순서대로 진행돼 흐름을 추적하기 쉽다. 현재 주문·상품 저장의 비관적 잠금 관례와 연결된다.
- 비용: 경쟁자가 TX 종료까지 기다릴 수 있다. 여러 모델을 잠글 때 일관된 잠금 순서와 짧은 TX가 필요하다.
- PG HTTP와 1/3/10초 재조회 대기 동안 DB 행 잠금을 유지하지 않는다.

```text
작업 행 잠금
→ 실행 가능 여부 확인
→ 실행 권한 기록
→ commit·잠금 해제
→ 권한을 얻은 실행이 조회 진행
```

## B. version 기반 낙관적 갱신으로 점유 · 미채택

- 미리 행 잠금을 요청하지 않고 작업 상태와 version을 읽는다.
- 실행 가능한 상태이고 읽은 version이 여전히 일치할 때만 점유 갱신이 성공하도록 한다.
- 경쟁 갱신이 충돌하면 해당 실행은 중복 작업을 시작하지 않고 저장된 진행을 확인한다.
- 이득: 읽을 때부터 비관적 잠금을 잡지 않고 저장 시점에 충돌을 판단할 수 있다.
- 비용: version/갱신 조건과 충돌 처리 경로가 추가된다. 경쟁이 많으면 충돌이 반복될 수 있다. 실제 쓰기의 DB 잠금까지 없어지는 것은 아니다.
- 실제 구현은 기존 JPA 쓰기 규칙을 유지하며 임의 JDBC 경로나 검사 완화를 도입하지 않는다.

## 유지하는 보호 범위

- TX commit 뒤 HTTP 이전까지도 실행 권한을 식별할 DB 기록이 필요하다. 최초 상태 변경 성공만으로 늦은 실행의 이후 갱신까지 보호했다고 판단하지 않는다.
- 프로세스 종료 후 자동 만료/회수는 도입하지 않는다. 수동 인계는 실행 ID 조건부 교체로 처리한다. 일반 save가 최신 ID/회차/진행을 옛 객체 값으로 덮어쓰지 않게 하며 정확한 조건식·JPA 정합성 처리는 후속 설계한다.
- 실행 권한 확보와 각 조회 회차 소비의 연결 방식은 추가로 정한다. 모든 재조회 예산을 작업 시작 시 한 번에 소비하지 않는다.
- 각 조회 직전에 남은 예산·종결/수동 상태·실행 권한을 확인하고 사용 횟수를 commit한다. 경쟁에서 진 실행이 같은 회차를 소비하지 않도록 한다.
- 자동 작업 점유와 callback/수동 대사의 검증된 결과 반영은 서로 다른 책임이다. 공통 결과 반영 TX가 주문·시도·작업·재고 기록을 보호해야 한다.
- 유효한 종결 결과 반영 후 남은 자동 조회가 상태를 되돌리지 않도록 한다. worker 실행 권한만으로 재고 복구의 멱등성을 보장했다고 기록하지 않는다.
- 어느 안도 PG create 재시도를 허용하지 않는다. 일반적인 분산 락 라이브러리·Redis 도입은 이번 비교에 포함하지 않는다.

## 선택 이유와 남은 질문

이전에는 기존 비관적 잠금 관례 때문에 A를 선택했지만, 사용자 결정으로 C의 원자적 조건부 상태 변경과 실행 식별자 검증을 채택했다.
시도 키의 전역 유일성·수동 실행 ID 교체 방향은 후속 확정했다. 정확한 점유 단위·작업 관계 제약·실행 식별자 형식·허용 인계 상태/응답·조건부 갱신의 영속성 처리는 후속 설계에서 정한다.
[자동 만료·회수 방식](09-recovery-lease.md)은 사용자 요청으로 보류했다. 현재 장애 복구는 [운영 담당자 수동 대사](../../r02-pg-order-payment/trade_off/06-interrupted-payment-reconcile.md)를 따른다.
다음은 [멱등성 키의 유일 범위와 요청 계약](02-idempotency-request-contract.md)을 논의한다.
이 문서와 다른 준비 문서는 구현·테스트 완료를 뜻하지 않는다.
