# 멱등성 키의 유일 범위·동일 요청 계약

현재 구현을 처음 읽는 개발자는 [멱등성과 동시성 제어 안내](../../resilience/idempotency-and-concurrency.md)를 먼저 읽는다. 아래의 구현 전·미정 표현은 당시 설계 논의의 기록이다.

[설계 질문 목록](total_trade_off.md) · [요구사항 G02/G03](../requirement.md) · [실행 권한 결정](08-recovery-claim-coordination.md)

상태: **전역 유일 A·조건 비교 C·카드 제외 F·실효 조건 고정 저장·UUID 채택·구현 전**. 표준 UUID 입력·소문자 36자 저장으로 구체화했다. 정확한 옵션 필드/기본값은 [구현 계획](../plan.md)을 따른다. 키 보존 기간 정책은 별도 구현하지 않는다.

## 먼저 구분할 식별자

- 결제 시도 키: 같은 고객 요청의 재전송을 식별한다. PG가 중복 제거해 주는 키는 아니다.
- 내부 시도 ID/주문 ID: 주문당 한 결제 시도 관계를 보호한다.
- 실행 식별자: 자동/수동 처리의 특정 실행을 구분하고 늦은 진행 갱신을 막는다. 결제 시도 키를 대신하지 않는다.
- PG 주문 ID/거래 키: 외부 거래를 조회·검증하는 식별자다.

주문당 한 시도와 멱등성 키의 유일 범위는 각각 DB에서 보호한다.
같은 주문에 다른 키가 들어와도 두 번째 PG 시도를 만들지 않는 기존 조건은 두 안 모두 유지한다.

## 판단할 문제 · 멱등성 키를 어느 범위에서 유일하게 관리할지

원문은 같은 키의 다른 주문·금액·요청을 충돌로 규정한다. 2026-10-21 사용자는 이를 전체 결제 시도에서 보호하는 A를 선택했다.
B는 비교한 대안이며 채택하지 않았다. 첨부 원문은 변경하지 않는다.

## A. 전체 결제 시도에서 키 유일 · 채택

- 같은 키는 전체 결제 시도 중 하나에만 연결한다.
- 다른 주문에 같은 키가 들어오면 충돌이며 고객이 달라도 재사용하지 않는다.
- 이득: 키 하나의 의미가 명확하고 원문의 같은 키/다른 주문 충돌 규칙에 직접 대응한다. 키로 시도를 찾는 경로가 단순하다.
- 비용: 고객 간 우연한 키 재사용도 충돌한다. 클라이언트가 충돌 가능성이 낮은 키를 생성해야 한다. 후속 선택으로 표준 UUID 형식을 사용한다.

## B. 고객 + 키 조합으로 유일 · 미선택

- 같은 고객 안에서 같은 키는 한 시도에만 연결하고 다른 고객의 같은 문자열은 별도로 취급한다.
- 이득: 고객별 키 재사용이 서로 영향을 주지 않는다.
- 비용: 조회·검증에 고객 범위가 함께 필요하다. 원문의 같은 키/다른 주문 규칙에 고객별 범위를 추가하는 계약 설명이 필요하다.
- 여기서 고객 범위를 논의하는 것이 인증/인가 구현을 확정하는 것은 아니다. 저장된 주문 사용자와 접근 정책의 연결은 R02에서 별도로 해소한다.

## 예시

| 요청 | A | B |
|---|---|---|
| 고객 A 주문 1에 키 K 최초 사용 | 생성 가능 | 생성 가능 |
| 고객 A 주문 2에 키 K 사용 | 충돌 | 충돌 |
| 고객 B 주문 3에 같은 문자열 K 사용 | 충돌 | 다른 키 공간으로 취급 |
| 주문 1에 새 키 L 사용 | 두 번째 시도 금지 | 두 번째 시도 금지 |

키가 충돌해도 다른 고객의 주문/결제 정보를 반환하지 않는다. 접근 검증·오류 우선순위의 상세는 미정이다.
전역 시도 키 유일 제약과 주문당 한 시도 제약을 각각 둔다. 키는 정규화한 소문자 UUID 36자로 비교한다. 자동 만료/삭제 기능은 이번 범위에 추가하지 않는다.
후속 사용자 선택은 표준 8-4-4-4-12 UUID다. 입력 공백은 거절하고 대문자는 소문자 36자로 정규화해 저장/비교한다. 위 미정 비교 기록보다 이 결정을 우선한다. 요청별 테스트 옵션의 생략은 NORMAL_SUCCESS로 해석하므로 최초 사용자 지정 조건과 달라지면 충돌이며 새 조건으로 기존 거래를 변경하지 않는다.

## PG 테스트 조건의 동일 요청 비교 · C 채택

상태: **2026-10-21 사용자 선택으로 C 확정·구현 전**. 주문·금액 불일치는 충돌이며 카드 입력은 아래 F 결정에 따라 비교에서 제외한다. 아래는 사용자가 추가한 학습용 옵션에 적용할 계약이다.

같은 주문과 키로 처음에는 '응답 유실 후 성공', 다음에는 '정상 실패'를 요청하는 예를 비교한다.

| 대안 | 재요청 처리 | 이득 | 비용 |
|---|---|---|---|
| C. 실제 적용할 테스트 조건까지 비교 · 채택 | 조건이 다르면 충돌. 처음 조건은 유지 | 바뀐 실험 요청을 발견하고 실행 조건이 명확해짐 | 프리셋과 덮어쓴 값을 해석한 실제 조건의 비교·보존 기준이 필요 |
| D. 테스트 조건은 비교에서 제외 · 미선택 | 바뀐 조건을 무시하고 처음 조건에 따른 기존 상태 반환 | 클라이언트가 테스트 옵션을 다르게 재전송해도 기존 결과 조회 가능 | 새 조건이 적용됐다고 오해할 수 있어 최초 조건 고정 계약을 명시해야 함 |

C는 프리셋 이름이나 JSON 필드 순서 자체가 아니라 프리셋에 세부 조건을 적용한 실제 조건이 같은지를 기준으로 한다. 후속 [최소 보완 결정](10-learning-scope-completion.md)에 따라 최초 적용 조건을 고정 필드로 저장·복원·비교한다. 기본값을 채워 비교하므로 생략/명시가 같으면 일치한다. 학습 중 기본값은 고정하며 실행 중 프리셋 편집·버전 관리 시스템은 도입하지 않는다. 정확한 필드/허용값·시간 기본값·조건 입력 경계는 미정이다.
동일한 실제 조건이면 기존 시도의 상태를 반환하고, 실제 조건이 다르면 충돌로 거절한다. 두 경우 모두 추가 create·재고 차감 없이 최초 거래와 조건을 유지한다.
두 대안 모두 재요청으로 기존 PG 거래의 테스트 조건을 변경하거나 PG create를 추가 호출하지 않는다. 새 실험은 새 주문과 새 키로 시작한다.

## 카드 입력은 요청 비교에서 제외 · F 채택

상태: **2026-10-21 사용자 요청으로 학습 범위를 단순화·F 채택·구현 전**. 사용자는 카드 변경 비교까지 다루지 않고 같은 주문의 중복 결제 방지에 집중하기로 했다.

- 카드 종류/번호는 재요청의 동일성 비교에서 제외한다. 카드 원문과 카드 기반 HMAC/해시 등 비교값을 저장하지 않으며 관련 비밀키 관리도 도입하지 않는다.
- 같은 주문·키이고 저장된 결제 금액·실제 테스트 조건이 일치하면 카드 입력이 달라도 기존 시도의 상태를 반환한다. 재요청 카드로 기존 결제를 변경하거나 PG create를 추가 호출하지 않는다.
- 카드 입력의 형식·허용 합성 값 검증과 카드 번호 비저장/로그 금지는 유지한다. 검증과 기존 시도 조회의 정확한 순서·오류 우선순위는 상세 설계에서 정한다.
- 전역 시도 키 유일성·주문당 한 시도·서버가 저장된 주문에서 금액 결정·테스트 조건 불일치 충돌은 유지한다. 이번 단순화는 멱등성 키를 없애거나 PG 테스트 조건 비교 결정을 철회하는 것이 아니다.
- 원문의 '같은 키의 다른 요청은 충돌'에서 카드 입력 변경은 제외하는 사용자 승인 범위 조정이다. 첨부 원문은 변경하지 않는다.

비교했던 E(HMAC 요청 비교값 저장)는 채택하지 않았다. 카드 변경 판별·비교값 저장·키 관리 설계는 이번 학습 범위에 포함하지 않는다.

## 현재 계약의 대표 검증 시나리오 · 구현 전

| 재요청 | 기대 동작 |
|---|---|
| 같은 주문·키·금액·실제 테스트 조건, 정상 형식의 다른 카드 입력 | 기존 상태 반환, 추가 create/재고 차감 없음 |
| 같은 주문·키, 실제 테스트 조건 변경 | 충돌, 최초 조건 유지, 추가 create/재고 차감 없음 |
| 다른 주문에 같은 키 사용 | 고객이 달라도 충돌, 다른 주문/결제 정보 노출 없음 |
| 같은 주문에 새 키 사용 | 두 번째 시도·create·재고 차감 금지. 정확한 응답은 후속 설계에서 정함 |

위 표는 검증할 계약이며 테스트 실행이나 구현 완료 기록이 아니다.
