# R01 설계 질문·결정 목록

상태: **R01 로컬 구현·검증 완료**. [실제 결과](../result.md)를 확인한다. 확정한 제약과 미정 질문을 구분한다. 각 주제를 논의한 뒤 번호별 설계 문서를 추가하고 이 목록에 연결한다.
후속 [구현 계획](../plan.md)은 세 관점 리뷰·사용자 승인 보완·재검토를 마쳤다. UUID·요청별 옵션과 실행/모델 기본값을 구체화했고 [상태별 문서](../../states/total.md)를 연결했다. 최신 사용자 요청으로 기능 구현만 리뷰하고 테스트는 핵심 최소 사례로 제한한다. 과거 미정 목록의 구체값은 최신 계획을 따른다.

2026-10-21 [요구사항 분석](../requirement.md)에 G01~G08의 빈틈·확인 사항을 정리했다.
사용자 추가 조건으로 독립 실행하는 테스트 PG와 기존 MySQL의 PG 전용 스키마에 DB 저장하는 구성이 확정됐다. 메모리 저장 선택은 철회됐다.
00에서 테스트 PG의 학습용 실행·입력 방향을 정리했다. PG 내부 작업은 이전 보류를 끝내고 후속 10에서 DB 예정 거래 주기 조회로 확정했다.
01에서 우리 서비스의 결제 시도를 pay의 독립 모델로 선택했다. 상태 설계에 앞서
[자동 재확인·수동 전환 정책](../../r03-payment-resilience/trade_off/01-reconciliation-retry-policy.md)을 논의한다.
최초 조회+추가 3회·1/3/10초·지터 ±20%와 실패/수동 전환 기준을 확정했다.
[재확인 저장·실행 방식](../../r03-payment-resilience/trade_off/06-reconciliation-execution.md)은 @Retryable + DB 진행 기록을 유지한다. 재시작 자동 재개는 후속 결정으로 운영 담당자 수동 대사로 변경했다.
[결제 결과·재확인 진행 상태 표현](05-payment-attempt-state.md)은 결과와 복구 진행을 나누는 B로 확정했다.
[재시도 횟수 소비 시점](../../r03-payment-resilience/trade_off/07-retry-attempt-accounting.md)은 조회 직전 DB 기록/commit으로 확정했다.
[복구 진행 기록 저장 경계](06-recovery-progress-storage.md)는 별도 pay 복구 작업 모델로 분리하는 B로 확정했다.
[재고 차감·복구 기록](07-stock-adjustment-boundary.md)은 mall의 별도 모델·확정 실패 반영 TX 안의 복구로 확정했다.
R02의 [파사드·트랜잭션 경계](../../r02-pg-order-payment/trade_off/01-facade-transaction-boundary.md)는 조율 파사드와 별도 준비/공통 결과 반영 TX 컴포넌트를 두는 A로 확정했다.
[복구 작업 실행 권한 확보](08-recovery-claim-coordination.md)는 기존 A를 변경해 멱등성 키 + 조건부 상태 갱신 + 실행 식별자의 C로 확정했다.
[실행 권한 자동 만료·회수](09-recovery-lease.md)는 사용자 요청으로 보류했다.
장애 중단 작업은 R02의 [미완료 작업 조회·운영 담당자 수동 대사](../../r02-pg-order-payment/trade_off/06-interrupted-payment-reconcile.md)로 처리하는 방향을 채택했다.
[멱등성 키·동일 요청 계약](02-idempotency-request-contract.md)은 전역 유일 A·실제 테스트 조건 비교 C·카드 입력 비교 제외 F로 확정했다. 카드 기반 HMAC/해시 저장·비밀키 관리는 도입하지 않는다. 후속 10에서 실효 조건 고정 필드 저장·보존용 프로필/명시 초기화 방향을 확정했다. 키 형식·정확한 필드/기본값·기존 POINT 호환 절차·프로필 설정 상세는 후속 설계 대상이다.
사용자 요청으로 [03 HTTP 호출·시간 제한](03-http-client-settings.md)과 [04 응답 해석·최소 HTTP 검증](04-adapter-fixture.md)을 함께 논의하고 모두 A로 확정했다. 동기 RestClient 직접 호출·전송 설정, 구분된 관찰 결과 반환·실제 PG와 작은 테스트용 HTTP 서버의 검증 분담을 채택했다. 상태/스키마 등 상세 설계까지 완료됐다는 뜻은 아니다.
서브에이전트의 비즈니스·사용자 경험·기술 검토 후 [10 최소 보완](10-learning-scope-completion.md)을 사용자와 확정했다. 검증 결과 먼저 commit/업무 TX 분리·조건 고정 필드 저장·PG 예정 거래 주기 조회·보존용 프로필/명시 초기화·수동 실행 ID 교체·commerce 지터/예약 정보 영속화 제외가 현재 기준이다.

## 확정한 제약

- 로컬에서 독립 실행하는 작은 테스트 PG를 직접 만들고 commerce가 실제 HTTP로 연결한다. 원문 경로·기본 필드를 유지하고 생성 요청에 학습용 옵션을 추가한다.
- PG 거래는 기존 MySQL의 PG 전용 스키마에 저장하며 PG 재시작 후에도 보존한다. 실제 카드·금전·외부 PG 계정은 사용하지 않는다.
- PG 결제 요청에 프리셋과 필요한 세부 테스트 조건을 포함한다. 별도 제어 API와 축별 직접 설정만 제공하는 안은 철회됐다.
- PG는 설정한 처리 시간에 따라 결과를 자동 반영한다. 거래 처리 시간과 생성/조회 응답 지연은 독립적으로 제어한다.
- 생성 요청에 제공자 멱등 보장이 없다. 실제 HTTP timeout을 적용하고 create 자동 재시도를 차단한다.
- HTTP는 RestClient + Apache HttpClient 5를 명시하고 자동 retry/redirect를 끈다. 초기값은 연결 1초·연결 풀 대기 1초·응답 대기 2초이며 전체 호출의 절대 제한을 뜻하지 않는다.
- adapter는 검증한 관찰/확인 불가 사유를 결과값으로 구분해 반환한다. 실제 PG는 정상·지연·유실·DB 보존을, 테스트용 HTTP 서버는 불완전 응답 등을 검증한다. 재시도/회로 연결에서 결과값 분류가 필요하다.
- 내부 시도·외부 거래·주문을 구분하고, 주문당 한 시도·차감 처리 기록을 영속화한다.
- 결제 시도 키는 전체 결제 시도에서 전역 유일하다. 다른 고객의 같은 문자열도 다른 주문에 재사용할 수 없다. 주문당 한 시도 제약은 별도로 유지한다.
- 같은 주문·키의 재요청은 실제 적용할 PG 테스트 조건도 비교한다. 다르면 충돌이며 기존 조건을 변경하거나 추가 create/재고 차감을 하지 않는다.
- 카드 입력은 재요청 비교에서 제외한다. 주문·키·저장 금액·실제 테스트 조건이 같으면 기존 시도의 상태를 반환한다. 원문 요청 일치 규칙의 카드 비교 범위를 조정한 사용자 결정이며 카드 원문/비교값은 저장하지 않는다.
- 우리 서비스의 결제 시도는 pay의 독립 모델·저장소로 두고 orderId로 연결한다. OrderRecord는 주문 확정 기록으로 유지하고 application이 같은 DB TX에서 주문·시도·재고를 조율한다.
- 확인한 결제 결과와 복구 진행은 분리한다. 수동 전환·조회 실패가 검증한 결제 결과를 덮어쓰지 않는다. 정확한 상태값·허용 조합은 미정이다.
- 복구 진행·사용 횟수·현재 실행/최근 시각·오류는 별도 pay 복구 작업 모델·저장소에 둔다. commerce 지터/다음 실행 예약 정보는 영속화하지 않는다. 재고 차감·복구 기록은 mall의 별도 모델로 둔다.
- 검증한 결과/확정 거절 사실은 먼저 짧은 TX로 commit한다. 업무 반영은 다음 공통 TX에서 처리하고 실패해도 관찰을 보존한다. 저장된 종결 결과의 미반영은 PG 재조회 없이 재적용할 수 있다. 관찰 저장 전 종료는 미확인 한계가 남는다.
- 수동 대사는 실행 ID를 조건부 교체해 중단 RUNNING도 인계하고 옛 진행 save를 차단한다. PG 주기 조회·commerce 수동 대사의 실행 정책을 혼동하지 않는다.
- 확정 실패 반영 시 실제 재고 증가와 기록의 복구 완료를 같은 로컬 TX에서 commit한다. application 파사드가 Context 간 진행을 조율한다.
- 복구 작업 실행 권한은 멱등성 키·DB 제약과 원자적 조건부 상태 갱신·실행 식별자 검증으로 보호한다. 명시적 비관적 잠금 조회는 필수로 두지 않는다. 갱신 commit 뒤 PG HTTP를 수행한다.
- 과거 POINT 결제 사실을 보존하고 카드 번호는 저장·로그 출력하지 않는다.

@Retryable 사용 방향과 03/04의 HTTP 설정·관찰 반환/검증 분담은 확정했다. 구체적인 의존성 버전·테이블·클래스 이름·마이그레이션 방식은 지금 선택한 것으로 기록하지 않는다.
PG의 독립 실행·DB 저장·기존 MySQL의 PG 전용 스키마 분리는 사용자 확정 사항이며 다시 미정으로 취급하지 않는다.
설계가 정해지면 대안·선택·이유·비용·미해결 한계를 기록하고 계획에 반영한다.
