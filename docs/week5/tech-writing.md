# 나는 아무것도 모르기 때문에 아무것도 모릅니다

### 결제 결과를 "모른다"고 말할 수 있는 시스템

![나는 아무것도 모르기 때문에 아무것도 모릅니다](/assets/img/2026-10-23/be-payment-unknown-result-1.jpg)

> 포인트 결제를 외부 PG 결제로 바꾸면서 가장 오래 붙잡은 질문은 "PG의 결과를 우리는 언제 안다고 말할 수 있는가"였다. 실무에서 본 두 장면, 그 질문에 답하려고 만든 상태와 구조, 그리고 돌아보며 더 해 봤으면 좋았을 것을 적는다.

## 1. 우리는 안다고 착각했다

**장면 1. 사람이 알았던 누락.** 이전 회사는 PortOne과 Toss로 결제를 받았다. 결과는 PG가 보내 주는 웹훅으로 반영했다. 웹훅이 자주 빠지지는 않았지만 가끔 빠졌다. 누락은 정산하다가, 혹은 우연히 화면을 보다가 알았다. 그러면 PortOne 관리자 콘솔에서 웹훅 재전송을 눌러 맞췄다.

돌아보면 **누락은 시스템이 아닌 사람이 알았다.** 사람이 보기 전까지 시스템은 자기가 결과를 모른다는 사실조차 몰랐다.

**장면 2. 모름을 실패로 단정한 코드.** 지금 일하는 곳의 정기결제 코드를 읽다가 이런 흐름을 발견했다.

1. 빌링키로 PG에 결제를 요청한다. 응답을 60초 기다린다.
2. 응답이 오지 않으면 catch에서 `{ success: false }`를 돌려준다. PG에서는 이미 승인됐을 수 있다.
3. 결제 기록은 실패, 청구서는 미결제로 남는다. 다음 재결제 배치나 사용자의 "다시 결제" 버튼이 다시 보낸다.
4. PG 주문번호는 `청구서_시도번호_현재시각`이라 매번 새로 만들어진다. PG도 같은 결제인지 알 수 없다.

같은 청구서를 동시에 결제하는 경우는 원자적 락으로 잘 막혀 있었다. **동시성은 막았지만 "모름"은 막지 못했다.** 락이 지키는 것은 동시에 들어오는 요청이고, timeout 뒤의 모름은 락의 바깥에 있다.

장면 1은 **모르는 걸 몰랐고**, 장면 2는 **모르는 걸 실패로 단정했다.** 둘 다 결과를 안다고 착각했다. 그래서 PG 결제를 새로 만들면서 질문을 이렇게 잡았다.

> 시스템이 스스로 "모른다"고 말하려면 무엇이 필요한가?

## 2. 결과는 둘이 아니라 셋이다

이번에 붙인 PG는 로컬 테스트용 PG다. 실제 PG 상당수는 멱등 키나 주문번호 중복 거절을 제공하지만, 이 PG는 일부러 둘 다 없다. 같은 주문번호로 다시 보내면 거래가 하나 더 생긴다. 가장 불리한 조건을 가정한 셈인데, 1장 장면 2도 사실상 같은 조건이다. 주문번호가 매번 바뀌니 PG의 중복 방지가 작동하지 않는다.

멱등 키가 있다고 해서 문제가 사라지지도 않는다. 다시 보내도 안전해질 뿐, timeout 직후에 결과를 모른다는 사실은 그대로다. 그래서 이 조건에서 PG 호출 하나의 결과는 성공·실패 둘로 나뉘지 않는다.

| 우리가 아는 것 | 예 | 해도 되는 일 |
|---|---|---|
| **안 보냈다** (확실) | 연결 실패, 연결 timeout, 회로 OPEN, 발송 풀 가득 참 | 실패로 닫고 재고를 돌려준다 |
| **보냈는데 모른다** | 응답 timeout, 5xx, 응답 본문이 깨짐 | 다시 보내지 않는다. 조회로만 확정한다 |
| **안다** | PG가 거절·처리 중·성공을 답함, 조회로 확인함 | 그 결과를 반영한다 |

가운데 줄이 핵심이다. 응답 timeout은 "실패"가 아니라 "모름"이다. 그래서 이 구분을 결제 상태에 그대로 옮겼다.

```text
REQUESTED  저장됨. 아직 아무도 보내지 않았다          → 안 보냈다
SENDING    보낼 권한을 얻었다. 실제로 갔는지는 모른다   → 보냈을 수 있다
PENDING    PG가 거래를 만들고 처리 중이라고 답했다      → 거래가 있다는 걸 안다
UNKNOWN    보냈을 수 있으나 결과를 모른다              → 모른다
SUCCESS / FAILED                                     → 안다 (덮어쓰지 않는다)
```

상태가 여섯 개다. 처음에는 "결제 하나에 상태가 이렇게 많아야 하나" 싶었다. 하지만 각 상태는 서로 다른 질문에 답한다. **"다시 보내도 되는가"에 REQUESTED는 예, SENDING과 UNKNOWN은 아니오라고 답한다.** 이 답이 다르면 상태도 달라야 한다.

## 3. 전체 그림

세부로 들어가기 전에 전체 구조부터 본다.

```text
[고객] ── POST /api/v1/orders/{id}/confirm  (Idempotency-Key 헤더)
   │
   ▼
┌─ TX A: 한 트랜잭션 ─────────────────────────────
│  주문 잠금 → 재고 선점 (5 → 3)
│  payments        : REQUESTED
│  payment_outbox  : PENDING      ← "보내야 한다"는 사실
└─ commit ────────────────────────────────────────
   │ commit 직후 이벤트
   ▼
발송 풀 (스레드 50, 대기열 0)
   │  가득 차면 → 보내지 않고 FAILED(NOT_SENT), 재고 반환, 200 응답
   │  고객에게는 여기까지 오면 202 "접수했다"
   ▼
장부 claim (PENDING → CLAIMED)  +  결제 REQUESTED → SENDING
   │
   ▼
PG 결제 생성 요청 1회 (재시도 없음) ──────────▶ [PG]
   │                                              │
   │ 응답 / timeout / 연결 실패                    │ callback ("확인해 보라")
   ▼                                              ▼
TX B: 결과 반영 ◀──── PG 조회 ◀──── callback 수신 · reconcile
      (결제 행 비관적 락 + 종결이면 무시)

스케줄러 셋
  정리       60초마다  30초 넘은 장부 PENDING → FAILED(NOT_SENT), 재고 반환
                       30초 넘은 장부 CLAIMED → UNKNOWN (보냈을 수 있음)
  reconcile   5초마다  PENDING·UNKNOWN 조회, 간격 5s → 10s → 30s → 1m → 5m
  만료       60초마다  30분 넘게 모르면 FAILED, 재고 반환
```

결제 하나의 상태는 이렇게 흐른다.

```text
REQUESTED ─┬─ 발송 풀 가득 참 / 30초 넘게 아무도 안 가져감 ──▶ FAILED (NOT_SENT)
           │
           └─ 장부 claim ──▶ SENDING
                               ├─ 연결 실패 · 생성 회로 OPEN ──▶ FAILED (NOT_SENT)
                               ├─ PG 거절 ─────────────────────▶ FAILED
                               ├─ 거래 생성 응답 ───────────────▶ PENDING
                               └─ 응답 timeout · 5xx ───────────▶ UNKNOWN
                                  · 30초 넘게 결과 없음

PENDING ─┬─ callback · 조회로 확인 ──▶ SUCCESS / FAILED
         └─ 30분 넘게 모름 ──────────▶ FAILED (만료)

UNKNOWN ─┬─ 조회로 거래를 찾음 ──▶ PENDING / SUCCESS / FAILED
         └─ 30분 넘게 모름 ──────▶ FAILED (만료)

SUCCESS · FAILED 는 덮어쓰지 않는다.
```

FAILED로 가는 화살표는 많지만, **"보냈을 수 있는" SENDING·UNKNOWN에서 FAILED로 바로 가는 길은 PG가 답한 경우와 30분 만료뿐**이다. 나머지 장은 이 그림의 각 부분을 설명한다.

## 4. 모르는 걸 잊지 않기: outbox, 그리고 relay를 달지 않은 선택

모른다고 말하려면 먼저 **"보내야 한다"는 사실을 잃지 않아야** 한다. 결제 확정 요청은 한 트랜잭션에서 주문을 잠그고, 재고를 선점하고(5→3), 결제 시도(REQUESTED)와 발송 장부 `payment_outbox`(PENDING)를 함께 저장한다. 서버가 commit 직후 죽어도 "보낼 결제가 있었다"는 사실은 DB에 남는다.

일반적인 Transactional Outbox는 여기에 relay를 붙인다. relay가 N초마다 장부를 폴링해 MQ로 발행하고, 실패하면 다시 발행한다. 최소 1회 전달이다. 이번에는 relay를 달지 않았다.

- **결제 생성은 1회를 넘으면 안 된다.** 멱등 키 없는 PG에 최소 1회 전달은 곧 이중 결제 가능성이다. 장부를 "다시 보낼 목록"이 아니라 **"보냈는지의 증거"**로 썼다.
- **1초 폴링은 대부분 빈 조회다.** 평소에는 commit 직후 수 ms 안에 발송된다. 폴링 주기를 정할 근거도 없었다.

그래서 흐름을 이렇게 잡았다.

1. commit 직후 이벤트로 발송 풀(스레드 50개, 대기열 0)에 넘긴다. 풀이 가득 차면 늦게 보내지 않고, 그 자리에서 실패(NOT_SENT)로 닫고 재고를 돌려준다.
2. 발송 스레드는 장부를 조건부 UPDATE(`PENDING → CLAIMED`)로 가져간 쪽만 PG를 부른다. 결제도 REQUESTED → SENDING이 된다.
3. 60초 주기 정리 스케줄러가 30초 넘게 남은 행만 본다.
   - 장부가 아직 **PENDING**이면 아무도 보내지 않은 것이 확실하다. 정리도 조건부 UPDATE(`PENDING → CLOSED`)라 발송과 동시에 이길 수 없다. 실패로 닫고 재고를 돌려준다.
   - 장부가 **CLAIMED**인데 결과가 없으면 보냈을 수 있다. 실패로 닫지 않고 UNKNOWN으로 넘긴다.

장부의 `PENDING`과 `CLAIMED`가 **"안 보낸 것이 확실한 상태"와 "보냈을 수 있는 상태"를 가르는 선**이다. 오래 남은 행은 `(status, created_at)` 인덱스로 찾는다.

## 5. 모를 때 하지 않는 것

모름을 상태로 만들고 나니, 오히려 **하지 말아야 할 일**이 분명해졌다.

- **다시 보내지 않는다.** PG 생성 호출은 코드에 한 곳뿐이고 재시도가 없다. 재시도(최대 3회, 100 ms부터 두 배씩, 지터)는 다시 물어도 부작용이 없는 **조회**에만 건다.
- **재고를 바로 돌려주지 않는다.** UNKNOWN은 PG에서 승인됐을 수 있다. 재고를 풀었는데 결제가 성공하면 팔 수 없는 상품을 판 셈이다. 선점은 결과가 확정될 때까지 유지한다.
- **회로 차단이 결과를 정하지 않는다.** 생성 회로가 OPEN이면 요청이 PG에 가지 않았으니 "안 보냈다"로 닫는다. 조회 회로가 OPEN이면 "이번에 못 물어봤다"는 기록만 남기고 상태는 그대로 둔다. 같은 회로 OPEN이라도 **무엇을 아는지**가 달라서 처리가 다르다.
- **HTTP 수락을 결제 성공으로 말하지 않는다.** 확정 API는 결과를 아직 모르면 202로 "접수했다"까지만 답한다. 응답하는 시점에 이미 결과가 정해진 경우(발송 풀이 가득 차 보내지 못함, 같은 키로 다시 물었는데 이미 종결됨)만 200으로 답한다.

timeout도 같은 기준으로 나눴다. 연결 timeout(1초)은 요청이 PG에 닿지 않았다는 뜻이라 "안 보냈다"다. 응답 timeout(생성 3초, 조회 1초)은 "모른다"다. 생성은 다시 보낼 수 없으니 조금 더 기다리고, 조회는 다시 물으면 되니 짧게 끊는다.

## 6. 모르는 걸 알아내기

모른다고 말하는 것으로 끝나면 안 된다. 스스로 알아내야 한다.

1. **callback(웹훅)**: PG가 결과를 알려 주면 받는다. 다만 본문을 믿지 않고 **"확인해 보라"는 신호**로만 쓴다. 받으면 PG에 직접 조회해서 그 결과를 반영한다.
2. **reconcile(조회)**: 5초마다 UNKNOWN·PENDING 결제 중 확인할 때가 된 것을 조회한다. 확인 간격은 5초, 10초, 30초, 1분, 5분으로 늘린다. 거래 키가 없는 UNKNOWN은 우리가 정한 PG 주문 식별자로 거래를 찾는다.
3. **만료**: 30분이 지나도 결과를 모르면 실패로 닫고 재고를 돌려준다. 끝없이 재고를 묶어 둘 수는 없다.

callback과 조회가 같은 결과를 두 번 가져와도, 순서가 바뀌어 와도 한 번만 반영된다. 결과 반영은 결제 행을 비관적 락으로 잠그고, 이미 종결된 결제에는 `ALREADY_APPLIED`를 돌려줄 뿐 아무것도 바꾸지 않는다. 종결 뒤 반대 결과(만료로 닫았는데 PG는 승인)가 오면 덮어쓰지 않고 환불이 필요하다는 에러 로그를 남긴다.

테스트는 이 장면들을 그대로 재현한다.

- **S-4 응답 유실**: PG가 거래를 만든 뒤 응답만 timeout이 나면 결제는 UNKNOWN, 재고 선점은 유지, PG 생성은 **1번**이다. reconcile이 거래를 찾아 확정한다.
- **S-5 동시 확정**: 같은 Idempotency-Key로 10번 동시에 확정하면 모두 같은 시도를 돌려받는다. 서로 다른 키 10개면 1건만 접수되고 9건은 409다. 어느 쪽이든 결제 1행, PG 생성 1번, 재고 5→3이다.
- **S-8 재시작**: commit 뒤 발송 이벤트를 잃으면(장부 PENDING) 30초 뒤 정리가 실패로 닫고 재고를 5로 돌린다. PG 생성은 끝까지 0번이다. 발송 권한만 얻고 죽으면(SENDING·CLAIMED) UNKNOWN으로만 넘기고, 조회 결과가 0건이어도 실패로 닫거나 다시 보내지 않는다.

## 7. 돌아보며: 이것까지 했다면

만들고 나서 돌아보니, 이것까지 해 봤다면 더 좋았겠다 싶은 것들이 있다.

- **일일 대사까지 붙였다면.** 결과를 맞추는 장치는 보통 웹훅 → 조회 배치 → 일일 대사 3단계로 겹친다. 이번에는 2단계까지 만들었다. 30분 만료로 실패가 된 결제는 조회 대상에서 빠진다. 그 뒤 PG가 승인했는데 웹훅까지 잃으면, 그 사실은 다시 **사람이** 알게 된다. 하루 한 번 PG 거래 내역과 우리 결제를 맞춰 보는 배치가 있었다면 1장 장면 1의 마지막 칸까지 시스템이 채웠을 것이다.
- **relay + MQ를 직접 붙여 봤다면.** relay를 달지 않은 이유는 분명했지만, 붙였을 때와 비교해 보지는 못했다. 폴링 주기는 허용 지연에서 출발한다. 이벤트가 몇 초 늦어도 되는지가 주기의 상한이고, 한 번에 읽는 건수 × 주기가 처리량이다. 같은 장부 위에 relay를 붙여서 지연과 DB 부하를 재 봤다면 "왜 안 달았는가"를 숫자로 말할 수 있었을 것이다.
- **장부를 지표로 봤다면.** 장부에는 "아직 안 나간 결제"가 쌓인다. **미발송 건수와 가장 오래된 미발송 건의 나이**가 계속 늘면 무언가 막힌 것이다. 지금은 이 두 값을 보지 않는다. 대시보드 하나만 있었어도 "모른다"를 사람에게도 보여 줄 수 있었다.
- **부하 아래에서 값을 검증했다면.** timeout(연결 1초, 생성 응답 3초, 조회 1초), 회로 기준, 발송 풀 50은 "타임세일 오픈 직후 100 TPS, PG가 3초로 느려짐"을 가정해 계산으로 정했다. 사용자가 기다릴 수 있는 시간에서 거꾸로 계산하고, 풀 크기는 TPS × 평균 처리 시간으로 잡았다. 장애를 하나씩 만들어 값을 하나씩 바꿔 보는 부하 테스트까지 했다면 계산이 맞는지 확인할 수 있었을 것이다.
- **확정 뒤 취소까지 다뤘다면.** 관리자 취소처럼 종결 뒤 PG에서 바뀐 결과는 이번에 반영하지 않고 이상으로 기록만 했다. 실무에서 가장 자주 마주치는 경우라 다음에 꼭 이어 보고 싶다.

처음 질문으로 돌아가면, 이번에 만든 것은 결과를 다 아는 시스템이 아니다. **모를 때 모른다고 말하고, 모르는 동안 아무것도 망치지 않고, 스스로 알아내려는 시스템**이다. 그리고 그 시스템이 어디까지 알고 어디부터 모르는지를 이제는 말할 수 있다.

더 견고한 시스템을 만들기 위해 오늘도 성장 중입니다.
