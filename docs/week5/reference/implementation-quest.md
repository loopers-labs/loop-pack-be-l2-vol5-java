## 💻 Implementation Quest

> **포인트 결제를 테스트 PG로 교체하고, 외부 결과를 기존 주문·재고에 한 번만 반영합니다.**
> 

4주차까지의 상품·주문·관리자 API, DB 트랜잭션·동시성 제어와 조회를 유지합니다. 이번 변경은 **결제 경계의 교체**입니다. 실제 카드·금전·외부 PG 계정은 사용하지 않으며 로컬 테스트 PG 계약으로 구현합니다.

### 📐 1. 교체 범위와 상태 설계

| 대상 | 이번 변경 | 유지할 것 |
| --- | --- | --- |

기존 DRAFT도 아직 결제하지 않았으므로 교체 후 시작하는 결제는 PG를 사용합니다. 이미 결제된 주문을 다시 처리하지 않습니다. 이번 범위는 **주문당 한 결제 시도**이며, 실패 후 새 결제 시도·환불·정산·사용자 취소·실제 카드 저장은 구현하지 않습니다.

설계 문서에 로컬 TX 전후, 외부 HTTP 호출, 결과 적용 경계를 표시합니다. PG 호출 동안 DB 트랜잭션·재고 잠금을 계속 보유하지 않습니다. AI에 응답 유실, 성공 뒤 내부 저장 실패, 중복 콜백의 반례를 물어보고 상태와 효과를 정한 뒤 구현합니다.

### 🔌 2. 로컬 테스트 PG 계약과 adapter

아래는 **이 실습에서 정의하는 로컬 HTTP 계약**입니다. 시작 저장소에 PG 앱이 제공된다는 뜻이 아닙니다. 테스트 내부 HTTP 서버 또는 작은 테스트 fixture로 구현하며, 별도의 PG 제품을 만들지 않습니다.

| 요청 | 계약 |
| --- | --- |
| `POST /api/v1/payments` | `orderId, cardType, cardNo, amount, callbackUrl` 입력. 거래를 생성하고 `transactionKey, orderId, amount, status` 반환 |
| `GET /api/v1/payments/{transactionKey}` | 거래 한 건의 위 필드 반환 |
| `GET /api/v1/payments?orderId={providerOrderId}` | 같은 주문의 거래 목록 반환. 빈 목록도 표현 |
| 공통 헤더 | 세 요청 모두 합성 제공자 계정 `X-USER-ID: 135135` |
| 외부 상태 | `PENDING, SUCCESS, FAILED`. 생성 수락과 최종 성공을 구분 |

`orderId`는 6자 이상 문자열, `amount`는 원화 정수입니다. 내부 주문 42를 `LP-ORD-0000000042`로 매핑했다면 생성과 조회에 동일하게 사용합니다. 테스트 PG는 **호출자 멱등 키를 받지 않으며 같은 orderId의 새 POST를 중복 제거한다고 가정하지 않습니다.**

- 공통 · 로컬 생성 요청과 처리 중 응답 예시
    
    ```json
    {
      "orderId": "LP-ORD-0000000042",
      "cardType": "TEST",
      "cardNo": "0000-0000-0000-0000",
      "amount": 7000,
      "callbackUrl": "http://127.0.0.1:8080/api/v1/payments/callback"
    }
    ```
    
    ```json
    {
      "transactionKey": "TEST-TX-0042",
      "orderId": "LP-ORD-0000000042",
      "amount": 7000,
      "status": "PENDING"
    }
    ```
    
    생성 수락 응답은 HTTP 202로 둡니다. 거래 조회는 HTTP 200, 주문 조회는 같은 거래 객체의 배열입니다. 존재하지 않는 transactionKey는 404입니다. 이 응답 규칙은 테스트 adapter와 fixture가 공유할 계약이며 실제 PG의 규격이라고 주장하지 않습니다.
    
- 공통 · 거래 생성 전 확정 거절과 UNKNOWN 구분
    
    로컬 fixture에서만 아래 거절을 정의합니다. 거래를 저장하거나 비동기 처리를 예약하기 **전에 종료하며, 나중에도 이 요청의 거래를 만들지 않는다**는 계약입니다.
    
    ```
    HTTP/1.1 422 Unprocessable Content
    Content-Type: application/json
    
    {"code":"TEST_PG_REJECTED_BEFORE_CREATE","orderId":"LP-ORD-0000000042","amount":7000,"transactionCreated":false}
    ```
    
    adapter는 고정한 로컬 PG의 생성 응답에서 **422 + 정확한 code + boolean false + 요청 orderId·amount 일치**를 모두 확인한 경우에만 `REJECTED_NO_EFFECT`로 매핑합니다. 이 내부 관찰은 결제 FAILED·예약 한 번 반환으로 연결하고, 거래가 없으므로 transactionKey를 꾸며 저장하지 않습니다.
    
    반대로 timeout, 본문 없는 422, 다른 오류 code의 4xx·5xx, 잘못된 JSON·식별·금액은 효과 0건의 증거가 아닙니다. 다른 확정 결과가 없는 해당 시도는 UNKNOWN·예약 유지로 두고 기존 거래 조회 경로를 사용합니다. 일반 조회 404·빈 목록도 이 생성 거절과 다릅니다.
    
    작은 HTTP 계약 테스트에서 위 응답은 **거래 0건·예약 반환 1회**, 거래 생성 뒤 응답 유실은 **거래 1건·UNKNOWN·예약 유지·create 추가 0회**로 대조합니다. 동일 거절의 중복 적용도 반환을 늘리지 않아야 합니다. 이 code와 상태 조합은 실습용 약속이며 실제 PG의 공통 규격이 아닙니다.
    

카드 값은 위와 같은 합성 값만 사용하고 DB·로그에 카드 번호를 남기지 않습니다. base URL·callback URL은 로컬 설정으로 고정하며 고객이 임의의 외부 주소를 주입하게 하지 않습니다. 외부의 고정 `X-USER-ID`는 내부 고객 인증을 대신하지 않습니다.

실제 adapter가 보내는 HTTP의 메서드·경로·헤더·JSON 타입·금액과 응답 매핑을 테스트합니다. query는 URI builder로 인코딩하고 `transactionKey` 조회를 연결합니다. 정상 형식 확인에는 무작위 지연·성공 확률을 넣지 않습니다.

### 💳 3. 기존 주문 확정에 PG 연결

| commerce API | 동작 |
| --- | --- |
| `POST /api/v1/orders/{orderId}/confirm` | 본인 DRAFT의 PG 시도 시작. `paymentAttemptKey`와 합성 카드 입력을 받고 금액은 저장된 주문에서 결정 |
| `GET /api/v1/orders/{orderId}` | 본인 주문·결제수단·시도 상태·최종 결과 조회. 새 결제 요청을 만들지 않음 |
| `POST /api/v1/orders/{orderId}/payment/reconcile` | 본인 미완료 시도의 기존 외부 거래 조회·결과 적용 |
| `POST /api/v1/payments/callback` | 로컬 PG 결과 알림을 받아 해당 거래를 권위 조회한 뒤 같은 결과 적용 경계 사용 |

대기·결과 미확인인 confirm/reconcile 응답은 HTTP 202와 주문·시도 상태 및 조회 경로를 반환합니다. 같은 PG 시도의 완료 결과는 HTTP 200으로 조회·반환할 수 있습니다. 소유권·잘못된 입력·상충하는 시도는 기존 오류 계약에 맞춰 구분합니다.

- 내부 시도 키·providerOrderId·외부 transactionKey의 역할을 나눠 DB에 보존합니다.
- 주문당 한 시도와 시도 키의 요청 일치를 유일 제약·상태 전이로 보호합니다. 메모리 잠금만 사용하지 않습니다.
- 같은 시도의 동시 confirm은 실제 발송 권한을 얻은 실행 하나만 PG POST를 호출합니다.
- 같은 키의 다른 주문·금액·요청은 충돌입니다. 같은 주문에 새 키를 보내도 두 번째 PG 시도를 만들지 않습니다.
- PG로 이미 종결한 같은 시도의 재요청은 저장 결과를 반환하며 추가 효과를 만들지 않습니다. 이전 POINT 확정 주문에는 기존 이미 확정된 상태 오류를 유지합니다.
- 시도에는 금액과 필요한 식별 관계만 보존하고 합성 카드 번호도 영속화하지 않습니다.

**발송 시작을 영속 기록한 뒤에는 자동으로 create를 다시 보내지 않습니다.** 발송 기록 이후 프로세스가 멈추면 실제 발송 여부가 불확실할 수 있으므로 재시작 후 기존 거래를 조회합니다. 생성 HTTP client·프록시·회복 라이브러리의 숨은 재시도도 끕니다.

### 📦 4. 재고 확보와 결과 반영

PG 성공 뒤 재고 부족을 발견하는 일을 피하기 위해 **PG 호출 전에 기존 재고를 주문에 확보**합니다. 기존 가용 재고를 차감하고 주문별 확보 수량·상태를 저장하는 최소 예약 방식으로 구현할 수 있습니다. 재고 확보와 반환은 기존 주문·재고 모델 안에서 연결합니다.

1. **로컬 TX A**: 주문·상품을 검사하고 필요한 재고를 확보합니다. 시도·예약·결제 대기 상태를 같은 TX에 저장합니다. 부족·삭제·잘못된 입력이면 PG 호출 없이 전체 rollback합니다.
2. **TX 밖**: 발송 권한을 가진 실행이 PG를 호출합니다. 다른 실행은 이미 저장된 상태를 조회합니다.
3. **로컬 TX B**: 검증한 PG 결과를 시도·주문·예약에 한 번만 적용합니다.

| PG 관찰 | 내부 결제·주문 | 재고 처리 |
| --- | --- | --- |
| 생성 수락 PENDING | 결제 처리 중, 주문 PAYMENT_PENDING | 예약 유지 |
| timeout·응답 유실·조회 불가 | 결과 UNKNOWN, 주문 PAYMENT_PENDING | 예약 유지 |
| 검증한 SUCCESS | 결제 SUCCESS, 주문 CONFIRMED | 예약 소비, 추가 차감 없음 |
| 검증한 FAILED 또는 효과 0건 확정 거절 | 결제 FAILED, 주문 PAYMENT_FAILED | 예약 한 번 반환 |
| 0건·2건 이상·금액/식별 불일치 | 미확인·충돌 보존, 재발송 금지 | 임의 반환 없음 |

상태 이름은 위 의미를 유지하는 범위에서 기존 모델에 맞게 정합니다. **외부 PENDING을 CONFIRMED로 바꾸지 않습니다.** 효과 0건 확정 거절은 테스트 PG가 그 사실을 명시적으로 보장하는 통제 결과이며, 일반 HTTP 오류·timeout을 그렇게 해석하지 않습니다. timeout만으로 실패·예약 반환을 결정하지 않습니다.

기존 재고 설정 API는 **예약을 제외한 가용 수량을 최종 설정**하는 의미로 연결하고, 관리자 변경도 같은 재고 행의 보호 규칙을 사용합니다. 예약 수량을 관리자 설정 때문에 지우거나 PG 성공 때 다시 차감하지 않습니다.

삭제된 상품은 계속 새 조회·새 주문에서 제외합니다. **이미 재고 확보를 마친 PAYMENT_PENDING 주문**은 저장된 품목·금액·예약으로 기존 PG 결과를 마무리합니다. 삭제 후 새로 시작하는 DRAFT 확정과 구분합니다. 물리 삭제가 미완료 예약의 참조·반환을 깨뜨린다면 종결까지 실제 행 제거를 미루고 비노출만 적용합니다. 실패 반환이 삭제 상품을 다시 노출하게 해서는 안 됩니다.

최종 성공·실패 반영이 DB 오류로 rollback되면 동일한 외부 결과를 다시 조회해 적용할 수 있어야 합니다. 성공·반환 상태와 재고 변경을 같은 TX에서 보호해 중복 callback·동시 reconcile이 두 번 확정·반환하지 못하게 합니다. 4주차 캐시가 가용 재고를 담았다면 기존 변경·복구 정책에도 연결합니다.

### 📬 5. callback·조회·회복 전략

callback 본문은 `providerOrderId, transactionKey, status`를 전달하는 알림으로 사용합니다. **알림의 성공 문자열만으로 주문을 확정하지 않습니다.** 고정한 PG adapter의 조회 결과에서 제공자 계정 범위·주문·transactionKey·저장 금액을 확인한 뒤 적용합니다.

- 같은 거래의 callback-first와 lookup-first가 같은 최종 상태로 수렴합니다.
- 중복 알림은 추가 재고·결제 효과가 없습니다.
- 다른 주문·금액·거래의 응답은 거절·충돌 기록하며 기존 상태를 바꾸지 않습니다.
- 종결 뒤 상충하는 응답은 덮어쓰지 않습니다. callback이 먼저 종결한 뒤 늦게 돌아온 생성 응답·timeout handler도 PENDING·UNKNOWN으로 되돌리지 않습니다.
- 콜백이 없어도 본인의 reconcile API로 기존 시도를 확인합니다.
- 조회 0건·PENDING·조회 실패에는 미완료 상태를 유지합니다. 조회 한도 소진은 새 결제 허용 근거가 아닙니다.

**Timeout·fallback**: 실제 PG HTTP 연결·응답 대기를 제한하고, 조회 실패·회로 차단에는 저장된 상태와 확인 불가를 반환합니다. 금액 0·가짜 성공·포인트 대체 결제로 바꾸지 않습니다.

**Circuit breaker**: PG 조회 한 경로에 적용하고 CLOSED→OPEN→HALF_OPEN→회복 또는 재차단을 확인합니다. 최소 표본·실패 조건·대기·탐색 호출 수를 정합니다. OPEN 동안 실제 외부 조회가 차단돼도 결제 결과를 FAILED로 확정하지 않습니다.

**제한된 재조회**: 조회 횟수·간격·총 대기 예산을 정합니다. 자동 retry를 추가하면 조회에만 적용하고 실제 호출 수를 검증합니다. create 자동 재시도는 하지 않습니다. 상시 스케줄러는 선택이며 수동 reconcile이 기본 복구 경로입니다.

- Java·Kotlin · 클라이언트와 회복 도구 연결
    
    두 트랙의 기존 Spring Web 의존성을 바탕으로 HTTP client를 선택합니다. `RestClient` 같은 동기 client를 사용할 수 있으며 Feign·WebClient를 새 필수로 만들지 않습니다.
    
    - timeout은 실제 사용하는 request factory·하위 HTTP client에 설정합니다.
    - Resilience4j를 선택하면 현재 Spring Boot 3/JDK 21에 맞는 모듈·버전을 의존성 관리에 명시합니다. 스타터에 이미 설치돼 있다고 가정하지 않습니다.
    - 직접 decorator를 연결하거나 Spring integration을 사용합니다. annotation 방식이면 필요한 AOP 연결·자기 호출·실제 proxy 적용을 확인합니다.
    - 조회 retry와 circuit breaker를 중첩하면 어느 호출을 실패 표본으로 세는지 확인합니다.
    
    Spring 6.2 HTTP client, Resilience4j Spring Boot 연결
    

### 🧪 6. 결정적 검증과 제출

PG 테스트 장치는 거래 수·create 횟수·상태를 관찰할 수 있게 작게 만듭니다. HTTP 형식용 고정 서버와 업무 순서용 대역을 분리하거나 같은 테스트 fixture를 재사용할 수 있습니다. 별도 PG 프로세스·관리 화면은 필요하지 않습니다.

| 장면 | 핵심 기대 결과 |
| --- | --- |
| 정상 PG 주문 | 외부 거래 1, 주문 CONFIRMED, 예약 소비 1, 포인트 변화 0 |
| 생성 수락 PENDING | 주문 미확정, 확보 재고 유지, 조회에서 SUCCESS 확인 후에만 확정 |
| 효과 전 확정 거절 | 외부 거래 0, 주문 실패, 예약 반환 1 |
| 거래 생성 뒤 응답만 유실 | 거래 1·UNKNOWN, create 추가 0, 같은 거래 조회로 종결 |
| 같은 주문·시도의 동시 요청 | 시도·예약 각 1, 실제 create 1, 다른 키·불일치 요청은 효과 없이 거절 |
| callback-first·lookup-first·동시 적용 | 같은 transactionKey와 최종 상태, 재고 추가 차감·중복 반환 0 |
| 외부 성공 뒤 내부 저장 실패 | 내부 TX rollback, 같은 거래 재조회로 한 번 확정, create 추가 0 |
| 발송 기록 뒤 재시작 | 저장된 시도·예약 유지, 미확인 시도 자동 재발송 0 |
| 조회 0건·복수 거래·금액/주문 불일치 | 임의 성공·실패·재결제 없음, 미확인·충돌 보존 |
| timeout·회로 OPEN·복구 | 대기·호출 수 제한, 기존 상태 유지, 회복 뒤 조회 재개 |
| 기존 기능 보호 | POINT 과거 기록·소유권, 재고 부족 시 PG 0회, 삭제·예약 결과의 구분 |

재고 5개에서 수량 2개를 확보했다면 가용 재고는 3개입니다. PG 성공 후에도 3개이며, 확정 실패 후에는 5개입니다. 중복 실패 알림으로 7개가 되거나 UNKNOWN에서 5개로 돌아가면 잘못된 처리입니다.

실제 DB 테스트는 기존 MySQL fixture를 사용합니다. callback 경로도 실제 controller를 거쳐 검증하며, 조작한 callback 본문만으로 성공하지 않는지 확인합니다. 재시작 실험에서는 서비스·클라이언트를 재생성하되 같은 DB와 외부 거래 상태를 유지합니다.

- Java·Kotlin · 관련 검사 예시
    
    이름은 직접 작성한 테스트에 맞춥니다. 형식 확인과 업무 상태 확인은 목적이 다르며 같은 모든 조건을 여러 계층에 반복할 필요는 없습니다.
    
    ```bash
    ./gradlew :apps:commerce-api:test --tests '*PaymentProviderContractTest'
    ./gradlew :apps:commerce-api:test --tests '*PaymentIntegrationTest'
    
    # Java: 기존 Checkstyle·ArchUnit·관련 회귀
    ./gradlew :apps:commerce-api:check
    
    # Kotlin
    ```

    테스트 0건·skip·연결 실패를 성공으로 세지 않습니다. 기다림은 유한하게 제한하고 자신이 시작한 HTTP 서버·worker·테스트 자원을 정리합니다.
    

기존 로컬 사용자 식별·관리자 MockMvc 설정과 `127.0.0.1` 실행 범위를 유지합니다. 실제 비밀정보·카드·공개 배포는 사용하지 않습니다.
