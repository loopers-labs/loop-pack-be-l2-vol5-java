## 💳 포인트 결제를 PG로 바꾸면 무엇이 달라지는가

> **PG(Payment Gateway)**는 결제 요청을 받아 외부 결제 처리를 연결하고 그 상태를 제공하는 시스템입니다. 이 과정에서는 실제 금전이 움직이지 않는 로컬 테스트 계약을 사용합니다.
> 

같은 주문을 두 방식으로 비교해 봅니다.

| 경계 | 포인트 주문 | 테스트 PG 주문 |
| --- | --- | --- |
| 결제 결과의 원본 | 우리 DB의 포인트 차감·결제 기록 | 테스트 PG 거래와 조회 결과 |
| 원자적으로 묶을 수 있는 것 | 재고·잔액·주문 등 같은 DB 변경 | 우리 DB의 주문·시도·예약·결과 반영 |
| timeout 뒤 알 수 있는 것 | 호출한 경계와 DB 결과에 따라 확인 | 외부 효과가 이미 생겼을 수 있음 |
| 실패 복구 | 로컬 rollback | 기존 외부 거래 확인 후 내부 상태 조정 |

“결제수단을 바꾼다”는 것은 **포인트를 차감하고 PG도 호출한다**는 뜻이 아닙니다. 새 PG 주문은 포인트를 사용하지 않습니다. 이전 포인트 결제 주문은 결제수단·금액·결과를 그대로 조회할 수 있어야 합니다.

전체 주문 도메인을 다시 만드는 대신 외부 연결을 별도 adapter로 분리할 이유가 여기에서 생깁니다. Controller나 주문 Entity가 카드 요청 JSON과 네트워크 오류를 모두 알아야 한다면 테스트·변경의 범위가 커집니다.

```
기존 주문 유스케이스
  ├─ 주문 소유권·품목·금액·상태 판단
  ├─ 우리 DB 변경의 트랜잭션
  └─ 결제 경계 → PG adapter → 로컬 테스트 PG HTTP
```

## ⏱ 기다림을 끊는 것과 결제를 취소하는 것

PG 응답이 늦어지면 요청을 처리하던 스레드·연결이 계속 사용됩니다. 여러 요청이 쌓이면 PG와 무관한 상품 조회까지 느려질 수 있습니다. 그래서 기다리는 시간에 한계를 둡니다.

> **Timeout**은 정한 시간 안에 호출을 끝내지 못했을 때 호출자의 대기를 제한하는 장치입니다. 상대 시스템의 업무 취소를 뜻하지 않습니다.
> 

| 시간 경계 | 무엇을 기다리는가 | 구분할 것 |
| --- | --- | --- |
| 연결 timeout | 상대와 연결 수립 | 응답·전체 작업 시간과 다름 |
| 읽기·응답 timeout | 상대의 응답 데이터 | 클라이언트별 설정 의미 확인 |
| 연결 풀 대기 | 사용 가능한 연결 확보 | DB SQL 실행 제한과 다름 |
| 전체 처리 예산 | 재시도·대기를 포함한 한 작업 | 각 호출 timeout만으로 자동 제한되지 않음 |

`TimeLimiter` 같은 도구로 Future 대기를 끝내도 하위 HTTP 작업이 실제로 취소됐는지 별도로 확인해야 합니다. 로컬에서 예외를 던졌다는 사실로 PG 거래가 사라지지는 않습니다.

### ❓ 응답을 잃은 결제

```
1. commerce가 PG에 결제를 요청한다.
2. PG가 거래를 만들고 처리를 진행한다.
3. 응답이 돌아오는 중 연결이 끊긴다.
4. commerce는 timeout을 관찰한다.
```

여기에서 세 사실을 구분합니다.

1. 요청을 발송했습니다.
2. 외부에서 거래·결제 효과가 생겼을 수 있습니다.
3. 호출자가 최종 결과를 확인하지 못했습니다.

**3번을 관찰했다고 2번을 부정할 수는 없습니다.** 무조건 실패로 기록하고 새 결제를 보내면 첫 결제가 이미 성공한 경우 이중 결제가 됩니다.

## 🚦 요청 수락·처리 중·결과 미확인

HTTP 성공 상태는 그 API가 약속한 단계의 성공입니다. 비동기 PG의 생성 응답이 “거래를 접수했다”는 뜻이라면 그때 주문을 결제 완료로 바꾸면 안 됩니다.

| 관찰 | 아는 사실 | 내부에서 표현할 의미 |
| --- | --- | --- |
| 거래 키와 PENDING 응답 | 거래가 존재하고 아직 처리 중 | 처리 중 |
| 해당 거래의 SUCCESS 확인 | 외부 결제 성공 | 내부 성공 반영 대상 |
| 해당 거래의 FAILED 확인 | 외부 결제의 확정 실패 | 내부 실패 반영 대상 |
| timeout·연결 유실·해석 불가 응답 | 최종 결과를 확인하지 못함 | 결과 미확인 |
| 새 호출 전 로컬에서 차단 | 이번 실행은 발송하지 않음 | 기존 시도의 상태에 따라 판단 |

**PENDING**은 상대가 처리 중이라고 알려 준 상태이고, **UNKNOWN**은 우리 쪽에서 결과를 확정할 수 없다는 상태입니다. 둘 다 새 결제를 임의로 만들어도 된다는 뜻이 아닙니다.

테스트 대역이 “거래를 전혀 만들지 않았음”을 확정해서 거절한 경우는 일반 timeout과 다릅니다. 이처럼 **효과가 없다는 권위 있는 증거**가 있을 때만 실패 종결과 자원 반환을 판단합니다.

## 🔑 같은 주문과 같은 거래를 찾는 식별자

| 식별자 | 만드는 곳 | 사용하는 목적 |
| --- | --- | --- |
| 내부 orderId | commerce | 주문 소유권·품목·상태 조회 |
| paymentAttemptKey | commerce | 내부 시도 기록과 동일 발송의 중복 제어 |
| providerOrderId | commerce adapter | PG 요청과 주문 단위 거래 조회 연결 |
| transactionKey | 테스트 PG | 외부 거래 한 건 조회 |

예를 들어 내부 주문 42를 `LP-ORD-0000000042`로 변환했다면 요청과 조회에 같은 문자열을 씁니다. 사용자·제공자 계정 범위도 같아야 같은 거래를 찾습니다.

> **멱등성(idempotency)**은 같은 논리적 작업을 반복해도 추가 업무 효과가 생기지 않는 성질입니다.
> 

키 문자열 하나를 만든다고 멱등성이 생기지는 않습니다. 어디에서 키를 저장하고, 어떤 유일성·상태 조건으로 한 번의 효과만 허용하는지가 필요합니다.

- 같은 요청 키로 다른 주문·금액을 보내면 같은 작업으로 받아들이지 않습니다.
- 새 키를 만들었다고 미확인 주문에 다시 결제를 허용하지 않습니다.
- 프로세스 메모리의 `Set`만으로는 재시작·다중 실행을 막지 못합니다.
- 내부 시도 키를 PG가 받아 중복 제거해 준다고 가정하지 않습니다.

실제 PG마다 멱등 키·보존 기간·조회 계약은 다릅니다. 이 과정의 테스트 PG는 호출자의 멱등 키를 받지 않는 계약이므로 **발송 후 불확실하면 기존 거래를 조회하고 create를 자동 재시도하지 않습니다.**

## 🔁 Retry는 어떤 호출에 적용할 것인가

> **Retry**는 일시적 실패 뒤 같은 작업을 다시 시도하는 전략입니다. 다시 수행해도 되는 업무인지가 먼저입니다.
> 

| 호출 | 다시 실행할 때의 효과 | 판단 |
| --- | --- | --- |
| 기존 거래 상태 조회 | 같은 거래의 현재 상태를 읽음 | 횟수·대기·전체 예산을 제한해 재조회 가능 |
| 멱등 보장 없는 결제 생성 | 새 거래가 생길 수 있음 | 결과 미확인 뒤 자동 재시도 금지 |
| 같은 외부 결과의 내부 반영 | 주문·재고를 다시 바꿀 수 있음 | DB의 종결 상태와 전이 조건으로 중복 효과 방지 |

**Backoff**는 시도 사이의 대기이고, **jitter**는 동시 재시도가 몰리지 않도록 대기 시점을 분산하는 방법입니다. 외부가 과부하인데 모든 요청이 즉시 여러 번 다시 호출하면 실패를 증폭합니다.

예를 들어 조회 한 번의 최대 대기를 1초, 최대 총 시도를 3회, 사이 대기를 100ms·200ms로 잡으면 호출·대기만 최대 약 3.3초가 됩니다. 실제 전체 예산에는 연결 풀·스케줄링 등도 포함해야 합니다. `maxAttempts=3`은 처음 1회와 재시도 2회를 뜻하는 설정인지 라이브러리 계약을 확인합니다.

클라이언트 내부 재시도와 서비스 annotation 재시도가 겹치면 실제 호출 수가 곱해질 수 있습니다. 테스트에서 adapter의 **실제 create·lookup 횟수**를 세는 이유입니다.

## 🔌 Circuit Breaker와 Fallback

> **Circuit breaker**는 반복 실패·지연을 관찰해 한동안 외부 호출을 차단하고, 제한된 탐색 호출로 회복을 확인하는 장치입니다.
> 

| 상태 | 외부 호출 | 다음 판단 |
| --- | --- | --- |
| CLOSED | 허용하고 결과 기록 | 최소 표본과 실패·지연 비율을 확인 |
| OPEN | 빠르게 차단 | 정한 대기 뒤 탐색 가능 여부 |
| HALF_OPEN | 제한된 호출 허용 | 회복하면 CLOSED, 악화하면 OPEN |

회로의 표본 크기는 동시 요청 수 제한이 아닙니다. 동시에 허용할 요청을 제한하는 **bulkhead**와 역할이 다릅니다. 회로 차단기는 개별 호출의 timeout도 대신하지 않습니다.

한도 초과 같은 정상 업무 거절과 연결 장애를 같은 실패율에 무조건 넣으면 정상 PG에도 회로가 열릴 수 있습니다. 기록할 오류와 제외할 업무 결과를 구분합니다.

**Fallback**은 원래 호출을 수행할 수 없을 때 선택하는 대체 동작입니다. 결과를 지어내는 것이 아닙니다.

| 잘못된 fallback | 안전하게 표현할 결과 |
| --- | --- |
| PG 조회 차단 → 결제 실패로 확정 | 마지막으로 아는 상태 유지, 조회 불가·다음 확인 경로 |
| timeout → 결제 성공으로 응답 | 결과 미확인과 주문 조회 위치 |
| PG 오류 → 포인트를 대신 차감 | 결제수단을 임의 변경하지 않음 |
| 오류 → 재고 예약 무조건 반환 | 외부 결제의 종결 사실 확인 전 유지 |

이미 발송한 시도를 조회하지 못한 것과 한 번도 발송하지 않은 새 요청이 차단된 것은 다릅니다. 기존 `REQUESTED/UNKNOWN`을 회로 OPEN이라는 이유로 미발송 상태로 되돌리지 않습니다.

## 🧩 DB 트랜잭션을 짧은 단계로 나누기

PG를 호출하는 동안 재고 행의 잠금과 DB 연결을 계속 잡고 있으면 다른 주문이 기다립니다. 그럼 호출을 TX 밖으로 옮기기만 하면 될까요? **PG 성공 뒤 재고가 부족해지는 문제**가 남습니다.

| 순서 | 새로 생기는 문제 |
| --- | --- |
| PG 성공 뒤 재고 차감 | 결제는 됐는데 재고가 없을 수 있음 |
| 재고 차감 뒤 PG 호출 | PG 실패 시 재고를 반환해야 함 |
| 한 로컬 TX 안에서 PG 호출 | 외부 효과는 rollback되지 않고 잠금만 오래 유지 |

이 과제에서는 실금전 환불 시스템을 새로 만들지 않습니다. 대신 호출 전에 주문에 필요한 재고를 **예약**하고, PG 결과를 확인한 뒤 확정하거나 반환하는 작은 단계로 연결할 수 있습니다.

> **재고 예약**은 특정 미완료 주문을 위해 수량을 확보한 사실입니다. 주문이 최종 성공했다는 뜻은 아닙니다.
> 

```
로컬 TX A: 주문 검사 → 재고 확보·예약 기록 → 발송할 시도 기록 → commit
                                  ↓
TX 밖: 테스트 PG HTTP 호출 또는 같은 거래 조회
                                  ↓
로컬 TX B: PG 결과와 주문·예약 확인 → 성공 확정 또는 확정 실패 반환 → commit
```

가능한 최소 모델은 가용 재고를 예약 시 줄이고, 예약의 수량·상태를 DB에 남기는 것입니다. 성공 때는 재고를 다시 차감하지 않고 예약을 소비한 상태로 마무리합니다. 확정 실패 때만 한 번 반환합니다. 실제 테이블·객체 분리는 기존 모델에 맞게 정합니다.

| 외부 결과 | 예약 | 주문·포인트 |
| --- | --- | --- |
| 처리 중·미확인 | 유지 | 결제 대기, 포인트 차감 없음 |
| 성공 확인 | 소비로 종결, 추가 차감 없음 | CONFIRMED, PG 결제 사실 저장 |
| 확정 실패 | 반환으로 종결, 한 번만 복구 | 실패 상태, 포인트 차감 없음 |

결과 미확인을 시간 경과만으로 실패 처리하면 아직 성공할 PG 거래의 재고를 다른 주문에 팔 수 있습니다. 이번 범위에서는 무조건 만료·자동 재결제로 회복을 가장하지 않습니다. 장기 미확인에는 거래 확인과 별도 판단이 필요하며, 예약이 오래 점유되는 비용을 남깁니다.

### 🧱 발송 기록 뒤 프로세스가 멈췄다면

발송 권한을 DB에 기록한 뒤 HTTP 호출 전에 멈추면 실제 발송은 0회일 수 있습니다. 반대로 HTTP가 끝난 뒤 내부 저장 전에 멈추면 외부 거래는 이미 있습니다. 재시작한 프로세스는 로컬 기록만으로 두 상황을 완벽하게 구분하지 못합니다.

이 계약에서는 재발송보다 중복 결제 방지를 우선합니다. 이미 발송을 시작한 시도는 재시작 뒤에도 조회 대상으로 남기고, 거래가 당장 0건이라고 create를 다시 보내지 않습니다. **중복 방지와 모든 시도의 자동 완료는 같은 보장이 아닙니다.**

## 📬 콜백과 조회를 같은 결과 적용 경계로 모으기

**콜백(callback)**은 제공자가 우리 endpoint로 결과를 알리는 요청입니다. **대사(reconciliation)**는 내부 기록과 외부 거래를 같은 식별자로 맞춰 상태를 확인하는 작업입니다.

콜백은 유실·중복·지연·순서 변경이 가능합니다. 콜백 본문만 믿어 주문을 성공시키면 위조된 요청도 결제를 완료할 수 있습니다. 실제 서비스에서는 제공자의 서명·재전송 계약을 검증해야 합니다. 로컬 실습에서는 콜백을 **확인 요청의 계기**로 쓰고 adapter로 조회한 거래를 검증하는 방식으로 경계를 유지할 수 있습니다.

| 확인할 것 | 다른 경우의 처리 |
| --- | --- |
| 제공자 계정·사용자 범위 | 다른 범위의 거래를 사용하지 않음 |
| providerOrderId·transactionKey | 다른 주문 거래를 적용하지 않음 |
| 저장된 요청 금액 | 금액 불일치를 성공으로 반영하지 않음 |
| 외부 상태·거래 수 | 미확인·중복·충돌은 격리하고 재발송하지 않음 |
| 내부 종결 상태·예약 상태 | 중복 확정·반환을 막음 |

```
콜백 먼저: 콜백 → 권위 조회 SUCCESS → 내부 확정 → 나중 조회 SUCCESS → 변화 없음
조회 먼저: 조회 SUCCESS → 내부 확정 → 나중 콜백 → 같은 거래 확인 → 변화 없음
```

HTTP 응답을 성공으로 보냈다는 것보다 **DB의 최종 상태와 업무 효과 수**가 중요합니다. 동시에 두 경로가 들어와도 상태 조건·잠금·유일 제약으로 같은 결과 적용이 한 번만 일어나게 합니다.

- Java·Kotlin · 결과 적용 경계의 의사코드
    
    특정 언어의 완성 서비스가 아니라 상태 판단 순서입니다. PG 조회는 이 DB 트랜잭션 밖에서 수행하고, 검증된 관찰만 넘깁니다.
    
    ```
    applyObservation(attemptId, verifiedObservation):
      로컬 TX 시작
      시도·주문·예약을 정한 순서로 잠금
      주문·거래·금액의 일치 확인
      이미 같은 종결 결과이면 아무 업무 효과도 추가하지 않음
      다른 종결 결과와 충돌하면 덮어쓰지 않고 충돌 기록
      SUCCESS이면 예약 소비 + 주문 확정 + PG 결제 사실 저장
      확정 FAILED이면 예약 반환 + 주문 실패
      PENDING 또는 불확실하면 예약·미완료 상태 유지
      commit
    ```
    
    중복 callback마다 단순히 `stock += quantity`를 실행하면 반환이 반복됩니다. 반환 여부 역시 같은 트랜잭션에서 한 번만 전이돼야 합니다.
    

거래 조회가 0건인 순간은 거래 없음의 영구적 증거가 아닐 수 있습니다. 1건이어도 `PENDING`이면 성공·실패로 종결하지 않습니다. 2건 이상이면 자동으로 첫 거래를 고르는 대신 미확인·충돌로 남깁니다.

## 🧪 무엇을 통제해서 테스트할 것인가

| 테스트 경계 | 목적 | 통제할 것 |
| --- | --- | --- |
| 실제 adapter → 로컬 HTTP 서버 | 요청·응답 형식 확인 | 경로·헤더·문자열 ID·JSON·조회 인코딩 |
| 업무 서비스 → 통제한 PG 경계 | 순서별 상태·효과 검증 | 처리 중 거래 생성 후 응답 유실, 성공·실패, 조회 지연 |
| 실제 DB | 재시작·중복 적용의 안전성 | 시도·예약·주문 저장, 동시 전이와 rollback |
| 회복 도구 | 호출 제한의 실제 작동 | timeout·조회 횟수·회로 상태·fallback |

서버를 무작위로 실패시키면 정상과 실패 중 무엇을 검증했는지 불명확합니다. 먼저 **거래 한 건 생성 → 응답만 유실 → 같은 거래 SUCCESS 조회**를 고정합니다. 결제 생성 호출 수, 외부 거래 수, 내부 상태, 가용·예약 재고와 포인트를 함께 비교합니다.

작은 HTTP fixture에서 거래 상태와 응답 유실 시점을 제어해 봅니다. 클래스 이름이 달라도 요청·응답 형식과 업무 결과가 같은지 확인합니다.

## 🧭 AI와 실패 경계를 검토하기

사람이 먼저 교체할 결제 경계, 상태 전이와 허용할 효과를 정합니다.

> **검토 예시:** “포인트 결제를 PG로 교체한다. 생성 POST는 자동 재시도하지 않는다. 거래 생성 뒤 timeout, 성공 뒤 내부 commit 실패, 콜백과 조회의 동시 적용에서 주문·예약이 어떻게 되는지 반례를 제시해 줘.”
> 

작은 변경을 받은 뒤 실제 호출 경로와 시도 수를 확인합니다. AI가 모든 예외를 `FAILED`로 묶거나 PG 장애 때 포인트를 대신 쓰게 했다면 요구가 바뀐 것입니다. 기존 상품·소유권·주문 기록과 lint·ArchUnit도 계속 확인합니다.

운영 관점에서는 결제 미완료의 체류 시간, 조회 불가·결과 충돌, 실제 발송 수와 예약 점유를 봅니다. 미확인 기록을 지우거나 서버를 재시작하는 것으로 외부 거래가 취소되지는 않습니다.
