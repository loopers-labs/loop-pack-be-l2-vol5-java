# 요구사항 명세서 (W5) · 포인트 결제를 테스트 PG 로 교체

원문 과제(`ref/week5/assignment.md`, 학습 자료 `ref/week5/study.md`)를 구현 · 테스트의 기준이 될 수 있는 수준으로 정제한 문서다.
2주차 명세(`docs/week2/requirements.md`, 아래 **W2**)의 규칙 ID 와 출처 구분을 그대로 쓰고, 이번 주에 생긴 것만 적는다.

| | |
|---|---|
| **원문** | Vol5 W5 — 포인트 결제를 테스트 PG 로 교체하고, 외부 결과를 기존 주문 · 재고에 한 번만 반영한다 |
| **이 문서가 하는 일** | ① PG 와 주고받는 계약을 못 박는다 ② 결제 시도 · 예약 · 결과 반영의 규칙을 적는다 ③ 아직 답이 없는 것을 질문으로 남긴다 |
| **이 문서가 하지 않는 일** | 상태 전이 · 트랜잭션 경계 · 회복 도구의 구조와 그 이유. 설계 기록(`docs/week5/design.md`)의 몫이다 |

## 출처 구분

W2 의 표기(`원문` · `정함` · `선택` · `보안` · `범위` · `질문`)를 그대로 쓴다.
**PG 계약의 응답 코드 · 본문은 이 실습이 정의하는 로컬 약속이다.** 실제 PG 의 규격이라고 주장하지 않는다(원문).

## 규칙 ID

W2 의 갈래에 넷을 더한다. 번호를 다시 쓰지 않는 규칙도 같다.

| 접두사 | 다루는 것 |
|---|---|
| `PG` | commerce ↔ 테스트 PG 의 HTTP 계약과 adapter |
| `PAY` | 결제 시도 · 식별자 · 상태 |
| `RSV` | 재고 예약과 그 소비 · 반환. 예약은 테이블이 아니라 "TX A 가 뺀 가용 재고 + `order_item` 수량 + 미완료 `payment`" 다(설계 3.2) |
| `SETTLE` | 결과 반영 — callback · reconcile · 생성 응답이 같은 경계로 모이는 규칙 |
| `RESIL` | timeout · 조회 재시도 · circuit breaker · sweeper |

## 바뀌는 기존 계약

| 기존 규칙 | 내용 | 이번 주 |
|---|---|---|
| `ORDER-013` | 확정 시 재고를 확인하고 차감한다 | **확정 요청(TX A)에서 예약으로 차감한다.** PG 성공 때 다시 차감하지 않는다(`RSV-001` · `RSV-002`) |
| `ORDER-014` | 확정 시 합계만큼 포인트를 차감한다 | **새 확정은 포인트를 차감하지 않는다**(`PAY-012`). 이전 POINT 확정 주문의 기록은 그대로 |
| `ORDER-015` | 확정의 차감은 전부 성공하거나 전부 취소된다 | 한 DB rollback 으로 묶이는 것은 **TX A 안**(예약 · 시도 · 주문 상태)뿐이다. 외부 효과는 rollback 되지 않는다 |
| `ORDER-016` | 결제 수단은 포인트다 | 결제 수단은 `POINT`(과거) 와 `PG`(새 확정) 둘이다 |
| `ORDER-018` | 동시 확정 두 건은 한 번만 확정된다 | 같은 시도의 동시 confirm 에서 **실제 PG 생성은 1회**(`PAY-004`) |
| `ORDER-010` | 확정은 `DRAFT` 에만. 아니면 409 `ORDER_NOT_DRAFT` | 이전 POINT 확정 주문에는 그대로 409. PG 시도가 있는 주문의 재요청은 `PAY-002` · `PAY-003` · `PAY-007` 이 정한다 |

유지하는 것: 소유권(`ORDER-011`) · 품목 · 저장 금액(`ORDER-005` · `006` · `017`) · 삭제 상품 검사(`ORDER-012`) · 포인트 충전 · 조회(`POINT-*`).

## PAY — 결제 시도

| ID | 규칙 | 출처 | 깨는 입력 | 기대 |
|---|---|---|---|---|
| `PAY-001` | 주문당 결제 시도는 하나다. **DB 유일 제약**으로 지킨다. 메모리 잠금만 쓰지 않는다 | 원문 | 같은 주문의 시도 두 번째 INSERT | 유일 제약 위반 → 기존 시도로 응답 |
| `PAY-002` | `paymentAttemptKey` 도 유일하다. 같은 키로 다른 주문 · 금액 · 요청이 오면 충돌이다 | 원문 | 같은 키 · 다른 주문 | 409, 효과 없음 |
| `PAY-003` | 시도가 있는 주문에 **새 키**가 와도 두 번째 PG 시도를 만들지 않는다. 주문이 이미 `DRAFT` 가 아니므로 `ORDER-010` 에 걸린다 | 원문 + 정함(응답, Q-1) | 같은 주문 · 새 키 | 409 `ORDER_NOT_DRAFT`, create 0 |
| `PAY-015` | confirm 의 판단 순서: ① 소유권 ② **같은 키의 시도가 있으면** 반복(저장된 상태) 또는 충돌(`PAY-002`) ③ 주문이 `DRAFT` 인가 ④ TX A. ② 를 ③ 보다 먼저 본다 — 바꾸면 같은 키의 재전송이 `ORDER_NOT_DRAFT` 가 된다 | 정함 | 같은 키 재전송 | 202 · 200, 저장된 상태 |
| `PAY-016` | `paymentAttemptKey` 는 클라이언트가 만든다(UUID 권장). 같은 결제 버튼의 재전송은 같은 키를 쓴다. 형식은 1~64자 영문 · 숫자 · `-` | 정함 | 65자 · 빈 문자열 | 400 |
| `PAY-019` | `cardType` 은 `TEST` 하나, `cardNo` 는 `0000-0000-0000-0000` 형식(숫자 4자리 × 4, `-` 로 구분)이다. 합성 값만 받는다. 요청 record 의 타입이 걸러 400 을 낸다 — 도메인까지 보내지 않는다 | 원문(합성 값만) + 정함(형식) | `cardType: VISA` · `cardNo: 1234` | 400 |
| `PAY-004` | 같은 시도의 동시 confirm 중 **발송 권한을 얻은 실행 하나만** PG 생성을 호출한다. 다른 실행은 저장된 상태를 돌려준다 | 원문 | 같은 키 confirm 동시 2건 | 시도 1 · 재고 차감 1 · create 1 |
| `PAY-005` | 발송 권한을 영속 기록(`REQUESTED` commit)한 뒤에는 create 를 다시 보내지 않는다. 재시작 뒤에도 기존 거래를 조회할 뿐이다 | 원문 | 발송 기록 뒤 재시작 | 자동 재발송 0 |
| `PAY-006` | 시도 상태는 `REQUESTED` · `PENDING` · `UNKNOWN` · `SUCCESS` · `FAILED` · `CONFLICT` 이고 **앞으로만** 간다 | 정함(이름) | — | 전이 표는 설계 5.2 |
| `PAY-007` | 종결(`SUCCESS` · `FAILED`)은 바뀌지 않는다. 같은 결과의 재관찰은 효과 0, **lookup 이 다른 결과를 말하면** 덮어쓰지 않고 불일치(`RESULT_AFTER_SETTLED`)를 기록한다(`PAY-017`). callback 본문만 다른 것은 불일치가 아니다(`SETTLE-002`) | 원문 + 정함(기록 수단) | `SUCCESS` 종결 뒤 lookup `FAILED` | 상태 · 예약 그대로, 불일치 1줄 |
| `PAY-008` | 조회 실패 · 회로 OPEN 은 **아무것도 쓰지 않는다.** `PENDING` 을 `UNKNOWN` 으로, 발송한 시도를 미발송으로 되돌리지 않는다 | 원문 + 정함 | 조회 timeout | 상태 · 예약 그대로 |
| `PAY-009` | 조회 0건 · 2건 이상 · 주문이나 금액 불일치는 성공도 실패도 아니다. 재발송 · 예약 반환을 하지 않는다. 0건은 미완료로 두고, 우리 주문의 거래가 2건 이상이거나 금액이 다르면 시도를 `CONFLICT` 로 멈추고 불일치를 기록한다(`PAY-017`). **다른 주문의 거래는 상태를 바꾸지 않고 기록만 한다**(원문 5장 "기존 상태를 바꾸지 않습니다") | 원문 + 정함(기록 수단) | 같은 주문 거래 2건 | `CONFLICT`, 불일치 `MULTIPLE_TRANSACTIONS` 1줄, 예약 유지 |
| `PAY-010` | 결제 시도는 주문과 별도 테이블 `payment` 다(주문 1 : 시도 0..1). 금액 · `paymentAttemptKey` · providerOrderId · `transactionKey` · `cardType` · 상태와 주문 관계만 저장한다. 과거 POINT 결제는 이 테이블로 옮기지 않는다 | 원문 + 정함(테이블) | — | 카드 번호 열이 없다. POINT 주문에는 `payment` 행이 없다 |
| `PAY-017` | **불일치 기록** `payment_discrepancy` — 검증한 lookup 결과가 우리 기록과 다를 때 TX B 안에서 한 줄 더한다. append-only(고치거나 지우지 않음). 이유는 `MULTIPLE_TRANSACTIONS` · `AMOUNT_MISMATCH` · `ORDER_MISMATCH` · `RESULT_AFTER_SETTLED`. 같은 관찰(결제 · 이유 · 관찰한 키 · 관찰한 상태)은 한 번만 남긴다. 업무 판단은 이 기록을 읽지 않는다 | 원문("충돌 기록") + 정함(형태) | 같은 모순 callback 10회 | 불일치 1줄 |
| `PAY-018` | `CONFLICT` 시도는 sweeper 가 집지 않고, reconcile 은 PG 를 부르지 않고 저장된 상태를 돌려준다. 주문 `PENDING` 과 차감한 재고를 유지한다. 해결은 사람의 판단이다 | 정함 + 범위 | `CONFLICT` 에 reconcile | 202, create · lookup 0 |
| `PAY-011` | 이전 POINT 확정 주문의 결제 수단 · 금액 · 결과 · 품목은 그대로 조회된다 | 원문 | POINT 주문에 confirm | 409 `ORDER_NOT_DRAFT` |
| `PAY-012` | PG 로 확정한 주문은 포인트를 차감하지 않는다 | 원문 | — | 잔액 · 원장 변화 0 |
| `PAY-013` | 주문 상태는 `DRAFT` → `PENDING` → `CONFIRMED` 또는 `FAILED`. **외부 `PENDING` 을 `CONFIRMED` 로 바꾸지 않는다** | 원문(의미) + 정함(이름) | — | — |
| `PAY-014` | 주문당 한 시도. 실패 뒤 새 시도 · 환불 · 정산 · 사용자 취소는 없다 | 범위 | `FAILED` 에 confirm | 409 |

## RSV — 재고 예약

| ID | 규칙 | 출처 | 깨는 입력 | 기대 |
|---|---|---|---|---|
| `RSV-001` | TX A 에서 가용 재고를 차감하고 품목 수량(`order_item`)만큼 가용 재고를 빼고, 결제 시도(`REQUESTED`)를 **같은 TX** 에 저장한다. 예약 테이블은 두지 않는다 — 수량은 `order_item`, 상태는 `payment.status` 가 이미 담는다. 부족 · 삭제 · 잘못된 입력이면 PG 호출 없이 전체 rollback | 원문 + 정함(저장 방식) | 재고 2 · 수량 3 | 409 `INSUFFICIENT_STOCK`, create 0 |
| `RSV-002` | `SUCCESS` 는 예약을 소비로 끝낸다. 재고를 다시 차감하지 않는다 | 원문 | — | — |
| `RSV-003` | `FAILED` · 효과 0건 거절만 `order_item` 수량만큼 가용 재고를 **한 번** 되돌린다. 한 번뿐인 것은 `FAILED` 전이가 잠금 아래 한 번만 일어나기 때문이다 | 원문 | 같은 실패 callback 2회 | 반환 1회 |
| `RSV-004` | `PENDING` · `UNKNOWN` · `CONFLICT` · timeout · 회로 OPEN 은 예약을 유지한다. 시간 경과만으로 반환하지 않는다 | 원문 | — | — |

## RESIL — 회복 도구

| ID | 규칙 | 출처 | 기대 |
|---|---|---|---|
| `RESIL-001` | circuit breaker 는 **PG 조회 경로에만** 둔다 | 원문 | create 는 회로를 거치지 않는다 |
| `RESIL-002` | 회로의 실패 표본은 timeout · 연결 실패 · 5xx · **429** 다. 404 · 빈 목록 · `PENDING` 은 업무 결과라 세지 않는다. 429 가 이어지면 회로가 열려 우리가 스스로 조회를 멈춘다 | 정함 | — |
| `RESIL-003` | CLOSED → OPEN → HALF_OPEN → CLOSED, HALF_OPEN → OPEN 을 테스트로 확인한다. 창(시간 기준) · 최소 표본 · 실패율 · 대기 · 탐색 호출 수는 설계 7.3 | 원문 + 정함(값) | — |
| `RESIL-004` | 회로 OPEN · 조회 실패에는 저장된 상태와 "확인 불가" 를 돌려준다. 금액 0 · 가짜 성공 · 포인트 대체 결제 · `FAILED` 확정을 하지 않는다 | 원문 | — |
| `RESIL-005` | 조회 재시도는 횟수 · 간격 · 총 예산을 정하고 **실제 호출 수**를 테스트로 센다. 재시도는 **sweeper 의 조회에만** 둔다 — 요청 스레드에서 도는 reconcile · callback 은 조회 1 회다. **429 는 재시도하지 않는다** — 바로 "조회 불가" 로 끝내고 회로의 실패로만 센다(`RESIL-002`) | 원문 + 정함(값 · 입구 · 429 제외) | 조회 5xx 에 reconcile · 조회가 429 | reconcile 조회 1 회 · 429 조회 1 회, 상태 그대로 |
| `RESIL-006` | sweeper — 미완료 시도를 정한 주기로 찾아 reconcile 과 같은 조회 · 반영을 부른다. 테스트에서는 주기를 끄고 한 번 실행을 직접 부른다 | 선택 | 수동 reconcile 이 기본 복구 경로 |
| `RESIL-007` | **bulkhead** — confirm 의 PG 생성 경로는 동시에 20 개까지만 진행한다(세마포어, 대기 0). 자리는 **TX A 전에** 잡고 TX B 뒤에 `finally` 로 반납한다. 자리가 없으면 503 `PAYMENT_BUSY` · `Retry-After`, 예약 · 마킹 · create 모두 0 | 정함 | 동시 confirm 21 건 → 20 건 진행, 1 건 503 · 효과 0 |
| `RESIL-008` | reconcile 은 같은 결제를 2초 안에 다시 확인하지 않는다(`last_checked_at`). 간격 안이면 PG 를 부르지 않고 저장된 상태를 돌려준다 | 정함 | 연속 reconcile 2 회 → lookup 1 회 |
| `RESIL-009` | HTTP client 는 동기 `RestClient`, 하위는 Apache HttpClient 5. 연결 · 응답 · **커넥션 풀 대기**에 각각 timeout 을 두고, 생성 풀 크기는 bulkhead 와 같다 | 원문(동기 client · 실제 factory 에 timeout) + 정함 | 값은 설계 7장 |
| `RESIL-010` | 생성과 조회는 커넥션 풀을 따로 쓴다. 생성이 생성 풀을 모두 써도 조회는 조회 풀에서 연결을 얻는다 | 정함 | 생성 풀이 모두 빌려진 채 주문 조회 | `NotFound`(조회 불가가 아님) |
| `RESIL-011` | 조회 풀을 기다리다 실패한 조회는 조회 불가로 끝내고 다시 시도하지 않는다. 우리 쪽 포화라 회로는 실패로도 성공으로도 세지 않는다 | 정함 | 조회 풀 1 이 빌려진 채 조회 | 조회 불가, PG 조회 0, 회로 기록 없음 |
| `RESIL-010` | confirm 은 결과를 기다리지 않는다. 생성 응답을 반영하면 202 와 `Retry-After` 를 돌려주고, 결과는 callback · 고객 폴링 · reconcile · sweeper 가 맡는다 | 정함 | confirm 의 lookup 0 회 |
