## 목표

> 비즈니스 코드는 `OrderConfirmed` 이벤트를 받아 업무에 사용한다는 사실만 알면 된다.

## 기존 컨슈머 흐름

```text
[1. Kafka Record 수신]             infrastructure.kafka
         │
         ▼
[2. JSON·메시지 계약·Key 검증]       infrastructure.kafka
         │
         ▼
[3. 업무 처리]                     application
         │
         ├── 처리 이력 조회
         │     ├── 최초 수신 → 구매 활동 + 처리 이력 저장
         │     ├── 중복 수신 → 저장 없이 종료
         │     └── ID 동일, 내용 다름 → 예외
         │
         ▼
[4. DB Commit]                    Spring @Transactional
         │
         ▼
[5. Kafka Ack]                    infrastructure.kafka
         │
         ▼
    Offset Commit
```


| 역할                         | 코드                                      |
| -------------------------- | --------------------------------------- |
| Kafka record 수신·분배         | Spring Kafka listener container         |
| JSON 파싱                    | `OrderConfirmedKafkaConsumer.parse()`   |
| eventType·schemaVersion 검증 | `validateMessageContract()`             |
| Kafka key와 orderId 검증      | `OrderConfirmedKafkaConsumer.consume()` |
| 업무 처리                      | `PurchaseActivityHandler.consume()`     |
| DB commit                  | Spring `@Transactional`                 |
| Kafka ack                  | `acknowledgment.acknowledge()`          |


### 기존 실패 및 재전달 흐름

```text
① DB Commit 이전 실패
   → Ack하지 않음
   → 컨테이너 중단
   → offset은 미커밋 상태로 남음

② DB Commit 이후, Ack 전 중단
   → 같은 record가 다시 올 수 있음
   → 처리 이력을 확인해 같은 사실을 중복 저장하지 않고 ack
```

## 리팩토링 후 컨슈머 흐름

```text
record 수신
└─ OrderConfirmedKafkaConsumer.consume(record, acknowledgment)
   └─ OrderConfirmedMessageParser.parse(record.value())
      ├─ value bytes → JSON 파싱
      ├─ DTO 필드·타입 호환성 확인
      │  ├─ eventId, orderId, confirmedAt, items
      │  └─ items의 productId, quantity
      ├─ 호환되는 payload → 애플리케이션 OrderConfirmedEvent 변환
   └─ PurchaseActivityHandler.consume(event)
      ├─ 업무 처리·중복 확인
      ├─ 신규 이벤트면 처리 이력·구매 활동 저장
      └─ 정상 반환하면서 DB 트랜잭션 commit
   └─ acknowledgment.acknowledge()
      └─ Kafka offset commit
```


| 단계 | 계층·객체 | 하는 일 |
| --- | --- | --- |
| record 수신 | Spring Kafka listener container · `OrderConfirmedKafkaConsumer.consume()` | 설정된 topic에서 record를 가져와 payload와 acknowledgment를 consumer에 전달한다. Kafka key는 업무 처리에 사용하지 않는다. |
| payload 파싱 | `OrderConfirmedMessageParser.parse()` | `record.value()`의 byte 배열을 JSON으로 읽는다. |
| DTO 호환성 확인 | `OrderConfirmedMessageParser` | DTO 필드와 타입이 맞는지 확인한다. DTO 필드는 `eventId`, `orderId`, `confirmedAt`, `items` 및 각 item의 `productId`, `quantity`다. `eventType`, `schemaVersion`, Kafka key, 전체 JSON Schema는 검사하지 않는다. |
| 업무 DTO 변환 | `OrderConfirmedMessageParser` | 호환되는 payload에서 필요한 값을 애플리케이션 `OrderConfirmedEvent`로 옮긴다. |
| 업무 처리 | `PurchaseActivityHandler.consume()` | 업무 규칙과 처리 이력을 확인한다. 새 이벤트면 처리 이력과 구매 활동을 저장한다. |
| DB commit | Spring `@Transactional` | handler가 정상 반환할 때 DB 트랜잭션을 commit한다. 같은 사실의 중복 이벤트는 저장 없이 정상 반환한다. |
| Kafka ack·offset commit | `acknowledgment.acknowledge()` | DB commit 뒤 record 처리가 끝났음을 알리고 Kafka offset을 commit한다. |

### 리팩토링 후 실패 및 재전달 흐름

```text
① 파싱·DTO 호환성 확인 실패
   → 업무 handler 호출 전 예외
   → Ack 없음
   → 컨테이너 중단
   → 재시작 시 재전달 가능

② DB 처리 중 commit 전 실패
   → DB 트랜잭션 rollback
   → Ack 없음
   → 컨테이너 중단
   → 재시작 시 재전달 가능

③ DB Commit 이후, Ack 이전 중단
   → DB 저장 완료
   → Offset 미커밋 가능
   → 재전달 시 처리 이력 확인
   → 중복 저장 방지 → Ack
```

같은 이벤트 ID·주문 ID인데 저장된 사실과 내용이 다르면 handler가 예외를 낸다. 이 경우에도 ack하지 않아 잘못된 이벤트를 정상 완료 처리하지 않는다.

> 메모: DTO 호환성 실패처럼 재처리해도 해결되지 않는 메시지가 listener container를 계속 멈추게 하지 않도록 DLQ 도입을 추후 고려한다. 현재는 DLQ를 구현하지 않았다.
