# Outbox insert 흐름

```text
PG 결과 수신 또는 대사 조회
└─ PaymentGateway.Approved
   └─ OrderPaymentTransactionService.recordResult(orderId, result)
      └─ TXB 시작
         ├─ 결제 성공 기록
         ├─ 재고 예약 소비
         ├─ 주문 CONFIRMED 처리
         ├─ 고정 eventId·messageKey·payload 생성
         ├─ Outbox PENDING insert (eventId UNIQUE)
         └─ commit
            └─ relay가 나중에 Outbox를 읽어 Kafka 발행
```

Outbox insert 실패 시 TXB 전체를 같은 PG 결과로 1회 재시도한다.

## `order_confirmed_outbox`


| 컬럼                | 비고                                                                                                                         |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `id`              | 테이블 내부 식별자                                                                                                                 |
| `event_id`        | 이벤트 식별,멱등키                                                                                                                 |
| `order_id`        | 원본 주문 식별자                                                                                                                  |
| `event_type`      | `OrderConfirmed`                                                                                                           |
| `schema_version`  | Producer 인프라가 `OrderConfirmedEvent`를 `OrderConfirmedV1Schema`로 변환할 때 설정하는 계약 버전(현재 `1`). 이 값을 payload와 Outbox 컬럼에 함께 저장한다. |
| `message_key`     | Kafka record key. 현재는 주문 ID 문자열                                                                                            |
| `payload`         | relay가 kafka에게 보낼 본문. insert 뒤 수정하거나 relay에서 재생성하지 않는다.                                                                    |
| `status`          | `PENDING`, `FAILED`, `BLOCKED`, `PUBLISHED`                                                                                |
| `created_at`      | Outbox 행 생성 시각                                                                                                             |
| `published_at`    | broker 성공 확인 시각. `PUBLISHED`일 때 설정                                                                                         |
| `attempt_count`   | relay가 시작한 Kafka 발행 시도 횟수. TXB 재시도 횟수와는 별개                                                                                 |
| `next_attempt_at` | 다음 발행 시도 가능 시각. 신규 행은 생성 시각으로 설정하고, 실패하면 현재 시각에 폴링 간격을 더해 설정한다. 해당 시각 이후 다음 폴링에서 시도한다.                                     |
| `last_error`      | 마지막 발행 실패의 예외 클래스명.                                                                                                        |


# 단일 relay

```text
Outbox PENDING 저장
└─ next_attempt_at = created_at (즉시 발행 대상)

Relay 실행
└─ 이전 조회·발행 처리가 끝난 뒤 1초 대기 (fixedDelay)
   └─ next_attempt_at ≤ 현재 시각인 PENDING·FAILED를 created_at·id 순으로 조회
      └─ 설정된 묶음 크기만큼 한 건씩 순차 처리
         ├─ 발행 시도 시작: attempt_count 증가·저장
         ├─ 주문 TX 밖에서 저장된 topic·message_key·payload를 Kafka로 전송
         └─ producer future 결과 확인 (broker 확인을 받을 수 있는 acks 설정)
            ├─ 성공
            │  └─ 별도 DB TX에서 PUBLISHED·published_at 저장
            └─ 실패
               ├─ 재시도로 해결할 수 없는 오류 → BLOCKED
               └─ 재시도 가능한 오류 또는 결과 불명(timeout)
                  ├─ 최대 시도 횟수 도달 → BLOCKED
                  └─ 시도 횟수 남음
                     └─ FAILED·next_attempt_at(현재 시각 + 폴링 간격)·last_error 저장
                        └─ 해당 시각 이후 다음 폴링에서 재시도
```

broker 장애가 회복되면 별도 복구 작업 없이 relay의 기본 폴링이 `PENDING`과 재시도 시각이 지난 `FAILED` 행을 다시 처리한다.


| 설정 항목    | 예시 설정 키                      | 의미                                                | 값       |
| -------- | ---------------------------- | ------------------------------------------------- | ------- |
| 폴링 간격    | `outbox.relay.poll-interval` | 한 번의 조회·발행 처리가 끝난 뒤 다음 실행까지 기다리는 시간(`fixedDelay`) | 기본 `1초` |
| 조회 묶음 크기 | `outbox.relay.batch-size`    | 한 번의 실행에서 순차 처리할 최대 Outbox 행 수                    | 미정      |
| 최대 시도 횟수 | `outbox.relay.max-attempts`  | 재시도 가능한 오류가 반복될 때 `BLOCKED`로 전환하기까지 허용할 발행 시도 횟수  | 미정      |
