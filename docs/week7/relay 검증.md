# Transactional Outbox의 Relay가 제대로 구현되었는지 검증하기

## 1. 연구 배경

Transactional Outbox 패턴은 비즈니스 데이터 변경과 이벤트 저장을 하나의 DB 트랜잭션으로 묶어, DB 커밋 이후 이벤트 발행에 실패하면서 발생하는 유실 문제를 해결한다.

하지만 Outbox에 이벤트를 저장했다고 해서 이벤트가 반드시 Kafka에 전달되는 것은 아니다.

실제 이벤트 전달은 Relay가 담당한다.

```
[Business Service]
        │
        ▼
[MySQL]
  ├── Business Data
  └── Outbox Event
        │
        ▼
[Outbox Relay]
        │
        ▼
      Kafka
```

Relay는 미발행 이벤트를 조회하고, Kafka에 발행한 뒤 전송 결과를 DB에 기록한다.

이 과정에서 잘못된 조회 조건, 상태 관리 오류, 재시도 로직 결함 등이 존재한다면 Outbox에 이벤트가 정상적으로 저장되었더라도 실제 전달은 실패할 수 있다.

그렇다면 다음 질문이 생긴다.

**우리는 Relay가 제대로 구현되었다는 사실을 어떻게 검증할 수 있을까?**

단순히 정상적인 이벤트 발행 테스트가 통과했다는 이유만으로 Relay를 신뢰할 수 있을까?

이번 연구에서는 Relay의 정확성을 정의하고, 의도적인 결함과 장애를 주입해 테스트가 잘못된 구현을 실제로 발견할 수 있는지 검증한다.

---

## 2. 연구 목표

**핵심 목표: Relay가 올바르게 구현되었는지 판단할 수 있는 검증 체계를 설계한다.**

이를 위해 다음 네 가지 영역을 다룬다.


| 영역                        | 핵심 질문                        |
| ------------------------- | ---------------------------- |
| 테스트 전략                    | Relay의 정확성을 어떤 기준으로 판단할 것인가? |
| 장애 주입 (Fault Injection)   | 장애 상황에서도 요구한 동작을 유지하는가?      |
| 변이 테스트 (Mutation Testing) | 잘못된 구현을 테스트가 실제로 발견하는가?      |
| 시스템 신뢰성                   | 검증 결과를 근거로 어디까지 신뢰할 수 있는가?   |


### 연구에서 답할 질문

1. Relay가 반드시 지켜야 하는 불변조건은 무엇인가?
2. 어떤 입력과 장애 상황에서 불변조건이 깨질 수 있는가?
3. 정상적인 통합 테스트만으로 구현 결함을 발견할 수 있는가?
4. 의도적으로 결함을 주입하면 기존 테스트는 얼마나 탐지하는가?
5. 테스트를 보강한 이후 실제로 검증력이 향상되었는가?

### 연구 범위

이번 연구는 **정확성 검증**에 집중한다.

처리량 최적화, 다중 Relay 확장, Kafka 파티션 확장, Consumer의 비즈니스 정합성은 주요 연구 범위에서 제외한다.

## 3. 실험 환경


| 구성 요소              | 기술                      |
| ------------------ | ----------------------- |
| Application        | Spring Boot / Java 21   |
| Database           | MySQL 8                 |
| Message Broker     | Apache Kafka            |
| Relay              | 단일 DB Polling Worker    |
| Testing            | JUnit 5, Testcontainers |
| Fault Injection    | 테스트 Hook 및 프로세스 강제 종료   |
| Mutation Testing   | 수동 결함 주입, 필요시 PIT       |
| Delivery Semantics | At-least-once           |


### 기본 처리 흐름

```
1. 비즈니스 트랜잭션 시작
           ↓
2. 비즈니스 데이터 변경
           ↓
3. Outbox 이벤트 저장
           ↓
4. DB COMMIT
           ↓
5. Relay가 PENDING 조회
           ↓
6. Kafka 이벤트 발행
           ↓
7. Kafka 성공 ACK 확인
           ↓
8. Outbox SENT 기록
```

이벤트에는 최소한 다음 정보를 저장한다.

```
event_id
aggregate_id
event_type
payload
status
created_at
published_at
retry_count
```

`event_id`는 이벤트를 유일하게 식별하며, 재발행 시에도 변경되지 않아야 한다.

초기 구현에서는 Outbox 기록을 삭제하지 않고 보존한다. 실험 중 이벤트의 생성, 발행, 재시도 이력을 확인하기 위해서다.

## 4. Relay의 불변조건 정의

테스트를 작성하기 전에 Relay가 반드시 만족해야 할 조건을 정의한다.

### INV-01. ACK 이전에는 발행 완료로 기록하지 않는다

Kafka의 성공 ACK가 확인되지 않은 이벤트를 `SENT`로 변경해서는 안 된다.

```
Kafka 전송 실패
       ↓
Outbox SENT  (잘못된 구현)
```

검증 기준:

- Kafka 전송에 실패하면 `SENT`가 되어서는 안 된다.
- Kafka 성공 ACK를 확인한 뒤에만 `SENT`로 전이한다.
- Kafka 발행 성공과 DB 상태 갱신 실패는 구분한다.

### INV-02. 커밋된 이벤트는 조회에서 영구 누락되지 않는다

DB에 커밋된 모든 Outbox 이벤트는 Relay의 처리 대상이 되어야 한다.

대표적인 위험은 ID 생성 순서와 트랜잭션 커밋 순서가 다른 상황이다.

```
Transaction A: ID 100 생성 (미커밋)
Transaction B: ID 101 생성 → COMMIT

Relay: ID 101 조회
Relay: last_id = 101

Transaction A: COMMIT

Relay: WHERE id > 101
```

이 경우 ID 100이 영원히 조회되지 않을 수 있다.

검증 기준:

- 트랜잭션 커밋 순서가 바뀌어도 이벤트를 놓치지 않는다.
- 배치 크기보다 이벤트 수가 많아도 모든 이벤트를 조회한다.
- 이전 조회에서 발견하지 못한 이벤트를 이후 폴링에서 발견할 수 있다.

### INV-03. 장애가 발생해도 미완료 이벤트는 복구 가능해야 한다

Relay가 어느 시점에 종료되더라도 미발행 이벤트가 재처리 불가능한 상태로 남아서는 안 된다.

검증 기준:

- 전송 전 종료 → 재시도 가능
- 전송 중 종료 → 재시도 가능
- ACK 이후 종료 → 중복 발행 가능, 유실 방지
- DB 상태 변경 실패 → 재시도 가능

단, 장애가 복구되고 Relay가 정상적으로 다시 실행된다는 전제가 필요하다.

### INV-04. 재발행 시 이벤트의 식별자는 유지된다

동일 이벤트를 재시도한다고 해서 새로운 비즈니스 사건이 생성되는 것은 아니다.

```
최초 발행: event-001
재시도:    event-001
```

검증 기준:

- 재시도 시 `event_id`가 변경되지 않는다.
- 이벤트의 핵심 payload가 임의로 변경되지 않는다.
- 동일 `event_id`의 중복 발행은 At-least-once 정책에서 허용한다.

### INV-05. 최종적으로 모든 커밋 이벤트가 전달되어야 한다

모든 장애가 복구되고 이벤트가 유효하다면, 커밋된 이벤트는 결국 Kafka에 전달되어야 한다.

MySQL에 커밋된 이벤트 ID 집합을 A, Kafka에서 실제 관측한 이벤트 ID 집합을 B라고 하자.

최종 검증 조건:

**A ⊆ B**

즉, 모든 커밋 이벤트의 ID가 Kafka 전달 결과에 최소 한 번 등장해야 한다.

단, 이 조건은 모든 이벤트가 발행 가능하고 Kafka와 Relay가 복구되어 정상적으로 동작한다는 전제에서 검증한다.

잘못된 payload처럼 재시도만으로 해결할 수 없는 영구 실패는 별도의 격리 및 복구 정책으로 다룬다.

## 5. 테스트 전략 수립

테스트를 세 가지 계층으로 나눈다.

### 5.1 단위 테스트

외부 시스템 없이 Relay 내부 로직을 검증한다.

- 발행 대상 조회 조건
- 상태 전이 규칙
- 재시도 가능 여부
- 재시도 지연 계산
- 이벤트 ID 유지

목표는 개별 로직의 정확성을 빠르게 확인하는 것이다.

### 5.2 통합 테스트

Testcontainers를 사용해 실제 MySQL과 Kafka를 실행한다.

- DB 트랜잭션 커밋
- Relay 폴링
- Kafka 발행 및 ACK 확인
- Outbox 상태 변경
- 실제 Kafka 이벤트 수신

Mock으로 성공을 가정하는 대신 실제 인프라와 연동해 검증한다.

### 5.3 장애 주입 테스트

Relay 실행 중 특정 지점에 장애를 발생시킨다.

- Kafka 전송 직전
- Kafka 전송 진행 중
- Kafka ACK 이후
- DB 상태 변경 직전
- DB 상태 변경 실패 시점

장애 시점을 정확히 통제하기 위해 테스트 Hook을 활용한다.

프로세스 종료가 필요한 경우 별도 Relay 프로세스를 실행해 강제 종료한다.

## 6. 결함 주입 실험 설계

두 종류의 실험을 구분한다.

- **Fault Injection:** 정상 구현에 장애를 발생시켜 복구 동작을 검증한다.
- **Mutation Testing:** 구현을 의도적으로 잘못 변경하고 테스트가 결함을 발견하는지 검증한다.

### 실험 A. Kafka ACK 이전에 SENT 처리

결함:

Kafka 전송을 요청한 직후, 성공 여부를 확인하지 않고 Outbox를 `SENT`로 변경한다.

검증:

1. 정상 Relay 테스트를 실행한다.
2. ACK 확인 로직을 제거한다.
3. Kafka 전송 실패를 발생시킨다.
4. 기존 테스트가 잘못된 `SENT` 전이를 발견하는지 확인한다.

기대 결과:

**ACK를 확인하지 않은 구현은 테스트에 실패해야 한다.**

### 실험 B. 커밋 순서 역전으로 이벤트 누락

결함:

Relay가 마지막으로 읽은 ID 이후의 이벤트만 조회하도록 변경한다.

```
SELECT *
FROM outbox
WHERE id > :last_id
ORDER BY id
LIMIT 100;
```

검증:

1. 트랜잭션 A에서 이벤트 ID 100을 생성하고 커밋을 지연한다.
2. 트랜잭션 B에서 ID 101을 먼저 커밋한다.
3. Relay가 ID 101을 읽고 커서를 이동한다.
4. 트랜잭션 A를 커밋한다.
5. 기존 테스트가 ID 100의 누락을 발견하는지 확인한다.

기대 결과:

**ID 100이 전달되지 않으면 테스트가 실패해야 한다.**

### 실험 C. ACK 이후 Relay 종료

장애:

Kafka 저장과 ACK 확인은 성공했지만, Outbox 상태를 변경하기 전에 Relay를 종료한다.

검증:

1. 이벤트를 Kafka에 발행한다.
2. 성공 ACK를 확인한다.
3. `SENT` 기록 전에 Relay를 강제 종료한다.
4. Relay를 재시작한다.
5. 이벤트가 다시 발행될 수 있는지 확인한다.

기대 결과:

- 이벤트 유실 없음
- 중복 발행 허용
- 동일한 `event_id` 유지
- 최종적으로 `SENT` 도달

### 실험 D. DB 상태 변경 실패

장애:

Kafka 발행에 성공했지만 MySQL의 `SENT` 갱신을 실패시킨다.

검증:

1. Kafka 발행 성공
2. Outbox 상태 갱신 실패
3. DB 장애 복구
4. Relay 재실행
5. 재발행 및 상태 수렴 확인

기대 결과:

**DB 업데이트 실패가 이벤트 유실로 이어져서는 안 된다.**

### 실험 E. 재시도 대상 조회 조건 오류

결함:

재시도해야 할 이벤트가 조회되지 않도록 조회 조건을 변경한다.

검증:

1. Kafka 전송 실패를 발생시킨다.
2. 이벤트가 재시도 가능한 상태로 남는지 확인한다.
3. Kafka를 복구한다.
4. Relay를 반복 실행한다.
5. 이벤트가 실제로 전달되는지 확인한다.

기대 결과:

**재시도 가능한 이벤트가 영구적으로 방치되면 테스트가 실패해야 한다.**

## 7. 테스트의 결함 탐지 능력 평가

이번 연구의 핵심 단계다.

정상 Relay가 테스트를 통과하는 것만으로는 충분하지 않다.

**잘못 구현한 Relay도 테스트를 통과한다면 테스트 자체에 사각지대가 존재한다.**

### 검증 절차

```
불변조건 정의
       ↓
정상 Relay 구현
       ↓
초기 테스트 작성
       ↓
정상 구현 테스트 통과
       ↓
의도적 결함 주입
       ↓
테스트 실행
       │
       ├─ 실패 → 결함 탐지 성공
       │
       └─ 통과 → 테스트 사각지대
                       ↓
                  테스트 보강
                       ↓
                    재검증
```

### 결과 기록


| 결함           | 초기 테스트 | 보강 후 | 관련 불변조건 |
| ------------ | ------ | ---- | ------- |
| ACK 확인 제거    | 미측정    | 미측정  | INV-01  |
| 커밋 순서 역전 누락  | 미측정    | 미측정  | INV-02  |
| 장애 복구 누락     | 미측정    | 미측정  | INV-03  |
| 재시도 시 ID 변경  | 미측정    | 미측정  | INV-04  |
| 재시도 조회 조건 오류 | 미측정    | 미측정  | INV-05  |


결함 탐지 결과는 다음과 같이 구분한다.

- **Killed:** 테스트가 결함을 발견
- **Survived:** 결함이 존재하는데 테스트 통과
- **Invalid/Equivalent:** 유효한 결함이 아니거나 관측 가능한 동작 차이가 없는 경우 별도 제외

### 정량 평가

결함 탐지율은 다음과 같이 계산한다.

[
\text{Mutation Score} =
\frac{\text{탐지된 유효 결함 수}}{\text{전체 유효 결함 수}}
\times 100
]

초기 테스트와 보강된 테스트의 탐지율을 비교한다.

다만 이 수치는 주입한 결함 집합에 대한 탐지율이며, 시스템 전체의 신뢰성을 직접 나타내는 수치는 아니다.

## 8. 독립적인 전달 결과 검증

Relay가 기록한 `SENT` 상태만으로는 이벤트 전달 성공을 검증할 수 없다.

따라서 Relay와 독립적인 검증 수단을 둔다.

### 검증 구조

```
[MySQL Outbox]
      │
      ▼
    Relay
      │
      ▼
    Kafka
      │
      ▼
[검증용 Consumer]
      │
      ▼
[수신 event_id 기록]
      │
      ▼
[MySQL Outbox와 대사]
```

검증용 Consumer는 Kafka에서 관측한 이벤트 ID와 수신 횟수를 별도로 기록한다.

### 검증 항목

1. MySQL에 커밋된 이벤트가 Kafka에서 최소 한 번 관측되었는가?
2. Outbox가 `SENT`인데 Kafka에서 관측하지 못한 이벤트가 있는가?
3. 중복 발행이 발생했다면 동일 `event_id`를 유지했는가?
4. 장애 복구 후에도 누락된 이벤트가 남아 있는가?

단, Kafka 관측 범위와 테스트 종료 시점을 명확히 통제해야 한다.

Kafka Consumer의 수신 지연이나 일시적 장애를 Relay의 유실로 잘못 판정하지 않도록, 검증용 Consumer가 테스트 대상 기록을 끝까지 읽었는지 확인한다.

또한 Kafka 보관 기간 때문에 과거 레코드가 삭제되지 않도록 테스트 환경을 구성한다.

## 9. 최종 평가 기준

이번 연구에서 Relay의 정확성은 다음 기준으로 평가한다.


| 평가 항목  | 성공 기준                    |
| ------ | ------------------------ |
| 불변조건   | 정의한 조건을 검증 가능한 시나리오에서 충족 |
| 정상 처리  | 모든 테스트 이벤트 전달 성공         |
| 장애 복구  | 장애 복구 후 미발행 이벤트 처리 가능    |
| 데이터 대사 | 커밋 이벤트의 전달 누락 0건         |
| 결함 탐지  | 주입한 유효 결함의 탐지 여부 기록      |
| 테스트 개선 | 초기 테스트가 놓친 결함을 보강 후 탐지   |
| 한계 분석  | 검증하지 못한 장애 및 보장 범위 명시    |


특히 **모든 테스트가 통과했다고 해서 모든 장애 상황에 대한 정확성이 증명되는 것은 아니다.**

이번 연구에서 어떤 조건을 검증했고, 어떤 조건은 검증하지 못했는지를 명확히 구분한다.

## 12. 기대 결과

이번 연구에서 얻고자 하는 결과는 단순히 정상적으로 동작하는 Relay가 아니다.

**Relay 구현이 잘못되었을 때 그 결함을 발견할 수 있는 검증 체계**다.

기존 성능 중심 실험에서는 병목을 발견하고 개선한 뒤, 응답 시간과 처리량으로 결과를 판단했다.

이번에는 불변조건을 정의하고 의도적으로 결함을 주입해, 테스트가 얼마나 효과적으로 잘못된 구현을 찾아내는지 평가한다.

최종적으로 다음 질문에 답하는 것을 목표로 한다.

**“테스트가 통과했다는 이유만으로 Relay를 신뢰할 수 있을까? 아니면 잘못된 구현을 실제로 걸러낼 수 있다는 증거가 필요할까?”**

이번 연구의 핵심은 Relay의 완전무결함을 증명하는 것이 아니라, **어떤 근거와 검증 범위 안에서 Relay를 신뢰할 수 있는지 설명하는 것**이다.
