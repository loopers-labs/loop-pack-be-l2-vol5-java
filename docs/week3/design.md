# 3주차 설계: 트랜잭션과 동시성

트랜잭션과 락을 별도로 정리하고, 각 항목에 **고민과 판단·이유**를 남긴다.

- **트랜잭션:** 한 요청에서 어떤 변경을 함께 성공하거나 되돌릴 것인가?
- **락과 동시성 제어:** 여러 요청이 겹칠 때 어떤 판단·변경을 보호할 것인가?

테스트 케이스와 실행 결과는 [구현 기록](./implementation-log.md)에 별도로 정리한다.

## 1. 트랜잭션

아래 진입점은 Controller 또는 다른 Spring bean에서 호출한다. `@Transactional` 프록시가 시작한 트랜잭션에 내부 서비스·repository가 기본 `REQUIRED`로 참여한다. 같은 객체 안의 메서드 호출이 새로운 트랜잭션을 시작한다고 가정하지 않는다.

| 흐름 | 호출 경로와 트랜잭션 경계 |
| --- | --- |
| 브랜드 삭제 | Controller → **BrandFacade.delete()** → BrandService·ProductRepository → JPA |
| 주문 확정 | Controller → **OrderFacade.confirm()** → OrderConfirmationService → OrderService·ProductService·PointBalanceService → repository·JPA |
| 충전 | Controller → **PointFacade.charge()** → UserService·PointBalanceService → repository·JPA |
| 배치 만료 | Scheduler → Batch → **PointExpirationWorker.expire()** → PointBalanceService·repository·JPA (사용자별 경계) |

업무 예외(`CoreException`)와 처리 중 RuntimeException을 바깥으로 전달해 이번 트랜잭션의 변경을 함께 롤백한다. `save()`나 `flush()`는 commit이 아니다. 배치의 실패 처리는 사용자별 트랜잭션이 종료된 뒤 바깥 Batch에서 한다. commit 응답 자체를 받지 못한 경우에는 DB 반영 여부가 불명확할 수 있어 오류 응답만으로 롤백 완료를 단정하지 않는다.

### 1.1 브랜드 일괄 삭제

**고민:** 브랜드만 삭제되거나 일부 상품만 삭제되면 사용 가능한 상품과 브랜드 상태가 어긋난다. 과거 주문 정보까지 지워져서도 안 된다.

**판단·이유:** `BrandFacade.delete()`에서 브랜드와 연결된 미삭제 상품의 논리 삭제를 한 트랜잭션으로 묶는다. 중간 실패 시 이번 요청의 변경을 모두 되돌리고, 다른 브랜드와 과거 주문은 유지한다.

### 1.2 주문 확정

**고민:** 재고만 줄거나, 포인트는 결제됐는데 주문이 미확정으로 남으면 안 된다.

**판단·이유:** 주문·상품 확인부터 재고 차감, 포인트 사용·사용 기록·2% 적립, 주문 확정·결제 결과 저장까지 한 트랜잭션으로 묶는다. `OrderFacade.confirm()`이 시작한 트랜잭션에 `OrderConfirmationService`와 내부 서비스가 참여한다. 안쪽 메서드마다 별도로 커밋하지 않는다.

### 1.3 포인트 충전

**고민:** 충전 지급건만 추가되거나 잔액만 증가하면 포인트 내역과 잔액이 맞지 않는다.

**판단·이유:** `PointFacade.charge()`에서 사용자 확인, 필요한 만료 처리, 충전 지급건·잔액 저장을 함께 묶는다. 현재 `balance`는 지급·사용·만료 내역으로 계산할 수 있는 잔액을 별도로 저장한 합계다. 이 합계와 내역을 함께 저장하므로 둘이 어긋나지 않는지 검증한다.

잔액을 저장하지 않고 매번 유효한 지급액에서 사용·만료 기록을 빼 계산한다면 “지급건과 저장 잔액의 일치” 검증은 필요 없어질 수 있다. 다만 만료 시각과 사용 기록을 반영한 계산, 지급건·기록 저장의 원자성, 동시 결제의 중복 사용 방지는 여전히 확인해야 한다. 단순히 지급액만 더하는 것은 잔액 계산이 아니다. 잔액을 별도로 두는 현재 구조는 유지한다.

### 1.4 사용자·포인트 계정 생성의 원자성

**고민:** 사용자만 저장되고 포인트 계정 생성이 실패하면, 회원에게 포인트 계정이 반드시 존재한다는 정책이 깨진다.

**판단·이유:** `UserRegistrationService.register()`에서 두 저장을 한 트랜잭션으로 묶는다. 계정 생성 정책과 누락 시 응답은 [ADR 0009](../adr/0009-user-owns-existing-point-account.md)에 두고, 여기서는 함께 성공·실패해야 하는 범위만 다룬다.

## 2. 락과 동시성 제어

처음에는 동시에 접근하면 무조건 락을 걸어야 한다고 생각했다. 하지만 UPDATE 자체도 잠금을 사용하면서 갱신 유실이 발생할 수 있었다. 그래서 **어떤 업무 오류를 막을 것인지**부터 정하고 방법을 선택한다.

### 2.1 재고 차감

**고민:** 처음에는 같은 상품에 요청이 몰리면 낙관적 락의 버전 충돌과 재시도가 많아질 수 있다고 생각했다. 여러 요청이 같은 버전을 읽으면 먼저 변경한 요청만 성공하고 나머지는 충돌할 수 있다. 다만 매번 한 요청만 성공하며 `100 → 99 → 98`번씩 재시도한다는 것은 극단적인 가정이지 실제 실행 횟수가 아니다. 충돌 빈도는 같은 행에 대한 요청이 얼마나 겹치는지와 처리 시간에 따라 달라지며, 자동 재시도 대신 충돌 응답으로 끝내는 정책도 가능하다.

비관적 락과 조건부 UPDATE는 기다린 뒤 현재 값으로 처리할 수 있어 버전 충돌 후 다시 읽고 계산하는 과정을 줄일 수 있다. 다만 교착·시간 초과까지 없어지는 것은 아니다. 여기서는 충돌 후 처리 비용을 고려해 다른 두 방법을 우선 비교했다.

그 다음으로는 조건부 UPDATE면 충분하다고 생각했다. 내가 먼저 읽은 재고로 새 수량을 계산해서 저장하면, 그 사이 다른 주문이 바꾼 재고를 덮어쓸 수 있었다. 반면 아래 SQL은 DB가 재고가 충분한지 확인하면서 바로 차감한다.

```sql
UPDATE product
SET quantity = quantity - :orderQuantity
WHERE id = :productId
  AND quantity >= :orderQuantity;
```

SQL 실험에서도 뒤 요청이 기다렸다가 앞 요청의 커밋 후 남은 재고로 조건을 판단했고, 부족하면 변경 건수가 0이었다. 재고 차감이라는 문제는 이 한 문장으로 해결할 수 있어 보였고, 별도로 잠그고 조회하는 단계도 줄일 수 있어서 이 방법을 골랐다. 양수 주문 수량 검증과 변경 건수 확인은 별도로 필요하다.

이후에는 “동시에 차감해도 안전한가?”뿐 아니라 “이미 만든 재고 코드를 어떻게 사용할 것인가?”도 비교했다. 현재 `Product`는 안에 `Stock`을 가지고 있다. 상품에 차감을 요청하면 `Stock.decrease()`가 수량을 검사하고 차감된 새 값을 반환한다. 이 행동을 유지할지, 실제 차감을 SQL에 맡길지 고민한 것이다.

| 대안 | 장점 | 고려할 비용 |
| --- | --- | --- |
| 비관적 락으로 조회 후 `Stock.decrease()` | 지금처럼 상품을 가져와 `Stock`으로 차감하면 JPA가 바뀐 재고를 DB에 저장한다 | 잠금 유지 시간·순서, 대기·교착 실패 처리 |
| 조건부 UPDATE | DB에서 현재 수량 검사와 차감을 함께 수행한다 | SQL과 `Stock`의 검사 조건을 맞춰야 한다. SQL로 바꾼 재고와 이미 가져온 상품 객체의 값이 달라질 수도 있다 |
| 낙관적 락 (버전 조건 UPDATE) | 읽는 시점에는 잠그지 않아 충돌이 드물면 비용이 적다 | 재고 5에 주문 8건이 몰리는 것처럼 충돌이 빈번하면, 충돌한 요청을 다시 처리하려면 새 트랜잭션에서 읽고 계산해야 한다. 재시도를 선택하면 횟수·시간 한도도 관리해야 한다. 충돌 오류로 종료하는 정책도 가능하다 |

**판단·이유:** 비관적 락을 선택했다. 지금의 “상품 조회 → 상품 안의 Stock으로 차감 → 바뀐 값을 DB에 저장” 흐름을 유지하고, 조회할 때 잠금을 추가하기로 했다. 조건부 UPDATE로 재고를 보호할 수 있다는 처음 판단은 여전히 맞다. 낙관적 락도 정확하게 구현할 수 있지만, 재고가 남은 요청을 충돌 후 다시 처리하려면 재시도 정책이 필요하다는 비용을 고려했다. 조건부 UPDATE는 한 SQL에서 검사와 차감이 함께 일어나 버전 충돌에 따른 재시도가 필요 없지만, 이번에는 기존 `Stock` 코드를 활용하기 쉬운 쪽을 우선했다.

SQL과 객체에 같은 조건이 있다는 사실만으로 잘못된 설계인 것은 아니다. 객체의 업무 규칙과 DB의 동시성 방어를 나누는 선택도 가능하다. 이번에는 기존 행동과 JPA 저장 흐름을 유지하는 비용을 더 중요하게 봤다. 수동 SQL 실험은 대기와 갱신 결과를 이해하는 근거이며, 두 방식의 실서비스 성능이 같거나 비관적 락이 더 빠르다는 근거로 삼지 않는다.

잠금을 얻었다고 재고 부족이 자동으로 거절되는 것은 아니다. 주문 서비스는 상품을 ID 순으로 하나씩 `FOR UPDATE` 조회하고, 잠금을 얻은 뒤 읽은 재고로 사전 검사한다. 모든 품목의 검사가 끝난 다음 차감하며, `Stock.decrease()`도 실제 차감할 때 다시 검사한다. 다른 코드가 주문 서비스의 검사를 거치지 않고 차감을 요청해도, `Stock`이 음수 재고를 만들지 않도록 하기 위해 두 검사를 유지한다.

주문 확정은 **상품 ID 오름차순**으로 잠금 조회·차감하며 잠금은 주문 트랜잭션 종료까지 유지한다. 잠금은 주문 차감에만 적용하면 충분하지 않다. 현재 코드에서 확인한 Hibernate SQL은 상품 이름만 바꿔도 재고 컬럼을 함께 저장한다. 예를 들어 수정 요청이 재고 5를 읽고, 다른 주문이 4로 줄인 뒤 수정 요청이 저장하면 5로 덮어쓸 수 있다. 그래서 관리자 재고 설정·수정·삭제와 브랜드 일괄 삭제도 상품을 잠그며 조회한다. 이는 현재 저장 방식에서 재고를 덮어쓰지 않기 위한 조치다. 이름만 갱신하는 SQL 등으로 바꾸면 잠금 범위를 다시 검토할 수 있지만, 삭제·재고 변경의 경쟁까지 자동으로 해결되는 것은 아니다. 일반 고객 조회는 기존 조회를 유지한다.

### 2.2 상품 등록과 브랜드 삭제

**고민:** 상품 등록이 브랜드를 확인한 뒤, 다른 요청이 그 브랜드를 삭제하면 삭제된 브랜드에 새 상품이 남을 수 있다.

**판단·이유:** 상품 등록은 브랜드를 `FOR SHARE`로 조회한다. “상품 등록이 끝날 때까지 이 브랜드를 삭제하거나 바꾸지 말아줘”라는 요청이다. A와 B가 서로 다른 상품을 등록하며 같은 요청을 하는 것은 함께 허용한다. 둘 다 브랜드를 바꾸려는 것은 아니기 때문이다.

브랜드 삭제는 `FOR UPDATE`로 조회한다. A·B가 등록 중이라면 둘의 트랜잭션이 끝날 때까지 기다린다. 반대로 삭제가 먼저 잠갔다면 상품 등록이 기다리고, 삭제가 커밋된 뒤 조회 결과의 삭제 날짜를 확인해 등록을 거절한다. **잠금이 자동으로 등록을 거절하는 것은 아니고, 기다린 뒤 읽은 상태를 코드가 검사한다.**

`ProductFacade.create()`가 브랜드 확인부터 상품 저장까지 묶고, `BrandFacade.delete()`가 브랜드와 상품의 삭제를 묶는다. 안쪽 조회 메서드가 끝나도 잠금은 바깥 트랜잭션의 커밋·롤백까지 유지된다. 브랜드 이름 수정도 삭제 표시를 오래된 값으로 덮어쓰지 않도록 `FOR UPDATE`를 사용한다.

처음에는 브랜드 조건으로 상품을 한꺼번에 잠금 조회하면 충분하다고 생각했다. 그런데 실제로는 다른 브랜드의 기존 상품까지 기다렸다. 그래서 **브랜드 잠금 → 대상 상품 ID만 조회 → ID 순으로 상품을 하나씩 잠금 조회**로 바꿨다. 먼저 상품 객체를 읽어 두지 않고, 잠금을 얻은 뒤 삭제 여부를 다시 판단한다. 호출 횟수는 늘지만 어느 상품을 어떤 순서로 잠그는지가 분명해진다. 후보 조회용 인덱스도 추가했다. 이 흐름은 브랜드 잠금 뒤에 첫 일반 조회를 하고, 새 상품 등록은 같은 브랜드 잠금에 참여하며 상품의 브랜드는 변경하지 않는다는 전제에 의존한다.

**벌크 삭제 대안 검토:** 브랜드 잠금과 트랜잭션은 유지하면서 상품 삭제를 브랜드 조건 UPDATE 한 문장으로 바꾸는 실험을 했다. 실제 SQL 이후 실패하면 두 방식 모두 브랜드·상품이 함께 롤백됐다. 다만 현재 REPEATABLE READ의 실험 조건에서는 벌크가 다른 브랜드의 기존 상품 잠금까지 막았다. 추가 실험에서는 브랜드 100개·통계 갱신 후 브랜드 인덱스를 사용하자 검사한 다른 브랜드 상품 수정이 삭제 커밋 전에도 완료됐다. 따라서 벌크가 항상 다른 브랜드 요청을 막는 것은 아니며, 데이터 분포와 실행 계획에 따라 달라진다. SQL을 줄이는 것과 잠금 범위를 줄이는 것은 다르므로, 이번에는 SQL 증가 비용을 감수하고 ID별 잠금 방식을 유지하기로 결정했다. 벌크의 성능 이점은 인정하지만, 실행 계획에 따른 다른 상품의 잠금 영향까지 고려했다. RC는 애플리케이션 전체뿐 아니라 새로 시작하는 브랜드 삭제 트랜잭션에만 적용할 수도 있다. 이 경우 검토 대상은 삭제 흐름과 경쟁하는 요청이며, 전체 조회 경로 변경이 필수는 아니다. 기존 트랜잭션에 REQUIRED로 합류하면 바깥 격리 수준을 따르므로 실제 시작 경계를 확인해야 한다. 이번에는 기존 방식을 유지하되, 삭제 비용이 문제가 되면 국소 RC·벌크를 먼저 재검토한다. 테스트 삭제 트랜잭션만 RC로 바꾼 추가 비교에서는 네 조건 모두 검사한 다른 브랜드 행의 잠금 충돌이 없었다. 이는 좁은 범위의 관찰이며 전체 서비스의 RC 전환을 검증한 것은 아니다. 비교 조건·수치와 대안은 [ADR 0019](../adr/0019-brand-bulk-deletion-comparison.md)에 분리했다.

주문 확정에는 참고 설계의 Brand 공유 잠금을 추가하지 않는다. 현재 브랜드 일괄 삭제는 연결 Product도 잠그고 삭제하고, 주문 확정은 같은 Product를 잠근 뒤 삭제 여부를 확인한다. 두 경로는 상품 행에서 경쟁한다. 따라서 “브랜드 삭제 요청이 먼저 시작했으니 확정은 반드시 거절”을 보장하는 설계는 아니다. 삭제가 상품 잠금을 얻어 커밋했으면 뒤 확정이 거절되고, 확정이 먼저 상품을 잠갔으면 해당 확정이 끝난 뒤 삭제가 진행할 수 있다.

### 2.3 같은 주문의 중복 확정

**고민:** 기존 주문 조회는 잠금 없는 일반 조회였다. 두 요청이 같은 주문을 모두 DRAFT로 읽으면 재고·포인트 사용·적립이 두 번 실행될 수 있다.

상품 잠금만으로는 부족하다. 뒤 요청이 상품 잠금을 기다리더라도, 앞에서 읽은 주문 상태는 여전히 DRAFT일 수 있다. 기존 코드는 기다린 뒤 주문 상태를 다시 확인하지 않아 재고·잔액이 충분하면 같은 주문을 다시 처리할 수 있다. 따라서 상품 수량뿐 아니라 **이 주문을 이미 확정했는지 판단하는 과정**도 보호해야 한다.

| 대안 | 가능한 처리 | 고려할 비용 |
| --- | --- | --- |
| 주문 행을 `FOR UPDATE`로 조회 | 앞 요청이 끝난 뒤 주문 상태를 읽고 확정 가능 여부를 판단한다 | 주문 트랜잭션이 끝날 때까지 잠금을 유지한다. 같은 주문을 잠그거나 변경하려는 요청은 기다릴 수 있다. 일반 조회까지 모두 막는 것은 아니다. |
| DRAFT일 때만 상태를 바꾸는 조건부 UPDATE | 상태 변경 건수로 처리 가능 여부를 판단하고, 재고·포인트 변경을 같은 트랜잭션에 묶는다 | UPDATE도 잠금을 사용하며 앞 요청을 기다릴 수 있다. 상태를 SQL로 바꿀 때 기존 주문 객체와 DB의 값을 맞추는 처리도 필요하다. |
| 버전을 사용하는 낙관적 락 | 읽은 뒤 다른 요청이 주문을 변경했으면 충돌을 감지하고 이번 요청 전체를 롤백한다 | 충돌 후 최신 상태를 확인해 어떤 오류로 응답할지 정해야 한다. 자동 재시도가 반드시 필요한 것은 아니다. |

**판단·이유:** 주문 행을 `FOR UPDATE`로 조회한 뒤 소유자·상태를 검사하기로 했다. 앞 요청이 성공하면 CONFIRMED를 보고 거절하고, 앞 요청이 롤백되면 DRAFT를 보고 다시 판단하는 흐름을 직접 표현하기 쉽기 때문이다. 다른 방법으로 해결할 수 없어서 제외한 것은 아니다.

조건부 UPDATE도 재고·포인트 처리와 **같은 트랜잭션**에 묶으면 중간 실패 시 상태 변경까지 롤백된다. 별도로 DRAFT로 되돌리는 보정이 필요한 것은 아니다. 또한 `WHERE status = 'DRAFT'`는 이 상태 전환을 보호할 수 있지만, 주문의 모든 변경을 감지하는 버전 검사와 완전히 같지는 않다.

과제에 따라 새 요청키(idempotency key)나 이전 성공 응답 재사용은 추가하지 않는다. 이미 확정된 주문은 상태 오류로 처리한다. 이는 이번 API의 응답 정책이며, 낙관적 락이나 요청키 방식이 일반적으로 불필요하다는 뜻은 아니다.

### 2.4 포인트 결제·충전·만료

만료일 계산과 매일 실행할 배치의 정책은 [ADR 0015](../adr/0015-point-expiration-uses-date-boundary-and-daily-batch.md)에 정리한다. 여기서는 배치와 결제·충전이 겹칠 때 지켜야 할 결과와 보호 방법을 다룬다.

**처음 생각 — 재고처럼 잔액만 조건부 차감하면 되지 않을까?**

처음에는 `balance >= 결제액`일 때만 잔액을 차감하면 충분하다고 생각했다. 재고에서 확인한 조건부 UPDATE처럼, DB가 현재 숫자를 확인하고 바로 차감하면 잔액이 부족한 결제를 막을 수 있기 때문이다.

**만료를 생각하니 — 저장된 잔액이 지금 사용할 수 있는 금액과 다를 수 있었다.**

예를 들어 저장 잔액은 1,000원이지만, 그중 300원의 만료 시각이 이미 지났고 배치가 아직 처리하지 않았다고 해 보자. 잔액 숫자만 보면 800원 결제가 가능하지만, 실제로 사용할 수 있는 금액은 700원이므로 거절해야 한다. 그래서 결제 전에 지급건의 만료일과 남은 금액을 확인하고, 만료 기록과 잔액을 함께 정리해야 한다. 배치가 먼저 실행됐는지에 따라 만료 포인트의 사용 가능 여부가 달라져서는 안 된다.

결제가 가능해도 끝이 아니다. 유효한 지급건 중 사용 순서에 따라 **어느 지급건에서 얼마를 쓸지** 고르고, 여러 지급건에 나누어 사용했다면 각각의 사용 기록을 남겨야 한다. 즉, 내 포인트의 결제는 잔액 숫자 하나를 빼는 일이 아니었다.

**그러면 어디서부터 다른 요청을 기다리게 해야 할까?**

지급건을 읽고 판단한 다음 잔액을 저장할 때만 순서를 정하면 늦을 수 있다. 결제와 배치가 같은 만료분 300원을 각각 발견해 중복으로 만료 기록을 남길 수 있고, 두 결제가 같은 지급건의 남은 금액을 각각 사용 가능하다고 판단할 수도 있다. 잔액의 초과 차감을 막는 것과 지급건별 사용·만료를 올바르게 기록하는 것은 함께 해결해야 할 문제다.

그래서 **같은 사용자의 지급건을 확인하고 선택하는 시점부터** 변경이 겹치지 않게 하기로 했다. 결제·충전·잔액 조회·배치가 모두 먼저 그 사용자의 잔액 행을 잠근다. 뒤 요청은 앞 요청의 트랜잭션이 끝난 뒤 최신 지급건·사용 기록을 읽고 판단한다. 잔액 행만 잠그면 다른 테이블까지 자동으로 보호되는 것이 아니라, 모든 포인트 변경 경로가 이 순서를 지키기 때문에 사용자의 처리를 차례로 진행할 수 있다.

```text
사용자 잔액 행을 FOR UPDATE로 조회
→ 지급건·사용 기록을 최신 상태로 조회
→ 이미 만료된 금액을 정리하고 사용 가능한 잔액 판단
→ 사용할 지급건 선택·사용 기록·잔액 차감·2% 적립
→ 주문의 재고·상태 변경과 함께 commit 또는 rollback
```

위 흐름은 주문 결제 기준이다. 충전·잔액 조회·배치도 같은 잠금으로 시작하지만, 이후에는 각 요청에 필요한 만료·충전 등의 행동만 수행한다.

**대안과 비교해 비관적 락을 선택한 이유**

| 대안 | 내 포인트 흐름에 적용하면 | 선택할 때 감수할 비용 |
| --- | --- | --- |
| 비관적 락 | 지급건을 판단하기 전에 잔액 행을 잠그고, 앞 요청이 끝난 뒤 최신 내역으로 만료·사용을 계산한다 | 판단·저장이 끝날 때까지 잠금을 유지한다. 내역이 많거나 앞 요청이 오래 걸리면 대기가 길어질 수 있다 |
| 조건부 UPDATE | 잔액 숫자의 초과 차감은 막을 수 있다. 만료·지급건 처리까지 보호하려면 UPDATE로 먼저 잠금을 확보하고 최신 내역을 읽는 등의 순서를 추가로 설계해야 한다 | 현재는 만료를 정리해야 실제 결제 가능액을 알 수 있다. 내역 처리 순서와 SQL·JPA 객체의 상태도 맞춰야 한다 |
| 대표 잔액 버전의 낙관적 락 | 먼저 지급건을 읽고 계산하되, 다른 포인트 변경이 있었으면 버전 충돌로 이번 변경을 거절한다 | 모든 변경 경로가 대표 버전을 확인·증가시켜야 한다. 충돌하면 주문 전체를 롤백하고, 오류로 끝낼지 새 트랜잭션으로 재시도할지 정해야 한다 |

사용자 단위라 충돌이 드물 것으로 예상해 낙관적 락도 고민했다. 하지만 이번에는 **만료 확인과 지급건 선택을 기존 객체 행동으로 수행하면서, 그 판단 전에 요청의 순서를 정하는 방식**이 더 직접적이라고 판단했다. 충돌 후 주문 전체를 되돌려 다시 판단하는 흐름보다, 먼저 기다린 뒤 판단하는 흐름을 선택한 것이다. 자동 재시도는 낙관적 락의 필수 조건은 아니며, 충돌 응답으로 끝내는 선택도 가능하다.

만료가 있거나 여러 테이블을 사용한다고 비관적 락만 가능한 것은 아니다. 조건부 UPDATE와 낙관적 락도 올바르게 설계할 수 있다. 이번 선택의 이유는 성능 우위가 아니라, **현재의 만료 정리 → 지급건 선택 → 사용·적립이라는 행동을 유지하면서 판단부터 저장까지 보호하기 쉽다는 점**이다.

**적용 범위:** 결제·충전·잔액 조회·배치가 모두 같은 사용자 잔액 잠금 규칙을 지킨다. 특히 결제와 충전이 같은 만료 지급건을 동시에 발견하는 경우, 그리고 잔액 조회와 배치가 겹치는 경우에도 동일한 만료 기록이 중복 생성되지 않아야 한다. 배치도 이 규칙에 참여하며, 한 번의 만료 처리에서 만료 기록과 잔액 변경은 함께 성공하거나 롤백되어야 한다. 배치는 사용자 한 명씩 트랜잭션을 적용한다. 실패한 사용자만 롤백하고, 배치는 다음 사용자를 계속 처리한다.

**잠금 대상의 전제:** 회원 생성 시 잔액 행도 생성한다는 [계정 생성 정책](../adr/0009-user-owns-existing-point-account.md)에 따라, 첫 포인트 요청부터 잠글 행이 존재한다.

**조회 방법:** 결제·충전·잔액 조회·배치는 `getRequired()`를 통해 잔액 행을 먼저 잠그고 지급건·사용 기록을 각각 잠금 조회한다. 이전 REPEATABLE READ 스냅샷을 사용하는 일반 지연 조회를 피하기 위해서다. 최초 포인트 조회부터 이 경로를 사용하며, 먼저 일반 조회한 객체가 나중의 잠금 조회만으로 최신 상태가 된다고 가정하지 않는다.

**남은 비용과 재검토 기준:** 현재 조회는 사용 완료·만료된 것을 포함한 지급건과 사용 기록 전체를 가져온다. 잔액 확인·사용·적립에서 같은 잠금 조회 경로를 다시 호출하기도 한다. 이력을 모두 읽고 계산하는 비용은 현재 모델·조회 방식의 비용이며, 낙관적 락으로 바꾸는 것만으로 사라지지 않는다. 이력이 늘면 처리 시간과 잠금 유지 시간이 길어질 수 있으므로, 실제 SQL 횟수·조회 행 수·처리 시간을 측정한 뒤 반복 조회와 조회 범위를 개선할지 판단한다. 아직 이력 규모별 성능은 측정하지 않았다.

사용자별 잔액을 잠근다고 다른 사용자에게 영향이 없지는 않다. 주문은 상품을 잠근 채 포인트를 처리하므로, 포인트 처리가 길어지면 다른 사용자의 같은 상품 주문도 기다릴 수 있다. 연결 부족에 따른 영향은 3.3에 정리한다.

## 3. 추가 동시성 판단

### 3.1 좋아요 관계의 동시성 범위

**고민:** 같은 사용자가 같은 상품에 좋아요를 동시에 등록하면 관계가 중복될 수 있다. 등록과 취소가 겹치거나 상품 삭제와 등록이 겹치는 경우에도 최종 상태를 정해야 한다.

**현재 판단:** 좋아요 수는 사용자–상품 관계에서 계산하고, 같은 관계의 중복 저장은 `(user_id, product_id)` 유니크 제약으로 막는다. 별도 카운터를 갱신하지 않으므로 좋아요 수를 맞추기 위한 별도 잠금은 두지 않는다. 다만 유니크 제약이 등록·취소의 처리 순서나 삭제된 상품에 관계가 남아도 되는지까지 결정하지는 않는다.

**구현 판단:** 유니크 제약이 중복 저장을 막는 것과, 중복 요청에 정상 응답하는 것은 별개였다. 미리 관계를 조회해도 두 요청이 모두 없다고 읽을 수 있어, 등록은 INSERT 결과와 해당 유니크 제약 충돌로 구분한다. 취소도 먼저 읽은 엔티티를 지우면 다른 요청이 이미 지운 경우 오류가 날 수 있어 사용자·상품 조건의 DELETE로 바꿨다. 최초 등록 201·중복 등록 200·취소 204 계약을 유지한다. 상품 전체를 잠가 서로 다른 사용자의 좋아요를 줄 세우지는 않는다. 명시적인 잠금 조회를 추가하지 않는 것이며, INSERT·DELETE와 유니크 검사에 필요한 DB 내부 잠금까지 없다는 뜻은 아니다.

좋아요 INSERT·DELETE에는 JdbcTemplate을 사용해 같은 DataSource의 바깥 JPA 트랜잭션에 참여시킨다. JPA 저장 실패로 트랜잭션이 롤백 전용이 된 뒤 예외만 삼키는 방식을 피했다. 해당 관계 유니크 충돌만 중복으로 처리하며 다른 저장 오류·교착·대기 초과는 숨기지 않는다. 기존 조회는 JPA를 유지한다.

**경쟁 정책:** 등록·취소가 겹치면 DB에서 실제 처리된 순서의 결과를 허용한다. 먼저 클릭한 순서를 서버가 보장하지 않는다. 삭제와 겹쳐 남은 관계는 목록에서 숨기고 본인 취소는 허용한다. 상품 삭제 완료 후 시작한 새 등록은 기존처럼 404로 거절한다. 삭제된 상품의 좋아요는 노출·구매에 사용하지 않으므로, 관계가 남는 것까지 막으려고 상품 잠금을 추가하지 않기로 했다.

### 3.2 전체 잠금 순서와 대기 실패

주문은 **주문 → 상품 ID 오름차순 → 포인트 잔액 → 지급건·사용 기록** 순서로 잠근다. 충전·잔액 조회·만료 배치는 포인트 경로만 사용하며 상품을 역으로 잠그지 않는다. 브랜드 삭제는 브랜드를 먼저 잠그고 연결 상품을 잠근다.

잠금 순서를 맞춰도 모든 교착과 대기 초과가 없어지는 것은 아니다. 발생하면 예외를 트랜잭션 밖으로 전달해 이번 요청의 변경을 롤백하고, 다른 요청이 커밋한 변경은 유지한다. 잠금 대기 초과·교착은 503으로 응답하며 자동 재시도는 하지 않는다. 재고·잔액 부족으로 바꾸지 않는다.

업무 조건 위반(409)과 잠금 경쟁으로 처리를 완료하지 못한 경우(503)를 구분한다. 다른 저장 오류는 기존 500을 유지하며, 503을 위해 모든 예외를 잠금 실패로 분류하지 않는다. 재시도는 새 요청의 현재 상태에서 다시 판단해야 하므로 이번 구현에서 자동 반복하지 않는다. 서비스의 잠금 대기 시간은 기존 DB 설정을 따른다. 정상 요청의 잠금 유지 시간과 부하 시 대기를 측정하지 않아 별도 대기 한도를 정하지 않았다. 기존값이 최적이라는 뜻은 아니며, 적절한 대기 한도 결정은 후속 작업으로 남긴다. 테스트에서만 세션 대기 한도를 짧게 설정해 실패 경로를 확인하며, 이 값을 운영에 적합한 시간이라고 판단하지 않는다.


### 3.3 커넥션 풀과 아직 확인하지 않은 비용

**고민:** 다른 사용자의 잔액 행을 직접 잠그지 않더라도, 잠금을 기다리는 요청은 DB 연결을 사용한다. 연결이 모두 사용 중이면 관련 없는 요청도 SQL 실행 전에 연결을 빌리려고 기다릴 수 있다. 따라서 사용자별 잠금이라는 이유로 다른 사용자에게 영향이 없다고 단정하지 않는다.

**현재 판단:** 정확성 검증과 처리량·응답 시간 검증을 구분한다. 동시성 테스트 통과는 해당 조건에서 업무 규칙을 지켰다는 근거이며, 운영 부하에서의 성능을 보장하지 않는다. 연결 수를 늘리거나 잠금 방식을 바꾸기 전에 연결 획득 대기와 DB 행 잠금 대기를 나눠 관찰한다. 현재 설정과 미검증 실험은 [구현 기록 3.3](./implementation-log.md#33-커넥션-풀과-성능의-확인-범위)에 둔다.
