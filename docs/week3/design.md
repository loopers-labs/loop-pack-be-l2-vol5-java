# 커머스 API 설계 — 3주차 · 트랜잭션과 동시성

2주차 설계(`docs/week2/design.md`, 아래에서 **W2**)를 바탕으로 하고, 이번 주에 정한 것만 적는다.
W2 의 절을 가리킬 때는 `W2 6.3` 처럼 쓴다.

## 0. 세 흐름의 경계

프록시를 거치는 곳은 표의 **시작점** 하나뿐이다. 그 아래 도메인 서비스 · 저장소는 같은 빈 안의 자기 호출 없이 다른 빈을 부르고,
`@Transactional` 은 응용 계층에만 있다(W2 6.1). 전파는 모두 기본값 `REQUIRED` 라 저장소 호출은 시작점의 트랜잭션에 합류한다.

| 흐름 | 시작점 (트랜잭션) | 호출 경로 | 잠금 순서 | 업무 예외 → 응답 | 같이 되돌리는 것 |
|---|---|---|---|---|---|
| 브랜드 일괄 삭제 | `BrandFacade.delete` | `BrandService.delete` → `ProductsInBrand.deleteAll` → `ProductRepository.deleteAllByBrandId`(벌크 UPDATE) → `BrandRepository.save` | 브랜드(배타) → 그 브랜드 상품 행(UPDATE) | `BRAND_NOT_FOUND` → 404 | 브랜드 · 연결 상품의 삭제 (2절) |
| 주문 최초 확정 | `OrderFacade.confirm` | `OrderConfirmation.confirm` → `OrderRepository` → `PointUsage.use` → `StockDeduction.deductStock` ×품목 | 주문 → 포인트 → 상품(id 오름차순), 전부 배타 | `ORDER_NOT_FOUND` 404 · `ORDER_NOT_DRAFT` 409 · `INSUFFICIENT_POINT` 409 · `PRODUCT_NOT_FOUND` 404 · `INSUFFICIENT_STOCK` 409 | 재고 · 잔액 · 원장 · `CONFIRMED` · 결제액 (3절) |
| 같은 행의 동시 변경 | `PointFacade.charge` · `ProductFacade.adjustStock` · 위 둘 | 각 서비스가 저장소의 `…ForUpdate` 로 읽고 애그리거트가 판단 | 행 하나(포인트 또는 상품) — 확정과 같은 방향 | `INSUFFICIENT_*` 409 등 | 각 요청 단위 (4절) |

잠금 대기 시간 초과와 데드락은 업무 예외가 아니므로 409 로 바꾸지 않고 503 `LOCK_UNAVAILABLE` 로 답한다(4.5). 커넥션 고갈 같은 그 밖의 기술 오류는 500 이다. 잠금 대기는 3 초에서 포기한다(4.4).
경쟁 테스트는 이것을 "기술 오류" 로 따로 세고, 0 이어야 한다(4.2).

## 1. 격리 수준은 READ COMMITTED 이고, MySQL 서버 옵션이 정한다

MySQL 서버를 `--transaction-isolation=READ-COMMITTED` 옵션으로 띄워, 서버 전체의 기본값(`GLOBAL transaction_isolation`)을 `READ-COMMITTED` 로 둔다.
테스트 서버(`MySqlTestContainersConfig`)와 로컬 서버(`docker/infra-compose.yml`)가 서버 옵션으로 걸고,
애플리케이션은 격리 수준을 지정하지 않는다 — `@Transactional` 에 `isolation` 이 없고, 커넥션 풀 설정도 없다.
`TransactionIsolationIntegrationTest` 가 애플리케이션 트랜잭션이 실제로 그 값으로 도는지 본다.

### 1.1 왜 READ COMMITTED 인가

InnoDB 의 행 잠금은 **인덱스 레코드 잠금**이다. 잠기는 것은 WHERE 에 맞는 행이 아니라 **실행 계획이 훑은 인덱스 레코드**다.

| | REPEATABLE READ | READ COMMITTED |
|---|---|---|
| 갭 · 넥스트 키 락 | 잡는다 | 잡지 않는다 (외래 키 · 중복 키 검사만) |
| 훑었지만 조건에 안 맞는 레코드 | 커밋까지 잠금 유지 | WHERE 평가 직후 푼다. UPDATE 는 잠긴 행의 최신 커밋 값을 보고 지나간다(semi-consistent read) |
| 일반 SELECT 의 스냅샷 | 트랜잭션의 첫 읽기에 고정 | 문장마다 새로 |

계획이 범위를 넓게 훑으면 REPEATABLE READ 에서는 그 범위 전체가 커밋까지 잠긴다.
`BrandProductDeletionScaleTest` 의 파트 2 가 브랜드 하나의 상품을 지우는 트랜잭션을 커밋 전에 붙들어 두고,
기본키가 이웃한 **다른 브랜드** 상품의 `FOR UPDATE NOWAIT` 와 INSERT 가 막히는지 본다.
방식 넷(하나씩 · 배치 · 벌크 · id 로 벌크) × 브랜드당 상품 수 × 통계 갱신 여부를 두 격리 수준으로 돌린 결과:

| 데이터 | 통계 | REPEATABLE READ 에서 막힘 | READ COMMITTED 에서 막힘 |
|---|---|---|---|
| 브랜드 100개가 같은 수, 기본키가 섞임 (대상 1%) | `ANALYZE` 후 | 0 / 12 | 0 / 12 |
| 〃 | 적재 직후 | **9 / 12** | 0 / 12 |
| 대상 브랜드 + 다른 브랜드 1개 (대상 50% 이상) | `ANALYZE` 후 | 8 / 16 | 0 / 16 |
| 〃 | 적재 직후 | 13 / 16 | 0 / 16 |

- **분포가 현실적이고 통계가 맞으면 REPEATABLE READ 도 번지지 않는다.** 네 방식 모두 `idx_product_brand_id` 를 탔고,
  갭 락이 대상 브랜드 범위 안에 머물렀다.
- **통계가 틀어지면 현실적인 분포에서도 테이블 전체가 잠긴다.** 브랜드당 1,000개(10만 행)를 적재한 직후,
  옵티마이저가 11~22행으로 예상하고 기본키 전체 스캔을 골라 `PRIMARY · X` 가 10만 행 전부와 supremum 에 걸렸다.
- **READ COMMITTED 는 계획과 무관하게 대상 레코드만 남겼다.** 기본키 전체 스캔에서도 `PRIMARY · X,REC_NOT_GAP` 이 대상 행 수만큼만 잡혔다.

그래서 READ COMMITTED 는 **계획이 어긋났을 때 잠금이 번지지 않게 하는 안전망**이다.
"적재 직후" 는 테이블을 비우고 바로 채운 실험 조건이지만, 운영에도 대량 적재 · 대량 삭제 직후처럼 통계가 늦는 순간이 있다.

측정하지 않은 것: 다른 트랜잭션이 이웃 행을 **먼저** 잡고 있을 때 READ COMMITTED 의 전체 스캔 `FOR UPDATE` 가 그 행에서 기다리는지.
UPDATE 는 semi-consistent read 로 지나가지만 잠금 읽기는 그렇지 않다(MySQL 8.0 문서).

복제는 걸림돌이 아니다. READ COMMITTED 는 갭 락이 없어 SQL 문을 다시 실행하는 STATEMENT binlog 와 함께 쓸 수 없지만,
MySQL 8.0 의 기본 `binlog_format` 이 행 변경을 기록하는 `ROW` 다.

### 1.2 무엇이 바뀌지 않는가

- **정합성은 격리 수준에 맡기지 않는다.** 재고 · 포인트 · 주문 · 브랜드는 잠금 읽기로 지킨다(W2 6.3).
  격리 수준이 무엇이든 결과가 같다.
- **쓰기 트랜잭션 안에서 판단에 쓰는 읽기는 전부 잠금 읽기다.** 잠금 읽기는 read view 를 쓰지 않고 최신 커밋을 읽으므로(바뀌는 중이면 undo 를 보여 주는 대신 기다린다),
  READ COMMITTED 의 "문장마다 새 스냅샷" 이 판단을 바꾸지 않는다. 같은 행을 다시 찾는 저장소의 `save` 는 영속성 컨텍스트에서 꺼내 DB 를 다시 읽지 않는다.
  일반 SELECT 가 남은 쓰기 경로는 주문 접수(상품 이름 · 가격 복사)와 좋아요(상품 생존 확인)이고, 둘 다 REPEATABLE READ 에서도 같은 성질이다.
- **같은 행을 두고 다투는 대기는 그대로다.** 같은 상품의 동시 확정, 같은 사용자의 충전과 결제는 레코드 락끼리 부딪히고,
  레코드 락은 두 격리 수준 모두 잡는다. READ COMMITTED 의 이득은 **범위로 잠그는 경로**에서만 난다.
- **잠금은 여전히 기본키 · 유니크 키의 단건 동등 조건(`WHERE id = ?`)으로 건다.** 그러면 계획이 무엇이든 잠금 범위가
  그 레코드로 고정되고, 격리 수준이 바뀌어도 따라 변하지 않는다. 기본키라도 **목록**(`WHERE id IN (...)`)은 이 보장이 없다 —
  위 실험에서 REPEATABLE READ 의 `id IN (...)` UPDATE 도 기본키 전체 스캔을 골라 테이블 전체를 잠갔다.

### 1.3 W2 의 판단 중 격리 수준에 걸린 것

**`readOnly` 조회의 시점 일관성 (W2 6.1 · 6.2).** READ COMMITTED 는 문장마다 스냅샷을 새로 잡으므로
`readOnly` 트랜잭션이 두 질의를 같은 시점으로 묶지 않는다. 그래도 한 응답이 어긋나지 않는 것은 **데이터가 지키기 때문이다:**

| 자리 | 질의 | 두 질의 사이에 커밋이 끼면 |
|---|---|---|
| `OrderFacade` 의 목록·상세 | 주문 · 품목(배치로 한 번 더) | 어긋나지 않는다 — 품목은 접수 후 바뀌지 않는다(`order_item` 의 컬럼이 전부 `updatable = false`). 확정이 바꾸는 것은 주문 행 하나이고, 그것은 한 질의로 읽는다 |
| 그 밖의 목록 · 상세 | **하나** | 어긋날 것이 없다 |

그러면 `readOnly` 가 하는 일은 응답 하나를 커넥션 하나로 만드는 것뿐이고, 그 대가로 세션을 읽기 전용으로 바꿨다
되돌리는 왕복이 붙을 수 있다. 떼어도 정합성은 같다.

**규칙: 한 응답이 같은 시점을 요구하지 않게 만든다.** 따로 바뀌는 데이터를 한 응답에서 여러 번 읽어야 한다면,
먼저 그 필요를 없앤다 — 바뀌지 않는 사본으로 만들거나(주문 품목), 한 행 · 한 질의로 읽게 한다(재고를 상품 안에 · W2 3.3,
총 개수를 세지 않음 · W2 7.3, 좋아요를 한 쿼리에 얹음 · W2 7.4). 그러면 격리 수준이 무엇이든 응답이 어긋나지 않는다.

**뒤집을 조건**: 그 필요를 없앨 수 없는 조회가 생길 때 — 품목이 접수 뒤에 바뀌는 기능(부분 취소 등),
여러 테이블의 집계를 한 시점으로 보여야 하는 화면. 그때 **그 조회만** `isolation = REPEATABLE_READ` 로 덮는다.
조회 지연에서 읽기 전용 전환 왕복이 보이면 `readOnly` 를 뗀다.

**없는 행의 `FOR UPDATE` (W2 6.5 ①).** 잠글 행이 없으면 두 트랜잭션이 함께 통과해 둘 다 INSERT 로 간다.
깨지는 모양만 격리 수준이 정한다:

| 격리 수준 | 없는 행의 `FOR UPDATE` | 결과 |
|---|---|---|
| **READ COMMITTED** | 아무것도 잠그지 않는다 | 뒤의 INSERT 가 앞의 커밋을 기다렸다가 **중복 키 위반** |
| REPEATABLE READ | 유니크 인덱스의 빈 구간에 갭 락. 갭 락끼리는 호환된다 | 각자의 INSERT 가 상대의 갭 락을 기다리는 **데드락** |

"행을 먼저 열고 잠근다"(`loadForUpdate`)는 결론은 같다. 둘 다 여는 것과 잠그는 것 사이의 틈에서 깨지기 때문이다.

**판단에 쓰는 읽기 (W2 6.5 남는 규칙).** 평범한 읽기는 잠그지 않는다. READ COMMITTED 에서는 문장마다 최신 커밋을 읽지만,
읽은 직후 남이 커밋하면 그 값은 낡고 그 값으로 한 판단도 낡는다. "판단에 쓰는 읽기는 잠금 읽기로" 는 그대로다.

### 1.4 왜 커넥션 풀이 아니라 MySQL 서버에 두는가

MySQL 서버 옵션은 이 애플리케이션뿐 아니라 **DB 에 붙는 모든 클라이언트**(배치 · 운영 도구)에 같은 규칙을 준다.
대가는 dev · qa · prd 서버가 이 저장소 밖에 있다는 것이다. **운영 서버 파라미터에도 `transaction_isolation = READ-COMMITTED` 를 요구한다.**
그 값이 다르면 운영만 다른 격리 수준으로 돈다 — 정합성은 그대로지만, 범위 잠금의 번짐과 1.3 의 실패 모양이 달라진다.

지금 고를 수 있는 다른 자리:

| 자리 | 장점 | 대가 |
|---|---|---|
| 커넥션 풀 (Hikari `transaction-isolation`) | 서버 설정과 무관하게 이 애플리케이션은 보장된다. 커넥션을 만들 때 한 번만 설정한다 | 다른 클라이언트는 서버 값을 따른다 |
| 트랜잭션마다 `@Transactional(isolation = ...)` | 필요한 곳만 다르게 돌린다 | 트랜잭션마다 세션 설정 왕복이 붙고, 빠뜨리기 쉽다. 예외에만 쓴다 |

**뒤집을 조건**:
- 운영 서버의 값을 맞출 수 없는 곳에 배포될 때 → 커넥션 풀로 옮긴다.
- 같은 시점을 요구하는 조회를 설계로 없앨 수 없을 때(1.3) → 그 조회만 `REPEATABLE_READ` 로 덮는다.

## 2. 브랜드를 지우면 연결된 상품도 함께 지운다

`DELETE /api-admin/v1/brands/{brandId}` 의 계약을 바꾼다. W2 의 `BRAND-004` 는 살아 있는 상품이 있으면 409 `BRAND_HAS_PRODUCTS` 로
거절했다. 이제는 **브랜드와 그 브랜드의 살아 있는 상품을 한 트랜잭션에서 함께 논리 삭제**하고 204 를 낸다. 재고 0 인 상품도 대상이다.
거절할 조건이 없어졌으므로 `BRAND_HAS_PRODUCTS` · `ProductsInBrand.hasAlive` · `ProductRepository.existsByBrandId` 도 없다.

### 2.1 흐름

```
BrandFacade.delete  @Transactional
  BrandService.delete
    브랜드 FOR UPDATE                    → 없거나 삭제됐으면 BRAND_NOT_FOUND (404)
    ProductsInBrand.deleteAll(brandId)   → UPDATE product SET deleted_at = ?, updated_at = ?
                                            WHERE brand_id = ? AND deleted_at IS NULL
    brand.delete() → 저장
```

**잠그는 순서와 지우는 순서는 다르다.**

- **잠금은 브랜드가 먼저다.** 상품 등록은 브랜드를 공유 잠금으로 읽는다(2.3). 삭제가 브랜드를 먼저 배타로 잡아야
  상품을 지우는 동안 새 상품이 끼어들지 못한다. 브랜드를 나중에 잠그면, 상품 UPDATE 와 브랜드 잠금 사이에 등록이 통과해
  삭제된 브랜드 아래 살아 있는 상품이 남는다. 없는 브랜드라면 상품을 건드리기 전에 404 로 끝난다는 이점도 있다.
- **변경은 상품이 먼저다.** 상품 UPDATE 는 문장이 즉시 DB 로 나가고, 브랜드 UPDATE 는 커밋 때 나간다. 브랜드 저장에서 실패하면
  "변경 SQL 이 나간 뒤의 실패" 가 되고 트랜잭션이 둘 다 되돌린다.

### 2.2 벌크 UPDATE 한 문장으로 지운다

| 고려 | 판단 |
|---|---|
| 규칙이 애그리거트를 우회하는가 | 우회할 판단이 없다. `Product.delete()` 는 `deleted = true` 한 줄이다. W2 6.2 가 조건부 UPDATE 를 거절한 이유(`INSUFFICIENT_STOCK` 을 던지는 주체가 저장소로 옮겨감)가 여기엔 없다 |
| 조건부 UPDATE 인가 | 아니다. WHERE 는 판단이 아니라 **대상 고르기**다. 바뀐 행이 0 이어도 정상(상품 없는 브랜드)이고, 행 수로 성공 · 실패를 가르지 않는다. `deleted_at IS NULL` 은 이미 단건 삭제된 상품의 삭제 시각을 덮지 않게 한다 |
| 잠금을 쥐는 시간 | 실험(`BrandProductDeletionScaleTest` 파트 1 · 3)에서 상품 10,000 개를 하나씩 지우면 5 초, JDBC 배치로 0.9 초, 벌크로 0.14 초 |
| 잠금 범위 | 1.1 의 실험에서 READ COMMITTED 는 계획과 무관하게 대상 행만 잠갔다 |
| 영속성 컨텍스트 | 벌크 UPDATE 는 영속성 컨텍스트와 `@PreUpdate` 를 거치지 않는다. 그래서 `updated_at` 을 직접 쓰고, 같은 트랜잭션에서 상품 엔티티를 미리 적재하지 않는다 |

**뒤집을 조건**: `Product.delete()` 에 판단이 생길 때 → 애그리거트를 거쳐 하나씩 지우고 UPDATE 는 JDBC 배치로 보낸다.
운영 서버가 REPEATABLE READ 일 때(1.4) → 이 문장도 계획에 따라 테이블 전체를 잠글 수 있으므로, 상품 id 를 읽은 뒤
단건 `WHERE id = ?` UPDATE 를 배치로 보낸다(측정하지 않았다).

### 2.3 동시 요청

| 겹치는 요청 | 무엇이 순서를 정하나 | 결과 |
|---|---|---|
| 같은 브랜드에 상품 등록 | 브랜드 행 — 등록은 공유, 삭제는 배타 잠금 | 등록이 먼저면 그 상품도 함께 지워진다. 삭제가 먼저면 등록이 `BRAND_NOT_AVAILABLE` 로 거절된다 |
| 그 상품의 확정 · 재고 변경 · 수정 | 상품 행의 배타 잠금 | 먼저 잡은 쪽이 끝난 뒤 진행. 삭제 뒤에 오면 잠금 읽기가 "삭제됨" 을 보고 `PRODUCT_NOT_FOUND` |
| 같은 브랜드의 수정 | 브랜드 행의 배타 잠금 | 수정이 먼저면 수정된 브랜드가 지워진다. 삭제가 먼저면 수정이 `BRAND_NOT_FOUND` 로 거절된다 |

수정은 브랜드 행 전체를 다시 쓴다(JPA 는 모든 열을 UPDATE 한다). 잠그지 않고 읽으면 삭제 전에 읽은 `deleted_at = NULL` 을
삭제 커밋 뒤에 덮어써 **브랜드만 되살아나고 상품은 삭제된 채** 남는다. 그래서 수정도 브랜드를 `FOR UPDATE` 로 읽는다.
`BrandRemovalRegistrationRaceTest.updateWaitsForDeletionAndDoesNotRevive` 가 이 순서를 재현하고, 잠금을 빼면 브랜드가 살아나 실패한다.
변경된 열만 쓰는 선택지(`@DynamicUpdate` · 조건부 UPDATE `where deleted_at is null`)도 같은 일을 하지만,
다른 쓰기 경로가 모두 "잠그고 읽고 애그리거트가 판단" 이라 그 방식을 따른다(4.1).

"삭제된 브랜드 아래 살아 있는 상품이 없다" 는 브랜드 행의 S/X 충돌이 지킨다. 갭 락에 기대지 않으므로 격리 수준과 무관하다.
과제의 선택 확장(브랜드 삭제와 상품 등록의 동시 실행)이고, 두 순서를 **결정적으로** 재현해 확인했다(`BrandRemovalRegistrationRaceTest`).
테스트가 바깥 트랜잭션을 열고 그 안에서 실제 Facade 를 불러(`REQUIRED` 로 합류) 커밋 전에 멈춰 두고, 다른 쪽 요청을 보낸 뒤
`performance_schema.data_lock_waits` 에 **브랜드 행의 잠금 대기가 실제로 생겼는지** 확인하고 나서 놓아준다. 운영 코드에는 장벽이 없다.

| 먼저 잡은 쪽 | 뒤에 온 쪽 | 결과 |
|---|---|---|
| 삭제 (브랜드 X) | 등록 — 브랜드 S 에서 기다림 | 삭제 커밋 뒤 등록이 최신 값을 보고 `BRAND_NOT_AVAILABLE` |
| 등록 (브랜드 S, 상품 INSERT) | 삭제 — 브랜드 X 에서 기다림 | 등록 커밋 뒤 삭제의 벌크 UPDATE 가 방금 등록된 상품까지 지움 |

등록의 `@Lock(PESSIMISTIC_READ)` 를 빼면 두 테스트 모두 "기다리지 않았다" 로 실패한다.
`BrandRepositoryIntegrationTest.doesNotLeaveAliveProductUnderDeletedBrand` 는 시작만 맞춘 동시 실행이라 순서를 고르지 못하고, 불변식(살아 있는 상품 0)만 본다.

막는 것은 **"확인한 뒤 행동하는" 등록의 두 단계 사이에 삭제가 끼어드는 순서**다 —
등록이 브랜드가 살아 있다고 읽고, 삭제가 커밋되고, 등록이 상품을 INSERT 한다.
등록은 `product` 에, 삭제는 `brand` 와 기존 `product` 에 쓰니 겹치는 행이 없는 **write skew** 이고,
삭제가 고른 "그 브랜드의 상품" 범위에 새 행이 생긴다는 점에서 팬텀이 낀다.
`FOR SHARE` 는 실무에서 드물게 쓰지만, 여기서는 그 이유인 S→X 승격이 없다 — 등록은 브랜드 행을 읽기만 한다.

| 다른 선택지 | 이 경합을 막나 | 고르지 않는 이유 |
|---|---|---|
| 격리 수준 REPEATABLE READ | 못 막는다 | 일반 SELECT 는 스냅샷이라 잠그지 않는다. 삭제의 벌크 UPDATE 가 거는 넥스트 키 락은 INSERT 를 삭제 커밋까지 늦출 뿐이고, 풀린 뒤 등록은 브랜드를 다시 보지 않고 INSERT 한다 |
| 격리 수준 SERIALIZABLE | 막는다 | 일반 SELECT 를 모두 `FOR SHARE` 로 바꾼다. 같은 일을 읽기 하나에만 하면 된다 |
| DB 외래키 | 못 막는다 | 외래키는 브랜드 행이 **있는지**를 본다. 삭제는 논리 삭제(`COMMON-007`)라 행이 남으므로 검사를 통과한다. 외래키가 이 경합을 막는 건 물리 삭제일 때뿐인데, 물리 삭제는 주문 품목 · 좋아요의 참조를 깨서 고르지 않았다 |
| 등록도 브랜드를 `FOR UPDATE` | 막는다 | 같은 브랜드의 등록끼리 줄을 선다. 관리자 기능이라 비용은 작다. 잠금 종류를 하나로 맞추고 싶어지면 이쪽으로 바꾼다 |
| 잠그지 않고 읽을 때 거름 | 못 막는다(숨길 뿐) | 고아 상품이 남는다. 모든 상품 조회가 브랜드 생존까지 걸러야 한다 |

**뒤집을 조건**: 등록이 브랜드 행에 쓰게 되면(브랜드별 상품 수 저장 등) 승격 데드락이 생기므로 처음부터 `FOR UPDATE` 로 읽는다.

**`ProductsInBrand.deleteAll` 은 혼자 커밋되면 안 되는 연산이다.** 브랜드 없이 상품만 지워진 채 커밋되면 안 되므로,
W2 6.1 의 셋(`OrderConfirmation.confirm` · `PointService.use` · `ProductService.deductStock`)과 같이 **호출자가 `BrandService.delete` 하나**라는 사실에 기댄다.
두 번째 호출자가 생기면 W2 6.1 의 뒤집을 조건을 따른다.

### 2.4 무엇을 보존하는가

- **다른 브랜드와 그 상품**: WHERE 가 `brand_id` 로 고른다.
- **기존 주문**: 주문 품목은 접수 때 이름 · 단가 · 수량을 복사해 두므로(W2 `ORDER-005` · `022`) 상품이 지워져도 그대로 조회된다.
  상품 행은 지우지 않고 남기므로(`COMMON-007`) 주문의 `product_id` 도 끊기지 않는다.
- **삭제 전에 만든 DRAFT**: 확정이 상품을 다시 잠가 읽으므로(`ORDER-012`) `PRODUCT_NOT_FOUND` 로 거절되고, 잔액과 DRAFT 는 그대로다.
- **고객 화면**: 목록 · 상세 · 새 좋아요 · 내 좋아요 목록 · 새 주문은 이미 `product.deleted_at` 으로 거른다(W2 9.2). 브랜드 삭제가 따로 할 일이 없다.

**새 좋아요는 쓸 때 막지 않고, 읽을 때 거른다.** 좋아요는 상품을 잠금 없이 읽어 "살아 있다" 고 판단한 뒤 `product_like` 에 쓴다.
그 사이에 삭제가 커밋되면 삭제된 상품에 좋아요 한 줄이 생긴다 — 두 요청이 서로 다른 테이블에 써서 부딪히지 않는 write skew 다.
막으려면 좋아요가 상품을 `FOR SHARE` 로 읽어야 하는데, 그 행은 확정이 배타 잠금을 거는 행이라 **좋아요와 구매가 서로를 기다리게** 된다.
지금은 대기일 뿐 데드락은 아니다 — 좋아요는 그 뒤 `product_like` 에만 쓰고 확정은 그 테이블을 건드리지 않아 순환이 없다.
그러나 좋아요 수를 상품 행에 저장하게 되면(`LIKE-008` 을 뒤집으면) 좋아요가 같은 행을 S 로 잡은 뒤 X 로 올려야 하고,
동시 좋아요끼리 서로의 S 를 기다리는 **승격 데드락**이 된다(W2 6.5 "승격을 만들지 않는다").

막지 않는 이유는 그 비용만이 아니다. **삭제된 상품에 좋아요가 남은 상태는 원래 정상이다** — 삭제 전에 누른 좋아요는 남고,
자기 좋아요 취소는 유지된다. 경합으로 생긴 행은 "삭제 직전에 누른 좋아요" 와 구별되지 않으므로, 막아도 다룰 상태가 줄지 않는다.
잠금 없는 생존 확인은 그대로 둔다 — 경합을 막는 장치가 아니라 `LIKE-004`(삭제된 상품에는 404)의 계약이고,
이미 삭제된 상품 · 없는 id 에 대한 요청은 전부 거기서 걸린다. 새는 것은 삭제와 겹친 순간뿐이다.
그러니 지킬 것은 **모든 읽기가 거르는가** 다: 내 좋아요 목록은 `p.deleted_at IS NULL` 로 거르고, 삭제된 상품의 상세는 404 라 좋아요 수가 보이지 않는다.

**뒤집을 조건**: 좋아요 수를 미리 집계해 두거나 랭킹 등 다른 곳에 쓰게 될 때 — 그 집계도 삭제된 상품을 걸러야 한다.
남은 행이 쌓여 문제가 되면 쓰기 경로 밖(삭제 커밋 뒤 이벤트, 배치)에서 치우되, 자기 좋아요 취소를 위해 보존 기간을 정한다.

### 2.5 중간 실패를 어떻게 확인하나

`BrandRemovalTransactionTest` 가 브랜드 1개 · 연결 상품 2개(하나는 재고 0) · 다른 브랜드 상품 · 확정된 과거 주문을 커밋해 두고,
정상 삭제와 중간 실패를 각각 돌린 뒤 **트랜잭션이 끝난 다음 `JdbcTemplate` 의 별도 질의로** DB 를 다시 읽는다.

**실패는 테스트 구성의 저장 경계에서 만든다.** 테스트 설정이 실제 `BrandRepositoryImpl` 을 감싼 `BrandRepository` 를 `@Primary` 로 올리고,
지정한 브랜드의 `save` 에서만 예외를 던진다. 그 밖의 호출은 진짜 저장소와 진짜 DB 를 그대로 지난다.
예외를 던지기 직전 같은 트랜잭션에서 그 브랜드의 살아 있는 상품 수를 읽어 두어, **상품 UPDATE 가 이미 DB 로 나간 뒤의 실패**였음을 확인한다(0 이어야 한다).

**중간 상태의 모양은 "상품 전부 삭제 · 브랜드 생존" 하나뿐이다.** 과제의 예시는 "브랜드와 P1 은 삭제 · P2 는 생존" 인데,
상품은 UPDATE 한 문장으로 바뀌므로 P1 과 P2 가 갈리는 상태는 생기지 않고, 브랜드는 마지막에 저장하므로(2.1) 순서도 반대다.
확인하려는 것은 같다 — **앞선 변경이 뒤의 실패보다 먼저 확정되지 않는가.** 테스트는 이 구현에서 실제로 생기는 중간 상태에서 실패시킨다.

이것은 "테스트 더블을 두지 않는다" 의 예외다. 그 규칙이 막으려는 것은 **규칙을 흉내 내는 가짜 저장소** —
가짜가 필요해지면 규칙이 애그리거트 밖으로 샜다는 신호라서다. 이 장치는 규칙도 저장도 흉내 내지 않고 **실패 시점 하나만** 만든다.
운영 DB 로는 "상품 UPDATE 뒤 브랜드 저장 직전" 의 실패를 골라 일으킬 방법이 없다.
**범위**: 실패 주입에만 쓰고, 테스트 클래스 안에 둔다. 규칙 검증에 가짜 저장소를 쓰는 일은 여전히 하지 않는다.

**테스트가 깨진 경계를 잡는지 확인했다** — 코드를 일부러 깨고 돌린 결과:

| 깨뜨린 것 | 결과 |
|---|---|
| `BrandFacade.delete` 의 `@Transactional` 제거 | 두 테스트 모두 실패. 상품 벌크 UPDATE(`@Modifying`)가 트랜잭션 없이 실행되지 않는다 |
| 상품 벌크 UPDATE 에 `@Transactional(propagation = REQUIRES_NEW)` | **중간 실패 테스트만 실패.** 상품 삭제가 따로 커밋되어, 브랜드가 되돌아간 뒤에도 상품은 삭제된 채 남았다. 정상 경로 테스트는 통과 — 정상 경로만으로는 독립 커밋을 잡지 못한다 |

### 2.6 트랜잭션을 더 짧게 가져갈 수 있는가

트랜잭션 안에 있는 것은 브랜드 잠금 읽기 · 상품 UPDATE 한 문장 · 브랜드 UPDATE 셋이고, 외부 호출이나 판단용 조회는 없다.
길이를 정하는 것은 상품 UPDATE 이고, 상품 10,000 개에서 0.14 초다(2.2). 같은 경계 안에서 더 덜어낼 것은 없다.
더 줄이려면 **경계를 쪼개야** 하고, 쪼개는 순간 2.5 의 "전체가 취소됨" 을 내준다.

| 선택지 | 트랜잭션 | 내주는 것 |
|---|---|---|
| 브랜드만 지우고 커밋, 상품은 뒤에서(이벤트 · 배치) 나눠 지움 | 브랜드 행 하나 + 묶음마다 하나 | 커밋 사이에 "삭제된 브랜드 아래 살아 있는 상품" 이 고객에게 보이고 주문도 확정된다. 뒤 단계가 실패하면 되돌릴 수 없고 재시도로 끝까지 가야 한다 |
| 브랜드에 `삭제 중` 상태를 두고(등록 · 노출 차단) 상품을 묶음으로 지운 뒤 브랜드를 삭제로 확정 | 짧은 것 여러 개 | 상태가 하나 늘고, 모든 상품 읽기가 브랜드 상태까지 걸러야 한다. 실패는 롤백이 아니라 **이어서 완료**다 |
| 상품은 건드리지 않고 읽을 때 브랜드 생존으로 거름 | 브랜드 행 하나 | 상품의 노출 기준이 `product.deleted_at` 하나가 아니게 된다 — 목록 · 상세 · 좋아요 · 주문 접수 · 확정이 모두 브랜드를 함께 봐야 한다(2.3 의 "읽을 때 거름") |

셋 모두 "중간 실패 후 브랜드와 상품이 작업 전 상태" 를 만들지 못한다. 이 요구가 있는 한 한 트랜잭션이 맞고,
짧게 만드는 일은 **경계를 쪼개는 것이 아니라 그 안의 문장을 줄이는 것**이었다 — 하나씩 5 초 → 벌크 0.14 초(2.2).

**뒤집을 조건**: 브랜드 하나의 상품 수가 커져 상품 UPDATE 가 쥔 잠금 때문에 같은 브랜드의 확정 대기가 받아들일 수 없게 되거나,
한 트랜잭션의 변경량이 복제 지연을 만들 때 → 둘째 선택지(`삭제 중` 상태 + 묶음 삭제)로 가고, "전체 취소" 요구를 "끝까지 완료" 로 바꾸는 것을 먼저 확인받는다.

## 3. 주문 확정은 재고 · 잔액 · 상태 · 결제 결과를 한 번에 확정하거나 하나도 남기지 않는다

경계는 W2 그대로다. `OrderFacade.confirm` 하나가 트랜잭션을 열고, 그 안에서 `OrderConfirmation.confirm` 이
주문 → 포인트 → 상품(id 오름차순) 순으로 잠그고 바꾼다(W2 6.1 · 6.3). 순서의 이유는 3.3 이고, 여기서는 **그 경계가 실제로 성립하는지**를 확인한다.

### 3.1 SQL 이 나가는 시점

변경 감지는 SQL 을 커밋 때까지 미룬다. 그래서 실패를 일으켜도 "나간 SQL 이 없는 rollback" 이면 DB rollback 을 확인한 것이 아니다.
확정 경로에서 SQL 이 나가는 시점은 다음과 같다:

```
주문 FOR UPDATE                    ← 바로
order.confirm → 저장                → 주문 엔티티만 바뀜 (보류)
포인트 FOR UPDATE → 차감 → 저장       ← 원장 INSERT 는 바로(IDENTITY), 잔액 UPDATE 는 보류
상품1 FOR UPDATE → 차감             → 상품1 엔티티만 바뀜 (보류)
상품2 FOR UPDATE                    ← 상품 테이블을 읽는 질의가 보류된 상품1 변경과 겹쳐 AUTO flush
                                      → 늦어도 여기서 UPDATE orders · user_point · product(상품1) 이 나가 있다
상품2 차감                          → 보류
커밋                                ← 상품2 UPDATE
```

**품목이 둘 이상이면 둘째 품목을 저장하기 전에 이미 주문 상태 · 결제 · 첫 품목 차감이 DB 에 나가 있다.** `OrderTransactionTest` 의 중간 실패 테스트가
실패 직전 같은 트랜잭션 안에서 잔액(50,000 → 25,000) · 첫 품목 재고(10 → 8) · 주문 상태(`CONFIRMED`)를 읽어 이것을 확인한다.
확인한 것은 "둘째 품목 저장 시점에 셋이 나가 있다" 까지이고, 주문과 잔액의 UPDATE 가 그보다 앞선 어느 질의에서 나갔는지는 가르지 않았다.

### 3.2 확인한 것

`OrderTransactionTest` — 상품 2개(재고 10), 두 품목 주문. 결과는 트랜잭션이 끝난 뒤 `JdbcTemplate` 별도 질의로 읽는다.

| 경우 | 실패 시점 | 결과 |
|---|---|---|
| 정상 | — | 두 재고 · 잔액 · `CONFIRMED` · 결제액 · 원장 `USE` 가 함께 반영 |
| 중간 실패 | 주문 상태 · 결제 · 첫 품목 SQL 이 나간 뒤, 둘째 품목 저장(테스트가 주입) | 전부 확정 전: 재고 · 잔액 그대로 · `DRAFT` · 결제액 · 확정 시각 없음 · 원장 `CHARGE` 만 |
| 두 번째 품목 재고 부족 | 결제 · 첫 품목 차감 뒤 `INSUFFICIENT_STOCK` | 위와 같음 |
| 잔액 부족 | 상품을 잠그기 전 `INSUFFICIENT_POINT` | 위와 같음 |
| 잔액 · 재고 함께 부족 | 상품을 잠그기 전 `INSUFFICIENT_POINT` | 위와 같음 |

모든 실패 경우에 **잔액 == 원장 합**(`POINT-004`)도 함께 본다. 실패 주입 방식과 그것이 "테스트 더블을 두지 않는다" 의 예외인 이유는 2.5 와 같다.

**테스트가 깨진 경계를 잡는지 확인했다:**

| 깨뜨린 것 | 결과 |
|---|---|
| `OrderFacade.confirm` 의 `@Transactional` 제거 | 다섯 테스트 모두 실패. 잠금 질의(`FOR UPDATE`)가 트랜잭션 없이 실행되지 않는다 |
| `OrderFacade.confirm` 이 `DomainException` 을 잡고 정상 반환 (예외 삼키기) | **재고 부족 · 잔액 부족 · 함께 부족 테스트가 실패.** 프록시가 정상 종료로 보고 커밋한다. 주입한 실패는 `DomainException` 이 아니라 잡히지 않아 그 테스트는 통과했다 |

**뒤집을 조건**: 3.1 의 AUTO flush 는 Hibernate 의 동작이다. 품목이 하나뿐인 주문은 커밋 전에 주문 · 잔액 UPDATE 가 나가지 않을 수 있다 —
그래도 결과는 같다(전부 커밋 때 나가거나 전부 안 나간다). 실패 직전에 SQL 이 나가 있다는 관찰이 깨지면, 테스트가 아니라 이 절의 설명을 고친다.

### 3.3 포인트를 상품보다 먼저 잠근다

잠금은 잡는 시점이 달라도 놓는 시점은 모두 커밋이다. 먼저 잡은 행일수록 오래 쥔다.
그래서 **여럿이 다투는 행을 가장 나중에 잡는다** — 상품 행은 모든 구매자가 다투고, 포인트 행은 그 사용자 혼자 쓴다.

| | 주문 → 포인트 → 상품 | 주문 → 상품 → 포인트 |
|---|---|---|
| 상품 잠금을 쥔 채 하는 일 | 재고 차감 | 재고 차감 + 포인트 잠금 대기 · 차감 · 원장 기록 |
| 잔액 부족 요청 | 상품을 잠그기 전에 끝난다 | 상품 줄에서 기다렸다가 잠근 뒤에야 실패한다 |
| 재고 부족 요청 | 자기 포인트 행을 쥔 채 상품 줄에서 기다린다 | 포인트를 건드리기 전에 끝난다 |
| 기다리는 동안 막히는 것 | 같은 사용자의 충전 · 다른 확정 | 다른 구매자의 확정 |

포인트를 먼저 잡는 대가는 한 사용자가 확정을 기다리는 바로 그 순간에 충전도 보낼 때만 생기고, 피해가 그 사용자에게 한정된다.
재고에서 실패하면 앞서 한 결제를 되돌려야 하지만, 포인트는 같은 DB 의 잔액이라 같은 트랜잭션의 롤백으로 끝난다(3.2).
두 순서의 대기 시간을 재지는 않았다 — 근거는 잠금을 쥐는 구간의 비교다.

**실패의 우선순위가 이 순서를 따른다.** 잔액과 재고가 함께 모자라면 `INSUFFICIENT_POINT` 가 나간다(`OrderTransactionTest`).
요구사항은 둘이 겹칠 때의 우선순위를 정하지 않는다(`ORDER-013` · `014`).

데드락은 두 순서 모두 없다. 여러 행을 잠그는 경로가 확정 하나이고, 충전은 포인트만, 재고 설정 · 상품 수정 · 삭제는 상품만 잡는다(4.1).

**뒤집을 조건**: 결제가 같은 트랜잭션에서 롤백되지 않게 될 때 — 포인트가 외부 결제(PG)로 바뀌거나 별도 서비스로 나갈 때.
그때는 되돌리기 쉬운 재고를 먼저 잡고 되돌리기 어려운 결제를 마지막에 둔다(상품 → 결제).
포인트 행을 쥔 채 상품을 기다리는 시간 때문에 충전 지연이 보일 때도 순서를 다시 본다.

## 4. 같은 행을 동시에 바꾸는 요청은 비관적 잠금으로 줄 세운다

### 4.1 무엇을 고르고, 같은 행을 바꾸는 경로가 모두 따르는가

재고 · 잔액 · 주문 상태는 **읽고 → 판단하고 → 쓰는** 값이다. 그 읽기를 `SELECT … FOR UPDATE` 로 하고, 판단은 애그리거트가 한다(W2 6.3).

| 행 | 그 행을 바꾸는 경로 | 잠그는 곳 |
|---|---|---|
| `product` | 주문 확정의 차감 · 관리자 재고 설정 · 상품 수정 · 상품 삭제 | 전부 `ProductService.findAliveForUpdate` (`PESSIMISTIC_WRITE`) |
| `product` (브랜드 단위) | 브랜드 삭제의 벌크 UPDATE | UPDATE 문 자체의 행 잠금 (2.2) |
| `brand` | 브랜드 수정 · 삭제 | 전부 `BrandService.findAliveForUpdate` (`PESSIMISTIC_WRITE`). 상품 등록은 읽기만 하므로 공유 잠금 (2.3) |
| `user_point` | 충전 · 확정의 결제 | `loadForUpdate` · `findForUpdate` (`PESSIMISTIC_WRITE`) |
| `orders` | 확정 | `findByIdForUpdate` |

잠금 순서는 **주문 → 포인트 → 상품(id 오름차순)** 이고(3.3), 충전은 포인트만, 재고 설정은 상품만 잡으므로 역순으로 잡는 경로가 없다.
잠금 대상은 모두 기본키 · 유니크 키의 단건 동등 조건이다(1.2).

### 4.2 경쟁 결과

`OrderConcurrencyTest` — 데이터를 커밋한 뒤 worker 의 **시작만** 맞추고, 요청마다 성공 · 업무 거절(에러 코드) · 기술 오류로 분류해 모은다.
대기와 future 에 제한 시간을 두고 `finally` 에서 executor 를 정리한다. 모든 worker 가 끝난 뒤 `JdbcTemplate` 로 DB 를 다시 읽는다.

| 시나리오 | 결과 |
|---|---|
| 재고 5, 1개씩 사는 서로 다른 주문 8건 | 확정 5 · `INSUFFICIENT_STOCK` 3 · 기술 오류 0 · 최종 재고 0 |
| 재고 5, 주문 12건 (선택 확장 — 테스트 커넥션 풀 10개보다 많다) | 확정 5 · `INSUFFICIENT_STOCK` 7 · 기술 오류 0 · 최종 재고 0 |
| 한 사용자 잔액 10,000원, 서로 다른 4,000원 주문 3건 (재고 충분) | 확정 2 · `INSUFFICIENT_POINT` 1 · 최종 잔액 2,000원 · 거절된 주문의 재고는 유지 |
| 잔액 10,000원에서 2,000원 충전과 7,000원 확정을 함께 | 둘 다 성공 · 최종 잔액 5,000원 |
| 같은 주문에 확정 10건 | 확정 1 · `ORDER_NOT_DRAFT` 9 · 차감 한 번 |

각 시나리오에서 DB 로 다시 확인하는 식:
**초기 재고 − 성공 주문의 품목 수량 합 = 최종 재고**, **초기 잔액 + 성공 충전 − 성공 결제 = 최종 잔액**, **잔액 = 원장 합**,
**성공 + 업무 거절 + 기술 오류 = 전체 요청**(기술 오류는 0 이어야 한다).

**요청이 커넥션 풀보다 많을 때.** 잠금을 기다리는 요청은 커넥션을 쥔 채 기다리므로, 풀(테스트 10개)을 넘는 요청은 커넥션부터 기다린다.
12건에서는 확정 하나가 짧아 커넥션이 금방 돌아와 기술 오류가 없었다. 잠금을 쥐는 시간이 커넥션 대기 한도(`connection-timeout` 3초)를 넘으면
커넥션을 못 받은 요청이 **기술 오류**로 실패할 것이고, 테스트는 그것을 재고 부족으로 세지 않고 따로 센다. 그 경계까지 밀어 보지는 않았다.

**테스트가 잠금 누락을 잡는지 확인했다.** 상품 조회의 `@Lock(PESSIMISTIC_WRITE)` 를 빼면 재고 경쟁에서 **8건이 모두 확정**된다(초과 판매).
상품 잠금 누락을 잡는 것은 재고 경쟁 하나다. 구매자가 모두 달라 포인트 행도 달라서, 상품 행 말고는 줄을 세우는 것이 없다.
포인트 경쟁은 상품 잠금 누락을 잡지 못한다 — 포인트를 상품보다 먼저 잠그고(3.3) 그 잠금을 커밋까지 쥐므로, 같은 사용자의 확정은 포인트에서 이미 한 줄로 선다.
포인트 경쟁이 잡는 것은 포인트 잠금 누락이다. 그 잠금이 없으면 세 확정이 모두 10,000 을 읽고 3건이 확정된다.

**충전과 결제가 실제로 겹치는지는 `ChargeAndPayRaceTest` 가 본다.** 경쟁 테스트는 시작만 맞추므로 둘이 차례로 끝나도 5,000 이 되어 통과한다.
그래서 한쪽을 바깥 트랜잭션에서 포인트 행을 쥔 채 멈춰 두고, 다른 쪽이 `user_point` 행에서 기다리는 것을 `data_lock_waits` 로 확인한 뒤 놓아준다.
확정이 먼저 쥔 경우와 충전이 먼저 쥔 경우를 모두 돌리고, 둘 다 성공 · 최종 잔액 5,000 · 잔액 = 원장 합을 본다.

### 4.3 조건부 UPDATE 와 비교

```sql
UPDATE product SET quantity = quantity - ? WHERE id = ? AND deleted_at IS NULL AND quantity >= ?
```

`ConditionalStockOrderConcurrencyTest` 가 확정의 재고 차감만 이 문장으로 바꾼 `StockDeduction` 을 테스트 설정에서 끼우고(`OrderConfirmation` 은 좁은 포트로만 재고를 안다),
4.2 의 다섯 시나리오를 그대로 물려받아 돌린다. **결과가 모두 같았고**, 재고 경쟁에서 차감 호출 8건(확정 5 · 재고 부족 3)이 실제로 그 경로를 지났음도 확인했다.

| | 비관적 잠금 (지금) | 조건부 UPDATE |
|---|---|---|
| 같은 상품을 기다리는 시간 | 상품 행 잠금을 **커밋까지** 쥔다 | 같다 — UPDATE 의 잠금도 커밋까지 쥔다. 확정은 차감 뒤 포인트 단계까지 같은 트랜잭션이다 |
| 왕복 | SELECT FOR UPDATE + UPDATE | UPDATE 하나 (실패 때만 원인을 구분하려고 한 번 더 읽는다) |
| "재고는 음수가 안 된다" 의 위치 | `Product.deduct` — DB 없는 애그리거트 테스트로 확인 | SQL — DB 통합 테스트로만 확인 |
| 0 행이 바뀌었을 때 | — | 삭제된 상품인지 재고 부족인지 다시 읽어야 안다 |

조건부 UPDATE 는 낙관적 잠금과 "쓰는 순간 WHERE 로 확인한다" 는 점이 같지만, 낙관적 잠금은 "읽은 뒤 누가 바꿨나(버전)" 를 묻고
조건부 UPDATE 는 "지금 값이 조건을 만족하나" 를 묻는다. 남이 재고를 조금 가져가도 충분하면 조건부 UPDATE 는 성공하고, 재시도가 필요 없다.

**비관적 잠금을 유지한다.** 이 흐름에서는 대기 시간이 같고, 아끼는 것은 왕복 한 번인데, 규칙이 애그리거트를 떠난다.
**뒤집을 조건**: 한 상품에 확정이 몰려 잠금 대기가 문제가 될 때 — 그때는 차감을 확정 트랜잭션 끝으로 옮기거나 트랜잭션을 나눠
잠금 구간을 줄여야 하고, 그 구조에서는 판단을 한 문장에 담는 조건부 UPDATE 가 맞다.

측정하지 않은 것: 두 방식의 처리 시간 비교. 위 표의 "같다" 는 잠금이 유지되는 구간에 대한 추론이다.

### 4.4 잠금 대기는 3 초에서 포기한다

모든 커넥션에 `innodb_lock_wait_timeout=3` 을 건다(`jpa.yml` 의 `sessionVariables`). MySQL 기본값은 50 초다.

| 기준 | 값 | 3 초와의 관계 |
|---|---|---|
| 정상 요청이 잠금을 쥐는 가장 긴 시간 | 브랜드 삭제, 상품 10,000 개에 0.14 초(2.2). 확정 한 건은 수 ms | 20 배 이상 여유. 한 상품에 확정 수백 건이 줄을 서야 닿는다 |
| 커넥션 획득 대기 한도 | Hikari `connection-timeout` 3 초, 풀 40 개 | 같게 맞춘다 |

잠금을 기다리는 요청은 그동안 커넥션을 쥔다. 50 초를 기다리면 한 행에 걸린 요청 40 개가 풀을 다 쥐고,
**그 행과 무관한 요청**까지 3 초 뒤 커넥션을 못 얻고 실패한다. 행 하나의 지연이 서비스 전체로 번진다.
잠금 대기를 커넥션 대기와 같게 두면 기다리던 쪽이 먼저 포기하고 커넥션을 돌려준다.
JPA 의 `jakarta.persistence.lock.timeout` 힌트는 MySQL 의 행 잠금 대기 시간 설정으로 쓸 수 없어서 세션 변수로 건다. JdbcTemplate 경로에도 같이 걸린다.

MySQL 은 대기 시간을 넘기면 기본 설정(`innodb_rollback_on_timeout=OFF`)에서 **마지막 문장만** 되돌린다.
트랜잭션 전체가 되돌아가는 것은 그 예외(`PessimisticLockingFailureException`)가 `@Transactional` 밖으로 전파되기 때문이다.
`LockWaitTimeoutTest` 가 이것을 본다 — 다른 커넥션이 둘째 품목을 쥔 채, 결제와 첫 품목 차감 SQL 이 나간 확정이 약 3 초에 포기하고
잔액 · 두 재고 · `DRAFT` 가 모두 확정 전 그대로다. 설정을 빼면 10 초 안에 끝나지 않아 실패한다.
응답은 503 `LOCK_UNAVAILABLE` 이다(4.5).

**뒤집을 조건**: 정상 요청이 잠금을 1 초 넘게 쥐게 되면(상품 수십만 개 브랜드의 삭제, 트랜잭션 안의 외부 호출) 늘린다.
그때 `connection-timeout` 도 함께 본다 — 잠금 대기가 커넥션 대기보다 길어지면 위의 전파가 다시 생긴다.

### 4.5 잠금을 얻지 못한 요청은 503 이다

잠금 대기 초과와 교착의 희생자는 `ApiControllerAdvice` 가 503 `LOCK_UNAVAILABLE` 로 바꾼다(`COMMON-012`). 둘 다 Spring 의 `PessimisticLockingFailureException` 으로 올라오므로 처리기는 하나다.

| MySQL | Hibernate | Spring |
|---|---|---|
| 1205 `Lock wait timeout exceeded` | `PessimisticLockException` | `PessimisticLockingFailureException` |
| 1213 `Deadlock found` | `LockAcquisitionException` | `CannotAcquireLockException` (위의 하위 타입) |

세 가지를 구분해 답한다.

| 응답 | 뜻 | 클라이언트가 할 일 |
|---|---|---|
| 409 (`INSUFFICIENT_STOCK` 등) | 요청이 지금 상태와 맞지 않는다 | 같은 요청을 다시 보내도 결과가 같다 |
| **503 `LOCK_UNAVAILABLE`** | 요청은 맞지만 지금 붐벼서 처리하지 못했다. 아무것도 반영되지 않았다 | 잠시 뒤 다시 보낸다 |
| 500 | 예상하지 못한 오류 | 상태를 확인한다 |

409 에 별도 에러 코드를 붙이는 선택지도 있다. 업무 거절과 같은 상태 코드라 클라이언트가 에러 코드까지 읽어야 재시도 여부를 안다. 상태 코드만으로 가를 수 있는 503 을 고른다.
서버가 자동으로 재시도하지는 않는다. 확정을 다시 돌리면 같은 행에서 다시 줄을 서고, 재시도는 요청한 쪽이 판단하는 것이 맞다.

`OrderLockFailureApiE2ETest` 가 확정 API 로 두 경우를 본다. 잠금 대기 초과는 다른 커넥션이 둘째 상품을 쥔 채 확정을 부른다.
교착은 다른 커넥션이 상품 30 행을 먼저 바꿔 확정보다 무거워진 뒤 둘째 상품을 잡고, 확정이 그 행에서 기다리는 것을 `data_lock_waits` 로 확인한 다음 첫 상품을 요청해 순환을 만든다.
InnoDB 는 트랜잭션의 무게(undo 기록 수 + 잠금 구조체 수)가 가벼운 쪽을 희생자로 고른다. 다른 커넥션은 undo 30 개를 쌓았고, 확정은 그 시점에 주문 · 잔액 · 첫 상품 UPDATE 와 원장 INSERT 정도라 확정이 진다.
교착이 실제로 일어났다는 것은 순환을 닫은 요청이 1 초 안에 잠금을 얻는 것으로 확인한다 — 교착이 아니라면 확정이 잠금 대기 한도(3 초)까지 쥐고 있었을 것이다.
두 경우 모두 503 이고, 잔액 · 재고 · `DRAFT` · 결제액 · 확정 시각 · 원장(`CHARGE` 만)이 그대로다. 확정 경로가 커져 무게가 30 에 가까워지면 다른 커넥션이 바꾸는 행 수를 늘린다.

**지금 애플리케이션 경로끼리는 교착이 생기지 않는다.** 여러 행을 잠그는 경로가 확정 하나이고 순서가 고정이다(4.1). 교착을 다루는 이유는 DB 에 붙는 다른 클라이언트(배치 · 운영 도구)가 다른 순서로 잡을 수 있어서다. 테스트도 바깥 커넥션으로 순환을 만든다.

**뒤집을 조건**: 클라이언트가 503 을 받고 무작정 재시도해 혼잡을 키우면 `Retry-After` 를 함께 준다. 교착이 애플리케이션 경로끼리 생기면(주문 취소처럼 상품 → 포인트 순서로 잠그는 경로) 응답을 바꾸기 전에 잠금 순서부터 맞춘다.

## 5. 갱신 유실을 재현하는 대조군

`StockLostUpdateControlTest` 는 **잠금이 왜 필요한지 보여 주는 음성 대조군**이다. 제품 코드를 거치지 않고 JDBC 커넥션 둘을 직접 쓴다.

```
T1: SELECT quantity → 5          T2: SELECT quantity → 5        (잠금 없는 읽기)
            └──── 둘 다 읽을 때까지 장벽 ────┘
T1: UPDATE quantity = 4; COMMIT   T2: UPDATE quantity = 4; COMMIT  (조건 · 버전 없이 읽은 값 − 1)
```

두 트랜잭션이 모두 5 를 읽었고, 둘 다 커밋했는데 최종 재고는 4 다. **성공 2 + 최종 재고 4 ≠ 초기 재고 5** — 한 차감이 사라졌다.
최종 재고가 음수가 아니어도 틀린 결과다. 두 번째 UPDATE 는 READ COMMITTED 에서도 첫 커밋을 기다렸다가 쓰지만,
쓰는 값이 **이미 낡은 읽기에서 계산한 상수**라 기다림이 결과를 고치지 못한다.

- 장벽은 이 대조군 안에만 있다. 제품의 잠금 경로에는 장벽 · sleep 이 없다.
- 장벽과 future 에 제한 시간을 두고, 시간 초과 · SQL 오류는 예외로 테스트를 실패시킨다 — 재현으로 세지 않는다.
- `quantity = quantity - 1` 처럼 DB 의 현재 값에서 빼는 문장은 이 예제와 다르다. 그 문장은 갱신을 잃지 않는다(4.3 의 조건부 UPDATE).

**대조군이 통과했다는 사실은 실제 주문의 정합성 증거가 아니다.** 그 증거는 4.2 의 경쟁 테스트다 —
같은 "읽고 → 계산하고 → 쓰는" 모양이지만 읽기가 `FOR UPDATE` 라, 두 번째 트랜잭션이 첫 커밋 뒤의 값을 읽는다.
잠금을 빼면 4.2 의 테스트가 이 대조군과 같은 방식으로 깨진다(재고 5 에 8건 모두 확정).
