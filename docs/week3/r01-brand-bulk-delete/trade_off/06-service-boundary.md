# 일괄 삭제 서비스를 분리할까?

[← 전체 선택 현황](total_trade_off.md)

## 판단할 문제

삭제 정책은 도메인이 수행하고 application은 조회·행동·저장과 트랜잭션을 조율한다.
이를 기존 `BrandService`에 추가할지, 삭제 전용 서비스로 분리할지 비교한다.

> **비교 보류 — 필수 결정에서 제외**
>
> 전용 서비스 분리를 추천한 의견은 있었지만 구현을 진행하기 전에 반드시 결정할 주제는 아니다.
> 기존 비교는 참고로 보존하고, 책임·의존성 분리가 실제로 필요한 경우에만 다시 검토한다.

## 장단점 비교

| 기준 | 기존 서비스 확장 | 삭제 전용 서비스 |
|---|---|---|
| 변경 규모 | 기존 클래스·구조 유지 | 클래스 추가·기존 역할 조정 |
| 책임 표현 | 생성·수정·삭제가 한 클래스에 모임 | 삭제의 경계와 의존성이 명확함 |
| 유지보수 | 공통 흐름을 한곳에서 관리 가능 | 삭제 흐름·테스트를 분리해 관리 가능 |
| 비용·주의 | 삭제가 커지면 다른 기능과 함께 관리 | 작은 흐름이면 분리 비용이 더 클 수 있음 |

## 옵션별 판단

> **비교 보류 — 기존 서비스:** 변경을 최소화할 수 있는 선택으로 기록한다.

> **비교 보류 — 전용 서비스:** 분리는 선택 사항이며, 추천 의견을 채택으로 간주하지 않는다.

## 재검토 조건

구현 중 기존 서비스의 책임·의존성이 커져 분리가 필요한 경우 다시 비교한다.
어느 쪽이든 프록시를 거치는 application 진입점에 전체 트랜잭션을 둔다.
실제 SQL 이후 실패를 유발할 테스트 경계는 구현 계획에서 정하며 별도 트레이드오프 주제로 두지 않는다.
