# R01 구현 계획

[요구사항](requirement.md) · [트레이드오프](trade_off/total_trade_off.md) · [전체 요구사항](../total_requirement.md)

작업 브랜치: `volume-3/r01-brand-bulk-delete` · PR 대상: `volume-3/main`

상태: 구현 계획대로 커밋 1~5 구현·검증 완료. 실제 결과와 계획 대비 차이·회고는 [result.md](result.md)를 따른다.

## 문서와 진행 원칙

이 문서는 코드 없이 커밋별 목표·TODO·완료 기준을 기록한다. 이번 준비 작업은 문서 작성까지이며 기능 구현·커밋·푸시는 포함하지 않는다.
기존 `BrandService`를 확장하고, 확정한 트레이드오프를 유지한다. 아래 커밋은 이후 구현 작업을 나누는 단위다.

각 구현 커밋은 **실패 테스트 작성·확인 → 구현 → 리팩터링 → 관련 테스트 통과 → 커밋** 순서로 진행한다.
기존 동작을 확인하는 테스트가 처음부터 통과하면 그 사실을 기록하며, Red를 만들기 위해 정상 코드를 변경하지 않는다.
테스트와 해당 구현·보완을 함께 커밋한다.

## 커밋 1 — 브랜드·상품 일괄 삭제 도메인 규칙

**목표:** 브랜드가 연결 상품의 삭제 생명주기를 책임지도록 순수 도메인에 규칙을 표현한다.

- [x] 브랜드가 소속 상품 컬렉션을 통해 삭제 생명주기를 책임지도록 테스트한다.
- [x] 미삭제 상품·재고 0·빈 컬렉션·이미 삭제된 상품의 처리 규칙을 구현한다.
- [x] 상품을 조회하지 않은 상태를 실제 빈 컬렉션으로 취급해 불완전하게 삭제하지 않도록 한다.
- [x] 기존 브랜드 생성·수정 동작의 호환성을 유지한다. API의 일괄 삭제 전환은 커밋 3에서 진행한다.
- [x] 신규 도메인 테스트와 관련 기존 테스트가 통과하면 커밋한다.

**완료 기준:** DB 없이 일괄 삭제 정책과 상태 보존을 검증할 수 있다.

## 커밋 2 — 삭제 전용 조회·저장 연결

**목표:** 삭제에 필요한 전체 상품을 조회하고, 도메인의 삭제 결과를 기존 관리 엔티티에 반영한다.

- [x] 실제 MySQL에서 상품 없는 브랜드와 모든 소속 상품을 누락 없이 조회하는 테스트를 작성한다.
- [x] 삭제 전용 LEFT JOIN FETCH와 조회용 단방향 OneToMany를 적용한다. FK 저장은 기존 상품의 brandId가 담당한다.
- [x] 일반 브랜드 조회에는 상품 전체 로딩을 강제하지 않는다.
- [x] 도메인 상품과 관리 엔티티를 ID로 대응시키고, 누락·잘못된 대응을 확인한 뒤 삭제 상태를 반영한다.
- [x] 브랜드 단위 저장 호출로 전체 삭제 상태가 반영되고, 가격·재고·소속 관계 등 무관한 값은 유지되는지 검증한다.
- [x] flush·영속성 컨텍스트 초기화 후 재조회하는 저장소 테스트가 통과하면 커밋한다.

> 구현 중 발견: `@OneToMany` 추가로 `ddl-auto: create`(test 프로필)가 `products.brand_id`에 물리적 FK 제약을 새로 생성해
> 기존 `ProductRepositoryIntegrationTest`(브랜드 없이 임의 brandId 사용)가 깨졌다. `@JoinColumn(foreignKey = @ForeignKey(NO_CONSTRAINT))`로
> 기존과 동일하게 물리적 FK 없는 상태를 유지해 해결했다.

**완료 기준:** 도메인에서 결정한 삭제 결과를 기존 관리 엔티티에 정확히 저장할 수 있다.

## 커밋 3 — 기존 브랜드 삭제 API에 연결

**목표:** 기존 삭제 API를 같은 트랜잭션에서 브랜드와 상품을 함께 삭제하는 흐름으로 전환한다.

- [x] 연결 상품이 있으면 거절하던 테스트를 일괄 삭제 성공 계약에 맞춰 변경하고 Red를 확인한다.
- [x] 기존 서비스에서 삭제 전용 조회 → 도메인 삭제 → 브랜드 단위 저장으로 연결한다.
- [x] 전체 흐름을 기존 Application 트랜잭션에 포함한다.
- [x] 활성 상품 존재를 이유로 거절하는 검사와 사용하지 않게 된 관련 코드를 참조 확인 후 정리한다.
- [x] 기존 URL·응답 형식·없는 브랜드와 삭제된 브랜드의 오류 계약을 유지한다.
- [x] 정상·경계·오류 API 테스트와 관련 회귀 테스트가 통과하면 커밋한다.

**완료 기준:** 기존 삭제 API로 브랜드와 연결 상품을 함께 논리 삭제할 수 있다.

## 커밋 4 — 실제 SQL 이후 전체 롤백 검증

**목표:** 변경 SQL이 실행된 뒤 실패해도 이번 요청의 변경 전체가 취소됨을 실제 DB로 검증한다.

- [x] 테스트 전용 저장 경계에서 실제 저장·flush 이후 예외를 발생시키는 통합 테스트를 작성한다.
- [x] 제품 코드에는 실패 주입용 분기나 직접 복구 코드를 추가하지 않는다.
- [x] 준비 데이터는 미리 커밋하고, 실제 Spring 서비스 호출이 끝난 뒤 별도 조회로 상태를 확인한다.
- [x] 브랜드·상품의 전체 롤백과 다른 대상·과거 주문의 보존을 검증한다.
- [x] 발견한 트랜잭션 참여·예외 전파 문제를 보완하고 관련 테스트가 통과하면 커밋한다.

> `@MockitoSpyBean`으로 ProductJpaRepository를 감싸 두 번째 상품 저장에서 실패를 주입했다. 별도의 트랜잭션 참여·예외 전파 문제는
> 발견되지 않았다(기존 `@Transactional` 서비스 경계가 그대로 전체 롤백을 보장).

**완료 기준:** 메모리 상태가 아닌 실제 DB 조회로 전체 롤백을 증명한다.

## 커밋 5 — 삭제 후 사용 제한·과거 데이터 보존

**목표:** 일괄 삭제가 기존 소비 경로에 적용되고 과거 거래 사실은 보존되는지 확인한다.

- [x] 브랜드 일괄 삭제를 실제로 실행한 뒤 상품 목록·상세·내 좋아요 목록에서 제외되는지 확인한다.
- [x] 새 좋아요·새 주문·상품 수정·재고 변경은 거절되고, 기존 자기 좋아요 취소는 가능한지 확인한다.
- [x] 삭제 전 생성한 DRAFT의 확정이 거절되며 재고·잔액·기록이 보존되는지 확인한다.
- [x] 과거 주문의 고객·관리자 조회에서 품목·수량·단가·총액·결제 결과가 유지되는지 확인한다.
- [x] 기존 테스트를 활용하고, 일괄 삭제와 연결해 부족한 검증·동작만 보완한다.
- [x] 관련 회귀 테스트와 모듈 check·Checkstyle·ArchUnit이 통과하면 커밋한다.

> 새 좋아요·새 주문·상품 수정·재고 변경 거절은 모두 기존 `products.deleted` 플래그 기반 로직이 그대로 적용되어
> 기존 회귀 테스트(LikeApiE2ETest.returnsNotFound_whenProductIsDeleted, OrderApiE2ETest.returnsNotFound_whenProductIsDeleted,
> ProductTest.rejectsChanges_whenDeleted)로 이미 커버됨을 확인했고 별도 테스트를 추가하지 않았다.

**완료 기준:** R01의 삭제 후 업무 계약과 관련 회귀 검증을 충족한다.

실제 실행 결과·계획과의 차이·회고는 구현 이후 `result.md`에 기록한다. 문서 작성만으로 구현·검증 완료를 표시하지 않는다.
