# R01. 브랜드·연관 상품 일괄 삭제

[전체 요구사항](../total_requirement.md) · 작업 브랜치: `volume-3/r01-brand-bulk-delete` · PR 대상: `volume-3/main`

상태: 트레이드오프 정리·[구현 계획](plan.md) 작성, 기능 구현·검증 완료. 실제 결과와 회고는 [result.md](result.md)를 따른다.
합의한 방향과 구현 시 확인할 사항은 [트레이드오프 전체 목록](trade_off/total_trade_off.md)을 따른다.
원문 대응: Implementation Quest 1의 브랜드 흐름, 2, 4의 브랜드 검증 및 Checklist 브랜드 일괄 변경.
관리자 접근 제한은 사용자 합의로 제외한다.

## 1. 목적

브랜드를 삭제할 때 연결된 미삭제 상품도 고객의 사용 대상에서 함께 제외한다.
성공하면 대상 전체에 반영되고, 중간에 실패하면 이번 요청의 변경 전체가 취소되어야 한다.
다른 대상과 이미 저장된 주문의 거래 사실은 보존한다.

## 2. 현재 동작과 변경점

| 구분 | 현재 코드에서 확인한 동작 | 요구하는 변경 |
|---|---|---|
| 진입 API | `DELETE /api-admin/v1/brands/{brandId}` | 경로를 유지하며 일괄 삭제 계약으로 확장 |
| 브랜드 삭제 | `BrandService`가 활성 연결 상품 존재 시 `BRAND_HAS_ACTIVE_PRODUCTS`로 거절 | 연결된 미삭제 상품을 포함해 함께 처리 |
| 저장 모델 | 브랜드·상품의 논리 삭제 모델과 application 트랜잭션 사용 | 기존 모델을 기준으로 전체 작업의 원자성과 사용 제한 보장 |
| 기존 소비 경로 | 상품 조회·좋아요·주문·상품 관리 기능 존재 | 일괄 삭제 결과가 각 경로에도 적용되는지 검증·보완 |

기존 단일 상품의 삭제·조회 정책은 참고하되, 일괄 삭제에 대한 검증이 완료됐다고 간주하지 않는다.

## 3. 포함·제외 범위

**포함**

- 대상 브랜드와 연결된 미삭제 상품 전체. 재고 0인 상품과 연결 상품이 없는 브랜드도 포함한다.
- 하나의 트랜잭션에서 전체 성공·전체 롤백, 삭제 후 고객·관리자 기능의 사용 제한.
- 삭제 전에 생성된 DRAFT의 확정 거절, 과거 주문 정보·결제 결과와 다른 대상의 보존.
- 실제 MySQL 실패 주입·재조회, 대표 HTTP 사례, 관련 회귀 검사와 설계 문서.

**제외**

- 관리자 식별·인증·인가 추가와 관련 401·403 검증.
- 브랜드 삭제와 상품 등록의 동시 실행 등 브랜드 관리 작업의 경쟁 제어 확장.
- 주문 경쟁 제어 구현은 R02에서 담당한다. R01에서는 삭제 상품의 확정 거절 계약을 확인한다.
- 상품마다 별도 commit하는 부분 성공 방식, 과거 주문까지 지우는 연쇄 삭제.

## 4. 업무 규칙

1. 삭제 대상은 해당 브랜드와 연결된 미삭제 상품 전체이며, 재고 수량으로 대상을 제외하지 않는다.
2. 연결 상품이 없어도 브랜드 삭제는 성공한다. 없는 브랜드는 기존 없는 대상 오류로 처리한다.
3. 전체 변경을 함께 확정한다. 어느 저장 단계든 실패하면 이번 요청의 브랜드·상품 변경을 모두 취소한다.
4. 다른 브랜드·상품은 변경하지 않는다. 이미 삭제된 상품을 되살리거나 새로 사용 가능하게 만들지 않는다.
5. 삭제 상품은 고객 상품 목록·상세·내 좋아요 목록에서 제외한다. 새 좋아요·새 주문은 거절한다.
6. 삭제 상품에 대한 기존 자기 좋아요 취소는 유지한다. 상품 수정·재고 변경은 거절한다.
7. DRAFT는 구매 가능성을 예약하지 않는다. 생성 후 상품이 삭제되면 확정 시 거절하며 차감·결제 기록을 남기지 않는다.
8. 기존 주문의 품목·상품 정보·수량·단가·총액·포인트 결제 결과를 보존한다. 현재 상품 가격으로 다시 계산하지 않는다.
9. 기존 URL·응답 형식·없는 대상과 삭제 대상의 오류 계약을 유지하되, 활성 연결 상품 존재로 삭제를 거절하던 정책을 변경한다.

## 7. 미정 사항

핵심 트레이드오프의 미정 사항은 없다. 도메인의 삭제 정책, 삭제 전용 조회, 브랜드 단위 저장과 관리 엔티티 반영을 합의했다.
조회는 [JPQL LEFT JOIN FETCH](trade_off/07-fetch-strategy.md), 매핑은 [조회용 단방향 OneToMany와 기존 brandId 저장](trade_off/08-association-mapping.md)을 따른다.

삭제용 조회의 상품 완전성, 상품 ID 대응·누락, 기존 삭제 후 사용 제한의 충족 여부는 구현 계획과 검증에서 확인한다.
실제 SQL 실행 후 실패 주입·트랜잭션 종료 후 재조회 방법은 구현 계획에서 구체화하며 별도 트레이드오프로 분리하지 않는다.
서비스 분리와 배치 최적화는 필수 결정으로 두지 않으며 구체적인 필요가 생길 때만 재검토한다.

결정한 내용은 `trade_off/`의 전체 목록·주제별 문서와 `plan.md`에 반영하며, 업무 계약을 바꿔야 하면 먼저 명세를 합의한다.
