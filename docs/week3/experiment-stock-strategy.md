# 재고 차감 전략 비교 실험 결과

3주차 설계 6.6의 선택 확장 실험이다. 제품 코드가 아니며, 기술 글의 근거로 쓴다.

- 실험 코드: `apps/commerce-api/src/test/java/com/loopers/experiment/StockStrategyExperiment.java`
- 실행: `RUN_EXPERIMENT=true ./gradlew :apps:commerce-api:test --tests '*StockStrategyExperiment'` (평소 `check` 에서는 건너뜀)
- 실행일: 2026-10-09, 로컬 Docker의 MySQL 8.0 Testcontainers, **한 번 실행한 결과**

## 조건

| 항목 | 값 |
|---|---|
| 대상 | 테스트 전용 테이블 `experiment_stock(id, stock, version)`. 세 전략 모두 같은 테이블 · 같은 모양의 트랜잭션 |
| 비관적 잠금 | `SELECT ... FOR UPDATE` → 확인 → 작업 → `UPDATE` |
| 낙관적 잠금 + 재시도 | 일반 읽기 → 확인 → 작업 → `UPDATE ... WHERE version = ?` (0행이면 충돌). 실제 `~Retrier` 와 같은 정책: 총 3회, 50ms부터 지수 백오프(최대 200ms) + 지터 |
| 조건부 갱신 | `UPDATE ... SET stock = stock - 1 WHERE stock >= 1` → 작업. 행 잠금은 UPDATE부터 commit까지 유지 |
| 작업(ms) | 확정 트랜잭션 안의 다른 작업 시간을 흉내 낸 실험 변수. **실험 코드 안에만** 두며 실제 서비스의 잠금 구간에는 넣지 않음 |
| 환경 | 테스트 커넥션 풀 10개, 커넥션 대기 한도 3초(`connection-timeout`), 잠금 대기 한도 3초(`innodb_lock_wait_timeout`) |
| 조회 | 실험이 도는 동안 별도 스레드가 50ms 간격으로 무관한 조회(`select 1`)를 보내 커넥션을 얻지 못한 실패와 가장 오래 걸린 시간을 기록 |
| 판정 | 모든 조건에서 "초기 재고 − 성공 = 최종 재고"를 assertion으로 확인 (24개 조건 모두 통과) |

## 관찰

1. **낙관적 잠금 + 재시도는 몰리는 상황에서 "남은 재고가 있는데 실패"를 만든다.**
   - 재고 5 · 요청 8 · 작업 100ms: 성공 3 · 한도 초과 5. 재고 2개가 남았는데 5건이 실패했다.
   - 재고 5 · 요청 12 · 작업 100ms: 품절 0 · 한도 초과 7. 품절이어야 할 결과가 충돌로 섞였다.
   - 재고 100 · 요청 30 · 작업 100ms: 성공 9 · 한도 초과 21. 재고 91개가 남은 채 21건이 실패했다.
   - 작업 0ms에서도 재고 100 · 요청 30이면 한도 초과 6건이 나왔다.
2. **작업이 짧을 때도 낙관적 방식이 가장 느렸다.** 작업 0ms 조건에서 비관적 · 조건부는 수십~130ms, 낙관적은 280~500ms였다. 백오프 대기와 재시도(총 시도가 요청 수의 약 2배)가 원인이다. "재시도를 포함해도 시간 차이가 크지 않다"는 가정은 이 조건에서 맞지 않았다.
3. **비관적 잠금은 모든 요청을 처리했지만, 무관한 조회까지 기다리게 했다.**
   - 재고 100 · 요청 30 · 작업 100ms: 30건 모두 성공, 소요 3,414ms. 같은 시간 동안 무관한 조회가 커넥션을 기다린 최대 시간이 **2,293ms**였다.
   - 잠금 시간 초과는 0건이었다. 커넥션이 10개뿐이라 잠금을 기다릴 수 있는 요청은 최대 9건이고, 나머지는 **커넥션 풀 앞에서** 기다렸다. 병목은 잠금보다 풀이었다.
   - 조회 실패(커넥션 대기 3초 초과)는 0건이었다. 소요 3.4초로 한도에 가까웠고, 요청이 더 많거나 작업이 더 길면 실패가 시작될 것으로 예상하지만 **이번에는 확인하지 않았다.**
4. **조건부 갱신은 비관적 잠금과 결과 · 대기 양상이 거의 같았다.** 차감 뒤 작업하는 동안 행 잠금을 쥐므로 재고 100 · 작업 100ms에서 소요 3,223ms, 조회 최대 대기 2,205ms였다. 작업이 없을 때(0ms)는 가장 빨랐다. 다만 이 실험은 재고만 다뤄서, 규칙이 `Product.decrease` 에서 SQL로 옮겨가는 비용(D-29)은 표에 나타나지 않는다.

## 설계 판단과의 연결

- 재고에 비관적 잠금을 고른 근거(4.1)인 "몰리면 재시도가 폭증하고 한도 초과가 재고 부족과 섞인다"는 관찰 1 · 2로 확인됐다.
- 알려진 한계(8장)인 "잠금을 기다리는 요청이 커넥션을 쥐어 무관한 API까지 영향을 받는다"는 관찰 3에서 **지연(최대 2.3초)으로** 확인됐고, 실패까지는 재현하지 않았다.

## 한계

- 한 번 실행한 결과다. 시간 값은 실행마다 달라지며 통계적으로 반복 측정하지 않았다.
- 로컬 Docker 환경이고, 실제 운영의 풀 크기(40개)와 다르다.
- 재고만 다루는 실험이라 실제 주문 확정(주문 · 포인트 · 재고)의 비용과 같지 않다.
- 작업 시간은 sleep으로 흉내 냈다. 실제 작업은 CPU · DB 부하를 함께 만든다.
