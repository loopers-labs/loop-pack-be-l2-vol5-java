# 3주차 테스트 케이스와 검증 기록

판단·이유는 [3주차 설계](./design.md)에 있다. 이 문서는 각 항목의 테스트 케이스와 현재 상태만 모은다.

테스트 표의 **통과**는 실제 코드로 검증한 사례, **예정**은 아직 검증하지 않은 사례다. 수동 SQL 실험과 실제 서비스 테스트는 구분한다.

### 1.2 주문 확정

**테스트 케이스** — `OrderPersistenceIntegrationTest`, `StockConcurrencyTest`, `TransactionFailureIntegrationTest`

| 상황 | 기대 결과 | 상태 |
| --- | --- | --- |

| 재고·포인트·적립 SQL을 실제 실행한 뒤 주문 저장 단계에서 예외 | 재고·잔액·사용 기록·적립·주문 상태·결제액 모두 원복. 이후 정상 확정 가능 | 통과 |
| 상품 J의 재고 UPDATE는 실행됐지만 포인트 결제 전에 실패 | J의 재고 원복. 포인트 사용·적립 없음, 주문 DRAFT·결제액 0 유지 | 통과 |
| J·K를 함께 주문하며 J의 재고 UPDATE 후 K 처리 중 실패 | 먼저 줄인 J의 재고도 원복. K·포인트·주문도 변경 전 상태 유지 | 통과 |
| J·K의 재고 UPDATE를 모두 실행한 뒤 포인트 처리 중 실패 | J·K의 재고 모두 원복. 실행된 포인트 변경도 롤백되고 주문은 DRAFT 유지 | 통과 |

**롤백 검증의 SQL 실행:** JPA는 객체 상태 변경 시점과 SQL 실행 시점이 다를 수 있다. 재고 차감 뒤 중간 실패를 주입하는 롤백 테스트는 `flush()`로 실제 UPDATE를 실행한 다음 실패시키고, 트랜잭션 종료 후 새 트랜잭션에서 원복을 확인한다. 객체만 변경하고 실패시키면 SQL 실행 전 실패일 수 있어 이 단계를 둔다. flush는 commit이 아니므로 실행된 변경도 롤백할 수 있다. 재고 부족은 모든 품목을 차감하기 전에 검사되므로, 이 테스트의 중간 실패는 재고 부족과 구분되는 기술 오류다.

**현재 상태:** 기본 저장과 재고·포인트 SQL 실행 후 롤백을 검증했다. `TransactionFailureIntegrationTest`에서 재고만 변경된 뒤, 두 번째 상품 차감 시점, 포인트 사용 SQL 이후의 실패도 각각 추가했다. 실패 직전 SQL로 변경된 값을 확인하고 트랜잭션 종료 후 새 조회에서 재고·잔액·기록·주문 원복을 확인한다. 만료로 잔액이 부족한 기존 테스트는 재고 차감 전 검사에서 실패하므로, 재고 UPDATE 이후 롤백 테스트를 대신하지 않는다. 동시 확정의 보호 방법은 2장에서 다룬다.

### 2.2 상품 등록과 브랜드 삭제

**테스트 케이스** — `BrandConcurrencyTest`

| 상황 | 기대 결과 | 상태 |
| --- | --- | --- |
| A가 상품 등록을 마쳤지만 아직 커밋 전. B는 상품 등록용 브랜드 조회, C는 브랜드 수정·삭제용 조회 시도 | B의 `FOR SHARE`는 허용. C의 `FOR UPDATE`는 A 종료 전에는 얻을 수 없고 커밋 후 가능 | 통과 |
| A가 브랜드 삭제를 처리했지만 아직 커밋 전. B는 상품 등록용 조회, C는 브랜드 수정·삭제용 조회 시도 | B·C 모두 A의 잠금과 충돌. 삭제 커밋 후 상품 등록은 삭제 상태를 확인해 거절 | 통과 |
| 상품 등록이 먼저 진행하고 삭제가 기다림 | 등록 커밋 후 삭제가 진행되어 새 상품도 함께 삭제 | 통과 |
| 미커밋 삭제가 있는 동안 상품 등록 요청 | 등록이 기다렸다가 삭제 커밋 후 삭제된 상태를 읽고 거절 | 통과 |
| 브랜드 삭제가 롤백된 뒤 상품 등록 | 잠금이 해제되고 브랜드는 미삭제 상태이므로 등록 성공 | 통과 |
| 상품 등록 8건과 브랜드 삭제를 함께 시작 | 먼저 등록된 상품은 삭제되고, 삭제 후 등록은 거절. 삭제된 브랜드에 미삭제 상품이 남지 않음 | 통과 |
| 같은 브랜드에 서로 다른 상품 2건 등록 | 두 등록 모두 성공. 공유 잠금끼리는 함께 허용됨을 별도 연결 검사에서도 확인 | 통과 |
| 브랜드 이름 수정과 삭제가 겹침 | 수정 요청이 삭제 표시를 지워 브랜드를 되살리지 않음 | 통과 |

위 첫 두 사례는 B·C의 전체 API가 아니라 그 요청이 사용할 잠금 조회 SQL을 다른 DB 연결에서 실행한 검사다. `NOWAIT`로 기다리는 대신 충돌을 즉시 확인한다. 실제 서비스 요청의 대기·커밋 후 결과는 이어지는 테스트에서 확인한다.

**잠금 범위 보완:** 다른 브랜드의 기존 상품을 별도 연결에서 `FOR UPDATE NOWAIT`로 읽는 테스트가 수정 전 잠금 충돌로 실패했다. 대상 ID 조회와 PK별 잠금 조회로 나눈 뒤 통과했다. `(brand_id, deleted_at)` 인덱스는 후보 ID 검색을 지원한다. EXPLAIN에서 후보 조회는 `idx_product_brand_deleted`(ref), 개별 잠금 조회는 `PRIMARY`(const)를 사용했다. 이는 테스트 데이터에서 확인한 실행 계획이며 모든 데이터 분포의 계획을 보장하지 않는다. 기존 로컬 DB에 DDL을 직접 실행하지 않았다.

**현재 상태:** 기존 8개 테스트와 잠금 범위 사례를 검증했다. 수정 전에는 등록·삭제 중 브랜드 잠금이 유지되지 않았고, 이름 수정과 삭제가 겹쳐 삭제 표시가 사라지는 실패를 확인했다. 수정 후 잠금 유지·해제와 커밋 후 상태 재확인까지 통과했다. 잠금 충돌을 즉시 확인하는 `NOWAIT`는 테스트에서만 사용하고, 실제 서비스는 일반 대기를 사용한다.

**벌크 삭제 비교 실험** — `BrandBulkDeletionExperimentTest`의 9개 사례를 통과했다. 서비스 구현은 유지하고 테스트 전용 벌크 경로와 비교했다.

| 확인 | 결과 |
| --- | --- |
| 상품 수 10·100·1,000개에서 삭제·커밋 | 두 방식 모두 활성 상품 삭제, 재고 0 포함 |
| 삭제 SQL 후 커밋 전 별도 연결의 잠금 조회 | 대상 상품은 두 방식 모두 충돌. 다른 브랜드 상품 한 행은 현재 방식에서 허용, 벌크에서 충돌 |
| 실제 삭제 SQL 이후 실패 | 브랜드·상품 모두 롤백 |
| 기존 데이터 보존 | 기존 삭제 시각·상품 재고와 가격·다른 브랜드·과거 주문과 품목 유지 |

잠금 검사는 10·1,000개 조건의 REPEATABLE READ에서 `FOR UPDATE NOWAIT`로 수행했다. 실제 HTTP 경쟁이나 다른 브랜드 전체의 잠금 범위를 검증한 것은 아니다. SQL 횟수·처리 시간과 실행 계획은 [ADR 0019](../adr/0019-brand-bulk-deletion-comparison.md)에 기록했다. 비교 후 이번에는 벌크를 채택하지 않고 현재 방식을 유지하기로 결정했다.

**분포·통계 추가 비교:** 브랜드당 100개, 브랜드 2개·100개와 통계 갱신 전후를 두 방식으로 비교했다. 현재 방식은 네 조건에서 다른 브랜드 상품 잠금 충돌이 없었다. 벌크는 100개 브랜드·통계 갱신 후 브랜드 인덱스를 사용할 때 검사한 다른 브랜드 상품 잠금 충돌이 없었고, 나머지 조건은 충돌했다. 실제 상품 수정 서비스도 비충돌 조건에서는 삭제 커밋 전에, 충돌 조건에서는 커밋 후 완료됐다. 이 검사는 최대 200ms 커밋 지연을 둔 원인 확인이며 성능 측정과 구분한다.

별도로 인위적 커밋 지연 없이 실제 삭제·수정 서비스를 동시 실행했다. 8개 조건에서 각 3회 모두 성공하고 삭제·수정 결과를 DB로 확인했다. 매회 DB 잠금 대기가 발생했다고 주장하지 않으며, 처리 시간은 ADR 0019에 분리했다. 제품 코드·격리 수준 변경은 없다.

800원 결제가 먼저 실패하면 그 요청에서 수행한 만료 처리도 함께 롤백될 수 있다. 그래도 결제에 만료 포인트를 사용할 수는 없으며, 배치가 정상 완료된 뒤 위 최종 잔액·기록을 확인한다. 배치가 먼저 완료한 만료 처리는 뒤 결제의 실패로 되돌리지 않는다. 두 순서 모두 만료 금액이 중복 차감되지 않아야 한다.

**현재 상태:** 포인트 비관적 락과 지급건·사용 기록의 잠금 조회를 구현했다. 수정 전에는 세 주문이 모두 성공하고, 만료 300원이 600원으로 중복 기록되거나 충전 2,000원이 잔액에서 유실되는 실패를 확인했다. 지급 기록은 JPA 컬렉션 두 개를 한꺼번에 fetch하지 않고 나눠 읽는다. 조회 SQL에 `FOR UPDATE`가 붙는 것도 확인했다. 지급건·사용 기록의 부모 외래 키는 INSERT부터 함께 저장하도록 `nullable=false`로 매핑했다. 다른 사용자 충전 진행을 검증했지만, 범위 조회·인덱스의 영향까지 포함해 모든 다른 사용자 요청이 절대 기다리지 않는다고 보장하지는 않는다. 과거 포인트 엔티티를 같은 영속성 컨텍스트에 일반 조회해 둔 뒤 재사용하는 경로는 만들지 않는다.

## 3. 추가 동시성 검증

### 3.1 좋아요 중복 등록·취소

`LikeConcurrencyTest`는 실제 HTTP·application·DB를 사용한다. 등록·취소가 각각 8건 겹칠 때 일부 응답이 500이 되는 Red를 확인했다. 유니크 제약 자체는 중복 저장을 막고 있었으므로, 데이터 중복과 정상 응답 계약을 구분했다.

| 사례 | 기대 결과 |
| --- | --- |
| 같은 관계 동시 등록 8건 | 최초 201 1건·중복 200 7건, 관계 1개 |
| 같은 관계 동시 취소 8건·없는 관계 재취소 | 모두 204, 관계 없음 |
| 서로 다른 사용자의 같은 상품 등록 | 각각 201, 관계·좋아요 수 2 |
| INSERT 뒤 바깥 트랜잭션 실패 | JDBC로 저장한 관계도 함께 롤백 |
| 등록 후 커밋 전 취소 요청 | 취소가 대기했다가 등록 커밋 후 204, 최종 관계 없음 |
| 취소 후 커밋 전 등록 요청 | 등록이 대기했다가 취소 커밋 후 201, 최종 관계 1개 |
| 등록 후 커밋 전에 다른 연결이 상품 삭제 완료 | 관계는 남지만 내 목록에서 제외, 새 등록 404·본인 취소 204 |

위 7개 테스트를 통과했다. 뒤 세 사례에서 관찰한 동작을 최종 정책으로 합의했다. 등록·취소는 첫 서비스 호출이 반환된 뒤 바깥 트랜잭션 커밋을 미룬 상태에서 다음 요청을 실행했다. 서비스 내부에 장벽을 넣지는 않았다. 삭제와 겹쳐 남은 관계는 숨기되 본인 취소를 허용하기로 확정했고 별도 상품 잠금을 추가하지 않았다.

### 3.2 잠금 대기 초과·교착

`LockFailureIntegrationTest`에서 테스트 연결에만 `innodb_lock_wait_timeout=1`을 적용했다. 실제 서비스 설정은 변경하지 않았다.

| 사례 | 확인 결과 |
| --- | --- |
| 다른 연결이 포인트를 잠근 상태에서 실제 HTTP 주문 확정 | MySQL 1205 대기 초과, HTTP 503, 주문 DRAFT·재고·포인트 유지 |
| 첫 상품 UPDATE 후 두 번째 상품에서 대기 초과 | Spring 트랜잭션 전체 롤백, 다른 연결이 커밋한 변경은 보존 |
| 두 연결이 서로 반대 순서로 상품을 UPDATE하는 SQL 대조군 | 성공 1·MySQL 1213 교착 피해 1, 피해 요청의 첫 UPDATE도 롤백 |

교착 장벽은 원인 재현용 SQL 대조군에만 둔다. 실제 주문 서비스에 장벽을 넣거나 주문 서비스가 역순으로 잠근다고 주장하지 않는다. 기술 실패는 품절·잔액 부족으로 집계하지 않는다. 503 응답·자동 재시도 없음으로 확정했다. 실제 DB 교착·롤백 검증과 별도로 `LockFailureResponseTest`에서 Spring의 잠금 실패 예외 HTTP 매핑을 확인한다.

### 3.3 커넥션 풀과 성능의 확인 범위

`modules/jpa/src/main/resources/jpa.yml`의 기본 최대 연결 수는 40개, test 프로필은 10개이며 `connection-timeout`은 3,000ms다. 이는 연결을 빌리기 위한 대기 제한이고, 3.2에서 설정한 MySQL 행 잠금 대기 제한과 다르다. 설정 파일에서 확인한 값이며 배포 환경의 최종 설정을 측정한 것은 아니다.

| 항목 | 현재 확인 범위 | 상태 |
| --- | --- | --- |
| 변경 SQL 실행 후 롤백 | 1.2의 flush·실패 주입·새 트랜잭션 재조회로 확인 | 통과 |
| 연결 부족과 행 잠금 대기 구분 | 전용 풀 2개에서 A가 잔액 잠금을 유지하고 B가 같은 잔액을 기다릴 때, C의 다른 사용자 조회가 연결 획득을 기다리는지 확인 | 미검증 |
| 서비스 잠금 대기 한도 결정 | 정상 처리·경쟁·데이터 증가 상황에서 잠금 유지 시간과 연결 획득 대기를 나누어 측정하고, 응답 시간 목표에 맞춰 1·3·5초 등의 후보별 성공·대기 초과·응답 시간을 비교 | 해야 할 일·미검증 |

| 재고 보호 방식 성능 비교 | 수동 SQL 실험의 동작 관찰과 구분하며, 재현 가능한 부하 조건·측정 결과를 이 문서에는 남기지 않았다 | 성능 결론 없음 |

연결 부족 실험에서는 풀의 사용 중·유휴 연결 수와 연결 대기 요청 수를 관찰한다. DB 잠금 대기가 먼저 끝나 결과를 가리지 않도록 두 대기 제한을 구분하고, 모든 작업 종료 뒤 데이터를 정리한다. worker 수가 풀보다 많으면 연결 대기로 실행이 나뉠 수 있으므로, 행 잠금 경쟁만 확인하려는 테스트와 연결 부족 실험을 구분한다. 위 성능 실험은 아직 실행하지 않았다. 서비스의 잠금 대기 시간은 DB 설정을 따른다. 실패 경로 검증용 테스트는 1초 제한을 사용하며, 커넥션 획득 제한은 3,000ms다.

## 5. 실행 기록

- 설계의 AI 제안 두 건을 반영했다. 재고 사전 검사는 잠금 조회 이후라는 점을 설계·ADR에 명시하고, 실제 SQL 이후 롤백 사례는 1.2에 추가했다.
- 2주차 문서는 당시 정책을 보존하고 이후 변경을 3주차·ADR로 연결했다.
- 참고 설계의 조건부 UPDATE는 대안으로 유지한다. 현재는 `Stock.decrease()`와 포인트 지급건·사용·만료 기록을 처리하는 기존 JPA 모델 행동을 유지한다. 2% 적립을 포함한 기대값도 그대로 적용한다.
- 이후 합의에 따라 잠금 실패는 503·자동 재시도 없음, 좋아요 경쟁은 DB 처리 순서 및 삭제 관계 비노출·본인 취소 허용으로 확정했다.

### 앞선 롤백 검증 보완

`TransactionFailureIntegrationTest`의 새 5개 사례를 통과했다. 이어서 `:apps:commerce-api:check`를 실행해 전체 164개 테스트(실패 0·오류 0·skip 0)와 Checkstyle·ArchUnit을 통과했다. 이번 추가 사례는 이미 구현된 트랜잭션의 누락된 검증을 보완한 것이며, 새 기능의 Red → Green 기록으로 주장하지 않는다.

실행 환경은 JDK 21·실제 MySQL Testcontainers이며 로컬 Docker 호환 설정 `JAVA_TOOL_OPTIONS=-Dapi.version=1.44`를 사용했다. 이 롤백 검증 보완 단계에서는 제품 코드를 변경하지 않았다. 이후 잠금 범위·좋아요 수정 결과는 아래에 별도로 기록한다.

### 잠금 범위·실패 경로·좋아요 보완

- 브랜드 범위 조회에서 다른 브랜드 상품의 잠금 충돌을 재현한 뒤, 대상 ID 조회·PK별 잠금과 인덱스 추가로 개선했다.
- 좋아요 중복 등록·취소의 500 응답을 재현한 뒤, INSERT의 특정 유니크 충돌 처리와 조건 DELETE로 기존 계약을 유지했다. JDBC 쓰기의 바깥 트랜잭션 롤백 및 UTC 기록도 반영했다.
- 혼합 요청의 두 처리 순서와 상품 삭제 경쟁의 현재 결과를 확인했다. 관찰 결과를 확인한 뒤 사용자가 정책을 확정했다.
- 최종 `:apps:commerce-api:check`: **175개, 실패 0·오류 0·skip 0**, Checkstyle·ArchUnit 통과. 커밋과 기존 로컬 DB 스키마 변경은 하지 않았다.

### 확정 정책 반영

잠금 실패를 503으로 기대한 HTTP 매핑 테스트 두 건이 기존 500 응답에서 실패하는 Red를 확인했다. 잠금 실패 예외 처리기를 추가한 뒤 실제 MySQL 대기 초과의 HTTP 503·롤백과 교착 대조군의 롤백을 확인했다. 별도 응답 테스트는 잠금 실패 503과 일반 저장 오류 500을 구분한다. 자동 재시도·실제 DB 대기 설정 변경은 없다.

좋아요 혼합 경쟁과 삭제 관계 비노출·본인 취소 허용도 합의된 정책으로 확정했다. 최종 `:apps:commerce-api:check`는 **178개, 실패 0·오류 0·skip 0**, Checkstyle·ArchUnit 통과다.

### 벌크 삭제 대안 비교

테스트 전용 비교 경로를 추가했으며 실제 삭제 구현·격리 수준은 유지했다. `:apps:commerce-api:check`에서 **187개, 실패 0·오류 0·skip 0**, Checkstyle·ArchUnit을 통과했다. 실험 결과는 2.2, 기존 방식 유지 결정은 ADR 0019에 기록했다.

### 벌크 분포·통계·실제 수정 경쟁 추가 검증

추가 8개 사례를 포함한 `:apps:commerce-api:check`에서 **195개, 실패 0·오류 0·skip 0**, Checkstyle·ArchUnit을 통과했다. 실제 상품 수정은 매 회 이름을 바꿔 UPDATE를 수행했다. 모든 worker 종료를 확인한 뒤 데이터를 정리한다.

### 삭제 트랜잭션 격리 수준 비교

`BrandBulkDeletionExperimentTest`의 분포 실험을 RR·RC로 확장했다. 브랜드 수 2/100·통계 갱신 전후 네 조건에서 다른 브랜드 기존 상품의 잠금 충돌은 ID별 RR·RC 각각 0/4, 벌크 RR 3/4, 벌크 RC 0/4였다. 실제 수정 서비스 완료 시점도 함께 확인했다. 서비스 기본값은 유지하고 테스트의 삭제 트랜잭션만 격리 수준을 지정했다. 세부 관찰과 한계는 ADR 0019에 기록했다.

전체 `:apps:commerce-api:check`: **203개, 실패 0·오류 0·skip 0**, Checkstyle·ArchUnit 통과. 이번에는 벌크·격리 수준 전환을 채택하지 않는다는 결론으로 문서의 미결정 표현도 정리했다. 제품 코드·서비스 DB 설정 변경과 커밋은 하지 않았다.

### 격리 수준 적용 범위 설명 정정

ADR 0019와 설계 2.2에서 전체 기본값 변경과 브랜드 삭제 트랜잭션만 RC로 시작하는 대안을 구분했다. REQUIRED 참여 시 바깥 격리 수준을 따른다는 조건과, 상품 삭제만 별도 커밋하지 않는다는 경계도 명시했다. RC 국소 적용이 불가능해서 기존 방식을 유지한 것은 아니다. 기존 RC 비교 결과와 미검증 범위를 유지했으며 이번 작업은 문서 정정이다. 코드·DB 설정은 변경하지 않았고 테스트를 새로 실행하지 않았다.
