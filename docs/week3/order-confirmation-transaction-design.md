# 주문 확정 — 트랜잭션 설계

대상은 `POST /api/v1/orders/{orderId}/confirm`의 최초 확정이다. 요청자 소유의 DRAFT 주문을 확정하고, 저장된 품목 수량만큼 재고를, 주문 총액만큼 포인트를 차감한다.

## 1. 트랜잭션 경계와 흐름

`OrderFacade.confirm()`을 유스케이스 트랜잭션 경계로 둔다. 주문 상태, 상품 재고, 포인트 잔액과 결제 결과를 같은 트랜잭션에서 변경한다.
브랜드·연결 상품 일괄 삭제와 실행 순서를 정하기 위해 주문 상품이 속한 활성 Brand를 공유 잠금으로 보호한다.
모두 성공하면 commit하고, 업무 조건을 만족하지 못하거나 처리 중 RuntimeException이 발생하면 Facade 밖으로 예외를 전달해 이번 시도의 변경을 전부 rollback한다.

```text
OrderV1Controller.confirm(): X-USER-ID 확인
  → OrderFacade 프록시: REQUIRED 트랜잭션 시작
    → UserValidator.validateExists(): 요청자 확인
    → OrderRepository.findById(): 주문 조회
    → 주문 소유자와 DRAFT 상태 검증
    → PointRepository.findByUserId(): Point 존재 확인
    → 주문 상품 조회로 각 Product의 Brand ID 확인
       없거나 삭제된 Product가 있으면 상품 사용 불가 업무 예외
    → 주문 상품의 Brand ID를 모아 오름차순으로 활성 Brand 공유 잠금 조회
       삭제된 Brand가 있으면 상품 사용 불가로 종료
    → OrderRepository.confirmIfDraft(): DRAFT 조건으로 CONFIRMED와 결제 결과 갱신
    → 저장된 OrderItem을 productId 오름차순으로 처리
       ProductRepository.decreaseActiveStock(): 판매 가능·재고 조건부 차감
    → PointRepository.decreaseBalanceIfEnough(): 주문 총액 조건부 차감
  ← 전체 성공이면 commit, 업무 예외 또는 처리·flush 실패면 rollback
← Controller 성공 응답 / ApiControllerAdvice 오류 응답
```

주문 상품의 Brand 공유 잠금은 브랜드 삭제와 확정의 순서를 정한다.
삭제가 배타 잠금을 먼저 얻으면 확정은 삭제 트랜잭션이 끝날 때까지 기다린다. 삭제가 commit되면 삭제된 Brand를 확인하고 `409`로 종료하며, rollback되면 활성 Brand를 확인하고 확정을 계속 판단한다.
확정이 공유 잠금을 먼저 얻으면 확정 처리가 끝난 뒤 삭제가 진행된다.
주문 상태 조건부 갱신은 해당 주문이 아직 DRAFT일 때만 성공하며,
상품이나 포인트 조건이 맞지 않으면 주문 상태와 결제 결과도 함께 DRAFT 상태로 rollback된다.
같은 주문을 동시에 확정하면 한 요청만 상태를 바꾸고, 나머지는 갱신 행 수 0을 확인해 상태 오류로 종료한다.

주문 소유자와 저장된 품목·총액은 주문 조회로 확인한다.
상품에서 관련 Brand ID를 얻은 뒤 Brand 공유 잠금을 ID 오름차순으로 획득하고, 실제 Product 갱신 SQL에서 현재 삭제 상태와 재고 수량을 다시 검사한다.
재고와 잔액의 조회값만 믿고 저장하지 않는다.
각 상품의 요청 수량은 주문 품목 기준으로 합산하고, 상품 갱신은 Product ID 오름차순으로 한다.

## 2. 동시성 보호 전략

| 대상 | 전략 | 보호하는 규칙 |
|---|---|---|
| Brand | 활성 Brand `PESSIMISTIC_READ` 공유 잠금 | 브랜드 삭제와 주문 확정의 순서를 정함 |
| Order | `id`, `user_id`, `status = DRAFT` 조건부 상태 갱신 | 같은 주문의 최초 확정은 한 번만 성공 |
| Product 재고 | `deleted_at IS NULL`, `stock >= :quantity` 조건부 차감 | 삭제된 상품과 재고 부족 차단 |
| Point 잔액 | `user_id`, `balance >= :amount` 조건부 차감 | 잔액 부족과 동시 초과 차감 차단 |
| Point 충전 | `balance = balance + :amount` 원자적 증가와 잔액 상한 조건 | 주문 차감과 겹친 충전의 갱신 유실·표현 범위 초과 차단 |

조건부 UPDATE의 영향 행 수가 1이면 갱신 성공, 0이면 해당 업무 조건을 만족하지 못한 것으로 판정한다.
Order 상태가 이미 바뀌었거나, 상품이 없거나 삭제됐거나 재고가 부족하거나, Point 잔액이 부족하면 Facade가 기존 API 계약에 맞는 업무 예외를 던진다.

Brand 공유 잠금은 브랜드 삭제의 배타 잠금과 충돌해, 두 유스케이스 중 먼저 잠금을 얻은 요청이 끝난 뒤 다음 요청이 최신 Brand 상태를 확인하게 한다.
InnoDB는 UPDATE 대상 행의 쓰기도 잠금으로 조정한다.
주문 확정은 Brand ID 오름차순 공유 잠금 → Order 조건부 상태 갱신 → Product ID 오름차순 재고 갱신 → Point 잔액 갱신 순서로 처리한다.
충전은 Point 행만 갱신한다.

포인트 충전과 주문 차감은 같은 Point 행을 바꾸므로 모두 원자적 갱신을 사용한다.
충전은 양수 입력을 검증한 뒤 잔액 상한을 넘지 않는 조건으로 증가시키고, 주문 확정은 주문 당시 총액 이상 잔액이 있을 때만 차감한다.
Point 잔액을 읽고 계산한 오래된 엔티티를 저장하는 경로를 함께 두지 않는다.

조건부·bulk UPDATE는 영속성 컨텍스트의 엔티티 상태를 자동으로 동기화하지 않는다.
필요한 변경은 bulk UPDATE 전에 flush하고, 실행 후 영속성 컨텍스트를 clear한다. 갱신된 값이 필요하면 clear 후 재조회한다.
이전에 조회한 엔티티를 다시 저장하지 않는다. 같은 관리 엔티티를 단순 재조회하는 것만으로 값이 갱신됐다고 보지 않는다.
commit 또는 rollback 결과의 검증은 트랜잭션 종료 후 새 경계에서 수행한다.

## 3. 실패 처리와 재시도

주문 상태·상품 재고·포인트 잔액의 조건을 만족하지 못한 결과는 업무 거절이며 자동 재시도하지 않는다. 갱신 행 수 0 자체가 트랜잭션을 rollback하지는 않는다.
Facade가 `CoreException` 등 RuntimeException을 던지고 프록시 밖으로 전달해, 같은 트랜잭션에서 이미 실행한 변경까지 rollback한다.
예외를 잡아 정상 반환하거나 실패한 트랜잭션 안에서 처리를 계속하지 않는다.
조건부 갱신에는 Order·Point의 `@Version` 충돌 재시도나 별도 RetryCoordinator를 두지 않는다.

| 결과 | 처리 |
|---|---|
| 식별값 누락 | 기존 `400`, 변경 없음 |
| User/Order/Point 없음 또는 타인 주문 | 기존 `404`, 변경 없음 |
| Order가 DRAFT 아님 또는 DRAFT 조건부 갱신 0행 | 기존 상태 오류 `409`, 전체 rollback |
| 상품 또는 Brand가 없거나 삭제됨, 재고 조건부 차감 0행 | 기존 업무 오류 `409`, 전체 rollback |
| Point 잔액 조건부 차감 0행 | 기존 잔액 부족 `409`, 전체 rollback |
| 교착, 잠금 시간 초과, 그 밖의 저장 또는 commit 전 flush 오류 | 전체 rollback 후 기존 기술 오류 처리; 자동 재시도하지 않음 |
| commit 자체의 오류 | 기술 오류 처리; commit 응답을 확인하지 못한 경우 확정 여부가 불명확할 수 있으므로 rollback 완료로 단정하지 않음; 자동 재시도하지 않음 |

DB는 충돌하는 같은 행의 쓰기를 잠금 대기 후 직렬화할 수 있다. 이 DB 잠금 대기는 애플리케이션 재시도나 별도 backoff와 다르다.
이 설계는 잠금 시간 초과나 교착을 잔액 부족·재고 부족으로 바꾸지 않는다.

## 4. 검증 기준

- 본인 소유의 DRAFT만 확정된다. 같은 주문의 동시 확정은 한 요청만 상태 조건부 갱신에 성공하고, 나머지는 추가 차감 없이 `409`를 받는다.
- 재고 차감은 상품별 총수량으로 검사한다. 상품이 없거나 삭제됐거나 Brand가 삭제됐거나 재고가 부족하면 주문·재고·포인트·결제 결과가 변경 전 상태로 남는다.
- 한 사용자 잔액 10,000원에서 서로 다른 4,000원 주문 3개를 동시에 확정하면 성공 2건, 잔액 부족 1건, 최종 잔액 2,000원을 기대한다. 각 주문은 서로 다른 상품을 사용하고 재고는 충분히 준비한다. 거절된 주문의 재고와 결제 결과가 유지되는지 확인한다.
- 재고 5개에 서로 다른 주문 8개가 각 1개를 요청하면 성공 5건, 재고 부족 3건, 최종 재고 0개를 기대한다.
- 잔액 10,000원에서 2,000원 충전과 7,000원 주문 확정을 동시에 실행하면 두 요청 모두 성공하고 최종 잔액 5,000원을 기대한다. Point 충전은 원자적 증가, 주문 확정은 조건부 차감으로 같은 행의 갱신을 보존한다.
- 중간 실패는 실제 변경 SQL이 실행된 뒤 유발한다. 일부 품목 갱신 뒤 실패와 Order·Product·Point를 모두 갱신한 뒤 commit 전 실패를 각각 확인한다. 트랜잭션 종료 후 새 DB 경계에서 모든 변경이 rollback됐는지 확인한다. 다른 요청의 commit은 보존한다.
- 요청별 성공·업무 거절·기술 오류를 구분해 수집한다. 모든 worker 종료 후 다음 불변식을 DB의 최종 상태로 확인한다.
  - 재고: 초기 재고 − 성공 주문 품목 수량 합 = 최종 재고
  - 포인트: 초기 잔액 + 성공 충전액 합 − 성공 결제액 합 = 최종 잔액
  - 주문: 성공한 주문은 CONFIRMED와 결제 결과를 가지며, rollback된 주문은 DRAFT와 확정 전 결제 정보를 유지

여러 Brand 공유 잠금과 Product UPDATE는 각각 ID 오름차순으로 처리한다.
JPA의 자동 flush 시점과 실제 SQL 순서는 저장 호출 순서와 같다고 가정하지 않고 DB 통합 테스트에서 확인한다.
