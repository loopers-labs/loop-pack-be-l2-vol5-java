# 주문 확정 — 트랜잭션과 동시성 보호

대상은 `POST /api/v1/orders/{orderId}/confirm`의 최초 확정이다. 요청자와 주문 상태를 확인하고, 상품 재고와 포인트 잔액, 확정 결과를 함께 반영한다.

Order와 Point는 `@Version`을 사용하는 낙관적 잠금으로 갱신 충돌을 감지하고, Product의 재고 차감은 조건부 갱신으로 처리한다.

## 1. 트랜잭션 범위

| 구분 | 설계 |
|---|---|
| 경계 | `OrderFacade.confirm()` 한 번의 실행을 한 DB 트랜잭션으로 처리 |
| 검증 | User 존재 여부, 요청자와 Order 소유자의 일치, DRAFT 상태, 상품 사용 가능 여부와 상품별 총수량, 포인트 잔액 |
| 함께 변경 | 상품 재고 차감, 포인트 차감, Order의 CONFIRMED 상태, 결제액과 결제 결과 |
| 보존 | 실패한 주문의 DRAFT와 변경 전 재고 및 잔액, 주문 소유자와 저장된 품목 및 총액, 다른 요청의 commit |
| 성공 | 본인 소유의 DRAFT 주문을 확정하고 전체 변경을 commit한 뒤 `200 OK` 반환 |
| 실패 | 해당 시도의 변경 전체 rollback. 다른 요청의 commit은 보존 |

Order의 소유자와 상태 검사부터 확정 저장까지 주문 확정 전체와 같은 트랜잭션에서 수행한다.

## 2. 호출 경로와 처리 순서

```text
고객 요청 → OrderV1Controller.confirm(): X-USER-ID 확인
  → OrderRetryCoordinator.confirm(): 트랜잭션 밖
    → 주입된 OrderFacade 프록시: 트랜잭션 시작
      → OrderFacade.confirm()
        1. UserValidator.validateExists(): User 존재 여부 확인
        2. OrderRepository.findById(): Order 조회 후 요청자 ID와 userId 비교
        3. Order.validateDraft(): DRAFT 상태 검사
        4. 저장된 품목의 합산 수량 검증
           → productId 오름차순으로 ProductRepository 조건부 차감
           → 각 상품의 영향 행 수 확인
        5. Point 조회와 버전 확보 → 잔액 검사 → 포인트 차감과 저장
        6. Order.confirm() → 확정 상태와 결제 결과 저장
    ← Facade 프록시: flush 후 commit, 실패 시 rollback 후 예외 전파
  ← Coordinator: 성공 반환 또는 버전 충돌 재시도
← Controller 성공 응답 / ApiControllerAdvice 최종 오류 응답
```

`OrderFacade`는 Order와 Point의 조회 및 행동 호출, ProductRepository의 조건부 재고 차감을 조율한다. Product의 재고 규칙은 조건부 차감 계약에 반영하고, Point는 잔액 검사와 차감, Order는 DRAFT 검사와 확정을 담당한다.<br>이 변경들은 같은 트랜잭션에서 처리하며, 하나라도 실패하면 해당 시도의 변경 전체를 rollback한다.

모든 품목의 재고 차감은 주문 확정 전체가 commit될 때 함께 반영된다.

Repository 호출은 **구현체 → Spring Data JPA Repository 프록시 → DB**로 이어진다.<br>조회와 변경은 같은 DB와 트랜잭션 관리자를 사용한다. Order와 Point의 변경은 같은 영속성 컨텍스트에서 매퍼로 처음 조회한 JPA 엔티티에 반영하고, Product의 차감은 같은 트랜잭션에서 직접 UPDATE로 실행한다.

전파는 `REQUIRED`, 격리 설정은 `DEFAULT`다. **Coordinator 진입 시 활성 트랜잭션이 없어야 하며**, 별도 Spring bean인 Facade 프록시를 시도마다 외부 호출한다.<br>바깥 트랜잭션에 참여하거나 자기 호출로 경계를 우회하면 시도별 종료와 재시도가 깨질 수 있다.

## 3. 예외 처리와 재시도

재시도 단위는 **`OrderFacade.confirm()` 전체**다. Order 또는 Point의 버전 충돌이 발생하면 해당 시도의 모든 변경을 rollback한다. OrderRetryCoordinator는 그 트랜잭션이 종료된 뒤 조회, 검증, 재고와 포인트 차감, 주문 확정을 처음부터 다시 실행한다.

| 결과 | 처리 |
|---|---|
| 요청자 식별값 없음 | 기존 `400`, DB 변경 없음 |
| User나 Order가 없거나 타인 소유의 주문 | 기존 `404`, 재시도 없음 |
| Order가 DRAFT가 아님 | 기존 상태 오류 `409`, 재시도 없음 |
| 포인트 잔액 부족 | 기존 업무 오류 `409`, 해당 시도 전체 rollback, 재시도 없음 |
| 재고 조건부 차감의 영향 행 수가 0 | 상품 사용 불가 또는 재고 부족을 나타내는 업무 오류 `409`, 해당 시도 전체 rollback, 재시도 없음 |
| Order 또는 Point 버전 충돌, 남은 시도 횟수 있음 | 해당 시도 전체를 rollback하고 종료한 뒤 새 트랜잭션에서 주문 확정 전체 재실행 |
| 최대 시도 횟수까지 모두 버전 충돌 | `CoreException(CONFLICT)` → `409`, 충돌 지속을 나타내는 메시지로 응답 |
| 저장, flush, commit 과정의 기술 오류 | 해당 시도 전체 rollback, `500`, 버전 충돌 재시도에 포함하지 않음 |

RuntimeException, Error는 Facade 밖으로 전파한다. OrderRetryCoordinator는 **Facade 프록시 호출 전체**를 감싸 flush와 commit 과정의 버전 충돌까지 처리한다. 업무 오류, 교착, 잠금 시간 초과를 버전 충돌로 분류하지 않는다.

재시도는 **전체 rollback 후 트랜잭션 종료 → 새 트랜잭션과 영속성 컨텍스트 시작 → 요청자, 주문 소유자와 상태 재검증 → 상품 전체의 조건부 차감과 포인트 차감, 주문 확정 재실행 → commit** 순서다.<br>요청자 ID, 주문 ID와 저장된 품목 수량은 유지하며 Order와 Point를 새로 조회하고 실패한 객체나 버전을 재사용하지 않는다.<br>재조회에서 이미 CONFIRMED면 기존 상태 오류 `409`로 종료한다. 조건부 차감에서 상품이 없거나 삭제됐거나 재고가 부족하면 업무 오류 `409`로 종료한다. Point 재조회 후 잔액이 부족해도 업무 오류 `409`로 종료하고 해당 시도 전체를 rollback한다. `open-in-view: false`를 유지한다.

### 재시도 횟수와 대기 정책

`maxAttempts`는 **한 요청의 최초 시도와 추가 재시도를 합친 최대 실행 횟수**다. 주문 확정의 Order와 Point 버전 충돌은 같은 시도 횟수에 누적하고, 매 시도마다 주문 확정 전체를 실행한다.

주문 확정은 **`maxAttempts = 2`**로 처리한다. 최초 실행 1회와 추가 재시도 최대 1회를 합친 값이며, 두 시도 모두 버전 충돌이면 `409 Conflict`로 종료한다. 추가 대기 시간은 **`0ms`**로 두며, 실패한 트랜잭션의 종료와 자원 반환이 끝난 뒤 즉시 새 트랜잭션에서 주문 확정 전체를 재실행한다.

**선택 이유:** Order의 경쟁은 같은 주문의 중복 확정 요청, Point의 경쟁은 같은 사용자의 주문 확정과 충전으로 한정되며 충돌이 드물다고 가정한다. 최신 상태에서도 가능한 요청에 추가 실행 기회를 1회 제공하고, 전체 확정을 반복하는 DB 작업량을 제한한다. 재시도 전 별도 대기를 생략해 추가 응답 지연을 줄인다.

주문 확정은 외부 시스템 호출 없이 같은 DB의 재고, 포인트와 주문 상태를 변경한다. 실패한 시도의 변경을 모두 rollback하고 새 트랜잭션에서 전체 명령을 다시 실행한다. 업무 오류와 기술 오류의 재시도 여부는 앞의 예외 처리 규칙을 따른다.

추가 대기는 같은 행에서 충돌한 요청들의 재시도 시점을 분산하기 위한 선택 사항이다. DB 잠금 대기는 SQL 실행 시 발생하며, 추가 대기 시간과 별개로 처리한다.

`maxAttempts = 2`와 추가 대기 시간 `0ms`는 보수적인 초기 정책이다. 아직 성능을 측정하지 않았으므로 모든 충돌의 해소나 최적의 설정을 보장하지 않는다. 충돌 빈도, 추가 재시도에서도 충돌한 비율, 재시도로 성공한 요청의 비율, 응답 시간과 DB 작업량을 측정해 조정한다.

## 4. 동시성 보호

같은 사용자의 중복 클릭이나 응답 지연 후 재요청이 겹치면, 두 요청 모두 본인 소유의 DRAFT 주문으로 판단할 수 있다. 소유자 확인과 DRAFT 검사부터 확정 저장까지 같은 트랜잭션에서 수행하고, Order의 버전 검사로 오래된 상태의 저장을 거절한다.

**선택 이유:** Order가 `validateDraft()`와 `confirm()`으로 상태 전이를 책임지고, Repository가 조회한 JPA 엔티티에 변경을 반영하는 저장 흐름에 맞춰 `@Version`을 선택한다. 같은 Order의 상태나 결제 정보가 조회 이후 바뀌었는지도 함께 감지한다.

DRAFT 조건부 갱신도 최초 확정 보호에 사용할 수 있다. 이를 전용 JPQL bulk UPDATE로 처리하면 영향 행 수 판단과 관리 중인 엔티티의 상태 동기화가 필요하다.<br>버전 검사와 병행한다면 검사와 증가도 직접 맞춰야 한다. 이 설계에서는 엔티티 저장을 통한 버전 검사를 사용한다.

**전제:** Order의 경쟁은 같은 주문의 중복 확정 요청으로 한정된다. 이 충돌이 드물다는 전제에서 낙관적 잠금을 선택하며, 충돌은 저장, flush 또는 commit에서 감지될 수 있다. 충돌 빈도는 아직 측정하지 않았다.

| 대상 행 | 전략과 이유 |
|---|---|
| User | fixture 사용자의 존재 여부를 확인한다. 사용자 수정과 삭제를 제공하지 않고 주문 소유자도 변경하지 않으므로 별도 잠금을 두지 않음 |
| Order | `@Version`. 같은 주문을 동시에 확정할 때 오래된 상태의 저장을 거절하고 최초 확정을 한 번만 반영 |
| Product 재고 차감 | 삭제 여부와 재고 조건을 포함한 UPDATE. DB의 현재 재고를 기준으로 검사와 차감을 함께 실행 |
| Product 관리 변경 | 미삭제 조건을 포함한 UPDATE. 상품 수정은 이름과 가격, 재고 설정은 입력한 최종 수량, 삭제는 삭제 상태만 갱신하며 각 변경의 수정 시각도 기록 |
| Point | `@Version`. 같은 사용자의 서로 다른 주문 확정과 충전이 겹칠 때 오래된 잔액 저장을 거절. 차감과 충전 모두 같은 버전 검사에 참여 |

Order의 버전 검사는 같은 주문의 중복 확정을 보호한다. 서로 다른 Order가 같은 Product나 Point를 변경하는 경쟁은 Order 버전만으로 보호되지 않으므로 각각의 보호 전략이 필요하다.

세 대상의 변경은 하나의 DB 트랜잭션에서 처리한다. Order와 Point는 조회한 상태로 계산한 변경을 버전 검사로 보호하고, Product는 SQL에서 현재 재고를 검사하고 직접 차감한다. InnoDB는 각 UPDATE에 필요한 배타 잠금을 획득하며, 갱신한 행의 잠금은 트랜잭션 종료까지 유지한다. 하나라도 실패하면 해당 시도의 변경 전체를 rollback한다.

`@Version`은 Infrastructure의 `OrderJpaEntity`에 둔다. 같은 Order를 갱신하는 경로는 모두 버전 검사와 증가에 참여하며, 버전 증가는 JPA 구현체가 관리한다.<br>처음 조회한 JPA 엔티티의 버전으로 갱신을 검사한다. 버전 조건을 설명하는 SQL은 다음과 같다.

```sql
UPDATE orders
SET status = 'CONFIRMED',
    payment_amount = :paymentAmount,
    payment_result = :paymentResult,
    version = version + 1
WHERE id = :orderId AND version = :readVersion;
```

### 상품과 재고

**검증과 차감:** 저장된 OrderItem의 `productId`와 합산된 총수량을 사용하고, 차감 수량이 양수인지 먼저 검증한다. 주문 생성은 재고를 예약하지 않으므로, 확정 시 DB의 현재 상품 상태와 재고로 차감 가능 여부를 판단한다.

StockQuantity는 Product 내부에서 재고 수량과 차감 계산 규칙을 표현한다. 실제 재고는 Product 행의 `stock` 컬럼에 저장되므로 동시성 보호 대상은 그 행이다. 주문 확정은 ProductRepository의 조건부 차감 계약을 사용하고, Infrastructure가 다음 SQL로 상품 사용 가능 여부와 재고 검사를 차감과 함께 실행한다.

```sql
UPDATE products
SET stock = stock - :quantity,
    updated_at = :updatedAt
WHERE id = :productId
  AND deleted_at IS NULL
  AND stock >= :quantity;
```

영향 행 수가 1이면 차감 성공이다. 0이면 대상이 없거나 삭제됐거나 재고가 부족한 것으로, 상품 사용 불가 또는 재고 부족을 나타내는 `409`로 거절한다. 0만으로 재고 부족을 단정하지 않는다. 한 상품의 차감 실패도 해당 시도에서 앞서 차감한 다른 상품과 포인트, Order의 변경을 모두 rollback한다.

**선택 이유:** 재고 차감은 양수 수량과 현재 재고의 비교로 표현할 수 있다. DB가 현재 값에서 수량을 빼므로 갱신 유실을 막으며, 재고가 충분한 주문끼리는 오래된 조회 버전 때문에 전체 확정을 재시도하지 않아도 된다. 상품의 삭제 여부도 같은 UPDATE 조건으로 검사한다.

**관리 작업과의 협력:** Product의 변경은 기능별 컬럼만 조건부 갱신한다. 상품 수정은 이름과 가격, 관리자 재고 설정은 입력한 최종 수량, 단독 삭제와 브랜드 일괄 삭제는 삭제 상태를 기록하며 각 변경의 수정 시각도 갱신한다. 모두 `deleted_at IS NULL` 조건을 포함하고, 조회했던 Product 전체를 다시 저장하지 않는다. 상품 수정과 삭제는 주문이 차감한 재고를 보존한다.

관리자 재고 설정은 최종 수량을 지정하는 명령이다. 차감이 먼저 commit되면 뒤의 설정이 입력한 수량을 적용하고, 설정이 먼저 commit되면 뒤의 차감이 설정된 재고에서 수량을 뺀다. 상품 수정도 같은 이름과 가격을 동시에 바꾸면 마지막으로 반영된 요청의 값이 남는다. Product의 조회 버전 검사와 버전 충돌 재시도는 사용하지 않는다.

**영속성 컨텍스트:** 조건부 UPDATE는 Product 객체의 재고와 수정 시각을 자동으로 갱신하지 않는다. 주문 차감 경로는 Product를 변경해 다시 저장하지 않고 조건부 UPDATE 결과로 판정한다. 이미 관리 중인 Product가 필요하면 변경 SQL을 보낸 뒤 해당 엔티티를 refresh한다. Order와 Point의 최초 조회 버전 및 미반영 변경을 유지하도록 영속성 컨텍스트 전체를 clear하지 않는다.

**비용:** UPDATE의 배타 잠금 대기는 남으며, 여러 행을 변경하면 교착도 고려한다. 갱신 컬럼과 엔티티 상태 동기화를 명시적으로 관리해야 한다.

### 포인트

**보호 대상:** `userId`로 식별되는 Point 행의 잔액이다. 같은 사용자의 서로 다른 주문 확정과 포인트 충전은 같은 행을 변경한다.

**검증과 차감:** 차감액은 Order에 저장된 총액을 사용한다. Point는 잔액 변경을 책임지고, PointBalance는 양수 금액, 잔액 부족과 계산 결과를 검증한다.

**선택 이유:** Point의 경쟁은 같은 사용자의 서로 다른 주문 확정과 충전으로 한정된다. 이 충돌이 드물다는 전제이며, PointBalance가 금액을 검증하고 계산한 값을 엔티티에 반영하는 흐름에 맞춰 `@Version`을 사용한다. 같은 주문의 중복 확정은 Order 상태와 버전으로 보호하고, 서로 다른 주문 확정과 충전의 잔액 경쟁은 Point 버전으로 보호한다. 충돌 빈도는 아직 측정하지 않았다.

**공통 보호 규칙:** `@Version`은 Infrastructure의 `PointJpaEntity`에 둔다. 주문 확정의 차감과 기존 충전은 모두 버전 검사에 참여한다. 각 요청은 자신의 트랜잭션과 영속성 컨텍스트에서 처음 조회한 Point JPA 엔티티에 변경을 반영한다. 버전 검사와 증가는 JPA가 관리하며, 처음 읽은 잔액으로 계산한 오래된 저장을 거절한다. 버전 조건을 설명하는 SQL은 다음과 같다.

```sql
UPDATE points
SET balance = :newBalance,
    version = version + 1
WHERE id = :pointId AND version = :readVersion;
```

**비용:** 버전 검사에서도 UPDATE의 배타 잠금 대기는 남으므로, 버전 충돌과 잠금 대기 및 교착을 구분한다.

### 업무 처리 순서와 동시성 보호 순서

Application은 어떤 대상을 어떤 순서로 조회하고 변경할지 조율한다. Repository의 SQL이 DB 잠금을 요청하고 DB가 실제 잠금을 관리한다. JVM의 애플리케이션 락으로 전체 주문을 직렬화하지 않는다.

Product는 조건부 UPDATE로 재고를 차감한다. InnoDB는 UPDATE 시 배타 잠금을 획득하고 트랜잭션 종료까지 유지한다. 여러 Product는 `productId` 오름차순으로 처리한다.

```text
트랜잭션 시작
→ Order 조회와 버전 확보 → 소유자와 DRAFT 검사
→ 저장된 품목의 합산 수량 검증
→ productId 오름차순으로 Product 조건부 차감 SQL 실행
  → 영향 행 수 확인: 1이면 차감 성공, 0이면 전체 rollback
  → 다음 Product 처리
→ Point 조회와 버전 확보 → 잔액 검사 → 포인트 차감과 저장
→ Order 확정과 결제 결과 저장
→ 자동 flush와 commit: Order와 Point 갱신 시 버전 검사, 실패하면 해당 시도 전체 rollback
```

상품별 조건부 UPDATE를 실행하고 영향 행 수를 확인한 뒤 다음 상품으로 진행한다. 이 단계에서는 Point와 Order의 변경을 아직 JPA 엔티티에 반영하지 않아 Product UPDATE를 ID 오름차순으로 실행한다. 각 UPDATE는 같은 트랜잭션에 참여하며 주문 확정 전체가 끝날 때 함께 commit한다. 실제 SQL 실행 순서는 DB 통합 검증에서 확인한다.

Point와 Order의 JPA 변경은 기본 자동 flush를 사용하며, commit 전이나 필요한 조회 전에 SQL이 실행될 수 있다. 저장 호출 순서와 UPDATE 순서가 같다고 가정하지 않는다. 두 엔티티 사이의 SQL 순서를 강제하기 위한 중간 flush는 추가하지 않는다. 실패 테스트에서 JPA 변경 SQL의 실행을 보장해야 할 때는 명시적으로 flush한다.

다른 변경 경로도 여러 Product를 갱신하면 ID 오름차순을 공통 기준으로 삼는다. 충전은 Point 행만 갱신하며, 주문 확정의 차감과 같은 버전 검사에 참여한다. 실제 SQL 실행과 잠금 순서는 DB 통합 검증에서 확인한다.

### 최초 확정과 멱등성

같은 `orderId`의 확정 요청을 반복해도 주문 상태, 재고와 포인트에 최초 확정의 변경만 남기는 것을 목표로 한다. 이를 위해 다음 규칙을 함께 적용한다.

- **상태 전이:** DRAFT 주문만 확정한다. 재조회에서 CONFIRMED라면 추가 차감 없이 기존 상태 오류 `409`로 종료한다.
- **버전 검사:** 같은 DRAFT를 읽은 요청들의 오래된 저장을 거절한다. 같은 Order를 갱신하는 모든 경로가 버전 검사에 참여한다.
- **트랜잭션:** Order의 버전 충돌을 포함해 하나라도 실패하면 해당 시도의 재고와 포인트 차감, 주문 상태와 결제 결과를 모두 rollback한다.
- **재검증:** 유스케이스 재시도에서도 소유자와 DRAFT 상태를 다시 확인한다. 이미 확정된 주문에는 차감과 확정을 다시 적용하지 않는다.

낙관적 잠금은 오래된 저장을 감지하는 수단이다. 최신 버전으로 같은 변경을 반복 적용할 수 있으므로, 멱등성을 보장하려면 위 상태 전이 규칙과 트랜잭션도 필요하다.

멱등성의 기준은 반복 요청이 추가 업무 변경을 만들지 않는 것이다. 최초 성공은 `200`, 이미 확정된 주문의 재요청은 `409`로 응답하며 저장된 성공 응답을 재사용하지 않는다. 응답이 달라도 서버에 반영되는 효과가 같으면 멱등적일 수 있다.

## 5. 핵심 검증 조건

- **식별과 소유자:** 식별값 누락은 `400`, 없는 User나 Order, 타인 소유의 주문은 `404`이며 DB 변경을 남기지 않는다.
- **최초 확정:** 본인 소유의 DRAFT 주문만 확정한다. 같은 주문을 동시에 확정해도 성공은 1건이며 재고와 포인트는 한 번만 차감한다. 이미 CONFIRMED인 주문의 재요청은 상태 오류 `409`이며 주문, 재고와 포인트에 추가 변경을 남기지 않는다.
- **상품과 총수량:** 중복 상품 수량 2와 3은 총수량 5로 검사하고 차감한다. 재고 5라면 성공 후 0이며, 재고 4라면 업무 오류 `409`로 전체 변경을 취소한다. 삭제 전에 생성됐거나 삭제와 겹쳐 생성된 DRAFT도 확정 시 상품 상태를 다시 검사해 삭제된 상품이 포함되면 거절한다.
- **재고 경쟁:** 관리자 재고 설정을 제외하고, 충분한 포인트를 가진 서로 다른 사용자의 주문이 같은 Product를 구매할 때 `초기 재고 - 성공한 주문의 해당 상품 수량 합 = 최종 재고`가 성립한다. 상품 사용 불가, 재고 부족, 버전 충돌 한도 초과와 기술 오류는 따로 집계한다.
- **포인트 경쟁:** 같은 사용자의 서로 다른 주문 확정과 충전이 겹쳐도 `초기 잔액 + 성공한 충전액 합 - 성공한 주문의 차감액 합 = 최종 잔액`이 성립한다. 거절된 주문은 DRAFT를 유지하고 해당 시도의 재고와 포인트 차감, 확정 결과를 남기지 않는다. 제한된 재시도는 잔액이 충분한 모든 요청의 성공을 보장하지 않으며, 잔액 부족과 최대 실행 횟수까지 지속된 버전 충돌을 구분한다. 모든 요청 종료 후 새 DB 조회로 확인한다.
- **중간 실패:** 앞 상품의 실제 UPDATE 이후 다음 상품의 재고 부족, 저장 실패나 이후 포인트 부족이 발생하면 모든 차감과 확정 결과를 취소한다. 저장 실패는 테스트 구성에서 주입하고, 서비스 트랜잭션 종료 후 새 DB 조회로 확인한다.
- **충돌과 재시도:** Order 또는 Point 버전 충돌로 해당 시도 전체가 rollback되고 다른 요청의 commit은 유지된다. 실패한 트랜잭션 종료 후 별도 대기 없이 새 트랜잭션에서 1회 재시도하고, Order와 Point를 다시 조회하며 모든 상품의 조건부 차감을 다시 실행한다. 재조회에서 CONFIRMED거나 조건부 차감이 실패하거나 잔액이 부족하면 업무 오류 `409`, 최초 실행과 추가 재시도 모두 버전 충돌이면 충돌 오류 `409`다.
- **충전과의 경쟁:** 초기 잔액 10,000원을 조회한 뒤 다른 요청의 충전 5,000원이 commit되어 주문 확정에서 Point 버전 충돌이 발생하면, 해당 확정 시도 전체를 rollback하고 충전의 commit은 보존한다. 새 시도에서 잔액 15,000원을 다시 읽고 4,000원 주문 확정에 성공하면 최종 잔액은 11,000원이다.
- **다른 변경 경로와 SQL 순서:** 상품 수정과 삭제는 차감된 재고를 보존한다. 관리자 재고 설정과 주문 차감은 DB의 쓰기 순서에 따라 최종 수량 설정 또는 현재 재고 차감을 적용한다. 브랜드 일괄 삭제가 먼저 commit하면 차감은 거절되고 주문 확정 전체가 rollback되며, 차감이 먼저 commit하면 일괄 삭제는 변경된 재고를 보존한다. 요청 품목 순서가 달라도 Product UPDATE는 ID 오름차순으로 실행된다.
- **객체 상태:** 조건부 차감 후 오래된 Product를 다시 저장하거나 같은 수량을 이중 차감하지 않는다. Order의 최초 조회 버전이 유지되어 같은 주문의 중복 확정을 거절한다.
