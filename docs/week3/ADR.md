# 3주차 동시성 설계 ADR

## ADR-001. Product와 Stock의 잠금 범위를 분리한다

- **상태**: 결정 (2026-10-08)
- **범위**: 주문 생성·확정·포인트 충전·좋아요 등록·관리자 상품/재고 변경·브랜드 삭제가 동시에 실행되는 경우
- **갱신**: 2026-10-09, 상품 생성의 브랜드 공유락 추가 (`7017661`), 주문 생성의 상품 공유락·충전 재시도 제거 반영, 브랜드 수정은 기존 비관적 배타락 유지

Product와 Stock을 분리해 잠금 범위를 나눴다. 주문끼리는 Product를 공유락으로 함께 읽으면서 수정·삭제를 막고, 재고 차감은 Stock 배타락으로 직렬화한다. 이를 통해 인기 상품의 재고 경합을 Stock에 집중시킨다.



## API·작업별 적용 목록과 선택 근거

### 잠금 순서와 재시도 경계

- 주문 생성은 중복 상품 ID를 제거한 뒤 ID 오름차순으로 Product를 공유락 조회하고, 주문 품목은 기존 요청 순서와 중복 품목 합산 계약을 유지한다. 주문 확정은 Product ID 오름차순으로 Product를 조회한 뒤 같은 순서로 Stock을 잠근다. 관리자 재고 변경도 Product → Stock 순서를 따른다.
- 브랜드 삭제는 Brand를 먼저 잠그고 연결 Product를 ID 오름차순으로 잠근다. 상품 생성도 Brand를 먼저 잠근다.
- 비관적 잠금은 해당 트랜잭션 종료까지 유지한다. 외부 API 호출 등 긴 작업을 잠금 구간에 추가하지 않는다.
- HTTP 호출처럼 기존 트랜잭션이 없는 경로에서는 주문 확정의 낙관적 충돌 시 `REQUIRES_NEW` 트랜잭션으로 처음부터 최대 2회 다시 실행한다. 충전은 재시도 횟수를 0으로 지정해 트랜잭션을 한 번만 실행하고 충돌 예외를 전달한다. 이미 트랜잭션이 있는 호출은 그 트랜잭션에 참여하며 내부 재시도하지 않는다.
- 브랜드 수정은 Spring 프록시를 거치는 `@Transactional` 메서드에서 Brand 배타락을 획득하고 트랜잭션 종료까지 유지한다. 재시도 실행기는 사용하지 않는다.

### 재시도 한도 초과의 응답 구분

- Spring의 `ObjectOptimisticLockingFailureException`에 포함된 엔티티 이름, JPA `OptimisticLockException`의 엔티티 또는 내부 Hibernate `StaleObjectStateException`의 엔티티 이름을 원인 체인에서 확인해 Point 충돌을 `409 POINT_CONFLICT`로 구분한다. 실제 flush 충돌에서는 JPA 엔티티가 비어 있고 Hibernate 원인에 이름이 들어 있는 경로도 확인했다. 재시도 횟수는 기존처럼 최대 2회이며 포인트 충전 정책은 변경하지 않는다.
- Point로 확인되지 않은 충돌은 실패 트랜잭션 종료 후 새 트랜잭션으로 본인 주문을 재조회한다. 실제 `CONFIRMED`일 때만 `ORDER_ALREADY_CONFIRMED`로 안내한다. 외부 트랜잭션에 참여 중이면 실패한 트랜잭션에서 재조회하지 않는다.
- 아직 DRAFT이거나 충돌 대상을 확인할 수 없으면 원래 예외를 전달한다. 기존 `500 INTERNAL_ERROR`로 처리하며, 잔액 부족·품절·이미 확정된 주문이라고 추측하지 않는다.
- `OrderConfirmationConflictHttpTest`는 실제 DB의 별도 트랜잭션에서 Point 버전을 매 시도마다 변경해 한도 초과를 유발한다. 추가로 JPA 엔티티 포함 충돌, DRAFT 주문 충돌, 대상 없는 충돌을 저장 경계에서 주입해 HTTP 오류와 전체 rollback을 검증한다. 별도 트랜잭션의 포인트 증가만 남고 실패한 주문의 차감·확정은 남지 않아야 한다.
