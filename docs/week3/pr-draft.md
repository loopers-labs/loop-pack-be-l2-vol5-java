## 📌 Summary

- 브랜드와 연결된 미삭제 상품을 하나의 트랜잭션에서 일괄 논리 삭제한다. 고객 사용 대상에서 제외하되 다른 대상과 과거 주문·결제 결과는 보존한다.
- 최초 주문 확정의 재고·포인트 차감과 확정 결과를 함께 반영하고, 실제 SQL 실행 뒤 실패해도 전체가 롤백되는지 검증한다. 이미 확정된 본인 주문의 재요청은 `409 ORDER_ALREADY_CONFIRMED`로 거절한다.
- READ_COMMITTED와 비관적 행 잠금을 사용한다. 필요한 행을 주문 → 사용자 → 브랜드 ID 오름차순 → 상품 ID 오름차순으로 잠그며 충전·관리자 재고 변경도 같은 행 보호 규칙을 따른다.
- 갱신 유실 대조군과 실제 서비스의 동시성 검증을 분리했다. 결과 집계뿐 아니라 주문별 상태·재고·결제액·잔액의 정합성과 무관한 데이터 보존을 확인한다.

### 트랜잭션·락 적용 방식

트랜잭션으로 **함께 성공하거나 취소되어야 할 변경**을 묶고, 비관적 행 잠금으로 **같은 데이터를 바꾸는 요청의 처리 순서**를 제어했다. `READ_COMMITTED`만으로 조회 후 변경의 갱신 유실을 막을 수는 없으므로, 변경 판단에 사용할 행을 먼저 잠근다.

| 처리 경로 | 하나의 트랜잭션에 묶은 변경 | 명시적 잠금 대상·순서 |
| --- | --- | --- |
| 브랜드 삭제 | 브랜드와 연결된 미삭제 상품의 논리 삭제 | 브랜드 → 대상 상품 ID 오름차순 |
| 주문 확정 | 재고 차감·포인트 차감·주문 상태·결제액·확정 시각 저장 | 주문 → 사용자 → 브랜드 ID 오름차순 → 상품 ID 오름차순 |
| 포인트 충전 | 사용자 잔액 증가 | 사용자. 주문 확정의 포인트 차감과 같은 행을 잠근다. |
| 관리자 재고 변경 | 상품 재고를 요청한 수량으로 설정 | 브랜드 → 상품. 주문 확정과 같은 상품 행을 보호한다. |
| 상품 등록 | 삭제되지 않은 브랜드에 상품 생성 | 브랜드. 브랜드 삭제와 등록이 동시에 진행되지 않도록 한다. |

- **트랜잭션 경계:** Spring이 관리하는 application 서비스에 `@Transactional(isolation = READ_COMMITTED)`를 적용했다. 기본 전파는 `REQUIRED`이며, 일반 HTTP 호출에서는 서비스 프록시가 트랜잭션을 시작한다. 재고·포인트를 `REQUIRES_NEW`로 분리하지 않고, 런타임 예외를 삼키지 않아 함께 롤백되도록 했다. 충전·주문 생성·주문 확정은 각각 별도 요청이므로, 확정 실패가 이전에 성공한 충전까지 취소하지는 않는다.
- **잠금 후 판단:** `PESSIMISTIC_WRITE`와 실제 `SELECT … FOR UPDATE`로 필요한 행을 잠그고, 잠금을 얻은 상태에서 삭제 여부·주문 상태·잔액·재고를 검사한다. 브랜드 잠금이 상품까지 자동으로 잠그는 것은 아니므로 상품 행도 명시적으로 잠근다. 공통 순서로 교착 위험을 줄이지만 완전히 없앴다는 뜻은 아니며, 같은 브랜드의 다른 상품 요청도 브랜드 잠금에서 대기할 수 있다.
- **일괄 삭제:** 상품별 잠금을 확보한 뒤 `flush` → 상품 일괄 `UPDATE` → 이미 로딩된 대상 상품 `refresh`로 DB와 메모리 상태를 맞춘다. 상품 UPDATE는 한 번이지만 잠금 SELECT 등 전체 SQL이 한 번인 것은 아니다. 중간 `flush`도 커밋은 아니므로 이후 실패하면 함께 롤백된다.
- **잠금 실패:** DB 행 잠금 대기 제한은 3초이며 전체 요청 시간 제한은 아니다. 교착·잠금 대기 초과에 따른 잠금 실패는 `409 CONCURRENT_MODIFICATION`으로 응답하고 서버에서 자동 재시도하지 않는다.

### 원자성·동시성 검증

- **롤백:** 실제 DB 변경 SQL이 실행된 뒤 저장 실패를 주입하고, 요청 종료 후 별도 DB 조회로 재고·포인트·주문 및 브랜드·상품 변경이 원복되었는지 확인했다. 테스트 자체의 자동 롤백으로 성공한 것처럼 보이지 않도록 구분했다.
- **경쟁:** 실제 Spring 서비스 프록시를 여러 작업 스레드에서 호출해 요청별 트랜잭션이 경쟁하도록 했다. 성공·업무 거절·기술 오류를 나누고, 모든 작업 종료 후 최종 DB 상태와 성공 주문별 차감 결과를 대조했다. 시작 신호를 맞춘 것이 모든 실행 순서를 강제로 재현했다는 뜻은 아니다.
- **대조군:** 별도 연결의 두 트랜잭션이 같은 재고를 읽은 뒤 진행하도록 장벽을 두어 갱신 유실을 재현했다. 실제 서비스의 잠금 검증과 분리해, 잘못된 결과를 제품의 기대 동작으로 사용하지 않았다.

| 검증 | 핵심 결과 |
| --- | --- |
| 재고 5에 주문 8개 | 확정 5·재고 부족 3·기술 오류 0·최종 재고 0 |
| 잔액 10,000에 4,000원 주문 3개 | 확정 2·잔액 부족 1·기술 오류 0·잔액 2,000, 거절 주문의 재고 유지 |
| 충전 2,000과 결제 7,000 | 두 요청 성공·기술 오류 0, 10,000+2,000−7,000=잔액 5,000 |
| 갱신 유실 대조군 | 두 트랜잭션이 재고 5를 읽고 상수 4를 저장해 커밋 2·재고 4 재현. 잘못된 결과의 재현을 확인하는 테스트이며 제품 동작이 아님 |

## 💬 Review Points

1. 브랜드 일괄 변경과 주문 확정의 트랜잭션 경계가 적절한지, 실제 SQL 뒤 실패와 별도 DB 재조회가 부분 반영을 충분히 검출하는지 확인 부탁드립니다.
2. 브랜드 삭제·상품 등록·주문 확정·충전·관리자 재고 변경이 공유 행과 잠금 순서를 일관되게 보호하는지 확인 부탁드립니다. 상품 일괄 UPDATE는 1회지만 대상별 잠금 SELECT 비용은 남습니다.
3. 대조군의 읽기 후 장벽과 실제 서비스의 시작 신호를 구분한 방식, 성공·업무 거절·기술 오류 집계 및 DB 보존식의 검증 범위를 확인 부탁드립니다. 모든 실행 순서나 장애를 강제로 재현했다는 의미는 아닙니다.
