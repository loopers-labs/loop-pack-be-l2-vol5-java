# 공유 자원의 문제 및 해결 방법

시스템을 복잡하게 만든 주 원인은 자원을 공유하는 것에서 비롯됐다.
앞으로 내 모든 욕은 공유 자원 같은 사람이라고 대체하겠다.
하지만 그 덕분에 훌륭한 시스템 설계부터 개발자로서 살아 있음을 느낀다.

## 스프링 프록시

스프링 프록시는 객체 레벨의 프록시로, 어떤 객체(Bean)를 감싸서 그 객체의 메서드 호출 전후에 추가 로직을 끼워 넣는 기법이다.
주로 **AOP(관점 지향 프로그래밍)**를 구현하는 데 사용된다.

```
클라이언트 → 프록시 객체 → 실제 객체(Target)
```

단, 프록시는 외부에서 호출되는 메서드에만 개입한다.
클래스 내부에서 자체 메서드를 직접 호출하는 경우엔 프록시를 거치지 않는다.
`@Transactional`이 붙은 메서드를 같은 클래스 안에서 내부 호출하면 트랜잭션이 걸리지 않는 이유가 여기에 있다.

## 동시성

아래는 실제 과제에서 겪은 문제들이다.

### 문제: 같은 재고를 동시에 차감하면?

재고가 1개인 상품에 두 명이 거의 동시에 주문을 확정하면 어떻게 될까.
두 트랜잭션이 각자 `SELECT`로 재고 1을 읽고, 각자 1을 빼서 0을 `UPDATE`하면 재고가 -1이 되어야 할 상황인데도 둘 다 성공한다.

이걸 **갱신 유실(lost update)** 이라고 한다. 한 트랜잭션의 쓰기가 다른 트랜잭션의 쓰기에 덮어씌워지는 현상이다.

### 해결: SELECT FOR UPDATE (비관적 락)

JPA에서는 `@Lock(LockModeType.PESSIMISTIC_WRITE)`를 붙이면 `SELECT ... FOR UPDATE` 쿼리가 나간다. 첫 번째 트랜잭션이 행을 읽는 순간 잠금을 걸어버리기 때문에, 두 번째 트랜잭션은 첫 번째가 끝날 때까지 대기한다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from ProductModel p where p.id = :id and p.deletedAt is null")
Optional<ProductModel> findByIdAndDeletedAtIsNullWithLock(@Param("id") Long id);
```

"비관적"이라는 이름은 충돌이 자주 일어날 거라고 가정하고 미리 막는다는 뜻이다.

반대로 **낙관적 락**은 "충돌이 자주 안 일어날 거다"라고 가정하고, DB 잠금 없이 진행하되 커밋 직전에 "내가 읽은 이후로 값이 바뀌었는지"만 확인하는 방식이다.
낙관적인 게 최근에 치이카와 보고 왔는데 우사기 같은 녀석이다.

주문 확정처럼 충돌이 빈번한 경로에서는 낙관적 락의 재시도 로직이 복잡해지므로 비관적 락을 선택했다.

### 데드락 방지: 잠금 순서 통일

여러 상품이 담긴 주문을 확정할 때, 트랜잭션 A가 상품 1→2 순서로 잠금을 얻고 트랜잭션 B가 상품 2→1 순서로 얻으면 서로 상대방의 잠금이 풀리기를 기다리다 영원히 대기하는 데드락이 발생한다.

해결법은 단순하다. **모든 트랜잭션이 같은 순서(상품 id 오름차순)로 잠금을 획득**하면 순환 대기가 생기지 않는다.

```java
order.getItems().stream()
    .sorted(Comparator.comparingLong(OrderItemModel::getProductId))
    .forEach(item -> productService.deductStock(item.getProductId(), item.getQuantity()));
```

## 트랜잭션 롤백: 중간에 실패하면 전부 되돌린다

주문 확정 흐름은 ① 재고 차감 → ② 포인트 차감 → ③ 주문 상태 변경 순서로 진행된다. ②에서 포인트가 부족하거나 예외가 발생하면 ①에서 이미 줄어든 재고도 원래대로 돌아와야 한다.

Spring의 `@Transactional`이 이걸 자동으로 처리한다. 예외가 전파되면 트랜잭션 전체를 롤백한다.

내부에서 호출하는 메서드도 `@Transactional`이 붙어 있으면 기본 전파 방식(`REQUIRED`)에 따라 **기존 트랜잭션에 합류**한다. 별도의 트랜잭션이 만들어지는 게 아니다.

## 영속성 컨텍스트, flush와 commit

JPA는 조회한 엔티티를 **영속성 컨텍스트**에서 관리하고, 변경 감지(dirty checking)로 SQL을 자동으로 생성한다. 이때 세 가지 개념을 구분해야 한다.

- **객체 변경**: 메모리 안의 엔티티가 바뀐다. DB엔 아직 아무것도 안 간다.
- **flush**: 변경 SQL을 DB에 보낸다. **commit은 아니다.** 트랜잭션이 아직 열려 있다.
- **commit**: 트랜잭션 결과를 확정한다. 이 시점에 flush가 자동으로 먼저 일어날 수 있다.
- **clear**: 영속성 컨텍스트가 관리하던 엔티티를 분리한다. DB rollback과는 무관하다.

같은 엔티티를 다시 읽어서 값이 바뀌어 보인다고 해서 DB에 commit까지 된 것은 아니다. 롤백 테스트에서는 앞의 변경 SQL이 실제 전송되도록 flush한 뒤 예외를 일으키고, **트랜잭션 종료 후 새 트랜잭션에서 재조회**해 롤백 여부를 확인한다.

`@Transactional(readOnly = true)`는 읽기 의도와 최적화를 위한 힌트이지, 모든 상황에서 쓰기를 금지하는 보안 장치가 아니다. 삭제처럼 상태를 바꾸는 유스케이스에는 쓰기 트랜잭션 경계를 사용한다.

또한 여러 행을 한 번에 바꾸는 JPQL bulk UPDATE는 엔티티별 변경 감지 경로와 다르다. 이미 영속성 컨텍스트에 올라와 있는 객체와 DB 상태가 어긋날 수 있으므로, bulk 변경 전에 필요한 변경을 flush하고 변경 후에는 해당 객체를 재조회하거나 컨텍스트를 정리하는 방법을 판단해야 한다.

## 테스트: 실제 DB로 검증한다

롤백과 동시성은 단위 테스트로 검증하기 어렵다. 실제 트랜잭션이 커밋·롤백되는 걸 봐야 한다. 그래서 `@SpringBootTest`로 전체 컨텍스트를 띄우고 TestContainers로 실제 MySQL을 사용했다.

**롤백 테스트**에서는 `@SpyBean`으로 실제 빈을 감싸 특정 메서드 호출에서만 예외를 던지게 했다. 재고 차감 이후 단계인 포인트 조회에서 강제로 예외를 발생시키고, 재고가 원래 값으로 돌아왔는지 DB를 직접 조회해 확인한다.

**동시성 테스트**에서는 `CountDownLatch`와 `ExecutorService`로 여러 스레드를 동시에 출발시켰다. 재고 5에 8개 주문을 동시에 보내면 5개만 성공하고 나머지 3개는 재고 부족으로 거절되어야 하며, 기술적 오류(예외)는 0이어야 한다.
