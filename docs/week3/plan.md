## 1. 세 흐름 — 같이 성공·실패할 것과 보존할 것

| 흐름 | 같은 트랜잭션으로 묶을 것 | 보존할 것 |
|---|---|---|
| 브랜드 일괄 삭제 `DELETE /api-admin/v1/brands/{brandId}` | 브랜드 `deleted_at` + 그 브랜드의 미삭제 상품 전체 `deleted_at` (재고 0 포함) | 다른 브랜드·상품, 주문·품목(이름·단가·수량·총액·결제액) |
| 최초 주문 확정 `POST /api/v1/orders/{orderId}/confirm` | 재고 차감, 포인트 그룹 남은 금액 차감 + 사용 이력, 주문 CONFIRMED·결제액·결제수단·확정 시각 | 실패 시 DRAFT와 변경 전 재고·잔액·이력 |
| 같은 재고·잔액의 동시 변경 | 읽기·검사·변경을 보호하는 행과 SQL (2장) | 성공한 업무 = 최종 재고·잔액 |

### 1-1. 호출 경로와 트랜잭션 경계 (프록시를 거치는 곳) — v0.4 구현 기준

```
BrandAdminController ──▶ BrandCommandUseCase.delete  (프록시: BrandCommandService, @Transactional REQUIRED)
                           ├─ BrandPort.findActiveByIdForUpdate            🔒 brands
                           ├─ brand.delete() → BrandPort.save (saveAndFlush) UPDATE 전송
                           ├─ ProductPort.findActiveByBrandIdForUpdate     🔒 products (id 오름차순)
                           └─ product.delete() → ProductPort.save ×N        UPDATE 전송 ×N

OrderController ──▶ OrderCommandUseCase.confirm  (프록시: OrderCommandService, @Transactional REQUIRED)
                      ├─ OrderPort.findByIdForUpdate → 소유·DRAFT 확인               🔒 orders
                      ├─ ProductPort.findAllByIdsForUpdate → OrderConfirmPolicy      🔒 products (id 오름차순)
                      ├─ PointGroupPort.findRemainingByUserIdForUpdate → checkPayable 🔒 point_groups (만료 시각·id)
                      ├─ product.decreaseStock ×N → ProductPort.save ×N              UPDATE 전송
                      ├─ pointWalletPolicy.pay → PointGroupPort.save ×N, PointHistoryPort.saveAll
                      └─ order.confirm → OrderPort.save (saveAndFlush)

같은 행 잠금에 참여하는 다른 경로: 관리자 상품 수정·재고 설정·삭제(🔒 products), 브랜드 수정(🔒 brands),
상품 등록(🔒 brands → INSERT products), 포인트 만료 배치(🔒 point_groups, 묶음마다 TransactionTemplate)
```

- 경계는 둘 다 **UseCase 공개 메서드 하나**다 (W2 ADR-11). 자기 호출로 경계를 놓치는 곳은 없다 — 확인 방법: 각 Controller가 인터페이스(프록시)를 주입받고, 서비스 안에서 다른 `@Transactional` 메서드를 `this.`로 부르지 않는다.
- 저장 어댑터의 `save`는 `saveAndFlush`라 **SQL이 즉시 나가지만 commit은 아니다.** 확정도 재고·그룹을 변경 감지에 맡기지 않고 포트로 저장해, "SQL이 실제로 나간 뒤 실패"(T-5)가 성립한다.
- 잠금 조회는 트랜잭션의 **첫 읽기**다. 같은 엔티티를 잠그기 전에 읽어 두면 영속성 컨텍스트의 옛 상태가 잠금 조회 결과로 재사용될 수 있어서다.

## 2. 지금 코드에서 깨지는 경쟁 — 그리고 정할 것

### 2-1. 경쟁 시나리오 (W2 코드 기준으로 찾은 것과 리뷰에서 찾은 것)

| ID | 동시에 오는 요청 | 지금 일어나는 일 | 깨지는 불변식 |
|---|---|---|---|
| R-1 | 같은 상품을 사는 서로 다른 주문의 확정 | 둘 다 재고 5를 읽고 4를 쓴다 (Lost Update) | 초기 재고 − 성공 수량 합 = 최종 재고 |
| R-2 | 같은 사용자의 서로 다른 주문 확정 | 둘 다 같은 그룹의 남은 금액을 읽고 각자 차감해 쓴다. 이력은 두 줄 다 남는다 | 잔액 식, "그룹 이력 합 = 남은 금액" (W2 4-1) |
| R-3 | **같은 주문**을 두 번 확정 | 둘 다 DRAFT를 보고 둘 다 결제한다 | 결제는 한 번 |
| R-4 | 관리자 상품 수정·재고 설정·삭제 vs 확정 | Hibernate가 **모든 컬럼을 UPDATE**하므로 나중에 commit한 쪽이 상대가 바꾼 재고·가격·`deleted_at`을 옛값으로 덮는다 | 재고 식, 삭제 상태 |
| R-5 | 브랜드 일괄 삭제 vs 그 브랜드 상품의 확정 | 확정이 읽은 상품(`deleted_at = null`)을 전체 컬럼 UPDATE로 써서 **삭제를 되살린다** | 브랜드 삭제 = 연결 상품 전부 비노출 |
| R-6 | 포인트 만료 배치 vs 확정 | 같은 그룹을 둘 다 바꿔 한쪽이 덮어써진다 (W2 ADR-09) | 잔액 식 |
| R-8 | 잠금 대기 초과·교착 (모든 잠금 경로) | `ApiControllerAdvice`에 처리기가 없어 **500**. 리뷰에서 추가 발견: 교착(1213)은 Hibernate 6.6이 잠금 조회 중 `jakarta.persistence.OptimisticLockException`으로 감싸 올려 타입 처리기로는 못 잡는다 | 기술 오류를 정해진 계약(ADR-W3-04)으로 알리기 |
| R-9 | bulk UPDATE와 JPA가 같은 행을 다룰 때 | DB 행 잠금은 서로 기다리지만(실습 실험 7), bulk UPDATE는 ① 이미 불러온 엔티티(영속성 컨텍스트)를 바꾸지 않아 뒤의 변경 감지가 옛 행 전체를 다시 쓸 수 있고 ② `@Version`을 올리지 않아 낙관적 잠금을 우회하며 ③ `@PreUpdate`(수정 시각)를 거치지 않는다 | 삭제 상태, 수정 시각 |
| R-10 | 브랜드 수정 vs 브랜드 일괄 삭제 (리뷰 발견) | 수정이 잠금 없이 읽은 브랜드를 전체 컬럼 UPDATE로 써서 **삭제를 되살린다** — 상품은 삭제된 채 | 브랜드 삭제 = 연결 상품 전부 비노출 |
| R-11 | 상품 등록 vs 브랜드 일괄 삭제 (리뷰 발견) | 등록이 브랜드를 살아 있다고 본 뒤, 삭제가 끝나면 INSERT가 진행되어 **삭제된 브랜드에 살아 있는 상품**이 생긴다 (갭 잠금은 늦출 뿐 막지 못함) | 같음 |
| R-12 | 좋아요 등록 vs 브랜드 일괄 삭제 | 좋아요는 상품을 잠그지 않고 읽은 뒤 관계 행만 INSERT한다. 겹치면 삭제된 상품에 좋아요 행이 하나 남을 수 있다 | 상품 행은 바꾸지 않음 — **허용**: 내 좋아요 목록이 삭제 상품을 거르므로 사용자에게 보이지 않는다 |
| R-7 | 충전 vs 결제 | 충전은 새 그룹을 **INSERT**만 해서 기존 행과 경쟁하지 않는다. 다만 충전 상한 검사(PNT-03)는 동시 충전 둘이 함께 통과할 수 있다 | 상한(표현 범위) — 실제 위험은 낮다 |

> 대응: R-1·R-4는 상품 행 잠금(ADR-W3-01), R-2·R-3·R-6은 주문·그룹 행 잠금(ADR-W3-02), R-5·R-10·R-11은 브랜드·상품 행 잠금(ADR-W3-05), R-8은 ADR-W3-04, R-9는 bulk UPDATE를 쓰지 않아 해당 없음(ADR-W3-05).
>
> R-4·R-5는 "재고만 잠그면 된다"는 직관의 반례다. **같은 상품 행을 바꾸는 모든 경로**(확정 차감, 관리자 수정·재고 설정·삭제, 브랜드 일괄 삭제)가 같은 규칙에 참여해야 한다 (C-5). R-10·R-11은 같은 원리가 **브랜드 행**에도 적용된다는 것을 처음 설계에서 놓친 예다 (5장 #1·#2).

### 2-2. 결정할 것

| ID | 질문 | 선택지 | 상태 |
|---|---|---|---|
| D-1 | **상품(재고) 행**을 어떻게 보호하나 | (a) 비관적 잠금 `SELECT … FOR UPDATE` (b) 낙관적 잠금 `@Version` + 한정 재시도 (c) 조건부 UPDATE `stock = stock - ? WHERE stock >= ?` | ✅ (a) — ADR-W3-01 |
| D-2 | **포인트 지갑**(한 사용자의 그룹 여러 행)을 무엇으로 보호하나 | (a) 사용자의 남은 그룹 행 전부 `FOR UPDATE` (b) 지갑 하나를 대표하는 행(예: `users` 행)을 잠금 (c) 그룹마다 `@Version` | ✅ (a) — ADR-W3-02 |
| D-3 | **주문 행**(R-3) | 확정 시작에서 주문을 `FOR UPDATE`로 읽고 DRAFT 확인 / `@Version` | 🔧 `FOR UPDATE` — ADR-W3-02 |
| D-4 | 잠금 **획득 순서** (교착 방지) | 주문 → 상품(id 오름차순) → 포인트 그룹(만료 시각·id 순), 브랜드 → 상품. 다른 경로도 이 순서의 부분집합만 쓴다 | 🔧 — ADR-W3-03 |
| D-8 | 잠금 대기 초과를 어떻게 응답하나 | 재고·잔액 부족(업무 거절)과 다른 `errorCode`로 `409` | ✅ — ADR-W3-04 |
| D-5 | 브랜드 일괄 삭제를 무엇으로 하나 | (a) 브랜드 잠금 후 상품을 잠금 조회해 엔티티마다 `delete()` (b) 브랜드 잠금 후 bulk `UPDATE products SET deleted_at … WHERE brand_id = ? AND deleted_at IS NULL`. 어느 쪽이든 **논리 삭제(soft delete)·같은 트랜잭션 동기 처리** — 주문 품목·좋아요가 `product_id`를 참조하고, 과제도 참조가 있으면 논리 삭제를 먼저 검토하라고 한다. 비동기·배치 분리는 C-1·C-2와 충돌해 이번 범위에서 제외 | ✅ (a) — ADR-W3-05 |
| D-6 | BRD-02 계약 변경 — "상품이 남으면 409" → "함께 삭제" | 과제 지정. 기존 E2E `rejectsDelete_whenActiveProductRemains`는 새 계약으로 바꾼다 (규칙 완화가 아니라 계약 변경) | ✅ 과제 지정 |
| D-7 | 만료 배치(R-6)와 충전(R-7)이 D-2 규칙에 어떻게 참여하나 | 만료 배치는 대상 그룹을 `FOR UPDATE`로 읽는다. 충전은 새 행 INSERT라 결제와 같은 행을 바꾸지 않는다 | 🔧 — ADR-W3-02 |

| T-9 | 우회 경로 (R-4·R-5) | ① 확정 vs 관리자 이름 변경(가격 그대로) ② 확정 vs 브랜드 일괄 삭제 | ① 순서와 관계없이 둘 다 성공 · 재고 4 · 새 이름 ② 상품은 반드시 삭제, 확정이 먼저면 재고 4·CONFIRMED / 삭제가 먼저면 409·재고 5·DRAFT |
| T-10 | 같은 주문 중복 확정 (R-3) | 같은 orderId를 3번 동시에 | 확정 1 · 이미 확정 409 2 · 기술 오류 0 · 재고·잔액·사용 이력 한 번만 |
| T-11 | 브랜드 수정 vs 일괄 삭제 (R-10) | 동시에 | 브랜드는 반드시 삭제된 채, 수정이 먼저면 새 이름 / 삭제가 먼저면 수정 404 |
| T-12 | 상품 등록 vs 일괄 삭제 (R-11) | 동시에 | 삭제된 브랜드에 살아 있는 상품 없음. 등록이 먼저면 함께 삭제 / 삭제가 먼저면 등록 404 |
| T-13 | 확정 vs 만료 배치 (R-6) | 잔액 10,000, 7,000원 확정과 유효기간 뒤 기준 시각의 배치 | 확정이 먼저면 사용 7,000·만료 3,000 / 배치가 먼저면 잔액 부족 409·만료 10,000. 어느 쪽이든 그룹 이력 합 = 남은 금액 0 |
| T-14 | 잠금 대기 초과 (R-8) | 테스트 트랜잭션이 상품 행을 잠근 채 둔다 | 확정·관리자 재고 설정 409 `Concurrency Conflict` · 변경 없음 · 풀린 뒤 재시도 성공 |
| T-15 | 실제 교착 (R-8) | 테스트 트랜잭션이 B → A, 확정이 A → B로 잠근다 (테스트 쪽을 무겁게 해 확정이 희생되게) | 409 `Concurrency Conflict` · 변경 없음 |
| T-16 | 잠금 SQL (C-5) | Hibernate `StatementInspector`로 보낸 SQL 기록 | 확정 `orders → products → point_groups`, 관리자 3경로 `products`, 브랜드 삭제 `brands → products`, 브랜드 수정·상품 등록 `brands`, 만료 배치 `point_groups` |

> 결과가 실행 순서에 따라 갈리는 T-9②·T-11·T-12·T-13은 **직렬 실행 결과 중 하나와 같은지**를 본다. 잠금이 빠졌을 때 이 테스트들이 실패하는 것은 순서에 따라 확률적이므로, 우회 경로의 결정적 증거는 T-16이다. 잠금 적용 전 코드에서 T-6은 성공 8, T-7은 성공 3, T-9는 재고 4·삭제 되살아남으로 실패했다.

**공통 규칙 (C-7)** — 초기 데이터는 worker 시작 전에 commit. 각 worker는 독립 트랜잭션으로 실제 Spring bean 호출. 시작 latch와 완료 future에 제한 시간. 요청별 결과를 성공·업무 거절(409 재고·잔액)·기술 오류로 수집해 `성공 + 업무 거절 + 기술 오류 = 전체`를 확인. 모든 worker 종료 후 새 조회로 DB 확인. `finally`에서 executor 종료. 테스트 메서드를 트랜잭션으로 감싸지 않는다. `Thread.sleep`·운영 코드의 테스트용 장벽 금지.

## 4. ADR

### ADR-W3-01. 재고는 비관적 잠금, 분산 락은 부하 측정 후 앞단에 더한다 ✅

- **가정** — 한정 수량 상품(오픈 시각에 몰림)과 일반 상품(고르게 분산)이 함께 있다. 충돌해서 마지막 재고를 놓치면 아고다처럼 사용자를 안내한다.
- **선택** — 상품 행을 바꾸는 **모든 경로**(주문 확정 차감, 관리자 수정·재고 설정·삭제, 브랜드 일괄 삭제)가 같은 트랜잭션 안에서 `SELECT … FOR UPDATE`로 행을 잠근 뒤 읽고 판단하고 바꾼다.
- **이유** — ① 정합성의 기준은 DB 행이다. 잠금이 행에 걸리므로 경로를 하나 빠뜨려도 SQL이 기다리게 만든다 (C-5, R-4·R-5). 분산 락은 "락을 잡자"는 약속이라 모든 경로가 지켜야 한다. ② 잠금 해제가 commit과 함께 일어난다. 분산 락은 트랜잭션 밖에서 잡고 commit 뒤에 풀어야 하며, lease가 먼저 끝나면 두 요청이 동시에 들어간다. ③ 여러 상품은 id 오름차순 한 문장으로 잠그고, 순서가 어긋나도 InnoDB가 교착을 감지해 한쪽을 끝낸다. ④ 서버 하나·DB 하나 구조다 (W2 ADR-09).
- **비용** — 기다리는 요청이 DB 커넥션을 붙잡는다(pool 40). 한정 수량 상품 오픈 때 다른 상품 조회까지 느려질 수 있다. REPEATABLE READ의 잠금 읽기는 **스캔한 행을 모두** 잠근다 — 조건이 인덱스에 없으면(만료 배치의 `remaining > 0`) 이미 0원이 된 그룹까지, 실행 계획이 전체 스캔이면 테이블 전체를 잠근다 (T-15를 만들며 실제로 겪음, 5장 #6). 데이터가 쌓이면 `EXPLAIN`과 `performance_schema.data_locks`로 잠금 범위를 확인하고, 필요하면 `(user_id, remaining, expires_at)` 같은 인덱스를 검토한다.
- **다음 단계** — k6 부하 테스트로 커넥션 대기를 측정하고, Redisson 분산 락을 **DB 잠금 앞에** 더한다(대체하지 않는다): 줄은 Redis에서 서고 최종 판단은 DB 잠금이 한다. 여러 상품은 키를 정렬해 `MultiLock`으로 한꺼번에 잡는다. 대형 오픈에서는 Redis 재고 카운터를 입구 필터로 쓰는 방법도 비교한다.

### ADR-W3-02. 포인트는 사용자의 남은 그룹 행을, 주문은 주문 행을 잠근다 ✅

- **가정** — 한 사용자는 한 번에 한 건씩 결제한다. 그래도 더블클릭·앱과 웹 동시 사용·네트워크 재시도로 같은 사용자의 확정이 겹칠 수 있다.
- **선택** — 확정은 주문 행을 먼저 `FOR UPDATE`로 읽어 DRAFT를 확인한다(R-3). 포인트는 그 사용자의 남은 그룹 행 전부를 `FOR UPDATE`로 읽고 결제한다(R-2). 만료 배치도 대상 그룹을 `FOR UPDATE`로 읽는다(R-6).
- **이유** — 가정상 같은 사용자의 경쟁이 드물어 잠금 대기 비용이 거의 0이고, 재고와 같은 방식이라 잠금 순서가 단순하다. 지갑을 대표하는 행으로 `users` 행을 잠그면 포인트 기능이 사용자 기능의 행을 잠가 경계가 흐려진다. 그룹 행이 0개인 사용자는 결제할 돈이 없어 어차피 거절되고, 충전은 새 행 INSERT라 결제가 잠근 행과 겹치지 않는다(R-7, T-8).
- **다시 열 조건** — 충전 상한(PNT-03)을 동시 충전까지 엄격히 지켜야 하거나 잔액 캐시 컬럼이 필요해지면, 포인트 기능이 소유하는 지갑 행(`point_wallets`, 사용자당 한 행)을 만들어 그 행을 잠근다.

### ADR-W3-03. 잠금 순서: 주문 → 상품(id 오름차순) → 포인트 그룹, 브랜드 → 상품 🔧

- 모든 경로가 이 순서의 부분집합만 쓴다. 관리자 상품 변경은 상품 하나, 브랜드 일괄 삭제는 브랜드 → 상품(id 오름차순), 브랜드 수정은 브랜드 하나, 상품 등록은 브랜드 → (새 상품 INSERT), 만료 배치는 포인트 그룹만 잠근다.
- 같은 사용자의 그룹은 결제와 만료 배치가 모두 (만료 시각, id) 순서로 잠근다 — 만료 배치를 id 순에서 이 순서로 바꿨다.
- 순서를 맞춰도 교착이 0이 된다고 단정하지 않는다. 생기면 InnoDB가 한쪽을 끝내고, 그 쪽은 ADR-W3-04 계약으로 응답한다 (T-15).

### ADR-W3-04. 잠금 대기 초과는 재고·잔액 부족과 다른 errorCode로 409 ✅

- 잠금은 **서버가 확정 요청을 처리하는 동안**(밀리초 단위)만 잡힌다. 사용자가 결제 화면에 머무는 시간과는 관계없다. 대기 초과는 "앞 요청의 트랜잭션이 정해진 시간 안에 끝나지 않았다"는 기술적 혼잡이다.
- 재고 부족(상대가 마지막 재고를 가져감) = 업무 거절 → 홈으로 안내. 대기 초과 = 혼잡 → 다시 시도 안내. 과제 요구대로 둘을 섞지 않는다. 상태 코드는 둘 다 `409`, `errorCode`로 구분한다.
- 대기 시간 🔧 3초. MySQL은 쿼리별 대기 시간 문법이 없고(`NOWAIT`만 있음) 세션 변수 `innodb_lock_wait_timeout`으로 정한다. 초과하면 `ERROR 1205`이며 기본 설정에서는 **그 문장만** 취소되므로 트랜잭션은 애플리케이션이 롤백해야 한다 (실습 `practice-locks.md` 실험 4). 적용: `application.yml`의 `datasource.mysql-jpa.main.connection-init-sql: "SET SESSION innodb_lock_wait_timeout = 3"` — Hikari가 커넥션을 만들 때마다 실행한다(Testcontainers 포함). 예외가 `@Transactional` 프록시 밖으로 나가므로 Spring이 트랜잭션 전체를 롤백한다.
- 응답 판별: 타입 처리기(`PessimisticLockingFailureException`, jakarta `PessimisticLockException`·`LockTimeoutException`)에 더해, 원인 사슬의 `SQLException` 오류 번호가 1205·1213이면 `CONCURRENCY_CONFLICT`. 교착은 경로에 따라 `OptimisticLockException`으로 감싸져 오기 때문이다 (5장 #3).

### ADR-W3-05. 브랜드 일괄 삭제: 잠금 조회 후 엔티티마다 논리 삭제, 같은 트랜잭션 ✅

- **선택** — `BrandCommandService.delete` 한 트랜잭션에서 ① 브랜드를 `FOR UPDATE`로 조회(없거나 삭제됐으면 404) ② `brand.delete()` 저장 ③ 그 브랜드의 미삭제 상품을 id 오름차순 `FOR UPDATE`로 조회 ④ 상품마다 `delete()` 저장. 저장은 `saveAndFlush`라 단계마다 UPDATE가 실제로 나간다.
- **이유** — (b) bulk UPDATE도 체크리스트를 통과하지만 R-9(영속성 컨텍스트·`@PreUpdate` 우회)를 막는 규칙이 더 필요하다. (a)는 도메인 메서드와 수정 시각을 그대로 쓰고, 과제 예시("P1까지 처리한 뒤 P2 저장에서 실패")를 테스트로 그대로 재현한다. 브랜드 하나의 상품 수가 적어 UPDATE 횟수 비용이 작다.
- **같은 행의 다른 경로** — 브랜드 수정은 브랜드를 잠금 조회한다(R-10). 상품 등록은 브랜드를 잠근 채 존재를 확인한다(R-11). 좋아요 등록은 상품 행을 바꾸지 않아 잠그지 않는다(R-12 허용).
- **다시 열 조건** — 브랜드당 상품이 많아 트랜잭션이 길어지면 (b) bulk UPDATE, 더 커지면 읽기 쪽에서 브랜드 상태를 함께 거르는 비동기 정리를 검토한다.
