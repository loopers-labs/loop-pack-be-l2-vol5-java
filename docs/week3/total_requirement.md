# 3주차 전체 요구사항

## 1. 목표와 기준 자료

브랜드와 연결 상품의 변경을 하나의 성공·실패로 묶고, 동시에 실행되는 요청에서도 주문·재고·포인트의 결과가 일치하도록 한다.
2주차 API·도메인·저장 구조·테스트에서 이어가며, 업무 결과 하나를 요구사항 폴더 하나와 PR 하나로 관리한다.

기준 자료는 사용자가 제공한 3주차 원문과 문답으로 확정한 작업 범위다.

- **Learning**: 브랜드 일괄 변경, Spring·JPA 트랜잭션 경계, 동시성 제어와 검증의 학습 배경.
- **Implementation Quest**: 1. 변경 범위와 트랜잭션 설계 ~ 5. 실행·제출 및 Checklist의 구현·검증 조건.
- **Technical Writing Quest**: 원문에 있으나 사용자 합의로 이번 작업에서 제외.
- **2026-09-23 문답 및 승인 계획**: 요구사항별 문서·PR 진행, 접근 제어·기술 글 제외, 초기 준비 범위의 기준.
- 기존 [2주차 설계 안내](../week2/README.md), [API 계약](../week2/05-use-cases.md), [개발 컨벤션](../week2/conventions.md).

이 문서는 전체 목록·공통 기준·진행 상태를 관리한다. 상세 업무 규칙과 시나리오는 아래 개별 요구사항 문서를 기준으로 삼는다.
문서 작성은 기능 구현이나 검증 완료를 의미하지 않는다.

## 2. 포함·제외 범위와 기존 정책

### 포함

- 브랜드·연관 상품 일괄 삭제와 실제 DB 변경 후 실패에 대한 전체 롤백.
- 주문 확정 원자성, 주문 상태·재고·잔액의 경쟁 제어, 같은 행을 변경하는 기존 경로의 보호.
- 갱신 유실 대조군, 실제 MySQL 서비스 검증, 관련 회귀·HTTP 연결·Checkstyle·ArchUnit 검사.
- 각 요구사항의 트랜잭션 설계, 주요 대안 비교, 구현 계획, 실제 결과와 회고.

### 원문 대비 제외

| 구분 | 제외 내용 | 적용 방식 |
|---|---|---|
| 접근 제어 | 관리자 식별·접근 제한, 본인 주문 확인, 인증·인가 추가 및 관련 401·403 검증 | 2주차의 학습용 사용자 입력 정책 유지 |
| 기술 글 | Technical Writing Quest 및 실행·제출의 기술 글 산출물 | 별도 글·요구사항·PR을 만들지 않음. PR별 결과·회고는 작성 |
| 선택 확장 | 다른 잠금 전략의 추가 구현·비교 실험, 재고 요청 12개 실험, 브랜드 삭제와 상품 등록의 동시 실행 | 필수 범위 밖으로 기록하고 검증 완료로 주장하지 않음 |

주문 모델 재작성, 새 요청키·성공 응답 재사용 체계, JVM 전역 잠금, 외부 서비스·공개 배포는 추가하지 않는다.
전략 선택을 위한 문서상의 대안 비교는 수행하되, 모든 후보를 구현할 필요는 없다.

### 유지·변경하는 기존 정책

- `X-USER-ID`는 fixture 사용자 입력이다. 필요한 API의 입력 검증·사용자 존재 확인을 유지한다.
- 주문 확정은 기존처럼 `orderId`로 대상을 찾고 저장된 주문 사용자의 포인트를 사용한다. 요청자 헤더·본인 여부 검사를 추가하지 않는다.
- 관리자 API는 기존처럼 기능 경로로 구분하며 새로운 관리자 인증·식별을 요구하지 않는다.
- DRAFT 생성 시 차감하지 않으며, 확정 금액은 저장된 주문 합계를 사용한다. 기존 주문 정보·금액·결제 결과는 보존한다.
- 기존 논리 삭제 모델을 기준으로 요구사항을 작성한다. 저장 방식·처리 전략 변경이 필요하면 해당 PR에서 논의한다.
- 계층·Context 책임, 도메인 규칙, TDD, Checkstyle·ArchUnit과 검사 완화 금지 원칙을 유지한다.
- 2주차의 '동시성 제외'는 이번 R02에서 확장한다. '연관 상품이 있으면 브랜드 삭제 거절'은 R01에서 변경한다.
- 기존 week1·week2 문서는 보존한다. 3주차에 바뀌는 범위와 계약은 이 문서와 개별 요구사항에 기록한다.

## 4. 진행 순서·브랜치·상태

기준 브랜치는 초기 준비 시점의 `corinB`에서 만든 `volume-3/main`이다.
요구사항별 브랜치는 이름만 먼저 확정하며, 실제 생성은 해당 작업을 시작할 때 수행한다.

| 순서 | ID | 폴더 | 작업 브랜치 | PR 대상 | 상태 |
|---|---|---|---|---|---|
| 1 | R01 | `r01-brand-bulk-delete/` | `volume-3/r01-brand-bulk-delete` | `volume-3/main` | 구현·검증 완료([결과](r01-brand-bulk-delete/result.md)), 병합 완료 |
| 2 | R02 | `r02-order-consistency/` | `volume-3/r02-order-consistency` | `volume-3/main` | 구현·검증 완료([결과](r02-order-consistency/result.md)), check 247건 통과·검증 한계 기록, [PR #14](https://github.com/corinB/loop-pack-be-l2-vol5-java/pull/14) 제출·병합 대기 |

R02는 최신 `origin/volume-3/main`에서 독립적으로 분기해 문서 준비·트레이드오프 문답과 결정까지 선행할 수 있다.
R02 구현은 R01 리뷰·병합 후 최신 `volume-3/main`을 반영하고 관련 저장 경로와 삭제 후 확정 거절 계약을 확인한 뒤 시작한다.
작업 브랜치끼리 직접 병합하거나 미리 쌓지 않는다.
상태는 실제 진행에 맞춰 갱신한다. PR 생성 후 링크를 추가하고, 병합 사실을 확인한 뒤 병합 완료로 표시한다.

## 5. PR별 작업 절차와 문서 양식

초기 준비에서는 이 문서와 두 `requirement.md`만 작성한다. 나머지 문서는 해당 PR을 진행할 때 생성한다.

1. 요구사항의 현재 코드·정책·미정 사항을 사용자와 확인한다.
2. 주요 선택의 대안을 문답으로 비교하고 `trade_off/`의 전체 목록과 주제별 문서에 결정과 한계를 기록한다.
3. `plan.md`에 설계·구현·검증 순서를 작성하고 계획을 합의한다.
4. 작은 기능 단위로 TDD와 구현을 진행하고 관련 테스트·diff를 확인한다.
5. 실제 검증 결과와 계획 변경·남은 문제·회고를 `result.md`에 작성한다.
6. 해당 요구사항의 코드·테스트·문서를 하나의 PR로 리뷰하고 병합한다.

| 문서 | 작성 항목 |
|---|---|
| `requirement.md` | 목적 / 현재 동작과 변경점 / 포함·제외 범위 / 업무 규칙 / 시나리오와 기대 결과 / 완료 조건 / 미정 사항 |
| `trade_off/total_trade_off.md` | 주제 링크: 옵션 / 옵션. 채택은 굵게, 미채택은 취소선, 검토 전·검토 중·보류는 별도 표시 |
| `trade_off/번호-주제.md` | 판단할 문제 / 인용구 결정 요약 / Mermaid 비교 흐름 / 장단점 비교표 / 옵션별 판단 / 필요한 남은 사항 |
| `plan.md` | 변경 책임·구조 / 실제 호출·트랜잭션 경계 / 구현 순서 / 검증 계획 / 완료 체크리스트 |
| `result.md` | 구현 결과 / 실제 검증 결과 / 계획과의 차이 / 남은 문제 / 회고 |

- 시나리오는 **사전 상태 / 실행 / 기대 결과 / 유지되어야 할 상태**로 구분한다.
- 트레이드오프는 깊은 번호 중첩 없이 주제별 파일로 나눈다. 미확정 옵션에는 채택 표시나 취소선을 사용하지 않는다.
- 현재 R01의 결정과 남은 사항은 [트레이드오프 전체 목록](r01-brand-bulk-delete/trade_off/total_trade_off.md)에서 확인한다.
- R02의 확정된 선택은 [전체 목록](r02-order-consistency/trade_off/total_trade_off.md), 7개 커밋의 목표·TODO·완료 기준은 [구현 계획](r02-order-consistency/plan.md)을 따른다. 추가 주제를 시작할 때 [템플릿](r02-order-consistency/trade_off/_template.md)을 복사하고 실제 파일이 생긴 뒤 목록에 연결한다.
- Mermaid는 비교 흐름을 표현하며 구현 완료를 뜻하지 않는다. 템플릿의 예시는 설계 결정으로 간주하지 않는다.
- 잠금 전략·재시도 정책·구체적인 코드 변경은 초기 요구사항에서 확정하지 않는다.
- 설계 문서에는 Controller부터 repository·SQL까지의 실제 경로, 프록시 진입점, 예외 전달, 전파와 잠금 순서를 표시한다.
- AI 제안의 자기 호출·예외 삼키기·독립 commit·빠진 보호 대상에 대한 반례를 검토하고 실제 코드·검증 결과와 대조한다.
- 구현 중 합의한 변경은 관련 명세·선택·계획에 반영하고, 결과 문서에는 실제 차이와 이유를 남긴다.
- PR 본문은 트랜잭션 경계·선택한 제어·핵심 결과와 문서 링크를 요약한다. 긴 원시 로그를 복사하지 않는다.

## 6. 공통 검증 기준

### 초기 문서 준비

원문 항목별 반영·제외, 상대 링크, ID·폴더·브랜치 대응, 요구사항 간 누락·중복을 확인한다.
코드 변경이 없으므로 빌드·테스트를 실행하지 않으며, 과제 검증 체크리스트를 완료로 표시하지 않는다.

### 각 요구사항 구현

- 실제 잠금·롤백은 기존 MySQL 8.0 fixture로 검증한다. 메모리 DB나 mock만으로 증명하지 않는다.
- 중간 실패는 실제 변경 SQL이 최소 한 번 실행된 뒤 테스트 구성의 저장 경계에서 유발한다.
- 서비스 트랜잭션 종료 후 새 경계에서 DB를 재조회한다. 같은 JPA 관리 객체의 값만 보고 성공·롤백을 판정하지 않는다.
- 준비 데이터는 worker 시작 전에 commit하고, 동시 요청은 각각 독립된 connection·transaction에서 실제 Spring bean을 호출한다.
- 테스트 전체를 부모 트랜잭션으로 감싸지 않는다. 시작만 동기화하고 제품 코드의 잠금 구간에 장벽·sleep을 넣지 않는다.
- 대기·future에 제한 시간을 두며, finally에서 대기를 해제하고 worker·executor·connection을 정리한다.
- 요청별 성공·업무 거절·기술 오류를 수집하고 전체 요청 수와 대조한다. timeout·SQL 오류·재시도 한도 초과를 품절로 숨기지 않는다.
- 대표 성공·실패의 HTTP 연결을 확인한다. 동일한 도메인 경계값을 모든 계층에서 중복 검증할 필요는 없다.
- 관련 회귀 테스트와 `./gradlew :apps:commerce-api:check`를 실행하고 실행 건수·실패·skip·종료 결과를 기록한다.
- Checkstyle·ArchUnit이 실제 변경 코드를 검사하는지 확인한다. 실행하지 못했거나 선택하지 않은 검증은 그 한계를 명시한다.
