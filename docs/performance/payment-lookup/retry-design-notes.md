# 조회 Retry 설계 메모

이 문서는 구현 전 후보 검토 기록입니다. 이후 합의한 값으로 Retry, RateLimiter, TimeLimiter를 구현했습니다. 확정한 실험 정책은 [후속 설계](scenario-2-4-design.md), 실제 결과는 [측정 기록](runs/policies-20261023/summary.md)을 기준으로 확인합니다. 아래의 미정, 후보 표현은 검토 당시의 기록입니다.

## 참고한 관점

[외부 PG 연동 전략 설계 글 #91](https://github.com/loopers-labs/loop-pack-be-l2-vol4-kotlin/issues/91)에서 중첩 순서의 선택 근거, 회로의 집계 단위, HTTP timeout·재시도 간격·느린 호출 기준의 관계를 참고했습니다. 아래는 우리 코드와 과제 계약에 맞춘 검토입니다. 원문의 설정 수치를 우리 정책으로 채택한 것은 아닙니다.

| 관점 | 우리 설계에 반영할 것 | 상태 |
| --- | --- | --- |
| 중첩 순서 | 논리적 조회를 기준으로 집계하는 `CircuitBreaker(Retry(HTTP 조회))`를 우선 검증할 후보로 둡니다. | 후보, 구현 전 결정 |
| HALF_OPEN | 논리적 탐색 허가 수와 실제 HTTP 호출 수를 따로 기록합니다. | 측정 항목에 반영 |
| 시간 예산 | 실제 HTTP 호출 시간·backoff·기타 대기를 합산합니다. | 산정 방식에 반영, 수치는 미정 |
| 오류 분류 | 조회 성공·재시도 가능 실패·로컬 차단·표본 제외를 구분합니다. | 분류 필요, 세부 정책 미정 |
| 관측 | 외부 호출 수와 회로 표본 수를 함께 기록하고 내부 상태·재고·포인트를 대조합니다. | 검증 항목에 반영 |

## 유지할 과제 계약

- Retry 대상은 두 조회 GET입니다. 생성 POST는 자동 재시도하지 않습니다.
- 조회 실패·회로 차단으로 주문을 실패 확정하거나 예약을 반환하지 않습니다.
- `PENDING`, 조회 404·빈 목록은 새 결제 허용이나 효과 0건의 증거가 아닙니다.
- 생성 전 확정 거절은 기존 로컬 PG의 정확한 422 계약으로만 판정합니다. 일반 4xx와 구분합니다.
- callback·수동 reconcile·주기 조회는 기존 결과 적용 경계를 사용합니다.

## 무엇을 한 번으로 집계할 것인가

이번 후보의 논리적 조회 1회는 `lookup` 또는 `lookupByOrder`에 들어온 한 번의 작업입니다. callback·주기 조회도 이 경계를 호출하므로 전체를 사용자 HTTP 요청 수라고 부르지 않습니다.

| 구성 | 회로의 표본 | 느린 호출의 시간 범위 | HALF_OPEN 허가 |
| --- | --- | --- | --- |
| `CircuitBreaker(Retry(HTTP))` | 재시도를 마친 논리적 조회 1회 | 재시도와 backoff를 포함한 전체 작업 | 논리적 조회마다 1개, 실제 HTTP는 여러 번 가능 |
| `Retry(CircuitBreaker(HTTP))` | 실제 조회 시도별 결과 | 개별 시도 시간 | 실제 시도마다 소비 가능 |

우리는 core decorator를 직접 합성하므로 Spring annotation의 기본 Aspect 순서에 의존하지 않습니다. 후보를 채택한다면 회로가 OPEN일 때 내부 Retry에 진입하지 않고, 바깥에서 기존 조회 불가 결과로 변환하도록 연결합니다. [공식 Aspect 순서와 직접 합성](https://resilience4j.readme.io/docs/getting-started-3#aspect-order)

바깥 회로는 재시도 끝에 성공한 작업을 성공으로 집계합니다. 이때 중간 HTTP 실패는 회로의 실패율에 남지 않으므로 실제 시도별 결과도 별도 관측해야 합니다. Slow Call도 재시도 전체 지연을 측정하게 됩니다. 회복률·지연·실제 발송 수와 차단 시점을 비교해 후보를 판단합니다.

기존 HALF_OPEN 허가 2회를 유지하고 총 시도 수를 N으로 정한다면 두 논리적 탐색에서 최대 2N번의 HTTP 시도가 생길 수 있습니다. 이는 해당 탐색 작업의 계산이며, 이미 진행 중인 다른 호출까지 제한하는 상한은 아닙니다.

## 시간 예산

```text
논리적 조회 시간
  = 각 실제 HTTP 호출 시간의 합
  + 재시도 사이 대기 시간의 합
  + 연결 확보·스케줄링 등 기타 대기
```

`maxAttempts=3`은 최초 1회와 재시도 2회입니다. 호출이 각각 응답 timeout 2초까지 기다린다면 호출 시간만 약 6초이며 backoff 등이 더해집니다. 예시의 3회·2초는 우리 정책으로 정한 값이 아닙니다. [Retry 공식 설정](https://resilience4j.readme.io/docs/retry)

지수 backoff와 jitter를 적용한다면 기준 간격·배수·분산 범위와 최대 대기도 함께 정해야 합니다. 대기 간격의 합과 실제 HTTP를 포함한 전체 작업 시간을 구분합니다. 추후 RateLimiter의 허가 대기를 추가하면 그것도 전체 예산에 포함하고, TimeLimiter를 적용할 때 해당 작업 경계를 명시합니다.

Slow Call 기준은 선택한 집계 단위의 정상 지연과 허용 예산을 보고 정합니다. 바깥 회로가 재시도 전체를 재는 경우에는 개별 HTTP read timeout과의 대소 관계만으로 충분한 설계가 되지 않습니다. 기존의 느린 호출 기준은 이번 메모로 변경하지 않습니다.

## 현재 반환 모델에서 확인할 것

우리 adapter는 예외를 `PaymentLookupObservation.Unavailable(reason)`으로 변환합니다. 예외 타입만을 대상으로 한 `retryExceptions` 설정을 그대로 적용해도 이 반환값에는 Retry가 동작하지 않습니다. 재시도 결과 predicate 또는 명시적인 내부 오류 변환을 설계해야 합니다. [반환값 기반 Retry](https://resilience4j.readme.io/docs/retry)

최소한 아래 경계를 유지합니다.

- 조회한 거래의 PENDING·SUCCESS·FAILED는 정상적으로 읽은 결과입니다. 결제 FAILED를 조회 통신 실패로 재시도하지 않습니다.
- 로컬 차단인 `Unavailable("CIRCUIT_OPEN")`을 HTTP 일시 실패와 구분하며, 차단된 회로를 자동 재시도로 반복 통과시키지 않습니다.
- 현재 `Unavailable`에는 timeout·네트워크·HTTP 상태·형식 오류가 섞여 있습니다. 모든 `Unavailable`을 한꺼번에 재시도 대상으로 잡지 않습니다.
- 앞서 관찰한 `CancellationException`도 발생 경계와 남은 예산을 확인합니다. 추후 전체 작업 취소까지 같은 문자열만으로 재시도하는 정책은 정하지 않습니다.

실패 표본에서 제외하는 것과 성공 표본으로 세는 것은 다릅니다. `recordExceptions` 목록에 없는 예외는 성공으로 집계될 수 있으며, 성공·실패 양쪽에서 빼려면 `ignoreExceptions` 등의 동작을 확인해야 합니다. 현재 반환값 모델에서 표본 제외를 구현하는 경계도 확인한 뒤 결정합니다. [Circuit Breaker 공식 분류](https://resilience4j.readme.io/docs/circuitbreaker)

## 다음 실험의 기대값

| 시나리오 | 적용 전 관측 | 적용 후 검증할 기대값 |
| --- | --- | --- |
| 첫 조회 실패 후 다음 조회 성공 | 조회 불가, 내부 미완료 상태 유지 | 제한된 재조회로 같은 거래 확인, 실제 호출 증가량 기록 |
| 모든 조회가 계속 실패 | 반복 조회 불가 | 횟수·대기 예산 안에서 종료, 최종 결과만 회로에 집계하는지 확인 |
| OPEN 상태에서 조회 | 외부 발송 차단 | Retry 진입·추가 HTTP 발송 0회 |
| HALF_OPEN에서 일시 실패 후 성공 | 기존의 탐색 결과 확인 | 논리적 허가 수·회로 표본·실제 HTTP 횟수 각각 대조 |
| 정상 조회로 PENDING·FAILED 확인 | 정상 조회 결과 | 업무 결과를 근거 없이 재시도하지 않음, 기존 결과 반영 규칙 유지 |

워밍업 이후 상태를 비교 기준으로 삼습니다. 워밍업 구간과 본 측정의 표본을 분리하고, 워밍업 충분성은 구간별 지연·처리량·오류율을 확인합니다. 통제 실험의 회로는 준비 단계에서 CLOSED·빈 관찰 창으로 맞추고, 측정 중에는 자연 전이를 관측합니다.

## 구현 전에 정할 것

중첩 순서 채택 여부, 재시도 가능한 오류 범위, 총 시도 수, backoff·jitter, 전체 조회 예산과 Slow Call 기준이 남아 있습니다. 해당 선택의 근거를 설계 문서·관련 테스트에 먼저 적은 뒤 구현합니다. 참고 글을 가져왔다는 이유로 이 값들을 확정하지 않습니다.
