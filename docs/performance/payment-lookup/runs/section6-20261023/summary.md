# 섹션 6 검증과 실행 자원 보강

## 업무 결과 검증

- 정상 PG 주문의 실제 거래 수가 1건인지 단언한다.
- callback-first, lookup-first, 동시 반영과 실제 중복 callback에서 저장된 거래 키가 PG 조회로 확인한 키와 같은지 단언한다.
- 실제 PG에서 거래 한 건을 성공시킨 뒤 주문 저장에 오류를 주입한다. TX B rollback 뒤 MySQL을 flush/clear하고 시도 REQUESTED, 거래 키 NULL, 주문 PAYMENT_PENDING, 가용 재고 8과 포인트 100,000을 확인한다. 같은 주문으로 PG를 재조회해 한 번 확정하고 원래 PG 거래 키를 저장한다. 종결 뒤 재확인에는 추가 조회가 없다. 최종 PG create 1회, 거래 1건, 조회 2회다.
- 다른 주문의 성공 관찰을 실제 MySQL 결과 적용 경계에 전달해 TRANSACTION_MISMATCH 기록과 상태, 거래 키, 재고 보존을 확인한다.

## 실행 범위와 자원

일반 test-pg 실행은 `127.0.0.1`에 바인딩한다. 새 테스트는 실제 Tomcat 수신 주소를 확인한다. 수정 전에는 주소가 NULL인 전체 인터페이스 수신이라 실패했고 수정 후 통과했다.

컨테이너 내부 수신은 `0.0.0.0`으로 재정의하지만 호스트 공개 포트는 Testcontainers와 Compose 모두 `127.0.0.1`로 제한한다. 검사 중인 PG의 실제 Docker 포트 바인딩과 Compose 해석 결과도 확인했다. Commerce와 PG의 수동 전체 흐름은 두 앱을 호스트의 loopback에서 실행하도록 README를 정리했다.

테스트 이미지는 JVM마다 고유 이름을 사용하고 `deleteOnExit=true`로 종료 시 삭제한다. 이전 이미지 14개(이름 없는 13개와 고정 이름 1개)를 삭제한 뒤, 부모로 연결된 PG 중간 이미지 84개도 PG JAR 포함 이력과 컨테이너 참조 0개를 확인해 삭제했다. 마지막 확인에서 PG 이름의 이미지, 이름 없는 이미지와 Testcontainers는 모두 0개였다. Prometheus와 Grafana는 후속 측정용으로 유지했다.

이전 [자원 정리 기록](../cleanup-20261023/summary.md)은 이름 있는 별도 PG 이미지 1개만 다뤘다. 이번 점검에서 기존 Testcontainers 이미지 누적을 추가로 확인하고 정리한 것이다. 공통 기반 이미지와 모니터링 스택은 삭제 대상에 포함하지 않았다.

## 검사 결과

- Red: 기본 PG 수신 주소 검사 1개 실패. 실제 주소가 NULL이었다.
- 대상 검사: Commerce 100개, test-pg 19개, 양쪽 Checkstyle 통과.
- 전체 검사: Commerce 701개, test-pg 113개. 실패, 오류, 건너뜀 모두 0개. 양쪽 Checkstyle과 ArchUnit 통과. 3분 50초, 30개 작업 모두 실행.

실행 명령, 소스 해시, 단언과 자원 확인 결과(`verification.json`)를 보관했다. [결과 파일을 분리한 전체 검사](../../README.md#결과-파일을-분리한-전체-검사)로 재현한다. 정상 결제 5분 부하를 다시 측정한 결과는 아니다. PR 설명에는 PG 최종 실패의 재고 결과와 Commerce 재시작 중 외부 거래 상태를 보존하기 위해 별도 fixture를 쓰는 이유를 추가했다.

전체 검사 종료 뒤 이번 임시 build 디렉터리도 삭제했다. 검증 결과, 소스 해시와 저장소의 재현 스크립트는 보존했다.
