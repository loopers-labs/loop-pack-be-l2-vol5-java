# 정상 PG 재측정

초당 새 결제 10건·5분·동일한 시간 목표를 유지하고 준비·최대 VU만 50개에서 100개로 늘려 재측정했습니다. 본 측정 3,001건 모두 확정됐고 누락은 0건입니다. 단건 smoke 1건과 워밍업 300건은 아래 결과에 합산하지 않았습니다.

## 변경과 조건

[첫 실행](normal-report.md)에서는 50 active VU에 도달한 구간에 iteration 3개를 시작하지 못했습니다. 부하 발생기에 여유를 두고 다시 확인하기 위해 VU를 100개로 바꿨습니다. 이번 실행의 관측 active VU 최대는 36개였으므로, 100 VU가 항상 필요하거나 이 변경이 앞선 지연의 원인을 해결했다고 단정하지 않습니다. 첫 실행의 지연 원인은 아직 분리하지 않았습니다.

그 밖의 조건은 동일합니다. 사용자 50명, 상품 하나, 새 결제 10건/초, 별도 워밍업 30초와 본 측정 5분, 주문 GET 관측 간격 250ms·한도 10초입니다. VU는 결제 흐름을 실행할 자원이며 사용자 계정 수는 50명으로 유지했습니다.

test-pg는 AUTO/SUCCESS·처리 대기 3초·조회 추가 지연 0ms입니다. Commerce의 PG 연결·응답 timeout은 1초·3초이고 Circuit Breaker는 비활성, 주기 조회는 활성입니다. 새 자동 retry는 없습니다. 나머지 JVM·임시 DB·Redis 조건은 원본 환경 기록(`results/normal-20261022T114330Z/environment.json`)에 있습니다. 기존 로컬 데이터와 서비스는 사용하지 않았습니다.

```bash
python3 docs/performance/payment-normal/run-normal.py --rate 10 --vus 100 --duration 5m --warmup 30s
```

## 검증과 범위

원시 흐름 3,001개와 summary의 수를 대조했습니다. 주문 ID는 모두 달랐고 모든 PG 주문별 카운터는 create·lookup·callback·거래 각각 1이었습니다. DB 증가량·재고 감소량·포인트 유지와 실행 소스·JAR 해시도 일치했습니다. 임시 서버와 컨테이너는 종료했습니다.

이 실행은 정상 결제 흐름의 기준 기록입니다. 짧은 로컬 부하만으로 운영 SLO나 최대 처리량을 입증하지 않습니다. 후속 조회 지연 실험은 외부 조회 경계를 별도로 통제하므로 해당 실험의 전후끼리 비교합니다.

- 환경과 실행 소스 해시(`results/normal-20261022T114330Z/environment.json`)
- k6 summary(`results/normal-20261022T114330Z/measurement-summary.json`)
- 흐름별 원본(`results/normal-20261022T114330Z/measurement-events.log`)
- DB 전후·주문별 PG 카운터(`results/normal-20261022T114330Z/measurement-state.json`)
- 대조한 수와 지연 통계(`results/normal-20261022T114330Z/measurement-analysis.json`)
