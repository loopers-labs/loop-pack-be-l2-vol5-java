# 설계 문서 작성 가이드

## 이 문서의 목적

부트캠프 한 주 과제에서 요구사항 정의서(`docs/weekN/requirements.md`)를 입력으로 설계 문서(`docs/weekN/design.md`)를 작성·검토할 때 따르는 구조와 판단 기준. 요구사항 정의서 작성 가이드와 짝이며, 그 가이드가 부여한 ID(FR-, INV-, ASM-, CON-)를 그대로 입력으로 받는다.

설계 문서는 한 파일이다. 5개 층을 5개 장으로 쓰고, 설계 판단 기록(DR)과 추적성 매트릭스는 부록에 둔다.

## 핵심 원칙

**설계 문서는 요구사항을 다시 쓰지 않는다. 요구사항 ID를 받아 "어디에 두고 어떻게 지키는가"만 정한다.**

- 요구사항에 있는 것은 ID로 참조한다. 복사하지 않고, 이름을 바꾸지 않는다. 유스케이스는 FR이고, 불변식은 INV이고, 실패 케이스 이름은 요구사항이 정한 도메인 이름이다.
- 요구사항에 없는데 설계에 필요한 것은 둘 중 하나다. 해법 공간 개념(스냅샷, 이력)이면 설계 문서에 출처와 함께 둔다. 문제 공간 개념(원문이 다른 말로라도 이야기하는 대상)이면 요구사항으로 올려보낸다(0-4).
- 모든 설계 항목은 근거 ID를 가진다. 근거 ID가 없는 항목은 존재할 자격이 없다.
- 설계가 요구사항을 완화하면(불변식을 최종 일관성으로 재분류하는 등) DR과 함께 요구사항 1-4에 ASM으로 남긴다. "원문이 그랬나, 설계에서 정했나"는 언제나 구분 가능해야 한다.

### 5개 층과 이 문서의 장

| 층 | 장 | 답하는 질문 | 주 입력 |
|---|---|---|---|
| 1 시스템 | 1장 | 무엇이 고정되어 있나 | 요구사항 4 제약 |
| 2 컨텍스트 | 2장 | 무엇이 같이 변하고, 어떤 규칙이 항상 지켜져야 하나 | 요구사항 1-1, 2, 3-1, 3-2 |
| 4 데이터 | 3장 | 어떤 사실이 존재하고, 각 사실은 어디 한 곳에 사나 | 2장, 요구사항 3-2, FR 비기능 |
| 5 계약 | 4장 | 밖과 무엇을 어떻게 약속하나 | 요구사항 1-2, FR 실패 케이스, 2·3장 |
| 3 객체 | 5장 | 앞의 결정이 코드에서 그대로 보이나 | 전부 |

작성 순서는 장 순서다. 흐름은 직선이 아니다. 뒤 장을 쓰다 앞 장의 오류가 드러나면 앞 장을 고치고 DR 하나를 남긴다(부록 A). 각 장 끝의 완료 조건이 전부 참이어야 다음 장으로 넘어간다. Claude는 다음 장을 시작하기 전에 완료 조건을 검사한다.

## 0. 공통 규칙

### 0-1. ID

| 접두어 | 대상 | 만드는 곳 |
|---|---|---|
| FR-, INV-, ASM-, CON- | 요구사항 항목 | 요구사항 문서. 설계 문서에서 만들지 않는다 |
| BC- | 바운디드 컨텍스트 | 2장 |
| AG- | 애그리거트 | 2장 |
| TB-, IX-, ST-, LK- | 테이블, 인덱스, 상태 컬럼, 락 | 3장 |
| EP-, ER- | 엔드포인트, 에러 | 4장 |
| DR- | 설계 판단 기록 | 부록 A. 문서 전체에 번호열 하나 |
| OQ- | 열린 질문 | 부록 A |
| EV-, EC- | 도메인 이벤트, 이벤트 계약 | 예약만. 1-2에 따라 미사용 |

두 자리 숫자. 한 번 부여한 ID는 재사용하지 않는다. 삭제된 항목은 번호를 비워둔다.

### 0-2. 형식

- 부록 A(DR, OQ) 외에는 자유 서술을 쓰지 않는다. 표 또는 고정 문형.
- 용어는 DDD 표준 용어를 그대로 쓴다. "도메인"이라는 단어를 서브도메인이나 바운디드 컨텍스트 대신 쓰지 않는다. "주문 도메인" 금지, "주문 컨텍스트" 허용. 단 다음은 예외. 요구사항 가이드가 정의한 용어("도메인 접두어", "실패 케이스 도메인 이름"), 계층 이름으로서의 `domain` 패키지, 거기서 던지는 도메인 예외.
- 각 장에 금지어가 있다(0-3). 금지어가 나오면 그 내용은 다른 장으로 옮긴다.

### 0-3. 장별 금지어

| 장 | 금지어 |
|---|---|
| 2 컨텍스트 | 테이블명·컬럼명·인덱스, 클래스명·메서드명·패키지명(BC 영문 식별자 제외), URL·HTTP 메서드·요청/응답 필드, 프레임워크·DB 제품명 |
| 3 데이터 | 클래스명·메서드명·패키지명·리포지토리 인터페이스, URL·HTTP·요청/응답 필드, ORM 어노테이션·매핑 설정. DB 제품 고유 기능은 DR 필수 |
| 4 계약 | 클래스명·메서드명·패키지명·DTO 이름, 프레임워크·어노테이션. 테이블·컬럼은 "출처" 칸에서 TB-ID로만 |
| 5 객체 | 클래스 다이어그램. 코드로 알 수 있는 것을 문서에 다시 쓰는 것 |

### 0-4. 요구사항 피드백

설계 중 요구사항의 문제가 드러나면 설계 문서 안에서 우회하지 않고 요구사항을 고친다.

| 발견 | 처리 (요구사항 문서의 어디) |
|---|---|
| FR 하나가 Facade 메서드 둘로 갈리거나, FR 둘이 메서드 하나로 합쳐진다 | FR 재분할 · 2절 |
| 원문이 (다른 말로라도) 이야기하는 대상인데 용어집에 없다 | 용어 추가 · 1-1 |
| 설계상 항상 참이어야 하는 규칙인데 INV에 없다 | 불변식 추가 · 3-1 |
| INV를 최종 일관성으로 재분류한다 | 가정 추가 · 1-4 |
| 실패 케이스의 결과 상태가 비어 있거나 3-2 전이와 안 맞는다 | 2절 실패 케이스 · 3-2 |
| 원문에 없는 값을 설계가 넣어야 한다 (기본 페이지 크기 등) | 가정 추가 · 1-4 |

규칙
- 설계 문서 쪽: DR을 남기고 "관련 ID"에 요구사항 ID, "요구사항 반영" 칸에 고친 절을 적는다.
- 요구사항 문서 쪽: 고친 항목 옆에 `(설계 피드백 DR-xx)`를 붙인다.
- 요구사항을 고치면 요구사항 가이드의 정합성 검사를 다시 돌린다.

### 0-5. 이 가이드가 처리하지 못하는 요구사항

1장 고정 결정 밖의 요구사항이 나오면 설계하지 말고 OQ로 올린다. 억지로 끼워 넣지 않는다.

| 요구사항에 등장 | 왜 처리 못 하나 | 도입 시 고칠 곳 |
|---|---|---|
| 시스템 행위자 (배치, 스케줄, 콜백) | 진입점이 HTTP뿐 | 1-2 진입점, 4-2에 진입점 유형 추가, 5-2에 클래스 역할 추가 |
| FR 결과 = 부작용 (외부 전송, 알림) | 외부 시스템·이벤트 없음 | 1-2, 2-4에 ACL 행, 2-5 최종 일관성, 5-5 |
| 외부 시스템 (PG 등) | CON에 없음 | 1-1 CON 추가, 2-4 ACL |
| 이벤트가 필요한 결합 해제 | 이벤트 미사용 | 1-2, 2-4 이벤트 절, 4장 이벤트 계약 절 신설 |

## 1. 시스템 (Level 1)

이 장은 프로젝트마다 거의 같다. 요구사항 4절 제약과 팀 고정 결정을 한 곳에 모아, 나머지 장이 "이번 과제에서 미사용"을 반복하지 않게 한다.

### 1-1. 제약 입력

요구사항 4절 CON 표를 그대로 옮겨 적는다. 설계 문서에서 유일하게 복사하는 항목이다. 1-2의 고정 결정이 CON과 충돌하면 CON이 이긴다.

```
| CON-ID | 제약 | 근거 |
```

### 1-2. 팀 고정 결정

| 항목 | 결정 |
|---|---|
| 구조 | 모놀리스. 단일 배포 단위 |
| 저장소 | 단일 RDB. JPA |
| 패키지 | layer-first. `com.loopers.{interfaces.api, application, domain, infrastructure}.<bc>`. `ApiResponse`, `ApiControllerAdvice`는 `interfaces.api` 직속. BC 하나 = 네 계층에 같은 영문 식별자로 존재하는 하위 패키지의 묶음 |
| BC 간 통신 | 동기 호출만. 하류 `application.<bc>.Facade` → 상류 `domain.<bc>.Service` |
| 이벤트 | 미사용. EV-, EC- 번호만 예약 |
| 진입점 | HTTP 요청뿐. 시스템 행위자는 0-5 |
| domain 계층의 JPA 의존 | 허용. 의도된 타협이며, 의존성 역전은 Repository 인터페이스에서만 |
| 트랜잭션 경계 | Facade public 메서드. Facade public 메서드 하나 = FR 하나 |
| 즉시 일관성으로 변경하는 AG | 원칙 1개. 2개 이상이면 근거 필수 |
| 실패 표현 | 도메인 예외 → `ApiControllerAdvice` → ER-. 예외 규칙은 5-4 |
| Shared Kernel | 미사용. 필요해 보이면 합치거나 소유를 한쪽으로 넘긴다 |

### 1-3. 계약 공통 규약 기본값

4장 계약의 공통 규약. 프로젝트별로 다시 결정하지 않고, 4-1에는 여기서 벗어나는 것만 적는다. "확정 필요"로 표시된 값은 팀에서 한 번 확정한 뒤 이 표를 고친다.

| 항목 | 기본값 |
|---|---|
| 버전 표기 | 경로 접두어 `/api/v1` |
| 응답 봉투 | `ApiResponse { meta { result: SUCCESS, errorCode: null, message: null }, data }` |
| 에러 봉투 | 같은 봉투. `meta { result: FAIL, errorCode: ER 코드, message: ER 메시지 }`, `data: null` |
| 에러 코드 체계 | 범용 `ErrorType`(BAD_REQUEST, NOT_FOUND, CONFLICT, INTERNAL_ERROR) 기본. 도메인별 코드는 요구사항 실패 케이스에 "클라이언트가 구분해야 함"이 있을 때만 추가 |
| HTTP 상태 고정 매핑 | 검증 → 400, 권한 → 403, 참조 없음 → 404, INV·ST 위반 → 409, 동시성 충돌 → 409, 서버 → 500 |
| 검증 에러 형식 | 400 + `message`에 실패 필드와 이유 한 문장. `details` 미사용 (확정 필요) |
| 페이징 | 오프셋. 요청 `page`, `size`; 응답 `meta`에 총 개수 (확정 필요) |
| 식별자 | 내부 PK 노출 |
| 시간 | ISO 8601, UTC |
| 금액 | 정수 (최소 단위). 부동소수 금지 |
| 인증 전달 | 헤더 (헤더명 확정 필요). 인증 로직은 계약 밖 |
| 멱등성 | 멱등 키 미사용 |
| 계약 변경 | 과제 기간 내 비호환 변경은 즉시 폐기. DR만 남긴다 |

## 2. 컨텍스트 (Level 2)

목적: **"무엇이 같이 변하고, 어떤 규칙이 항상 지켜져야 하는가"를 정한다.**

이 장은 요구사항을 정리하지 않는다. 요구사항 1-1 용어집, 2 FR, 3-1 불변식, 3-2 상태 전이가 정합성 검사를 통과한 상태로 들어온다.

### 2-1. 바운디드 컨텍스트

해법 공간의 경계. **그 안에서 단어 하나가 한 가지 뜻만 갖는 범위**다. 컨텍스트마다 아래 블록을 반복한다.

```
### BC-XX 한글 이름 (영문 식별자)

- 유형: 코어 | 지원
- 책임: (한 문장. "~을 결정한다" 또는 "~을 보장한다")

#### 소유 개념
| 명사 | 이 컨텍스트 안에서의 정의 | 출처 |

#### 참조 개념
| 명사 | 소유 컨텍스트 | 참조 이유 |

#### 용어 충돌
| 단어 | 여기서의 뜻 | 다른 컨텍스트(BC-XX)에서의 뜻 |
```

규칙
- 영문 식별자는 패키지 이름이다. 소문자 한 단어.
- 유형: 코어 = 이게 없으면 이 서비스가 아니다, 최대 2개. 지원 = 필요하지만 차별점은 아니다.
- 책임 문장에 "그리고", "및"이 들어가면 컨텍스트가 둘이다. 나눈다.
- **소유 개념** = 이 컨텍스트가 정의의 주인인 명사. 이 표가 유비쿼터스 언어 사전이고, 3장에서 이 컨텍스트가 소유하는 테이블은 이 명사에서만 나온다. 같은 명사가 두 컨텍스트의 소유 개념에 나오면 오류.
- 출처는 둘 중 하나.
    - `용어집`: 요구사항 1-1의 단어. 이름을 바꾸지 않는다. 용어집의 모든 단어는 정확히 하나의 BC 소유 개념이어야 한다.
    - `설계 도입 ← 원천 용어, DR-XX`: 해법 공간에서만 필요한 개념(주문 항목, 스냅샷, 이력). 어느 용어집 단어에서 파생됐는지와 DR 필수. 원천 용어 없는 개념은 만들 수 없다. 원문이 이 대상을 다른 말로라도 이야기한다면 설계 도입이 아니라 용어집 누락이다 → 0-4.
- **참조 개념** = 쓰지만 정의의 주인이 아닌 명사. 3장에서 ID 컬럼으로만 나오고 테이블이나 FK로 나오지 않는다. 참조 개념의 소유 컨텍스트가 2-3의 상류다.
- **용어 충돌** = 같은 단어를 다른 컨텍스트가 다른 뜻으로 쓰는 경우. 양쪽 블록에 모두 적는다. 참조 개념을 자기 식으로 재해석하고 있다면 그건 참조가 아니라 새 소유 개념이다. 이름을 새로 붙여 "설계 도입"으로 올린다.

예시
```
| 상품 | 주문 시점 단가가 고정된 구매 대상 (→ 소유 개념 "주문 항목") | BC-01 카탈로그: 현재 판매가를 가진 판매 목록 항목 |
| 주문 항목 | 주문에 담긴 상품 하나와 주문 시점 단가·수량 | 설계 도입 ← 상품, 주문. DR-01 |
```

### 2-2. 불변식 배치와 애그리거트 후보

**애그리거트** = 어떤 불변식을 지키기 위해 반드시 같이 읽고 같이 저장해야 하는 개념의 묶음. 곧 트랜잭션 경계다.

#### 2-2-A. 불변식 배치

요구사항 3-1의 INV를 그대로 받아 두 컬럼을 붙인다. INV를 새로 만들지 않는다. 새 규칙이 보이면 0-4.

```
| INV-ID | 대상 용어 (요구사항 3-1) | 소속 AG-ID | 위반 시 |
```

규칙
- 위반 시는 셋 중 하나.
    - **거부 (AG 내)**: 대상 용어가 전부 하나의 AG 안에 있다. 루트 Model이 검증하고 트랜잭션을 실패시킨다. 기본값.
    - **거부 (FR 트랜잭션)**: 대상 용어가 2개 이상의 AG에 걸친다. 어느 AG도 단독으로 검증하지 못하고, 이 INV를 건드리는 모든 FR이 2-4에서 "즉시, 다중 AG"로 그 AG들을 한 트랜잭션에서 변경하기 때문에 원자성으로 지켜진다. 소속 AG 칸에 관련 AG 전부, 위반 시 칸에 근거 FR-ID와 DR. 관련 FR 중 하나라도 2-4에서 최종/혼합이면 이 값을 쓸 수 없다.
    - **최종 일관성**: 잠깐 어긋나도 된다. 요구사항은 "항상 참"으로 적었으므로 이건 요구사항 완화다. 소속 AG "없음", DR 필수, 요구사항 1-4에 ASM 추가(0-4). 이번 과제 조건(1-2)에는 재시도·배치·이벤트가 없어 수렴 수단이 Facade의 보상 호출뿐이다. 보상까지 실패한 뒤의 상태를 DR에 적고 OQ에 올린다. 앞의 둘로 안 될 때만 쓴다. 어느 FR의 Facade에서 별도 트랜잭션으로 처리하는지 2-4 근거 칸에 적는다.
- 거부(AG 내) 불변식은 정확히 하나의 애그리거트 안에서 검증 가능해야 한다.
- **AG 도출 규칙**: INV의 대상 용어가 2개 이상이면 같은 AG / 거부(FR 트랜잭션) / 최종 일관성 중 하나. 순서대로 검토한다.

#### 2-2-B. 애그리거트 후보

```
| AG-ID | BC-ID | 루트 | 포함 개념 | 근거 INV-ID | 상태 전이 (요구사항 3-2 용어) |
```

규칙
- 근거 INV가 없는 애그리거트는 존재할 자격이 없다. 편의로 묶지 않는다.
- 요구사항 3-2에 상태 전이를 가진 용어는 루트 후보다. 상태 전이를 가진 용어가 포함 개념에 들어가면 근거를 DR로 남긴다.
- 포함 개념에 다른 애그리거트의 루트가 나오면 오류. 애그리거트 간 참조는 ID로만.
- 루트와 포함 개념은 2-1 소유 개념에 있는 명사만 쓴다.
- 여기서는 **후보**다. 3장에서 조회 패턴과 크기를 보고 확정한다. 뒤집히면 이 절을 수정하고 DR을 남긴다.

예시
```
| INV-01 | 포인트 | AG-02 | 거부 (AG 내) |
| INV-02 | 포인트, 주문 | AG-01, AG-02 | 거부 (FR 트랜잭션: FR-PAY-02, DR-03) |
| INV-04 | 주문 | AG-01 | 거부 (AG 내) |

| AG-01 | BC-02 | 주문 | 주문 항목 | INV-04 | 주문 |
```

### 2-3. 컨텍스트 맵

컨텍스트 사이의 의존 관계. 2-1의 참조 개념에서 방향이 나온다.

```
| 상류 BC | 하류 BC | 관계 유형 | 교환 개념 | 목적 |
```

규칙
- 상류 = 정의를 가진 쪽. 하류 = 그 정의를 따르는 쪽.
- 순환 금지. 순환이 나오면 경계를 재검토한다.
- 관계 유형은 Conformist / Customer-Supplier / ACL / Published Language 중 하나. 이번 과제 조건에서 실제로 쓰이는 값은 아래와 같고, 그래도 컬럼은 남긴다.
    - Conformist: 기본값. 같은 팀·같은 코드베이스면 전부 이것.
    - Customer-Supplier: 상류와 하류 팀이 다를 때만. 1인 과제에서는 나오지 않는다.
    - ACL: 외부 시스템. 1-1 CON에 외부 시스템이 있을 때만.
    - Published Language: 이벤트 도입 전 미사용.
- 교환 수단은 동기 호출뿐이므로 컬럼을 두지 않는다(1-2).
- 목적은 조회 / 변경. 동기 호출은 **하류가 상류의 상태를 조회하는 경우**가 기본이다. "변경"은 진입 BC의 Facade가 상류 BC의 Service를 순차 호출해 상태를 바꾸는 경우이며, 2-4에 변경 AG와 일관성이 반드시 적혀 있어야 한다.
- 교환 개념은 개념 수준으로 쓴다. 필드나 타입은 4장.

예시
```
| BC-01 카탈로그 | BC-02 주문 | Conformist | 상품 ID → 판매 가능 여부, 현재가 | 조회 |
| BC-03 재고     | BC-02 주문 | Conformist | 주문 항목 수량 → 재고 차감 | 변경 (FR-PAY-02, 2-4 참조) |
```

### 2-4. FR × 컨텍스트 매핑

각 FR이 어느 컨텍스트에서 시작해 어디를 건드리는지. **경계 오류 검출기**이자 **트랜잭션 경계의 단일 출처**다. 3-8과 5-5는 이 표를 검증·참조만 한다.

```
| FR-ID | 진입 BC | 참여 BC | 변경 AG-ID | 일관성 | 근거 |
```

규칙
- 요구사항 2절의 모든 FR이 한 줄씩 있다.
- 진입 BC는 정확히 하나. 참여 BC는 진입 BC를 제외하고 동기 호출로 관여하는 컨텍스트.
- 변경 AG는 이 FR이 상태를 바꾸는 애그리거트. 조회 FR은 "없음". FR 실패 케이스 중 결과 상태가 전이인 것이 있으면 실패 경로에서도 변경이 일어나므로 변경 AG에 포함하고 근거에 "실패 경로 쓰기 (실패 케이스 이름)"을 적는다.
- 일관성은 즉시 / 최종 / 혼합.
    - 즉시: 변경 AG가 모두 한 트랜잭션.
    - 최종: Facade가 별도 트랜잭션으로 이어서 호출. 앞이 성공하고 뒤가 실패했을 때 어떻게 되는지 근거에 적는다. 뒤가 실패하면 보상 호출뿐이다. 보상도 실패한 뒤의 상태를 근거에 적는다.
    - 혼합: 근거에 어느 AG가 어느 쪽인지 적는다.
- **즉시 일관성으로 변경되는 AG는 원칙적으로 1개.** 2개 이상이면 근거 필수. 근거를 쓸 수 없으면 2-2 경계 오류.
- **참여 BC가 3개 이상인 FR은 자동으로 OQ에 올린다.** 경계가 행동 기준으로는 맞지만 조회 기준으로 틀렸을 가능성이 높다. 대응은 경계 재조정.

이 표가 잡아내는 것
- 주인 없는 개념 → 2-1에서 소유 개념을 못 정하는 명사
- 경계를 가로지르는 일관성 → 두 AG에 걸친 INV, 즉시 일관성 다중 AG
- 경계를 가로지르는 조인 → 참여 BC 3개 이상, 4장에서 다중 BC 응답

### 2-5. 완료 조건

- [ ] 요구사항 1-1 용어집의 모든 단어가 정확히 하나의 BC 소유 개념에 있다.
- [ ] 출처 "설계 도입"인 모든 소유 개념이 원천 용어와 DR을 가진다.
- [ ] 모든 참조 개념의 소유 컨텍스트가 2-3에 상류로 나타난다.
- [ ] 요구사항 3-1의 모든 INV의 위반 시가 거부(AG 내) / 거부(FR 트랜잭션) / 최종 일관성 중 하나로 정해져 있다. 최종 일관성인 것은 DR과 ASM을, 거부(FR 트랜잭션)인 것은 DR을 가진다.
- [ ] 거부(FR 트랜잭션)인 INV의 관련 FR이 전부 2-4에서 즉시 다중 AG다.
- [ ] 모든 AG가 근거 INV를 가진다.
- [ ] 요구사항 3-2의 상태 전이를 가진 모든 용어가 어느 AG의 루트이거나, 포함 개념인 근거 DR이 있다.
- [ ] 2-3에 순환이 없다.
- [ ] 2-3에서 목적이 "변경"인 행은 전부 2-4에 변경 AG와 일관성이 적혀 있다.
- [ ] 요구사항 2절의 모든 FR이 2-4에 있고, 진입 BC가 정확히 하나다.
- [ ] 즉시 일관성으로 2개 이상 AG를 변경하는 FR에 전부 근거가 있다.
- [ ] 참여 BC 3개 이상인 FR이 전부 OQ에 올라가 있다.
- [ ] 이 장에 금지어가 없다.

3장으로 인계되는 것
- 2-1 소유 개념 → 각 BC가 소유하는 테이블의 후보
- 2-1 참조 개념 → ID 컬럼으로만 존재, FK 금지
- 2-2 AG → 같은 트랜잭션에서 저장하는 테이블 묶음, FK 허용 범위
- 2-4 일관성 → 절대 같은 트랜잭션에 있으면 안 되는 테이블 쌍

## 3. 데이터 (Level 4)

목적: **"어떤 사실이 존재하고, 각 사실은 정확히 어디 한 곳에 사는가"를 정한다.**

2장이 뭐라고 하든 지켜야 하는 데이터 자체의 규율을 다룬다. 사실의 중복 금지, 참조 무결성, 조회 패턴, 동시성. 이것들은 2장에서 도출되지 않고 여기서 독립적으로 검증한다.

컬럼명은 snake_case, 테이블명은 단수형. 5장에서 바꿀 수 없다.

### 3-1. 소유 매핑

**"모든 테이블은 정확히 하나의 BC가 소유한다"**를 검사하는 표.

```
| TB-ID | 테이블명 | 소유 BC | 소속 AG | 대응 소유 개념 |
```

규칙
- 소유 BC를 정할 수 없는 테이블은 2장의 문제다. 경계가 잘못됐거나 이름 안 붙은 개념이 숨어 있거나. 2-1로 돌아가 DR을 남긴다.
- 대응 소유 개념은 2-1 소유 개념에 있는 명사만.
- 소속 AG가 "없음"인 테이블은 없다. 모든 테이블은 어느 AG의 루트 또는 포함 개념에 대응한다.
- 하나의 소유 개념이 여러 테이블로 쪼개질 수 있다(1:N 속성, 이력). 이력 테이블은 원본과 같은 AG. 여러 소유 개념이 한 테이블에 들어가면 안 된다.

### 3-2. 테이블 정의

테이블마다 반복한다.

```
### TB-XX 테이블명

- 소유 BC: BC-XX / 소속 AG: AG-XX / 대응 개념: (명사)
- 기본키: (컬럼)
- 고유 제약: (컬럼 조합, 없으면 "없음")

| 컬럼 | 타입 | NULL | 제약 | 의미 | 출처 |
```

출처는 넷 중 하나.
- `소유`: 2-1 소유 개념의 속성. 이 테이블이 이 사실의 유일한 거처.
- `참조: BC-XX`: 다른 컨텍스트 개념의 ID. FK 없음. ID 외의 값을 복사하면 `스냅샷`.
- `스냅샷: BC-XX`: 다른 컨텍스트의 값을 특정 시점에 복사한 것. 원본과 달라지는 것이 의도된 경우에만(주문 시점 단가). 2-1 용어 충돌 표 또는 설계 도입 개념에 근거가 있어야 한다.
- `시스템`: 생성일시, 수정일시, 버전 등 도메인 의미 없는 컬럼.

규칙
- **사실 하나는 한 곳에만 산다.** 같은 사실이 두 테이블에 있으면 하나는 `스냅샷`이어야 한다.
- 계산 가능한 값(합계, 개수)은 컬럼으로 두지 않는다. 두려면 DR(조회 빈도)과 갱신 책임(3-8).
- NULL 허용 컬럼은 "왜 없을 수 있는가"를 의미 칸에 적는다. "선택 입력"은 이유가 아니다.
- 상태 컬럼은 3-4의 ST-ID를 제약 칸에 적는다.
- 3NF 기본. 벗어나면 DR.
- 동시성 제어(3-6)가 낙관 락이면 대상 테이블에 버전 컬럼(`시스템`)을 둔다.

### 3-3. 관계와 참조 무결성

```
| 자식 TB | 자식 컬럼 | 부모 TB | 부모 컬럼 | FK 여부 | 삭제 시 | 근거 |
```

규칙
- **FK는 같은 애그리거트 안에서만.** 근거에 AG-ID.
- 애그리거트가 다르면(같은 BC여도) FK 없음. 근거 "AG 간 참조". 컨텍스트가 다르면 근거 "BC 간 참조".
- FK 없는 참조의 무결성은 애플리케이션 책임. 어느 FR에서 검증하는지 근거에 FR-ID. 검증하는 FR이 없으면 "검증 안 함, 고아 허용"이라고 명시한다.
- 삭제 시는 CASCADE / RESTRICT / 없음 중 하나. CASCADE는 같은 AG 안에서만.

### 3-4. 상태 컬럼

상태의 정의와 전이는 요구사항 3-2가 유일한 출처다. 여기서는 그 상태가 어느 컬럼에 사는지만 정한다. 전이 표를 다시 쓰지 않는다.

```
| ST-ID | 요구사항 3-2 용어 | TB.컬럼 | 상태값 목록 | 종료 상태 | 실패로 인한 전이 |
```

규칙
- 요구사항 3-2에 있는 모든 용어가 정확히 하나의 ST-를 가진다.
- 상태값은 요구사항 3-2의 이름 그대로.
- 실패로 인한 전이: 요구사항 3-2에서 실패 케이스가 트리거인 전이 중 결과 상태가 "유지"가 아닌 것을 "실패 케이스 이름 → 상태"로 적는다. 없으면 "없음". 이 칸이 비어 있지 않은 FR은 2-4 변경 AG와 5-4 실패 표현 예외 규칙의 대상이다.
- 요구사항 3-2에 없는 전이는 금지된 전이다. 4장에서 ER-로 거부된다.

### 3-5. 삭제와 이력

```
| TB-ID | 삭제 방식 | 이력 보존 | 근거 FR-ID |
```

규칙
- 삭제 방식은 삭제 없음 / 논리 삭제(deleted_at) / 물리 삭제. **기본값은 삭제 없음.** 삭제하는 FR이 없으면 다른 방식을 고르지 않는다.
- 논리 삭제를 선택한 테이블은 모든 조회에서 삭제 행을 제외하며, 3-7 조건 컬럼에 반영한다.
- 이력 보존 "예"면 이력 테이블을 3-1에 등록한다. 소속 AG는 원본과 같다. 원본 루트 Model이 이력을 만들고, 원본 Repository가 같은 트랜잭션에서 저장한다. 근거는 이력을 읽는 FR. 읽는 FR이 없으면 만들지 않는다.

### 3-6. 동시성 제어

요구사항 FR 비기능에 "동시에", "동시 요청 하에서도"가 있는 FR만 대상이다. 없으면 이 절은 "없음".

```
| LK-ID | 근거 FR-ID (비기능) | 지키는 INV-ID | 대상 TB.컬럼 | 방식 | 충돌 시 결과 |
```

규칙
- 방식은 낙관 락(버전 컬럼) / 비관 락(행 잠금) / DB 제약(CHECK, UNIQUE) 중 하나. 고른 이유는 DR.
- 충돌 시 결과는 둘 중 하나. 요구사항 실패 케이스 이름(클라이언트에게 실패로 나감) / 재시도(횟수와 최종 실패 시 이름). 실패로 나가는 것은 4-4에 ER-가 있어야 한다.
- 비관 락은 잠금 순서를 DR에 적는다. 두 FR이 서로 다른 순서로 잠그면 교착이다.
- 성능 비기능("N초 이내")은 이 절이 아니라 3-7 예상 빈도의 근거로 쓴다.

### 3-7. 조회 패턴과 인덱스

#### 3-7-A. 조회 패턴

2-4의 모든 FR에 대해 읽는 테이블과 조건을 적는다. 명령 FR도 읽는다.

```
| FR-ID | 읽는 TB | 조건 컬럼 | 정렬/페이징 | 예상 빈도 | 걸치는 BC 수 |
```

규칙
- 조건 컬럼은 WHERE에 들어가는 컬럼. 조인 키 포함.
- 정렬·필터·기간 기준은 요구사항 FR "출력" 필드에서 온다. 거기 없는 기준을 넣으면 0-4 가정.
- 예상 빈도는 높음 / 중간 / 낮음 / 미정. 근거 없이 "높음"으로 쓰지 않는다. 근거는 FR 비기능 또는 DR.
- **걸치는 BC 수가 2 이상이면 컨텍스트 경계를 가로지르는 조회다.** 2-4 "참여 BC 3개 이상"이 놓친 것을 잡는 두 번째 그물.
    - 진입 BC의 Facade가 각 BC의 Service를 따로 호출해 조합한다. 유일한 방법이다. 어느 Service를 부르는지는 5-6.
    - Facade 조합으로 안 되는 조회(여러 BC 기준의 정렬·페이징, N+1로 감당 불가)는 설계하지 않고 OQ에 올린다.
    - 다른 BC의 테이블을 SQL 조인으로 직접 읽는 것은 허용하지 않는다.

#### 3-7-B. 인덱스

```
| IX-ID | TB-ID | 컬럼 (순서대로) | 유형 | 근거 FR-ID |
```

규칙
- 근거 FR이 없는 인덱스는 만들지 않는다.
- 유형은 일반 / 고유 / 복합. 복합은 컬럼 순서를 고른 이유를 DR에.
- FK 컬럼은 인덱스 기본. 근거 "FK".
- 예상 빈도 "낮음"인 조회를 위한 인덱스는 만들지 않는다.

### 3-8. 트랜잭션 경계 확인

2-4가 단일 출처다. 여기서는 테이블 수준에서 대조만 하고, **불일치가 있을 때만** 줄을 쓴다. 기본은 "2-4와 전부 일치".

```
| FR-ID | 2-4의 변경 AG | 실제 쓰는 TB의 소속 AG | 불일치 내용 | 처리 (2-4 수정 DR-XX / 트랜잭션 분리 DR-XX) |
```

규칙
- 쓰는 TB의 소속 AG가 2개 이상인데 한 트랜잭션이면, 2-4에 "즉시, 다중 AG, 근거 있음"이 있어야 한다. 없으면 여기 줄을 쓰고 어느 쪽이 맞는지 정한다. 대부분 2-4가 낙관적이었던 경우다.
- 이력 테이블은 원본 AG 소속이므로 별도 확인 대상이 아니다.
- 최종 일관성 FR은 앞 트랜잭션 성공 후 뒤가 실패했을 때의 상태가 2-4 근거에 있는지 확인한다. 없으면 불일치.
- 3-4 "실패로 인한 전이"가 있는 FR은 실패 경로도 쓰기이므로, 2-4 변경 AG에 포함되어 있는지 확인한다.

### 3-9. 완료 조건

- [ ] 모든 TB가 정확히 하나의 소유 BC를 가진다.
- [ ] 모든 TB의 대응 소유 개념이 2-1에 존재한다.
- [ ] 모든 TB가 정확히 하나의 소속 AG를 가진다.
- [ ] 출처 `소유`인 컬럼이 두 테이블에 같은 사실로 존재하지 않는다.
- [ ] 모든 FK가 같은 AG 안에 있다.
- [ ] FK 없는 참조마다 검증 FR 또는 "고아 허용"이 명시되어 있다.
- [ ] 요구사항 3-2의 모든 용어가 정확히 하나의 ST-를 가진다.
- [ ] FR 비기능에 동시성 문장이 있는 모든 FR이 3-6에 있다. 낙관 락 대상 TB에 버전 컬럼이 있다.
- [ ] 모든 FR이 3-7-A에 있다.
- [ ] 걸치는 BC 수 2 이상인 조회가 SQL 조인으로 처리되지 않는다.
- [ ] 모든 IX-에 근거 FR이 있다.
- [ ] 3-8이 비어 있거나, 모든 줄에 처리 DR이 있다.
- [ ] 이 장에 금지어가 없다.

4장으로 인계되는 것
- 3-1 소유 매핑 → API가 어느 BC의 데이터를 노출하는지
- 3-4 ST- → 상태 변경 API의 허용 전이와 에러
- 3-6 LK- → 동시성 충돌 에러
- 3-7-A 정렬/페이징 → 목록 API의 페이징

테이블 구조는 API 응답 형태를 결정하지 않는다. 4장에서 응답 필드를 컬럼에서 그대로 가져오면 4장 오류다.

## 4. 계약 (Level 5)

목적: **"밖에서 이 시스템과 무엇을 어떻게 약속하는가"를 정한다.**

계약은 한 번 공개되면 바꾸기 어렵다. 규모는 작아도 결정 비용은 1장급이다.

필드명은 camelCase, 경로는 kebab-case 복수형 명사. 계약의 일부이므로 5장에서 바꿀 수 없다.

### 4-1. 공통 규약

1-3 기본값을 따른다. **여기서 벗어나는 항목만 적는다.** 벗어나는 항목이 없으면 "1-3과 동일".

```
| 항목 | 1-3 기본값 | 이 프로젝트 | 근거 |
```

반드시 결정하는 항목 하나: **에러 코드 체계**. 요구사항 FR 실패 케이스에 "클라이언트가 실패 케이스를 구분해야 함"이 하나라도 있으면 도메인별 코드를 쓴다. 없으면 범용 `ErrorType`으로 충분하고, 실패 케이스 이름은 `message`와 테스트 이름에만 남는다. 어느 쪽이든 근거 FR-ID를 적는다.

### 4-2. 엔드포인트 목록

```
| EP-ID | 메서드 | 경로 | 종류 | 근거 FR-ID | 소유 BC |
```

규칙
- **하나의 EP는 정확히 하나의 FR에 대응한다.** 하나의 FR이 여러 EP를 가지는 것은 허용하되(같은 행위의 단건/목록) 근거를 4-3 블록에 적는다.
- 요구사항 2절의 모든 FR이 최소 하나의 EP를 가진다. 예외는 행위자가 시스템인 FR뿐이며 그건 0-5로 간다.
- 종류는 명령 / 조회. 조회 EP가 상태를 바꾸면 오류.
- 소유 BC는 근거 FR의 진입 BC(2-4)와 같아야 한다.
- 경로의 리소스명은 소유 BC의 소유 개념(2-1)에서만. 참조 개념을 리소스로 쓰지 않는다. 주문 BC가 `/products/...`를 열면 오류.
- 경로 깊이는 최대 2단계 리소스(`/orders/{id}/lines`).

### 4-3. 엔드포인트 정의

엔드포인트마다 반복한다.

```
### EP-XX 메서드 경로

- 근거 FR: FR-XX / 소유 BC: BC-XX / 종류: 명령|조회
- 권한: (요구사항 1-2 행위자명)
- 멱등성: 예|아니오

#### 요청
| 위치 | 필드 | 타입 | 필수 | 제약 | 의미 | 출처 개념 |

#### 응답 (성공 상태 코드)
| 필드 | 타입 | NULL | 의미 | 출처 |

#### 상태 전이
| ST-ID | 허용 전이 (현재 → 다음) |

#### 에러
| ER-ID | 발생 조건 (이 EP 기준) |
```

요청 규칙
- 위치는 경로 / 쿼리 / 바디 / 헤더.
- 권한은 요구사항 1-2 표의 행위자 이름 그대로. 1-2에서 그 행위자가 그 리소스 권한을 갖는지 확인한다.
- 출처 개념은 2-1의 소유 개념 또는 참조 개념. 참조 개념이면 ID만 받는다. 참조 개념의 속성(상품명, 고객 이메일)을 요청으로 받으면 오류. 그 값은 상류 BC가 안다.
- 제약은 검증 가능한 것만. 길이, 범위, 형식, 열거값. 요구사항에 없는 값(최소 금액 등)이 제약에 들어가면 0-4 가정.
- 명령 EP의 바디에 응답용 필드(생성일시, 계산값)가 있으면 오류.

응답 규칙
- 출처는 `TB-XX.컬럼` / `조합: BC-XX` / `계산` 중 하나.
- **응답 필드의 출처를 소유 BC 밖의 TB로 직접 쓰면 오류.** 다른 BC 데이터는 `조합: BC-XX`로만(5-6에 호출 기록).
- 필드명은 컬럼명이 아니라 개념 언어로 다시 쓴다. 각 필드는 근거 FR의 "출력"이 필요로 하는 것이어야 한다. 근거를 못 쓰는 필드는 뺀다.
- 목록 응답의 항목 형태와 단건 응답이 다르면 둘 다 정의한다.

상태 전이 규칙
- 명령 EP가 상태를 바꾸면 3-4의 ST-ID와 허용 전이를 명시한다. 여기 없는 전이 시도는 ER-로 거부된다.
- 조회 EP는 "해당 없음".

### 4-4. 에러 규약

요구사항이 정한 실패 케이스 도메인 이름을 HTTP로 매핑하는 표. 이름을 새로 짓지 않는다.

```
| ER-ID | 코드 | HTTP | 메시지 (사용자 노출) | 근거 FR 실패 케이스 | 유형 | 상태 변화 |
```

규칙
- 코드는 4-1 결정에 따라 둘 중 하나.
    - 도메인별: 요구사항 실패 케이스 도메인 이름 그대로 (`INSUFFICIENT_STOCK`). 재작명 금지.
    - 범용: `ErrorType` 값. 여러 실패 케이스가 하나의 ER-를 공유할 수 있고, 근거 칸에 전부 나열한다.
- **요구사항 2절의 모든 실패 케이스가 정확히 하나의 ER-에 나타난다.** 실패 케이스 없는 ER-는 검증·참조·동시성 유형뿐이다.
- 유형은 INV / ST / 검증 / 참조 / 동시성. INV·ST는 실패 케이스에서 따라 나온다. 검증은 요청 형식·제약 위반. 참조는 참조 개념의 ID가 상류에 없음(3-3에서 "검증 FR"로 지정된 경우만). 동시성은 3-6 충돌 시 결과.
- HTTP 상태는 1-3 고정 매핑을 따른다. 같은 유형이 EP마다 다른 상태 코드를 쓰면 오류.
- **상태 변화**는 요구사항 실패 케이스의 "결과 상태"에서 온다. "없음"(롤백) 또는 "상태명"(커밋). 클라이언트의 재시도 판단에 필요하므로 계약에 남긴다. 상태명이 있는 ER-는 5-4 예외 규칙의 대상이다.
- 메시지는 사용자에게 보여도 되는 문장. 테이블, 컬럼, 예외명을 담지 않는다.
- 하나의 ER-가 여러 EP에서 쓰일 수 있다. 4-3 블록에서 발생 조건을 그 EP 기준으로 다시 쓴다.

예시
```
| ER-03 | INSUFFICIENT_STOCK | 409 | 재고가 부족합니다 | FR-PAY-02 / INSUFFICIENT_STOCK | INV (INV-03) | 없음 |
| ER-04 | ORDER_NOT_PAYABLE  | 409 | 결제할 수 없는 주문입니다 | FR-PAY-02 / ORDER_NOT_PAYABLE | ST (ST-01) | 없음 |
```

### 4-5. 계약 변경

1-3 "과제 기간 내 비호환 변경은 즉시 폐기". 변경은 DR로만 남긴다. 호환성 분류 표는 두지 않는다.

### 4-6. 완료 조건

- [ ] 4-1 에러 코드 체계가 결정되어 있고 근거 FR이 있다.
- [ ] 모든 EP가 정확히 하나의 근거 FR을 가진다.
- [ ] 행위자가 시스템이 아닌 모든 FR이 최소 하나의 EP를 가진다.
- [ ] 모든 EP의 소유 BC가 근거 FR의 진입 BC와 같다.
- [ ] 모든 EP의 권한이 요구사항 1-2 표와 일치한다.
- [ ] 모든 경로 리소스명이 소유 BC의 소유 개념이다.
- [ ] 모든 응답 필드의 출처가 소유 BC의 TB, `조합`, 또는 계산이다.
- [ ] 모든 요청 필드의 참조 개념이 ID만 받는다.
- [ ] 상태를 바꾸는 모든 명령 EP가 ST- 허용 전이를 명시한다.
- [ ] 요구사항 2절의 모든 실패 케이스가 정확히 하나의 ER-에 있다.
- [ ] 모든 ST-가 최소 하나의 ER-를 가진다.
- [ ] 3-6에서 충돌 시 결과가 실패인 모든 LK-가 ER-를 가진다.
- [ ] 모든 ER-의 HTTP 상태가 1-3 고정 매핑을 따른다.
- [ ] 모든 ER-의 상태 변화 칸이 요구사항 실패 케이스 결과 상태와 일치한다.
- [ ] 이 장에 금지어가 없다.

5장으로 인계되는 것
- 4-3 요청·응답 → Dto. 필드명·타입·NULL 여부 그대로. 코드가 계약을 바꾸면 안 되고, 바꿔야 하면 이 장을 먼저 고친다.
- 4-4 ER- → 도메인 예외와 `ApiControllerAdvice` 매핑. 코드에 있는 예외 중 ER-에 없는 것이 밖으로 나가면 오류.
- 1-3·4-1 공통 규약 → `ApiResponse`, `ApiControllerAdvice`, 페이징 처리. 한 곳에 구현하고 EP마다 반복하지 않는다.

## 5. 객체 (Level 3)

목적: **"앞 장의 결정이 코드에서 그대로 보이게 한다."**

대부분 코드가 곧 문서다. 이 장에 쓰는 것은 5-6 BC 간 호출 표뿐이고, 판단은 부록 A로 간다. 클래스 다이어그램은 그리지 않는다. 나머지는 코드가 지켜야 할 규칙이다.

### 5-1. 계층 규칙

| 계층 | 맡는 일 | 참조할 수 있는 것 | 참조하지 않는 것 |
|---|---|---|---|
| `interfaces.api.<bc>` | 요청 파싱, 응답 변환, HTTP 오류 매핑 | `application.<bc>` | `domain`, `infrastructure`, 다른 BC의 어떤 계층 |
| `application.<bc>` | FR 실행. 여러 domain Service를 조합 | `domain.<bc>`, `domain.<other>.Service` | `interfaces`, `infrastructure`, 다른 BC의 `Repository` |
| `domain.<bc>` | 상태·규칙, Repository 약속 | `domain.<bc>` 자신만 | `interfaces`, `application`, `infrastructure`, **다른 BC의 `domain`** |
| `infrastructure.<bc>` | Repository 약속의 JPA 구현 | `domain.<bc>` | `interfaces`, `application`, 업무 규칙 |

규칙
- `domain.<A>`는 `domain.<B>`를 import하지 않는다. Model, Service, Repository 전부. 다른 BC의 개념은 ID(원시 타입 또는 자기 BC가 정의한 VO)로만 든다. 2-1 참조 개념이 코드에서 이렇게 나타난다.
- `application.<A>.Facade`는 `domain.<B>.Service`를 부를 수 있다. 조회 메서드가 기본. 상태를 바꾸는 메서드는 2-4에 그 FR이 "다중 AG 변경"으로 명시된 경우에만.
- 다른 BC의 Model은 그 BC Service의 반환값으로만 받는다. Facade에서 값을 꺼내 자기 domain에 넘기고, `ProductModel` 자체를 `OrderService`나 `Order`의 파라미터로 넘기지 않는다.
- Facade 참조 방향은 2-3 컨텍스트 맵 방향과 같아야 한다. 맵에 없는 방향의 호출이 코드에 생기면 코드가 아니라 맵을 먼저 고친다.

### 5-2. 클래스 역할

| 클래스 | 계층 | 대응 | 규칙 |
|---|---|---|---|
| `XxxV1ApiSpec` | interfaces | 4-2 EP- 목록 | 메서드 하나 = EP 하나. 문서 주석에 EP-ID |
| `XxxV1Controller` | interfaces | 4-3 | 요청 Dto → Facade → Info → 응답 Dto. 분기 없음 |
| `XxxV1Dto` | interfaces | 4-3 요청·응답 | 필드명·타입·NULL은 4-3과 동일. Dto가 Model을 참조하지 않는다 |
| `ApiResponse` | interfaces | 1-3 응답 봉투 | 한 곳 |
| `ApiControllerAdvice` | interfaces | 4-4 ER- | 예외 → ER- 매핑. 여기 없는 예외가 밖으로 나가면 오류 |
| `XxxFacade` | application | 요구사항 FR- | **public 메서드 하나 = FR 하나.** 주석에 FR-ID. 트랜잭션 경계 |
| `XxxInfo` | application | Facade 출력 | 다른 BC 조합 결과도 여기. Model을 밖으로 내보내지 않는 벽 |
| `XxxModel` | domain | 2-2 AG 루트 / 소유 개념 | JPA 엔티티. 거부 INV-를 여기서 지킨다 |
| `XxxService` | domain | Model 하나로 못 지키는 같은 BC 규칙 | 다른 BC를 모른다 |
| `XxxRepository` | domain | 저장 약속 | 의존성 역전 지점. 도메인 언어로 된 메서드만 |
| `XxxJpaRepository` | infrastructure | JPA | domain이 모른다 |
| `XxxRepositoryImpl` | infrastructure | `XxxRepository` 구현 | 저장·조회만 |

### 5-3. 애그리거트와 불변식을 코드로

- 2-2 AG 하나 = 루트 Model 하나. 포함 개념은 루트가 소유하는 컬렉션 또는 값 객체.
- **AG 밖에서 포함 개념을 직접 만들거나 바꾸지 않는다.** `OrderLine`을 생성하는 코드는 `Order` 안에만 있다.
- 거부(AG 내) INV-는 루트 Model의 메서드 안에서 검증하고 도메인 예외를 던진다. 예외 클래스 또는 코드에 INV-ID를 주석으로. Facade나 Controller에서 INV-를 검증하면 오류.
- 여러 Model에 걸친 같은 BC의 규칙은 `XxxService`. 여러 AG에 걸친 규칙(거부·FR 트랜잭션)은 Facade가 한 트랜잭션 안에서 각 AG의 메서드를 순차 호출한다. Facade가 그 INV를 직접 검증하지 않는다. 원자성이 지킨다.
- 요구사항 3-2의 전이는 루트 Model의 메서드로 표현한다. `pay()`, `fail(reason)`. 상태 필드에 setter를 두지 않는다. 3-2에 없는 전이 메서드를 만들지 않는다.
- Repository는 AG 단위로만 존재한다. 포함 개념의 Repository를 만들지 않는다.
- 이력(3-5)은 포함 개념과 같다. 루트 Model이 만들고, 루트 Repository가 저장한다. 이력 전용 Repository를 만들지 않는다.

### 5-4. 실패 표현

기본: **실패 케이스는 도메인 예외로 던진다.** 예외는 Facade 트랜잭션을 롤백시키고 `ApiControllerAdvice`가 ER-로 매핑한다. 요구사항 실패 케이스의 결과 상태가 "변화 없음" 또는 "유지"인 경우가 전부 여기 해당하며, 대부분의 실패가 이쪽이다.

예외: 결과 상태가 **다른 상태로의 전이**인 실패 케이스(3-4 "실패로 인한 전이", 4-4 상태 변화 칸이 상태명). 실패 상태가 저장되어야 하므로 기본 규칙(전부 롤백)으로는 안 된다.

처리 방법을 미리 정하지 않는다. 해당 FR마다 DR로 정한다. DR에 반드시 적는 것:
- 실패 상태를 어느 트랜잭션에서 저장하는가
- 그 시점에 같은 FR이 건드린 다른 AG의 변경은 롤백되어 있는가
- 클라이언트에 무엇이 나가는가 (ER-)

관련 ID: FR, 실패 케이스 이름, ST-, ER-.

실패를 결과값으로 반환하고 Facade나 Controller에서 분기하는 방식은 쓰지 않는다. 예외 경로가 하나로 모여야 "매핑 없는 예외가 밖으로 나가지 않는다"를 검사할 수 있다.

### 5-5. 트랜잭션

- 트랜잭션 경계는 Facade public 메서드. domain Service와 Repository에 트랜잭션을 걸지 않는다.
- 2-4에서 "즉시"인 FR: Facade 메서드 하나에 트랜잭션 하나.
- 2-4에서 "최종"인 FR: Facade 메서드 안에서 트랜잭션을 나눈다. 나누는 방법과 앞이 성공하고 뒤가 실패했을 때의 처리를 DR에. 2-4 근거와 일치해야 한다.
- 조회 FR의 Facade 메서드는 읽기 전용 트랜잭션.
- Facade 조합 조회(3-7-A)는 읽기 전용 트랜잭션 하나 안에서 여러 BC의 Service를 호출한다. 5-6에 기록.
- 3-6 LK-가 있는 FR: 낙관 락이면 버전 충돌 예외를 4-4 ER-로 매핑한다. 비관 락이면 잠금은 Repository 메서드에서 걸되 트랜잭션은 여전히 Facade.
- 5-4 예외에 해당하는 FR은 그 DR을 따른다.

### 5-6. BC 간 호출 표

Facade가 다른 BC의 Service를 부르는 모든 지점. 2-3 컨텍스트 맵의 코드 버전이며, 이 장에서 유일하게 문서에 쓰는 표다.

```
| 호출하는 Facade.메서드 | 근거 FR-ID | 호출받는 Service.메서드 | 목적 (조회/변경) | 2-3 행 |
```

규칙
- 이 표에 없는 BC 간 호출이 코드에 있으면 오류.
- 목적이 "변경"인 행은 2-4 다중 AG 근거와 DR이 있어야 한다.
- 이 표의 방향과 2-3의 상류·하류가 다르면 코드가 아니라 2-3을 먼저 고친다.

### 5-7. 테스트

요구사항 가이드 "추적성"이 요구하는 것을 코드에서 지킨다.

| 대상 | 테스트 | 이름 규칙 |
|---|---|---|
| FR 성공 경로 | Facade 통합 테스트 하나 이상 | `FR-XX` 포함 |
| FR 실패 케이스 각각 | 테스트 하나. 결과 상태(롤백/전이)까지 검증 | `FR-XX`와 실패 케이스 이름 포함 |
| 거부 INV- 각각 | Model 단위 테스트 | `INV-XX` 포함 |
| ST- 금지 전이 각각 | Model 단위 테스트. 3-2에 없는 전이가 거부되는지 | `ST-XX` 포함 |
| LK- 각각 | 동시 요청 테스트. INV가 유지되는지 | `LK-XX`, `INV-XX` 포함 |
| ER- 각각 | ApiSpec 수준에서 HTTP 상태와 코드 | `ER-XX` 포함 |

규칙
- 테스트가 없는 실패 케이스는 구현되지 않은 것으로 본다.
- 테스트 이름의 ID가 부록 B 매트릭스의 마지막 열이 된다.

### 5-8. 완료 조건

- [ ] `domain.<A>`에서 `domain.<B>`로의 import가 없다.
- [ ] `application.<A>`에서 `domain.<B>.Repository`로의 import가 없다.
- [ ] `interfaces`에서 `domain`, `infrastructure`로의 import가 없다.
- [ ] 모든 Facade public 메서드가 정확히 하나의 FR-ID를 주석으로 가지고, 모든 FR이 정확히 하나의 Facade public 메서드를 가진다.
- [ ] 모든 EP-가 ApiSpec 메서드 하나에 대응한다.
- [ ] 모든 거부(AG 내) INV-가 Model 메서드 안에서 검증된다.
- [ ] 요구사항 3-2의 모든 전이가 Model 메서드로 존재하고, 3-2에 없는 전이 메서드와 상태 setter가 없다.
- [ ] `ApiControllerAdvice`가 모든 ER-를 매핑하고, 매핑 없는 예외가 밖으로 나가지 않는다.
- [ ] 실패 상태를 저장하는 모든 FR에 5-4 DR이 있다.
- [ ] 5-6 표가 코드의 BC 간 호출과 일치한다.
- [ ] Repository가 AG 루트 단위로만 존재한다.
- [ ] 5-7의 모든 대상에 테스트가 있다.

## 부록 A. 설계 판단 기록과 열린 질문

문서 전체에서 유일하게 자유 서술이 허용되는 곳. 번호열은 하나다.

### A-1. 결정

```
| DR-ID | 장 | 관련 ID | 결정 | 버린 대안 | 이유 | 되돌릴 조건 | 요구사항 반영 |
```

- 관련 ID에는 설계 ID뿐 아니라 FR-, INV-, ASM-, CON-도 온다. 어떤 ASM이 뒤집히면 어느 DR을 재검토하는지 이 컬럼으로 찾는다.
- "되돌릴 조건"은 "~하면 이 결정을 재검토한다" 문형.
- 요구사항 반영은 0-4에 해당할 때 고친 절. 아니면 "없음".
- 뒤 장에서 앞 장을 고친 경우 DR 하나에 두 장을 관련 ID로 적는다. 피드백 표를 따로 두지 않는다.

반드시 DR이 있어야 하는 것
- 2장: 설계 도입 소유 개념, 거부(FR 트랜잭션) INV, 최종 일관성으로 재분류한 INV, 상태 전이 용어가 루트가 아닌 경우, 즉시 일관성 다중 AG
- 3장: 3NF 이탈, 계산값 컬럼, 스냅샷 컬럼, 복합 인덱스 순서, 동시성 방식, 비관 락 잠금 순서, 3-8 불일치 처리, DB 제품 고유 기능
- 4장: 1-3 기본값에서 벗어난 공통 규약, 하나의 FR에 여러 EP, 다른 BC 데이터를 조합하지 않고 필드를 뺀 경우, 계약 변경
- 5장: 다른 BC의 상태 변경 메서드 호출, 최종 일관성 트랜잭션 분리 방식, 5-4 예외 규칙 적용, Repository 외 새 인터페이스, 계층 규칙 이탈, 4장 계약을 코드가 바꿔야 했던 경우

### A-2. 열린 질문

```
| OQ-ID | 관련 ID | 질문 | 상태 (열림 / DR-XX로 닫힘) |
```

- 2-4 참여 BC 3개 이상 FR, 3-7-A Facade 조합 불가 조회, 0-5 처리 불가 요구사항은 자동으로 여기 온다.
- 답이 나오면 DR로 옮기고 상태를 바꾼다. 지우지 않는다.

## 부록 B. 추적성 매트릭스

요구사항 가이드가 요구하는 "FR × 설계 결정 × 테스트" 한 페이지. 새로 판단하지 않고 앞 장에서 기계적으로 모은다.

```
| FR-ID | 진입 BC (2-4) | 변경 AG (2-4) | 쓰는 TB (3-8) | EP (4-2) | ER (4-4, 실패 케이스별) | 테스트 (5-7) |
```

- 모든 FR이 한 줄. 조회 FR은 변경 AG·쓰는 TB가 "없음".
- 빈 칸은 누락이다. EP가 비면 4-2 누락, ER이 실패 케이스 수보다 적으면 4-4 누락, 테스트가 비면 5-7 누락.
- 이 표가 채워지면 설계 문서는 끝이다.

## 작업 순서

1. 요구사항 정합성 검사가 통과됐는지 확인한다. 안 됐으면 요구사항부터.
2. 1장: CON을 옮겨 적고, 1-2·1-3에서 벗어날 것이 있는지만 본다.
3. 2장: 용어집 단어를 전부 BC에 배치한다(2-1) → INV에 AG를 붙인다(2-2) → 참조 개념에서 맵을 그린다(2-3) → FR을 전부 매핑한다(2-4). 완료 조건.
4. 3장: 소유 매핑부터. 상태 컬럼과 동시성은 요구사항 3-2와 FR 비기능만 보고 채운다. 완료 조건.
5. 4장: 에러 코드 체계를 먼저 정한다. EP 목록 → 정의 → ER. 완료 조건.
6. 5장: 코드. 5-6 표와 DR만 문서에.
7. 부록 B를 채운다. 빈 칸이 있으면 해당 장으로 돌아간다.
