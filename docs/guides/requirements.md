# 요구사항 정의서 작성 가이드

## 이 문서의 목적

부트캠프 한 주 과제 수준에서 요구사항 정의서를 작성·검토할 때 따르는 구조와 판단 기준. 요구사항 정의서는 설계 문서와 별도로 두며, 이후 5개 층위의 설계(시스템/아키텍처, 모듈/컴포넌트, 객체/클래스, 데이터, 인터페이스/계약)에 근거를 공급하는 문서다.
이 가이드로 작성한 결과물은 docs/weekN/requirements.md에 둔다. 설계 문서는 같은 폴더의 design.md.

## 핵심 원칙

**요구사항 정의서는 원문을 설계 가능한 단위로 쪼개고, 원문에 없는 것은 없다고 명시하는 문서다.**

- 원문 FR에서 파생 가능한 것은 적는다.
- 원문에 뿌리가 없는 개념은 도입하지 않는다.
- 다루지 않는 것은 "범위 밖"에 명시적으로 적어 "빠뜨린 것"이 아니라 "판단한 것"으로 읽히게 한다.
- 이 문서는 "무엇이 참이어야 하는가"까지만 말한다. "어떻게 만들 것인가"(구현), "어떻게 확인할 것인가"(테스트 시나리오), "어떻게 약속할 것인가"(HTTP 코드, 에러 타입)는 설계 문서의 일이다.

### 파생과 창작의 경계

원문에 없는 것을 적어야 할 때 용어집(1-1)을 게이트로 쓴다.

| 상황 | 판정 | 처리 |
|---|---|---|
| 용어집이 그대로인데 기존 용어에 조건만 붙는다 (예: 충전 금액 > 0) | 파생 | FR 실패 케이스 / 불변식에 적는다 |
| 용어집이 그대로인데 원문에 없는 값이 들어온다 (예: 최소 충전 금액 1,000원) | 가정 | 1-4에 적는다 |
| 용어집에 새 단어가 생긴다 (예: 쿠폰, 배송, 환불) | 창작 | 도입하지 않는다. 필요하면 1-3 범위 밖에 적는다 |

규칙을 파다가 새 단어가 필요해지는 순간이 멈출 신호다. 그 지점을 1-4 가정으로 내려보낸다. 이 기준으로 안 갈리는 경우는 판단해서 1-4에 근거와 함께 적는다.

## 문서 구조

### 1. 머리

#### 1-1. 용어집
원문에 등장한 단어를 그대로 정의한다. 주문, 상품, 재고, 포인트 등.

- 여기서 정한 이름이 바운디드 컨텍스트와 클래스 이름의 후보가 된다.
- 생애주기를 갖는 용어는 정의에 "상태를 가짐 (→ 3-2)" 포인터만 둔다. 상태 정의 자체는 3-2에 둔다.

**왜:** 용어는 2층(컨텍스트 경계)과 3층(클래스 이름)에 직접 먹이를 준다. 상태 정의를 여기 두면 전이 그림과 분리되어 읽는 사람이 왔다갔다 해야 하므로 3-2에 모은다.

#### 1-2. 행위자
원문이 구분하는 만큼만 나눈다.

| 행위자 | 리소스별 권한 |
|---|---|
| 고객 | 상품 조회, 주문 생성, 포인트 충전/사용 |
| 관리자 (원문에 있을 때만) | 상품/재고 등록·수정 |
| 시스템 (원문에 있을 때만) | 배치, 스케줄, 외부 콜백 |

판단 기준:
1. 원문에 그 역할이 등장하는가. 등장하지 않으면 만들지 않는다.
2. 같은 리소스에 대해 권한이나 흐름이 다른가. 다르지 않으면 나눈 의미가 없다.
3. 사람이 아닌 트리거(스케줄러, 배치, 콜백)를 놓치지 않는다. 원문에 "매일", "자동으로", "일정 시간 후"가 있으면 시스템 행위자다.

#### 1-3. 범위 밖
원문에 없어서 다루지 않는 개념 + 한 줄 이유.

| 개념 | 이유 |
|---|---|
| 배송 | 원문에 언급 없음 |
| 환불 / 취소 | 원문에 언급 없음 |

#### 1-4. 가정 / 해석
원문이 모호해서 해석이 필요했던 지점과, 어떻게 해석했는지.

| ID | 원문의 모호한 지점 | 해석 | 근거 / 영향 |
|---|---|---|---|
| ASM-01 | "주문하면 결제된다" — 한 단계인지 두 단계인지 불명 | 두 단계로 본다 (PENDING → PAID) | 결제 실패 시 주문 흔적을 남겨야 한다는 문장이 있음 → 3-2 |
| ASM-02 | 충전 금액 하한 없음 | 하한을 두지 않고 > 0만 요구 | 원문에 값 없음 → 값 도입은 창작 |

규칙:
- 어느 FR 필드에도 안 들어가는 문장, 파생/창작 경계에서 판단이 필요했던 것은 전부 여기로 온다.
- 가정이 영향을 주는 FR·INV·상태 전이 ID를 "근거 / 영향"에 적는다.
- 가정이 뒤집히면 어디를 고쳐야 하는지 이 표만 보고 알 수 있어야 한다.

**왜:** 부트캠프 원문은 보통 몇 문장이라 실제로는 이 섹션이 가장 두꺼워진다. 가정을 FR 안에 숨기면 나중에 "원문이 그랬나, 내가 정했나"를 구분할 수 없다.

### 2. 기능 요구사항

원문을 문장 단위로 쪼개 하나씩 항목화한다.

| 필드 | 내용 |
|---|---|
| ID | `FR-ORDER-01` 식. 도메인 접두어 필수 |
| 행위자 | 1-2에서 정의한 것 중 하나 |
| 사전 조건 | 이 행위가 가능하려면 참이어야 하는 것 |
| 행위 | 한 문장. "~하면 ~된다" |
| 결과 | 아래 셋 중 해당하는 것. 상태 변화 / 출력 / 부작용 |
| 실패 케이스 | 조건 / 결과 상태 / 도메인 이름 (예: `INSUFFICIENT_STOCK`) |
| 지켜야 할 불변식 | INV ID 나열 |
| 비기능 (선택) | 원문·과제 조건에 명시된 것만. 예: "동시 요청 하에서도 INV-03 유지", "응답 1초 이내" |

결과 필드:
- **상태 변화** — 어떤 데이터가 어떻게 바뀌나. 쓰기 행위.
- **출력** — 무엇을 돌려주나, 정렬·필터·기간 기준은 무엇인가. 조회 행위. (예: 최근 3일 판매량 상위 5개)
- **부작용** — 외부 전송, 이벤트 발행, 알림. 부작용 실패가 본 행위 실패로 이어지는지는 원문에 없으면 1-4 가정으로 적는다.

규칙:
- 실패 케이스는 원문에 없어도 사전 조건 위반에서 파생 가능하므로 빠짐없이 적는다. 원문은 보통 성공 경로만 적고, 설계 품질은 실패 경로에서 갈린다.
- 실패 케이스마다 **결과 상태**를 적는다. 대상 용어가 3-2 상태 전이를 가지면 어느 상태로 가는지(또는 유지인지), 아니면 "변화 없음". 같은 FR의 실패 케이스라도 결과 상태가 다를 수 있다.
- 실패 케이스에 HTTP 상태 코드, ErrorType enum을 적지 않는다. 도메인 이름까지만 적는다. HTTP 매핑은 5층 결정이며 설계 문서에서 "도메인 이름 → HTTP 코드" 표로 만든다.
- 클라이언트가 실패 케이스를 서로 구분해야 하는지가 중요하면 실패 케이스에 그 사실을 적는다. 이것이 설계 문서에서 "범용 ErrorType 유지 vs 도메인별 코드 추가"를 결정하는 근거가 된다.
- 비기능은 원문에 "동시에", "N초 이내", "장애 시에도" 같은 문장이 있을 때만 그 행위의 FR에 붙인다. 4번 제약과 같은 게이트다. 언급 없는 비기능(성능, 가용성, 보안 등)은 1-3 범위 밖에 "해당 주차 과제 조건에 없음"으로 적는다. 어떻게 보장할지(락, 재시도, 큐)는 적지 않는다.

### 3. 도메인 규칙 / 불변식

#### 3-1. 불변식

| ID | 불변식 | 대상 |
|---|---|---|
| INV-01 | 포인트 잔액 ≥ 0 | 포인트 |
| INV-02 | 차감된 포인트 = 결제 금액 | 포인트, 주문 |
| INV-03 | 재고 ≥ 0 | 재고 |
| INV-04 | 주문 금액 = 항목 금액 합 | 주문 |

규칙:
- "대상"은 반드시 1-1 용어집의 단어만 쓴다.
- 불변식 표는 FR을 참조하지 않는다. 관계는 FR → INV 한 방향으로만 흐른다.
- 불변식은 어느 시점에 봐도 참인 것이다. 특정 행위 직후에만 참인 것은 사후조건이며 FR의 결과 필드에 속한다.

**왜:**
- 불변식은 행위가 아니라 상태(용어)에 붙는 성질이다. 하나의 불변식은 여러 FR에 걸리고(잔액 ≥ 0은 결제·충전·취소 전부), 하나의 FR은 여러 불변식을 건드린다. 다대다 관계를 양쪽에 두면 한쪽을 고칠 때마다 두 곳을 고쳐야 한다. FR은 유스케이스라서 "이 행위가 어떤 규칙을 건드리는가"를 자기가 아는 게 자연스럽고, 불변식은 FR을 모르는 게 맞다.

#### 3-2. 상태 전이

생애주기를 갖는 용어에 대해 허용된 상태의 목록·정의와 허용된 전이만 적는다.

```
주문 상태
  PENDING   생성됨. 재고·포인트 미차감. FR-PAY-02 가능.
  PAID      결제 완료. 재고·포인트 차감 완료. 더 이상 전이 없음.
  FAILED    결제 실패. 재고·포인트 미차감. 더 이상 전이 없음.

전이
  PENDING ──(FR-PAY-02 성공)──────────────────▶ PAID
  PENDING ──(FR-PAY-02 실패: INSUFFICIENT_STOCK)──▶ FAILED
  PENDING ──(FR-PAY-02 실패: INSUFFICIENT_POINT)──▶ PENDING (유지, 재시도 가능)  ← ASM-03
```

규칙:
- 상태 개수도 원문 기준이다. 원문이 두 단계를 구분할 때만 중간 상태가 파생된다. "주문하면 결제된다"가 한 문장이면 중간 상태는 창작이다.
- 전이마다 트리거 FR을 붙인다. 실패로 인한 전이는 실패 케이스의 도메인 이름까지 붙인다. 그림에 없는 전이는 금지된 전이다.
- 어떤 실패가 종료 상태로 가고 어떤 실패가 현재 상태를 유지하는지는 원문에 없으면 1-4 가정이다. 위 예시의 ASM-03처럼 가정 ID를 붙인다.
- 상태가 하나뿐인 용어는 3-2에 올리지 않는다.

**왜:** 상태 전이는 3층(상태를 어디에 둘지)과 4층(컬럼, 일관성)으로 바로 이어진다. 어떤 용어가 불변식의 대상이면서 상태 전이도 갖는지는 설계에서 애그리거트 후보를 고를 근거가 되지만, 그 결론은 설계 문서에서 내린다.

### 4. 제약

밖에서 주어진 조건. 요구가 아니라 설계 선택지를 좁히는 울타리.

| ID | 제약 | 근거 |
|---|---|---|
| CON-01 | Java / Spring Boot | 과제 조건 |
| CON-02 | 단일 RDB | 과제 조건 |
| CON-03 | 외부 결제 없음, 포인트만 결제 수단 | 원문 범위 |

## 정합성 검사

문서 작성 후 다음을 확인한다.

- 불변식의 대상이나 상태 전이의 주어로 나오는데 용어집에 없는 단어 → 용어집 누락
- 용어집에는 있는데 어떤 FR·불변식·상태 전이에도 안 나오는 단어 → 범위 밖으로 갔어야 할 단어
- FR의 행위자가 1-2에 없음 → 행위자 누락 또는 창작
- FR의 "지켜야 할 불변식"이 3-1에 없음 → 불변식 누락
- 3-2의 전이에 트리거 FR이 없음 → FR 누락 또는 전이 창작
- FR 실패 케이스의 결과 상태가 3-2에 없거나, 그 전이가 그림에 없음 → 상태 누락 또는 전이 누락
- 원문에 없는 값·해석이 FR·INV·3-2에 들어 있는데 1-4에 대응 가정이 없음 → 가정 누락

## 설계 층으로의 연결

| 섹션 | 먹이를 주는 층 |
|---|---|
| 1-1 용어집 | 2층 컨텍스트 경계, 3층 클래스 이름 |
| 1-2 행위자 | 5층 API 진입점, 인가 규약 |
| 1-4 가정 | 설계 결정의 전제. 뒤집힐 때 영향 범위 추적 |
| 2 FR 행위·결과 | 2층 유스케이스 단위, 4층 스키마 |
| 2 FR 실패 케이스 | 5층 에러 규약, 3층 검증 위치 |
| 2 FR 비기능 | 4층 동시성 제어 범위, 1층 구조 선택 |
| 3-1 불변식 | 4층 일관성 경계, 1층 덩어리 분리 근거 |
| 3-2 상태 전이 | 3층 상태 위치, 4층 컬럼 |
| 4 제약 | 1층 선택지 제한 |

## 추적성

ID 하나로 통일한다.
- 설계 문서: 각 결정 옆에 "관련: FR-…, INV-…, ASM-…"
- 코드: 테스트 이름에 FR/INV ID, 실패 케이스 도메인 이름
- 마지막에 한 페이지 매트릭스: FR × 설계 결정 × 테스트

## 작업 순서

1. 원문을 문장 단위로 쪼개 FR ID를 붙인다.
2. 어느 필드에도 안 들어가는 문장, 파생/창작 경계에 걸리는 것이 나오면 1-4 가정에 ID를 붙여 적는다.
3. FR을 다 적고 나면 불변식과 상태 전이가 보인다. 그때 3을 채운다.
4. 정합성 검사를 돌린다.
