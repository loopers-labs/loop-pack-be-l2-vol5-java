# 주간 구매 랭킹 결정 기록

주간 구매 랭킹 설계에서 선택한 사항의 맥락, 대안, 근거와 영향을 기록한다. 계약과 규칙은 [주간 구매 랭킹](weekly-ranking.md), Spring Batch 구현은 [주간 랭킹 Job 설계](../../../apps/commerce-batch/docs/weekly-ranking-job.md)를 따른다. 과제가 정한 계약을 그대로 따른 결정과, 과제가 맡긴 부분을 고른 결정을 함께 적는다.

## 결정 기록

### R-01. 기간은 UTC 월요일로 자른다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 저장된 순간은 UTC이고 앱은 `Asia/Seoul`로 동작한다. 지금까지는 순간과 길이만 비교해서 달력을 어느 시간대로 자를지 정할 일이 없었다. 과제 계약은 기간을 "UTC 월요일 00:00부터 다음 월요일 00:00 전까지"로 정했다. |
| 선택한 안 | 과제 계약대로 UTC 월요일로 자른다. 시간대는 코드 한 곳의 값으로 둔다. |
| 비교 대상 | `Asia/Seoul` 월요일로 자른다. |
| 선택 근거 | 계약과 같고, 저장된 값과 바로 비교할 수 있다. 실제 한국 서비스라면 `Asia/Seoul`을 골랐겠지만, 이번 과제의 학습 목표는 배치의 고정과 재실행이다. |
| 영향 | 한국 시간 월요일 00:00~09:00의 구매는 지난주에 들어간다. API 계약에 적는다. JVM 기본 시간대에 기대지 않으므로 테스트가 실행 환경의 시간대와 무관하게 같은 기간을 계산한다. |

### R-02. 점수와 동점 규칙은 과제 계약대로 둔다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 점수는 구매 수량의 합이라 작은 정수가 많고 동점이 잦다. 상품 ID는 판매와 상관없는 기준이라 동점일 때 오래된 상품이 늘 앞에 선다. |
| 선택한 안 | 점수 내림차순, 동점이면 상품 ID 오름차순만 쓴다. |
| 비교 대상 | 점수 → 좋아요 수 → 상품 ID 순으로 정렬한다. |
| 선택 근거 | 과제 계약이 동점 규칙까지 정했다. 좋아요는 취소하면 지워지는 값이라, 쓰려면 회차를 계산할 때 함께 고정하고 배치가 `likes`를 읽는 경계도 새로 생긴다. |
| 영향 | 좋아요 2차 기준은 필요해지면 넣을 확장으로 남긴다. |

### R-03. 계산 순위는 정렬 순서의 위치로 매긴다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 동점 상품에 다른 번호를 줄지 같은 번호를 줄지 정해야 했다. 계약은 순서를 정했지만 동점의 번호는 정하지 않았다. |
| 선택한 안 | 점수 내림차순, 상품 ID 오름차순 순서의 위치를 순위로 쓴다(1, 2, 3). |
| 비교 대상 | 동점이면 같은 번호를 준다(1, 1, 3). |
| 선택 근거 | 쇼핑몰이나 음원 차트 같은 상품 목록은 보통 겹치지 않는 번호를 쓴다. 같은 번호를 주면 API 응답의 간격이 동점 때문인지 제외된 상품 때문인지 구분되지 않는다. 순위가 1부터 N까지 이어지는지 확인하기도 쉽다. |
| 영향 | 동점이 너무 많아 공동 순위가 필요해지면 정책을 다시 정한다. |

### R-04. API는 계산 순위를 그대로 주고 화면 번호는 클라이언트가 정한다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 삭제된 상품을 빼면 1위, 3위처럼 간격이 생긴다. 보이는 상품끼리 1, 2, 3으로 다시 매기는 안을 먼저 골랐으나, 계약은 "저장된 계산 순위는 유지"다. |
| 선택한 안 | API는 계산 순위를 그대로 준다. 목록은 정렬하고 거르고 자른 상태로 주므로, 위치로 번호를 붙일지는 클라이언트가 정한다. |
| 비교 대상 | API가 표시 순위를 다시 매긴다. 계산 순위와 표시 순위를 함께 준다. |
| 선택 근거 | 계약과 같고, 화면 번호는 화면의 영역이다. 이번 API는 `limit`만 있고 페이지 넘김이 없어 응답 하나 안에서 위치 번호가 어긋나지 않는다. |
| 영향 | 페이지 넘김처럼 순위에 대한 요구가 늘면 다시 정한다. |

### R-05. 공개본이 없으면 그 사실을 그대로 알린다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 계산 전이거나 실패한 기간을 요청받을 수 있다. 처음에는 "계산 중이면 지난주를 보여 준다"는 방식을 떠올렸다. |
| 선택한 안 | 요청한 기간에 완성된 회차가 없으면 `NOT_PUBLISHED`와 빈 목록, 구매가 없던 완성 회차면 `PUBLISHED`와 빈 목록을 준다. 둘 다 `200 OK`다. |
| 비교 대상 | 지난주 결과를 기간을 밝혀 대신 준다. 공개 전을 오류로 응답한다. |
| 선택 근거 | 클라이언트가 `periodStart`로 기간을 직접 고르므로, 지난주가 필요하면 지난주를 요청하면 된다. 과제도 다른 기간을 대신 주지 말라고 했다. 공개 전은 오류가 아니라 상태다. |
| 영향 | "아직 모름"과 "확인해 보니 0건"이 응답으로 구분된다. |

### R-06. 테이블은 쓰는 앱이 주인이고, 다른 앱은 정한 테이블만 읽는다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨. 기존의 "`commerce-api`와 `commerce-streamer`는 서로의 테이블을 읽거나 쓰지 않는다"를 바꾼다. |
| 맥락 | 배치가 streamer의 구매 활동을 읽고, API가 배치의 결과를 읽어야 한다. |
| 선택한 안 | 쓰는 앱이 주인이다. 읽기는 시스템 개요와 이 기능 문서에 적은 테이블만 허용한다. 배치는 `product_purchase_activity`를, API는 `weekly_ranking_revisions`와 `weekly_ranking_scores`를 읽는다. |
| 비교 대상 | 배치가 결과를 API 소유 테이블로 복사하거나 메시지로 보낸다. |
| 선택 근거 | 같은 DB를 쓰는 지금 구조에서 가장 단순하고, 쓰는 주체가 하나라 데이터가 엉키지 않는다. 복사나 전달을 두면 그 실패 처리가 또 생긴다. |
| 영향 | 읽는 앱이 테이블 구조에 묶이므로 구조를 바꿀 때 읽는 앱의 매핑도 확인한다. |

### R-07. 회차는 `(기간, revision)`으로 식별한다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-18 다시 정함) |
| 맥락 | 과제 예시의 `weekly-20260817-r1`은 종류, 기간, revision을 한 문자열에 담아 `periodStart`와 정보가 겹친다. 잡 파라미터는 잡이 시작되기 전에 정해져야 한다. |
| 선택한 안 | 회차 정보와 점수 모두 `(period_start, revision)`을 키로 쓴다. 숫자 ID를 따로 두지 않는다. 잡 식별 파라미터도 `periodStart`, `revision`이다. |
| 비교 대상 | snapshot 정보에 숫자 ID를 두고 하위 테이블을 그 ID로 잇는다(이전 안). 사람이 읽는 문자열 ID를 쓴다. |
| 선택 근거 | 하위 테이블이 점수 하나뿐이라 짧은 숫자 키로 이을 이유가 작다. 키가 잡 파라미터와 같아 잡 시작 전에 알 수 있고, 같은 정보를 두 번 들지 않는다. 기준일자에 버전을 더한 모양은 현업의 흔한 형태다. |
| 영향 | API 응답에서 `snapshotId`를 빼고 `revision`을 준다. 파라미터의 모양은 R-24를 따른다. |

### R-08. 점수는 한 문장으로 넣어 그 결과를 고정본으로 쓴다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | 원본 구매 활동은 계산 중에도 늘어난다. 원본을 묶음으로 나눠 읽으면 재시작할 때 원본을 다시 읽게 되어, 앞 묶음과 뒤 묶음이 서로 다른 시점의 데이터로 계산된다. MySQL 기본 격리 수준 `REPEATABLE READ`에서 `INSERT ... SELECT`는 읽는 쪽에도 공유 잠금과 gap 잠금을 걸어 streamer의 저장을 막는다. |
| 선택한 안 | 그 기간의 구매 활동을 `GROUP BY product_id`로 묶어 점수를 내고, `INSERT ... SELECT` 한 문장으로 점수 테이블에 넣는다. 순위는 비워 두고 고정한 점수로 따로 매긴다(R-12, R-29). 트랜잭션은 `READ_COMMITTED`라 원본을 잠그지 않는다. 원본에 `confirmed_at` 인덱스를 추가한다. |
| 비교 대상 | 점수와 순위를 `ROW_NUMBER()`까지 한 문장으로 넣고 같은 트랜잭션에서 공개까지 끝낸다(이전 안). 원본을 snapshot 입력 테이블로 먼저 복사하고 그 입력으로 나눠 계산한다(처음 안). 원본을 chunk로 읽고, 재시작 때 늦은 구매가 섞이는 것을 받아들인다. |
| 선택 근거 | 한 문장은 시작 순간의 커밋된 데이터만 일관되게 읽으므로, 넣은 점수가 곧 그 순간의 고정본이다. 다음 단계는 원본이 아니라 이 점수만 읽으므로 나눠 처리하고 다시 시작해도 같은 입력으로 이어 간다. 로컬에서 구매 100만 건, 상품 1,000개를 0.3초 안에 넣어, 점수를 나눠 계산할 이득은 없었다. |
| 영향 | 점수 고정이 실패하면 남은 것이 없어, 다시 실행할 때 그 순간의 원본을 읽는다. 데이터가 아주 많아 이 트랜잭션이 너무 길어지면 입력을 따로 고정해 나눠 계산하는 구조로 바꾼다. |

### R-09. 이미 있는 회차는 상태에 따라 이어 가거나 그대로 둔다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | 세 단계로 나뉘면 실패 지점에 따라 다시 실행이 만나는 회차의 상태가 다르다. 커밋 직후 프로세스가 죽어 실행 기록만 정리한 경우처럼, 이미 끝난 단계를 다시 만나는 Step도 생긴다. |
| 선택한 안 | 각 Step이 회차 상태를 보고 할 일을 정한다. 점수 고정은 `CALCULATING`이면 고정한 점수를 그대로 쓰고, `COMPLETED`면 아무것도 쓰지 않으며, `CANCELLED`면 실패한다. 순위 매기기는 `CALCULATING`인 회차의 순위만 비우고 그 점수만 읽으므로, 다른 상태에서는 아무것도 쓰지 않는다. 공개는 `CALCULATING`이면 완성하고, `COMPLETED`면 아무것도 쓰지 않으며, `CANCELLED`면 실패한다. |
| 비교 대상 | Job 흐름에 분기(decider)를 두어 `COMPLETED`면 Job을 끝낸다. 각 Step이 시작할 때 `CALCULATING`이 아니면 실패시킨다. 한 트랜잭션 계산이라 `COMPLETED`면 아무것도 쓰지 않고 `CANCELLED`면 실패하는 확인 하나만 둔다(이전 안). |
| 선택 근거 | 분기를 둬도 각 Step은 결국 자기 상태를 확인해야 한다. 시작할 때 무조건 실패시키면 "커밋 뒤 실행 기록만 남은 경우, 정리하고 다시 실행하면 완료로 끝난다"는 운영 절차가 깨진다. 순위 Step은 읽는 조건 하나로 같은 효과를 낸다. |
| 영향 | 완성된 회차는 다시 실행해도 점수와 순위 행이 한 번도 바뀌지 않는다. 과제의 "이미 있는 snapshot의 기간·입력·revision이 다르면 덮어쓰지 않고 충돌로 처리"는 "이미 있는 회차의 점수는 다시 넣지 않는다"로 지킨다. |

### R-10. checksum은 결과의 업무 값만 정해진 모양으로 이어 SHA-256으로 만든다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨. 2026-11-18에 입력 checksum을 뺐다. |
| 맥락 | 같은 결과인지 실행과 환경에 상관없이 확인할 값이 필요하다. 과제는 필드 사이 TAB, 줄 끝 LF처럼 규칙을 고정하라고 했다. |
| 선택한 안 | 결과는 순위 순으로 `productId TAB score TAB rank`를 LF로 이어 SHA-256을 계산하고 회차 정보에 남긴다. 앱에서 줄 단위로 계산한다. |
| 비교 대상 | 건수와 합계만 비교한다. DB의 `CRC32`를 XOR로 합친다. 입력 checksum도 둔다(이전 안). |
| 선택 근거 | 합계는 두 상품의 점수가 서로 바뀌면 못 잡는다. CRC32는 32비트라 약하고, XOR는 같은 줄 두 개가 서로 지워진다. SHA-256은 자바와 MySQL에 기본으로 있다. MySQL `GROUP_CONCAT`은 기본 1024바이트에서 오류 없이 잘리고 경고만 남긴다. 원본을 복사하지 않으므로 입력 checksum은 다시 셀 대상이 없다. |
| 영향 | checksum은 같은지만 알려 주므로 기대 점수와 순위도 함께 확인한다. |

### R-11. 잘못된 입력은 점수를 넣기 전에 원본에서 확인해 실패시킨다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-18 다시 정함) |
| 맥락 | 수량이 양수가 아닌 행처럼 계약에 어긋난 입력을 만날 수 있다. 고정 입력 테이블이 없어 그 테이블의 DB 제약으로 막는 이전 방식을 쓸 수 없다. |
| 선택한 안 | 같은 트랜잭션에서 점수를 넣기 전에 그 기간 원본에 수량 0 이하인 행이 있는지 보고, 있으면 실패한다. 결과 쪽은 점수 0 초과 CHECK와 회차 안 순위 유일 제약이 막는다. |
| 비교 대상 | 건너뛰고 계속한다. 점수 합계가 0 이하인지만 본다. 확인하지 않고 streamer의 검사를 믿는다. snapshot 입력의 DB 제약으로 복사 전체를 취소한다(이전 안). |
| 선택 근거 | 입력은 streamer가 검사해 저장한 내부 사실이라 이상값은 앞 단계 결함의 신호다. 건너뛰면 잡은 완료로 끝나고 원인이 묻힌다. 합계 검사는 정상 행 사이에 섞인 0을 놓친다. 확인 한 문장과 제약 두 개로 끝난다. |
| 영향 | `READ_COMMITTED`라 확인과 넣기 사이에 잘못된 행이 새로 들어오면 놓친다. 이 한계를 문서에 적는다. |

### R-12. 회차 계산은 점수 고정, 순위 매기기, 공개의 세 Step이다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | 운영 Job이 Tasklet 하나면 chunk, reader 위치 저장, 재시작 같은 Spring Batch 기능은 실제 구현에 없고 학습용 테스트에만 남는다. 과제 §3·§4·§6도 세 Step, chunk 계산, 실패한 곳부터 이어서 끝내는 재시작을 Job에 두라고 했다. |
| 선택한 안 | 1번 점수 고정은 Tasklet, 한 트랜잭션이다(R-08). 2번 순위 매기기는 chunk Step으로, 고정한 점수를 읽어 순위를 쓰고 묶음마다 커밋한다(R-29). 3번 공개는 Tasklet, 한 트랜잭션으로 순위를 확인하고 checksum을 채워 완성한다(R-14). 다시 실행하면 완료한 Step은 건너뛰고, 2번은 순위를 처음부터 다시 매긴다(R-30). |
| 비교 대상 | 확인부터 회차 정보까지 Tasklet Step 하나, 트랜잭션 하나로 한다(이전 안). 원본을 snapshot 입력으로 복사하고 점수를 chunk로 계산한다(처음 안). |
| 선택 근거 | 점수를 먼저 고정하면 다음 단계는 그 점수만 읽으므로, 나눠 처리하고 몇 번을 다시 해도 같은 입력으로 계산한다. snapshot 입력 테이블 없이 세 Step과 chunk를 운영 Job에 둘 수 있다. |
| 영향 | 점수만 있고 순위는 아직인 중간 상태가 생긴다. 회차에 `CALCULATING` 상태를 두고 조회는 `COMPLETED`만 본다(R-13). 학습용 테스트 Job은 두지 않는다(R-27). |

### R-13. 공개본은 그 기간에서 가장 최근에 완성된 회차다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | 과제는 snapshot 정보에 상태를 두되 이름은 자유롭게 정하라고 했고, 공개본을 읽는 방법으로 "한 query에서 pointer를 join"을 예로 들었다. 회차가 여러 개면 어느 회차를 보여 줄지 정해야 한다. 세 Step으로 나누면 점수는 고정됐지만 순위는 덜 매겨진 회차도 생긴다. |
| 선택한 안 | 상태는 `CALCULATING`(점수를 고정하고 순위를 매기는 중), `COMPLETED`(완성), `CANCELLED`(운영자가 닫음) 셋이다. 계산 중에는 계산 순위와 결과 checksum을 비워 둔다. 공개 표시를 따로 두지 않고, 그 기간에서 `COMPLETED`인 회차 중 번호가 가장 큰 회차를 공개본으로 본다. |
| 비교 대상 | 상태는 그대로 두고 결과 checksum이 비어 있으면 계산 중으로 본다. 순위를 별도 테이블에 쓴다. 상태를 `COMPLETED`, `CANCELLED` 둘만 둔다(이전 안). 기간마다 공개 pointer를 두고 조건부로 바꾼다(처음 안). |
| 선택 근거 | 계산 중임을 상태로 드러내야 닫기와 동시 실행 규칙이 그 상태에 기댈 수 있다. checksum이 비었는지로 보면 규칙이 조건 속에 숨는다. 순위 유일 제약은 NULL끼리 겹친다고 보지 않으므로 순위를 비워 둔 채로도 제약을 그대로 둘 수 있다. pointer는 과제의 예시이고, 요구는 완성본만 보이고 계산 중인 값이 섞이지 않는 것이다. |
| 영향 | 조회는 `COMPLETED`만 읽는다. 이전 회차로 되돌리려면 최근 회차를 `CANCELLED`로 닫는다(R-21). |

### R-14. 공개 전에 순위가 빠짐없이 매겨졌는지 확인한다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | 과제는 모든 상품 점수와 예상 상품 수를 확인한 뒤 순위를 만들라고 했다. 순위를 묶음으로 나눠 쓰므로, 공개 전에 모든 점수에 순위가 들어갔는지 봐야 한다. 점수를 원본과 다시 대조하려면 원본을 한 번 더 읽어야 하는데, `READ_COMMITTED`에서는 그사이 들어온 구매 때문에 숫자가 달라진다. |
| 선택한 안 | 공개 트랜잭션에서 고정한 점수마다 계산 순위가 있고, 순위가 1부터 상품 수까지 빠짐없이 이어지는지 확인한다. 어기면 실패하고 회차는 `CALCULATING`으로 남는다. 넣기 전 원본 확인(R-11), 점수 양수 CHECK, 회차 안 순위 유일 제약은 그대로 둔다. |
| 비교 대상 | 점수를 원본과 상품별로 다시 대조한다. 확인 없이 DB 제약에만 맡긴다(이전 안). |
| 선택 근거 | 점수는 고정본이라 그대로 믿고, 나눠 쓴 순위만 빠짐과 끊김을 본다. 원본과 다시 대조하면 고정한 뒤 들어온 구매 때문에 거짓 실패가 난다. |
| 영향 | 계산 SQL 자체의 오류는 테스트의 기대 점수, 순위, checksum으로 잡는다. |

### R-16. 같은 기간에는 계산 중인 회차를 하나만 둔다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | 같은 식별값의 실행은 배치 실행 기록이 막지만, 같은 기간의 다른 회차는 서로 다른 작업이라 동시에 돌 수 있다. 과제는 같은 기간의 계산을 하나씩 실행하라고 했다. 점수 고정이 커밋되면 `CALCULATING` 회차가 다른 실행에 보이므로, 회차 번호 규칙만으로는 회차 2가 순위를 매기는 동안 회차 3이 시작될 수 있다. |

| 영향 | 끝나지 않는 계산 중 회차는 그 기간의 다음 계산을 막는다. 운영자가 닫아 풀어 준다(R-21). |

### R-19. 테스트는 앱마다 독립으로 두고, 여러 앱 연결은 로컬 검증 도구로 확인한다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | 과제는 정상 실행과 재시작을 비교하고, 주문 확정부터 랭킹 API까지 한 연결 테스트로 확인하라고 했다. 6·7주차는 각 앱 테스트를 따로 두고, 앱을 잇는 연결은 실제 앱을 띄운 로컬 검증 도구로 확인했다. |
| 선택한 안 | 정상 실행과 실패 뒤 다시 실행은 각각 깨끗한 DB의 독립 테스트에서 같은 기대 checksum과 기대 점수·순위로 확인한다. 배치는 DB 결과로, API는 같은 모양의 fixture로 각 앱에서 확인한다. 여러 앱 연결은 실제 앱을 띄우고 로컬 검증 도구로 확인해 결과를 기록한다. |
| 비교 대상 | 한 테스트에서 같은 입력을 다른 기간에 복사해 정상 실행과 직접 비교한다. 세 앱을 Gradle 테스트 하나로 묶는다. 연결 확인용 검증 프로필을 두고 그 프로필에서만 시계를 옮기고 실패를 주입한다(이전 안). |
| 선택 근거 | 테스트끼리 독립적인 편이 실패 원인을 좁히기 쉽다. 두 테스트가 같은 기대 checksum과 같으면 서로도 같다. 세 앱을 한 테스트 실행 환경에 올리면 설정이 무겁고 "두 앱을 한 테스트에 묶지 않는다"는 기존 규칙을 바꿔야 한다. |
| 영향 | 연결 확인은 실제 시계로 돌린다. 도구가 실행하는 주의 UTC 월요일을 기간으로 쓰고, 주가 끝나기 30분 전부터는 주문이 다음 주로 갈라질 수 있어 실행하지 않는다. 앱에 연결 확인만을 위한 프로필이나 코드를 두지 않기 위해서다. 정확한 경계 순간은 각 앱 테스트의 고정 시계로 확인한다. 연결 확인에는 "점수 고정 → 순위를 매기다 실패 → 늦은 구매 도착 → 같은 회차를 다시 실행하면 고정한 점수로 순위를 처음부터 다시 매겨 끝남 → 다음 회차에 늦은 구매 포함" 흐름을 넣어, 과제 7절의 "고정 뒤 늦은 구매가 도착해도 현재 입력·재시작 결과는 바뀌지 않는다"를 실제 이벤트로 확인한다. 실패는 도구가 chunk 크기 2로 실행하고, 격리 DB에 3위를 쓰는 순간 실패하는 트리거를 잠깐 걸어 만든다. 연결 확인은 `check`에 들어가지 않는다. |

| 상태 | 선택됨 |
| 맥락 | `commerce-batch`의 local 프로필은 공통 JPA 설정의 `ddl-auto: create`를 그대로 받는다. 다른 두 앱은 `validate`로 덮어쓴다. 배치가 테이블을 엔티티로 매핑하는 순간, 로컬에서 배치를 띄울 때마다 그 테이블을 지우고 다시 만든다. 읽기 전용으로 매핑한 streamer의 구매 활동 테이블도 예외가 아니다. |
| 선택한 안 | 새 테이블 두 개와 원본 인덱스는 `init.sql`과 기존 DB용 전환 SQL로 만든다. 배치 local을 `validate`로 바꾸고 test는 `create`를 유지한다. 각 앱은 읽고 쓰는 테이블을 엔티티로 매핑하고, 남의 테이블은 읽기 전용으로 둔다. |
| 비교 대상 | 배치 엔티티의 `create`에 맡긴다. 테스트도 SQL 스크립트로 스키마를 만든다. |
| 선택 근거 | 기존 앱들과 같은 방식이고, 로컬 실행이 공유 테이블을 지우는 일을 막는다. 앱마다 매핑이 실제 스키마와 어긋나면 로컬 `validate`가 잡는다. |
| 영향 | 기존 로컬 DB는 시작 전에 전환 SQL을 적용해야 한다. |

### R-21. 끝낼 수 없는 계산이나 공개를 되돌릴 때 운영자가 `CANCELLED`로 닫는다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | 공개 pointer가 없어(R-13) 이전 회차로 되돌리는 방법이 따로 필요하다. 세 Step이 되면서 원인을 고쳐도 계속 실패하는 계산 중 회차가 남을 수 있고, 이 회차는 그 기간의 다음 계산을 막는다(R-16). |
| 선택한 안 | 운영자가 원인을 확인한 뒤 `CALCULATING`이나 `COMPLETED`인 회차를 `CANCELLED`로 바꾸고 닫은 시각과 사유를 기록한다. 완성 회차를 닫으면 남은 완성 회차 중 가장 큰 회차가 공개본이 된다. 계산 중 회차를 닫으면 다음 회차를 시작할 수 있다. 닫은 회차는 다시 계산하지 않고, 회차 번호는 닫은 것까지 포함해 센다. |
| 비교 대상 | 계산 중 회차는 닫지 못하고 다시 실행으로만 끝낸다. 끝낼 수 없는 회차를 지우고 다시 계산한다. `COMPLETED`만 닫는다(이전 안). |
| 선택 근거 | 닫는 상태 하나로 되돌리기와 포기를 함께 표현하고, 지우지 않으므로 무엇이 있었는지 남는다. 계산 중 회차를 닫지 못하면 데이터 문제로 끝까지 실패하는 회차가 그 기간을 영영 막는다. |
| 영향 | 닫기는 상태 조건을 붙인 SQL로 한다. 앱이 Job 하나를 실행하고 끝나는 구조라 관리 API를 두지 않는다. 배치 실행 기록은 따로 표시하지 않는다. 닫은 회차를 다시 실행하면 점수 고정이나 공개의 상태 확인에서 실패한다. 순위를 매기는 중에 닫으면 순위 Writer의 상태 조건 때문에 그다음 묶음에서 실패하고, 닫힌 회차의 행은 더 바뀌지 않는다. |

### R-22. API는 회차 정보와 순위를 두 번 나눠 읽는다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨. 2026-11-18에 첫 번째 조회를 공개 pointer 대신 가장 최근 완성 회차로 바꿨다. |
| 맥락 | 회차 정보, 순위, 상품을 한 쿼리로 join해 읽으면 순위가 0행인 완성 회차나 상품이 모두 제외된 경우 결과 행이 없어, 회차 정보까지 사라지고 `PUBLISHED`와 `NOT_PUBLISHED`를 구분할 수 없다. |

| 선택 근거 | 완성된 회차의 점수와 순위 행은 바뀌지도 지워지지도 않아, 나눠 읽어도 서로 다른 회차의 행이 섞이지 않는다. 각 쿼리가 단순하고 공개 조건과 `limit`을 두 번째 조회에만 두면 된다. |
| 영향 | 두 조회 사이에 새 회차가 완성돼도 그 요청은 처음 찾은 회차를 끝까지 보여 준다. |

### R-23. 계산 시각은 점수를 넣은 뒤에 읽고, 점수 고정 트랜잭션에 남긴다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19 다시 정함) |
| 맥락 | `calculatedAt`은 "이 시각 뒤에 도착한 구매는 결과에 없다"는 약속이다. |
| 선택한 안 | 점수를 넣는 문장이 끝난 뒤 시계에서 계산 시각을 읽고, `CALCULATING` 회차 정보에 넣어 점수와 함께 커밋한다. 결과 checksum은 공개 때 채운다. |
| 비교 대상 | 계산을 시작할 때 시각을 읽는다. 공개할 때 시각을 읽는다. 점수·순위·checksum과 함께 한 트랜잭션에 넣는다(이전 안). |
| 선택 근거 | 넣기 전에 읽은 시각은 그 시각과 넣기 사이에 도착한 구매를 결과에 넣어 약속을 깬다. 공개할 때 읽으면 기준 시점이 실제로 점수를 자른 순간보다 늦어진다. 그사이 도착한 구매는 결과에 없는데도 기준 시점 전으로 보인다. |
| 영향 | 완성된 회차에는 계산 시각과 결과 checksum이 있고, 계산 중 회차에는 계산 시각만 있다. 이를 규칙과 테스트로 둔다. |

### R-24. 잡 파라미터는 문자열로 받고 검증기가 모양을 엄격하게 본다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | Spring Batch 5.2.2는 JobInstance를 가를 때 파라미터의 값과 함께 타입도 본다. `revision=1,java.lang.Long`으로 정해 두면 누군가 `revision=1`로 실행하는 순간 문자열이 되어 다른 JobInstance가 되고, 다시 실행과 동시 실행 보호가 깨진다. |
| 선택한 안 | `periodStart`, `revision` 모두 문자열로 받는다. 검증기(`JobParametersValidator`)가 `periodStart`는 `yyyy-MM-dd` 형식의 월요일, `revision`은 0으로 시작하지 않는 양의 정수, 둘 다 식별 파라미터인지 확인하고 모르는 파라미터를 거절한다. |
| 비교 대상 | 타입을 붙여 받고 검증기가 타입을 확인한다. |

| 영향 | 실행 명령은 `periodStart=2026-08-17 revision=1`이다. |

### R-25. 계산 규칙 버전은 두지 않는다

| 선택한 안 | 회차 정보에 계산 규칙 버전을 두지 않는다. 순위는 다시 실행할 때마다 비우고 처음부터 매기므로(R-30) 한 회차의 순위는 한 코드가 매긴다. 점수는 점수 고정에서 한 번에 정해진다. |

| 영향 | 점수 규칙을 바꾸는 배포 전에 고정한 계산 중 회차는 옛 규칙의 점수로 끝난다. 그 점수로 공개하면 안 될 때는 닫고 다음 회차로 계산한다(R-21). 어느 코드로 계산했는지는 실행 ID로 배포 기록과 대조한다. |

### R-28. 논리 삭제된 구매 활동은 점수와 원본 확인에서 뺀다

### R-29. 순위는 고정한 점수를 정해진 순서로 읽은 순번으로 매긴다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19) |
| 맥락 | 순위를 묶음으로 나눠 쓰면 중간에 실패하고 다시 실행해도 순위가 어긋나지 않아야 한다. |
| 선택한 안 | Reader가 고정한 점수를 `score DESC, product_id ASC` 순서로 페이지 단위로 읽고, Processor가 그 아이템이 몇 번째로 읽혔는지를 계산 순위로 정한다. 순번은 Spring Batch가 아이템에 넣어 주는 읽은 순번을 쓰고, Writer는 `UPDATE ... SET rank_no = ?`로 계산 중인 회차에만 절대값을 쓰고, 바뀐 행 수가 묶음의 아이템 수와 다르면 실패한다. |
| 비교 대상 | Processor가 순번을 메모리에 센다. SQL `ROW_NUMBER()`로 계산한 순위를 읽어 그대로 쓴다. |
| 선택 근거 | 읽은 순번은 reader가 읽은 순서 그대로라 정렬과 순위가 어긋나지 않고, Processor가 상태를 갖지 않는다. 메모리 순번도 처음부터 다시 매기는 지금 구조에서는 맞게 나오지만, 실행마다 새로 시작해야 하는 상태가 Processor에 생긴다. 페이지 단위 reader에서 `ROW_NUMBER()`는 페이지마다 1부터 다시 매겨지고, cursor reader로 하면 점수 고정에서 같이 계산할 일을 일부러 나눈 모양이 된다. |
| 영향 | 순위의 순서는 Reader의 정렬이 정한다. FR-03의 순서를 Reader 쿼리가 지킨다. |

### R-30. 순위 Step은 다시 실행하면 이어 가지 않고 처음부터 매긴다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19) |
| 맥락 | 순위를 묶음으로 나눠 쓰므로, 실패한 뒤 다시 실행할 때 저장한 위치부터 이어 갈지 처음부터 다시 할지 정해야 한다. 과제 §6은 chunk 2로 상품 9 직전에 실패시키고 상품 9부터 이어서 완료하는 장면을 확인하라고 했다. |
| 선택한 안 | 순위 Step이 시작할 때 계산 중인 그 회차의 순위를 모두 비우고, 고정한 점수를 처음부터 읽어 1위부터 다시 매긴다. reader는 위치를 저장하지 않는다(`saveState(false)`). 다시 실행할 때 점수 고정은 완료한 Step이라 건너뛰므로 입력은 그대로다. |
| 비교 대상 | reader 위치를 실행 기록에 저장하고 마지막으로 커밋한 묶음 다음부터 이어 간다(이전 안). 순위를 비우지 않고 처음부터 덮어쓴다. Tasklet 하나로 돌아가 실패하면 처음부터 계산한다. |
| 선택 근거 | 입력이 고정돼 있고 순위를 절대값으로 쓰므로 처음부터 다시 해도 결과가 같다. 상품 1,000개의 순위는 밀리초 단위라 이어 가서 아끼는 시간이 없다. 이어 가면 페이지 크기를 chunk 크기와 맞춰야 하고, 실패와 다시 실행 사이에 순위 규칙이 바뀌면 한 회차에 두 규칙이 섞인다. 비우지 않고 덮어쓰면 규칙이 바뀐 경우 남아 있던 순위와 유일 제약이 부딪힌다. Tasklet 하나로 돌아가면 chunk가 운영 코드에서 다시 사라진다. |
| 영향 | 과제 §6의 "상품 9부터 이어서 완료"는 운영 Job에서 보이지 않는다. 대신 실패 뒤 다시 실행한 결과가 정상 실행과 같은지 확인한다. chunk는 묶음마다 커밋해 트랜잭션 크기를 일정하게 두는 데 쓴다. 상품이 아주 많아져 순위 단계가 길어지면 이어 가는 방식을 다시 검토한다. |

### R-31. Step 안에서는 재시도하지 않고, 실패하면 같은 파라미터로 Job을 다시 실행한다

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨(2026-11-19) |
| 맥락 | 실패에는 잠금 대기 시간 초과, 교착 상태, 연결 끊김 같은 일시적 오류와 잘못된 원본, 제약 위반, 순위 확인 실패 같은 데이터 오류가 있다. Spring Batch는 chunk Step에 재시도(`faultTolerant().retry()`)와 건너뛰기(`skip`)를 제공한다. |
| 선택한 안 | Step 안에서는 재시도하지도 건너뛰지도 않는다. 실패하면 Job은 실패로 끝나고 0이 아닌 종료 코드를 돌려준다. 다시 시도는 같은 파라미터로 Job을 다시 실행하는 것이다. 다시 실행하면 점수 고정은 건너뛰고 순위는 처음부터 매기므로 결과가 같다(R-09, R-30). 자동으로 다시 띄울지와 그 횟수·간격은 실행을 띄우는 스케줄러의 설정이다. |
| 비교 대상 | 순위 Step에서 잠금 오류만 2~3회 재시도한다. Tasklet 안에 `RetryTemplate`을 둔다. 실패한 상품을 건너뛰고 계속한다. |
| 선택 근거 | 일시적 오류가 날 자리가 거의 없다. 점수 고정은 `READ_COMMITTED`라 원본을 잠그지 않고, 같은 회차를 쓰는 다른 실행은 Spring Batch가 막는다. 남는 것은 운영자가 회차를 닫는 순간 정도다. Job 전체를 다시 해도 몇 초 안에 끝나고 결과가 같다. Step에 재시도를 두면 재시도할 예외와 하지 않을 예외를 나눠 관리해야 한다. 예를 들어 회차가 닫혀 바뀐 행이 0인 실패는 다시 해도 소용없다. Tasklet에는 chunk 재시도가 적용되지 않아 따로 만들어야 한다. 건너뛰면 상품이 빠진 틀린 랭킹이 완성본이 된다. |
| 영향 | 데이터 오류는 다시 실행해도 같은 이유로 실패하므로 원인을 고친 뒤 다시 실행하고, 끝낼 수 없으면 회차를 닫는다(R-21). 스케줄러가 자동으로 다시 띄우더라도 다시 실행이 멱등해 결과를 해치지 않는다. 실행 기록이 `STARTED`나 `UNKNOWN`으로 남으면 다시 실행이 거절되므로 정리 절차를 먼저 거친다. |
