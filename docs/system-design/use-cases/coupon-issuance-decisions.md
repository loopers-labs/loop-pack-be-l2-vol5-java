# 쿠폰 발급 결정 기록

쿠폰 발급 설계에서 선택한 사항의 맥락, 대안, 근거와 영향을 기록한다.
기능 계약과 현재 처리 흐름은 [쿠폰 발급 설계](coupon-issuance.md)를 참고한다.

## 결정 기록

### D-01. 쿠폰별 재고 행을 발급 전에 준비

| 항목 | 내용 |
|---|---|
| 상태 | 현재 선택됨 (학습 목적, 실험 후 재검토 가능) |
| 맥락 | 캠페인 총량은 100장이고 couponId는 쿠폰별 내부 식별자다. 발급 때 총량을 넘기지 않으면서 사용자별 발급 결과를 남겨야 한다. |
| 선택한 안 | 캠페인 준비 시 쿠폰별 행 100개를 만들고, 발급 트랜잭션에서 미발급 행 하나를 사용자에게 배정한다. |
| 비교 대상 | 발급 요청마다 발급 기록을 새로 insert하고 캠페인 행의 누적 발급 수로 총량을 제한한다. |
| 선택 근거 | 쿠폰 한 장을 DB의 한 행으로 표현해 서로 다른 재고 단위를 할당하는 경합과 DB 보호 방식을 살펴보고 싶다. |
| 구현·검증 영향 | 캠페인의 쿠폰 행 수는 `totalQuota`와 같아야 하며 seed 생성·reset 때도 이 조건을 유지한다. 후보 조회의 인덱스와 실행 계획에 따라 탐색 비용을 확인한다. 캠페인 issuedCount도 매 발급마다 갱신하므로 캠페인 행의 갱신 경합은 남는다. |

이 선택은 범위락이 없거나 경합을 반드시 줄인다고 전제하지 않는다. 후보 조회의 인덱스와 실행 계획은 별도로 확인한다. 남은 수량은 totalQuota - issuedCount로 계산하며 별도 카운터는 두지 않는다.

### D-02. 사전 생성 쿠폰 행을 발급 기록으로 사용

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 쿠폰별 행 100개를 발급 전에 준비한다. 발급 뒤에는 해당 couponId가 누구에게 갔는지와 발급 정보를 조회해야 한다. |
| 선택한 안 | 쿠폰별 행을 발급 전 재고 단위로 사용하고, 발급 시 같은 행에 사용자와 발급 정보를 채운다. 본인 보유 목록도 이 행에서 조회한다. |
| 비교 대상 | 재고 테이블에서 행을 할당한 뒤 별도 발급 기록 테이블을 insert한다. |
| 선택 근거 | 현재 범위에서는 재고 단위와 발급된 쿠폰의 식별자가 같고, 별도 재고·발급 기록 테이블을 유지할 추가 규칙이 없다. |
| 영향 | 쿠폰별 행은 발급 전후 상태를 함께 표현한다. userId NULL은 미발급, userId가 설정된 행은 발급 완료다. 카운터 증가에 성공했는데 미발급 쿠폰 행이 없으면 품절이 아닌 데이터 불일치로 처리하고 전체 트랜잭션을 rollback한다. |

### D-03. 후보 쿠폰 행을 조건부 갱신해 선점

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 쿠폰 후보를 먼저 조회하면 같은 미발급 행을 여러 요청이 고를 수 있고, `SKIP LOCKED`는 잠긴 마지막 재고를 건너뛰어 일시적인 빈 결과를 만들 수 있다. |
| 선택한 안 | 발급 트랜잭션 격리 수준은 `READ_COMMITTED`로 둔다. 모든 신규 발급 경로가 먼저 캠페인 발급 가능 조건과 잔여 수량을 조건부 갱신해 같은 캠페인의 발급을 직렬화한 뒤, 미발급 couponId를 일반 조회하고 기본키와 `userId IS NULL` 조건으로 배정한다. 쿠폰 조회에 별도 `SELECT ... FOR UPDATE`는 추가하지 않는다. |
| 비교 대상 | 후보를 먼저 읽고 조건부 갱신으로 경합을 확인한 뒤 새 트랜잭션에서 다시 시도하거나, `FOR UPDATE SKIP LOCKED`로 잠긴 후보를 건너뛴다. |
| 선택 근거 | 마지막 재고를 다른 트랜잭션이 처리 중이라는 이유로 현재 요청을 품절처럼 거절하지 않는다. Redis permit이 없는 경우만 즉시 429로 거절하고, DB 내부의 캠페인 경합은 트랜잭션 안에서 기다린다. |
| 영향 | 캠페인 카운터 행이 같은 캠페인 발급을 직렬화한다. `READ_COMMITTED`는 잠금 대기 뒤 후보 조회가 앞 트랜잭션의 commit을 보게 한다. 쿠폰 행 조건부 갱신은 최종 방어로 유지하며, 0행이면 rollback한다. |

후보 조회는 캠페인 카운터 갱신 뒤에 수행한다. `REPEATABLE_READ`에서 앞선 일반 SELECT가 스냅샷을 고정하면 잠금 대기 뒤에도 오래된 미발급 후보를 읽을 수 있으므로, 발급 TX는 `READ_COMMITTED`를 사용한다.

### D-04. 누적 발급 수를 캠페인 행에 저장

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 캠페인 계약에 총 발급 한도와 현재 발급 수가 있고, 발급 수는 실제 사용자 발급 결과와 일치해야 한다. |
| 선택한 안 | issuedCount를 0에서 시작해 신규 발급마다 1 증가시킨다. 남은 수량은 totalQuota - issuedCount로 계산한다. |
| 비교 대상 | 발급된 쿠폰 행 수를 조회해 현재 발급 수를 계산한다. |
| 선택 근거 | 과제 계약의 현재 발급 수를 캠페인에서 직접 확인하고 트랜잭션 안에서 발급 결과와 함께 갱신한다. |
| 영향 | 쿠폰 행 배정과 issuedCount 증가는 같은 DB 트랜잭션에 둔다. 모든 신규 발급이 캠페인 행도 갱신하므로 해당 행의 경합은 남는다. |

### D-05. 발급 총량을 조건부 카운터 갱신으로 보호

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 여러 신규 발급이 마지막 남은 수량을 동시에 확인해도 issuedCount가 totalQuota를 넘으면 안 된다. |
| 선택한 안 | 발급 트랜잭션에서 읽은 `issueNow`가 발급 기간 안이고 `terminated_at IS NULL`, `issuedCount < totalQuota`일 때만 카운터와 조기 종료 시각을 한 조건부 UPDATE로 갱신한다. `terminated_at = CASE WHEN issued_count = total_quota - 1 THEN :issueNow ELSE terminated_at END`를 먼저 대입하고, 그 뒤 `issued_count = issued_count + 1`을 대입한다. 영향 행 수가 1이면 계속 진행하고, 0이면 최신 캠페인 상태를 확인해 없음·기간 밖·조기 종료·품절을 구분한다. |
| 비교 대상 | 캠페인 행을 먼저 잠금 조회한 뒤 잔여 수량을 확인하고 카운터를 증가시킨다. |
| 선택 근거 | 조건 검사와 증가를 한 DB 문장으로 원자적으로 처리해 마지막 수량 경쟁을 막는다. |
| 영향 | MySQL 단일 테이블 UPDATE의 왼쪽부터 대입하는 규칙을 고려해 종료 시각을 증가 전 수량으로 판단한다. 카운터 증가, 조기 종료 기록, 쿠폰 행 배정은 같은 트랜잭션으로 보호한다. `recordIssue()`는 도메인 전이를 표현하며 DB 갱신 뒤 다시 호출하지 않는다. 갱신 전 조회 수량으로 마지막 발급 여부를 판단하지 않는다. 도메인 전이와 SQL 결과는 DB 테스트로 대조한다. 같은 캠페인의 발급은 카운터 행 갱신에서 경합할 수 있다. |

### D-06. 동시 수용량을 서버 YAML 설정으로 관리

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 신규 발급 실행의 동시 처리 수용량은 캠페인 발급 총량과 별개이며 클라이언트가 정하는 값이 아니다. |
| 선택한 안 | 애플리케이션이 서버 YAML 설정에서 동시 처리 수용량을 읽는다. 로컬·테스트 실험은 3으로 하고, 배포 환경의 값은 부하와 SLO를 측정한 뒤 정한다. |
| 비교 대상 | HTTP 요청 입력으로 수용량을 받거나 코드 상수로 고정한다. |
| 선택 근거 | 신뢰 가능한 서버 정책으로 유지하면서 환경별로 조절할 수 있다. |
| 영향 | 로컬·테스트 YAML에만 3을 둔다. 다른 프로필은 수용이 닫힌 채 수용량 없이 기동할 수 있지만, 시작 시 수용을 열려면 양의 값을 명시해야 한다. YAML 값은 DB 연결 풀을 예약하거나 직접 조정하지 않는다. |

### D-07. 신규 발급 실행마다 UUID permit token 생성

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | Redis Set에서 각 활성 실행을 구분해야 같은 사용자의 동시 요청도 별개의 처리 자리를 점유하고, 완료 시 자기 자리만 반환할 수 있다. |
| 선택한 안 | 기존 발급 결과가 없어 신규 발급을 시작할 때 서버가 실행별 UUID token을 생성하고 permit 획득을 한 번 시도한다. Redis 응답이 불확실하면 같은 token으로 재시도하지 않고 신규 수용을 닫는다. |
| 비교 대상 | userId를 token으로 사용하거나, 여러 실행에서 같은 token을 재사용한다. |
| 선택 근거 | 실행마다 Set 원소가 분리되어 동시 점유 수와 소유 실행을 구분할 수 있다. 불확실한 획득 결과를 재시도하지 않아 같은 permit을 두 업무 흐름이 공유하지 않는다. |
| 영향 | token은 사용자 ID·요청 입력·couponId가 아니며 고객에게 전달하지 않는다. Lua의 같은 token 확인은 중복 스크립트 호출에 대비한 방어 로직일 뿐 애플리케이션 재시도 계약은 아니다. 반환은 자기 token만 제거한다. |

### D-08. permit 상태 변경과 판단은 Redis primary에서 수행

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | replica 복제가 지연되면 현재 활성 token 수가 실제보다 적게 보일 수 있어 수용량 제한을 넘길 수 있다. |
| 선택한 안 | Lua 수용 판단과 token 추가, token 반환은 모두 전용 primary 연결(`redisTemplateMaster`)로 수행한다. |
| 비교 대상 | `REPLICA_PREFERRED` 연결에서 점유 수를 읽고 별도 판단하거나, replica 값을 수용 근거로 사용한다. |
| 선택 근거 | 현재 점유에 대한 판단과 변경을 권위 있는 동일 primary에서 원자적으로 처리한다. |
| 영향 | primary 전환·상태 유실이 의심되면 연결이 살아났다는 사실만으로 수용을 재개하지 않고 복구 절차를 따른다. |

### D-09. 캠페인과 개별 쿠폰을 별도 aggregate로 둠

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 캠페인 하나에 쿠폰 단위 행 100개가 있지만, 발급 시마다 전체 쿠폰을 메모리에 올릴 필요는 없다. |
| 선택한 안 | `CouponCampaign`은 정책·총량·현재 발급 수를 관리하고, 각 `Coupon`은 한 장의 미발급/발급 상태와 발급 정보를 관리한다. 두 개를 별도 aggregate로 둔다. |
| 비교 대상 | 캠페인 aggregate가 쿠폰 100장을 내부 컬렉션으로 소유하고 함께 로드한다. |
| 선택 근거 | 쿠폰 단위로 후보 조회·조건부 선점을 할 수 있고, 전체 재고를 불필요하게 로드하지 않는다. |
| 영향 | aggregate 분리는 DB 트랜잭션 분리를 뜻하지 않는다. 발급 수 증가와 쿠폰 배정은 애플리케이션 흐름에서 한 DB 트랜잭션으로 조정한다. |

### D-10. 혜택 설명은 캠페인에만 저장

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 한 캠페인의 쿠폰은 같은 고정 혜택을 가지며, 이번 범위에서는 발급 이력의 핵심이 수령 사용자와 발급 시각이다. |
| 선택한 안 | benefitDescription은 CouponCampaign에 한 번 저장하고 이번 범위에서는 변경하지 않는다. 발급된 Coupon 행에는 campaignId를 저장하며, 혜택 정보는 이 관계를 통해 조회한다. Coupon 행에 혜택 스냅샷을 복사하지 않는다. |
| 비교 대상 | 발급할 때마다 같은 혜택 설명을 각 Coupon 행에 복사해 발급 당시 문구를 보존한다. |
| 선택 근거 | 혜택이 고정이고 캠페인 CRUD가 범위 밖이므로 쿠폰 행마다 같은 설명을 중복 저장할 필요가 없다. |
| 영향 | 과제의 발급 결과에 필요한 혜택 정보는 Coupon의 campaignId 관계로 조회한다. 혜택이 발급 후 변경되지 않으므로 이번 범위에서는 캠페인 혜택으로 과거 발급 결과도 표시할 수 있다. 향후 캠페인 혜택을 변경 가능하게 만들거나 과거 문구 보존이 필요하면 발급 시점 스냅샷 또는 혜택 버전 모델을 다시 검토한다. |

### D-11. 캠페인 발급 기간과 품절 조기 종료 시각을 분리

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 신규 발급은 예정된 캠페인 기간에만 가능하고, 총량이 소진되면 예정 종료 시각보다 일찍 끝날 수 있다. |
| 선택한 안 | `start_at`과 `end_at`은 예정 발급 기간을 나타낸다. 발급 트랜잭션의 신규 발급 가능 조건은 `start_at <= issueNow < end_at`, `terminated_at IS NULL`, `issuedCount < totalQuota`이다. |
| 조기 종료 기록 | `terminated_at`은 총량을 모두 발급해 조기 품절된 실제 시각만 기록한다. 마지막 쿠폰 발급과 같은 트랜잭션에서 저장한다. 예정 종료 시각에 끝나는 캠페인에서는 NULL로 남는다. |
| 비교 대상 | 활성/비활성 boolean으로 기간을 표현하거나, 별도 종료·품절 상태를 중복 저장한다. |
| 선택 근거 | 시작·예정 종료·품절 조기 종료 시각을 구분해 캠페인 일정을 읽기 쉽게 한다. 활성/비활성 값은 별도로 두지 않는다. |
| 영향 | permit 전 사전 조회와 발급 트랜잭션은 각각 `Clock`에서 시각을 읽는다. 사전 조회 시각은 조기 404·409 분류에만 쓰고 트랜잭션에 전달하지 않는다. 최종 발급 판단은 트랜잭션에서 새로 읽은 시각을 도메인 판단, DB 조건부 UPDATE, `issuedAt`, 마지막 발급의 `terminated_at`에 함께 사용한다. 시간 값은 UTC 기준으로 다룬다. |

### D-12. 발급 기간 판단에 애플리케이션 `Clock` 사용

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 캠페인 발급 기간을 확인하고 마지막 쿠폰 발급의 조기 종료 시각을 기록해야 한다. |
| 선택한 안 | permit 전 캠페인 사전 조회와 발급 트랜잭션에서 `Clock`을 각각 읽는다. 사전 조회 시각은 조기 분류에만 쓰며 트랜잭션까지 전달하지 않는다. 트랜잭션은 시작 후 새 `issueNow`를 한 번 얻고, 같은 값을 도메인 기간 판단, DB 조건부 UPDATE의 시간 조건, `issuedAt`, 마지막 발급의 `terminated_at`에 사용한다. UTC 기준 `Instant`로 다룬다. |
| 비교 대상 | 하나의 발급 트랜잭션 안에서 각 계층이 시스템 시각을 따로 읽어 서로 다른 기준 시각을 쓰거나, DB의 `CURRENT_TIMESTAMP`를 최종 기준으로 사용한다. |
| 선택 근거 | 한 발급 판단 안에서 같은 시각을 사용하고, 테스트에서 고정 시각으로 경계 조건을 재현하기 쉽다. |
| 영향 | `issueNow`는 트랜잭션의 발급 판정 시각이며 DB commit 시각을 뜻하지 않는다. 조건부 갱신이 캠페인 행 잠금을 기다리는 동안 `end_at`이 지나더라도 이미 읽은 `issueNow`로 판단할 수 있다. 잠금 획득 뒤의 엄격한 마감 시각 보장이 필요해지면 판정 시각을 읽는 위치나 잠금 방식을 다시 검토한다. 여러 애플리케이션 인스턴스의 시스템 시계가 어긋나는 환경에서도 DB 시계를 기준으로 하는 방식을 검토한다. |

### D-13. 쿠폰은 미발급에서 발급 완료로 한 번만 전이

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 쿠폰 행 100개는 발급 전 재고 단위로 준비되고, 발급 뒤에는 사용자 보유 쿠폰 이력으로 사용한다. |
| 선택한 안 | 미발급 쿠폰은 `userId`와 `issuedAt`이 비어 있다. 발급 시 두 값을 기록하고, 발급된 쿠폰은 소유자를 바꾸거나 재고 상태로 되돌리지 않는다. 혜택 설명은 campaignId를 통해 캠페인에서 조회한다. |
| 비교 대상 | 발급 뒤 쿠폰을 회수하거나 다시 미발급 재고로 되돌리는 생애주기, 혹은 혜택 설명을 쿠폰마다 복사하는 모델. |
| 선택 근거 | 현재 범위에는 쿠폰 사용·환불·회수 기능이 없고, 발급 이력은 보존해야 한다. |
| 영향 | 상태는 별도 status 컬럼 없이 `userId`와 `issuedAt`의 NULL 여부로 표현한다. 재발급은 기존 사용자·캠페인 쿠폰 조회와 DB 유일 제약으로 처리한다. |

### D-14. Redis permit 획득 뒤에 발급 DB 트랜잭션 시작

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 자리가 없는 요청은 신규 DB 작업에 진입하지 않아야 하고, DB 트랜잭션이 끝난 뒤에만 permit을 돌려줄 수 있다. |
| 선택한 안 | 요청 조정 흐름 전체는 비트랜잭션으로 둔다. 기존 쿠폰 조회, 잠금 없는 캠페인 사전 조회, 앱 허용 상태 확인, Redis permit 획득을 먼저 수행하고, permit 획득 뒤 각각의 DB 발급 시도를 별도 트랜잭션으로 실행한다. 트랜잭션 종료가 확인된 다음 자기 token을 반환한다. |
| 비교 대상 | 기존 조회·Redis 호출·DB 발급·permit 반환을 하나의 바깥 DB 트랜잭션으로 감싼다. |
| 선택 근거 | 이미 발급 불가하거나 없는 캠페인을 permit과 신규 발급 트랜잭션 전에 분류한다. Redis 호출 동안 DB 트랜잭션과 연결을 점유하지 않으며, 같은 캠페인의 최종 발급 경쟁은 DB 카운터 행 갱신으로 판정한다. |
| 영향 | 잠금 없는 사전 조회 뒤 캠페인 상태가 바뀔 수 있으므로 DB 트랜잭션에서 다시 확인한다. 캠페인 카운터 갱신에서 같은 캠페인의 발급 트랜잭션이 직렬화될 수 있고, Redis permit은 commit 또는 rollback까지 유지한다. |

### D-15. 쿠폰 후보 조회에 `SKIP LOCKED`를 사용하지 않음

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 잠긴 쿠폰 후보를 건너뛰면 남은 쿠폰이 처리 중인 경우에도 조회 결과가 비어 사용자가 재요청해야 할 수 있다. 이번 API는 후보 행 경합 때문에 사용자가 다시 누르는 흐름을 만들지 않는다. |
| 선택한 안 | 같은 캠페인의 발급 트랜잭션은 조건부 카운터 갱신에서 차례로 진행하고, 그 뒤 미발급 쿠폰 후보를 조회해 조건부 갱신한다. 일반 DB 잠금 대기는 트랜잭션 안에서 처리한다. |
| 비교 대상 | 후보를 `FOR UPDATE SKIP LOCKED`로 조회해 잠긴 행을 건너뛰고, 후보가 없으면 현재 요청을 실패시킨다. |
| 이점 | 잠금 중인 마지막 쿠폰을 품절로 오인하지 않는다. DB가 앞선 트랜잭션의 commit/rollback을 확인한 뒤 다음 발급을 판정하므로 후보 행 경합 때문에 사용자가 다시 요청할 필요가 없다. |
| 비용 | 같은 캠페인의 발급은 카운터 행에서 직렬화된다. 앞선 DB 트랜잭션이 느리면 뒤 요청은 트랜잭션과 permit을 점유한 채 기다리고, 다른 신규 요청은 permit 부족으로 429를 받을 수 있다. 이 방식은 발급 순서를 보장하지 않는다. |
| 선택 근거 | 사용자 재요청과 잠긴 재고를 품절로 처리하는 응답을 피하는 점을, 같은 캠페인 카운터 행의 직렬화 비용보다 우선한다. `SKIP LOCKED`는 후보 행 경합을 줄일 수 있지만 이번 응답 계약에는 맞지 않는다. |

### D-16. 장애 복구용 신규 발급 허용 상태는 앱에서 닫힘 우선으로 관리

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | Redis 상태가 불확실한 동안 신규 발급을 막아야 하며, Redis 연결 복구만으로 이전 permit 상태가 정확하다고 볼 수 없다. |
| 선택한 안 | 앱 메모리의 신규 발급 허용 상태를 기본 실행에서 false로 시작한다. Redis 접근 실패·수용 결과 불확실·permit 반환 실패·정상 획득 token의 첫 `SREM` 결과 0·Lua 입력 또는 스크립트 오류 시에도 false로 바꾼다. 복구 조건을 확인한 뒤 `coupon.issue.admission.open-on-startup=true`를 지정해 재시작할 때만 열기를 시도하고, Redis primary의 permit Set이 비어 있을 때만 true로 시작한다. |
| 비교 대상 | 허용 상태를 Redis 키로만 관리하거나, Redis health check가 회복되면 자동으로 true로 바꾼다. |
| 선택 근거 | Redis에 접근할 수 없는 순간에도 닫힘 상태를 적용하고, 이전 점유 상태를 확인하기 전에 신규 발급이 재개되는 것을 막는다. |
| 영향 | 로컬·테스트 단일 실행을 위한 선택이며 여러 앱 인스턴스에 걸친 전역 허용 상태는 제공하지 않는다. 기본 실행 옵션에는 열기 값을 넣지 않는다. permit Set에 token이 남았거나 primary 확인이 실패하면 앱은 시작하더라도 허용 상태를 false로 유지한다. Set이 비어 있어도 이전 DB 작업 종료 확인은 별도로 필요하다. Redis CLI로 앱 상태를 직접 바꾸지 않으며, 확인된 비활성 token 정리에만 사용한다. |

### D-17. DB commit 뒤 permit 반환 실패는 발급 성공으로 응답

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 쿠폰과 발급 수의 DB commit은 끝났지만 Redis `SREM`에서 0, 연결 오류, timeout이 발생하면 token 반환 상태가 정상 기대와 다를 수 있다. |
| 선택한 안 | DB commit이 확인되면 첫 발급은 201, 기존 발급 결과 반환은 200으로 응답한다. 정상 획득 token의 첫 `SREM`이 0이거나 반환 호출 오류가 나면 이미 commit된 쿠폰은 취소하지 않고 신규 발급 수용을 닫아 복구 절차를 시작한다. |
| 비교 대상 | permit 상태가 불확실하다는 이유로 발급 성공 결과 대신 503을 반환한다. |
| 선택 근거 | 발급의 원본인 DB에는 쿠폰이 확정되어 있으므로, 응답도 실제 업무 결과를 나타내게 한다. 응답을 받지 못한 사용자의 재요청은 유일 제약과 기존 결과 조회로 같은 couponId를 받는다. |
| 영향 | 정상 획득 token의 첫 `SREM` 결과는 1이어야 한다. 0·오류·timeout 뒤에는 새 발급을 수용하지 않는다. DB rollback 뒤 반환 이상은 발급 성공이 아니므로 원래 DB 결과에 따라 응답한다. 이미 제거된 token의 반복 `SREM` 결과 0은 멱등성 검증에서만 정상으로 취급하며, 운영 흐름의 첫 반환 결과와 구분한다. |

### D-18. 쿠폰 발급 오류는 공통 `ErrorType`으로 표현

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 처리 자리 없음과 Redis 수용 상태 확인 불가는 각각 HTTP 429와 503으로 구분해야 한다. 기존 API는 공통 `ErrorType`과 `meta.errorCode`를 사용한다. |
| 선택한 안 | 공통 `ErrorType`에 `TOO_MANY_REQUESTS`와 `SERVICE_UNAVAILABLE`을 추가한다. 쿠폰 전용 오류 코드 체계는 만들지 않는다. |
| 비교 대상 | `COUPON_ISSUE_CAPACITY_FULL` 등 쿠폰 도메인 전용 코드를 새로 정의한다. |
| 선택 근거 | 기존 API 오류 응답 방식을 따르고, 이번 기능에만 별도의 코드 규약을 만들지 않는다. |
| 영향 | `ErrorType` 식별자는 각각 `TOO_MANY_REQUESTS`, `SERVICE_UNAVAILABLE`이고 응답의 `meta.errorCode`는 기존 규칙대로 HTTP reason phrase를 사용한다. 처리 자리 없음은 429, Redis 상태 확인 불가는 503이며 두 응답 모두 발급 성공이나 대기열 등록을 의미하지 않는다. |

### D-19. 로컬 seed 캠페인은 명시적 옵션으로만 초기화

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 수동 발급 테스트 뒤 캠페인의 잔여 수량이 줄고 조기 종료될 수 있다. 앱을 다시 실행하는 것만으로 기존 seed 발급 결과를 지우면 안 되지만, 반복 실험을 위해 초기 상태로 되돌리는 방법은 필요하다. |
| 선택한 안 | `local` 프로필의 seed runner에 `coupon.seed.reset=true` 옵션을 둔다. 옵션을 명시한 실행에서만 seed 캠페인의 쿠폰 할당, issuedCount, terminated_at을 초기화하고 실행 시각부터 하루의 발급 기간을 설정한다. 기본 재시작은 기존 기간·발급 결과를 보존한다. |
| 비교 대상 | 매번 DB에서 수동으로 데이터를 삭제하거나, 앱 시작 때마다 seed 데이터를 자동 초기화한다. |
| 선택 근거 | 재테스트를 한 번의 명시적 실행 옵션으로 반복할 수 있고, 평소 재시작은 기존 실험 결과를 보존한다. |
| 영향 | 초기화 범위는 예약된 이름 `local-coupon-seed`로 식별하는 로컬 seed 캠페인으로 한정한다. 캠페인 reset SQL로 잠금을 얻은 뒤 같은 TX에서 쿠폰 userId·issuedAt을 비우고 issuedCount를 0, terminated_at을 NULL로 되돌리며 기존 쿠폰 ID를 유지한다. 이름 중복·쿠폰 행 수 불일치에는 임의 선택·자동 보충 없이 실패한다. 이전 발급 작업이 종료된 로컬 단일 인스턴스에서만 실행하며 다른 캠페인은 초기화하지 않는다. |

### D-20. 전역 permit Set은 고정 키 `coupon:issue:permits`를 사용

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 모든 캠페인의 신규 발급 실행이 전역 동시 처리 수용량을 공유해야 하며 permit token은 자동 만료되지 않는다. |
| 선택한 안 | 전용 Redis 키 `coupon:issue:permits` 하나에 현재 활성 permit token을 저장한다. 캠페인 ID나 키 버전 접미사는 붙이지 않는다. |
| 비교 대상 | 캠페인마다 별도 Set을 만들거나 키 형식에 `v1` 같은 버전을 붙인다. |
| 선택 근거 | 캠페인별 키는 전역 수용량을 나누고, 버전이 바뀐 키로 전환하면 기존 활성 token이 남은 키와 신규 실행이 보는 키가 달라질 수 있다. |
| 영향 | 이 키는 캐시 키와 분리해 사용한다. 키 형식을 바꿀 때는 신규 발급을 닫고 기존 실행과 token 상태를 확인한 뒤 전환한다. |

### D-21. permit 입력은 앱 시작과 Lua에서 검증

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | Lua는 수용량과 실행 token을 입력으로 받으며, 잘못된 값으로 Set을 변경하면 수용 판단과 token 소유권이 깨질 수 있다. |
| 선택한 안 | 수용량을 설정한 경우 앱 시작 때 1 이상의 정수인지 검증한다. 시작 시 수용을 열려면 수용량 설정도 요구한다. Lua는 수용량과 비어 있지 않은 token을 Set 변경 전에 다시 검증한다. |
| 비교 대상 | YAML 설정과 서버가 생성한 UUID token을 신뢰해 Lua 검증을 생략한다. |
| 선택 근거 | 수용을 켜는 배포 환경에서 설정 오류를 시작 시 드러내고, 스크립트 경계에서도 잘못된 입력의 상태 변경을 막는다. |
| 영향 | 0 이하의 수용량 또는 수용을 열 때 누락된 수용량은 앱 시작을 실패시킨다. Lua 입력 검증 실패나 permit 키 `WRONGTYPE`은 429·503과 구분해 500 `INTERNAL_ERROR`로 응답하고 신규 발급 허용 상태를 닫는다. Redis 연결·timeout과 `READONLY`, `LOADING`, `OOM`, `BUSY` 등 서버 상태 오류는 503으로 구분한다. |

### D-22. 잠금 없는 캠페인 사전 조회로 404·409를 permit 전에 분류

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 없는 캠페인이나 이미 발급 불가한 캠페인 요청이 permit을 차지하거나 신규 발급 트랜잭션을 열 필요는 없다. |
| 선택한 안 | 기존 쿠폰 조회 뒤 캠페인을 잠금 없이 읽는다. 캠페인 없음은 404, 기간 밖·조기 종료·품절은 409로 반환한다. 조건을 통과한 요청만 앱 허용 상태와 Redis permit을 확인하고 DB 발급 트랜잭션으로 진행한다. |
| 비교 대상 | Redis permit과 DB 발급 트랜잭션을 먼저 거친 뒤 조건부 갱신 결과로 캠페인 없음·발급 불가를 판정한다. |
| 선택 근거 | 명백히 발급할 수 없는 요청이 전역 처리 자리를 차지하거나 DB 발급 트랜잭션을 열지 않게 하면서, 기존 발급 결과는 캠페인 종료 뒤에도 반환한다. |
| 영향 | 사전 조회는 잠금 없는 조기 판정이고 최종 업무 판정은 DB 트랜잭션의 조건부 갱신이 맡는다. 사전 조회와 트랜잭션은 각각 시각을 읽으며, 사전 조회 시각은 트랜잭션에 재사용하지 않는다. 조회 뒤 상태가 바뀌면 permit을 얻은 요청도 최종 DB 결과로 409를 받을 수 있다. 기존 쿠폰 조회와 캠페인 조회는 permit 획득 전의 DB 읽기이므로 동시 처리 수용량에 제한되지 않으며, 이후 429가 될 요청도 이 조회 비용을 낸다. 두 조회를 한 쿼리로 합칠 수 있는지는 구현 때 확인한다. |

### D-23. 로컬 요청자 ID에는 사용자 FK를 두지 않음

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | `X-USER-ID`는 이번 로컬 실행에서 요청자를 구분하는 값이고 실제 인증된 계정을 보증하지 않는다. 기존 `likes`, `orders`도 사용자 ID를 FK로 검증하지 않는다. |
| 선택한 안 | `coupons.user_id`를 ID 값으로 저장하고 `users` FK를 두지 않는다. `campaign_id`의 FK와 `(campaign_id, user_id)` 유일 제약은 유지한다. |
| 비교 대상 | 사용자 행을 발급 전에 확인하고 쿠폰의 `user_id` FK로 존재를 강제한다. |
| 선택 근거 | FK를 두면 과제 범위 밖인 사용자 등록·존재 확인이 발급 조건이 되고, 임의 `X-USER-ID` 요청은 카운터 갱신 뒤 DB 오류로 실패한다. |
| 영향 | 실제 사용자 존재와 헤더 위조 방지는 보장하지 않는다. 사용자 인증을 도입할 때는 요청자 ID의 출처와 FK 도입을 함께 재검토한다. 기존 로컬 DB에는 쿠폰 스키마 준비 SQL을 다시 적용해 이전 사용자 FK를 제거한다. |

### D-24. DB 작업 종료를 확인하지 못한 발급 실행의 permit은 반환하지 않음

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 발급 트랜잭션이 예외로 끝나도 DB 작업이 끝났는지는 예외 종류로 알 수 없다. 캠페인 행 잠금 대기 timeout은 Spring이 rollback을 마친 뒤 전달되지만, commit 중 연결이 끊기면 서버가 COMMIT을 받았는지 알 수 없다. 끝나지 않은 실행의 token을 반환하면 새 요청이 자리를 얻어 동시 실행 상한을 넘을 수 있다. |
| 선택한 안 | 발급 트랜잭션 첫 줄에서 Spring 트랜잭션 동기화를 등록해 commit 요청 여부와 완료 상태를 기록한다. 정상 반환, 발급 SQL 실행 전 실패, commit 완료, commit 요청 전 rollback 완료일 때만 token을 반환한다. 그 밖에는 token을 남기고 오류 로그에 `campaignId`와 permit token을 기록하며, 신규 수용은 닫지 않는다. |
| 비교 대상 | 예외와 관계없이 `finally`에서 반환한다. 예외 종류(업무 거절·중복·트랜잭션 시작 실패)로 반환 여부를 정한다. Spring 완료 상태만 보고 commit 요청 여부는 보지 않는다. token을 남기면서 신규 수용도 닫는다. |
| 선택 근거 | 예외 종류로 정하면 잠금 대기 timeout처럼 rollback이 끝난 실패에서도 자리를 잃는다. 요청이 몰려 잠금 대기가 길어질수록 자리가 줄고, DB가 회복돼도 수용량이 돌아오지 않는다. Spring은 commit 요청 뒤 연결이 끊긴 실패를 ROLLED_BACK으로 알릴 수 있어(E2E에서 확인) commit 요청 여부를 함께 본다. 남은 token이 자리를 점유하므로 상한은 지켜지고, Redis 상태는 확인된 상태라 신규 발급 전체를 닫지 않는다. |
| 영향 | 결과를 확인하지 못한 실행마다 쓸 수 있는 자리가 하나씩 줄고, 모두 남으면 신규 요청은 429를 받는다. 남은 token은 TTL이 없으므로 운영자가 DB 작업 종료와 쿠폰·발급 수를 확인한 뒤 해당 token만 제거한다. permit token은 인증 정보가 아니라 실행별 내부 ID라 로그에 남긴다. commit 요청 뒤 실패에는 서버가 실제로 rollback한 경우도 섞이므로 보수적으로 자리를 남길 수 있다. 발급 트랜잭션 메서드는 첫 줄에서 기록을 시작해야 하며, 바깥 트랜잭션에 참여하면 완료 통지가 늦어 token을 남긴다. 현재 facade는 트랜잭션 밖에서 호출한다. 잠금 대기는 MySQL 기본 대기 시간까지 자리를 쥐며, 발급 트랜잭션 timeout은 측정 뒤 정할 남은 개선으로 둔다. |
