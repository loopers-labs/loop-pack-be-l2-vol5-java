# 상품 목록 조회

고객 상품 목록의 필터·정렬·페이지 조회와 좋아요 수 조합을 정리한다. 요청과 응답의 기준 계약은 [API 계약](../api-contracts.md)의 고객 브랜드·상품 API 절을 따른다. 측정 조건, 목표 판정 기준, 인덱스 대안과 단계별 실행계획·측정값은 [상품 목록 성능 기록](../../performance/product-listing/report.md)과 결과 원본에 둔다.

## 정렬과 조회 설계

- `latest`: Product의 `createdAt` 내림차순, `productId` 내림차순
- `price_asc`: Product의 가격 오름차순, `productId` 오름차순
- `likes_desc`: Like 관계 수 내림차순, `productId` 내림차순

상품 목록은 저장소에서 필터와 정렬을 적용한 뒤 `page`·`size`에 해당하는 결과만 조회한다.
범위를 벗어난 페이지는 빈 목록을 반환하며, 기존 목록 응답 형태를 유지한다.

목록 응답의 좋아요 수는 페이지 상품 ID를 JPQL의 `IN` 조건으로 묶고 `productId`별 `GROUP BY`로 한 번에 조회한다.
중복 상품 ID는 제거하고 파라미터로 바인딩한다.
캐시 미사용 시 상품이 있는 페이지는 상품·브랜드·좋아요 SQL을 각각 1회 실행하며, 빈 페이지에서는 좋아요 조회를 생략한다.
좋아요가 없는 상품은 집계 결과에 없으므로 `0`으로 채워 반환한다.
`likes_desc`는 전체 후보의 좋아요 수로 정렬한 뒤 페이지를 선택한다.

상품별 좋아요 검색을 위해 `likes(product_id)` 단일 인덱스를 추가한다. 기존 `(user_id, product_id)` 유니크 인덱스는 유지한다.
이 인덱스가 없으면 `IN + GROUP BY`는 유니크 인덱스 전체를 읽어 상품별 `UNION ALL`보다 느리다.
따라서 좋아요 조회 방식은 `likes(product_id)` 인덱스가 있다는 전제에서 선택한다.

브랜드 필터·가격순 목록은 `(brand_id, deleted_at, price)` 복합 인덱스를 사용한다.
`products(price)` 단일 인덱스와 비교한 결과는 성능 기록에 있으며, 기존 상품·좋아요 조회 계약은 유지한다.

## 캐시 연결

고객 상품 목록은 Redis 캐시를 사용한다. 캐시를 쓰지 않는 경로는 위 조회 규칙으로 결과를 만든다.
저장 필드·키, 쓰기 무효화, 삭제 상품 확인과 장애·기동 시 동작은 [상품 목록 캐시](product-list-cache.md)를 따른다.
