# 쿠폰 발급 대기열 결정 기록

쿠폰 발급 대기열 설계에서 선택한 사항의 맥락, 대안, 근거와 영향을 기록한다.
기능 계약과 처리 흐름은 [쿠폰 발급 대기열 설계](coupon-issuance-queue.md)를 참고한다. 동기 발급의 결정은 [쿠폰 발급 결정 기록](coupon-issuance-decisions.md)의 D-01~D-24를 따른다.

## 결정 기록

### Q-01. 대기 작업을 Redis List 두 개로 보관

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 접수한 요청을 보관했다가 worker가 꺼내 처리해야 한다. 꺼낸 직후 worker가 멈춰도 작업을 잃지 않아야 하고, 한도 확인과 작업 추가는 원자적으로 처리해야 한다. |
| 선택한 안 | 대기 List와 처리 중 List를 둔다. 작업 가져오기는 대기 List 맨 앞을 `LMOVE`로 옮기고, 특정 작업의 완료와 재대기는 `LREM`으로 그 ID를 찾아 처리한다. 작업 정보와 사용자, 캠페인별 작업 ID는 Hash에 저장하고, 상태 기록과 List 이동을 Lua 한 번으로 묶는다. |
| 비교 대상 | Stream의 consumer group과 pending 목록을 사용한다. Sorted Set에 점수로 순서를 매겨 순번을 조회한다. |
| 선택 근거 | 순번 안내와 엄격한 선착순을 요구하지 않으므로 Sorted Set의 순번 조회가 필요 없다. Stream의 pending 목록은 아직 확인하지 않은 메시지만 보여 주므로 작업 상태는 어차피 따로 저장해야 한다. 두 List와 `LMOVE`, `LREM`으로 꺼낸 작업을 잃지 않는 구조를 직접 만들고, 상태 기록과 함께 Lua로 묶는 편이 이번 학습 범위에 맞다. |
| 영향 | 작업 소유권(실행 token), 처리 중 작업의 확인과 복구를 직접 구현한다. Redis 재시작 뒤 작업이 남는지는 RDB, AOF 설정에 따른다. |

### Q-02. worker를 기존 앱 안의 전용 스레드로 실행

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 대기 작업을 꺼내 기존 DB 발급 흐름으로 처리할 실행 주체가 필요하다. |
| 선택한 안 | `commerce-api` 안에서 대기열 전용 스레드 최대 3개로 실행한다. 대기열이 비었거나 실행 자리가 없으면 100ms 뒤 다시 확인하며, 자동 실행은 기본 비활성이다. |
| 비교 대상 | 별도 애플리케이션이나 프로세스로 worker를 분리한다. 공용 비동기 실행기나 스케줄러 스레드를 함께 쓴다. |
| 선택 근거 | 기존 발급 트랜잭션, 완료 상태 판단, permit 코드를 그대로 재사용하고 로컬 실험에서 실행 단위를 늘리지 않는다. 전용 스레드 수를 제한해 Java 안에 작업이 쌓이지 않게 한다. |
| 영향 | API와 같은 JVM과 DB 연결 풀을 공유하므로 자원 격리는 아니다. 여러 인스턴스의 전체 실행 수 제한은 primary Redis의 permit Set을 신뢰할 수 있는 동안에만 보장하며, 조용한 데이터 유실이나 자동 장애 전환 뒤의 안전성은 범위 밖이다. 인스턴스를 늘리면 worker도 늘지만 전체 실행 수는 공유 permit이 제한한다. 공유 Redis command timeout이 100ms라 blocking 명령 대신 짧은 주기로 호출한다. |

### Q-03. worker는 permit을 먼저 얻고 작업을 가져옴

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 동기 요청과 worker가 같은 permit을 나눠 쓴다. 작업을 먼저 꺼낸 뒤 permit을 시도하면, 자리가 없을 때마다 작업을 꺼냈다가 다시 넣어야 하고 순서가 섞이며 Redis 호출이 반복된다. permit 응답이 유실되면 이미 `PROCESSING`이 된 작업까지 따로 처리해야 한다. |
| 선택한 안 | 대기 작업이 있는지 확인하고, 실행 token으로 permit을 먼저 얻은 뒤 같은 token으로 작업을 가져온다. 대기 작업이 없으면 permit만 반환한다. |
| 비교 대상 | 작업을 먼저 꺼내고 permit 0이면 대기 List 뒤로 되돌린다. 작업을 먼저 꺼내되 permit 0이면 대기 List 맨 앞으로 되돌린다. |
| 선택 근거 | 자리가 없으면 작업을 건드리지 않으므로 순서와 상태가 바뀌지 않고 꺼냈다 넣는 반복도 없다. permit 응답이 유실돼도 작업은 `WAITING`이라 수용만 닫고 확인하면 된다. |
| 영향 | permit을 얻은 뒤 작업을 가져오기까지 짧은 동안 자리를 차지하므로 그 사이 동기 요청이 429를 받을 수 있다. 그 사이 앱이 중단되면 어떤 작업에도 기록되지 않은 token이 남으며, 모든 발급 인스턴스를 멈추고 DB 작업 종료를 확인한 뒤 정리한다. 작업 가져오기 응답이 유실되면 DB를 시작하지 않으므로 permit 반환을 시도하고 신규 수용을 닫는다. |

### Q-04. 작업 상태 5개와 reasonCode로 결과 표현

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 사용자가 접수한 작업의 진행과 결과를 조회해야 한다. 업무 거절, 확인된 시스템 실패, 결과 불명을 구분해야 한다. |
| 선택한 안 | `WAITING`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `UNKNOWN` 5개를 사용한다. 업무 거절과 확인된 시스템 실패는 `FAILED`로 합치고 6개 reasonCode로 원인을 구분한다. 본인 작업 조회는 5개 상태 모두 HTTP 200으로 응답한다. |
| 비교 대상 | 업무 거절을 `REJECTED`로 따로 둔다. 원인마다 별도 상태를 둔다. |
| 선택 근거 | 사용자에게는 발급되지 않았다는 결과가 같고 원인은 reasonCode로 충분하다. 결과 불명은 실패가 아니므로 `UNKNOWN`으로 분리한다. |
| 영향 | Java 도메인은 상태와 reasonCode의 의미, 상태별 값 조합, 재접수 처리만 정하고 상태 전이는 Lua가 원자적으로 처리한다. 같은 규칙을 두 곳에 두지 않으려는 것이며, 전이는 실제 Redis 테스트로 검증한다. 같은 `FAILED`라도 reasonCode에 따라 재접수 동작이 다르다(Q-07). 작업 조회의 HTTP 200은 작업을 읽었다는 뜻이며 발급 성공 여부는 `data.status`로 판단한다. |

### Q-05. 접수 한도는 미완료 작업 20건

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 처리량보다 접수가 많으면 대기 작업이 계속 늘어나므로 대기열에도 크기 제한이 필요하다. |
| 선택한 안 | `WAITING`, `PROCESSING`, `UNKNOWN`을 합쳐 최대 20건으로 제한하고 `SUCCEEDED`, `FAILED`는 제외한다. 한도를 넘는 신규 접수는 429로 거절하며, 같은 사용자와 캠페인의 재접수는 한도를 추가로 쓰지 않는다. 시스템 실패로 끝난 작업을 다시 대기시킬 때만 미완료 작업이 늘어나므로 한도를 확인한다(Q-07). 값은 서버 YAML로 설정한다. |
| 비교 대상 | 대기 List 길이만 센다. 완료 이력까지 포함한 전체 저장량을 제한한다. 한도를 두지 않는다. |
| 선택 근거 | 처리 중 작업과 결과 불명 작업도 실행이나 수동 복구를 기다리는 미완료 작업이므로 함께 센다. 20은 한도 도달과 반환을 검증하기 위한 로컬 값이다. |
| 영향 | 완료 이력은 계속 쌓이므로 전체 저장량 제한은 아니다. 운영에 맞는 값은 측정 뒤 정한다. |

### Q-06. 결과를 확인하지 못한 작업은 수동 복구

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | worker가 꺼낸 작업은 DB 결과를 확인하지 못하거나 worker가 중단돼 처리 중으로 남을 수 있다. 시간이 지났다고 이전 DB 작업이 끝났다고 볼 수 없다. 동기 발급의 D-24와 같은 이유다. |
| 선택한 안 | DB 결과를 확인하지 못하면 `UNKNOWN`으로 기록하고 처리 중 List에 남긴다. 중단된 작업도 처리 중 List에 남긴다. 자동 재시도, TTL, 시간 기반 회수는 하지 않고 이전 실행과 DB 작업의 종료를 확인한 뒤 수동으로 복구한다. |
| 비교 대상 | 일정 시간이 지난 처리 중 작업을 대기로 되돌린다. 결과 불명을 `FAILED`로 기록한다. |
| 선택 근거 | 이전 실행이 아직 DB를 쓰는 중에 같은 작업을 다시 실행하면 동시 실행 상한과 중복 확인이 흔들린다. 결과 불명을 실패로 기록하면 이미 발급된 쿠폰을 실패로 알릴 수 있다. |
| 영향 | 결과 불명 작업은 미완료 한도와 permit을 계속 점유할 수 있다. 운영자가 확인할 때까지 해당 사용자는 결과를 기다린다. |

### Q-07. 시스템 실패로 끝난 작업만 사용자 재접수로 다시 대기

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | `DB_ERROR`, `INTERNAL_ERROR`는 DB 작업 종료와 미발급을 확인한 시스템 실패다. 완료된 작업은 재접수 때 저장된 결과를 반환하므로, 그대로 두면 잠금 대기 timeout 한 번으로 그 사용자는 이 캠페인을 대기열로 다시 신청할 수 없다. |
| 선택한 안 | 사용자가 다시 접수하면 신규 접수와 같은 확인을 거쳐 같은 작업 ID를 `WAITING`으로 다시 대기시킨다. 그사이 쿠폰이 발급됐으면 `SUCCEEDED`로 바꾼다. 업무 거절과 성공은 저장된 결과를 반환한다. |
| 비교 대상 | rollback이 확인된 시스템 오류는 횟수 제한을 두고 자동으로 다시 대기시킨다. 지금처럼 두고 한계로 기록한다. |
| 선택 근거 | 사용자가 직접 다시 요청할 때만 실행하므로 자동 재시도를 하지 않는 원칙과 맞고, 반복 횟수를 관리할 필요가 없다. 요청이 몰려 생긴 일시적 오류로 사용자가 영영 신청하지 못하는 일을 막는다. |
| 영향 | 작업 정보는 최신 시도의 상태만 보존하고, 이전 실패 사유는 다시 대기시킬 때 서버 로그에 남긴다. `requestedAt`은 처음 접수한 시각으로 유지한다. 다시 대기한 작업은 미완료 한도에 다시 포함된다. 동시에 재접수해도 Lua 상태 비교로 대기 항목은 하나다. worker와 복구 절차는 `FAILED`를 자동으로 다시 대기시키지 않는다. |

### Q-08. 캠페인 거절 사유를 사유 포함 도메인 예외로 전달

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 품절과 기간 밖은 모두 `CoreException(CONFLICT)`이고 메시지만 다르다. worker가 `SOLD_OUT`과 `CAMPAIGN_NOT_ISSUABLE`을 나누려면 사유를 코드로 받아야 한다. |
| 선택한 안 | `CoreException(CONFLICT)`를 상속하고 품절, 기간 밖 사유를 가진 도메인 예외를 `validateIssuable`이 던진다. 조기 종료는 총량 소진으로만 기록되므로 품절로 분류한다. |
| 비교 대상 | 실패 뒤 캠페인을 다시 읽어 사유를 판단한다. 공통 `ErrorType`에 쿠폰 전용 코드를 추가한다. |
| 선택 근거 | 동기 API의 409와 메시지를 바꾸지 않으면서 거절 시점의 사유를 그대로 전달한다. 다시 읽는 방식은 rollback 뒤 상태가 바뀌면 다른 사유를 기록할 수 있고, `ErrorType` 추가는 동기 API의 `meta.errorCode` 계약을 바꾼다. |
| 영향 | 도메인 코드와 테스트를 바꾼다. reasonCode 분류에 메시지 문자열 비교를 쓰지 않는다. |

### Q-09. 쿠폰만 있는 사용자의 접수는 작업 없이 바로 반환

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 작업 이력은 없고 쿠폰만 있는 사용자의 접수에 성공 이력을 만들면 Lua 하나와 동시 접수 경쟁 처리가 필요하다. 또 이미 받은 쿠폰을 알려 주는 데도 Redis가 필요해 Redis 장애 때 503이 된다. |
| 선택한 안 | 작업을 만들지 않고 `status=SUCCEEDED`와 기존 couponId를 HTTP 200으로 바로 반환한다. 응답의 `requestId`와 `requestedAt`은 비운다. |
| 비교 대상 | 새 requestId로 `SUCCEEDED` 이력을 만들어 반환한다. |
| 선택 근거 | 결과가 이미 확정이라 다시 조회할 작업이 필요 없다. Redis에 쓰지 않으므로 경쟁 처리가 없고, 동기 API처럼 Redis 장애 중에도 이미 받은 쿠폰을 알려 줄 수 있다. |
| 영향 | 이 응답에만 requestId가 없다. 시스템 실패 작업을 재접수하는 중에 쿠폰이 확인되면 그 작업을 `SUCCEEDED`로 바꾸는 흐름은 Q-07을 따른다. |

### Q-10. 수동 복구는 문서 절차와 조건부 Lua로 처리

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | 결과 불명과 중단 작업은 사람이 확인한 뒤 복구해야 한다. 작업 ID를 받는 전용 복구 명령은 HTTP 서버, runner, seed를 띄우지 않는 별도 진입점과 옵션 충돌 검사가 필요해 구현량이 크다. |
| 선택한 안 | 첫 버전은 `redis-cli`와 SQL로 조회하고, 저장소에 둔 조건부 Lua를 `redis-cli EVAL`로 적용하는 절차를 문서로 둔다. Lua는 기대 상태와 실행 token이 맞을 때만 상태 기록, List 이동, 자기 permit 정리를 함께 수행한다. |
| 비교 대상 | 조회와 적용 모드를 가진 전용 복구 명령을 만든다. 절차만 두고 Lua 없이 운영자가 직접 상태를 바꾼다. |
| 선택 근거 | 상태와 token을 조건으로 바꾸는 핵심 안전장치는 Lua가 맡으므로 명령 없이도 유지된다. 동기 발급의 token 정리와 같은 수준의 수동 절차다. |
| 영향 | 운영자가 입력값을 직접 다루므로 실수할 여지가 있다. 조건이 맞지 않으면 Lua가 변경하지 않고 사유를 반환한다. 복구가 잦아지면 명령으로 감싸는 방안을 다시 검토한다. |

### Q-11. seed reset이 해당 캠페인의 대기열 정보도 정리

| 항목 | 내용 |
|---|---|
| 상태 | 선택됨 |
| 맥락 | seed reset은 DB의 발급 수와 쿠폰 배정만 되돌린다. Redis에 성공 이력이 남으면 초기화된 DB와 다른 결과를 응답한다. 이를 막으려고 reset을 차단하면 로컬 초기화 때마다 별도 수동 절차가 필요하다. |
| 선택한 안 | `coupon.seed.reset=true`일 때 해당 캠페인의 작업이 대기, 처리 중 List에 있거나 permit token이 남아 있으면 DB 변경 전에 거절한다. 남은 실행이 없으면 해당 캠페인의 작업 정보와 중복 접수 정보를 Lua로 지운 뒤 DB를 초기화한다. |
| 비교 대상 | 이력이 남은 reset은 막고 별도 4단계 절차로 초기화한다. 대기열 키 전체를 직접 지운다. |
| 선택 근거 | Redis를 먼저 정리하면 DB 초기화가 실패해도 다시 접수할 때 기존 쿠폰을 반환하는 흐름으로 이어지고, 옛 성공 이력과 초기화된 DB가 함께 남지 않는다. 다른 캠페인의 이력은 남긴다. |
| 영향 | 모든 API 인스턴스를 멈춘 상태에서만 reset한다. 수용 닫힘이 인스턴스별 상태라 다른 인스턴스의 접수와 발급을 막지 못하기 때문이다. permit Set은 캠페인을 구분하지 않으므로 다른 캠페인의 남은 token도 reset을 막는다. 해당 캠페인의 field를 찾으려고 중복 접수 Hash를 훑는다. |
