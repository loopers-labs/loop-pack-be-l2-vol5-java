# 주간 구매 랭킹 검증 기록

> 계약과 규칙은 [주간 구매 랭킹](weekly-ranking.md), 구현은 [주간 랭킹 Job 설계](../../../apps/commerce-batch/docs/weekly-ranking-job.md)와 [주간 랭킹 조회 설계](../../../apps/commerce-api/docs/weekly-ranking-query.md)를 기준으로 한다. 이 문서는 검증 시나리오와 기대값, 실행 결과, 확인하지 않는 범위를 모은다.

## 검증 범위

| 위치 | 확인하는 것 | 실행 |
|---|---|---|
| `commerce-batch` Job 테스트 | 점수 고정, 순위 매기기와 실패 뒤 다시 실행, 공개 전 확인, 회차 번호와 동시 실행, 늦은 구매와 재계산, 닫기. 실제 MySQL과 테스트 시계 | `./gradlew :apps:commerce-batch:check` |
| `commerce-api` 테스트 | 랭킹 API의 입력 검증과 응답. 배치가 남기는 것과 같은 모양의 랭킹 fixture를 넣고 확인 | `./gradlew :apps:commerce-api:check` |
| 로컬 연결 확인 | 실제 주문 확정부터 Kafka, 구매 활동, 배치, 랭킹 API까지 | 로컬 검증 도구를 직접 실행하고 결과를 기록 |

두 앱을 한 테스트에 묶지 않는다. 두 앱의 약속은 "배치가 이 테이블을 이 모양으로 쓰고, API가 그대로 읽는다"이며, 그 약속을 양쪽에서 각각 확인한다. 테스트 0건, skip, 연결 실패는 통과로 보지 않는다.

## 과제 요구와 확인 위치

과제 요구마다 이 설계가 어떻게 지키는지와 어디서 확인하는지 모은다. 운영 Job이 과제와 다르게 가는 곳에는 결정 기록의 번호를 적었다.

| 과제 | 이 설계 | 확인 위치 |
|---|---|---|
| §1 기간, 주간 소속, 점수, 순서 | 그대로 | Job 테스트 "기간 경계", 정상 실행 |
| §1 조회 입력 검증, `NOT_PUBLISHED`와 0건 `PUBLISHED` 구분, 다른 주로 대신하지 않음 | 그대로 | API 테스트 "입력 검증", "공개 전", "0건 완성 회차", "미래 기간" |
| §1 응답의 `snapshotId`와 입력 고정 시점 | `revision`과 `calculatedAt`으로 준다(R-07, R-23) | API 테스트 "공개본 조회" |
| §1 삭제 상품 제외, 저장된 계산 순위 유지, 거른 뒤 `limit` | 그대로 | API 테스트 "삭제 상품", "거른 뒤 limit" |
| §1 과거 활동·점수 행을 지우지 않음 | 그대로 | Job 테스트 "회차를 올린 재계산", "최근 회차 닫기" |
| §2 변경하지 않는 입력 묶음, 입력 건수와 checksum | 입력을 복사하지 않고, 한 문장으로 넣은 점수를 고정본으로 쓴다. 입력 건수와 입력 checksum은 두지 않는다(R-08, R-10, R-26) | "실패와 다시 실행"의 늦은 구매 |
| §2 일관된 읽기, `max(id)`로 경계를 정하지 않음 | 한 문장의 일관된 읽기 | Job 테스트 "원본을 잠그지 않음" |
| §2 실패한 고정을 쓰지 않음, 완성된 입력을 다시 만들지 않음, 이미 있는 것을 덮어쓰지 않음 | 점수 고정이 실패하면 아무것도 남지 않는다. 고정한 점수는 다시 넣지 않고 이어서 쓴다(R-09) | Job 테스트 "점수 고정 중 실패", "계산 중 회차의 점수 고정", "실패와 다시 실행" |
| §2 같은 주문의 여러 품목 | 그대로 | fixture의 주문 42 |
| §3 입력 고정 → 점수 계산 → 공개, 완료한 입력 고정은 다시 돌지 않음 | 점수 고정 → 순위 매기기 → 공개의 세 Step이다. 점수는 고정하는 문장에서 함께 계산하므로, chunk로 나눠 처리하는 것은 점수가 아니라 순위다(R-08, R-12) | "실패와 다시 실행" |
| §3 업무 값의 식별 파라미터, `RunIdIncrementer`·`ResourcelessTransactionManager`·메모리 JobRepository 금지, 같은 DB 트랜잭션, 자동 실행 끄기 | 그대로(R-24) | Job 테스트 "파라미터 검증", Job 설계의 구현 체크리스트 |
| §3 probe, reader 파라미터의 step scope 바인딩 | probe Job은 두지 않는다. 순위 Step의 reader는 잡 파라미터를 받는 `@StepScope` 빈이다. 운영 Job은 reader 위치를 저장하지 않으므로 probe가 보려던 "저장한 위치부터 이어 가기"는 확인하지 않는다(R-27, R-30) | "실패와 다시 실행" |
| §4 Reader·Processor·Writer, 절대값 upsert, 결과와 위치의 같은 커밋 | 순위 Step이 고정한 점수를 읽어 순위를 절대값으로 쓰고 묶음마다 커밋한다. 점수 행은 점수 고정이 이미 만들었으므로 upsert가 아니라 순위만 바꾸는 UPDATE다. 위치는 저장하지 않는다(R-29, R-30) | "실패와 다시 실행", Job 테스트 "남아 있던 순위" |
| §5 모든 점수와 예상 상품 수를 확인한 뒤 순위 | 점수를 한 문장으로 모두 고정한 뒤 순위를 매기고, 공개 전에 모든 점수에 순위가 1부터 빠짐없이 매겨졌는지 확인한다(R-14) | Job 테스트 "잘못된 원본", "순위가 빠진 회차" |
| §5 완성과 공개를 한 트랜잭션으로, 계산 중·실패에는 기존 결과 유지 | 공개 Step이 순위 확인, checksum, 완성을 한 트랜잭션으로 한다. 계산 중 회차는 조회에 보이지 않는다(R-13) | Job 테스트 "공개 직전 닫힘", API 테스트 "공개 전", "가장 최근 완성 회차" |
| §5 공개를 다시 해도 같은 결과, 공개 커밋과 실행 기록 저장이 다른 순간 | 완성된 회차는 다시 공개하지 않고(R-09), 어긋난 실행 기록은 운영 절차로 정리한다 | Job 테스트 "커밋 뒤 실행 기록만 남은 경우" |
| §5 revision 명시적 증가, 같은 기간 직렬, 오래된 실행이 공개를 되돌리지 않음 | 마지막 회차 + 1, 계산 중 회차 없음, 기본키로 막고(R-16), 공개본은 가장 최근 완성 회차다(R-13) | Job 테스트 "회차 번호", "계산 중 회차가 있는 기간", "같은 기간의 다른 회차 동시 실행", "같은 회차의 동시 실행" |
| §5 API가 한 회차의 행만 읽음 | 두 번 나눠 읽는다(R-22) | API 테스트 "가장 최근 완성 회차" |
| §6 chunk 2, 상품 9 직전 실패, 같은 JobInstance로 상품 9부터 이어서 완료 | 순위 Step을 chunk 2로 실행하고 3위를 쓰는 묶음에서 실패시킨다. 점수 순으로 읽으므로 세 번째 아이템은 상품 9가 아니라 상품 8이다. 같은 JobInstance로 다시 실행하면 점수 고정은 건너뛰고, 순위는 이어 가지 않고 1위부터 다시 매긴다(R-30) | "실패와 다시 실행" |
| §6 checksum 규칙, 실행 ID는 따로 기록, 정상 실행과 각각 비교 | 결과 checksum만 둔다(R-10). 점수를 고정한 실행 ID를 회차 정보에 남긴다(R-18). 정상 실행은 독립 테스트다(R-19) | "실패와 다시 실행", "정상 실행과의 비교" |
| §7 실제 이벤트부터 API까지, 재발행해도 늘지 않음, 늦은 구매, 새 revision 재계산 | 로컬 검증 도구로 확인한다(R-19) | 로컬 연결 확인 |
| §7 구간 경계, 빈 주, 미공개, 삭제 상품 제외 | 각 앱 테스트의 고정 시계와 fixture로 확인한다(R-19) | Job 테스트 "기간 경계", "빈 기간", API 테스트 "공개 전", "삭제 상품" |
| §7 이어 가는 재시작과 새 revision 재계산을 구분 | 같은 회차를 다시 실행하면 고정한 점수로 순위를 다시 매겨 끝내고, 새 회차는 그 순간의 원본으로 다시 계산한다 | "실패와 다시 실행", Job 테스트 "회차를 올린 재계산", 로컬 연결 확인 4~8 |

## fixture

기간 `[2026-08-17T00:00:00Z, 2026-08-24T00:00:00Z)`의 구매 활동 네 줄이다.

| orderId | productId | quantity | confirmedAt |
|---|---|---|---|
| 42 | 7 | 2 | 2026-08-17T01:00:00Z |
| 42 | 8 | 1 | 2026-08-17T01:00:00Z |
| 43 | 7 | 3 | 2026-08-18T01:00:00Z |
| 44 | 9 | 5 | 2026-08-19T01:00:00Z |

| 기대값 | 값 |
|---|---|
| 점수와 순위 | 상품 7 = 5점 1위, 상품 9 = 5점 2위, 상품 8 = 1점 3위 |
| 결과 checksum | `745d50bbd2f04a2e8c937f9ebf5f2cddbf75b958540e964934a424903b0a67d2` |

한 줄로 주문 42의 두 품목이 모두 들어갔는지, 동점(상품 7과 9)을 상품 ID로 정렬했는지 함께 확인한다. checksum 직렬화는 [규칙 문서](weekly-ranking.md#checksum)를 따른다. 기대 checksum은 기대 점수와 순위에서 직접 만든 값이다.

## 실패와 다시 실행

순위 Step을 chunk 2로 실행하고, 3위를 쓰는 묶음에서 한 번 실패시킨다. 고정한 점수를 점수 순으로 읽으면 상품 7, 9, 8 순서라 첫 묶음이 1·2위, 둘째 묶음이 3위다. chunk 크기는 테스트 설정 `weekly-ranking.chunk-size=2`로 주고, 실패 스위치도 테스트 설정이며 식별 파라미터가 아니다. 테스트를 시작할 때 업무 테이블과 Batch 실행 기록을 한 번 비우고, 두 실행 사이에는 비우지 않는다. `DatabaseCleanUp`은 엔티티 테이블만 비우므로 실행 기록은 `JobRepositoryTestUtils`로 지운다.

| 순서 | 동작 | 확인 |
|---|---|---|
| 1 | `periodStart=2026-08-17, revision=1`로 실행, 3위를 쓰는 묶음에서 실패 | 첫 JobExecution `FAILED`. 점수 고정 Step `COMPLETED`, 순위 Step `FAILED`, 공개 Step은 실행되지 않았다 |
| 2 | 첫 실행이 끝난 뒤 새 연결로 조회 | 회차 1은 `CALCULATING`이고 결과 checksum은 비어 있다. 점수 세 행은 기대값과 같고, 순위는 상품 7 = 1위, 상품 9 = 2위만 있으며 상품 8은 비어 있다. 순위 Step의 실행 기록에는 reader 위치가 없다 |
| 3 | 같은 기간의 상품 9 구매 활동(수량 2)을 원본에 더한다 | 점수를 고정한 뒤 도착한 늦은 구매다 |
| 4 | 실패 스위치를 끄고 같은 파라미터로 다시 실행 | 같은 JobInstance, 새 JobExecution, `COMPLETED`. 새 JobExecution에는 점수 고정 StepExecution이 없다. 순위 StepExecution은 읽기 3건, 쓰기 3건이다 |
| 5 | 다시 실행 결과 | 점수와 순위가 기대값과 같고 결과 checksum이 기대 checksum과 같다. 늦은 구매는 들어가지 않아 상품 9는 5점이다. 회차 정보의 계산 시각과 점수를 고정한 실행 ID는 첫 JobExecution에서 넣은 값 그대로다 |

4의 읽기·쓰기 3건이 순위를 이어 가지 않고 처음부터 다시 매겼다는 증거다. 5가 기대값과 같다는 것은 처음부터 다시 매겨도 결과가 같다는 증거다.

## 정상 실행과의 비교

정상 실행은 위 시나리오와 다른 독립 테스트다. 업무 테이블과 Batch 실행 기록을 비운 DB에서 같은 fixture를 chunk 2로 한 번에 실행하고, 결과가 기대 점수·순위, 기대 결과 checksum과 같은지 확인한다. 두 테스트가 같은 기대 checksum과 같으므로 정상 실행과 실패 뒤 다시 실행의 결과도 서로 같다.

## commerce-batch Job 테스트

### 점수 고정

| 장면 | 준비·실행 | 기대 |
|---|---|---|
| 기간 경계 | 확정 시각이 `2026-08-16T23:59:59.999999Z`, `2026-08-17T00:00:00Z`, `2026-08-23T23:59:59.999999Z`, `2026-08-24T00:00:00Z`인 활동 | 가운데 둘만 2026-08-17 기간 점수에 들어간다 |
| 빈 기간 | 구매 활동이 없는 기간 | 회차 정보 `COMPLETED`, 점수 0행, 결과 checksum은 빈 문자열의 SHA-256. 순위 Step은 읽기 0건이다 |
| 잘못된 원본 | 그 기간 원본에 수량 0인 활동 | 점수 고정에서 실패하고, 점수와 회차 정보 모두 없다. 그 활동을 논리 삭제한 뒤 같은 파라미터로 다시 실행하면 성공 |
| 논리 삭제된 활동 | fixture에 더해 그 기간의 상품 9 활동(수량 3)을 하나 넣고 논리 삭제한다 | 점수에 들어가지 않는다. 상품 9는 5점이다 |
| 점수 고정 중 실패 | 점수를 넣은 뒤, 회차 정보를 넣기 직전 한 번 실패 | 점수 행도 회차 정보도 없다. 점수를 넣은 뒤 실패했으므로, 남은 것이 없다는 사실이 한 트랜잭션이라는 증거다. 같은 파라미터로 다시 실행하면 점수 고정부터 다시 돌아 기대값과 같다 |
| 점수 고정 중 checked 예외 | 점수 고정 Tasklet이 점수를 넣고 회차 정보를 넣은 뒤 checked 예외를 던진다 | Job이 실패하고 점수와 회차 정보 모두 없다. Step 트랜잭션이 모든 예외에서 롤백하는지 보는 장면이다 |
| 원본을 잠그지 않음 | Job 실행 중 점수를 넣은 직후, 커밋 전에 붙잡아 둔다. 그동안 다른 연결로 같은 기간의 구매 활동을 짧은 잠금 대기 제한으로 INSERT | INSERT가 잠금을 기다리지 않고 끝난다. 그 활동은 이 회차에 들어가지 않는다. Step의 격리 수준 설정을 지우면 이 테스트가 잠금 대기 시간 초과로 실패하는지 한 번 확인한다 |
| 계산 시각 | 테스트 시계를 `2026-08-24T06:00:00Z`로 두고, 점수를 넣는 순간 시계를 1분 옮긴다 | DB의 계산 시각이 UTC 기준 `2026-08-24 06:01:00.000000`이다. 점수를 넣은 뒤에 읽었고, 9시간 밀리지 않는다 |
| 계산 중 회차의 점수 고정 | `CALCULATING` 회차와 그 점수가 있고 원본에는 그 기간의 활동이 더 있을 때, 점수 고정 Step만 실행 | 아무것도 쓰지 않는다. 점수, 계산 시각, 점수를 고정한 실행 ID가 그대로다 |

### 순위 매기기와 공개

| 장면 | 준비·실행 | 기대 |
|---|---|---|
| 남아 있던 순위 | `CALCULATING` 회차에 상품 8 = 1위, 상품 7 = 2위처럼 기대와 다른 순위가 남아 있을 때 그 회차로 Job을 실행. 점수 고정은 계산 중 회차라 그대로 지나간다 | 남아 있던 순위를 비우고 기대 순위를 쓴다. 비우기를 지우면 순위 유일 제약에 걸려 실패하는지 한 번 확인한다 |
| 순위가 빠진 회차 | `CALCULATING` 회차에서 순위가 빈 점수가 있을 때, 순위가 2부터 시작할 때, 1·3처럼 끊길 때 각각 공개 Step만 실행 | 셋 다 실패하고, 회차는 `CALCULATING`이며 결과 checksum은 비어 있다 |

### 회차와 다시 실행

| 장면 | 준비·실행 | 기대 |
|---|---|---|
| 회차 번호 | 회차 1이 없는 기간에 회차 2로 실행. 회차 1을 닫은 뒤 회차 3으로 실행 | 둘 다 실패하고 아무것도 남지 않는다. 닫은 회차도 번호에 포함되므로 그다음에 회차 2는 실행된다 |
| 계산 중 회차가 있는 기간 | 회차 1을 순위 매기기에서 실패시켜 `CALCULATING`으로 남긴 뒤 회차 2로 실행 | 회차 2는 점수 고정에서 실패하고 아무것도 남지 않는다. 회차 1을 이어서 완성한 뒤에는 회차 2가 성공한다 |
| 커밋 뒤 실행 기록만 남은 경우 | 회차 1을 완성한 뒤, Job과 세 Step의 실행 기록을 모두 `STARTED`로 되돌린다. 완성된 회차에서 세 Step이 모두 다시 도는 경우다. 점수 고정을 커밋한 직후 죽어 계산 중 회차가 남은 경우는 "계산 중 회차의 점수 고정"과 "남아 있던 순위"가 본다. Step 기록이 완료로 남아 있으면 다시 실행할 때 그 Step을 건너뛰어 확인이 돌지 않는다 | 같은 파라미터의 실행이 거절된다. `STARTED`인 실행 기록만 `FAILED`와 종료 시각으로 정리하고 다시 실행하면, 세 Step이 다시 돌지만 이미 완성된 회차라 아무것도 쓰지 않고 완료된다. 순위 Step은 읽기 0건이다. 점수, 순위, 계산 시각, 결과 checksum, 점수를 고정한 실행 ID가 그대로다 |
| 같은 기간의 다른 회차 동시 실행 | 회차 1을 완성한 뒤, 회차 2를 점수를 넣은 직후 커밋 전에 붙잡아 두고 그동안 회차 3을 실행 | 회차 3은 실패한다(마지막 회차가 1로 보임). 회차 2가 끝난 뒤 회차 3을 실행하면 성공한다 |
| 같은 회차의 동시 실행 | 회차 1을 점수 고정 커밋 전에 붙잡아 둔 동안 같은 파라미터로 실행 | 두 번째 실행이 거절된다. 회차 1은 하나만 완성된다 |

| 회차를 올린 재계산 | 이어서 회차 2로 실행 | 회차 2에만 추가한 활동이 들어간다. 회차 1의 행은 그대로이고, 공개본은 회차 2다 |

### 닫기

| 장면 | 준비·실행 | 기대 |
|---|---|---|
| 최근 회차 닫기 | 회차 1, 2를 완성한 뒤 회차 2를 `CANCELLED`로 닫는다 | 회차 2의 행은 남고, 그 기간의 공개본은 회차 1이다 |
| 닫은 회차 다시 실행 | 닫은 회차 2를 같은 파라미터로 다시 실행한다. 따로, 회차 2를 완성한 뒤 실행 기록이 `STARTED`로 남은 상태에서 회차 2를 닫고, 실행 기록을 정리해 다시 실행한다 | 앞의 경우는 완료된 작업이라 거절된다. 뒤의 경우는 점수 고정의 상태 확인에서 실패한다. 둘 다 아무것도 쓰지 않는다 |
| 닫은 뒤 새 회차 | 회차 3으로 실행 | 성공한다. 닫은 회차도 번호에 포함되므로 회차 2로는 실행할 수 없다 |
| 계산 중 회차 닫기 | 회차 1을 순위 매기기에서 실패시켜 `CALCULATING`으로 남긴 뒤 닫는다 | 점수 행은 남는다. 회차 1을 같은 파라미터로 다시 실행하면 순위 Step은 읽을 행이 없고 공개에서 실패하며, 아무것도 쓰지 않는다. 회차 2로 실행하면 성공한다 |
| 묶음 사이에 닫힘 | 첫 묶음이 커밋된 직후, 둘째 묶음이 페이지를 읽기 전에 다른 연결로 그 회차를 닫는다 | 둘째 묶음은 읽을 행이 없어 순위 Step이 `COMPLETED`(읽기 2, 쓰기 2)로 끝나고 공개에서 실패한다. 회차는 `CANCELLED`이고 상품 8의 순위는 비어 있다. 같은 파라미터로 다시 실행하면 순위 Step은 건너뛰고 공개에서 다시 실패하며 아무것도 바뀌지 않는다. Reader의 상태 조건을 지우면 둘째 묶음이 상품 8을 읽어 실패하는지 한 번 확인한다 |
| 쓰기 직전에 닫힘 | 둘째 묶음을 읽은 뒤 쓰기 직전에 다른 연결로 회차를 닫는다 | 둘째 묶음에서 실패하고 그 묶음은 롤백된다. 회차는 `CANCELLED`이고 상품 8의 순위는 비어 있다. Writer의 상태 조건을 지우면 상품 8에 순위가 써지는지 한 번 확인한다 |
| 공개 직전 닫힘 | 공개가 checksum을 만든 뒤 완성으로 바꾸기 전에, 다른 연결로 그 회차를 닫는다 | 공개가 실패하고 회차는 `CANCELLED`, 결과 checksum은 비어 있다 |
| 닫은 회차는 다시 닫히지 않는다 | 이미 `CANCELLED`인 회차에 닫기 SQL을 다시 실행 | 바뀌는 행이 없다 |

## commerce-api 테스트

배치가 남기는 모양 그대로 회차 정보와 점수·순위를 fixture로 넣고 실제 HTTP로 확인한다. 계산 중 회차는 결과 checksum이 비어 있고 순위가 일부만 있다.

| 장면 | 준비·실행 | 기대 |
|---|---|---|
| 공개본 조회 | fixture 결과를 회차 1로 완성 | `PUBLISHED`, 기간, `revision`, `calculatedAt`(JSON 문자열까지 UTC), 상품 7·9·8의 순위와 점수, 현재 상품 정보 |
| 공개 전 | 회차 정보가 없거나, 계산 중이거나 닫힌 회차만 있음 | `NOT_PUBLISHED`, `revision`과 `calculatedAt`은 `null`, 빈 목록 |
| 0건 완성 회차 | 순위 0행인 완성 회차 | `PUBLISHED`, 회차 정보, 빈 목록 |
| 가장 최근 완성 회차 | 회차 1, 2를 완성하고 회차 3은 계산 중 | 회차 2의 결과만 보인다. 회차 2를 닫으면 회차 1의 결과가 보인다 |
| 삭제 상품 | 상품 9를 삭제 | 상품 7(1위), 상품 8(3위). 순위 행은 그대로 남는다 |
| 거른 뒤 limit | 상위 상품 일부를 삭제하고 `limit=2` | 남은 상품 중 계산 순위 순으로 두 개 |
| 입력 검증 | `periodStart` 누락, 형식 오류, 날짜 뒤 시간대 표기(`2026-08-17Z`, `2026-08-17+09:00`), 월요일 아님, `limit` 0·101 | `400 Bad Request` |
| 미래 기간 | 아직 오지 않은 월요일 | `NOT_PUBLISHED` |

## 로컬 연결 확인

과제 7절의 연결 확인이다. 6·7주차의 [로컬 검증 도구](../../verification/order-confirmed-event/README.md)와 같은 방식으로 실제 앱을 띄우고 흐름을 돌렸다. 이번 도구와 실행 결과는 저장소에 올리지 않고 로컬에 둔다.

모든 앱이 실제 시계로 돈다. 도구는 실행하는 주의 UTC 월요일을 기간으로 쓰고, 주가 끝나기 30분 전부터는 실행하지 않는다. 한국 시간 월요일 09:00 전후에 주문이 서로 다른 주로 갈라지면 "같은 주의 늦은 구매"가 성립하지 않기 때문이다. 배치는 주중에 계산하게 되지만, 잡은 실행 시각을 검사하지 않으므로 연결 확인에는 영향이 없다.

배치는 `weekly-ranking.chunk-size=2`로 실행해 상품 세 개의 순위가 두 묶음으로 나뉘게 한다. chunk 크기는 앱 설정이고 잡 파라미터가 아니라서 JobInstance 식별에 영향이 없다.

| 순서 | 동작 | 확인 |
|---|---|---|
| 1 | `commerce-api`, `commerce-streamer`, Kafka, MySQL, 테스트 PG 실행 | 각 앱이 같은 DB와 broker를 쓴다 |
| 2 | 기존 주문·결제 API와 테스트 PG 성공으로 주문 세 건 확정 | Outbox, Kafka record, 구매 활동이 생긴다 |
| 3 | 같은 이벤트를 다시 발행: Outbox에 저장된 같은 key와 payload를 Kafka에 한 번 더 보낸다 | 구매 활동이 늘지 않는다 |
| 4 | 격리 DB에 3위를 쓰는 순간 실패하는 트리거를 걸고, `commerce-batch`를 다음 회차로 실행한다 | JobExecution `FAILED`. 회차는 `CALCULATING`이고 1·2위만 매겨졌다. API는 `NOT_PUBLISHED`다 |
| 5 | 같은 주에 주문 하나를 더 확정 | 구매 활동에는 생긴다. 점수를 고정한 뒤 도착한 늦은 구매다 |
| 6 | 트리거를 지우고 같은 파라미터로 다시 실행 | 같은 JobInstance로 완료된다. 점수 고정은 건너뛰고, 순위 Step은 세 상품을 처음부터 다시 매긴다. API는 이 회차를 보여 주고, 5의 주문은 들어 있지 않으며, 재발행한 주문의 점수는 한 번만 센 값이다 |
| 7 | 같은 파라미터로 다시 실행 | 완료된 작업이라 거절되고, 결과는 그대로다 |
| 8 | 다음 회차 실행 | 공개 전에는 6의 회차, 공개 뒤에는 늦은 구매가 들어간 새 회차가 보인다 |

4~6이 과제 7절의 "고정 뒤 늦은 구매가 도착해도 현재 입력·재시작 결과는 바뀌지 않는다"를 실제 이벤트로 보여 주는 부분이다. 4에서 점수 고정은 이미 커밋됐으므로, 6은 원본을 다시 읽지 않고 고정한 점수로 순위를 처음부터 다시 매긴다. 트리거는 3위를 쓰는 순간 DB 오류를 내므로 그 묶음만 롤백되고, 앞 묶음의 1·2위와 고정한 점수는 남는다. 6은 남아 있던 1·2위를 비우고 다시 쓴다. 도구가 띄운 격리 DB에서만 걸고 지우므로 앱에는 연결 확인용 코드가 없다. 7·8은 완성한 회차를 같은 파라미터로 다시 실행해도 그대로이고, 늦은 구매는 새 회차에만 들어간다는 것을 보여 준다.

기대값은 실제로 만든 주문의 수량으로 계산한다. 실제 시계로는 정확히 경계 순간에 주문을 확정할 수 없어서, 경계·빈 기간·공개 전·삭제 상품은 위의 각 앱 테스트에서 고정한 테스트 시계와 fixture로 확인한다. 같은 이벤트는 Outbox에 저장된 key와 payload를 Kafka에 한 번 더 보내 재전달을 만든다. 7주차 규칙대로 Outbox 행을 직접 `PENDING`으로 덮어쓰지 않는다. 도구는 그 기간의 마지막 회차를 읽어 다음 번호로 실행한다. 실행마다 격리 DB를 새로 띄우므로 회차는 1, 2가 된다.

| 순위 Step의 순위 비우기 listener를 뺌 | "남아 있던 순위"가 `Duplicate entry '2026-08-17-1-2' for key 'weekly_ranking_scores.uk_weekly_ranking_scores_revision_rank'`로 실패 |
| 점수 고정 Step의 `READ_COMMITTED` 설정을 뺌 | "원본을 잠그지 않음"이 잠금 대기 시간 초과로 실패 |
| 순위 Writer의 `status = 'CALCULATING'` 조건을 뺌 | "쓰기 직전에 닫힘"에서 닫힌 회차에 3위가 써지고 순위 Step이 `COMPLETED`로 끝나 실패 |
| 공개 전 순위 확인을 항상 통과로 바꿈 | 순위 확인 단위 테스트와 공개 테스트 3건이 실패 |
| 점수 고정에서 시계를 점수 INSERT 앞에서 읽음 | "계산 시각" 테스트가 `expected 06:01 but was 06:00`으로 실패 |
| 점수 고정 Step의 롤백 규칙을 일반 `DefaultTransactionAttribute`로 둠 | "점수 고정 중 checked 예외"에서 예외를 삼키고 커밋한 뒤 Tasklet을 다시 불러 Job이 `COMPLETED`로 끝나 실패 |
| 순위 Reader의 `status = 'CALCULATING'` 조건을 뺌 | "묶음 사이에 닫힘"에서 둘째 묶음이 상품 8을 읽고 Writer에서 막혀 순위 Step이 `FAILED`가 되어 실패 |
| 순위 Reader를 위치를 저장하게(`saveState(true)`) 바꿈 | 실패한 순위 Step의 실행 문맥에 `frozenScoreReader.read.count`가 생겨 "실패와 다시 실행"이 실패 |

## 확인하지 않는 범위

| 항목 | 이유 |
|---|---|
| 여러 앱을 잇는 자동 테스트 | 연결은 로컬 검증 도구로 확인하고 `check`에는 넣지 않는다. 연결 확인은 실제 시계로 돌리고, 경계 순간은 각 앱 테스트의 고정 시계로 확인한다 |
| 처리량, 점수 고정 트랜잭션의 길이, chunk 크기 | 측정하지 않았다. 점수를 넣는 한 문장의 로컬 소요 시간(구매 100만 건, 상품 1,000개에 0.3초 안)은 설계를 정할 때의 참고 값이고 운영 수치가 아니다. chunk 크기 기본값 100도 측정한 값이 아니다 |
| 같은 새 회차를 두 실행이 거의 동시에 커밋하는 경쟁 | 기본키가 막는 설계이고, 테스트는 한 실행을 붙잡아 두는 방식으로 규칙만 확인한다 |
| 원본 확인과 점수 넣기 사이에 들어온 잘못된 행 | `READ_COMMITTED`라 놓칠 수 있다. 규칙 문서의 한계로 적었다 |
| 정기 실행의 대기 시간과 스케줄러 | 아직 정하지 않았다 |
