## A.33 PG 단독 실행 앱으로의 전환

**상태·문제:** 2026-10-25 사용자가 방향과 아래 결정을 승인했다. 상세 설계(2.10·5.7)는 같은 날 사용자 검토를 마쳤고 R1~R5로 구현·검증했다(근거는 4.5). 구현 중 callbackSent 집계 시점을 결과 완료 뒤로 바꾸는 결정을 추가로 받았다(5.7). A.31에서 PG를 commerce-api 테스트 소스의 fixture로만 두어 commerce-api를 직접 실행하면 PG가 없었다. 그래서 confirm이 UNKNOWN·예약 유지로 남고, 회로가 열린 뒤에는 미발송 실패가 되어 결제가 확정되는 경로가 없었다(코드 흐름으로 확인, 실제 실행 확인은 아님). 또 fixture에 PG 기능과 테스트 장애 주입·관측·수명 관리가 섞여 읽기 어렵다는 사용자 의견이 있었다. 사용자가 직접 실행 확인을 요구해 A.31의 재검토 조건("직접 앱 시연 요구")에 해당했다.

|선택|이유·대안이 유리한 조건|포기한 것·비용·재검토|
|---|---|---|
|새 모듈 `apps/pg-simulator`의 단독 실행 앱. 테스트도 같은 코드를 같은 JVM에서 시작|수동 실행과 테스트가 한 PG 구현을 공유한다. 라이브러리로만 옮기면 직접 실행 문제를 풀지 못한다|모듈·실행 설정 관리가 늘어난다. 실습 문서의 "별도 PG 제품을 만들지 않는다"는 안내와 거리가 생기므로 범위를 5.5 계약·메모리 저장·관리 화면 없음으로 제한한다|
|JDK `HttpServer` 유지(Spring MVC 아님)|테스트 안에서 객체로 바로 시작·종료할 수 있고, commerce 컴포넌트 스캔과 충돌할 걱정이 없다. 검증된 5주차 코드를 옮길 수 있다. MVC는 코드가 짧고 yml·로그 구성이 익숙하다는 장점이 있다|경로·JSON·검증 코드를 직접 작성한다. 실행 인자 해석과 로그 구성을 직접 만든다. 장애 주입을 프록시로 빼서 남는 handler가 작아진다는 판단에 기댄다. handler가 다시 커지면 재검토|
|PG main에는 PG 동작과 확장점(결과 정책, 저장소 접근, 콜백 전송기)만 두고 테스트 조작은 commerce-api 테스트 래퍼에 둠|main에 테스트용 조작 코드를 섞지 않는다. 대안인 "main의 public 제어 메서드"는 구조가 한 단계 짧다|래퍼·프록시·정책 구현이 테스트 쪽에 생긴다. 확장점의 모양을 테스트 요구에 맞춰 유지해야 한다|
|장애 주입(DELAY·GATE·CLOSE_EARLY·RAW)을 PG 앞의 테스트 프록시로 분리|네트워크 장애는 PG 기능이 아니다. 프록시가 PG의 실제 응답 뒤에 개입하므로 "거래 효과 뒤 응답 손상" 순서가 그대로 재현된다. 대안인 PG 내부 hook은 main에 테스트 seam을 남긴다|HTTP 한 단계가 늘고, createOutcome과 reply의 소비 정렬 규칙(5.7)이 필요하다. 같은 orderId에 plan 여러 개 + 동시 생성이면 두 FIFO의 짝이 엇갈릴 수 있다(plan을 나눠 새로 생긴 제약, 5주차 fixture에는 없었음). 이 경우 테스트가 순차 전송·gate로 순서를 통제한다. 대안인 "프록시가 plan을 통째로 꺼내 결과를 헤더로 PG에 전달"은 엇갈림이 없지만 PG main이 테스트 헤더를 읽게 되어 채택하지 않았다(2026-10-25 사용자 결정). commerce는 같은 주문에 생성 POST를 한 번만 보내므로 드문 조합으로 판단했고, R3에서 그런 테스트가 여럿 나오면 재검토한다|
|pg-simulator만 일반 jar를 켜서 commerce-api가 `testImplementation`으로 의존|모듈 하나로 끝난다. 대안인 핵심 라이브러리 모듈 분리는 정석적이지만 모듈이 2개가 된다|앱 모듈을 라이브러리처럼 쓰는 예외가 생긴다. 실제 classpath 포함은 R1에서 확인하며, 안 되면 분리 대안을 다시 정한다|
|수동 실행 결과는 `amount % 3`(0 PENDING→SUCCESS, 1 즉시 SUCCESS, 2 PENDING→FAILED)|요청 하나로 세 경로를 고를 수 있고 계약 변경이 없다. 1의 자리 규칙은 흔한 가격(끝자리 0)이 모두 기본 경로로 가서 다른 경로를 고르기 어렵다. 카드번호 선택은 5.5의 합성 카드 값 계약을 바꿔야 한다. 설정 전환은 경로를 바꿀 때마다 재시작해야 한다|금액만 보고 경로를 바로 알기 어렵다(계산 필요). 원하는 경로에 맞춰 상품 가격·수량을 정해야 한다|
|422 생성 전 거절은 금액 규칙에서 제외|실습 문서의 422 요구는 HTTP 계약 테스트·업무 시나리오 테스트이며 수동 시연은 요구하지 않는다. 응답 코드는 PG main에 있어 테스트가 정책으로 고른다|수동 실행에서는 422 경로를 볼 수 없다. 수동 확인 요구가 생기면 규칙 추가를 검토|
|자동 처리 지연 기본 1초, 설정 가능(0 허용)|사람이 PAYMENT_PENDING을 조회로 관찰할 시간을 준다. 정합성은 지연과 무관하게 콜백 권위 조회·공통 결과 반영으로 지킨다(2.10)|운영 PG의 처리 시간을 흉내 내지 않는다. 테스트는 자동 처리를 끄므로 이 값의 영향을 받지 않는다|
|자동 콜백 1회, 재전송 없음. 즉시 SUCCESS에도 전송|실제 PG처럼 중복 알림의 무효과를 수동으로도 볼 수 있다. 재전송이 없으므로 콜백 유실 → reconcile 회복 경로를 수동으로 확인할 수 있다|commerce가 꺼져 있던 동안의 결제는 사용자가 reconcile을 호출해야 확정된다|

**바뀌지 않는 것:** 5.5 PG HTTP 계약, commerce-api main 코드·설정(기본 base URL 18080을 PG 앱 기본 포트로 맞춤), 5.7의 테스트 제어 메서드 의미·콜백 판정·재시작 절차, 기존 테스트의 기대값.

**재검토 조건:** R1에서 plain jar 의존이나 `bootRun`이 동작하지 않을 때, R2에서 프록시가 5.7 의미(특히 CLOSE_EARLY·GATE 타이밍)를 재현하지 못할 때, R3에서 기존 테스트가 기대값 변경 없이 통과하지 못할 때 해당 선택을 사용자와 다시 정한다. 결과 근거는 6주차 진행 기록과 4.5에 남긴다.
