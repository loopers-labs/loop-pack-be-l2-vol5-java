# 쿠폰 발급 설계 판단

## 상태와 문서 역할

쿠폰 발급의 문제·제약·선택·대안·비용을 기록한다. 현재 계약의 원본은 [쿠폰 상세설계](../features/coupons.md)이며 CQ16은 대기실/등록 제한, CQ17은 기발급·품절 캐시의 승인 판단이다. CQ15/§11은 대체된 구안이다. `0e53078` 기준 구현·전체 검사와 통제된 실제 Redis 장애/수동 재개 검증은 [쿠폰 실행 기록](../verification/coupons.md)을 따른다. 아래 후속 합의 문단의 미정·구현 전 표현은 당시 논의 이력이며 최신 계약을 덮어쓰지 않는다. 비교 실험은 사용자 선택으로 중단해 성능 개선량은 주장하지 않는다. CQ 식별자는 이 문서의 판단 식별자다.

## CQ1. 행사·발급 결과·현재 실행의 분리

**문제:** 발급 총량을 지키는 것과 현재 처리할 실행 수를 제한하는 것은 서로 다른 책임이다. 처리 자리 반환으로 쿠폰 재고를 복구하면 발급 총량이 깨지고, 누적 발급 수를 현재 점유로 사용하면 자리가 영구 소진된다.

**선택:** 캠페인 한도·사용자 중복·실제 쿠폰은 DB, 현재 신규 발급 실행 점유는 Redis Set이 책임진다. C는 캠페인별이 아니라 신규 발급 경로 전체의 공통 값이다. 같은 사용자의 동시 HTTP 실행도 token을 공유하지 않으며 DB 효과만 하나로 만든다.

**대안·범위:** 동기 발급과 즉시 거절을 선택한다. 대기열·비동기 worker는 추가하지 않는다. 요청률 제한은 CQ15의 별도 추가 기능으로 구분한다. 정확한 전역 도착 순서와 DB 자원 풀 격리를 보장하는 구조는 아니다.

**비용:** 초과 요청은 재요청이 필요할 수 있다. 정상 Redis의 원자 수용이 장애 전환 전체의 안전성을 증명하지 않는다.

## CQ2. 캠페인 준비: CRUD 대신 테스트 fixture와 로컬 준비 코드

**문제:** 자동 테스트의 조건 준비와 일반 앱을 실행한 수동 API 확인을 모두 지원해야 한다. 테스트 소스의 fixture만으로 일반 실행 데이터가 준비되지는 않는다.

| 대안 | 얻는 것 | 비용·판단 |
|---|---|---|
| 캠페인 전체 관리 API | 실행 중 생성·수정 가능 | 총량 감소·혜택 수정·삭제와 기존 쿠폰 보존·접근 정책까지 필요. 제외 |
| SQL 준비 스크립트 | 직접 실행이 단순함 | 스키마 의존·도메인 검증 우회. 채택하지 않음 |
| **테스트 fixture + 명시적 로컬 준비 코드** | 검증 조건별 준비와 수동 실행 지원 | 별도 실행 수단을 관리하는 비용을 수용 |

준비 코드는 DB에 사용자·캠페인을 마련하는 수단이다. 이미 DB에 있는 ID로 발급 API를 호출할 수 있고 호출마다 새 캠페인을 만들 필요는 없다. ID·요청 예시 출력은 편의 수단이며 DB 직접 조회도 허용한다.

**실행 선택:** 기본 false인 `commerce.coupon.fixture.enabled`를 true로 명시한 앱 시작 때 ApplicationRunner로 한 번 준비한다. 별도 준비 앱보다 실행 절차를 줄이고 main의 옵션부 준비 구성을 관리하는 비용을 수용한다. 준비 코드 자체가 수용을 열지 않는다.

**기본 데이터·재실행:** 사용자 8명·활성 캠페인 1개·총량 5·정액 5000원·기발급 0의 작은 수동 확인 데이터를 선택한다. 200명/100장 같은 대량 기본 데이터 대신 자동 테스트 fixture가 각 검증의 규모·조건을 준비한다. 보존된 DB에서 준비를 다시 켜면 새 데이터를 추가하며 기존 이름으로 재사용·덮어쓰기하지 않는다. 별도 seed 식별/재사용 규칙을 줄이는 대신 반복 준비로 데이터가 늘어나는 비용을 수용한다. 기존 쿠폰·발급 수를 초기화하지 않는다.

**현재 설정의 제약:** local/test ddl-auto 기본값은 create다. 수동 확인에서는 실행 옵션으로 새 시작에 create, 기존 ID 재사용에 update를 선택한다. 공통 설정 파일의 기본값이나 자동 테스트 초기화를 일괄 변경하는 선택은 아니다. create에 따른 DB 재생성과 준비 코드의 보존 동작을 구분하며 운영 마이그레이션·재시작 복구를 보장하지 않는다. 구조·호출 예시는 상세설계 §9가 원본이다. 준비 실패는 기동 오류로 전달한다. 이번 준비 데이터의 미저장은 준비 TX의 rollback 확인에 근거하며, 앞서 수행한 스키마 재생성과 구분한다.

## CQ3. 사전 조회와 수용·오류 우선순위

**선택:** 사용자 식별·기존 쿠폰 사전 조회 뒤 신규 수용을 판단하고, 수용된 실행만 캠페인을 검증·발급한다. 기존 쿠폰은 비활성·품절보다 우선 반환하고, 쿠폰이 없으면 비활성을 품절보다 먼저 판단한다.

**대안:** 캠페인 사전 검증을 먼저 하면 캠페인 오류를 먼저 보여줄 수 있지만, 초과 요청에도 추가 DB 읽기를 수행하고 발급 TX에서 다시 검증해야 한다. 신규 발급 DB 자원 보호를 우선해 수용 판단을 먼저 한다. 따라서 없는/비활성 캠페인도 수용 거절이면 429·503이 먼저일 수 있다.

**FULL 이후 추가 조회:** 그사이 완료된 쿠폰을 찾아 반환하는 대안 대신 추가 조회 없이 429로 종료한다. 초과 요청의 DB 읽기를 늘리지 않는 대신, 결과가 생겼어도 이번 응답은 429일 수 있다. 다음 요청은 기존 결과를 조회할 수 있다.

### 사전 조회가 제한 밖인 비용

User 존재 확인과 기존 쿠폰 조회는 C로 보호하지 않는다. Redis를 먼저 두면 기존 결과 요청도 수용 거절·Redis 장애의 영향을 받는다. DB가 정상일 때 완료 결과를 유지하기 위해 사전 조회를 선택했다.

추가 보호 대안은 비교했으나 채택하지 않았다.

- 완료 결과 Redis cache: 반복 요청의 DB 읽기는 줄일 수 있으나 신규 사용자 miss와 Redis 장애 시 DB 조회는 남는다. commit 전 게시하면 rollback된 결과를 노출할 수 있다.
- 앞단 bulkhead: 사전 조회를 포함한 동시 실행을 제한할 수 있으나 별도 한도·거절/대기 정책·다중 인스턴스 합산 문제가 추가된다.

전체 유입·DB 자원 격리를 검증한 것으로 표현하지 않는다. 추가 보호가 필요하면 별도 목적·범위·검증을 정한다.

## CQ4. 최소 쿠폰 모델과 구조화된 혜택

**선택:** 캠페인 활성/비활성은 포함한다. 시작·종료 시각, 쿠폰 사용/만료 시각·여부, 별도 공개 UUID는 추가하지 않는다. 유한 총량 1 이상을 지원하고 무제한은 제외한다.

**대안·비용:** 시간 일정은 경계 시각·시간대·수동 비활성과의 관계가 필요하다. 사용·만료 필드는 현재 동작에서 판단할 기능이 없고, 저장된 만료 boolean은 시간 경과로 실제 상태와 어긋날 수 있다. UUID는 별도 공개 식별 요구가 없으며 소유권 검사를 대체하지 않는다. 무제한을 지원한다면 0·Long.MAX_VALUE를 겸용하지 않고 별도 표현·검증이 필요하다.

혜택은 설명 문자열만 두는 대안과 유형·값을 구조화하는 대안을 비교했다. 문자열은 단순하지만 계산에 사용할 수 없다. **정액/정률 + 수치**를 선택해 혜택의 의미와 단위를 명확히 한다. 정률은 정수 1~100%, 정액은 양의 원 단위 long이며 별도 업무 상한은 두지 않는다. 상품 가격 상한을 쿠폰에 그대로 적용할 근거는 없다.

실제 할인 적용·최소 주문액·최대 할인액·반올림은 범위 밖이다. 이 필드만으로 할인 기능이 완성되는 것은 아니다.

## CQ5. 혜택 snapshot, 캠페인 이름 참조, 물리 FK 없음

**선택:** 혜택 유형·값은 발급 당시 값을 쿠폰에 복사한다. 캠페인 이름은 복사하지 않고 발급·목록 응답에서 조회한다. 물리 FK 없이 campaignId/userId를 참조하고, 사용자·캠페인 유일 제약은 별도로 둔다.

**대안·반례:** 혜택을 현재 캠페인에서만 읽으면 과거 쿠폰의 혜택이 바뀌어 보일 수 있어 snapshot을 선택했다. 이름 snapshot은 과거 표시를 유지하지만 저장이 중복되고 오타 수정도 과거 쿠폰에 반영되지 않는다. 이름은 현재 값을 보여주는 쪽을 선택하고 응답 조회 비용·과거 표시 이름 변경을 수용한다.

FK를 두지 않는 대신 부모 존재 검증과 연결 손상 처리가 필요하다. FK 생략은 UNIQUE 생략이 아니다. 연결 손상으로 쿠폰이 조용히 누락되지 않게 하는 처리와 목록 인덱스는 상세 구체화안이다.

## CQ6. 조건부 UPDATE 선택과 동시 중복 처리

| 대안 | 이점 | 비용·판단 |
|---|---|---|
| 캠페인 SELECT FOR UPDATE 후 판단 | Entity 중심으로 상태·처리 순서를 표현하기 쉬움 | 선행 조회·잠금 대기·연결 점유. 채택하지 않음 |
| **조건부 UPDATE** | 활성·잔여량 확인과 수량 증가를 한 SQL로 표현 | 0건 분류·중복·혜택 조회 비용을 수용 |
| 낙관적 잠금 | 저충돌에서 충돌 감지 | version·충돌 처리/재시도 정책 필요. 도입하지 않음 |

쿠폰에는 기존 재고의 before/after History 보존 요구가 없으므로 그 비용을 그대로 적용하지 않는다. 수량 검사·증가를 한 SQL로 표현하는 조건부 UPDATE를 선택한다. 비관적 잠금보다 빠르다는 실측 결론은 아니다. 문제가 발견되면 명시적 잠금 조회를 설계에서 다시 비교하며 운영 요청 중 자동 전환하지 않는다.

조건부 UPDATE도 행/인덱스 잠금을 사용하므로 무잠금·무대기는 아니다. 동일 사용자의 동시 중복은 두 방식에 공통인 문제이며, 최종 중복 저장 방어는 유일 제약이다.

### INSERT 전 중복 재조회 생략

UPDATE +1 뒤 중복을 조회해 있으면 rollback하는 대안은 불필요한 쓰기·rollback을 일으킬 수 있다. 중복을 먼저 재조회하더라도 동시에 없음으로 판단하는 경쟁은 남는다.

**선택:** 사전 조회 뒤 쓰기 TX에서 중복 조회를 한 번 더 하지 않는다. UPDATE·INSERT를 수행하고 유일 제약으로 보호한다. 정상 경로 조회 비용을 줄이는 대신 충돌 시 rollback·결과 조회 비용을 수용한다.

- named unique 충돌: 전체 rollback 종료 확인 후 기존 쿠폰 조회·200. 다른 제약·연결 오류를 성공으로 변환하지 않는다.
- UPDATE 0건: 기존 쿠폰·캠페인 없음·비활성·품절을 판별한다. 같은 사용자의 앞 요청이 마지막 수량을 발급하면 뒤 요청은 유일 제약까지 도달하지 않을 수 있다.
- 모두 품절로 반환하는 대안은 기존 결과 200·캠페인 404·비활성 우선 계약과 충돌하므로 채택하지 않는다.

중복 충돌 뒤 조회와 UPDATE 0건 뒤 조회는 실패 결과를 확인하는 경로이며, 정상 발급 전 조회를 반복하는 경로와 구분한다. 동시 중복·마지막 수량·rollback에서 실제 효과와 응답 계약을 함께 검증한다.

## CQ7. 단일 TX 대안과 순차 TX 분리

사전 조회·Redis·발급을 하나의 TX로 수행하는 것도 가능한 대안이다. 두 방식 모두 발급 수 증가와 쿠폰 INSERT는 한 TX로 묶어야 한다.

| 대안 | 얻는 것 | 비용 |
|---|---|---|
| 단일 TX | 시작/종료 한 번, 단순한 범위 | 사전 조회 후 Redis 응답 대기 중 DB 연결 유지 |
| **사전 조회 TX 종료 → Redis → 발급 TX** | 거절될 요청이 Redis를 기다리며 DB 연결을 붙잡지 않음 | TX 시작/종료·연결 재획득 |

신규 발급 자원 보호를 위해 Redis 지연이 DB 연결 점유로 이어지는 것을 줄이는 분리를 선택했다. 성능 실측 결론은 아니다. 같은 요청 스레드에서 선행 TX 종료 뒤 다음 TX가 실행된다. 바깥 TX가 없으므로 기본 REQUIRED이며 REQUIRES_NEW·새 worker를 추가하지 않는다. 한 요청 전체가 단일 TX인 구조는 아니다. 실패 후 읽기는 필요한 경우에만 추가한다.

**실패 구분:** 콜백 진입 전 업무 SQL 미시작이 확인된 연결 획득 실패를 종료 불명으로 묶지 않는다. 500·자기 token 반환으로 끝내고 반환 정상이면 수용을 유지한다. 일시적 풀 획득 실패까지 전체 수동 복구로 연결하는 비용을 피한다. 반면 콜백에 진입해 종료 통지가 없거나 UNKNOWN이면 예외 종류보다 종료 판정을 우선하고, 앞선 불명을 후속 조회로 덮어쓰지 않는다. 관찰은 요청 내부의 진입/완료 정보이며 새 공유 실행 저장소가 아니다.

## CQ8. 클래스 수와 명명, TransactionTemplate

**제약:** 단순 전달 객체를 늘리지 않고 TX·Redis 접근·수용 상태 관리의 실제 책임을 구분한다.

- 별도 CouponTransactionService + 애노테이션 경계 대신 **Facade의 TransactionTemplate**을 선택한다. 클래스 수를 줄이고 범위를 직접 드러내는 대신 콜백·명시적 TX 코드가 Facade에 들어온다.
- 수용 조율은 application의 **CouponAdmissionService**다. 별도 Control을 추가하지 않는다.
- Redis 포트는 **CouponAdmissionRepository**, 구현은 **CouponAdmissionRedisRepository**다. 역할을 드러내는 Repository 명명을 사용한다.
- 실제 Redis 명령은 기존 redisTemplateMaster로 수행한다. 인터페이스·구현 분리는 기존 domain 포트/infrastructure 구현 구조를 따른다. Lua 자체가 별도 계층을 요구하는 것은 아니다.
- Facade에 master template을 직접 주입하는 것도 기술적으로 가능하며 그것만으로 ArchUnit이 반드시 실패한다고 주장하지 않는다. 현재 선택은 기존 책임·기술 의존 분리를 유지한다.
- 단순 전달용 운영 Facade를 추가하지 않고 두 Controller가 CouponFacade를 거치는 구조를 제안한다. 자기 호출로 @Transactional 프록시가 적용된다고 가정하지 않는다.

## CQ9. 캠페인 CHECK와 발급 시각

**선택:** 캠페인에 totalQuota 양수·issuedCount 비음수·총량 이하 CHECK를 추가한다. 애플리케이션 검증을 우회한 잘못된 쓰기도 DB가 거절하도록 한다. UNIQUE와 다른 역할이며 혜택 DB CHECK까지 추가하는 것은 아니다.

CHECK 평가 비용의 실제 영향은 측정하지 않았다. 이 제약만으로 실제 쿠폰 행 개수와 issuedCount가 일치하지는 않으므로 같은 TX가 필요하다. 위반은 품절·중복 성공으로 바꾸지 않는다.

발급 시각은 기존 `created_at`에 저장하고 목록 정렬에 사용한다. 생성 시각이 DB commit 시각이나 정확한 전역 도착 순번을 뜻하지 않는다. 보유 목록에서만 저장된 발급 시각을 `createdAt`으로 제공하며 UTC·ISO-8601·소수점 6자리·Z로 통일한다.

발급 응답에도 시각을 제공하는 대안을 검토했다. INSERT 뒤 DB 값을 읽으면 신규 발급마다 조회가 한 번 추가된다. 메모리 시각을 사용하면 저장 정밀도 차이가 응답에 나타날 수 있다. **발급 응답은 다섯 필드로 두고 시각은 보유 목록에서 제공**하기로 했다. 발급 응답용 시각 읽기와 최초/재요청 응답 간 시각 오차 규칙이 사라지고, 사용자에게 저장된 발급 시각을 보여주는 목록은 유지된다. 응답 계약과 검증은 상세설계 §4.1·Q2·Q15를 따른다.

## CQ10. 제어 API와 수동/자동 테스트 경로

내부 운영 객체를 IDE·테스트에서만 호출하는 방식은 구현이 작지만 실행 중 수동 조작이 불편하다. **공통 로직 + 제어 API + 자동 테스트**를 선택하고 API·접근 경계·실패 응답·검증 비용을 수용한다.

두 경로는 두 벌의 로직이 아니다. 수동 호출은 Controller를 통해, 자동 테스트는 같은 application 로직을 직접 호출한다. HTTP 계약도 검증하고 서로 다른 업무 규칙을 사용하지 않는다.

경로는 **/api/coupon/admission**이며 상태·닫기·정리·열기를 제공한다. 모든 프로필에서 동일하게 등록하고 별도 활성화 옵션·제어 키·관리자 로그인을 추가하지 않는다. local/test 전용 등록 대안 대신 환경별 동작을 동일하게 하는 선택이다. 기존 관리자 경로의 접근 규칙은 유지한다.

**비용·한계:** 현재 loopback 바인딩은 local/test에만 있으므로 그 제한이 없는 환경에서는 인증 없이 제어 API를 외부 호출할 수 있다. 이 노출을 수용한 선택이며 운영 인증·다중 인스턴스 안전성을 제공한 것으로 설명하지 않는다.

제어 API 사용 가능과 신규 발급 허용은 별개다. 신규 수용은 전 프로필 기본 닫힘이며 직접 실행에서는 열기 API, 자동 테스트에서는 같은 공통 열기 동작을 호출한다.

**수용량 설정:** commerce.coupon.admission.capacity 기본값은 전 프로필 3, 생략 시 기본값 적용, 유효하지 않은 명시 값은 기동 실패다. 신뢰한 시작 설정으로 관리하고 실행 중 변경 API를 추가하지 않는다. 재설정에 재시작이 필요하며 3을 최적 운영 용량으로 주장하지 않는다.

## CQ11. 반환 실패의 응답과 불확실성

**선택:** 발급 commit 확인 뒤 token 반환 실패는 쿠폰·issuedCount·성공 응답을 유지하고 오류를 기록하며 신규 수용을 닫는다. 해당 요청까지 503으로 덮어쓰는 대안은 실제 발급 결과를 오류처럼 알리는 비용이 있어 선택하지 않았다. 이후 기존 결과 조회는 200, 신규 수용은 닫힘 503이다.

**정상 첫 반환 0:** ACQUIRED 확인 뒤 처음 반환한 token이 없다면 기대 점유 부재를 관찰한 것이다. 구체 원인이 확정되지 않아도 결과 유지·로그·신규 수용 닫힘을 선택한다. 조용히 성공 처리하는 대안은 점유 유실 신호를 놓치는 비용이 있다. 반복 SREM/cleanup의 0은 멱등 정리로 정상 처리한다. 명령 반복 안전성과 정상 실행의 이상 감지를 분리하며 Map 같은 추가 추적 장치를 넣지 않는다.

**DB 종료 불명:** 해당 token만 유지하고 나머지 자리를 계속 받는 대안도 가능하지만, 실행 확인이 필요한 상태를 드러내기 위해 token 유지·전체 신규 수용 닫힘을 선택한다. 종료가 끝내 확인되지 않으면 수동 재개가 계속 보류되는 가용성 손실을 수용한다. Java 잠금이나 기존 실행 취소를 추가하는 선택은 아니다.

**COMMITTED 뒤 예외:** commit과 응답 값이 확보됐다면 성공 유지·예외 로그·종료 후 token 반환이다. 응답 값을 확보하지 못하면 500이며 저장 효과를 보존하고 재요청에서 확인한다. 예외만 보고 무조건 500으로 바꾸는 대안 대신 확인된 결과를 우선한다. 현재 별도 afterCommit 쿠폰 업무는 없으며 이 방어 규칙 때문에 새 후처리 기능을 추가하지 않는다. HTTP 응답 전송까지 성공을 보장하는 규칙도 아니다.

HTTP timeout·연결 종료는 DB 취소·종료 증거가 아니다. Redis 획득 timeout도 token이 추가되지 않았다는 증거가 아니므로 신규 DB 발급을 시작하지 않는다. DB 종료 불명에서 자리가 끝났다고 추측해 반환하지 않는다. TTL 회수·PONG만으로 자동 재개하지 않는다.

## CQ12. 종료 증거와 token 정리 분리, 전체 실행 추적 제외

**문제:** Redis token은 점유 표식이지 DB 작업 종료 증거가 아니다. 장애 후 안전한 정리를 위해 종료 근거와 제거 대상을 구분해야 한다. 정상 경로에 실행별 기록·갱신·동기화 비용을 추가할 필요성도 검토한다.

| 비교한 후보 | 이점·비용 | 판단 |
|---|---|---|
| 전체 실행 Map | 상세 상태·소유권 조회 편의. 모든 실행의 추가 등록·갱신·삭제와 동시성 관리, 재시작 유실 | 제외 |
| 캐시 라이브러리 | 관리 기능 제공 가능. 만료·퇴출은 작업 종료가 아니고 같은 유실 문제가 있음 | 제외 |
| DB 실행 기록 | 내구성·다른 인스턴스 조회. 추가 쓰기·TX·기록 실패 처리, 기록만으로 종료 증명 불가 | 제외 |
| 파일·로그에 의존한 자동 판정 | 별도 업무 테이블 없이 가능. 구체 증거·검증 절차가 없으면 판단 근거가 아님 | 자동 판정 방식으로 채택하지 않음 |
| Redis 추가 실행 상태 | 공유 가능. 장애·유실과 확인 자료가 함께 사라질 수 있음 | 제외 |
| 전역 진행 수·DB 불명 표시 | 전체 Map은 줄지만 갱신·동시성·유실 처리가 필요 | 제외 |
| read/write lock으로 종료 대기 | 표준 동기화 수단 사용. 추가 잠금 비용과 불명 처리 필요 | 제외 |
| 앱 실행 ID token prefix | 소유 범위 구분 가능. 종료 증거가 아니며 재시작·지연 명령 문제는 남음 | 추가하지 않음 |

Redis는 정리할 점유를 조회·조작하는 수단으로만 사용한다. 별도로 실행·DB 종료가 확인됐다면 복구된 Redis에서 자기 token을 제거할 수 있다. 쿠폰 COUNT 일치·로그 부재·카운터 0·PONG만으로 종료를 판단하지 않는다.

전역 실행 추적 없이 확인할 수 있는 범위에 맞춰 수동 절차를 선택한다. 확인되지 않는 경우 재개하지 않는다. 기본 닫힘과 종료 증거를 잃은 재시작 후 복구 보장은 다른 문제이며, 재시작 파일 표식·추가 복구 저장소는 도입하지 않는다.

## CQ13. 통제된 로컬 수동 확인 뒤 제어 API 호출

**선택:** 알려진 요청만 있는 동일 로컬 앱에서 운영자·테스트가 실행·DB 종료와 실제 결과를 확인한 뒤 정리·열기 명령 API를 호출한다. API가 모든 실행을 독립적으로 관찰해 자동 판정하는 기능은 추가하지 않는다.

| 대안 | 책임·비용 | 판단 |
|---|---|---|
| 전역 종료 자동 검사 API | 실행 상태 수집·동시성 처리가 필요. 잘못된 조작을 방어하는 범위가 넓음 | 제외 |
| **수동 확인 + 명령 API** | 전체 실행 추적을 줄임. 단일 앱·알려진 모든 요청·순차 운영 전제가 필요. 잘못된 조작을 API가 전부 막지는 못함 | 선택 |

정상 201/200·업무 거절 응답을 완료 근거로 사용하려면 동기 처리·TX 종료 뒤 응답이라는 계약을 통합 테스트로 먼저 입증한다. HTTP client future timeout은 서버 종료가 아니다. 서버 측 관찰이나 완료 뒤 응답을 연결하지 못하면 닫힘을 유지하고 정리·재개 성공으로 기록하지 않는다.

운영 가이드는 상세설계 §8.3이 원본이다. 적용 전제·요청 목록 대조·TX 완료 증거·DB 조회 SQL·token 선정·중단 조건을 실행 기록에 남긴다. 획득 불명·DB 종료 불명·반환 실패·정상 첫 반환 0에서 token·사용자·캠페인·실패 단계·확인된 결과를 반드시 로그로 남기며 모르는 결과는 불명으로 표기한다. Set 조회는 실제 master에 SMEMBERS를 직접 실행하고 replica·추가 조회 API·미사용 조회 포트는 사용하지 않는다. 상태값은 accepting 하나이며 해당 요청의 기존 token·TX 결과 처리는 유지한다. 별도 로그 DB·쿠폰 token 열·전체 실행 추적·추가 UUID는 도입하지 않는다.

Redis 호출 오류·불확실 응답을 관찰하면 코드에서 닫는다. 감지되지 않은 상태 유실까지 알아내는 탐지기는 없다. SREM 0의 맥락별 판단은 CQ11을 따른다. 반복 정리의 0과 정상 첫 반환의 기대 점유 부재를 구분한다.

늦은 SREM이 종료된 실행의 자기 token만 지울 수 있으면 실행·DB 종료 확인과 자기 점유 정리 뒤 재개한다. cleanup과 늦은 반환의 순서는 새 실행의 token에 영향을 주지 않으므로 Redis 연결 추적 없이 판단할 수 있다. Q9는 상세설계 §10.1의 같은 master 연결 후속 응답으로 선행 획득 명령 경과를 확인한 뒤 자기 token을 정리한다. 종류·영향이 불명확하거나 그 확인을 얻지 못한 명령은 닫힘 유지 사유다.

수동 절차의 명령·전제·중단 조건을 검증하며, 자동 종료 검사나 동시 운영 조작 조율을 보장한 것으로 표현하지 않는다. 실제 C=3 원자 수용·총량·반환 실패·닫힘·정리·재개와 기존 회귀 검증은 유지한다.

**한계:** 잘못된 token 지정·숨은 요청·동시 운영 조작·다중 인스턴스·앱 재시작 후 종료 증명은 보장 범위 밖이다. 운영 환경 확대가 필요하면 별도 계약·증거를 설계한다.

## CQ14. 공유 Redis 장애와 DB 종료 불명 검증의 분리

**Redis 대안·선택:** 전용 Redis는 장애 격리가 쉽지만 추가 환경이 필요하다. 기존 컨테이너를 재사용하고 다른 테스트와 직렬 실행하는 선택을 했다. 프록시·새 Redis는 추가하지 않는다. stop/start·재생성 대신 pause/unpause로 메모리를 유지한 통신 불가를 재현한다. 같은 컨테이너를 쓰는 테스트 전체가 영향을 받을 수 있으므로 실행 중첩 금지·finally 복구·실제 서버 작업 종료 확인 비용을 수용한다. 이 검증은 상태 유실·failover 안전성의 증거가 아니다.

**실제 지점 통제:** test 소스의 Repository decorator가 실제 ACQUIRED 이후·TX 전, 실제 수량 증가 이후·INSERT 전, 실제 commit 뒤·반환 전을 관찰한다. 제품 hook이나 전역 실행 기록은 추가하지 않는다. Q10은 §8.3의 조건으로 수동 정리·재개와 새 요청 수용을 확인한다.

**로컬 장애 검증의 실행 선택:** Q9·Q10은 현재 실행 중인 로컬 Redis를 pause하므로 명시 실행으로 둔다. 환경변수 COUPON_LOCAL_REDIS_FAULT_TEST=true와 기존 test 작업의 클래스 필터를 사용한다. 일반 회귀의 환경 의존·로컬 앱 간섭을 줄이는 대신 명시 실행과 실제 결과 기록이 필요하다. 비활성은 미실행이며 필수 검증 완료 판단에 명시 실행 결과를 포함한다. 명령의 --rerun·--no-build-cache와 작업/보고서 확인으로 과거 결과·최신 상태 판정이 실제 실행을 대체하지 않게 한다.

**Q9의 환경·정리 선택:** Q9·Q10은 같은 로컬 장애 검증 클래스와 Redis를 사용한다. static nested 부트스트랩에서 기존 속성 스캔과 Boot의 TypeExcludeFilter·AutoConfigurationExcludeFilter를 유지하고, 새 Redis를 시작하는 RedisTestContainersConfig와 재귀 스캔을 일으킬 CommerceApiApplication을 제외한다. 전용 test 패키지와 명시 classes 지정을 사용해 다른 테스트의 기동에 영향을 주지 않게 한다. 별도 Gradle 작업·새 JVM·마지막 클래스 순서·컨테이너 종료를 통한 정리 대안은 현재 Redis 재사용 요구와 맞지 않아 채택하지 않았다. 기존 서버를 pause/unpause한 뒤 같은 master 연결로 확인 명령을 보내고 자기 token만 정리하는 방식을 선택한다.

장애 전후 CLIENT ID와 INFO server의 run_id를 함께 대조한다. 서버 요청 종료·unpause 뒤 같은 master 경로의 후속 응답에서 두 값이 모두 동일하면 선행 명령이 지나온 경계로 사용한다. run_id는 서버 재시작 뒤 연결 ID가 다시 쓰이는 상황을 판별한다. 별도 CLI나 새 연결의 ID를 쓰지 않는다. 기존 master template은 공유 native 연결과 ReadFrom.MASTER를 사용한다는 코드 확인을 바탕으로 한 선택이며, 실제 획득과 확인 명령이 그 경로를 사용하는지 구현에서 검증해야 한다. 관찰 callback은 기존 master template의 비파이프라인·비Redis트랜잭션 경로에서 native clientId()/info를 사용한다. 사전 정상 발급·반환과 별도 관찰 연결의 CLIENT LIST로 같은 경로를 확인한다. 연결이 바뀌거나 확인을 못 받으면 검증 실패·닫힘 유지다. 자기 token 제거와 master Set 0개 확인 뒤에도 Q9는 수용을 닫아 두며, Redis는 기존 실행 상태로 돌려놓는다. 재개 동작은 Q10에서 확인한다.

**실행 기록의 보존:** 테스트가 실패한 뒤에도 소유 token과 종료 근거를 확인할 수 있어야 한다. 메모리·버퍼된 로거·덮어써질 Gradle 결과에만 의존하는 대신 로컬 JSONL 파일에 append·flush한 후 획득 명령을 위임한다. 위치는 저장소의 `docs/week8/verification` 아래이며 명시 실행에서 절대 경로로 전달한다. 쓰기 실패는 명령 전 테스트 장치 실패로 끝낸다. JVM 비정상 종료와 test/clean 뒤 기록을 남기는 비용을 수용하며, 머신·파일시스템 유실 복구까지 보장하지 않는다. MySQL 테스트 컨테이너 ID와 접속 주소도 남겨 DB 자원 종료를 대조한다.

**실패한 테스트의 사후 정리:** 정상 정리 근거를 얻지 못한 실패도 테스트 자원을 다시 사용할 경로가 필요하다. 테스트 JVM·쿠폰 획득 가능 로컬 앱 종료, 관련 DB 종료/결과 확인, 정리용 연결 외 일반 Redis 클라이언트 부재를 확인한 뒤 실행 기록의 자기 token만 수동 SREM하는 예외를 선택했다. beforeId 하나만 확인하는 대안은 재연결된 다른 클라이언트를 놓칠 수 있어 채택하지 않았다. JVM 종료와 unpause를 확인한 뒤 정리 연결을 새로 열고 SREM 전후의 클라이언트/Set 상태를 대조한다. accept 순서만으로 모든 늦은 명령의 종료를 보장한다고 설명하지 않는다. 기록이나 종료 근거가 부족하면 정리는 보류한다. 이는 실패를 통과로 바꾸거나 제품 수용을 자동으로 재개하는 절차가 아니다. 구체 증거·순서·정리 결과는 상세설계 §10.1이 원본이다.

각 사례는 닫힘·빈 Set·명시 열기로 초기화한다. 같은 master를 쓰는 상품 캐시 요청도 관찰 중 멈춰 마지막 명령 대조를 보존한다. 메서드 순서나 앞선 사례의 상태에 의존하지 않는다.

**비용·한계:** 테스트가 master 연결의 ID와 명령 경로를 관찰해야 한다. 소스 확인은 실측 결과가 아니며 연결 재생성·Redis 재시작 복구까지 자동으로 확정하는 기준으로 확대하지 않는다. 절차의 원본은 상세설계 §10.1이다.

**DB 검증 선택:** 실제 MySQL에서 commit/rollback·경쟁·HTTP timeout 동안 작업 유지와 token 조기 반환 금지를 검증한다. UNKNOWN/완료 통지 없음은 테스트가 Facade 생성자에 TX 관리자 대역을 직접 넘겨 분기를 검증한다. 같은 생성자에서 읽기·쓰기 template을 만들므로 Spring 전체의 TX 관리자 교체와 전용 template 빈 추가를 피할 수 있다. 실제 세션 KILL로 UNKNOWN이 반드시 발생한다는 가정은 채택하지 않았다. 재현의 불확실성과 추가 장애 실험을 줄이는 대신 실제 DB 통신 장애에서 UNKNOWN이 발생한 것을 검증하지 않았다는 한계를 명시한다.

실제 SQL/DB 결과와 대역의 token 유지·닫힘·로그 결과를 구분해 기록한다. 실제 작업이 계속 중인데 대역의 종료 통지만으로 끝났다고 추정하지 않는다. 구체 위치·절차·검증 기대값은 상세설계 §10.1~§10.2가 원본이다.

## CQ15. 사용자 식별보다 앞의 인스턴스별 요청률 제한

**변경 전 구안:** 발급 POST에 적용하던 이 선택은 미구현 상태에서 CQ16과 상세설계 §12로 대체했다. 아래 발급 POST 적용·기존 결과 재요청 제한·기존 세마포어 유지 설명은 당시 판단이며 새 구현 지시가 아니다.

**문제:** Redis 자리를 바로 반환하는 짧은 실행도 연타·집중 요청이면 사용자 존재 DB 조회·쿠폰 사전 조회·Redis 호출을 반복한다. 현재 점유 C만으로 도착 요청률을 제한할 수 없다.

**선택:** Resilience4j RateLimiter 하나를 각 인스턴스의 발급 POST 앞에 둔다. 사용자별·캠페인별 분리는 하지 않는다. 초기 1초 주기 10건, 대기 0, 초과 시 전용 429를 반환한다. 상세 설정·실행 순서·검증 기준은 [상세설계 §11](../features/coupons.md#11-발급-post의-앱-인스턴스별-요청률-제한)에 둔다.

| 대안 | 이점·비용과 판단 |
|---|---|
| **인스턴스 로컬 제한** | 제한 판단에 Redis가 필요 없고 선행 DB 조회도 줄임. 인스턴스 수에 따라 합산 허가량이 늘어나는 비용을 수용해 선택 |
| Redis/Redisson 분산 제한 | 여러 인스턴스의 공통 한도에 유리하나 요청마다 Redis 판단·통신 장애 처리가 필요. 이번에는 채택하지 않음 |
| 사용자별 + 인스턴스 제한 | 개별 연타의 공정성에 유리하나 사용자 식별/키 관리·limiter 수명·퇴거 처리가 추가됨. 사용자 선택으로 인스턴스 제한만 적용 |
| Controller/Facade의 RateLimiter annotation | 간단하지만 현재 사용자 resolver의 DB 조회 이후에 실행됨. 선행 조회 보호 목적에 맞지 않아 MVC preHandle 선택 |

**비용·한계:** 기존 쿠폰 보유자의 POST도 제한된다. 단일 사용자가 전체 허가를 쓸 수 있고, 주기 경계의 집중·앱 재시작·인스턴스 증설에 걸친 전역 요청률은 보장하지 않는다. limiter는 요청 허가를 시간에 따라 갱신하며 Redis 실행 token처럼 종료 후 반환하지 않는다. 동시 DB 작업 수는 기존 Redis 수용이 계속 제한하고, 별도 Bulkhead/풀 격리는 이번에 도입하지 않는다.

**재검토 조건:** 인스턴스 수와 무관한 전역 한도·사용자별 공정성이 필요해지거나 제한을 통과한 요청도 자원을 과점유하는 관찰이 생기면 분산 제한·사용자별 제한·별도 Bulkhead의 비용을 다시 비교한다. 캐시 도입은 별도 설계이며 이번 판단의 성능 근거로 가정하지 않는다.

## CQ16. 대기 순서에 따른 실행 자리 배정과 입구 요청률 제한

**문제·제약:** 캠페인별 입장 대기실에서 차례를 기다린 사용자에게 다시 자리 부족·요청률 초과를 반환하면 대기 경험이 무너진다. 시간마다 N명씩 입장시키는 방식은 느린 DB 작업의 누적을 제한하지 못하고, 기존 세마포어를 발급 시 다시 획득하면 이중 경쟁이 된다. 쿠폰 수량은 예약하지 않으며 최종 총량·사용자 중복 보호는 DB에 남아야 한다.

**사용자 선택:** 대기열과 실행 자리 관리를 통합한다. 실행 자리를 배정한 뒤 입장을 허용하고 발급 시작 시 그 자리를 그대로 사용한다. 입장 가능+진행 점유의 합을 상한으로 제한하고, 진행 중인 작업은 DB 종료 확인 전까지 유지한다. Resilience4j 요청률 제한은 발급 POST에서 대기 등록 입구로 옮긴다. 기존 인스턴스별 공유·1초/10개·대기 0·시작 설정 정책은 유지한다. 현재 정책 원본·불변식·미정 계약은 [상세설계 §12](../features/coupons.md)를 따른다.

| 대안 | 이점·비용과 판단 |
|---|---|
| 주기당 N명 입장 + 기존 세마포어 재경쟁 | 기존 코드 재사용은 쉽지만 입장 후 FULL 거절과 요청률 429가 남음. 새 사용자 경험에 맞지 않아 대체 |
| 실행 자리 배정과 입장 권한 통합 | 정상 입장자의 자리 재경쟁을 없애고 상한 유지. 권한 소비·만료/실행 경합·종료 불명·재시작 복구를 상세설계해야 하는 비용을 수용 |
| 수량 예약 또는 서버 자동 비동기 발급 | 입장 후 결과를 더 강하게 보장할 수 있으나 수량 예약 회수나 작업 전달/재처리 계약이 필요. 사용자는 발급 시도 기회만 선택했으므로 채택하지 않음 |

**입장 권한 수명 합의:** 실행 자리 배정과 입장 허용 시점부터 유효기간을 계산하고 조회·재요청으로 연장하지 않는다. 미사용 권한이 만료되면 회수하되 진행 중인 실행은 DB 종료 전 회수하지 않는다. 이유는 미사용 입장자가 재요청으로 자리를 계속 독점하지 않게 하기 위해서다. 비용은 상태를 늦게 확인한 사용자의 실제 사용 가능 시간이 짧아진다는 점이며, 조회 API에서 만료 시각을 어떻게 알릴지는 상세설계한다. 입장 유효기간은 30초로 사용자 최종 확인을 받았다. 서버에서 발급 진행 상태로 전환하기 위한 기한이며 DB 처리 완료 기한이 아니다. 입장 전 대기에는 시간 만료를 두지 않는다.

**서버 스케줄러 채택:** 상태 조회와 변경을 분리하고 사용자 요청이 없어도 미사용 권한 회수·빈자리의 순차 입장 배정을 진행하기 위해 주기적 서버 스케줄러를 둔다. 요청 시에만 처리하면 유휴 중 회수가 지연되고, 발급 종료 시에만 처리하면 미사용 권한의 만료를 처리하지 못한다. 비용은 주기별 배정 지연·정기 저장소 접근과 작업 수명/실패 처리다. 실제 쿠폰 발급은 사용자의 POST로 유지한다. 초기 실행 간격은 1초이며 Redis 자료구조·원자 전이·실패 복구의 구체화는 아직이다.

**실패 단순화·관찰용 초기값:** 발급 실행 실패 뒤 입장 권한 복원·자동 재시도는 하지 않는다. 실행 자리는 기존 종료 확인 원칙으로 반환한다. 사용자의 초기값 위임에 따라 실행 자리 3개·스케줄러 간격 1초·입장 권한 30초로 정해 소수 요청의 대기와 만료를 관찰하기 쉽게 한다. 운영 최적값을 검증한 것은 아니다. 입장 전 대기는 생존 신호 갱신 없이 유지하고, 이탈자도 차례가 온 뒤 30초 안에 사용하지 않으면 회수한다. 클라이언트가 없는 범위에서 별도 heartbeat와 갱신 정책을 줄이기 위한 선택이며, 이탈자가 많으면 이후 대기를 지연시키는 비용이 있다.

**기존 결과·품절·중복·실패 후 등록 선택:** 기존 쿠폰은 입장 권한 없이 반환해 응답 유실 재요청이 다시 줄 서지 않게 한다. 품절이 확인되면 새 입장을 중단하고 남은 대기자를 품절 종료로 안내해 불필요한 대기를 줄인다. 진행 중 재요청은 추가 실행 없이 처리 중을 반환해 중복 실행/응답 장기 대기를 피한다. 실패 후 권한 복원·자동 재시도는 없지만 사용자가 새로 등록하는 것은 발급 가능한 상태에서 맨 뒤로 허용한다. 비용은 기존 결과 조회와 진행 상태의 경합·품절 전파/미사용 권한 정리·종료 응답의 구체화이며 상세설계에서 해결한다. 종료 불명 실행을 확정 실패로 처리해 새 실행을 허용하지 않는다. 정책 원본은 상세설계 §12.6이다.

**API 응답 합의:** 신규 waiting 등록 201·유효 재등록/조회 200으로 생성과 재사용을 구분하고, 등록 이력 없음은 404로 표현한다. 발급은 X-WAITING-ID를 기존 결과 조회 뒤에 검증해 기존 쿠폰 재요청을 보존한다. 진행 중 중복은 202, 대기/만료/이미 사용은 상태 충돌 409, 사용자·캠페인 불일치/없는 ID는 404로 구분한다. 최초 발급 201·기존 결과 200의 다섯 필드는 유지하고 202만 대기 상태 응답을 사용한다. 헤더/상태별 오류·필드의 원본은 상세설계 §12.7이다.

**Lua 작업 경계 합의:** 등록·스케줄러 회수/배정·실행 시작·DB 종료 확인 뒤 기록/반환의 네 변경 작업을 각각 Lua로 묶는다. 이유는 중복 등록·만료/실행 경합·자리 배정을 분리된 명령 사이의 경합 없이 판단하기 위해서다. 실제 DB 트랜잭션과 Redis 스크립트를 하나의 원자 트랜잭션으로 취급하지 않는다. 키·자료구조·검증 순서·상세 실패 처리는 아직 구체화 전이다.

**Redis 구체화 방향:** 키는 사용자 제안인 waiting:{종류}:v1:{campaignId} 형식으로 맞추고, Java 스케줄러가 Redis Lua를 호출한다. 사용자별 최신 항목 Hash와 대기/만료 정렬용 두 Sorted Set·진행 Set을 구분해 다른 만료 규칙을 표현하고 별도 점유 카운터는 추가하지 않는 안이다. 상태/순번 조회도 일관된 읽기 단위로 다루되 상세 경합과 입력/반환 규약은 구체화·최종 검토 전이다. 원본은 상세설계 §12.8이다.

**Lua 단순화 합의:** 만료 회수는 Java 스케줄러가 호출하는 Lua 한곳에 두고 등록 Lua가 대신 회수하지 않는다. 기한이 지난 READY가 회수되기 전에는 EXPIRED 안내만 하고 새 등록을 잠시 기다리게 한다. 이미 입장한 사용자의 품절 판정은 DB 조건부 UPDATE에 맡겨 실행 시작 Lua의 중복 검사를 제외한다. 종료는 현재 waitingId/PROCESSING 대조만 유지하고 별도 반복 호출 이력·복구 조율을 만들지 않는다. 비용은 회수까지의 짧은 재등록 지연과 DB 단계의 품절 응답이며 실행 상한·중복 실행 방지·종료 전 반환 금지 검사는 유지한다. 구체안은 상세설계 §12.8이다.

**클래스/주기 처리 구체화 동의:** 기존 CouponFacade·CouponAdmissionService·CouponAdmissionRepository/Redis 구현을 확장하고 Java CouponWaitingScheduler를 추가한다. 대기 등록 registerWaiting과 입장 처리 processAdmissions를 구분한다. 직전 실행 종료 후 1초 fixed delay와 시작 설정의 운영 캠페인 ID 한 개를 사용하고, 매 실행 짧은 DB 조회로 품절을 확인한 뒤 TX 밖에서 Lua를 호출한다. 별도 품절 감지 작업을 줄이는 대신 캠페인 조회 비용과 주기별 전파 지연을 수용하는 안이다. 클래스별 책임·흐름 원본은 상세설계 §12.9다. 설정/기동/조립과 구체 입력/결과 규약은 아직 최종 구체화 전이다.

**설정·수용 제어 합의:** 기존 capacity=3과 waiting의 campaign-id/scheduler-delay=1초/admission-duration=30초를 시작 설정으로 사용한다. 캠페인 미지정은 앱 기동 실패 대신 대기실 비활성으로 처리해 기존 기능을 유지한다. 수용은 닫힘 시작·명시 open/close이며 진행 중 종료 처리는 close 뒤에도 계속한다. 이후 사용자는 cleanup API 자체 제거를 승인했다. 정상 회수는 스케줄러/종료 Lua로 충분하므로 409만 반환하는 엔드포인트와 새 수동 삭제 기능을 추가하지 않는다. API/DTO·Facade/서비스 전용 경로의 실제 삭제는 확장 구현 단위에서 수행하고 기본 커밋/과거 검증은 보존한다. 원본은 상세설계 §12.10이다.

**Redis 상태 저장 채택:** 기존 Redis에 순번·입장 권한·실행 점유를 저장하고 원자 전이로 관리한다. 이미 사용하는 인프라를 재사용하고 앱 메모리만으로 상태가 소실되는 구조를 피하되, Redis 상태 보존이 DB 종료·재시작 복구의 자동 보장을 뜻하지는 않는다. 사용자 승인으로 자동 복원·순번 보존 없이 수동 재시작한다. 이전 발급 작업의 DB 종료/결과 확인 뒤 대기 순번·미사용 권한을 무효화하고 새로 등록하게 한다. 선택 이유는 복원·재조정 로직을 줄여 정상 대기/발급 흐름에 집중하기 위해서다. 비용은 장애·앱 재시작 후 순번 상실이며 사용자가 이번 범위에서 수용했다. 이미 발급한 DB 결과는 보존한다. 이후 사용자는 epoch 도입을 보류하고 장애 시나리오별 복구 상세설계·실험을 정상 흐름의 설계/구현 뒤로 미루도록 요청했다. 이전 요청/권한과 새 대기실 분리·구체 수동 재개는 후속에 검토하고, 지금은 기본 중단/종료 전 회수 금지와 정상 전이·DB 불변식을 유지한다. 보류 상태를 장애 복구 검증 완료로 취급하지 않는다.

**범위 축소 합의:** 단일 앱 인스턴스에서 동시에 신규 발급을 운영하는 캠페인도 하나로 제한한다. 캠페인별 상태 귀속은 유지하되 캠페인 간 자리 배분·기아 정책을 제외해 대기/입장/발급·만료·장애 복구에 집중한다. 이는 운영 범위 가정이며 다중 운영 자동 차단 기능·DB 유일 제약을 추가하지 않는다. 과거 캠페인·쿠폰은 보존하고 운영 캠페인 전환의 권한/점유 처리는 상세설계 대상에 남긴다.

**비용·한계:** 대기 등록 자체는 요청률 429로 거절될 수 있다. 이미 유효한 항목의 순번/권한을 이 거절로 변경하지 않는다. 품절·권한 오류·장애는 별도 실패이며 입장=쿠폰 확보가 아니다. 조회·잘못된 권한 호출 등 남은 경로의 부하 보호는 아직 미정이다. 단일 앱 인스턴스로 한정하고 다중 인스턴스 조율을 검증했다고 주장하지 않는다.

**재검토 조건:** 권한 만료/실행 경합에서 초과 실행·중복 반환, 종료 불명 점유 조기 회수, 입장 후 정상 요청의 FULL/요청률 거절, 조회 부하·운영 캠페인 전환 중 점유 혼선이 발견되면 해당 흐름을 재검토한다. 현재는 합의 방향과 검증 필요 조건이며 실행·성능 결과가 아니다.

- 재검토 계기: 실제 경쟁에서 불변식·응답 계약 불이행, SQL/격리·제약 식별 근거 부족, 사전 조회·Redis·DB 대기 비용, 수동 절차 전제 불충족. 새 정책은 승인 후 반영하며 검사 기준을 통과시키려고 완화하지 않는다.

## 2026-11-12 정상 흐름 최종 검토용 상세 마감

사용자 요청으로 정상 흐름의 DTO/시간 표현·메서드/Lua 반환 규약·설정 바인딩/빈/W6·O11·검증 체크리스트를 쿠폰 상세설계 §12.11~12.13에 구체화했다. 등록/조회/진행 중 재요청에서 선행 DB 조회와 Redis ISSUED/PROCESSING 관찰 사이에 commit이 끼면 DB를 한 번 재확인해 기존 쿠폰 우선 계약을 보존한다. 이는 업무 재실행이나 자동 재시도를 추가하는 선택이 아니다. 사용자별 최신 항목·명시적 terminal 상태만 두고 이력/TTL 청소기를 추가하지 않는다.

품절은 스케줄러가 읽은 DB snapshot으로만 true를 반영하고 실행 시작 Lua의 추가 품절 검사는 두지 않는다. 만료 회수 전 재등록은 기존 항목의 EXPIRED 200 안내로 기다리게 해 등록 Lua에 회수 책임을 넣지 않는다. 정상 검증은 WQ1~WQ12로 모으고, 기존 FULL/cleanup 검사는 승인된 계약 변경 근거와 대체 검증을 명시한다. 기존 DB/TX/응답 유실의 유효한 검증은 유지한다.

현재는 읽기 전용 전체 설계 검토 대상 초안이며 최종 사용자 승인·구현/실행 검증이 아니다. 보류한 장애/epoch/자동 복구·선택 캐시/Bulkhead는 별도 후속이다. 지적에서 계약 공백·과도한 복잡성이 발견되면 수정안을 사용자와 대조하고 필요한 판단만 확인한다.


## 2026-11-12 첫 Claude 정적 검토 보완과 사용자 판단

- F1은 start가 ISSUED를 정상 관찰할 수 있다는 반례를 수용했다. 선행 DB 조회 뒤 다른 요청이 commit/finish한 경우 ID 일치 ISSUED를 반환하고 Facade가 DB 한 번 재조회해 기존 결과를 반환한다. F3은 사용자 승인으로 운영 ID 불일치 신규 진입을 기존 503으로 거절하며 기존 쿠폰 조회는 우선한다.
- F2는 사용자 승인으로 정상 결과(대기/만료/진행 중/옛 종료 UNCHANGED)는 수용을 유지하고 실제 Redis 예외·반환 형식 오류·INVARIANT는 수용을 닫는다. 조회 Redis 실패도 같은 원칙이다. finish 실패는 확정된 DB 결과를 바꾸지 않는다. 현재 ID/PROCESSING 기록과 실제 점유 불일치는 UNCHANGED로 숨기지 않는다. 상세 표는 쿠폰 §12.12다. 모든 UNCHANGED를 닫는 검토 제안은 반복/옛 호출의 정상 무변경 계약과 달라 채택하지 않았다.
- F4는 사용자가 내부 단일 실행기 관리를 선택했다. CouponWaitingScheduler가 SmartLifecycle에서 소유 실행기 하나를 시작/정지하고 fixed delay로 Facade를 호출한다. @EnableScheduling/@Scheduled·새 공통 TaskScheduler bean을 추가하지 않는다. W7의 relay.enabled/pool/gate/lifecycle은 그대로여서 쿠폰을 위해 W7 기능을 끄지 않는다. 코드량은 늘지만 공통 실행기 후보/스케줄링 인프라·W6/O11 조립 영향을 줄이는 선택이다. CouponWaitingConfig는 MVC 등록만 하며 @Bean 메서드가 없다.
- F5는 일반 테스트에서 테스트 조립으로 자동 scheduler를 대체하고 수동 processAdmissions로 검증한다. 자동 fixed delay/종료는 실제 scheduler의 WQ11 별도 컨텍스트로 검증한다. 첫 회차와 수동 작업의 경쟁을 긴 delay만으로 해결했다고 가정하지 않고, 컨텍스트별 고정 캠페인 fixture를 시작 설정과 맞춘다. 제품 hook/자동 실행 스위치는 추가하지 않는다.
- O1/O3는 오류 메시지 일반화·반환 표 누락을 문서에 보완했다. commit 확인 후 응답 미확보 분기는 기존 API 500/재요청 확인을 보존하면서 Redis 종료 상태를 ISSUED로 구분했다. O4의 결과 wrapper 축소는 선택 개선이며 정책/구현 blocker가 아니므로 현재 명세를 유지한다.
- 첫 검토를 받은 사실과 수정된 전체본의 재검토·사용자 최종 승인·구현을 구분한다. 제품 코드/검사 실행은 아직이다.


## 2026-11-12 두 번째 정적 검토 N1/N2와 작은 보완

두 번째 Claude 검토는 F1/F2/F4 해소, 신규 정상 동시성/DB 정합성 문제 없음으로 보고했다. 남은 N1은 기존 테스트의 경로 기대가 승인된 운영 ID/대기 진입 계약과 달라졌으므로 §12.13에 구체적 대체 검증을 기록했다. 운영 ID 밖 요청 503, 운영 ID 등록의 캠페인 없음 404/비활성·품절 409, READY 뒤 상태 변경의 발급 거절을 구분한다. 목록의 과거 캠페인 쿠폰은 DB fixture로 준비해 목록/과거 결과의 기대값을 유지한다.

## CQ17. 캐시 대상을 기발급 결과와 품절에 한정 — 승인·구현·검증 완료

**문제·제약:** 대기 등록/조회·발급은 기존 쿠폰을 선행 조회하며, 품절 이후에도 반복 요청이 들어올 수 있다. 한편 캠페인 정보 캐시는 실제 발급의 조건부 UPDATE와 발급 데이터 조회를 없애지 못한다. 사용자 존재 조회는 공통 resolver의 별도 비용이다. 성능 병목이나 개선량은 아직 실측하지 않았다.

**사용자 선택:** 먼저 기발급 positive 결과와 DB에서 확인한 품절 true만 캐시하고 캠페인 정보 전체/사용자 존재 여부는 제외한다. 미발급 negative 결과와 품절 false는 저장하지 않는다. 기존 결과 우선과 DB 불변식을 유지한다. 기발급 응답의 캠페인 이름에는 짧은 반영 지연을 허용하며 정확한 상한은 아직 정하지 않았다. 계약 원본은 [쿠폰 상세설계 §13](../features/coupons.md)다.

**대안·이유·비용:** 전체 캠페인 캐시는 공유 조회 절감 후보지만 변경/발급 정합성 판단이 늘어 이번에는 제외한다. 기발급 결과는 재조회가 반복될 때 유리하나 미발급자가 대부분이면 이득이 작고, 이름까지 캐시하면 이전의 조회 시 최신 이름 계약을 완화해야 한다. 사용자는 변경 빈도가 낮다는 이유로 이름의 짧은 지연을 수용했다. 품절 true만 저장하면 키 없음은 DB 재확인 대상으로 남고 재고 있음이라는 stale 허가를 캐시하지 않는다. 다만 총량 변경/재개 시 stale true 거절 문제는 별도 무효화/수명 설계가 필요하다. 후보를 전부 넣거나 새로운 공통 사용자 캐시로 범위를 확대하지 않는다.

**미정·재검토 조건:** Redis/로컬 배치·TTL/용량·적용 API·commit 뒤 저장·무효화/장애 fallback·재개 정책·측정 지표는 아직 미정이다. 품절 정보가 기존 쿠폰 반환을 막거나, 캐시 실패가 DB 확정 결과를 바꾸거나, 측정에서 miss 비용만 늘면 설계를 재검토한다. 원칙 문서 반영 승인은 상세 전체 승인·구현/실험 착수가 아니다.

**품절 배치 후속 합의:** 사용자는 Redis에 먼저 품절 정보를 두어 공유하고, 그다음 로컬 캐시를 앞에 확장해 local true hit에서 품절용 Redis 조회를 생략하기로 했다. 로컬에만 두는 제안은 채택하지 않는다. Redis 적용/로컬 추가 단계를 나눠 비교할 수 있으나 구체 실험/구현 착수는 아직 아니다. 공유 Redis 선택을 현재 단일 앱 운영 범위의 자동 확장·다중 인스턴스 정합성 검증으로 해석하지 않는다. TTL/채움/무효화·장애 처리와 기발급 결과의 계층 범위는 미정이다.

**품절 수명/운영 후속 합의:** Redis30초·로컬5초를 관찰용 초기 TTL로 선택했다. 조회 비연장·로컬은 Redis 잔여 수명 이내이며 시작 설정/짧은 테스트 값으로 변경 가능하게 한다. 같은 캠페인은 품절 뒤 재개하지 않고 새 캠페인 ID를 쓴다. 따라서 24시간/5분 제안은 채택하지 않는다. 대기실 meta 전체를 만료시키지 않으며, 기존 실행/운영 전환의 안전한 종료 정책은 유지한다. 구체 채움·남은 수명 판정·장애 처리와 기발급 TTL은 다음 미정 사항이다.

**캐시 장애 처리 후속 합의:** 조회 예외/timeout은 로그 후 DB fallback, 형식 오류는 miss로 DB 확인한다. DB 조회 성공/신규 발급 commit 확인 뒤 캐시 저장 실패는 확보된 결과를 유지하며 자동 재시도/보상 취소하지 않는다. DB도 실패하면 기존 DB 오류를 유지한다. 캐시 자체는 최적화이므로 그 오류만으로 수용을 닫지 않되, 이후 대기실 상태 Redis 오류는 기존 fail-closed/finish 결과 보존을 적용한다. 동일 Redis를 사용한다는 이유로 두 책임을 합치거나 fallback을 신규 발급 우회로 사용하지 않는다. 정확한 API/메서드 배치·저장 순서·검증은 아직 상세화 전이다.

**기발급 miss 후 DB 확인 재합의:** 사용자는 미발급 false 선저장 제안을 논의한 뒤 positive-only와 miss 후 DB 확인을 선택했다. 품절 캐시 hit도 기존 쿠폰 DB 확인을 생략할 근거가 아니다. 만료/저장 실패 때문에 cache miss일 수 있고, 발급 뒤 갱신 실패·늦은 negative 채움이 기존 쿠폰 반환을 가릴 수 있으므로 negative 캐시의 정합성/동기화 복잡성을 추가하지 않는다. 미발급 대기 요청에서 선행 DB 조회가 남는 비용을 명시한다.

**기발급 배치/수명 합의:** 사용자에게 Redis60초·조회 비연장·DB 기존 결과 또는 신규 commit/결과 확인 뒤 채움·캐시 발급 반환200을 제안했고, 사용자는 TTL을30초로 지정했다. 기발급 Redis30초로 반영하며60초 제안은 채택하지 않는다. 품절 Redis30초/로컬5초와 별도 대상이고 기발급 로컬 계층은 추가하지 않는다. API별 채움/동시성/최신성 경계는 아직 상세화 전이다.

**등록의 품절 캐시 우선순위 합의:** 사용자는 기존 쿠폰·운영 ID/열림 조건 뒤 유효한 품절 true가 있으면 캠페인 DB 조회를 생략하고 품절409를 우선하는 것을 승인했다. 같은 캠페인은 재개하지 않는 운영 범위에서, 품절 뒤 INACTIVE 변경에도 cached 품절을 반환하는 비용을 수용한다. DB 경로는 기존 없음/비활성/품절 순서를 유지한다. 이 선택을 발급 권한 오류/PROCESSING보다 품절을 우선하거나 GET/스케줄러도 캐시로 단축하는 승인으로 확대하지 않는다.

**API 적용 범위 합의:** 사용자는 기발급 결과 캐시를 등록/대기 조회/발급에, 품절 캐시를 등록에만 적용하는 표에 동의했다. 보유 목록·자동 입장 처리는 두 캐시 모두 미적용이다. 대기 GET의 실제 상태/PROCESSING, 발급 권한/진행/DB 최종 판단을 유지하고 자동 주기의 기존 캠페인 조회/회수·배정을 보존해 변경 범위를 제한한다. 목록의 현재 이름/정렬/시각 계약도 유지한다. 구체 키·값/채움/검증은 아직 미정이다.

**기발급 채움 예외 합의:** 사용자는 commit 확인/응답 결과 미확보 시 캐시용 추가 조회 없이 기존 오류/재요청 확인 유지, DB 종료 불명 시 성공 캐시 미기록·PROCESSING/닫힘 유지에 동의했다. 캐시를 위한 추가 DB 처리가 기존 실패 흐름을 바꾸거나 미확정 결과를 성공으로 유통하지 않게 한다. 서버가 결과를 확보한 HTTP 응답 유실은 별개다.

**정상 신규 채움 순서 합의:** 사용자는 commit/결과 확인→기존 finish 처리→확보한 결과로 캐시 저장에 동의했다. 캐시 때문에 DB를 추가 조회하거나 자리 반환보다 먼저 부가 캐시 저장을 수행하지 않는다. 정상 결과 보존과 예외 두 분기의 미기록 원칙은 유지한다.

**Bulkhead 제외·상세 초안 통합:** 사용자는 기존 RateLimiter가 있으니 Bulkhead를 제외하고 남은 캐시 상세를 묶어 작성하도록 요청했다. 요청률 제한과 동시 실행 상한의 역할은 구분하며, 추가 Bulkhead가 전체 자원을 격리한다고 가정하지 않는다. §13.8~13.13에 4개 제품 책임과 읽기 Lua1·키/JSON/NX TTL·TX 밖 채움·로컬 한 슬롯/단조 시계·검증/분할을 구체화했다. 아래 내부 선택들은 전체 Claude 정적 검토/사용자 최종 승인 전 상세 초안이다.

- 캐시 서비스가 DB/TX를 가지는 대안 대신 Facade가 기존 DB 흐름을 조율하고 서비스는 캐시 I/O/로컬만 맡는다. 신규 Facade/전달 서비스·Entity 응답 캐시를 늘리지 않으면서 기존 계층/TX 판정을 유지한다. 다섯 응답 필드의 포트 중첩 값은 created/createdAt 문제를 분리하기 위해 둔다.
- 유효 키 overwrite/TTL refresh 대신 SET NX+TTL로 최초 채움만 허용한다. 최신 이름으로 즉시 덮어쓰는 이득은 포기하지만 late writer의 유효 항목 덮어쓰기와 수명 연장을 줄인다. 만료 뒤 늦은 최초 채움·원본 손상 즉시 감지까지 보장하지 않으며 엄격한 변경 시점 기준 최신성/취소 기능은 후속이다.
- Redis GET과 PTTL을 따로 읽는 대신 단일 키 읽기 Lua로 같은 시점의 값/수명을 얻는다. Java가 요청 시작부터 경과를 보수적으로 차감해 local 수명이 관찰한 Redis 잔여를 넘지 않게 한다. local 전용 version/epoch/pubsub 동기화는 만들지 않는다.
- 현재 local 품절은 단일 운영 ID 확인 뒤만 사용하므로 bounded Map/Caffeine 등의 새 의존성 대신 AtomicReference 한 슬롯을 선택한다. 여러 캠페인의 local 캐시/TTL 관리가 필요해지면 범위와 구현을 재검토한다. 오래된 ID는 hit이 아니며 새 캠페인 슬롯으로 교체한다.
- 별도 on/off 비교 스위치 대신 정상 기준3bc158a→Redis-only→local 추가 커밋을 비교 기준으로 보존한다. 정합성 KQ와 실제 장애/부하 비교 실행은 구분하고, 기존 WQ 검사를 cache hit으로 우회해 허위 통과시키지 않는다.

정상 사용자 정책의 개별 합의와 이번 상세 초안/검토·최종 승인·코드/검증 완료를 구분한다. 현재 새 cache 코드/실험은 없다.


**첫 캐시 정적 검토 보완(사용자 승인):** C1은 고정 캠페인·truncate 뒤 ID 재사용·공유 singleton 때문에 기존 검사가 이전 캐시를 읽을 수 있는 공백이다. 기존 컨텍스트는 @Primary miss/no-op 포트로 격리하고, 실제 캐시는 별도 소유 키·종료 확인 정리·새 로컬 서비스로 검사한다. S2/S3은 값 불변식을 IssuedCoupon 생성자/CouponBenefits에 모으고 adapter는 엄격 JSON 타입/키 일치만 맡도록 명확히 했다. S1의 기발급 GET 단순화는 채택하지 않는다. TTL 없는 키를 miss로 취급하는 기존 초안 조건을 유지하며 이미 품절에 필요한 읽기 Lua 하나를 공유한다. 단독 GET 도입은 그 조건을 없애거나 별도 TTL 관찰을 추가하므로 이번 단순화 이득보다 계약 유지가 낫다. 전체 설계 최종 승인은 보완본 재검토 후 별도다.
