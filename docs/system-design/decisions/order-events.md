# 주문 확정 이벤트 발행·소비 판단

기존 절 번호 참조: [2.11](../features/order-events/publication.md#211-주문-확정-이벤트-발행의-책임과-설정) · [3.7](../features/order-events/README.md#37-최초-pg-확정-시각과-사건-값) · [4.6](../features/order-events/publication.md#46-주문-확정-이벤트-발행).

기존 문서의 계약·절 번호·승인/검증 상태를 보존해 이동했다. 재편 자체는 제품 계약 변경이나 새 실행 검증을 뜻하지 않는다.

**W7 읽기 구분:** A.34·A.35와 아래 기존 상태 설명은 W6 당시의 선택·승인·검증 이력이다. 문서 마지막의 A.36~A.41은 W7 변경 경계·저장/TX·relay/복구·검증/검토 보완 초안의 판단 기록이다. 단계별 착수·선택 승인과 W7 전체 설계 최종 승인·구현·검증을 구분한다.

**현재 상태:** 2026-10-29 사용자 최종 승인 설계다. 아래 2026-10-28의 초안/보완 설명은 당시 판단 이력이며 현재 승인 상태를 대신하지 않는다. 승인된 구현 단위와 관련 실행 검증을 마쳤다. 결과·한계는 [검증 기록](../verification/order-events.md)을 따른다.

## A.34 주문 확정 사실의 직접 발행

**상태·근거 구분:** 2026-10-28 사용자와 사건 ID·확정 시각·AFTER_COMMIT·비동기 결과 관측·로그·producer 내부 재시도·유한 종료 대기 정책을 합의하고 발행 측 상세설계 작성을 승인받았다. 2.11·3.7·4.6·5.8은 그 정책의 상세 초안으로 작성했고 2026-10-29 최종 승인했다. 설계 검토는 구현·실험 결과가 아니다. GPT 검토는 제공한 코드 요약에 대한 제안으로 검토했고 사용자의 선택을 대신하지 않았다. 원문 요구는 최초 PG 확정 뒤 직접 발행·구매 활동 저장·두 공백 검증이며 Outbox·랭킹 API는 이번 주 제외다.

**중간 검토 후 추가 합의:** 공통 설정 복사·전용 override 이후 `transactional.id`가 있거나 전용 factory가 transaction-capable이면 기동 오류로 거절한다. 비트랜잭션 발행이라는 기존 선택을 조용히 바꾸지 않기 위해서다. 충돌 설정을 제거하고 실행하는 대안은 기동을 이어갈 수 있지만 설정 오류를 숨길 비용이 있어 채택하지 않았다. 현재 공통 설정에 실제로 충돌이 발견됐다는 뜻은 아니며 2.11·P5에서 확인할 조건이다. 품목의 합산 전 검증·독립 DB 연결의 commit 관측·모든 partition의 누락 검사도 기존 계약을 명확히 하는 보완이며 새 전달 보장을 추가한 것은 아니다.

초기 제안의 max.block=1초·request=3초·delivery=10초·retries=3은 빠른 실패 관측을 우선한 안이었다. 그러나 응답시간 요구·실측이 없는 상태에서 정상 최초 metadata 확보와 일시 지연까지 조기에 포기할 근거가 부족했다. 사용자는 max.block=5초·기존 request=20초·delivery=30초·retries 기본값으로 시간 예산을 우선하는 수정안에 동의했다. 2.11이 현재 초기값의 단일 기준이며 이전 수치는 구현값이 아니다. 수정안도 실측된 최적값은 아니고 실제 cold start·오류·종료 관찰로 재검토한다.

### 공식·코드 근거와 입증하지 않은 것

- **공식 소스 확인:** 로컬 Kafka clients 3.8.1의 ProducerConfig는 idempotence의 acks=all·retries>0·in-flight<=5 조건, delivery/request/linger 관계, metadata·buffer만 다루는 max.block 설명, 횟수보다 delivery timeout 중심 제어 권고를 포함한다. CommonClientConfigs는 backoff·jitter를 설명한다. KafkaProducer.close(Duration)는 종료 대기 후 미완료 전송 강제 종료 경로를 가진다. 설정 의미·구현 읽기이며 실제 runtime의 동작 확인은 아니다.
- **공식 소스 확인:** 로컬 Spring Kafka 3.3.4 DefaultKafkaProducerFactory의 setPhysicalCloseTimeout·getPhase·stop·destroy 경로를 읽었다. 기본 구조를 근거로 HTTP 정리 뒤 producer 종료를 설계하지만 실제 bean 순서·스레드 정리는 4.6에서 확인한다. Spring Framework 6.2의 TransactionalEventListener·TransactionPhase 계약에 따라 commit 성공 후 처리·fallbackExecution=false를 명시한다. 구체 버전의 afterCompletion 예외 처리에만 기대지 않고 서비스 로그·명시적 동기 오류 처리로 정책을 표현한다.
- **코드 확인:** 현재 PG는 공통 applier·TX B·Order 잠금·CONFIRM/FINAL_UNCHANGED를 구분한다. 기존 OrderModel에 confirmedAt은 없고 품목은 LAZY·생성 뒤 고정이다. 공통 YAML은 retries=3·request timeout=20초·backoff=500ms·type headers=false다. 공통 factory는 KafkaProperties에서 map을 만든다. YAML 선언은 실제 적용 증거가 아니다.
- **코드/공식 매핑 기준:** 기존 JPA의 NORMALIZE_UTC·jdbc.time_zone=UTC와 ZonedDateTime을 유지한다. MySQL 8.0 Reference Manual의 Fractional Seconds in Time Values가 설명하는 마이크로초 저장 정밀도를 목표로 삼지만 실제 DATETIME(6) 생성·왕복·JSON은 미검증이다. 로컬 캐시 jar 버전·Docker image 선언은 실행 중인 의존성·서버 버전 확인을 대신하지 않는다.
- **사용자 제공 사실:** 보존할 실데이터가 없어 이번 신규 컬럼의 이관·backfill은 제외한다. DB 조회 결과가 아니며 유효한 POINT·PG 보존 테스트의 제거 근거도 아니다.

### 남은 한계와 재검토 조건

DB commit→send 사이에는 여전히 미발행 공백이 있다. idempotent producer·안정 ID·정상 종료 대기·동기 완료 대기 어느 것도 이를 제거하지 않는다. broker에 같은 사건의 별도 record가 생길 수 있고 구매 효과의 유일성은 소비 DB 계약이 맡아야 한다. timeout이나 실패 Future는 broker 미기록의 일반 증거가 아니다. 로그만으로 자동 복구나 완전한 관측도 보장하지 않는다.

재확정·멀티테넌트 ID 공간·다중 broker·더 강한 HTTP 응답시간/복구 보장·민감 payload·consumer 스키마 진화 요구가 생기면 관련 판단을 다시 검토한다. 실제 cold start 실패·요청 지연·종료 중 미완료·DB/payload 시각 차이가 관측되면 먼저 유효 설정·실행 경계를 확인하고, 계약 변경이 필요하면 사용자에게 판단받는다. 모든 검토를 추가 실험으로 확장하지 않으며 선택적 글감 실험은 주제 선정 후 별도 승인한다.

## A.35 구매 활동 소비의 정합성과 전달 경계

**상태:** 2026-10-28 사용자가 소비 측 상세설계 문서 작성을 승인했다. 유효 committed offset이 없는 새 group의 `earliest` 시작은 사용자가 선택했다. 상세 검토·보완 후 2026-10-29 전체 설계를 최종 승인했으며 구현·실행 검증은 하지 않았다.

기준은 `docs/system-design/features/order-events/consumption.md`다. 3~5절에 완료/활동 단일 TX·정확한 사실 비교·완료 unique 경쟁과 rollback 후 새 TX 재확인, 6절에 전용 record listener·DB 종료 후 ack·중단/재시작, 7절에 실제 전달·두 공백·DB 효과 검증, 8절에 문제·대안·비용·재검토 조건을 둔다. 근거를 중복 복사하지 않는다. 기존 주문·PG·상품 업무를 소비자에서 다시 실행하거나 DLQ·Outbox·자동 재발행을 추가하지 않는다.

### 전체 Claude 검토 후 사용자 합의 — A1~A4·B·C

- **회귀와 실제 발행 분리:** 기존 API 회귀는 테스트 전용 기록용 포트로 대체하고 실제 adapter 검증은 별도 컨텍스트에서 명시한다. broker 부재의 metadata 대기와 공유 topic 오염을 막으면서 기존 회귀 의미를 유지한다. 모든 테스트에 실제 broker를 붙이는 대안은 실행/기동 비용과 callback 시간 영향을 늘리므로 채택하지 않았다. fake를 broker 근거로 쓰지 않는 비용·실제 adapter 선택 검증은 publication 2.11이 기준이다.
- **손상 우선 분류:** 저장 eventId 유도·고정 타입/버전과 품목 정합성부터 검사하고, OR 두 완료 행도 STORAGE_INTEGRITY_ERROR로 정한다. 정상 저장 상태와 다른 incoming만 충돌이다. 추가 구매 차단 동작은 유지하되 오류 원인을 구현자가 추측하지 않도록 분류를 명확히 했다. 소비 3·5절·C3이 기준이다.
- **공유 테스트 DB:** 기존 MySQL 테스트 컨테이너의 같은 DB를 사용하고 독립 시나리오 전 두 구매 테이블을 명시 정리·0행 확인한다. 별도 MySQL/스키마는 격리에 유리하지만 자원·권한·초기화 구성을 늘리므로 사용자는 공유안을 선택했다. 같은 시나리오의 listener/consumer 재시작 동안 데이터 보존·직렬 실행이 비용이며 소비 6절이 기준이다.
- **공유 개발 broker:** 사용자가 뜻한 운영 Kafka는 실서비스가 아닌 로컬 Docker Kafka임을 확인했다. 이를 공유하고 실행별 topic/group·bootstrap/admin 주소·소유 자원 cleanup을 통제한다. 새 Kafka Testcontainers/이미지 변경은 하지 않는다. 자동 준비 대신 Docker 사전 기동·환경 의존과 접속 실패를 명시적으로 보고하는 비용을 수용한다. publication 2.11이 기준이다.
- **종단만 별도 JVM:** 다른 검증은 각 앱의 일반 테스트로 두고 C10에서만 streamer 별도 JVM을 사용한다. 앱 classpath/scan을 섞지 않는 대신 bootJar 준비·자식 설정·배정 확인·종료 관리 비용을 수용한다. callback 1초 제한은 유지하고 준비된 종단 결과와 cold start 한계를 구분한다. 소비 7절이 기준이다.

사용자는 위 방향을 합의한 뒤 문서 보완 착수를 별도로 승인했다. 이 문단은 보완 당시의 기록이며 실제 MySQL/Kafka/JVM 검증 완료를 뜻하지 않는다. 현재 설계 승인 상태는 문서 상단을 따른다. 기존 Kafka 이미지·테스트 컨테이너 설정은 코드/선언 확인에 한하며 실행 환경 버전은 구현 검증에서 기록한다.

### 재검토 잔여 보완과 시작 위치 재확인

사용자는 재검토 잔여 A1·A3·B·C 보완과 전용/테스트 consumer의 `allow.auto.create.topics=false` 적용을 승인했다. fake의 공통 상위 클래스·Spring TestBean override와 테스트 전역 guard/실제 marker를 정해 적용 누락을 기동 실패로 드러낸다. 독립 streamer 컨텍스트는 각자 자기 테이블 create로 준비하고, 보존 구간은 같은 컨텍스트/JVM 안에서 끝내 테스트 클래스 순서 의존을 없앤다. validate는 보존한 DB로 새 프로세스를 띄우는 향후 별도 검증에 적용하며 현재 C1~C10의 선행 조건으로 요구하지 않는다.

새 group의 earliest 선택도 유지한다. latest는 client 기본값이지만 새 group 시작 전에 보존된 주문 확정 사실을 건너뛰는 비용이 있다. 이 기능은 구매 사실 누락을 피하는 쪽을 선택하고 재전달 비용은 DB 동일 사실 비교로 감당한다. 유효 offset이 있는 기존 group의 재개 위치·retention 밖 복구 보장은 바뀌지 않는다. 자동 topic 생성 금지는 offset reset과 별개로 명시적 topic 준비와 정리 책임을 지키기 위한 선택이다. 기본 true는 준비가 간단하지만 잘못된 이름/순서에 따른 생성과 cleanup 뒤 재생성 위험이 있어 채택하지 않았다. 이 client 설정은 producer·다른 client나 broker 전역의 자동 생성까지 막지 않는다.

구체 계약은 publication 2.11·소비 6~7절이 원본이다. P2 hook/연결 여유·P6/P8 준비 연결·UTF-16/32 거절 단계·식별 충돌 방어 분기도 명확히 했으며, 새 기능·선택적 실험을 추가하지 않았다. 근거는 재검토 제안과 로컬 Spring Test 6.2.5의 TestBean/ContextCustomizerFactory 소스 확인이다. 구현·실행 검증은 아직 하지 않았다.

### 최종 승인과 DLQ 범위 — 2026-10-29

사용자는 설명용 요약과 추가 질의로 확정 사건·시각·JSON·전송 관측·전용 producer·동시 오류·streamer/JVM·DLQ 범위를 확인한 뒤 현재 설계 확정 및 관련 파일 스테이징을 요청했다. 이를 현재 기준 설계의 최종 승인으로 기록한다. 현재 중단형 오류 처리 구현/검증이 우선이며 DLQ는 후속 확장 후보다. 실습의 명시적 제외와 우리가 선택한 미구현 범위를 구분하고, 근거·한계·후속 판단 항목은 소비 상세설계의 DLQ 절을 따른다. 실제 코드 구현·테스트 통과나 다음 구현 단위의 착수 허락으로 해석하지 않는다.

### 회귀 격리 범위 축소 — 2026-10-29

- **문제:** 구현 검토에서 전체 Spring 컨텍스트에 적용한 guard가 브랜드·포인트 등 PG 확정을 실행하지 않는 회귀에도 주문 이벤트 부모 상속을 강제했다. 상속을 공통 annotation으로 치환해도 무관한 테스트에 설정을 요구하는 원인은 남는다.
- **사용자 승인 선택:** 전역 guard·mode marker·전체 회귀용 공통 부모를 제거하고, 실제 최초 PG 확정을 실행하는 회귀에만 명시적인 test bean override를 둔다. 기존 PG 전용 fixture는 활용하되 새 전체 앱 annotation·범용 bean 교체 프레임워크는 만들지 않는다. 정확한 적용 계약과 P9는 publication 2.11·4.6을 따른다. 이 선택은 앞선 상속/guard 합의를 대체하며 PG·이벤트 제품 계약은 바꾸지 않는다.
- **근거·예외:** 현재 브랜드 검증의 과거 주문은 POINT fixture이고 삭제 상품 확정은 최초 PG 확정 전 거절이다. 반면 상품 캐시 무효화 검증은 실제 PG SUCCESS를 만들어 격리가 필요하다. 스키마 전환 검증은 PG 결제 시작까지만 수행하므로 별도 발행 교체가 필요하지 않다. 이 판단 당시에는 코드 정적 확인이었다. 이후 코드 축소와 관련 회귀를 실행했으며 결과는 별도 검증 기록에 둔다.
- **대안·비용:** 전역 guard는 적용 누락을 기동 실패로 탐지하지만 모든 컨텍스트를 주문 이벤트 설정과 결합한다. 범위를 좁히면 이 결합과 조립 코드를 줄이는 대신 새 PG 확정 테스트의 fake 누락을 전역 자동 차단하지 못한다. 관련 테스트의 실제 호출 경로와 포트 선택을 명시적으로 검토·검증한다. mock/fake 기록을 broker 저장 근거로 사용하지 않는 원칙은 유지한다.
- **상태:** 기준 설계의 범위 변경을 반영했다. 이후 코드 축소·삭제와 회귀 재실행을 마쳤고 `779512f`에 반영했다. 종전 849건 결과는 축소 후 통과 근거가 아니다.

### 발행 검증 전용 임시 스키마 — 2026-10-29

- **문제:** 실제 broker 발행 검증(P4·P6~P8)은 SpringApplicationBuilder로 앱을 create/validate 기동·재기동한다. 기본 테스트 스키마를 쓰면 캐시된 다른 테스트 컨텍스트의 데이터·DDL과 섞인다.
- **사용자 승인 선택:** 기존 MySQL 테스트 컨테이너 안에 임시 스키마 `order_event_kafka`를 만들어 쓰고 종료 시 삭제한다. 새 DB 컨테이너는 만들지 않는다. streamer·C10의 별도 스키마 허용으로 확대하지 않는다.
- **비용·한계:** 테스트가 root 접속으로 스키마 생성·권한 부여·삭제를 수행한다. 정리 일부가 실패해도 나머지를 시도하고 오류를 보존하지만, JVM 강제 종료 시 스키마가 컨테이너 수명 동안 남을 수 있다(컨테이너는 테스트 종료와 함께 사라짐).

## A.36 W7 Outbox 교체 경계와 W6 준비→복구의 기본 방향

**상태:** 2026-11-03 사용자가 기존 W6 테스트 구성 보존·활용을 기본으로 전체 흐름·변경 경계 초안 작성을 승인했다. 흐름 원본은 [발행 설계의 W7 절](../features/order-events/publication.md)이다. 아래는 원문 요구·합의한 기본 방향·대안과 비용의 기록이며, 제품 상세설계 최종 승인이나 실행 검증 결과가 아니다. A.34·A.35의 W6 당시 Outbox 제외·직접 발행 판단은 삭제하지 않는다.

### 문제와 제약

- **원문 요구:** 최초 PG 확정·예약 소비·PG 성공 사실과 Outbox를 같은 로컬 TX에 저장하고 단일 relay가 broker 확인 뒤 상태를 기록한다. W6의 안정 ID·불변 사실과 소비 멱등성은 계속 사용한다. 원문의 근거는 실습 Implementation Quest 1~8절·Checklist와 발제의 원자성·relay·재발행·보존 설명이다.
- **원문 요구:** W6 직접 발행의 미발행 A·소비 완료 B를 실제 API·PG로 준비한 뒤 같은 실행 상태에서 복구한다. 과거 수치 비교만으로 충족하지 않으며, W7 실행 뒤 Outbox 삭제·SUCCESS 직접 삽입·운영용 우회 스위치로 준비하지 않는다. 준비와 복구의 PG 호출·거래 수를 분리하고 복구 중 추가 호출·재확정·예약 추가 소비는 0이다.
- **코드 확인:** 현재 `PaymentTransactionService.applyObservation`이 최초 CONFIRM에서 사건을 등록하고 `OrderConfirmedEventListener`가 AFTER_COMMIT 직접 발행한다. W7로 이 경계를 교체하면 최신 경로로 확정한 주문은 이미 Outbox를 가지므로 과거 출발 상태를 그대로 만들 수 없다. 현재 `void publish`는 전송 오류를 로그로만 관측해 relay 상태 판단에 그대로 사용할 수 없다.
- **코드·과거 기록 확인:** C10은 두 사례와 고정 입력·실제 broker/소비 관찰을 제공하지만 종료 시 API 데이터·구매 테이블·PG·소유 Kafka 자원을 정리한다. 원본 임시 상태가 계속 남는다는 뜻이 아니다. 이번 작업에서는 실제 인프라 상태를 조회하지 않았고, 보존한 원본 DB가 별도로 존재한다고 가정하지 않는다.

## A.37 JSON payload 보존·due 조회와 최초 확정 TX

**상태:** 2026-11-03 사용자가 2단계 문서 작성을 승인했고, 질문 뒤 JSON 문자열의 텍스트 보존과 due 대상의 다음 시도 시각→ID 순서를 선택했다. 저장 책임·타입/제약·클래스/메서드·처리 의사코드·검증 기준의 원본은 [발행 설계 W7.2](../features/order-events/publication.md)다. 설계 초안이며 구현·실행 검증·전체 설계 최종 승인은 아니다.

### 원문·코드 사실·사용자 선택의 구분

- **원문:** messageKey·payload를 생성 뒤 변경하지 않고 같은 확정 TX에서 저장한다. serialization 실패도 TX 실패다. 필수 메타데이터·eventId 유일 제약·작은 묶음의 안정된 due 조회·인덱스 검토를 요구하지만, TEXT 대 JSON 열이나 정렬 우선순위는 지정하지 않는다.
- **사용자 선택:** 두 payload 후보의 차이를 묻는 과정에서 사용자는 개별 업무 컬럼의 재조합보다 JSON 저장이 일반적인지 질문했다. 두 후보 모두 JSON 본문 한 값을 보존하며 차이는 DB 열 타입임을 설명한 뒤, 사용자는 "텍스트 열에 JSON 문자열 보존"을 선택했다. 이 해설 질문 자체를 선택 승인으로 처리하지 않았다. 이후 "다음 시도 시각 → ID 순서"를 별도로 선택했다.
- **코드:** 현재 Kafka adapter는 내부 v1 DTO를 `JsonSerializer<Object>`로 전송하고 송신 Future의 실패를 로그로만 관측한다. 현재 Order 잠금·공통 CONFIRM 분기·snapshot 생성·BEFORE_COMMIT probe를 유지하면서 직렬화·Outbox 저장을 TX 안에 배치할 수 있도록 설계한다. 공통 BaseEntity·EnumNameConverter·계층별 포트/JPA 규칙을 사용한다.
- **외부 문서 확인:** Microservices.io의 「Pattern: Transactional outbox」 Solution 절은 전달할 메시지 자체를 업무 변경 TX에 보존하는 구성을 설명한다. Debezium 3.7 「Outbox Event Router」 Basic outbox table·Payload serialization format 절은 메타데이터와 JSON payload를 분리한 예시와 JSON 형식을 설명한다. 이는 JSON payload 구성의 대표 근거이며 TEXT가 JSON 열보다 더 널리 쓰인다는 통계·이번 CDC 도입 근거가 아니다.

### relay 설명의 정정과 미정 경계

사용자가 relay가 스케줄러인지 물었을 때 Codex가 특정 앱 내부 스케줄러를 먼저 확정하겠다고 답했고 사용자는 원문 기준으로 답하라고 지적했다. 발제는 한 프로세스의 단일 polling 흐름, 실습 3절은 scheduler/수동 실행 중첩 방지와 로컬 활성화 설정을 요구한다. 특정 앱 내부 배치나 별도 서버를 강제하지 않는다. 2단계 당시 commerce-api 내부 스케줄러는 미승인 제안이었으며 두 저장 선택으로 승인된 것이 아니었다. 이후 3단계에서 별도 질문으로 확인한 선택은 A.38을 따른다.

전송 포트·factory/template·상태 전이·시도 증가·유한 대기/재시도·오류 분류·실행 위치·보존과 W6 복구의 비교/TX/경쟁 처리는 후속 단계에서 구체화한다. TEXT 보존을 선택했다고 복구의 동일 사실 비교를 raw 문자열 동등성으로 정하지 않으며 기존 v1의 표현 차이 허용을 유지한다. 현재 결과는 문서·소스 대조이며 MySQL DDL·조회 계획·Kafka wire·원자성/복구 실행 결과가 아니다.

## A.38 내부 단일 relay·자동 시도 예산·BLOCKED와 주문별 복구

**상태:** 사용자가 2단계 검토 요약을 확인하고 3단계 작성을 허락한 뒤 아래 선택을 개별 확인했다. 계약·클래스/메서드·내부 처리 의사코드·검증 기준의 원본은 [발행 설계 W7.3](../features/order-events/publication.md)이다. 문서 초안이며 코드·설정 변경·실행 검증·전체 설계 최종 승인은 아니다.

### 원문 요구와 사용자 선택

- **원문:** 한 프로세스의 단일 polling 흐름·scheduler/수동 중첩 방지·DB TX와 외부 전송 대기 분리·실제 Future 성공 뒤 별도 상태 TX·같은 사건 재시도/재개를 요구한다. 특정 실행 앱·간격/횟수 숫자·BLOCKED는 지정하지 않는다. BLOCKED를 쓰면 미해결 보존과 같은 행 재개 경로가 필요하다.
- **사용자 선택:** commerce-api 내부 전용 스케줄러를 채택했다. 초기 두 상태 유지 제안에는 바로 동의하지 않고 BLOCKED·간격 상한·DLQ 관계·대표 중단 기준을 질문했다. 이 질문들을 선택 승인으로 처리하지 않았고, 설명 후 "오류 구분·시도 한도·BLOCKED 적용"을 확인받았다. DLQ 전송은 추가하지 않는다.
- **숫자 선택:** 자동 scheduler 기본 OFF·로컬 한 인스턴스 명시 활성화, 완료 후 1초 대기·최대 10행 직렬, Future 대기 35초·재시도 5초 시작/60초 상한·최초 포함 회차당 10회 조합을 사용자가 선택했다. 장애 중 회차가 수분 걸릴 수 있고 실측 적정값이 아님을 설명했다.
- **재개·복구 선택:** 누적 시도 수는 보존하며 재개 후 예산을 새로 부여하는 안, 여러 대상의 주문별 TX·부분 완료/오류 대상 명시를 사용자가 선택했다. 자동 재개·전체 목록의 암묵적인 원자 처리로 확대하지 않는다.

### 근거와 미검증 경계

원문 근거는 발제의 relay·재처리·관찰/보존과 실습 3~7절이다. 현재 전용 producer의 설정·비트랜잭션 검사·Clock/consumer 계약을 코드와 대조했다. Microsoft Azure Architecture Center 「Retry pattern」 Retry strategies 절은 재시도 불가능한 오류의 중단과 지연/최대 시도 횟수를 구분한다. Spring Modulith 2.1.1 「Working with Application Events」 Publication details·Failed publications and resubmission은 시도 수·시각을 이용한 재시도 정책과 명시 재개 사례다. 이는 대표 설계의 설명 근거이며 BLOCKED라는 표준 상태·이 숫자의 보편성·새 라이브러리 도입을 뜻하지 않는다.

현재 숫자와 gate/상태/TX 구조는 실행 결과가 아니다. DB 결과 불명·producer 늦은 완료·장애 시 회차/종료 지연·불완전한 원본·DB 손상·사람의 미재개가 수렴을 막을 수 있다. 특히 본문 자체가 잘못된 경우 immutable 사실을 임의 덮어쓰는 자동 수리 경로를 추가하지 않았다. W6 소스/컨텍스트 보존의 테스트 조립 설계와 전체 기준 문서/검증 통합은 W7.4·A.39를 따른다. 실제 기동/실행 검증은 남아 있다.

정상 종료의 정지 순서는 로컬 Spring Context 6.2.5 ExecutorConfigurationSupport의 기본 phase=MAX_VALUE/2·setPhase·stop/shutdown과 Spring Kafka 3.3.4 DefaultKafkaProducerFactory의 phase=MIN_VALUE·stop→destroy 소스를 확인했다. relay phase=0·전용 scheduler pool=-100을 명시해 기본값에 의존하지 않는 구성으로 설계했다. 소스 대조는 실제 종료 순서·완료/timeout 검증의 대체 근거가 아니다.

## A.39 W6 기록 역할 분리·보존 테스트 구성과 동일 실행 복구 검증

**상태:** 2026-11-04 사용자가 4단계 문서 작업을 요청했고, 직접 Outbox 기록의 책임 분리를 질문한 뒤 “기록 역할 분리·W6 테스트 구성 연결”을 선택했다. 상세 구성·내부 순서·필수 검증의 원본은 [발행 W7.2~W7.4](../features/order-events/publication.md)다. 전체 Claude 검토·사용자 최종 승인·구현/실행 검증 전의 통합 초안이다.

### 문제·제약·선택

원문 실습 5절은 과거 수치와 새 결과를 비교하는 실험이 아니라, 실제 W6 확정/직접 발행 경로로 A(미발행)·B(소비 완료)를 준비하고 같은 실행의 DB·broker·PG 상태를 W7 복구에 연결하는 검증이다. C10의 고정 입력/재현 코드/관찰은 재사용하지만 당시 원본 행을 복원했다고 하지 않는다. 중간 cleanup·PG reset·W7 Outbox 삭제·SUCCESS 직접 삽입·운영용 우회 스위치는 허용하지 않는다.

2단계의 PaymentTransactionService 직접 encoder/Outbox 의존으로는 같은 구체 서비스를 실행해 Outbox 없는 W6 준비를 만들 수 없다. Facade들이 그 구체 타입을 참조하므로 W6 TX 서비스 전체 복제는 타입 연결과 공통 PG/잠금/상태 규칙의 이중 관리가 따른다. 사용자는 확정 사실 기록만 application의 OrderConfirmedRecorder로 분리하는 안을 선택했다. 제품 구현은 항상 같은 TX Outbox 기록이며 테스트 구성에서만 기존 Spring 이벤트 등록→실제 AFTER_COMMIT 전송을 연결한다. 기록 위치·PG 판정·예약·시각은 공유하고 제품의 실행 모드는 추가하지 않는다.

### 검증·회귀 판단과 한계

사용자는 추가 질문에서 “복구 검증을 별도 테스트 작업으로 격리”를 선택했다. 실제 MySqlTestContainersConfig는 static container를 JVM 안에서 공유하며, root의 기존 JUnit/profile/시간대 설정과 API의 streamer bootJar 연결은 일반 test에만 적용돼 있다. 따라서 전용 w6OutboxRecoveryTest는 그 설정/입력 연결을 명시하고 일반 test와 정확한 대상 분리·check 연결·실제 결과 수집을 수행한다. W7.4-2가 구성 계약의 원본이며 Gradle/코드 변경이나 실행은 아직 없다.

실제 API/PG·DB·Kafka·streamer 연결은 O7/O11로 확인하고 통제 sender/Future/Clock의 예산/늦은 완료 검증과 구분한다. broker 성공 뒤 상태 저장 전 중단은 실제 metadata와 두 broker record/offset·두 번 이상 수신·한 번의 구매 효과로 입증한다. O11은 준비 C/T 및 모든 PG 호출 기준을 고정한 뒤 전환/복구에서 증가 0, A 생성/B 전체 행 불변·두 번째 복구 불변을 확인한다. 기존 PG/HTTP/소비 기대값을 완화하지 않으며 W6의 직접 호출 기대만 보존 구성으로 옮기고 W7의 실제 Outbox 원자성 검증으로 대응한다.

단일 broker 장애 재현은 소유 topic에만 영향을 주고 finally 원복하며, 긴 broker 실패를 열 번 반복해 예산 정책을 증명하지 않는다. 배정은 실제 E2E 준비 조건으로 유지하되 W6 배정/성능 실험은 새 필수 실험으로 반복하지 않는다. 테스트 0건·skip·연결 실패·과거 통과는 이번 통과가 아니다.

Boot 3.4.4 JpaBaseConfiguration의 managedTypes/filter 연결과 Spring Context 6.2.5 ConfigurationClassUtils의 명시 @Bean 클래스 인식을 로컬 배포 소스로 확인했다. 이는 테스트 구성을 설계한 근거이며 실제 scan/기동·DDL 보존·전송/복구·회귀/종료 결과는 미확인이다. 보존 구성의 기계적 변경이 wire/AFTER_COMMIT·오류/PG 확정 계약까지 바꾸거나 update가 기존 사실을 바꾸는 관찰이 나오면 멈추고 사용자와 구성 대안을 재검토한다. 문서 세트만으로 같은 계약을 구현하는 것이 완료 조건이며 실제 누락/모순을 구현자가 추측해 메우지 않는다.

## A.40 Claude 1차 검토 대조와 W7 보완

### 문제·선택·비용

- W6 준비는 @Bean을 해석할 CCPP 전의 등록과, 생성된 W7 정의를 지울 CCPP 뒤 BDRPP를 구분한다. 기존 C10 교체 도구를 모든 조립 시점에 그대로 사용할 수 있다는 설명을 보완했다. 조립 순서가 늘어나는 것이 아니라 이미 있는 Spring 단계별 책임을 명시한 것이다.

- O6/O7은 새 relay 객체·기존 협력 bean/공유 gate와 가변 outbox Clock으로 명시한다. 새 context/producer/별도 gate를 만들지 않아 기동 비용·동일 프로세스 잠금 혼입을 줄인다. JVM/OS 강제 종료 검증이라고 확대하지 않으며 실제 broker/consumer 증거는 그대로 필요하다.
- 기존 flush 경계는 유지한다. Spring Data 예외 변환과 기존 결제 제약 분류를 보존하고, SQL/예외가 드러나는 위치와 기존 SUCCESS 회귀를 W7에 연결한다. flush를 없애 실패 주입의 의미를 바꾸거나 기존 테스트가 전혀 없다는 전제로 중복 검증을 만들지 않는다.

기존 단위/회귀를 두 테스트로 대체한다는 뜻은 아니다. 큰 E2E 두 흐름 외에 원자성·모델·설정·재시도/차단·종료·PG/소비 회귀는 목적에 맞게 유지한다. 제품의 새 서버·우회 모드·새 운영 DB 구조·범용 테스트 프레임워크는 추가하지 않는다. 실제 시간/비용 개선을 측정한 결과는 아니다.

### G1~G5 처리·근거

- G1: O6을 실제 APPLIED·완료 1·품목 활동/수량·group offset·업무 추가 효과 0까지 명시했다. O6→O7의 첫 중단/활동 0→새 relay 첫 발행/ACK 뒤 상태 중단→첫 실제 활동→새 relay 재발행/중복 수렴을 같은 사건에 연결한다. 중간 PENDING은 소비 미완료가 아니라 이어진 O7 중단의 결과이며 최종 PUBLISHED는 재발행 뒤 확인한다.
- G2: 신규 전달 클래스는 정상 W7 context·기본 테스트 DB·실제 child 하나, O11은 별도 worker/같은 상태의 W6→W7 전환, O5/O10만 발행 전용 임시 스키마다. 빈 시작/배정·writer 정지 후 DROP·부분 실패 정리·기존 300초 전체 예산을 명시했다. O9 probe는 O6/O7 대상에 적용되지 않게 하고 PG/업무 기준은 각 확정 뒤 idle 상태에서 고정한다.
- G3: 대상 TX 전 STOPPING/interrupt 확인을 추가했다. 아직 TX를 호출하지 않은 대상은 failedOrderId를 비우고 현재부터 모두 unattempted로 보고한다. 진행 TX 실패만 해당 ID를 failed로 남긴다. 이전 commit/interrupt는 보존하며 경계 사이 경쟁을 원자적으로 차단했다거나 DB 결과 불명을 확정 rollback이라 하지 않는다.
- G4: 소비 문서의 보존된 streamer 재기동 validate와 O11의 API 스키마 추가 update는 다른 앱/목적임을 명시했다. W6의 “C10에만 child JVM” 문구와 W7의 전달/O11 범위를 읽기 안내로 구분하고 제품 소비 계약 본문은 보존한다.
- G5: [과거 실행 기록](../verification/order-events.md) 앞에 W7 읽기 안내와 구현 후 목표 명령만 추가한다. W6 명령/결과 본문은 변경하지 않는다. 현재 W7 클래스/작업이 실행됐다는 뜻이나 0건 통과의 근거로 쓰지 않는다.

2차 Claude는 이전에 생략한 소비/과거 실행 기록 본문도 전체 읽었다고 보고했다. F1·F3·F4·R1 등 기존 보완의 재대조와 새 G1~G5를 구분하며, 검토 제안을 사용자 승인/실제 실행 결과로 대신하지 않는다. 실제 DDL·wire·시간/종료·consumer/PG/E2E·회귀는 모두 미실행이고 사용자 전체 최종 승인을 남긴다.

### 3차 정적 재확인과 마지막 명확화

2026-11-04 사용자가 전달한 3차 Claude 답변은 G1~G5 해결·구현 전 계약 결함 0·새 사용자 결정 없음으로 정리했다. Codex가 최신 계약/코드 경계와 실제 Boot 3.4.4 BOM을 대조하고, 기존 보완 승인 범위에서 C1/C2를 명시했다. 이는 검토자의 승인이나 사용자 전체 설계 승인·실행 통과를 뜻하지 않는다.

- C1: afterBrokerConfirmed의 통제 예외는 그대로 호출자에게 전파하고, 상태 TX 없이 finally에서 gate를 해제한다. 기존 send catch 바깥/예외 전파 계약을 명확히 한 것으로 오류를 정상 결과로 삼키지 않는다.
- C2: 복구 대상 사이 장벽은 테스트측 위임 대역이 실제 TX 프록시의 commit 반환 뒤에 둔다. 테스트용 Operations 조립·실제 공유 gate를 쓰고 대역을 별도 TX bean으로 재등록하지 않는다. 제품 probe/새 정책을 추가하지 않으며 장벽 자체의 interrupt와 다음 대상 전 종료 판정을 혼동하지 않는다.
- 실행 확인: 캐시 context/이전 실행 잔여물의 진단, min ISR 실패의 실제 오류 코드/같은 producer 회복, 전체 300초 단계별 시간과 probe/gate 상태는 구현 때 실제 관찰한다. 기존 검증 기준·timeout을 완화하지 않고 미실행을 통과로 쓰지 않는다.

현재 신규 정책 질문은 없다. 사용자 전체 최종 승인 뒤 승인된 작은 구현 단위에서 검증하며 이 문서 보완만으로 구현을 시작하지 않는다. 정적 검토에서 발견하지 못한 실제 누락/모순은 발견 시 다시 질문한다.

## A.42 W7 전체 설계 최종 승인과 구현 검토 인계

2026-11-04 사용자는 최종 설계 요약과 발제·실습 원문 부합 검토를 확인한 뒤 설계 문서만 스테이징하고 커밋 메시지 및 새 Codex 구현 검토 탭의 프롬프트를 요청했다. 이 요청을 W7 보완본 전체의 사용자 최종 승인으로 기록한다. Claude는 구현, 새 Codex 탭은 구현 검토를 담당하고 사용자가 프롬프트와 결과를 전달한다. AI 검토가 승인을 대신하지 않는다.
