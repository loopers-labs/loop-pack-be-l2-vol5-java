기존 문서의 계약·절 번호·승인/검증 상태를 보존해 이동했다. 재편 자체는 제품 계약 변경이나 새 실행 검증을 뜻하지 않는다.

## A.17 결제 시도·재고 예약의 저장 단위

2026-10-22 사용자 검토에서 주문당 한 시도·품목 불변·부분 취소 없음의 현재 범위에 맞춰 저장 구조를 단순화했다. payment 한 행이 준비·대기·성공·실패를 모두 나타내며 성공 전용 결제나 별도 시도 테이블을 추가하지 않는다. 재고 예약은 별도 행 대신 고정 주문 품목과 주문·결제 상태로 표현하고, 충돌 상세만 payment_conflict에 분리한다. 이름과 배치 변경은 새로운 결제·취소 기능 추가가 아니다.

|대안|이점|비용·유리한 조건|
|---|---|---|
|orders·order_item에 결제 정보까지 병합|새 테이블·조회 감소|주문에 PG 키·확인 책임이 섞임. 결제 자체의 별도 수명이 없을 때 유리|
|payment + 고정 order_item + 마지막 payment_conflict — 채택|품목 수량 중복 저장·독립 예약 상태 관리 감소, 결제/충돌 책임 분리|Order/Payment와 재고 효과의 원자적 전이·품목 불변 검증 필요. 현재 한 시도·일괄 처리 범위에 맞음|
|별도 상품별 예약 모델 유지|상품별 확보·소비·반환을 직접 조회·검사|테이블·Repository·수량/상태 중복 검증 증가. 부분 확보·해제·독립 예약 수명이 필요할 때 유리|
|전체 결제 관찰·충돌 이력 저장|감사·사건 순서 복원에 유리|저장량·중복 판정·보존 정책 추가. 현재 마지막 요약 범위를 초과|

**근거 구분:** 실습은 확보 수량·상태와 중복 반환 방지를 요구하지만 별도 예약 테이블을 강제하지 않는다. 기존 OrderItem의 상품·수량·단가는 생성 뒤 고정이라는 **코드/계약 확인**과 한 시도·부분 취소 없음의 **합의**를 근거로, 고정 품목+주문/결제 종결을 확보 증거로 사용한다는 **설계 추론**이다. 별도 예약 테이블이 정합성에 필수라는 주장은 철회하며 구현·비교 실험 결과는 아니다.

Product.Stock은 가용 재고다. TX A의 선차감·payment 생성·PAYMENT_PENDING·ORDER_RESERVATION 이력은 함께 commit한다. TX B는 Order 잠금 후 미종결을 확인한 확정 실패에만 고정 품목 수량을 현재 재고에 더하고 FAILED·PAYMENT_FAILED·ORDER_RELEASE를 함께 commit한다. 같은 종결은 재고를 바꾸지 않는다. 성공은 CONFIRMED·SUCCESS가 확보 소비를 나타내고 추가 재고 이력이 없다. 과거 ORDER_DEDUCTION과 POINT 사실은 보존한다.

### 근거·대안이 유리한 조건

orders.payment_method로 과거 POINT를 명시하고 금액·품목을 보존한다. 새 PG 행을 역으로 만들거나 시도 부재로 방식을 매번 추측하지 않는다. 새 열·기존 금액 컬럼 이름 전환·행 검증·POINT 보정 비용은 [3.6](../features/order-payment/model.md#36-pg-저장-모델과-제약)의 전환 계약을 따른다. 값 불일치는 임의 보정하지 않고 전환 중단이다.

payment의 unique는 order_id·attempt_key·(provider, provider_account, transaction_key) 세 개다. 외부 주문 ID는 내부 order_id의 결정적 매핑이므로 네 번째 unique를 제거하고 같은 컬럼의 일반 조회 인덱스를 유지한다. 정상 생성 규칙에서 중복 방어가 겹친다는 단순화이며 외부 ID 매핑 버그·우회 SQL까지 DB에서 잡던 추가 방어를 포기한다. 생성·적용 때 매핑을 검증하고 콜백 후보가 복수면 500·PG 호출 없음으로 종료한다. 다양한 매핑·키 재사용 규칙으로 바뀌면 unique를 재검토한다.

### 숨은 비용·미확인 가정

- 주문·결제 상태는 같은 TX에서 전이해야 하며 직접 SQL이 상태만 바꾸면 선차감·반환 사실을 복원할 수 없다. 품목 수량의 수정/삭제와 부분 반환은 금지한다.
- 상품별 독립 예약 상태는 저장하지 않는다. 여러 결제 시도·부분 결제·예약 일부 해제·주문 품목 변경 요구가 생기면 재설계한다.
- payment_conflict는 충돌 때만 생성/갱신하고 일반 주문 응답에는 조인하지 않는다. 한 결제의 마지막 요약 하나를 보장하는 UNIQUE(payment_id)가 이 별도 테이블에 필요하며 payment의 세 unique와 목적이 다르다.
- 마지막 요약은 전체 감사 이력이 아니다. 정상 확인 뒤에도 남아 있는 과거 충돌과 현재 verificationStatus를 구분해야 한다. 확인 metadata를 별도 payment_info로 분리하는 대안은 결제 컬럼을 줄이지만 매 확인마다 두 행의 생성·잠금·조회/저장을 관리하므로 채택하지 않았다.
- 기존 POINT 전환 데이터의 예외 빈도와 새 구조의 쿼리/쓰기 비용은 실측하지 않았다. 테이블 수 감소를 성능 개선의 실험 결과로 주장하지 않는다.

### FK와 애플리케이션 정합성

**합의:** payment·payment_conflict는 scalar ID로 참조하고 물리 FK는 두지 않는다. scalar ID와 FK는 독립이며 FK는 부모 부재/하드 삭제를 DB에서 막는 대안이다. 현재는 같은 TX의 주문·품목·결제 검사와 부모 잠금을 사용하고 하드 삭제/cascade 제거 경로를 제공하지 않는다. unique·CHECK는 고아 참조나 테이블 간 상태 일치를 대신하지 않으며 우회 SQL·잘못된 fixture는 보호되지 않는다. conflict 요약도 부모 잠금 아래 생성하고 같은 TX의 오류는 rollback한다.

### 재검토 조건

부분 처리·다중 시도·품목 수정·예약 만료·하드 삭제·외부 쓰기·FK 필요성이 생기거나 고아/상태 불일치·조회 중복이 발견되면 저장/보호 경계를 다시 검토한다. 모든 충돌의 감사·재현이 필요하면 마지막 요약과 전체 이력을 비교한다. 현재 비용·빈도 실측이나 자동 복구는 없다.

## A.18 외부 호출 전후의 동시성 제어

|대안|이점|비용·한계|
|---|---|---|
|짧은 비관적 잠금 + DB unique — 채택|기존 관리자·상품 변경과 같은 행 보호, Entity 행동·정확한 재고 이력 재사용|잠금 대기·deadlock, 모든 변경 경로의 획득 순서 관리|
|낙관적 version + 로컬 충돌 재처리|저충돌에서 잠금 대기 감소 가능|version 스키마·충돌 처리·PG 발송과 로컬 재처리의 엄격한 분리 필요|
|조건부 SQL 갱신|조건 검사·변경을 SQL로 결합 가능|수정 행 0의 원인 분류, 정확한 before/after 이력, 기존 관리자 변경 경로와의 규칙 추가|

Order PK를 먼저 잠그고 Payment/PaymentConflict는 일반 조회한다. TX A/실패 반환에서 필요한 Product만 ID 오름차순으로 추가 잠금하며, 확인 준비·충돌 기록은 Order 잠금으로 해당 결제의 쓰기를 직렬화한다. 모든 자식 생성·변경 경로가 같은 Order 잠금을 commit까지 지키는 것이 전제다. 실제 잠금 순서·대기·한계는 SQL과 실행계획·경쟁 검증으로 확인하며 비관적 잠금이 모든 deadlock을 없앤다고 주장하지 않는다. 기존 상품 단일 쿼리 선택과 전환 기준을 유지한다.

**2026-10-22 Claude 지적 1에 대한 사용자 승인 변경:** 결제/요약 부재에도 자식을 선행 FOR UPDATE로 찾던 초안은 서로 다른 주문의 INSERT에 불필요한 구간 간섭을 만들 수 있다는 검토를 받았다. TX A의 최초 payment INSERT 자체는 유지한다. Order 잠금으로 같은 주문을 직렬화하는 현재 범위에서는 자식의 별도 잠금 조회를 제거하고 기존 REPEATABLE READ를 유지한다. INSERT/UPDATE·unique 검사·공유 Product의 DB 잠금은 남으며, 지적의 실제 재현·해결 검증을 수행한 것은 아니다.

|추가 검토 대안|이점|비용·현재 판단|
|---|---|---|
|Order 잠금 + 자식 일반 조회 — 채택|부모로 쓰기 직렬화, 없는 자식의 선행 잠금 조회 제거, 격리 수준 유지|업무 TX의 첫 업무 SQL을 Order 잠금으로 제한하고 최신 읽기/영속성 컨텍스트 경계를 검증해야 함|
|존재할 때만 자식 잠금을 유지하는 혼합안|기존 행의 locking read를 유지할 수 있음|부재/존재 경로의 조회 규칙 분기, 콜백 선행 Entity/스냅샷 문제는 별도 해소 필요. 부모 직렬화와 중복된 잠금은 현재 추가하지 않음|
|PG TX만 READ COMMITTED로 변경|자식 잠금 조회 구조를 유지하는 대안|PG TX의 읽기 의미/영향을 다시 검토해야 하므로 사용자 선택에 따라 미채택. 모든 unique 검사 잠금·deadlock 제거를 보장하는 대안도 아님|

**조회 수명·근거·검증:** 같은 TX에서 Order 잠금 전에 일반 조회하면 오래된 스냅샷/Entity를 후속 판단에 사용할 수 있다. 콜백은 별도 readOnly TX의 스칼라 orderId 후보 식별을 끝내고, 새 업무 TX의 첫 업무 SQL로 Order를 잠근 뒤 자식을 처음 일반 조회한다. 상위 TX 없음·OSIV=false·Entity 재사용 금지로 호출별 경계를 유지하고 고정 외부 ID 매핑을 잠금 뒤 재검증한다. 이는 기존 부모 직렬화 규칙과 읽기 수명을 맞춘 설계 판단이며 실제 MySQL/JPA 동작의 통과 근거는 아니다. 4.3·4.5에서 독립 주문/결제의 첫 INSERT, 같은 부모의 중복 생성/교체, 잠금 대기 후 최신 종결/요약, 후보 식별 뒤 종결된 콜백의 terminalAtStart를 필수 검증한다. 미충족 시 원인을 확인해 설계를 재검토한다.

외부 HTTP 동안 TX와 잠금을 유지하는 대안은 느린 응답·timeout 동안 재고 변경 요청까지 대기시키므로 채택하지 않는다. TX A commit으로 먼저 확보하고 검증된 결과를 별도 TX B에 반영한다. DB unique는 주문 외부의 동일 UUID·동일 PG 거래 경합도 보호한다. local TX 실패와 외부 요청 실패는 구분하고 자동 create 재시도는 금지한다.

### 근거·대안이 유리한 조건

**코드 확인:** 기존 Order·Product 관리자 변경 경로는 비관적 잠금을 사용한다. **합의:** 짧은 비관적 잠금과 DB unique를 유지한다. **설계 추론:** 동일 상품을 변경하는 기존 경로와 보호 규칙을 맞추고 변경 전후 이력 구조를 재사용하는 이점이 현재 크다. 낙관적 잠금보다 빠르다는 성능 결과는 없다.

낙관적 잠금은 실제 충돌이 적고 로컬 TX 재처리 비용을 감당할 수 있을 때, 조건부 갱신은 Entity와 이력 조립을 우회하는 비용보다 왕복·처리량 이점이 클 때 유리할 수 있다. 둘 다 구현 가능한 대안이다. 낙관적 잠금을 선택해도 외부 create를 같은 재처리 루프에 넣을 수는 없다.

### 숨은 비용·미확인 가정

- **미검증 가정:** 선행 일반 조회가 없는 새 업무 TX에서, 대기하는 Order SELECT FOR UPDATE가 잠금 획득 전에 스냅샷을 정해 후속 일반 조회를 대기 전 상태에 고정하지 않는다고 전제한다. 이것은 확인된 실행 사실이 아니며 V36의 잠금 대기 후 최신 종결/요약 조회로 검증한다. 실패하면 선행 스칼라/exists 조회·영속성 컨텍스트 재사용·실제 TX 수명을 먼저 확인하고, 경계를 지켜도 재현되면 부모 잠금/일반 조회 선택을 재검토한다.
- Order 잠금은 같은 주문의 중복 반영을 막지만 다른 주문의 동일 UUID·동일 외부 거래 경쟁은 막지 못한다. unique 제약이 별도로 필요하다.
- ID 오름차순은 잠금 요청의 일관성을 위한 규칙이다. 실제 DB 접근 계획·인덱스·격리 수준에 따라 잠금 범위가 달라지고 deadlock도 남는다. 기존 POINT의 EXPLAIN은 새 예약·삭제 포함 반환 경로의 검증 결과가 아니다.
- 짧은 TX라도 인기 상품 대기와 connection 점유가 생긴다. 여러 상품을 예약하는 동안 앞서 잡은 잠금은 유지된다. 다건 쿼리를 PK별 조회로 바꾸면 순서를 직접 제어하기 쉬워지지만 DB 왕복은 늘어난다.
- 자동 로컬 TX retry를 두지 않아 일시적 잠금 실패도 사용자에게 500으로 드러난다. 도입 시 TX A와 TX B, commit 결과 미확인을 구분하고 외부 create를 반복하지 않는 경계가 필요하다. 이는 현재 미채택 대안이다.

### 재검토 조건

앞의 대기 전 스냅샷 고정 가정이 V36에서 성립하지 않거나, 실제 lock 대기·deadlock·연결 대기·TX 지연이 허용 목표를 넘거나, 관리자/배치가 보호 규칙을 우회하면 잠금·쿼리·변경 경계를 재검토한다. 아직 목표 수치와 비교 실측은 없다. 격리 수준 변경·대량 품목 주문·인덱스 변경도 새 접근 계획과 경쟁 검증의 계기다.

|---|---|---|
|TX 없는 Facade + 별도 TX bean — 채택|호출 순서와 DB 원자성의 책임 분리, 외부 호출 위치를 드러냄|별도 객체·불변 입력/결과 계약 추가|
|TransactionTemplate|한 흐름에서 TX 구간을 명시적으로 감쌀 수 있음|처리 코드가 프로그램 방식의 TX 제어와 결합|
|전체 Facade @Transactional|기존 단일 TX 구조와 유사|외부 I/O까지 TX에 포함되므로 요구 경계에 맞지 않음|

별도 application PaymentTransactionService를 사용한다. Facade 간 호출 금지·순수 Domain Service 원칙을 유지하면서 기존 모든 변경 Facade 단일 TX 규칙에 PG 예외를 둔다. 기본 proxy mode의 자기 호출에는 TX가 적용되지 않으므로 별도 bean의 public 메서드를 외부에서 호출한다. 출처: Spring Framework 6.2 Reference, Using @Transactional 절의 프록시 모드·자기 호출 규칙.

충돌 요약을 저장한 뒤 TX 안에서 일반 RuntimeException을 던지면 기본 rollback 정책으로 기록도 사라질 수 있다. 결과 값을 반환해 commit한 뒤 409로 변환한다. 기술 DB 실패는 해당 TX 전체를 rollback한다. 외부 거래 unique 경합은 실패 TX 밖에서만 새 기록 TX를 실행하며 기록 자체 실패는 500이다. 모든 DB 오류를 충돌로 바꾸거나 실패한 TX 안에서 처리를 계속하지 않는다.

### 근거·대안이 유리한 조건

- **합의:** 외부 호출은 로컬 TX 밖, Facade는 다른 Facade를 호출하지 않음, Domain Service는 순수 규칙 유지. **공식 규칙:** Spring Framework 6.2 Reference의 Using @Transactional 절은 기본 프록시 모드의 자기 호출 한계를 설명한다. 별도 TX bean은 이 경계를 코드에서 드러내기 위한 선택이다.
- TransactionTemplate은 TX 구간을 한 메서드에서 직접 읽는 것이 더 중요하고 프로그램 방식 TX 제어를 받아들일 때 합리적이다. 별도 bean보다 원자성을 덜 제공하는 방식이 아니다. 메서드 분리만으로 원자성이 생기는 것도 아니다.
- 충돌을 정상 결과로 돌려 commit한 뒤 409로 변환하는 안은 증거 보존과 업무 결과를 함께 표현한다. 별도 독립 감사 TX·이벤트로 충돌을 남기는 대안은 실패 TX와 감사 기록의 수명이 달라야 할 때 유리하지만, 전달 실패·기록 순서·별도 자원 관리가 추가된다. 현재는 도입하지 않는다.

### 숨은 비용·미확인 가정

- 모든 API를 하나의 TX로 감싸던 관례에 예외가 생겼다. 이후 class-level @Transactional을 Facade에 다시 붙이거나 상위 호출자가 TX를 열면 경계가 깨질 수 있다. 코드 구조·실제 HTTP 중 TX 비보유 검증이 모두 필요하다.
- TX 밖에서는 Entity를 계속 사용할 수 없으므로 불변 요청·토큰·OrderInfo 복사와 변환 코드가 늘어난다. 오래 보관한 값은 상태 원본이 아니며 TX B가 잠근 최신 상태로 다시 검증한다.
- commit 시 발생한 unique 실패는 메서드 본문에서 놓칠 수 있다. TX 호출 바깥의 분류와 새 기록 TX가 필요하고, 제약 이름을 식별하지 못하면 무리하게 409로 바꾸지 않고 500이 된다.
- DB 접속이 끊겨 commit 결과를 확인하지 못한 경우, 예외가 났다는 사실만으로 모든 변경이 rollback됐다고 단정할 수 없다. 저장 상태 재조회가 필요하며 이미 수행한 PG create를 다시 호출할 이유가 되지 않는다.
- 오류 응답 변환 전에 충돌 TX가 commit돼야 한다. 테스트가 HTTP 코드만 보면 충돌 요약의 소실이나 부분 반영을 놓칠 수 있다.

### 재검토 조건

단계가 늘어 조율 코드가 여러 Facade에 반복되거나, 새로운 상위 TX·다른 진입 인터페이스가 생기면 TX 담당 객체와 공통 흐름의 경계를 다시 검토한다. 제약 예외의 이름 해석이 실제 MySQL/JPA에서 일치하지 않거나 기록 TX 실패가 반복되면 오류 분류·증거 보존 방식을 재검토한다. 원자성 검증 전에 예외를 삼키거나 새로운 전파 속성을 추가하지 않는다.

## A.20 업무 종결과 확인 순서·충돌 요약

2026-10-22 사용자 검토에서 확인 시작/적용 카운터와 충돌 순번을 제거하기로 승인했다. 최근 확인과 마지막 충돌은 DB에 마지막 반영해 commit한 관찰로 정의한다. 순번은 실습·PG가 제공한 필수 번호가 아니라 시작 순서 기준 metadata 최신성을 위해 초안에서 선택했던 내부 설계였다. 현재 한 결제·고정 종결 계약에서 이 표시 보장보다 단순화를 우선한다.

|대안|이점|비용·한계|
|---|---|---|
|DB 반영 순서로 마지막 확인 결정 — 채택|발급 카운터·번호 토큰·비교 제거, 기존 Order 잠금과 commit 순서 사용|먼저 시작한 느린 조회가 마지막에 반영되면 더 나중 시작 조회의 확인 정보를 교체할 수 있음|
|확인 시작 순번으로 metadata 보호|더 나중에 시작한 확인 결과 우선|발급 쓰기·카운터/토큰·비교 규칙 증가. PG의 실제 상태 버전이나 결제 중복 방지 수단은 아님|
|PG 조회 전체를 DB 잠금 안에서 직렬화|관찰 경쟁 단순화|외부 대기 동안 DB 연결·잠금을 유지하므로 채택하지 않음|

업무 종결 보호는 확인 표시 순서와 독립이다. 미종결의 유효 SUCCESS·FAILED를 적용하고 같은 종결의 업무 효과는 반복하지 않는다. 반대 종결은 기존 상태를 보존하고 충돌로 남긴다. 재고 반환과 실패 상태 변경은 같은 TX에서 처리해 두 번 반환하지 않는다. 순번 제거는 종결 후퇴·재발송·임의 반환 허용을 뜻하지 않는다.

CREATE의 늦은 UNAVAILABLE과, 저장 거래와 같고 식별·금액 충돌이 없는 늦은 PENDING은 종결 뒤 업무/확인 정보를 모두 변경하지 않는다. 다른 유효 거래의 늦은 CREATE는 3.6의 업무 충돌 코드 순서에 따라 IDENTITY_MISMATCH다(2026-10-22 지적 8 후속 합의). QUERY의 PENDING은 준비 때 미종결이면 늦은 관찰로 무시하고 준비 때 종결이면 후퇴 충돌이다. 이 구분에 필요한 source·terminalAtStart는 유지한다. 그 밖의 적용 가능한 PG 관찰은 TX B에서 최근 확인 결과·시각을 갱신한다. LOCAL_NOT_DISPATCHED는 PG 응답/조회가 아니므로 기존 확인 정보를 유지하며, 최초 NOT_CHECKED/null인 FAILED도 허용한다. 먼저 시작한 정상 PENDING이 뒤에 시작한 조회 실패보다 늦게 반영되면 마지막 확인은 VERIFIED가 될 수 있다. 표시 시각은 순서 판정용 버전으로 사용하지 않는다.

충돌 상세는 payment_conflict의 결제당 마지막 요약 0~1행이다. 충돌을 반영할 때마다 같은 Order 잠금 아래 Payment/기존 PaymentConflict를 일반 조회하여 생성/교체하고 payment의 확인 정보와 같은 TX에 저장한다. 정상 재확인으로 VERIFIED·UNAVAILABLE가 되어도 요약을 지우지 않는다. 다음 충돌만 교체하며 모든 충돌의 사건 순서·전체 감사 이력은 보장하지 않는다. 카드·원문 본문은 저장하지 않고 복수 거래에서 임의 대표 거래를 선택하지 않는다.

내부 고객 ID·시도 UUID·외부 주문 ID·거래 키는 별개다. 키 형식·제공자 범위·비노출과 금액/종결 검증은 그대로 유지한다. 결제 결과·확인 결과·충돌 상세를 구분한 API 의미는 [A.24](#a24-결제-상태확인-상태금액의-공개-표현), 토큰·처리 원본은 [3.6](../features/order-payment/model.md#36-pg-저장-모델과-제약)·[4.3](../features/order-payment/processing.md#43-주문-확정)을 따른다.

### 근거·대안이 유리한 조건

**합의:** 마지막 DB 반영 관찰 기준, 순번 제거, 종결 불변·같은 TX의 중복 반환 방지·별도 마지막 충돌 요약 유지. **설계 추론:** 업무 효과 정합성은 잠금·상태 전이·원자성으로 보호할 수 있고 내부 시작 순번이 PG의 진짜 최종 상태를 판별하지는 못하므로 현재 표시 보장에 비해 복잡성이 크다. 단순화는 실험 성능 우열의 결론이 아니다.

시작 순서 기준 최신성이 제품 요구일 때는 카운터를 재검토할 수 있다. PG가 권위 있는 거래 버전·이벤트 번호를 제공한다면 그 값으로 인과관계를 판단하는 대안이 더 직접적이다. 현재 PG에는 그 계약이 없다. 전체 관찰/충돌 감사가 필요하면 마지막 요약과 이력 테이블을 별도로 비교한다.

### 숨은 비용·미확인 가정

- 확인 준비의 짧은 TX·부모 잠금은 소유권/조회 대상과 terminalAtStart 복사를 위해 유지한다. 순번 발급 쓰기는 없지만 동시 확인 준비나 TX B끼리의 잠금 대기 자체가 사라지는 것은 아니다. 외부 HTTP는 항상 TX 밖이다.
- 최근 확인은 요청 시작·PG 사건의 최신이 아니라 마지막 DB 반영이다. 느린 이전 조회의 실패가 나중 반영돼 성공 결제 + UNAVAILABLE로 보일 수 있으며 업무 성공은 유지한다.
- terminalAtStart=false의 늦은 PENDING 무시는 불필요한 충돌을 줄이지만 실제 상태 후퇴인지까지 증명하지 않는다. 종결 뒤 시작한 새 조회의 PENDING은 여전히 충돌이다. PG 최종 상태 조회의 일관성은 현재 로컬 계약이며 일반 PG의 보편 속성으로 주장하지 않는다.
- 마지막 충돌은 현재 활성 충돌과 다를 수 있다. 정상 확인 뒤 남은 과거 요약을 현재 verificationStatus와 구분해야 하며 전체 사건 복원은 불가능하다.

### 재검토 조건

확인 정보가 반드시 요청 시작 순서를 따라야 하거나, 제공자가 권위 버전/다른 일관성의 조회를 제공하거나, 전체 충돌 감사·재현이 필요하면 표시/토큰/저장을 다시 비교한다. 확인·충돌 반영 순서 역전과 rollback을 구현 뒤 검증해야 하며 현재 실측·통과 결과는 없다.

## A.21 주문 생성·재고 확보·외부 결제의 순서

**선택·근거:** DRAFT는 품목·당시 단가·총액만 저장한다. confirm의 TX A에서 재고를 확보한 뒤 PG를 호출하고 검증된 성공의 TX B에서 주문을 확정한다. 이는 합의한 흐름이다. 외부 성공 뒤 재고 부족이 드러나는 상황을 피하고, 아직 결제를 시작하지 않은 초안은 재고를 점유하지 않기 위한 판단이다(**설계 추론**). 저장 품목·금액과 실행 순서는 [4.3](../features/order-payment/processing.md#43-주문-확정)을 따른다.

|대안|유리한 조건|받아들여야 할 비용|
|---|---|---|
|DRAFT 생성 때 재고 확보|초안 자체가 재고 확보를 약속하는 상품·판매 정책|결제를 시작하지 않은 주문의 장기 점유, 만료·해제 정책 필요|
|confirm에서 선확보 — 채택|결제 시작 전에 판매 수량을 확보해야 하는 현재 계약|불확실한 결제 결과 동안 예약 유지·실패 보상 필요|
|PG 성공 뒤 재고 차감|별도 재고 보장이나 결제 취소·보상 절차가 있는 경우|외부 성공 후 품절 가능성. 현재 제외한 취소·환불과 연결될 수 있음|

**숨은 비용·가정:** DRAFT 생성은 구매 가능 수량을 보장하지 않는다. 생성 후 confirm까지 가격은 저장값을 유지하지만 재고·삭제 상태는 다시 검사하므로 사용자는 결제 시작에서 거절될 수 있다. 오래된 DRAFT도 저장 단가를 사용하는 정책이며 가격 유효 기간을 검증한 것은 아니다. 재고 예약의 장기 점유 비용은 A.22를 따른다.

**재검토 조건:** 초안 자체에 재고 보장·가격 유효 기간이 필요하거나 예약 장기 점유가 허용되지 않으면 생성 시점·만료·보상 범위를 함께 다시 정한다. 사용자가 요구하지 않은 TTL·자동 취소는 추가하지 않는다.

## A.22 한 시도·발송 권한과 불확실한 외부 효과

**선택·근거:** 주문당 한 시도, TX A에서 발송 권한 기록, 기록 후 자동 create 재발송 금지다. PG가 호출자 멱등 키를 받지 않고 같은 외부 orderId의 새 POST가 중복 거래를 만들 수 있다는 [PG 계약](../features/pg-simulator/README.md#55-로컬-pg-http-계약)에 따른다. UUID는 내부 중복 시도를 구분하며 PG가 그 UUID로 중복 제거해 주지는 않는다.

|대안|유리한 조건|받아들여야 할 비용·전제|
|---|---|---|
|발송 기록 후 재발송 금지 — 채택|외부 중복 방지 수단이 없어 중복 결제를 피하는 것이 우선|실제 발송 전 중단도 미완료로 남음. 모든 주문의 완료를 보장하지 않음|
|동일 키로 PG 생성 재시도|PG가 멱등 키와 동일 요청의 결과 재현·보존 기간을 보장|제공자 계약·요청 일치·보존 기간 검증 필요. 현재 PG에서는 사용할 수 없음|
|Outbox·worker로 발송|프로세스 중단 후에도 발송할 의도를 내구성 있게 전달해야 할 때|전달 재시도와 외부 효과의 중복은 별개. Outbox만으로 현재 PG의 중복 거래 문제가 해결되지 않음|
|실패 후 새 결제 시도|고객의 재결제를 허용하고 이전 효과를 확정·격리할 수 있을 때|여러 시도·예약 귀속·이전 거래 지연 성공·취소/환불 정책 필요. 현재 범위에서 제외|

### 숨은 비용·미확인 가정

- dispatch_claimed_at은 발송 권한 기록이다. HTTP 전송 완료·PG 수신·외부 효과 발생의 증거가 아니다. 실제 호출은 0회일 수도 있어 ‘외부 결제가 정확히 한 번 실행됨’을 보장한다고 표현하지 않는다.
- 발송 전 중단과 발송 뒤 응답 유실을 DB 기록만으로 구별할 수 없다. 조회 0건도 외부에서 앞으로 거래가 나타나지 않는다는 증거로 사용하지 않는다. 이 선택으로 UNKNOWN과 예약이 계속 남을 수 있다.
- 고객 대사와 콜백만으로 모든 미완료가 결국 종결된다고 보장하지 않는다. 관리자 일괄 복구·스케줄러·수동 보정 절차는 현재 범위에 없다. 실제 서비스의 운영 완료 기준으로 쓰기에는 부족한 지점이다.
- 생성 HTTP client·프록시·회복 도구의 숨은 retry도 중복을 만들 수 있다. 구체 도구·재시도/redirect 비활성·시간 제한은 2.8~2.9에 기록했으며 실제 하위 client 적용은 구현 뒤 검증한다.
- DB commit 결과를 모르면 같은 키로 저장 상태를 다시 확인해야 한다. 단순히 예외가 났다는 이유로 새 키나 새 발송 권한을 만들지 않는다.

### 확정 실패와 효과 0건의 근거

유효 조회 FAILED는 거래가 있었고 실패로 종결했다는 관찰이다. REJECTED_NO_EFFECT는 지정된 생성 응답의 422·code·false·주문·금액을 모두 검증했을 때 거래가 생성되지 않았다는 별도 계약이다. 일반 timeout·HTTP 오류·조회 404/0건과 구분한다. 이 두 PG 관찰과 별개로 실제 생성 회로의 POST 진입 전 차단은 LOCAL_NOT_DISPATCHED/CIRCUIT_REJECTED으로 구분한다. 생성 POST의 확실한 최초 풀 획득 timeout도 2.8의 확정·client 보장 조건을 모두 충족할 때만 LOCAL_NOT_DISPATCHED/POOL_ACQUIRE_TIMEOUT으로 구분하며, 판정·반환 계약은 2.8과 A.32를 따른다. TX A 전 차단과 이후 반환의 판단·비용은 A.32를 따른다. 확정 실패는 예약 반환으로 이어지지만 failure_kind·거래 키 유무를 구분해 서로 모순되는 관찰을 탐지한다. HTTP 상태만으로 실패를 추정하는 대안은 구현이 작지만 외부 성공 뒤 재고를 반환할 위험이 있어 채택하지 않는다.

**재검토 조건:** 제공자 멱등 생성·확정 취소·권위 있는 거래 미생성 증명이 추가되거나, 장기 UNKNOWN·예약 점유가 운영 요구를 만족하지 못하면 발송·조회·보상·다중 시도 범위를 함께 재검토한다. 현재는 수치·빈도 실측이나 자동 해제 정책이 없다.

## A.23 즉시 응답·콜백·대사의 권위와 복구 경계

**선택·근거:** 고정 PG의 200 SUCCESS는 주문·거래·금액 검증 후 추가 조회 없이 TX B에 반영한다. 콜백은 알림으로만 사용하고 PG를 권위 조회한다. 고객 reconcile도 기존 거래 조회만 수행하며 종결 주문도 다시 확인한다. 세 경로는 같은 내부 결과 반영을 사용한다. 이 내용은 합의한 [대표 흐름](../features/order-payment/processing.md#43-주문-확정)이며 추가 조회 횟수의 성능 우위를 실험한 결과는 아니다.

|대안|유리한 조건|비용·현재 판단|
|---|---|---|
|즉시 SUCCESS도 다시 조회|생성 응답의 최종성이 약하거나 별도 조회를 권위로 정한 계약|조회 지연·장애에 추가 의존. 현재는 검증한 생성 최종 응답을 권위로 인정|
|서명된 콜백의 최종 결과 직접 반영|제공자가 서명·재전송·최종성·이벤트 식별 계약을 보장|서명·재생·순서 검증 필요. 현재 콜백에는 이 계약이 없어 채택하지 않음|
|콜백마다 PG 조회 — 채택|알림 본문만으로 결제를 확정할 수 없는 현재 계약|중복 알림도 조회 부하 발생, PG 조회 장애 시 알림만으로 완료 불가|
|종결 reconcile은 저장 결과만 반환|종결 뒤 외부 재검증이 필요 없고 조회 비용이 더 중요할 때|새 충돌·외부 상태 변화를 확인하지 못함. 현재는 종결도 재검증하기로 합의|
|관리자/배치만 대사|운영 주체가 미완료 복구를 책임지는 서비스|관리자 명령·자동화·권한·실행 관리 추가. 현재 고객 본인 재확인만 제공|

### 숨은 비용·미확인 가정

- 즉시 성공 응답과 콜백은 신뢰 경로가 다르지만, 반영 결과는 동일해야 한다. 콜백 선도착·중복·응답 역전을 DB 상태로 방어해야 하며 경로별 구현을 복제하면 규칙이 달라질 수 있다.
- 고객 헤더를 요구하지 않는 콜백도 외부 조회를 유발한다. 알림의 위조만으로 성공을 만들 수 없도록 권위 조회하지만, 반복 알림으로 인한 자원 사용까지 해결한 것은 아니다. 공개 운영용 인증·수신 보호를 제공하지 않는 로컬 경계다.
- 저장 transactionKey가 없을 때 외부 주문 ID로 조회하는 경로는 생성 응답 유실 복구에 필요하다. 복수 거래에서 임의 한 건을 선택하면 다른 효과를 숨길 수 있어 충돌로 남긴다. 0건은 새 create의 허가가 아니다.
- 고객 reconcile은 본인 결제 결과를 다시 확인하는 요청이다. 관리자용 운영 대사의 대체물이나 새 결제 승인이 아니다. 고객이 다시 확인하지 않고 콜백도 유실되면 복구가 진행되지 않을 수 있다.
- 종결 대사도 외부 호출·로컬 확인 쓰기를 발생시킨다. 기존 CONFIRMED가 PG 장애 때 202·UNAVAILABLE로 보이는 화면 해석 비용도 생긴다.

**재검토 조건:** PG 서명·권위 버전·콜백 재전송 계약이 추가되거나, 중복 조회 부하·미완료 방치·운영 복구 요구가 드러나면 권위 경로와 대사 주체를 다시 비교한다. 승인된 조회 횟수·자동 retry 없음·회로·fallback 정책은 [2.8](../features/order-payment/pg-client.md#28-pg-http-도구와-테스트-서버의-구성), HTTP 제한과 회로 초기 가설은 [2.9](../features/order-payment/pg-client.md#29-http-제한과-pg-회로의-초기-정책)를 따른다. 정책 승인과 구현·실제 연동 검증 완료는 구분한다.

## A.24 결제 상태·확인 상태·금액의 공개 표현

**선택·근거:** payment 객체로 결제를 묶고, 결제 결과와 마지막 확인 결과를 분리한다. 준비 직후도 UNKNOWN으로 표현하며 공개 REQUESTED를 추가하지 않는다. payment.amount는 요청액, paidAmount는 실제 성공액, 신규 PG pointAmount는 0이다. DRAFT는 payment가 없고 과거 POINT는 보존한 사실만 제공한다. 이 내용은 합의한 [응답 계약](../common/api-contract.md#api-요청응답-dto-스키마)이다. 기존 JacksonConfig의 NON_NULL은 **코드 확인**에 해당한다.

|대안|유리한 조건|비용·현재 판단|
|---|---|---|
|결제 결과·조회 오류를 하나의 상태 enum으로 표현|오류 뒤 기존 결과를 보존할 필요가 없는 단순 흐름|PENDING 중 조회 실패나 성공 뒤 확인 불가의 의미가 섞임|
|payment.status + verificationStatus — 채택|저장 업무 결과와 이번 확인 결과를 동시에 보여줘야 함|가능한 조합과 화면·테스트 경우의 수 증가|
|REQUESTED를 별도 공개 상태로 노출|고객이 내부 발송 단계를 알아야 할 계약|발송 권한과 실제 전송 완료를 혼동할 수 있음. 현재 공개 UNKNOWN을 선택|
|결제 필드를 주문 최상위에 계속 추가|단순 평면 DTO가 우선인 클라이언트|주문·결제 의미가 섞임. 현재 payment 객체에 묶음|
|대기에도 paidAmount에 요청액 표시|필드 자체가 요청액이라는 계약인 경우|현재의 ‘실제 성공액’ 의미를 바꾸므로 채택하지 않음|

**숨은 비용·가정:** UNKNOWN만으로 아직 호출 전인지 timeout인지 알 수 없으며 내부 발송 기록을 봐야 한다. null 생략과 0은 다르다. 클라이언트가 필드 부재를 0원 결제나 실패로 해석하면 잘못된 화면을 만든다. 기존 JSON 모양을 그대로 유지하는 변경이 아니므로 고객·관리자 DTO와 테스트를 함께 바꿔야 한다. verificationStatus=VERIFIED는 현재 관찰이 유효하다는 뜻이지 반드시 성공했다는 뜻이 아니다. 정상 재검증 뒤에도 마지막 충돌 요약은 내부 증거로 남는다.

**재검토 조건:** 실제 클라이언트가 발송 단계·다중 시도·부분 금액을 필요로 하거나 상태 조합을 잘못 해석하면 표현과 버전 호환을 다시 비교한다. 지금 enum·필드를 더 추가하겠다는 뜻은 아니다.

## A.25 HTTP·오류·멱등 응답의 의미

**선택·근거:** 정상 확인한 확정 실패도 200의 PAYMENT_FAILED 결과로 반환한다. 미완료·확인 불가는 202, 시도 충돌·결과 충돌은 별도 409, 유효 JSON의 잘못된 입력은 기존 INVALID_REQUEST, 기존 변환 오류의 400·소유권 404·기술 실패 500을 유지한다. TX A 전 생성 회로 차단은 503 PG_CREATE_UNAVAILABLE이며 DRAFT·결제 행 없음·재고 효과 없음을 유지한다. TX A 후 실제 회로 거절과 생성 POST의 확실한 최초 풀 획득 timeout(A.32)의 확실한 미발송은 별도 TX B에서 반환·PAYMENT_FAILED를 반영하고 200으로 종결한다. 콜백은 200/202 ACK에서 data를 생략한다. 이는 합의한 API 선택이며 모든 외부 결제 API에 보편적으로 적용되는 HTTP 규칙이라는 주장은 아니다. 상세는 [오류 계약](../features/order-payment/api-contract.md#pg-결제-입력오류-계약)을 따른다.

|대안|유리한 조건|비용·현재 판단|
|---|---|---|
|PG 확정 실패를 4xx로 반환|그 API에서 결제 거절 자체를 요청 실패로 정의할 때|고객 입력 오류·외부 결제 결과의 구분을 다른 계약으로 제공해야 함|
|확정 실패도 200의 결과 상태 — 채택|요청 처리와 결제 업무 결과를 구분하는 현재 계약|HTTP·meta.result만 보고 결제 성공으로 처리하면 오류|
|종결 뒤 조회 불가는 저장 결과 200|저장 사실 조회를 우선하고 이번 확인 실패를 metadata로만 알릴 때|이번 대사 확인 불가를 HTTP로 구분하지 못함. 현재는 202 선택|
|기존 모든 400 코드를 한 코드로 통일|전체 오류 계약 개편·클라이언트 전환이 가능한 경우|PG와 무관한 기존 변환 오류 동작·테스트 변경. 현재 유지|

### 숨은 비용·미확인 가정

- 200 또는 ApiResponse.meta.result=SUCCESS는 결제 성공의 증거가 아니다. payment.status와 주문 상태를 읽어야 한다. 반대로 조회 불가의 202가 기존 CONFIRMED를 취소하지도 않는다.
- 이 API의 202가 서버 안에 후속 작업을 반드시 예약했다는 보장은 아니다. 고객 재확인 또는 콜백 없이 자동 완료되는 것으로 안내하면 안 된다.
- 종결 confirm 재요청은 저장 결과를 반환하고 종결 reconcile은 재조회한다. 같은 주문이라도 요청 목적이 다르므로 같은 HTTP만 보고 동작을 추론할 수 없다.
- 콜백 ACK에는 본문 결과가 없어 PG가 200/202를 어떻게 해석하는지 별도 실행 계약이 필요하다. 현재 콜백 자동 재전송을 가정하지 않는다.
- 동일 결과 멱등 응답과 충돌 409를 분리해야 한다. 모든 중복을 오류로 처리하면 재확인 경로가 불필요하게 실패하고, 모든 중복을 성공으로 처리하면 서로 다른 거래·금액을 숨긴다.

**재검토 조건:** 클라이언트·운영 도구가 HTTP 성공과 결제 성공을 혼동하거나, 인터페이스별 오류 변환 요구가 생기면 응답·업무 오류·HTTP 매핑을 함께 재검토한다. 확정 실패·일시 조회 장애·정합성 충돌의 관측 지표도 HTTP 코드만으로 합치지 않아야 한다.

## A.26 식별자·합성 입력·외부 정보의 노출 범위

**선택·근거:** 내부 주문 ID·UUID 시도 키·외부 주문 ID·외부 거래 키를 구분한다. 외부 주문 ID는 LP-ORD- + 최소 10자리 숫자로 저장하고 transactionKey는 대소문자를 구분하는 1~255자 합의 형식만 허용한다. 제공자·계정·금액·callback URL은 서버에서 결정하고 카드 입력은 고정 합성 값만 허용한다. 외부 키·카드는 고객/관리자 응답에 노출하지 않으며 카드 원문·hash를 저장하지 않는다. 이는 합의한 [PG 계약](../features/pg-simulator/README.md#55-로컬-pg-http-계약)이며 실제 PG 호환 규격은 아니다.

|대안|유리한 조건|비용·현재 판단|
|---|---|---|
|외부 주문 ID를 별도 UUID로 생성|내부 식별 패턴을 분리하거나 여러 ID 체계를 통합해야 할 때|매핑 저장·추적이 필요. 현재는 숫자 ID와 결정적 매핑 선택|
|고정 접두사 + 숫자 ID — 채택|한 로컬 저장소의 주문과 외부 거래를 쉽게 대응시켜야 함|내부 번호 패턴과 결합, DB 초기화·이관 시 ID 재사용 주의|
|임의 카드·금액·callback URL 입력|해당 입력을 검증·보호할 별도 제품 계약이 있을 때|현재 합성 입력 범위를 벗어나고 금액 불일치·외부 주소 주입 등 검증 부담 증가|
|외부 키를 공개 응답에 제공|고객용 외부 조회·지원 계약이 명시된 경우|제공자 식별에 클라이언트가 결합. 현재 내부 추적에만 사용|

**숨은 비용·미확인 가정:** 10자리 패딩은 가독성 선택이며 보안 장치가 아니다. UUID나 외부 키를 안다고 다른 고객의 주문을 조회할 권한이 생기지 않는다. 같은 PG 상태를 보존한 채 커머스 DB만 초기화하면 외부 주문 ID가 충돌할 수 있으므로 재시작·초기화 경계는 실행 설계에서 맞춰야 한다. 255자·허용 문자는 로컬 계약 선택이며 다른 PG의 키를 수용한다는 근거는 없다. 코드에서 문자열을 trim하거나 DB collation이 대소문자를 합치면 선택한 키 의미가 바뀐다.

시도 UUID의 전역 unique는 다른 주문에 같은 키를 쓴 요청을 충돌로 드러낸다. 다른 고객이 같은 값을 사용한 경우도 충돌이므로 key 소유 자체를 인증으로 삼지 않고 주문 소유권을 별도로 확인한다. 고정 카드만 허용하므로 저장한 카드 digest 없이 요청의 일치를 확인할 수 있다. 다른 합성 카드도 허용하면 요청이 달라졌음을 판단할 비민감 정보·보존 정책을 다시 정해야 한다. 서버 고정 계정 135135는 내부 고객 인증이 아니다. 현재 고객 헤더·로컬 콜백 경계는 운영용 인증을 제공하지 않는다. [A.23](#a23-즉시-응답콜백대사의-권위와-복구-경계)의 조회 부하 한계도 남는다.

**재검토 조건:** 복수 제공자·계정, DB 병합·ID 재사용, 실제 PG 연결, 다른 합성 입력, 고객용 외부 거래 식별 요구가 생기면 키 범위·노출·요청 일치·보존 규칙을 함께 재검토한다. 운영 인증을 현재 헤더 규칙으로 확장해도 된다는 뜻은 아니다.

## A.27 예약 반환·상품 삭제·관리자 재고·캐시

**선택·근거:** Product.Stock은 예약을 제외한 가용 수량이다. 성공은 예약 소비만 하고 추가 차감하지 않는다. 확정 실패는 현재 가용 수량에 예약량을 한 번 가산한다. 관리자 재고 설정은 현재 가용량의 최종 설정이다. 예약 뒤 삭제된 상품도 내부 결과 처리를 마무리하되 삭제 상태는 유지한다. 예약·반환 commit 뒤 기존 캐시 DEL 정책을 사용한다. 합의한 [예약·삭제 계약](../features/order-payment/processing.md#상품-변경기존-기능-보호와-검증)과 기존 Product/Stock·AfterCommitRunner 구현을 전제로 한다.

|대안|유리한 조건|비용·현재 판단|
|---|---|---|
|예약 전 수량으로 복원|그 사이 다른 변경이 없음을 독점적으로 보장할 때|다른 주문·관리자 변경을 덮을 수 있어 현재 채택하지 않음|
|현재 수량에 예약량 가산 — 채택|여러 주문·관리자 변경과 예약을 구분하는 현재 계약|중복 반환 방지·가산 overflow·현재 상태 잠금 필요|
|총재고·예약량을 따로 집계해 가용량 계산|창고 실재고·예약 총량을 별도로 관리할 때|조회·관리자 입력 의미·집계 정합성 개편. 현재 Stock 모델 유지|
|삭제 상품의 미완료 처리를 거절|삭제 자체가 결제 취소까지 보장하는 계약|이미 발생한 외부 성공·예약을 방치할 수 있음. 현재 soft delete와 결과 종결 분리|
|캐시를 TX 안에서 먼저 변경|DB·캐시 사이 실패·순서 정책이 별도로 정의된 경우|DB rollback과 캐시 상태를 함께 원자 처리할 수 없어 현재 afterCommit 유지|

**숨은 비용·미확인 가정:** 관리자에게 보이는 가용 수량은 창고 실재고 총량이 아니다. 예를 들어 예약 후 관리자가 가용량을 10으로 설정한 뒤 예약 2가 실패하면 가용량은 12다. 이 해석이 관리자의 재고 조사 의도와 맞는지는 제품 정책에 달려 있으며 현재 계약은 전자를 선택했다. 삭제 상품을 내부 조회하는 포트는 공개 활성 상품 조회와 구분해야 한다. 삭제 때문에 실패 반환이 누락되거나 반환 때문에 상품이 다시 노출되어서는 안 된다.

반환 가산 overflow·예약 상품의 물리 누락은 내부 정합성 오류다. 고객 수량 입력의 400과 구분해 TX B를 실패시키고 500으로 드러낸다. 외부 FAILED를 이미 확인했어도 로컬 반환과 종결은 완료되지 않을 수 있다. 임의 수량 보정·일부 반환으로 숨기지 않으며 정상 데이터 조건을 회복한 뒤 같은 거래 결과를 다시 반영할 수 있다.

캐시 DEL 실패는 DB commit을 취소하지 않으며 늦은 fill·TTL 한계도 기존 정책대로 남는다. 이로 인해 결제 시점 재고와 잠시 다른 조회 재고가 보일 수 있지만 결제 확보는 DB 잠금 상태로 판단한다. 캐시 문제를 결제 실패·재발송으로 연결하지 않는다.

**재검토 조건:** 관리자가 총 실재고를 입력해야 하거나 창고·예약 만료·부분 반환을 도입하면 재고 정의부터 다시 정한다. 고아 상품·반환 overflow·중복 반환·캐시 최신성 요구 변화가 발견되면 저장·검증·운영 복구 범위를 재검토한다. 기존 브랜드 bulk 삭제의 경쟁 한계까지 해결했다고 주장하지 않는다.

## A.28 과거 POINT와 조회·DTO·권한의 호환

**선택·근거:** 과거 POINT 주문의 결제·품목은 보존하고 신규 PG는 Point 행·잔액에 의존하지 않는다. POINT confirm에는 기존 상태 오류를 유지한다. 고객·관리자는 별도 DTO 경계를 유지하고 공통 OrderInfo를 TX 안에서 값으로 복사한다. 페이지의 결제 시도는 일괄 조회하며 주문 순서·total을 유지한다. 관리자 응답에도 고객용 reconcileUrl을 제공하지만 실행은 고객 소유권을 따른다. 합의한 응답과 [조회 조립](../features/order-payment/processing.md#주문-응답-조립)의 선택이다.

|대안|유리한 조건|비용·현재 판단|
|---|---|---|
|과거 주문을 PG 형식으로 소급 변환|이력 전환의 별도 사업·감사 규칙이 있는 경우|존재하지 않은 거래·시도 사실을 만들어낼 수 있어 현재 채택하지 않음|
|새 결제도 Point 존재 요구|포인트 계정 생성이 별도 필수 가입 계약인 경우|결제 수단과 무관한 거절·의존을 유지. 현재 PG에서는 제거|
|고객·관리자 DTO 공유|필드·노출·URL이 같은 수명으로 바뀔 때|현재 userId·orderUrl 등 경계가 달라 각각 선언|
|Order Entity를 TX 밖에서 결제와 조합|지연 로딩·조회 수·세션 경계를 다른 구조로 보장할 때|현재 열린 세션에 기대지 않도록 Info 복사 선택|
|관리자 전용 대사 URL/명령|관리자 직접 복구가 제품 범위에 들어올 때|권한·명령 계약·운영 이력 추가. 현재 고객용 URL만 제공|

**숨은 비용·미확인 가정:** POINT 보정의 예외 데이터·배포 순서는 A.17을 따른다. 유효 JSON의 새 카드 의미 검증을 과거 POINT 상태 판정보다 먼저 수행하면 기존 오류가 바뀐다. 이 호환 순서가 잘못된 JSON 자체의 파싱 오류를 무시한다는 뜻은 아니다.

Info·DTO 변환 코드와 페이지 결제 일괄 조회가 추가된다. 페이지별 일괄 조회는 주문별 결제 조회 반복을 피하지만 전체 요청의 DB 왕복이 0이 되는 것은 아니며 실제 쿼리 수는 구현 뒤 확인해야 한다. 저장 주문 품목에는 이름 스냅샷이 없어 현재 상품명을 과거 이름처럼 응답할 수 없다. DRAFT의 저장 단가 정책은 A.21을 따른다.

관리자 화면이 제공된 reconcileUrl을 관리자 권한만으로 호출하면 소유권 규칙 때문에 사용할 수 없을 수 있다. URL 제공과 기능 사용 가능성은 다르며 관리자용 복구 기능으로 안내하면 안 된다. 민감 외부 키를 숨기면 고객·관리자 응답만으로 PG 거래를 직접 대응시킬 수 없다는 추적 비용도 있다.

**재검토 조건:** 관리자 직접 복구·서로 다른 API 버전·외부 거래 추적·과거 품목명 요구가 생기면 권한·DTO·저장 스냅샷을 함께 다시 정한다. POINT 예외 데이터나 페이지 조회 비용이 확인되면 해당 전환·읽기 모델도 재검토한다.

## A.30 회로 의존성과 Spring 연동의 재검토

**상태·문제:** 2026-10-20 사용자는 Spring 생태계 방식의 사용을 원해, 기존 Resilience4j 코어 직접 decorator 선택을 Spring Cloud CircuitBreaker starter와 재비교하도록 요청했다. 대안 비교 후 사용자는 `resilience4j-spring-boot3`와 명시적 코어 API를 사용하는 B안을 승인했다. 코어만 구성하던 의존성 계획을 Boot 자동 구성으로 확장하되 명시적 실행 경계는 유지한다. 의존성 선택과 호출 방식은 구분한다. Spring starter를 사용해도 명시적 호출을 유지할 수 있으므로 starter 도입이 곧 annotation/AOP 사용을 뜻하지 않는다.

### 대안과 조건

|대안|얻는 것·유리한 조건|비용·한계|
|---|---|---|
|A. `io.github.resilience4j:resilience4j-circuitbreaker` 직접 연결|회로·예외·fallback의 실행 범위를 직접 보며 필요한 모듈만 사용. 회로 동작을 명시적으로 제어할 때 유리|Spring 빈·설정 바인딩·이벤트/지표 연결을 직접 구성. 직접 연결도 Spring Bean으로 사용할 수 있음|
|B. **채택** `io.github.resilience4j:resilience4j-spring-boot3` + 명시적 코어 API|Spring Boot의 설정 바인딩·registry 자동 구성·조건부 관리 기능을 사용하면서 명시적 decorator 유지. Cloud 공통 호출 추상화 없이 Spring 설정 연동을 원할 때 유리|추가 자동 구성·기능 모듈이 들어오며 AOP도 포함 가능한 환경이므로 실제 사용 기능을 확인해야 함. 호출 코드는 Resilience4j API에 의존|
|C. `org.springframework.cloud:spring-cloud-starter-circuitbreaker-resilience4j` + `factory.create(id).run(supplier, fallback)`|Spring Cloud 공통 호출 API·Customizer·설정·관찰 연동을 활용. 여러 컴포넌트에서 같은 Factory 사용 규칙을 두거나 Spring Cloud 구성을 학습할 때 유리|Factory 실행에 TimeLimiter·executor가 개입할 수 있고 classpath에 따라 bulkhead도 연결됨. 세부 predicate·설정은 여전히 Resilience4j 전용이므로 구현체 교체가 무비용은 아님|

**요구 명확화:** 사용자는 Spring Cloud Factory 자체가 목적은 아니며, Boot 설정·빈 연동과 YAML 구성이면 요구를 충족한다고 밝혔다. 이 요구에 맞춰 Boot starter를 선택했다. 추가 TimeLimiter/Bulkhead의 제품 도입은 이번 선택에 포함하지 않는다.

**선택 근거:** 사용자 목표인 Spring 설정·빈·YAML 연동에 B가 맞고 현재 동기 MVC·명시적 오류 경계를 유지하면서 바꿀 실행 요소를 줄인다. Spring Cloud Factory 자체의 사용 경험과 공통 호출 규칙이 목적이면 C도 타당하다. 이번 범위에는 다른 회로 엔진으로 교체할 요구가 없으므로 교체 가능성만으로 C의 추가 비용을 정당화하지 않는다. 사용자 학습 목표도 선택 근거로 인정하되 실제 제품 요구·운영 효과와 구분한다. 사용자가 이 비교를 검토한 뒤 B를 선택했다. 자동 구성·설정 바인딩을 추가로 검증하는 비용을 수용하며 회로 성능 우열을 근거로 선택한 것은 아니다.

### 확인한 공식 코드·기본 동작

출처는 Spring Cloud CircuitBreaker **3.2.1**의 starter POM·Resilience4JCircuitBreakerFactory.create·Resilience4JCircuitBreaker.run/loadTimeLimiter·Resilience4JConfigurationProperties·ConfigurationPropertiesUtils, Resilience4j **2.2.0**의 TimeLimiterConfig·TimeLimiterImpl.decorateFutureSupplier·CircuitBreaker.decorateCallable·CircuitBreakerStateMachine.onResult, Spring Boot 연동 모듈의 POM·CircuitBreakerAutoConfiguration이다. 해당 버전의 공식 원본과 현재 BOM 자료를 읽어 확인했으며 신규 의존성 해결·연동 실행 검증은 수행하지 않았다.

- 현재 저장소는 Spring Cloud 2024.0.1 BOM을 가져오며 관련 CircuitBreaker 관리 버전은 3.2.1, Resilience4j는 2.2.0이다. groupId는 배포 저장소 주소가 아니다. 저장소의 Gradle 의존성 저장소는 Maven Central이고 두 계열 모두 그 경로로 해결할 수 있다. 실제 runtimeClasspath의 최종 버전은 변경 후 별도 확인해야 한다.
- Cloud starter는 코어와 TimeLimiter를 포함하고, 구현 모듈을 통해 Resilience4j Spring Boot 3 연동을 포함한다. 코어 엔진을 다른 알고리즘으로 대체하는 별도 회로 구현이 아니다. 3.2.1 구현 POM에서 bulkhead는 optional이고 Boot 연동의 해당 전이 의존도 제외되어 있다. 따라서 starter만으로 bulkhead가 무조건 적용된다고 주장하지 않는다. 다른 의존성이 bulkhead를 classpath에 넣으면 조건부 자동 구성이 켜질 수 있다.
- Factory의 기본 executor는 cached thread pool이며 `disableThreadPool=false`, `disableTimeLimiter=false`다. 기본 경로는 supplier를 executor에 제출한 뒤 TimeLimiter로 Future를 기다린다. Resilience4j 2.2.0 TimeLimiter 기본값은 **1초·cancelRunningFuture=true**다. 이는 우리 HTTP timeout으로 승인한 값이 아니라 라이브러리 기본값이다.
- 하위 HTTP client의 대기 제한과 TimeLimiter의 Future 대기 제한은 별개다. TimeLimiter가 먼저 끝나면 HTTP 자체 timeout보다 먼저 fallback에 도달할 수 있다. `Future.cancel(true)` 호출은 인터럽트 요청이며, 실제 소켓·연결 반환·작업 종료를 보장했다고 취급하지 않는다. 별도 실행 스레드의 요청 문맥·로그 문맥 전달과 종료도 검증 대상이다.
- `spring.cloud.circuitbreaker.resilience4j.disable-time-limiter` 및 id/group별 설정으로 TimeLimiter를 끌 수 있지만 executor가 자동으로 사라지는 것은 아니다. 3.2.1에서는 executor가 남으면 `Future.get()`을 거친다. 반면 `disable-thread-pool=true` 경로는 executor 없는 wrapper를 만들어 실제 호출을 같은 스레드에서 감싸는 분기로 들어간다. TimeLimiter·bulkhead의 실제 적용 여부는 선택한 조합에서 확인해야 하며 이번 조사로 특정 설정을 채택하지 않는다.

### 분류·Customizer·fallback 경계

- `Customizer<Resilience4JCircuitBreakerFactory>`의 configure/configureDefault에서 Resilience4JConfigBuilder에 **CircuitBreakerConfig**를 넣어 recordResult·recordException·ignoreException 조건을 표현할 수 있다. 공통 Factory API 자체가 이 모든 정책을 제공하는 것은 아니므로 세부 구성은 Resilience4j에 결합된다. 속성으로 만든 registry·instance와 코드 설정을 함께 쓸 때 최종 적용값을 확인한다.
- `addCircuitBreakerCustomizer`는 만들어진 코어 instance의 이벤트 등 동작 연결 지점이며, 불변 설정 builder를 바꾸는 것과 같지 않다. 3.2.1 run 경로에서 customizer가 실행될 수 있으므로 같은 instance에 이벤트 listener를 중복 등록하지 않는지 확인한다.
- Cloud의 `run(supplier, fallback)`은 코어 decorator를 실행한 바깥 catch에서 fallback을 호출한다. 따라서 회로 실패 기록 뒤 확인 불가로 변환하는 경계를 표현할 수 있다. 무시 예외도 caller 쪽으로 전파되므로 fallback 대상이 될 수 있다. 모든 Throwable을 정상 결과로 덮지 말고 이미 합의한 내부 오류·DB 경계를 보존한다.
- **recordResult가 실패 표본으로 분류했다고 자동으로 fallback이 실행되지는 않는다.** 2.2.0 코어 onResult는 실패를 기록하면서 정상 반환값 자체를 반환할 수 있다. 반환값을 관찰로 처리할지, 명시적 예외로 흐름을 바꿔 fallback할지는 별도 설계가 필요하다. 두 방식을 중복 적용해 한 조회를 두 번 집계하지 않는다.
- TimeLimiter를 끄고 executor만 남기면 `Future.get()`의 ExecutionException이 원인 예외를 감쌀 수 있다. 내부 풀 대기 예외를 그대로 클래스 비교한 ignore 설정이 의도대로 적용되지 않을 수 있다. 기본 TimeLimiter 경로는 해당 예외의 cause를 풀어 전달하는 코드가 있다. 실제 wrapper 조합에서 원인 분류·예외 전파·표본 제외를 확인해야 한다.

### 채택한 구성의 검증과 재검토 조건

기존 코어 학습 코드는 유지할 수 있지만, 코어 동작 관찰만으로 starter 빈 등록·설정 바인딩·Factory의 wrapper·fallback·HTTP 취소가 검증되지는 않는다. 학습 테스트의 결과를 PG 연동 통과 근거로 사용하거나 별도 학습 자료를 D3의 구현 필수 근거로 연결하지 않는다.

채택한 구성에서 ① BOM의 Resilience4j 2.2.0·실제 의존성 해결, ② Boot YAML·registry 빈과 콜백/대사 공유 pgLookup·별도 pgCreate 생성 회로, ③ 현재 승인한 성공/실패/제외 집계, ④ 회로 바깥 fallback·미확인 상태 보존, ⑤ 추가 wrapper의 비적용과 실제 HTTP 종료·자원 반환을 연동 검증한다. `02`의 선택과 설정 책임을 갱신했고 Spring 전용 학습의 세부 범위·실행은 별도로 정한다. Cloud Factory의 기본 실행 경로는 대안 비교 자료이며 현재 제품의 실행 경로가 아니다. 운영 코드·Gradle 의존성·학습 테스트는 이번 설계 반영에서 수정하지 않았다.

Spring Cloud 공통 API 요구, 실제 운영 지표 연동 요구, 실행 스레드·취소 보장 요구가 생기거나 자동 구성 때문에 기대 집계가 달라지는 관찰이 나오면 선택을 재검토한다. 아직 비교 실험 결과나 성능 우열을 입증한 결론은 없다.

## A.31 로컬 초기 정책과 테스트 PG의 선택

**상태·문제:** 2026-10-20 사용자는 제안한 세 묶음을 승인했다. 구현 가능한 로컬 통신/회복 기준이 필요하지만 실제 PG의 부하·정상 지연·장애 회복 측정값은 없다. 제품 목표가 없는 상태에서 수치를 운영 최적값처럼 설명하지 않는다.

|선택|이유·대안이 유리한 조건|포기한 것·놓치기 쉬운 비용·재검토|
|---|---|---|

|테스트 내부 HTTP fixture·메모리 저장·명시 제어/콜백, commerce만 재시작|과제 검증/속성 비교를 실제 HTTP 테스트로 통합하고 별도 모듈/main/기동·데모 DB를 줄임. 단독 앱은 직접 수동 탐색, 영속 저장은 PG 재시작 복구에 유리|수동 장기 실행 방식은 제공하지 않음. fixture 종료 시 거래 소실·제어 메서드/worker 정리 비용은 남음. 별도 제어 HTTP는 제거하고 typed fixture 제어와 실제 결제/콜백 HTTP를 구분함. 재시작 검증은 fixture/DB를 유지. 직접 앱 시연/PG 영속 복구 요구 시 재검토. **2026-10-25 직접 시연 요구로 재검토해 단독 실행 앱으로 전환([A.33](pg-simulator.md#a33-pg-단독-실행-앱으로의-전환))**|

수치별 근거/공식 기본값/가설은 [2.9](../features/order-payment/pg-client.md#29-http-제한과-pg-회로의-초기-정책), 서버 책임은 [2.10](../features/pg-simulator/README.md#210-pg-시뮬레이터-앱의-책임과-수명), 제어/기동은 [5.7](../features/pg-simulator/fixture-contract.md#57-테스트-pg-제어와-상태-보존)에 한 번씩 기록한다. 기존 local/test의 ddl-auto=create로 재시작 데이터가 사라지는 코드 사실을 확인해, 테스트 DB/PG fixture 유지와 두 번째 commerce 컨텍스트의 validate 기동을 구분했다. 사용자 검토로 단독 실행/데모 DB/프로필은 제외했으며 실제 DB 설정 파일을 고친 것은 아니다.

비교 관찰은 [4.5](../features/order-payment/verification.md#45-pg-연동의-검증과-관찰)의 지표/통제 원칙을 따른다. 테스트 PG에서도 통제한 상태·지연·응답 유실 아래 실제 HTTP·회로와 MySQL의 업무 반영을 관찰할 수 있다. 이는 실습 계약 준수와 설정별 동작의 관찰이며, 실제 외부 PG의 지연·장애 분포나 운영 적정값을 측정하는 것은 아니다. 연결 거절과 connect timeout의 실제 재현도 구분하며, 재현하지 못한 항목은 4.5의 실행 근거에 한계로 남긴다. 코드·실험 결과와 운영 일반화는 아직 없다. 구현과 통제 실험의 관찰이 초기 가설과 다르면 이유를 기록하고 사용자와 계약/설정 변경을 결정한다.

## A.32 생성 회로 추가와 미발송 차단의 두 경계

**문제·승인 범위:** 사용자 전체 검토에서 PG 통신 보호 의도에는 생성도 포함된다는 점을 확인해 2026-10-22 생성 회로 추가를 요청받았다. TX A 전 차단은 DRAFT·재고/결제 변경 없음, TX A 후 실제 회로의 확실한 미발송은 반환 후 PAYMENT_FAILED 방향을 승인했다. 이전 조회 전용은 실습의 조회 회로 최소 요구에 맞춘 범위였으며 생성 적용이 기술적으로 금지된 것은 아니다. 생성 회로는 재시도를 뜻하지 않는다.

**선택·이유·대안:** DRAFT 유지는 기존 상태를 그대로 사용하므로 새 상태/테이블/취소 API가 필요 없다. 기존 결제 재요청은 저장 결과를 우선하고 신규 준비만 사전 확인한다. actual POST 권한 거절은 이후 별도 TX B에서 현재 상태·거래 결합을 검사하고 현재 가용 재고에 고정 품목 수량을 한 번 반환한다. TX A 후 DRAFT로 되돌리는 대안은 같은 주문의 두 번째 시도/키 재사용/이력 정리 계약을 바꾸므로 채택하지 않는다. 모든 차단을 UNKNOWN으로 유지하는 대안은 코드가 작지만 확실히 요청하지 않은 주문의 재고까지 장기 점유한다.

**비용·한계:** 사전 읽기 TX와 차단 직전 경쟁 재확인, 생성용 관찰·실패 원인·503 응답·반환 검증이 늘어난다. 새로운 DB 열/테이블이나 라이브러리는 추가하지 않는다. 사전 확인과 실제 호출 사이의 상태 변화는 가능하므로 사전 확인을 발송 보장으로 쓰지 않는다. TX A 후 확실한 미발송도 주문당 한 시도를 소비하며 실패 주문은 재결제하지 않는다. 반환 TX 실패/프로세스 중단 뒤에는 DB의 UNKNOWN과 조회 0건만으로 로컬 미발송 증거를 복원할 수 없는 한계가 남는다. 외부 효과가 불확실한 timeout/일반 오류와 확실한 회로 거절·확실한 최초 풀 획득 timeout은 섞지 않는다.

**승인·남은 검토·근거·검증:** 생성과 조회의 독립 회로·생성 표본 분류·미발송 원인 CIRCUIT_REJECTED 명칭은 사용자 승인 완료다. 공통 YAML 수치의 독립 적용과 HALF_OPEN 최대 대기 10초도 승인했으며 2.9가 원본이다. 공유 회로는 관리가 단순하지만 생성과 기존 거래 복구를 함께 차단한다. 분리 회로도 공유 풀의 자원 경쟁까지 해결하지는 않는다. Resilience4j 2.2.0 로컬 소스의 권한 획득/반환과 supplier 전 거절을 확인했으며 실제 제품 동작을 검증한 것은 아니다. 4.3·4.5에서 사전 차단/최종 거절/동시 중복/반환 rollback/각 회로 독립 전이를 검증한다. 일시 장애의 주문 실패율·추가 DB 왕복·반환 실패와 복구 요구를 관찰하면 사전 허용 방식과 미발송 증거 보존을 재검토한다.

**사전 확인과 실제 권한 분리의 유지 (2026-10-22 사용자 결정):** 사용자 검토에서 사전 확인 통과 뒤 실제 호출이 거절될 수 있다는 지적을 다시 논의했고, 기존 정책을 유지하기로 했다. 새 기능 변경이 아니라 기존 선택의 재확인이다.

- **문제:** 사전 확인은 tryAcquirePermission 성공 직후 releasePermission하고, TX A 동안 권한을 보유하지 않은 채 commit 뒤 실제 decorator에서 다시 얻는다. 그 사이 OPEN 전환이나 HALF_OPEN 탐색 슬롯 소진이 생기면 이미 재고를 확보한 주문이 CIRCUIT_REJECTED로 실패하고 주문당 한 시도를 소비한다.
- **대안:** 사전 권한을 TX A 끝까지 보유하면 사후 거절은 줄지만 DB TX 동안 HALF_OPEN 탐색 슬롯을 점유하고, 대기·rollback·예외 경로마다 권한 반환을 직접 관리해야 한다. 수동 회로 집계는 core decorator 자동 기록과의 이중 집계 위험을 만든다. 거절 뒤 자동 재결제·재시도는 주문당 한 시도·재발송 금지 계약을 바꾼다.
- **선택·수용한 비용:** 기존 구조를 유지한다. 일시적인 로컬 회로 차단으로 그 주문이 영구 실패할 수 있는 비용을 사용자가 수용했다. 사전 권한 보유·수동 집계·자동 재결제/재시도는 추가하지 않는다.
- **재검토 조건:** 사전 통과 뒤 실제 거절의 빈도와 그로 인한 주문 실패율, 고객 재주문 부담이 관찰상 커지면 권한 보유 방식이나 재시도 정책을 다시 검토한다. 현재 근거는 설계 판단이며 실행 결과가 아니다.

**생성 최초 연결 풀 획득 timeout의 미발송 분류 (2026-10-22 사용자 결정):**

- **문제:** 기존 계약은 생성 POST의 내부 풀 대기 실패를 UNKNOWN·재고 유지로 두었다. 그런데 최초 연결 획득 단계의 lease timeout은 요청을 보내지 않은 것이 확실한 경우라서, 재고를 장기 점유할 이유가 약하다.
- **선택:** 2.8의 조건(이 POST의 최초 acquireEndpoint에서 난 `ConnectionRequestTimeoutException`, Apache 자동 retry·redirect 비활성 등 client 보장 조건)을 모두 충족할 때만 LOCAL_NOT_DISPATCHED(reason=POOL_ACQUIRE_TIMEOUT)로 확정 미발송 처리한다. TX B 실패·반환 한 번·확인 정보 유지·HTTP 200은 CIRCUIT_REJECTED와 같다. failure_kind enum 값 하나만 추가하고 새 컬럼·테이블·API는 두지 않는다. 회로 표본 제외는 유지한다.
- **근거:** Apache HttpClient 5.4.2의 로컬 source에서 lease timeout 예외의 생성 지점이 `InternalExecRuntime.acquireEndpoint` 하나이고, 그 호출이 `ConnectExec`의 연결과 `MainClientExec`의 전송보다 앞서며, 재 lease 경로인 redirect·retry 실행기가 비활성 설정으로 체인에서 빠지는 것을 확인했다. source 확인이며 실제 실행 검증은 아니다.
- **대안·비용:** 모든 풀 실패를 미발송으로 넓히면 원인 불명·후속 exchange 뒤 실패까지 확정 실패로 오분류할 수 있다. 기존처럼 모두 UNKNOWN으로 두면 단순하지만 보내지 않은 주문의 재고를 대사 전까지 점유한다. 현재 선택은 그 사이를 택했다. 대신 client 설정 계약(retry/redirect·interceptor)에 의존하고 원인 타입 식별·설정 검증 비용이 늘며, 내부 풀 포화로 주문당 한 시도가 소비되는 비용을 진다.
- **재검토 조건:** HTTP client 버전·실행 체인 구성·재시도 정책이 바뀌거나, 실제 실행에서 lease timeout 뒤 PG 수신이 관찰되거나, 풀 포화로 인한 주문 실패가 많아지면 이 분류와 풀 용량·보호 수단을 재검토한다. 반환 TX 실패/증거 저장 전 종료 뒤 UNKNOWN이 남는 한계는 CIRCUIT_REJECTED와 같다.
