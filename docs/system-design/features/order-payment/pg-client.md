# PG HTTP·회로·실행 계약

기존 절 번호 참조: [3.6](model.md#36-pg-저장-모델과-제약) · [4.5](verification.md#45-pg-연동의-검증과-관찰).

기존 문서의 계약·절 번호·승인/검증 상태를 보존해 이동했다. 재편 자체는 제품 계약 변경이나 새 실행 검증을 뜻하지 않는다.

## 2.8 PG HTTP 도구와 테스트 서버의 구성

이 절은 사용자에게 후보·비용을 제시한 뒤 승인받은 도구·표본 분류·실행 구조다. 2026-10-20 HTTP 제한·추가 보호 범위, 회로 초기값, 공유 PG 제어·상태 보존도 승인했다. 구체 설정과 초기 가설의 근거는 [2.9](#29-http-제한과-pg-회로의-초기-정책), 서버 구성은 [2.10](../pg-simulator/README.md#210-pg-시뮬레이터-앱의-책임과-수명)을 따른다. 목표 설계의 작성과 구현·실측 완료는 구분한다.

### HTTP와 회로 연결 도구

2026-10-20 사용자는 Boot의 YAML·빈 연동을 위해 `io.github.resilience4j:resilience4j-spring-boot3`를 선택했다. 명시적인 코어 회로 호출과 회로 밖 fallback은 유지한다. [의존성·실행 경계의 선택 근거](../../decisions/payment.md#a30-회로-의존성과-spring-연동의-재검토)에 코어만 사용하는 구성·Boot 연동·Cloud Factory의 대안과 소스 확인·재검토 조건을 기록했다. 이 절의 도구·호출 경계는 PgHttpGateway·PgHttpConfig·PgCircuitConfig와 application.yml에 구현했다. 아래 표와 검증 절은 설계 작성 당시 미실행 상태에서 정한 계약·판정 기준이다. 현재의 사례별 실행 결과와 이 작성 이력을 구분한다. 현재 사례별 근거·허용 한계는 [4.5의 I4·I5 기록](verification.md#45-pg-연동의-검증과-관찰)을 따른다.

- HTTP는 `RestClient`와 Apache HttpClient 5를 사용한다. 현재 Servlet·동기 Facade 흐름에 맞추며 WebClient·Feign 의존성은 추가하지 않는다. 실제 사용하는 request factory와 하위 client에서 대기·연결·재시도를 제어한다. 생성 POST의 자동 재시도는 기존 계약대로 금지한다. 조회 GET에는 하위 client의 redirect 비활성 설정을 적용해 3xx를 자동 추적하지 않는다.
- 생성·조회 회로는 Resilience4j Boot 연동이 구성한 `CircuitBreakerRegistry` 빈을 사용하고, infrastructure의 PG adapter가 명시적 코어 decorator/execute API로 감싼다. `@CircuitBreaker` annotation·AOP나 Cloud Factory에 호출 경계를 맡기지 않는다. decorator 내부에서 실제 HTTP와 응답 해석을 수행하고, 회로 밖의 fallback에서 회복 대상 오류를 확인 불가 관찰로 변환한다. 아래 승인된 분류를 적용하며 모든 예외를 같은 실패로 세거나 먼저 정상 관찰로 삼켜 회로에 성공을 기록하지 않는다.
- 콜백·대사는 같은 조회 회로를 공유하며 각 요청에서 PG GET을 최대 1회 수행한다. 자동 retry·요청 내부 polling·sleep을 추가하지 않는다. 거래 키가 없으면 주문별 목록 GET 하나로 판단하며, 1건을 찾았다는 이유로 단건 GET을 연이어 보내지 않는다. 후속 알림 또는 사용자 대사 요청은 새로운 확인 실행이다. 이 제한은 사용자의 모든 후속 확인을 평생 1회로 제한한다는 뜻이 아니다.
- 구현 시 `org.apache.httpcomponents.client5:httpclient5`와 `io.github.resilience4j:resilience4j-spring-boot3`를 commerce-api의 구현 의존성으로 추가한다. 버전은 현재 프로젝트의 Boot/Cloud BOM 관리값인 HttpClient 5.4.2·Resilience4j 2.2.0을 사용하도록 설계하며 별도 최신 버전 override를 추가하지 않는다. Cloud BOM은 버전 관리에 활용하되 Cloud CircuitBreaker starter는 선택하지 않았다. 실제 HTTP·빈·최종 설정의 재현 가능한 검사는 PgHttpConfigTest·PgHttpGatewayContractTest를 따른다. 설계 작성 당시의 코어 학습 테스트는 사용자 요청으로 삭제했으며 현재 제품 검증에 전용하지 않는다.

**근거·대안·비용:** RestClient는 현재 동기 호출 모델을 유지한다. Apache client는 연결 풀·실제 하위 대기와 재시도 설정을 드러낼 수 있지만 의존성·종료·연결 관리 비용이 늘어난다. JDK client는 의존성을 줄일 때, WebClient는 비동기 처리가 필요한 범위에서 유리한 대안이다. 직접 decorator는 적용 범위·예외·fallback 순서를 코드로 확인하기 쉬운 대신 연결 코드를 직접 작성한다. annotation 방식은 선언을 줄이지만 프록시 적용과 자기 호출·중첩 순서를 검증해야 한다. 조회 1회는 증폭을 줄이는 대신 일시 실패도 다음 확인 요청까지 회복을 기다린다. 비동기 처리 요구·지연 측정·일시 실패 비율이 달라지면 이 선택을 재검토한다. 성능 우열을 실험한 결론은 아니다.

### Boot 설정·빈과 명시적 호출의 연결

- 생성에는 `pgCreate`, 콜백의 거래 조회와 고객 대사의 거래/주문별 조회에는 공유 `pgLookup`을 두는 분리 구성을 승인했다. 각 YAML 설정에서 2.9의 수치를 읽고 Boot 연동의 registry 빈을 재사용한다. 생성 회로 추가·두 차단 시점의 상태 정책·분리 구성·생성 표본 분류는 승인됐으며, 공통 YAML 수치를 두 인스턴스에 독립 적용하며 HALF_OPEN 최대 대기는 10초로 승인했다. adapter가 요청마다 새 회로를 만들거나 `ofDefaults()` registry로 YAML 설정을 덮지 않는다.
- 단순 수치·인스턴스 구성은 YAML, 결과·예외 판정은 해당 인스턴스의 Java predicate/설정 Customizer로 구성한다. 같은 설정을 여러 곳에 중복 선언하지 않고, 실제 registry 인스턴스의 최종 설정·분류를 검증한다. 공통 base에서 수치를 상속해도 인스턴스별 predicate를 덮지 않는지 확인한다. 수치·분류의 원본은 각각 2.9·이 절의 승인 표이며 라이브러리 기본값을 조용히 적용하지 않는다.
- Boot의 자동 구성은 registry·설정을 준비한다. PG HTTP를 실제로 감싸는 실행 경계는 adapter의 명시적 호출이다. YAML을 등록했다는 사실만으로 HTTP가 보호됐다고 판단하지 않는다. 실제 실행 회로는 생성 POST 또는 조회 GET의 HTTP·해석만 감싸고 로컬 TX A/B·DB 처리를 감싸지 않는다. 생성 사전 확인은 별도 로컬 호출이며 HTTP·DB를 실행하지 않는다.
- 현재 동기 호출에서 코어 회로만 명시적으로 적용한다. starter에 관련 타입이 포함될 수 있다는 이유로 TimeLimiter·별도 executor·Bulkhead·Retry·RateLimiter를 실행 체인에 추가하지 않는다. 2026-10-20 이 기능과 별도 전체 deadline/강제 취소를 추가하지 않기로 승인했다. 글·학습의 확장 후보와 제품 도입을 구분한다.
- **검증 기준:** Spring 컨텍스트에서 YAML이 registry의 `pgCreate`/`pgLookup`에 적용되는지, 콜백/대사가 같은 lookup instance를 사용하고 생성과는 상태/표본이 분리되는지, 실제 POST/GET의 성공/실패/제외와 회로 밖 fallback이 합의한 분류대로 동작하는지 확인한다. 코어 학습 테스트의 통과를 이 연동 검증으로 대신하지 않는다.

### 생성 회로와 사전 차단

2026-10-22 사용자는 생성 POST에도 회로 적용, TX A 전 차단 시 DRAFT 유지, TX A 후 확실한 회로 미발송 시 재고 반환·PAYMENT_FAILED를 승인했다. 이어서 생성/조회 분리 인스턴스·아래 생성 표본 분류·실패 원인 CIRCUIT_REJECTED 명칭도 승인했다. 공통 초기 수치의 생성 적용과 HALF_OPEN 최대 대기 10초도 승인했으며 원본은 2.9다. 승인과 구현/연동 검증 완료를 구분한다.

- 생성/조회를 한 회로로 묶으면 한 경로 장애로 다른 경로도 차단된다. pgCreate/pgLookup 분리는 생성 장애 중 조회 복구와 조회 장애 중 생성을 독립 허용하는 대신 두 설정·분류·검증을 관리한다. HTTP 풀은 공유하므로 자원까지 격리하는 Bulkhead는 아니다.
- prepareConfirmation의 짧은 TX에서 기존 결제·소유권·입력·키를 먼저 확인한다. STORED면 회로와 무관하게 기존 결과를 반환한다. 결제 없는 DRAFT만 사전 확인하고, 차단 시 결제 행·발송 기록·재고/이력 변경 없이 503 PG_CREATE_UNAVAILABLE로 거절한다. 새 결제 행을 만들지 않았으므로 나중에 같은 주문·키로 고객이 다시 요청할 수 있다. 자동 retry는 아니다.
- 사전 확인은 tryAcquirePermission 성공 시 releasePermission을 즉시 호출한다. OPEN 대기 경과의 HALF_OPEN 전환과 탐색 슬롯 허용 여부도 실제 라이브러리 규칙을 따른다. 상태 이름만 읽어 차단하거나 DB TX 동안 탐색 슬롯을 보유하지 않는다. 사전 확인은 성공/실패/느림 표본 0, 거절 계수만 별도 관찰한다.
- 사전 확인 통과 뒤 TX A에서 주문·입력·기존 결제·재고를 다시 검증한다. 다른 요청이 결제를 만들었으면 STORED다. 실제 create decorator는 TX A commit 뒤 권한을 다시 얻는다. 이 사이 회로가 열리거나 탐색 슬롯이 소진되면 POST 0임을 adapter가 보장한 LOCAL_NOT_DISPATCHED만 반환한다. 일반 CallNotPermitted 예외나 임의 프로그램 오류를 모두 미발송 증거로 삼지 않으며, 두 조건은 아래 표 뒤의 미발송 판정 장치로 연결한다.
- 실제 POST 권한을 이미 얻은 호출은 이후 OPEN이어도 진행할 수 있다. 진행 중 HTTP를 취소하는 기능은 추가하지 않는다. DB 실패·STORED·사전 거절을 PG 실패 표본으로 기록하지 않는다. 실제 POST의 측정 구간에는 풀 대기·연결·수신·해석만 포함하며 사전 TX·TX A/B는 제외한다.
- **사전 확인과 실제 권한의 분리 유지 (2026-10-22 재확인):** 사용자는 위 구조를 바꾸지 않기로 결정했다. 사전 확인의 권한은 즉시 반환하고 TX A 동안 회로 권한을 보유하지 않으며, TX A commit 뒤 실제 pgCreate decorator에서 다시 얻는다. 그 사이 OPEN 전환이나 HALF_OPEN 탐색 슬롯 소진으로 실제 호출이 거절되면 기존 LOCAL_NOT_DISPATCHED/CIRCUIT_REJECTED·TX B 실패/재고 반환 한 번·주문당 한 시도 소비를 적용한다. 일시적인 로컬 회로 차단으로 그 주문이 영구 실패할 수 있는 비용을 사용자가 수용했다. 사전 권한 보유, 수동 회로 집계, 자동 재결제·재시도는 추가하지 않는다. 근거·재검토 조건은 부록 A.32에 둔다.

PgCreateResult(observation, directCreateResponseMismatch)는 조회의 PgLookupResult와 다른 값 타입이다. 생성 result predicate는 이 직접 계약 위반 표시만 사용하고 REJECTED_NO_EFFECT 자체를 실패로 세지 않는다. ignore/record/fallback의 순서는 조회와 같다. LOCAL_NOT_DISPATCHED는 원인별 증거를 충족한 CIRCUIT_REJECTED(아래 미발송 판정 장치)와 POOL_ACQUIRE_TIMEOUT(아래 풀 획득 판정)에만 적용한다. 두 원인의 조건은 서로 독립이며, 일반 timeout·불명확한 오류로 넓히지 않는다. 생성별 나머지 2xx·3xx·4xx·5xx는 기존 CREATE_UNAVAILABLE 계약을 유지하고 redirect/retry는 없다.

**미발송 판정 장치(CIRCUIT_REJECTED):** 정책은 바꾸지 않고, "일반 CallNotPermitted를 미발송 증거로 삼지 않음"과 "actual decorator의 권한 거절·POST 진입 0이면 LOCAL_NOT_DISPATCHED"를 아래 장치로 연결한다.

- **호출별 진입 표시:** PgHttpGateway.create 호출마다 그 호출 안에서만 쓰는 로컬 실행 진입 표시를 새로 만든다. 최초값은 미진입이다. Gateway 필드·전역 상태·다른 요청과 공유하는 객체로 만들지 않는다.
- **표시 시점:** 실제 pgCreate decorator로 감싼 callable/supplier 본문의 첫 동작에서 진입으로 바꾼다. 그 뒤에 풀 대기를 포함한 POST와 응답 해석을 수행한다. 따라서 본문 진입 뒤의 풀 대기 실패도 진입 상태이며 CIRCUIT_REJECTED가 될 수 없다. 그중 확실한 최초 풀 획득 timeout만 아래 POOL_ACQUIRE_TIMEOUT 판정을 따르고, 나머지는 기존 분류를 따른다.
- **미발송 조건:** 다음을 모두 만족할 때만 CREATE/LOCAL_NOT_DISPATCHED(reason=CIRCUIT_REJECTED)를 반환한다. ① 예외가 이 호출의 실제 pgCreate decorator 실행 호출에서 잡혔다. ② CallNotPermittedException이다. ③ 거절한 회로가 주입 registry의 pgCreate instance다(예외의 causing circuit 이름). ④ 이 호출의 진입 표시가 미진입이다. 예외 타입·회로 이름·미진입 표시 중 하나만으로 판정하지 않는다.
- **catch 범위:** 미발송 catch는 실제 decorator 실행 호출만 감싼다. 사전 확인(checkCreateAdmission), 요청 준비 등 decorator 호출 전 단계, pgLookup 같은 다른 회로, 다른 계층에서 난 예외를 이 분기로 합치지 않는다.
- **본문 진입 뒤 예외:** 진입 표시가 진입이면 같은 CallNotPermittedException 타입이 본문 안에서 발생해도 미발송 분기로 처리하지 않는다. 알려진 통신·해석 오류, 풀 대기, 식별한 프로그램 오류는 위 표의 기존 분류를 그대로 따른다.
- **본문 안의 예상 밖 CallNotPermittedException (2026-10-22 합의):** 현재 생성 본문에는 다른 회로 호출이 없으므로, 본문에서 나온 이 예외는 의도한 pgCreate 진입 거절이 아닌 내부 제어 흐름 오류로 식별한다. 본문(callable) 안의 catch에서 원인을 보존한 기존 PgAdapterProgrammingException으로 감싸 다시 던진다. core decorator의 onError는 본문이 던진 예외를 받으므로 감싼 예외가 기존 pgCreate 프로그램 오류 ignore predicate로 판정되어 성공·실패·느림·전체 표본에서 빠진다. 회로 밖 감싸기는 onError가 원래 예외를 먼저 실패로 기록하므로 쓰지 않는다. 회로 밖에서는 HTTP 500으로 전파한다. LOCAL_NOT_DISPATCHED·CREATE_UNAVAILABLE 관찰 합성, TX B 호출, 재고 반환, 자동 재전송은 없다. 본문 진입 사실이나 이 오류로 실제 외부 효과 유무를 추정하지 않는다. 이 추가 식별은 본문 안의 CallNotPermittedException에 한정하며, 다른 RuntimeException·통신 오류를 프로그램 오류로 일괄 감싸지 않는다.
- **decorator 실행 호출 전 예외 (2026-10-22 합의):** create 안에서 실제 pgCreate decorator 실행 호출 전(요청 준비 등)에 난 예상 밖 예외는 pgLookup 이름의 CallNotPermittedException이든 일반 RuntimeException이든 pgCreate 표본 증가가 0이다(decorator에 도달하지 않음). 별도 catch에서 pgCreate에 수동 표본을 기록하지 않고 HTTP 500으로 전파한다. LOCAL_NOT_DISPATCHED·CREATE_UNAVAILABLE 관찰 합성, TX B 호출, 재고 반환, 자동 재전송은 없다. 입력·소유권·DB 업무 거절 등 기존에 정의된 오류는 각자의 기존 계약을 따르며 이 규칙으로 500으로 바꾸지 않는다.
- **두 오류의 상태 보존:** 위 두 경우 TX A에서 commit한 주문·결제·확보 재고를 되돌리지 않고, 다른 경로가 이미 종결했다면 그 결과도 덮지 않는다. TX B 관찰이 없으므로 이 오류로 확인 정보를 갱신하지 않는다.
- **기존 장치 유지:** 명시적 core decorator(executeCallable 등)의 권한 획득과 onResult/onError 기록을 그대로 사용한다. 수동 acquirePermission·onSuccess/onError를 추가하지 않으므로 이중 획득·이중 집계가 없다. 사전 확인의 tryAcquirePermission/releasePermission과 TX A 후 실제 권한 재획득 구조도 유지한다.
- **범위:** 일반 timeout·HTTP 오류·풀 대기·프로그램 오류를 이 CIRCUIT_REJECTED 분기로 넓히지 않는다. 이 장치는 신규 DB 컬럼·테이블·공개 API·상태·failure_kind 값을 추가하지 않는다. POOL_ACQUIRE_TIMEOUT은 아래 별도 판정이며 이 조건 ①~④를 완화하지 않는다.

**생성 최초 연결 풀 획득 timeout의 미발송 판정(POOL_ACQUIRE_TIMEOUT, 2026-10-22 합의):** LOCAL_NOT_DISPATCHED의 증거는 원인별로 나눈다. CIRCUIT_REJECTED는 위 ①~④, POOL_ACQUIRE_TIMEOUT은 아래 조건이며 서로의 조건을 빌려 쓰지 않는다. 풀 획득 timeout은 본문 진입 뒤에 발생하므로 진입 표시로 판정하지 않는다.

- **확정 조건(모두 충족):** ① 이 create 호출의 실행 본문이 수행한 단일 POST exchange에서 발생했다. ② Apache/Spring 원인 사슬에 httpcore5 `ConnectionRequestTimeoutException`이 정확한 타입으로 있다. 상위 타입 InterruptedIOException이나 SocketTimeoutException·ConnectTimeoutException으로 판정하지 않는다. ③ 아래 client 보장 조건을 충족한다. ④ 본문 안에서 PgPoolAcquireException으로 정규화되어 pgCreate의 ignore로 표본에서 빠졌다.
- **source 사실(Apache HttpClient 5.4.2, parent POM의 httpcore5 5.3.3, 로컬 source 읽기 전용 확인):** `InternalExecRuntime.acquireEndpoint`는 endpoint가 없을 때만 lease한다. lease 대기의 `TimeoutException`만 `ConnectionRequestTimeoutException`으로 바꾸며, interrupt는 `RequestFailedException`, lease 뒤 연결 준비 실패(`ExecutionException`)도 `RequestFailedException`이다. classic client source에서 이 예외를 만드는 곳은 이 메서드뿐이다. `ConnectExec`는 endpoint를 얻지 않았을 때만 이 메서드를 호출한 뒤 연결하고, 요청 전송은 그 뒤의 `MainClientExec`가 한다. 다시 lease하는 경로는 `RedirectExec`·`HttpRequestRetryExec`이며, builder에서 끄면 실행 체인에 추가되지 않는다. `ProtocolExec`의 인증 재요청은 endpoint 참조를 유지하므로 추가 lease가 없다. 따라서 아래 조건에서 이 예외가 나면 그 실행은 요청을 한 바이트도 보내지 않았다. 이는 source 확인이며 실제 실행 검증이 아니다.
- **client 보장 조건:** PG 전용 client를 HttpClientBuilder로 만들고 disableAutomaticRetries·disableRedirectHandling을 적용한다(2.9). 다시 실행하는 exec interceptor를 추가하지 않고, PG RestClient에 재시도 interceptor를 두지 않는다. create 본문은 RestClient exchange를 한 번만 수행한다. 구현에서 하나라도 충족하지 못하면 확인된 풀 획득 오류라도 이 분기를 쓰지 않고 기존 CREATE_UNAVAILABLE(표본 제외, UNKNOWN·재고 유지)을 유지한 채 보고한다. 최종 client 설정 검증(4.5)으로 확인한다.
- **변환 위치:** callable 본문 안에서 원인 사슬을 식별해 원인을 보존한 PgPoolAcquireException으로 던진다. core decorator의 onError가 이 예외를 받아 ignore로 성공·실패·느림·전체 표본에서 제외한다. 본문 안에서 정상 결과로 바꿔 반환하면 onResult가 성공 표본으로 세므로 그렇게 하지 않는다. decorator 밖 catch에서 create는 위 확정 조건과 client 보장 조건을 모두 충족하면 CREATE/LOCAL_NOT_DISPATCHED(reason=POOL_ACQUIRE_TIMEOUT)로, 확인된 풀 획득 오류지만 보장 조건을 충족하지 못하면 기존 CREATE_UNAVAILABLE(UNKNOWN·재고 유지)로 바꾼다. 두 경우 모두 앞의 ignore로 표본에서 빠진 상태이며, PgPoolAcquireException 타입 하나만으로 미발송을 확정하지 않는다. lookup은 기존대로 QUERY/UNAVAILABLE로 바꾼다.
- **제외:** 일반 연결 timeout·응답/읽기 timeout, 취소·interrupt, lease 뒤 연결 준비 실패, 원인 불명 예외, 재시도·redirect·후속 exchange 뒤의 풀 실패는 이 분기가 아니며 기존 분류(생성은 UNKNOWN·재고 유지)를 따른다. 조회 GET의 풀 획득 실패는 기존대로 표본 제외·UNAVAILABLE·업무 상태/재고 유지다.
- **TX B와 응답:** 공통 TX B가 현재 상태·거래 결합을 검증한 뒤 PAYMENT_FAILED·FAILED(failure_kind=POOL_ACQUIRE_TIMEOUT)로 종결하고, 고정 품목 재고와 ORDER_RELEASE를 한 번 반환한다. 거래 키는 만들지 않는다. PG 확인 결과가 아니므로 verificationStatus·verification_checked_at은 기존 값을 유지하며 최초 NOT_CHECKED/null인 실패도 허용한다. confirm은 기존 확실한 미발송 실패와 같은 HTTP 200·실패 상태로 응답한다. 같은 원인 재적용은 추가 반환이 없고, 결합 거래·반대 종결·다른 실패 원인 공존은 기존 TERMINAL_MISMATCH 보호를 따른다. 자동 POST 재전송·새 결제 시도는 없다. 새 컬럼·테이블은 없고 failure_kind Java enum에 POOL_ACQUIRE_TIMEOUT 값을 추가한다(DB는 기존 VARCHAR(32)).

**소스 사실·한계·검증:** Resilience4j 2.2.0 로컬 source JAR의 CircuitBreaker.tryAcquirePermission/releasePermission 및 decorateCallable에서 권한 거절은 supplier 실행 전임을 확인했다. 같은 source에서 decorateCallable은 acquirePermission 뒤 callable을 호출하고, 본문 예외는 onError 뒤 다시 던진다. CallNotPermittedException은 거절한 회로 이름을 getCausingCircuitBreakerName()으로 제공한다. 위 판정 장치의 ①~④는 이 source 사실에 기대며, 실제 제품 실행에서는 아직 확인하지 않았다. 사전 허용 뒤의 DB 대기 중 상태 변화까지 막는 예약 토큰은 아니며 최종 decorator 거절을 따로 처리한다. HALF_OPEN 슬롯 반환·사전 거절의 DB 효과 0·실제 거절의 POST 0/반환 1·DB/PG 표본 분리·각 회로 독립 OPEN/회복을 구현 뒤 검증한다. 실제 연동의 실행 범위는 4.5의 I4·I5 근거를 따른다. 임시 장애로 주문이 영구 실패하는 비용을 줄이려 사전 확인을 두지만 추가 짧은 TX/왕복이 생긴다. TX A 뒤 차단만 처리하는 대안은 단순하지만 불필요한 확보/반환과 주문당 한 시도 소비가 늘어난다. 실제 왕복 비용·거절/반환 비율·경로 간 장애 상관을 보고 재검토한다.

### 합의한 조회 회로 표본 분류

회로 표본은 PG 조회 기능의 가용성을 판단하는 관찰이다. HTTP 응답 도달 여부·PG 자체의 장애 원인·결제의 업무 성공 여부와 구분한다. 아래 분류는 조회 GET에 적용하며 고객/관리자 API 자체의 인증·권한 오류 계약을 바꾸지 않는다.

|발생 지점·상황|회로 표본|요청 처리|
|---|---|---|
|우리 HTTP 연결 풀에서 연결을 빌리기 전 대기 실패|제외. 성공·실패·느린 호출·최소 표본 수에 포함하지 않음|조회 UNAVAILABLE 관찰을 공통 TX B에 전달. 저장 결제 상태·예약은 유지하고 확인 정보만 마지막 DB 반영 관찰로 갱신|
|정상 PG 응답을 처리하는 adapter 내부 프로그램 오류. 예: 계약 검증 후 내부 로직의 NullPointerException|ignoreException으로 제외. 성공·실패·느린 호출·최소 표본 수 모두 증가하지 않음|UNAVAILABLE fallback으로 정상화하지 않고 기존 500 처리로 전파. 관찰을 합성해 TX B를 호출하지 않으며 기존 업무 상태/예약/종결 보존|
|정상 HTTP 조회 응답을 해석하고 식별·금액·거래 관계까지 검증한 결제 FAILED|통신 성공 표본. 결제 FAILED를 이유로 회로 실패를 기록하지 않음|검증한 FAILED를 공통 TX B에 전달. 기존 상태·충돌·중복 적용 규칙에 따라 실패 종결·예약 반환 또는 기존 종결 보존|
|요청한 거래의 유효한 응답을 받았으나 내부 주문 또는 저장 거래 키와 충돌. 예: A 주문 알림의 B 거래 키를 조회해 B의 정확한 응답을 받음, 또는 같은 주문·금액이지만 저장 키 KA와 다른 KB의 정확한 응답을 받음|통신 성공 표본. 이 내부 업무 충돌을 회로 실패로 집계하지 않음|공통 TX B에서 CONFLICT 기록·기존 409 처리. 저장 키와 다른 거래는 종결 비교 전에 IDENTITY_MISMATCH(3.6). 주문·예약·기존 종결·저장 키 보존|
|요청 대상의 거래 키·외부 주문 ID가 맞고 금액 형식도 유효하지만 저장한 기대 금액과 다름|회로 성공 표본 1회. 내부 기대 금액과의 차이만으로 조회 실패를 기록하지 않음|회로 밖 TX B가 AMOUNT_MISMATCH 충돌 요약을 commit한 뒤 409. 주문·시도 업무 상태·예약·기존 종결 보존|
|식별·금액·형식이 정상인 새 권위 조회가 저장 종결과 반대 종결을 반환하거나, 종결 후 시작한 조회가 PENDING을 반환|회로 성공 표본 1회. 저장 상태와의 업무 충돌을 조회 실패로 기록하지 않음|TX B가 기존 종결을 유지하고 TERMINAL_MISMATCH 또는 TERMINAL_REGRESSION 요약 commit/409. 종결 전에 시작한 늦은 PENDING 무시 규칙은 별개로 유지|
|PG 단건 조회 요청 거래 키 A에, 형식은 유효하지만 응답 거래 키 B를 반환|회로 실패 표본. 요청한 대상을 돌려주지 않은 직접 조회 계약 위반|CONFLICT(IDENTITY_MISMATCH) 관찰을 보존해 TX B에 전달. UNAVAILABLE로 덮지 않고 기존 충돌 commit/409·업무 상태/예약 보존|

**선택·근거:** 사용자가 내부 풀 대기 실패를 PG 회로 표본에서 제외하기로 했다. 풀 포화는 우리 자원의 부족으로도 발생하므로 이것만으로 외부 PG 가용성을 판단해 공유 조회 회로를 열지 않는다. 회로 내부에서는 내부 풀 대기 실패임을 식별 가능한 예외로 유지해 제외하고, 회로 바깥에서 UNAVAILABLE로 변환한다. 생성 POST의 확실한 최초 풀 획득 timeout도 같은 방식으로 제외하되 회로 바깥 변환만 [생성 회로와 사전 차단](#생성-회로와-사전-차단)의 POOL_ACQUIRE_TIMEOUT 판정을 따른다. 먼저 정상 반환으로 삼킨 뒤 성공 표본으로 기록하는 것도 금지한다. 연결을 빌린 뒤의 PG 연결·응답 timeout과 구분하며, 모든 I/O 예외를 내부 풀 대기 실패로 분류하지 않는다. TX B의 DB 오류를 이 경로로 삼키지 않는다.

**대안·비용·재검토:** 내부 포화도 실패로 세면 회로 차단으로 후속 조회량을 줄일 수 있지만, PG가 정상인 상황에도 콜백·대사 전체의 확인을 지연시킬 수 있다. 제외하는 현재 선택은 그 오판을 피하는 대신 내부 포화 자체를 회로로 차단하지 못한다. 풀 용량·대기 제한·동시 실행 제어는 별도 설계 대상이며 이번 합의로 새 bulkhead를 도입한 것은 아니다. 실제 관찰에서 내부 포화가 반복되고 연결 자원 보호가 부족하면 그 원인과 별도 보호 수단을 재검토한다. 아직 실험 결과는 없다.

**구현 검증 기준:** 초기 CLOSED·다른 동시 조회 없음으로 시작하고 풀을 점유한 통제 조건에서 조회가 연결 대기 실패를 만나도록 한다. 해당 요청의 실제 PG GET은 0회이고 회로의 성공·실패·느린 호출·집계 표본은 증가하지 않아야 한다. 저장 업무 상태·예약 유지와 UNAVAILABLE 반영을 확인하고, 풀을 반환한 뒤 다음 조회를 실행할 수 있는지 검증한다. 회로 밖의 오류 분류와 자원 정리까지 확인한다. 나머지 분류는 이 절의 표, 수치는 2.9를 따른다.

**결제 FAILED의 선택·근거:** 사용자는 유효하게 조회한 결제 실패를 통신 성공으로 세기로 했다. 회로가 확인하려는 외부 조회의 가용성과 결제의 업무 결과를 분리한다. 결제 실패를 회로 실패로 세는 대안은 실패 결제가 많을 때 후속 조회를 줄일 수 있으나 정상 PG까지 차단해 다른 주문의 결과 확인을 지연시킨다. 현재 선택은 이 결합을 피한다. 단, 정상 JSON의 FAILED 문자열만으로 유효한 결과라고 확정하지 않으며 식별·금액·종결 충돌은 기존 TX B 계약대로 별도 검증한다. 늦은 FAILED가 저장 SUCCESS와 상충하면 통신 표본과 별개로 업무 충돌을 보존한다.

**비용·검증·재검토:** 성공 표본이라는 이유만으로 응답이 빠르거나 업무 결과가 옳다고 보장하지 않는다. 느린 호출 집계·차단은 2.9의 800ms/50%를 따르므로, 통신 성공이 모든 조건에서 회로를 닫힌 채 유지한다는 뜻은 아니다. 검증 시 초기 CLOSED·독립된 빠른 유효 FAILED 조회를 사용해 성공/전체 표본 증가·통신 실패 표본 불변을 확인하고, 업무 실패·예약 반환의 1회 적용도 별도로 확인한다. 응답 검증 전후의 집계 경계가 구현에서 어긋나거나 정상 실패 응답이 반복적으로 잘못된 거래 사실을 전달하는 관찰이 나오면 계약 검증·분류 경계를 재검토한다. 그 경우도 FAILED라는 업무 상태만으로 통신 장애라고 단정하지 않는다.

**거래 조회 404의 선택·근거:** 사용자는 고정 PG 계약상 거래 부재 404를 통신 성공으로 집계하기로 했다. 거래를 찾지 못했어도 조회 요청에 정상적인 답을 받았으므로, 조회 가용성과 결제 사실의 확인 여부를 구분한다. 회로가 성공으로 기록한 뒤 gateway는 UNAVAILABLE 관찰을 반환한다. 실패 예외를 catch해 성공으로 위장하는 경로와 달리, 이 404는 의도적으로 성공으로 분류한 계약상 결과다. 확인 정보의 마지막 DB 반영 기준과 기존 업무 종결 보존 규칙은 유지한다.

**대안·비용·재검토:** 표본 제외는 거래 부재를 회로 판단에 사용하지 않지만 정상 조회의 가용성 정보도 버리고 최소 표본 집계를 늦춘다. 실패 집계는 거래 부재와 조회 장애를 섞어 다른 주문의 확인까지 차단할 수 있다. 현재 선택은 거래 부재 응답을 가용성 정보로 사용하므로 부재 조회가 많으면 다른 통신 실패의 비율은 낮아진다. 거래 키 오류·장기 부재는 별도로 살펴야 하며 회로 성공만으로 결제 확인·정합성까지 정상이라고 판단하지 않는다. 적용 대상은 고정한 PG의 계약상 단건 조회 404다. 잘못된 URI·다른 경로·프록시의 임의 404가 같은 의미라는 근거는 없다. 현재는 별도 오류 본문 식별 코드를 합의하지 않았으므로 HTTP 상태만으로 응답 원인까지 구별할 수 있다고 주장하지 않는다. PG 경계·조회 계약이 달라지면 식별 방법과 분류를 재검토한다.

**검증 기준:** 알려진 고정 PG 단건 조회 경로에서 존재하지 않는 거래 키로 404를 재현한다. 성공/전체 표본 증가·실패 표본 불변, UNAVAILABLE 반영·주문/예약 유지·추가 create 0을 함께 확인한다. 실제 요청 URI도 검증해 잘못된 경로의 404로 정상 계약 테스트를 통과시키지 않는다. 느린 호출 집계·차단은 2.9를 따른다.

**조회 5xx의 선택·근거:** 2026-10-20 사용자는 PG 조회의 5xx를 우선 실패 표본으로 집계하기로 했다. HTTP 응답 도달 여부와 조회 기능의 가용성을 구분하며, 정상 거래 부재를 알리는 계약상 404와 달리 조회 처리 실패를 후속 호출 제한의 관찰로 사용한다. 현재는 500·502·503·504뿐 아니라 501·505도 이 분류에 포함하며 코드별 예외를 임의로 추가하지 않는다. 5xx 본문의 업무 상태 문자열을 최종 결제 결과로 인정하는 계약은 없고, 조회 불가 처리·저장 상태/예약 유지·create 재발송 금지를 지킨다.

**대안·비용·재검토:** 501·505 같은 기능/규격 불일치나 특정 오류 코드를 제외하는 대안은 회로가 일시 장애와 계약 오류를 섞는 것을 줄일 수 있지만 별도 분류 계약과 검증이 필요하다. 현재의 일괄 실패 집계는 단순하고 실패 조회의 반복을 줄이는 대신, 호출 설정 오류에도 회로를 열어 다른 확인을 지연시키거나 원인 수정을 늦출 수 있다. 회로가 열린다고 잘못된 경로·규격을 고치거나 PG 장애 원인을 판별하는 것은 아니다. 제공자 오류 계약이 구체화되거나 특정 5xx가 반복되는 원인을 확인하면 코드·본문별 분류를 재검토한다.

**검증 기준:** 실제 adapter가 조회 5xx를 받을 때 실패/전체 표본 증가·UNAVAILABLE 반영·주문/예약 유지·추가 create 0을 확인한다. 코드별 고정 응답과 5xx 본문에 업무 상태 문자열이 있는 경우도 최종 성공·실패로 적용하지 않는지 검증한다. 회로 밖 fallback이 실패 집계를 삼키지 않는지 확인한다. 응답을 받은 5xx의 대기 시간과 응답 없는 timeout의 대기는 구분해서 관찰한다.

**조회 429의 선택·근거:** 2026-10-20 사용자는 호출 빈도·한도 초과로 조회를 거절한 429를 회로 실패 표본으로 집계하기로 했다. HTTP 응답을 받았어도 필요한 조회 결과를 얻지 못한 관찰을 후속 호출 제한에 사용한다. 회로의 실패 기록 뒤 바깥 fallback에서 UNAVAILABLE로 변환하며 저장 상태·예약은 기존 규칙을 따른다. 자동 retry·sleep은 추가하지 않고 요청당 GET 최대 1회·create 재발송 금지를 유지한다. Retry-After 해석·대기나 별도 RateLimiter의 도입을 이번 결정에 포함하지 않는다.

**대안·비용·재검토·검증:** 429를 표본에서 제외하면 한도 거절이 다른 원인의 회로 차단과 섞이지 않지만 반복된 거절만으로는 실패율 차단 근거가 쌓이지 않는다. 현재 선택은 실패 조회 반복을 줄이는 대신 공유 회로의 다른 확인도 지연시킬 수 있고 회로 OPEN 시간이 실제 한도 회복 시점과 다를 수 있다. PG 한도의 적용 범위나 회복 시점을 확인하면 회로 단위·대기 정책·별도 호출량 제어 필요성을 재검토한다. 통제된 429에서 실패/전체 표본 증가·UNAVAILABLE 반영·예약 유지·추가 GET/create 없음, 확정할 임계값 이후 OPEN의 GET 차단을 검증한다.

**조회 401/403의 선택·근거:** 사용자는 인증·권한 거절도 우선 회로 실패로 집계하기로 했다. HTTP 응답을 받았지만 고정 제공자 계정으로 필요한 조회 기능을 이용하지 못한 관찰을 후속 호출 제한에 사용한다. 이는 PG가 고장났다는 판정이나 결제의 최종 실패가 아니다. 회로 실패 기록 후 UNAVAILABLE로 변환하고 업무 상태·예약을 보존한다. 원인인 계정·권한 설정의 확인·수정은 회로 차단과 별개다.

**대안·비용·재검토·검증:** 표본 제외는 인증/권한 문제를 가용성 집계에서 분리하지만 같은 계정의 거절 요청이 계속 나갈 수 있다. 현재 선택은 반복 조회를 줄이는 대신 우리 설정 오류로 공유 회로를 열 수 있고, 설정을 수정한 뒤에도 OPEN 대기 때문에 결과 확인이 늦어질 수 있다. 거절 응답이 짧다면 timeout보다 자원 보호 이익이 작을 수도 있다. 실제 원인·거절 응답 시간·수정 후 확인 지연과 계정별 영향 범위를 관찰해 분류·회로 단위를 재검토한다. 통제된 401/403에서 실패/전체 표본 증가·UNAVAILABLE·주문/예약 유지·추가 create 0을 확인하며, 커머스 자체의 접근 제어 오류와 구분해 검증한다.

**나머지 조회 4xx의 선택·근거:** 사용자는 아직 별도 분류하지 않은 조회 4xx도 기본 실패 표본으로 집계하기로 했다. 계약상 정상 조회 응답으로 해석할 근거가 없으므로 조회 기능을 이용하지 못한 관찰로 사용한다. 앞서 정한 거래 부재 404의 성공 집계·401/403과 429의 실패 집계는 유지한다. 적용 범위는 PG 조회 GET이다. 생성 POST에서만 인정하는 422+정확한 code+거래 미생성 false+주문/금액 일치의 확정 거절과는 별개이며, 조회 422로 예약을 반환하지 않는다.

**대안·비용·재검토·검증:** 나머지 4xx를 제외하면 요청·경로 오류가 공유 회로를 열지 않지만 동일한 실패 조회를 계속 보낼 수 있다. 현재 선택은 실패 조회의 반복을 줄이는 대신 우리 요청·계약 오류로 회로를 열어 다른 확인을 지연시킬 수 있다. 새로운 PG 계약이 특정 4xx를 정상적인 업무 응답으로 보장하면 해당 코드·본문과 표본 분류를 승인받아 재검토한다. 대표 400·405·409·422에서 실패/전체 표본 증가·UNAVAILABLE·업무 상태/예약 유지·추가 create 0을 확인하고, 거래 조회 404 및 생성 422의 기존 규칙이 유지되는지 검증한다.

**조회 연결 실패의 선택·근거:** 사용자는 PG 조회의 연결 거절·연결 timeout 같은 접속 실패를 회로 실패 표본으로 집계하기로 했다. PG 조회를 시작하지 못한 관찰이 반복될 때 후속 호출을 제한한다. 같은 HTTP client에서 발생하더라도 내부 풀 대기 실패는 별도로 식별해 제외한다. RestClient 등의 상위 예외가 원인을 감싸면 cause를 확인하며, 모든 I/O 예외를 내부 풀 대기 또는 연결 실패로 일괄 해석하지 않는다.

**대안·비용·재검토·검증:** 연결 실패 제외는 주소/포트 설정·일시 네트워크 문제를 회로와 분리하지만 실패한 접속 시도가 계속될 수 있다. 현재 선택은 반복 접속·대기를 줄이는 대신 우리 설정이나 경로 문제로 공유 회로를 열고, 수정·회복 후 조회를 지연시킬 수 있다. PG 자체의 장애 원인을 확정한 것으로 보지 않는다. 연결 실패의 실제 원인과 빈도·접속 대기·회복 후 확인 지연을 관찰해 설정과 분류를 재검토한다. 통제된 연결 거절/timeout에서 실패 표본·UNAVAILABLE·업무 상태/예약 유지·추가 create 0, 임계값 이후 후속 접속 차단과 회복을 검증한다. 내부 풀 대기 제외가 감싼 예외에서도 유지되는지 대조한다. 연결 timeout은 2.9의 300ms를 적용한다.

**응답 해석 불가의 선택·근거:** 사용자는 JSON 파싱 불가·필수 필드 누락·계약과 다른 타입/형식 등 조회 응답을 유효한 값으로 해석할 수 없는 경우를 회로 실패 표본으로 집계하기로 했다. HTTP 200이더라도 사용할 조회 결과를 얻지 못했다는 관찰을 후속 호출 제한에 사용한다. adapter는 계약상 응답 해석 오류를 식별해 회로에 실패를 기록한 뒤 바깥 fallback에서 UNAVAILABLE로 변환한다. 예상하지 못한 프로그램 오류나 TX B의 DB 오류까지 같은 catch로 정상화하지 않는다. 형식이 유효한 식별·금액·종결 충돌은 기존 CONFLICT 판단을 유지한다. 요청한 거래를 정확히 조회한 뒤 내부 주문과 충돌한 예시는 성공 표본이고, 단건 조회의 요청 거래 키와 반환 거래 키가 다른 경우는 아래 별도 합의대로 실패 집계한다. 다른 데이터 충돌의 집계로 임의 일반화하지 않는다.

**대안·비용·재검토·검증:** 해석 불가를 제외하거나 HTTP 200만으로 성공 집계하면 잘못된 매핑 코드가 회로를 여는 위험을 피할 수 있지만, 실제로 쓸 수 없는 응답이 반복돼도 실패율 차단 근거가 쌓이지 않는다. 현재 선택은 사용할 수 없는 조회의 반복을 줄이는 대신 DTO/응답 매핑과 실제 응답 계약의 불일치·계약 변경 때문에 공유 회로를 열 수 있다. 여기서 계약상 응답 해석 오류로 분류한 경우와, 아래 별도 합의의 정상 응답 검증 후 내부 프로그램 오류를 구분한다. 실제 원문과 고정 계약의 차이·매핑 정확성을 확인해 원인을 구분하고, 계약이 바뀌면 판정·adapter를 재검토한다. 응답 원문·카드를 진단 로그나 충돌 요약에 무분별하게 저장하지 않는다. 통제된 잘못된 JSON/필드에서 실패 표본·UNAVAILABLE·상태/예약 유지·추가 create 0, 예상 밖 프로그램 오류의 비정상 전파와 유효 형식 충돌의 CONFLICT 보존을 확인한다.

**올바른 거래 조회와 내부 업무 충돌의 분리:** 사용자는 A 주문에 B 거래 알림이 들어와 B를 조회했고 PG가 B의 정확한 결과를 반환한 예시를 회로 실패로 집계해서는 안 된다고 확인했다. 이 경우 회로는 정상 조회의 성공을 기록하고, TX B가 저장 주문과 비교해 충돌을 기록한다. 요청한 거래를 올바르게 알려준 PG의 조회 가용성과 알림/주문의 업무 정합성을 분리한다. TX B는 기존대로 회로 바깥이며 CONFLICT를 조회 불가로 삼키지 않는다.

**대안·한계·검증:** 이런 내부 비교 충돌까지 실패 집계하면 잘못된 알림으로 공유 조회 회로를 열 수 있다. 현재 선택은 이를 피하지만 모든 데이터 정합성 문제를 회로가 탐지·차단한다는 보장은 없다. 이 합의를 ‘형식만 유효하면 어떤 PG 응답도 무조건 성공’으로 일반화하지 않는다. 요청 키 A에 PG가 B를 반환하는 단건 조회 계약 위반은 아래 별도 합의대로 실패 집계한다. 검증은 A 주문/B 거래 알림과 실제 B 조회를 통제해 회로 성공 표본 증가·실패 표본 불변·TX B 충돌/409·기존 주문/예약 불변·추가 create 0을 확인한다.

### 단건 조회의 거래 키 불일치와 판단 근거

- **선택 사실:** 사용자는 `GET /api/v1/payments/TX-A`에 거래 키 TX-B를 반환하는 경우도 회로 실패로 집계하도록 승인했다. 반면 B를 요청해 B를 정확히 받은 뒤 A 주문과 충돌한 앞선 예시는 성공 표본으로 유지한다. 조회 요청·응답 사이의 직접 위반과 내부 주문 비교를 구분한다.
- **문제·근거:** 요청한 거래 대신 다른 거래를 반환하면 해당 조회를 업무에 사용할 수 없다. 후처리의 CONFLICT는 잘못된 반영을 막지만, 사용할 수 없는 조회의 반복까지 줄이지는 않는다. 실패 집계는 이런 응답이 반복될 때 후속 호출을 제한하기 위한 선택이다. 정합성 보호를 위해 반드시 회로 실패가 필요하다거나 데이터를 더 정확하게 만드는 장치라고 설명하지 않는다.
- **대안·비용:** 성공 표본+CONFLICT만으로 처리해도 잘못된 주문/재고 반영은 막을 수 있고 회로 판단은 단순하다. 현재 선택은 여기에 반복 호출 제한을 더하지만 일시적 응답 오류·잘못된 요청/매핑 구현으로 공유 회로를 열어 다른 정상 확인도 지연시킬 수 있다. 실제 PG 원인으로 단정하지 않는다.
- **실행 계약:** 실패 표본은 1회 기록하면서 파싱한 충돌 식별자·금액·상태는 보존한다. 관찰은 기존 CONFLICT/IDENTITY_MISMATCH로 TX B에 전달하고, TX B가 충돌 요약을 commit한 뒤 409로 반환한다. 실패로 집계했다는 이유로 UNAVAILABLE로 바꾸거나 이미 파싱한 충돌 근거를 버리지 않는다. TX B는 회로 밖이며 주문·예약·기존 종결은 유지한다.
- **표현 선택:** 2026-10-20 사용자는 `recordResult`로 결과를 실패 집계하는 방식을 승인했다. adapter가 파싱한 충돌 관찰과 승인된 직접 조회 대상 불일치 여부를 함께 반환하고, `pgLookup`의 결과 predicate가 그 불일치를 실패로 센다. 같은 날 주문별 조회가 다른 주문의 거래 1건을 반환한 경우에도 이 방식을 확장하도록 승인받았다. 집계 때문에 예외를 던지거나 일반 fallback으로 보내지 않으며 충돌 관찰은 그대로 TX B로 전달한다. 아래 내부 처리 순서를 따른다.
- **검증·재검토:** 요청 A/응답 B에서 실패 표본 증가·TX B의 충돌 요약/409·주문/예약 불변·추가 create 0을 확인한다. 요청 B/응답 B와 내부 A 주문 충돌은 성공 표본임을 대조한다. 계약에 맞는 정상 확인을 회로가 얼마나 지연시키는지, 오류 원인이 PG인지 요청/매핑 구현인지 관찰해 분류를 재검토한다. 위 근거는 논의에 따른 설계 판단이며 성능·보호 효과를 실증한 결과는 아니다.

**recordResult 선택의 근거·대안·비용:** 이미 해석한 충돌 결과를 보존해야 하므로 결과를 예외로 변환했다가 회로 밖에서 복원하는 단계를 줄인다. 전용 예외 방식도 가능하지만 충돌 근거를 예외에 담고 일반 UNAVAILABLE fallback보다 먼저 잡아 복원해야 하며, catch 순서가 잘못되면 근거가 소실될 수 있다. 선택한 방식도 adapter 내부 결과 metadata와 predicate의 일치가 필요하다. `CONFLICT` 또는 `IDENTITY_MISMATCH`라는 업무 분류 전체를 실패 조건으로 사용하지 않고, 승인한 직접 대상 위반, 즉 단건 조회의 요청 거래 키·응답 거래 키 불일치와 주문별 조회 결과에 요청 외부 주문 ID와 다른 거래가 포함된 경우를 구분한다. 후자는 1건이면 IDENTITY_MISMATCH, 2건 이상이면 MULTIPLE_TRANSACTIONS 관찰이지만 둘 다 결과의 직접 대상 위반 표시로 실패 집계한다. 공통 예외 정책 변경 등으로 결과 metadata 유지 비용이 커지면 전용 예외 대안을 재검토한다.

**adapter 내부 처리 순서 — 승인한 조회 대상 비교:** `PgLookupResult(observation, directLookupTargetMismatch)`는 infrastructure adapter 내부의 불변 반환 형태다. boolean은 단건 조회의 요청 거래 키·응답 거래 키 불일치 또는 주문별 조회 배열 중 요청 외부 주문 ID와 다른 orderId가 하나라도 있는지로 만든다. 빈 배열은 false이며 복수 거래라는 사실만으로 true로 만들지 않는다. 각 응답은 파싱·필수 형식 검증을 마친 값이어야 한다. 공개 응답·domain gateway 반환 계약·DB 저장 필드를 추가하지 않는다. 공통 회로 predicate는 이 내부 결과의 불일치 표시를 읽으며 요청별로 회로 설정을 바꾸지 않는다.

```text
pgLookup의 recordResult predicate(result):
  return result가 PgLookupResult이고 directLookupTargetMismatch == true

adapter.findByTransactionKey(requestedKey):
  try:
    result = pgLookup의 명시적 decorator/execute 호출:
      자동 redirect 없이 실제 GET 최대 1회
      200 이외 2xx/3xx이면 본문 거래 해석 전에 회복 대상 조회 오류로 전파
      나머지 HTTP 상태와 응답 형식은 합의한 오류 분류대로 해석
      validPayment = 파싱·필수 형식 검증을 마친 거래
      if validPayment.transactionKey != requestedKey:
        observation = CONFLICT/IDENTITY_MISMATCH + 파싱한 충돌 근거
        return PgLookupResult(observation, true)
      return PgLookupResult(QUERY 거래 관찰, false)
    // core가 recordResult로 집계한 뒤에도 반환한 result를 그대로 사용
    return result.observation
  catch 합의된 회복 대상 조회 예외:
    return 회로 밖 fallback의 UNAVAILABLE 관찰
  // 식별한 내부 프로그램 오류는 ignoreException으로 표본 제외 후 500으로 전파
  // 제외됐다는 이유로 일반 조회 불가 fallback에 넣거나 관찰을 합성하지 않음
  // 호출 Facade가 반환 관찰을 회로 밖 TX B에 전달
```

이 의사코드는 유효한 단건 거래 응답의 대상 비교 위치를 확정하며, 아래 주문별 조회의 유일한 거래에도 같은 반환 경계를 적용한다. 계약상 404·해석 불가 등 기존 분류를 변경하거나 아직 정하지 않은 다른 오류·충돌의 회로 집계를 결정하지 않는다. 혼합 주문 목록은 아래 추가 합의대로 실패 집계하고 업무 충돌은 MULTIPLE_TRANSACTIONS를 우선한다. 정상 200 빈 목록은 아래 추가 합의대로 성공 집계한다. 요청 주문의 정확한 복수 거래는 아래 추가 합의대로 성공 집계한다. 비교에는 내부 주문 ID·저장 금액·알림 status를 쓰지 않는다. `recordResult=true`는 실패 표본을 남기지만 결과를 자동으로 예외로 바꾸거나 fallback을 실행하지 않는다. 같은 호출에 수동 `onError`/추가 decorator를 적용해 실패를 중복 집계하지 않는다. 해당 결과로 회로가 OPEN이 되더라도 현재 충돌 관찰은 TX B로 전달하며, 후속 호출의 허용 여부와 구분한다.

**소스 근거·추가 검증:** Resilience4j 2.2.0 `CircuitBreaker.decorateCallable`의 `onResult` 후 결과 반환과 `CircuitBreakerStateMachine.onResult`의 결과 predicate 실패 집계 경로를 확인했다. 이는 라이브러리 동작의 근거이며 제품 연동 테스트 통과 근거가 아니다. 요청 A/응답 B에서 실패 1회·성공 0회·일반 UNAVAILABLE fallback 실행 0회, TX B의 충돌 commit/409를 확인한다. 요청 B/응답 B 뒤 내부 A 주문 충돌은 실패 0회·성공 1회이며, 같은 `IDENTITY_MISMATCH`만으로 회로 실패가 되지 않는지 대조한다. 각 검증은 독립된 초기 CLOSED·동시 호출 없음 조건으로 시작한다.

**주문별 조회 대상 불일치로 확장한 선택·근거:** 2026-10-20 사용자는 `GET /api/v1/payments?orderId=A`에서 다른 외부 주문 ID B의 유효한 거래 1건을 반환한 경우도 회로 실패로 집계하도록 승인했다. 정상 형식이어도 요청한 주문의 조회 결과를 제공하지 못했으므로 단건 조회의 거래 키 불일치와 같은 직접 계약 위반으로 본다. 같은 이유·대안·공유 차단 비용은 위 조회 대상 불일치 판단을 따른다. 성공 집계 또는 표본 제외 후 CONFLICT만 처리해도 잘못된 반영은 막을 수 있지만 반복된 대상 위반을 실패율 차단 근거로 사용하지 못한다. 실제 요청 query 인코딩·매핑 오류가 원인일 수도 있으므로 PG 원인으로 단정하지 않으며, 정상 조회 지연·원인 관찰에 따라 재검토한다.

```text
adapter.findByOrderId(requestedProviderOrderId)의 대상 비교:
  같은 pgLookup의 decorator 안에서 자동 redirect 없이 주문별 GET 최대 1회
  200 이외 2xx/3xx이면 본문 거래 해석 전에 회복 대상 조회 오류로 전파
  나머지 HTTP 상태/응답 파싱은 기존 분류 적용
  계약에 맞는 HTTP 200과 빈 거래 배열을 받은 경우:
    return PgLookupResult(QUERY/UNAVAILABLE 관찰, false)  // 성공 표본 1회
  유효한 거래 배열의 크기가 1인 경우:
    payment = 유일한 거래
    if payment.orderId != requestedProviderOrderId:
      observation = CONFLICT/IDENTITY_MISMATCH + 파싱한 충돌 근거
      return PgLookupResult(observation, true)
    // 대상이 맞으면 이 직접 대상 위반 표시를 만들지 않고 기존 검증으로 전달
  유효한 거래 배열의 크기가 2 이상인 경우:
    observation = CONFLICT/MULTIPLE_TRANSACTIONS + 기존 충돌 요약 근거
    mismatch = 어느 거래라도 orderId != requestedProviderOrderId
    return PgLookupResult(observation, mismatch)
    // 전부 요청 주문이면 성공 1회, 다른 주문이 포함되면 실패 1회
    // 업무 충돌은 두 경우 모두 MULTIPLE_TRANSACTIONS를 우선
  // recordResult 집계 후 결과 관찰을 회로 밖 TX B로 전달
```

**확장 범위·검증:** 비교 대상은 저장하고 요청에 사용한 외부 주문 ID와 응답 `orderId`다. 다른 주문의 거래를 임의로 걸러 빈 목록으로 바꾸거나, 추가 단건 GET/create로 보정하지 않는다. 초기 CLOSED·동시 호출 없음에서 A 주문 요청/B 주문 거래 1건 응답을 재현해 실패 1·성공 0·일반 UNAVAILABLE fallback 0, IDENTITY_MISMATCH 충돌 요약 commit/409, 주문·예약·기존 종결 불변·추가 GET/create 0을 확인한다. 충돌 식별자·금액·상태는 기존 요약 규칙으로 보존한다. 유일한 거래의 주문 ID 불일치 실패 집계와 아래 정확한 복수 거래 성공 집계를 구분한다. 다른 주문이 섞인 2건 이상 목록은 아래 추가 합의대로 회로 실패 1회·업무 MULTIPLE_TRANSACTIONS 우선으로 처리한다.

**정확한 복수 거래 조회의 선택·근거·대안:** 2026-10-20 사용자는 요청한 주문의 유효한 거래를 정확히 조회했지만 2건 이상인 경우 회로 성공으로 집계하도록 승인했다. PG가 실제 복수 거래를 올바르게 알려 준 조회 가용성과, 한 주문의 거래를 임의로 선택할 수 없는 업무 충돌을 구분한다. 실패 집계 대안은 같은 충돌의 반복 조회를 줄일 수 있지만 정확한 조회 때문에 공유 회로를 열어 다른 주문의 확인까지 지연시킬 수 있다. 현재 선택은 이런 결합을 피하는 대신 복수 거래 충돌의 반복 확인 자체를 회로 실패율로 차단하지 못한다. 복수 거래가 생긴 원인과 후속 해결은 회로 성공 표본만으로 설명하거나 해결했다고 보지 않는다.

**처리·검증·재검토:** adapter는 `PgLookupResult(CONFLICT/MULTIPLE_TRANSACTIONS 관찰, false)`를 반환해 성공 표본 1회를 기록한다. 거래 수만큼 집계하거나 CONFLICT 전체를 recordResult 실패 조건으로 사용하지 않는다. 회로 밖 TX B가 기존 요약 규칙으로 충돌을 commit한 뒤 409로 반환하며, 주문·예약·기존 종결은 유지하고 어떤 거래도 임의 선택하지 않는다. 초기 CLOSED·동시 호출 없음에서 요청 주문의 유효한 서로 다른 거래 2건과 3건 이상을 각각 정확히 반환시켜 성공 1·실패 0·일반 UNAVAILABLE fallback 0, MULTIPLE_TRANSACTIONS commit/409·추가 GET/create 0을 확인한다. 다른 주문이 섞인 목록은 아래 추가 합의대로 실패 집계한다. 해석 불가 응답·다른 계약 위반과의 조합을 성공으로 일반화하지 않는다. 반복 충돌의 원인·조회량·미해결 기간을 관찰하고, PG 조회 계약이나 중복 거래 처리 범위가 바뀌면 재검토한다.

**정상 빈 목록의 선택·근거·대안·비용:** 2026-10-20 사용자는 주문별 조회의 정상 `200 + []`를 회로 성공 표본 1회로 집계하도록 승인했다. 계약상 거래 부재를 정확히 표현한 조회와 결제 결과를 확인하지 못한 업무 상태를 구분하며, 정상 단건 조회의 거래 부재 404와 같은 기준을 적용한다. 실패 집계는 반복된 빈 조회를 줄일 수 있지만 정상 부재 때문에 공유 회로를 열 수 있다. 표본 제외는 이를 피하지만 정상 조회가 성공·전체 표본에 반영되지 않는다. 현재 선택은 부재를 정상 조회로 세는 대신 빈 응답만 반복되는 상황을 회로 실패율로 차단하지 못한다. 빈 배열을 거래 미생성의 확정 증거나 재발송 허가로 사용하지 않는다.

**처리·검증·재검토:** adapter는 회로 안에서 `PgLookupResult(QUERY/UNAVAILABLE 관찰, false)`를 정상 반환한다. 통신 예외나 일반 UNAVAILABLE fallback을 거치지 않는다. 회로 밖 TX B는 마지막 DB 반영 기준으로 verificationStatus=UNAVAILABLE을 기록하고 저장 결제 상태·예약·기존 종결은 유지한다. 고객 대사 응답은 기존 조회 불가 계약대로 202다. 초기 CLOSED·동시 호출 없음에서 실제 `200 + []`를 재현해 성공 1·실패 0·일반 fallback 0, 요청당 GET 1·추가 GET/create 0과 UNKNOWN/PENDING/종결 상태 보존을 확인한다. 본문 없음·JSON null·깨진 배열은 정상 빈 배열로 바꾸지 않으며 기존 해석 불가 분류를 따른다. 거래 저장 가시성 계약·반복 빈 응답의 원인/지속 시간이 달라지면 처리·보호 수단을 재검토한다.

**기대 금액 불일치의 선택·근거·대안:** 2026-10-20 사용자는 거래 키·외부 주문 ID가 요청 대상과 일치하고 금액 형식이 유효한 조회에서, PG 금액이 내부 저장 기대 금액과 다른 경우 회로 성공으로 집계하도록 승인했다. 거래 키/주문 ID 조회에는 기대 금액을 조회 조건으로 보내지 않는다. 반환된 거래 금액과 내부 기대 금액의 비교는 업무 정합성 검증이므로 조회 가용성과 구분한다. 이 판단은 PG 금액이 옳거나 내부 금액이 틀렸다는 원인 확정이 아니다. 실패 집계 대안은 반복된 금액 충돌 조회를 줄일 수 있지만 내부 금액 계산·저장 오류만으로도 공유 회로를 열어 다른 주문의 확인을 지연시킬 수 있다. 현재 선택은 이를 피하는 대신 금액 충돌의 반복 조회를 회로 실패율로 차단하지 못한다.

**처리·검증·재검토:** adapter는 기대 금액 비교 때문에 예외나 직접 조회 대상 불일치 표시를 만들지 않고 `PgLookupResult(QUERY 거래 관찰, false)`를 정상 반환한다. 회로 밖 TX B가 기존 금액 검증으로 AMOUNT_MISMATCH를 판단해 충돌 요약을 commit한 뒤 409로 반환한다. 승인된 직접 대상 위반·금액 타입/형식 오류의 회로 실패 분류는 유지하며 이 합의는 그 오류와의 조합을 성공으로 바꾸지 않는다. 초기 CLOSED·동시 호출 없음에서 거래 키/외부 주문 ID가 맞고 응답 금액만 유효한 다른 값인 경우를 재현해 성공 1·실패 0·일반 UNAVAILABLE fallback 0, AMOUNT_MISMATCH 요약 commit/409, 주문·시도 업무 상태·예약·기존 종결 불변·추가 GET/create 0을 확인한다. 내부 기대 금액과 관찰 금액은 기존 충돌 요약 규칙으로 확인하고, 원문/카드는 저장하지 않는다. 실제 금액 차이의 원인·반복 빈도와 조회 계약 변경을 관찰해 재검토한다.

**종결 상태 충돌의 선택·근거·대안:** 2026-10-20 사용자는 식별·금액·응답 형식이 정상인 권위 조회가 저장 종결과 충돌하는 경우 회로 성공으로 집계하도록 승인했다. 저장 SUCCESS에 조회 FAILED 또는 저장 FAILED에 조회 SUCCESS가 오는 경우와, 종결 뒤 시작한 새 조회가 PENDING을 보고하는 경우에 적용한다. 조회가 반환한 상태와 내부 종결의 일관성은 업무 정합성 문제로 보존하고 조회 가용성과 분리한다. 실패 집계는 반복된 충돌 조회를 줄일 수 있지만 저장/반영 오류나 PG 상태 차이 때문에 공유 회로를 열어 다른 정상 주문의 확인도 지연시킬 수 있다. 현재 선택은 이를 피하는 대신 상태 충돌 반복을 회로 실패율로 차단하지 못하며, PG나 내부 중 어느 상태가 옳은지 판정하거나 충돌을 해결하지 않는다.

**처리·검증·재검토:** adapter는 `PgLookupResult(QUERY 거래 관찰, false)`를 정상 반환하고 회로 밖 TX B가 기존 상태 규칙을 적용한다. 반대 종결은 TERMINAL_MISMATCH, `terminalAtStart=true`인 새 조회의 PENDING은 TERMINAL_REGRESSION을 요약 commit한 뒤 409다. 저장 종결·주문/시도 업무 상태·예약은 유지하고 재고 효과를 추가하지 않는다. 초기 CLOSED·동시 호출 없음에서 각 경우 성공 1·실패 0·일반 UNAVAILABLE fallback 0, 해당 충돌 요약 commit/409·추가 GET/create 0을 확인한다. 대조군으로 종결 전에 시작한 조회의 늦은 PENDING은 `terminalAtStart=false` 규칙대로 무시하고 기존 FINAL을 반환하며, 회로 성공 집계만으로 이를 409로 바꾸지 않는다. 직접 대상 위반·해석 불가 등 다른 오류의 기존 실패 분류와 늦은 CREATE 응답 처리도 변경하지 않는다. 충돌 원인·반복 빈도·PG 상태 전이/가시성 계약이 달라지면 업무 회복 정책과 회로 분류를 재검토한다.

**혼합 주문 목록의 선택·근거·대안:** 2026-10-20 사용자는 주문별 조회의 유효한 2건 이상 배열에 요청한 외부 주문 ID와 다른 주문의 거래가 포함된 경우 회로 실패 표본 1회, 업무 충돌은 MULTIPLE_TRANSACTIONS·409를 우선하도록 승인했다. 예: A 주문 요청에 A 거래와 B 거래를 반환. 조회 필터의 직접 계약 위반과 거래가 여러 건이라는 업무 위험을 별도로 표현한다. 1건의 다른 주문 거래를 실패 집계한 기준을 유지하되, 2건 이상이면 임의 선택하지 않는 기존 업무 규칙도 유지한다. IDENTITY_MISMATCH를 업무 코드로 우선하는 대안은 대상 위반을 앞세울 수 있지만 복수 거래 규칙과 충돌 우선순위가 달라진다. 회로 성공/표본 제외 대안은 공유 차단을 피하지만 반복된 필터 위반을 실패율 차단 근거로 사용하지 못한다. 현재 선택은 요청/매핑 오류로도 공유 회로를 열어 정상 주문의 확인을 지연시킬 수 있으며 원인을 PG로 단정하지 않는다.

**처리·검증·재검토:** 먼저 전체 배열의 파싱·필수 형식을 검증한다. 유효한 배열이 2건 이상이면 업무 관찰은 MULTIPLE_TRANSACTIONS로 만들고, 요청 외부 주문 ID와 다른 거래가 하나라도 있으면 `directLookupTargetMismatch=true`로 반환한다. recordResult가 실패를 1회 기록한 뒤 같은 관찰을 TX B로 전달하며, 충돌 요약 commit 후 409로 반환한다. 다른 주문 거래를 필터링해 1건/빈 목록으로 바꾸거나 IDENTITY_MISMATCH로 충돌 코드를 덮지 않는다. 기존 요약의 관찰 식별자·금액·상태·건수로 근거를 보존하고 새 원문/카드 저장이나 이력 테이블은 추가하지 않는다. 초기 CLOSED·동시 호출 없음에서 혼합 순서·다른 주문 거래의 위치를 바꿔 실패 1·성공 0·일반 UNAVAILABLE fallback 0, MULTIPLE_TRANSACTIONS commit/409·주문/예약/기존 종결 불변·추가 GET/create 0을 확인한다. 전부 요청 주문의 유효한 복수 거래인 성공 대조군도 유지한다. 요청 query·파싱/매핑과 PG 필터 동작의 원인, 정상 확인 지연 또는 조회 계약이 달라지면 분류·업무 우선순위를 재검토한다.

**내부 프로그램 오류의 선택·근거·대안:** 2026-10-20 사용자는 PG 응답은 정상인데 adapter 내부 버그로 발생한 프로그램 오류를 회로 표본에서 제외하도록 승인했다. 우리 코드 결함으로 PG 조회 가용성을 판단해 공유 회로를 열지 않는다. 성공 집계도 하지 않으며 성공·실패·느린 호출·최소 표본 수에 모두 포함하지 않는다. 실패 집계 대안은 반복 오류 호출을 줄일 수 있지만 코드 수정 없이 해결되지 않는 내부 결함으로 다른 주문의 조회까지 차단할 수 있다. 현재 선택은 그 오판을 피하는 대신 반복된 내부 오류와 자원 소모 자체를 회로 실패율로 차단하지 못한다. 오류는 기존 500 처리로 전파하며 UNAVAILABLE·202로 감추지 않는다.

**식별·집계·전파 순서:** 정상 응답의 파싱·필수 계약 검증 후 adapter 내부 로직에서 식별한 프로그램 오류는 infrastructure의 전용 `PgAdapterProgrammingException`으로 구분해 원인을 보존한다. 이 타입은 알려진 응답 해석/HTTP/전송 오류를 일괄 감싸는 용도로 사용하지 않는다. `pgLookup`의 ignoreException predicate에 기존 내부 풀 대기 제외와 이 내부 오류 식별을 합성한다. 같은 제외 설정을 별도 Customizer에서 덮지 않는다. recordException에서 false만 반환해 제외를 흉내 내거나 예외를 정상 관찰로 바꿔 성공 집계하지 않는다. 회로 밖에서는 내부 풀 대기만 기존 회복 대상에 따라 UNAVAILABLE로 바꾸고, 프로그램 오류는 fallback 허용 대상에 넣지 않고 다시 전파한다. 파싱/필수 필드/타입·형식 오류는 기존 응답 해석 오류 실패 집계·UNAVAILABLE 경로를 유지한다. 모든 RuntimeException·I/O 오류를 프로그램 오류로 간주하지 않으며, 아직 분류하지 않은 원인을 이번 합의로 임의 확정하지 않는다.

```text
정상 응답 검증 뒤 adapter 내부 로직의 식별된 프로그램 오류:
  원인을 보존한 PgAdapterProgrammingException을 회로 안에서 전파
pgLookup.ignoreException(error):
  내부 풀 대기 실패 또는 PgAdapterProgrammingException이면 true
회로 밖 예외 처리:
  내부 프로그램 오류이면 기존 500 처리로 재전파
  기존에 합의한 회복 대상 조회 오류만 UNAVAILABLE로 변환
  // 내부 프로그램 오류에 관찰 합성·TX B 호출·create/GET 재시도 없음
```

**소스 근거·검증·재검토:** Resilience4j 2.2.0 `CircuitBreakerStateMachine.handleThrowable`은 ignoreException이면 표본 기록 전에 반환하지만, 무시하지 않은 예외에서 recordException=false이면 성공으로 기록한다. 로컬 source JAR에서 이 경로를 확인했으며 제품 연동 검증을 대신하지 않는다. 초기 CLOSED·동시 호출 없음에서 정상 응답 후 내부 프로그램 오류를 주입해 성공/실패/느린 호출/전체 표본 증가 0·일반 UNAVAILABLE fallback 0·HTTP 500·TX B 미호출·업무 상태/예약/기존 종결 불변·추가 GET/create 0을 확인한다. 확인 준비 TX는 번호 발급·확인 정보 변경 없이 종료되며, TX B를 호출하지 않으므로 기존 확인 정보를 보존하고 새 UNAVAILABLE 관찰을 합성하지 않는다. 정상 응답 뒤 오류와 잘못된 응답의 실패 집계를 대조한다. 실제 원인·오류 빈도와 자원 점유를 관찰해 내부 오류 식별 및 별도 보호 필요성을 재검토한다.

**조회의 계약 외 2xx/3xx 선택·근거·대안:** 2026-10-20 사용자는 정상 조회 200 이외의 2xx 및 3xx를 회로 실패로 집계하고 회로 밖에서 UNAVAILABLE로 변환하며, 3xx 자동 redirect를 금지하도록 승인했다. 조회는 200 거래 객체/배열 또는 합의한 부재 응답을 따르므로, HTTP의 성공 계열 코드나 본문 상태만으로 승인하지 않은 조회 계약을 추측하지 않는다. 정상 데이터가 담긴 다른 2xx를 수용하는 대안은 제공자 변경에 관대하지만 계약 누락을 숨길 수 있다. redirect를 따라가는 대안은 주소 이전을 수용하지만 요청당 실제 GET 수·호출 대상·대기 범위가 달라진다. 현재 선택은 이 경계를 명확히 하는 대신 정상 데이터가 있어도 확인을 지연시키고 계약/주소 변경 시 명시적인 수정이 필요하다. 우리 endpoint 설정 오류로도 공유 회로가 열릴 수 있으며 PG 장애로 단정하지 않는다.

**처리 순서·적용 범위:** 이 정책은 거래 단건/주문별 조회 GET에 적용한다. 하위 Apache client의 조회 요청 설정에서 `RequestConfig.Builder.setRedirectsEnabled(false)`를 적용해 RestClient가 최종 응답을 받기 전의 자동 추적을 막는다. adapter는 응답의 HTTP 상태를 먼저 확인하고 200 이외 2xx 또는 3xx이면 본문 거래/배열 검증에 들어가지 않고 식별 가능한 회복 대상 조회 오류로 전파한다. 회로가 실패를 기록한 뒤 바깥 fallback에서 QUERY/UNAVAILABLE 관찰로 변환하고 TX B의 마지막 관찰 반영·업무 상태/확보 수량 보존·고객 대사 202를 따른다. 204를 빈 배열로, 조회 202를 검증한 PENDING으로, 3xx 본문을 검증한 성공/실패 또는 CONFLICT로 해석하지 않는다. Location 수동 추적·추가 GET/create도 없다. 생성 POST의 승인된 202 PENDING·200 SUCCESS 및 정확한 422 무효과 거절은 유지하되 생성 회로는 이 절의 별도 생성 계약을 따른다. 이번 선택으로 생성 POST의 미합의 응답을 새로 승인하지 않는다.

**소스 근거·검증·재검토:** Apache HttpClient 5.4.2 로컬 source JAR의 `RequestConfig.Builder.setRedirectsEnabled` 설정 지점 확인과 실제 RestClient 요청 적용 검증을 구분한다. 후자는 PgHttpConfigTest·PgHttpClientBehaviorTest의 현재 실행 근거를 따른다. 초기 CLOSED·동시 호출 없음에서 201·202·204 및 대표 301·302·303·307·308을 재현해 각각 실패 1·성공 0·일반 UNAVAILABLE fallback 1, QUERY/UNAVAILABLE·대사 202·업무 상태/예약/기존 종결 불변을 확인한다. 유효한 SUCCESS/PENDING 본문을 넣어도 적용하지 않고 204는 빈 목록 성공으로 바뀌지 않아야 한다. 최초 endpoint GET 1·redirect 대상 수신 0·추가 GET/create 0을 검증하고, 생성 202/200의 기존 동작은 회귀 검증한다. 제공자 계약·주소 이전 요구 또는 실제 설정 적용이 달라지면 이 정책을 재검토한다.

**수신 중 통신 오류의 선택·근거·대안:** 2026-10-20 사용자는 조회 연결 후 응답 수신 도중 끊김·본문 전송 중단 같은 실제 통신 I/O 오류도 회로 실패로 집계하고 UNAVAILABLE로 처리하는 추천안을 승인했다. 접속 성공만으로 조회 완료를 보장하지 않으므로 사용할 응답을 받지 못한 관찰을 후속 호출 제한에 사용한다. 표본 제외는 일시 네트워크 문제가 공유 회로를 여는 일을 줄이지만 반복된 수신 실패가 실패율 차단 근거로 쌓이지 않는다. 현재 선택은 우리 네트워크 문제로도 정상 PG의 조회를 지연시킬 수 있으며 PG 자체 장애로 단정하지 않는다. 내부 풀 대기·식별한 내부 프로그램 오류의 제외와 알려진 응답 해석 오류 분류는 유지한다. 같은 요청의 수신 I/O와 파싱 실패를 중복 집계하지 않는다.

**처리·검증·재검토:** 실제 조회 HTTP의 원인 예외를 구분해 회로 내부에서 실패를 기록한 뒤, 바깥 fallback에서 QUERY/UNAVAILABLE로 변환한다. TX B는 마지막 관찰 반영과 업무 상태/확보 수량/종결 보존·고객 대사 202를 따른다. 초기 CLOSED·동시 호출 없음에서 조회 응답 도중 연결을 끊거나 본문을 중단시켜 실패 1·성공 0·일반 UNAVAILABLE fallback 1, 상태/예약 보존·최초 GET 1·추가 GET/create 0과 연결 자원 반환을 확인한다. 부분 본문에서 읽은 업무 상태를 적용하지 않는다. 실제 원인·반복 빈도·자원 반환이 달라지면 원인 분류와 보호 설정을 재검토한다. 사례를 계속 늘려 개별 승인받지 않고 승인한 공통 원칙으로 예외 타입을 매핑하며, 실제 정책 변경이나 문서 충돌이 발견될 때 질문한다.

### 응답 timeout의 실패 집계와 반환 경계

**선택·근거:** 사용자가 대안을 논의한 뒤 PG 조회의 응답·읽기 timeout을 회로 실패 표본으로 집계하도록 명시 승인했다. 정한 시간 안에 조회를 완료하지 못한 관찰을 쌓아 반복 실패 시 후속 외부 조회·대기를 줄인다. 내부 연결 풀 대기 실패 제외와는 별도 분류다. 회로 내부에서 timeout을 실패로 기록한 뒤 바깥 fallback에서 UNAVAILABLE 관찰로 변환한다. 회로 안에서 정상 반환으로 삼켜 성공 표본으로 기록하지 않는다. 업무 상태·예약 유지·create 재발송 금지는 기존 계약을 따른다.

**대안·숨은 비용:** timeout 표본을 제외하면 개별 HTTP 대기 제한은 유지되지만 timeout 반복이 실패율 기준의 차단 근거로 쌓이지 않는다. 명시적으로 제외한 호출은 느린 호출 집계에서도 빠지므로, 해당 timeout 자체가 느린 호출 기준으로 차단을 일으킨다고 가정하지 않는다. 현재 선택은 장애 중 불필요한 조회를 줄이는 대신 짧은 timeout·네트워크 지연으로 정상 PG까지 차단하거나 회복 뒤 확인을 지연시킬 수 있다. 실패 표본만으로 PG 자체의 장애 원인을 확정하지 않는다. 느린 호출 차단·회로/timeout 수치와 별도 전체 deadline/취소 제외는 2.9에 정의했다.

**반환 경계:** CLOSED와 HALF_OPEN의 허용된 호출은 실제 HTTP를 수행하므로 timeout까지 기다릴 수 있다. OPEN 또는 탐색 허용량 소진으로 거절된 후속 호출은 외부 GET 없이 확인 불가로 처리한다. 기존 확인 준비·TX B의 로컬 DB 처리는 남으므로 API 전체의 즉시 반환을 보장한다는 뜻은 아니다. 회로를 열어도 이미 실행 중인 HTTP를 취소하지 않으며, 회로의 창 크기를 동시 실행 수 제한으로 해석하지 않는다.

**검증·재검토:** 통제된 응답 지연에서 실제 HTTP 종료·실패 표본 증가·상태/예약 유지·추가 create 0을 확인한다. 2.9의 최소 표본·임계값을 채우면 OPEN 중 후속 조회의 PG GET 0과 확인 불가 반환, 회복 탐색·재조회 후 동일 거래의 종결을 검증한다. 정상 지연과 timeout 비율, 호출 점유, 회복 후 결과 확인 지연을 관찰해 timeout·회로 설정을 재검토한다. 로컬 통제 실험을 운영 최적값의 근거로 삼지 않는다.

## 2.9 HTTP 제한과 PG 회로의 초기 정책

**선택·상태:** 2026-10-20 HTTP/보호 범위·조회 초기값을 승인했고 2026-10-22 생성에도 공통 수치를 독립 적용·HALF_OPEN 최대 대기 10초를 승인했다. 아래 값은 **적은 호출과 짧은 대기로 상태 전이를 재현·관찰하기 위한 로컬 초기 가설**이다. 실제 PG의 정상 지연·요청량·회복 시간을 측정해 도출한 운영 적정값이 아니다. 초기값 채택은 검증 결과가 아니며, 글의 비교 실험 조건을 미리 고정하지 않는다.

### HTTP 설정과 시간의 경계

|항목|설정|책임·주의|
|---|---|---|
|PG 전용 풀|총 10·경로별 최대 10|다른 외부 연동과 분리. 생성과 조회는 같은 풀 공유. 대기 중인 모든 Servlet worker 수까지 제한하지 않음|
|풀 연결 대기|200ms|Apache RequestConfig.connectionRequestTimeout. 내부 풀 대기 실패는 회로 표본 제외. 생성의 확실한 최초 획득 timeout은 POOL_ACQUIRE_TIMEOUT 미발송(2.8)|
|TCP 연결|300ms|Apache ConnectionConfig.connectTimeout. 연결 실패는 해당 생성/조회 회로의 실패 표본|
|응답/읽기|1초|RequestConfig.responseTimeout 및 ConnectionConfig.socketTimeout. 실제 header/body 수신 경로 적용 검증|
|재시도·redirect|모두 비활성|Apache 자동 retry·redirect를 끄고 adapter에도 재호출 루프를 두지 않음. 생성 POST도 동일. POOL_ACQUIRE_TIMEOUT 판정의 보장 조건|
|추가 보호|전체 deadline·강제 취소·TimeLimiter·Bulkhead·Retry·RateLimiter 없음|현재 동기 경로와 HTTP 자원 종료를 먼저 검증. 회로는 이미 시작한 호출을 취소하지 않음|

조회 제한은 다음과 같이 해석한다. 새 정책이나 추가 타이머를 도입하는 것이 아니라 승인한 단일 조회·HTTP 제한의 범위를 명시한다.

|대상|현재 계약|
|---|---|
|한 callback/reconcile의 조회 횟수|PG GET 최대 1회. 회로가 거절하면 0회이며 내부 자동 재조회는 없음|
|자동 재조회 간격|해당 없음. 반복 호출·sleep·backoff를 수행하지 않음|
|사용자의 후속 수동 reconcile 간격|서버가 자동 간격을 예약하거나 최소 간격을 강제하지 않음|
|한 GET의 대기 제한|풀 대기 200ms·연결 300ms·응답/읽기 1초. 단순 합 1,500ms는 각 단계 설정값의 합이며 단일 요청 전체의 강제 deadline이 아님|
|재조회 전체 예산|자동 재조회 묶음이 없으므로 별도 반복 예산 없음. 하나의 GET에 위 제한을 적용하며 여러 수동 요청을 합친 wall-clock 상한은 보장하지 않음|

풀 대기·연결·응답 제한의 합을 API 전체의 엄밀한 상한으로 주장하지 않는다. DB 대기/commit, 요청 처리, 본문 해석 등은 별도이며 응답이 조금씩 계속 오면 총 수신 시간은 길어질 수 있다. timeout은 PG의 거래 취소나 외부 효과 없음의 증거가 아니다. 조회 회로 OPEN에서 차단해도 로컬 확인 준비/TX B는 수행한다. 생성 사전 차단은 TX A/B 없이 DRAFT를 유지하고, TX A 뒤 실제 생성 거절에는 실패 반환 TX B를 수행한다.

**근거·대안·비용:** 작은 로컬 경계에서 무한 대기를 피하고 timeout/풀 부족을 짧게 재현할 출발점으로 200ms·300ms·1초와 최대 10을 선택했다. 부하량·지연 목표에서 산출한 값은 아니므로 정상 지연도 실패로 판단할 수 있다. 공유 풀은 설정/종료를 단순화하지만 생성 부하가 조회를, 조회 부하가 생성을 지연시킨다. 생성/조회 분리 풀은 격리에 유리한 대신 풀 수명·용량 배분을 더 관리한다. 전체 deadline+취소는 긴 총 지연을 제한할 때 유리하지만 호출 취소·실제 소켓/worker 반환·불확실한 외부 효과를 별도로 검증해야 한다. 동시성 격리 요구나 점진적 본문 수신으로 인한 장기 점유가 관찰되면 보호 범위를 재검토한다.

### 회로 설정과 값별 근거

Resilience4j 2.2.0 `CircuitBreakerConfig`의 로컬 소스에서 기본 상수와 필드 초기값을 확인했다. 아래 수치는 pgCreate/pgLookup의 공통 승인 초기값이다. YAML의 configs.pgBase에 한 번 선언하고 각 instance가 baseConfig로 참조한다. 수치만 재사용하며 상태·표본·거절 계수는 각 인스턴스별이다. 생성/조회별 Java predicate는 해당 이름의 Customizer로만 적용하며 공통 base에는 넣지 않는다. 생성 지연/실패 분포로 검증한 값이 아니다. 기본값도 서비스 적정값의 근거를 대신하지 않는다.

|속성|승인 초기값|2.2.0 기본값|선택 이유·숨은 비용|
|---|---|---|---|
|slidingWindowType|COUNT_BASED|COUNT_BASED|호출 순서·건수로 재현하기 쉬움. 저빈도에서는 오래된 결과가 남으므로 시간 창이 유리할 수 있음|
|slidingWindowSize|10|100|적은 호출로 창 교체를 관찰. 실제 요청량 기준이 아니며 표본 변동에 민감|
|minimumNumberOfCalls|5|100|1건 실패만으로 열지 않되 빠르게 관찰. 통계적 신뢰도로 도출하지 않은 절충|
|failureRateThreshold|50|50|절반 이상 실패 시 차단하는 기본 출발점. 최소 5건에서는 3/5, 10건에서는 5/10에서 개방 조건 충족|
|slowCallDurationThreshold|800ms|60초|1초 읽기 timeout 전의 느린 성공도 관찰하려는 가설. 정상 지연 분포 근거가 없고 전체 HTTP timeout과 측정 구간도 다름|
|slowCallRateThreshold|50|100|느린 성공이 절반이어도 차단. 결제/통신 성공과 느린 호출이 겹칠 수 있으며 정상 PG를 막을 위험|
|waitDurationInOpenState|5초|60초|로컬 회복 관찰의 대기 단축. 실제 PG 복구 시간과 무관하며 짧으면 장애 중 재탐색, 길면 복구 확인 지연|
|permittedNumberOfCallsInHalfOpenState|2|10|적은 탐색으로 판정 관찰. 1건 성공·1건 실패도 50%라 다시 OPEN. 정상 성공이어도 느린 호출 비율로 열릴 수 있음|
|automaticTransitionFromOpenToHalfOpenEnabled|false|false|백그라운드 전환 없이 다음 요청으로 탐색. 대기 경과만으로 PG를 능동 확인하지 않음|
|maxWaitDurationInHalfOpenState|10초|0|HALF_OPEN 진입부터 판정 미완료 상태를 10초로 제한. 결과가 부족하면 OPEN으로 돌아가며 HTTP 취소/결제 실패 확정은 아님. 저빈도에서는 정상 성공 1건 뒤에도 OPEN 복귀 가능|

최소 5건 전에는 실패/느림 비율로 열지 않는다. HALF_OPEN의 판정은 허용한 탐색 2회 결과로 하며 CLOSED 최소 표본 5건을 다시 요구하지 않는다. 창 10과 HALF_OPEN 2는 전체 동시 요청/연결 수 제한을 뜻하지 않는다. HALF_OPEN은 10초 전에 2개 결과로 성공/실패·느림 비율을 판정하며, 10초까지 판정하지 못하면 OPEN으로 돌아간다. 자동 OPEN→HALF_OPEN 전환 false와 HALF_OPEN 만료→OPEN 타이머는 방향이 달라 함께 적용된다. 라이브러리 내부 상태 타이머이며 TimeLimiter·사용자 executor를 추가하는 것이 아니다. 시간 만료는 이미 실행 중 HTTP 취소나 업무 실패/재고 반환의 증거가 아니다. 생성 사전 확인에서 시작된 HALF_OPEN도 10초가 흐르므로 TX A가 오래 걸려 actual 호출 전에 만료되는 경우는 기존 미발송 거절 경로를 따른다.

  circuitbreaker:

|위치·타입|조립 계약|
|---|---|
|`infrastructure/payment/PgHttpProperties`|commerce.pg를 불변 설정으로 바인딩·양수 timeout/풀 크기 검증. base/callback URL은 로컬 설정, 고객 입력 불가. callback-url은 컨텍스트 기동 때 한 번 바인딩하며 기동 후 알아낸 포트로 늦게 교체하지 않는다. 콜백 HTTP 테스트는 기동 전에 선택한 포트를 server.port와 함께 주입한다([5.7](../pg-simulator/fixture-contract.md#57-테스트-pg-제어와-상태-보존))|
|`infrastructure/payment/PgHttpConfig`|PG 전용 connection manager → CloseableHttpClient → HttpComponentsClientHttpRequestFactory → RestClient. Apache 자동 retry/redirect 비활성, 재실행 exec interceptor·RestClient 재시도 interceptor 없음(2.8 POOL_ACQUIRE_TIMEOUT 보장 조건). Spring 종료 때 client가 전용 manager까지 한 번 정리|
|`infrastructure/payment/PgCircuitConfig`|각 이름의 CircuitBreakerConfigCustomizer로 result/ignore/record predicate 연결. 실패로 세는 result 조건은 생성·조회가 각자의 결과 타입으로 따로 두고, 표본에서 빼는 우리 쪽 오류(풀 대기 실패·식별한 프로그램 오류) 조건은 내용이 같아 하나를 함께 쓴다(2026-10-25 C1 정리, 동작 변경 없음). 수치 재선언 없음|
|`infrastructure/payment/PgHttpGateway`|도메인 PaymentGateway 구현. 주입 registry의 생성/조회 인스턴스 재사용. 사전 확인은 실제 권한을 즉시 반환하고, 실제 create/lookup은 각각 HTTP+해석+직접 대상 표시까지 한 번 감쌈. create는 호출별 진입 표시로 미발송을 판정([2.8 미발송 판정 장치](#생성-회로와-사전-차단)). HTTP 송수신은 아래 `PgHttpTransport`에 맡김|
|`infrastructure/payment/PgHttpTransport`|2026-10-25 C1에서 Gateway에서 분리(동작 변경 없음). 생성 본문·URI 인코딩, POST·GET 1회 exchange와 64KB 응답 상한, `ResourceAccessException` 원인 사슬로 풀 대기 실패(`PgPoolAcquireException`)와 통신 실패(생성/조회별 Unavailable 예외) 구분. 회로·관찰 변환은 하지 않음|
|`infrastructure/payment/PgResponseDecoder`|상태코드 우선 분기·JSON 필수값/타입/형식 검증, 알려진 계약 오류와 내부 프로그램 오류를 구분. 도메인 객체의 최종 주문·금액·종결 판단은 TX B|

예외 판정은 Apache/Spring의 원인 사슬에서 알려진 lease timeout, 연결/읽기 timeout, 수신 I/O, 계약 해석 오류를 식별해 인프라 예외로 정규화한다. `PgPoolAcquireException`과 식별한 `PgAdapterProgrammingException`은 ignore predicate에 합성한다. `PgLookupUnavailableException`은 승인된 회복 대상 실패를 표현한다. 풀 대기 예외도 회로 밖에서 UNAVAILABLE로 변환하되 실패 표본은 남기지 않는다. PgPoolAcquireException은 원인 사슬에 `ConnectionRequestTimeoutException`이 있을 때만 만들며, 생성에서는 2.8 판정에 따라 POOL_ACQUIRE_TIMEOUT 미발송으로 바꾼다. 계약 검증 후 내부 처리 단계에서 식별한 프로그램 오류만 전용 marker로 구분해 제외/500으로 전달한다. 생성 본문 안의 예상 밖 CallNotPermittedException도 [2.8 미발송 판정 장치](#생성-회로와-사전-차단)에 따라 본문 안에서 같은 marker로 감싼다. 원인을 식별하지 않은 모든 RuntimeException/I/O를 내부 오류로 일괄 감싸지 않으며 새로운 정책이 필요하면 질문한다. 원본을 보존하되 카드·응답 본문을 예외 메시지에 복사하지 않는다.

result predicate는 `PgLookupResult.directLookupTargetMismatch`만 검사한다. 정상 결제 FAILED·빈 배열·내부 금액/종결 충돌을 실패로 확장하지 않는다. recordException=false는 표본 제외가 아니므로 ignore predicate를 대체하지 않는다. fallback은 `CallNotPermittedException`·풀 대기 제외 예외·명시한 회복 대상 조회 예외만 QUERY/UNAVAILABLE로 바꾸고 DB/프로그래밍 오류는 전파한다.

```text
lookup(target):                    // 로컬 TX 없음
  try:
    result = pgLookup.executeCallable(() ->
      response = GET target 한 번   // 풀 대기/연결/본문 해석까지 같은 경계
      return decoder.decodeLookup(response, target)
    )
    return result.observation      // recordResult 실패여도 원래 CONFLICT 보존
  catch CallNotPermitted / PgPoolAcquire / PgLookupUnavailable:
    return QUERY_UNAVAILABLE
  catch identified programming error:
    throw original/cause          // 500; 관찰 합성·TX B 호출 없음

checkCreateAdmission():          // 로컬 TX·HTTP 없음
  if pgCreate.tryAcquirePermission() == false: return BLOCKED
  pgCreate.releasePermission()   // HALF_OPEN 탐색 슬롯도 즉시 반환
  return READY                  // 이후 실제 POST 권한을 보장하는 표가 아님

create(request):                 // retry 없음, DB 처리 포함 금지
  entry = 이 호출 전용 진입 표시 새로 생성(최초 NOT_ENTERED)  // 필드·전역·다른 요청과 공유 금지
  // entry 생성 뒤 try 전(요청 준비 등)의 예상 밖 예외는 잡지 않음:
  //   500 전파, pgCreate 표본 0, 관찰 합성·TX B·반환·재전송 없음
  try:                           // 실제 decorator 실행 호출만 감쌈
    result = pgCreate.executeCallable(() ->  // decorator가 권한 재획득 → 본문
      entry.markEntered()        // 본문의 첫 동작; 이후 풀 대기·POST·해석
      try:
        response = POST 한 번   // RestClient exchange 1회; Apache retry/redirect 비활성
        return decoder.decodeCreate(response, request)
      catch 원인 사슬에 ConnectionRequestTimeoutException(정확한 타입):
        throw PgPoolAcquireException(cause)  // 본문 안 정규화 → onError가 ignore로 표본 제외
      catch CallNotPermittedException unexpected:  // 본문 안: 의도한 진입 거절 아님
        throw PgAdapterProgrammingException(cause=unexpected)
        // 본문 안에서 감싸므로 onError가 감싼 예외를 받아 ignore로 표본 제외
    )
    202+유효 PENDING / 200+유효 SUCCESS: 검증한 CREATE 거래 관찰
    정확한 422 무효과 계약: REJECTED_NO_EFFECT
    파싱 가능한 식별/금액 불일치: 실패 표시가 있는 CONFLICT 결과 보존
  catch CallNotPermittedException e
      when entry.notEntered() and e.causingCircuitBreakerName == pgCreate 이름:
    return CREATE/LOCAL_NOT_DISPATCHED(reason=CIRCUIT_REJECTED)  // 표본 0
  catch 알려진 통신/해석 오류·나머지 응답: decorator가 실패 기록, CREATE_UNAVAILABLE
  catch PgPoolAcquireException:  // 본문 안 정규화 → core ignore로 표본 제외(아래 두 분기 공통)
    if 2.8 풀 획득 판정의 확정 조건 ①~④와 client 보장 조건을 모두 충족:
      return CREATE/LOCAL_NOT_DISPATCHED(reason=POOL_ACQUIRE_TIMEOUT)  // 표본 0
    else:  // 확인된 풀 획득 오류지만 보장 조건 미충족
      return CREATE_UNAVAILABLE  // 기존 UNKNOWN·재고 유지, 표본 0
    // 예외 타입 하나만으로 미발송을 확정하지 않음; 연결/읽기 timeout·취소는 이 catch에 오지 않음
  catch PgAdapterProgrammingException(식별한 프로그램 오류, 본문 안 CallNotPermitted 포함):
    ignore로 표본 제외, 500 전파; 관찰 합성·TX B·반환·자동 재발송 없음
  // 본문 진입 뒤의 같은 타입 예외·decorator 호출 밖 예외는 미발송 분기에 넣지 않음
  // 수동 acquirePermission/onSuccess/onError 추가 없음
```

**소스 사실과 실행 검증의 구분:** Apache HttpClient 5.4.2 `ConnectionConfig.Builder`의 connect/socket timeout, `RequestConfig.Builder`의 connectionRequest/response timeout·redirect, PoolingHttpClientConnectionManagerBuilder의 total/per-route 설정 메서드를 로컬 소스에서 확인했다. 실제 RestClient에 적용되는지·읽기 중단 뒤 연결이 반환되는지는 구현 뒤 실제 HTTP 검증 대상이다.

**관찰·재검토:** 정상 지연 분포, timeout 비율, PG 수신 create/GET 수, 풀 leased/pending, 회로 상태/실패/느림/차단, 회복 후 정상 확인까지의 지연을 함께 기록한다. 느린 호출 차단을 제외하는 대안, 시간 창, 더 큰 최소 표본은 정상 요청 차단과 탐지 지연의 교환을 비교할 후보다. 글의 실험 축/최종 결과는 실행본 이후 별도 결정한다. 결과를 초기값에 맞춰 만들지 않는다.
