# R01 트레이드오프와 사용자 질문

2026-11-04. 사용자가 설계 전에 질문·트레이드오프 논의를 요구했다.
초기 추천안과 구분해 사용자가 답한 T01~T08의 선택을 아래에 기록했다.
이 선택은 설계 방향의 합의이며 업무 코드/DB 적용/기능 검증 완료를 뜻하지 않는다.
답이 없다는 이유로 추천안을 자동 확정하지 않는다.

| 항목 | 사용자 선택 |
|---|---|
| T01 계약 코드 | 앱별 DTO — JSON 계약 테스트로 일치 보장 |
| T02 최초 확정 시각 | 기존 확정 기록의 createdAt 재사용 |
| T03 Inbox 비교 근거 | 정규화 snapshot 저장·필드 비교 |
| T04 사건 ID | 최초 확정 TX에서 UUID 생성·저장 |
| T05 같은 v1의 추가 필드 | 추가 필드 무시·필수 계약 엄격 검증 |
| T06 소비 오류 대응 | 제한 재시도 후 보관이 확인되면 offset 진행. 최종 보관 위치는 T08 적용 |
| T07 공통 DB 장애 | 재시도 소진 후 리스너 중단, 원본 offset 유지 |
| T08 개별 실패 보관 | DB에만 실패 이벤트 저장. 실패 기록 commit 뒤 offset 진행 |

## 요구사항으로 이미 정해진 부분

- 6~7주차 통합 진행, 최종 Outbox와 consumer Inbox 적용.
- 사건 identity·최초 확정 시각·확정 품목 보존, 같은 사실의 재수신과 충돌 구분.
- Inbox 기록과 모든 구매 활동을 한 DB TX로 반영하고 성공 후 ack.
- DB 유일 제약으로 동시 중복 보호. 실패 TX 안에서 오류를 삼키고 완료 처리하지 않음.
- W6 직접 발행 누락과 W7 복구를 실제 DB/Kafka에서 검증하고 기존 PG/예약/POINT를 보존.

위 조건 자체를 다시 고르게 하지 않는다. 아래는 이 조건을 구현하는 선택이다.

## 우선 논의할 세 가지

### T01 · 두 앱의 계약 공유

| 선택 | 이점 | 비용 |
|---|---|---|
| 공통 순수 Java 계약 모듈 | 같은 record/정규화 규칙을 함께 변경하고 컴파일로 연결 확인 | 새 모듈과 Gradle 범위 조정, 두 앱의 변경 결합 |
| 앱별 독립 DTO + JSON 계약 검사 | 기존 구조 변경이 작고 producer/consumer가 독립적으로 발전 | DTO/규칙 중복, 계약 드리프트를 wire 검사로 관리 |

추천: 같은 저장소의 단일 v1 계약을 함께 개발하므로 공통 계약 모듈.
다만 학습 범위에서 새 모듈/빌드 변경을 줄이는 것이 우선이면 독립 DTO도 요구사항을 만족한다.
사용자 질문: 공통 계약 모듈을 둘지, 앱별 DTO와 계약 검사로 관리할지.
사용자 답: **앱별 DTO — JSON 계약 테스트로 일치 보장**. 새 계약 모듈과 그에 따른 root 빌드 변경을 제외한다.

### T02 · 최초 확정 시각의 저장 위치

| 선택 | 이점 | 비용 |
|---|---|---|
| 기존 확정 기록 createdAt 재사용 | 이미 최초 확정 TX에서 저장됨, 중복 컬럼/값 동기화 감소 | 기록 생성 시각이 확정 시각이라는 의미를 명시하고 유지해야 함 |
| 별도 confirmedAt 컬럼 | 업무 의미가 직접 드러나며 기록 생성 시각과 분리 가능 | schema/Mapper/기존 데이터 처리 변경, 중복 시각의 일관성 관리 |

추천: 현재 OrderRecord가 최초 확정 때 한 번 만들어지므로 createdAt 재사용.
어느 쪽이든 DB datetime(6)과 이벤트 시각을 맞추고 중복 callback에서 최초 시각을 바꾸지 않는다.
사용자 질문: 기존 기록의 시각을 재사용할지, 별도 확정 시각 컬럼을 둘지.
사용자 답: **기존 확정 기록의 createdAt 재사용**. 최초 저장 시각의 마이크로초 정밀도를 유지한다.

### T03 · Inbox에서 사실을 비교할 근거

| 선택 | 이점 | 비용 |
|---|---|---|
| 정규화 snapshot | 필드 단위 비교·장애 분석·충돌 내용 확인이 쉬움 | 이벤트 내용 저장량과 복원 처리 |
| 정규화 hash | 저장량이 작고 비교가 단순 | 정확한 정규화/버전 관리, 원문 없이 차이 분석 어려움, hash-only 판단의 한계 |
| snapshot + hash | 내용 분석과 hash 조회/비교를 함께 사용 가능 | 저장/계산 중복, 두 근거의 일관성 관리 |

추천: 현재 학습 범위에서는 정규화 snapshot과 필드 비교.
snapshot과 hash를 모두 저장한다고 모든 경우에 이득은 아니므로 실제 용도 없이 추가하지 않는다.
사용자 질문: 내용 snapshot, hash, 둘 다 중 어떤 근거를 저장할지.
사용자 답: **정규화 snapshot 저장·필드 비교**. 별도 hash 컬럼은 추가하지 않는다.

## 두 번째 질문 · 사용자 선택 반영

| ID | 선택지 | 주요 차이 |
|---|---|---|
| T04 사건 ID | 주문에서 안정적 유도 / 최초 확정 TX에 UUID 저장 | 추가 저장·복구 비용과 사건 identity의 확장성 |
| T05 같은 v1의 추가 필드 | unknown field 거절 / 알려진 필드만 검증하고 추가 필드 허용 | 잘못된 입력 발견과 additive 변경 호환성 |
| T06 소비 오류 대응 | 즉시 중단 후 수동 재개 / 제한 재시도 후 중단 / DLQ 격리와 별도 복구 | 단순성·정상 소비의 지연·운영 책임 |

이 선택들은 원문의 필수 경계를 지키는 범위에서 논의한다. 실패 record를 조용히 성공 처리하거나
DLQ 이동을 구매 활동 완료로 취급하는 것은 선택지에 포함하지 않는다.
구체 모듈/패키지·설정 숫자·실험 실행 방식도 현재 추천 가정이며 중요한 비용이 있는 항목은 구현 전에 설명한다.

T04 사용자 답: **최초 확정 시 UUID 생성·저장**. 주문 확정 기록에 영속화하고 재발행/복구에서도 같은 UUID를 사용한다.

T05 사용자 답: **추가 필드는 무시하고 필수 계약 검증**. 같은 v1의 모르는 필드는 소비 사실 비교에서 제외한다.
알려진 필드의 의미 변경/새 버전은 자동 수용하지 않는다.

T06 사용자는 **일부 재시도 후 DLQ 격리** 조합을 제안했다. 두 정책을 함께 적용할 수 있음을 설명하고
DLQ 전송과 원본 offset의 연결 방식을 추가로 질문했다.

| 연결 방식 | 이점 | 비용 |
|---|---|---|
| 전송 확인 후 offset 진행 | Kafka transaction 없이 단순하게 구성, 기존 Inbox 재사용 | 확인 후 commit 전 중단 시 DLQ 중복 가능 |
| Kafka transaction으로 DLQ+offset 처리 | Kafka 내부 두 기록을 원자적으로 연결 | transaction producer/consumer와 복구 검증 증가, 별도 DB 원자성은 여전히 별개 |

사용자 답: **DLQ 전송 확인 후 offset 진행·DLQ 중복 허용**.
DLQ는 업무 완료가 아니라 격리된 미해결 사건이며 재처리에서도 eventId·payload를 바꾸지 않는다.
이 답변에서 합의한 제한 재시도와 영속 보관 뒤 offset 진행 순서를 유지한다. T08에서 보관 위치를 DB로 변경했다.
재시도 수치와 저장 필드의 초기 제안은 [재시도·DB 실패 기록](retry-failure-record.md)에 기록한다.

## 후속 질문 · T07과 T08

### T07 · 공통 DB 장애 시 소비 지속 여부

| 선택 | 이점 | 비용 |
|---|---|---|
| 제한 재시도 후 해당 리스너 중단 및 offset 유지 | DB 장애 중 정상 이벤트가 DLQ로 계속 이동하는 상황을 줄인다 | 복구 확인과 리스너 재개가 필요하고 해당 리스너의 뒤 이벤트도 기다린다 |
| 제한 재시도 후 DLQ 격리 및 소비 계속 | 오류 처리 흐름이 하나이고 뒤 이벤트의 처리를 시도할 수 있다 | 공통 장애가 길면 정상 이벤트도 DLQ에 쌓여 개별 재처리가 늘어난다 |

추천은 DB 연결 획득 실패처럼 공통 의존성 문제로 분류할 수 있는 오류가 재시도 후에도 이어지면 해당 리스너를 중단하는 것이다.
복구 후 기존 group offset에서 다시 소비한다. 예를 들어 주문 하나의 데이터 충돌은 개별 사건으로 격리하고,
DB 접속 불가가 지속되는 경우는 해당 리스너의 진행을 멈춘다.
재시도 수치의 시작점은 최초 시도 후 1초 간격으로 추가 최대 2회다. DB 오류의 구체 분류는 실제 예외와 검증 결과에 맞춘다.

사용자 답은 **공통 DB 장애 시 리스너 중단과 offset 유지**다.

### T08 · 실패 보관 위치와 범위

| 선택 | 이점 | 비용 |
|---|---|---|
| 운영자가 한 건을 명시해 재처리 | 조치 대상과 결과를 확인하기 쉽고 잘못된 재발행 범위가 작다 | 사건이 많으면 지정과 확인을 반복해야 한다 |
| 운영자가 선택한 여러 건을 일괄 재처리 | 같은 원인의 여러 사건을 빠르게 복구할 수 있다 | 대상 목록 확인, 처리량 제한, 일부 실패 후 재실행 기준이 필요하다 |

추천은 운영자가 한 건을 지정하는 방식이다. 원본 topic·partition·offset으로 중복 격리 기록을 식별하고,
재발행할 DLQ record는 실제 DLQ 위치로 지정한다. 두 선택 모두 원인 해결 후 원래 UUID·key·payload로 재발행하며,
구매 활동이 반영됐는지는 Inbox와 저장 결과로 확인한다.

사용자는 재처리 단위 대신 실패 이벤트를 저장만 하자고 답했고, 이어서 **Kafka DLQ를 DB 실패 기록으로 대체**하는 선택을 확정했다.
개별 이벤트의 최종 실패는 별도 트랜잭션으로 보관하고 commit 확인 뒤 원본 offset을 진행한다.
공통 DB 장애 또는 실패 기록 저장 실패에는 T07과 같이 해당 offset을 유지하고 리스너를 중단한다.

## 진행 방식

1. 선택지·각 비용·추천 이유를 사용자에게 제시한다.
2. 합의한 답과 아직 열린 질문을 이 문서에 구분해 기록한다.
3. 상세 설계·계약·DDL·검증 초안을 그 답에 맞춰 수정한다.
4. 합의하지 않은 선택을 확정했다고 기록하거나 해당 선택에 의존한 구현을 진행하지 않는다.

기능 변경에 대한 기존 세 관점 리뷰와 중요한 수정 확인 규칙은 그대로 적용한다.
