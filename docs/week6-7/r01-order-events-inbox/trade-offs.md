# R01 트레이드오프와 사용자 질문

2026-11-04. 사용자가 설계 전에 질문·트레이드오프 논의를 요구했다.
기존 상세 설계는 작성자의 추천 초안이며 사용자 확정으로 취급하지 않는다.
현재 선택한 답은 없으며 아래 질문에 답을 받은 뒤 관련 문서를 갱신한다. 답이 없다는 이유로 추천안을 자동 확정하지 않는다.

## 요구사항으로 이미 정해진 부분

- 6~7주차 통합 진행, 최종 Outbox와 consumer Inbox 적용.
- 사건 identity·최초 확정 시각·확정 품목 보존, 같은 사실의 재수신과 충돌 구분.
- Inbox 기록과 모든 구매 활동을 한 DB TX로 반영하고 성공 후 ack.
- DB 유일 제약으로 동시 중복 보호. 실패 TX 안에서 오류를 삼키고 완료 처리하지 않음.
- W6 직접 발행 누락과 W7 복구를 실제 DB/Kafka에서 검증하고 기존 PG/예약/POINT를 보존.

위 조건 자체를 다시 고르게 하지 않는다. 아래는 이 조건을 구현하는 선택이다.

## 우선 논의할 세 가지

### T01 · 두 앱의 계약 공유

| 선택 | 이점 | 비용 |
|---|---|---|
| 공통 순수 Java 계약 모듈 | 같은 record/정규화 규칙을 함께 변경하고 컴파일로 연결 확인 | 새 모듈과 Gradle 범위 조정, 두 앱의 변경 결합 |
| 앱별 독립 DTO + JSON 계약 검사 | 기존 구조 변경이 작고 producer/consumer가 독립적으로 발전 | DTO/규칙 중복, 계약 드리프트를 wire 검사로 관리 |

추천: 같은 저장소의 단일 v1 계약을 함께 개발하므로 공통 계약 모듈.
다만 학습 범위에서 새 모듈/빌드 변경을 줄이는 것이 우선이면 독립 DTO도 요구사항을 만족한다.
사용자 질문: 공통 계약 모듈을 둘지, 앱별 DTO와 계약 검사로 관리할지.

### T02 · 최초 확정 시각의 저장 위치

| 선택 | 이점 | 비용 |
|---|---|---|
| 기존 확정 기록 createdAt 재사용 | 이미 최초 확정 TX에서 저장됨, 중복 컬럼/값 동기화 감소 | 기록 생성 시각이 확정 시각이라는 의미를 명시하고 유지해야 함 |
| 별도 confirmedAt 컬럼 | 업무 의미가 직접 드러나며 기록 생성 시각과 분리 가능 | schema/Mapper/기존 데이터 처리 변경, 중복 시각의 일관성 관리 |

추천: 현재 OrderRecord가 최초 확정 때 한 번 만들어지므로 createdAt 재사용.
어느 쪽이든 DB datetime(6)과 이벤트 시각을 맞추고 중복 callback에서 최초 시각을 바꾸지 않는다.
사용자 질문: 기존 기록의 시각을 재사용할지, 별도 확정 시각 컬럼을 둘지.

### T03 · Inbox에서 사실을 비교할 근거

| 선택 | 이점 | 비용 |
|---|---|---|
| 정규화 snapshot | 필드 단위 비교·장애 분석·충돌 내용 확인이 쉬움 | 이벤트 내용 저장량과 복원 처리 |
| 정규화 hash | 저장량이 작고 비교가 단순 | 정확한 정규화/버전 관리, 원문 없이 차이 분석 어려움, hash-only 판단의 한계 |
| snapshot + hash | 내용 분석과 hash 조회/비교를 함께 사용 가능 | 저장/계산 중복, 두 근거의 일관성 관리 |

추천: 현재 학습 범위에서는 정규화 snapshot과 필드 비교.
snapshot과 hash를 모두 저장한다고 모든 경우에 이득은 아니므로 실제 용도 없이 추가하지 않는다.
사용자 질문: 내용 snapshot, hash, 둘 다 중 어떤 근거를 저장할지.

## 다음으로 논의할 선택 · 아직 확정하지 않음

| ID | 선택지 | 주요 차이 |
|---|---|---|
| T04 사건 ID | 주문에서 안정적 유도 / 최초 확정 TX에 UUID 저장 | 추가 저장·복구 비용과 사건 identity의 확장성 |
| T05 같은 v1의 추가 필드 | unknown field 거절 / 알려진 필드만 검증하고 추가 필드 허용 | 잘못된 입력 발견과 additive 변경 호환성 |
| T06 소비 오류 대응 | 즉시 중단 후 수동 재개 / 제한 재시도 후 중단 / DLQ 격리와 별도 복구 | 단순성·정상 소비의 지연·운영 책임 |

이 선택들은 원문의 필수 경계를 지키는 범위에서 논의한다. 실패 record를 조용히 성공 처리하거나
DLQ 이동을 구매 활동 완료로 취급하는 것은 선택지에 포함하지 않는다.
구체 모듈/패키지·설정 숫자·실험 실행 방식도 현재 추천 가정이며 중요한 비용이 있는 항목은 구현 전에 설명한다.

## 진행 방식

1. 선택지·각 비용·추천 이유를 사용자에게 제시한다.
2. 합의한 답과 아직 열린 질문을 이 문서에 구분해 기록한다.
3. 상세 설계·계약·DDL·검증 초안을 그 답에 맞춰 수정한다.
4. 합의하지 않은 선택을 확정했다고 기록하거나 해당 선택에 의존한 구현을 진행하지 않는다.

기능 변경에 대한 기존 세 관점 리뷰와 중요한 수정 확인 규칙은 그대로 적용한다.
