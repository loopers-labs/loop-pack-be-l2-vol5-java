# 주문 확정 이후 전달과 복구

## W6에서 같은 offset을 다시 읽어도 구매 활동이 한 번만 생기는 이유

Kafka 그룹의 커밋된 offset은 다음에 읽을 위치다. 소비자가 offset 5의 주문 이벤트로 Inbox와 구매 활동을 커밋하고 offset 6을 커밋하기 전에 중단되면, 같은 그룹은 offset 5를 다시 받는다. 이때 이미 커밋된 Inbox의 UUID와 주문·확정 시각·품목을 대조한다. 같은 사실이면 기존 활동을 그대로 두고 offset을 6으로 진행한다.

두 번째 품목 저장이 실패하면 첫 번째 품목과 Inbox까지 함께 롤백한다. 이 상태에서 먼저 offset을 진행하면 다음 소비자는 복구할 이벤트를 읽을 수 없다. 개별 이벤트를 끝내 처리할 수 없으면 원문과 원본 위치를 별도 DB 트랜잭션에 기록한 뒤 offset을 진행한다. 실패 기록도 커밋하지 못하면 리스너를 중단해 원래 위치를 유지한다.

UUID 유일성만 검사하면 동일 UUID에 변경된 수량이 들어온 경우도 정상 중복으로 처리된다. 정규화한 사실을 비교하고, 충돌은 실패 기록으로 남긴다. 상품별 활동과 Inbox를 같은 트랜잭션에 둔 덕분에 Inbox가 있는지를 보는 것만으로 업무 트랜잭션의 완료를 판별할 수 있다.

## W7에서 전송이 중단돼도 기존 확정 사실로 복구하는 이유

W6의 직접 발행은 주문 트랜잭션이 커밋된 뒤 전송한다. 그 사이에 프로세스가 멈추면 주문 확정은 남지만 전송을 다시 시도할 작업이 없다. W7은 주문 확정과 동일한 트랜잭션에 Outbox 행을 넣어, 별도 Relay가 그 행을 다시 찾을 수 있게 한다.

Outbox가 있어도 MySQL 상태 저장과 Kafka 수신 확인은 각각 커밋된다. Kafka가 첫 record를 수신한 뒤 상태 저장 전에 Relay가 중단되면, 다음 Relay는 예약이 만료된 PENDING을 읽고 같은 UUID·토픽·키·payload를 보낸다. W6 재전달과 달리 여기서는 두 개의 Kafka record와 서로 다른 offset이 생긴다. 두 record가 하나의 업무 사건이라는 판단은 Streamer의 Inbox가 한다.

W6에서 이미 커밋된 누락 건은 새 PG 거래를 만들 필요가 없다. 저장된 UUID·최초 확정 시각과 확정 주문 품목으로 대상 Outbox를 복구할 수 있다. 다른 사건을 추측해 만드는 일을 막기 위해 주문 ID와 UUID를 함께 검증한다. 기존 Outbox와 사실이 같으면 상태·시도 횟수·payload를 보존한다. 같은 주문에 다른 UUID나 내용이 있으면 명령을 종료한다.

| 중단 지점 | MySQL에 남는 사실 | 복구 관찰 |
|---|---|---|
| W6 주문 커밋 후 직접 send 전 | 확정 주문과 UUID, 소비된 예약 | 기존 사건으로 Outbox를 추가한 뒤 활동 생성 |
| Streamer 업무 커밋 후 offset 커밋 전 | Inbox와 품목별 활동 | 같은 offset 재수신 뒤 활동 불변 |
| W7 broker 수신 확인 후 PUBLISHED 저장 전 | 예약이 있는 PENDING과 기존 확정 주문 | 새 offset으로 동일 사건 발행, 구매 활동 불변 |

디버거로 두 발행 경계를 정확히 정지시킨 뒤 실험용 프로세스를 종료한다. 복구 검증은 준비 때의 DB와 브로커를 그대로 사용한다. [재현 절차](operations.md)
