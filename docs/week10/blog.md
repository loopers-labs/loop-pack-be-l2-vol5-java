# (모니터링) health는 UP인데 결제 3건이 멈췄다 — 메트릭·로그·trace를 나눠 본 이유

## 상황

결제 10건 중 3건이 UNKNOWN 상태로 멈췄다. PG는 결제를 성공으로 저장했는데, 3초 timeout. 그런데 health 체크는 계속 UP이었다.

```text
장애 발생 (실제 앱·Kafka·MySQL·테스트 PG)
        │
        ▼
증거가 세 저장소에 쌓임
  메트릭 → Prometheus · trace → Tempo · 로그 → Alloy → Loki
        │
        ├─▶ 사람: Grafana 대시보드 한 화면
        └─▶ AI : Grafana MCP(읽기 전용)로 같은 저장소를 조회 → 사람이 판단
```

## health 체크로는 왜 못 잡았나

health 체크는 서버에 상태를 묻고 200(UP)을 받는 것이다. 
우리 health는 DB·Redis 같은 내부 구성요소만 본다. 이번 장애는 PG가 죽은 것도 아니었다. PG는 성공했고 응답만 잃었다. 
**외부 의존과 조용한 실패는 health에 보이지 않는다.**

그렇다고 health에 PG를 넣으면, PG가 느려질 때 우리 서버 전체가 DOWN으로 빠진다. 그래서 health 대신 업무 메트릭(결과 모르는 결제 수)을 따로 두었다. 이 값이 0 → 3 → 0으로 움직였다.

## 메트릭·로그·trace는 답하는 질문이 다르다

| 질문 | 신호 | 못 하는 것 |
|---|---|---|
| 얼마나, 언제부터? | **메트릭** | 어느 주문인지 (label에 orderId를 넣으면 시계열이 끝없이 는다) |
| 어느 건, 무슨 일? | **로그 — 어느 시점의 사건 하나** | 구간별 시간 |
| 어디서 기다렸나? | **trace — 요청 하나가 지나간 구간 전체와 시간** | 지금 상태 |

### 왜 MySQL에 영속저장을 하지 않았는가

- 메트릭은 몇 초마다 쌓인다. 매번 SQL로 시간 구간을 계산하면 느리다.
- 로그는 글자를 찾는 일이라 DB에서 꺼내기가 비싸다. 색인을 걸면 이번엔 쓰기가 비싸진다.
- trace는 구간이 트리 형태이고, 원하는 결과를 보려면 join을 해야 한다.
- 그리고 MySQL이 문제가 생긴다면 관측 데이터도 같이 못 본다. 

그래서 로그도 **목적 별 저장소로 나누고, 화면은 Grafana 하나로 모았다.** 한 화면에서 로그 줄의 traceId를 누르면 trace로 넘어간다.

## 누가 무엇을 하나 — push와 pull

| 역할             | 도구 |
|------------------|---|
| 저장             | Prometheus · Tempo · Loki |
| 데이터 전달 주체 | Alloy(로그) · 앱 자신(trace) · Prometheus 자신(메트릭) |
| 시각화           | Grafana |

- **Prometheus는 저장하면서 직접 가지러 간다(pull).** 5초마다 앱의 `/actuator/prometheus`를 읽는다. 그래서 메트릭 쪽엔 운반 역할을 하는게 없다
- **trace는 앱이 보낸다(push).** 하나씩 보내지 않고 메모리에 모았다가 512개가 차거나 5초가 지나면 한 번에 보낸다. 앱이 죽으면 모아 둔 것은 사라진다. trace는 관측 기록이라 감수한다. 반대로 결제 완료 이벤트는 잃으면 안 되므로 메모리가 아니라 DB(Outbox)에 같은 트랜잭션으로 저장하고 Kafka로 보낸다.
- **로그는 앱이 파일에 쓰기만 하고 Alloy가 Loki로 보낸다.** 앱이 Loki로 직접 보내면 Loki가 느릴 때 앱도 영향을 받는다.
- **Tempo는 trace를 숫자로 바꿔 Prometheus로 보낸다.** 누가 누구를 몇 번 불렀는지(서비스 지도)를 시계열로 본다.

성능은 측정하지 않았다. 구조상 앱이 하는 일은 메트릭 창구 대답, trace 큐에 넣기, 원래 쓰던 로그뿐이다. 이번엔 모든 요청을 trace로 남겼지만(샘플링 1.0) Spring 기본은 0.1이다.

## 무엇이 판단을 갈랐나

| 가설 | 예상 | 실제 | 판정 |
|---|---|---|---|
| 1. PG가 아직 처리 중 | PG 조회 PENDING | PG 조회 SUCCESS 3/3 | 기각 |
| 2. PG 성공 응답을 잃음 | 로그 `result=UNKNOWN cause=READ_TIMEOUT`, 반영 실패 로그 없음 | 3/3, 반영 실패 0줄, PG 호출 span 3초 error | **지지** |
| 3. 성공 조회 뒤 내부 반영 실패 | 응답 받음(ACCEPTED), 반영 실패 로그 있음 | 0/3, 0줄 | 기각 |

DB만 보면 2와 3의 결과는 똑같다(UNKNOWN, 거래 키 없음, PG는 SUCCESS). 
3번은 응답을 받았지만 저장이 rollback되면서 흔적이 지워지기 때문이다. 둘을 가른 것은 **어디까지 응답을 받았나**를 남긴 로그였다. rollback이 돼도 로그는 남는다.

복구는 결제를 다시 만들지 않고, 같은 3건을 PG에 조회해서 반영했다. 복구 요청 → PG 조회 → Outbox → Kafka → 구매 활동이 trace 하나로 이어지는 것도 확인했다. 결과: PG 생성 호출 추가 0, 재고 그대로, 랭킹 점수 20.

## AI에게 같은 화면을 줘 봤다

읽기 전용 Grafana MCP만 주고 가설 3개를 판정하게 했다. 3분 동안 질의 23개로 메트릭·로그·trace를 넓게 훑었고, 결론도 맞았다.

그런데 가설 1을 기각한 근거가 우리가 만든 테스트 PG의 로그였다. 
그 로그에는 "응답 유실 목록 = 12, 15, 18"이라고 정답이 적혀 있다. 운영에서는 PG 내부 로그를 볼 수 없으니, 확정으로 말하기에는 위험해보였다.

**결론이 맞아도 근거가 틀릴 수 있다.** AI는 넓게 빨리 볼 수 있지만 책임자는 아니다. 사람은 근거와 결론을 모두 확인해야 하고, 그러려면 "이 근거가 운영에서도 있나"를 알 만큼 인프라와 백엔드를 알아야 한다.
