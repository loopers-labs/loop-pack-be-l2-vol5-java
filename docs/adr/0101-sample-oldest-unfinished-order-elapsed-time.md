# ADR 0101. 결제를 시작한 뒤 끝나지 않은 주문 중 가장 오래된 주문의 경과 시간을 gauge로 제공한다

Status: Accepted

Extends: [ADR 0100](0100-sample-unknown-payment-attempt-count.md) (UNKNOWN 결제 시도 수 gauge)

## 결정과 근거

UNKNOWN gauge는 생성 응답을 받지 못한 결제만 센다. 정상 주문이 계속 들어오는 중에 멈춘 주문 세 건(생성 응답 저장 실패로 `REQUESTED`, PG가 끝내지 않은 `PENDING`, 주문 반영(TX C)만 실패해 결제 시도 `SUCCESS`)을 섞었을 때 UNKNOWN gauge는 내내 0이었다. 결제 시도 상태(`REQUESTED`·`PENDING`·`UNKNOWN`)로 세면 앞의 두 건만 보였고, 주문 `PAYMENT_PENDING`으로 세면 세 건이 모두 보였다. 건수는 정상 흐름에서도 22건이라 22건과 24·25건의 차이로는 가르기 어려웠다. 결제를 시작한 뒤의 경과 시간은 정상 주문이 2.2초를 넘지 않는 동안 멈춘 주문만 계속 늘어나 구분됐다. [10주차 실험](../week10/implementation-log.md#k-멈춘-주문을-결제-시도-기준과-주문-기준으로-세어-비교) `PaymentStuckSignalExperimentTest`

commerce-api에서 `commerce.payment.orders.unfinished.oldest` gauge(단위 초)를 등록한다. 주문이 `PAYMENT_PENDING`인 결제 시도 중 생성 시각이 가장 이른 것을 찾아, 그 시각부터 집계한 순간까지의 경과 시간을 저장한다. 해당 주문이 없으면 0이다. 출발점은 주문 생성이 아니라 결제 시도 생성(결제 시작)이다. 주문을 만들어 두고 나중에 결제한 정상 주문이 오래된 것처럼 보이지 않게 하기 위해서다. 주문 ID는 label에 넣지 않는다. 어느 주문인지는 runbook의 주문 기준 DB 질의로 찾는다.

집계는 UNKNOWN gauge와 같은 규칙이다. 기본 5초(`commerce.payment.unfinished-order.refresh-delay`)마다 다시 읽고, 첫 집계 전과 조회 실패 뒤에는 `NaN`을 내며, 실패는 WARN 한 줄(`미완료 주문 결제 시작 시각 집계 실패: error=<예외 이름>`)로 남긴다. 결제 시도 생성 시각이 시스템 시계로 저장되므로 경과 시간도 시스템 시계로 잰다. 같은 DB를 보는 인스턴스는 같은 값을 내므로 대시보드는 `max()`로 모은다.

## 대안과 영향

- **결제 시도 상태로 세기**: TX C만 실패한 주문은 결제 시도가 `SUCCESS`라 빠진다. 실험의 53번이 그랬다.
- **상태별 건수**: 정상 흐름의 처리 중 주문과 섞여 구분이 약했다.
- **시작 시각만 저장하고 읽을 때마다 경과 시간을 계산**: 처음 구현이었다. 이미 끝난 주문의 시작 시각이 다음 집계까지 계속 늙어, 정상 흐름(DB에서 센 최대 2.2초)이 2.6~6.6초로 보였다. 이 값을 알림 기준으로 쓰면 정상 흐름에서 오탐이 난다.

집계 순간의 값을 저장하므로 멈춘 주문은 최대 집계 주기만큼 늦게 보인다. 실험에서 실제 9.0초일 때 gauge는 4.891초였다. 주문 기준이라 정상 주문도 TX B가 결과를 저장한 뒤 TX C가 끝나기 전까지 잠깐 포함된다(실험의 정상 최대: 결제 시도 기준 2,186ms, 주문 기준 2,268ms). 주문이 이미 `PAYMENT_FAILED`로 끝난 뒤 PG 거래가 `SUCCESS`로 바뀌는 경우는 이 값에 나타나지 않는다. `orders.status`에 인덱스가 없어 주문이 많아지면 집계마다 주문 테이블을 훑는다.

몇 초부터 사람에게 넘길지와 알림 기준은 정하지 않았다. 실험의 2.2초는 PG가 2초 뒤 결과를 확정한다고 가정한 로컬 조건의 관찰값이라 운영 기준으로 옮길 수 없다.
