# ADR 0026: 좋아요순·인기순 원본은 DB가 정렬해 한 페이지의 ID만 읽는다

Status: Accepted
Supplements: [ADR 0020](0020-like-count-denormalized-counter.md), [ADR 0025](0025-popular-page-snapshot-with-ttl.md)

## 배경

likes_desc와 popular의 원본(인기순 캐시가 없거나 miss일 때)은 브랜드의 활성 상품을 모두 엔티티로 읽고, 그 상품들의 카운터를 IN으로 조회해 앱에서 정렬한 뒤 20개를 잘랐다. 앱 메모리와 시간이 브랜드 상품 수 × 동시 요청 수로 커지는 구조다.

브랜드 7을 87,390개로 키운 측정에서 캐시 없는 동시 20 요청은 300개 중 271개가 실패했다. 인기순 키가 비는 순간의 동시 20 요청도 200개 중 175개가 실패했다. 실패는 앱의 `OutOfMemoryError: Java heap space`(힙 512MB)였고, 이후 키가 찬 요청까지 실패하거나 앱이 종료됐다. 캐시가 평소 응답을 지켜도 만료 순간 원본이 앱을 무너뜨렸다([implementation-log 35절](../week4/implementation-log.md#popular-cache-growth-stampede)).

## 결정

- DB가 활성 상품·활성 브랜드를 `좋아요 수 DESC → 생성 시각 DESC → ID DESC`로 정렬하고 `LIMIT/OFFSET`으로 한 페이지의 상품 ID만 돌려준다. 앱은 그 ID의 상품과 좋아요 수만 읽어 기존 응답을 만든다.
- 정렬 기준이 like 도메인의 `product_like_count`에 있어 상품 저장소의 SQL에서만 조인한다. 도메인 코드는 좋아요 도메인을 참조하지 않는다.
- 이 SQL은 JPA native query로 실행한다. 같은 쓰기 트랜잭션에서 앞서 바꾼 상품(예: 삭제)이 아직 flush되지 않았더라도, 조회 전에 반영되어 순위가 그 변경을 본다.
- 인기순 캐시(60초 ID 재사용, hit 검사, 저장 시점)와 API 요청·응답은 바꾸지 않는다.

## 기존 결과와 같게 지킨 것과 달라진 것

- 동점 규칙은 이전 앱 비교기와 같다. 삭제 브랜드는 SQL에서 걸러 브랜드 없는 목록의 페이지가 덜 차지 않게 했다. 같은 읽기 트랜잭션의 스냅샷에서 ID와 상품을 읽는다.
- 카운터는 `LEFT JOIN`하고 정렬에는 0으로 둔다. ADR 0020의 "누락 카운터를 0으로 감추지 않는다"는 반환된 페이지에서 기존 좋아요 수 조회의 예외로 지킨다. 이전에는 후보 전체 중 하나라도 누락되면 예외였으므로, 반환 페이지 밖의 누락은 더 이상 목록 조회에서 드러나지 않는다.

## 비용과 남은 것

- 원본 SELECT가 하나 늘었다(정렬된 ID 페이지 + 그 상품 조회). DB는 여전히 브랜드의 활성 상품과 카운터를 모두 읽고 정렬한다. 앱이 하던 정렬을 DB가 맡은 것이다.
- 측정에서 쏠림 데이터의 원본 DB 시간은 약 182ms → 84ms, API는 약 540ms → 99ms, 정상 데이터는 DB 약 4.6ms → 2.3ms였다. 쏠림 데이터의 동시 20 요청은 캐시 없음·cold·warm 모두 실패 0이었다. 실패는 없어졌지만 캐시 없음·키가 빈 순간의 동시 20 요청 p50은 약 1초였다. 허용 응답 시간은 정하지 않았으므로 만료 순간 지연은 남은 것으로 본다. ([implementation-log 36절](../week4/implementation-log.md#likes-db-sorted-page)).
- 만료 순간의 중복 계산(ADR 0025 한계 3)은 없어지지 않았다. 계산이 긴 쏠림 데이터의 cold 20에서는 모든 요청이 각자 계산했다. 같은 키의 계산을 하나로 합치는 처리와 만료 전 갱신은 이번 범위에 넣지 않는다.

## 검토한 대안

| 대안 | 택하지 않은 이유 |
| --- | --- |
| 앱 힙을 늘린다 | 실패가 시작되는 동시 수가 뒤로 밀릴 뿐이고, 상품이 늘면 다시 같은 문제가 생긴다. 지금까지의 측정과 비교도 깨진다 |
| 같은 키의 계산을 하나로 합친다(single-flight) | 인기순 캐시의 miss만 보호하고, 캐시가 없는 likes_desc와 다른 키의 동시 계산은 그대로 앱 메모리를 쓴다. 이 변경 뒤의 후속 후보로 남긴다 |
| 카운터에 브랜드·삭제 여부·생성 시각을 복사하고 정렬 인덱스를 둔다 | 20행에서 멈출 수 있지만 같은 사실을 두 테이블이 들고, 상품 등록·삭제·브랜드 삭제가 카운터도 고쳐야 한다. likes_desc 속도가 실제 요구가 될 때 다시 본다 |
| 상품 테이블에 좋아요 수를 둔다 | ADR 0020에서 상품 행 잠금 경합 때문에 택하지 않았다 |

## 검증

새 통합 테스트로 같은 쓰기 트랜잭션에서 삭제한 상품이 순위에서 빠지는지, 동점 규칙과 페이지, 삭제 브랜드·삭제 상품을 거른 뒤의 페이지 채움, 반환 페이지의 카운터 누락 예외를 확인했다. 기존 likes_desc·인기순 테스트의 기대값은 바꾸지 않았다. `:apps:commerce-api:check` 338건과 Checkstyle·ArchUnit이 통과했다.
