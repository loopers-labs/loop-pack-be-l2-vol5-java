# ADR 0068: 쿠폰 발급 대상은 DB 앞의 Redis에서 먼저 판단한다

Status: Superseded
Superseded by: [ADR 0074](0074-confirm-coupon-reservations-after-db-outcome.md) (Redis 앞단 판단·도입 근거는 유지. 사용자 예약 표현·결과 불명 보상 정책은 후속 결정으로 대체. 본문은 당시 기록으로 보존)
Extends: [ADR 0067](0067-issue-coupon-with-conditional-update-in-db.md)
Related: [8주차 설계](../week8/design.md), [8주차 실험](../week8/experiments.md)

## Context

1단계(요청 → DB)는 정합성을 지켰지만, 600/s에서 보낸 발급 요청 18,478건 중 18,007건이 DB에서 조건부 UPDATE를 실행했다. 매진 뒤 요청(13,184건)도 결과가 정해졌는데 DB 연결과 캠페인 행 잠금을 거쳤고, 같은 연결 풀·톰캣 스레드를 쓰는 상품 조회가 p95 5.5초까지 느려졌다.

요구사항: 받음/매진은 누르는 순간 알려 준다. 발급된 쿠폰은 잠깐 뒤 쿠폰함에서 확인해도 된다.

결과가 정해진 요청을 DB 전에 걸러 내는 후보로 로컬 품절 표시(매진 뒤만 막음), Redis 발급 대상 체크(매진 전 초과분까지 막음), 대기열(누르는 순간에는 "접수됨"만 줄 수 있음), 서버별 수량 분배, 응모 후 추첨(선착순이 아님)을 비교했다.

## Decision

**판단 정보**

- 캠페인마다 Redis에 판단 정보(hash: 남은 수 `remaining`, 종료 시각 `endAt`)와 통과한 사용자(set)를 둔다. 키는 `coupon-issue:{캠페인 ID}:stock`, `coupon-issue:{캠페인 ID}:users`.
- Lua 스크립트 하나로 판단과 기록을 한 번에 한다. 순서: 판단 정보 없음 → 준비 안 됨, 통과한 사용자 → 이미 통과, 종료 시각 지남 → 종료, 남은 수 0 → 매진, 그 외 → 남은 수 −1·사용자 추가·통과.
- 판단은 복제 지연이 없도록 master에만 보낸다(`redisTemplateMaster`). 명령 응답 대기는 200ms다.

**응답**

| 판단 | 응답 | DB |
| --- | --- | --- |
| 통과 | DB 발급 결과(201 등) | 발급 TX |
| 이미 통과 + DB에 쿠폰 있음 | 200, 기존 쿠폰 | 조회 1번 |
| 이미 통과 + DB에 쿠폰 없음 | 409 "같은 쿠폰 발급이 처리 중입니다" | 조회 1번 |
| 매진·종료 | 409 | 가지 않음 |
| 준비 안 됨 | 503(없는 캠페인이면 404) | 캠페인 조회 1번 |
| Redis 응답 없음·오류 | 503 | 가지 않음 |

**DB 결과에 맞춰 되돌리기**

판단과 DB는 한 TX로 묶이지 않는다. 판단은 "이 사용자가 한 장 받을 것"을 미리 적어 두고, DB가 다르게 끝나면 되돌린다.

| DB 결과 | 남은 수 | 통과한 사용자 |
| --- | --- | --- |
| 201 새로 발급 | 그대로 | 그대로 |
| 200 이미 있던 쿠폰 | +1 | 그대로 |
| 거절(409·404)·오류·결과 모름 | +1 | 제거 |

결과를 모르면 되돌린다. 실제로 발급됐더라도 DB 조건부 UPDATE·유일 제약이 다음 요청을 막는다(되돌림이 지나치면 DB 요청이 하나 늘 뿐이다). 되돌리지 않으면 쿠폰이 남는데도 아무도 받지 못한다. 되돌리기 Lua는 사용자를 실제로 뺐을 때만 남은 수를 올려 두 번 불려도 한 번만 반영한다.

**준비와 보존**

- 캠페인에 종료 시각(`end_at`)을 둔다. DB 조건부 UPDATE에도 `end_at > 지금` 조건을 더한다.
- 관리자가 행사 시작 전에 `POST /api-admin/v1/coupon-campaigns/{campaignId}/issue-gate`로 판단 정보를 DB 기준(남은 수 = 총 한도 − 발급 수, 이미 발급된 사용자)으로 채운다. 기존 정보는 지운다. 비활성·종료된 캠페인은 409로 거절한다.
- 판단 정보는 종료 시각 + 1시간에 Redis가 지운다(PEXPIREAT, Redis 서버 시각 기준).
- 판단 정보가 사라졌거나 되돌리기가 실패하면 관리자가 준비를 다시 불러 DB 기준으로 맞춘다. 발급 요청이 처리되는 중에 부르면 그 사이 발급이 빠질 수 있으므로 발급이 없을 때 부른다.

**마지막 방어선**: ADR 0067의 조건부 UPDATE와 유일 제약은 그대로 둔다. Redis 값이 틀려도 한도 초과·중복 발급은 DB가 막는다.

## Alternatives and costs

| 대안 | 판단 |
| --- | --- |
| 로컬 품절 표시 | 새 부품 없이 매진 뒤 요청을 막는다. 매진 전 남은 수보다 많이 몰린 요청은 그대로 DB로 간다. 채택하지 않음 |
| 대기열·Kafka만 | 처리하는 쪽이 하나라 메모리에서 세도 안전하다. 누르는 순간에는 "접수됨"만 줄 수 있어 요구사항과 맞지 않는다. 채택하지 않음 |
| 서버별 수량 분배 | 새 부품이 없다. 한 서버에 몰리면 그 서버만 먼저 매진되고 남은 수량을 다시 나눠야 한다. 지금 실험은 서버 1대다. 채택하지 않음 |
| 응모 후 추첨 | 한도 경쟁이 사라지지만 선착순이 아니다. 채택하지 않음 |
| Redis 장애 시 DB로 보내기 | 몰릴 때 1단계처럼 DB와 다른 기능이 같이 느려진다. 채택하지 않음 |
| 따닥 뒤 요청: 잠깐 기다렸다 다시 조회 | 200 계약을 지키지만 기다리는 동안 스레드를 잡는다. 채택하지 않음 |
| 따닥 뒤 요청: DB로 보내 유일 제약이 정리 | 200 계약을 지키지만 앞 요청이 지면 남은 수가 실제보다 1 많아진다. 채택하지 않음 |
| 따닥 뒤 요청: 409 "처리 중" | 아직 끝나지 않은 같은 요청이라는 사실을 그대로 알린다. 채택 |
| TTL: 준비 때 고정 1일·TTL 없음 | 모델을 늘리지 않지만 행사 기간과 무관하다. 수업 메모의 "종료 시각 + α"를 따랐다 |

비용:

- Redis가 하나의 부품으로 늘고, 판단 정보와 DB가 어긋날 수 있다. 어긋남은 안전한 쪽(남은 수가 실제보다 많음)이면 DB가 막고, 위험한 쪽(남은 수가 실제보다 적음)이면 준비를 다시 해야 한다.
- 따닥의 뒤 요청은 과제 계약의 200 대신 409(처리 중)를 받는다. 앞 요청이 끝난 뒤 다시 누르면 200이다.
- 앞 요청이 DB에서 실패했는데 되돌리기도 실패하면, 그 사용자는 준비를 다시 할 때까지 "처리 중"을 받는다.
- Redis는 비활성 전환을 모른다. 비활성 캠페인 요청은 DB까지 가서 거절된다.
- 시작 시각은 두지 않았다. 시작은 준비 API 호출로 정한다.

## 검증

- `RedisCouponIssueGateTest`(실제 Redis): 남은 수만큼만 통과, 이미 통과한 사용자가 종료·매진보다 먼저 판단됨, 준비 전 판단·되돌리기가 상태를 만들지 않음, 되돌리기가 한 번만 반영됨, 준비가 상태를 교체하고 만료를 걺(2,500명), 100명 동시에 10자리면 정확히 10명 통과.
- `CouponIssueIntegrationTest`(실제 Redis·MySQL): 매진·종료는 DB에 가지 않음, 20명이 5장 경쟁하면 DB 조건부 UPDATE 5번, 따닥 8번이면 한 장과 200·409(처리 중)만, DB 거절·저장 실패 시 통과를 되돌림, Redis가 틀려도 DB가 한도를 지킴, Redis 장애면 503이고 DB에 가지 않으며 보유 목록은 조회됨, 준비가 DB의 남은 수·발급된 사용자를 옮김.
- `CouponApiIntegrationTest`: 준비 전 503, 관리자 헤더 없으면 403, 준비 뒤 201.
- 부하 실험 결과는 [실험 기록](../week8/experiments.md) 2단계.
