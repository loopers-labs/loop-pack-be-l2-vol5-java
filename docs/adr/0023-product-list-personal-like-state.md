# ADR 0023: 목록의 개인별 좋아요 여부는 DB에서 합성한다

Status: Accepted
Date: 2026-10-16

## 결정과 이유

사용자가 상품 목록에서 자신이 좋아요한 상품의 하트 상태를 표시하도록 요청했다. 목록 항목에 `isLiked`를 추가한다. 공통 상품 페이지는 여러 사용자가 함께 재사용하므로 개인별 여부를 캐시에 넣지 않는다.

- 목록의 `X-USER-ID`는 선택 헤더다. 없으면 기존 공개 목록 조회를 유지하며 `isLiked=false`를 반환한다.
- 헤더가 있으면 기존 UserService로 활성 사용자를 확인한다. 없거나 삭제된 사용자는 기존 규칙대로 NOT_FOUND, 숫자가 아닌 헤더는 BAD_REQUEST다.
- 공통 상품 페이지를 고른 뒤 그 페이지의 상품 ID와 현재 사용자 ID로 product_like를 한 번에 조회한다. 상품별 반복 조회나 사용자의 전체 좋아요 목록 조회는 하지 않는다. 빈 페이지에서는 관계 조회를 생략한다.
- ProductListQueryService가 공통 조회·사용자 확인·개인별 관계 조회를 조정하고 목록 전용 응답에 합친다. 상세·내 좋아요 목록의 기존 응답은 이번 범위에서 바꾸지 않는다.
- 좋아요 등록/취소 commit이 완료된 뒤 시작한 새 목록 요청에서 isLiked와 현재 likeCount를 확인한다. 변경과 겹쳐 이미 시작한 조회의 트랜잭션 snapshot까지 최신이라고 주장하지 않는다.
- 좋아요 변경은 공통 가격순 캐시를 지우지 않는다. 캐시 값·키·TTL·삭제 보호는 ADR 0021을 따른다. 총상품수는 제공하지 않는다.

## 검증과 비용

사용자 A/B가 같은 Redis/로컬 캐시를 재사용해도 서로 다른 하트 상태를 받고, 등록/중복 등록/취소/rollback 뒤 새 조회에 올바르게 반영되는지 확인했다. 페이지 경계·세 정렬·비로그인·없는/삭제된 사용자·잘못된 헤더·관계 조회 오류도 검증했다. 가격순 개인화 단계의 전체 310건·Checkstyle·ArchUnit이 통과했다([검사 집계](../week4/measurements/price-cache-personal-validation.json)).

로그인 목록에는 사용자 확인과 페이지별 관계 SELECT가 추가된다. 10만 건·브랜드 7·가격순 첫 20개를 실제 API로 조회한 대표 SQL은 로그인 5개, 헤더 없음 3개였다. 개인 관계 조회는 기존 `(user_id, product_id)` 유니크 인덱스를 사용했다. 이 수를 빈 페이지·다른 모든 조회의 SQL 수로 일반화하지 않는다. 익명 목록과 로그인 목록의 지연을 구분하고 이전 공통 조회 측정을 새 개인화 경로의 성능으로 취급하지 않는다.
