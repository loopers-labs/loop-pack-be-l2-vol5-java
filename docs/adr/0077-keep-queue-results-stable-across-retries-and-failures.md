# ADR 0077: 작업 큐는 접수한 작업을 잃지 않고, 재처리에서 확정한 결과를 뒤집지 않는다

Status: Accepted
Extended by: [ADR 0078](0078-remember-final-closure-in-app-memory.md) (저장 전 예약 수를 세어, 확정 취소로 자리가 돌아올 수 없는 매진만 서버 메모리에 기억한다)
Extends: [ADR 0076](0076-accept-coupon-issue-into-redis-stream-and-save-by-worker.md) (작업 큐 모드의 만료·재처리·실패 격리 정책을 보강한다)
Related: [8주차 설계](../week8/design.md), [구현 기록](../week8/implementation-log.md)

## Context

ADR 0076의 작업 큐를 검토하며 다음을 확인했다. 코드 경로를 따라간 정적 검토이며 장애를 주입해 재현한 결과는 아니다.

- 작업 큐에 판단 정보와 같은 만료(종료 + 1시간)를 걸어, DB나 Worker가 오래 멈추면 접수한 작업이 처리 전에 사라질 수 있었다.
- 접수 Lua가 큐 키의 상태를 쓰기 전에 확인하지 않았다. 큐가 잘못된 타입이면 차감·사용자 기록 뒤 등록에서 실패해 작업 없는 예약이 남는다. Lua는 끼어들기를 막을 뿐 중간 오류를 rollback하지 않는다.
- 재처리가 이미 기록한 취소를 보지 않아, 취소 뒤 조건이 바뀌면 다시 발급할 수 있었다.
- 재처리가 사용자 확인을 기존 쿠폰보다 먼저 해, 저장 뒤 사용자가 사라지면 이미 발급한 쿠폰의 수량을 돌려줄 수 있었다. 작업 동일성을 발급 시각으로만 판단했다.
- 처리 완료 전 작업을 먼저 읽어, 계속 실패하는 작업 하나가 새 작업을 막았다. 실패 뒤 50ms마다 다시 시도했다.

## Decision

- **작업 큐에는 만료를 걸지 않는다.** 접수가 끝났고(종료 시각 지남) 아직 안 읽은 작업·처리 완료 전 작업·보류 작업이 모두 없을 때 Worker가 판단 정보와 큐를 함께 지운다. QUEUE의 판단 정보 보존은 종료 뒤 7일이다(`commerce.coupon.issue-queue.retention-after-end`).
- **접수 Lua는 모든 키의 상태를 쓰기 전에 확인한다.** 큐가 없으면 준비 안 됨(503), 다른 타입이면 오류이며 둘 다 아무것도 쓰지 않는다. 준비는 처리 목록 등록 → 큐 생성 순서로 해, 큐가 생겼는데 Worker가 모르는 상태를 만들지 않는다.
- **재처리는 취소 기록 → 기존 쿠폰 → 사용자 순서로 확인한다.** 한 번 확정해 기록한 결과(취소·발급)는 지금 조건으로 다시 판단하지 않는다.
- **작업 동일성은 예약 값으로 판단한다.** 쿠폰에 그 쿠폰을 만든 접수의 예약 값(`reservation_id`)을 저장하고, 기존 쿠폰의 예약 값이 이 작업과 같으면 이 작업이 만든 쿠폰으로 본다.
- **확정 취소는 사용자 기록을 C로 남긴다.** 같은 캠페인에 다시 신청하면 409다. 이것은 정책이며, 재신청을 받으려면 접수마다 결과를 구분해야 한다.
- **연결 장애와 작업 하나의 실패를 나눈다.** DB·Redis 연결·시간 초과는 처리 완료하지 않고 Worker 전체가 쉰다. 쉬는 시간은 100ms에서 두 배씩 늘려 최대 30초다. 그 밖의 실패가 한 작업에서 5번(`max-attempts`) 쌓이면 보류함(`coupon-issue:{campaignId}:held`)으로 옮기고 처리 완료로 표시해 뒤 작업을 막지 않는다. 보류된 사람의 예약은 지우지 않으며 상태는 처리 중이다. 보류함은 수동 확인 대상이다.
- 예약 확정이 맞지 않으면(판단 정보 유실·예약 변경) DB 결과는 그대로 두고 로그로 남긴다.

## Alternatives

| 대안 | 판단 |
| --- | --- |
| 처리 기한을 두고 넘기면 최종 취소 | 사라지지는 않지만 "종료 전 접수는 발급" 약속을 못 지키는 경우가 생긴다. 채택하지 않음 |
| 취소 뒤 재신청 허용 | 한 사람의 결과를 (캠페인, 사용자) 하나로 기록하는 지금 구조와 맞지 않는다. 매진·종료 취소는 받아도 다시 거절되고, 없는 사용자는 로그인을 쓰는 실제 서비스에서는 드물다. 채택하지 않음 |
| 실패한 작업이 끝날 때까지 뒤를 멈춤 | 저장 순서는 지키지만 작업 하나가 전체를 멈춘다. 받을 사람은 접수 때 정해져 저장 순서가 공정성과 무관하다. 채택하지 않음 |

## Consequences

- Redis 자체가 데이터를 잃는 경우(재시작·failover, AOF everysec)는 이 결정으로 막지 못한다. 감수 범위는 정하지 않았다.
- 판단 정보는 종료 뒤 7일에 만료된다. 그보다 오래 남은 작업은 처리되지만 상태 조회가 처리 중을 보여 주지 못한다.
- 보류함을 비우는 절차(원인 확인 뒤 다시 넣기·취소)는 만들지 않았다. 보류함이 비기 전에는 큐를 정리하지 않는다.
- 실패 횟수는 Worker 메모리에 있어 재시작하면 다시 센다.

## 검증

- `CouponQueueFailureBoundaryIntegrationTest` 9개: 큐에 만료 없음, 종료 뒤에도 남은 작업이 처리될 때까지 큐 유지·처리 뒤 정리, 큐가 없으면 쓰지 않고 503(다시 눌러도 처리 중이라 하지 않음), 큐 타입이 다르면 쓰기 전에 실패, 취소 기록 뒤 조건이 바뀌어도 재처리에서 취소 유지, 취소된 사람의 재신청 409, 저장 뒤 사용자가 사라져도 재처리에서 환불하지 않음, 계속 실패하는 작업 보류·뒤 작업 처리, 연결 장애는 보류하지 않고 복구 뒤 처리.
