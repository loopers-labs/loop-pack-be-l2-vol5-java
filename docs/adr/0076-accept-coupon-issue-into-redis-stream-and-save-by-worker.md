# ADR 0076: 작업 큐 모드 — Redis 판단과 함께 Stream에 등록하고 202로 답한 뒤 Worker가 저장한다

Status: Accepted
Extended by: [ADR 0077](0077-keep-queue-results-stable-across-retries-and-failures.md) (큐 만료 제거, 재처리 확인 순서·예약 값 동일성, 확정 취소 C, 연결 장애 backoff·실패 작업 보류)
Extends: [ADR 0075](0075-judge-in-redis-before-any-db-lookup.md) (Redis 판단을 먼저 하는 흐름에, 판단 뒤 DB 저장을 요청 밖으로 옮기는 모드를 더한다. REDIS_SYNC는 그대로 둔다)
Related: [ADR 0074](0074-confirm-coupon-reservations-after-db-outcome.md), [8주차 설계](../week8/design.md), [8주차 실험](../week8/experiments.md), [구현 기록](../week8/implementation-log.md)

## Context

REDIS_SYNC에서 Redis를 통과한 요청은 DB 저장이 끝날 때까지 톰캣 스레드·커넥션을 쥐고 같은 캠페인 행 앞에서 기다렸다. 그래서 상품 조회도 수 초씩 느려졌다. DB 앞에서 들어가는 수를 묶어 봤더니(분산락·세마포어), 기다리게 하면 톰캣 스레드가 묶였고 바로 거절하면 쿠폰이 남았는데도 먼저 온 사람이 떨어졌다. DB는 어떤 방식이든 한 줄씩이므로, 바꿀 수 있는 것은 그 줄을 누가 서느냐였다.

## Decision

`commerce.coupon.issue-mode=QUEUE`를 둔다. 기본값은 REDIS_SYNC로 두고, QUEUE는 같은 조건에서 비교하는 경로로 쓴다.

```text
요청 → Redis Lua 한 번: 중복 확인 + 남은 수 차감 + 사용자 기록(R) + Stream 등록(XADD)
        통과 → 202 PENDING / 매진·종료 → 409 / 이미 통과 → 쿠폰이 있으면 200, 없으면 202 PENDING
Worker → 작업을 꺼냄 → 사용자 확인 → DB 발급 TX → 예약 확정 → 처리 완료(XACK)
상태 조회 GET .../issues/me → ISSUED / PENDING / CANCELLED / NONE
```

- **큐는 Redis Stream이다.** 판단과 등록을 같은 Lua에서 해 "차감은 됐는데 작업이 없는" 상태가 생기지 않는다. 소비자 그룹이 처리 완료 전 작업을 보관해, Worker가 꺼낸 뒤 멈춰도 다음 처리에서 다시 받는다.
- **선착순은 Redis가 받은 순서**다. 받을 사람은 접수 순간에 정해지고, 저장 순서는 받는 사람을 바꾸지 않는다.
- **202는 발급 완료가 아니라 접수다.** 결과는 상태 조회로 확인한다. 접수 ID 대신 (캠페인, 사용자)로 조회한다(1인 1매라 유일하다).
- **종료 직전에 접수한 요청은 종료 뒤에 처리돼도 발급한다.** Worker는 처리 시각이 아니라 접수 시각으로 종료를 판단하고 발급 시각으로 남긴다.
- **확정 거절은 취소, 일시 오류는 재시도.** 없는 사용자·DB 매진·비활성·없는 캠페인은 취소 기록(`coupon_issue_cancellation`)을 남기고 예약을 돌린 뒤 처리 완료한다. DB 오류·결과 불명·Redis 확정 실패는 처리 완료하지 않고 다시 처리한다. 돌아온 수량은 그 뒤에 온 요청이 가져간다.
- **재처리에서 수량을 잘못 돌려주지 않는다.** DB에 쿠폰이 이미 있을 때 그 발급 시각이 이 작업의 접수 시각과 같으면 이 작업의 앞선 시도가 만든 것으로 보고 확정만 한다. 다르면 접수 전부터 있던 쿠폰이라 이번 예약의 수량을 돌려준다.
- **Worker는 앱 안의 스케줄 스레드 하나다.** 한 번에 커넥션 하나만 써 상품 조회가 쓸 커넥션을 남긴다.

## Alternatives

| 대안 | 판단 |
| --- | --- |
| Redis List | 등록은 같은 Lua에서 되지만 꺼내는 순간 사라진다. 처리 중 목록·되찾기를 직접 만들어야 한다 |
| Redis Sorted Set | 순번 조회가 강점인데 작업 큐에는 필요 없다. 꺼내면 사라지는 문제는 List와 같다 |
| Kafka | 디스크에 남아 더 안전하지만 Redis 판단과 Kafka 등록이 두 곳에 나뉘어 틈이 생긴다 |
| 신청자 전부를 FIFO 큐에 넣고 Worker가 판단 | 매진 뒤 요청도 큐에 쌓이고, 받음·매진을 Worker 처리 뒤에야 안다 |
| 입장 대기실(순번 → 입장 → 발급) | 입장 뒤 할 일이 긴 곳에 맞는다. 쿠폰은 한 번 누르면 끝나고, 판단(Redis)은 이미 빠르다 |
| 별도 앱(commerce-streamer)의 Worker | 커넥션 풀이 완전히 나뉘지만 Redis 설정·발급 코드를 옮겨야 한다. 비교 실험에서는 앱 안 1개로 시작한다 |

## Consequences

- 과제의 동기 201 계약과 다르다. 클라이언트는 상태 조회나 쿠폰함으로 결과를 확인해야 한다.
- "받음"과 쿠폰함 반영 사이에 시간이 생긴다. Worker 1개의 저장 속도가 동기 경로보다 느려 실제 발급 완료는 늦어질 수 있다.
- 받을 사람 기록과 작업 큐가 모두 Redis에 있다. Redis 재시작·failover로 데이터를 잃으면 둘 다 잃는다. 감수 범위(AOF 설정 등)는 정하지 않았다.
- 앱을 여러 대 띄우면 Worker도 여러 개가 된다. 소비자 이름과 남의 처리 완료 전 작업 넘겨받기(XCLAIM)를 정해야 한다. 지금은 한 대 전제다.
- 준비 API는 작업 큐도 비운다. 발급 요청과 처리 중인 작업이 없을 때만 부른다.

## 검증

- `CouponQueueIssueIntegrationTest` 9개: 접수 뒤 Worker 저장·확정·처리 완료, 매진은 작업 없이 409, 처리 중 재요청은 작업 하나, 없는 사용자는 취소·수량 복구, DB 일시 오류는 재처리, 저장 뒤 확정 실패 재처리에서 수량을 돌려주지 않음, 접수 전부터 있던 쿠폰은 수량 복구, 종료 전 접수는 종료 뒤 처리돼도 발급, HTTP 202 → PENDING → ISSUED → 200.
- 부하 결과는 [실험 2-6](../week8/experiments.md)에 있다.
