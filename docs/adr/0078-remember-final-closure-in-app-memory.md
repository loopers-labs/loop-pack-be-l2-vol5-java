# ADR 0078: 다시 풀리지 않는 마감(최종 매진·종료)은 서버 메모리에 기억해 Redis에 보내지 않는다

Status: Accepted
Extends: [ADR 0075](0075-judge-in-redis-before-any-db-lookup.md) (Redis 판단 앞에 서버 메모리의 마감 확인을 더한다), [ADR 0077](0077-keep-queue-results-stable-across-retries-and-failures.md) (확정 취소로 자리가 돌아오는 정책을 유지한 채 캐시한다)
Related: [8주차 설계 8절](../week8/design.md), [구현 기록](../week8/implementation-log.md)

## Context

작업 큐 모드에서 매진 뒤 요청은 Redis Lua 한 번으로 409가 된다. 마지막 설계 측정(600/s·40초·5,000장, 1회)에서 매진 뒤 요청은 접수 요청의 79.2%(19,380건)였고 p95 2ms였다. 지금 부하에서는 아낄 것이 거의 없다.

확장을 가정하면 다르다. 서버를 늘려도 한 캠페인의 Redis 키는 해시 태그 때문에 한 노드에 있고, Redis는 명령을 한 줄로 실행한다. 매진 뒤 요청이 대부분이라면 그 노드에 가는 요청을 줄이는 것이 먼저다. 이 상한 값은 이 PC에서 재지 못했다(추정).

캐시의 어려움은 매진이 다시 풀릴 수 있다는 점이다. 남은 수가 0이어도 저장 전 예약이 남아 있으면 Worker의 확정 취소로 자리가 돌아온다.

## Decision

- Redis 판단 정보에 저장 전 예약 수(`pending`)를 둔다. 예약할 때 +1, 자기 예약이 확정·보상·확정 취소로 바뀔 때 -1, 준비 때 0이다.
- 남은 수 0이고 pending 0이면 판단은 `SOLD_OUT_FINAL`이다. pending이 남아 있으면 `SOLD_OUT`이다.
- `SOLD_OUT_FINAL`·`ENDED`를 받은 서버는 그 캠페인을 메모리에 10초 기억한다. 기억하는 동안 발급 신청은 Redis에 가지 않고 409로 답한다. 받은 사람인지 확인하지 않으므로 "이미 받으셨다면 쿠폰함에서 확인해 주세요"를 붙인다.
- 준비 API는 그 서버의 기억을 지운다. 다른 서버는 기억 시간 안에 다시 확인한다.

## Alternatives

| 대안 | 판단 |
| --- | --- |
| 남은 수 0을 짧게(예: 1초) 기억 | 단순하지만 그 시간 동안 돌아온 자리가 있어도 거절한다. 몰릴수록 잘못 거절되는 사람이 많다 |
| 자리를 돌려주지 않는다 | 매진이 다시 풀리지 않아 캐시가 단순해진다. 확정 취소 정책(ADR 0077)을 바꿔야 한다 |
| 받은 사람은 Redis·DB로 확인해 200 | 매진 뒤 요청마다 다시 저장소에 가 캐시의 목적이 사라진다 |
| 캐시 없음 | 600/s에서는 충분하다. 확장 가정에서 한 노드의 상한을 줄일 수단이 없다 |

## Consequences

- 이미 받은 사람이 마감 뒤 다시 누르면 200(쿠폰) 대신 안내가 붙은 409를 받는다.
- 저장 전 예약이 남아 있는 동안은 매진 요청이 Redis에 간다.
- 다른 서버가 재준비한 캠페인을 최대 10초 늦게 안다.
- 결과를 모르는 예약이 남으면(REDIS_SYNC 결과 불명) 재준비 전까지 최종 매진이 되지 않는다.
- Redis 요청 감소량은 부하로 재지 않았다.

## 검증

- `CouponClosedCampaignIntegrationTest`(QUEUE) 4개: 저장 전 예약이 남은 매진은 기억하지 않고 다음 신청도 Redis 판단, 예약이 모두 저장된 뒤 최종 매진은 기억하고 Redis 없이 안내 409(받은 사람 포함), 확정 취소로 돌아온 자리를 다음 신청자가 받음, 준비 API가 기억을 지움.
- `CouponClosedCampaignsTest` 3개: 기억 시간이 지나면 잊음, 즉시 잊기, 끄면 기억하지 않음.
