# ADR 0024: 좋아요순 첫 페이지는 상품 ID를 캐시하고 변경 commit 후 삭제한다

Status: Superseded by [ADR 0025](0025-popular-page-snapshot-with-ttl.md)
Date: 2026-10-16

이 문서는 첫 비교 구현의 기록이다. 현재는 `likes_desc`를 DB 조회로 유지하고, 좋아요마다 지우지 않는 별도 `popular` 순위를 사용한다. 아래 수치는 당시 빌드의 결과다.

## 범위와 결정

기존 `likes_desc`의 현재 좋아요 수 DESC·생성 시각 DESC·ID DESC와 정상 변경 완료 후 새 조회의 반영 규칙을 유지한다. 브랜드 필터·page=0·size=20만 Redis cache-aside로 비교한다. 시간대별 인기 점수나 일정 집계 시점의 스냅샷 순위로 바꾸지 않는다.

캐시 값은 정렬된 상품 ID 20개다. 상품 이름·가격·브랜드 표시·좋아요 수·개인별 isLiked는 저장하지 않는다. hit에서는 활성 상품을 읽고 기존 순서를 유지한 뒤 현재 좋아요 카운터와 개인별 표시를 합성한다. 누락/다른 브랜드 상품이 있으면 현재 DB의 전체 후보로 다시 고른다. 브랜드 유효성은 항상 DB로 확인한다. 총상품수는 구하지 않는다.

원본 경로는 브랜드의 활성 상품과 카운터를 읽어 기존 comparator로 전체를 정렬한 뒤 페이지를 고른다. 임의의 20개를 읽고 그 안에서 좋아요순으로 정렬하지 않는다. 먼저 원본 API의 기준선을 확인하고, 같은 응답의 DB-only/miss/hit을 비교한다.

## 변경과 실패

- 실제 좋아요 등록·취소, 상품 생성·삭제, 브랜드 삭제가 해당 브랜드 첫 페이지의 무효화 대상이다. 현재 페이지 밖 상품의 좋아요 변경도 순서에 영향을 줄 수 있다.
- 중복 등록·없는 취소는 관계와 카운터가 바뀌지 않으므로 무효화하지 않는다. 이름·가격·재고·브랜드 표시 변경은 ID 순서와 저장 값을 바꾸지 않는다. 현재 표시 정보는 DB에서 읽는다.
- 변경 트랜잭션 안에서 알림을 발행하고 commit 후 DEL한다. rollback은 DEL하지 않는다. 미확정 쓰기 트랜잭션 안의 조회는 캐시 읽기/저장을 우회한다.
- Redis GET/SET/DEL 실패는 DB 우회 또는 실패 기록으로 처리한다. 이미 commit된 DB 변경을 rollback됐다고 보고하지 않는다. DB 오류는 감추지 않는다.
- 정상 변경 후 새 순차 조회는 최신 순서를 반환한다. DEL 실패·늦은 채움에서는 순서/멤버 구성이 일시적으로 오래될 수 있다. 표시 정보·좋아요 수·isLiked는 DB에서 합성한다. 삭제 상품/브랜드와 다른 사용자 정보의 비노출은 유지한다.
- TTL은 저장부터 300초이며 hit로 연장하지 않는다. 실패 시 오래된 순위가 영구히 남는 것을 제한하는 출발값이다. 정상 좋아요 변경을 5분간 늦게 반영한다는 정책이 아니며, 변경 후 모든 요청에 적용되는 300초 상한도 주장하지 않는다.

## 비용과 후속 판단

원본의 전체 후보 조회·카운터 조회·Java 정렬을 hit에서 페이지 상품 조회로 줄이는 것이 비교 대상이다. hit도 DB를 사용하고, 실제 좋아요 변경마다 Redis DEL이 생긴다. 먼저 이 기본 방식의 정확성과 읽기·변경 비용을 확인한다. 빈번한 무효화를 피하려고 기존 최신성 계약을 임의로 완화하지 않는다.

실제 취소 여부를 repository/service에서 boolean으로 반환해 변경이 있을 때만 알림을 발행한다. HTTP 취소의 204 계약은 유지한다. 취소가 반영되면 같은 트랜잭션에서 상품의 브랜드 ID 확인 SELECT도 추가된다. 이 비용은 변경 API 시간에 포함하며 순수 DEL 시간과 구분한다.

local/benchmark에서 `commerce.cache.likes.enabled=true`로 학습 구현을 사용한다. 꺼진 모드는 읽기/저장과 commit 후 DEL을 함께 우회하므로 같은 DB를 공유하는 캐시 사용/비사용 쓰기 앱의 혼합 배포용 설정으로 사용하지 않는다.

로컬 캐시·Sorted Set·revision·주기적 순위 집계는 이번 첫 구현의 필수 범위에 포함하지 않는다. 특히 Sorted Set은 DB 변경 반영·실패 복구·동점 정렬을 별도로 설계해야 한다. 현재 조회의 필요성과 실제 변경 패턴을 근거로 후속 판단한다.

전체 326건·Checkstyle·ArchUnit이 통과했다. 같은 현재 JAR의 10만 건 복제 DB 비교에서 원본/miss는 상품/카운터 각 990행, hit는 각 20행이었다. 정상 로그인 요청의 SELECT는 모두 5개다. 읽기·실제 변경·동시 조회의 측정 GET 6,000개가 독립 기대값과 같았다. 변경이 잦을 때 재사용이 사라지는 비용도 함께 확인했다.
