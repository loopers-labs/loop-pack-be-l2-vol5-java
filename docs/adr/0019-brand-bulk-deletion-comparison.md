# ADR 0019: 브랜드 상품 삭제의 벌크 UPDATE 대안 비교

Status: Accepted
Date: 2026-10-09

## Context

현재는 브랜드를 잠근 뒤 대상 상품 ID를 구하고, ID 순서로 하나씩 잠금 조회하여 삭제한다([ADR 0016](0016-brand-deletion-locks-products-by-id.md)). 대상 행을 명확히 잠그지만 상품 수만큼 조회·UPDATE가 늘어난다.

재고에서는 `Stock.decrease()`의 판단을 유지하려고 비관적 락을 선택했다. 반면 현재 `ProductModel.markDeleted()`는 삭제 시각만 표시한다. 상품을 브랜드 조건으로 한 번에 삭제하면 기존 정책을 유지하면서 SQL을 줄일 수 있는지 비교했다. 빠르다는 이유만으로 채택하지 않고, 다른 브랜드의 요청을 막는지와 실패 시 원자성도 확인한다.

## Decision

**이번에는 벌크를 채택하지 않고 기존 ID별 잠금·삭제 방식을 유지한다.** 테스트에만 대안을 구성했고 실제 서비스는 ADR 0016을 유지한다. 격리 수준도 바꾸지 않았다.

| 대안 | 이점 | 비용 |
| --- | --- | --- |
| 현재 ID별 잠금 조회·엔티티 삭제 | 잠금 대상·순서를 명시하고 기존 모델 행동 유지 | 상품 수에 비례한 SQL |
| 브랜드 조건 벌크 UPDATE | 상품 삭제 SQL 한 문장 | 실행 계획에 따른 잠금 범위, JPA 변경 감지·콜백 우회 |

두 방식 모두 브랜드 삭제의 `FOR UPDATE`, 등록의 `FOR SHARE` 및 브랜드·상품을 함께 되돌리는 트랜잭션은 유지한다. 벌크도 UPDATE가 잠금을 얻으며 커밋·롤백까지 유지한다.

## Experiment

`BrandBulkDeletionExperimentTest`에서 현재 Facade와 테스트 전용 벌크 경로를 비교했다. 벌크 경로는 브랜드를 잠가 삭제 표시하고 flush한 뒤 다음 SQL을 실행한다. 상품 엔티티를 미리 읽거나 이후 다시 저장하지 않는다.

```sql
UPDATE product
SET deleted_at = UTC_TIMESTAMP(6), updated_at = UTC_TIMESTAMP(6)
WHERE brand_id = :brandId AND deleted_at IS NULL;
```

기존 삭제 시각을 보존하고, 벌크가 JPA 콜백을 거치지 않으므로 수정 시각도 직접 기록한다. 실제 채택 시에도 미리 적재한 상품 엔티티가 오래된 상태로 남거나 다시 저장되지 않도록 해야 한다.

### 처리 시간·SQL

로컬 JDK 21·MySQL Testcontainers에서 브랜드 두 개의 상품 ID를 교차 적재했다. 브랜드당 10·100·1,000개이며 대상 비율은 약 50%다. 기존 삭제 상품 한 개와 과거 확정 주문도 준비했다. 기존 `(brand_id, deleted_at)` 인덱스를 사용하며 강제 인덱스나 `ANALYZE TABLE`은 적용하지 않았다.

각 방식 준비 실행 1회 후 순서를 교대하여 3회 측정한 단독 실행 결과다. 데이터 준비·검증은 제외하고 트랜잭션 시작부터 커밋까지 측정했다. 정확한 잠금 보유 시간이나 운영 부하 성능을 측정한 것은 아니다.

| 브랜드당 상품 수 | 현재 중앙값(ms) | 벌크 중앙값(ms) | 현재 SQL 준비 횟수 | 벌크 SQL 준비 횟수 |
| --- | ---: | ---: | ---: | ---: |
| 10 | 44.699 | 9.245 | 23 | 3 |
| 100 | 209.049 | 7.529 | 203 | 3 |
| 1,000 | 1,551.608 | 26.810 | 2,003 | 3 |

횟수는 Hibernate `prepareStatementCount`이며 네트워크 왕복 수와 동일하다고 주장하지 않는다. 작은 표본의 비교 관찰이며 성능 임계값으로 테스트를 통과시키지 않는다.

### 잠금 범위·롤백

실제 연결의 격리 수준은 `REPEATABLE-READ`였다. 삭제 트랜잭션을 커밋하기 전에 별도 연결에서 대상 상품 및 이웃한 다른 브랜드 상품 한 행에 `FOR UPDATE NOWAIT`를 실행했다.

| 조건 | 현재 방식 | 벌크 방식 |
| --- | --- | --- |
| 10개·1,000개에서 삭제 대상 상품 잠금 | 충돌 | 충돌 |
| 같은 조건에서 다른 브랜드의 기존 상품 잠금 | 가능 | 충돌 |
| 커밋 후 두 상품 잠금 | 가능 | 가능 |
| 실제 브랜드·상품 SQL 실행 후 예외 | 전체 롤백 | 전체 롤백 |

해당 데이터의 벌크 `EXPLAIN`은 후보 인덱스가 있어도 `key=PRIMARY`, `type=index`, `Using where`였다. 이번 조건에서는 다른 브랜드 행까지 영향을 줬다. 다른 브랜드 전체가 잠겼다거나 벌크가 항상 같은 계획을 고른다는 증거는 아니다. 일반 SELECT 차단을 검사한 것도 아니다.

성공·실패 후 별도 JDBC 조회로 기존 삭제 시각, 재고·가격 등 상품 값, 다른 브랜드, 과거 주문·품목 보존도 확인했다. 재고 0인 상품도 삭제 대상에 포함했다.

## Follow-up

벌크의 성능 이점은 확인했지만 이번에는 기존 방식의 명시적인 대상·잠금 순서를 선택했다. SQL이 늘어나는 비용은 감수한다. 실제 삭제 지연이 문제로 관측되거나 데이터 규모가 커지면 실행 계획과 다른 요청의 지연을 함께 측정해 재검토한다. 벌크가 항상 다른 브랜드를 막거나 운영에서 더 느리다는 결론은 아니다.

## 브랜드 삭제 트랜잭션만 RC로 적용할 수 있다

RR에서 넓은 스캔이 다른 브랜드 기존 행까지 잠글 수 있는 현상을 갭 락만으로 설명하지 않는다. 스캔한 인덱스 레코드의 잠금과 범위·갭 잠금이 함께 관련된다. RC의 UPDATE는 조건 불일치 레코드의 잠금을 해제하며, 이미 잠긴 행의 조건 판단에는 semi-consistent read를 사용할 수 있다. 이는 불필요한 잠금 유지를 줄이는 성질이지 실행 계획·제약 검사·인덱스 변경과 무관하게 모든 대기나 교착이 없어진다는 보장은 아니다.

**애플리케이션 전체의 격리 수준을 바꿀 필요는 없다.** 서버·풀의 기본값을 유지하면서 브랜드 삭제 트랜잭션만 RC로 시작할 수 있다. 이 경우 변경 범위는 해당 트랜잭션이며, 전체 서비스의 일반 조회를 RC로 바꾸는 것이 아니다. 서버·풀 기본값 변경은 별도의 대안이다.

| 대안 | 적용 범위와 검토 사항 |
| --- | --- |
| RR·ID별 잠금 유지(현재) | 기존 구현을 유지한다. 상품 수에 비례하는 SQL 비용을 감수한다 |
| 브랜드 삭제만 RC·벌크 UPDATE | 삭제 유스케이스 안의 조회·변경과 다른 요청과의 경쟁을 검토한다. 다른 유스케이스의 기본 격리 수준은 유지할 수 있다 |
| 서버·풀 기본값을 RC로 변경 | 해당 기본값을 따르는 경로의 일반 조회 가정까지 넓게 검토한다 |

국소 적용은 새 트랜잭션을 시작하는 `BrandFacade.delete()`에 `@Transactional(isolation = Isolation.READ_COMMITTED)`를 지정하는 방식으로 검토할 수 있다. 다만 기존 트랜잭션에 `REQUIRED`로 참여하면 기본적으로 바깥 격리 수준을 따르므로, 내부 repository에 선언만 추가해서 바뀐다고 가정하지 않는다. 상품 벌크만 `REQUIRES_NEW`로 분리하면 독립 커밋되어 브랜드와 상품의 원자성을 깨뜨릴 수 있다. 브랜드 잠금부터 상품·브랜드 삭제까지 한 경계는 유지한다.

현재 유지 결정은 RC 국소 적용이 불가능해서가 아니다. ID별 잠금의 명시적인 대상·순서를 유지하기로 한 선택이며 SQL 비용을 감수한다. RC 벌크는 아래 비교에서 유효한 대안으로 확인됐으므로, 전면 전환보다 먼저 재검토할 수 있다. 채택 전에는 실제 Facade 진입점의 격리 수준, RC에서의 등록·삭제 양방향 경쟁과 중간 실패 롤백, 바깥 트랜잭션 참여 여부를 확인한다. 기존 RC 실험이 이 모든 조건을 검증한 것은 아니다.

**재검토 조건:** 삭제 지연이나 SQL 비용이 문제가 되면 브랜드 삭제만 RC·벌크로 적용하는 대안을 먼저 비교한다. 시스템 전반의 범위 쓰기·조회 요구가 바뀌면 전체 기본값 전환을 별도로 검토한다.

## 추가 실험: 브랜드 분포·통계와 다른 상품 수정

브랜드당 상품 100개로 고정하고 브랜드 2개·100개, `ANALYZE TABLE product` 실행 전·후, 두 삭제 방식을 비교했다. 총 8개 사례다. 대상과 첫 다른 브랜드의 ID는 교차하고, 나머지 98개 브랜드 상품은 뒤에 적재했다. 기존 삭제 상품 한 개가 추가로 있다. 삭제 대상 비율은 각각 약 50%·1%이며 격리 수준은 기존 RR이다. 통계 갱신은 테스트 DB에만 수행했다.

| 브랜드 수 | 명시적 통계 갱신 | 벌크 실행 계획 | 다른 브랜드 기존 상품의 잠금 충돌 |
| --- | --- | --- | --- |
| 2 | 전 | PRIMARY 스캔 | 있음 |
| 2 | 후 | PRIMARY 스캔 | 있음 |
| 100 | 전 | PRIMARY 스캔 | 있음 |
| 100 | 후 | idx_product_brand_deleted 범위 검색 | 없음 |

현재 ID별 방식에서는 네 조건 모두 검사한 다른 브랜드 상품에 충돌이 없었다. 인덱스의 존재만으로 해당 인덱스 사용이나 좁은 잠금 범위가 보장되지는 않았다. 또한 100개 브랜드·통계 갱신 후 결과는 벌크가 항상 다른 브랜드를 막는다는 주장을 반박한다. 모든 다른 브랜드 행·INSERT 범위까지 확인한 것은 아니다.

잠금 충돌 확인과 실제 수정 처리를 구분했다.

- **커밋 전 검사:** 삭제 SQL 실행 후 별도 연결의 NOWAIT로 충돌을 확인하고, 실제 `ProductFacade.update()`를 다른 스레드에서 호출했다. 최대 200ms 동안 수정 완료를 기다린 뒤 삭제를 커밋했다. 충돌 조건에서는 수정이 커밋 후 완료됐고, 비충돌 조건에서는 커밋 전 완료됐다. 이 지연은 잠금 영향을 드러내기 위해 만든 것으로 운영 응답 시간으로 해석하지 않는다.
- **지연 없는 동시 실행:** 준비 데이터를 복원한 뒤 삭제와 `ProductFacade.update()`의 시작만 맞추고 즉시 정상 커밋했다. 각 조건을 3회 실행하고 매번 상품명을 달리해 실제 UPDATE가 발생하도록 했다. 삭제·수정 모두 성공하고, 대상 삭제·다른 브랜드 상품 유지·수정 반영을 DB로 확인했다. HTTP가 아닌 서비스 호출이며, 측정값에는 연결 획득·SQL·커밋 시간이 포함된다. 매 실행에서 DB 잠금 대기가 실제로 발생했다는 의미는 아니다.

추가 측정 수치는 아래 표에 기록한다. 세 번의 표본은 긴 대기나 높은 부하의 상한을 보장하지 않는다. 특히 삭제가 상품을 잠근 후 다른 이유로 오래 머무는 상황은 정상 동시 실행과 구분해야 한다.

| 브랜드 수 | 통계 갱신 | 방식 | 삭제 중앙값(ms) | 다른 상품 수정 중앙값(ms) |
| --- | --- | --- | ---: | ---: |
| 2 | 전 | 현재 | 256.680 | 6.639 |
| 2 | 전 | 벌크 | 9.696 | 6.418 |
| 2 | 후 | 현재 | 169.919 | 5.282 |
| 2 | 후 | 벌크 | 11.748 | 7.791 |
| 100 | 전 | 현재 | 140.174 | 5.386 |
| 100 | 전 | 벌크 | 12.393 | 5.136 |
| 100 | 후 | 현재 | 137.276 | 4.814 |
| 100 | 후 | 벌크 | 7.321 | 4.694 |

수치는 추가 실험을 포함한 전체 check 실행에서 수집했다. 위 조건에서는 모두 정상 완료했지만, 높은 부하나 다른 데이터 분포의 응답 시간 목표까지 검증한 것은 아니다.

## 추가 검증: 삭제 트랜잭션만 RC로 실행

`TransactionTemplate`에서 테스트 삭제 트랜잭션의 격리 수준을 RR·RC로 명시하고, 실제 연결의 `@@session.transaction_isolation`도 확인했다. 서버·서비스 기본값은 변경하지 않았다. 다른 브랜드 수정 서비스와 NOWAIT 검사 연결은 기존 기본값을 따른다. 브랜드당 100개·브랜드 수 2/100·통계 갱신 전후의 네 조건을 두 삭제 방식으로 실행해 총 16개 조합을 비교했다.

| 삭제 방식·격리 수준 | 검사한 다른 브랜드 상품의 잠금 충돌 | 실제 수정 완료 시점 |
| --- | --- | --- |
| ID별·RR | 0/4 | 삭제 커밋 전 |
| ID별·RC | 0/4 | 삭제 커밋 전 |
| 벌크·RR | 3/4 | 충돌 3조건은 삭제 커밋 후, 나머지는 전 |
| 벌크·RC | 0/4 | 삭제 커밋 전 |

RC 벌크는 PRIMARY 스캔이 선택된 세 조건에서도 검사한 다른 브랜드 행에 잠금 충돌이 없었다. 조건 불일치 행의 잠금 유지가 줄어드는 효과를 이번 조건에서 확인했다. 지연 없는 동시 실행도 16개 조합에서 각 3회 정상 완료했다.

관찰 범위는 삭제 SQL 완료 후 기존 다른 브랜드 행 한 개와 실제 수정 서비스다. 대상 외 행을 모두 열거하거나 INSERT·외래키·유니크 검사·인덱스 변경의 모든 잠금을 확인하지 않았다. 다른 요청이 먼저 잠근 경우의 반대 방향 대기, 애플리케이션 전체 RC 전환, RC 전용 실패 주입 롤백은 이번 추가 실험의 대상이 아니다. 따라서 RC가 모든 계획에서 대기·교착·업무 오류를 없앤다는 결론으로 확대하지 않는다. 기존 방식 유지 결정도 변경하지 않는다.
