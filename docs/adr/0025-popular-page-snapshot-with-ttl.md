# ADR 0025: 인기순은 ID 목록을 60초 재사용하고 좋아요 변경으로 무효화하지 않는다

Status: Accepted
Date: 2026-10-16
Supersedes: [ADR 0024](0024-likes-page-cache-with-commit-eviction.md)

## 배경과 결정

좋아요마다 브랜드 순위 키를 삭제한 첫 실험은 변경 사이에 재사용할 때만 이점이 있었다. 순위의 잠시 늦은 반영을 허용하고 하트와 좋아요 수는 현재 값을 보여주기로 했다. 재사용할 ID 목록과 현재 표시 정보를 분리해 좋아요마다 순위를 다시 만들지 않는다. Redis가 없거나 실패해도 DB에서 순위를 재생성할 수 있도록 원본 조회 경로를 유지한다.

기존 `likes_desc`는 DB의 현재 누적 좋아요 수 DESC·생성 시각 DESC·ID DESC를 유지한다. 새 `sort=popular`는 브랜드 조건·page=0·size=20에서만 제공하는 최근 계산 순위다. 다른 조건의 popular 요청은 400으로 거절해 서로 다른 시점의 페이지를 섞지 않는다. 기존 정렬의 요청·응답은 바꾸지 않고 총상품수도 추가하지 않는다.

Redis에는 정렬된 상품 ID만 저장한다. 캐시가 없을 때 브랜드의 전체 활성 상품과 DB 카운터로 순위를 계산한 뒤 첫 20개를 저장한다(계산은 DB가 정렬해 20개 ID만 돌려준다, [ADR 0026](0026-likes-ranking-sorted-in-database.md)). hit에서는 해당 상품·브랜드·현재 카운터·사용자별 하트를 DB에서 합성한다. 현재 숫자는 저장 당시 순서와 어긋날 수 있다. 이는 허용한 표시 정책이며 현재 좋아요순이라고 설명하지 않는다.

### 캐시를 두는 근거

인기순 원본은 정렬 기준인 좋아요 수가 상품 인덱스에 없어 브랜드의 활성 상품과 카운터를 모두 읽어야 20개를 고를 수 있다. 원본 비용이 브랜드 상품 수에 비례하고 hit는 20개 ID 확인으로 일정하다. 현재 코드에서 브랜드 7이 990개일 때 원본 2,056행·DB 약 2.3ms, 87,390개일 때 174,856행·DB 약 84ms·API 약 99ms이고, hit는 두 경우 모두 56행·DB 약 1.1ms·API 약 10~13ms다(같은 JAR·같은 실행기로 측정). 데이터가 클수록 hit가 피해 가는 비용이 커진다([캐시 대상 기준](../week4/design.md#cache-target-criterion), [상세](../week4/cache-db-work.md)).

## 만료와 변경

- TTL은 저장부터 60초이고 hit나 좋아요 변경으로 연장하지 않는다. 최적값을 측정한 결과가 아니라 합의한 지연으로 시작하는 설정이다.
- 좋아요 등록·취소·중복 요청은 인기순 키를 지우거나 갱신하지 않는다. 관계와 DB 카운터의 기존 트랜잭션은 유지한다.
- 상품 생성·삭제, 브랜드 삭제는 commit 후 해당 브랜드 키를 지운다. rollback은 지우지 않는다. 이름·가격·재고·브랜드 표시 변경은 현재 DB 정보를 읽으므로 순위 키를 유지한다.
- 만료 후 다음 조회가 다시 계산한다. 정시 배치나 자동 주기 집계가 아니다. 진행 중인 오래된 조회가 늦게 저장될 수 있으므로 모든 요청에 적용되는 DB 변경 후 60초의 절대 상한을 주장하지 않는다.
- 삭제 상품·브랜드의 비노출, 사용자별 정보 분리, 쓰기 트랜잭션 안의 캐시 우회는 유지한다. Redis GET/SET/DEL 실패 시 원본으로 우회하거나 실패를 기록하며 DB 오류는 감추지 않는다.
- Redis는 DB로 재생성할 수 있는 사본이다. 엄밀한 원천은 `product_like` 관계이며 `product_like_count`는 같은 DB 트랜잭션에서 유지하는 파생 카운터다. 순위 재생성은 이 카운터를 이용한다.

## 알고 있는 한계

허용한 정책이지만 사용자에게 보이는 결과와 비용이 있어 따로 적는다.

1. **새 상품이 최대 TTL만큼 늦게 들어올 수 있다.** hit 검사는 캐시된 ID가 아직 활성이고 같은 브랜드인지만 확인한다. 그래서 삭제된 상품은 바로 걸러지지만, 순위에 새로 들어와야 할 상품이 빠졌는지는 알 수 없다. 보통은 상품 생성 commit 뒤 키를 지워 문제가 없다. 다만 생성과 겹쳐 시작한 조회가 삭제 뒤에 옛 목록을 다시 저장하면(늦은 채움), 다음 만료까지 그 상품이 빠진다. `lateFillCanKeepOldOrderButCurrentCountsAndPersonalStateUntilExpiry`가 이 동작을 확인한다.
2. **화면의 좋아요 수와 순서가 어긋날 수 있다.** 순서는 저장 당시 계산이고 좋아요 수는 현재 카운터라서, 아래 순위 상품의 좋아요 수가 더 많아 보일 수 있다. 응답의 `popular`는 "최근 계산한 순위"이며 현재 좋아요순이 아니다. 현재 좋아요순이 필요하면 `likes_desc`를 쓴다.
3. **만료 순간 동시 요청은 같은 계산을 반복한다.** 키가 만료되면 다음 요청들이 각각 브랜드 전체 활성 상품과 카운터를 읽고 정렬한다(10만 건 브랜드 7 기준 990개). 요청 합치기는 하지 않는다. 가격순(300초)보다 TTL이 짧아 같은 상황이 더 자주 생긴다. 측정에서 990개 브랜드는 키를 지운 직후 동시 20·80 요청 중 묶음당 8~22번이 각자 계산했고 실패는 없었다. 브랜드를 87,390개로 키우자 앱이 정렬하던 당시 구조에서는 동시 20 요청 대부분이 메모리 부족으로 실패했다. 원본을 DB 정렬로 바꾼 뒤([ADR 0026](0026-likes-ranking-sorted-in-database.md)) 실패는 없어졌지만 모든 요청이 각자 계산하는 일은 남았다. 스레드 20개로 150초 동안 계속 조회해 TTL이 저절로 끝나게 하면, 87,390개 브랜드에서 만료마다 20번 겹쳐 계산했고 그 순간 요청은 약 0.5~1초를 기다렸다. 그래도 만료 비용을 포함한 요청당 DB 시간은 캐시 없음 약 885ms 대비 약 1.5ms였다([implementation-log 35·36·41절](../week4/implementation-log.md#popular-cache-growth-stampede)).

## 검증 계획

실제 MySQL·Redis에서 순위 재사용 중 등록/취소의 현재 숫자·하트, 페이지 밖 상품의 만료 후 진입, 기존 likes_desc의 즉시 반영, 생성/삭제/rollback, 사용자 분리, 손상 값, 장애·늦은 채움을 검증한다. 동일 빌드의 캐시 없음/miss/hit과 실제 변경 혼합을 별도 기대값으로 비교한다. 이전 ADR의 성능 수치는 이전 구현의 기록으로 유지한다.

Sorted Set·로컬 캐시 추가·분산 잠금·revision·별도 집계 배치는 이번 범위에 넣지 않는다. 이번 결과와 만료 시 부하를 보고 후속 필요성을 판단한다.

## 실행 결과

현재 production JAR에서 상품 10만 건·브랜드 7·첫 20개·사용자 95를 고정하고 세 번 반복했다. 변경 없는 비교의 API 중앙값은 DB-only 15.139~17.222ms, miss 16.073~17.810ms, hit 9.237~11.513ms였다. 매 GET 전 좋아요 변경 조건에서도 현재 정렬 DB-only 12.792~14.620ms, 순위를 재사용하는 Redis 7.091~8.633ms였다. 지연을 허용한 순위라는 비용 차이를 함께 명시한다.

대표 SQL 21개 요청에서 SELECT 5개·상품 총수 COUNT 0번, 상품/카운터 접근 행은 원본 990개와 캐시 재사용 20개였다. 측정 GET 6,000개는 각 정책의 기대값과 같았다. 기본 60초 만료도 실제 관찰해 페이지 밖 상품의 다음 재선택을 확인했다. 56 suites·331건·Checkstyle·ArchUnit이 통과했다.
