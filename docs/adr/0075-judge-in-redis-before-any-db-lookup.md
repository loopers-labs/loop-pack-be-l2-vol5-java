# ADR 0075: REDIS_SYNC에서는 Redis 판단을 DB 조회보다 먼저 한다

Status: Accepted
Extended by: [ADR 0076](0076-accept-coupon-issue-into-redis-stream-and-save-by-worker.md) (판단 뒤 DB 저장을 작업 큐와 Worker로 옮기는 QUEUE 모드를 더한다), [ADR 0078](0078-remember-final-closure-in-app-memory.md) (다시 풀리지 않는 마감은 Redis 판단 앞에서 서버 메모리로 끊는다)
Extends: [ADR 0074](0074-confirm-coupon-reservations-after-db-outcome.md) (예약 확정·보상 정책은 그대로 두고, Redis 판단 앞의 사용자 확인·기존 쿠폰 조회를 없앤다)
Related: [8주차 설계](../week8/design.md), [8주차 실험](../week8/experiments.md), [구현 기록](../week8/implementation-log.md)

## Context

REDIS_SYNC는 요청마다 DB에서 사용자 확인과 기존 쿠폰 조회를 한 뒤 Redis Lua로 수량·중복을 판단했다. 그래서 매진 뒤처럼 결과가 이미 정해진 요청도 DB를 두 번 거쳤다.

- Redis 사용자 기록에는 준비 때 DB의 발급자를 `A`로 채우고, 새 발급도 `R:UUID` → `A`로 남긴다. "이미 받았는가"는 Redis가 판단할 수 있다. 기존 쿠폰 조회는 Lua가 하는 일을 DB에 한 번 더 묻는 것이다.
- 작업 큐를 검토하며 요청 안에서 DB를 쓰지 않는 것이 목표가 됐다. Lua 앞의 DB 조회는 요청이 커넥션을 쓰게 하고, 요청마다 다르게 늦어지면 Redis 도착 순서(선착순 기준)를 더 흐트러뜨린다.
- Redis는 사용자가 실제로 있는지 모른다. 사용자 확인을 그냥 빼면 없는 사용자 ID가 수량을 가져갈 수 있다. 쿠폰 테이블은 사용자 존재를 확인하지 않는다.

## Decision

REDIS_SYNC의 흐름을 다음으로 바꾼다. DB_ONLY는 비교 기준선이라 바꾸지 않는다.

```text
ID 형식 확인(400)
→ Redis Lua 판단
   매진·종료 → 409 (DB에 가지 않음)
   준비 안 됨 → 503 (없는 캠페인은 DB 확인 후 404)
   이미 통과(A 또는 R) → DB에서 쿠폰 조회: 있으면 200 / 없으면 409 처리 중
   통과 → 사용자 확인: 없으면 예약을 돌리고 404
→ DB 발급 TX → 201 또는 200 → 예약 확정·보상 (ADR 0074)
```

- 사용자 확인은 Redis를 통과한 요청만 한다(최대 남은 수량만큼).
- Redis 판단 자체가 실패하면 새 발급은 하지 않고, 이미 받은 쿠폰만 DB에서 찾아 200으로 돌려준다. 없으면 503이다.

## Alternatives

| 대안 | 판단 |
| --- | --- |
| 지금처럼 Redis 앞에서 사용자 확인·기존 쿠폰 조회 | 결과가 정해진 요청도 DB를 쓴다. 채택하지 않음 |
| 사용자 확인도 완전히 뺀다(인증이 보장한다고 가정) | 이 프로젝트는 인증 대신 `X-USER-ID` 헤더를 쓴다. 없는 사용자가 수량을 가져가 DB에 저장된다. 채택하지 않음 |
| 사용자 확인을 DB 발급 TX 안으로 옮긴다 | 효과는 같지만 발급 TX와 무관한 조회가 TX 시간을 늘린다. 채택하지 않음 |

## Consequences

- 매진·종료 요청은 DB 조회 없이 Redis에서 끝난다. 이미 통과한 사용자는 사용자 확인 없이 실제 쿠폰만 DB에서 읽는다.
- 없는 사용자가 매진 뒤에 요청하면 404가 아니라 409를 받는다. 사용자 존재보다 결과가 정해진 판단이 먼저다.
- 준비되지 않았거나 판단 정보가 사라진 캠페인에서는, 이미 쿠폰을 받은 사용자도 503을 받는다. 예전에는 DB 조회로 200을 받았다. 본인 쿠폰 목록은 DB에서 그대로 조회된다.
- 이 결정 전의 REDIS_SYNC 측정(2-0~2-4)은 Lua 앞 DB 조회가 있는 구조의 기록이다. 결론이 이 변경에 영향을 받는지는 [실험 2-5](../week8/experiments.md)에 정리한다.

## 검증

- `CouponRedisIssueIntegrationTest`: 매진 요청은 사용자 확인·기존 쿠폰 조회·발급 TX를 하지 않는다. 없는 사용자는 Redis를 통과해도 404이고 남은 수가 돌아온다. 기존 시나리오(Redis 오류 시 기존 쿠폰 200, 보상, 동시 중복 등)도 통과한다.
