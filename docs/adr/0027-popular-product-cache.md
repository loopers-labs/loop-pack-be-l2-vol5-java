# ADR 0027: 인기순 목록 ID 캐시와 상품별 캐시를 나누는 구조를 시도했다가 되돌린다

Status: Rejected (구현·측정 뒤 되돌림)
Related: [ADR 0025](0025-popular-page-snapshot-with-ttl.md)

## 요약

인기순 목록 캐시(ID 20개)와 상품마다 이름·가격을 두는 상품 캐시를 나누는 구조를 구현하고 측정했다. hit에서는 DB 작업이 줄지 않았고 API 지연 개선도 확인하지 못했다. 가격순 목록은 운영 시 캐시 없이 조회하기로 했으므로([ADR 0021](0021-price-page-cache-aside-with-after-commit-eviction.md)) 상품 캐시를 공유해 이득을 낼 경로도 없었다. 그래서 코드는 되돌리고 이 문서는 시도와 측정의 기록으로 남긴다. 현재 인기순은 ADR 0025·0026 그대로 hit 때 상품 20개를 DB에서 읽는다.

## 배경

인기순 목록 캐시는 상품 ID 20개만 저장하고, hit 때 그 20개 상품을 DB에서 다시 읽는다([ADR 0025](0025-popular-page-snapshot-with-ttl.md)). 상품 이름·가격은 목록마다가 아니라 상품마다 같은 값이다. 목록 캐시와 상품 캐시를 나누면 상품 정보를 상품 단위로 재사용하고, 상품이 바뀔 때 그 상품 키 하나만 지우면 된다. 가격순 캐시는 목록 키 안에 이름·가격을 함께 저장한다([ADR 0021](0021-price-page-cache-aside-with-after-commit-eviction.md)).

## 시도한 구조

- 인기순 목록 캐시는 그대로 ID 20개만 저장한다. 60초 재사용과 무효화 규칙(ADR 0025)은 바꾸지 않는다.
- 상품 캐시를 추가한다. 키는 `prefix:product:{id}`, 값은 ID·브랜드 ID·이름·가격·생성 시각이다. TTL은 저장부터 300초이고 hit로 연장하지 않는다. 좋아요 수·하트·재고·삭제 여부는 저장하지 않는다.
- 인기순 hit: 목록 ID → DB에서 ID만으로 활성·같은 브랜드인지 확인 → 상품 캐시 MGET → 없는 상품만 DB에서 읽어 저장 → 좋아요 수(카운터)·하트를 DB에서 합성한다. 활성 확인에서 하나라도 빠지면 기존처럼 순위를 다시 계산한다.
- 인기순 miss: 순위 계산(DB 정렬, [ADR 0026](0026-likes-ranking-sorted-in-database.md))으로 ID를 얻은 뒤 같은 방식으로 상품 캐시를 쓴다.
- 상품 수정·삭제는 같은 트랜잭션에서 `ProductChanged`를 발행하고, AFTER_COMMIT listener가 그 상품 키를 지운다. rollback에서는 지우지 않는다. 브랜드 삭제는 상품 키를 지우지 않는다. 삭제된 상품은 활성 확인에서 빠지므로 노출되지 않는다.
- 상품 캐시는 인기순 캐시가 켜진 읽기 트랜잭션에서만 쓴다. `commerce.cache.product.enabled=false`면 기존 인기순 hit와 같다. 가격순·likes_desc·상세는 바꾸지 않는다.

## 최신성과 오류

- 이름·가격은 정상 변경 뒤 순차 조회에서 새 값을 보인다. 키 삭제 실패·늦은 채움에서는 옛 이름·가격이 최대 TTL 300초 남을 수 있다. 순서의 지연(최대 60초 허용)은 ADR 0025 그대로다([캐시별 최신성 표](../week4/design.md#cache-freshness)).
- 삭제 상품 비노출은 캐시에 맡기지 않는다. 목록 키와 상품 키 삭제가 모두 실패해도 DB 활성 확인에서 빠진다.
- Redis 읽기 실패·손상 값은 없는 것으로 보고 DB에서 읽는다. 저장·삭제 실패는 기록만 하고 요청과 이미 commit된 변경을 실패로 바꾸지 않는다. DB 오류는 감추지 않는다.

## 측정 결과와 판단

같은 JAR로 상품 캐시만 끄고 켜서 요청 하나의 DB 작업을 쟀다([흐름과 측정](../week4/popular-product-cache.md)).

| 브랜드 7 | 경우 | 끔: SELECT / DB / API | 켬: SELECT / DB / API |
| ---: | --- | --- | --- |
| 990개 | hit | 5 / 1.04~1.24ms / 10.3~11.1ms | 5 / 1.13~1.18ms / 10.8~11.0ms |
| 990개 | miss | 6 / 2.77~2.93ms / 13.8~14.0ms | 5 / 2.55~2.70ms / 12.9~13.4ms |
| 87,390개 | hit | 5 / 1.11~1.16ms / 12.8~13.2ms | 5 / 1.21~1.26ms / 13.3~13.8ms |
| 87,390개 | miss | 6 / 77.1~77.7ms / 90.8~92.4ms | 5 / 76.7~77.1ms / 89.1~90.2ms |

- hit에서는 DB 작업이 줄지 않았다. 삭제 확인 문장이 남고, 전체 행 20개 조회와 ID 확인은 MySQL 문장 실행 시간이 모두 0.2~0.3ms로 차이가 드러나지 않았다. API 지연 개선도 확인하지 못했다. MGET이 API 시간에서 차지한 몫은 따로 재지 않았다.
- miss에서는 상품 조회 문장이 빠져 990개 브랜드에서 DB 약 0.2ms·API 약 1ms 줄었다.
## 되돌린 이유

- 인기순에서 비싼 일은 순위 계산이고, 목록 캐시가 이미 없앤다. 상품 캐시가 없앨 수 있는 것은 PK로 20행을 읽는 싼 문장 하나뿐인데, 삭제 상품을 숨기는 ID 확인 문장이 그 자리에 다시 들어간다. 싼 문장 하나를 비슷하게 싼 문장 하나로 바꾸고 Redis 조회가 하나 더해졌다.
- 공유로 이득을 낼 후보였던 가격순 목록은 원본이 인덱스로 이미 20행만 읽고, 운영 시 캐시 없이 조회하기로 했다. 상품 캐시를 가격순에 붙이면 가격을 캐시에 다시 두게 되어 그 판단과도 어긋난다.
- 남는 것은 이름·가격을 캐시에 하나 더 두는 부담(키 삭제 실패·늦은 채움 시 옛 표시 값, 무효화 코드, Redis 왕복)뿐이었다.

## 다시 볼 조건

상세 화면처럼 상품 조회 문장 자체를 없앨 수 있는 경로가 생기고 그 경로의 DB 부하가 실제로 문제가 될 때 다시 검토한다. 그때는 삭제 확인을 어디서 할지와 가격을 캐시에 두는 것이 허용되는지를 먼저 정한다.

## 당시 검증

되돌리기 전 `PopularProductCacheIntegrationTest` 5건: hit에서 상품 정보를 DB 대신 캐시에서 읽고 ID만 확인하는지, 상품 수정이 그 상품 키만 지우고 다음 hit에 새 값이 보이는지, 목록·상품 키 삭제가 모두 실패해도 삭제 상품이 보이지 않는지, 손상 값은 DB로 대신하고 다시 채우는지, 순서와 상품 값을 재사용해도 좋아요 수는 현재 값인지. 기존 인기순 통합 테스트는 상품 캐시를 끈 설정으로 그대로 통과한다. `:apps:commerce-api:check` 342건과 Checkstyle·ArchUnit이 통과했다. 되돌린 뒤에는 이 테스트와 상품 캐시 코드를 지웠고 337건·Checkstyle·ArchUnit이 통과했다.
