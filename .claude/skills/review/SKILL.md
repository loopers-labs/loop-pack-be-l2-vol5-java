# Review — 필요한 리뷰어만, 한 번에

> jarip-server 하네스의 리뷰 팀·린 리뷰 원칙과, https://github.com/obra/superpowers `requesting-code-review`(MIT, © 2025 Jesse Vincent)의 보고 형식을 이 과제에 맞게 줄였다.

## 1. 범위를 정한다

- 기준 커밋(`BASE`)을 정한다 — 기능을 시작하기 직전 커밋. 커밋 전이면 `git diff HEAD`와 untracked 파일.
- `git diff --stat BASE`로 바뀐 계층과 파일 종류를 본다.

## 2. 리뷰어를 고른다 — 1~3명, 전원 호출 금지

| 바뀐 것 | 리뷰어 |
|---|---|
| 엔티티·VO·도메인 서비스·Facade, 패키지 의존, 트랜잭션 | `domain-reviewer` |
| `@Entity` 매핑, Repository·QueryDSL·네이티브 쿼리, 인덱스·제약, 동시성 | `persistence-reviewer` |
| Controller·DTO·`ApiControllerAdvice`·`ErrorType`, 요청자 식별, 관리자 경계 | `api-contract-reviewer` |
| 테스트 코드 (거의 항상) | `test-reviewer` |

- 파일 한두 개의 작은 변경이면 1명. 대표 TDD 커밋이나 기능 완료 시점에는 `test-reviewer`를 포함한다.

## 3. 호출한다

- 고른 리뷰어를 **한 메시지에서 병렬로** 부른다. 프롬프트에는 기능 이름, 관련 규칙 ID, `BASE`, 확인하고 싶은 우려를 넣는다.
- 리뷰어는 읽기 전용이다. 코드를 고치게 하지 않는다.

## 4. 합친다

- 같은 지적은 하나로 합치고 가장 높은 심각도를 쓴다.
- **지적마다 코드로 사실을 확인한다** — 파일:라인을 직접 연다. 틀린 지적은 "기각 — 이유"로 남긴다. 리뷰어의 보고만 믿지 않는다.
- 합의된 ADR과 충돌하는 지적은 반영하지 않고 학습자에게 🤔로 올린다.

## 5. 보고하고 멈춘다

```markdown
### 리뷰 요약 — (기능 이름)
리뷰어: domain, test (고른 이유: …)

| 심각도 | 지적 | 파일:라인 | 사실 확인 | 제안 |
|---|---|---|---|---|
| Critical | … | … | ✅ 맞음 / ❌ 틀림 | … |

### 판정
커밋해도 되는가: 예 / 아니오 / 고친 뒤

### 학습자가 정할 것 (🤔)
```

- 고칠지는 학습자와 정한다. 고친 뒤에는 **재리뷰하지 않고** `verify` 스킬로 검사만 다시 돌린다.

## 리뷰어 공통 보고 형식

리뷰어 에이전트는 이 형식으로 보고한다.

```markdown
### 잘한 점
- (구체적으로, 파일:라인)

### 문제
- [Critical|Important|Minor] `파일:라인` — 무엇이 문제인가 / 왜 중요한가 (가능하면 실패하는 입력 예) / 고칠 방향 / 근거 (plan.md 절·규칙 ID·ADR)
  - Critical: 잘못된 결과, 데이터 손상, 설계 계약 위반, 검사·테스트 완화
  - Important: 책임 배치, 빠진 테스트, 오류 처리
  - Minor: 이름, 중복, 문서

### 확인 필요
- (확신이 없는 것과 그 이유)

### 실행한 명령
| 명령 | 결과 |
|---|---|

### 판정
예 / 아니오 / 고친 뒤 — 이유 한두 문장
```

## 리뷰어를 다듬는 법

- 리뷰에서 **틀린 지적이나 반복되는 쓸모없는 지적**이 나오면 해당 리뷰어의 "확인할 것"을 고친다. 한 번에 하나씩 고치고 `chore:` 커밋으로 남긴다.
- 새 주차 주제(인증, 동시성, 이벤트·Kafka 등)가 오면 필요한 리뷰어를 그때 추가한다.
