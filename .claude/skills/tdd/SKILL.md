# TDD — Red → Green → Refactor

> 원본: https://github.com/obra/superpowers `test-driven-development`·`writing-good-tests` (MIT, © 2025 Jesse Vincent). 이 저장소(Java·JUnit 5·AssertJ·Gradle)와 과제 규칙에 맞게 고쳤다.

## 철칙

```
실패하는 것을 직접 본 테스트 없이 제품 코드를 쓰지 않는다
```

실패하는 것을 보지 못한 테스트는 올바른 것을 검사하는지 알 수 없다.

## 0. 기대값은 사람이 정한다 (시작 전 필수)

과제 발제: "구현과 그 구현을 평가할 기대값을 동시에 맡기지 않는다."

1. `docs/week2/plan.md`에서 대상 규칙 ID와 기대값을 찾는다.
2. 테스트 후보를 표로 제안한다 — `규칙 ID | 입력 | 기대 결과 | 이 테스트가 잡는 잘못된 구현`.
   - **정상 사례와 거절 사례를 함께** 넣는다. 정상 사례가 없으면 "전부 거절"하는 구현도 통과한다.
   - 거절 사례에는 **거절 후 기존 값 유지**를 함께 넣는다. 값을 바꾼 뒤 예외를 던지는 구현을 잡는다.
3. 학습자가 확정한 목록만 테스트로 옮긴다. 목록에 없는 기대값이 필요해지면 먼저 묻는다.

## 1. RED — 실패하는 테스트 하나

- 테스트 하나 = 행동 하나. `@DisplayName`에 규칙 ID와 기대를 쓴다. 예: `"PNT-06 남은 금액보다 많이 쓰면 거절하고, 남은 금액은 그대로다"`.
- 스타터 관례를 따른다: `@Nested`로 상황 묶기, `// arrange // act // assert`, AssertJ.
- domain 규칙은 Spring·DB 없이 테스트한다. "지금 시각"이 필요하면 인자로 넘긴다.
- 기대값은 **손으로 계산한 리터럴**로 쓴다. 테스트 대상 코드나 그 helper로 기대값을 만들면 무엇을 해도 통과한다.

### Red 확인 — 생략하지 않는다

```bash
./gradlew :apps:commerce-api:test --tests '*{테스트 클래스 이름}'
```

- **컴파일 오류는 Red가 아니다.** 필요한 타입·생성자·메서드 시그니처만 먼저 만들고(본문은 비우거나 기본값 반환), 컴파일된 상태에서 **assertion이 실패**하는 것을 본다.
- 실패 이유가 의도한 것인지 확인한다 — 기능이 없어서여야 한다. 오타·DB 연결 실패·테스트 이름 오류는 Red가 아니다.
- 테스트가 바로 통과하면 이미 있는 동작을 검사하고 있는 것이다 → 테스트를 고친다.
- 실패 출력의 핵심 줄을 보고에 붙인다.

## 2. GREEN — 통과시키는 최소 구현

- 그 테스트를 통과시키는 가장 단순한 코드만 쓴다. 아직 요구하지 않은 범용화·옵션을 넣지 않는다.
- 같은 명령으로 다시 실행해 대상 테스트와 같은 클래스의 다른 테스트가 모두 통과하는지 본다.
- **실패하면 코드를 고친다. 테스트·기대값을 고치지 않는다.** 기대값이 틀렸다고 생각되면 멈추고 학습자에게 묻는다.

## 3. REFACTOR — 동작을 유지하며 정리

- 중복된 검사식을 이름 있는 메서드로 묶고, 호출자에 흩어진 계산을 상태를 가진 객체로 옮긴다 (Tell, Don't Ask).
- 행동을 추가하지 않는다. 정리할 것이 없으면 "Refactor 없음 — 이유"를 보고한다. 억지로 인터페이스를 만들지 않는다.
- 다시 실행해 초록을 확인한다. **기대값을 바꿔 실패를 없애는 것은 리팩터링이 아니다.**

## 4. 반복과 마무리

- 다음 후보 사례로 1~3을 반복한다.
- 대표 규칙(체크리스트 대상)은 단계마다 커밋해 PR에서 변화를 보여 준다: `test: …(Red)` → `feat: …(Green)` → `refactor: …`. 커밋은 학습자 확인 후에 한다.
- **변이 점검** — 제품 코드를 머릿속으로 바꿔 본다: 경계 비교(`<` ↔ `<=`), 분기 누락, 상태 변경 누락, 기본값 반환, 0·음수·null·만료 입력 검증 누락. 어떤 테스트도 실패하지 않는 변이가 있으면 그 행동은 보호되지 않는다.
- 끝났다고 말하기 전에 `verify` 스킬을 따른다.

## 멈춰야 하는 신호

| 신호 | 할 일 |
|---|---|
| 테스트보다 제품 코드를 먼저 썼다 | 멈추고 알린다. 학습자 동의 후 코드를 지우고 테스트부터 다시 한다 |
| 실패를 보지 않았다 / 왜 실패했는지 설명하지 못한다 | Red 확인으로 돌아간다 |
| 테스트가 처음부터 통과했다 | 이미 있는 동작을 검사 중이다. 테스트를 고친다 |
| 통과시키려고 assertion을 약하게 하거나 `@Disabled`를 붙이려 한다 | 금지(과제 규칙 4). 멈추고 묻는다 |
| mock 준비가 테스트의 절반을 넘는다 / mock 자체를 검사한다 | 실제 객체로 바꾸거나 통합 테스트로 옮긴다 |
| 테스트 준비가 거대하다 | 설계가 복잡하다는 신호다. 책임 배치를 다시 본다 |

## 좋은 테스트인지 묻는 질문

- 이 테스트를 실패시킬 **제품 코드의 잘못**을 말할 수 있는가? 말할 수 없으면 필요 없는 테스트다.
- 상수 값·메시지 문구·private 구조만 검사하는 "변경 감지기"가 아닌가?
- Spring·JPA가 원래 해 주는 동작이 아니라 **우리 코드의 계약**을 검사하는가?
- 테스트에서만 쓰는 메서드를 제품 클래스에 추가하지 않았는가? (테스트 유틸로 옮긴다)
