# Domain Modeling — 누가 답하고, 누가 누구를 아는가

> 기준: 발제 「설계를 코드로 옮기는 객체지향과 AI 협업」, 참고 자료 「도메인 모델링 예시 (영화 예매)」, jarip-server `ddd-bounded-context`의 애그리거트 규칙, wshobson/agents `architecture-patterns`의 DDD 전술 패턴 정의. 결과는 `docs/week2/plan.md` 3~5장과 ADR에 적는다.

## 1. 요구사항을 질문으로 바꾼다

- 요구 문장마다 "이 규칙에 **누가** 답할 수 있는가?"를 묻는다.
- 기준은 "조회가 필요한가"가 아니다. 모든 규칙은 DB에서 불러온 뒤 판단한다. 기준은 **불러온 뒤 한 객체가 자기 필드만으로 답할 수 있는가**다.
  - 답할 수 있다 → 그 Entity·VO
  - 여러 행의 집합이 답한다 → Repository (+ DB 제약)
  - 여러 객체를 함께 봐야 한다 → 도메인 서비스
  - 순서·트랜잭션·조합만 필요하다 → Facade (응용 서비스)
- 요구의 종류를 구분한다: "재고는 음수가 되지 않는다"(상태의 규칙) ≠ "목록에 브랜드명을 보여 준다"(조회 결과의 구성).

## 2. 종류를 정한다

| 종류 | 판별 질문 | 지킬 것 |
|---|---|---|
| Entity | 내용이 같은 두 개가 **다른 것**이고, 상태가 바뀌는가 | protected 기본 생성자 + 검증하는 생성자·정적 팩토리. **setter 금지**, 상태 변경은 의미 있는 행동 메서드로 |
| Value Object | 내용이 같으면 **같은 것**이고 불변인가 | 생성자에서 불변식 검증(유효하지 않은 값은 만들 수 없게), 연산은 새 값을 반환, `record` 권장 |
| 도메인 서비스 | 가진 상태 **없이** 여러 객체를 함께 보는 판단인가 | Spring·DB 없이 테스트할 수 있게. 이름으로 판단을 드러낸다 (스타터의 domain `*Service`와 구분) |
| 응용 서비스 (Facade) | 유스케이스의 순서·트랜잭션·조합인가 | 업무 규칙을 두지 않는다. HTTP를 모른다. 메서드 하나 = 트랜잭션 하나 |

- 판단 로직만 있고 값이 없으면 VO가 아니다. 한 엔티티만 쓰는 값이라도 VO일 수 있다.

## 3. 애그리거트 경계와 참조 방식

- 애그리거트는 **함께 생성되고 함께 바뀌어야 일관성이 지켜지는 묶음**이다. 외부는 루트의 메서드로만 내부를 바꾼다 (`order.getItems().add(...)` 금지).
- 같은 애그리거트 안은 객체 참조(예: Order–OrderItem, cascade), 다른 애그리거트는 **ID 참조**다. "화면에 같이 보여 준다"는 객체 참조의 이유가 아니다 — 조회 조합은 Facade가 한다.
- 반례로 확인한다: "**B의 응답·필드가 바뀌면 A도 바뀌는가?**" 바뀐다면 참조나 책임이 잘못 놓였다.
- 이 과제의 예외: 주문 확정은 과제가 재고·포인트·주문 변경을 **한 트랜잭션**으로 요구한다(ORD-05). "애그리거트마다 트랜잭션을 나누고 이벤트로 잇는다"는 DDD 권고는 ADR-09(outbox)의 도입 조건에서 다시 본다.

## 4. 화살표와 메시지를 먼저 정한다

- 표로 쓴다: `누가 → 누구를 | 보내는 메시지 | 보내는 쪽이 모르는 것`. 오른쪽 열이 많을수록 그 화살표는 덜 부러진다.
- **없는 화살표**를 적는다 (예: Order ↛ Product, Money ↛ 아무도). 구현·리뷰에서 import로 깨지지 않는지 본다.
- 메시지는 필드를 묻지 않고 **행동을 요청**한다 (Tell, Don't Ask). `stock.decrease(q)`는 좋고, `if (p.getStock() >= q) p.setStock(...)`는 나쁘다. 조회 화면용 getter는 괜찮다.
- 계층 화살표는 `interfaces → application → domain ← infrastructure`. domain은 아무도 모른다(HTTP 포함). ArchUnit이 확인한다.

## 5. SOLID로 점검한다

| 원칙 | 점검 질문 | 이 저장소의 예 |
|---|---|---|
| SRP | 이 클래스가 바뀌는 이유가 둘 이상인가 | 상품 규칙은 Product, 목록 조합은 Facade (ADR-02) |
| OCP | 예상되는 정책 변경이 한 곳만 바꾸는가 | 포인트 사용 순서가 포인트 지갑 판단 한 곳에 있다 (ADR-04) |
| LSP | 하위 타입이 상위 타입의 약속(사전·사후 조건)을 깨는가 | 영화 예매 예시의 `DiscountPolicy` 하위 타입. 상속보다 조합을 먼저 본다 |
| ISP | 쓰지 않는 메서드까지 의존하게 만드는가 | 상품 상태 변경 저장소와 조회 전용 저장소를 나눴다 (ADR-02) |
| DIP | 정책이 저장 기술의 구현에 직접 의존하는가 | Repository 인터페이스는 domain, JPA 구현은 infrastructure |

- SOLID는 클래스를 늘리는 규칙이 아니다. 같은 계산을 여러 클래스로 흩으면 협력만 복잡해진다(발제). 클래스를 추가할 때는 **"이 분리가 막아 주는 변경"**을 한 문장으로 말할 수 있어야 한다.

## 6. 결정을 남긴다

- 대안이 둘 이상이면 ADR 형식(상황 / 선택 / 버린 대안과 비용 / 재검토 조건)으로 `plan.md`에 적는다.
- 책임 배치와 대안의 비용은 **학습자가 결정한다.** 선택지와 비용을 제시하고 멈춘다 (🤔).
- JPA 엔티티를 도메인 모델로 쓴다(분리하지 않는다). 분리가 필요해 보이면 먼저 묻는다.

## 멈춰야 하는 신호

| 신호 | 의심할 것 |
|---|---|
| 엔티티에 setter를 만들고 있다 | 상태를 지키는 행동 메서드가 빠졌다 |
| Facade에 `if`로 업무 판단이 늘어난다 | 엔티티·도메인 서비스로 옮길 규칙이다 |
| 엔티티가 Repository나 다른 애그리거트 객체를 필드로 가진다 | 참조 방식과 애그리거트 경계를 다시 본다 |
| 도메인 클래스가 `HttpStatus`·DTO를 import한다 | 계층 화살표 위반 (ADR-12) |
| "나중에 쓸 수도 있어서" 인터페이스를 만든다 | 막아 주는 변경을 말하지 못하면 만들지 않는다 |
